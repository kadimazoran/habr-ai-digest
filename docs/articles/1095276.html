The official app keeps the map, vision, and identity in the cloud. The robot's body doesn't have this: motors, head, light, cliff sensor, and charge are available via Bluetooth. I'm writing my own client com.looidev in Kotlin. There are two modes. In the first, the phone is in hand and acts as a joystick. In the second, it's mounted on the robot's head: there's a screen, front camera, and a GATT recording loop. Dialogue, speech synthesis, and page console parsing are handled by a Node-host on a computer on the same network. The host doesn't write to the movement characteristic.

Below is the system boundary, the robot's channel, why the movement frame is 20ms, how the manual and autonomous loops are structured, the map and the 'wall only from contact' rule, and how the page console is separated from the model that talks.

Boundary

I don't flash or update the robot's body. The client has no sequence or OTA channel: that's a different class of commands, unrelated to navigating the apartment.

Spatial vision and official owner identification also don't reside in the robot's body. The local slice is honest: the phone's front camera, face recognition is done on the device, the snapshot stays in the app's files. I don't replace the cloud camera or cloud name.

Movement must survive host absence. While Ollama is thinking of a response, the autonomous loop continues sending speed. If the host is unavailable, it still moves forward. The phrase 'didn't understand' only applies to dialogue.

Decompilation

Before. The LOOI product page lacks a developer guide and SDK. It comes with a ready-made app, and the robot's protocol is not described externally.

After. I captured the protocol from the official client com.TangibleFuture.looiRobot version 2.9.2. The entry point is the APK. I used REA, https://rea.tools/, for analysis: the package opens like an installed artifact, classes and methods are viewed by index, and decompilation happens per selected class rather than dumping the entire tree to the editor.

The robot's body is written in Kotlin, the source file is TangibleBody.kt, which in dex is classes5.dex, class com.tf.devicemanager.impl.body.TangibleBody. The connection is built with coroutines, so the subscription to notify in the analysis is not called reallyConnect, but

com.tf.devicemanager.impl.body.TangibleBody$reallyConnect$1$onSuccess$afterSNRunning$1$7

UUID strings are taken from the constructor. Formulas for bytes are taken from move, toAngle, and switchLight: speed * 127, (1 - angle) * 255, lamp 1/0. From the nested onSuccess after the serial number comes the reading order FED5, FED6, FED8, FED4 and the notify subscription on FED9 and FEF0.

The behavior catalog is not code but assets within the same APK: *_behaviors.json, app_setting.json, voiceRecognition.json. They are located in assets/looi and read as data. The step with robotAction is present in this catalog. It is not serialized into the robot's package.

In the same TangibleBody, there's sequence sending and OTA (sendSequencePolling, genCommandPacket, sector ack parsing). I didn't port this. The client needs channels for speed, head, light, cliff sensor, TOF, and charge.

Two Modes

Before. Remote control and autonomous driving in the official app are modes of a single client. The compatibility table does not recommend foldable phones, as they lack an external cover screen.

After. I separated the joystick and the mounted phone. On the Galaxy Z Flip, the second mode continues in folded state via the cover screen widget.

The first mode is joystick. The phone is not mounted, Manual is enabled, and only sticks are sent to GATT. The autonomous loop and regular speech are disabled in this mode.

The second mode is the phone on the head. Mounting is magnetic, on a single panel. Manual is disabled, and the autonomous loop takes over: camera, map, speech, looking down.

If the phone is a Galaxy Z Flip, it can be folded in the second mode and used with the external screen. A widget is placed on the cover screen. This is not a separate app or player: the widget displays the current eye reaction frame, a PAG snapshot at 0.35 progress, file cacheDir/cover-eyes.png. As long as the activity is open on the cover screen, the eyes there are alive. An ongoing session does not stop when folded.

Vertical Screen

Before. The official client is built as a desktop companion. It lacks a vertical layout for the phone on the head.

After. Portrait is the primary frame. Rotation follows the sensor, status and map don't shift under the side rail.

In the second mode, the phone on the head is positioned vertically, so portrait is the primary frame, not a rotated landscape.

screenOrientation = fullSensor. I don't use fixed landscape: orientation follows the sensor. During rotation, only the chrome shifts.

Portrait: status bar (equalizer and percentage) top right. Map bottom right, above the recognized phrase bar and an 84 dp rail. Landscape: the same status bar top left, an 80 dp rail is pressed to the screen edge, the map has marginEnd of 96 dp, and top buttons have marginStart of 148 dp, otherwise the rail covers the percentage. System panels do not overlap content.

Until GATT is in a connected state, a Connect button occupies the center of the screen instead of eyes. After connection, eyes return. Videos are Tencent PAG from official URLs, cached on the device; I don't include them in the APK.

In autonomous mode, the head looks down: look(0.92). Center is 0.5, up is 0.08. While approaching a face, escaping a cliff, or talking after waking up, I don't force the head down.

Manual Loop

Manual is a separate flag, not an 'explore' menu item.

Enabled: only sticks are sent to GATT. The autonomous loop and regular speech are disabled (mayTalk == false). Disabled: the same loop as exploration. There is no separate Explore button. Voice commands 'walk' and 'sleep' still select modes, but exploration has been removed from the rail.

The stick and autonomous movement share a single repeater. The firmware doesn't latch speed: one FED0 packet results in approximately 1–2 cm, and the robot stops. Therefore, both the stick and autonomous commands are repeated every 20 ms.

There is one GATT queue. Writing is sent from the looi-wheels HandlerThread. Frame repetition is from the looi-hold HandlerThread. A repeated drive with the same UUID discards the previous packet that hasn't been sent yet, rather than accumulating them. For movement, WRITE_TYPE_NO_RESPONSE with a 12 ms pause is preferred. Other writes use WRITE with a 40 ms pause, if write-without-response is not available.

Zero speed releases the hold and sends drive(0, 0). Non-zero speed initiates a hold once, after which only heldForward and heldVeer change.

Positive veer is to the left. A face in the right half of the frame results in a negative veer.

FED9 types I parse: 1 — cliff sensor (4 bytes, 0x00 is the edge); 8 — percentage; 11 — dock (1 means charging); 14 — TOF; 5/6 — stick engaged or disengaged; 9/10 — touch; 18 — button. Type 7, sequence callback, is not used.

The cliff sensor reacts to raw 0x00 immediately: lamp and reverse gear command(-0.7, ±0.55) until the byte clears. Confirmation for face and 'mind' is the same 600 ms as before. This 600 ms does not apply to movement: one cannot wait for forward movement into a black table.

I don't consider TOF a wall based on absolute millimeter measurement. The floor is remembered. A nose-to-wall impact is three consecutive samples where the distance is less than 90 mm and at least 30 mm shorter than the learned floor. mm <= 0 is not considered a wall. If the floor is already learned and moving faster than 0.4 results in three consecutive ticks with invalid distance, it's a black surface in front of the nose, not 'sensor silent'.

Charge: speech at a threshold below 20% and again below 10%, even in manual mode. It doesn't drive to the dock itself. Wheel stop due to charging only occurs if the charging loop is enabled or the robot body signals dock, type 11.

Modules, Not a Single Loop

Before. On the website, behavior is described as a single system: perception, decision, animation, and mechanics are glued together and delivered as a package.

After. Eyes and voice follow the catalog, wheels operate in a separate loop, dialogue and console use different models, and memory is stored in the user's database.

The autonomous tick is divided.

  1. MindBook.step takes one step of the official behavior chain, without unfolding it entirely. At each step, eyes, buzzing, and the voice string are executed. The next code is put on hold for the duration of the video, but no longer than 14s and no shorter than 4s.

  2. The robotAction performer (performer 2) is discarded. It is not converted into a robot package. I don't need the wheel choreography from behavior recordings: its timings are calculated for a different channel.

  3. Wheels remain with the local loop: forward movement, map-based avoidance, escape, cliff sensor. Face behavior does not stop or adjust this loop.

  4. Dialogue calls POST /api/think and must return act: "stay". Even if the model sends a different act, the host overwrites it for conversation purposes.

  5. Memory is read from and written to the host. The phone is unaware of Supabase addresses.

An empty model response or a crashed host does not put the wheels in halt.

Console

Before. The official LOOI remains a desktop companion: it drives, sees, and talks. There is no channel to the active browser tab or its error parsing. Its usefulness ends with entertainment on the desk.

After. The console is the first functional module. The robot stays on the desk but reads the console of an already open page. An assistant on Ollama, the Qwen model, parses these logs and returns the cause and a fix. Subsequent functional modules can be added with the same approach: a separate loop on the host, without the ability to write to the movement characteristic.

This is not a WebView or an embedded Chrome. The page is already open on the computer, in the browser where work is being done. The host sends POST /api/cdp/connect with pageHost to the page's host field. The host checks GET {cdp}/json/version and GET {cdp}/cdp/json/list, rewrites webSocketDebuggerUrl to its own CDP base, and performs Target.attachToTarget.

On the phone, RecyclerView displays the stream from /api/events and /api/console. Reopening the screen pulls the history and stream. A repeated CDP connect is not performed.

The Brain button invokes the assistant. The phone sends POST /api/analyze, the host collects the last console lines — level, text, URL, and line number, no more than 12 KB — and sends them to Ollama, POST {ollama}/api/chat. The Ollama address is taken from config.ollamaBaseUrl, defaulting to http://127.0.0.1:11434. The model is specified by the config.model field, defaulting to qwen2.5-coder. This is not a conversation model: the kitten is not substituted into this request, nor does it receive wheel commands from it.

The assistant's system instruction is narrow: explain the console error and suggest a specific fix. The response has three parts: cause, where to look, what to change. Stack frames not present in the log must not be added. If the console is empty, state that. The response is streamed to the phone via token events. The instruction from the button is fixed: analyze console errors.

This loop is experimental and intentionally narrow. It requires Chrome with remote debugging on the computer running the host. I do not transfer the page to the robot's screen. This minimum is sufficient to elevate the robot from being just a buzzing toy next to a laptop.

Map

Before. Edge and obstacle detection in the official client is closed-source. There is no local coordinate grid that can be erased and redrawn.

After. The grid is calculated on the phone: camera cone, short TOF, cliff sensor, and odometry. Walls are written based on contact, not room imagery.

Occupancy grid: UNKNOWN, FREE, OBSTACLE, DROP. Sources:

  • free cone from the head camera;

  • robot's short TOF;

  • cliff sensor;

  • odometry from commands, not encoders. There are no encoders on this channel.

Pose integration:

dt          = clamp(dt, 0.05, 0.35) // dt is clamped between 0.05 and 0.35 seconds. poseTheta += veer * 1.15 * dt // Theta angle is updated based on veer (turning) and dt. translation = forward * 0.18 * dt // Forward translation is based on forward speed and dt.

The angle is always updated. XY translation is disabled only if the command is moving, the camera frame doesn't change, and a counter for this state reaches 6. A static frame by itself is not considered a wedge; otherwise, on a flat, bright floor, the pose would freeze while the robot moves.

Walls are written by the bumper. traceWall is called on contact ticks and extends the trace: the front is a 0.18 m arc, the side is a lateral stamp plus an arc. This is not a segment drawn based on the room's silhouette in the frame. A large room is not drawn into the lens of the wall. Short, stable TOF also doesn't draw it: it's the floor, until it dips relative to the baseline.

Wedge: the distance traveled by command sentForward * 0.036 m per tick accumulates. The condition is more than 0.8 m of commands with a pose shift of no more than 0.08 m, and only in conjunction with contact (nose, cliff sensor, or raw edge). The 'bumped' speech is not uttered without contact. After leaving a corner, there's an 8-second pause to prevent a few centimeters from triggering a new turn.

Clear floor in autonomous mode: command(1, 0) every tick, without pause between packets. Every 24–38 seconds, the loop stops for about 1.5 seconds and utters a short beep. This is a behavior pause, not an obstacle avoidance logic.

Cliff sensor and nose override forward movement. Escape: one backward movement, then a turn in place, followed by cooling the nose. A dead end is declared once, when exit attempts are exhausted or the map is closed and there's no alternative route. The flag resets when contact is lost or the path ahead is clear again. Pathfinding does not stop during this.

The map is written to disk. A long press erases it. If the robot is lifted, odometry is inaccurate: there's no tie-in to external beacons. This is not LiDAR or cloud SLAM.

Dialogue and Two Models

Before. Dialogue and memory in the official LOOI are handled by a contracted cloud AI. The user cannot choose the model. For Android, the product page lists English and Chinese.

After. Two local models in Ollama: one speaks, the other reads the console. Dialogue is in Russian, with separate switching for character and console.

Wake-up: 'Hi LOOI' and similar phrases, including strings from the official app_setting.json. There is no 'listen' button. Recognition waits for activation via VAD, the phrase is collected entirely, and the command is executed after a pause of about 1.6 seconds. Partial results do not trigger commands. For Cyrillic, the string is converted to lowercase before comparison: the (?i) flag in Android does not include UNICODE_CASE.

While synthesis is speaking, the microphone is held; otherwise, the robot hears itself. The recognition stream is not restarted in the loop because of this.

After wake-up, there's a window of about 50 seconds. The next phrase within this window does not require a new wake-up. 'Bye', 'goodbye', 'be quiet' close the window. Movement commands from this window are still commands, not utterances to the model.

An utterance without a command is sent to the host as POST /api/think with talk: true and the text of recent utterances. The system prompt requires its own opinion, a response to the last phrase, and one insertion of 'Purr' within the text, not instead of the answer. The response is a JSON:

{"say":"...", "act":"stay", "hold":""}

say is spoken. hold, if not empty and not yet recorded, becomes an opinion. act is forcibly stay for this request. On the phone, if the string lacks purring, the prefix 'Purr.' is added locally. During the utterance, the head is set to 0.5, and eyes simulate a wink. Looking down is disabled for these seconds.

Synthesis: POST /api/say returns audio/mpeg. The host calls python3 -m edge_tts. Russian voice: ru-RU-SvetlanaNeural, rate +12%, pitch +52 Hz. English: en-US-AnaNeural. Cache up to 48 phrases. If the neural network is unavailable, locally say and ffmpeg with pitch transfer are used. If even that fails, Google TTS on the phone, female voice, pitch 1.48. Samsung's system voice for Russian locale is male, so the language is not set after voice selection: this call resets the voice to default.

Models are separated in the UI and the host.

  • Brain: body.model, otherwise config.brainModel, otherwise granite4.1:3b. An empty field in the app means the host's default. Changes in Models or Personality are written to the phone's preferences and sent in the next /api/think.

  • Console: config.model, defaulting to qwen2.5-coder. The list of both is obtained from Ollama's GET /api/tags via the host.

  • num_predict is 320 for conversation and 80 for short behavior signals. Conversation should not sound like one-word driving cues, and driving cues should not turn into paragraphs.

While Manual is enabled, autonomous speech is silent. Responses to spoken phrases and low battery warnings bypass this flag: otherwise, dialogue and low battery would only exist in autonomous mode. The phrase still doesn't get wheel commands.

Memory

Before. The official LOOI's memory is processed along with conversation history on the cloud AI side. Custom databases cannot be connected.

After. Memory resides in the Supabase of whoever launched the host. A foreign project is connected with its own .env and the same two tables. Without a database, the host writes to a local JSON.

Dialogue memory is a separate loop on the host. Before responding, the host reads previously spoken opinions and recent utterances from the database and inserts them into POST /api/think. After the response, it appends the new utterance and, if the model returned a non-empty hold, a new opinion. The phone is unaware of the database addresses. The GATT loop does not wait for this database: read timeout is 4 seconds; in case of error, the host uses the local memory.json and still delivers the phrase.

The database is not shared. Each person sets up their own Supabase project and points the host to it. In devtools-host/.env, there are two variables; they are not in config.json or the APK:

SUPABASE_URL=https://YOUR_PROJECT.supabase.co // Replace YOUR_PROJECT with your actual Supabase project name. SUPABASE_KEY=sb_publishable_your_key // This is your Supabase publishable key.

SUPABASE_KEY is the public key for this project. The secret key and Postgres password are not included in the client. If the variables are absent, opinions and utterances remain in memory.json on the computer.

In your project, within the SQL Editor, create two tables:

  • looi_opinions(text unique, created_at) — opinions, the last 24 are used in the prompt;

  • looi_turns(who, text, created_at) — utterances from Owner and LOOI, the last 40 are used in the prompt.

RLS is enabled; roles anon and authenticated require select and insert permissions. Another person connects their database in the same way: their own .env and the same two tables on their end. Conversation data is not mixed between projects.

What Else is Tied to the Host and Not to the Wheels

While the robot is connected, the host accepts buffer text (POST /api/clip → pbcopy) and short phrase notifications (POST /api/note → osascript). Phrase duplicates are filtered for 8 seconds. The buffer content is not written to the host log.

The percentage on the screen is updated from FED8 and notify type 8. The label without product name: 42% or --. The equalizer in the same bar is enabled only during live recognition.

Corner

The angle is not perceived from the wall image. It continues to move, but the coordinates do not change. Wheel commands are issued, the robot pushes forward, but the point on the map stays in the same place. This means it's not going anywhere. It's bumping into a wall. In practice, this is a corner: the area ahead and to the side is already occupied, and it spins at the same coordinates.

If it gets stuck there, it needs to be moved out. I remember this point. While it remains there and is still trying to move, it backs up and turns until the coordinates change. Once it leaves this spot, the corner is passed. I don't initiate a new turn immediately: otherwise, a few centimeters later, it might get stuck there again.
