For parallel work, it's no longer necessary to spin up a team of sub-agents every time. Already open sessions accept tasks, return results, and pass the necessary context to each other.

In Claude Code, these are inter-session messages. In Codex CLI from version 0.149.0, codex queue has appeared; in Desktop, there are separate tools for adjacent tasks. Via the app-server, data can be placed directly into the thread history.

If one chat has already figured out the backend, and the second is working on the frontend, they can be linked. It's not necessary to re-explain the project to a new executor for every clarification.

1. What is a Sub-agent and What Are We Paying For

A sub-agent is an executor with a separate context window. The main agent assigns a piece of work, provides the necessary data, and retrieves the result.

Useful feature: the main chat fixes a bug, the sub-agent reads the logs, and the output, not the entire log file, is returned to the main context. Isolation works.

We pay for something else: each child re-reads the repository, and while it's working, the parent waits. The task needs to be formulated, the executor needs to be given context, the result needs to be checked, and then used in the main work. If the task is small, these actions can cost more than the fix itself.

2. How Spawn Works in Codex

The main chat spawns a child via spawn_agent, sends clarifications, and waits for the result. Everything revolves around the parent; spawn hasn't gone anywhere.

The overhead lies in two places. If one file is needed, but the child receives a long discussion of the entire project, the input is disproportionate to the task. If the parent repeatedly calls for short waits and goes back to the model after each return, it burns tokens on intermediate checks. The actual coordinator cycle is important: the default wait timeout itself doesn't prove that the model inevitably wakes up every 30 seconds.

Codex sub-agents could already inherit context: in the V1 interface, fork_context was used for this. Not every old child started with an empty history. Comparison of V1 and V2 Mechanisms.

3. Where Claude Code Falls Short

A regular Claude Code sub-agent receives a separate task, instructions, and tools. The main chat retrieves the result. Profiles like Explore or code-reviewer specialize the executor.

A separate window doesn't necessarily mean a new OS process, nor does it mean an obligatory cache miss. But re-loading instructions and transferring results can indeed create significant overhead.

In an HTTP measurement for Claude Code 2.1.234, a small reviewer sub-agent on Haiku received 20,993 input tokens on the first turn. Of these, 7,133, or 34%, was automatically added memory MEMORY.md. For a short review, this is a cost even before useful work.

In other telemetry across 95 sessions and 1,777 sub-agents, the author found about 30,000 tokens of static context at startup: instructions, tool schemas, project rules, and environment.

Losses of cache during nested agent waiting are also analyzed there: the median idle time was about nine minutes with a TTL of five minutes. The 96% figure refers to confirmed cache losses in the considered group of such episodes, not all launches. For frequently launched similar agents, cache reuse, on the contrary, worked.

There are also losses upon return. In issue #81838, a long response was cut into messages, and only the last one was given to the calling party. Out of 151,652 characters, it received 24,353, about 16%. Approximately 84% of the text did not reach the recipient.

A separate case: experimental Agent Teams. In the report for version 2.1.39:

  • 42,226 calls to readMailbox

  • 4,296 file not found responses

  • 23 participant launches, of which eight were productive

  • approximately 2 hours 24 minutes with the team, after which the leader finished the remaining work alone in 18 minutes

These are bug reports for specific configurations and versions, not the final product. These cases explain why it's worth limiting excessive coordination. They themselves do not show how much cheaper communication between persistent sessions is.

4. What Has Changed: MultiAgent V2 and Forks

In Codex MultiAgent V2, you can choose how much history to give to a new executor:

fork_turns

What the descendant receives

"all"

The entire history

"none"

The task without conversation history

Number of last turns

A limited fragment of history

In the described V2 interface, the default is "all". A full fork inherits the agent type, model, and reasoning effort of the parent. This is convenient when it truly needs previously made decisions. For a small task, the full history might be excessive. Analysis of V2 Behavior.

In Claude Code, there's a fork of the current conversation. It inherits the history, system prompt, and tools, and the first request can use the parent's cache. The new executor no longer needs to re-explain the project. Claude Code Forks Documentation.

A fork also creates a new executor. If the needed working session is already active, message it.

5. How Chats Communicate Now

Three different operations: read a neighboring conversation, send it a message, put completed data into its history.

Codex: Messages to Existing Sessions

In Codex CLI 0.149.0, codex queue appeared: a message is sent to an already existing local or remote session. Nearby is codex agents for searching, launching, and managing tasks. These are functions of the CLI itself. Official Changelog.

In Desktop, separate tools are used for working with adjacent tasks: list_threads, read_thread, and send_message_to_thread. They allow you to find a neighboring task, read its history, and send a message. Operations are visible in the Desktop Regression Report; availability depends on the environment and application version.

The session on the left finds a neighboring thread (Listed chats), sends an instruction (Sent message to chat), and retrieves the result (Read chat). On the right is the service tag Sent by ChatGPT from another task.

Find the chat where we agreed on authorization. Read the decisions made, pass them to the implementation task, and ask to check the token expiration handling.

The context is taken from already completed work. There's no need to spawn a sub-agent to re-investigate the same issue.

Codex: Direct Context Injection

At the codex app-server level, this is programmatic control over history and the current turn:

Sessions go through the daemon, not directly into each other. Inject places data into history without a new turn.

Operation

What it does

thread/read with includeTurns

Reads thread history

turn/steer

Adds an instruction to an already executing turn

thread/inject_items

Places completed items into history without starting a new turn

Via thread/inject_items, you can place the result of a calculation or already obtained data directly into the history that the model will see. Items are saved and included in subsequent requests. App Server Reference.

This is not the same as a regular message. Adding without immediate generation doesn't make subsequent processing free.

Claude Code: Messages Between Live Sessions

ListAgents and SendMessage find another session and write to it. On the same machine, delivery goes through a local socket or Named Pipe.

If the receiving session is busy, the message waits for a pause between tool calls. If it's idle, it starts a new turn.

For example:

Inform the client session: the expires_at field is now mandatory, the contract has been updated. Ask it to check deserialization.

How this looks in full. The backend session sends this text. The client session is running pytest at this moment: the message doesn't interrupt the test and waits for a pause between tool calls. After the step, the client reads the fact about expires_at, fixes deserialization, runs tests again, and replies: expiration handling is in place. If the session is idle, the message starts a new turn.

Only text is sent. The sender's history and files are not copied automatically: the necessary decision, piece of context, or artifact path must be included in the message, otherwise the recipient won't see it.

For waiting, there's notify_when_idle. The main session can request a one-time notification when another local session becomes idle or completes. Cyclic polling is not needed. A sub-agent or an Agent Teams participant cannot subscribe to this. Idle here means the end of a turn with an empty queue, not that the task is necessarily completed. 6. What This Offers in Practice

For communication, codex queue or SendMessage are used; with parallel edits to the same repository, sessions can be separated by worktree. This isolates files at the Git working copy level, and communication between sessions occurs via direct messages, without polling a shared state file.

Four work scenarios.

Scenario

How to Organize

Manager + Executor

One chat holds requirements and decisions, the second completes the steps. Tasks and results are exchanged between them

Independent Review

A working chat sends the diff and criteria to a separate session, possibly on a different model

Parallel Development

Sessions in separate worktrees, report changes that affect neighbors

Multiple Projects

A library session informs the backend or frontend that the contract and version have changed

Worktree provides a separate working copy, but conflicts may arise when merging changes. A message about a new library version doesn't install it: the receiving session must update the dependency and run integration tests.

The main economy is where the required session has already figured out its part of the project. A short clarification is enough for it. A new executor and repeated context gathering can be avoided.

If you are creating the second session from scratch anyway, consider its preparation cost. Otherwise, it's the same onboarding, just in a neighboring window.

7. When Chats Are Enough, and When a Sub-agent Is Needed

For bug fixing, a local feature, or sequential refactoring, I would stick to one working chat. For an independent long-term task, I would add a second chat and link them with messages.

This way, clear control points remain: you can see which session is doing what, read the history, clarify the task, and return later. A separate orchestrator for this set of tasks is not needed.

Sub-agents remain useful in three cases:

  • Isolation of heavy output. Reading large logs or documentation and returning a compact result.

  • One-time independent check. Verifying a diff without the prior discussion history.

  • Broad parallel search. Multiple independent directions where additional cost is justified by completeness or speed.

My default: one session, then a few stable working chats as needed. A sub-agent appears for a specific sub-task, not as permanent staff.

This is precisely why, in practice, I am switching to workflow-herdr myself — because of the ability to work visually through fixed long-lived sessions that communicate with each other.

Instead of a swarm of invisible disposable sub-agents that burn cache and require re-feeding project context, you have a unified transparent workspace before your eyes. Each agent is tied to its own session, maintains local history, and communicates with neighbors via messages and wait queues (herdr agent wait), and you can see the real system state at any moment.

Communication between chats already exists: messages, history reading, context injection. Two or three open windows often complete the task, and a blind staff of planner, executor, tester, and reviewer doesn't need to be assembled.
