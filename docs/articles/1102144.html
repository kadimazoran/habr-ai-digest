We will try to quickly write an NTFS alternate data streams scanner using a non-trivial stack and architecture. I did this primarily to test the capabilities of the Qwen family of models.

A brief explanation for those who haven't worked in this area. NTFS (an abbreviation for New Technology File System) is the standard file system for the Windows NT family of operating systems. One of its little-known features is the presence of Alternate Data Streams (ADS), which are metadata associated with an NTFS file system object. Thus, several data streams can be attached to a file that will not be visible through standard OS tools.

How ADS are structured

  1. Main stream (default): Unnamed stream: $DATA contains the usual file content (text, code, image).

  2. Alternate (named) streams: Can contain any data of arbitrary size and are attached to the file name via a colon, for example: file.txt:streamname:$DATA.

  3. When writing data to ADS, the size of the main file in Windows Explorer does not change, which makes the hidden streams invisible to standard viewing tools (Explorer does not display their presence).

  4. When copying a file to another drive with an NTFS file system, the streams are preserved. When transferring to FAT32, exFAT, or loading via most network protocols, alternate streams are lost.

For legitimate use, ADS are used in the following cases:

  1. Metadata storage: Windows uses ADS for security labels (e.g., the famous Mark of the Web flag in the Zone.Identifier stream, which warns when launching files downloaded from the internet).

  2. For compatibility: the feature was originally introduced to support Macintosh file systems (HFS), where a file could store an icon, a resource part, and text separately.

  3. For data classification: Classification tools (e.g., Microsoft FCI) can store document labels within streams.

Task Definition for Qwen

As a software stack for implementation, I decided to use Rust for the application core and Avalonia for the GUI, as there is a need to ensure operation on both Windows and Linux. The Linux version must be able to work with both ntfs3 and ntfs-3g. Everything that resulted is available on GitHub: https://github.com/BlackEric001/NtfsStreamsViewer.

To start, I sent the following prompt to https://chat.qwen.ai/: "I need to create an application with a GUI to scan NTFS drives for alternate data streams in files. It should be possible to view and download data from the streams.".

The program must be able to run on both Windows and Linux.

I envision the implementation as a disk interaction module that will scan disks, folders, and files, load and unload data into streams, create and delete them. And provide an API for the GUI.

The GUI will use the disk interaction module.

I would like the data interaction module to be implemented in Rust.

By default, Qwen3.7-Plus is suggested.

In general, it said that the proposed architecture is ideal, without detailed elaboration. Not good... Let's try Qwen3.8-Max, sending the same prompt. Here the response is much more detailed, with very sensible suggestions. The long and detailed response from Qwen3.8-Max can be read at the link: https://chat.qwen.ai/s/t_9566645d‑b473-48b9-ac18-a00b79ee105c. I am not including it here because there is a lot of it, but in short, 3.8 also agreed with my proposed architecture but suggested supplementing it with another command-line application, which was ultimately implemented.

In the end, I asked it to write a technical specification describing the implementation of the core in Rust for Qwen Coder. We save the technical specification in the ..\SPEC.md file and push it to the repo along with the initial directory structure.

Working with Qwen Coder

To start working with Qwen Coder (https://coder.qwen.ai/), we give it access to the GitHub repository:

We write a short prompt: "Write an application according to the specification in the file https://github.com/BlackEric001/NtfsStreamsViewer/blob/master/SPEC.md" and the agent starts working.

As a result of its work, it constantly tried to give me non-compiling code, so with the next prompt, I asked it to make the code compile. As a result, in a couple of iterations, each of which took no more than 10 minutes, we got a fully working console application.

The next step was to ask Qwen3.8-Max to write a technical specification for the GUI part. What we got after a short discussion, I again pushed to the repo: https://github.com/BlackEric001/NtfsStreamsViewer/blob/master/docs/GUI.md, after which I asked Qwen Coder to implement the interface in Avalonia. On the first attempt, it again produced non-compiling code. But here it should be noted that the agent does not have access to Windows; it checked everything on the Linux it had access to. I checked everything on Win 10. After I told it that the code was not compiling, it corrected it, and we got a decent, but very simple interface. After a short testing period on my part, I asked it to add logs and display them in a separate window, which was quickly done. I merged all pull requests from Qwen Coder without edits. After each stage, I asked Qwen3.8-Max to check the result. In this implementation, it found no problems and suggested moving to the next stage.

Conclusion

Everything became very simple and fast, and it boils down to defining the task for the agent and checking the result. An IDE is also not needed. In fact, development is starting to look like analysis > defining the task for the agent > checking the agent's work results with a neural network to find errors, vulnerabilities, etc. > testing the resulting application. Code is now generated at such a speed that an agent is also needed for review. People will not be able to review all of this manually as before.

Unfortunately, I didn't manage to measure the time spent on development, but all the programming and communication with the neural networks took me about 4 hours, no more. Estimate for yourself how long it would have taken to write this the old-fashioned way. Source code will soon be viewed as often as before the era of AI agents, people looked at what the compiler generated, because a person simply won't have time to study such a volume. And since neural networks don't care what language to write in, at least among the popular ones, traditional development is living its last years.
