Suppose I ask an agent to visit a restaurant website and find out the price of a small order of fries. If I open the website myself, I immediately look for "Menu" and then for fries within it. The agent also needs to somehow get to the price. Only instead of scanning the page, it receives HTML, cleaned text, or a screenshot from a tool, depending on what it's equipped with. And if the tool returns the entire menu, burgers, drinks, and everything else on the page get into the context along with the fries.

I thought: what if I give the agent a site map to help it directly access the relevant part of the menu? In Deckard, we created the open-source generator agent-sitemap for this purpose. It breaks down pages into Markdown notes and links them together. Then we gave Claude Code two questions about its own website. Using the map, it downloaded less text, but the statistics showed more input tokens. Below, I'll show where this difference came from.

The site now has another way to be read

With SEO, we're used to thinking about how a person finds a page through a search engine. Then they open it and figure out where to look. With an agent, another question arises: what will it receive once the page is found? For example, in an article that spans ten screens, the necessary condition might be in a single paragraph in the middle. If the tool returns the entire article, the agent will search for that paragraph among all the other text.

I am specifically discussing this stage here, when the website address is already known. Whether the site appears in search engine results or in the assistant's source list is a separate question. With the map, I want to shorten the path from a known address to a specific answer.

What do sitemap.xml and llms.txt offer?

In sitemap.xml, you can see which pages exist on the site. With it, I can find the URL for the menu, but this file doesn't show where the fries are within the menu. In llms.txt, you can describe what's at each link and provide Markdown versions of the pages. For a small site, this might be enough. But if the menu is long, after clicking the link, the agent still receives a long menu, just without the HTML.

In the generator, we created a separate Markdown file for each section. An index leads to a page card, from the card you can go to the relevant section, and from there to related materials. A link to the index can be placed in llms.txt.

Let's take the same menu. For example, I would write its card like this:

# Menu

## Sections

- [Burgers](https://example.com/ai/menu/burgers.md)
  Ingredients, sizes, and prices of burgers.
- [Fries and appetizers](https://example.com/ai/menu/sides.md)
  Portions and prices of side dishes.
- [Drinks](https://example.com/ai/menu/drinks.md)
  Volume and prices of beverages.

The agent opens the index, goes to the menu, and based on the description, selects "Fries and appetizers." There's no need to read about burgers and drinks in this pass. The note retains the original page's address so it can be referenced and the price checked. The generator records the same links in graph.json if the map needs to be read by custom code.

Where the text and links come from

The generator takes either local HTML and Markdown files or a website with its own sitemap.xml as input. Text is divided by second-level headings (##). Some links are already present in the document: a page contains sections, one section follows another, and the author might have linked to another page on the site within the text.

To find links that are not in the source, we compare words from sections on different pages. For this, TF-IDF and cosine similarity are sufficient in the basic setup. It's easy to get a false match here: the word "delivery" might appear frequently in both pricing and return policies. Therefore, an additional pass with an LLM can be enabled. It writes short explanations for notes and transitions and can filter out some word-based links. Author links remain in the map.

Where is the vector search here?

If the site has thousands of pages or visitors ask questions in completely different terms than what's written in the documentation, I would also consider vector search. For the map, it's enough for me to host static files alongside the site and give the agent a tool that can open URLs. It then navigates the links itself, so it might choose the wrong section or open five adjacent ones when only one would suffice. If the index grows to the size of a long article, it will also need to be read entirely or split into parts.

These approaches can be used together. Search finds the section with the rule, and a link from the section leads to exceptions. On a site with a few pages, I would start with the table of contents and see where the agent actually needed search.

Let's look at what the counter in the benchmark calculates. The character count includes the content of HTTP responses. The input token count includes other context that the model receives at various steps. So far, this is based on one run for two questions in Claude Code. An assistant with standard web search and a browser might take a different route.

What does "approximately N tokens" mean?

Next to the link in the map, there's a size estimate. I view it similarly to the length of an article before opening it: will the link be a single paragraph or another ten-screen page? In the generator code, the estimate is calculated by characters, with different coefficients for predominantly Cyrillic text and other cases. The tokenizer of a specific model is not used here.

There's a nuance: the estimate includes the main text, but the file also contains headings, metadata, and links. For a short note, these additions can be longer than the section itself. A page card might even have an estimate for the entire original page, although the card itself consists of an introduction and a table of contents. Here, I would show two numbers: the size of the file the agent will currently open, and the size of the original text.

How to test the approach on your own site

npx agent-sitemap https://example.com

The generator will create an `ai` directory. You need to place it alongside your site, verify that `/ai/index.md` is accessible, and provide this address to the agent. The link can also be added to llms.txt, but during measurement, I would pass the address explicitly: otherwise, it's easy to confuse the navigation result via the map with whether the agent found the map at all.

For the next measurement, I would take 10-30 real questions and repeat each several times under identical conditions. Some answers should be in one section, some require multiple pages, and some are not on the site at all. I would check if the agent answered correctly and cited the source, how many requests it made, how much text it downloaded, and how much time and money it cost. If the model also verifies answers, the time for this verification should be reported separately from the time the agent spent on the answer.

In the current measurement, I'm missing two scenarios. The first is to give the agent llms.txt with entire Markdown pages to understand what even just cleaning the HTML provides. The second is to provide the correct page directly. If it has two paragraphs, going through the index and card is likely slower than reading it entirely.

Where the map requires caution

I would look at what happens at the boundaries of sections. If a rule falls into one note and an exception into another, the agent might only provide correct answers for half the cases. A heading like "Additional Information" also tells little about whether there's an answer underneath. At this point, both the agent and the LLM that wrote the explanation during assembly can make mistakes.

For the menu, there's also a simple question: when was the price updated? If the site changed it today, and the Markdown copy was updated a week ago, it's more useful to check the site or the current API. And the content of the notes comes from external sources, like any web page: instructions found within the text cannot be taken as commands from the user.

I'm now interested in where a regular table of contents is sufficient for an agent, and where transitions between sections are truly helpful. The generator and benchmark can be viewed in the agent-sitemap repository; the code is open-source under MIT. If you try it on your own documentation or catalog, I'd be interested to compare which questions led it to follow links and which ones it found the answer to directly.
