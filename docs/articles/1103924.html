The agent writes: "Done, all tests pass." Then I have two options: believe it or show it to someone who understands. There's no one to show it to. There's no developer on the project, and I don't read code myself.

I'm a product manager. Since January, I've been building a Chrome extension this way. All the code was written by two AI agents, Claude Code and Codex. The scope of work as of October 28:

  • 593 commits;

  • 78,478 lines of code in the product itself;

  • 177,511 lines of tests;

  • version 1.0.1 in the Chrome Web Store.

The same agent that wrote the code also wrote the tests, so their number in itself proves nothing. Why I trust them, and where I don't, is lesson 3.

Over these months, I've started demanding more from the agent than just a "done" message:

  • checks that fail if a rule is violated;

  • a report on what the agent itself saw in the browser;

  • a process where I manage tasks step-by-step: from discussion to acceptance.

The models have also gotten smarter during this time. I haven't measured how much the result has improved thanks to them versus thanks to the harness. Next, I'll explain how I set up checks and work with the agent:

  3. What I'll change in the next project. Five improvements. Each with an argument against it.

This article is for two types of readers:

  • A manager or product manager who wants to build themselves without waiting in line for developers.

  • A developer who wants to hand over a task to an agent for a few hours, trusting the result.

If you are a manager, you won't need to program. You also won't need the command-line interface (CLI) that programmers use. Everything described below is done with plain text in a chat with the agent: you write what you need, and the agent runs programs and shows you the results.

I've released the harness as an open template – a set of files that anyone can take: https://github.com/yesgenius/agent-harness. It contains everything discussed in the first part, plus a demonstration. It breaks a copy of the project in forty-two ways and shows which check caught each breakage. On my computer, it runs in under a minute.

The template is entirely in English, which acts as a guard: a line with non-Latin characters will cause tests to fail. The agent will communicate with you in the language you use to write to it. How to read its pages in Russian directly on GitHub is explained in the "How to try the template" section.

What this has been tested on

The harness grew out of one product – a Chrome extension called "Chat with Multiple AI." It sends one request to 15 AI chats simultaneously: ChatGPT, Claude, Gemini, and others.

These chats are third-party websites, and they change without notice. Therefore, the description of how to work with each chat is in a separate configuration file. When a chat changes, I fix this file, and the fix reaches users without a new version in the store.

What has already happened:

  • two versions in the Chrome Web Store;

  • two fixes to this file, on October 19 and November 1;

  • 70 acceptance scenarios that the agent passed itself in the browser before version 1.0.1.

Who Checks What

I don't read the code. I open the extension and check against the report list: what happens after clicking, whether the result appeared, what happens if something goes wrong. If a check can be delegated to a machine, I delegate it. But I still have to decide for myself whether the product's behavior is acceptable.

Some rules are written only in AGENTS.md, and the agent can violate them. I'll explain how I handle this in the second part.

1. AGENTS.md Does Not Stop the Agent

On February 2, a file with rules for the agent was added to the project. It contained:

  • general principles like KISS ("keep it simple") and DRY ("don't repeat yourself");

  • a list of technologies;

  • a folder structure.

In March, the rule "no magic numbers" was added. A magic number is a number in the code whose meaning is not specified anywhere: for example, 3600 instead of "one hour." The file grew: 61 lines in February, 179 in October.

The agent could violate any of these rules, and without a check, I wouldn't know. The first guard appeared only on May 11.

I'll use an example to show why text alone is insufficient. My product promises: if I fix the configuration file, the extension checks it at least once an hour. How often the extension re-reads this file is determined by a single number in the code.

Suppose the agent changes the hour to a day. The test takes the new number from the same code, compares it to itself, and is satisfied. I see: everything is green. The user waits a day.

The green test suggests the frequency is under control. Although the limit "at least once an hour" is not specified in it at all.

This requires a guard: a test that will check that the interval is not more than an hour. Developers call a rule that must always be true an invariant. This guard has two comparisons:

test('the configuration is read at least once an hour', () => {;! assert.ok(PROVIDER_CONFIG_REFRESH_MS > 0);;! assert.ok(PROVIDER_CONFIG_REFRESH_MS <= ONE_HOUR_MS);;});!

How to read this:

  • the string in quotes is the guard's name: "the configuration is read at least once an hour";

  • PROVIDER_CONFIG_REFRESH_MS is that number: how often to re-read the configuration file, in milliseconds;

  • ONE_HOUR_MS is one hour in milliseconds;

  • assert.ok means "must be true": the number is greater than zero and not greater than an hour.

If the agent sets it to a day, the second condition will not be met, and the guard will fail.

The guard enforces exactly what the number specifies – the frequency. It doesn't check if the program actually downloads the file. The example is taken from the template, and the template lacks the code section that re-reads the file; however, the guard upholds the promise to the user "time to re-read."

The name of the guard file is the promise itself, written as a plain phrase. Therefore, the list of files reads like a list of product promises:

a-published-provider-fix-reaches-a-user-within-an-hour;no-reminder-leaves-before-the-intent-is-recorded;no-provider-name-outlives-the-provider-config;!

In other words:

  1. A published provider fix reaches the user within an hour.

  2. A reminder is not sent until it's recorded that it's about to be sent. Without this record, the product, after restarting, won't know it has already sent it and will send it again.

  3. The provider name appears only in the configuration file: it's not in the code, tests, or documentation. The service changes without notice, and a line with its name outside the configuration file would continue to describe something that no longer exists.

On September 25, I kept only one file. Now, a guard fails if someone creates:

  • CLAUDE.md alongside AGENTS.md;

  • a separate rules file in a subdirectory;

  • a file with a backup name that the agent would also read as rules.

Each agent's skills are in their own folder, so each skill is written twice. The guard compares each pair and fails if the texts diverge.

I now handle other copies of rules the same way:

  • keep the rule in one place;

  • delegate to a machine the task of comparing copies and failing if they diverge.

3. A Green Build Might Not Check Anything

I have a program that finds type errors in code. A type error occurs when code confuses data types, for example, treating text as a number. On July 27, the count of such errors reached zero.

Zero can be achieved in two ways:

  • fix all errors;

  • stop looking for them.

The result looks the same from the outside. And stopping the search is easy, just one line is enough:

  • disable strict checking mode, and it will start forgiving more;

  • add a folder that the check will not scan.

The build remains green. On July 27, I noted in the project history: zero errors can be trusted as long as the check searches for them with the same scope and rigor.

I have two methods against this.

Minimum threshold. The check counts how many files it read and fails if there are fewer than the threshold. Otherwise, a failure might go unnoticed: the check found no files, found no errors, and reported success.

Intentional breakage. In a copy of the project, the rule is deliberately broken, and the guard must fail. If it remains green, it means it misses such a violation. Developers know this technique as mutation testing: a small error is introduced into the code, and tests are observed to see if they detect it. In the template, each such error violates one project rule, and for each, it's pre-recorded which guard should catch it.

The purpose of this is best illustrated with a smoke detector. A detector with a dead battery is silent, just like a working one in a house with no smoke. Therefore, the detector has a "Test" button: press it, and it should beep. Intentional breakage is such a button for every guard.

The template's demonstration includes 42 intentional breakages. How to run it is described in the "How to try the template" section. Here are three examples from the output:

  2. The check stopped seeing files and turned green because of it. The demonstration directed the check to an empty folder. Caught by the minimum threshold.

  3. Two lines swapped. The product started sending the reminder before recording that it was about to send it. Caught by the guard "reminder is not sent until it's recorded."

What to ask the agent in your project or for an extended harness:

For each build check, break its rule in a project copy and show that the check fails. 1. Consider a check that found no files and reported success as non-existent. 2. The agent makes breakages in a project copy. 3.

The agent introduces breakages into a copy of the project.

In the product itself, I rely on guards because I can read the rule in each name, and on the browser run, where the behavior is visible. I trust other product tests on their word: they are not verified by intentional breakages. Even among the 89 guards, not all are verified this way. I created the registry, where each intentional breakage is recorded with the guard that catches it, within the template itself.

4. Protection is Verified by Attempting to Bypass It

Protection is a check that doesn't just warn about a violation but prevents the action from occurring.

At the end of August, I separated development and releases: each had its own branch. For the release branch, a forced push is the most dangerous. A regular push appends new commits to the history on GitHub. A forced push rewrites it, and old commits disappear.

The specification stated that a forced push is prohibited by a rule in the GitHub repository settings. I asked the agent to check, and it found:

  • the rule could be created, and it appeared enabled in the settings;

  • on my plan for a private repository, GitHub did not enforce it.

The plan limitation is described in GitHub's documentation. But the setting looked functional, and I believed it instead of testing it by rejection.

I was counting on protection that didn't work. On August 31, I deleted this rule and recorded the reason in the project history.

Now, the release branch is protected by a hook. A hook is a small program that Git itself runs before a specific action. If the hook responds "disallowed," the action is canceled. My hook runs before every push to GitHub and resides in the project folder, not in the site's settings:

  • it rejects pushes to the release branch;

  • it only allows them if the command includes explicit confirmation that the push is intentional;

  • the confirmation is valid for a single command.

The hook can be bypassed with the command git push --no-verify, and the push confirmation is set by the pusher themselves. These limitations are recorded in the hook itself. If the agent accidentally repeats the previous command and forgets to change the branch, it will receive a rejection. If it decides to bypass the protection, the hook won't stop it. More on this in the "What the harness doesn't do" section.

There's no need to read the hook's code. It's checked by a guard: it attempts to push changes to the release branch without confirmation or with incorrect confirmation and fails if the push goes through.

Now I ask for the rejection to be shown:

Show that the release branch protection works: in a test copy of the project, try to push changes to the release branch without confirmation and output the full rejection. 1.

In the response, you should see the rejection message itself, not the agent's explanation that protection exists.

5. The Agent Must Speak the Language of Behavior

Until July 26, AGENTS.md did not specify how the agent should communicate with me in chat. Then, a section called "Verification model" was added: who checks the agent's work and how. Here's an excerpt in translation:

Questions to the user must be framed in the language of system behavior: what happens, when, and what is visible. 6. The Agent Must See What It Has Done

Previously, the agent could read the code and convincingly explain that everything works. That became insufficient for me. Since August 22, it has its own Chrome: let it open the extension, click buttons, and observe. If it didn't reach the browser, the report must explicitly state: the conclusion is based on the code.

It connects to the browser via Chrome DevTools MCP – a tool that allows the agent to control the browser: open pages, click buttons, read the console.

I delayed the end-to-end run for longer. An end-to-end test is a pass through the product from start to finish, like a user would experience. Until September 7, it was only a line in the to-do list and a stub command that intentionally failed. Now it's a protocol – a step-by-step description of the check:

  • at least 70 scenarios;

  • 40 sample pages that simulate external services and are part of the project itself;

  • the agent runs them all itself in a real Chrome browser.

Before the 1.0.1 release, the run took about two hours: 69 scenarios passed, 1 deviation. The agent passed the scenarios without me. My part was to read the report and decide what to do about the deviation. The deviation was real: with almost full storage, 17,674 templates, a modified template appeared in another extension window after 1.8 seconds, while the norm was one second. On October 12, I decided to release: the measurement was taken on a very weak laptop, and its numbers don't transfer to user machines. The run found a deviation from the norm, but I made the decision, and it's recorded in the release report as a deviation with a link to this decision. The protocol itself (end-to-end test) is also checked: if a scenario lacks a sample page or a rule it verifies, the test fails.

The template includes a reduced copy of such a run. The test process sends a reminder, and four sample pages simulate four possible outcomes. Here's what the agent sees in the console on the page where the service accepted the request, but the reminder never appeared:

[Dispatch] [reminder.intent-recorded] fixture-reminder;! [Dispatch] [reminder.send-started] fixture-reminder;! [Dispatch] [reminder.send-accepted] fixture-reminder;! [Dispatch] [reminder.delivery-unproven] fixture-reminder;!

[Dispatch] is the part of the program that writes to the log, here it's sending. The second set of brackets indicates the step in the process. The steps show the following history:

  1. It's recorded that a reminder is about to be sent.

  2. Sending has started.

  3. The provider accepted the request.

  4. It was not possible to prove that the reminder was delivered.

The final status here is "unproven." The product doesn't claim it sent because it can't prove it.

7. The Most Critical Process is Described by a Diagram

Almost every product has an action that cannot be undone: charging money, sending an email, deleting. For me, it's sending a prompt to a third-party chat. Such a process cannot be left solely in the code: it needs to be verified, and I cannot verify the code.

I encountered the second reason firsthand. Every change the agent made to the extension's main process, sending a prompt, broke something that had previously worked well. This means the agent didn't see the process as a whole: it fixed one part and didn't realize what depended on it elsewhere. A diagram shows it the entire process at once, not just the part it's fixing.

Since June, sending has been described by a strict process diagram: 15 states and 69 transitions. Developers call such a diagram a finite automaton.

  • State – where the process is currently, e.g., "recorded that a reminder is being sent."

  • Transition – a step from one state to another.

For a manager, this is a standard process diagram. The difference is that the machine enforces some of the diagram's agreement with the code:

  • each log line starts with the transition name, exactly as in the diagram;

  • the build compares the names: each transition in the diagram exists in the code, and there are no names in the code that are not in the diagram;

  • the description of the process for humans is automatically generated from the diagram.

Therefore, any log line from a failed run can be found in the diagram by its name, and the agent doesn't have to guess what happened. The order in which the code executes the steps is not checked by the name comparison: if you swap two log lines in the code, it will remain green. The order that is costly to violate is enforced by a separate guard, discussed below.
