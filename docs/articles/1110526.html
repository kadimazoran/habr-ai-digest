Yes, my name is actually Anton. Today I want to tell you a story that led to the creation of such a magnificent tool as NCF Agent Interconnect. I hope you enjoy it, and even better, find it useful.

TL;DR Here is a brief overview and a version with pictures

Once upon a time…

Well, yes… Once upon a time, on my work Mac, I was sitting and vibing, developing an application I really needed, using Cursor and ChatGPT/Codex (let's not argue about tastes), but suddenly a version for Windows was also needed.

I was about to pull up the repository on a neighboring computer when an idea struck me: I could install ChatGPT there too. Since I have one account, the chats should appear on both systems. Why not ask the agents to synchronize the repository themselves, build the Windows version, find problems, solve them, and thus close the issue. And then return to the main computer, getting the Windows build details into the context of the existing chats.

But in ChatGPT, I needed to enable remote control for such a configuration, and with my Business subscription, I also needed administrator permission. However, I wasn't immediately granted it.

Then I remembered stories about how agents at OpenAI used third-party resources to interact and synchronize their work. For fun, I did just that: I added a Google Drive plugin to both ChatGPT instances, created a shared folder, and explained in each chat that they could communicate, exchange files, and diagnostic data through it. I suggested the agents agree on a communication protocol themselves.

By the way, it all worked. The agents created a file, defined a message protocol, agreed on the synchronization frequency, and everything else. The work began. The repository was downloaded, and the build started. Problems arose during the build — they started solving them. The agent on Windows was the subordinate, and the agent on Mac was the main coordinator and acted as the product owner.

Everything, in principle, worked, but it worked very slowly. Communication went through remote file editing (they decided that communicating through one file would be best for them), and file exchange was also not fast. Even though the computers were right next to each other, on the same local network.

By that time, I still hadn't received permission for remote control in ChatGPT.

Idea!

I really liked the idea of agents dialoguing. I thought, why not create a specialized tool through which different agents (chats) can communicate with each other and exchange information.

Scenarios quickly formed in my mind. I often work in multiple tabs: first, I do research, maybe more than one, then in a neighboring tab, I create a quick project based on it, look at the concept. Then I gather the results of discussions and create a large implementation plan. This is how I traditionally do it; I'm not urging anyone to do the same.

Connecting two computers is a task that seems to lie on the surface. But only later did it dawn on me that such a connection would be useful even between two adjacent chat tabs, or, for example, between Cursor and ChatGPT, or other applications.

By the way, as it turned out later, some harnesses allow this out of the box, but only within themselves and with limitations.

I want, I want, I want…

I wanted to continue working where I like. I like Cursor, I like ChatGPT, some people like Claude. Or maybe it's not even about "liking" — whatever people have is good. Many companies have their own solutions, their own LLMs, and use, for example, OpenCode as their application.

I myself had several applications and subscriptions: OpenCode with DeepSeek — corporate, ChatGPT — personal and corporate, Cursor — personal. And I thought: why should I limit myself to just one application? I want to use the strengths of each and the resources of all available subscriptions. Not all of them were actually expensive. I wanted to use them within some project, but cohesively.

I looked at existing ways to connect agents. There is the ACP protocol, but it didn't solve my task on its own: an AI harness becomes a kind of service, and you need a UI to work with it. You would either have to create it yourself or use a ready-made application that can work with ACP with its own UI.

Such applications were found. For example, AionUi is a decent application that combines agents under one interface. But it uses agent CLIs, through which these protocols are accessed, not the desktop applications in which I wanted to continue working.

I definitely didn't want to create another UI environment. And all the power lies in ready-made solutions: they are thoroughly developed by large companies. I wasn't going to duplicate them or even compete with them. On the contrary, I wanted the most transparent integration possible.

Eat the elephant one bite at a time

To continue working in my favorite application, I needed to connect to its API and integrate into its pipeline. I specifically needed integration with the application. A message from another agent should arrive in the specific chat it is addressed to.

This is where the whole complexity emerged. Each application has its own API, its own documentation, its own connection method. Naturally, I was doing this with the help of AI. But simply choosing a large and expensive model in ChatGPT and saying, "I want a universal solution that works with everything" — that didn't work.

Each application required a separate approach, a separate implementation, a series of tests and experiments. One integration took up to three days, and sometimes more, if something didn't work out.

As a result, I couldn't connect all 100,500 applications. I made integrations with those that were at hand and that I could test. For example, I couldn't test Claude myself — I had to ask a friend for help. So, I can't boast of great variety yet, but the project covers the most popular applications.

I didn't expect such difficulties. I thought current technologies were already sufficient for a universal solution. As a result, all adapters are currently embedded in the project itself. The plan is to extract them into a plugin system and define a format, a contract, so that anyone can create the necessary connection for themselves. If anyone will ever need this at all.

This was the backstory.

Successful success

The result was NCF Agent Interconnect, and I really liked how seamless the team of agents' workflow became.

Usually, I do several tasks simultaneously. While one chat is busy with a task, I open another, solve something else, check ideas and concepts. When it's time to gather everything and move on to implementation, I simply type in the chat:

Connect as agent Dan

The name is arbitrary. I get a response: "Connected as Dan." I do the same in adjacent chats, just giving different names. Then I ask one of the agents to gather the results of the work and the conclusions of our discussions.

Gather the results of the experiments from agents John, Carl, and Clara and adjust the plan

Then they communicate without me, addressing each other by name.

I can do everything as needed and even use past consultations. I work as usual, solve my tasks, and along the way, I say something like:

Connect as agent Fix. Register the bug we found with agent Alex, coordinate the fix work with agent Bob

If necessary, I can provide skills in advance or during the process. And all this without separate configurations, exchange boxes, preparatory work, or other dances with a tambourine.

Everything I usually use remains in place: favorite skills, favorite MCPs, work organization by SDD, OpenSpec. But now it's enhanced, as they say, with a new incredible communication capability.

I continue to work with context as usual: sometimes I intentionally let the conversation grow and pass through a compact. In many harnesses, the context is now compressed very well, or other technologies are used so that I don't feel its loss. But if I need to save the context window, I can move the agent under my name to a new chat and ask it to re-read the entire correspondence with other agents to restore the context.

Connect as agent Bob, then re-read the entire correspondence yourself

"Yourself" means not sending sub-agents to summarize, otherwise the effect will be significantly weakened. Usually, this correspondence is like a concentrate, often even better than a compact. In the old chat, the agent disconnects, and in the new one, it continues working. Such a transfer of thoughts.

New experience

Over time, my scenario became more systematic. I pre-create an agent coordinator and task it with monitoring the others, resolving collisions and conflicts, building a work queue, and preparing releases. I usually use the name Bob for brevity.

I connect other agents as work comes in. Each agent knows that coordination issues should be discussed with Bob.

Thus, I can throw tasks into one pot without waiting for previous tasks to be completed. Bob not only distributes tasks but also creates separate git worktrees for each agent so they don't interfere with each other locally.

Later, I assigned one agent solely to documentation, another to incidents. The latter records problems, creates incidents, and at my request, maintains the roadmap. Information is distributed among agents in real-time: they perform their tasks and simultaneously stay informed about what concerns them.

Building on multiple computers has also become a routine process.

Yes, I know you can build in the cloud and/or locally on one machine, but the point is different.

When a release is being prepared, the agent on Windows receives the task, the necessary repository branch, and other coordination data. It builds the project and transfers the result through the same channel the agents communicate: you can send files through it too.

If conflicts or unusual behavior related to a specific system are detected, they are handled on that system. Bob records the problems, solutions, workarounds, and so on in the documentation.

The biggest benefit for me is the ability to work on one task in several chats simultaneously, in multiple directions. I understand that the work likely overlaps, but it no longer bothers me: the agents can discuss the overlaps among themselves.

It's different

Colleagues, if you are already working with agents and sub-agents, you will recognize a familiar approach: ask the main agent to create subordinates, assign them tasks, gather information, and coordinate the work.

It's similar, but slightly different. In the sub-agent scheme, the human primarily interacts with the main agent, and the others remain under its command. In this space, the human is almost absent.

Here, you remain in your chats and can directly interact with each participant. A connection appears between them, and with it, other interaction possibilities. Moreover, one does not exclude the other. In general, one can fantasize about this topic endlessly.

Another anecdote

There was a task: to prepare documentation for future AI employees. It was necessary to gather a complete picture of the operation of a specific frontend module, relying on both the code and existing documentation. Not a full scan of the entire codebase — just one module. Our documentation is still in the standard place — Confluence, and its translation into Markdown was ongoing as a separate project.

In the corporate OpenCode, I created two projects, each with its own folder: one with code, the other with documentation. One agent sits and looks at the code, another — at the documentation in Confluence. And a central editor agent compiles the overall picture and formats the result.

I chose the code as the source of truth. It's tested, it's a working tool, it's used — it implements current business requirements. The documentation describes how the module should work. Priority was given to the code, but differences between it and the documentation were also recorded.

The editor assigned tasks to the researchers and directed further study of the module. I deliberately didn't monitor their context windows overflowing: their knowledge was sufficient for assignments even after compacting. Each harness has its own way of handling compression, but even in this case, I was satisfied with this approach. I ran the editor itself on a large model where compacting didn't bother me much.

In my opinion, the work went very quickly: within 15-20 minutes, a complete picture of the module's operation was compiled into structured Markdown documents.

Telegram vs MAX

"NCF Agent Interconnect" is essentially just a messenger for your agents. They can communicate in adjacent chats of one application, in different applications on the same computer, or in applications on different computers.

The essence of messengers is simple, but imagine if your Telegram was suddenly turned off. A joke, of course, who would turn it off? We would feel discomfort immediately: the familiar connection would disappear, and we would have to find another way to communicate.

We have become so accustomed to communication tools that we don't even see much value in them. We consider them a part of our lives. But if we are deprived of them, it will be extremely uncomfortable.

So, with "NCF Agent Interconnect" constantly running, I had a similar feeling. I got used to agents being able to communicate with each other, and it becomes uncomfortable to do things any other way.

Love is…

Once, I introduced an agent working on DeepSeek V4 in OpenCode and an agent working on ChatGPT Luna. I asked them to maintain a dialogue with each other, without setting any topic or goal.

I won't retell the conversation here: it's an interesting experiment that everyone can do for themselves. But it was very interesting to observe. At some point, they started telling each other about their internal workings — studying each other from the inside, so to speak. They asked how they make decisions, what theses and tools they use.

Fantasies

There are also scenarios that I still want to try. For example, two developers are working remotely on the same project, and their agents are connected and communicating with each other. How this will work in practice — I don't know yet, but it's incredibly interesting.

Or I want to test an arbitrary process based on agents, but without writing a separate program and/or configuring a harness for it, but first checking the concept. You can connect agents, assign roles on the fly, give skills, connect MCPs, and adjust interaction rules as you go: one finishes their part and passes the result to the second, the second to the third, and so on. Without pre-created special configurations or programming. This way, you can get an experimental base.

But it's not necessary to invent a special scenario. I gained benefits simply in my regular work. You can handle more tasks in parallel and be more relaxed about overlaps when there is coordination between agents.

I recommend trying it. Conduct your own experiments, find your own use cases, hone your team lead skills.
