Postmortem of an Electron menu editor: SceneTree, PDFKit, and tests that proved the wrong thing

I returned the 'Volume' to the field it was intended for.

Text overlapped the price.

Four consecutive releases passed automated tests. The green status only confirmed a workaround that the model itself devised, implemented, and then solidified with checks.

When everything looked good visually, a detailed check began, at which point the test results diverged from reality. I checked manually and saw that the volume was not where it should be. Not in Position.volume, but inside PriceNote. Four releases. Four green gates. Four times the process said 'everything is correct' to something that was not correct. After that, I had to deal not only with the bug but also with the contract that allowed it to pass.

A mundane task with typographical tolerances

I am a system architect. Ten years ago, I wrote websites in PHP and JavaScript; now, I write small scripts in Python and VBS. In my main job, I spend more time analyzing requirements, constraints, and architectural decisions than writing application code. My wife works for a large restaurant chain. She received new requirements for printed materials and Adobe Illustrator templates, but they didn't have Illustrator, and no one knew how to work with it. Initially, the task was reduced to a single menu edit. My local Qwen 2.5 handled it, but you can't install it in a restaurant. This is where I saw a suitable testing ground, a real task where I could see: How quickly can something be created, and can it be understood, tested, supported, and managed?

What was needed was not a replacement for Illustrator, but an editor with a narrow scope of action.

Over several iterations, one template turned into three document families, Russian and English versions appeared, undo/redo, text formatting, project saving, preflight, PDF export, and builds for two OS. The list of functions itself was ordinary. What was unusual was the cost of the discrepancy between what was visible on the screen and what was produced in the PDF output.

The first interface appeared quickly. There was no mockup: I described the panels in FT and TZ, and the model assembled a working screen and even added drag-and-drop elements that I hadn't asked for. It looked convincing.

By 2026, the story of 'an architect building an application with agents' is no longer news. Therefore, there will be no excursion into prompts. What's more interesting is how a process with separated roles, release gates, and a large set of tests still produced the wrong entity.
