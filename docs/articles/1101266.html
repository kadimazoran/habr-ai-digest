Introduction

Typically, RAG systems and AI agents are built around cloud APIs (OpenAI, Anthropic) and managed vector databases. However, for many tasks, complete autonomy is crucial: resilience to sanctions and independence from external providers.

In this article, I'll explain the architectural decisions and engineering compromises that allowed me to build such a system entirely on local models. We'll cover the journey from collecting RSS feeds to a smart agent that calls tools itself, and discuss the pitfalls I encountered.

Stack: Python 3.12, FastAPI, PostgreSQL + pgvector, Celery, LangGraph, Ollama (Qwen 2.5 14B, BGE-M3), Streamlit, Langfuse, Docker.

Architecture

The project is divided into layers (domain, db, scraper, rag, agents, api). The main principle is isolating domain logic from frameworks. This allows for easy swapping of LLMs or frameworks without rewriting business logic.

Search Selection

We collected 12,000+ articles. We embedded them (BGE-M3) and started searching by cosine distance.

Simple queries worked fine. But with complex ones (e.g., 'central bank key rate'), vector search returned garbage. The most illustrative example was the query 'gold': the system honestly found articles where a figure skater 'won gold' in competitions, not news about metal prices. A classic problem of homonymy.

The solution: Hybrid Search. We combined semantic search (vectors) with precise lexical search (BM25 on PostgreSQL tsvector) using the RRF (Reciprocal Rank Fusion) algorithm. BM25 is excellent at capturing exact terms ('gold', 'OPEC', 'rate'), while vectors capture synonyms. Thanks to this, Recall@5 increased from 0.2 to 0.53.

The 'Garbage Pile' Problem: How LLM Hid in the 'Other' Category

We asked the LLM to classify articles. The first result: 74% of articles ended up in the other category. The model was afraid of making mistakes.

Solution: We rewrote the prompt, added clear descriptions for each category (including retail, macro, incident), and removed the phrase 'if in doubt, use other'.

Result: other was reduced to 0.03%. Now we have a structured dataset, not a pile of text.

But this is not the final point. After completing background processing, I conducted a round of manual quality assessment (Data-Centric AI): I took a random sample of articles from different categories and checked if the LLM had indeed labeled them correctly. The classification accuracy was 85%, confirming the approach's effectiveness.

LangGraph: An Agent That Can Calculate

A standard RAG answers questions like 'What's being written about oil?'. But we need analytics. We wrote a State Machine on LangGraph with three tools:

  • search_articles: standard hybrid search.

  • get_metrics: SQL aggregation (how many articles about energy in 3 days).

  • search_by_entity: search by extracted company names and sentiment (NER/Sentiment).
    Now, when asked 'Are there negative news about the Central Bank?', the agent decides which tool to call itself.

Observability: How We See What's Happening Inside

We deployed a self-hosted Langfuse. We can see every agent step (Planner → Tools → Finalizer), how many tokens were consumed, and what arguments the LLM passed to the tools. This is invaluable for debugging.

Major Pitfalls (and How We Overcame Them)

  1. VRAM Ping-Pong: Ollama unloaded models when switching. A request took 60 seconds. Solved by setting OLLAMA_MAX_LOADED_MODELS=2.

  2. LangChain Overhead: ChatOllama internally uses streaming aggregation, causing a 9x slowdown. We removed LangChain from the RAG pipeline and switched to a direct ollama.AsyncClient.

  3. Celery + Async: SQLAlchemy binds the connection pool to the event loop. When Celery killed a task, connections became 'zombies'. Solved by using await engine.dispose() after each task.

  4. Ollama processed requests sequentially. Classification is a rather lengthy procedure; on my hardware, it took about 10 seconds per article. By increasing OLLAMA_NUM_PARALLEL from 1 to 2, I sped up the process by at least 1.5 times (there's still room for optimization here).

What's Next?

The project is currently in Public MVP stage. It's an excellent foundation for demonstrating AI engineering expertise. The next step (already in private mode) will be to move from 'general news background' to personal stock market analytics: linking companies to Moscow Exchange tickers (SBER, GAZP), extracting specific market facts, and building predictive dashboards for individual stocks. The architecture (ADR-001) is specifically designed so that this expansion will not require rewriting the core.

The project code is open and available on GitHub: [https://github.com/tzar26/news_scrapper].

Conclusion

Building a production-ready AI system on local models is achievable. It not only saves money but also provides full control over data. The project is fully containerized (docker compose up -d) and covered by tests (GitHub Actions).
