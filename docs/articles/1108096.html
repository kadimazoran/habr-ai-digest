In one morning, I merged 64 pull requests prepared by AI agents into three applications. The initial briefing helped convey my decisions and approach to work to the agents. But one bug, which I missed during the merge, showed that my oversight was not yet sufficient.

On Saturday, October 31st, at 9:30 AM, I started merging PRs. Within the first two minutes, 11 pull requests were sent to the task manager. By 11:38 AM, I had managed to merge 64 PRs across three repositories: 27 for the web application, 22 for the iPhone, iPad, and Mac application, and 15 for Android. The sprint on the board was scheduled for November 2nd-13th.

By lunchtime, none of these changes had reached users yet.

I didn't write a single line of code for this sprint. The AI tech lead planned the work, prepared task descriptions, distributed them among the AI engineers, assigned each a dedicated terminal session, reviewed their PRs, and updated the task board. My role was to approve the plan, make decisions on issues the agent presented to me, and merge the PRs. From my perspective, everything looked great.

GSD is my free task management applications based on the Eisenhower Matrix. By default, tasks are stored locally on the device, and synchronization can be enabled optionally. GSD works in the browser, on iPhone, iPad, and Mac, and the native Android app is undergoing testing in Google Play. The goal of this sprint is to achieve consistent behavior across all three implementations. The source code for the web version, the app for Apple devices, and the Android app is available to everyone.

Eleven AI engineers worked in two waves under the guidance of a lead agent. On my Mac mini, the load average reached 275 with 14 cores. All questions were initially directed to the lead agent, who then involved me when a decision or confirmation was needed.

However, in the final report, the lead agent listed everything that remained unchecked. The release build of Android 0.10.1 still needed to be tested on a real device, including verifying account login and synchronization. Manual checks, from deleting a temporary test account to logging out during synchronization, were also not performed. iOS simulators 27 on my machine wouldn't launch under Xcode 27.2, so checks had to be conducted on iOS 26.5.

Pre-defined decisions and requirements helped the agents complete and merge a large volume of work. But now I had to decide if the verification results were sufficient for releasing updates. The number of merged PRs didn't answer this question.

I'm happy to entrust agents with writing code. But I'll retain responsibility for the outcome.

Write Kickoff Instructions as if Briefing a New Tech Lead

It all started with a single post, based on which I prepared a document with initial instructions. I placed it alongside the repositories of the three applications and asked Claude Code to first create a plan and then stop at a checkpoint. It turned out to be something like the instructions I would give a new tech lead on their first day.

First, the document assigns roles. The lead agent plans the work, prepares task descriptions, assigns engineers, handles escalated issues, reviews PRs, and manages the task board. Engineers make commits, push their branches, and open PRs. In this sprint, only I could merge changes. An engineer here refers to a separate Claude Code session with a task description and ticket. One of the eleven engineer agents was solely responsible for preparing a summary of the sprint materials.

Next are the rules for parallel work. Each agent writing code was allocated a separate Git worktree and branch. A file responsibility distribution scheme determined which engineer was allowed to modify each shared file. Issues regarding contracts, data security, or areas of responsibility were recorded by engineers in a separate file for the lead agent, while they switched to independent tasks or waited for a response. I organized the terminal sessions using herdr, which marks a waiting agent as blocked.

If I had to keep only one thought from all the kickoff instructions, I would choose this: whatever you don't clarify, the agent will have to figure out. Each engineer starts work without the context of the lead agent's conversation history. They can study the repository and instructions, but they won't know about decisions I haven't documented anywhere.

An agent is quite capable of filling this gap with a plausible assumption and continuing the work. Therefore, the task description must specify the goal through the expected application behavior from the user's perspective, verifiable acceptance criteria, and precise commands to check the result. It must also list the files the engineer is responsible for, files they are forbidden to touch, and situations where they need to seek help.

Select Agents Based on the Cost of Error

In the kickoff instructions, three levels of engineers correspond to three models. Lead agents on Opus 5.5 handle contracts, synchronization, data migrations, architecture, complex bugs, and reviews. Senior agents on Sonnet 5.5 implement functionality according to approved contracts. Junior agents on Haiku 5.5 handle mechanical work with clear verification criteria, as well as report preparation.

These role names are merely for task distribution. They help the lead agent understand whom to assign what work and what kind of review will be needed. However, this does not mean the model is capable of making decisions at the level of an experienced senior engineer.

For junior agents writing code, there were particularly strict limitations: no changes to data schemas, synchronization, or authentication, and no tasks whose results could not be verified deterministically. If an error could lead to the loss of user tasks, I chose a more powerful model and involved an additional reviewer. The more costly an error, the more powerful the model should be used.

I did not track token consumption or costs, so I cannot say how much this morning cost or how economical this task distribution was. In the second sprint, I plan to measure both.

Evaluate the Morning's Results Like Benchmark Results

In one of my articles, I used Dan Shipper's term "smuggled intelligence." This refers to human expertise embedded in a task before the model begins working on it. It's easy to attribute the entire result to the model and overlook the effort put into preparation.

My morning should be evaluated with the same caution. I wrote the kickoff instructions together with Claude. Claude did most of the drafting, while I determined the document's content and the wording of the rules. By my estimates, preparing the instructions, reviewing the plan, and making decisions on issues escalated to me took three to four hours of my time.

Furthermore, the agents didn't start from scratch. They already had mature repositories, existing tests, and results from previous behavior equivalence checks. The Android branch already contained 17 commits awaiting integration. These changes were also included in the 64 merged PRs. The planned two weeks were not a measurement of how long it would take a human. And the interval from the first PR to the last merge doesn't account for preparatory work at all.

The morning was productive. However, its results cannot determine what portion of the success is attributable to the models' capabilities and what portion to the organizational structure around them. On the other hand, I have a detailed history of this organization that can be studied and improved.

In a previous article, I referred to a versioned specification that preserves decisions and passes them along with the task as a Context Spine.

The kickoff instructions serve a similar function in coordinating work: they define who is responsible for decisions, what confirmations are needed for them, and where to turn in case of uncertainty.

First, Fix the Contract, Then Start Implementation

When ensuring the behavioral equivalence of three codebases, a common problem can arise. Each platform interprets the same rule differently, and a task synchronized from the web application behaves differently on Android. Shared contracts and test data allow all implementations to rely on the same examples and expected results.

By the end of the sprint, the corpus contained 352 test examples. Of these, 155 were checked by all three clients: 117 related to the time of day a task was scheduled for, and 38 to task escalation by deadline.

The remaining 197 covered the representation of three priority tasks and the weekly review, scheduled for the second sprint. The lead agent verified 74 copies of test data in the repositories and Git worktrees and found no discrepancies.

However, in practice, the workflow was not as neat as anticipated. According to the established merge order, the test case corpus for checking task execution times should have been merged into the main branch first. Instead, I merged the web application implementation a minute earlier.

Some tasks also used interdependent branches. Such dependencies are acceptable, but each engineer must know exactly which contract version they are targeting. If PRs are merged in a different order, the "contracts first" principle requires explicitly documented dependencies and a verification plan.

The number of lines should also be treated with caution. Of the 25,882 added lines, the lead agent attributed 13,714 to the test case corpus and test data, including their copies across different repositories, and 3,817 to application code.

Another 7,166 lines were for tests. This explains the large size of the changes but says nothing about their value or correctness. During the evening review, bugs were found that these tests missed.

All coordination went through the lead agent. Previously, I concluded that discussions between agents justify the cost when a task truly requires conflicting viewpoints. Here, a significant portion of the implementation could have been done independently, based on shared rules.

However, during the review phase, I specifically wanted these rules to be critically examined, especially when the implementation on one platform was used as a benchmark for another.

Working on Behavioral Equivalence Reveals Bugs Unnoticed on a Single Platform

I expected the sprint to focus on new functionality. However, when distributing PRs by type, it was evenly split: 24 with new features, 24 with fixes, eight with tests, and another eight with documentation and auxiliary tasks. iOS even had more fixes than new features: 14 versus seven.

The most serious issue was found in Android 0.10.0. A task created between two database read operations could be deleted without saving a copy to the trash. The lead agent reproduced the bug in a storage simulation, and the fix was included in version 0.10.1. On iOS and in the web application, a rejected authentication token could cause the task list to appear as if all tasks on the server had been deleted.

After the fix, the deletion reconciliation mechanism during synchronization first checks the session's validity and only then deletes local tasks. In the web application, it was discovered that during quiet hours, reminders set for a specific time were simply discarded instead of being postponed.

Here, the rule from the kickoff instructions for cases where the reference implementation raises doubts proved useful: if something looks like a bug, report the issue first, and then port the implementation to another platform.

Engineers submitted 20 questions to the lead agent and received answers to all of them. The lead iOS engineer agent questioned a task description that would have removed existing iOS protection. In the same message, they pointed out the lack of user ID verification, which ultimately led to the creation of iOS #45.

The lead Android engineer agent paused before changing the specification, calling it a "data integrity affecting decision." This issue led to an investigation of the saved_at problem, which will be the starting point for the second sprint.

The most valuable aspect here is that the agents were willing to question their assignments. I had anticipated this possibility in the instructions, and the work history shows they utilized it. For an agent to successfully handle tasks, they must be given the opportunity to report that the task description itself is flawed.

The Lead Agent Also Made Mistakes, and This is Evident from the Work History

The final report includes a section titled "Where the Sprint Went Off Track." Checks on the web application's main branch (`main`) failed twice. First, two PRs related to synchronization caused a conflict during testing, and the mock issue had to be fixed with a separate PR.

Later, a PR adding the ability to postpone a reminder in the editing panel broke a selector in an end-to-end test. The lead agent admitted to missing this during review. However, I merged the changes, so the responsibility for the missed error also lies with me.

One of the iOS commits was merged into the branch after its parent PR was merged and remained without its own pull request until the lead agent discovered it at the end of the sprint. The agent also documented five of their own decisions that were later revised.

In one instance, they instructed the iOS engineer to replicate the web application's behavior entirely, even though the native implementation with deferred writes required a different approach.

There was also an exception in the work organization itself that I should have considered. According to the plan, each coding agent was supposed to work in a separate Git worktree. However, the launch script explicitly directed the lead Android engineer agent to the main repository directory, into the existing Saved branch.

This resulted in the rule in the document contradicting how the agent was actually launched.

The task board, decision log, and final report helped identify all these issues. Without such a history, the sprint might have appeared smoother, but there would have been less confidence in its results.

Now I Myself Have Become the Bottleneck in Merging Changes

Two hours and eight minutes passed between the first and last merge. The lead agent, in their report, measures time from the opening of the first PR at 8:40 AM, resulting in two hours and 58 minutes. I merged changes mostly in batches, as reviews were completed.

In the web repository, SonarQube Cloud performs a quality gate check, and Codex reviews code and checks its security.

The iOS and Android repositories had no CI at all, so the only confirmation of functionality remained the results of local tests run by the authors themselves. PR #650, which adds support for sending data via the system "Share" menu to an installed Android web application, clearly illustrates why, even after such checks, a separate decision is needed regarding the readiness of changes.

SonarQube successfully checked this PR: the test coverage for new code was 96.6%. However, Codex detected a P2-level issue: if both a header and text content were present when transferring data, the latter was lost.

After updating the documentation, the lead agent approved the PR, and another automated check found no issues. I merged it anyway, along with the others. The error was found during review, but I ignored the comment and merged the changes.

The test coverage metric was correct. Codex's remark was also valid. The fact that the code executed during testing did not mean it preserved the information shared by the user.

There are two points where human decision-making is required: plan approval and release approval. This sprint added a checkpoint for contract verification and my decisions on merging each PR. By lunchtime, the release decision had yet to be made.

In the evening, I instructed the agent to check deployment readiness on the main branches of all three repositories and to perform a critical code review separately, looking for potential issues. According to the report, all automated tests passed successfully: 4059 web application tests, 312 Swift package tests, 466 Android JVM tests, and another 339 tests on an emulator. Yet, the final verdict was: "Cannot release everything together yet."

On iOS, new actions with reminders (Complete and Snooze) did not work when the application's database was paused. Additionally, if an account deletion completed with a partial error, the next synchronization could delete local tasks. This bug existed before the sprint.

In the web application, selecting a predefined interval for postponing a reminder could lead to its loss. Android received conditional release approval, provided I conducted smoke testing on a real device. Fixes for three bugs were later incorporated into the web repository via #662 and into the iOS repository via #62. However, merging these PRs did not yet mean releasing the updates.

Merged PRs represent completed work. The actual result that matters is that a user's task doesn't disappear after synchronization on someone's phone.

Application deployment and uploading builds to stores were not initially part of the sprint's tasks. By its completion, tasks remaining included verifying account login on a real Android device, deleting a temporary test account, functionality with the Mac trackpad, actual iPad notifications and keyboard, and making four decisions requiring my involvement. After implementation completion, these specific tasks became the critical path.

In a large organization, such responsibilities might be distributed among device testing labs, release engineers, product owners, and specialists responsible for synchronization changes. Some of this work can also be automated.

The main conclusion I drew after this sprint is that verification and release capabilities must be planned concurrently with implementation capabilities. Otherwise, accelerated development will only increase the queue of changes awaiting acceptance.

Previously, I wrote about how decision-making shifts to an earlier stage—task definition. This sprint equally demonstrated the importance of another end of the process: deciding what confirmations are sufficient to accept the result. Someone must be responsible for both decisions, even if an agent makes the actual choice.

What to Consider in the Kickoff Instructions for the Next Sprint

In the second sprint, I will give the agents more autonomy in merging changes. They will evaluate review results and decide which PRs to merge themselves. I will still approve the release, and the responsibility for the outcome will remain with me.

This is an experiment whose results are yet to be evaluated. I ignored a useful comment during the merge, but the lead agent and another automated reviewer also didn't pay sufficient attention to it. An agent making a merge decision might well make the same mistake.

Next time, I want to see in the work history what happened to each significant comment: was the issue fixed, rejected with a reason, or escalated for consideration. PR #650 will serve as a specific example for such an evaluation. The warning that user-provided text might disappear requires a solution before merging the changes.

I expect reviews to take longer and will evaluate the outcome not only by the pace of work completion but also by the number of unresolved comments, the amount of rework, and release readiness.

There is another issue I need to fix myself. The lead agent published review results through my GitHub account, so their comments appeared under my name, even though the agent made the decisions. In the second sprint, I intend to resolve this problem.
