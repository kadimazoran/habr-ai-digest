My Workflow

Before OpenSpec, my work session with an agent looked like this. At the input, there was already a task elaborated by the business analyst. I start by checking how detailed it is. If the description is sufficient, I immediately send the task for planning. If not, I detail it.

For detailing, I use the grill-me and brainstorming skills. The output is not just a task description, but system requirements: how exactly the new functionality should look in my application or system. If the task involves the user interface, I ask the agent to prepare several UI mockups.

Next step: the spring-planning skill. I pass the resulting system requirements and UI mockups, if any, to the prompt. As a result, the agent prepares a plan of changes to be made. I review the plan and, if I already see from the text that the initial requirements have not been interpreted quite correctly, I leave comments and ask for the document to be revised.

Separately, I always check that the plan includes tasks that "guarantee" the agent won't consider the work complete if tests fail, coverage drops, or there are Checkstyle issues. Additionally, the plan must include a separate task for reviewing the implementation by another agent.

For implementation, I create a new agent session and, importantly, a separate worktree where the agent executes tasks according to the prepared plan.

When all plan tasks are completed, Checkstyle passes, tests pass, and coverage doesn't decrease, I proceed to code review. The agent generates too much code to read every line with equal attention, so I have to rank changes by importance. I always check models, services, repositories, db migrations, and tests; everything else depends on the initial task.

For code that has passed my review, I run mutation testing using PITest and analyze its results. If I find an important scenario that should have been tested but is missed by existing tests, I generate a separate test for it.

In the final stage, I always check for the presence of end-to-end tests. If automating them is impossible, I test the feature's functionality "manually."

Next is the standard process: commit, push, PR/MR, review by other team members (if required), and merge.

OpenSpec

OpenSpec is an open framework for Spec-Driven Development. Its main task is to help us work with specifications throughout their entire lifecycle: from the moment an idea for new functionality first arises in the product owner's mind to the moment it's implemented in the application. In my situation, OpenSpec is only introduced at the development stage, so I'll focus on that.

First, let's understand what a specification is. A specification is a document (or set of documents) that records system requirements and the expected development outcome. "Ideally," it answers several questions: what problem are we solving and for whom; what user scenarios do we support; how should the system behave in normal and error situations; what constraints must be considered; by what criteria will we know if the functionality is implemented correctly.

OpenSpec has two types of specifications: main specs and delta specs. Main specs store the description of the system's current behavior and serve as the source of truth. Delta specs are created for a specific change and describe only the difference between the current and desired state: what requirements need to be added, changed, deleted, or renamed.

The specification itself consists of a set of requirements, and each requirement must have at least one scenario. Both requirements and scenarios are formatted with separate headings: ### Requirement: and #### Scenario: respectively. A requirement describes a single observable and verifiable system behavior, is formulated using SHALL or MUST, and does not contain implementation details. For example: The system SHALL return the collection of all stored veterinarians.

A scenario, in turn, defines the acceptance criteria for a requirement and describes specific conditions and the expected result in the GIVEN/WHEN/THEN format — or WHEN/THEN if there are no preconditions. For example, the scenario List with existing records defines that the request GET /api/vets, when veterinarians exist, should return 200 OK and a JSON array with all records.

At first glance, it might seem that these requirements and scenarios are too obvious. But, firstly, obvious things also need to be documented somewhere. Secondly, OpenSpec generated them on its own — apparently, it still needs them. And since they correctly describe how our application should work, let's leave them as they are.

Naturally, in the age of AI, we only write prompts by hand — and even those we sometimes just dictate. Therefore, it's time to figure out how to generate specifications using OpenSpec.

OpenSpec Change

Any modification in OpenSpec is done by creating a "change."

Inside it, OpenSpec stores the delta spec and artifacts related to the modification. By default, this includes a proposal — it captures the intent and scope of the change; design — it describes the technical solution; tasks — it defines the sequence of work that the agent will follow. This list is not exhaustive: if necessary, it can be supplemented with artifacts that you specifically need.

Let's create our first change. As an example, we'll develop a typical application — a veterinary clinic. We'll use a clean project on Spring Boot 4.1.1 and Java 26 with Spring Web MVC, Spring Data JPA, Validation, and PostgreSQL connected. For now, it's an empty template without a domain model or endpoints. With the first change, we'll add storage for veterinarian information and a CRUD REST API to work with it.

But before creating the first change, we need to initialize OpenSpec in the repository.

For this, we'll need the OpenSpec CLI. You can find installation instructions for your platform and OS in the official documentation.

Next, we execute the command openspec init and select the agents we will use for application development.

What happened under the hood? openspec init created an openspec/ directory in the repository root, which will store project configuration, current specifications, and future changes. At the same time, the CLI installed skills and slash commands for the selected agents. There are no specifications at this stage: init only prepared the project structure and instructions for the agents to follow.

Next, we'll go through the full change cycle, consisting of three stages: Propose, Apply, and Archive. We'll cover each one separately.

Propose

To create the first change, we'll use the command /opsx:propose and pass it a prompt describing what we want to change in the application.

In a real project, the task description is usually already in a ticket or on a Wiki/Confluence page, so in /opsx:propose, I just need to provide a link. Since my agent is connected to these corporate systems, it will load the initial requirements itself and create the change based on them.

During the propose phase, the agent first looks at what's already documented in the main specs. If specifications exist, it determines which ones the change will affect: which requirements need to be added, clarified, or removed. If main specs don't exist yet (as in our clean Spring Boot project), the agent describes the new behavior from scratch. The result of this work is delta specs: requirements and scenarios describing only the difference between the current and desired system behavior.

Then, the agent analyzes the current codebase: what modules and dependencies are already in place, where it's logical to integrate new functionality, and what technical constraints cannot be ignored. Based on this, it prepares design.md — the technical design of the change — and tasks.md — a work plan according to which the agent will implement the task in the next step.

When propose is complete, we check the generated artifacts. I read them in this order: proposal.md → specs → design.md → tasks.md. We need to ensure that the agent correctly understood the initial task and that the proposed implementation meets our expectations: in terms of interface, user scenarios, and internal architecture. In tasks.md, I specifically check that the plan includes tasks related to guardrail checks: unit and integration tests, Checkstyle, ArchUnit architectural checks, coverage, and PITest mutation testing. Additionally, I make sure there's a task for code review by another agent: if the main development was done by Claude Code, Codex reviews it, and vice versa.

In my situation, I often had to ask the agent to make the same corrections from one change to another during the propose stage. To reduce the number of corrections and adjust the agent's behavior, there are several ways:

  1. Add a "control" prompt to your agent's CLAUDE.md or AGENTS.md

  2. Place instructions in openspec/AGENTS.md — OpenSpec maintains this file itself

  3. Describe the rules in the OpenSpec configuration file — openspec/config.yaml

  4. Create your own artifact schema

Artifacts checked, corrections made — we can move on to the actual implementation.

Apply

To have the agent start developing the specification, simply call /opsx:apply. It will take the tasks.md of the selected change and go through the plan items. But before that, I take a few preliminary steps.

First, I commit the change specification. At this stage, there is no feature code in the repository yet — only the proposal, delta specs, design, and tasks. If something goes wrong during implementation, you can always return to the agreed-upon artifacts.

Next, I create a separate worktree and conduct all development within it. This way, the current implementation doesn't interfere with other unfinished changes, and if necessary, several specifications can be developed in parallel.

Then, I clear the context of the current session or start a new one. The propose session has already accumulated discussions, comments, and intermediate corrections, which are unnecessary and potentially harmful for implementation: everything needed is already in the change files.

After that, I call /opsx:apply, specifying the particular change specification.

At this stage, the agent is no longer planning but writing code. OpenSpec defines *what* needs to be done, but it doesn't replace instructions on *how* to do it in Spring. Therefore, the Spring Skills we connected earlier remain relevant: the agent still relies on them when creating entities, repositories, DTOs, and REST controllers.

As before, after the code is written, it needs to be reviewed. The agent still generates too many changes to read each one with equal attention, so I only look at the most significant code: models, services, repositories, db migrations, and tests.

I always check for the presence and correctness of automated end-to-end tests. If automating certain end-to-end scenarios is impossible for some reason, I perform them manually (or ask QA to do it). Then, I run PITest on the newly written or modified code to ensure that the agent didn't miss any important scenarios during development.

After completing the review and all necessary checks, you might want to commit the changes immediately, create a PR/MR, and move on to the standard process. But wait, wait: we haven't yet converted the delta specifications into main specifications. Therefore, we commit the changes in the source code, but don't create a PR/MR yet. First, we need to synchronize the specifications and archive the change.

Sync & Archive

Why synchronize specifications at all? While delta specifications live only within a change, main specifications still describe the system *before* our modification. But it's the main specifications that are the source of truth the agent will rely on for subsequent proposes. If they are not updated, the next change will start with an outdated picture of the world: the agent won't see the requirements already added and will either describe them again or calmly propose behavior that we just implemented differently. Synchronization transfers ADDED, MODIFIED, and REMOVED from delta specifications to main specifications. For this, OpenSpec has a special command /opsx:sync. But don't rush to call it.

The thing is, synchronization is only half the job. As long as the change resides in changes/, OpenSpec considers it incomplete. To complete a change, it must be archived. For this, OpenSpec has the command /opsx:archive.

During the archiving process, the agent, first, synchronizes delta specifications with main specifications, and second, moves the change directory from changes/ to changes/archive/ with the current date. The proposal, design, tasks, delta specifications, and other artifacts don't disappear: you can always return to them later.

Just like before apply, I clear the current session or start a new one and call /opsx:archive specifying the change name.

We commit the results of synchronization and archiving, create a PR/MR, perform the remaining steps of the standard development process, and move on to the next task, starting again from the propose step. Thus, we have completed the full cycle of making a change with OpenSpec.

Conclusion

Let's summarize. In my case, OpenSpec didn't become something revolutionary, but rather formalized what I was already doing: first clarifying requirements, then checking the plan, implementing it in a separate worktree, and only after review merging the changes. Therefore, the "top-down" implementation turned out to be not as painful as I expected.

Among the advantages, I've lost the fear of starting a new session in the middle of work. Now it can be done at any time without fear of losing accumulated context: everything necessary is already documented in the proposal, design, specs, and tasks. With current context windows of a million tokens, this isn't as crucial as it was with 250,000, but it can still be useful. A long session inevitably accumulates intermediate solutions and already irrelevant discussions, while a new one gets only what's truly needed for the current stage.

Regarding the main specs themselves, I don't have a definitive opinion yet. On one hand, consistent application development through OpenSpec truly forms a general description of the system's behavior. On the other hand, the specifications themselves are not easy to read. Partly, this is because we are used to describing systems differently. Moreover, elements of completely different abstraction levels can coexist. In one specification, you might find a business requirement and a description of the column type to be used in the database. A separate question is the Gherkin format for scenarios. I haven't decided yet how appropriate it is here.

But it seems that SDD is confidently entering corporate development. Therefore, I recommend not postponing acquaintance and not waiting until they come for you, but trying it yourself.
