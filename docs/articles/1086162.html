When the knowledge base became too large for "just dense"

The first large export contained 7,991 pages. After expanding the index to 20 Confluence spaces, the corpus grew to 34,949 pages and 79,671 chunks: the number of pages increased 4.4 times, and chunks approximately 5.5 times.

Along with useful documentation, the index included old versions of instructions, overview architectural pages, tables, JSON, macros, endpoints, and internal identifiers. On a small corpus, dense search easily finds the semantically closest document. On a large one, a dozen almost correct candidates appear around the query: they are semantically similar, but only one contains the needed fact. Therefore, a precise instruction might end up in the 6th–7th position.

Manual checking of a dozen queries is useless here: you can improve them and imperceptibly worsen hundreds of others. Therefore, the first result of R&D was not a new model, but a proper benchmark.

We generated 5,000 queries for 1,700 unique pages: 4,459 prose queries and 541 code/API queries. The set included regular Russian questions, exact keywords, mixed Russian-English formulations, troubleshooting, and API terms. The expected page was defined by the source page on which the question was built, not selected from search results. This is an LLM-generated and then LLM-corrected regression benchmark, not a human gold standard: the source page is not necessarily the only relevant document or the corporate source of truth.

All these queries were distributed among three experts: Minimax, Kimi, and Qwen. After the first pass, 3,859 queries were deemed correct, 1,097 were sent for rewriting, and another 44 were marked as incorrect. In the second pass, Minimax rewrote 1,002 queries, leaving 139 unchanged; the final set retained all 5,000 lines.

At the page level, we calculated Page@1, Page@5, Page@10, and MRR@10, where Page@1 is particularly important for us, as the context window capacity is limited, and passing more candidates to the local LLM means paying for latency and throughput. Separately, we collected a chunk benchmark of 3,000 queries and calculated Chunk@1/5/10/20 and EvidenceRecall. The chunk gold standard was obtained heuristically, not fully labeled by humans, so it's a tool for comparing configurations, not an absolute production truth. Page-level and chunk-level are different samples, so we don't combine them into a single "growth line."
