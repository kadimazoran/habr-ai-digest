Over the past year, the number of tools for agent development has exploded, making it easy to get lost: some promise to maintain context between sessions, others to "understand" the entire codebase, and yet others offer memory, planning, and autonomy in one package. Every week, GitHub repositories appear with impressive (and not always honestly earned) star counts, promising everything at once, only to turn out to be README projects. Others work honestly on demo repositories and crash with OOM at the first encounter with a real enterprise project – and so on, the list can go on.

Last fall, I used a combination of Claude + RooCode + semantic search on Ollama, and it was my primary work tool – right up until the combination stopped working (more on that below). I decided to switch entirely to Claude Code and started looking for a replacement for the semantic index, but never found one: alternatives simply didn't work for me – on a 3.5M+ line monolith, they either indexed for hours, required sending code to the cloud (and paying a hefty sum for embeddings!!!), or supported Ruby, to put it mildly, nominally. As a result, I made a difficult decision for myself to create my own tool – starting with a fork of a simple semantic search engine on Ollama + Qdrant – and, characteristically, I succeeded: completely local, so that neither the code nor its derivatives (index, embeddings, call graph) go anywhere. To date, it has taken more than six months (and, I confess, more than a few hundred cups of tea).

And here are the problems I was solving:

  1. The agent can't find logic that I find in two minutes. Grep, a hundred matches, files read in sequence, and burned context – even though throughout the codebase, what the product calls an invoice is called a bill in the code, and payment lives under a third name; such a dictionary gap cannot be bridged by any number of grep iterations.

  2. Indexing a large monolith takes hours. The original project I forked takes four to ten hours for a full index and forty minutes for an increment on a hundred commits; Roo takes fifty to sixty minutes. I needed minutes.

  3. Ruby is supported nominally. Chunks are not cut by AST, the quality leaves much to be desired – and for Ruby, the project's style is half the accuracy of generation. Regarding resolving calls in a dynamic language where half the code is DSL (Rails macros, delegate, scope, plus the DSL of every second gem), agents at that time didn't even mention it.

  4. The agent copies the first similar code, not the correct one. It doesn't distinguish stable code from hotspots, doesn't know whose it is or where bugs most often appear – the very knowledge that usually resides in a senior's head.

  5. The agent doesn't see the structure. Who calls this method? What will a change affect? Where are the cyclic dependencies? For it, these are just adjacent files.

  6. The agent reinvents the wheel. The Nth retry helper, the Nth validation, the Nth date formatter – the only class of damage that has no duplicate protection: hallucinations are caught by the compiler, style by reviews, regressions by tests, but the Nth correct way to do the same thing is caught by no one.

  7. Even with the index connected, the agent doesn't use it – or uses it inappropriately. Out of habit, it goes to grep, calls semantic search for the exact symbol name instead of an instant lookup, ignores ranking modes, and confuses parameters. Connecting an MCP server is not yet a working process: the knowledge of "when and which tool" should come with the tool.

Why these problems weren't invented by me

I first tried Claude in June 2025 – and was disappointed. Not because the model was weak: it was simply difficult for it to navigate my work repository – a large US B2B SaaS monolith, where to find the necessary logic, you need to know its historical name. The token limit was burned through in minutes in exchange for dubious results, and after a couple of weeks, I canceled the subscription. Everything changed with the advent of semantic search in Roo: I appreciated the advantages of the semantic index – despite the drawbacks, which seemed minor at the time. And then, working with the index month after month, I began to truly notice these drawbacks – points 4–6 from the list above.

But the real turning point came after the appearance of TeaRAGs (yes, that's what I named my own tool, the origin of the name is below) and its demonstration within the company. My CTO (ex-FAANG) asked one question: "How will your engine distinguish good code from bad?" I had no answer at the time. However, this question initiated research that has not ended to this day – and during which it turned out that none of the problems above were invented by me: under each lies either research (sometimes half a century old), or the move of one of the killer whales whales, or both. Below is a brief summary of each.

An important caveat before the list. Some of these problems – primarily the first one – are already solved by semantic search itself: as a meaning-based discovery tool, not as a naive RAG, which is criticized for automatically injecting "similar" context just in case. Semantics does not solve the rest – and below you can see why.

1. The agent can't find logic – navigation and context

An agent without an index searches by text and reads files sequentially – and the more it reads, the worse it thinks. This is not a feature of Claude or a matter of context window size: degradation on long inputs has been measured on all tested top models, and the benefit of context retrieved by meaning is evident on the main benchmarks of repository code.

  • Context Rot – Chroma researchers (2025) took 18 top models at the time, including GPT-4.1, Claude 4, and Gemini 2.5, and repeatedly lengthened their input on the same simple tasks of "find the line" level. The quality dropped for all – unevenly and poorly predictably – and irrelevant fragments in the context dropped it even further. It is precisely such fragments that the agent picks up with a grep loop.

  • Lost in the Middle – Liu, Liang, and colleagues from Stanford, UC Berkeley, and Samaya AI (TACL 2024) moved the desired document within a long context and obtained a U-shaped curve: what is at the beginning or end is found by the model, what is in the middle is lost, even by models specifically trained for long context.

  • NoLiMa – Researchers from LMU Munich and Adobe Research (ICML 2025) removed literal word matches from the classic "needle in a haystack" test so that the model would search by meaning, not by substring. They took 13 models with claimed 128K+ tokens – and at 32K, eleven of them dropped below half their quality on short context. And 32K is less than what an agent picks up in a couple of minutes of grep reading.

  • CrossCodeEval – Researchers from AWS AI Labs and Columbia University (NeurIPS 2023) created a code completion benchmark where correctly completing a line is impossible without knowing adjacent files, and compared models with and without context. Without cross-file context, even strong models fail; adding fragments from other files found by the retriever to the prompt significantly increases accuracy. A telling detail: the simplest baseline in their retriever comparison is BM25, i.e., full keyword search.

  • Better Call Grep – A more recent work (ISSTA 2026), published three years after CrossCodeEval. Its result is real: on the same CrossCodeEval, grep search outperformed RAG on BM25 – 38.6% exact matches versus 25.0% for Python and 41.7% versus 29.6% for Java. But the conclusion "grep makes RAG and graphs unnecessary" does not follow from it, and the issue is with the methodology. The main thing is that the work measures repository-level code completion, not repository understanding or agent development; these are fundamentally different tasks. Moreover, the benchmark significantly favors grep: CrossCodeEval selects lines that use a name from another file, the import of this name remains in the code above the cursor, and the model writes queries to ripgrep precisely based on this code. Grep finds what is already named two steps from the cursor. Where there is no name, the authors themselves note failures: common words like init, config, and run drown in irrelevant matches, and implicit connections like inheritance are not found. Searching for a place by task description, navigation, and issue resolution is completely absent in the work – and the first problem from my list is exactly about this: the ticket contains not a single name from the code.

  • Own measurement. At one stage of testing the tool, I encountered a working task of finding and fixing a bug, and decided to "find the bug" in two ways – with TeaRAGs and without. In both cases, the input was the same ticket: a textual description of the symptom, without a single detail about the code – no class name, no file, no stack trace. With plain grep, the agent searched for the cause for 10+ minutes, with TeaRAGs the search along with report generation took only 40 seconds.

  • Claude Code has an answer for this, and not just one. Anthropic itself does not abandon RAG: in Claude Projects, it is enabled selectively – when project knowledge reaches the limit of the context window, Claude retrieves what is needed by searching the project database, rather than loading it entirely (RAG for projects). And for large codebases, Claude Code documentation directly advises: if your organization already has code search or a RAG index, connect it as an MCP server so Claude can access it instead of reading files sequentially (Set up Claude Code in a monorepo or large codebase). If such an index does not exist, the built-in answer remains – Explore: a separate sub-agent that runs grep itself and returns a short summary to the main agent. And here's why this doesn't help: the sub-agent has the same context window and the same degradation on long input – it's just not visible now. The summary it provides is its guess about what is important; if it's wrong, the main agent launches it again. And again. Ten minutes from my measurement above is sequential launches, not the actual grep time: it works in seconds. An external measurement says the same – grepai ran the same five questions on Excalidraw (155K lines of TypeScript, January 2026): the agent with grep launched five sub-agents and made 139 tool calls, the agent with the semantic index – zero sub-agents and 62 calls; fresh input tokens 51,147 vs 1,326, tokens for cache creation 563,883 vs 162,289, cost $6.78 vs $4.92. The sub-agent only decides where to put the dirt. I wanted a tool to eliminate dirt altogether – or at least significantly reduce it.

It is precisely this problem that semantic search solves.

2. Indexing takes hours – the industry considers the index expensive

A code index is an expensive thing, and the industry knows it: some giants have abandoned it, others have moved it to their own cloud. It's expensive, however, for a "one-size-fits-all" vendor – not for a team indexing its own monolith.

  • The RAG Obituary – Nicolas Bustamante (2025) wrote an obituary for RAG that hit the Hacker News front page: the thesis is that agents like Claude Code don't retrieve fragments but investigate – by parallel grep and file reading – and RAG remains a crutch of the era of small contexts (yes, yes, especially for legacy monoliths of three and a half million lines). Anthropic indeed doesn't build indexes, and their reasons are understandable: embeddings for millions of third-party codebases, their freshness, and hosting third-party code at fleet scale.

  • How Cody understands your codebase – Sourcegraph (2024) explained how context is structured in Cody, and incidentally reported that they are abandoning embeddings – "leaving embeddings behind (for now)". They stated the reasons directly: to build embeddings, all code had to be sent to a third party – OpenAI, whose model they used – and clients, to put it mildly, did not like their code going there; creating and updating embeddings added complexity for administrators; and finally, the vector database grows with the code, and searching it for organizations with hundreds of thousands of repositories turned out to be too expensive – so much so that it hindered creating multi-repository context. They replaced it with their own keyword search, which doesn't send code anywhere.

  • Cursor: Security – Cursor indexes the codebase by default and entirely on its own: files go to their servers, are chunked there, and turned into embeddings stored in a cloud vector database (Turbopuffer); the source code itself is not stored – only embeddings and obfuscated metadata. The cost of the index, however, has not disappeared – it is simply embedded in the subscription.

  • JetBrains Context – JetBrains (July 2026) released a semantic repository index for code agents and addressed the cost in the same way: the index lives in their cloud on GCP.

  • Own experience – embeddings consume 92% of the wall time for a full index, and there are two reasons for this. First: I experienced firsthand that building an optimized indexing pipeline takes months of work and good parallel programming skills; in general, it's not a simple task. Second, and most importantly: the throughput of a built-in or home graphics card – it sets the ceiling, no matter how many parallel embedding requests are sent.

Time to a ready semantic index – embeddings only; git enrichment and graph are counted separately, in the background. The same repository, the same hardware; author's measurements – January 2026 (fork, RooCode) and July 2026 (TeaRAGs). The 4–10 hour spread for the fork is due to different engine parameter combinations, possibly different embedding models, and non-idempotent runs: each restart gave a different time, not matching the previous one. The 22 minutes of TeaRAGs on the diagram is a bare MacBook and embeddings only; the same 22 minutes in the text below is a full run including the graph, but on an external GPU: numbers match, not magnitudes.

3. Ruby is supported nominally – and not for nothing

Ruby is a blind spot in this area, and the reason is not the laziness of tool developers, but the language itself: half of the calls exist only at runtime, and the other half are written in DSL.

  • Code localization graph benchmarks – RepoGraph, LocAgent (links in point 5) – are built on Python repositories. Ruby in agent benchmarks appears only in the form of tasks "fix the entire issue" (SWE-bench Multilingual), and I haven't found any public measurement of what proportion of calls a static graph resolves in Rails.

  • Language semantics: method_missing, send(verb) with a variable instead of a literal, define_method("#{x}") leave no edge in the AST – no parser can extract them from there. This is a property of Ruby, not someone's laziness.

  • Rails-DSL and the DSL of every second gem – has_many, scope, delegate, validates, page(2).per(20) – calls that are not present in the AST as calls. It's the language where building an honest call graph is most difficult.
