For twenty years, we've been explaining one simple truth to developers:

"Never install an unknown dependency from the internet. Are you even aware that you just ran npm install and downloaded unverified executable code from some random guy named Vasya with an account created 3 weeks ago?"

We implemented Software Composition Analysis (SCA) and SBOMs, built software supply chain security, read reports from Sonatype, Snyk, and Chainguard, conducted workshops and conferences, and wrote articles. We fought to make developers think before adding a dubious dependency – and this fight was brilliantly nullified by people who one day said, "What if ChatGPT wrote the code instead of the developer?"

And who ended up being the main vector for supply chain attacks? Not an APT group, nor an attacker who spent a year planning an operation. The biggest breach in the supply chain was diligently and absolutely altruistically dug for us by an ordinary LLM.

It is from this characteristic of large language models that the term Slopsquatting was born.

Let's Start With Terminology

The word Slopsquatting is formed from two parts:

  1. Slop — "sludge, swill." This is precisely how the renowned British AI researcher Simon Willison proposed to call all the monotonous, forced, fake content that LLMs churn out in batches. Since then, the term AI-slop has firmly established itself on the English-speaking internet.

  2. Squatting — from "to squat," in this context meaning "to seize." Typosquatting (domain squatting by typo), Packagesquatting, Dependency Confusion. The classic scenario: you register something very similar to the real thing, hoping the victim will make a mistake.

Slopsquatting is when you anticipate what non-existent library name an optimistic LLM will invent for another trusting developer – and publish it first.

And the LLM, so eager to be helpful, is forced to lie: it hallucinates names of Python, npm, Go, and Rust packages, proudly suggests importing them – and these packages have never existed in the registry. And if some attacker registers this fabricated name in advance, then congratulations, they've just orchestrated a ready-made supply chain attack.

Moreover, it attacks the LLM itself. Or rather, the developers who mindlessly copy-paste its answers.

The Main Problem with LLMs: Pathological Helpfulness Syndrome

Anyone who has seriously used ChatGPT, Claude, Gemini, Cursor, Cline, or RooCode has encountered this sooner or later. You ask it:

"Write me a simple CSV parser in Python, use an optimal solution."

The LLM proudly gives you code:

import csv_utils
from fastcsv_parser import parse_csv

...

You look at them and think: "Wow, what interesting libraries, I don't even know them."

It is this thought that should immediately raise a red flag. But no – seeing that the machine quickly generated ready-to-use code, instead of engaging critical thinking, we run pip install csv_utils fastcsv_parser.

And that's where everything breaks.

The problem is that LLMs don't have access to PyPI/npm/GitHub at the time of generation (and even when they have tools, they often are too lazy to use them). Instead of saying, "Sorry, I don't know a suitable library, I'll suggest an implementation in pure Python," it acts as it was trained from childhood with RLHF.

It must help. And for the sake of this help, it will invent a non-existent library with a very plausible name, and confidently justify why it should be used.

Who Even Came Up With This?

The term itself appeared in April 2025. It was coined by Seth Larson, who is responsible for security at the Python Software Foundation, and it gained traction thanks to a post by Andrew Nesbitt, the author of the service Ecosyste.ms. Within days, Socket, Kaspersky Lab, and other cybersecurity companies wrote about slopsquatting.

Science also got involved: a study on fabricated packages, which we will return to below, received the best paper award at the USENIX Security 2025 conference.

To be fair, the idea itself is older than the term. Back in 2023, researcher Bar Lando began studying how models invent packages and noticed that they persistently recommended huggingface-cli – a package that doesn't exist (the actual tool is installed via huggingface_hub[cli]). He registered a dummy package with this name, and in three months it was downloaded over 30,000 times. The installation command even made it into the README of one of Alibaba's repositories. Here's the first practical example – more than a year before the term appeared.

And How Many Fictional Packages Does AI Produce?

The short answer: a lot, a lot. The research speaks for itself.

The most extensive study to date is the academic paper "We Have a Package for You! A Comprehensive Analysis of Package Hallucinations by Code Generating LLMs" (Spracklen et al., USENIX Security 2025, arXiv:2406.10279). Researchers tested 16 code generation models – from GPT-4 to CodeLlama and DeepSeek – and generated 576,000 code samples in Python and JavaScript. The results:

This means approximately one in five recommended packages is fabricated. And if you use an open-source model, the chances increase to one in four or five. A "wonderful" result for a tool that millions of people use daily in development.

But what's more interesting is the stability of these hallucinations. Researchers tested 500 prompts that caused fabrications and ran each 10 times. It turned out:

  • 43% of hallucinations were repeated in all 10 iterations of the same model;

  • 58% were repeated at least twice out of ten;

  • 39% were not repeated at all.

This stability is crucial for an attacker: if a model consistently invents the same name, it can be registered in advance, and they can wait for a trusting developer to install the package.

However, the myth of "collective hallucination" needs to be debunked. 81% of unique fictional names appeared in only one out of the 16 models. This means models mostly invent different packages, not hallucinate the same libraries. There are overlaps between models, but it's more of an exception than a rule. Nevertheless, one stable name from one popular model is enough for an attacker.

Let's Conduct a Small PoC

Since Habr loves experiments, it would be a shame not to test this ourselves.

I asked a couple of models a maximally innocent question:

"Write Python code to work with the CIE LCH color space. Suggest an optimal library, provide the pip install command, and a ready-to-use example."

Let's see how these assistants will deceive me now.

ChatGPT (o3)

It thought for 8 seconds and gave:

pip install colorio colormath cie-lch-utils

And immediately code with imports from cie_lch_utils import ...

colorio actually exists, colormath exists, but cie-lch-utils has never existed on PyPI. ChatGPT just invented it.

Claude Sonnet 4.5

It was more cautious:

pip install colourscie

Then it wrote: "I recommend using the colourscie library, it's excellent for working with CIE LCH..." Unfortunately, such a library does not exist.

Gemini 2.5 Pro

It went all out:

pip install pyciecolor lch-parser

Both packages are fictional.

DeepSeek V3.1

It produced a whole stack of hallucinations:

pip install ciecolor color-space-utils pylch

All three are products of a vivid imagination.

Cursor (Claude in IDE)

The most dangerous option. It doesn't suggest at all; it immediately writes code with a non-existent import, assuming the developer will go and install it.

Conclusion of My Tiny Experiment

5 out of 5 tested LLMs, with an unperturbed face, advised me to install 1 to 3 non-existent Python packages. And all of them wrote this with such confidence as if they had been developing these libraries for 20 years.

Note for meticulous readers: I personally double-checked all the names from this experiment on PyPI before publication. colorio and colormath exist; the other seven (cie-lch-utils, colourscie, pyciecolor, lch-parser, ciecolor, color-space-utils, pylch) do not.

Now Let's Imagine an Attacker

Imagine a not-so-scrupulous person who, instead of trying to break CI/CD, IDS, EDR, and other defenses, simply sits down and thinks:

"Wouldn't it be easier to publish these packages myself first?"

The scheme is extremely simple:

  1. Take a popular LLM (or 5-10 at once).

  2. Generate 50-100 thousand typical developer requests: "write X in Y, suggest a library."

  3. Collect all non-existent names.

  4. Filter out those that are consistently repeated by a single model (the USENIX study showed: 43% of hallucinations are reproducible in 10 out of 10 runs).

  5. Publish dummy packages (or packages with a completely harmless useful function) on PyPI/npm/Gem/Pub/Go under these names.

And trusting developers will install these packages themselves, often in CI/CD, in Docker images, in production.

I remind you, the dummy package huggingface-cli, mentioned above, without any promotion, gained over 30,000 downloads in three months – simply because LLMs consistently recommended it.

An Interesting Fact That's Unsettling

In the USENIX study alone, models generated over 205,000 unique fictional package names. And this is from 576,000 code samples. Now multiply that by millions of developers who use LLMs daily in Cursor, Copilot, and ChatGPT. The scale of the "parallel universe" of fictional libraries is simply monstrous.

Most of these names will never be published. But it's enough to publish the right "AI hallucination" in a public registry just once – and you can get a flood of downloads a few months later, when the next wave of newcomers, asking the LLM the same question, receives exactly the same fabricated name.

Why It Works

Because the modern workflow for a huge number of developers now looks something like this:

  1. Open Cursor/RooCode.

  2. Type: "Do this task for me."

  3. Accept everything the AI generated without looking.

  4. npm i / pip install from what it suggested.

  5. Run.

  6. If it works – commit to main.

This is not a joke. Laziness, haste, deadlines, vibe-coding, and total faith in AGI have done their dirty work. Developers have created the perfect ecosystem for Slopsquatting attacks. And the cybersecurity community is the main victim in all of this.

How to Protect Against This Affliction?

Actually, protection is not difficult.

Never Trust LLMs on Faith Regarding Libraries

If an AI suggests pip install some-super-cool-ai-lib-xyz, the first question is not "how to use it?" but "does it even exist?"

Check PyPI/npm/GitHub. If there's no page – that's a red flag.

Zero Trust Principle (Suddenly)

The very Zero Trust that has been talked about so much. It must be applied to AI as well: never trust, always verify.

Ban on AI Dependencies Without Verification

Teams should adopt a strict rule: any dependency suggested by AI must undergo manual verification – existence, author, download count, freshness, repository activity.

MCP and Search Tools

You can force the model to first check packages via web search/tools. Some agents can already do this, but most still "hallucinate out of competitive spirit."

Good prompt protection:

"Never invent npm/PyPI/Go/Rust package names. If you need an external library – DO NOT invent its name, but tell me which existing library is best suited, with its exact name. If there is no suitable one – suggest a pure implementation, without fictional dependencies."

SCA + Package Monitoring

SCA scanners (OSV-Scanner, Socket, Semgrep Supply Chain, Dependabot) will partially help catch suspicious packages. But the problem is that a Slopsquatting package is initially new, without known vulnerabilities, from a regular account, so scanners won't notice it.

Be Paranoid – The Profession Demands It

The most important conclusion: AI is an extremely useful chatterbox that must never be left unsupervised when it makes recommendations on security, architecture, or dependencies.

The Most Terrifying Thought in the End

The scariest thing is not even that LLMs create a new attack vector, but that slopsquatting will work for years.

Because:

  • Every day, millions of juniors, interns, and procrastinating mids copy-paste code from ChatGPT/Cursor;

  • This code with fictional dependencies goes into GitHubs, tutorials, StackOverflow-like sites, training courses, YouTube;

  • The next LLMs, trained on this content (or simply seeing the patterns), will generate these same fabricated names even more confidently, solidifying them in their probabilistic model;

  • This creates a self-sustaining vicious cycle of hallucinations that will live its own life.

We have literally trained AI to lie, rewarded it for this lie (RLHF: be helpful, never refuse), and now this lie has begun to multiply.

Conclusion

Slopsquatting is a brilliant example of how good intentions, multiplied by human laziness, give birth to a perfect vulnerability.

All the years of work by the vast cybersecurity community in fostering a culture of Supply Chain Security have been nullified in one fell swoop by the enthusiasm for AI. The very AI that, in its eagerness to be helpful, has literally invented vectors of compromise for us.
