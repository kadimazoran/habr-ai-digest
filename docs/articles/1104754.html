In custom development, there are often cases where a project needed to be done yesterday, with tight resources and no available hands. Usually, the choice is limited: either refuse the order or move the deadlines. We became interested in whether it's possible in principle to tackle such an insurmountable task with a limited team by involving AI agents and building a meaningful process around them?

We decided to test this in an experiment: the two of us set out to build a complex automation system and set strict time limits. We handed over the coding entirely to the agents, keeping the task definition, control, and testing for ourselves.

In two months, we brought the product to the pilot stage and learned firsthand what agent development is truly worth. We want to share this experience. Below is how our process of working with agents is structured, the challenges we faced, and what this experiment taught us.

What we were building

Briefly about our "given." The task: to build a business process automation system with an integrated local LLM, external service integrations, and complex request processing logic. We are two engineers with relevant, but certainly not exhaustive, skills for a task of this scope. And the experiment condition: to complete this path with this team, without involving a full development team.

Building such a product from scratch would be not just bold, but very bold, so first we looked at what's already available in open source. We compiled a list of promising bases, filtered out those that didn't fit our capabilities or license, and deployed the finalists for a joint review. Ultimately, we settled on a project that provided a solid framework: a scenario editor and basic execution logic.

However, it didn't fully cover our initial concept. Many important functions either didn't work as we needed them to, or were dependent on the developers' cloud. We had to completely decouple the system from external cloud services, rebuild the internal logic for working with the local model, and set up interaction with external tools via MCP. Plus, we had to build a role-based access control system from scratch, without which the product couldn't be released into the real world.

These modifications, along with everything else that needed to be finalized, constituted the scope of work that couldn't be handled by two people. So, we armed ourselves with Codex and got to work.

Mechanics of working with agents

From the classic process, we only kept the initial meetings and basic git-flow. We gather, discuss what needs to be done, and outline the roadmap for the current stage. We don't have a traditional separation of front-end and back-end, so we divide tasks in half without regard to specialization. We don't interfere with each other. Each of us runs Codex locally, development happens in a personal folder on the server, and we push finished features to a shared dev branch in the old-fashioned way and merge them there.

We chose GPT-4.6 Sol for our work. While the model might be inferior to Opus 5.5 in some capabilities, it offers a significant advantage in price-performance ratio and allows for flexible adjustment of the reasoning level for different tasks.

It's understandable that no matter how capable an agent is, you can't just give it a command like "build me a wrapper for this." Well, you can, but then the agent will quickly fill up its context window, start compressing it and losing details, go back to re-reading files, overfill the context again, and so on, until all tokens are burned.

Therefore, we first describe what needs to be done and ask the agent to break the task down into small steps. Often, this results in a long list of a dozen items, each with 10-15 sub-items, and not all of them are sensible: the agent tends to over-cautious, adding redundant checks or including unnecessary steps. We challenge these questionable parts and ask for them to be removed until the plan is in a workable state. Essentially, the plan becomes a specification: before the first line of code, it's fixed what, in what order, and with what tools we will do it.

The same consideration for context saving determines the agent's operational algorithm. Everything it needs to know about the project and the progress is stored in files, structured so that the AI only takes what's necessary from them at each step.

It all starts with AGENTS.md, the agent's main file, which Codex loads at the beginning of each session. Since this file is always in the context, putting all documentation in it would be wasteful. Therefore, we put links to all other mini-documents in it: need project architecture? See this document. Need server information? Open this one. The documentation itself is not much different from what's maintained in classic development, just broken down into small files by topic.

Next, the agent opens the progress file. In it, it notes which point of the plan it stopped at and what it managed to do in the previous step, so it doesn't need to keep the entire history in memory. From here, it learns the number of the next item and loads it from the plan.

Then, the agent decides for itself if it has enough information. If a specific task requires understanding the server configuration or a service's API, it follows the link from AGENTS.md directly to the relevant document. After completing an item, the agent commits the changes, updates the progress file, and the cycle repeats with the next item.

How closely you need to monitor the agent depends primarily on deadlines and the task. The agent can either stop after each sub-item and check with a human, or work until the end of a block, bringing a finished result for review. And if time is really tight, you can loosen control almost completely, and the agent will work all night until deployment to the dev stand. In the worst case, if it turns out in the morning that it went down the wrong path, we'll simply roll back.

What we definitely don't risk delegating is testing. Theoretically, the agent could test the UI itself. To do this, it's enough to connect Playwright via MCP, and it will open a browser, click through the interface, and take screenshots. Each such run, of course, will consume a noticeable amount of tokens, but that's only half the problem.

The main issue is that the agent tests purely functionally. If a button doesn't click or does nothing, it will notice. But it might miss accompanying bugs: for example, the function works when clicked, but the button itself doesn't visually react, or an element is misaligned and looks crooked. A human notices such things immediately, even if not actively looking for them, so the coverage density of manual testing is still higher. It turns out to be both more reliable and faster.

Tokens remain the natural regulator of this entire mechanism. No matter how we try, they still run out periodically, and that's where having two of us comes in handy. When one runs out of quota, the other takes over the task. And thanks to progress tracking, it's enough for the colleague to point their agent to the working folder, and it will pick up from the right place. If both are out of tokens, work doesn't stop. There are always enough questions in the project that require good old-fashioned manual research: reading open sources, looking at successful implementations in other products, thinking about the layout of your own interface elements, or searching for information for future tasks.

The cost of the issue

Although we've structured the process intelligently, we won't idealize it. Agent development has a downside and its own price for all the possibilities it opens up.

The most painful part is losing knowledge of your project. When you write code yourself, over time you start navigating it almost with your eyes closed and can immediately name the module, and sometimes even the line, where what you need is happening. Here, the codebase is formed without your direct participation. We have a good understanding of what blocks the system consists of and what each is responsible for. But what exactly happens inside, for example, a specific module, we can no longer say offhand. Sometimes you even formulate the task for the agent less precisely than you could with full immersion in the code.

Second point: we cannot yet confidently assert that the internal code is written no worse than a team of humans would have done it. There haven't been large-scale tests yet, and we had to temporarily abandon intermediate code reviews and security audits for the sake of speed. Before a full launch, we will run the codebase through specialized agents and check for vulnerabilities, but at the current stage, we have to accept that there might be non-obvious surprises under the hood.

Estimating deadlines is a separate problem. A task that seems simple might take an agent a day, and the deadline can easily be multiplied by two or three. And sometimes it's the opposite: the agent quickly and on the first try delivers exactly what's needed. It's practically impossible to predict in advance which scenario will play out. For example, this happened with builds: at some point, the agent decided to make the process more reliable and started rebuilding the Docker image after every change to have a rollback point in case of issues. We noticed this when it spent about three hours on a minor fix, whereas it would have taken half an hour manually.

In general, the illusion that with the advent of agents, a developer can relax, shatters very quickly. There is indeed less manual work, but the freed-up energy now goes into management and constant control. If you don't oversee it, the agent might start being cunning or improvise on the task. For example, we are currently working on the role-based access control system. In the plan, there was another item: "create a new user by the administrator." The agent took it and reported completion, but upon review, it turned out that instead of directly creating an account, it implemented sending an email invitation for the user to register themselves. It certainly completed its task, and this feature will be useful in the future, but at that moment, something else was required.

As a result, the work turns into an endless stream of small interactions. Here you clarify, there you forbid, here you confirm, you log in in the evening or before bed to click a couple of buttons so that the task is ready by morning. Each such action takes at most a minute and seems trivial. However, because of these minute-long edits, working time is spread throughout the day, and the boundary between work and non-work gradually blurs.

Why it still works

Despite all the listed disadvantages, agent development has the main advantage for which we started all this: overall work speed. Individual tasks may take longer, but in total, we are moving noticeably faster than we would if we were two people working classically. This means we build the MVP faster, hand it over for pilot testing, and verify the hypothesis. And this verification is cheaper: it requires less effort and fewer people, so mistakes are not as costly.

Moreover, the barrier to entry into unfamiliar technologies is significantly lowered. It's clear that without basic development experience, you can't get anywhere. But with this foundation, you can dive into almost any language or framework with an agent without a long ramp-up. In our case: the open-source core of the product is written in JS, which is not our primary specialization. We could have learned it, of course, but it would have taken time. With agents, this stage is practically skipped, and they write particularly confidently in common languages with the most examples and documentation.

Speaking of related tasks. A separate discovery for us was how easily the agent handles layout and design issues. If you need to adapt the product to a company's corporate style, you can give the agent links to its resources and ask it to compile a brand book. Then, set the task: "You have the project and the brand book – bring the interface into compliance." The agent handles this from the first request and almost always without remarks.

And, of course, project economics, where would we be without it. Without agents, for this project, according to our estimates, we would have needed a front-end developer, two back-end developers, a tester, and a DevOps engineer. We are managing with two people and two Pro subscriptions at $200 each. Each subscription essentially replaces another person on the team but costs incomparably less. If we had one more, we could have agents working every night, not just when deadlines are tight, and things would have moved even faster.

What's the result?

The experiment is not yet over, and there is still plenty of work ahead. All the basic functionality of the system is already built and working, and we are finishing the role-based access control system. Since access rights affect almost all components, a thorough manual check awaits us. As soon as we merge these changes and fix minor related bugs, we will hand the build over to a staff tester, and then roll it out to employees within our company.

We are more anticipating than fearing the influx of real users. Under a load of a hundred or two people, something will likely break or not go according to plan, but there's no point in making a drama out of it. At the current stage, it's much more important to get live feedback and test the main hypothesis – will people use the product at all? If it turns out to be useless to anyone, then no amount of stability and security will save it. And the inevitable bugs and rough edges at the start are a normal working situation that we will address as feedback comes in.

Would we transfer this practice to the next project? If we were to start it tomorrow, at the concept and pilot stage – definitely yes. Further on, when it comes to production, we will still have to expand the staff: someone needs to check and validate the modules written by the agent. But there are projects where such an approach is unlikely to take root at all. For example, in the public sector or companies with strict security requirements, where a developer can be held accountable for every line of code.

Final conclusions can be drawn when we bring the service to a stable release. If we reach this goal faster and with fewer costs than a large development team would have, then the approach has paid off.

And if you are also considering development with AI agents and want to conduct a similar experiment in your company, here are a few tips:

  • Don't expect a magic wand. Simply opening the console and asking the agent to "make it beautiful" in one endless session might only work for a simple one-page site that takes a couple of days to build. Therefore, set up the process in advance, think through a detailed plan, prepare documentation, and decide what your final result should look like.

  • Don't let weak models handle development, and don't remove restrictions entirely. It's always better to leave potentially risky actions in the terminal for manual confirmation, and use only high-end, strong models for code. When we were still making mistakes on our test tasks before the project started, one of us ran a weaker model without command execution restrictions. At some point, the agent simply deleted the database and calmly reported: "I don't have backups, but there wasn't much data, so I decided you didn't need it." Such self-will would be too costly on a work project.

  • Budget for subscriptions with a buffer. If speed is important, don't skimp on them. It's not just about having more limits, meaning more agent work hours. A buffer is also needed as insurance against unexpected events like forced iterations or prolonged runs that consume more tokens than planned.
