What is AI Model Routing

A customer asks an online store assistant how to track an order. The answer is in one help article, so the request is directed to Mistral Small. Another customer reports that the item arrived damaged, money was debited twice, and the delivery address is incorrect. Here, the answer needs to be compiled from several materials, and the request is directed to Claude Sonnet. To the customer, it's the same assistant. But before answering, the system decides which model to assign the request to each time.

Model routing is the selection of the most suitable model for a specific task.

Routing is used when there is a fundamental difference between tasks. For example, in one case, the system needs to retrieve several document fragments, extract a short answer from them, and return it to the user. In another, it will require performing a complex sequence of actions, using multiple tools, analyzing intermediate results, and making decisions at each stage.

Different levels of models may be needed for these scenarios. A more complex model is usually needed where reasoning quality is important. A simpler one may be sufficient for a clearly formalized task.

In addition to quality, speed and cost must be considered. Models differ in size, computational resource requirements, token tariffs, and response times. Therefore, the choice comes down to finding an acceptable combination of quality, speed, and adequate price.

Manual and Automatic Routing

With manual routing, the developer predetermines which model should be used for a specific class of tasks. The decision is usually made either based on expert assessment or on the results of testing. For example, after checking several options, the team might decide that one type of request will always be processed by one model, and more complex tasks by another.

Automatic routing works differently. When a request arrives, the system analyzes its properties and selects a model right before performing the task. The choice is most often based on fixed rules. In a more complex scheme, a separate router is used – a component that determines which model is best suited for a specific request. Such a router can also be based on LLMs or classical classification models. In this scenario, the request first goes to the selection mechanism, and only then is it passed to the selected model.

Routing is Needed Not Only for Quality

The choice of model may also depend on the infrastructure situation. For example, the system accesses the model through a specific provider, but its service is unavailable for some reason. Then the request can be redirected to another provider if the same model is available there. If this is not possible, the system can choose another model with similar capabilities.

This approach can also be used for cost management. It happens that access to a certain model is available through different providers. Then the system can choose the provider with the most favorable cost.

It turns out that routing answers several questions at once: which model will best solve the task, how much the request will cost, how quickly the answer will arrive, and what to do if one of the available options stops working.

Why Use Multiple AI Models in Development

Imagine an autonomous development agent. It is tasked with adding an order status filter and bringing the change to a ready pull request. Before writing code, it is necessary to find out what statuses already exist, what orders the user is allowed to see, and how the filter should work with pagination. An error in these decisions will carry over to the specification, code, and tests. To research the project and prepare the specification, the team might choose a model designed for complex multi-step tasks, such as GPT-6 Astra.

Once the filter's behavior is defined, the agent breaks down the implementation into limited steps. Adding a parameter to an existing API according to a ready contract and tests for the listed scenarios can be entrusted to a more economical GPT-5.6 Terra. The result is checked by running tests and reviewing changes. This does not mean that writing code is always easier than analysis: an economical model is suitable only for those steps where it achieves the required quality.

If a contradiction in requirements is discovered during implementation, the change affects access rights, or retries fail verification, the task can be returned to a more powerful model. A similar principle was tested by the authors of SWE-Router, who chose a model considering what the agent learned about the task in the initial steps of work. Thus, the choice is not necessarily made once for the entire project and does not always follow the rule "one model writes specifications, another writes code": it depends on how much uncertainty remains in a specific step and how reliably the result can be verified.

Savings in such a scheme should be calculated based on the cost of the completed verified change, including retries, not just the token rate. This is how models were compared in the experiment by Arize and Fireworks. Sometimes a more expensive model will complete a complex task cheaper because it will require fewer corrections. At the same time, switching between models does not guarantee savings if failed attempts are too costly.

When Company Requirements Dictate Model Choice

An organization may have restrictions on transferring data to external services. For example, working with source code may only be allowed for models deployed within the corporate infrastructure. This is a common security requirement, especially in fintech.

However, external services can be used for less sensitive tasks. In this case, routing becomes part of the data access architecture. The choice of model depends not only on its capabilities but also on what data it is allowed to transmit.

For example, a fintech company needs to account for changes in customer identification requirements. An external model can be given published regulatory acts and asked to extract requirements relevant to the task with references to specific clauses. Then, an internal model will compare this summary with the company's source code and procedures and prepare the changes. The code and internal documents do not leave the corporate network.

Can Models Contradict Each Other

If multiple models are used in a system, their results may differ. Consider a scheme where one model performs a task, and another verifies its work. The verifying model may interpret the initial condition differently and return the first model's result for revision. Theoretically, this could repeat indefinitely. For example, in an experiment, Gemini solved tasks, and gpt-oss-20b verified its answers. The verifying model rejected the correct answer, among others, and returned it for revision.

Discrepancies do not necessarily arise because one model found an error in another. In a study analyzing public comments on a USDA rule, four models received the same comment and the same task: to determine if the author supports the proposed rule. Gemini classified the same text as objections, while GPT, Llama, and Mistral classified it as support. If one model is asked to draw a conclusion, and another to verify it using the same source, a dispute may arise at the text interpretation stage.

However, the problem is not necessarily related to using different models. A similar situation can occur with a single model if it receives different instructions for different roles. For example, in an experiment, an author and a critic worked on the same Llama 3.1 8B. In none of the 60 tasks did the critic's approval complete the cycle before the set limit of six rounds.

A separate case is autonomous systems where models act as agents and gain the ability to use tools and interact with the environment independently. In such conditions, their behavior becomes significantly more complex: agents can interact, compete, and conflict. For example, in a controlled experiment by Anthropic, three agents were given access to one Python backend, but each was tasked with porting it to its own programming language. Encountering each other's changes, the agents began to interfere with each other's work – to the point of blocking access to the server. Such scenarios belong to a separate class of autonomous systems, not ordinary request routing.

How to Start Building a Routing System

Learning about routing is best started with an overview of existing approaches: it helps to understand how choosing a model based on fixed rules differs from choosing based on request complexity or previous attempt results. Then, you can study open-source solutions and choose a platform or library where you can integrate a suitable router. Rules can be fixed, but the decision about the route can also be made by a separate model.

For a practical start, you can deploy your own routing gateway on LiteLLM, or if you don't want to maintain it yourself, you can use a ready-made SaaS service, such as OpenRouter with automatic model selection.

When Routing is Not Needed

Despite the broad capabilities of multi-model systems, routing is not always necessary. If technical and economic conditions allow the use of a single model for all tasks, it is worth checking this option first. In the LLMRouterBench study, several routers could not confidently outperform the single best model among those compared. This does not mean that routing is useless, but it shows that its advantages must be measured on your own tasks, considering the additional engineering effort to support the selection scheme.

If the need for multiple models is confirmed, it is worth looking for the simplest solution. Models are updated, new options appear, prices change, and the composition of available models changes. The authors of the overview of routing research specifically highlight router obsolescence: a scheme configured for a fixed set of models may stop working well when that set changes. Therefore, complex routing makes sense to build for a specific measurable problem and periodically re-compare with the option without it.

How to Test New Models Before Implementation

Implementing new models does not necessarily require redoing the entire system.

If the application architecture is stable, a new model can simply be substituted for the old one and tested on the same tasks. This requires a set of tests with a defined input and expected output. It is not critical whether a single model or a system of several components is being tested. The main thing is that there is a task, a result, and a criterion that allows evaluating the quality.

After that, different models can be run through the same set of tests. If the new model provides a higher quality result and its cost remains acceptable, the model can be implemented. If the improvements are minimal or the price is too high, it is better to postpone the model replacement. This scheme allows making decisions based on the specific results of the system's operation.

What's the Bottom Line

Model routing makes sense where different tasks truly require different tools.

For complex analysis, a more powerful model can be used; for large-scale generation, a cheaper and faster one. Separate models may only work with specific data types. A router, on the other hand, can consider cost, provider availability, and infrastructure limitations.

However, do not complicate the system from the outset. If one model solves the task with acceptable quality and cost, additional architecture is unnecessary.

If multiple models are indeed necessary, it is more beneficial to start with a simple scheme, limit model permissions according to the principle of least privilege, and test each change on a stable set of tests. This way, models can be changed as technology evolves without rebuilding the entire system from scratch each time.
