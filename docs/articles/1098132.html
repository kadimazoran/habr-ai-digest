One of the most frequent questions we get asked: how do we deploy large models on Cerebras wafer-scale chips? A single Cerebras WSE-3T wafer has 44GB of on-chip memory, and state-of-the-art models with trillions of parameters need terabytes just to store weights.

In this article, we explain how we distribute a large model across multiple WSE-3T wafers to run models with trillions of parameters at 1000-2000 tokens per second and higher.

As a concrete example, we'll use the open-source Kimi K3 model, which has about 3 trillion parameters.

By the end of this article, you will understand:

  • how we fit the entire model into the chips' on-chip memory;

  • how we distribute it across multiple chips;

  • how we handle a large number of concurrent requests.

Breaking it down with Kimi K3

Kimi K3 is an open-source model with 3 trillion parameters, 69 layers of linear attention, and 24 layers of full attention.

The model shows impressive results: 88.3% on Terminal-Bench 2.1 compared to 88.8% for GPT-5.6 Sol and 91.2% on BrowseComp compared to 90.4% for GPT-5.6 Sol. These results indicate a state-of-the-art capability in programming and agent tasks: in some benchmarks, the model even outperforms leading closed-source models. For our example, we'll assume the following conditions:

  • average prompt size of 256,000 tokens;

  • 4-bit quantization of weights, as in the Hugging Face implementation;

  • 8-bit KV cache.

1. Size of Each Layer

To determine how many Cerebras WSE-3T wafers are needed to run Kimi K3, we first calculate the size of each model layer.

Kimi K3 has 3 trillion parameters. Storing each parameter in 4-bit format results in a weight size of:

3 trillion parameters × 4 bits ÷ 8 bits per byte = 1.5 TB

Dividing this size by 93 layers:

1500 GB ÷ 93 ≈ 16 GB per layer

2. Number of Wafers

Now we know that each layer requires approximately 16 GB. This allows us to determine how many layers fit on a single wafer with 44 GB of memory. The answer depends on the layer type.

  • Full attention layers require additional space for the KV cache. Each such layer stores keys and values for every token of every active request. Therefore, we place one full attention layer per wafer and allocate the remaining SRAM for its KV cache.

  • Linear attention layers do not require additional space for the KV cache. Instead of storing keys and values for each token, a linear attention layer maintains a small, fixed-size state for each request—regardless of context length. This allows us to fit two linear attention layers per wafer: 2 × 16 GB = 32 GB.

Thus, for Kimi K3's 69 linear attention layers and 24 full attention layers, we get:

69 linear attention layers ÷ 2 layers per wafer, rounded up = 35 wafers

24 full attention layers ÷ 1 layer per wafer = 24 wafers

Total: 35 + 24 = 59 wafers.

3. Connecting the Wafers

Cerebras executes model computations in a pipelined fashion. First, the Cerebras compiler distributes the model layers across wafer regions, and then the runtime determines the path for tokens to travel between them. To ensure minimal latency, only activations are transferred between wafers. This can be achieved using RDMA over Ethernet. The latency is approximately 2 microseconds per hop.

It's important to emphasize here: since each Cerebras wafer has 44 GB of on-chip SRAM, and each layer occupies only 16 GB, we can typically place entire model layers directly on the chip.

This means that in most cases, model weights don't need to be moved at all, and layers don't need to be split across wafers. Only activations are transferred from one wafer to another.

4. How We Process a Single Request

Now that the wafers are connected and the model is distributed across them, each wafer can be thought of as a stage in an assembly line. The model weights at each stage remain in place, and the intermediate results of the request pass through a sequence of layers.

For example, the first wafer performs computations for layers 1-2 and sends the activations to the second wafer. The second wafer computes layers 3-4 and passes the results to the third, and so on, until the last wafer outputs the next token.

5. How We Process Many Requests

Here lies a common misconception. If a token must sequentially pass through each wafer, don't the other wafers sit idle waiting for their turn? Doesn't this mean the system effectively operates with a batch size of one?

No! If we were to send only one request through the pipeline and wait for it to complete before starting the next, the pipeline would be used inefficiently. Instead, we continuously fill it with different requests. The model is already broken down into stages, so each stage can work on its own request simultaneously.

While the third stage is processing a token for request A, the second stage is processing a token for request B, and the first stage is processing a token for request C. In our example, a single layer corresponds to one stage. In actual operation, Cerebras uses much finer-grained stages, and there are significantly more of them.

Each stage can also process a micro-batch—a small group of requests instead of just one. Therefore, the number of requests being processed concurrently is approximately the number of stages multiplied by the micro-batch size.

The trade-off is as follows: smaller micro-batches speed up the processing of each individual request, while larger ones increase overall throughput.

6. How Many Requests Can We Process

The maximum number of concurrent requests is determined by the amount of on-chip memory allocated for the KV cache. Each request in progress requires its own KV cache on each wafer with a full attention layer. Therefore, the amount of memory on the chips sets an upper limit on the number of concurrent requests. As explained above, KV cache requirements only need to be calculated for full attention layers.

For each 44 GB wafer, which already hosts one full attention layer, the remaining space for the KV cache is calculated as: total wafer memory minus the size of one full attention layer. In our case:

44 GB - 16 GB = 28 GB

Calculating the Number of Concurrent Requests

To determine how many concurrent requests a specific model placement scheme supports, we first calculate how much cache a single request of 256,000 tokens occupies:

Cache size for one sequence on one layer = bytes stored per token for that layer × context length

576 bytes × 256,000 ≈ 147 MB per sequence

Then, we divide the available cache memory by the cache size of a single request:

28 GB ÷ 147 MB ≈ 190 concurrent requests

The total number of concurrent requests is the number of requests that are passing through the pipeline at any given moment. Unlike GPU batching, these requests do not wait for each other to complete: they continuously flow through the pipeline.

Of course, neither the number of concurrent requests nor the batch size alone indicates how efficiently an inference system is performing. When evaluating its throughput, a more meaningful metric is the total token generation speed per unit of power, for example, tokens per second per megawatt, with the same generation speed for an individual request.

How This Approach Scales to Models Larger Than 3 Trillion Parameters

The same approach applies to larger models: calculate the memory required for weights and request states, distribute the model across wafers, and connect them in a pipeline. Each additional wafer adds compute resources and on-chip memory. This allows us to run models that do not fit on a single chip.
