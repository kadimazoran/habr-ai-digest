Let me try to explain. A fat harness surrounds the model with a software loop and takes on most of the work behind the scenes: request routing, context gathering, permission checking, scenario execution, long-term state, and result verification.

Unlike a fat harness, in a thin harness, the loop can mainly pass messages and provide tools, and then the model itself decides how to proceed. In a fat harness, the application additionally defines which operations are supported, how they are executed, and where they should stop for verification or confirmation. The model itself is primarily needed for understanding human text and choosing the appropriate solution path, but it does not become the sole source of truth. The harness makes some decisions: it receives the product state through code and applies rules that cannot be reliably ensured by text instructions alone. And where it doesn't decide itself, it prompts the model on where to go next.

The software loop of a fat harness allows explicit definition of constraints, testing them, and separating the model's suggestion from actual data changes. To avoid being unsubstantiated, let's consider a specific case: the model recognizes the intent and fills in the parameters, and the application selects a registered operation or a ready-made workflow.

Simplified diagram of user request processing

When a user simply sends a message within the harness and waits for a response, their message is processed according to the following program.

User → request normalization → event/exact/semantic routing → intent and parameters → context requirements → capability → workflow → policy and approval → tool → verifier and audit

User → request normalization

  • What happens: Raw human input (text, voice, or button press) is cleaned and prepared for analysis.

  • Essence: Typos are corrected, extraneous "noise" (greetings, emojis, if they interfere) is removed, and the text is converted to a uniform case. If it's voice, it's converted to text (Speech-to-Text).

2. Event / Exact / Semantic routing

  • What happens: The system decides which "brain center" to give the request to. Three levels of logic are used:

    • Event: Reaction to system triggers (e.g., user pressed the "Exit" button).

    • Exact: Search by hard rules or regular expressions (e.g., if /help is written, help opens immediately).

    • Semantic: Analysis of meaning using an LLM if the user writes in their own words (e.g., "Listen, transfer a hundred to Sanya").

3. Intent and parameters

  • What happens: From the understood meaning, the goal (Intent) and variables (Parameters / Entities) for its execution are extracted.

  • Example:

    • Intent: send_money (transfer money).

    • Parameters: amount = 100, recipient = "Sanya".

4. Context requirements

  • What happens: The system determines what data it is missing to fulfill this intent and requests it from session memory or databases.

  • Example: To transfer money to Sanya, the agent needs to know: Who is Sanya? (his ID or phone number) and Does the current user have 100 rubles in their account?

5. Capability

  • What happens: Checking if this agent can handle such a task in principle.

  • Essence: The system matches the Intent with its list of modules and plugins. If the agent doesn't have a banking plugin, it will honestly say at this stage: "I cannot transfer money".

6. Workflow

  • What happens: A step-by-step plan (graph) for task execution is built.

  • Essence: For simple tasks, it's one step. For complex ones, it's a chain of actions. For example: [Block amount] -> [Send request to bank] -> [Wait for response] -> [Deduct amount].

7. Policy and Approval

  • What happens: Checking the operation for legality and security (Guardrails).

  • Essence:

    • Policy: Limits are checked (is the user trying to transfer more than allowed?) and access rights.

    • Approval: If the operation is critical (money withdrawal, data deletion), the workflow pauses, and a button appears on the user's screen: "Do you confirm the transfer of 100 rubles to Sanya?".

8. Tool

  • What happens: Direct execution of the action in the external world.

  • Essence: The agent calls a software function (API, database, external utility, or calculator). In our example, a real API request is made to the banking gateway to conduct the transaction.

9. Verifier and Audit

  • What happens: Final quality control and logging.

  • Essence:

    • Verifier: The system checks the response from the tool. (Did the bank really return a Success status? Did an error occur? Did the neural network output nonsense?).

    • Audit: The fact of a successful (or unsuccessful) action is recorded in an immutable log (audit database). This is necessary for security, incident analysis, and for the agent to remember this experience in subsequent steps.

Intent is everything

A fat harness almost always starts with an intent. It answers the local question: what action does the user want to initiate. The model has a list of intents, and when it hits the semantic route, it must choose one of the paths by which the message will be processed. It doesn't have to describe the entire plan. Parameters and composite behavior should live separately.

Intent is a formalized representation of what the user wants to achieve in the application.

The user expresses their desire in ordinary words, and the application transforms it into a goal understandable by the system, which can be verified, matched with available capabilities, and passed for execution.

For example, the user writes:

"Check if the project has enough money for two MON-24 monitors, and if it does, prepare the order."

The system needs to determine not just the words "project," "monitors," and "order," but the meaning of the request:

● Goal: prepare a purchase order.

● Object: two MON-24 monitors for a specific project.

● Prerequisite: check available budget.

● Execution condition: prepare the order only if the budget is sufficient.

● Constraint: do not make the purchase without user confirmation.

As a result, the free-form wording is converted into a structured task description.

Users can phrase the same goal in different ways:

In the first three cases, the phrasing is different, but the goal is the same – to get budget information.

Thus, intent describes not a specific phrase, but the meaning of the action the user wants to perform.

Intent itself is not a function or a workflow

Intent answers the question "What does the user want?", and workflow answers "How should the system achieve it?".

For example: INTENT

prepare_purchase_order

Prepare purchase if budget allows

WORKFLOW

  • Get project budget

  • Get monitor prices

  • Compare sum with budget

  • Prepare draft order

RESULT

Draft order or explanation why it was not prepared. Note that one intent can trigger multiple operations. Conversely, one operation can be used to implement different intents.

What to do if the user requests multiple actions.

Not every request can be correctly expressed by a single simple intent.

For example: "Show the remaining budget, find three suitable monitors, and prepare an order for the cheapest one if the budget allows." This involves three interconnected goals: getting the budget, selecting products, and preparing the order.

There are two common approaches: First, a composite intent. A high-level goal, prepare_budget_constrained_purchase, is created, for which a workflow with the necessary steps is defined.

Second, multiple intents with dependencies. The system identifies get_project_budget, find_products, prepare_purchase_order and preserves the order, constraints, and transition conditions.

The choice depends on the application architecture. The main thing is not to lose the dependencies between actions and not to turn a conditional request into an unconditional one.

How the system determines intent

Various sources are possible:

● Event: the user clicked the "Create Order" button, so the intent type is known from the interface event.

● Exact: the command /budget project_42 matches a registered rule.

● Semantic: the LLM analyzes free text and suggests a suitable intent from the allowed catalog.

During semantic routing, the model can make mistakes, so its result cannot be automatically considered a correct or allowed command.

After determining the intent, the server checks if such an intent exists, if the parameter structure matches the schema, if the specified objects are available, and if the user is allowed the requested action. If important parameters are missing or the intent is ambiguous, the system clarifies the request or chooses a safe scenario without irreversible actions.

A good intent is project_report or purchase_order.
