How an AI agent sees a page. The observation contract between a browser and a model

An AI agent might err not because of the model itself, but due to how the browser describes the interface to it. A user opens a delivery form and sees a city field, a list of pickup points, a map, and a "Continue" button. The browser agent receives the same task but reports that it cannot find a pickup point. Or it finds the button, clicks it, and the form is not submitted.

Typically, after such issues, one starts tweaking the prompt, the model, or the locators. However, the phrase "the agent doesn't see the element" doesn't fully describe the problem. First, it's necessary to determine exactly what the tool showed the model, how it designated the available targets, and what state it returned after the action.

The model does not see the web page directly. An interface exists between the browser and the model, which can be called the observation contract. It defines what representation of the page the model will receive, what part of the page it will cover, how an element will be linked to a subsequent action, when the observation will be updated, and by what data the agent will understand the result.

If this contract does not align with the task, a powerful model will confidently reason based on an incomplete or outdated picture.

Page, Observation, and Action

A browser maintains several representations of the interface simultaneously. The DOM describes the document nodes. The accessibility tree contains element roles, accessible names, states, and relationships. The rendered frame stores position, color, overlaps, and graphics.

These are not three formats of the same file. There is no complete one-to-one correspondence between them.

Chrome calls the accessibility tree a derivative of the DOM and explains that presentation nodes without semantic content may be excluded from it. The remaining nodes have roles like button and heading, and their names can be computed from content or ARIA attributes.

The W3C specification lists role, name, value, states, relationships, events, and accessible actions among the accessibility API data. How Chrome builds the accessibility tree, Core Accessibility API Mappings W3C.

The simplest agent loop looks like this:

  1. Control code reads the browser state and collects the observation.

  2. The model selects the next action.

  3. Control code executes it in the browser.

  4. The new state is again converted into an observation.

In practice, errors occur not only at the second step. The tool might fail to include a necessary element in the observation, link a command to the wrong target, execute it on an already changed interface, or return insufficient data to verify the result.

Therefore, it is useful to describe the observation contract with five parameters.

Two Real-World Contracts

The difference is clearly visible in the standard outlines of Playwright MCP and OpenAI Computer Use. This is not a comparison of model quality or an experimental result. Below, we compare the interfaces described in the official documentation.

Structured Playwright MCP Outline

Playwright MCP uses a snapshot of the accessibility tree by default, not pixel input. The browser_snapshot tool returns the current accessibility representation of the page. The snapshot can be limited by a selected element and depth, and coordinate bounding boxes for nodes can be added.

Actions receive a precise reference to an element from the snapshot or a unique selector. Screenshots are supported separately, and coordinate commands are included as an optional vision capability. README Playwright MCP.

In the current API, the Playwright ARIA snapshot is presented in YAML. It shows roles, accessible names, text, and some states.

The ai mode adds references like [ref=e2], and the depth and boxes parameters control the tree depth and element coordinates. locator.ariaSnapshot() Documentation, ARIA snapshots guide.

A simplified observation might look like this:

- heading "Select pickup point" [level=1] - textbox "City": Rostov-on-Don - region "Pickup point map" - button "Close map" [ref=e7] - button "Continue" [ref=e9]

This is an illustration of the documented format, not the result of running on a specific site.

For a typical form, this representation is convenient. The button name aria-label="Close map" is clearer to the model than a drawn cross. The textbox role immediately indicates how to interact with the field. The ref link connects the model's reasoning to the subsequent command.

The price of this certainty is dependence on the page's semantics. If a developer created a dropdown list from a clickable div but did not assign it a role, name, and state, the interface structure for the agent will be poorer than the visible page.

The content of a canvas also does not automatically transform into a set of meaningful markers. Furthermore, a full snapshot of a large application can occupy a significant portion of the context, so the observation scope and depth must be limited.

Visual OpenAI Computer Use Outline

In the built-in loop of OpenAI Computer Use, the model receives a screenshot of the current interface and returns structured actions, including click, scroll, type, key press, and drag. The control code executes the actions, takes a new screenshot, and passes it to the model.

The documentation explicitly describes this path as visual interaction. It also provides two other options: a custom harness with Playwright, Selenium, VNC, or MCP, and a code execution environment where images can be combined with DOM operations. OpenAI Computer Use Guide.

A screenshot preserves what the accessibility tree loses: geometry, relative positioning, graphics, map state, and a loading indicator overlaying a button. It is closer to what a human sees.

However, pixels do not contain an explicit object like "Continue button." The model needs to recognize the element, estimate its coordinates, and infer the interaction method. An icon without a label can be ambiguous, and a small coordinate error leads to clicking a neighboring element. After scrolling, animation, or scaling changes, old coordinates no longer describe the current frame.

How the Contract Breaks on a Single Form

Let's return to the delivery form. It's not necessary to run two agents to find potential gaps. It's sufficient to sequentially check in which representation each significant fact exists.

  1. Custom pickup point list. On the screen, it's a field with an arrow. In the DOM, it might be a div with an onclick handler, but in the accessibility tree, it remains without the combobox role, accessible name, and expanded state. A visual agent will recognize its similarity to a control. A structured agent will see the text but might not understand that it's interactive. Here, the representation parameter is violated.

  2. Map closing button. Only a cross is visible on the screen, but the markup contains aria-label="Close map". A structured snapshot gives the model the precise purpose. A visual agent has to interpret a symbolic sign. Here, the semantic channel is more informative than the image.

  3. Markers inside canvas. For the browser, this is a raster area unless the application provides separate accessible elements or an alternative description. A structured snapshot might show the map itself but not the coordinates and labels of the drawn points. A screenshot will preserve the markers and their relative positions. This requires a visual channel or a special application interface.

  4. Button under the loading indicator. The tree might still contain the "Continue" button, even though an opaque layer is superimposed on it. A screenshot will show the overlap. However, the correct solution is not just to enable vision. The action executor must verify that the element is indeed clickable, and the agent must receive the updated state after the attempt.

  5. List redraw after city selection. The snapshot, element reference, and coordinates are only correct for a specific page state. After DOM updates, scrolling, or animation, the previous target description may no longer match the interface. Here, it's not the representation that breaks, but the recency.

The last two cases are particularly important. Discussions about browser agents often boil down to choosing between a tree and an image, although the method of updating and verifying observations affects reliability no less.

Four Places to Look for Errors

When an agent misses the mark, the phrasing "the model failed" is too crude. It's more useful to divide the trajectory into four stages.

Stage

Diagnostic question

Symptom of the problem

Observation

Did the desired element or state even make it into the model's input?

The snapshot lacks the control; the frame doesn't show the required area

Interpretation

Did the model correctly understand the role and intent?

The element is present, but the wrong action method was chosen

Execution

Did the command reach the correct target in the current state?

Click intercepted, coordinates shifted, target changed

Verification

Is there evidence of achieving the result?

The command executed without error, but the page remained unchanged

For diagnostics, it's advisable to save not just the final model output. You need the observation before the action, the selected target, command parameters, and the observation after it. This makes it clear where the information was lost. Otherwise, an executor error can be mistaken for weak reasoning, and the absence of an element in the input might be treated with a new prompt.

How to Design Observations for Your Agent

There is no universal format, but there are several practical rules.

For forms, tables, navigation, and text operations, it's beneficial to start with a structured representation. It clearly conveys roles and names, allows targeting elements, and usually contains less visual noise. For maps, graphic editors, canvas, drag-and-drop, and tasks where position or overlap is important, a screenshot is needed.

A hybrid contract doesn't mean "pass both the full tree and a full-size screenshot after each step." This quickly inflates the context and leaves the model to resolve contradictions between channels.

It's more useful to route the observation: first get a compact structure, then request an image if there's a visual widget, an ambiguous target, or a failed action. On a large page, it's better to provide a selected subtree or search results rather than the entire interface.

After any action that could change the page's layout or content, the observation should be updated. For an important step, a verifiable success criterion must be defined in advance: an address appears in the final block, a modal window closes, the URL changes, an indicator disappears, the next button becomes available. The mere fact of sending a click command is not such a criterion.

Before implementation, it's useful to answer five questions in writing:

  1. What representation does the model receive for this type of task?

  2. How is the observation scope defined, and how does the agent expand it?

  3. How is the action target addressed?

  4. What events make the previous observation outdated?

  5. What data confirms success or requires recovery?

If the answers exist only within the code of a few tools, the contract is already in place, just implicitly. These are the contracts that are hardest to debug.

Where This Model Ends

The observation contract does not explain all browser agent errors. Even with complete and fresh input, the model might build an incorrect plan, forget a constraint, mishandle ambiguity, or violate confirmation policies. Authorization, protection against on-page instructions, sensitive actions, and recovery from network failures remain separate issues.

Furthermore, tool capabilities are evolving. Structured solutions are gaining coordinate and visual functions, while visual outlines are being supplemented with DOM and programmatic execution. Therefore, it's useful to evaluate not the product name, but the specific interface configuration between the browser and the model.

The main takeaway is simple. An AI agent sees not the page, but the observation collected for it by the tool.

Before adjusting the prompt, check the five parts of the contract:

  1. Representation.

  2. Scope

  3. Target binding.

  4. Recency.

  5. Feedback.
