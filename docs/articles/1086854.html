Imagine you're handed a system for support. It works—and works brilliantly: writes code, translates, reasons, jokes. No documentation. No source code. Just a binary of several hundred gigabytes and a log of how it was compiled. When asked "how does it work inside?" the team honestly shrugs.

This is roughly what LLMs look like today. We've learned to compile intelligence from data, but we haven't learned to write, or even properly read, its source code. All we have are weights: hundreds of billions of numbers where knowledge, skills, and algorithms are smeared.

This article is an attempt to pull on one thread and see where it leads. The thread is simple: how exactly does a neural network differ from a program? After a few steps, it unexpectedly leads to the question of AGI architecture and the hypothesis that strong AI might not only be trained but also searched for—as a program with readable code, explicit memory, and understandable modules.

Behavior is a Function. Just with Memory

Let's start with the most general framework. Any observable behavior—of a human, animal, or program—can be described as a mapping dependent on input and internal state:

(input, state) → (action, new state)

For humans, it's more natural to think not of a single static function but of a dynamic system with a vast number of interconnected processes and feedback loops:

Here, sₜ is the complete internal state, and xₜ is the input from the environment. Behavior over time is a trajectory s₀ → s₁ → s₂ → …

The existence of a trajectory doesn't mean it can be predicted far into the future: errors accumulate, and in chaotic systems, they grow exponentially. Therefore, "approximating behavior" is not about predicting a specific person's life thirty years in advance. It's about reproducing the mechanism F itself, which generates only plausible trajectories.

Neural Network and Program—Two Representations of the Same Thing

A trained neural network is simply a computable function. A regular program is also a function: from input and state to output and new state.

Mathematically, they are not opposites but two ways to represent computation. In one case, the structure is spread across weights; in the other, it's explicitly written: variables, branches, loops, subroutines.

This is where the universal approximation theorem is usually recalled: "a network can do anything." This isn't entirely true. The theorem concerns the approximation of certain classes of functions (e.g., continuous) over a bounded domain with a given accuracy. It doesn't claim that a single finite feed-forward network can precisely replace any program: a program can run indefinitely and use arbitrarily much memory, while a fixed-size network cannot.

However, if we limit the input, runtime, and memory of a program, its behavior becomes a finite mapping—and in principle, it can be reproduced by a sufficiently expressive model. The only question is the cost.

Parameters ≠ Complexity

The intuition "more parameters mean more complex behavior" is only partially correct. Computational complexity is also determined by recurrence and memory. A classic example is the Rule 110 cellular automaton. All its "learnable" content is eight bits, but when applied repeatedly, it becomes Turing-complete:

RULE = 110  # the entire "model" is 8 bits: 0b01101110def step(cells: list[int]) -> list[int]:    n = len(cells)    return [        (RULE >> (cells[i - 1] << 2 | cells[i] << 1 | cells[(i + 1) % n])) & 1        for i in range(n)    ]# 8 bits of rules + loop = Turing-complete system (M. Cook, 2004)

A small program, applied recursively many times, can generate arbitrarily complex behavior without a single new parameter. This leads to the question for which all this was initiated:

Could it be that a huge neural network uses billions of parameters mainly as a convenient search space, while the pattern it found has a much shorter algorithmic description?

For some tasks, the answer is yes, and there's a clear illustration. In the paper on grokking (Nanda et al., 2023), a single-layer transformer was trained on addition modulo 113. When the model, after a long memorization phase, suddenly began to generalize, it turned out to implement a specific algorithm: it encoded numbers using sines and cosines of several frequencies and added them via trigonometric identities—essentially, rotating a point on a circle. Hundreds of thousands of parameters, yet the algorithm itself is described by a couple of formulas.

The theoretical limit of compression is set by the algorithmic (Kolmogorov) complexity of the function itself. If the pattern is structural and repeatable, the network can be orders of magnitude larger than its minimal description. If the function is essentially random, it cannot be radically compressed without losing behavior—no method will help here.

Can We Extract a Program from Weights?

Tools that reduce or structure a learned function have existed for a long time. Broadly, they can be divided into two groups.

Compression—doing the same thing, but more compactly:

  • distillation—a large model teaches a small one to reproduce its behavior;

  • pruning—removing weights, neurons, or entire blocks with little contribution;

  • low-rank factorization—replacing large matrices with compact decompositions;

  • symbolic regression—finding an explicit mathematical formula from behavior;

  • program synthesis—finding a program that reproduces the observed mapping.

Understanding—mechanistic interpretability. Today, understanding modern AI models is more like experimental science than reverse engineering:

observation → hypothesis → intervention → measure effect → refine hypothesis

Mechanistic interpretability methods—in brief:

  • ablation—disable a component and see what stops working;

  • activation patching—transfer internal activations from one run to another;

  • causal tracing—locally restore "damaged" representations and find where information is actually stored;

  • feature steering—amplify or suppress found internal features;

  • sparse autoencoders—decompose dense activations into sparse, more interpretable features;

  • circuit analysis—find chains of components that jointly implement computation.

But there is no universal "neural network decompiler." Even when an automated method finds a stable internal structure, questions remain: what does it mean, and what causal role does it play? Interpretability today resembles neurobiology on silicon more than disassembling a binary.

What If We Search for a Program Directly?

The advantage of the approach is that the output consists of variables, branches, loops, and subroutines that can be read, tested, and edited manually. The disadvantage is obvious to anyone who has seen generated code: the code itself doesn't guarantee understandability. An automatically found program can easily turn into a kilometer-long spaghetti code. Therefore, the goal is not "any code" but a short, modular, and verifiable program.

Combinatorial Explosion

The main problem with program synthesis is the size of the search space. If a language has k allowed tokens, the number of programs of length n grows exponentially:

Even for a toy language with 20 tokens and programs 30 tokens long, this is about 10³⁹ possibilities. Neither current nor future GPUs can handle a full brute-force search. A directed search is needed:

  • evolutionary algorithms and genetic programming;

  • reinforcement learning;

  • Monte Carlo Tree Search and related tree search methods;

  • LLMs as generators of plausible mutations;

  • an automatic evaluator that runs a candidate and measures its quality.

Neural Network—Not the Destination?

Here, the analogy with AlphaZero is useful. The neural network in it doesn't play the game alone—it guides the tree search, suggesting which moves are worth considering. The system's strength lies in the combination of "trained heuristic + search."

A neural network can play exactly the same role in program search: not to be the solution, but to suggest where to dig. This is how FunSearch and AlphaEvolve from Google DeepMind work. Simplified, the loop looks like this:

FunSearch found new constructions for the cap set problem—a long-standing open problem in extremal combinatorics. AlphaEvolve found a way to multiply complex 4x4 matrices using 48 scalar multiplications, improving for the first time in this formulation the result derived from Strassen's algorithm of 1969. And its heuristic for scheduling tasks in Google's data centers, according to DeepMind, saves about 0.7% of the company's global computing resources on average.

The Main Idea: AGI as a Cognitive OS

Now we can move from the question "how to compress a neural network" to a bigger one. If the human brain is a complex but physical and systematic information processing machine, is it necessary to reproduce it with a single end-to-end network?

My working hypothesis is no. It might be more productive to systematize individual cognitive mechanisms and implement them as an interacting architecture. If some cognitive processes have a compact algorithmic structure, there's no reason to require that this entire structure be implicitly stored in the parameters of a single model.

Furthermore, human cognition involves processes that standard LLMs do not explicitly model:

  • biographical (episodic) memory—"what happened to me last Tuesday";

  • learning from a single episode without retraining the entire system;

  • consolidation—transforming experience into generalized knowledge;

  • stable goals that outlast a single context window;

  • continuous sensorimotor loop;

  • internal world model and long-term strategy change.

An important caveat to save time in the comments. I am not claiming that a transformer is "in principle incapable" of approximating these patterns. The claim is more precise: its standard computational organization does not provide these mechanisms with explicit architectural support. Everything has to be either implicitly learned in the weights or emulated through the context window and external crutches.

The alternative can be summarized in one line:

AGI ≈ cognitive OS + trainable specialized modules

Here, the neural network is not the entire system but one type of computational component. Much like a GPU in a computer: indispensable for its tasks, but not the operating system itself.

Translating this into code, the main loop of such a system might look something like this. This is not an implementation but a sketch of interfaces—to show where explicit logic resides and where neural networks are used:

class CognitiveOS:    """Explicit framework. Neural networks are only within individual modules."""    def step(self, observation):        percept = self.perception.encode(observation)     # neural network        recalled = self.episodic.recall(percept)          # explicit memory        self.workspace.update(percept, recalled,          # limited buffer                              self.goals.active())        plan = self.planner.search(self.world_model,      # search in world model                                   self.workspace.state())        action = self.executive.select(plan, confidence=self.meta.assess(plan))        self.episodic.store(percept, action)              # fast learning        return action    def sleep(self):        """Offline: replay and consolidation."""        for episode in self.episodic.replay():            self.semantic.consolidate(episode)            # slow learning            self.world_model.fit(episode)

Note the sleep() method: consolidation here is a separate offline process, not a side effect of learning. In an end-to-end model, such a process simply has no place to live.

"But These Are LLM Agents" and "This Has Been Done Before"

Two objections come to mind.

"So these are LLM agents with RAG and tools." It looks similar, but with an inversion of roles. In a typical agent, the LLM is the central processor, and memory and tools are attached to it from the side via prompts. Here, it's the opposite: the framework is an explicit architecture with its own long-term state, and neural networks are its coprocessors.

"Cognitive architectures already existed: SOAR, ACT-R, Global Workspace." They did—and largely hit two walls: fragile perception and manual design of every rule. Today, both walls are significantly lower: perception is handled by neural networks, and the "glue" between modules can be found automatically. The hypothesis is precisely that this combination can move the old idea forward.

Neuroscience Helps in the Search

There's no need to copy the brain literally: airplanes don't flap their wings, although they obey the same aerodynamics as birds. But neuroscience is useful as a source of a priori constraints for the search space. Judging by it, the system will likely benefit from:

  • fast and slow learning—in the spirit of the complementary learning systems theory, where the hippocampus quickly memorizes episodes, and the neocortex slowly extracts patterns;

  • separation of episodic and semantic memory;

  • limited working memory;

  • replay and consolidation;

  • models of future states;

  • priority and action selection systems;

  • meta-learning—changing strategy based on experience.

With such constraints, the automatic search doesn't explore "all possible programs" (remember 10³⁹) but a much narrower space: how components should interact, which memory update algorithms to use, and what signals to pass between modules.

Leading to Conclusions

Instead of approximating human cognition entirely with one large network, we can view the brain as a complex dynamic system, identify computational mechanisms within it, implement some of them explicitly, and use local neural network modules for unknown or high-dimensional transformations. Neuroscience provides the structure for the hypothesis space, while trainable and evolutionary search finds specific programs and interaction rules.

Ideally, the final system is not an opaque mass of weights but an explorable cognitive architecture with explicit states, memory, and algorithms. It can be debugged like software and studied like a brain—with ablations that are unthinkable on a living brain.

I would welcome criticism—especially from those working in program synthesis, cognitive architectures, or neuroscience.
