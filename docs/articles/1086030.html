Today, Small Language Models (SLMs) are increasingly in the spotlight: at first glance, they are almost as good as LLMs, while using significantly fewer resources.

But, as always, there's a catch (and not just one): we discuss whether SLMs are really that good, where they can be truly useful, and where they still struggle. We also explore why, in our opinion, they are unlikely to become serious competitors to LLMs anytime soon.

What are Small Models?

A Small Language Model (SLM) can range from a few million to 10 billion parameters. Models like Alibaba's Qwen3.5-0.8B and some from Google DeepMind's Gemma family, particularly those with 2 to 9 billion parameters, can be considered SLMs. Gemini also offers lighter variants like Nano-1 and Nano-2 with 1.8 billion and 3.25 billion parameters respectively, designed for smartphones and tablets — these can also be called SLMs.

Incidentally, the industry also uses a definition of SLM not tied to a specific number of parameters. For example, NVIDIA proposes classifying anything that can run on consumer electronic devices: personal computers or laptops, as small language models. This approach suggests that as the computing capabilities of personal devices grow, the boundaries between small and larger models will blur — and this is already happening. For instance, models with 14 billion parameters are now more often classified as "medium," yet Microsoft still calls its Phi-4 14B a small language model precisely because its quantized version can run on a single consumer graphics card.

Unsurprisingly, the ability to deploy a model on average hardware directly impacts the popularity of such solutions. According to Hugging Face's Summer Report, models with over 100 billion parameters account for only 1% of all downloads, while models with less than one billion account for about 83%. Typically, enthusiasts, researchers, and educational institutions turn to them. A notable example is the combination of three models with 3–7 billion parameters (Llama3.2-3B, Qwen2.5-7B, and Neural-Chat 7B) deployed at John Abbott College in Montreal. The system runs on a macOS server without high-end GPUs. It helps physics instructors grade student lab reports — for now, college specialists have limited themselves to prompt engineering, leaving model fine-tuning for the future.

However, even such fine-tuning can be relatively inexpensive, especially when using the LoRA method. This allows adapting a neural network to a specific style, response format, or subject area using an additional set of parameters. This approach requires significantly fewer computational resources than full model fine-tuning, enables rapid creation of different versions of the base neural network, and is quite cost-effective — in some cases, fine-tuning costs as little as eight dollars. This is particularly relevant for independent researchers and participants in university projects, who often have to operate with tight budgets.

Where SLMs Can Be Useful

Small models can be truly effective in highly specialized scenarios where speed is particularly important: for example, in call classification or spam filtering. However, much depends on the specific scenario of working with SLMs: it may require additional effort in terms of deployment and infrastructure. For example, when using a pipeline approach, where several models work sequentially, or an orchestrator approach:

The most likely scenario for small language models is their use in agent systems, where there is a central orchestrator brain that is given a task. And this brain, knowing the descriptions of specialized models, determines which task to assign to which model (one for classification, another for code correction, and so on).

It's not necessary for these to be different models from different vendors. I think it's a perfectly viable option to take the same base architecture, the same base model, and fine-tune it to get a family of specialized models. You can train its adapter using LoRA, for example, or train the entire model for a specific task. Obviously, full training is more expensive and resource-intensive than some LoRA adapters, but it yields higher quality results. Although in practice, a combined approach is likely best.

— Maxim Shkut, Data Scientist, VTB

There are other features worth considering when working with SLMs. For instance, they can be used without fine-tuning, leaving them in their original state, while all necessary specifics are moved to the "wrapper" — providing relevant materials in the context or connecting a local knowledge base. Here are a few scenarios where SLMs (with or without fine-tuning) can show good results:

1. Code Review and Code Unification

Data to "tune" a small model for refactoring and standardizing a codebase can be taken from a corporate repository, which effectively already contains labeled examples — commits show the code state "before" and "after." If ready-made data is insufficient, synthetic data can be generated. For example, NVIDIA fine-tuned Llama 3 8B Instruct using LoRA for internal code review, with training examples generated by a teacher model, GPT-4, using knowledge distillation. The accuracy of assessing the criticality of remarks by the fine-tuned model increased by more than 18%; the result was better than that of Llama 3 70B and Nemotron 4 340B Instruct, with lower cost and latency.

However, a number of studies show that open-weight SLMs can perform well in unifying and standardizing code even in their "raw" state — without fine-tuning. Researchers from Eötvös Loránd University in Hungary tested twelve models ranging from 0.5 to 8 billion parameters on three thousand Python programs from the APPS benchmark. The models were given a single, short instruction: refactor the program without using new libraries or modules. The results were evaluated based on unit tests and code quality metrics. After the edits, the number of PEP-8 violations decreased by 65–86%.

A similar experiment was conducted by researchers from Concordia University and Polytechnique Montréal in 2024. They noted that compact models are better at modifying existing code rather than writing new code from scratch — on these tasks, their performance can be comparable to LLMs. The researchers compared two open models with 7 billion parameters — CodeLlama and Llama 2 — with the results of ChatGPT 3.5 on two thousand program modification tasks. SLMs performed best on local changes: for example, renaming entities and formatting code according to project conventions.

2. Working with Databases

Here again, small models can perform well — but with limitations. The schema of a real database is usually too large to fit entirely into a prompt, so a method is needed to prune unnecessary tables and columns. This technique is called schema linking, and for small models with smaller context windows, it is more critical than for large ones.

However, there are cases where one can abandon the traditional Text-to-SQL approach and embed language model calls directly within SQL queries. A couple of months ago, specialists from the American fintech company Capital One conducted an experiment. They replaced a proprietary API with a local Gemma 4 E4B with FP8 weight quantization, running on a single RTX 5080 with 16 GB of VRAM. Using BlendSQL — a query language that combines standard SQL with language model calls — they managed to reduce operational costs by 390 times and latency by 3.8 times, with comparable response quality [for those interested in implementation details, the experiment code is available on GitHub under Apache 2.0].

3. Speculative Decoding

This is a method to speed up LLM performance, where a small, fast model predicts several subsequent tokens in advance, and the main, larger model verifies them. SLMs are particularly well-suited for the role of "predictor" because they are not required to guess every token flawlessly. Their task is to quickly and cheaply generate many probable options from which the larger model can choose a suitable one.

Typically, speculative decoding is used for tasks where inference speed is important: for example, in interactive programming systems that need to complete code almost instantly, or in machine translation. Today, speculative decoding is used in Google's AI Overviews.

However, it's worth noting that the balance between prediction quality and the cost of obtaining them is important here. In Google's experiments, where this approach was proposed, T5-large with 770 million parameters predicted tokens (obviously) more accurately than T5-small with 60 million: the main model accepted 82% of the tokens proposed to it, compared to 75% from T5-small. But T5-large itself ran about twice as slow. This means too small a "predictor" can save resources on generation but will make more mistakes, negating the benefit of speculative decoding. Too large a predictor, in turn, will guess tokens more accurately but will require more time and resources for the predictions themselves.

Overall, working with small language models is a story about constantly seeking a balance between speed, quality, and cost. As AI becomes more widespread, the cost of generation becomes critically important. When there are millions of requests, inference costs take center stage — and the trend towards cost reduction becomes decisive. In this logic, running specialized tasks on devices using small models is one of the natural and most probable paths for the industry's development. A local SLM processes a "narrow" task faster, cheaper, and without data leakage, and after deployment, the marginal cost of generation tends towards zero. Large LLMs can then be used for complex and creative tasks: it's not about replacing the approach, but about dividing the labor. Back in 2023, Nvidia CEO Jensen Huang stated that the future of language models would be hybrid, with models of different sizes handling different tasks. This is no longer a prediction but a reality, yet this approach is not without its limitations, primarily related to the intricacies of working with SLMs.

And a Few More Nuances

Despite all the obvious advantages of small models, they have a number of peculiarities.

Their Size Inevitably Affects Response Quality

In 2025, researchers from universities in the Netherlands, UK, and Czech Republic tested how accurately 15 different models could extract specialized medical information. The models were divided into four groups by parameter count: large — over 150 billion, medium — 40 to 150 billion, small — 4 to 40 billion, and miniature — less than 4 billion.

It's worth noting that the authors interpret the term "small model" much more broadly than usual; looking at the composition of this group, only one model out of three (DeepSeek R1 Qwen3 8B) falls within the 10 billion parameter limit. Their *miniature model* category better corresponds to the popular definition of SLM.

Regarding the experiment itself, model performance was evaluated on a scale from 0 to 1, where one meant complete agreement with the consensus labeling by professional doctors. Large, medium, and small models showed almost identical results — 0.78, 0.77, and 0.77 respectively. However, miniature models lagged significantly, scoring only 0.57. In other words, reducing model size begins to affect performance quality, which can be particularly evident when solving specialized tasks.

Increasing SLM Accuracy Is Not Always Possible, Even with Distillation

Researchers from the University of Washington, Carnegie Mellon University, and Western Washington University described an effect they termed the "small model learnability gap." According to their findings, models with 3 billion parameters or fewer (i.e., those the specialists from the previous study called "miniature") do not gain significant advantages from training on long reasoning chains or from distillation from large teacher models. To achieve good results, one must carefully select and combine different types of training data.

Finding Quality Datasets for SLM Training Can Be Difficult

Preparing them independently is also a non-trivial task. In February 2025, the Hugging Face team released SmolLM2 with 1.7 billion parameters — a versatile model additionally trained to work with code and mathematical formulas. To achieve this, the developers had to assemble three datasets: FineMath, Stack-Edu, and SmolTalk, as existing datasets were deemed either too small or of insufficient quality.

Given the complexity and duration of this experiment, it will be easier for many companies to use a suitable and sufficiently "smart" LLM rather than spending time and resources on data preparation, fine-tuning, and adapting a compact model. Routing Between Models Is Sometimes Inadvisable

“I don't use small models in production in my work; I mostly handle all tasks through large models, including Qwen. In general, using small models for narrow tasks like text classification is an interesting topic. But here's the next point that comes up.

On one hand, you can use a single large model for all requests. From an infrastructure perspective, everything is clear: one service, one place to maintain. But running some simple tasks through it might seem excessive. On the other hand, you can set up a separate small model — but then you'll also have to deploy, maintain, monitor, and update it. The load on the team effectively doubles.

And the question is: starting from what volume of such requests will routing between models become cost-effective and beneficial? I don't work on high-load systems with LLMs, so the question of when using routing between different models will pay off (or if it will pay off at all) is not trivial for me.”

— Maxim Shkut, Data Scientist, VTB

Our skepticism regarding routing is shared by scientists. Researchers from the Chinese Academy of Sciences in May 2025 conducted a systematic review of works dedicated to the joint use of large and small language models. They examined about two hundred studies and systematized the main interaction patterns between them. One of the main reasons to use SLMs is to reduce request processing latency. However, a slow router can negate this advantage. Furthermore, such an architecture is more complex to operate: you have to monitor several models and components separately, and if response quality drops, the culprit is not always obvious.

SLMs (Especially Open-Weight Ones) Are Vulnerable from an Information Security Perspective

It is often easier to remove built-in developer restrictions from them, meaning they are easier to force into performing undesirable operations. Moreover, the methods for "hacking" compact models are largely the same as for large LLMs. In May 2026, Financial Times journalists, along with researchers from the AI security group Alice, demonstrated that using the open-source tool Heretic, which implements the "abliteration" technique (a method of destructive weight modification), it's possible to remove restrictions in less than ten minutes. After modification, one of the Gemma 3 family models began answering questions about dispersing chlorine in an enclosed space and generated code for stealing bank card data.

Small Models Generate Less Public Hype Than Large LLMs

This is not a technical problem, but its consequences affect investments. Large businesses and IT companies primarily invest in infrastructure for large models, resulting in SLMs currently receiving fewer resources and development opportunities. Therefore, it's difficult to claim that "the future belongs to SLMs." Most likely, in the coming years, large and small models will not so much compete as be used for different types of tasks.

“I think the most realistic application area for small models is in narrow classification tasks where you need to save time, and where precision is much more important than recall. But, for the most part, there are few such tasks, and using large models is more cost-effective by metrics. LLMs can also be fine-tuned using an adapter for a specific task, which won't require as many resources as fine-tuning an entire model. And it will handle the narrow task much better than a small one, even if fine-tuned.”

— Andrey Sitnikov, Data Scientist, VTB
