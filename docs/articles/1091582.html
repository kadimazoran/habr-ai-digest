Let's Agree on Terms First

There isn't a single, universally agreed-upon definition for "agent" and "harness" yet. For this article, I'll define them as follows:

  • Agent — The core that orchestrates work with the model, processes its responses, calls tools, and decides whether to continue the loop.

  • Harness — Everything surrounding this core that helps it function within a specific product: the user interface, settings, data, tools, MCP connections, skills, memory, and integrations.

  • Model — A separate system that performs inference and returns tokens. It doesn't become an agent just because it can answer questions.

The agent is in the center, the harness surrounds it, and the model is a separate participant. This is a simplified diagram, but useful for our discussion.

Even in this diagram, several independent components are hidden. The executable code of the agent can be thought of as a stateless process: it receives input, executes logic, and shouldn't expect its operational memory to persist indefinitely. There's an environment where this process gets CPU and RAM. There's a separate persistent storage for conversations, files, images, and user settings. There are external APIs the agent interacts with.

And if we're building an enterprise product, an LLM proxy usually sits between the agent and the model. It's convenient for authorization, protecting secrets and personal data, maintaining a model catalog, and managing limits and costs. Behind the proxy is the provider with the hardware running the inference.

It's crucial to distinguish these parts before you start writing code. Otherwise, it's very easy to call an entire platform that needs to be built a "small agent."

Moreover, each component operates under its own rules. The agent process can be restarted, but the user's conversation should remain after the restart. The model can be replaced without losing access rights or action history. An external service might fail—the agent still needs to clearly report what happened, not just hang silently on a tool call. The boundary between components isn't just for diagram aesthetics; it helps understand who is responsible for recovery and where to look for failures.

There Are Already Many Agents, and They Solve Different Problems

To avoid abstract discussions, let's look at a few existing solutions. Codex is tightly integrated into the OpenAI stack. OpenCode focuses on working with various providers: behind this statement lies significant architectural work, as providers don't fully agree on requests, tools, and response events. Claude Code is built around Claude models.

There are other types of products too. OpenClaw positions itself as a personal assistant. Hermes pays a lot of attention to developing memory and skills as it interacts with the user. Ouroboros experiments even more boldly and can change its own code, not just the instructions around it. Grok Agent focuses on parallel and background scenarios.

There's no universal winner here. There are different sets of trade-offs. But before creating yet another set, it's useful to look inside at least the basic loop.

Agent Loop: Four Steps Hiding a Large System

On a slide, it all looks almost harmless:

  1. The agent sends the model a request along with instructions, tool descriptions, and conversation history.

  2. The model returns a stream of typed events. This can include text, tool calls, service events, and other data.

  3. The agent performs the requested actions: runs local logic, calls an API or storage, waits for the result.

  4. If there's a reason to continue, the tool's result is sent back to the model. Otherwise, the loop terminates.

The diagram shows the loop in four points. In a working product, each point grows its own conditions, errors, and states.

For example, the set of available tools depends on the model and settings. The difference isn't just between OpenAI and Anthropic: individual model versions and intermediate services can also support different formats. A tool might fail, return unexpected data, or not respond at all. Calls can sometimes be executed in parallel, and sometimes the result of one is needed to start another.

And it all works over a network. This means you need to decide when to retry a request after a connection drop, how many times to retry, and whether retrying will cause a side effect twice. "Just retry" sounds easy until a tool call costs money or changes user data.

Constraints on time and memory, telemetry, provider configuration, personalization, cost tracking, and how to show status to the user appear alongside these. Therefore, the agent loop is not just a while loop. It's the foundation of a product's lifecycle.

Moreover, tool errors cannot simply be returned to the chat as raw exception text. The agent needs to understand if the action can be retried, if the user should be prompted to correct the input, and if the error indicates that further steps are already meaningless. When a tool is provided by an external MCP server, it's impossible to know all its failure modes in advance. This uncertainty must be managed with general rules and observability.

Event Stream: Where the Romance of a Simple API Ends

Various methods are used to communicate events with the model. SSE allows sending a request and reading the response as a stream of events over HTTP. WebSocket provides a two-way connection: you can send data while interaction is ongoing and work with binary data. On the model's side, there are also several APIs: OpenAI has Chat Completions and Responses API, Anthropic has Messages API.

The transport differs in capabilities. On top of it, the agent will still have to understand the event structure of a specific API.

The most unpleasant part isn't the protocol name but the fact that the response arrives in pieces. One event signals the start of the response, another adds an element, a third brings another text fragment, a fourth closes the element. Tool calls can also be assembled gradually. You need to correctly match parts, handle stream interruptions, not lose already received results, and not show the user a state that doesn't actually exist yet.

If you feel the urge to write your own streaming parser for multiple providers, I can only wish you good luck. Smart people have already worked on this, and for more than a month.

The complexity also lies in the fact that a server-side 200 OK doesn't mean the agent task was completed successfully. The connection might have dropped mid-way, the tool might have executed after the drop, and the client might not have received the final event. If you then repeat the request without understanding the state, it's easy to trigger an action twice. Such cases are rare in demos but very common in production.

Prompt: Not a Magic Phrase

Remember the era of advice like "you're an architect with 15 years of experience" and "write only in English"? Today, powerful models often need not such rituals, but clear context and accessible actions. However, the most important rule remains: instructions don't turn a model into a deterministic program. It might not execute a step or interpret it differently.

We can conditionally divide the sent context into a system part and a conversation history. Real APIs might have other instruction levels, but two are sufficient for our scheme. The system part contains information about the agent's role, environment, available tools, skills, and memory. The history contains requests, responses, and action results.

The instruction about the agent's role might seem like a boring "header": who you are, where you work, what the date is, what you have access to. But writing it well is not easy. Too vague doesn't help; too detailed eats up context and starts conflicting with user tasks. At one point, system prompts from popular products were even tried to be lured out and collected. More interesting is that no secret text negates the need to verify the agent's work results.

The tool description is also mostly text. We explain to the model: here is the shell tool, here are its parameters, this is what it's for. The model reads the description and decides when to call the tool. The magic works so well that a significant part of the agent's meaning relies on it. But this is precisely why the instruction text and the result format become part of the software interface that needs to be designed and tested.

Context Needs to Be Compressed Without Losing Meaning

The chat history the user sees and the actual model context are not the same thing. The agent decides which messages, tool results, and service blocks to pass to the next request. As work progresses, the context grows, and with it, latency and cost increase.

One way to deal with this is compaction. A long history is given to the model with a request to extract the main points, and then this summary is used instead of the old part of the conversation.

A concise summary replaces a long history. Space is saved, but the model that created the summary had to guess what would be needed later.

Here's an unpleasant scenario. Five messages ago, the user agreed with the agent on an important limitation. The system performed compaction, the limitation wasn't included in the summary, and the agent now confidently acts as if the conversation never happened. To the user, this looks like the model suddenly acting foolishly. In reality, the error lies in our context management logic.

You need to choose the moment of compression, the model for it, and the instruction that won't discard important details. At the same time, the operation itself consumes tokens. This isn't about "checking a compact checkbox" but a task with its own quality assessment.

There's another saving technique—prompt prefix caching. Instructions and tool descriptions at the beginning of many requests rarely change. The provider can save computations for the unchanged prefix and process only the added part. With a successful cache hit, the cost is lower, but the prefix must remain truly unchanged. Developers of some agents meticulously monitor the stability of this block down to the byte. Yes, optimizations become this fine-grained when you build your own agent.

Both compaction and caching aim for savings but affect different things. The first changes the content of the context and risks forgetting something important. The second aims to keep part of the context unchanged to avoid recalculating it. They cannot be mixed into a single "make it cheaper" setting: they have different effects and different verification methods.

Each Tool Name Represents a Separate Product

Suppose we've survived streaming and learned to work with context. What should the agent be able to do? Users expect something like this:

  • read and modify files, often within projects and team workspaces;

  • run commands, monitor processes, and work on Linux, macOS, and Windows;

  • search the internet and access external APIs;

  • generate images;

  • ask clarifying questions to humans, sometimes during task execution;

  • maintain a plan, manage its own context, and delegate work to sub-agents.

Each point looks like a single line in a tool list. Behind it are access rights, limitations, UI, error handling, and testing. For example, "ask a human" isn't just displaying text. The agent might pause an action, offer three response options, receive a choice, and continue from the correct point. And sometimes it needs to continue working while the question is still displayed. This requires explicitly designing the process and interface state.

You also need to access tools through configuration. The agent needs to know which provider to ask for inference and whose key to pay for it. It needs environment parameters, telemetry, and a clear response to insufficient memory or execution time. The product might offer personalization—for example, pre-setting the user's role and their team's context. All this affects the model request but lives outside the neat four-arrow diagram.

Sub-agents add another layer. The parent agent needs mechanisms to launch them, pass context and available tools, wait for results, and figure out who is responsible for what. And if several sub-agents communicate with each other, we get a small coordination protocol. The simplest error here is familiar to any manager: the task was formulated seemingly clearly, and the executor did exactly what was said, but not what was implied. Agents are also prone to this.

In a simple scenario, you can give the agent a CSV and ask it to run a separate job for each row. In a more complex one, you can assign roles like researcher, executor, and verifier to sub-agents. Then the parent agent has to not only distribute tasks but also write instructions for them, combine results, and spot contradictions. Delegation doesn't remove complexity; it shifts it to task formulation and coordination.

MCP: Connecting Tools is Easy, Maintaining Them is Hard

MCP allows connecting tools from external services. Their list is formed not only by the agent developer: the user can add their own servers. Imagine they connect 30 servers, and each has 10 tools. What will happen to the system prompt size? Even if the agent can load tool descriptions on demand, the model still has to decide when to load them.

An external MCP server might not respond, send an unexpected result, or turn out to be untrusted.

And then there are MCP protocol extensions. For example, MCP Apps add interactive widgets. The agent can show the user a diagram, the user clicks an element, and the agent uses this choice for the next action. Excellent UX—and simultaneously a task of isolating third-party code that shouldn't access secrets or harm the user's browser. Good luck implementing this in your agent!

Skills: An Instruction That Needs to Be Used at the Right Moment

Skills have a different mechanism. They are a set of instructions, often in a SKILL.md Markdown file, and tools through which the agent can find and read these instructions. The main prompt usually doesn't contain the entire text of each skill, but a short catalog: name, purpose, file path, and the rule for when to read it. Here, you already have to design routing: the description should help the model choose the right skill without bloating every request.

The prompt shows imagegen with a short description and the path to SKILL.md. The detailed instruction itself is not yet loaded.

Let's consider a case. The user writes: "Create a picture of Moscow City." The model receives this request along with the skill catalog and sees that imagegen is suitable for generating images. But to use it correctly, it needs to go through another round of the agent loop:

  1. The model decides to read the skill and returns not an image, but a call to skills.read with the instruction address.

  2. The agent executes this call. skills.read returns the plain text of SKILL.md: what actions are available, in what order to perform them, what parameters to pass, and how to handle the result.

  3. The agent adds this text to the next request to the model. Only now can the model follow the detailed instruction and, for example, call the image generation tool with the description "Moscow City."

  4. The generation result goes through the loop again: it needs to be received, shown to the human, or work continued if the instruction requires another step.

The slide highlights an important point: reading a skill does not execute it. The instruction text is returned to the model, which then decides what to do next.

This means "the agent has a skill" doesn't yet mean "the agent will reliably use it." It might not match the request to the description, fail to call skills.read, skip part of the instruction, or call the correct tool with incorrect parameters. Links to other files, scripts, and templates add new steps. During testing, you have to check the entire chain with different phrasing of requests, and after updating the model, check again. The complexity of skills is hidden precisely in this transition between text, model selection, and actual action.

Memory: Forgetting is Bad, Remembering Too Much is Worse

The "agent's memory" often refers not to a single file but also to a separate process. A background task reviews conversations, asks the model to extract important information, and saves individual memory entries. From these, memory_summary is compiled—a short map of what the agent generally knows about the user and their work.

A background process turns conversations into individual entries, and then into a summary. At each transition, something important can be lost or too much can be generalized.

What happens next? The agent's instruction template has a placeholder: {{ memory_summary }}. Before the next request, the current summary is inserted there. Thus, the agent immediately sees a summary of its memory in the prompt, even if it hasn't opened any files. Nearby are rules on how to find details: first look at the summary, then, if necessary, open the memory index and specific entries.

The very slide with MEMORY_SUMMARY BEGINS and {{ memory_summary }}: the summary is injected directly into the instructions, and the agent must read the full memories separately.

There are at least three potential problems that you need to consider in your implementation.

  1. The model didn't save something important—and the user explains the same thing for the hundredth time.

  2. The agent only received a brief summary and didn't fetch details, even though they were needed.

  3. Or, conversely, it remembered a casual request as a permanent preference.

It's hard to even formulate the criterion for correctness here. What counts as a stable preference, and what is context for a single task? When should a new entry replace an old one? How can you let the user correct the memory without forcing them to understand the internal format? If these questions aren't answered, "memory" will regularly surprise the person in the worst way.

I once asked for a JavaScript example—now the agent might decide I've always dreamed of working only in JavaScript. The user usually doesn't even see the specific memory entry causing this. Old memories need to be reviewed and deleted, contradictions resolved. This is a separate area of engineering, not a free feature of the model.

Guardrails: Not Just One Check Before Running a Command

An agent with tools can make costly mistakes. It might suggest a destructive command, send data to the wrong place, or change something the user didn't intend to change. Therefore, protection is built from several layers: model training, system instructions, deterministic action checks, additional checks using the model, process isolation, and network restrictions.

Each layer covers a part of the risk. None alone makes the system safe.

Let's break down this pie from the inside. The first layer is the model itself: during training, it's instilled with rules for safe behavior. The second is the system prompt: the agent receives instructions about permissible actions within the product. Both layers are necessary, but both rely on the probabilistic behavior of the model. They don't provide a firm guarantee that a specific tool call is safe.

The third layer is deterministic checks in the agent's code. Before executing, for example, a shell call, you can parse the command and look for dangerous operations. This sounds simple until the command consists of multiple parts, variables, redirects, and nested calls. The check needs to understand what will actually be executed, not block many normal tasks, and yet not miss a bypass. For each tool type, the rules have to be designed separately.

The fourth layer is checking with another model. When danger depends on the meaning of the request and the task state, a set of hard rules is insufficient. You can prepare a separate request and ask an evaluator model to decide if the action is permissible. But then you have another prompt that needs protection from injections, another model with errors, and another delay before execution. Its response also cannot be considered proof of safety.

The fifth layer is the operating system sandbox and network policy. Even if previous checks fail, the process should only have necessary access to files, other processes, and the network. On macOS, I mentioned Seatbelt in the talk; Linux and Windows have different mechanisms. You need to define access boundaries, run the tool within them, and not break useful scenarios. This layer cannot be replaced by a single system prompt.

And finally, there's human agreement. The stricter the rules, the more often the agent asks for confirmation. If every step requires an "Approve" click, the user gets used to pressing Enter without reading—or enables full access. Therefore, you need to decide which actions to allow automatically, when to ask, and how to clearly explain the risk. An error in this interface can nullify all the work of the previous layers.

This is why guardrails are a monstrously complex engineering part, not a single if before running a command. You need rules for different tools, isolation on different platforms, testing on real scenarios, and a review of protection after changes to models and tools. If you start writing your own core, you're also taking on this work.

When Your Own Core Actually Makes Sense

After all that has been said, it would be dishonest to claim that your own core is never needed. I see several reasons to seriously consider this path.

The first is if you require unusually strict process control. For example, the agent works with legal documents, and each assertion must be based on a specific source. Or it performs operations with orders and money, where you cannot let the user persuade it to give a 100% discount. In a medical scenario, the cost of error can be even higher. This will require many checks and clearly defined transitions between stages. However, even such requirements don't automatically mean rewriting the agent loop: first, check if control can be provided around a ready-made core.

The second reason is if you are truly exploring a different way of agent operation. For instance, in LangGraph, the developer defines a graph of steps and states, and execution follows its transitions. In the experimental SKILL.state architecture, a long dialogue history is replaced by an explicit mutable skill state: at each step, the model receives instructions, the current state, and the last observation. And Jev shows another option for parts of such a process: instead of generating text, the model quickly returns typed decisions that code can use to choose the next branch. These are examples with different structures, but each forces you to re-solve the question of who controls transitions and what to pass to the model at the next step. This is a reason to change the agent loop, not just add another tool.

However, saving tokens by itself is a weak reason to start with your own agent. Often, the desired effect can be achieved in an LLM proxy: route different tasks to different models, use a cache, change the limit policy. This is an incomparably smaller area of responsibility than API compatibility, streaming, memory, tools, and guardrails all at once.

How to Build Your Product Without Rewriting the Agent Loop

The first method is surprisingly simple: clearly set tasks for a ready-made agent. If you know what tools it has, you can ask it to use the necessary data and return the result in the desired format. This isn't an absolute guarantee—the model might ignore the hint, and an overly detailed plan can sometimes be a hindrance. But before writing a new architecture, this option is worth testing in practice.

If you need your own interface and control over integrations, another path is more interesting—the app-server. This is a separate process with a ready-made agent core. On one side, it interacts with the model. On the other, your application connects to it: locally via stdin/stdout, remotely via WebSocket. Structured messages, JSON-RPC, are exchanged between the application and the server.

You can build your own GUI and tools around a ready-made agent loop. The application communicates with the app-server, which handles the model interaction.

Such an interface allows passing settings, declaring your own tools, receiving events about the work progress, and returning call results. Codex is one example of this approach; other agent projects have their own server interfaces. Of course, integration doesn't become free. However, you focus your efforts on the specifics of your product, rather than re-solving the entire list of tasks above.

And here lies a large, often underestimated field of work: UX. A simple "fork thread" button can allow safely exploring an alternative line of thought. Two conversations side-by-side—one exploring a problem, the other working on code—change how a person uses the agent. For non-programmers, it's even more useful when the agent immediately knows their role from the corporate system and receives the necessary data through tools, without being asked to explain the company structure every time.

Writing your own tools is precisely what makes sense. They connect the agent to the real tasks, data, and constraints of your product. Here, the harness stops being an abstract "wrapper" and becomes the reason why a user chooses your solution specifically.

Instead of a Conclusion, or TLDR

If you skipped straight here, here's the short version:

  • Streaming, provider compatibility, tools, context, memory, security, and UI are independent engineering tasks. You don't get them for free with access to an LLM API.

  • Skills are incredibly complex to operate: the model must choose the skill at the right time, read the instruction, and go through all the steps; the SKILL.md text won't execute itself.

  • Memory isn't just about saving facts: you need to extract what's important, compile a memory_summary, insert it into the prompt, and ensure the agent accesses details at the right time and forgets outdated information.

  • Guardrails involve several different layers, from model rules to command checks and sandboxing. They need to be combined so the agent doesn't cause harm and the user doesn't get used to confirming everything.

  • For most product tasks, it's more reasonable to use a ready-made core and build your own tools, integrations, and user experience around it.

  • Your own core is justified when you truly need a different agent loop or a level of control that cannot be achieved on top of an existing solution.

If you want to take one thought away from this article, let it be this one.

I came to these conclusions not only from reading others' code. I had to figure out questions about models, tools, memory, and the boundary between the core and the product while developing the Ardor agent. This experience is a good reality check: the most interesting result for the user is born not where we rewrote another model call loop, but where the agent finally managed to reliably work with their tasks and environment. If you are also building such systems, I would be interested to discuss which parts of your harness you consider truly unique.
