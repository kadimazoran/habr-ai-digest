In the spring, a $100 subscription was enough for all my pet project tasks. The idea of fully exhausting the five-hour token limit seemed like a challenge. By early summer, I was managing it well, but by August, limits were only sufficient for technical design, delaying implementation until the next week. I'd start tasks and use up the weekly limit in about 3 days.

In September, I had a $200 subscription, but even its limits weren't insurmountable. Some friends and colleagues mentioned they were already on maximum Claude and GPT subscriptions simultaneously and planning to get a third!

Pouring more money seemed like a dead end, so I started looking into optimizing token consumption. The main reason wasn't the complexity of tasks or code volume, but simple daily convenience.

Batches of Tasks

I liked to group a batch of well-defined tasks together, 5-15 items, and send them for development all at once. A top-level agent could process them all night without ever reaching the session compact limit.

This was exceptionally convenient because I would work on defining tasks in the evenings, and their execution could proceed without my direct involvement. At most, if the internet dropped, I'd just need to say, "You were interrupted, resume work from where you stopped."

A fortunate coincidence was that from around 9 PM Moscow time until 9 AM the next day, there was a dip in activity from US clients (the main market for Anthropic by user count). The models worked quickly.

Typically, the agent would complete the entire batch within its own 500-800k context, leaving me with an independent verification of the completed work, along with GPT. This was effective and helped catch bugs that Claude, with its fuzzy vision and loose approach, might miss.

This scheme had several unpleasant side effects, all related to cache behavior:

  1. Sub-agents don't warm the cache. The top-level agent keeps a cache for 1 hour between requests. If sub-agents work for a long time, its cache can expire. Long independent sub-agent sessions led to dramatic consequences: almost every analytics/development/review task could hang for over an hour, and each time it would re-initialize the top-level agent;

  2. A cache miss on a large context will cost you dearly. A repeated request to an 800K token session will force you to pay for every token again (either by consuming subscription limits or paying via API);

  3. The sub-agent's cache lives for only 5 minutes between tool calls. If it goes into a long task, like running all integration tests at the very end of its work, then upon completion, the agent's entire context will be re-read. My sub-agents could grow to 400-600k on average. You can tune the sub-agent cache with the parameter subagentPromptCacheTtl: 1h (or env CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL), but the maximum is also 1 hour. It's important to remember that the cost of cache interaction for sub-agents increases in this case, so it might not save you money;

  4. Accessing caches has a cost. As the session context grows, the cost of reading the cache also increases. Every tool call requires reading the cache in its entirety. A simple bug fix might involve around 20-50 such calls. Working with an 800K token session is about 8 times more expensive than the same actions on 100K tokens. This applies to sub-agents as well. We can conclude that the cost of cache reading is proportional to the context size (a conditional "1" for 100K and "8" for 800K).

There's only one solution: abandon long-running sessions altogether and break down large tasks into smaller pieces. However, this approach also has its downsides.

Heavy Development Cycles

Ever since Opus 4.5, I've used the classic agile team of sub-agents with different prompts. It looked like this: an analyst breaks down a task and hands it over for development, a programmer writes the code, and a reviewer and QA check it from different angles. A single top-level agent orchestrates all of this. There's one task, but each agent has its specific goal within a narrow area of expertise. Surprisingly, they found many real flaws in each other's work.

Even back then, I understood a peculiarity of neural networks: a specific prompt seems to steer the model along a particular vector of movement, and it doesn't look into adjacent logical branches. Prompts have since become orders of magnitude shorter (kudos to those who still write 1000-line essays). Nevertheless, different agents, launched with different prompts but working on the same task, continue to show high efficiency.

Now, the models have gotten smarter. For example, Sonnet 5 is quite capable of competing with Opus 4.8 and even surpassing it, and recently the 5.5 generation was released. If that's the case, why pay more for expensive agents? I thought about this when I realized all my sub-agents were running on top-tier Opus 5 and Fable 5.1, and on a large context at that.

The solution is obvious:

  • for inexpensive tasks (minor cross-repo fixes, development), use Sonnet, and for searching, use Haiku (does anyone even use it?);

  • delegate expensive analytics and reviews to Opus/Fable;

  • explicitly instruct the analyst sub-agent to break down large tasks into batches so that the performers' context doesn't explode;

  • prohibit the top-level agent from waking up sleeping sub-agents for minor edits, as you'll end up paying for their entire context again.

Ban on Writing Comments

Neural networks particularly love to write verbose comments for infrastructure code. Ansible is a perfect area for their twisted understanding of what comments should contain. This includes descriptions of task/playbook logic, knowledge about the real infrastructure (which VM is where, how it was configured, what's inside it), and even, damn it, the principles of how Ansible modules work. Sometimes you see 20 lines of comments for a single line with a variable.

The situation isn't much better when generating application code. It's common for comments to take up a third or more of the total volume. Once, in a conversation with Claude, it admitted to me why the comments turn out so verbose, and it said it quite honestly:

Because sub-agents write comments for themselves, not for future readers. In comments, they simply articulate what they intend to do and how it will work.

The problem arises when a subsequent code change doesn't involve updating the comments. This leads to a crucial conclusion: if comments are not maintained, their accumulation forms a second codebase for the application.

This significantly harms future sub-agents because they inexplicably start considering the information in comments to be more important. It's absurd, but that's the reality. Sometimes it got ridiculous: the formulation of a new task was based on analyzing comments, not the code, and during execution, adjustments had to be made on the fly to the "suddenly" discovered different implementation.

All this led me to understand that it's easier to ban writing comments than to deal with their content. I formulated the following rule (you can simply add it to your skills as a separate line):

It is strictly FORBIDDEN to write comments based on the principle "a comment is useful if the information is correct and relevant." Use the approach: no comment by default; it must justify its existence. Give sub-agents this exact brief verbatim.

Code cleanliness increased exponentially, and the principle the best specification is the code itself finally began to mean something.

Chronicle in CLAUDE.md

The files CLAUDE.md and AGENTS.md are crucial for agents to quickly grasp the essence of a project, as each new session effectively sees your project for the first time. In this context, I can't understand why agents maintain these files so poorly on their own.

I started with a basic 20-30KB, but after a few months, I found the top-level CLAUDE.md weighing 140KB. Each sub-agent felt obligated to explain its completed work in detail.

But that's not even the main problem. For effective agent onboarding, I built an entire project hierarchy:

  • At the top level was CLAUDE.md with a brief description of the entire project and the interconnections of its various repositories, invariants (how neural networks love this word), and operating rules;

  • The repositories themselves were cloned into subdirectories, each with its own CLAUDE.md providing a detailed description of its area.

I really liked this approach because it allowed me to implement cross-repo features with a single request. Entire classes of problems disappeared, such as when the UI agent said, "Everything is fine on my end," and the backend agent replied, "The problem is definitely on the UI side," and so on (this sounds familiar). The top-level agent was responsible for everything and organized the resolution of requests of almost any complexity.

What could go wrong?

When launching sub-agents from a parent session, there's one crucial nuance: a sub-agent always starts in the working directory of the main session. This means it automatically reads the top-level CLAUDE.md and then (according to my operating rules) the same file in the target repository where it will perform the task. If you add the sizes of both files, it turns out that before even starting work, a sub-agent could consume 150-200K tokens just to understand where it is. Over a night, 20-50 such sub-agents could be launched.

Unfortunately, you can't tell a sub-agent, "Don't read the top-level CLAUDE.md." The only possible optimization path is to compress all such files. I don't recommend abandoning them entirely, but when optimizing their content, you could tell the agent something like: "leave only the information in the file whose absence would break the project." Such a request will result in approximately 90% compression (depending on how neglected things are).

Frequent Compacting is the Solution

I remember before the 1 million context limit was introduced, I felt a slight anxiety when an agent, in the middle of a large task, approached the point of automatic compaction. I thought then that something important would surely be lost, and everything would go awry.

The truth is, you can control when the context compression operation is performed. Agents are now smart enough to automatically save all their intermediate work (and that of sub-agents) within the session's temporary directory. After compaction, it's not lost; it's important only to ask the agent to tidy it up periodically and to prompt you when the compression operation is appropriate and data loss won't occur.

Notably, context compression can even be done while sub-agents are actively working. Upon their completion, they will report to the top-level agent as usual.

How to choose a good moment for compression? For example, when you transition from task design to its implementation.

I also found a pleasant side effect of the compression process. During operation, the active context window contains all information, including detailed tool calls, command and script output, all read files, and logs of interactions with sub-agents. About 90% of this is not needed at all, and compaction cleans up this volume. As a result, the agent is left with a summary of the most important information for continuing its work. This is very similar to human "working" memory, where overnight sleep discards all the details you remembered since waking up but leaves the most important and memorable things in memory, sometimes for decades.

If you work in a single session for a long period and constantly compact it, the agent will remember some details from the very beginning of that session, and it's sometimes very pleasant when nuances it recalls are things I had long forgotten. Memory doesn't provide this effect; the agent doesn't clean it, and it usually accumulates a lot of garbage, with the level of detail leaving much to be desired.

Welcome to 200k, Again

Rational resource utilization was one of the main engineering tasks during my university studies. Wasting register memory could easily lead to a retake. Perhaps that's why the issue of optimizing token usage in the moment captivated me even more than the process of agent development itself.

I want to say that creating elaborate solutions for storing agent memory and session contexts seems like a unpromising direction, because each time, the new volume won't be enough. But the main side effect isn't even the increased token consumption (rumor has it OpenAI is preparing a $500 subscription for everyone), but the degradation of the agents' quality of work, which is more severe the more context is consumed.

Dropping everything and setting CLAUDE_CODE_DISABLE_1M_CONTEXT=1 right now is probably not advisable, but you can start monitoring resource consumption at any moment; it's entirely within your control.
