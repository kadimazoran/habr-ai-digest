Having mastered connecting MCP and SKILLs to Harness AI, I decided to move to the next level of abstraction and explore the overhyped new concept of an 'agent swarm.' I remember being scared to learn SKILLs and MCP, thinking I'd go broke and my limits would be blown on a $20 monthly plan. But the devil isn't as black as he's painted. If I didn't go broke last time, why not try my luck with agents? It's cool to have a whole swarm of agents working for you, like the big players who spend tens or hundreds of thousands of dollars on tokens.

There are currently two very popular projects.

The first, garrytan/gstack, has 140k stars. It was created by Garry Tan, head of Y Combinator. The project turns Claude Code into a virtual development team using skills and slash commands:

/plan-ceo-review, product analysis from a CEO's perspective.
/plan-eng-review, architectural review.
/plan-design-review, design review.
/review, code review.
/qa, browser testing.
/ship, preparing changes for release. /cso, security audit.

The second, wshobson/agents, has 42k stars. It's a large collection of agents for all occasions. It contains hundreds of components for development:

  • Specialized agents: frontend, backend, database, security, DevOps, and others.

  • Skills for languages, frameworks, architecture, and testing.

  • Commands for typical tasks.

  • Plugins that combine agents, skills, and commands.

  • Ready-made multi-agent workflows.

But I, as always, have my own approach. If you want to understand something and try a technology in practice, don't take ready-made solutions, but build your own 'bicycle' from scratch. First, I studied what agents are and how to work with them. It turns out that Codex has a built-in sub-agent system. The idea is that you can assign a task to Codex and launch several agents to complete it, either in parallel or sequentially. Each of them will have its own context. The main Codex instance will handle the orchestration (or, in Russian, management) of the launched sub-agents and consolidate their work into a final result.

This approach has two advantages and one disadvantage. First, agents can work in parallel, although not all tasks can be broken down into parallel subtasks. Second, each agent has its own context and task, so the quality of work can improve: it's easier for an LLM to maintain focus on a task when the context doesn't grow too large. The third point, the disadvantage: ultimately, more tokens will be spent to solve the entire task. Here's an example of such a request to Codex:

Launch three sub-agents in parallel. Let the first find the five largest files in the project, the second count the lines of code, and the third determine which programming languages are used. Wait for the results of all three and output a general report.

In the example above, everything is very simple: all three sub-agents perform different tasks while remaining agents of the same type. Codex allows you to describe how agents should work and what they should do. General instructions can be set at the top level so they apply to all repositories you work with. You can also create individual agents for each repository, considering its specifics. As a result, I added the following agents:

  • analyst, analyzes requirements, business logic, domain, and tasks.

  • architector, designs system architecture, defines technical solutions and development standards.

  • planner, studies the repository and creates a plan for a new project and feature tasks.

  • frontend-developer, develops the client-side of the application, interfaces, and API integration.

  • backend-developer, develops server-side logic, APIs, and integrations.

  • database-developer, designs database structure, writes migrations, and optimizes SQL queries.

  • devops, configures servers and infrastructure, responsible for CI/CD and application deployment.

  • security-engineer, checks code, architecture, and infrastructure security, identifies vulnerabilities.

  • ux-ui-expert, designs user interfaces, prototypes, and interaction scenarios.

  • unit-tester, creates, maintains, and runs unit tests.

  • ui-tester, creates and runs UI/E2E tests, checks user scenarios.

  • technical-writer, writes and maintains documentation, help files, guides, and instructions.

  • code-reviewer, checks code quality, adherence to standards, and correctness of changes.

Next, I created the AGENTS.md file, where I clearly described when, how, and which agent to use. This way, Codex doesn't have to decide which agent to use and for what. The result is a project template with pre-installed agents, documents, and rules for their use. The template can be copied into a project repository and used. Here is my repository with the template. Overall, my verdict is this: If you need a high-quality, polished result, it's worth using an agent swarm, but the time to complete the task will increase significantly. By the way, it doesn't consume my five-hour limits to the fullest; it uses about half. But if you need to quickly whip something up, on the principle of a 'student project: wrote it, it works, and that's that,' then the regular, bare Codex out of the box is the best option for you.

P.S.

Oh, and by the way, you can specify for each agent which LLM to use and what reasoning level to choose. This is set directly in the agent description file. But since I'm trying to save money, I have Luna 6 set by default with the maximum reasoning level to stay within the $20 monthly plan.
