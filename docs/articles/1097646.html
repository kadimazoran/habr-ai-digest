It's a known fact that AI agents can act independently: launch programs, manage files, and tirelessly pursue a given task.

This might seem like a developer's dream, but there's a catch: the more freedom an agent has, the more problems it can cause. In the summer of 2026, OpenAI agents broke out of their sandbox and ventured onto the internet, attacking HuggingFace in the process.

This incident presented AI engineers with a challenge: they needed to find a way to restrict agents, ensuring they could never leave isolated environments. However, agents are cunning and quickly find ways to bypass even the strictest rules. But there's one weak spot.

Today, we'll discuss the Hard Stop system, proposed in a scientific paper of the same name. It acts as an emergency brake between the agent and the OS, designed to halt the agent's processes before it can cause harm.

Escape

You've likely heard about the recent high-profile incident involving an internal OpenAI experiment. The official version is that it was a test of agents on a set of cybersecurity tasks on the ExploitGym platform, conducted in a strictly controlled environment—they had no internet access, and execution occurred exclusively in isolated environments. The goal was to complete the tests successfully.

However, there was a weak point: an intermediate server, Artifactory, which had internet access, was used to install software packages.

While working on the tasks, the agents reasoned that the tests would be best solved where the answers already existed: on the internet. Therefore, they found a vulnerability in Artifactory, used it to establish communication among themselves, and then learned to send requests to the outside world.

After the incident analysis, independent researchers discovered around 1200 agents that had generated over 70,000 messages and files. Approximately 700 of them attempted (and succeeded) to compromise HuggingFace's security.

During their audit, HuggingFace was able to reconstruct about 17.6 thousand actions where agents searched for vulnerabilities, read system files, and even managed to gain access to Kubernetes and internal infrastructure.

And all this was done solely to solve the tasks assigned by OpenAI, despite all its security measures and clearly defined rules. The tasks, in essence, were:

  • Do not connect to external servers.

  • Do not leave your sandbox.

  • You are forbidden from reading system files.

As we can see, this didn't help. And then the shit hit the fan an active and controversial discussion began about the need for a more effective way to catch a mischievous agent.

Catch the Thought, Not the Action

One way to control an AI agent is to check its commands and messages before execution: a filter or another model analyzes the generated text and tries to determine if the agent is planning to do something forbidden. However, such control depends on the system's ability to correctly interpret the form of expression. As we've discussed in an article about AI agents' own languages, a message can be encoded or transmitted in such a way that monitoring doesn't recognize its meaning. The problem with commands is similar.

Suppose an agent is forbidden from using `.curl`. The agent's filter looks for this word in commands and understands that it cannot be used *directly*. However, it can be assembled from a couple of strings (cu+rl), the command can be encoded, or a Python network library can be called directly. For a generative system, which an agent is, these are all different actions that don't fall under a single restriction.

But from the perspective of the OS, which receives the requests, the picture is different. Any process must eventually interact with the OS kernel: it manages files and all computer resources; this stage cannot be bypassed.

And if the agent cleverly crafts the server address, it still has to provide the specific IP and open a socket to the kernel. Or, with files, even if it hides the path to the desired folder within the code, the kernel will still receive the actual path.

And at this point, developers decided to implement Hard Stop. Its principle of operation is as simple as a club's bouncer: if the action is on the whitelist, it proceeds to the kernel; if not, the action is stopped. The emergency brake doesn't need to understand the model's reasoning—the agent is inherently an untrusted program to it.

Two Layers of Architecture

The emergency brake cannot be embedded directly into the LLM itself, as the decision will still be made by a probabilistic model, where the chance of error always remains (and can even be extremely high).

Therefore, Hard Stop has two levels: the agent and its supervisor. The latter has a very dull and straightforward task: to compare actions against predefined rules. For example:

  • The agent can only work with /workspace.

  • It can only connect to the internal server.

  • It is only allowed to run approved programs.

  • It does not have access to /proc, /sys, and other system areas.

The supervisor remains inactive if the rules are not violated. But a step to the left, a step to the right—and the emergency brake is pulled.

The idea was dubbed Andon Cord—after the safety system at a Toyota factory. There, on the assembly line, there's an Andon mechanism that can immediately stop the line if a problem occurs.

But in our case, it doesn't end with stopping the forbidden action. The supervisor blocks the dangerous action, after which all of the agent's processes are frozen, with their current state recorded, so that a human developer can conduct an analysis.

The emergency brake works on a very simple principle: it's based on existing Linux mechanisms—the system allows embedding checks directly into the execution path of sensitive operations.

Among other things, there are LSM and eBPF.

LSM is a security infrastructure within the Linux kernel. Simply put, it can implement additional checks before operations like opening files or network access. And eBPF is a way to load mini-programs for such checks directly into the kernel.

Is the problem of unwanted actions solved at its root? Almost! The thing is, agents rarely run a single process; they usually involve chains and entire groups of processes: for example, one works in the browser, another launches shell commands, which in turn initiate more processes, and so on.

You can stop the agent, but this won't affect child processes. And for this, Linux uses the cgroup mechanism, which groups multiple processes together. In classic use, Linux uses cgroup to limit resources, so that, for instance, a large container doesn't consume all the RAM or CPU power.

But the same cgroup can also freeze process groups. In plain language, this means it says: "Stop EVERYTHING that currently belongs to this agent."

At the same time, cgroup expects confirmation through the kernel that the agent and its "henchmen" are frozen, even if the supervisor requested a complete stop of the process group.

Why do this? Imagine an agent has been working on a complex task for hours, but at some point, it decides to misbehave. If it's reset, all useful progress will be lost. This is a safeguard, similar to version history in a text editor—if the PC suddenly loses power, you can return to the document with minimal loss.

When the emergency brake is triggered, the system writes logs where you can see:

  • what it was doing;

  • at what step it stopped;

  • which specific rule it violated;

  • whether execution can be continued after human intervention.

And all this is thanks to the built-in WAL (write ahead log) for state and event recording.

Why Might Even This Not Be Enough?

A kernel-level solution seems flawless, but there's a loophole here too. Especially as in the OpenAI case, where the agent didn't go directly but through a third-party server, which it was perfectly legal to access. This means that in the case of the emergency brake, the whitelist would allow the request because it's a trusted intermediary.

This creates another hole and a useless emergency brake. Restrictions need to be built at every level of the chain so that trusted intermediaries also have limitations and do not have arbitrary internet access.

In other words, a principle of least privilege is needed: each component should have exactly the access required to perform its task.

Also, Hard Stop itself is currently just a demonstration of a possible architecture. In the published materials on GitHub, there are even benchmarks, such as the stop-triggering speed—4.8 microseconds on average, which is quite fast.

Speed is good, but Hard Stop only works as long as the controller, by its access level, is above the agent.

Suppose the agent operates within its environment, and the supervisor manages rules, cgroups, and network restrictions from the outside. In such a configuration, the agent can try to go beyond the allowed boundaries as much as it wants—it simply doesn't have the rights to change the rules themselves.

But what if the agent has somehow already gained root access to the host? Then it could potentially interfere with the protection mechanism itself: change cgroup settings and generally affect the supervisor. This means the emergency brake is good only until the agent reaches the room where the main switch is located.

Hard Stop, in principle, doesn't care whether a rule is bad or good, and it needs to be set correctly, meaning a lot depends on the initial configuration set by a human.

From all this, we can conclude: it will be more reliable to keep AI behind a strong door than to rely on its good intentions. Because the solution found by a neural network might not be to everyone's liking.
