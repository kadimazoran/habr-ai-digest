Ilya Kuchmin, author of the "AI Agents Software Development" course, raises a thought that is difficult to ponder in everyday life:

Where is the code that your agent writes actually executed?

Over the past year, agent sandboxes have evolved from simple environments for running suspicious code into full-fledged infrastructure. They have snapshots, pause and resume, branching, and even their own browser. But a reverse trend has also emerged: many agents don't need a whole computer at all.

If you haven't thought about this yet, now is the time to see where the industry is heading.

AI Agent Sandboxes: The Current State

Does every agent really need its own computer, or can most of its work be done in a much simpler environment? Over the past year, agent sandboxes have transformed from relatively simple environments for running untrusted code into infrastructure capable of running entire agents.

Vendors are competing on startup speed, isolation levels, persistent file storage capabilities, snapshotting, and support for pausing and resuming. Some already offer full development environments and browser automation.

Pydantic recently introduced Agent Sandboxes—a managed sandbox service based on the Monty Python interpreter. The service uses a lightweight interpreter written in Rust to execute programs in a restricted subset of Python. A separate isolated machine is not needed for this. This example shows how quickly sandbox architectures are changing, even though many of their basic capabilities are already becoming standard.

Today, sandbox architectures are evolving in several directions simultaneously: where agents run, how execution state is saved, how security and observability are ensured, and how to manage multiple environments.

Let's look at which sandbox capabilities have already become standard and in which areas vendors continue to seek new solutions.

Isolation is Becoming Standard

The primary task of a sandbox is to isolate code execution from the environment in which it is run. Agents can execute arbitrary code, install dependencies, and work with files while having limited access to the underlying infrastructure.

Vendors such as E2B, Daytona, Modal, Vercel Sandbox, and Cloudflare Sandboxes offer similar APIs for creating environments, executing commands, exchanging files, and managing lifecycles.

For isolation, they use technologies like Firecracker, which runs lightweight virtual machines with their own guest kernels, and gVisor, which implements a kernel in user space and intercepts system calls. Regular containers share the host kernel, so the attack surface is wider than with virtual machine isolation.

Local development agents have their own isolation requirements. Claude Code uses OS-level sandboxing mechanisms to restrict access to the file system and network. Codex employs platform-specific mechanisms to limit what an agent can modify and execute. Both approaches protect the developer's machine during local execution.

The Kubernetes project Agent Sandbox introduces resources for managing sandboxes with state persistence, templates, sandbox allocation requests, and pools of pre-provisioned environments. Developers can manage multiple sandboxes through Kubernetes and use ready-made mechanisms for managing their lifecycles.

Sandboxes Without Operating Systems

Many agents only need to execute short programs that combine tool calls and process intermediate results.

When using Monty, the model generates Python code that is executed in a restricted interpreter. The application defines which functions this code can call and sets resource limits. The code only gets access to capabilities explicitly made available to it.

For example, an agent might generate a program that loads customer records, filters results, performs calculations, and calls another tool. The interpreter executes the entire program in a single run, without separate calls to the model for each operation. Pydantic AI implements this approach in CodeMode through a single `run_code` tool.

In Monty, you cannot arbitrarily install packages or execute operating system commands. These restrictions allow for significantly less infrastructure than is required for a full virtual machine.

Agent Sandboxes from Pydantic also support long-running interpreter sessions, state snapshots, and branching. A session can preserve Python state between runs, and snapshots allow restoring it or creating independent sessions based on it. There is no need to save the state of the entire operating system.

Sandbox State Persistence and Snapshots

State persistence has become a common requirement for agents whose work extends beyond a single run. If the development environment is recreated after each pause, dependencies must be reinstalled, files restored, and processes started.

Major vendors support various combinations of persistent file systems, snapshots, and environment restoration. E2B allows pausing and resuming sandboxes, Daytona supports snapshots, and Modal offers persistent storage and file system snapshots.

File system snapshots save source code, installed dependencies, and created artifacts. Memory snapshots can additionally save running processes and interpreter state. A paused virtual machine can restore a significant portion of the environment's previous state without going through the entire boot process again.

Snapshots also enable branching. Multiple agents can start work in identical environments and independently try different implementation approaches. The result of each branch can be reviewed before deciding which changes to keep.

Restoring a large environment, taking a memory snapshot of a running system, and branching without full state duplication require different infrastructure mechanisms. Vendors differ in what exactly can be saved in a snapshot, how much its storage costs, and how quickly an environment can be restored from it.

The Economics of Long-Lived Agents

Startup speed has become one of the main competitive parameters among sandbox providers. Pools of pre-provisioned environments, ready-made images, lazy loading, and restoration from snapshots have reduced waiting times.

E2B and Daytona claim that under certain conditions, startup takes milliseconds or fractions of a second. Launching a provisioned sandbox can be significantly faster than booting a new machine, installing dependencies, or restoring a large working environment.

A significant portion of the time, agents wait for a response from a model, an external service, human confirmation, or the results of another agent's work. During these periods, they use very little CPU. Maintaining thousands of predominantly idle sandboxes can be expensive, so it's beneficial to shut them down between periods of activity.

Platforms like Fly.io Sprites and Blaxel offer stateful environments that pause during idle periods and resume on demand. Applications can preserve working environments without continuously paying for active compute resources.

When managing multiple sandboxes, you need to consider placement, pools of provisioned environments, quotas, lease times, timeouts, and resource cleanup. The Kubernetes project Agent Sandbox helps address some of these tasks using declarative resources. Managed service providers use their own management systems.

Sandbox Security

Even within a secure micro-virtual machine, an agent can access sensitive credentials, send unauthorized API requests, or transmit information through an allowed network connection.

Permissions granted to an environment determine which external resources an agent can access and what operations it can perform with them.

In Docker Sandboxes, credentials are injected on the host side. A proxy intercepts allowed outgoing requests and adds credentials to them outside the agent's environment. The sandbox can access the service, but the secret itself remains inaccessible to it.

Network policies define which external services an agent can interact with. Authorization policies specify whether it can, for example, modify a specific repository, retrieve a customer record, or perform a particular transaction.

Permissions for a specific run can be managed outside the sandbox. An orchestrator or authorization service determines what capabilities an agent will have, and a tool gateway verifies permissions when operations are performed.

The orchestration system coordinates these mechanisms throughout the agent's execution. The sandbox isolates execution, the identity management system handles credentials, and the gateway controls access to external resources.

Where the Agent Runs

Where the agent's control environment (agent harness) is run determines which parts of the execution are isolated and how the sandbox interacts with the rest of the infrastructure.

The control environment can run outside the sandbox and pass tool calls to it. The main agent loop runs externally, while the sandbox provides an isolated file system and execution environment.

The control environment can be run entirely inside the sandbox. The model client, tools, and working directory are in a single isolated environment. This simplifies access to local processes and files, but the sandbox must support the agent's dependencies and necessary network connections. Credentials and agent state management must also be considered within the same isolation boundary.

A third approach distributes the agent and its tools across multiple execution environments. For example, a restricted interpreter executes programs generated by the model, while a separate micro-virtual machine runs shell commands or performs repository operations. Each environment can have its own permissions and resource limits.

If the control environment runs externally, the orchestrator can replace the agent process and connect a new process to an already existing working environment. When running inside the sandbox, restoration depends on whether the agent's state is saved within the environment itself or in external storage.

Sandboxes for Browsers and Graphical Applications

For browser automation and working with graphical applications, an agent may need more than just executing commands in a shell. A sandbox can provide a graphical desktop, browser profiles, logged-in sessions, screenshots, mouse and keyboard control, and real-time screen streaming to allow human intervention.

Browserbase offers a managed browser infrastructure with session persistence and automation capabilities. Cua provides environments where agents interact with graphical applications through virtual desktops.

In a logged-in browser, an agent can perform actions through the interface that would require explicit authorization if accessed via API. In such environments, session isolation and control over allowed agent actions are particularly important.

Execution Observability

Even if execution is isolated, it can be difficult to understand what happened inside the sandbox. By observing process activity, file system changes, network requests, and resource consumption, one can reconstruct what the agent did.

Agent Sandboxes from Pydantic integrates with Logfire and links sandbox execution events with agent traces. Daytona uses OpenTelemetry to collect sandbox logs, resource metrics, and application traces, as well as data about SDK operations used to manage the sandbox.

This data helps verify results and monitor execution. Before moving to the next stage, the orchestrator can check file changes, identify unexpected network activity, or ensure that expected artifacts have been created.

Sandboxes as Agent Workspaces

A sandbox can exist longer than the session that created it. This allows multiple agents to work with the same persistent environment. Pydantic AI Workspaces provides a unified interface through which agents can access file systems and execution tools in different types of sandboxes.

One agent might make changes to a repository, a second might verify the result, and a third might decide if further refinement is needed. Each agent can have its own control environment or model, while the workspace remains shared.

Collaboration raises issues of concurrent access and workspace ownership. Two agents might interfere with each other if they edit the same files simultaneously. If they work in separate branches, mechanisms for comparing and merging results are needed. Workspace ownership, locking, and branching rules must be controlled outside of individual agent sessions.

The orchestration system must also track which working environment belongs to which task, what has already been done, and when the environment needs to be saved or deleted. The file system stores execution results, while information about the progress of work needs to be saved separately.

The Future of Agent Sandboxes

Most of these capabilities will likely become standard sandbox infrastructure over time. Isolation, state persistence, snapshots, branching, observability, and lifecycle management are already offered in some form by several vendors.

The question remains how much room for innovation will be preserved at the sandbox level itself. Will vendors continue to add features that change what agents are capable of doing? Or will the main development occur in the models that manage environments, tools, and orchestration systems that use sandboxes?
