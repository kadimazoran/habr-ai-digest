My name is Andrey Nepryakhin, and I am the CTO of AGIMA.

At AGIMA, we are building an internal environment through which employees interact with LLMs and agents. One of the most challenging tasks in such an environment is not just hiding a name or phone number before sending a request to an external model, but preserving the meaning of the request.

Imagine an employee writing, "Find Petrov's latest tasks for project X and compare them with meeting discussions." If you replace Petrov with NAME_1, and in a neighboring message, with a random NAME_7, the search will no longer understand that it's the same person. If you leave the name as is, it might leave the trusted environment. This creates a conflict between privacy and utility.

In this article, I will discuss an architectural approach that helps reconcile these requirements: entity mapping is stored within a secure environment, and only a typed alias is transmitted to the model. This is not "permanent anonymization" nor legal advice. It's more accurate to speak of reversible depersonalization or pseudonymization: additional information allows for the restoration of the original value, thus the mapping table itself requires protection.

Why NAME_1 Is Not Enough

A naive scheme has two flaws.

The first is the locality of numbering. A number is usually assigned based on its position in a specific message. In a neighboring request, the same person gets a different marker, and within a long dialogue, it's easy to end up with two entities of the same role but different numbers.

The second is the loss of type and relationships. For an LLM, the string NAME_1 says almost nothing. A phone number, surname, organization, and login all become identical pieces of text. The model might continue the phrase but will have a harder time correlating the entity with data from search and won't understand which operations are permissible.

Therefore, it's useful to separate two tasks:

  1. Hide the value. The external model doesn't need to see "Andrey Petrov."

  2. Preserve entity identity. Within a single request and related results, it's necessary to understand that [PERSON_1] is the same object as in the found documents.

This is similar to a foreign key in a database. A foreign key doesn't reveal the entire record but allows tables to be joined. The difference is that in our case, the key cannot be given to the user or the model as a way to restore the original value.

Basic Scheme: Mapping Lives Next to the Gateway

AGIMA's internal environment is structured as a gateway before the LLM: the request undergoes authorization, DLP check, depersonalization, and then is sent to the provider. On the way back, the response undergoes controlled rehydration. The user's identity is transmitted via a service header and proxy rights, not as text that the model can read or substitute.

req_map is not a dictionary that we inject into the prompt, but rather server-side session state. In production, the session mapping lasts for two hours, is limited to 500 tokens, and operates in insert-only mode: a repeated token does not overwrite the value. Context is not mixed with the mapping of another session. If incident investigation is required, the mapping is stored encrypted; access for disclosure is separated by the pii_reveal right and is audited.

A token can have a predictable format, for example, [PERSON_1]. This increases the chance that the model will not distort it in the reasoning context or when generating JSON. Security, in this case, should not rely on the secrecy of the token text, but on the inaccessibility of the mapping itself. If an attacker manually types [PERSON_1], the gateway should not "guess" the value: only tokens present in the current request's req_map are rehydrated.

This is precisely why a random ciphertext isn't always better. It's more difficult for the model, and its cryptographic properties don't save the architecture if the key or mapping table lies next to the prompt. In Microsoft Presidio's documentation, a similar separation is visible at the operator level: there's replacement, masking, encryption, and decryption; stateful sessions and secure state storage remain the integrator's responsibility.

Entity Resolution: One Employee – One Entity in the Correct Context

The most common mistake in searching corporate data is treating every name as equally sensitive and equally useless. In a work request like "call Petrov for a review," the surname might be a regular reference to an employee the user is already authorized to search for. In a request to a client export, the same string might require a different policy.

We solved this not with another large model, but with a directory and matching rules. In the dev tenant, the directory includes several hundred employees and client legal entities from internal systems and about thirty internal tools. Records are divided into employee, legal_entity, and other, are updated and revoked via API/UI by the tenant administrator, and transliteration and lemmas are calculated on the matcher's side. Suppression is transparent: reason=directory is highlighted separately in the UI.

For a new request, the pipeline might look like this:

  1. A detector finds a span and type: Petrova, PERSON.

  2. A normalizer receives the lemma and morphological features: Petrov, genitive/dative context.

  3. An entity resolver matches variants like Petrov, Petrova, Petrov, apetrov with an internal entity_id.

  4. A policy engine checks if this entity can be used in the specific source and action.

  5. [PERSON_1] is sent to the prompt, not the original string; the internal entity_id from the directory is not passed in the prompt.

For search, this changes everything. The index and filters work on the stable internal entity_id of the directory corpus, while only [PERSON_1] is sent in the prompt. The LLM receives a typed reference but not the entity_id itself or a way to reveal the full name.

Where the Directory Should Not "Resolve Everything"

The employee directory is not a whitelist to bypass DLP. It answers the question "which object is meant," not "is it permissible to show its data." These decisions must be separated.

For example, searching for an employee's tasks might be allowed, but displaying their phone number might not be. A single surname without a first name should not be automatically resolved by the directory: in case of ambiguity, the policy chooses masking. An employee and a client legal entity are different types of entities with different rules. For clients, the directory should be a separate environment altogether, and client names and metrics cannot be transferred to public material without permission.

Four Verdicts Instead of One "Block" Button

Internal discussions on DLP converged on the idea that the detector and depersonalizer solve different problems. A practical policy usually has at least four outcomes:

Such a breakdown is more useful than a total ban. If every name is blocked, employee search will cease to be functional. If everything from the internal directory is passed through, data might accidentally be exposed to an inappropriate source. Mapping preserves connectivity, but the policy engine still decides what is allowed.

The Way Back Is More Complex Than the Way Forward

Checking only the prompt is insufficient. The model can return an entity in text, JSON, a quote, tool arguments, or a streaming response.

For regular text, only tokens present in the current request's mapping can be rehydrated. For JSON, the structure and allowed fields must be checked. For tool calls, the tool name and arguments must be checked before execution. For streaming, the mode is selected by policy: buffer (response is returned entirely after checking), window (checking with a sliding fragment with truncation), or pass-through with post-scan. This is a conscious trade-off of latency for strictness.

Law and Terminology

In the Russian legal context, it's important not to call such a scheme full anonymization. Federal Law 152 defines anonymization as actions after which, without additional information, it's impossible to determine the data's affiliation with a specific subject. If the gateway has a protected mapping, it's more accurate in technical writing to speak of "reversible depersonalization" or "pseudonymization" and to separately describe where the additional information is stored.

The same law requires limiting processing to specific purposes, not collecting excessive data, maintaining its accuracy, and anonymizing or destroying it when the processing purpose is achieved. This is not a ready-made compliance checklist: the operator needs to assess their roles, processing grounds, cross-border transfers, retention periods, and security measures.

How to Check That Search Hasn't Broken

The minimum test set should check not only "was PII found" but also the preservation of meaning:

  • One employee in six grammatical cases and two transliteration variants;

  • Two employees with the same surname;

  • One name in the query, found document, and model response;

  • Repeated mention of an entity in a neighboring message;

  • Attempt to manually forge an entity token;

  • A query without rights to the source, where a directory match should not grant access;

  • JSON and tool calls with entity tokens;

  • A streaming response where a forbidden value appears after the first fragment.

Metrics should be separate: detection completeness, false positives, entity match success rate, policy decision correctness, and absence of rehydration of someone else's mapping. There is no automatic search relevance test yet: instead, a canary test mask → upstream → rehydrate runs every 10 minutes, along with policy verdict match metrics, red teaming, and a feedback loop for FP/miss. A single overall "protection percentage" hides where exactly the system is making mistakes.

Practical Checklist

  1. Define the boundary of the trusted environment and prohibit the model from accessing the mapping.

  2. Separate detection, entity resolution, policy engine, and rehydration.

  3. Store the original value and entity ID separately; use request-scoped mapping by default.

  4. Normalize cases, transliterations, and homonyms, but do not turn the directory into an access permission system.

  5. Assign a source to each signal: regex, NER, PII model, decoder, or rule.

  6. Check the response, JSON, tool calls, and streaming, not just the input text.

  7. Maintain an audit log of disclosures; store keys and long-term mapping separately from the main database.

  8. Publish internal details only to the extent that they do not reveal client data, secrets, or real identifiers.

The main takeaway is simple: depersonalization doesn't have to destroy meaning. To achieve this, stop considering a placeholder as a substitute for a name and start designing an identity layer—with mapping, lifecycle, rights, and tests. The model sees a stable entity, and the trusted environment decides what value it represents and whether it can be returned.
