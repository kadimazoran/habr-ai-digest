Why approved=true doesn't link a human's decision to the actual call—and how Action Envelope, a fresh pre-read, and a post-write verification closed this specific failure scenario.

I've been reading Habr since 2010, but decided to write my own article for the first time. And the last days of August gave a good reason for this.

On August 26, details of a very unusual story emerged: about 1200 AI agents, which were supposed to work in isolation, found a way to communicate through an unauthorized channel. Approximately 700 of them then participated in an attack on Hugging Face.

In the dry language of a police report, it turns out almost like this: "a group of agents, by prior conspiracy, using their own communication channel...". Only this is no longer a scenario.

So what – is it time to look for a deserted island without electricity and internet? Or should we still try to figure out what exactly is the problem here?

I chose the second option.

Because if you remove all the drama, what remains is a rather down-to-earth engineering question: what was the system allowed to do, what did it actually do, and can we prove it?

It is this question that I decided to test on my own laboratory workflow on n8n + Groq + MCP + Bitrix24. I put human approval before the task modification operation, conducted a series of control runs—and quite quickly discovered an unpleasant thing.

A human could see and approve action A, and the next part of the workflow—try to perform action B.

APPROVED A ≠ ATTEMPTED B

Bitrix24 rejected that attempt, so no undesirable change occurred in the system. But the defect itself was already established: the positive flag approved=true existed, but the link between the approved parameters and the parameters of the actual call—did not.

The devil turned out not to be in the "disobedient model," but in the wiring between the nodes.

In short. A human approved action A, but an independently configured downstream node could attempt to call action B. Bitrix24 rejected this attempt, and the task state did not change. Fix: a single Action Envelope, a fresh pre-read, a linked update_task, and post-write verification.

First—evidence: observable technical confirmations

In the early version of the workflow, the approval screen and the execution node received parameters independently. In a simplified form, it looked like this:

BEFORE

Approval:
  requested_title = "A"

Downstream execution node:
  title = "B"  ← configured independently

The human confirmed the change they saw on the screen. After that, a separate MCP client node formed an update_task from its own configuration. There was no technical invariant approved parameters == invoked parameters between them.

In one of the runs, this ceased to be just an architectural assumption:

It is important not to overstate the result in hindsight. The experiment did not show that the unapproved change was successfully applied to Bitrix24. Nor did it show that the LLM independently substituted parameters. It showed a narrower and practically important fact: the orchestration path allowed an attempted call whose material parameters did not match what the human approved.

This was already enough to stop and redesign the architecture.

How the experiment was set up

I was not trying to test "AI agent security in general." There is no single honest test for such a setup. A narrow, observable operation was chosen: to change the title of a synthetic task in Bitrix24 and save evidence—observable technical confirmations—at each significant boundary.

In different runs, I intentionally changed the configuration of approval, the execution path, the comparison with the fresh state, and the extractor. Some scenarios were supposed to end with a permitted exact write, others—to remain without a write, and a third reproduced parameter drift. After the fix, the mechanism was re-tested on a positive linked path.

Such a setup has a practical advantage: you argue not with the general impression of the demo, but with a sequence of observed events. What was shown to the human? What was in the actual call? What did the target system return? What did the new read show? If there is no data for one of the links, it remains a gap in the evidence, not filled by guesswork about the status of the entire workflow.

Where the write authority was actually located

The first suspicion in the AI agent story usually falls on the model: "it hallucinated," "it decided on its own," "it bypassed the human." However, in this experiment, such an explanation would be technically incorrect.

The architecture looked like this:

User intent ↓ AI Agent: Groq model + read-only Bitrix24 tools ↓ Proposed action ↓ n8n orchestration: approval + deterministic MCP write ↓ Bitrix24 MCP ↓ Synthetic Bitrix24 task

The authorities were divided.

  • AI Agent authority: only read-only Bitrix24 tools. The model could read the task state and suggest a change, but could not perform a write.

  • Downstream orchestration authority: a separate deterministic MCP client node could call update_task after passing control nodes.

  • Human authority: the human approved the target system and object, the operation, the observed initial state, the requested change, and the fields that should remain unchanged.

Consequently, parameter drift occurred not because the model received approval for A and "changed its mind" in favor of B. The Approval node and the execution node simply had independent sources of material parameters.

This difference seems minor when we discuss the system in words. For investigation, it is fundamental: the mechanism must be corrected, not the most visible component. A stricter system prompt here will not create the missing data binding between the two n8n nodes.

What approved=true actually doesn't prove

The flag itself is useful:

{ 
  "approved": true 
}

It establishes that a human made a positive decision. But for a workflow that changes the system state, this is not enough. From such an object, it is impossible to restore:

  • which target system and object the human saw;

  • which operation they authorized;

  • what values of material parameters were shown;

  • what initial state they considered current;

  • where the execution node got its arguments from;

  • whether they matched the approved ones;

  • what state resulted after the call.

The problem is not in the logical type boolean. The problem is that boolean does not carry the decision object.

Approval status ≠ approved action object
Approval status ≠ invoked parameters
Approval status ≠ verified outcome

Therefore, the corrected version began not with an additional check of the flag, but with a single Action Envelope.

After the fix: a single Action Envelope

In our narrow test, the object looked like this:

{ 
  "target_system": "Bitrix24", 
  "task_id": 4, 
  "operation": "update_task", 
  "expected_title": "LAB-AGENT-EXEC-002 - BOUND ACTION TEST", 
  "requested_title": "LAB-AGENT-EXEC-002 - CLEAN TRUE PATH" 
}

There is no universal schema for all agent systems here. The fields are chosen for one title modification operation:

  • target_system defines the destination system;

  • task_id—the specific object being modified;

  • operation—the authorized operation;

  • expected_title—the baseline against which the human makes a decision;

  • requested_title—the requested new state.

The Approval message was now built from this same object:

CONTROLLED ACTION APPROVAL

Target system: {{ target_system }}
Target object: Task ID {{ task_id }}
Operation: {{ operation }}
Observed baseline: title = {{ expected_title }}
Requested change: title = {{ requested_title }}

Approve execution of exactly this action?

After approval, the same values were used further:

AFTER

ActionEnvelope.requested_title = "A"

Approval:
  title ← ActionEnvelope.requested_title

Execution:
  title ← ActionEnvelope.requested_title

The Action Envelope does not make all conceivable forms of substitution or circumvention of approval impossible. It eliminated the specific mechanism discovered: independently set parameters in the approval node and execution node.

Between approval and write: is the initial state fresh

Even a perfectly linked object can become outdated while the human thinks or the workflow waits for continuation.

S0 — state shown during approval
S1 — state immediately before execution

If S0 ≠ S1, the premises for the decision have changed. Therefore, before writing, the corrected workflow performed a new get_task_by_id using the task_id from the Action Envelope:

get_task_by_id(
  taskId = {{ Edit Fields.task_id }}
)

The obtained title was compared with expected_title:

fresh_title = response.content[0].text.match(/"title":"([^"]+)"/)?. [1]
expected_title = EditFields.expected_title

continue only if fresh_title == expected_title

But the surprises didn't end there.

In one of the debug runs, the target system's response contained the correct current value, but the old extractor expression returned undefined. The comparison node went to FALSE, and the write did not execute. After fixing the extractor, the same value started to be extracted correctly.

This means the check was also a regular software system—with its own parser, its own errors, and failure scenarios.

From this, an important practical point follows. Binary logic is not enough:

MATCH / MISMATCH / UNKNOWN / ERROR

MATCH: the fresh baseline matches the approved one;

  • MISMATCH: the state of the target object has actually changed;

  • UNKNOWN: a usable comparison value could not be obtained;

  • ERROR: the preliminary read or evidence processing resulted in an error.

undefined should not be masked as a real mismatch of states. Moreover, it should not accidentally become MATCH. In our run, execution remained closed—the check worked on a fail-closed principle. But diagnostically, "the check could not compare" and "the state has changed" are different facts.

A separate run with a stale state indeed recorded S0 ≠ S1, and the write did not occur. However, it used an old extractor, later caught returning undefined. Therefore, the fact of the stale state is established, and attributing the blocking solely to the comparison mechanism would be stronger than the available evidence.

Linked call: the same parameters reach update_task

After a fresh pre-read and a positive comparison result, the workflow constructed the write from the Action Envelope:

update_task(
  taskId = {{ Edit Fields.task_id }},
  title  = {{ Edit Fields.requested_title }}
)

In the positive run, this meant:

taskId = 4
title  = "LAB-AGENT-EXEC-002 - CLEAN TRUE PATH"

At this point, it's very easy to put a green checkmark and finish. The target responded: Task successfully updated. What else to check?

But acknowledgement and final state are not the same evidence. In a simple synchronous operation, the response is sometimes sufficient. In another API, it might only mean received, accepted, or queued. Therefore, the semantics of the response should not be guessed from friendly text, but linked to the behavior of a specific integration and the cost of error.

For this experiment, I did not consider the acknowledgement the final point.

Verification: what remained in Bitrix24 after the write

After update_task, the workflow performed a new read:

verified = get_task_by_id(ActionEnvelope.task_id)

The check conceptually looked like this:

verified.title == ActionEnvelope.requested_title

This is a conceptual record, not the literal production code string. In fact, the workflow made a new MCP call get_task_by_id, and the returned state was saved as evidence.

How I reconstructed the run, not just looked at the workflow status

The success status of the entire n8n execution is convenient for operation, but too coarse to answer our question. Therefore, the approval object, the actual call, the target system's response, and the re-read state were saved and considered as different evidence objects.

Approval object
        ↓
Invocation evidence
        ↓
Target acknowledgement
        ↓
Fresh target state
        ↓
Deterministic comparison

Screenshots helped to see the configuration and the progress of the run, but were not the main source of truth during the analysis. Structured call data and the state re-read from the target system were stronger evidence.

This is the role of the Harness in this experiment. Not "a smart system that decided if everything is safe," but a discipline of reconstruction: not to lump different events into one word success, to save them separately, and to check which conclusion each of them actually supports.

The minimal control contract derived from the experiment

For an agent workflow that changes the system state, I would now check eight things:

  1. The action object exists before approval.

  2. The human's decision is linked to the target system and object, operation, and material parameters.

  3. The actual call receives values from the same linked object—or is deterministically compared with it.

  4. Material preconditions are re-read immediately before the write.

  5. MATCH, MISMATCH, UNKNOWN, and ERROR remain distinct states.

  6. The target system's acknowledgement is saved separately and not automatically renamed to "confirmed result".

  7. A new read after the write confirms the requested state where the consequences of an error require such depth of verification.

  8. Approval, actual call, response, and verification remain separately reconstructible.

This is not a new universal standard for agent safety. It is a compact engineering pattern derived from a specific tested workflow.

Why this boundary became a separate engineering topic

While I was preparing the experiment and its public version, several publications appeared almost simultaneously with adjacent problem statements.

On April 18, 2026, Christopher Koch and Joshua Andreas Wellbrock published the preprint Beyond Task Success: An Evidence-Synthesis Framework for Evaluating, Governing, and Orchestrating Agentic AI. The authors call the problem close to ours the governance-to-action closure gap: rules define what should be allowed, but the system must still show where these obligations are linked to a specific action and how this is then confirmed.

On June 1, Xiaoqi Weng published What You Approve Is What Executes: Consent Integrity for Black-Box LLM Agents. Here, the question is posed even closer to our case: a human's decision must be tied to the exact executable action, not to the agent's retelling of that action.

On June 29, the preprint Behavioral Governance for Autonomous AI Agents: The AgentBound Framework introduced the idea of a canonical action—a structured object with operation, resource, parameters, risk, and execution context, which undergoes external verification before the call.

These are different projects, threat models, and levels of formalization. Together, they show a more precise problem statement: the binding between human approval or governance and a specific runtime action is becoming a separate subject of engineering attention. The practical question here is simple: what exactly did the human see, to what action does their decision relate, and what ultimately reached the execution boundary?

Another similar story appeared on Habr. On August 25, Alexander (LightBearing) published the article "The agent said it was ready and lied. How I put a judge over it." His case is different: an AI agent was writing an application, green reports diverged from the actual interface behavior, and the author introduced independent acceptance. I particularly remember the wording: "the agent and I simply have different definitions of the word 'ready'." In both cases, the same question arises: what actually happened behind the formal message "ready"?

What I would check in a real agent system

If I had an industrial or pre-production workflow with human approval, I would start with six questions:

What exactly did the human see?
What material parameters did they approve?
Where did the actual call get these parameters from?
Is the state of the target object checked immediately before the write?
Is the acknowledgement saved separately?
Is there an independent check of the fresh state after the action?

These questions do not require immediately rebuilding the entire system. They quickly show where the evidence is, where real control exists, and where only the assumption that the approved and executed actions coincide currently lives.

Instead of a conclusion

Human approval is not just a decorative button. It can be a full-fledged control when the approved object remains linked to the actually invoked action.

In the early version of my workflow, this link was missing: the human approved A, and the downstream orchestration attempted to execute B. Bitrix24 rejected the attempt, so the task state did not change. But the experiment allowed us to see the mechanism of the break itself.

In the corrected version, the approval screen and the actual call received material parameters from a single Action Envelope. A fresh preliminary read checked the initial premises, the linked call executed the request, the target system returned an acknowledgement, and a new read after the write confirmed the final state.

Therefore, for an AI workflow that changes the system state, it is not enough to store approved=true. You need to be able to restore four things:

→ what the human saw
→ what exactly they approved
→ what the system actually called
→ what state resulted after the call
