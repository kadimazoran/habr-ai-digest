There's a lot of talk about Harness itself lately. Skills, MCP, tools, orchestration, and sub-agents are all recent innovations. However, the current state has shortcomings: in one configuration, an agent reads directory structures, finds key files, and requests specific snippets. In another, it greedily reads everything, filling up the context. Or an agent might forget something, or misuse tools and MCP/sub-agent calls.

Engineers then tweak Harness settings. But manual tuning is difficult and resource-intensive. Now, Google has released the open-source framework Harness² for self-improving AI agents. It allows agents in OpenCode and Codex to independently adjust instructions, skills, and other components during operation.

This article explores Harness² – a plug-and-play framework from Google Research for recursive harnessing in an open world.

The word "harness" in the context of AI originated from engineering and wasn't immediately adopted. Literally, it means "a set of straps." In development, it came from the testing domain, signifying the infrastructure and conditions for running code. In our case, it has evolved to encompass the actions needed after an LLM to ensure it solves tasks effectively and with fewer errors. Currently, this includes context management, tools, memory, skills, MCP, and multi-agent logic.

In the ideal perception of an AI agent, the LLM is merely an endpoint that accepts JSON (or another format) and returns JSON.

Without a quality harness, even a top model remains a chatbot; with a good harness, an average model sometimes solves tasks more reliably. This is precisely why we have things like orchestration and multi-agent systems – an expensive model for verification and complex design/reasoning, a medium one for generation and orchestration, and a fast, cheap one for mass sub-agent calls.

Such a distribution requires a unified access layer to different models, and here, the OpenAI-compatible gateway BotHub (https://openai.bothub.chat/v1) becomes a practical solution. Official SDKs work without changes, and upon registration via the referral link, you receive 300,000 CAPS.

In the README of the Harness² framework on GitHub, there are exactly eight Harness components, neatly organized: system prompt, guardrails, memory, tool guidance, subagents, skills, scripts, and plugins. The first four dictate how the model builds context, what it reads first, what it's forbidden to do, what to remember between steps, and how it's instructed to use tools. Tool guidance and scripts define the interface with tools – when to call search_docs and when to simply respond in its own words. Subagents are involved in delegation when one agent breaks down a task into parts, and another agent executes those parts. Plugins are middleware that fine-tune behavior within the tool invocation loop.

Now, about the square in the name. The "two" signifies two levels of recursion. The first level – task-level recursion – operates within a single task. The agent initiates it within the basic harness, receives a result, then the harness editor suggests modifications. These modifications are tested on the same task, and an improved harness version is assembled from successful ones. The second level – harnessing-level recursion – operates *between* tasks. After a task is completed, the system records accepted changes and "lessons learned through behavior" into a persistent library called the improvement harness, which then guides the editor on what modifications are worthwhile to suggest next time.

Simply put, the first level fixes the harness for a specific task. The second level fixes the fixing process itself, making the next task's fix faster and more accurate. Hence the square: a harness that improves the harness. Incidentally, in the arXiv preprint, the authors explicitly state that each new task still starts with the same basic harness – only the experience library is carried over.

Let's now explore this Harness squared.

How Does It Work?

The first level of recursion is what happens within a single task while it's being executed. The heart of this level is the Propose-Probe-Compose loop. This cycle involves proposing modifications, testing their effect on the same task, and composing an improved harness from the behavioral differences between runs.

It all begins with a reference execution – the first run of the task with the basic harness. This run is crucial for capturing the task's solution method and its operation sequence – where it stopped, what it read, which tool it called unnecessarily, what it failed to check. The trajectory and artifacts of this run become the baseline for comparison.

Next, the editor comes into play. In the default configuration, this is Claude Opus 4.8 (a slightly older model, but a newer one can be used). Yes, the framework from Google Research uses a competitor's model. The editor receives the task, the current harness, the reference run's trajectory, and, if available, the library of past harnesses. Based on this data, it proposes two candidates.

The first is an invariant edit. It addresses common agent weaknesses such as planning, tool usage, context management, and delegation. For instance, if an agent greedily reads the entire repository, an invariant edit might add a new explicit rule to Tool Guidance, instructing the agent to first examine the directory structure before selectively requesting files.

The second option is a domain-specific edit, created to solve problems within a particular domain – be it legal procedures, office standards, or specifics of working with budgets or tables.

Then comes the Probe step – the most straightforward and most important. Each candidate is run on the exact same task, under the same conditions, and with the same executor. Then, the analysis of behavioral differences begins – checking if the trajectory has changed, if new steps have appeared, if old ones have disappeared, and if the output artifact is different. This step verifies what has changed and whether the change leads to the elimination of the observed weakness. In other words, there is no single correct answer here.

In one of the JobBench tasks (a benchmark we'll discuss later), the agent was supposed to compile a set of documents with consistent figures. The first run scored 43.1: numbers in different files didn't match, and the output documents were not re-opened or verified. The modifications added two things – source verification and mandatory re-opening of final artifacts – and a repeat run yielded 77.8. Of course, this is a single example and doesn't prove that the same modification will work on another task.

Finally, the Compose step. The composer examines three sets of data – the reference run, the runs with the invariant and domain-specific candidates – and decides which modifications to accept, reject, or merge. The accepted changes are incorporated into the final harness, which is then run again as the final version for this task. All of this is within the budget of k: with k=1, the cycle runs once; with larger values, it either runs in parallel (multiple candidates simultaneously) or sequentially (a chain of several PPC steps). Parallel recursion expands the pool of candidates, while sequential recursion deepens the refinement. On benchmarks, increasing the budget from 1 to 5 added more points but also cost significantly more.

However, there are limitations – behavioral difference does not guarantee correctness. If two versions of the harness behave differently, it doesn't mean one is better. The system might adopt a change that simply looks better but is unlikely to work on the next task. This is why the mechanism strives for comparison and reflection.

The second level, harnessing-level recursion, comes into play after the task is completed. A special component, called the reflector in the code, reviews the entire recorded process, which includes the reference run, proposed candidates, the composer's decision, and the final selection. It extracts lessons learned – under what conditions did a particular modification have what behavioral effect. A lesson is saved only if it's confirmed by comparing executions, not just articulated by the editor in words. Then, the accepted harness and these lessons are stored in a persistent library called the improvement harness. Subsequently, an EXPERIENCE.md file appears next to the file tree, describing applicable scenarios that inform the lessons.

The next task does not inherit the configured harness of the previous one, by the way. Only the experience library is inherited to guide the editor.

Putting it all together, we get a rather neat construction. Within a task, a fast "propose-check-compose" loop operates, fixing the harness for the current context. Between tasks, a slow loop accumulates confirmed experience and makes subsequent modifications more targeted. Neither of these loops modifies the model's weights.

About Benchmarks

It's time to talk about benchmarking. The authors ran Harness² on three benchmarks, each testing a different aspect of agent work.

WorkBuddy-Bench covers office, web, and coding tasks – from compiling documents to writing scripts. JobBench involves end-to-end professional tasks with a long execution horizon, closer to what a person does during a workday. And LAB by Harvey is a legal benchmark where the metric is partial pass rate across specific criteria.

But the most interesting part emerges when you look not at the averages, but at the breakdown by models and executors.

Table 1 from the preprint shows WorkBuddy-Bench with two open executors, Gemini 3.5 Flash and GLM-5. Pay attention to the Harness² row for GLM-5 under OpenCode: it went from 58.4 to 77.1, a +14.7 point increase on the Code subset. This is even higher than the average gain of 11.5 and clearly illustrates what "behavioral difference" means in practice. Even more intriguing is the + Recursion row: with k=5, GLM-5 gains an additional +4.8 on Code, which is no longer a single jump but an accumulated effect from several sequential or parallel steps.

Table 2 takes us to JobBench and LAB. Here, the absolute numbers are more modest but no less telling. For Gemini 3.5 Flash under OpenCode on JobBench, the gain from 31.5 to 36.0 represents the aforementioned +4.5 from the summary. And on LAB for GLM-5, there's a jump in Partial Pass Rate from 59.6 to 71.4 – a +11.8 percentage point increase. Incidentally, if you look closely at the + Recursion row for LAB, there's also a +6.7 – this is an addition from budget scaling, and it's almost as significant as the initial step itself.

Now, about the pattern the authors call "weaker executors benefit more." This sounds like a consolation prize for weaker models, but in reality, it's a significant shift in how to think about the quality of an agent system. GLM-5, after one step of harness optimization, reaches 75.7 on WorkBuddy-Bench (OpenCode) and 75.3 (Codex), while the base Gemini 3.5 Flash without optimization shows 72.4 and 74.5 respectively. This means a weaker model with an improved harness outperforms a stronger model with the default harness.

ReasoningBank and Harness Scaling are alternative methods against which Harness² was compared. ReasoningBank on coding tasks drops by 6.6 points below the base harness, and Harness Scaling underperforms the base in seven out of twelve "benchmark – configuration" pairs. Harness², on the other hand, exceeds the base harness on WorkBuddy-Bench Avg. and JobBench Score in all four configurations. Recursive harness improvement is not an automatic "make it good" button. The method matters, and naive approaches can be detrimental.

And the last image is perhaps the most direct answer to the question "what if the editor and executor are the same model?". The bar charts for WorkBuddy-Bench, JobBench, and LAB show results for five different models acting as both executor and editor simultaneously, with k=2. It's evident that all models show improvement, but Opus 5's gain is modest (+3.0 on WorkBuddy, +5.5 on JobBench), while GLM-5's is more noticeable (+4.1 and +2.9). It can be cautiously stated that Harness² does not require the editor to be smarter than the executor. The behavioral difference comparison mechanism works even when both roles are filled by the same model, although the absolute numbers naturally depend on its capabilities.

The cost is also worth mentioning. Each recursion step involves additional task runs, meaning more tokens and time. The preprint includes a separate analysis of the trade-off between the k budget and the gain, showing diminishing returns from scaling. For example, moving from k=1 to k=5 adds 2.9–3.9 points on WorkBuddy-Bench, 3.0–4.2 points on JobBench, and 2.6–6.7 percentage points on LAB. This is not free, and in production, you'll need to decide if you're willing to pay for these extra points by increasing runs fivefold. However, the mere fact that there is an improvement and it's predictable already distinguishes Harness² from methods that yield negative results on the same benchmarks.

How to Try It?

The theory and numbers are more or less clear. If you're interested and want to get your hands on Harness², you should start with the GitHub repository.

The easiest way to see how it works is with a local demo. You'll need a Linux machine (macOS is not officially supported), Python 3.12, and the uv package manager. The demo runs both recursion levels with deterministic "editors" and actual Python script execution, so you can observe the system's behavior in about ten minutes, without a single model call. It looks something like this:

git clone https://github.com/google-research/harness2.git
cd harness2
uv venv --python 3.12 .venv
source .venv/bin/activate
uv pip install -e '.[render]'
harness2-demo --output runs/demo --k 2

The --k 2 flag sets the recursion budget, meaning how many times the "propose-check-compose" loop will run within a single task.

For actual runs on benchmarks, you'll need more infrastructure. A Google Cloud project with Vertex AI access, the installed gcloud CLI, Node.js 20+, and, depending on the benchmark, Docker for WorkBuddy-Bench or Pandoc with Poppler for LAB. Models are invoked via Vertex AI, which is a paid service, so you'll have to pay for runs on real models. Two executors are supported: OpenCode (default) and Codex. The latter is accessed via the Responses API, and for Gemini on Vertex AI, there's a special bridge on a local LiteLLM server.

Running a single job on the LAB legal benchmark looks like this:

cp .env.example .env
# edit .env: Vertex AI project and model IDs
gcloud auth application-default login

harness2-setup lab
harness2 --bench lab --k 1 --mode parallel \
  --only-domains antitrust-competition --max-tasks 1
harness2-judge --bench lab --k 1 --mode parallel
harness2-report --bench lab --k 1 --mode parallel

Here, --mode parallel enables parallel recursion – multiple candidates are tested simultaneously. The sequential option (--mode sequential) deepens the refinement but requires more time. You should start with --max-tasks 1 and a small k just to see how the system behaves and what its token cost is.

Harness2 is a research framework, not an officially supported Google product. The API may change, things might be unstable, and the community is still forming.

Conclusion

The main shift brought by Harness² is the separation of agent engineering from model engineering. Previously, the quality of an agent system was almost entirely determined by the strength of the base LLM, and the harness was considered auxiliary – "just tweak the prompt, add tools." Now, a mechanism emerges that systematically and automatically improves the harness itself, based on observed behavior.

If harness quality can yield +11 points without a single fine-tuning step, then competition might shift. Instead of competing on models, they will compete on the sophistication of their harnesses. The gap between a flagship and a budget model can be closed with a quality harness, though not always.
