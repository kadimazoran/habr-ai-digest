I write books, and besides the books themselves, a lot of other text accumulates during the day: messages, letters, tasks for neural networks. Speaking is faster than typing, so I dictate most of it. Only live speech, transcribed word for word, reads poorly. Here is a phrase that Whisper recognized without a single error:

So, like, I, uh, wanted to say that, uh, tomorrow... the call tomorrow is postponed, uh, to three o'clock, no, to four.

And this is what I wanted to send:

I wanted to say that the call tomorrow is postponed to four.

The second option is the actual response from the program this article is about. From the moment I released the key to the text being inserted, less than two seconds passed. I'll tell you how it works and what pitfalls I stumbled into, and at the end, I'll provide a link to the code: it's open-source and free.

Recognition: Handy and Whisper

For the dictation itself, I used Handy, an open-source program (MIT) based on Tauri. You hold down a hotkey, speak, release it, and the text appears wherever the cursor is, in any window. Speech is recognized by Whisper directly on the computer; the audio doesn't go anywhere.

The model is Whisper Large v3 Turbo. On an RTX 4080 Super, eight seconds of speech are recognized in 0.17 seconds, and forty-two seconds in 0.45 seconds. It will be noticeably slower without a graphics card.

For Russian, there's a build called klava-nevinovata: it includes a pre-trained Whisper model for Russian and protection against looping on silence – that's when the model, instead of a pause, writes "and I want and I want and I want...".

One tip right away: in the settings, set "Unload model" to "Never". Otherwise, after a period of inactivity, the first dictation will wait for the model to load into memory again.

Why Regex Isn't Enough

The first thought is to clean up "uh" and "like" with a list of replacements. It won't work:

  • "This course" becomes "course", and "Like, great" becomes "Great". The word is the same, but in the second case, you also need to remove the comma and capitalize the first letter. And sometimes "like" is necessary and cannot be removed.

  • "To three o'clock, no, to four" becomes "to four". Self-correction cannot be described by a rule.

  • The same applies to repetitions, cut-off words, "you know" and "listen" in the middle of a phrase.

This requires a model that understands meaning. Handy has post-processing for this: the recognized text is sent to any OpenAI-compatible API, and the model's response is inserted into the window. I use Claude Sonnet 5.5; cleaning takes from one and a half to three seconds.

Why an Intermediary?

You can configure Handy with the API address, key, and prompt, and it will work. I started that way, but I quickly created a layer in between and called it Chistovik (Clean-up). It's a single Python file using only the standard library. It listens on localhost:8765, and Handy sees it as a regular API. In Handy's settings, instead of a prompt, there's just one line ${output}, and the intermediary does the rest:

  1. The prompt and dictionary are in two text files and are re-read with each dictation. Correct a line, dictate again – without restarting and without going into settings. I corrected the prompt dozens of times in the first few days, so this is the main convenience.

  2. One warm connection. Handy creates a new HTTP client for each request, meaning it goes through TCP and TLS anew each time. The intermediary maintains a single connection and refreshes it if there haven't been any dictations for a while.

  3. The API key is not stored in Handy's settings but in a separate file or environment variable.

  4. 10-second timeout. If the API is silent, Handy inserts the raw text instead of freezing.

The main substitution looks like this:

def rewrite(payload): 
    msgs = payload.get("messages") or []
    if not msgs or not isinstance(msgs[-1].get("content"), str):
        return False
    tmpl = here(CFG["prompt_file"]).read_text(encoding="utf-8-sig")
    text = msgs[-1]["content"].strip()
    msgs[-1]["content"] = tmpl.replace("${dictionary}", dictionary() or "(empty)").replace("${output}", text)
    return True

A Dictionary That Understands Context

Whisper confuses rare words, names, and slang. For me, for example, "ИИшный" (AI-ish): Whisper hears it as "яичный" (egg-related). Handy has a built-in dictionary, but judging by the description in the program itself, fuzzy correction only works for words with Latin characters and numbers, so it doesn't help with Russian words.

Moreover, simple replacement is harmful here: "яичный" can also be literal... perhaps... someone has such a word in their correspondence. However, you can explain the condition to the model in words. A dictionary entry looks like this: on the left is how to write it, on the right is how the recognition hears it, and in parentheses is when to replace it.

ИИшный, ИИшные, ИИшно ← иишный, яичный (replace «яичный» only when the text is not about eggs or food)
Claude (always written Claude, in any grammatical case) ← Клод, Клоду, Клода, Clod, Clot

The explanations in the repository are in English, but the model understands them equally well in Russian. Test:

Suggest, uh, a recipe for an egg salad, like, something quick.

→ Suggest a recipe for an egg salad, something quick.

Listen, the text turned out kind of egg-related, like, you can really feel that a neural network wrote it.

→ Listen, the text turned out kind of AI-ish, you can really feel that a neural network wrote it.

The salad remained salad.

Prompt Pitfalls

The Model Responds to Dictation

I dictated "write a letter to the boss saying I won't come tomorrow" and got a letter. The model took the dictation as a request to itself. Two things helped: the transcription is enclosed in a <dictation> tag, and the rules explicitly state that questions and requests from the text are not executed; it's just text for cleaning.

Write, please, uh, a letter to the boss, that I, uh, won't come tomorrow, I'm sick.

→ Write, please, a letter to the boss, that I won't come tomorrow, I'm sick.

The Model "Ennobles" Speech

Models like to replace colloquial words with "proper" ones: "прикольно" (cool) becomes "интересно" (interesting), "пофигу" (don't care) becomes "неважно" (unimportant), "чё" (what) becomes "что" (what). Messages start to sound like someone else's voice. Rule: colloquial remains colloquial; do not replace a person's words. Examples directly in the rule work better than general statements.

Well, that's cool, I really don't care, what they say.

→ That's cool, I really don't care, what they say.

The Model Comments

When I dictated about recognition errors themselves ("instead of Claude, it wrote me some Clot, Silod"), the model added an explanation: here, the person is talking about recognition. But the response is inserted directly into the window where I'm typing. The last rule in the prompt helped: the response is inserted where the person is typing, so it should only contain the finished text. And a separate rule: if the person provides examples of recognition errors, leave those examples as they are.

"Вот" (Like/Here) Can Be Necessary

If "вот" is in the list of filler words, the model cleans it out entirely, but sometimes it carries meaning. Examples in the rule itself helped:

Like, great, like this course, uh, and we'll take it.

→ Great, this course and we'll take it.

Personal Rules

My short "чё" (what) Whisper hears as "чёрт" (devil), although I don't say that word. Such a rule lives only in my prompt; it's not in the public version: everyone has their own peculiarities, and it's convenient to add them yourself.

Integration Pitfalls

Post-processing errors are not visible. With any error, Handy silently inserts the raw text. For several days, my dictations went through without cleaning, and I thought the model was just performing poorly. Therefore, the intermediary writes a log for each dictation: time, status, and duration, without the text itself. It's also better to check through the program itself, not with a separate console request.

localhost may first go to ::1. Windows often assigns the IPv6 address for localhost, so the intermediary listens to both 127.0.0.1 and ::1.

What's the Result?

The code is open-source (MIT): github.com/Tataut/chistovik. On Windows, it's installed with a single PowerShell script; then you need to fill in a couple of fields in Handy's settings; everything is described step-by-step in the README. The intermediary itself is cross-platform, and Handy is also available for macOS and Linux.

I only tested with Claude Sonnet 5.5. Any OpenAI-compatible API will work: OpenAI, OpenRouter, local models via Ollama or LM Studio – with a local model from your computer, nothing goes out at all. But I haven't tested how well small local models handle such rules. If you've tried, please share in the comments which one performs well.

Most of all, this helps me communicate in Telegram and other messengers. It's an invaluable time saver, so I decided to share it publicly. Perhaps it will be useful to someone else.
