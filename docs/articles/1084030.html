Jev: How its decision API works and what's already being built on it

In three days, a small ecosystem has grown around Jev: a browser agent found flight tickets in seven seconds, developers built a trading bot, content filters, and even a Tesla FSD. But Jev doesn't write text. Its API selects an answer from a space pre-defined by the application. What is Jev: Outputting Decisions, Not Text

A standard LLM receives context and continues the token sequence. Even when we ask for JSON, its work is essentially generation: the model writes a serialized object, a validator checks the format, and upon error, the familiar retry loops begin.

Jev accepts a different contract:

state + questions → answers + probabilities

state contains the text or structured state of the application. In questions, the developer poses one or more typed questions. Answers are returned under the same keys. There are three public primitives:

  • Noul answers a yes/no question with a probability from 0 to 1;

  • Choice selects one of pre-defined options and returns a distribution across the entire list;

  • Score distributes probability across 2–10 levels and calculates the expected value.

Consider a support request: "I've been charged twice, fix this urgently." With one request, you can ask if it's urgent (Noul), which department should handle the ticket (Choice), and how annoyed the customer is (Score). All questions see the common state but not each other's answers. If the second question depends on the first, that dependency must be built into the code.

The independence of questions allows for speculative fan-out. The application sends questions for multiple possible branches in advance, receives answers simultaneously, and then the code selects the necessary ones. Some answers might not be used, but there's no need to wait for another API call.

This feature underpins the popular launch slogan: "zero hallucinations." In a narrow sense, it's true. If only billing, technical, and sales are permissible, the API won't return legal, a lengthy explanation, or a poem about refunds. However, Jev might confidently select sales. Type safety guarantees the format and a set of permissible answers, not factual correctness.

The same trap applies to confidence. It's a characteristic of the distribution's shape, not the probability that the decision is correct. A value of 0.9 doesn't mean "it will be wrong in one out of ten cases." TypeSafe explicitly recommends calibrating thresholds on your own labeled data and considering the cost of error. A single threshold is clearly unsuitable for moderating a comment, blocking a payment, and deleting a production database.

Regarding System One and the RLCD (Reinforcement Learning for Calibrated Decisions) training method, only TypeSafe's descriptions are currently available. The company has not published the weights, architecture, data, loss function, or reward scheme. Archer Hume's experiments align with question isolation and show the influence of the entire list of options. However, a causal decoder, KV cache, separate output heads, let alone a sparse MoE model, do not follow from this.

For now, only what happens at the boundary between the model and the application can be verified with Jev. A similar interface can be built on top of LLMs with structured output, constrained decoding, or local logit scoring; TypeSafe itself has even released a System One adapter for standard LLMs. Therefore, the interface should be evaluated based on model quality, calibration, latency, and the overall system's operational behavior.

Josh Kuechly compared Jev and the open-weight classifier GLiNER 2.5 on Banking77. Without fine-tuning, GLiNER lagged Jev by about 9 percentage points, despite running 10 times faster. After 51 minutes of training on approximately 10,000 examples, it gained 18 points, surpassing Jev by about 9, and ran 8 times faster locally. The author did not publish the code or logs, so this remains a single experiment, not an independent benchmark. However, the divergence is clear: Jev buys zero-shot flexibility, while a narrow classifier offers speed and accuracy on a stable task.

Jev doesn't replace these options. It adds another: a universal cloud-based decision layer between standard code and LLMs.

How to Try Jev Without Waiting for TypeSafe to Reveal More

You can try Jev at askjev.ai or easyjev.app.

Direct access from TypeSafe was still in early access as of September 18. After approval, users create a key, purchase credits, and call POST /v1/systemone. Without direct access, Jev could be invoked via Vercel AI Gateway, where the model is named typesafe-ai/jev and paid for with Vercel credits. OpenRouter uses an early endpoint /api/alpha/decisions, and Cloudflare Workers AI calls typesafe/jev through its ai/run. These are four different routes with their own keys, billing, and limitations, not interchangeable proxies.

As of September 18, the aliases jev-latest and jev-preview pointed to jev-1.13.0. The model documentation listed the price at $0.042 per million input tokens; output tokens were not charged. Early access limits were: 64k tokens per request, 32k for the combined length of state and the longest question, 1200 requests per minute, and 250 thousand input tokens per second. TypeSafe warned that limits might change.

The minimal request from the official quick start looks like this:

curl -X POST https://api.typesafe.ai/v1/systemone 
  -H "Authorization: Bearer $TYPESAFE_API_KEY" 
  -H "Content-Type: application/json" 
  -d @- <<'EOF'
{
  "state": "Hi, I've been trying to connect my Stripe account for 3 days and it keeps failing. I'm losing sales. Please help ASAP.",
  "model": "jev-latest",
  "questions": {
    "urgency": {
      "type": "noul",
      "instructions": "Does this message express urgency?"
    }
  }
}
EOF

The request illustrates the contract: the state is sent in its entirety, the question is typed, and there's no free-form text field for a textual answer. SDKs for Python and JavaScript hide the HTTP calls and retries but do not change the operating model.

The price seems almost scandalously low until you remember that the agent resends the large context at each step, and you pay for all its tokens. Output tokens are free not because the entire chain is free, but because there are few of them.

TypeSafe states that it does not train Jev on user requests and responses, but for a standard account with direct access, it does not publish a specific retention period. ZDR is offered to enterprise clients. Vercel does not retain the request and response after the call completes, but it does store operational metadata, and routing attempt details can be kept for 30 days. "Not used for training" and "nothing stored" are still different promises.

For direct accounts, TypeSafe's Master Customer Agreement restricts reverse engineering and publishing benchmarks or service performance information. This may apply not only to your own measurements.

How the Jev Browser Agent Works

The browser agent doesn't start with the model. The jev-ultrafast repository is convenient because the hyped video can be deconstructed back into code. We'll analyze the MVP version 0.1.0 at a fixed commit: Jev selects the next action, and the agent's code implements the browser mechanics.

One cycle looks like this:

snapshot.js
  → visible text and indexed action space
  → batch of Choice questions
  → Jev selects operation and target
  → Mercury 2.5 writes value only for TYPE_TEXT
  → browser.py verifies and executes action

snapshot.js collects visible text and interactive elements of supported types. Standard Python code transforms them into a list of allowed operations: CLICK, TYPE_TEXT, SELECT, scroll, wait, DONE, and BLOCKED. Jev doesn't invent CSS selectors, coordinates, JavaScript, or shell commands. It sees the already constructed list and chooses an index.

In model.py, the question about the operation and questions about targets are bundled into one batch. Here's a real snippet from the choose() function:

questions = {
    "operation": {"type": "choice", "criteria": operations, "instructions": {"goal": goal, "rules": NEXT_ACTION}}
}

The next cycle adds targets from observed elements to questions. Jev evaluates operation, click_target, type_text_target, and other branches in parallel. If CLICK wins, the answer for type_text_target is not used.

Free text is still needed when the agent fills a field. The strings Zurich and London in the demo were generated by Mercury 2.5, not Jev. After selection, the executor re-verifies the page, DOM node, properties, geometry, and element overlap. The model suggests an action, and the code decides if it can be physically performed.

This is a strong architectural boundary, but it also shows where the complexity has shifted. The action space is truncated to the first 250 entries, and visible text to 6000 characters. The first version does not support, or only partially supports, frames, <canvas>, file uploads, new tabs, nested scrolling, shadow DOM, and non-standard elements. If the desired button isn't captured, Jev won't select it, even with perfect accuracy.

The issues already include an empty initial action space, invisible clickable elements, and a report of a run lasting 81.62 seconds: two Page.captureScreenshot timeouts and manual resumes increased the total time, and the author cited a background rendering limit as a probable cause. These single reports cannot assess failure frequency. They highlight three points for verification: completeness of the action space, visibility of interactive elements, and stability of the browser environment.

Freshness and geometry checks filter out actions based on outdated page states but do not protect against prompt injection. The project lacks a general policy for confirming dangerous operations and a list of allowed domains. A narrow set of allowed actions narrows the range of possible errors, but doesn't inherently make the chosen action safe.

What Actually Fit into Seven Seconds

The published Flights trace took 7073 ms. During this time, the agent made 17 Jev requests, 11 browser actions, and two Mercury calls. It found Google Flights results for the Zurich → London route on the specified date. It did not book a ticket.

Jev accounted for 3720 ms, or 52.59% of the total measured time. Two text calls added 927 ms. Calls to both models took 4647 ms, which is 65.70% of the total time. The remaining time was spent on page snapshots, execution, and browser environment operations.

These 7073 ms cover only the agent's cycle. The timer starts after the initial observation, before the first model call, and stops upon receiving DONE. Browser setup, initial navigation, and the final verifier are not included in the seven seconds. Notably, the DONE is chosen by the same policy model. Success is proven by a separate check of the route, date, and visible results, which occurs outside the timer's scope.

In an arbitrary task, such a verifier doesn't exist until the developer writes it. An agent that declares its work complete is like a student grading their own exam. Sometimes it's correct, but the control is still not independent.

The cost of model calls here can be calculated quite precisely. 90,558 input tokens for Jev at the current price cost $0.003803436. Mercury added $0.00006272. A total of $0.003866156, excluding browser infrastructure costs. Approximately 98.38% of the model expenses were for Jev: resending the state proved more expensive than two short text generations.

The authors compared the old and new execution environments on three alternating pairs of the same task. The median dropped from 9,450 to 7,092 seconds, about a 25% improvement, and the number of CDP calls from 1092 to 101. All six runs passed the verifier, but a sign-test yields p = 0.25. This is an improvement in the environment's speed on one task, not a comparative test of Jev against LLMs, local classifiers, or Playwright.

A third-party Retriever test adds a useful counterexample. In two scenarios, the Jev configuration was 31% and 43% faster but 38% and 51% more expensive. Out of 50 requests, 39 were Score: preliminary filtering consumed the savings of the cheaper solution. There was one run per configuration, no raw traces are available, so the percentages cannot be generalized. In these two scenarios, the fast model did not make the system cheap.

15 Projects on Jev: From Flights to StarCraft

The final fifteen include projects that best showcase Jev's range. This is not a ranking: released code, single demos, and author claims are placed side-by-side. A repository confirms the project's existence but says nothing about its accuracy or reliability in production.

Selecting the Next Action

  1. jev-ultrafast demonstrates a dynamic action space: Jev selects the operation and target, the browser wrapper executes the action, and Mercury writes text for fields. We analyzed the architecture and boundaries of the seven-second run above.

  2. mobile-jev adapted the same principle to Android. Jev receives available interface elements and selects the next tap; in the demonstration, the agent ordered an Uber in about nine actions over approximately 21 seconds. The code is open, but there are no other scenarios yet for reliability assessment.

  3. Justin Schroeder claimed to have reassembled Tesla Full Self-Driving on Jev in under an hour. The subsequently published JevPilot turned out to be a playable simulator on Three.js: the model selects trajectory and speed, while geometry, route finding, and emergency braking remain in standard code.

  4. One completed mission is insufficient for systematic evaluation. However, original StarCraft fits Jev's contract well: the game has a finite set of commands, the model controls the keyboard and mouse, and preserves probabilities of chosen actions. Astra completed the mission on the first try. Of course, it's far from Androide and his WCG 2005 silver medal.

Verifying the Agent Before Action

  1. pi-warden sits between the agent and its tools. Before executing a command, Jev assesses irreversibility, plan adherence, external consequences, recurring loops, and suspicious early done states. The author ran the check on 17,000 of his own tool calls but did not publish the original sessions or the full results.

  2. A permissions plugin for OpenCode checks the agent's intent before allowing it to access a domain. The author states that Jev caught all demonstrated attempts to bypass restrictions. Since there is no public attack set, this is currently a successful demo of a defensive gateway, not a proven security boundary.

  3. A Discord bot assesses messages for spam, phishing, and social engineering. The code translates Jev's probabilities into four levels of response: from пропуска (skip) to strict escalation. The authors did not provide accuracy metrics. However, the separation of roles is visible in the code: the model assigns a score, and the program determines the consequences.

Assisting Other Models

  1. fast-jev-compaction ranks old Claude Code tool calls and verbatim saves those it deems useful. In the demonstration, the context size was reduced from one million to 86 thousand tokens in about a second. The repository confirms the selection mechanism but doesn't prove that important information wasn't lost among the discarded 914 thousand tokens.

  2. jev-router selects a model for Claude Code and Codex requests: simple tasks can be sent to a cheaper model, complex ones to a more powerful one. Savings only appear with sufficiently accurate routing; otherwise, a cheap initial decision leads to expensive corrections.

Processing Large Data Streams

  1. pg-jev adds a function to PostgreSQL for natural language conditions. This results in a kind of fuzzy WHERE: rows can be filtered by meaning without pre-prepared embeddings. The cost, accuracy, and speed of a full table scan have not yet been measured.

  2. unclutter turns Jev into a semantic filter for web pages. The user defines a rule with a natural phrase, and the extension classifies page elements and remembers deletion patterns. This way, the model is not called every time a site is opened, although the quality of the rules themselves has not been independently verified.

  3. Another extension listens to YouTube audio and skips in-video ad integrations. The author estimated the cost at about $0.005 per video. How accurately it catches the start and end of ads, and how much regular speech it consumes in the process, is unknown from the publication. But it's better to use SponsorBlock.

  4. In an experiment with 1018 AI articles, Jev distributed the materials into 24 topics. The author claimed $0.08 for the entire set and a median of 256 ms per article. However, Jev only saw pre-generated summaries from DeepSeek, so these figures describe only the second stage of the pipeline.

Testing Edge Cases

  1. jev-trader selects buy, sell, or hold for the MON-USDC pair in each 300-millisecond block on Monad. Demo. The code includes a real order mode, but by default, the bot operates in mock/dry-run. The author has not shown any public transactions or profitability history. So, ready for a dip?

  2. killmyidea asks about ten questions about a startup in parallel and compiles a numerical assessment from the answers. Free text from the model is not needed here at all: Jev assigns scores, and the interface translates them into an analysis. Such a digital wolf from Wall Street is useful only as much as its criteria are good.

Two Tests Where Speed Didn't Save the Day

On 1565 German and English business emails, Gemini proved more accurate than Jev in classifying into ten categories. The author still considered Jev for production due to other advantages, but a universal victory in quality did not materialize.

In an open test on 2000 phishing emails, Jev lost to Claude Haiku 4.5 in accuracy. The code is published, and the result itself has not yet been independently reproduced. Two different datasets do not form a general ranking but serve as a good reality check after videos featuring cars, games, and trading bots.

Is Jev Worth It Right Now?

Jev is worth testing if your LLM already selects a label, route, or action from a finite list, and you want to reduce latency and cost. If you don't have such a task yet, the hype around Jev itself won't create one.

Worth Trying If

  1. The LLM returns a category, score, or yes/no, and you discard the generated explanation anyway.

  2. Several sequential decisions are slowing down the system, and they can be combined via speculative fan-out.

  3. You already have a list of allowed actions, result verification, and a fallback scenario. Jev only selects; the code still executes.

The best initial candidates have already been mentioned: routing models and tools, defensive checks before external actions, mass classification, and ranking. In all three cases, the correct answer can be pre-defined, and an error can be caught before it becomes costly.

Not Yet Worth It If

  • The output should be new text, code, or a plan;

  • The task is reliably solved by standard code or Playwright;

  • You have a stable, narrow domain and enough labeled data for a local classifier;

  • The state cannot be sent to a closed cloud;

  • The error cannot be cheaply verified;

  • The decision immediately triggers an irreversible action.

Jev 1.13 Limitations page adds arithmetic, dates, indirect questions, large amounts of irrelevant context, contradictory criteria, and adversarial content to this list. TypeSafe advises leaving these parts to standard code.

What the Pilot Should Prove

Run Jev and your current solution on one labeled dataset. Compare accuracy, latency, and the total cost of the pipeline, then select a confidence threshold and a fallback route. If there's nothing to compare against, it will be another beautiful demo, not a basis for changing the system.

If the idea of typed selection itself is suitable, but the closed cloud is not, jevlike and openjev allow testing a similar interface with local models. They do not reproduce the closed Jev, its quality, or RLCD. One of the claimed Qwen-RLCD artifacts doesn't even have its own uploaded weights.

The first wave has found many niches for Jev, but has not yet proven that one model is equally good in all of them. For a technology that is three days old, this is a normal outcome.

Jev offers a contract where the application pre-defines the world of permissible answers, the model distributes probabilities among them, and the code retains control over actions and verification. This limitation becomes an advantage only when the developer correctly defines such a world.

If the desired button isn't among the 250 elements, the correct class isn't in Choice, and there's no one to check a dangerous action, Jev will still return an ideally valid answer. Just not the one you need.
