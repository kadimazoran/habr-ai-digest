A model's name in the code becomes obsolete the day the next model is released. If you have ten services, you'll rewrite it ten times and distribute vendor keys across ten configurations.

Keystone. The Model Switchboard. (KTMS) removes this from your code. A service indicates the task's complexity, and the gateway decides which model to call, with which key, and whether to use your own GPU. At rest, it uses 7 MiB of memory, and since version 1.0, its API within the 1.x range is backward compatible.

Alongside the gateway 1.0, the ktms-admin web console and light-tokenmeter cost tracking service were released, all three in Go and under Apache 2.0. Features are described below for the current version 1.3.

What is Keystone in a Minute

Keystone is a self-hosted gateway between your services and LLM vendors. Services connect to a single point, and KTMS:

  • stores vendor keys in Postgres, encrypted with AES-256-GCM, and does not expose them to clients;

  • selects a model based on rules, not by name in the code;

  • switches to the next model if the vendor is down or rate-limiting requests;

  • limits requests, tokens, and money per key, user, and team;

  • sends an event for each call to the accounting service.

 your services ──gRPC / HTTP /v1──▶ Keystone ──▶ OpenAI / Anthropic / Gemini / DeepSeek / Bedrock / ...                                      │   │  └──▶ your GPU nodes (Ollama, vLLM, TGI, llama.cpp)                             Postgres ┘   └ Redis (limits, cache)       └──▶ light-tokenmeter (accounting)

A service doesn't write gpt-4o. It requests complexity: LOW, MEDIUM, or HIGH, and adds arbitrary attributes (language, task, user_id). An ordered list of rules transforms this into a model chain with fallbacks:

grpcurl -plaintext -H "authorization: Bearer $ADMIN_KEY" -d '{"rules":[   {"name":"spanish-high", "priority":30, "effort":"EFFORT_HIGH",    "attributes":{"language":"es"}, "use":["gemini-2.5-pro","gpt-4o"], "enabled":true},   {"name":"low-default", "priority":20, "effort":"EFFORT_LOW",    "use":["deepseek-chat","gpt-4o-mini"], "enabled":true},   {"name":"anything-else", "priority":1, "use":["gpt-4o-mini"], "enabled":true} ]}' localhost:9090 ktms.v1.AdminService/ReplaceRules

Rules can be changed on the fly, without releasing services. A new model is released—you edit a rule, not forty microservices.

Integration Without Rewriting Code

There's typed gRPC (ktms.v1) and OpenAI-compatible HTTP. Existing code using the OpenAI SDK can switch by changing the base_url:

from openai import OpenAI client = OpenAI(base_url="http://localhost:8080/v1", api_key="ktms_<your key>") reply = client.chat.completions.create( model="auto", messages=[{"role": "user", "content": "Say hi in three words."}] ) print(reply.choices[0].message.content, reply.model)

The response includes headers X-KTMS-Vendor, X-KTMS-Rule, and X-KTMS-Placement, indicating who responded, by which rule, and where.

What It Can Do (Version 1.3)

  • Routing: effort LOW/MEDIUM/HIGH and attributes, rules with priorities that change on the fly, fallback chains, model: "auto" with a judge (250 ms, fallback to MEDIUM), canary releases tied to users, shadow traffic with evaluation, dry run with ktms route explain.

  • Reliability: circuit breaker, model pause based on Retry-After, one attempt—one call, operation during Postgres and Redis failures.

  • Money and Limits: RPM/TPM and allowlist of models per key, daily and monthly spending limits per key and user, monthly team budget, prompt cache prices, vendor Batch API.

  • Own GPUs: node agent for Ollama, vLLM, TGI, and llama.cpp, admission based on actual queue, placement "own nodes only", power levels and load scheduling, local log ktms-node stats.

  • Security: vendor keys in Postgres under AES-256-GCM and their rotation, PII masking, prompt injection detection, latent guardrails and semantic cache (experimental).

  • API: gRPC ktms.v1 and OpenAI-compatible HTTP, streaming, tool calling, lossless JSON Schema, embeddings, TTS, images, Judge.

  • Management: CLI ktms with contexts and ktms init, YAML configuration (plan/apply), MCP server ktms mcp for AI assistants, plugin for Claude Code, scope admin:read, ktms-admin web console.

  • Operations: ktms_* metrics with ready alerts, Helm chart in OCI, signed images with SBOM and SLSA, update test on every PR.

Resource Costs

Keystone is a single Go process without an interpreter. On a testbed of 11 gateways (Google Cloud c3-standard-4, 4 vCPUs, mock upstream, two runs):

  • ~7 MiB of memory at rest and ~20 MiB at 200 RPS (Postgres and Redis not included);

  • ~0.64 ms added latency at p50 and ~1.1 ms at p99;

  • at least 4000 RPS on 4 vCPUs without errors;

  • ~170 ms from docker start to the first response;

  • an image size of ~21 MB for download.

We are not the fastest: agentgateway, Apache APISIX, and Kong add less latency and consume less CPU per request. However, in terms of memory, startup time, and features, Keystone is in the top tier.

What's in the Release

What appeared between versions 0.13 and 1.0.

Organizations and Teams. Keys are grouped into organizations and teams. A team has its own list of allowed models and a monthly budget for all its keys. ListModels shows the team only its models.

Vendor Call Reliability. Built-in SDK retries are disabled, so one router attempt is exactly one vendor call. The gateway reads Retry-After (and similar headers from Gemini) and pauses the model for a specific vendor key, while the chain continues. Plus, a circuit breaker for the (vendor, model) pair.

Behavior on Dependency Failures. Described and tested for each case. If Postgres fails, keys verified in the last 5 minutes continue to work, and routing uses the last configuration snapshot. If Redis fails, limits do not block traffic (the money mode is selected separately). Accounting events are queued and delivered exactly once.

Lossless Structured Output. JSON Schema is passed to vendors along with enum, format, nullable, and additionalProperties. If the vendor does not support structured output, the gateway checks the response itself, retries the request once, and moves to the next model.

Local Nodes by Actual Queue. The node agent transmits the engine's queue depth (vLLM, TGI, llama.cpp), and the gateway does not send a request to a node where it would wait longer than acceptable.

Encryption Key Rotation. Secure procedure: new records are encrypted with the new key version, RotateEncryption re-encrypts vendor keys and node tokens in a single transaction. The sequence is run on Postgres in CI.

Signed Releases. Images and checksums.txt are signed with cosign in keyless mode; images have SBOM and SLSA provenance; archives have SPDX SBOM. govulncheck is run on every pull request.

Apache 2.0 License instead of MIT: an explicit patent license for those embedding the gateway into their products.

A recent compromise of a popular Python library's release reminded us that the gateway stores keys to all vendors at once. A detailed analysis of that incident and its implications is in a separate article.

Two Adjacent Projects

ktms-admin is a web console: models, rules, keys, vendor credentials, and a sandbox for querying through your rules. Login via password, Google, or any OpenID Connect, GitHub, or your access proxy (oauth2-proxy, Authelia, Authentik, Pomerium, Cloudflare Access) with an allowlist of addresses. A single binary, built-in interface, no frontend build required.

light-tokenmeter answers the question "who is spending tokens and is it worth it?". It accepts an event for each call and provides summaries by projects, users, actions, vendors, and models. The console marks groups as greedy or worthy based on these summaries. A single binary, one Postgres table, ClickHouse optionally.

What 1.0 Means

Before 1.0, we made no promises. From 1.0 onwards, within the 1.x range, backward-incompatible changes are not made:

Surface

What is preserved in 1.x

gRPC ktms.v1

RPCs, fields, enums, and field numbers. buf breaking checks every pull request

HTTP /v1 and X-KTMS-* headers

Paths, request and response fields, header names

Environment variables

Names, default values, and meaning

Database

Any 1.x can upgrade the previous version's database automatically, without manual SQL

ktms_* metrics, usage.v1 events, node agent

Names, labels, backward compatibility

Error codes and reasons

Meaning is preserved, new reasons may appear

What is marked as experimental and may change in a minor release: effort selection by judge, shadow traffic, semantic cache and latent guardrails, JudgeStream and EvaluateRollouts, YAML configuration format, and the ktms command before configuration format version v1. The full list is in the README, and fields in proto are marked with an Experimental: comment.

The promise is automatically verified. On every pull request and before every release, an update test spins up the database from the previous release and the oldest release of the same major version, migrates it with the new build, and then runs the old version again on the migrated database. This verifies both updates and rolling deployments. A release is published only after this test and buf breaking.

What's Next

After 1.0, plans include: routing sensitive data only to own nodes, hedged requests, corrective retries for JSON, a Grafana dashboard, and recipes in the documentation. None of this breaks the 1.x API
