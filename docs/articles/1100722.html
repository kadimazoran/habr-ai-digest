An article on how abandoning unnecessary ASCII processing sped up BERT's tokenizer 50x

For the past few months, we've been actively revitalizing the tokenizers library. Our goal is to speed up tokenization and reduce resource consumption. We are now preparing these improvements for a stable release, v1.0.0.

Our main benchmark has been tokenization speed in MB/s of source text, primarily for BPE (Byte-Pair Encoding) — the algorithm used in most LLM tokenizers.

Now, classic BPE tokenizers process text up to 30 times faster than in tokenizers 0.23.

Other types of tokenizers have also sped up, but I wasn't satisfied with the result of the good old bert-base-uncased, which was now only about 8.6 times faster.

In this article, I'll explain how we managed to speed up the BERT tokenizer by another 5.7 times, achieving a total speedup of approximately 50 times compared to version 0.23. At the time of writing, the changes are still in the pull request stage.

BERT? Seriously?

Why bother with BERT, you might ask? It was released back in 2018, long before ChatGPT (!!!). It seems like it's long overdue, right? ..

Not quite. BERT-like models are used everywhere. They serve as encoders for creating embeddings, for search and RAG, and form the basis of re-rankers and classifiers. And in terms of download counts, only a few LLMs can compare.

Moreover, the three most downloaded models on the entire Hugging Face Hub use BERT's normalizer:

  • all-MiniLM-L6-v2 — 218 million downloads per month;

  • cross-encoder ms-marco-MiniLM-L6-v2 — 79 million;

  • bge-small-en-v1.5 — 59 million.

bert-base-uncased itself ranks sixth with 34 million downloads.

If we take the 10,000 most downloaded models on the Hugging Face Hub, BPE tokenizers (used in most LLMs) account for 842 million downloads per month. WordPiece, the tokenization algorithm for BERT-like models, accounts for 627 million. And in all these cases, the text goes through BERT's normalizer.

Furthermore, normalization isn't just for BERT: more than half of BPE model downloads come from tokenizers that use some form of Unicode normalization (most often NFC, as in Qwen or ModernBERT). Our improvements also speed up this processing.

How to Read a Flame Graph

Imagine we take a snapshot of the program's state a thousand times per second. Each snapshot shows which function is currently executing and who called it. For example: "encode called normalize, which in turn called is_mark_nonspacing".

Now, let's collect all snapshots and count how often each function appears. If a function appears in most snapshots, it means the main part of the time is spent on it.

A flame graph visually represents this statistic:

  • Each rectangle corresponds to a function. The wider it is, the more often the function appeared in snapshots and the more time its execution took.

  • Rectangles are placed above the functions that called them. encode is at the very bottom because all other functions execute within its call.

  • Look for the widest rectangles near the top of the graph. This is where the program spends most of its time.

The horizontal axis does not show the passage of time—it's just a way to arrange the rectangles. Colors represent different processing stages: yellow — normalizer, blue — Unicode table lookups within it, purple — text pre-segmentation, green — WordPiece.

Several important conclusions can be drawn from the graph:

  • 88% of tokenization time is spent on text normalization. The WordPiece itself, which directly selects tokens, accounts for only 8%.

  • Approximately two-thirds of the total tokenization time is consumed by the mysterious function binary_search_by. It is called from char::is_mark_nonspacing() in the unicode_categories library, which checks if a character belongs to non-spacing combining marks. We'll explore why this check is so expensive a bit later.

So, we've found the bottleneck — text normalization. Next, I'll explain how we managed to make this stage work at a completely different speed.

Unicode Normalization in Three Minutes

Unicode is a way of representing text using numbers. Text consists of code points: the letter a, the digit 5, the letter with a diacritic è, the character 中, the emoji 🤗.

Each code point corresponds to a number from 0 to 0x10FFFF — about 1.1 million possible values in total. In Unicode 17.0, 159,801 code points are in use.

In UTF-8, each code point occupies 1 to 4 bytes. This encoding is used almost everywhere. All 128 ASCII characters are represented in it by a single byte with a zero most significant bit, while other code points are encoded by sequences of 2–4 bytes whose first byte's most significant bit is 1. Remember this bit — we'll come back to it.

The same character on the screen can be represented in different ways. What a reader perceives as a single character is called a grapheme cluster. It can consist of one or more code points. For example, é can be written as a single code point U+00E9 or as two: e followed by the combining acute accent U+0301.

BERT Normalization

Great, we've figured out normalization. But why does BERT spend 88% of its time on it?

BertNormalizer (with the lowercase=True parameter, as in bert-base-uncased) performs five operations in the following order:

  1. Cleanup: removes control characters and replaces all whitespace characters (tabs, newlines, Unicode spaces) with a regular space 0x20.

  2. Chinese characters: adds a space on both sides of each CJK ideographic character.

  3. NFD: decomposes each character into its components (more on this in the previous section).

  4. Diacritic removal: removes combining marks identified during NFD decomposition.

  5. Lowercasing.

In versions 0.23 and 1.0, all of this is implemented as a single character processing pipeline (tokenizers/tk-encode/src/normalizers/bert.rs in the main branch, simplified version):

input.chars() 
    .filter(|&c| !clean_text_removes(c)) // is_control(c): Unicode table lookup 
    .map(clean_text_map)                 // whitespace characters → ' ' 
    .flat_map(pad_chinese_char)          // ' ', c, ' ' 
    .nfd()                               // unicode-normalization 
    .filter(|c| !c.is_mark_nonspacing()) // diacritic removal: Unicode table lookup 
    .flat_map(char::to_lowercase)        // Unicode table lookup

    A. Processor Memory Levels and Access Latencies
    A processor doesn't read data from memory byte by byte. It loads entire cache lines of 64 bytes into small, fast caches near the core.
    Reading from L1 cache takes about a nanosecond, while accessing main memory takes about 90 nanoseconds.
    This is precisely why the code point block cache, described in the "Other characters also come in groups" section, works so fast.
    Binary search on a 6 KB table requires jumps between different memory locations, and each comparison is accompanied by branching, which is difficult for the processor to predict.
    A block of 256 pre-computed answers, however, occupies only four cache lines that remain in L1 as long as characters from the same script continue to appear in the text.
    B. How to Reproduce Measurements
    I'll state the obvious, but still: MB/s speed depends on the hardware. Moreover, results can differ not only between computers but also on the same machine depending on what else is running on it.
    Absolute throughput values will vary depending on the processor model, memory subsystem state, and even whether you're simultaneously playing the latest Call of Duty on ultra settings...
    However, speedup ratios are much more reliable. We conducted measurements on two machines with AMD EPYC 7R13 and one with Intel Xeon Platinum 8488C (different machines are marked on the graphs), using a single thread. The results for speedup ratios varied by only a few percent.
    To make the experiment reproducible, I've prepared all the necessary code and put it in a GitHub repository.
    Here is the full configuration we used to obtain the results in the graphs of this article:
    • Machines. We ran benchmarks via Hugging Face Jobs on two machines with AMD EPYC 7R13 (cpu-performance configuration), and also on one internal server with Intel Xeon Platinum 8488C. Before trusting the results, we compared the same binary build against itself to estimate measurement variance due to system load. On EPYC machines, results between runs differed by 0.35%, on Xeon — by about 2%.
    • What was compared. The main branch of the tokenizers library (a few commits after 1.0.0-rc2, commit fb49a29) and the optimization branch (5b5a3fc). Both versions were compiled from source with the same compiler (rustc 1.99.0) using parameters lto = "fat" and codegen-units = 1. For the release comparison graph, version 0.23.2 from crates.io was used.
    • How measurements were taken. One thread, pinned to a single CPU core. In each measurement, a 5–6 MB text corpus was tokenized repeatedly in a loop for 5 seconds. First, a warm-up run was performed, followed by five more runs where main and the optimization branch alternated. This way, gradual system performance changes affected both versions equally. The median of the speedup ratios calculated for each run was used as the final result. The proportion of CPU time taken by other server users did not exceed 0.002%.
    • Identical output tokens. At each run, a hash of the resulting token IDs was calculated. For all test corpora, the hashes were completely identical between main, the optimization branch, and version 0.23.2.
    • Test Corpora. Data from hf-internal-testing/tokenizers-test-data, revision 5f5c652: texts in English, Russian, Greek, Arabic, and Chinese, as well as mixed source code. A separate corpus of Greek text with decomposition represented the same Greek text normalized to NFD form.
    • Input Data Sizes. For individual normalizer performance measurements (section "Limitations"), fragments from 8 bytes to 64 KB were used. Each combination of conditions processed about 4 MB of data. The best result was chosen from three measurements, with four rounds conducted in total. A control comparison of the binary build against itself determined the measurement error (±3%).
    • Profiling. perf could not be run in Hugging Face Jobs containers, so flame graphs were generated using pprof-rs, which collected profiling data directly within the process at a frequency of 999 Hz. Results were further verified by the number of executed instructions measured via callgrind, excluding tokenizer loading costs. When tokenizing 1 MB of English text, the number of instructions decreased from 482 million to 72 million (6.7x), and the proportion of normalizer instructions dropped from 87% to 12%.
