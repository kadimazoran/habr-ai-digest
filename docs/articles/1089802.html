I built an MCP server for my product. Writing and testing the code took one evening—the agent did the writing, of course.

But the "everything else" turned out to be decisions about the composition and visibility of tools, and things that couldn't be planned in advance—only discovered post-factum, and almost always as a result of someone's external reaction.

What the agent did, and what was left for me

The agent wrote the endpoint. MCP over streamable HTTP is JSON-RPC in the POST body: the client asks the server to introduce itself, asks for a list of tools, then calls them one by one. Dictionaries in, dictionaries out. No framework needed, no SDK needed. A single route was added on top of the existing backend, with no new dependencies.

What was left for me is what the agent cannot decide for me, because it has neither product context nor understanding of the goals.

How many tools and which ones. Four to eight is a reasonable number. Each additional tool will be another entity that the model on the other side must choose correctly. Fewer tools make it easier for the model to choose.

Access rules. Some things can be read by anyone, others only by an authorized user, and you also need to check if they have rights to that resource.

Names. Scoring in directories encourages names that read like a tree—a dot path like stories.search. My listing scored 98 out of 100 on the smithery.ai list precisely because of this rule. However, if you add a server to the ChatGPT server library, such a listing will not be accepted—^[a-zA-Z0-9_‑]{1,64}$, the dot is discarded. A criterion worth consciously failing.

And most importantly—names cannot be changed later. As soon as the registry scans you, you appear in the directory, and your application is accepted, each published name becomes a name you'll have to keep: listings, applications, and others' saved configurations carry it. This is no longer refactoring, but migration across systems you don't control. A fifteen-minute decision that will be difficult to change later—and the agent won't warn you about it because it doesn't know what will happen next.

Authentication

This is probably what was the hardest part. What needs to be considered:

First: find out who is calling. The server needs to understand on whose behalf it is being called: publishing and editing stories is only allowed for your own, and a private story can only be read by its author. A regular API would suffice with a key that a person sets themselves in the settings or environment variables. With MCP, this is almost never possible: Claude or ChatGPT connect to the server themselves, and there's nowhere to insert a key. They need a login like on websites: the person clicks "connect," sees the "allow access" screen, and returns already under their own name. To do this, you'll have to set up your own OAuth authorization server. This is the most expensive part of the entire project, and you are now responsible for its security.

Second: decide what doesn't require login. After adding authorization, I initially blocked all access for unauthorized clients—including the list of what the server can do. The logic seemed flawless. As a result, after registering in one of the directories, I only saw the service name, description, and zero tools, because the registry mirror had no one to authorize. The fix took about fifteen lines, the rule is simple: anonymously provide exactly what is publicly available elsewhere.

Third: allow external access. The app store reviewer needs to use the server. If the only way to log in is through a social network, this option won't work for reviews. You need to create a special account for the sandbox.

Fourth: have the correct token for publishing yourself. In the official MCP registry, the server is published under the GitHub account name: personal or organization. Mine lives under the organization—io.github.worklore/worklore. To grant you access to the organization's space, the registry checks that you are its owner, and for this, you need a GitHub token with read:org permission. Regular login via mcp-publisher issues a token without it. And the error doesn't say "token lacks permissions"—it responds with 403 and states that you can only publish under your personal login. I thought the issue was with the visibility of organization membership, but nothing changed. The GitHub CLI token, which already has read:org, helped: mcp-publisher login github -token "$(gh auth token)".

How much does it cost to maintain

An MCP server is a small service with infrequent and uneven load: most of the time it's idle and only starts when an agent calls it. The computations themselves cost pennies per month and usually fall within the free cloud limits. Listing in the official registry is free. Applying for an app in ChatGPT is free. The only non-free line for me is the Claude connectors directory: it requires a Team organization, about $40 per month for a minimum of two seats.

The ongoing cost is not about computation. It's about maintaining the authorization server, the fact that each client release can uncover new incompatibilities, and that without request logging, you don't know who is calling what.

What couldn't be planned

I planned a lot with the agent. The list of tools, the naming scheme, what it writes and reads, the workflow—we figured all this out in advance, and quite well. But the actual adjustments were made after publication.

Logs showed a client calling a method I don't have. I added one structured line per call to the server, which almost no one used—and it seemed pointless. A day later, it turned out that the client was regularly calling a method from a newer revision of the protocol, getting an error, and silently reverting to the old path. Nothing broke externally. Not a single test looked for this, because no one knew what to look for.

The directory (or MCP Inspector without authorization) showed my server without tools—I found out by opening its page, not from my code.

The review rejected the application due to the document. The privacy policy described a server that no longer existed: it was written when the connector was four read-only tools without login, but by the time of the check, it was six tools behind OAuth, two of which write on behalf of the user. The rejection was one sentence and absolutely fair. The reviewer reads it, comparing it to the live endpoint. You write a policy and forget to update it.

And the most interesting part—testing with a real client. I already shared a story about creating an MCP server on dev.to and received a comment: the person described how to test an MCP server as a real client would—ask for the list of tools and check each response against the schema that the server itself just provided. I tried it and found several bugs that had been live in production for several days. Despite the fact that 79 green tests had already been written. This confirms once again: you need to test not the code (which the agent loves to test based on what's actually written), but real connections. And of course, talk about the project, share experiences, and get feedback.

A bit more detail about the errors, because they were also interesting. We wrote a test, ran it—and it passed. Until the fix. Because the database mock returns regular integers, while the real database uses its own decimal type, and the test passed due to incorrect assumptions about the data format in the DB.

The simplest solution was to manually set the inconvenient type where it was important. This turned out to be a weak solution, and the same commenter explained why: a fix written manually inherits the author's assumptions, not production types—meaning it fixes the error you already know about. The correct solution is for the fake to convert types itself, just like the real driver does.

And one small detail, without which the entire check is worthless. When a tool in MCP fails, the server doesn't return a protocol error—it sends a regular response with an isError: true flag and the error text inside. There is no data in such a response that can be compared against the schema. If the test immediately proceeds to comparison, it has nothing to check, and it counts the call as successful. Therefore, first, make sure there is no isError in the response, and only then compare it against the schema.

And a listing that lagged behind the server. The story with the outdated privacy policy repeated itself in another place. In the official registry, my server was listed as version 0.1.0: four tools, all read-only. In two weeks, there were six at the same address, two of which write on behalf of the user, but the version remained 0.1.0. server.json in the registry stores no server surface—only name, version, and address—so you can only compare versions, and the version only changes if you remember to increment it.

A reader of the article suggested it again—Sydney Bissoli, author of open data MCP servers for the Central Bank of Brazil. His idea: hash the initialize response along with the lists of tools, resources, and prompts, commit the hash next to the version, and fail the build if the hash changes but the version doesn't. It's great for preventing forgetfulness (both mine and the agent's).

Perhaps you don't need to publish

A significant portion of the difficulties above are not about the server itself, but about publication: registry, directories, app store review, reviewer account, privacy policy, publishing token. And this part is optional. Without it, the server still works: it returns data, can describe itself, is visible in logs. Many good servers stop there.

If your users already live in the terminal or IDE, or are willing to paste the server address into Claude or ChatGPT settings—you're done: publish the address and one installation line in the README, and they'll add the server in about ten seconds. No forms, no reviewer, no waiting. For an internal tool or an audience you know personally, this isn't the "easier option," it's the right option.

Publication in the registry and directories only provides one thing: for someone who has never heard of you to find you. Pure marketing.

The only number that matters

The real question is not an engineering one, and no directory will answer it: has anyone connected besides you?

My numbers from September 16 to October 1: over 3700 connections—the client connects, asks for a list of tools and resources, and repeats. For the first twelve days, there were a few dozen connections per day, and from September 28—700–1000 per day. And 147 actual tool calls. All 147 were made either by me—from the main and test accounts—or by a ChatGPT reviewer under a demo account I set up for them. Real users—zero so far. These numbers are public and updated daily: worklore.dev/stats.html.

Moreover, these thousands of connections are not people. Almost all of them are bots from directories and monitoring services: they check if the server is alive and never call a tool. My experience

Six things I would do differently if I were starting over:

  1. I would set the tool names in a document beforehand, not in code. Without strong reasons, there's no point in changing them later; everything else will rely on them.

  2. I would enable request logging in the very first deployment. One structured line per call: time, method, tool, who called, success or error. Without this, you know nothing about your server.

  3. I would decide separately what is served without a token. The list of tools is a description of the server, not data: there's no need to hide it. Some data can also be provided without a token as publicly accessible.

  4. I would create a database mock based on the actual DB response: let it handle type conversions itself, rather than relying on the test author remembering them.

  5. I would set up a check that doesn't allow deployment if the tools or their descriptions have changed, but the server version has not. The version is the only thing the registry stores about your server, and it relies solely on memory.
