A small model quickly generates a few next tokens, and a large one verifies them all at once in a batch. Matching tokens are accepted, and at the first divergence, the large model continues generation itself. With correct implementation, the final distribution remains the same as with regular decoding. In speculative decoding, the large model literally tells the draft model: "Let's try again, Misha."

At first glance, it seems that acceleration here is necessarily bought at the cost of quality. But no: this is precisely the case where generation can be accelerated without such a compromise.

The reason lies in how the inference of a large model works. When generating each next token, it has to access a huge amount of weights in memory. For modern LLMs, this is tens, and sometimes hundreds of gigabytes of data. Therefore, generation often bottlenecks not so much on GPU computational power as on memory bandwidth.

Speculative decoding allows some of this sequential work to be combined. Instead of verifying one token per pass, the large model verifies several proposed tokens at once, better utilizing the GPU.

Next, we will try to understand the entire cycle: how the draft model works, by what rule tokens are accepted, what the size of the draft should be, why the same tokenizer is important, and how to integrate it all into Transformers and vLLM. We will also look at approaches where the second model is not needed at all: EAGLE, Medusa, LayerSkip, and DFlash.

Google uses speculative decoding in AI Overviews. Typical gains are 2–3×, but they strongly depend on the acceptance rate of tokens and the cost of the draft.

Why is generation so slow in general?

A 70 billion parameter model in FP16 occupies about 140 GB. And each token requires a full pass through all these weights. Generation is autoregressive: the next token cannot be calculated without obtaining the previous one.

Let's estimate the order of magnitude. The memory bandwidth of an H100 is about 3.35 TB/s. This means that just moving 140 GB of weights takes about 42 ms per token. So, the upper bound is about 24 tokens per second, and we haven't even computed anything yet, just transferred the weights.

There is, of course, an important caveat: 140 GB of weights do not fit into a single H100 with 80 GB of memory. In practice, such a model is distributed across multiple GPUs, for example, using tensor parallelism. If two cards are used, each stores and reads approximately half of the weights, about 70 GB. The theoretical read time is reduced to about 21 ms, but now there is another cost: at each layer, the cards have to exchange data.

Specific numbers change depending on the hardware, batch size, quantization, and parallelism scheme, but the overall picture remains the same: with sequential generation, LLMs often bottleneck primarily on memory bandwidth.

Hence, many methods for accelerating inference. Quantization reduces the amount of weights that need to be read. Batching allows using a single pass through weights for multiple requests. MoE activates only part of the model's parameters. Speculative decoding approaches the same problem from a different angle: it tries to get more than one useful token in a single pass of the large model.

And here's the observation on which the whole idea rests: a significant portion of tokens are predictable. In stable expressions, the continuation is often obvious. The same applies to auxiliary words, punctuation marks, and many code fragments. For such cases, a model that is tens of times smaller than the main one often suggests the same next token.

So why run the large model separately for each such token?

How it works

Let's take a simple scheme with two models: a small draft model and a target model.

  1. The draft model (e.g., Qwen2.5-0.5B) autoregressively generates tokens, say 5. It is a hundred times smaller than the target model, so it costs about one to two percent of a single pass of the large model.

  2. The target model (e.g., Qwen2.5-7B) processes all 5 draft tokens in one pass; structurally, it's the same as a prefix fill. At this point, the GPU is finally loaded with computations, not waiting for memory.

  3. The draft tokens are verified from left to right. The first consecutive matching tokens are accepted, and at the first divergence, the target model substitutes its token (it's already calculated in the same pass), and everything to the right is discarded.

In the best case, the main model accepts all five proposed tokens. In the classic scheme, from the same pass, one more next token can be obtained – a total of six tokens instead of six sequential runs of the large model.

In the worst case, the very first draft token fails verification. Then, per iteration, approximately the same one useful token will be obtained as with regular decoding, only the work of the draft model will be added to the cost of the main model.

This means speculative decoding does not guarantee acceleration at every step. Everything depends on how often the draft model guesses the continuation well enough.

For sampling, the verification scheme is slightly more complex: tokens are not simply compared for equality. A probabilistic acceptance rule is used, which allows preserving the original distribution of the target model. We will return to this below.

Why doesn't the response get corrupted?

It's often explained this way: a token is accepted only if the large model would have predicted the same one. For greedy decoding (temperature = 0), this is true, as verification boils down to comparing argmax. But with sampling, a different mechanism is at play, and it's this mechanism that provides the guarantee.

Let be the probability of a token by the draft model, and be the probability by the target model. A draft token is accepted with probability

If the token is rejected, a new token is sampled from the residual distribution

It is this correction that compensates for tokens that the draft model proposed too frequently. As a result, after the acceptance and rejection procedure, the final token has the same distribution as with regular sampling directly from the target model.

The quality of the draft model does not affect this guarantee. If it poorly predicts the continuation, most tokens will be rejected, and the acceleration will disappear. But the distribution of the result itself will not change because of this.

There is an important clarification here. "The same distribution" does not mean "the same sequence of tokens." With sampling, generation is initially random, so two runs can produce different answers even without speculative decoding.

And even with greedy decoding, absolute bitwise reproducibility across different inference modes is not always guaranteed. Regular decoding and checking multiple tokens at once can use different CUDA cores and a different order of floating-point operations. This usually doesn't affect anything, but with nearly equal logits, a small numerical shift can sometimes change the argmax.

If regression tests require exact string matches between different inference modes, this effect should be considered.

def expected_tokens(alpha: float, gamma: int) -> float: 
    return (1 - alpha ** (gamma + 1)) / (1 - alpha)

def speedup(alpha: float, gamma: int, c: float) -> float:
    return expected_tokens(alpha, gamma) / (gamma * c + 1)


def best_gamma(alpha: float, c: float, max_gamma: int = 15) -> tuple[int, float]:
    g = max(range(1, max_gamma + 1), key=lambda k: speedup(alpha, k, c))
    return g, speedup(alpha, g, c)

The reason is exactly what the formula shows: a stronger draft can more often match the target model's distribution, but if each of its steps becomes significantly more expensive, the additional acceptance rate is no longer justified.

The picture also changes with temperature. With greedy decoding, both models simply compare the most probable token, and similar models often match well. With sampling, it's more important not just the argmax match, but how similar the distributions and are. Therefore, changing the temperature can significantly alter the acceptance rate and the final speedup. How exactly depends on the specific pair of models and the task.

And here it's important not to treat the formula as a predictor of real speed to the second decimal place. It well illustrates the balance between draft length, its cost, and the acceptance rate, but the actual result additionally depends on the implementation of verification, batch size, KV cache, context length, parallelism, and specific hardware.

Try it in five minutes: Hugging Face Transformers

In Transformers, speculative decoding is enabled with almost one line: just pass the draft model via `assistant_model` in `generate()`.

For a simple example, let's use OPT-6.7B as the main model and OPT-125M as the draft. They use the same tokenizer, so no additional token alignment is required.

import time

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer


TARGET = "facebook/opt-6.7b"
DRAFT = "facebook/opt-125m"

tokenizer = AutoTokenizer.from_pretrained(TARGET)

target = AutoModelForCausalLM.from_pretrained(
    TARGET,
    torch_dtype=torch.float16,
    device_map="auto",
)

draft = AutoModelForCausalLM.from_pretrained(
    DRAFT,
    torch_dtype=torch.float16,
    device_map="auto",
)

inputs = tokenizer(
    "Explain how transformers process input tokens.",
    return_tensors="pt",
).to(target.device)


def timed(**kwargs):
    torch.cuda.synchronize()
    t0 = time.perf_counter()

    out = target.generate(
        **inputs,
        max_new_tokens=200,
        do_sample=False,
        **kwargs,
    )

    torch.cuda.synchronize()
    elapsed = time.perf_counter() - t0
    n_tokens = out.shape[1] - inputs.input_ids.shape[1]

    return elapsed, n_tokens / elapsed


# Warm up CUDA and both generation schemes.
target.generate(
    **inputs,
    max_new_tokens=10,
    do_sample=False,
)

target.generate(
    **inputs,
    max_new_tokens=10,
    do_sample=False,
    assistant_model=draft,
)

# Compare regular generation with generation via draft model.
baseline_time, baseline_tps = timed()
spec_time, spec_tps = timed(assistant_model=draft)

print(
    f"Without speculative decoding: {baseline_time:.2f} s, "
    f"{baseline_tps:.1f} tokens/s"
)
print(
    f"With speculative decoding: {spec_time:.2f} s, "
    f"{spec_tps:.1f} tokens/s"
)
print(f"Speedup: ×{spec_tps / baseline_tps:.2f}")

The numbers will be different on specific hardware, but the output might look something like this:

Without speculative decoding:   2.63 s,   81.2 tokens/s
With speculative decoding:    1.39 s,  154.0 tokens/s
Speedup:                  ×1.90

Here, it's important to compare the two schemes on the same machine, with the same prompt and generation parameters. The absolute number of tokens per second strongly depends on the GPU, PyTorch and Transformers version, context length, and other implementation details.

If you add `TextStreamer`, the difference becomes noticeable even without a stopwatch. With regular decoding, text appears almost uniformly, token by token. With speculative decoding, output can come in small bursts: when several sentences from the draft model pass verification, the target model accepts several tokens at once.

The `assistant_model` itself is just the simplest option. Transformers can dynamically change the draft length depending on how confidently the assistant model works, so the actual scheme no longer has to verify a fixed five tokens per iteration.

Why can't I use any small model?

In classic speculative decoding, the target and draft models must have the same tokenizer.

The reason is quite simple. Verification is done token by token: for each position, the draft model's proposal needs to be compared with the target model's distribution. If the vocabularies are different, such direct comparison is no longer possible.

The same text can be split into different tokens by two models. One might have a word as two tokens, another as three. After that, neither the positions nor the token IDs themselves match.

Therefore, early implementations usually used models with a shared tokenizer: for example, a small and a large Llama, or two Qwen models of the same generation.

This severely limited the choice of draft models. A large model might simply not have a sufficiently small relative: a formally suitable model exists, but it's too heavy and eats up most of the gains.

In Transformers 4.46 (October 2024), Universal Assisted Generation was introduced. UAG decodes draft tokens back into text, re-encodes them with the target model's tokenizer, and aligns the sequences. This allows using a draft from a different family, for example, a small Qwen with Gemma.

The idea is to translate the continuation between two tokenizations.

The draft model generates several tokens with its tokenizer. They are decoded back into text, after which this text is encoded by the target model's tokenizer. The resulting sequence can then be passed to the large model for verification.

On the next iteration, the reverse translation is needed: the continuation confirmed by the target model is converted into the draft model's representation so that it can continue generation.

A simple decode → encode is not enough here. Due to the specifics of BPE and other tokenizers, token boundaries near the concatenation point can change. Therefore, Transformers additionally aligns the old and new sequences and finds their common part.

In code, the difference is minimal: `generate()` needs to be passed both tokenizers.

from transformers import AutoModelForCausalLM, AutoTokenizer


TARGET = "google/gemma-2-9b"
DRAFT = "double7/vicuna-68m"

target_tok = AutoTokenizer.from_pretrained(TARGET)
draft_tok = AutoTokenizer.from_pretrained(DRAFT)

target = AutoModelForCausalLM.from_pretrained(
    TARGET,
    device_map="auto",
)

draft = AutoModelForCausalLM.from_pretrained(
    DRAFT,
    device_map="auto",
)

inputs = target_tok(
    "The capital of France is",
    return_tensors="pt",
).to(target.device)

out = target.generate(
    **inputs,
    assistant_model=draft,
    tokenizer=target_tok,
    assistant_tokenizer=draft_tok,
    max_new_tokens=64,
)

Now the draft and target are not required to belong to the same family at all.

But "you can use any small model" does not yet mean "any small model will provide acceleration." Recoding and alignment add overhead, and the draft model itself still needs to predict the target well enough. If it too often suggests an unsuitable continuation, the gain will disappear.

Therefore, a shared tokenizer remains the simplest and usually the cheapest option. Universal Assisted Decoding is primarily needed when the large model lacks a good small counterpart.

Pitfall: same tokenizer - not always same vocab_size

Compatible models have another non-obvious detail. The same tokenizer does not necessarily mean the same output layer size of the model.

Let's take Qwen2.5-7B-Instruct and Qwen2.5-0.5B-Instruct:

from transformers import AutoTokenizer

t1 = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
t2 = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")

print("Vocabulary size:     ", t1.vocab_size, "and", t2.vocab_size)
print("Vocabularies are equal:      ", t1.get_vocab() == t2.get_vocab())
print("Chat templates are equal: ", t1.chat_template == t2.chat_template)

Their tokenizers are effectively the same:

Vocabulary size:      151643 and 151643
Vocabularies are equal:       True
Chat templates are equal:  True

But `generate(..., assistant_model=draft)` still fails:

ValueError: The main and assistant models have different tokenizers.
Please provide `tokenizer` and `assistant_tokenizer` to `generate()`

The first suspicion is different chat templates. But the output above shows they match. The real reason is buried in the Transformers code: the check before generation compares not the tokenizers, but the `config.vocab_size` of the two models, i.e., the number of rows in the embedding matrix. And this is padded to different sizes in Qwen2.5:

config.vocab_size

There is no contradiction here. `tokenizer.vocab_size` describes the actual tokenizer vocabulary, while `config.vocab_size` defines the size of the model's embedding and output matrices. They can be padded with extra rows for convenient size alignment on hardware. The tokenizer never generates these additional IDs.

In older assisted generation implementations, such a difference could be an unpleasant surprise: the code expected identical vocabulary sizes even where the actual tokenization matched.

In the current Transformers, this case is already handled separately. Internally, there is a mapping between the token spaces of the target and assistant, and Qwen2.5-7B with Qwen2.5-0.5B are directly given in the source code as examples of models with a common tokenizer but different `vocab_size`.

Therefore, today, such a pair by itself is not a reason to abandon speculative decoding.

But before benchmarking, it's still useful to check both values:

print(target.config.vocab_size, draft.config.vocab_size)

In production: vLLM

For serving, speculative decoding is supported in vLLM out of the box: separate draft model, EAGLE and EAGLE-3, Medusa, MTP, n-gram, and even DFlash. Configuration is done via `speculative_config`:

from vllm import LLM, SamplingParams

# Separate draft model of the same family
llm = LLM(
    model="meta-llama/Llama-3.1-70B-Instruct",
    tensor_parallel_size=2,
    speculative_config={
        "method": "draft_model",
        "model": "meta-llama/Llama-3.2-1B-Instruct",
        "num_speculative_tokens": 5,
    },
)

# Without a second model: draft from n-grams of the prompt itself
llm_ngram = LLM(
    model="meta-llama/Llama-3.1-8B-Instruct",
    speculative_config={
        "method": "ngram",
        "num_speculative_tokens": 5,
        "prompt_lookup_min": 2,
        "prompt_lookup_max": 4,
    },
)

out = llm.generate(["Explain speculative decoding."], SamplingParams(temperature=0, max_tokens=200))

The format is based on the current vLLM documentation; in older versions, the keys were named differently, so check your version.

I'll specifically mention the n-gram draft, which is undeservedly rarely recalled. No second model, no extra KV cache – it just looks into the prompt. And it works well where the response repeats parts of the input: code editing, document extraction, RAG with citations.

If you have such a workload profile, start with it, not with selecting a second model. It's one line of configuration.

Can it be done without a second model at all?

Classic speculative decoding has an additional cost: a separate draft model needs to be selected, loaded into memory, and its own KV cache maintained. Moreover, a good small counterpart doesn't exist for every large model.

Therefore, several approaches have emerged where a full second LLM is not needed at all.

EAGLE: draft from the model's own hidden states

EAGLE uses a small trainable draft part that works not only with tokens but also with the target model's hidden representations.

In the original EAGLE, the key idea is this: predicting the next representation at the penultimate layer level is easier than predicting the next token directly. The draft module receives the hidden states of the target model and the already selected tokens, predicts the next hidden state, and through the LM head, converts it into the probability distribution of the next token.

The draft is still built autoregressively: the obtained token participates in predicting the next one. After several such steps, the candidates are verified by the main model.

The advantage is that the draft relies on a much richer signal than just a sequence of tokens. At the same time, a separate full-fledged small LLM is not needed, and the token space automatically matches the target model. For LLaMA2-Chat 70B, the EAGLE authors reported a speedup of 2.7–3.5× while preserving the original model's distribution.

Later, EAGLE-2 and EAGLE-3 appeared. In EAGLE-2, the candidate tree is built dynamically considering their acceptance probability, and EAGLE-3 uses features from several levels of the target model instead of initially predicting one type of hidden state.

Medusa: multiple heads, multiple positions at once

Medusa takes a different path. Several small decoding heads are added to the main model: one tries to predict the next token, another the token one position ahead, the next one even further.

The main difference from EAGLE is that these predictions can be obtained in parallel in one pass.

But parallelism comes at a cost. The head for the third position doesn't know in advance which token will be chosen for the second. Therefore, Medusa gets several possible continuations, builds a tree of candidates from them, and then verifies it with the main model using tree attention.

There are two main versions of the method. In Medusa-1, only the additional heads are trained, and the LLM itself remains frozen. The authors achieved over 2.2× speedup without changing the main model. In Medusa-2, along with the heads, the backbone is also fine-tuned; the claimed speedup in experiments was 2.3–3.6×.

Self-speculative: early exit from the same model

In LayerSkip, there is no separate draft module at all. The draft is generated by the target model itself, but only using its initial layers.

For example, instead of all 80 layers, one can pass through the first 12 and make an early exit. The tokens obtained this way become the draft, and then the remaining layers of the same model verify them and correct them if necessary.

This means verification doesn't necessarily mean another full model pass from scratch: the draft and verification can reuse some computations and activations.

For early exits to actually predict tokens, LayerSkip specifically trains the model with layer dropout and an additional loss on intermediate layers. Simply taking an arbitrary Llama and starting to exit after the twelfth layer is not the same.

The authors achieved up to 2.16× on CNN/DM summarization, up to 1.82× on code generation, and up to 2.0× on TOPv2.

The main advantage is no additional draft model weights. The disadvantage is that for good results, the target model itself must be prepared for early exit.

DFlash: draft in one pass via diffusion

Classic draft models and EAGLE have one common problem: the draft is built autoregressively.

A diffusion model generates a block of tokens in parallel: it starts with noise and refines the entire sequence in a few steps. DFlash trains a small diffusion head conditioned on the target model's hidden states and obtains the entire draft in one pass. And here's what's interesting: the cost of the draft stops increasing with its length. In terms of the formula above, is no longer multiplied by .

The authors report over 6× speedup without loss and up to 2.5× compared to EAGLE-3.

In the demonstration from the DFlash repository on a single mathematical task, it looks like this: autoregressive Qwen3-8B - 48.5 tokens/s, block diffusion SDAR-8B as a standalone model - 97.5 tokens/s with quality loss, EAGLE-3 - 114.2 tokens/s, DFlash - 415.7 tokens/s without loss. This is one example, not an average across benchmarks.

When it's not needed

Speculative decoding looks good in theory, but the acceleration is not achieved under all loads. There are several cases where the gain quickly diminishes or even turns into a slowdown.

Large batch and high GPU utilization. With a small batch size, decoding usually bottlenecks on memory, and the GPU's computational units are underutilized. It is precisely these free computational resources that speculative decoding uses to verify multiple candidates at once.

As the batch size increases, the situation changes. If for each of the sequences, we also check speculative tokens, the effective amount of work approaches . When the GPU is already loaded with computations, rejected candidates are no longer almost free and start consuming bandwidth.

Therefore, a fixed five or eight speculative tokens, which work well for a single request, may be a poor choice for a hundred simultaneous requests. Modern engines can reduce the speculation depth as the load increases.

Sampling and open-ended generation. Here too, there is no simple rule like "the higher the temperature, the lower the acceptance rate." Everything depends on how the overlap of draft and target model distributions changes after applying sampling parameters.

In practice, open-ended tasks often turn out to be more difficult for the draft than code continuation, summarization, or generation strongly tied to the input text. If the draft frequently diverges from the target, most of the extra work is wasted.

Therefore, the acceptance rate should be measured on real requests, not transferred from someone else's benchmark.

Memory for the draft model. The classic scheme requires storing not only its weights but also a separate KV cache for active requests. If the target model already occupies almost all GPU memory, a few gigabytes for the draft can reduce the available batch size, and the latency gain will have to be paid for with a loss in overall throughput.

In such a situation, methods with a small speculator module, EAGLE, or variants without a neural draft like n-gram and suffix decoding are more interesting.

Bitwise match of results. Lossless speculative decoding means preserving the target model's distribution, not necessarily matching every floating-point computation.

A different batch size, a different order of operations, or a different CUDA core can slightly change the logits. This usually doesn't affect anything, but with nearly equal probabilities, even greedy decoding can sometimes choose a different token.

If tests require exact string matches between different inference modes, this should be checked separately.

KV cache and speculative decoding work together

Speculative decoding does not replace the KV cache – on the contrary, without it, there would be much less practical sense in such a scheme.

With regular decoding, the KV cache stores keys and values for already processed context, so that the entire sequence is not re-processed for each new token.

In the classic scheme, the draft model maintains its own KV cache, allowing it to cheaply generate subsequent candidates. The target model, in turn, verifies the entire speculative block and saves the state for the part that was actually accepted. Computations for the rejected tail are not used further.

This results in two independent optimizations:

The KV cache prevents re-calculating already processed context; speculative decoding reduces the number of sequential decode steps of the large model.

They solve different parts of the same problem and are almost always used together.

Conclusion

The main idea of speculative decoding is quite simple: sequential generation by a large LLM often bottlenecks on memory bandwidth, while verifying several next positions can be done much more efficiently than several separate decode steps.

A small or specialized drafter tries to guess several tokens ahead, and a large model verifies them in one batch.

With sampling, quality is preserved not because "the large model agreed with the small one." In classic speculative sampling, this is backed by an acceptance rule and a correction distribution that preserve the target model's distribution.

And speed, in the first approximation, is determined by three things: how often the draft is correct, how much it costs itself, and how many tokens are proposed per iteration.

Therefore, the main practical advice here is simple: do not choose speculative decoding based on a nice number from an article. Measure the acceptance rate and latency on your traffic, with your batch size, and on the same hardware where the system will run.

The table of speedups above shows how much the result depends on the conditions: from 1.19× to 4.46×. The same algorithm, a difference of almost four times.
