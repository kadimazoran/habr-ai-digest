What is this Pokémon?

“First things first” — let's start with a brief overview of the product itself. Agentgateway (I'll shorten it to AGW) is a master orchestrator for AI. It's written in Rust by Solo.io and is part of the Linux Foundation. The first release was v0.0.2 in March 2025. Now, a year and a half later, the project has reached tag v1.6.0. One of its features, which I believe is super, is that the project is open-source on GitHub.

AGW Usage Diagram. From Official Documentation

AGW, as you can see in the diagram above, performs the following functions:

— Gateway to LLM providers;

— Gateway for MCP/A2A (Agent-to-Agent);

— Traffic management;

— Inference routing.

Traffic management implies:

— Controlling the number of tokens consumed and setting limits;

— Adding or removing headers in requests;

— Validating request content.

There are two ways to deploy this product: standalone and Kubernetes.

Why AGW Specifically

A reasonable question might arise for the reader: “Did you consider other products?” — “Yes,” I would answer. And now I'll explain why we settled on AGW. Before we got to the Solo.io project, we also considered lunar.dev and MCPJungle.

After researching the Docker images of these products, deploying them, testing core functionalities, and evaluating ease of use and availability of necessary features, it turned out that either the product configuration was too complex and unclear out-of-the-box, or they couldn't work without internet access. Moreover, one of the images had variables with credentials and an external host for sending logs (which, of course, we disliked).

We didn't come to using AGW on our own — thanks to recommendations from colleagues in another department. We later had meetings with them to adopt their best practices and avoid additional mistakes.

How to Run

I think there's enough theory — it's time for practice. Here's an example of setting up the standalone version 1.5.0. We'll need Docker installed and the AGW Docker image.

1) Pull the image:

docker pull cr.agentgateway.dev/agentgateway:v1.5.0

2) Create a directory for mapping into the container, which will contain the AGW configuration (config.yaml) and the SQLite database file:

mkdir agw-config

3) Run AGW (in this command, I specifically specified 127.0.0.1 so that the UI is not accessible to everyone from the internet, as we haven't configured authorization for it yet):

docker run -d 
  --name agentgateway 
  --user "$(id -u):$(id -g)" 
  -v "$PWD/agw-config:/config" 
  -p 127.0.0.1:4000:4000 
  cr.agentgateway.dev/agentgateway:v1.5.0

Core AGW Concepts

Gateways

A gateway is an entity responsible for entering our proxy. It represents a named port and endpoints through which traffic passes. In addition to the port, you can also select the protocol (HTTP, HTTPS, TCP, TLS) and attach certificates.

Each gateway object has one or more listeners. Multiple listeners might be needed when AGW has multiple hostnames.

Listeners

Listeners can “split” gateways. As written above, they are needed when a gateway has multiple hostnames assigned and, consequently, different TLS certificates are used. The gateway always has one listener under the hood.

Routes

Routes handle the processing and redirection of traffic entering the gateway. They are defined at the top level and are bound to gateways by name (one route can be used by multiple gateways).

Backends

Responsible for redirecting traffic to an IP address, hostname, LLM provider, or MCP server.

Policies

Policies are used for traffic management, monitoring configuration, and setting security rules.

Best Practices

To conclude this overview, I'd like to share some best (or production-ready) practices that my team and I learned while studying AGW.

Admin Panel Authorization using OIDC

Ideally, authorization in the AGW UI should only be available to gateway administrators. Why? Because users have endpoints for connection and MCP; they likely won't need more. This also protects against users accessing settings.

If you have a GitLab system or something similar, you can configure authorization using the OIDC protocol. This setting in AGW is located in Settings → OIDC.

In the gateway policies, you can specify which specific users have access to Settings → Authorization:



This way, we separate access zones and increase peace of mind.

Immutable Config

When working in the AGW UI and changing any settings, the config (config.yaml) is edited. It's available in the Tools → Raw configuration section:

However, this might be inconvenient for some. In such cases, you can change the file permissions (make it read-only) so that AGW cannot edit it.

HTTPS

The gateway allows configuring HTTPS connections and attaching certificates. This is more secure than HTTP. I recommend it.

Sensitive Headers

During the gateway's processing of various requests, HTTP headers with sensitive data might end up in the logs. The gateway can mask the necessary headers, but you need to specify them in the sensitiveHeaders field:

# yaml-language-server: $schema=https://agentgateway.dev/schema/config
config:
  sensitiveHeaders:
  - x-api-key
  - cookie
  - x-tenant-secret

This field is in the config (config.yaml), so the gateway only reads its values upon startup. You need to restart AGW after changing the sensitiveHeaders field.

AGW masks the specified headers when a request is received and again after request transformations and CEL (Common Expression Language, used in policies, transformations, and monitoring rules) backend execution.

Thus, not only the header sent by the client is edited, but also the header created as a result of the transformation.

Editing only affects the trace and debug output. The gateway still forwards the actual header value to the backend, and this value remains readable in the CEL expression, so policies or custom logging fields that read the header continue to work.
