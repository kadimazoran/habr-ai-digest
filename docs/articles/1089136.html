With the advent of AI agents in development, there's more code and more noise. Pull requests are growing, keeping an agent within the scope of a task is becoming more difficult, and more code is passing through a person's head. Reviewing is becoming the main workload, and the green numbers of added lines in the header start to become stressful even before you open it.

A typical scenario: a pull request for a small feature, and in it, changes in a dozen files that are not related to the task. Individually, they might be useful, but together they turn the pull request into a mishmash.

The Problem: The Agent Sees More Than It Can Handle

When an AI agent works on a task, it constantly stumbles upon side issues. An outdated dependency, duplicate code, a function not covered by tests, a strange variable name in a neighboring module. All of these are valid observations, but they are not related to the current task.

Then the agent does one of two things. Either it gets distracted and starts fixing everything: the diff inflates, the review turns into torture, and the context window is wasted on the wrong things. Or it mentions the finding in one of a hundred messages, and it gets lost forever.

A separate pain point is the context window. If the agent works in a waterfall mode and does everything in one session, the context gets clogged with side changes. The fuller it is, the worse the agent remembers why it came here in the first place: it forgets earlier agreements, gets confused by what has already been done, and after context compression, it loses details. Sometimes the session simply hits the limit in the middle of work.

Moreover, models differ. Some have larger windows, others smaller, and a task that one model completes in a session might not fit into another. Yet, tokens are limited for all: every incidental refactoring eats into the budget that should have gone to the main task.

The Idea: A Backlog Managed by the Agent Itself

After the euphoria of the first months of working with agents, when everything seems like magic, at some point you realize that the entire code writing system can be structured even better. First, you ask the agent not to do extra work. Then you look for ready-made solutions. Then you write your own skill that gives the agent instructions taking into account the specifics of your domain, and in the end, you get a solution you want to share with the team.

This led to the idea of a local development backlog—a full-fledged one, with a task lifecycle and checks. It's needed to avoid distractions for both the agent and the human in the moment. When working on a task, everything extraneous goes into the backlog:

  • observations and ideas found during work;

  • incidental refactorings that beg for a separate branch;

  • side effects of changes that need to be checked separately;

  • technical debt that would otherwise remain a TODO comment in the code;

  • questions for a human that the agent cannot answer itself.

The principle is simple: if we're automating, we automate everything. The backlog is primarily an agent's tool. It records tasks itself, takes them into work itself, and closes them itself with a link to the commit. And a Stop-hook after each agent's move checks if the code of open tasks has changed and asks to re-check them. The human doesn't need to maintain the backlog manually.

At the same time, the human still has a window to observe the work: how effective the agent is, what's already done, and what's left. Control without micromanagement.

From Idea to Implementation

To make the idea work, we had to answer three questions: where to store tasks, how the agent should work with them, and how the human should monitor this. The answers resulted in four parts:

Component

What it does

Core

Stores tasks and epics, backlog management logic

CLI

Add, view, take, close tasks from the terminal

Agent Skill

Instructs the agent when and how to record observations and how to take tasks from the backlog

Stop-hook

After each agent move, checks if the code of open tasks has changed and asks to re-check them

Server and Web App

Conveniently view and manage the backlog in a browser

The main interface became the CLI: it's easiest for the agent to call a command in the terminal, without tokens, APIs, or network. But the CLI alone is not enough—the agent needs to know when to use it. This role was taken by the skill: it turns "the agent has a CLI" into "the agent records tasks itself at the right time and takes them itself.".

The web part covers the second half of the idea—the window for the human. In the browser, you can see what's done, what's left, and how effectively the agent is working, without having to read a hundred tasks in the terminal.
