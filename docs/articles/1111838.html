Where it all began:

I use local language models for my tasks, automation, and scripts. But the thought that I could do more was constantly on my mind. I decided to try using local models in the development of large projects.

During testing, I quickly ran into a problem: first, you explain the task in detail: what needs to be changed, what restrictions to follow, what data not to touch, and what result to consider acceptable. Then the agent reads the code, calls tools, fixes something, runs tests… And after another context compression, it turns out that it still remembers the task name, but half of the original requirements are lost. Or another scenario: the agent confidently refers to an old successful test, even though it has already changed the source code since then.

Sometimes the model starts re-examining already explored files. Sometimes it returns to long-closed issues. And sometimes it confidently declares the task completed, even though the tests show the opposite. After a lot of struggling, I came to the question of how to fix this, tried many solutions, to-do lists, reminders for agents, RAG, and other shamanic rituals. Then the idea came up to try to solve this not through another system prompt, but through separate storage of requirements, history, and the verifiable state of the task.

Thus, the Code Context Engine (CCE) project was born. Now it's 0.1.0-alpha.1: TypeScript, local operation, npm packages, and the first full-fledged adapter for Pi. In this article, I will explain what already works, what is not yet proven, and why I need independent testers.

Why ordinary RAG is not enough

When it comes to memory for LLMs, the first suggestion is usually to use embeddings and a vector database. This helps find fragments of documentation and source code. But a coding agent has at least two fundamentally different problems.

The first is finding the right code. For example, the user asks to change the contact archiving rules in Django CRM. The agent needs to determine where the models, database operations, API facade, permission checks, and related calls are located.

The second is remembering what exactly needs to be done. For instance, the user previously set restrictions: data of different tenants must be isolated; a user with the role of viewer cannot change records, and so on. Even perfect code search does not guarantee that the agent will retain these requirements after several context compressions. I tried to solve these two problems in CCE.

Project Memory

The first layer is responsible for knowledge about the codebase. It uses a persistent index on SQLite, Tree‑sitter, FTS5/BM25 full-text search, symbol information, and a dependency graph. The index is not tied to a specific Pi session. If you open a new conversation in the same project, there is no need to rebuild the entire source map from scratch. However, the stored information cannot be considered eternal: CCE uses content hashes and checks the relevance of the source code.

Task Continuity Memory

The second layer is responsible for the task itself. It stores:

  • original user requirements;

  • versions of the Task Contract;

  • the history of events in the Context Event Ledger;

  • the current state of Verified Task State;

  • source code changes;

  • results of registered checks;

  • information about freshness and provenance.

And here I encountered and tried to solve an interesting problem (don't trust models): you cannot consider a model's statement "I fixed the error" as proof that the error is actually fixed. The model can write code. But this is just an observable change in the source code. The model can run tests. But the usual text in the terminal is not yet a confirmed result for the entire user contract.

I tried to teach CCE to distinguish between a fact of change, source code relevance, the result of a registered check, and task completion. For example, if a test passed, and then the corresponding file changed, the previous PASS should not automatically remain valid. This is a simple idea, but it proved very useful for long-term development.

How CCE survives compaction

The main integration at the time of the experiments was with Pi SDK 1.4.0. CCE connects to the agent's lifecycle and can form recovery and compaction handoff based on the saved task state. It is important that the handoff should not grow indefinitely at the expense of previous summaries. Simply put, the target principle is:

New recovery = current Task Contract + current Verified Task State + current source code information.

Not "previous summary plus new summary plus another summary." The detailed history remains on disk. The necessary current projection is passed to the context. But here I discovered the first serious error in my implementation.

How I managed to count 55 thousand tokens where there were none...

In one of the first long tests, CCE successfully processed two compactions, but refused to form its own handoff on the third. The reason seemed convincing: the system reported that there was no more space in the model's window. The window was 65,536 tokens. The old capacity guard estimated the saved history at approximately 55,025 tokens. Considering other reserves, the new handoff indeed did not fit.

At first, I suspected that previous compaction summaries were accumulating. But a subsequent audit showed otherwise.

It turned out that the old guard was counting archival native history entries that were no longer part of Pi's active message projection. One of these compaction entries occupied over 10,000 tokens when tokenized separately, but did not add a single message to the model's current history. CCE tried to estimate the size of the future context based on data that should not have been included in the future request at all.

After the fix, CCE began using Pi's prospective projection and checking the final serialized provider packet. This allowed for more accurate capacity calculation without changing the context window settings or native compaction. The lesson was useful: when integrating with an agent, it is important to consider not how much data is stored in its history, but what will actually be included in the next model request.

The next serious test: an eight-hour experiment with 16 real compactions

Conditions:

  • local Cyber Tiel Coder 35B A3B MTP in IQ3_XXS quantization;

  • Intel Arc A770 16 GB;

  • LM Studio;

  • Pi SDK 1.4.0;

  • 65,536 token context;

  • multi-phase CRM implementation task;

  • independent verification of intermediate results.

The experiment lasted eight hours and ended due to a watchdog before all 12 phases were completed. The main result was STOPPED / NOT_EVALUATED. It would be incorrect to declare the entire task successfully completed. However, the technical results were interesting.

The model did not just receive summaries. It continued actual development: changed source code, ran tests, and fixed errors discovered in previous stages. After 15 compactions, an independent oracle accepted the accumulated functionality of the seventh phase: 60 out of 60 checks passed. In the eighth phase, the model did not manage to complete the work. A partial snapshot received 63/68, but this does not change the main result.

Another observation: the handoff size increased with the addition of new mandatory requirements, but leveled off within an unchanged stage. There were no signs of simply copying all previous summaries into each new one. Nevertheless, 16 compactions do not mean 16 perfect recoveries. In one cycle, the original contract was preserved, but the fresh Task State did not fit into the additional automatic recovery. The system correctly indicated incompleteness, but this does not negate the problem of delivery reliability.

Where did 80 minutes go

During the eight hours, there were 16 HTTP request timeouts, each occurring approximately every five minutes. Initially, one might suspect a network problem, relay, or CCE itself. However, correlating all 204 requests with LM Studio logs revealed a different picture.

In all 16 cases, the backend was still processing the input prompt. Response generation had not yet begun. By the time of the interruption, prefill had reached approximately 66–89%. After changing the history, especially after compaction, KV-prefix reuse dropped sharply. The retry often used an already warmed cache and transitioned to generation faster.

Thus, the mechanism looked like this:

Compaction > early part of prompt change > reduced KV-cache reuse > long prefill > standard 300-second HTTP idle timeout > retry.

Additionally, the backend warned about partial attention execution on the CPU. Later, the idle timeout was increased to 480 seconds. This allowed requests with waiting for the first body for more than five minutes, but did not speed up prefill itself. One conclusion: placing a request in the context window does not mean that the local model can process it quickly.

Can the project continue in a new session?

The next stage was transferring the state between two independent Pi sessions. Scenario:

  • Session A performs the initial development phase.

  • CCE saves a verifiable checkpoint with requirements, task state, and links to the project index.

  • Session A is closed.

  • A clean session B is opened—without the old Pi transcript.

  • CCE restores the contract and project map from persistent storage.

Technically, the mechanism worked. Actual provider requests confirmed the delivery of original requirements, project map, and historical check state. However, independent coding acceptance in B was negative.

In the first experiment, the model returned sqlite3.Row from the archiving operation, which cannot be directly serialized by the standard JSON encoder. The model's own tests passed. The public check also passed. An independent oracle found the problem. It's particularly unpleasant that the requirement to return JSON-compatible structures was indeed in the delivered context. It turns out that the presence of a requirement in memory does not guarantee that the model will fulfill it.

In the second experiment, a different problem arose: after correcting the schema, the model repeatedly ran the same successful contact creation check but did not proceed to fix the remaining errors. This made me think about the third aspect of continuity—not just what the model knows, but also what next action it chooses.

Current Working State: Does a brief map of the next step help?

Here, another layer appeared—a small Current Working State block was added to the usual recovery. It contained the current goal, confirmed results, open issues, and a reasoned next step. For example, the system could report that the creation operation had passed local checks, but errors in unit tests and unverified update/archive operations remained. Importantly, such a block does not have independent authority. It is built from existing facts, not from arbitrary model statements.

Initially, I only checked the choice of the next action. Both baseline and CWS chose to run tests. No advantage was found. Then the idea came to conduct a series of short coding continuations with real tool execution and an independent oracle. The results were ambiguous.

In two comparisons, when CWS was launched second, it improved the partial result from 17/21 to 20/21. In two completed comparisons with the reverse order, both variants remained at 17/21. Neither variant completed all 21 checks. Additionally, CWS increased the known total input/output token consumption of completed attempts by approximately 3.6%.

The result was an interesting, but inconvenient for a nice presentation, picture: there is partial progress, but it is impossible to separate the influence of CWS from the order of launches, backend state, cache, and model variability. Therefore, I do not consider this experiment proof that CWS improves the quality of a coding agent. For now, the feature remains experimental.

What resulted in the end

At the current stage, CCE is a TypeScript project with two main memory layers. Project Memory helps work with current code. Task Continuity Memory stores requirements, task history, fact sources, and verified results. Integration with Pi allows delivering restored state during regular requests and during compaction. A mechanism for explicit state transfer to a new clean session has also been implemented.

However, the project still has limitations:

  • not every request is guaranteed to receive a full, up-to-date task projection;

  • the local model may exhibit repetitive actions without progress;

  • the API contract may be delivered correctly but violated in the final code;

  • the effect of CWS is not proven;

  • token savings relative to Pi-only have not been measured;

  • porting to other coding agents has not yet undergone similar testing.

I separately tested vector retrieval. On a small diagnostic set, it provided limited improvement for English search but did not help find target definitions for Russian queries. Therefore, I do not plan to make embeddings a mandatory part of CCE yet.

Why am I publishing all this

Initially, CCE was conceived as a tool for enthusiasts who run their own models and want to use them for real development. I want the project to remain open, and for other developers to be able to experiment with it, find weaknesses, and suggest improvements.

There is also a practical reason for publishing this article: my test environment is very limited. I have one home computer with an Intel Arc A770 16 GB. The eight-hour experiment described above is not an abstract example: such runs take a lot of time, and after each configuration change, some checks have to be repeated.

It is difficult to test different combinations of operating systems, models, backends, context sizes, and project types on a single machine. And even if you run all this sequentially, the results will still be heavily tied to one hardware configuration. Therefore, I need help from people interested in local LLMs and coding agents.

For a first acquaintance, it is sufficient: Node.js version 22.19 or higher, npm, Git, and ripgrep are required. Demo and offline evaluation do not access the model.

If you already have Pi set up and a local or cloud model, longer scenarios will be particularly useful:

  • several natural compactions within a single task;

  • continuing work in a new session;

  • modifying source code after a successful check;

  • long prefill and backend timeouts;

  • repetitive model actions;

  • comparing baseline and CCE on the same task.

For reporting, it is desirable to specify the OS, Node.js, Pi, model and backend, context size, scenario, and result. You do not need to publish private code, credentials, prompts, or full sessions—anonymized reproduction and diagnostics are sufficient. Especially useful are not only successful runs but also FAIL, UNKNOWN, native fallback, and cases where the behavior differs from expectations. If it turns out that CCE provides no advantage or creates additional problems, that is also an important result.

The project and instructions are available on GitHub. Setting up the lifecycle in Russian is described in a separate guide, and experiment protocols and results are published in the evaluation directory. The main idea of CCE remains quite simple: conversation history, project knowledge, and proof of task completion are different entities. They cannot be replaced by a single generated summary without loss. I want to find out how useful this approach is in practice, beyond my home setup, through independent tests.
