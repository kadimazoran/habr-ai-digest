I finished a piece of a project on my laptop in the evening, sat down at my PC in the morning, and started explaining to the assistant what was done yesterday. The second time this week.

By then, it already had memory. A folder with notes on the disk, it writes to it and reads from it itself. The trouble is that the folder was on only one of the two computers.

I didn't want to set up cloud storage for this, and even less so pay for note synchronization. In the end, it all came down to a private repository and two hooks of twenty lines of bash.

Below: why a cloud folder, Obsidian Sync, and a plugin didn't work, how the script is structured, what broke along the way, and why a separate storage is needed at all if Claude Code has built-in memory.

What is this brain and where did it come from

I work in Claude Code. Two months ago, I allocated a folder for it and told it that it could write anything it needed for working with me there.

Now there are 114 notes and 367 links between them: profile, project cards with figures, infrastructure, daily log, workdays. The format is standard markdown, with Obsidian as a reader on top. The agent doesn't need Obsidian; files are enough for it.

Next, about what I had to do with this setup to make it work on two machines.

Why a separate storage if there's built-in memory

This is the first question I get asked, so I'll answer it right away.

Claude Code has built-in memory, located in ~/.claude/projects/<project>/memory/, with a MEMORY.md index file and short notes nearby. The index is automatically loaded into each session.

There are three problems with it, all related to boundaries.

It's tied to the machine. The directory is in the user's system profile; it doesn't automatically transfer to the second computer.

It's tied to the project. A folder is created for a working directory, but my facts aren't about a single project. Where a disk is located, what was discussed on a call in August, what figures are in my resume, all this moves from task to task.

Its structure is limited. The index is loaded entirely into each session, meaning it has no room to grow. It's a table of contents, not a database.

Therefore, I use both. The built-in memory holds a few lines like "details are in such-and-such storage," while the storage itself lives in a separate repository and can be as large as needed. One doesn't replace the other.

In storage, not volume, but routing is important

The temptation is obvious: feed the agent everything it has. This should not be done, not because of limits, but because with a full context, the model starts confusing adjacent facts and latching onto things discussed five screens ago.

Therefore, the main file of the storage is not a table of contents, but a routing table. It looks like this:

Query about

Open

who I am, experience, education

01 - Profile/Profile

my projects and their figures

02 - Projects/00 - Project Map

any text to send to people

04 - Resume and Texts/Anti-AI Style

what is where on disks, server

06 - Infrastructure/File Map

"what happened then"

07 - Log by date

The agent opens this file, finds the line for the task, follows it, and stops. Two notes instead of one hundred and fourteen.

The rules for reading and writing are in the global ~/.claude/CLAUDE.md, which is picked up in any session. There are three of them.

Read selectively. Only what the routing points to. Do not read the entire storage, do not scan it with search unnecessarily.

Do not ask what is already recorded. If a fact exists, use it silently. If it contradicts what the agent sees in the files right now, trust the files and correct the note.

Append after work. A new fact about a person to the profile, a project update to the card, a significant session to the log. Dates are absolute; "last week" cannot be deciphered a month later.

The third rule is the most fragile; without it, the database becomes stale in two weeks. I've made it an automatic process with a separate line in the config: at the end of the response, the agent states in one sentence exactly what it has recorded. This line is for me to see that it hasn't forgotten.

Another small thing that cost me an evening. Links between notes must be written as wiki-links, [[02 - Projects/Name]]. I used to use backticks for paths, and it looked fine until the day I opened the graph: out of 104 notes, 25 were hanging without a single link, including the routing file itself. The graph only sees wiki-links.

What I tried for synchronization

Cloud folder. Inside, there are almost a thousand small files that are modified by automation several times per session. Cloud clients turn this into "START HERE (conflict copy).md". This was immediately discarded.

Obsidian Sync. Paid and only works through Obsidian.

Obsidian Git plugin. Free and does everything needed, but only works while Obsidian is open. I don't want to keep the editor running for background synchronization, especially on a laptop.

Agent's own hooks. This is what I settled on. The logic is simple: the storage is needed precisely at the moments when I am talking to the agent. Therefore, synchronization should happen at the start of the session and after each response, and at other times, nothing needs to be done.

Twenty lines of bash

The storage was moved to a private repository on GitHub. First commit: 105 files, 0.86 MB.

Next is the script that is triggered by hooks.

#!/usr/bin/env bash
# sync.sh start - SessionStart hook: clone (if storage doesn't exist yet) or pull
# sync.sh stop  - Stop hook: if there are changes, commit, pull --rebase, push

BRAIN_DIR="${SECOND_BRAIN_DIR:-D:/Obsidian/Claude_brain}"
REPO_URL="${SECOND_BRAIN_REPO:-https://github.com/USER/second-brain.git}"
DEVICE="${SECOND_BRAIN_DEVICE:-$(hostname)}"

# No interactive login prompts from the hook. Export GIT_TERMINAL_PROMPT=0 GCM_INTERACTIVE=never

# The hook passes JSON to stdin, it's not needed, just read it.
[ -t 0 ] || cat >/dev/null

g() { timeout 60 git -C "$BRAIN_DIR" "$@"; }
system_message() { printf '{"systemMessage": "%s"}\n' "$1"; }

start() {
  local status last
  if [ ! -d "$BRAIN_DIR/.git" ]; then
    if timeout 180 git clone -q "$REPO_URL" "$BRAIN_DIR" >/dev/null 2>&1; then
      status="cloned from GitHub for the first time"
    else
      echo "[Second Brain] Not available yet: no repository or network."
      return 0
    fi
  elif g pull -q --rebase --autostash >/dev/null 2>&1; then
    status="updated"
  else
    g rebase --abort >/dev/null 2>&1
    status="NOT updated (no network or conflict), working with local copy"
  fi
  last=$(g log -1 --format='%cd, %s' --date=format:'%Y-%m-%d %H:%M' 2>/dev/null)
  echo "[Second Brain] $status. Path: $BRAIN_DIR. Last commit: ${last:-none}."
}

stop() {
  [ -d "$BRAIN_DIR/.git" ] || return 0
  if [ -n "$(g status --porcelain 2>/dev/null)" ]; then
    g add -A >/dev/null 2>&1
    g commit -q -m "$DEVICE: autosync $(date '+%Y-%m-%d %H:%M')" >/dev/null 2>&1
  fi
  local ahead
  ahead=$(g rev-list --count '@{u}..HEAD' 2>/dev/null) || return 0
  [ "${ahead:-0}" -gt 0 ] || return 0
  if ! g pull -q --rebase --autostash >/dev/null 2>&1; then
    g rebase --abort >/dev/null 2>&1
    system_message "Second Brain: failed to pull changes before sending."
    return 0
  fi
  g push -q >/dev/null 2>&1 ||
    system_message "Second Brain: push failed, changes will go in the next sync."
}

case "$1" in
  start) start ;; 
  stop) stop ;; 
  *) echo "usage: sync.sh start|stop" >&2; exit 2 ;; 
esac
exit 0

It is connected in ~/.claude/settings.json:

{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "C:/Program Files/Git/bin/bash.exe",
            "args": ["C:/Users/USER/.claude/second-brain/sync.sh", "start"],
            "timeout": 200,
            "statusMessage": "Syncing second brain…"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "C:/Program Files/Git/bin/bash.exe",
            "args": ["C:/Users/USER/.claude/second-brain/sync.sh", "stop"],
            "timeout": 120,
            "async": true
          }
        ]
      }
    ]
  }
}

Four places that seem minor, but each of them I added for a reason.

GIT_TERMINAL_PROMPT=0 and GCM_INTERACTIVE=never. The hook runs in the background; you won't see the login prompt window. You'll only see the session start hang and won't understand why. Also, timeout for each git call, so a dead network doesn't cost two minutes before each response.

--autostash. I often edit a note manually in Obsidian and don't commit; without this flag, pull would fail.

[ -t 0 ] || cat >/dev/null. The agent passes JSON to the hook via stdin. If it's not read, the script risks catching SIGPIPE out of nowhere.

The output of start goes to stdout and directly into the model's context. This means the agent knows from the first tokens whether its database is fresh or if it's working with a local copy from two days ago. Errors in stop, on the other hand, are sent to me via systemMessage because I have to fix them anyway.

Commits are signed with the machine name: DESKTOP-7RNA8QS: autosync 2026-09-29 22:28. The history shows where I was sitting.

No configuration was needed on the laptop. The same script, the same config, the first session, and the storage downloaded itself.

What broke

Two synchronization channels clashed. I didn't disable the Obsidian Git plugin, and both worked for some time. The plugin pulls changes by merging, the hook by rebasing. It ended with the plugin committing the agent's edits in the middle of a session, pulling lines from the laptop, and leaving <<<<<<< markers inside the main routing file. I had to resolve it manually and necessarily with a merge commit, which had to be pushed immediately, otherwise the hook's pull --rebase would re-play the same conflict. The conclusion is banal: there should be only one channel.

Absolute paths. Half of the infrastructure notes are lines like D:\Obsidian\... and F:\ComfyUI\..., but the laptop doesn't have D and F drives. I had to write directly in the routing file that the paths lead to the PC and create a separate note for the laptop.

Commit after each response. Over a long evening, a dozen "autosync" commits accumulate. This suits me; the history is messy but honest. For those who find it bothersome, it's easy to add a condition for a minimum interval.

What to check before putting personal data in a repository

There were no keys or tokens inside, but there were lines like "bot tokens are in such-and-such file on the desktop." Formally, this is not a secret, but in practice, it's a map to secrets, and it's worth keeping it consciously.

.gitignore includes .obsidian/workspace*.json, .trash/, system garbage, and most importantly, .obsidian/plugins/*/data.json. The latter is not obvious: Obsidian plugins store API keys from third-party services in these files.

Check the repository's privacy setting using the command, not by remembering which button you pressed.

What it gives and what it doesn't

It gives this. I sit down at my laptop, write to the same brain, and in the evening at my PC, it's already there. The agent doesn't ask my stack for the third time and remembers how a specific conversation ended on a specific day. The side effect turned out to be more pleasant than the main one: over two months, a database of facts about myself with figures has accumulated, and it's unexpectedly convenient to assemble a resume from it.

Now, you could say, Claude is collecting information for my resume. I don't need to calculate, study the stack, or recall decisions. Claude is aware of my project, which means information about it is already recorded in the second brain. One prompt "update resume," and the struggle with updating information has turned into an automated information collection system.

It doesn't give this. The model doesn't become smarter because of it. The quality of responses depends on the quality of notes, and the notes are written by the same agent under my supervision. If you let it go on its own, in a month it will be a dump where one question has three answers of varying freshness. Therefore, I consider the rule about selective reading and the rule about absolute dates no less important than the entire git.

And separately: this is not a place for work secrets. The repository is private, but a private repository is a locked door, not a safe.

What's next

I want to run the storage for contradictions and outdated facts once a month; I don't get around to it manually.

If you decide to repeat this, don't start with the script. Synchronization is twenty lines of bash, but deciding which query leads to which note is something no one can do for you.
