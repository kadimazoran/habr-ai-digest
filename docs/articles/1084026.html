Terms Used in the Article

Project-DR ERP Technology Distribution — the full name of the technological assembly. Hereinafter referred to as the "Project-DR ERP technological assembly," version.

Project-DR — Project Digital Replica — an internal production technology and project environment in which a professional enterprise model is built and structurally restructured as needed. Project-DR is not transferred to the client as a technological environment.

Project Core — a project carrier of a specialized resource, which stores the detailed result of its work on a specific project.

Unified Project Store — a machine-readable layer of Project-DR where accepted projections of specialized Project Core results are collected.

Enterprise-DR — Enterprise Digital Replica — an operational machine-readable model of a specific enterprise, obtained from the accepted state of Project-DR. It is Enterprise-DR that is transferred to the client.

Enterprise-DR Runtime — the operational environment for Enterprise-DR — a physically running system where the client model is loaded into a database and accessible via the Enterprise-DR API.

Enterprise-DR Runtime Kit — the kit transferred to the client for deploying and operating Enterprise-DR.

PostgreSQL — the database management system used in version 2.5.1 as the reference implementation of the Enterprise-DR database. Hereinafter referred to as the "Enterprise-DR database.".

Enterprise-DR API — the programmatic interface for accessing the operational model. It is used to obtain professional context, reasons for decisions, dependencies, signals, and change operations.

Local LLM — Local Large Language Model — a natural language interface to Enterprise-DR. For example, a compact Qwen2.5-0.5B-Instruct or a similar local model can be used for this role. This is an example, not an advertisement or a mandatory choice. In the reference delivery 2.5.1, the control model gate_seq2seq_transformer.pt is used for self-checking. Hereinafter referred to as "LLM.".

Baseline — the accepted state of the model, relative to which subsequent changes are recorded. Hereinafter, the short form "baseline" is used.

Project-DR — the technology for building and structurally restructuring the enterprise's digital replica. Enterprise-DR — the operational result of this work.

The client receives Enterprise-DR of a specific enterprise. Project-DR remains an internal production technology.

Introduction

The first part of the article "ERP Implemented. What's Next?" was published on Habr. After its publication, colleagues asked to separately and without literary prose show the engineering structure of the operational core: where project knowledge is accumulated during Project-DR, how Enterprise-DR is obtained from the accepted state, what is physically transferred to the client, and how this model is operated after launch.

This third part is dedicated precisely to this. Below, we examine the route from specialized Project Cores and the Unified Project Store to the client's Enterprise-DR Runtime, normal operation through queries and signals, and the boundary beyond which changes to the professional model must be returned to Project-DR.

1. What Engineering Question Remains After the ERP Project is Completed

After reconstructing a working ERP, a question remains that cannot be resolved with a set of reports, instructions, and project files: in what form should the restored professional enterprise model continue to exist after the project is completed? While Project-DR is underway, this model is actively built and refined. The survey defines the subject perimeter, the operational model links processes to procedures and operations, the accounting layer solidifies the rules for reflecting economic events, the information layer defines data requirements, and the scenario loop verifies that the adopted decisions are indeed executed. By the end of the reconstruction, not just a set of documents emerges, but a connected description of how the enterprise should operate and how this state is implemented in the ERP.

If only Excel files, human-readable documents, and project archives are saved at this point, the project's result will be recorded, but not the operational professional memory. After some time, part of the meaning will again be in correspondence, part in ERP settings, part in instructions, and part in the memory of individual specialists. Therefore, the adopted Project-DR model must transition to a separate form designed not for building the model, but for its long-term operation.

In version 2.5.1, this transition is formalized as a separate technological route: Project-DR produces the accepted professional model, and Enterprise-DR receives its operational projection.

The key boundary is formulated unequivocally. Project-DR is the production technology for reconstructing and building the professional enterprise model. Enterprise-DR is the operational digital replica of a specific enterprise obtained from the accepted Project-DR result. Therefore, Enterprise-DR cannot be considered either a copy of the entire Project-DR or another report within the project.

2. Why Project-DR is Not Transferred to the Client

Project-DR contains significantly more information than is required for the operation of a specific enterprise. It includes not only the accepted data and decisions of the client but also universal masters, donor libraries, model-building mechanisms, survey generators, technological templates, verification rules, control contracts, and starter kits. It is these components that allow taking another enterprise and repeating the reconstruction technological cycle.

Therefore, transferring the complete technological assembly with its 29 resources to the client would mean transferring not only the result of the work on their enterprise but also the production technology that allows creating new Project-DRs. Such a volume is not needed for operation. The enterprise needs to receive its own accepted professional model and tools to work with it, not a universal tool for producing similar models for other projects.

In the v2.5.1 technological assembly, this boundary is physically secured. The client release undergoes a separate delivery scrub: universal donor models, factory and generative logic, the complete Project-DR ERP technological assembly, the internal Project-DR control loop, and universal reconstruction templates must not be included. Not only the presence of prohibited files is checked, but also residual technological links within the data. Critical technology leakage must be zero.

The final rule for delivery is simple: the client receives Enterprise-DR of their enterprise; Project-DR as a reconstruction technology remains the internal technological know-how of the provider. At the same time, the client's professional data, their processes, operations, standards, scenarios, decisions, and evidence are not lost. They pass through the controlled boundary into the operational model, while universal production mechanisms do not.

3. Where Project Information is Accumulated During Project-DR

The enterprise's professional model does not appear immediately in one general file. It is formed by specialized technological resources, and each is responsible for its own part of the project result. Therefore, during Project-DR work, information is initially distributed across the Project Cores of the corresponding resources.

Survey results are stored in the QNR Project Core: accepted answers, perimeter clarifications, operational facts, decisions, and model changes remain there. The operational model is stored in the OEM Project Core: project items, process library, business directions, chains, procedures, and operations appear there. The accounting layer is formed in the ACC Project Core, the information architecture in the NPA Project Core, scenarios and verification results in the SCN Project Core, and the history of accepted changes is maintained in the corresponding origin and versioning loops.

This is not temporary fragmentation or an architectural defect. The detailed project result must remain with the resource responsible for its construction and verification. In the v2.5.1 technological assembly, this principle is preserved: the specialized Project Core remains the owner of the detailed project content, and its traceable accepted projection is transferred to the unified store.

Therefore, the answer to the question "where were the results recorded after the work of a specific core?" consists of two parts. The detailed result remains in the Project Core of the corresponding resource. After acceptance, the result needed for general project and future operational memory is synchronized into the unified project store.

4. Why a Unified Project Store is Needed

A distributed model is convenient during design but inconvenient for subsequent machine operation. If only specialized Project Cores are retained, any end-to-end query would first require identifying the object's owner, then searching for related information in other cores, and separately retrieving decisions, versions, and evidence. This method is acceptable for production technology but not for the permanent operational memory of an enterprise.

Therefore, between the distributed Project Cores and Enterprise-DR, the Unified Project Store of Project-DR is introduced. It does not replace specialized cores or relieve them of responsibility for detailed content. Its function is to collect accepted project objects in a common structure and maintain their unified identity, relationships, versions, origin, decisions, evidence, and baseline states.

For example, the detailed description of an operation continues to belong to the OEM Project Core. But the unified store must unequivocally know that operation OP-117 exists, to which procedure and process it relates, what business item it modifies, what role performs it, what ERP object implements it, what scenario verifies it, and by what decision its current version was changed. It is this end-to-end connectivity that the Unified Project Store creates.

The unified project store is therefore not a new methodology or another report. It is a machine assembly of accepted Project-DR results necessary to obtain a unified state of a specific enterprise from a distributed production environment.

5. How Project-DR Accumulates the Unified Enterprise State

The Unified Project Store is not manually assembled once at the end of the project. The state is accumulated as specialized results undergo acceptance. While an item, process, operation, or rule is under development, its detailed state remains in the owner's Project Core. After acceptance, a versioned projection of this object is published to the unified project store along with its source, type, natural identifier, status, baseline version, and origin.

If a business item is confirmed during the survey, its accepted projection appears in the Project Store. When the operational model links a process and operations to it, corresponding entities and relationships are added. After the accounting rule is accepted, it is linked to the same professional objects. When a scenario verifies an operation, evidence is generated. If a decision modifies an existing object, a link is maintained between the previous version, the new state, and the reason for the change.

By the end of Project-DR, the unified project store contains not a set of independent records, but the connected accepted state of the enterprise. At the same time, backward traceability is preserved: any object can be linked to its Project Core, original record, decision, and evidence. In version 2.5.1, Project Core additionally maintains synchronization states, Enterprise-DR state, an index of released Enterprise-DR releases, and an index of assembled runtime kits. A separate Project Enterprise-DR Core maintains synchronization of the Project Store, release issues, runtime instances, change sets, structural rollbacks, evidence, QA, and runtime kits.

This is fundamentally different from a traditional project archive. Human-readable documents can be generated in parallel, but they cease to be the sole carrier of meaning. The accepted result of each professional layer becomes part of the overall machine-readable project memory.

6. What is Fixed Before Enterprise-DR Release

Project-DR contains not only final results. During the work process, it includes hypotheses, intermediate versions, yet-to-be-accepted links, and working versions. Enterprise-DR cannot be built from this entire array. The operational model must start with a clearly defined accepted enterprise state.

Therefore, before compilation, the accepted baseline version of the Unified Project Store is fixed. First, the accepted projections of specialized Project Cores are synchronized, then the identity, relationships, and origin of objects are verified, after which the project state is fixed as the initial baseline for the release. Only then is the client perimeter defined, and the compilation of Enterprise-DR is permitted.

This order ensures three properties. Accidental working versions do not enter the operational system. Every included assertion has a source in Project-DR. Subsequent changes are compared against a specific baseline version, not an undefined "state at launch." This is where the project model becomes a versioned professional result suitable for operational release.

7. How Project-DR Becomes Enterprise-DR

After fixing the accepted baseline, not file copying, but operational model compilation begins. The Unified Project Store is fed into the compiler. Then, the client compilation policy is applied: only accepted objects of the specific enterprise, their current versions, permitted relationships, necessary evidence, and decisions are selected. The result is a candidate Enterprise-DR release.

The next step is the delivery scrub, i.e., checking the delivery boundary. It removes and blocks everything related to the Project-DR reconstruction technology that is not required for enterprise operation. After successful verification, a neutral Enterprise-DR release is formed — a machine-readable package of the specific enterprise model, logically separated from the physical server on which it will run.

The transition sequence looks like this: specialized Project Core → accepted projections → Unified Project Store → accepted Project-DR baseline → customer compile policy → Enterprise-DR release candidate → delivery scrub → neutral Enterprise-DR release. Only after this does the separate client runtime route begin.

The result boundary is now formulated unambiguously. Project-DR produces the professional enterprise model. Enterprise-DR receives sufficient professional memory for the operation of this enterprise but does not receive the universal production technology required to build a new Project-DR.

Project Core → Unified Project Store → accepted Project-DR baseline → compile → delivery scrub → Enterprise-DR release

8. What is Inside Enterprise-DR

After compilation, Enterprise-DR is a self-contained operational object. Its primary unit is not a document or a report page, but a professional entity: a business item, process, procedure, operation, role, rule, scenario, decision, evidence, or application binding. These entities do not exist in isolation but within a system of explicit relationships.

An operation can relate to a procedure and a process, modify the state of an item, be performed by a specific role, be implemented by an ERP object, and be verified by a scenario. A decision is linked to the modified objects and the version it generated. Evidence is linked to the result it confirms. Thanks to this, Enterprise-DR stores not only "what is" information but also the causal structure of "how it is related" and "why it was decided.".

Versioning is a mandatory part of operational memory. The current version of an object does not destroy the previous one. If an operation was changed, the old state is preserved, and the new version receives a basis, effective date, and links to the decision and verification. As a result, the enterprise's history becomes part of the same machine-readable model, not a separate correspondence archive.

Human-readable books, reports, and instructions remain useful derivative results, however, the central operational asset is precisely the machine-readable professional memory. It allows not only reading the project result but also using it as a source of context in daily work.

9. Why the Reference Implementation Uses PostgreSQL

Excel is convenient as a working medium for Project-DR because it allows quick viewing, verification, and restructuring of complex project structures. For long-term operation, different properties are required: multi-user access, transactions, stable relationships, version control, API access, and the ability to safely use data without transferring the entire model to each user.

In the v2.5.1 technological assembly, the physically verified reference implementation of Enterprise-DR is PostgreSQL 18.1. For semantic search, the pgvector 0.8.5 extension is provided. This does not mean that the professional model belongs to a specific DBMS or must always be deployed only on PostgreSQL. PostgreSQL is the reference implementation on which the full route from client release to running runtime has been verified.

The professional model in the database is not reduced to numerical identifiers and foreign keys. Entities have a type, human-readable name, purpose, description, status, version, and additional structured attributes. Relationships also have their own professional type. Therefore, the database stores both strict structure and the meaning necessary for an analyst and API.

Vector search, in this case, is an additional navigation mechanism, not a source of professional truth. It can help find an object by the user's natural formulation, after which the current state and dependencies are restored using precise entities, relationships, versions, and decisions. The accepted truth is in the versioned Enterprise-DR model, not in the proximity of embedding vectors.

10. Why an Analyst and Language Model Do Not Work Directly with PostgreSQL

If a lead analyst has to know the physical database schema and write SQL for every query, Enterprise-DR turns into a technical storage. Connecting a language model directly to PostgreSQL with read and write permissions would be even more risky. In this case, the model would simultaneously have to understand the data structure, independently select queries, and potentially have the ability to modify professional memory.

Therefore, between the database and the user is the Enterprise-DR API. Its task is not simply to retrieve rows from tables, but to perform professional operations on the model: restore object context, explain the origin of a decision, identify dependent elements, register a signal, and prepare a manageable change package.

The resolve_context operation collects the current version of the object, its immediate relationships, origin, and necessary evidence. For the user or local model, the result is a compact package of professional meaning, not a set of PostgreSQL tables. Thanks to this, the physical database schema can evolve independently of the user interface.

The API also serves as a security boundary. The language model does not get arbitrary UPDATE or DELETE access. It can only access provided operations. Therefore, the large professional memory of the enterprise does not turn into a huge context window: for a specific query, the API selects only the part of the model that is actually needed for the answer.

11. What Role Does the Local Model Perform

The local language model is not the owner of professional knowledge and does not determine which version of the enterprise model is considered current. The knowledge resides in Enterprise-DR. The model performs an interface function: it understands the human request, calls an authorized API operation, and transforms the obtained professional context into an understandable answer.

This separation significantly reduces dependence on a specific LLM. If the search for objects, relationships, versions, and evidence is performed by Enterprise-DR, the language model does not need to reconstruct the enterprise from a large set of documents each time. It is passed an already assembled context. Therefore, the local LLM can be replaced without rebuilding the professional memory.

The standard Windows runtime kit version 2.5.1 physically includes the local control model Gate-B gate_seq2seq_transformer.pt. This is a frozen neural model used in the research Gate-B and re-verified during the assembly of version 2.5.1. It is not positioned as a universal industrial LLM for a real enterprise. Its function is to provide a known local interface, self-checking, and to prove that the entire loop can operate without mandatory cloud calls.

For industrial operation, the enterprise can use another local LLM that matches its language, load, hardware, and information security requirements. In a closed loop, the database, API, local LLM, and evidence can reside within the corporate network; an external cloud is not required for normal operation.

12. Normal Operation: A Professional Question

The simplest mode of operation does not change the model. The user or analyst wants to understand the already accepted enterprise state: who performs an operation, why a specific field is required, to which process an action relates, what scenario verifies the result, or based on what decision the current rule is acting.

In traditional operation, such a question often triggers manual investigation. The analyst opens the configuration, old technical specifications, instructions, emails, and tries to reconstruct the original meaning. Enterprise-DR should reduce precisely this repetitive work. The user asks a question, the system determines the professional address, the API collects the current context, after which the local model forms an explanation.

The language model should not guess relationships. If the question relates to an operation, the context may include the process, role, rule, application binding, decision, and evidence. If no confirmed basis is found, the correct result is an indication of the absence of such a basis, not a plausible explanation generated by the model.

The reference customer release within the v2.5.1 technological assembly is minimal and intended only for checking the launch route. It does not represent a real enterprise model. In a working project, this demonstration set is replaced by a compiled customer release obtained from the specific client's Unified Project Store.

question → professional address → resolve_context → current context → local model → answer

13. Operational Signal: When a Question Becomes an Event

The second mode arises when the user reports not a question, but a new fact: a Service Desk request, an email, an error, a deviation, a result of observation, or a suggestion to change something. Such input cannot be immediately interpreted as a command to change the professional model. First, it is registered as a signal and receives a professional address.

Enterprise-DR links the signal to an item, process, operation, rule, or application implementation and determines if existing context is available. If the situation is known, the system can return an existing instruction, decision, recovery route, or other confirmed knowledge without changing the model itself.

If the signal indicates a possible discrepancy between the accepted model and actual operation, it becomes grounds for analysis. But even in this case, the enterprise model is not automatically changed. First, it must be established whether only the operational state and evidence are affected or if a review of the accepted professional model is indeed required.

This boundary is fundamental: an email, ticket, or user suggestion is not new professional truth. They are operational events that Enterprise-DR must preserve, link to context, and forward to the correct route.

14. What Enterprise-DR Can Change Independently

Enterprise-DR must be able to accumulate operational history without launching a new Project-DR for each event. Therefore, within the runtime, execution states, signals, observations, evidence, verification results, runtime kit statuses, and other data describing the life of an already accepted model, but not changing its professional structure, can be modified.

Versioning the technical representation of an already known object is also permissible if such a change does not revise its professional meaning and does not require new subject engineering. For example, a new verification result, a new runtime state binding, or a new evidence record can be fixed. At the same time, the origin of the change and the previous version are preserved.

However, this article uses a strict product boundary: if the accepted professional enterprise model itself needs to be changed — its items, processes, operations, standards, authorizations, or causal relationships — Enterprise-DR must not rebuild this model independently. Such a change becomes grounds for returning to Project-DR. This separates the operation of the accepted state from the re-design of the enterprise.

15. Why a New State Cannot Be Overwritten on the Old One

Even operational changes must be versioned. If an object had one state yesterday and another today, it is important for professional memory to preserve both states and understand the reason for the transition. Overwriting the last value destroys the digital thread and makes it impossible to reliably answer why the enterprise operated differently in the past.

Therefore, object identity and its version are separated. An operation remains the same operation but can have a sequence of states. The previous version is closed by its effective date, and the new one receives its own basis, date, decision, or evidence. As a result, it is possible to reconstruct which version was active at a specific moment and why it was replaced.

This is how the operational digital thread is formed: initial signal → reviewed context → decision → affected object → new version → verification evidence. Even if the outcome is a return to Project-DR, this package already contains the entire operational history with which the project loop must begin work.

16. Who Has the Authority to Change the Professional Model

The presence of a local LLM does not change the distribution of professional authority. A language model can parse a signal, retrieve context, show dependencies, and prepare a change proposal, but it does not have the right to independently declare a new professional enterprise model as current.

If the analysis shows that a change to the accepted model is required, Enterprise-DR generates a structured package: signal, current context, affected objects, preliminary impact analysis, authorized person's decision, and available evidence. This package becomes the input for a new Project-DR route.

This limitation is architectural, not a consequence of a specific neural model's weakness. Changes to the professional model can affect accounting, production, quality, user rights, automated executors, and enterprise obligations. Therefore, the new model must undergo the same level of subject engineering and verification used during its initial construction.

17. When Enterprise-DR Returns Work to Project-DR

The return boundary arises when a problem can no longer be solved within the framework of the current accepted model. This could be the emergence of a new independent business item, a new significant process, a change in an object's lifecycle, a restructuring of a business direction, a new authorization system, or another change that cannot be correctly expressed by existing entities and relationships.

In the technology, there is a structural Project-DR handoff route for this. Enterprise-DR should not invent missing professional structures. It records the fact, collects the context, and transfers the task back to Project-DR. Thus, the operational core explicitly defines the limit of its authority.

This rule can be summarized briefly: Enterprise-DR operates the accepted professional model; Project-DR builds and restructures the very structure of this model. Therefore, changing the model is not free database editing, but a new order for Project-DR of the corresponding scale.

18. How the Result of a New Project-DR Returns to Enterprise-DR

Returning to Project-DR does not mean re-reconstructing the entire enterprise. Enterprise-DR transfers a specific structural change package: the initial signal, current objects, history, decision, and preliminarily identified dependencies. Project-DR opens only those professional routes necessary to change the affected part of the model.

If a new management item appears, its subject processing is performed. If the operational model is restructured, the corresponding OEM section is changed. If accounting, data, quality, interface, or scenarios are affected, the corresponding Project Cores are involved. After acceptance, the new results are again synchronized into the Unified Project Store.

Then, the standard release process is repeated: a new accepted Project-DR baseline is fixed, the customer compile policy is applied, the delivery scrub is performed, and a new version of Enterprise-DR release is formed. This version is loaded into the runtime and, after verification, becomes the new operational state of the enterprise.

This results in a closed lifecycle: Enterprise-DR detects the boundary of the current model → Project-DR restructures the necessary part → the new accepted Project-DR baseline is compiled → Enterprise-DR receives a new version and continues operation.

Enterprise-DR → structural handoff → Project-DR → new baseline → new Enterprise-DR release → continued operation

19. What the Client Physically Receives

After separating Enterprise-DR, the composition of the client delivery becomes unambiguous. The client does not receive the Project-DR ERP technological assembly with its 29 resources. They receive the operational runtime of a specific enterprise, assembled from the accepted client release.

In version 2.5.1, the standard format for such a delivery is ENTERPRISE-DR_<CUSTOMER>_<VERSION>_WINDOWS_x64_RUNTIME_KIT.zip. The kit includes the client Enterprise-DR release, the database schema and deployment tools, the Enterprise-DR API, the local LLM, configuration, startup and self-test scripts, manifest, checksums, and evidence materials. The reference delivery physically includes the Gate-B control model.

The technology provides two modes. Connected reference bootstrap can automatically obtain fixed external runtime components. For a completely closed enterprise, the same runtime kit must be pre-assembled with a filled vendor_cache so that after transfer to the client, no internet access is required. Preparing an autonomous set becomes a provider operation before delivery acceptance.

Human-readable books, process libraries, scenario documents, instructions, and reports may be part of the project results, but they do not replace the runtime. The central operational asset is Enterprise-DR — the machine-readable professional memory of a specific enterprise.

20. How Delivery is Verified and the Project Ends

In version 2.5.1, the project route ends not with the generation of a neutral release, but with physical client delivery. In XCORE-EDR 1.1.0, operations EDR-015 "Client Runtime Kit Assembly" and EDR-016 "Runtime Kit Acceptance and Transfer" were introduced. They are completed by the blocking Gate EDR-G09 "Client Runtime Delivery.".

Before transfer, the client release, database and its initialization mechanism, API, configuration, local control model, checksums, self-test, and evidence are checked. For a closed profile, the completeness of the vendor_cache is additionally checked. Therefore, Enterprise-DR is considered delivered not at the moment of JSON or SQL generation, but only after the operational kit is physically assembled and ready for launch in the agreed environment.

After successful acceptance, Enterprise-DR becomes the working professional memory of the enterprise. It answers questions about the accepted model, registers operational signals, maintains current states, evidence, and history. If the need arises to change the professional model itself, Enterprise-DR forms a return to Project-DR. After engineering rework, the new result is compiled again and delivered as the next version of Enterprise-DR.

As a result, the ERP lifecycle ceases to end with the archiving of project materials. Project-DR is used to build and structurally change the professional model; Enterprise-DR is for its daily operation. There is a controlled transition between them in both directions. Project-DR is not transferred to the client as a production technology. The client receives Enterprise-DR — the machine-readable, versionable, and operable professional model of their enterprise.

Brief Summary

Version 2.5.1 architecture separates production technology from the client operational result. Specialized Project Cores accumulate detailed project content, the Unified Project Store collects accepted projections into a unified machine-readable memory, and the compiler releases a scrubbed Enterprise-DR for a specific enterprise. After this, the client runtime deploys this model in the database, provides controlled API access to it, and, if necessary, a local language interface.

In normal operation, Enterprise-DR answers questions and registers events based on the already accepted professional model. If the enterprise model itself needs to be changed, the operational core does not redesign it independently but forms a structural return to Project-DR. After a new project pass, the accepted baseline is compiled again and released as the next version of Enterprise-DR. This boundary preserves the Project-DR technology with the provider while simultaneously transferring the client a self-sufficient machine-readable professional memory of their enterprise.
