In our Telegram bot, the "Migalka" emergency alert system, we need to process messages from about a thousand Telegram channels in real-time and deliver relevant events to users in specific locations.

Official warnings about drone arrivals and missile strikes often arrive hours late, and sometimes not at all. Hundreds of Telegram channels report danger before official services. Reading them directly is difficult: one channel mixes events from different regions, and a single incident can be described by dozens of sources simultaneously. Moreover, users are interested in tracking other risks as well – raids and crackdowns.

The main engineering challenge here is to transform a stream of unstructured text from hundreds of Telegram channels into events that the rest of the system can work with: determine the event type, location, brief description, remove duplicates, and understand who exactly needs to receive it.

We initially built the system without constant manual moderation. Events appear around the clock, and several hundred occur daily, so manual verification doesn't scale well. Part of the work is done by an LLM pipeline, and part by users who can report events themselves and verify each other's messages.

A user enters a location into the bot – it can be of any level of detail, from an entire region to a city district, as well as categories of danger they are interested in. These filters are used by the bot to send relevant alerts, which means each post must have its event category and location extracted.

How It Works Overall

A separate Telegram scraper reads the channels, placing new posts into an incoming queue. The message then goes through several stages:

  1. Thematic filtering;

  2. Event extraction;

  3. Location determination and verification;

  4. Deduplication;

  5. Recipient selection;

  6. Delivery queueing.

The system uses several storage solutions. Postgres stores the main data – events and user settings – and is used for a reliable delivery queue. Qdrant stores vectors for searching potential duplicates. Redis is used for the incoming queue and managing sending speed to comply with Telegram's limits.

Turning Text into a Structured Event

The central task of the system is to convert a publication into a set of structured events: determine the topic, region, and a more precise location, and then create a short description.

This is done by the LLM. Everything that happens next – geographic binding, deduplication, and delivery – works with the result of this transformation.

One post can generate multiple events in different places or none at all. Therefore, after this stage, the main object of the system becomes the event, not the original publication.

When processing a single message, the model performs several tasks:

  1. Checks the relevance of the publication to the selected topic.

  2. Extracts "region + location" pairs. One publication can describe events in several cities at once.

  3. Formulates a brief description that the user will see.

  4. Verifies the location: did the event actually happen in the specified place, or is it just mentioned in the text?

  5. Acts as an arbiter in ambiguous deduplication cases.

Prompts are configured separately for each category and stored in Postgres. They can be changed without modifying the application code, so adding a new danger category mainly involves configuring instructions and the result schema.

At the same time, a significant part of the complexity turned out to be around the LLM calls themselves. Timeouts, a fallback model, and retries with exponential backoff are provided for them. This is necessary because the external API might respond slowly, be temporarily unavailable, or return a result that doesn't match the expected schema.

Deduplication

Dozens of channels can describe the same event in a short period. If each publication is converted into a separate notification, the user will receive dozens of messages about the same thing.

Comparing the original texts directly is not enough. One source might write about "explosions in the industrial zone area," another about "air defense activity over the city." The wording varies greatly, even though it might be about the same event.

Therefore, deduplication consists of two levels. First, embeddings quickly select potentially similar events. The comparison is based on semantic text similarity, so an exact match is not required.

Then, we compare the locations of the events – more on this in the next chapter. It is necessary to check the geography separately: semantically almost identical messages from different cities cannot be merged.

A found duplicate is not deleted but added to an existing event as an additional source. If a new publication clarifies information, the already created notification can be updated.

Geocoding: OSM, PostGIS, and ltree

After extraction, the LLM might return a string like "Shebekino." The geographic module must convert it into a structure that allows solving two tasks: determining which users the event relates to, and comparing event geographies during deduplication.

Comparing names as strings is inconvenient. "Shebekino" and "Shebekinsky Urban Okrug" might refer to the same territory, and identical place names occur in different regions.

Therefore, both the event location and the user-selected territory are converted to a unified representation – a path in the administrative boundaries tree.

Russia
└── Krasnodar Krai
    ├── Tuapse
    └── Sochi
        └── Central District

The path is built in two stages. First, the name goes through Google Maps. The geocoder normalizes it and returns additional information: official name, region, city, and coordinates. This helps in cases where a specific place in the city was indicated in the post without an address: for example, if the location is "TC Evropeyskiy," Google Maps will understand that it is in Moscow and determine the exact address.

After that, based on the normalized data, the corresponding territory is searched among the administrative boundaries of OpenStreetMap. Polygons are stored in PostGIS, and the resulting chain of administrative levels is stored in Postgres as ltree.

Recipient selection then boils down to comparing paths. For example, a subscriber interested in Krasnodar Krai should receive events from Tuapse. A user who selected Tuapse should also receive events relevant to the entire region.

The same structure is used for deduplication. If two texts are very similar but correspond to different branches of the geographic tree, the system will keep them as separate events.

There is an important exception here. The path of a city lies within the path of a region, meaning they are formally on the same branch of the tree – but we intentionally do not consider an event "in the entire region" and an event "in a specific city" within that region as one. Some users might pay little attention to an alert about a drone threat for the entire region, as the probability of a drone hitting their specific settlement is low. Therefore, if information about the user's specific settlement appears, they need to be notified again.

If a duplicate is added to an existing event, and the location is broader, the system additionally finds users in the new territory and sends them a notification. Those who have already received the event will have their existing message updated; others will receive it for the first time.

How Telegram's Limit Became Part of the Architecture

The Telegram Bot API limits the sending speed to 30 messages per second per bot. With several thousand recipients for one notification (and currently 15,000 users in the bot), this quickly becomes a bottleneck, with delays reaching several minutes.

Our main solution to this problem is to use multiple bots. Since the limit applies to each bot individually, the total throughput increases with their number. New Migalka users are automatically distributed among them: the main bot that the user launched first provides a link to another bot. Essentially, the delivery layer itself is horizontally scaled.

In addition, of course, we use a common outgoing message queue. It supports priorities: sending a new notification on time is more important than adding a source to an existing one. The main task of such a scheduler is to centrally account for rate limits. Doing this independently in each worker is inconvenient: workers don't know how many messages other processes have already sent through a specific bot. We use Redis for the queue, and some information is written to Postgres.

In the current configuration, the average delay between the appearance of the original publication and delivery is about a minute. During this time, the system manages to perform several model calls, geocoding, deduplication, user selection, and the delivery itself.

User Reports and Distributed Verification

So far, we've been talking about posts from channels. But Migalka has a second source – the users themselves: sometimes a person hears air defense or notices a raid before any channel writes about it. For this, the bot has a "Report an Incident" button. Such messages must be verified by other users.

A user clicks "Report an Incident" and briefly describes the situation. The message goes through the same pipeline as publications from channels: thematic filtering, event extraction, and location verification. If the system detects a duplicate, the report becomes an additional source for an already known event. For a new event, verification by other users is initiated.

Reports are verified by verifiers – ordinary users who have agreed to evaluate other people's messages. When a person has been using the bot for some time, the bot asks if the user is willing to help verify others' messages – with "Yes" and "No" buttons. Those who answer "Yes" are added to the pool of verifiers; they can change their mind and revert the decision at any time in the settings.

Several verifiers from the same region participate in the verification. They see the text of the message but not the author, and vote using one of three buttons: ✅, ❌, or "don't know." The "don't know" option is used to track which verifiers remain active. The system gradually disables those who frequently ignore verification requests.

If, after five minutes, the message has received at least one confirmation and no objections, it is considered verified and sent out. In other cases, the round continues for up to 15 minutes.

This verification filters out meaningless and obviously implausible messages but does not guarantee the truthfulness of every report. For Migalka, this balance is justified: the cost of a missed or delayed correct alert is higher than a false positive.

The Same Community Catches Errors

Verification continues even after an event is sent. A user can report an error in any received notification. To do this, they need to not only press a button but also write an explanation.

The explanation is automatically checked for coherence using an LLM. If the number of error reports is insufficient to make a decision, the event is sent for additional voting by verifiers.

This allows using the distributed audience as an additional quality control layer for the automatic pipeline. As with verifying user incidents, we delegate quality control to the community, without a moderator in this pipeline. Moreover, a person located directly in the relevant area will detect an error faster than a moderator from another city would.

Privacy

User identifiers are sensitive data. Therefore, they are protected not only by TLS and database access rights but also by application-level encryption.

Standard probabilistic encryption makes database searches difficult: the same value produces a new ciphertext each time it is encrypted. Migalka uses deterministic encryption, where identical source values result in identical outputs. This preserves equality searches and unique indexes.

We encrypt Telegram user IDs and bot tokens. Internal identifiers linking tables remain open: by themselves, they do not reveal identity.

A user can delete all their data from the bot via a special command. In this case, the data is completely anonymized: encrypted identifiers are removed from the database, and correspondence with the team (if any) is deleted from the internal team chat.

What Was Achieved

During the system's operation, about 150,000 events have passed through the Migalka pipeline, and the delivery layer has sent over 12 million messages. With such a volume, several decisions proved to be most important.

First, it is convenient to use LLM as one of the ETL stages, but you still have to build a standard fault-tolerant infrastructure around it: retries, timeouts, and concurrency control.

Second, text deduplication cannot be considered separately from geography. High semantic similarity says nothing about whether the event occurred in the same place.

Third, external API limitations can dictate the architecture of an entire system layer. In our case, Telegram's limits led to multiple bots, a common queue, and a centralized scheduler.

Finally, for a distributed system, user verification has proven to be a useful addition to automatic processing. It is applied both to user messages and as a feedback mechanism for already published events. The community handles the role that an editorial team would perform in a typical media product. Users report incidents, verify each other's reports, and find system errors. This does not require a staff of moderators, and publication is not delayed waiting for manual approval.

The main result is 15,000 users who receive alerts from the Migalka bot. More than 30% of them continue to regularly use the bot two weeks after registration (we measure user retention using feedback surveys). Unfortunately, there is currently a need for such a product.
