When a code agent solves a task, the LLM itself doesn't edit files or run tests directly. It operates through an agent wrapper, or harness. It receives system instructions, selects tools, reads their output, and decides what to do next.

Therefore, the same model in different agents can show different results. Somewhere it's more convenient for it to search the project, somewhere it gets clearer errors, somewhere the context of a long session is better managed. Even a small difference in tools or system prompts can turn into a noticeable difference in output over dozens of steps.

To separate model quality from wrapper quality, we ran identical models with identical reasoning levels in Koda, OpenCode, KiloCode, Claude Code, and Ouroboros.

To compare agent wrappers, we chose the DeepSeek V4 Flash model and ran it with identical reasoning levels in several harnesses. Measuring harnesses is not a cheap endeavor, so we chose a budget-friendly model that is very popular on Open Router. And it turned out that it works like a native with our harness. Code Index

To compare models and wrappers, we created a unified metric, the Code Index. We selected various tasks from open-source benchmarks. It combines tasks from three categories:

  • Development in an existing codebase;

  • Software design and implementation;

  • Data analysis.

All tasks are agentic. A task cannot be solved with a single message, so the agent operates in an isolated sandbox, independently navigating files, running commands, reading errors, and refining the solution. A single task might require dozens of model calls.

We disabled most network capabilities and git commands in the sandbox. Thus, the agent cannot find a ready-made patch on the internet or look up the correct solution in the repository history.

How the Index is Calculated

A run consists of 261 tasks. Each has a reproducible automatic check that determines whether the agent solved the task or not. There are no partial scores within a single task; the result is either accepted or rejected.

Tasks in the "Software Design" category are weighted 2.5 times more than others. They require more than just fixing a few lines; they involve designing and implementing an entire project or a significant feature.

Development

This category includes 125 tasks from five benchmarks:

  • SWE-bench Verified;

  • SWE-bench Multilingual — Java;

The agent receives a working copy of the real repository at the commit before the fix and the issue text from the user. The output should be a patch to the source code. Modifying tests is prohibited.

A solution is counted if it passes the hidden tests from the actual pull request that closed the issue, and the project's existing tests are not broken.

Data Analysis

This category includes 91 tasks from SpreadsheetBench and DA-Code.

The agent needs to analyze input tables, understand the requirements, perform transformations, and save the result in a strictly defined format. The output can be a CSV file, a pivot table, a chart, or a script for calculating statistics.

The created artifact is what's checked. Correct reasoning in the chat doesn't count if the final file is missing, has the wrong structure, or contains incorrect values.

New Koda Base and Koda Pro

As a reminder, KodaCode has two proprietary models for different scenarios.

Koda Base is now based on Qwen 3.8 Flash 125B. It helps understand a project, fix bugs, refactor, write tests, or implement small features. Base remains available for free with daily limits.

Koda Pro is now based on GLM 5.3. It is designed for more complex tasks where the agent needs to maintain focus for a long time, explore multiple parts of the project, make architectural decisions, and perform many sequential actions.

Behind these numbers are 261 tasks from several agent benchmarks. These include bug fixes in existing repositories, creating projects from scratch, and data analysis. HOWEVER, it's not enough for the agent to write a good answer once. It must explore files, make changes, run code, read errors, correct the solution, and ultimately pass an automated check.

However, we didn't just replace the models under the hood. Their operation has been adapted to the Koda agent wrapper. This includes tools, feedback format, context management, and system instructions. This is important because a model and an agent are far from being the same thing.

What the Models Showed

We compared Koda Base and Koda Pro with several external models within the Koda wrapper. For each run, we calculated not only the final index but also the average cost per task in the run.

The new Koda Pro achieved the maximum score in the entire published set at 54.3%. The Koda with DeepSeek V4 Flash Max combination came in second at 52.2%.

Koda Base scored 49.5%. This is almost the same level as Koda with external GLM 5.3 Flash Max — 49.2% and GLM 5.2 High — 49.0%, but with an average calculated cost of about 11.9 rubles per task in the run.

How Koda Base and Koda Pro Grew

The most telling comparison is not with external models, but with previous versions of our own.

Koda Base: from 38.5% to 49.5%

The previous Koda Base was based on Qwen3.6–35b, a very small model. It was the weak link in the lineup. It was suitable for short, everyday actions, but in long agent chains, it too often lost track of the goal, made mistakes when working with tools, or stopped without completing the task to a verifiable result.

This was particularly noticeable in the software design category. The old Base solved 7 out of 45 tasks, the new one solved 13 out of 45. In development, the increase was from 77 to 94 solved tasks out of 125, and in data analysis, from 32 to 36 out of 91.

After migrating koda-base to the Qwen 3.8 Flash 125B foundation, the overall index increased from 38.5% to 49.5%, a gain of 11 percentage points. The average number of steps remained almost unchanged. It was 38.5 for the previous version and is now 39.7 for the new one. This means the main gain came from quality, not from longer and more expensive trajectories. Due to its special attention architecture, the new model also does not lag behind the previous one in generation speed.

Koda Pro: Higher Quality, Fewer Steps

The new Koda Pro is based on GLM 5.3, one of the strongest open models for development according to public benchmarks. It's not the fastest, but it excels at complex agent tasks. To achieve stable model performance on our GPUs, we had to seriously optimize inference.

The Koda Pro index increased from 46.7% to 54.3%. In development, the new version solved 102 tasks out of 125 compared to 85 for the previous one; in design, 15 versus 13; in data analysis, 39 versus 36.

The average number of steps decreased from 70.3 to 52.1, a reduction of about 26%. Koda Pro did not become faster on every individual request, but it now requires significantly fewer actions to reach the correct result.

What This Means

Conclusion #1

Model choice affects the result more than ordinary chat tests suggest. Within the same Koda wrapper, the difference between models in the published run reaches over 16 percentage points (from 37.7% to 54.3%).

Conclusion #2

The harness also matters. On the same DeepSeek V4 Flash Max, the Koda wrapper scored 52.2%, while the other tested wrappers scored between 47.6% and 49.5%. System instructions, tools, and their result processing truly change the outcome.

Conclusion #3

An agent cannot be evaluated solely on fixing minor bugs. Models that perform confidently in the development category can sharply decline when required to design a full-fledged solution or create a correct data analysis artifact.

Finally, cost-effectiveness. This is not just the price per request. A model might be cheap but take more steps, frequently go in the wrong direction, and repeatedly run tools. Therefore, on the graph, we compare quality with the cost of the entire agent trajectory, not with the formal price per million tokens.

Koda Base Remains Free

The new Koda Base is available for free with daily limits in KodaCode for VS Code, JetBrains IDE, Koda CLI, and Koda Desktop.

We want the free model to be a fully functional agent for everyday tasks, not a demo version. That's precisely why the growth of Base is more important to us than simply replacing one model with another. With almost the same number of steps, it now solves significantly more tasks and has approached much more expensive configurations.

Koda Pro remains the option for tasks where maximizing the chance of completing complex work is crucial. This includes major changes, design work, long-term research, and multi-step implementation.

Benchmark Limitations

The Code Index does not claim to be a universal measure of model intelligence. It answers a more practical question: "How successfully does a specific combination of model and agent wrapper solve a chosen set of tasks in a fixed environment?"

The results apply to specific versions of models, wrappers, system prompts, and reasoning levels. After updating any component, the numbers may change. Cost also depends on trajectory length, provider rates, and model behavior in a specific run.

However, for choosing a model in real-world work, personal experience might be more important than its position in the table. The benchmark averages results across the selected task set, but your scenario might differ significantly. A model with a lower index might better understand your specific requests and work more stably with a particular codebase. Therefore, metrics should be used as a guide, and the final decision should be made after testing with your own tasks.

We plan to expand the task set, update results, and keep the methodology open. This will allow us to compare future versions of models and harnesses under identical conditions and distinguish reproducible growth from impressions gained on a few individual tasks.

Instead of a Conclusion

After the update, Koda Base grew by 11 percentage points and, with almost unchanged step count, approached strong external models. Koda Pro gained 7.6 points, took first place in our set, and simultaneously started completing tasks significantly faster.

But the main result for us is not even the specific position in the table. The extensive run once again showed that the quality of a code agent cannot be reduced to the model's name. The result emerges at the intersection of the model, tools, system instructions, context management, and the ability to correctly handle dozens of sequential steps.
