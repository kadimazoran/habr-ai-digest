Introduction

In the first part, I discussed how I built a RAG system with a LangGraph agent on local LLMs. It could search for news, answer questions, and extract entities. But for trading, this is not enough – you need not just to read, but to predict.

In this article, I will explain how I turned a news scraper into an ML pipeline that generates trading signals (BUY/SELL/NEUTRAL) with evidence. We will go from linking news to tickers to an Explainable UI, analyze pitfalls with small data, and look into the project's architectural future.

Stack: Scikit-learn, Plotly, FastAPI, Streamlit, PostgreSQL, Ollama.

0. What has changed since the first article

In the first part, we stopped at the point where we had a RAG system and an agent. But when the database grew from 12,000 to 37,000 articles, it turned out that processing everything "head-on" was too expensive.

Previously, we had three independent background tasks (Classify, NER, Enrich) that worked in parallel and interfered with each other by querying Ollama. Each task tried to load its model into VRAM, causing "ping-pong" (which I wrote about in the first article). Plus, we were spending GPU resources on news that doesn't affect the market (sports, culture, incidents).

What we did:

  1. Transitioned to a Unified Pipeline. Now an article goes through a chain: Classification → Junk Filter → Market Impact → NER → Summary → Embed. If an article fails the filter, it's marked as skipped, and we don't spend resources on it.

  2. Changed Ollama settings (increased parallelism and allowed holding two models in memory) to make this pipeline work as fast as possible. Details in section 3.

It was this architectural shift (from "process everything" to "process only what's important") that allowed us to move to ML signals without an explosion in GPU load.

1. From Text to Tickers: Entity Linking

For the model to predict stock profitability, it needs to know which company a news article is about. NER (Named Entity Recognition) finds "Sberbank" or "Lukoil," but doesn't know they are tickers SBER and LKOH.

Solution: a synonym dictionary (tickers.yaml) that is automatically updated from the Moscow Exchange API. For each news item, we match the extracted NER entities with tickers.

Special Case: Alfa-Bank.
Initially, we encountered a false positive: "Alfa-Bank" matched SVCB (Sovcombank). But upon closer inspection, it turned out that NER had correctly extracted both "Alfa-Bank" and "Sovcombank" from the text – the dictionary simply didn't have Alfa-Bank.

We added a dummy ticker ALFAMOCK. This is not a workaround, but a placeholder for the future: we collect news now, and when the bank goes public, we will simply replace the ticker with the real one.

Currently, the database contains 37,268 articles from 24 sources. Entity Linking runs in the background, associating news with 50+ liquid Moscow Exchange stocks.

2. Feature Engineering: What Constitutes a Signal

Each news item has a market_impact (bullish, bearish, neutral). For each day and ticker, we calculate features:

  • market_pressure — sum of directions (+1 for bullish, -1 for bearish).

  • news_count — number of news items.

  • has_summary — whether summarization was performed (an indicator of importance).

  • vol_5d, vol_20d — volatility (standard deviation of returns).

  • adv_20d — average trading volume (liquidity).

New Feature: Volume Anomaly.
We added tracking of abnormal trading volumes. If the volume for a day exceeds the average (ADV) by 3 or more times, it often precedes a price movement (entry or exit of a large player). The feature volume_ratio = volume / adv_20d is already built into the architecture and will be tested on historical data.

Pitfall: Time Decay.
We tried to implement time decay (fresher news weighs more). But market_pressure became fractional (0.85 instead of 1), and RandomForest "broke" – Accuracy dropped from 0.52 to 0.36. On 55 records, this added noise, not signal. We postponed it until we accumulate 200+ records (ADR-023) to avoid premature optimization.

3. Tuning Ollama on a Single Tesla P100

In the first article, I mentioned that I increased OLLAMA_NUM_PARALLEL from 1 to 2, which gave a 1.5x speedup. With the database growing to 37,000 articles, this was no longer enough. We have a server with two Tesla P100s (16 GB each), but we consciously decided to optimize the pipeline so that everything works on one card.

Why not on two?
When a model doesn't fit into 16 GB, Ollama starts "spreading" layers across GPUs. This causes data transfer over PCIe and a 3-5x speed drop, as well as increased instability with parallel requests. For our tasks (multiple models + parallel runs), the stability of a single card turned out to be more important than the hypothetical possibility of loading a larger model.

Problem: VRAM Ping-Pong.
Even on a single card, Ollama tried to unload models if it ran out of space. This caused delays: while the model was loading into memory, requests were waiting in the queue.

Solution 1: OLLAMA_MAX_LOADED_MODELS=2.
We allowed Ollama to keep both necessary models (Qwen 14B and BGE-M3) in memory simultaneously. This eliminated the "idle time" effect.

Solution 2: OLLAMA_NUM_PARALLEL=6 (empirically determined).
We enabled parallel request processing. The parameter was chosen empirically:

  1. Increased to 6, measured batch processing time (Ollama logs + nvidia-smi).

  2. At 8, we started noticing that the GPU was hitting its memory ceiling, and requests began timing out.

  3. We settled on 6 parallel requests – this gave a 1.5-2x speedup compared to the default value, while leaving a VRAM buffer (about 6.3 GB free).

Concerns: "Spreading" models across cards.
We deliberately did not increase NUM_PARALLEL above 6 and are not using the second GPU. If the combined size of the two models no longer fits into the 16 GB of one card, Ollama will start distributing layers between GPU #0 and GPU #1. This risks a 3-5x speed drop (due to data transfer over PCIe) and instability. Currently, we have a memory buffer, but we monitor this through logs to stop in time.

Result: After tuning (MAX_LOADED_MODELS=2, NUM_PARALLEL=6, KEEP_ALIVE=-1, and CUDA_VISIBLE_DEVICES=0), the article processing pipeline accelerated by 1.5-2 times, with the entire system running stably on one card, leaving the second one as a reserve or for other tasks.

4. ML Model and Walk-Forward Validation

We use RandomForest with calibration (Platt scaling). This provides not just a prediction, but a calibrated probability (if the model says 0.65, it means it's correct 65% of the time).

Why standard train/test split is not suitable?
Financial time series are non-stationary. If we train a model on the first 80% of the data and test it on the last 20%, we might accidentally hit an "lucky" period. Therefore, we use Walk-Forward Validation.

Honest Limitation: Our target architecture (ADR-020) is a 30-day training window, 7-day test. But with the current data volume (59 records with news), we are using 14/3/3 (14 days training, 3 days test, 3 days shift) to get at least some validation window. Once we accumulate 200+ records, we will switch to the target 30/7/1.

Result: On 59 records with news, we achieved an average Accuracy of 0.62 (median 0.67). However, the test set size was only 45 examples. This is a preliminary estimate. We are honestly waiting for data accumulation (there are still 30,457 articles in the queue) so that the model finds a stable signal, not just learns noise.

5. API and Explainable UI

We created two endpoints:

  • GET /signal/{ticker} — returns the signal (BUY/SELL/NEUTRAL), confidence, and evidence (list of news that influenced the decision).

  • GET /candles/{ticker} — historical candles for charts.

In Streamlit, we built a trader's terminal:

  • Candlestick chart (Plotly Candlestick).

  • Confidence progress bars.

  • Expandable news items with links and influence direction.

Main Feature: Explainable AI. The trader sees not just "BUY," but why the model made that decision. This reduces distrust and allows for quick context verification.

6. The Problem of Mixed Signals (and why we didn't patch it)

During testing, we noticed that VKCO received a BUY signal (64%), even though its news was neutral (market_pressure=0). The model had simply learned that the market grows 55% of the time.

We considered two options:

  • A: A hard filter in the API (if market_pressure == 0, set to NEUTRAL).

  • B: Add dominance features to the model (bullish_count, bearish_count, dominance).

We rejected A because it masks the symptom. If a ticker has 2 positive news items and 1 negative (market_pressure=1), the API will still issue BUY, even though the sentiment is mixed.

We chose B, but postponed its implementation until we accumulate 200+ records. Currently, the API issues "dirty" signals, but we honestly document the reason and do not hide the problem behind placeholders. This is a conscious technical debt.

6. Vision 2.0: Where We Are Heading

The project is not standing still. We have fixed the development concept (ADR-025), dividing features into three tracks:

  • Quick Wins: Volume anomalies (volume_ratio), extraction of corporate events (buybacks/SPOs via LLM), expected return E[return] for Risk/Reward calculation.

  • Core R&D: Event Horizons — forecasting the exit horizon (Take Profit) depending on the event type (geopolitics, macro, corporate). Global Risk Factor — accounting for the influence of the global environment (VIX, S&P 500, Brent).

  • Moonshot: Fragility Score — detecting market "fragility" (inspired by Nassim Taleb's work). We don't promise to predict a "black swan," but we can signal divergence between the news background and price reaction.

Conclusion

Building an end-to-end ML pipeline on local news is feasible. The main thing is to honestly acknowledge data limitations and not to patch where waiting is necessary. We have shown that even with small data (59 records), it's possible to get a working pipeline and UI with evidence, and the architecture (ADR, Vision 2.0) is ready for scaling.
