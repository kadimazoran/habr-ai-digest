What is Bitrix24 Co-work/Code

It is a desktop AI assistant application within the Bitrix24 environment. Co-work/Code is connected to your Bitrix24 portal via REST API and can interact with its data: search and create deals, contacts, and companies, work with tasks, calendar, and other sections.

Before modifying or deleting data, Co-work/Code explains what it intends to do and requests user confirmation. It can also highlight duplicates, consolidate data, organize the database—all without touching anything without explicit approval from the portal owner.

"Co-work/Code" is a hybrid workspace within Bitrix24: "Co-work" provides a chat interface for working with the portal through the assistant, while "Code" offers the ability to assemble small applications and automations and publish them on the Bitrix24 Vibecode platform infrastructure.

Why the Agent Needs an Order of Operations

When a user gives a task, the agent must execute it without breaking anything. To do this, it must see the actual state of the CRM and understand the consequences of the operation.

The example we are working with today is duplicate contacts. Different records may have the same name but refer to different people. Conversely, one record might have a phone number, while another has an email and associated deals. In this case, simply deleting the "extra" record could leave a manager without an important part of the customer communication history.

Here is the sequence for a safe operation:

  1. The user gives a task to find and merge duplicates.

  2. The agent reads the data and finds candidates for merging.

  3. It shows exactly what it proposes to change: which record to keep and what data to transfer.

  4. It receives user confirmation.

  5. It performs the action and reports the result.

This order allows the user to review the solution before it affects the CRM.

Confirming the Operation

After reviewing the plan, I allowed Co-work/Code to proceed with the merge. I also explained in detail what the agent should do: perform the merge, check the CRM again, show the result, and report any problems encountered during the process.

A simple text confirmation is not enough to delete contacts. When the agent reached the dangerous operation, Co-work/Code displayed a separate system warning: the records were not yet deleted, and the action required explicit manual authorization.

The user can reject the operation or allow it once; such confirmation applies only to the current action and does not grant the agent permanent permission to delete data.

After authorization, the agent executed the agreed-upon plan:

  1. Kept contact #1617 as the primary.

  2. Transferred two emails from records #1619 and #1621 into it.

  3. Deleted the two duplicate records.

  4. Re-searched for contacts by the common phone number.

The result: one contact with the original phone number and three email addresses. The duplicates had no associated deals or companies, so no additional links needed to be transferred.

What Actions Require Confirmation

Let's see how the agent worked during the duplicate search.

Reading CRM data — freely: it retrieved contact cards, compared fields, and checked related entities. These actions did not change information on the portal, so no separate permission was required.

Before merging — it first showed a full plan. I could see which record would remain primary, what values would be transferred to it, and which records would be deleted. After that, the user confirmed the proposed option with a regular message.

For deletion — an additional layer of protection was activated. Co-work/Code stopped execution and displayed a system window with "Reject" and "Allow Once" buttons. Nothing was sent to the portal until the user clicked a button.

In total, two confirmations were needed in the experiment. The first to approve the general merge plan, and the second for the specific dangerous deletion operation.

Here's how it works: the deletion permission is requested by Co-work/Code itself when calling the corresponding tool. The agent cannot confirm such an action independently or interpret the user's lack of response as consent.

The "Allow Once" button grants permission only for the current operation. The next deletion will require a new user decision.

What Other Restrictions Protect the CRM

User Permissions. Co-work operates only with the data and actions accessible to the current user. If an employee cannot modify a specific CRM record, the agent will not have such rights either.

Confirmation of Dangerous Operations. The mandatory confirmation of changes, which we have already discussed, always applies. A dangerous operation is impossible without user involvement, and Co-work will either request confirmation or explain that it cannot perform dangerous operations without confirmation:

We will still see what the agent intends to delete from the portal and can reject this action, or allow it once. And only once: the next dangerous operation will require a new user confirmation.

Therefore, even if the initial command was formulated too broadly, the user retains control.

Built-in Regulations. Before modifying data, the agent checks the current state of objects and the potential consequences of its actions.

Can You Work on the Code Tab?

Yes, you can.

Technically, it is more optimal to work with the portal through the Co-work tab and for creating applications—through the Code tab. This separation works due to the different operating schemes of the modes.

However, you can also work with the portal through Code, and it will also perform tasks. Here's the difference:

Characteristic

Co-work (Writes Code)

Code (Develops)

Context

Sees only what you have copied into the chat.

Sees the entire project, folder structure, and dependencies.

Tools

Only the chat text editor.

Terminal, Git, compilers, tests, deployment.

Complexity

Suitable for "write a regular expression" or "explain this piece of code.".

Suitable for creating full-fledged services and complex systems.

Result

Code text that needs to be manually copied.

A ready, tested, and deployed application.
