Imagine: a technical specification on the table and three contractor proposals. Prices are for different periods, some conditions are in appendices, one proposal is missing an obligatory work item. You need to read everything, compare, recalculate under the same conditions, and prepare a memo with sources.

You can ask an AI to explain how to do this, or you can give it documents and tools and assign the work itself: let it read, compare, calculate, and return the result. In the second case, the model is already managing the task execution. This is an agent.

Under the hood, it's a familiar loop: the model selects a tool and call parameters, ordinary code executes the tool, and the result is returned to the model. And so on. This principle—reason, act, observe the result—is the basis of ReAct.

The simplified loop fits into ten lines:

    messages = [user_message(task)] 
    
    while budget_available(): 
        response = LLM(messages, tools) 
        messages.append(response) 
        if not response.tool_calls: 
            break 
        outputs = tool_executor.apply(response.tool_calls) 
        messages.extend(outputs)

Why are there so many different products built around these ten lines?

An engine and four wheels are present in both a truck and a car, but they are not interchangeable. The same applies to agents: all the interesting stuff starts with questions that didn't make it into the pseudocode.

  • Is the proposed command even executable?

  • What to do if the tool returns a gigabyte of text?

  • How to continue working when the context window is full?

  • Is the model's phrase "done" enough to close the task?

All this is assembled into a harness—the agent's execution environment: the loop, tools, memory, checks, limits, and action history. This is where most of the engineering work lies.

We at GigaCode R&D develop models for agent tasks. We needed an executor with which we could experiment, get training data, and solve applied problems. Thus, GigaCode Universal Agent was born—an open-source Python project with model connections via chat/completions API.

We'll explain what surrounds the agent loop and how a single core is used for working with documents, code, and external systems.

Who sets the route?

There are two main approaches to automation with LLMs.

The first is to pre-define the process: read the document, extract fields, query the system, format the output. Forks and repetitions appear—forming a graph. As long as the route is known, it's convenient: each step is in its place.

But comparing contractors quickly goes beyond the command "extract three prices." In one proposal, support is included; in another, it's paid separately; in a third, there's no mention of it at all. For each case, specific clarifications and calculations are needed. The more such scenarios, the more expensive it is to maintain a separate route for each.

The second approach is to let the model choose steps based on the situation. It reads a proposal, notices a link to an appendix, opens it, finds missing conditions, and returns to the comparison. The execution environment provides tools and controls the work.

We are building an agent around the second approach. A new scenario is often connected by an instruction and tools without changing the core. And where a sequence is mandatory, it can still be fixed in the external code calling the agent.

Task, Skill, and Tools

Let's return to the contractors. The user sets the task:

In the folder are the technical specification and three contractor proposals. Compare the scope of work, cost, and deadlines. Prepare a table and a short memo: differences, non-compliance with requirements, and questions for clarification. For conclusions, indicate sources. Do not send anything to the contractors.

For the agent to perform it, we need:

  • Task—specific work: which documents to take and what to get as output.

  • Skill—a reusable procedure. Similar to instructions for a new employee:

    1. Read the technical specification and create a list of comparison criteria.
    2. Study the proposals and their appendices.
    3. Adjust prices to a common period and comparable scope of work.
    4. If a condition is missing, mark it as "not specified" and add a question.
    5. For facts, indicate the source; for calculations, use the source data.
    6. Prepare a table and a memo. Separate facts from assessments.

    The procedure is stored separately: the user doesn't need to insert it into the request every time; the agent receives the necessary instructions when working on the task. A skill package can also include a report template, reference materials, and a calculation script.

  • Tools—access to data and actions: read a document, perform a calculation, save a file. External systems can be connected via MCP (Model Context Protocol). Behind the general interface can be a corporate repository, a browser, or a database. MCP allows you to find out which tools are available and call them.

As a result, the rules of operation live in the skill, access to systems is in the tools, and the core executes the task. To connect another scenario, you don't have to rewrite the agent loop.

Let's see how this works in our example. Suppose the first contractor's price is annual, the second's is monthly, and the third's implementation is paid separately. Comparing three numbers is not enough. The agent needs to check the scope of services, account for one-time payments, and recalculate the cost for a single period. If the calculation is complex, the agent can write and run a small Python script.

The memo includes conclusions, calculations, and references to documents. If data is insufficient, a specific question to the contractor appears. "Not specified" does not automatically turn into "free."

The skill defines the analysis rules but doesn't list all possible discrepancies. The agent decides which documents to re-read and what to recalculate as it works. The human receives material for decision-making, not three retold proposals.

Twenty minutes means twenty minutes

In a chat, you can notice the agent going in circles and stop it. A background task has no such observer. Therefore, our unit of execution is a Run, a single launch. For it, we fix the task, skill version, model, tools, workspace, and limits: time, tokens, steps, tool calls.

If twenty minutes are allocated for comparing documents, it should not imperceptibly turn into an overnight research project. If the token limit allocated for the task is exhausted, the launch must be completed, what has been done saved, and the reason for stopping reported.

Each launch has a trace—a history of work: model calls, tool calls, received results. These allow you to understand where the conclusion came from and where the agent went wrong. And the fixed settings help to figure out why the task was solved yesterday but stopped working today: was the model, instruction, or data source changed?

The trace is useful for both the developer looking for an error and the manager who needs to understand the basis of a recommendation. However, you cannot blindly repeat the history: re-reading a document and resending an email are different actions.

The model said "done." Let's check

The agent compared contractor prices and wrote a neat report. But it missed the obligatory work item from the technical specification. Externally, everything is finished; in substance, it is not. Therefore, Universal Agent has a separate judge: a model with its own instruction that looks at the trace and report and compares the result with the task. Is a check missing, a requirement lost, a conclusion not supported by a source? The agent receives remarks and continues working as long as the budget allows.

Where the result can be checked programmatically, it's better to do so: the file is created, the calculation matches, the JSON conforms to the schema, the test passes. The judge helps with the substantive part: was the question actually answered, was everything considered, are there enough grounds for the conclusion? The judge can also make mistakes, but the executor's phrase "I'm finished" at least ceases to be the sole criterion for success.

Long tasks create another problem: the work history gradually fills the model's context. Here, auto-logging comes into play: the agent saves a compact description of the state—what has been figured out, what has been done, what remains—and continues with a reduced context. This allows working beyond a single window. Details may be lost during compression, so returning to the original task and checking the result at the end is especially useful.

Read access is not write access

The prompt stated: "Do not send anything to the contractors." Such a restriction should also be ensured by tool configuration. For comparing documents, it's enough to read the sources and save the report; access to sending emails is not needed here.

Universal Agent has read and write checks, moderation of commands by the judge, and a mode with environment separation: the agent works in one container, and commands on task files are executed in another.

These mechanisms have different roles. The judge evaluates the action; isolation limits the capabilities of the executed code. Access rights determine which data and systems it can reach at all. The specific set is chosen for the task.

One core, different launch methods

A manager sets a task in a web chat, a developer calls the agent from an application, an external system sends an event, and the task is launched in the background. Internally, the same tools, skills, and checks are used.

For example, calling from Python looks like this:

from gc_core.aio import AsyncAgent
from gc_core.config import load_config

config = load_config("~/.gc/config.yml")

async with await AsyncAgent.create(config) as agent:
    answer = await agent.run(
        "Compare contractor proposals with the technical specification in the working folder. Prepare a table, conclusions, and questions for clarification.",
        thread_id="t1",
    )

The model, tools, and working environment are already configured here; the user only needs to set the task.

There are also /v1/chat/completions and /v1/responses interfaces: you can interact with the agent through the familiar language model API. Behind the request lies a whole process—reading documents, calculations, creating files. The client sent one message, the agent performed dozens of steps and returned the result.

On the terminal, the lead is noticeable: more than three points ahead of the closest competitor, and Qwen Code lags by almost twenty-five. The agent has a stubborn nature: on the most difficult tasks, it takes significantly more steps than its rivals—it gives up the longest. Sometimes this saves it, sometimes it just burns tokens. But the main conclusion is not in the numbers: the same model in a different harness yields a different result because the execution environment matters.

In cybersecurity, we tested CyberGym lvl1 with DeepSeek-V4-Flash. Without a specific skill—70.6%; with a skill—76.7%, an increase of 6.1 percentage points. The core remained the same; only the operating procedure was added.

In scientific search, we used the MiniMax M2.7 model and science-mcp. However, the absolute results are still modest: all agents still have a lot to learn in searching for scientific sources.

These experiments show how a single core works in different domains. For comparing contractors or other business tasks, quality must be measured on your own examples: did it catch omissions, did it calculate correctly, how much time did it save a person?

How much does a completed task cost?

The price of a single model call says little about an agent's economics. A cheap model might take thirty steps and fail. A more expensive one might solve the task in ten. And sometimes a strong model spends half an hour on something a smaller one could handle. Therefore, we calculate the cost of a successful task: Cost of a successful task = cost of all runs / number of successfully completed tasks. Failed attempts remain in the numerator, as does manual rework: if an employee re-compares all proposals and rewrites the memo after the agent, then cheap tokens help little.

Our own measurements confirm this. On SWE-bench Verified, the agent cost about a third less than Qwen Code and solved more. On Multilingual, the savings were about a quarter. A low price per token and a cheap completed task are different things, and the latter is more important here.

To avoid choosing one model for the entire job, we added auto-routing to our agent. At each step, the execution environment selects a level—light, default, or max. We try to assign simple operations to fast models, and complex planning and fixing difficult errors to stronger ones. In our experiments, 50-60% of requests could be offloaded to junior models while maintaining quality at the max level. Savings in individual configurations are manifold. This direction is still experimental, but the practical meaning is clear: an expensive model is not needed at every step.

What is left for humans?

We started with data for training agent models. To obtain it, we needed tools, state, action history, limits, and result verification. For applied tasks, the same things were needed.

This led to a general core. One scenario works with documents, another with a repository, a third with scientific sources. Skills and tools change, but the execution environment remains. Humans still need to define what constitutes a good result, grant access to the necessary data, and describe the rules of operation. If the tools are already connected, a new scenario can often be assembled without programming; if not, integration will be required.

In our example, everything starts with a folder of documents and a comparison procedure. The output requires a table, calculations, and questions that would otherwise have to be compiled manually. This is precisely why the entire harness around the ten lines of the agent loop exists.

You can use our project as an automation tool and with its help solve many scenarios at once: automate your business tasks in the background, use it for development, install it on employees' computers, deploy a web version in the cloud within your internal network. If you're looking for a silver bullet in AI, ReAct agents are very close to it. You can do a lot with them.
