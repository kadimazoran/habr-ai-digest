A person asked ChatGPT to make an exact copy of an image and not change anything. They provided a real photograph of Dwayne Johnson. With each iteration, the photograph changed beyond recognition until it turned into a cartoonish mess. At each step, they asked not to change anything.

It's the same with code. You told the AI which fonts to use, and it uses the same font. But the sizes are flying all over the place: on every page, the font sizes are different. This causes the overall site style to be lost.

This is architectural drift. I'm giving an example from the frontend as the easiest to understand, but the principle applies to all other development areas. The main problem is that the source of truth is drifting apart.

I don't read code at all. I only control the specs. Below is how to fix drift in agent development.

Architectural drift is cured by three principles. The truth is not the code, but the documentation (specs).

  1. The single source of truth is defined by the specs.

  2. The AI must first read the specs associated with the task before executing it.

  3. Spec tests verify the code against the documentation in a deterministic way.

1. The single source of truth is defined by the specs

The truth is not in the code

How do we solve the drift problem? Using the single source of truth principle. The truth is in one place. And this truth is not in the code, but in the documentation.

Why is the truth in the spec and not in the code? The architectural principle works here: the spec acts as a blueprint, and the code is the part that is machined according to the pre-made blueprint. The part is checked against the blueprint, not against another part. If a project has two sources of truth, it leads to chaos and bad code.

7 thousand documents, and it's not a dump

All documentation is in one folder, `docs`, in the project root. There are now over 7,000 documents, and each is in its place. It's not a dump, but a structured folder with ten levels of nesting, where each folder in 90% of cases has no more than 7 files. I structure according to the 7 plus-minus 2 rule: no more than 9 objects for key entities in each folder. That's why I know where everything is.

The spec itself is just an .md file that describes what is what. Specs are written by agents. They are also read by agents. As a user, I read the admin panel: each spec has its own page in the admin panel, which describes everything the same way, but in a more human-friendly format.

When an agent works with a piece of a problem, it has a specific folder containing the necessary documentation. Because each doc is in its place, it's easy for the agent to ensure that nothing within the folder contradicts the design. The agent ensures that the specs are kept in a uniform format and that nothing within them contradicts each other.

2. AI reads specs before the task

It needs to be forced to read the correct document, and this is specified in the base document AGENTS.md. It outlines the rules: it must read documents that correspond to the task. When I need to make a change on the site, the agent always reads the folder with the source documentation first, and in 9 out of 10 cases, it doesn't violate the rules.

For example, I see that cloud costs have skyrocketed, and I set a task to audit and figure out what can be cut. The agent must go and read all the documentation on clouds. It will see that there is a separate folder specifically for this, it will see all cloud providers and analyze them.

3. Spec tests verify the code

Specs and the admin panel are in an indeterminate plane: there's a chance the agent will follow the examples or not. On the tenth try, we have spec tests. We write a test based on the spec. The spec lists the allowed font sizes, and the spec test checks that no other sizes are being applied to the site. If we release something to the site that doesn't pass the spec test, it doesn't pass.

When the doc and code diverge

When the doc and code diverge, three things come into play. First, the testing phase, which should catch the problem. Second, self-healing, which will catch the problem in production. There will be a separate article about that. And if the first and second didn't work, I, as a human, step in. My job is not to catch the problem, but to understand why this mistake happened and to ensure that it doesn't happen again next time.

It often happens that the spec existed, but the agent did its own thing. This is often because the agent didn't read the correct spec. That's why we have strict rules for it to read. But sometimes you have to point it directly to the right spec.

In short

One of the main goals of the entire approach is to have a single source of truth. And how we enforce this with spec tests is how we solve the problem of architectural drift.

The term is not new: the pair architectural drift / architectural erosion was introduced by Perry and Wolfe in 1992 in the article Foundations for the Study of Software Architecture. With agents, it has come alive again: The Spec Growth Engine, October 2026. On Habr: "What to do with architectural drift in the age of AI?", April 2026.
