TL;DR

  • An AI engineer doesn't train their own model. They build a system around a pre-trained one: feeding it the right data, giving it tools, verifying the results, and monitoring costs.

  • The model remembers nothing and does nothing on its own. At each step, the harness resends everything to it: tools, rules, and the entire history.

  • That's why, over 30 steps, the agent read 1.63 million tokens, even though it was never given more than 100,000 at once.

  • A cache reads the repeating beginning of a request for 5–10% of the cost. But only if it exactly matches the previous request down to the character. Therefore, put unchanging parts at the beginning and new parts at the end.

What is AI Engineering and Why It Concerns Every Developer

How it differs from machine learning is well explained by Chip Huyen in her book "AI Engineering." An ML engineer trains the model themselves: collecting and labeling data, training, and testing. An AI engineer takes a pre-trained model, trained by someone else, like Claude or GPT. Their job is to ask the right questions, provide the model with the necessary data, and sometimes fine-tune it slightly. For them, the model is just an external service, like a database or a payment gateway. The only difference: it responds with text and sometimes makes mistakes.

For the average developer, this is no longer exotic. In the 2026 Stack Overflow survey, 73% of respondents said they write code with assistants and agents daily. Among agents, Claude Code (66%) and GitHub Copilot (59%) are most frequently mentioned. And in the 2025 survey, the main complaint was "AI responses are almost correct, but not quite." 66% answered this way.

The difference between "almost" and "correct" is rarely hidden in the prompt. For an agent to solve a task without eating up the budget, you need to understand four things. What the model receives at each step. Who actually performs the actions. Where the agent typically makes mistakes. And how much each step costs.

Model and Context

Token. The model reads text not letter by letter or word by word, but in chunks. These chunks are called tokens. Everything is counted in tokens: how many fit in a request, what the limits are, and how much you'll pay. More details in the section about tokens.

Context Window. How many tokens the model can read at once, including its response. Most new Claude models have 1 million. It's not advisable to fill the window to its limit. Each token costs money, and the longer the context, the worse the responses. Anthropic calls this "context rot."

System Prompt. Rules for the model that precede user messages: who it is, what it can do, in what format to respond. In Claude Code, this also includes the CLAUDE.md file from the repository. The system prompt is sent to the model with every request. Therefore, you pay for every extra line in it many times over.

How the Model Acts

Tool Use. This is how the model gets hands. You describe a function: its name, what it does, its parameters. For example, get_weather with the parameter location. The model itself doesn't run the function. It responds: "call get_weather for Moscow." Your code then calls the function and returns the result to the model. Anthropic calls this a contract: you decide what the model can do, and it decides when.

Chain (workflow, agents chain) and Agent (AgentsLLM). In a chain, the order of steps is defined in code. For example: understand the request and send it to the correct branch. An agent chooses the order itself: which steps to take and which tools to call. A chain is more predictable and cheaper; an agent is more flexible. Anthropic recommends starting with the simplest. Often, a single well-crafted prompt to the model is sufficient.

Agent Cycle. The same thing repeats: request, tool call, result, request again. This continues until the model responds with text. This cycle is what makes a model with tools an agent. Pseudocode and a diagram are below, in the section on system architecture.

Harness. All the code surrounding the model. It assembles the request, runs the cycle, calls tools, stores history, and verifies actions. Claude Code, Cursor, Agent SDK, and your Python service are all harnesses. The same model behaves differently in different harnesses. Therefore, an AI engineer most often builds the harness itself. Its components are detailed in the article "What is Harness?"

How Agents are Extended

MCP (Model Context Protocol). An open standard for connecting external systems to AI applications. It's compared to USB-C. An application, like Claude Code, connects to MCP servers. The server provides it with tools, data, and pre-made prompt templates. Integrations with GitHub, a database, or Jira are written once and work in any MCP-compatible application. The standard changes rapidly. I am referencing the version from July 28, 2026.

Skill (Agent Skill). A folder with a SKILL.md file, sometimes with scripts and reference materials. Initially, the model only sees a short description of the skill, about 100 tokens. It reads the full text, up to 5,000 tokens, only when the task matches the description. Other files cost nothing until they are opened. And if there's a script inside, only its output enters the context.

How a skill enters the context. Numbers from Anthropic's documentation on Agent Skills.

Sub-agent. An assistant with its own context and tools. The main agent gives it a task and receives only the summary back. Why this is useful: noisy operations, like searching code or reading logs, don't clutter the main context. A sub-agent can be given a cheaper model. But its requests count towards the same limits.

Hook. Your script that the harness runs automatically when something happens. The model is not involved. There are many triggers: session start, new user request, before and after a tool call, response end, context compression, sub-agent launch.

The script receives JSON with details as input: for example, which tool is being called and with what parameters. In response, it can deny the action: exit with code 2 or return deny with a reason, which the model will see. It can pass the question to a human (ask) or allow it without further ado (allow). It can append text to the model's context. Or it can simply do its job: run a linter after a file edit, log an action, send a notification.

Project hooks are located in .claude/settings.json. Mandatory hooks for the entire company are placed in managed settings: developers cannot disable them. There are also hooks that ask the model itself when judgment is needed. But a regular hook works without the model and is consistent every time. This is its difference from a line in the prompt: the model might ignore an instruction, but a hook will always execute. Hence the rule: a skill suggests, a hook guarantees.

Quality and Data

RAG (Retrieval-Augmented Generation). Before calling the model, the system searches for relevant document snippets and includes them in the request. The model responds based on what was found, not from memory. Agents are increasingly just given a search tool, and they search themselves.

Eval (Evaluation). These are tests for the agent. You collect tasks for which you know the correct answer and run them after every change to the model, prompt, or tools. A regular test expects an exact result, but the model's responses vary slightly each time. Therefore, testing an agent is more complex. Huyen considers evaluation the main difficulty in AI engineering.

The cache only gets one line in the glossary table. Judging by job postings, it's the least inquired about, so it gets its own section.

How the System is Structured

The model remembers nothing between requests. Everything the agent "knows" about the task is reassembled by the harness and sent at each step. The request is always structured the same way: first, tool descriptions, then the system prompt, then the entire conversation history.

Components of an LLM system. The model receives the assembled request and returns text or a request to call a tool.

The agent cycle itself, in Anthropic's documentation, is a standard while loop. Here it is in pseudocode:

# Pseudocode for the agent cycle algorithm. 1. Initialize history with the user's task. 2. Loop indefinitely: 3. Call the model with tools, system prompt, and history. 4. Append the model's response to history. 5. If the model's stop reason is not 'tool_use', break the loop (model responded with text or hit a limit). 6. Execute the tools requested by the model. 7. Append the tool results to history. 8. Continue the loop.

The stop_reason field explains why the model stopped. If it's tool_use, the model wants to call a tool, and the loop continues. Any other value, such as end_turn or max_tokens, means the model has finished or hit a limit. Then the loop ends.

Step 3 executes the application code. This is where a hook can deny the action.

The cycle itself is short. Almost all the work happens around it:

  • tools: your own, connected via MCP, and server-side tools executed by the vendor, such as internet search or code execution;

  • sub-agents: take on part of the work and return a short report;

  • hooks: verify actions before and after;

  • memory: stored not in the model, but in files and git.

Anthropic explains the need for memory in their article on long-running agents. Each new session starts from a clean slate. Therefore, the agent leaves a progress file, a task list with statuses, and a commit history for the next session.

How this looks in practice can be seen in the standard Claude Code setup. In my personal repository, a hook logs risky actions before each Bash, Write, and Edit call. Another hook suggests the appropriate model for the task with each request. There are three sub-agents: a cheap one for reading only, a medium one, and a powerful one. And over a dozen skills that are loaded only when needed. All of these are simple configuration files. But they are what determine what reaches the model and what the agent is allowed to do.

A common pitfall: the agent confidently says "done," but only half the job is completed. In the same article, Anthropic describes two typical failures. The agent tries to do everything in one go. Or it declares completion too early. Persuasion in the prompt helps little here. The harness helps: a list of requirements with statuses and a way to verify the result. For example, running tests or opening the application in a browser.

How Tokens Are Counted

You pay for LLMs with tokens, and input and output tokens have different costs. As of October 28, 2026, a million input tokens for Claude Sonnet 5.5 cost $2, and a million output tokens cost $10. Output is 5 times more expensive. Tool descriptions also count as input. In the documentation example, one tool with a short schema and a user's question together take up 403 tokens.

The model remembers nothing, so at each step, the entire history is sent again. Let's calculate with a hypothetical example:

  • at the start of each request, 12,000 tokens: tool descriptions and system prompt;

  • the first user message takes 200 tokens;

  • at each step, the model responds with 400 tokens, and the tool returns another 2,500;

  • a total of 30 steps on Sonnet 5.5.

Hypothetical scenario. Sonnet 5.5 prices as of 10/28/2026.

On the last step, the request weighs 96,300 tokens. This is less than a tenth of the window. But over all 30 steps, the model read 1.63 million tokens, 17 times more. Each step re-pays for everything that came before it, and the sum grows faster than you might think. Without caching, such a task would cost $3.38. The model's responses across all steps combined only take up 12,000 tokens. Almost all the money goes to input.

A separate question is how many tokens Russian text occupies. Different languages are tokenized differently. In the study by Petrov et al. (NeurIPS 2023), the same text in different languages occupied up to 15 times more tokens. For Russian and English, I did my own small measurement. I took three pairs of identical texts: documentation, prose, and code with comments. About 1,000 characters per language, Claude tokens.

Measurement on 10/28/2026, script calc/claude_cli_ru_en.py. The sample is small; this is a guideline, not a study.

On older models (Sonnet 4.6, Haiku 4.5), Russian text occupied 1.6 times more tokens than English. On the new Sonnet 5.5, the difference is only 1.27 times.

It's interesting to see why. Russian has hardly changed: it was 402 tokens, now it's 415. But English increased from 252 to 327, by 30%. This aligns with Anthropic's documentation: starting with Opus 4.7, models tokenize text differently and yield about 30% more tokens for the same text.

The conclusion is simple: count tokens using the model you intend to use. For this, Anthropic provides a free endpoint, count_tokens. However, it provides an estimate and doesn't account for caching.

How Prompt Caching Works

Let's return to the 1.63 million tokens. Almost everything the model reads in step 30, it has already read in step 29: the same tools, the same system prompt, the same history. Only the end part is new. Caching allows not reprocessing the repeating beginning.

Block order and what resets the cache, according to Anthropic's documentation on 10/28/2026.

How it works. The request is always read in the same order: tools, system prompt, messages. You place a marker in the request indicating up to which point to cache. There can be up to four such markers. Everything up to the marker is saved. The next request will only hit the cache if its beginning exactly matches the saved part, down to the character and image. The cache lasts for 5 minutes, and each hit extends its duration for free. For an additional fee, it can be stored for an hour. Short requests are not cached: new Claude models require at least 512 tokens. No error will occur; the cache simply won't activate.

In our example with caching, each step reads the old data for $0.10 per million and caches only the new part. The total is $0.51 instead of $3.38, 6.6 times cheaper. The requests are identical; only how the server processes them changes. When paid cache storage becomes profitable is detailed in the article "How Much Does an LLM Request Really Cost?" With Anthropic's five-minute cache, it's profitable from the second request with the same beginning.

It's easier to break the cache than you might think. Any difference at the beginning of the request invalidates everything after it:

  • changed a tool description: the entire request will be reset;

  • enabled internet search or inserted the current time into the system prompt: the system prompt and history will be reset;

  • changed tool_choice or added an image: the history will be reset.

From this, one rule emerges: put unchanging parts at the beginning, new parts at the end. The beginning of the request should not contain dates, random IDs, or reordered tools.

Checklist: Ten Practices for Your First Agent

  1. Start with a single model request. A chain is better than an agent if the task steps can be defined in code.

  2. Place unchanging content at the beginning of the request, and new content at the end. The system prompt should not contain time, random IDs, or other changing data.

  3. Do not change the set or order of tools mid-session.

  4. Check the usage field in each response. If cache_read_input_tokens is almost always zero, your cache is not working.

  5. Count tokens using the model you will be using. Tokens differ between models, with differences up to 30%.

  6. Keep the history short. Offload noisy tasks like search and logs to sub-agents, and store state in files, not in the conversation.

  7. Move long instructions into skills, not the system prompt. This way, only their short descriptions will appear in each request.

  8. Implement actions that must always execute as hooks, not as lines in the prompt.

  9. Give the agent a way to verify itself: tests, builds, a browser. Otherwise, it might declare completion too early.

  10. Connect MCP servers and load skills only from trusted sources, and grant the agent only necessary permissions. Anthropic's documentation compares a third-party skill to third-party software you install.
