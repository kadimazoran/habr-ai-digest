Let's start with the wall.

The Beginning: Tools Living in a Browser Tab

I'm involved in implementing AI assistants for a company. I work with OpenWebUI. At the beginning of 2025, I hit a wall that I foresaw: the assistant confidently answers questions but can't do anything. And business needs not "tell me," but "do it": check bonus balance, find an order, check delivery status, retrieve a regulation, create a request.

The first thought was the most obvious. OpenWebUI has a "Tools" section where you can write a Python function with a docstring, and the model will call it. Fifteen minutes, and it works. That's enough for a demo.

Then came the details.

  • The code lives in the web interface. Not in git, not in review, not in CI. Who changed it and when: a philosophical question.

  • Dependencies live in the platform container. Install a library, and pray it doesn't conflict with others.

  • The tool is not reusable between instances and models. Copy the script, get two versions that have already diverged.

  • Secrets are in the code or in the platform's environment variables, not where they belong.

  • A long operation blocks the chat. The user sees "thinking," while the tool waits for a response from someone else's API.

  • There's no audit. No one will tell you who, when, and with what parameters a write-off was made.

In this scheme, the tool lives in the administrator's browser tab. One day someone will click "Save," and no one will remember what was there before.

It's fine for a pet project. Not for a company.

Stage Two: Web Services and a Phone Directory

The logical next step: move the tools into separate web services. The tool becomes an endpoint. An endpoint has a contract, the service is deployed separately, secrets are on the server, logs are collected properly.

It got better. Exactly until there were twenty tools.
