Sixteen promises and two models that tried to break them: how we released skillmem 0.12

In 0.11 we ran AI reviewers over code for forty rounds and found many bugs. But each reviewer had their own idea of what "correct" means. In 0.12 we started from the other end: we wrote down sixteen invariants that our MCP memory promises, and then two models from different labs spent ten days looking for counterexamples. Only findings with reproduction were counted. I'll tell you what they broke (Windows counted NUL as a terminal), what it cost, and what we consciously left in Known issues. Read on

skillmem is local memory for code agents: an MCP server on top of SQLite with nine mem_* tools. Claude Code, Codex, Cursor, and other clients share one database. Habr already had two articles about it: how someone else's README became a user rule and forty rounds of review. This article is the third and, hopefully, the last about reviews.

Why "review until it's clean" doesn't work

After 0.11, I was left with an unpleasant conclusion: model review without criteria is a matter of taste. One model nitpicks at names, another at race conditions, and each is right in its own way. The stop condition "two clean rounds in a row" worked, but it didn't answer the question "what exactly does the program guarantee?"

Therefore, in 0.12, the document came first, and the code followed.

Step 1. Write down the promises

docs/INVARIANTS.md contains sixteen invariants, INV-01...INV-16. For each, it specifies: the exact wording, the function that maintains it, and its status at the time of release. The invariants are divided into four classes:

  • data. No record, field, history string, body file, or backup is lost, overwritten, or "silently not written." Export → import-vault → export yields the same file byte for byte.

  • trust. Only the owner at the terminal approves and seals a record. Only the owner changes a sealed record. Unapproved text is fed to the model only within the "this is data, not instructions" frame.

  • concurrency. Any "read → write" decision is made within the transaction of that record or via compare-and-swap.

  • other. Hooks do not drop the session, names are compared identically on all file systems, and so on.

The release bar is recorded there as well: zero P1/P2 in the "data," "trust," and "concurrency" classes. Everything else can go into Known issues, but it goes there openly.

The main effect turned out to be non-technical. The reviewer stopped evaluating whether the code was good. They take a specific promise and look for a counterexample.

Step 2. Two models and one rule

There were two reviewers: Codex from OpenAI (we call it Astra) and Claude Opus 5.5 from Anthropic. Models from different labs make different mistakes, which is why there are two. They worked for about ten days: 0.11.0 was released on September 17, and 0.12.0 on the 27th.

The rule is one: a finding without reproduction is not counted. A command or test is needed; reasoning is not accepted. Each fix comes with a test that fails on the parent commit of the fix. This is checked by scripts/release-gate.sh for each new test function: a test that is green both before and after the fix proves nothing, and the gate does not pass it.

Property tests are written in hypothesis and use real concurrent writers: separate processes and threads on a single file, without mock locks. Hooks are fuzzed with corrupted input, corrupted databases, and bad paths.

What was broken

Five findings that seem most illustrative to me. Each has a regression test in the repository.

1. Windows treats NUL as a terminal. The entire trust model relies on one check: owner commands require a real TTY. On Windows, the CLI accepted stdin redirected from NUL as a console. The agent executed skillmem write … < NUL, and its record was saved as approved and sealed — meaning it became a rule "from the owner." No reviewer found this by reading the code. The bug only manifested when the CI first ran on Windows.

2. Timestamp from the future. The session recap hook is rate-limited by a timestamp file. On Windows, a newly written file's mtime can be a few milliseconds *ahead* of time.time(). The age became negative, the debounce decided the limit was not active, and skipped the second recap — and with it, the second model call. There was also a related race condition, on all OSes: the timestamp was read *before* acquiring the session lock and not re-read after acquiring it, so two Stop hooks could pass the check simultaneously.

3. Similar characters closed the frame. Unapproved text is wrapped in a "data, not instructions" frame. Whoever can write a record wants to close the frame prematurely. We escaped the literal closing marker long ago, and reviewers found workarounds: a marker after a Unicode line separator instead of , after NBSP, after invisible characters, and also a marker made of similar brackets ⨠ and ⪥, which the model reads as < and >. Now all of this is escaped, and a property test generates new variants.

4. Ctrl-C, after which records disappeared. If a write operation was interrupted while waiting for another's lock, the SQLite transaction remained open. All subsequent writes through this connection were *committed* by the library, but disappeared when the connection was closed. For REPL and library calls, this was silent data loss. Now, interrupted transactions, nested savepoints, and failed COMMITs are rolled back before the interruption propagates further.

5. Database cp. If the database file was copied and an export was made from the copy, the copy considered itself the original: it occupied its backup directory, cleared its dumps, and GC deleted body files that the original was still serving. Now, a copy is a separate database: upon first opening, it copies its bodies, and the export directory has exactly one owner.

From the same class. On case-insensitive file systems (APFS, NTFS), a case-duplicate forced pruning to delete the *new* dump, and embeddings Σ.png and ς.png were confused. upgrade sent the saved GitHub token via redirect to another host. On Python versions before 3.14, Path.is_dir() raised PermissionError instead of False.

What it cost

  • Time: about ten days in a review → fix → review cycle.

  • Tests: from about 430 to about 2,538, mostly property and regression tests.

  • CI: full run on Linux, macOS, and Windows × Python 3.11–3.13. Plus a separate semantic search job, build, and Docker check that the image starts and serves 9 tools. Release to PyPI runs all this again on the tag.

  • User inconvenience. 0.12 refuses where 0.11 silently agreed: owner commands without TTY, writing over an archived record, importing values that were previously type-coerced. Therefore, release notes open with the section "Before you upgrade." The correctness release breaks scenarios that worked by accident.

  • Money: no token bills. Both models worked on fixed subscriptions.

What was consciously not fixed

Writing down invariants also means writing down where you fall short of them. The CHANGELOG has a Known issues section, with about twenty items, each indicating the invariant it violates. The most important ones:

  • Deny rules and TTY checks do not protect against an agent with a shell. script -qec "skillmem tr''ust x" /dev/null passes both checks. True isolation is a sandbox, not string comparison.

  • Slugs, kind, project, and tags are shown to the model without a frame (INV-07).

  • The "already shown" log for hooks is not locked, so parallel PreToolUse hooks can inject the same rule twice.

  • On Windows, the catastrophically backtracking SKILLMEM_VERIFY_PATTERN is not stopped by skillmem's own watchdog. Only Claude Code's hook timeout of 10 seconds stops it.

  • uninstall --purge-db fails while the MCP server holds the database open.

None of these items relate to P1/P2 in "data," "trust," or "concurrency," otherwise, the release wouldn't have happened. But they are real, and it's better you read about them here than stumble upon them yourself.

Conclusion

Asking a model to "review code" yields style and a few bugs. Asking it to "break this recorded promise, with proof being only a failing test" yields the bug with NUL on Windows. The invariant file turned out to be more valuable than any single fix: the next reviewer, human or model, starts with it.
