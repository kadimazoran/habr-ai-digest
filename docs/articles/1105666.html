However, there are cases where speed and memory efficiency are crucial, and "cost is no object." Here we need to go deeper and look at how Goose works. Three pictures.

Goose in Section

Picture number one. For memory management, Goose uses structures called data stacks. Their number is calculated at compile time.

Here, it should be noted that:

  • These are NOT call stacks: they don't contain function frames, only data. But they are freed like a stack – upon exiting the scope, the top simply shifts back.

  • Memory is reserved but not immediately allocated to the process (lazy allocation).

Picture number two. Data stack structures are distributed among functions at compile time.

Seven functions, three data stacks. The compiler calculates the number of data stacks based on the deepest call chain in the program, considering only functions that hold growing arrays: N is the maximum number of such arrays alive simultaneously. No new data stacks appear during runtime. Each growing array needs a separate data stack as long as it's alive, meaning if a function creates multiple growing arrays, each will have its own data stack. When a function finishes, its data stacks are passed to subsequent calls: in the picture, fn0, fn2, fn4, and fn5 take data stack 1 in turn.

This approach, of course, imposes limitations on recursive functions: at the moment of a recursive call, the function must not have any live growing arrays, otherwise each recursion level would require its own data stack. Anything that needs to survive the call is created externally and passed in by reference.

Picture number three. Data packing.

Here's the structure:

struct Item  { sku: u8[varint], qty: varint, cents: varint } struct Order { id: varint, customer: u8[varint], items: Item[varint] }

Filled with this data:

{ "id": 1001, "customer": "alice", "items": [ { "sku": "SKU-441", "qty": 2, "cents": 1999 }, { "sku": "SKU-7", "qty": 1, "cents": 500 } ] }

Who is whoosh?

So, values in Goose do not live on the heap, and complex structures are packed as sequentially as possible.

Can this be done in C? Of course. Goose is a transpiler, here's the source in Goose (named order.goose.rs so GitHub highlights the syntax), here's its equivalent in C. You can look, but changing is dangerous.

Since values don't live on the heap, Goose is already faster than languages with a "heap" in scenarios with many memory allocations and single-threaded operation.

Full "dominance" is currently partial potential, not kinetics. To match other languages in computational capabilities, a number of features need to be implemented, such as parallel loops across threads (par for) and loop vectorization (simd for):

Watching the Hands

I completely agree with MrTeamlead that Goose's benchmarks are specifically designed to demonstrate Goose's advantage in scenarios with intensive memory usage and minimal computation. From this perspective, there's no point in optimizing the measured code in the benchmarks.

But let's take a look. Again, in my Goose fork.

Change 1. It was Vec::new(), now it's Vec::with_capacity(N as usize).

Well, it's something. The benchmark models a situation – a stream of events hits us, we collect and process them. We don't know how many events there will be in advance. N is a benchmark parameter (500,000 for the author, 2,000,000 in the video), and for the code being tested, this number, in theory, is unknown.

Change 2. It was String, now it's MyString. In this case, the comparative optimization is justified, because the equivalent in Goose, records_fixed.goose, also uses a fixed size.

The comment for records_fixed.goose states:

// The same event log in fixed mode, which is the only mode Rust and C++ can // express.

This means it's supposedly how Rust would store the same events. But in records.rs, the text is stored on the heap (String), while in records_fixed.goose, it's directly inside the event (up to 15 characters). The layouts are different, and comparing them directly is unfair. When MrTeamlead places the text in Rust similarly, inside the event, the difference disappears: 46.7 vs. 46.5 ms in the video. Essentially, he wrote the missing records_fixed.rs.

However, Goose has another benchmark, records_var.goose, and here it makes no sense (within the benchmark) to use a fixed size. A word of 4…15 letters is a parameter for generating benchmark data, not a size known in advance to the processing code. And records.rs is a suitable pair for it, illustrating the types of cases where Goose excels.

By the way, while writing the article, I discovered that the Goose author was informed about the critical review. The author replied that records_fixed.goose was just an illustration, and the real benchmark is records_var.goose, and removed records_fixed.goose from the repository…

Conclusion

The artifacts examined demonstrate the optimization capabilities of Rust programs well, but they do not diminish Goose's advantages (partially potential) in the scenarios modeled by Goose's benchmarks.

A few years ago, Goose would have been just a cool pet project, requiring years to develop. Now the situation is different. Our CEO once told me: "I'm using Orca to track business documents." I looked at this Orca… Started in March 2026, nearly 17,000 commits, over six million lines of code (with tests)… So black swan events are more possible than ever. However, Goose's fundamental problems remain, and no one has canceled them.
