Hello everyone! I am the CTO of Documenterra. We make a platform for documentation websites, so I can talk about documentation for hours. But today's story is not about the product. It's about how documentation, which testers previously checked as an afterthought, has become the main source for their autotests.

How it was

For as long as I've been writing software, documentation has lived at the very end of the pipeline. We wrote code, rolled out a feature, someone described it. Clients read the documentation. Within the company, it was needed by almost no one: developers know how everything works anyway (or so they think), and testers were asked to check it as a favor when time permitted. Time, as you can imagine, rarely permitted.

How it is now

This year, documentation gained an internal reader. Testers started feeding it to Claude and getting test cases and autotests from it. Documentation moved from the end of the pipeline to the beginning: testing now starts with it.

Here's what we can do now. At the beginning of 2025, I would have considered half of this list overly optimistic.

  • Autotests without fussing with selectors. An hour of prompting, five hours of Claude's work, and we have working autotests for a feature. No one picks selectors, no one invents steps manually. Only test case descriptions are provided.

  • Tests for unfinished features. We write and fix tests by feeding the model documentation. If a new feature relies on old functionality, a test that prepares preconditions can be written even before the new part is available.

  • "Test and write autotests." We give the model a new feature, PR, Jira ticket, and documentation. Manually clicking through the feature to understand how it works and what to check is no longer necessary.

  • Tests for a feature the tester has never seen. If there's documentation for it, Claude will figure it out.

  • Hunting for outdated test cases. We find manual and automated test cases that contradict the current documentation and update them.

  • Bugs as a bonus. The model usually understands when it encounters a bug: from test cases, documentation, or simple logic (an error pops up, a button doesn't click). Another source of bugs is analyzing run logs.

I'll show you how this looks in practice with a simple feature: password recovery.

Step 1. Documentation. The model received this fragment via the MCP server:

  1. Open the portal and click the Login button to go to the login page.

  2. On the login page, click Forgot password?.

  3. On the password recovery page, enter your login or email address associated with your account, and click Reset password.

  4. You will receive an email with a link to set a new password.

Step 2. Test cases. These were generated by an AI agent. The precondition for both is: the user is not authorized.

TC-1. The "Forgot password?" link opens the recovery page (steps 1–2 from the documentation)

Step

Expected result

1. Open /login/

The login form has a Forgot password? link

2. Click Forgot password?

The /forgot-password/ page is open with a login field and a Reset password button

TC-2. A request without a login is not submitted (step 3, negative)

Step

Expected result

1. Open /forgot-password/

The login field is empty

2. Click Reset password without entering a login

A validation error appears for the field, the page does not change

Note TC-2: the documentation says nothing about an empty login. The model inferred the negative case itself, from the form's standard logic.

Step 3. Autotest.
