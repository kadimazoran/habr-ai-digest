In the previous article, I discussed how I use generative models as opponents: asking them not to confirm the first decision, but to find conditions under which it would fail.

This practice led to a question that is no longer about organizing my work.

Why do we so often expect a single answer from the AI system itself? Why should it choose a single route as early as possible if the task allows for multiple strategies, the cost of error is unknown, and the best action is sometimes to refrain from acting?

The recent release of Qwen3.8-Flash-Next has made this question particularly clear. A large model can store a huge amount of parameters but use only a small portion of them for a specific token. This is similar to economical attention distribution—and simultaneously highlights the boundary between choosing computations and choosing strategies.

I want to discuss this boundary.

I'll preface this by saying that what follows includes known architectural approaches, my interpretation, and a research hypothesis. These are not the same thing. I will distinguish them directly in the text.

Large Model, Small Active Circuit

The technical report by the authors of Qwen3.8-Flash-Next describes a sparse MoE model with 125 billion parameters and approximately 6 billion active parameters per token. Additionally, 51 billion parameters of n-gram representation tables are used, stored outside the accelerator in host memory.

If we set aside the numbers, the idea seems simple. The system has a large capacity available, but it doesn't use it all at once for each small step.

Moreover, "activating little" doesn't mean "the whole system fits on a small graphics card." Weights need to be stored somewhere and delivered on time, and memory and latency also depend on context, caches, and data exchange. For my idea of small models, this is the same limitation: savings will have to be measured for the entire system.

Imagine a large engineering organization. It might employ data, security, infrastructure, interface, and machine learning specialists. To discuss video stream quality, it's not necessary to gather the entire company simultaneously. We need those whose expertise relates to the current issue.

In MoE, this function is performed by a router. It directs the token's representation to selected experts. The experts process it, after which the results are returned to the model's general flow.

Such conditional activation is not new. In Switch Transformer, for example, simplified routing to a single expert was used. The main idea was to increase model capacity without a proportional increase in computation for each input. Along with the advantages, the authors discussed very practical problems: training instability, communication costs, and load balancing among experts.

Qwen develops this same general line of economical computation, adding its own mechanisms for handling long contexts, residual streams, and large n-gram memory.

This looks very similar to my initial intuition: there can be a lot of knowledge, but the active area is relatively small.

But it's easy to take an extra step here.

An Expert within MoE is Not Yet an Independent Interlocutor

When we hear the word "expert," our imagination quickly paints a picture of a team of specialists. One suggests building a bridge, another looks for a ford, a third assesses the risk, and a fourth asks if crossing the river is even necessary.

A standard MoE doesn't have to work that way.

Its experts are parts of a single trainable model. Usually, they are computational blocks with similar structures, trained together in a common system. The router chooses which parameters to use for the current representation. But this doesn't mean the model has formed several complete plans, compared their consequences, and saved the losing options.

This is an important distinction:

MoE router: which parameters to use now? Router of strategies: which action options to save, how to test them, and when not to choose any?
