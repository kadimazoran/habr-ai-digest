Recently, we tried to summarize the results of semantic search using small language models running directly in the browser. It didn't work very well: the models often hallucinated. But models with 0.6 billion parameters don't necessarily need to know everything. It's enough for them to read four text snippets and either summarize their content or admit that there's no answer to the question within them. "It seems fine-tuning will help here. It'll also be a good reason to write a follow-up article."

And here it is. To achieve the result, I had to rework the training data four times, and the unsuccessful attempts turned out to be no less interesting. In short: my blog's search page now uses a fine-tuned Qwen3-0.6B by default. It answers correctly about as often as the original model, but makes mistakes three times less often. And it never tried to answer a question that wasn't covered in the blog. Plus, it now requires downloading less data to load. The model, dataset, and code are open-source, so you can deploy all of this on your own website and check it out for yourself.

The Task and Action Plan

The model receives a system prompt ("Answer in no more than two sentences, using only these snippets. If the answer is not in them, say that the blog does not seem to cover this topic"), four numbered snippets found by semantic search, and a question. Nothing more. A good answer should either convey information from the found snippets or, if the answer is not in them, state: "It seems this topic is not covered in the blog."

To fine-tune the model to handle such a task, several thousand examples of correct behavior will be needed. I don't have several thousand blog posts, so the plan is as follows:

1. Use training data from open-licensed technical texts. The questions from the previous article – all 45 used for quality evaluation (eval) – will become the test set. Therefore, training the model on my own publications would be practically cheating (especially since I only have 16 of them). Instead, I took the Go blog, the Rust blog, Rust RFCs, and Python PEPs. In total, this resulted in 2193 technical documents with licenses that permit such use.

2. Use the same search and retrieval mechanism. Each document is split into chunks, for which embeddings are created – exactly as in the semantic search of my blog. For each training question, the search returns the four most relevant snippets. This way, the model learns to work with the same noisy results it will encounter in real conditions: sometimes the answer is in the first snippet, sometimes in the fourth, and sometimes a nearly identical snippet from another publication appears nearby.

3. Have Claude prepare the examples. Claude Sonnet 5.5 generated questions for individual text snippets. For some questions, the answer is contained within the four retrieved chunks. In other cases, I excluded the document on which the question was based, so the model learns to refuse to answer. There were also near-miss examples: questions on a related topic that the retrieved snippets did not actually answer. Then, Claude Opus 5.5 answered each question, relying on the relevant chunks and using the same system prompt as on my website. Formally, this is a form of knowledge distillation: a large model shows how to perform a task, and a small model learns to replicate its behavior.

4. Train the model on my Mac. For this, I used Low-Rank Adaptation (LoRA) with the mlx-lm library on a Mac mini with an M4 chip and 24 GB of memory. This same computer serves as my home lab and media server. I trained each version of the model for one epoch – one full pass over 4500 training examples. This is 2265 iterations of two examples each, with weight updates every second iteration and saving a training checkpoint after every quarter epoch. The entire process takes about 1 hour and 20 minutes.

5. Export the model for the browser in the same 4-bit format that the page already loads, and perform the same quality evaluation as last time. For this, 30 questions were used for which answers exist in the blog, and another 15 for which the blog does not provide answers. Opus evaluated the model's answers by comparing them to the provided text snippets.

One more nuance of the last step: each fine-tuned version is compared to the base model exported in exactly the same way. So, the only difference between them is the fine-tuning itself. This version of the base model gave 17 answers corresponding to the source out of 30, not 18 as in the previous article.

v1: It Only Got Worse

The first dataset contained about 4500 questions with answers written by Opus. Usually, these were two sentences, rich in detail. After fine-tuning, Qwen3-0.6B correctly relied on the source in only 8 out of 30 cases, whereas before the intervention, there were 17 such answers. However, the model learned to refuse to answer: it never made up an answer to any of the 15 questions not covered in the blog. The base model made mistakes in two such cases. But things got significantly worse with questions that did have answers in the blog.

The model developed two habits. The first it adopted directly from the training data. If Opus could only answer part of a question, it would answer that part and add something like "the blog does not provide a more detailed explanation of the reasons." For a large model capable of understanding what information is missing, this is a perfectly normal response. About 10% of the training answers contained such caveats. The fine-tuned model adopted this mannerism and started adding them even where they weren't needed – in fact, in every third answer. Moreover, it usually stated that information was missing which was actually present in the provided snippets.

The second habit was even worse: the model tried to include more details in the answer, and if there weren't enough, it simply made them up. Here's how the base model and v1 answered the question "What does the blog say about embeddings and cosine similarity?":

"In the blog, embeddings are considered a way to represent semantic relationships between words, and cosine similarity is used to measure the proximity between vectors." (Qwen3-0.6B)

"The blog states that embeddings reflect semantic, not just lexical, relationships. Specifically, 'King' and 'bicycle' are close to each other, 'King' and 'bicycle' are far apart, and 'Beer' and 'alcoholic beverage' are neighbors." (v1)

The base model's answer is vague but correct. The v1 answer sounds as if the model actually read the article, but in reality, it's incorrect. In the semantic search article, 'king' and 'queen' are close to each other, and 'bicycle' is far from them. The model adopted the format of Opus's answers: a few specific facts, terms in quotes, a second sentence. But at the same time, it didn't learn to read the source text as carefully.

v2: Loss Decreased, But Answers Got Worse

Getting rid of the caveats was the easiest part. I wrote a small script that removed phrases like "the blog doesn't explain X" from the training answers (and excluded examples starting with such phrases entirely), and ran the training again. The caveats disappeared. But the quality of the answers hardly improved: 9 out of 30.
