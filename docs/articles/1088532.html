I need my own book canon. A canon is a single stable record of "this text" to which everything else is attached: files in different formats, audiobooks, editions, duplicates.

Not because external sources are bad. If I need to quickly get the author, title, or identifier of a book, I can easily get it from an existing catalog. Even if the catalog has garbage, it's not a disaster: garbage can be gradually fixed. The problem is different — it's not my catalog. I can spend years accumulating the results of my own analyzers around an external identifier: linking audiobooks to it, finding duplicates, identifying editions, collecting statistics, building recommendations. And then the external source will change identifiers, structure, or simply disappear, and all the accumulated work will hang in the air.

Therefore, I decided to create my own corpus of books. It will also be dirty, and that's okay. The main thing is that it's my dirty corpus: I can gradually improve it, and I control its identifiers myself.

The corpus currently contains about 664 thousand books. And the task for which all this was needed, at first glance, was very simple: take a few minutes of an audiobook, run it through Whisper, and find the corresponding book by text.

What could be difficult? It turned out — almost everything.

First, there was a regular text search

The idea is standard: break the text into shingles (a few words in a row), build an index, and search for similar sequences. I started with MinHash on shingles.

It quickly became clear that the naive approach breaks down in a very real scenario: one book is entirely contained within another. There's a short novel and a huge collection of works that includes it. The novel has tens of thousands of shingles, the collection has millions. MinHash estimates Jaccard similarity: the size of the intersection divided by the size of the union. But I need containment — whether a small book is entirely within a large one. The novel within the collection has a containment of one, while the Jaccard similarity is approximately the ratio of their sizes, i.e., around hundredths. As a result, two books, one of which literally contains the other, barely overlap in their fingerprints.

I started experimenting with MinHash and Winnowing variants, and here's where the first useful mistake happened: I changed several parameters simultaneously and at some point decided that MinHash was completely unsuitable. Later, it turned out that I simply didn't understand which specific parameter was ruining the result.

So, I returned to MinHash and took the main idea from Winnowing — local minima. The fingerprint is calculated not for the entire book, but for blocks of 300 shingles, each block having its own minima. Blocks of the novel within the collection strongly overlap with the blocks of the novel itself, and a significant portion of their minima coincide — the size of the collection no longer affects anything. The second half is chaining verification: a candidate is counted only if a contiguous piece of the query, about ten words in a row, was found in it, not a scattering of randomly matching shingles. This is how the current version emerged: block MinHash plus chaining verification.

It works well enough to build the rest of the system on it. But I don't know if it's the best: I still don't have a dataset on which I can honestly compare variants. That's what the rest of the article is about.

Finding a book doesn't mean understanding that the search works

After the working index appeared, a natural question arose: how well does it work? For a proper evaluation, you need a dataset where the correct answer is known in advance: this query corresponds to book A, this one to book B, this one should return several duplicates, and for this one, there's no correct answer in the corpus at all.

I didn't have such a dataset. A small corpus is useless: it doesn't show how the system behaves in a large search space (there will be an example below of how little it shows). A large corpus cannot be manually labeled. So, I went down a path that now seems both obvious and quite insane: building a dataset from existing data and verifying it with LLM agents. I have parallel sessions of an agent family, each on its own machine.

From then on, almost every new source of "truth" went through the same cycle. First: "this seems like it can be used for labeling." Then verification. Then: "no, this is also garbage."
