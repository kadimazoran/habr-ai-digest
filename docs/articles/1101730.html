Hello everyone, this is the TM.Tech team from "Third Opinion Platform" company. We specialize in artificial intelligence in medicine. A significant portion of our company's products are built around computer vision tasks in the field of radiation diagnostics.

The data we work with includes X-rays, fluorographies, CT scans of various body parts, and mammographies. Medical organizations send us studies and receive processed results with various findings: localized pathological areas, measurements, probability assessments of pathology, and other data.

We'll discuss the specifics of this work in more detail another time. Today, we'll talk about Ray and why it became necessary in our architecture.

Why Ray?

Typically, we work with medical studies in DICOM format. Each DICOM file contains visual data—for example, CT slices or X-ray images—and detailed metadata about the study (patient data, equipment, dosage, dates, and much more). As a result, a single study can be a rather hefty file or a set of files, which the service needs to perform several actions on before the final result can be obtained.

Some operations are CPU-intensive and require a significant amount of RAM. If the hardware is limited, setting up, maintaining, and scaling a whole zoo of such services quickly becomes a complex task.

There are several reasons for this.

Firstly, different services can reside on the same server, competing for resources. The flow of studies is unevenly distributed over time: in the morning, the load on the brain CT service might increase, and at lunchtime, the load on the mammography service might increase. Therefore, we wanted to flexibly allocate resources to each service, avoid maintaining large overhead in reserve, and still react quickly to load changes.

Secondly, within a single service, there can be different bottlenecks. Replicating the entire service in such cases is too wasteful. However, extracting each small, heavily loaded function or class into a separate service is also not very convenient: maintaining and debugging such objects separately is more difficult than within a single application.

Finally, a large project with a mix of asynchronous and multithreaded operations, resource contention, task queues, and various bottlenecks quickly becomes complex to maintain. We wanted a tool that would wrap this into understandable abstractions and allow managing the system's behavior through configuration parameters.

And such a tool exists. Meet Ray.

What is Ray

Ray is a unified, open-source framework for scaling AI and Python applications.

Its main idea is to take ordinary Python functions and classes and run them in parallel on a single computer or distributed across a cluster, without rebuilding the application around low-level RPCs, task queues, and process management.

The foundation of the system is Ray Core.

Out of its main objects, we will need four for further discussion:

1. Distributed functions — tasks;

2. Distributed objects with state — actors;

3. Distributed data storage — Object Store;

4. Resource scheduler — scheduler.

Let's briefly go over them.

Tasks

A Task can be defined as a regular function by adding the @ray.remote. decorator.

For example:

@ray.remote def preprocess(path: str) -> dict: data = load_file(path) return transform(data)

Each call is logically independent. Here's an example of using the task described above:

refs = [ preprocess.remote(path) for path in paths ] results = ray.get(refs)

Unlike regular functions, Ray can execute such calls in different processes, on different cores, and (if a cluster is configured) on different machines. The execution order can be arbitrary if the tasks are independent. If there are dependencies, the order is determined by the task graph within Ray itself.

Actors

If we draw an analogy with Python, a Task is a wrapper around a regular function. It's a stateless object where each Task call runs in a new or random Ray worker. An Actor, on the other hand, is a wrapper around a Python class instance, elevating it to the level of a stateful service.

One of the basic applications of an actor is model loading:

@ray.remote(num_gpus=1) class ModelWorker: def init(self, model_path): self.model = load_model(model_path) self.model.cuda() def predict(self, batch): return self.model(batch)

After initializing the actor, Ray assigns a separate worker (allocates a separate process) to it and schedules the execution of the class methods within that process.

Unlike tasks, actors can modify their internal attributes through their methods.

Object Store

Object Store is a distributed object storage system, including results from remote tasks. It is particularly useful for large shared objects. In a Ray cluster, each node has its own Object Store. If an object is created, for example, via ray.put(), it is stored by default in the store of the node where it was created and is not automatically broadcast to other nodes. Data is transferred to another node when it becomes necessary.

Scheduler

The Scheduler distributes tasks and actors across cluster nodes, considering the requested resources: CPU, GPU, memory, and custom resources. Based on these requirements, Ray determines where and when a specific task or actor can be launched.

Libraries based on Ray Core

Ray Core is the foundational layer of the Ray ecosystem. High-level libraries for various scenarios are built on top of it:

● Ray Tune — scalable hyperparameter tuning;

● Ray RLlib — reinforcement learning;

● Ray Serve — serving models in production;

● Ray Datasets — distributed data processing with Apache Arrow integration;

● Ray Train — distributed training.

All of them use a unified Core and can be combined with each other.

For our tasks, we primarily use two levels: Ray Core — for creating multiprocessing algorithms for CPU- and RAM-intensive operations, and Ray Serve — for assembling manageable API applications from such components.

Ray Core: Drawing Parallels

There are three typical scenarios that are of interest here.

1. Pipeline Parallelism

You can start a heavy operation in the background if its result will only be needed later.

Consider a typical scenario. A CT study comes in. For the final report, a 2D projection needs to be generated, but it will only be needed at the end of the pipeline.

@ray.remote(num_cpus=2) def render_projection(volume: "np.ndarray") -> "np.ndarray": return build_2d_projection(volume) volume_ref = ray.put(volume) projection_ref = render_projection.remote(volume_ref) findings_ref = detect_findings.remote(volume_ref) measurements_ref = calculate_measurements.remote(volume_ref) projection, findings, measurements = ray.get( [ projection_ref, findings_ref, measurements_ref, ] )

The .remote() call immediately returns an ObjectRef—a reference to the result, similar to a Future.

The task is passed to the Ray execution environment, and the scheduler selects a node and worker process with suitable resources.

ray.get() blocks execution until the result is ready. In asynchronous Python code, ObjectRef can be awaited using await ref; using blocking ray.get() inside an event loop is generally not recommended.

2. Batches and Chunks

Another scenario is parallelizing the processing of a set of arrays or a single large array. For example, when creating a dental report from a CBCT scan, you first need to find all teeth on the computed tomography image and visualize them.

Suppose after running the segmentation model inference, you get about 30 masks of individual instances. To represent each tooth, you need to analyze its orientation in space, perform volume rotation, and interpolation operations. These are heavy CPU-intensive operations, so processing individual teeth naturally lends itself to parallel execution.

A large shared object can be placed in the Object Store once:

ct_volume_ref = ray.put(ct_volume) tooth_report_refs = [] for tooth_id, tooth_mask in tooth_masks: tooth_mask_ref = ray.put(tooth_mask) tooth_report_refs.append( process_one_tooth_pipeline.remote( tooth_id, ct_volume_ref, tooth_mask_ref ) ) tooth_reports = ray.get(tooth_report_refs)

However, you don't always want to launch all tasks uncontrollably. If you need to limit the number of simultaneously processed tasks, ray.wait() allows implementing backpressure:

ct_volume_ref = ray.put(ct_volume) pending = [] results = [] for tooth_id, tooth_mask in tooth_masks: if len(pending) >= max_inflight: done, pending = ray.wait( pending, num_returns=1 ) results.extend(ray.get(done)) tooth_mask_ref = ray.put(tooth_mask) pending.append( process_one_tooth_pipeline.remote( tooth_id, ct_volume_ref, tooth_mask_ref ) ) if pending: results.extend(ray.get(pending))

3. Computation Graph

Often, code consists of a sequence of remote functions. In such cases, Ray allows passing objects via ObjectRef.

Because of this, the intermediate result doesn't necessarily need to be materialized between each step: it can be left in the Object Store, and a computation chain can be built.

projection_ref = render_projection.remote(volume) encoded_ref = encode_png.remote(projection_ref) # Materialize only the final result in the driver. png_bytes = ray.get(encoded_ref)

The Ray scheduler will not start encode_png until render_projection is completed.

Moreover, if ray.get(projection_ref) returns an np.ndarray, then encode_png contains logic that works specifically with np.ndarray. The developer doesn't have to separately consider whether the function receives the object itself or an ObjectRef.

Convenient.

Resource Management

When writing remote functions, you can specify the number of required resources. For this, there are parameters num_cpus, num_gpus, and custom resources.

Essentially, the developer informs the scheduler: this task or actor can only be launched when a certain amount of CPU, GPU, or custom resources is available. If the resources are available, the scheduler launches the task and marks them as occupied. There are two opposing scenarios here. If you underestimate the consumed resources, processes will start competing with each other for resources. This can lead to unstable latency and OOM errors. If you overestimate, tasks will queue up, even though some real resources are still available.

Therefore, the parameters are convenient for management, but fine-tuning them is only possible after profiling.

By default:

num_cpus = 1 num_gpus = 0

Ray Serve: Assembling a Manageable API

Ray Serve runs on top of Ray Core and allows transforming function execution into an online service.

The basic unit of Serve is a deployment.

Technically, its replicas are executed as Ray actors, but a deployment provides a higher level of abstraction. Serve manages the number of replicas, distributes requests among them, checks their status, restarts crashed instances, and applies configuration updates.

Several deployments can be linked via a DeploymentHandle to form a Serve application.

Let's consider a simplified pipeline for processing a medical study:

● ingress receives the request;

● Preprocessor performs CPU-intensive data preparation;

● Model stores the model in GPU memory;

● Postprocessor generates the final report.

Each stage can be scaled and updated independently.

The API receives a study ID, not an arbitrary path in the file system. The data itself must be in a storage accessible by the necessary cluster nodes. This could be a shared file system, object storage, or a separate data loading layer.

Another important aspect is passing results between stages.

Calling DeploymentHandle.remote() returns a DeploymentResponse—an object similar to ObjectRef. If the result of one stage is immediately needed by the next, the DeploymentResponse can be passed further without an intermediate await:

image = self.preprocessor.remote(study_id) prediction = self.model.remote(image) report = self.postprocessor.remote(prediction) return await report

In this case, the ingress replica does not retrieve the image and prediction into its own memory only to immediately send them further. It forms a chain of calls and waits for the final response. This is very similar to the computation graph with ObjectRef that we discussed in Ray Core. At the code level, the transition between stages looks almost like a regular Python method call, even though each stage remains a separate manageable component.

How an Application Appears in the Cluster

Locally, an application can be launched using:

serve.run(application)

For managed deployment, the application is defined as an importable object, and operational parameters are placed in the Serve config.

For example:

applications: - name: medical-api route_prefix: / import_path: app:application

On a self-managed cluster or a set of virtual machines, the head node can be started separately:

ray start --head

After that, worker nodes connect:

ray start --address="<head-address>"

And the Serve configuration is applied using commands:

serve deploy serve_config.yaml serve status

After serve deploy, the Serve controller creates the ingress, deployments, and their replicas on available nodes according to the declared resources.

The Serve config describes the desired state of the application. A subsequent serve deploy brings the running system to the new configuration.

Changing some parameters, including num_replicas, autoscaling_config, user_config, and max_ongoing_requests, is considered a soft update and does not require recreating all replicas of the corresponding deployment.

What's the Result

Ray Core and Ray Serve in combination provide an architectural model for production ML services. Ray Serve handles the external aspects: deployment, routing, scaling, fault tolerance, and service lifecycle management. Ray Core handles the internal aspects: computation graphs, parallelism, resource scheduling, and data transfer via the Object Store. The result is a system where you can control development speed, operational reliability, and performance under load.
