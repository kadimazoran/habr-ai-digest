Slonik-LLM, or How We Taught a Model PostgreSQL Kernel Development

Have you noticed how AI agents for programming are usually evaluated? Most often, two approaches are used:

  1. The agent is tested on benchmarks, i.e., sets of tasks with unified evaluation rules, and statistical tests are conducted to compare model results.

  2. The agent is asked to implement something spectacular in one request, for example, a game or a complex algorithm.

If you look at the tasks in these categories, you'll notice that few pay attention to DBMS development. Although this is a rather important, relevant, and specific domain with its own pitfalls. In the context of PostgreSQL, the model is required to write code that adheres to database invariants, code style, and can pass strict review and discussion in the PostgreSQL community mailing lists.

In recent papers from authoritative ML conferences, research primarily focuses on general tasks rather than creating DBMS-oriented ones. Among recent examples from ICML 2026, we can point to the SWE-rebench benchmark, which is populated with diverse repositories from GitHub.

Popular task sets like SWE-SQL or BIRD primarily test a model's ability to write SQL code or evaluate debugging capabilities. However, few look towards systems development, and specifically, database kernel code development.

Thus, the general trend in agent development and testing does not favor the DBMS kernel. Our team posed the question: can we create a model that will perform at the level of open frontier models in DBMS development tasks, specifically PostgreSQL? To do this, we collected data, created benchmarks, and conducted three stages of training for a model we named Slonik.

The initial results of this work were accepted at AAAI2027. Here, we will detail how Slonik was trained and what the outcomes were. Spoiler: the result exceeded expectations. The full technical report and model weights are available on Hugging Face.

Goal

So, the goals were set: train a model for Postgres kernel development tasks, improve its quality relative to its base version, and achieve a metric comparable to open frontier models.

We took the dense models Qwen3.5-9B and Qwen3.8-27B as our base and divided the training into three stages. The final training pipeline takes approximately a week using eight NVIDIA H200 GPUs.

Main Benchmarks

In all benchmarks, the model operates autonomously for up to 30 minutes (an empirically chosen limit: 60 turns and 28k tokens), simulating a C developer. We used our in-house developed solution as the agent harness. The agent had access to tools such as directory browsing via `tree` and standard Unix commands for reading, creating, and editing files. The agent harness was kept minimal, without enhancements like a knowledge base, to honestly measure the model's capabilities.

We selected the following benchmarks for comparison and evaluation:

  • PG17 consists of 36 tasks. 18 of these tasks involve fixing errors in PostgreSQL 17, which we obtained by reverting commits in git. The other 18 tasks require implementing built-in SQL functions in C. This benchmark served primarily as a validation set. We used it to select the training policy and models.

  • PG18 is less similar to the previous one. For it, we identically selected 53 PostgreSQL 18 fixes to test skill transfer to a later version of the same codebase.

  • Apache AGE is a graph extension for PostgreSQL. Our benchmark for it consists of 57 bug-fixing tasks. It is used to measure the model's development capabilities in a less familiar code tree.

  • SWE-bench Verified is the standard SWE-benchmark. We used a subset of 58 code error fixing tasks. On our end, this benchmark tests knowledge transfer across domains and allows us to assess whether the model forgets general development skills.

  • Terminal-Bench 2.0 evaluates an agent's autonomous operation in the command line. For each task, it receives a goal and a prepared environment, and it chooses the sequence of commands itself. In our experiments, we used a sample of 56 tasks.

The PG17, PG18, and Apache Age benchmarks were created with the help of active experts—developers of the Postgres kernel and extensions. The agent solved all tasks within a container without access to the internet or git, preventing it from looking up solutions. Each autonomous model run was time-consuming, so we limited the benchmarks to 60 tasks. We also took care to ensure that evaluation tasks did not end up in the training data.

Stage 1. Continual Pre-Training

In the first stage, we infused the model with general domain knowledge. This is called Continual Pre-Training (CPT), and we selected about 0.5 billion tokens for it. The data corpus included: PostgreSQL documentation and mailing lists, materials on other DBMS, system programming, SQL, analytics, and more. At this stage, we aimed to make the model more "domain-specific.".

To verify the acquired knowledge, we assembled a QA benchmark of 995 questions based on PostgreSQL 17.11 source code and documentation. Each question has four answer choices. For example, the set includes the following question:

What Unix socket permission does PostgreSQL consider for access control?

  1. A) Write permission (Slonik-27b's choice).

  2. B) Read permission.

  3. C) Execute permission.

  4. D) All three permissions equally (DeepSeek-V4-Flash's choice).

Correct answer: A) Write permission.

After CPT, the average accuracy on this benchmark for the 27b model increased from 60.8% to 67.1%. This tested memory specifically, as the agent had no access to documentation or code search.

In reality, 0.5 billion tokens is quite small for CPT. However, we were primarily training an agent model, and this amount allowed us to improve its domain specificity without losing other skills. In future iterations, we will increase the volume and quality of data.

Stage 2. Supervised Fine-Tuning

In Supervised Fine-Tuning (SFT), the model learns from ready-made examples of problem solutions. We used successful agent trajectories that showed the entire workflow from problem description to finding the correct code, making modifications, and verifying the result. This way, we aimed to "warm up" the model and teach it to navigate the PostgreSQL codebase.

To collect trajectories, we ran GLM-5.3-Flash and DeepSeek-V4-Flash on PostgreSQL training tasks. Tasks from evaluation benchmarks were excluded to prevent data leakage. Only successful episodes were included in the dataset, with a maximum of three per task. This resulted in 725 trajectories across 372 tasks, totaling 17.2 million tokens.

In our SFT experiments, we compared full fine-tuning of all weights with LoRA (Low-Rank Adaptation). With LoRA, the main model weights remain unchanged, while training adjusts their modifications, which can then be merged with the original weights. On the expanded SFT dataset, full fine-tuning of Qwen3.8-27B yielded 41.2% pass@1 on the validation set, while LoRA with a rank of 16 and a learning rate of 1e-4 achieved 37.0%. The difference was 4.2 percentage points.

We also tried NoRA, a variant of LoRA with normalization during weight adjustment calculation. It scales groups of numbers to a common magnitude, helping to stabilize training. In an early experiment on Qwen3.5-27B, this method yielded the best result. However, on the expanded dataset, there was no stable advantage over full fine-tuning: 42.3% versus 41.2% pass@1, with the difference within the margin of error between runs.

Stage 3. Reinforcement Learning

Next, we moved on to training the model on its own code writing attempts. For this, we used Reinforcement Learning (RL). The model independently solved tasks and received a reward if the changes made passed the tests. Based on the test results, we updated the model's parameters. Passing tests does not guarantee the correctness of the solution, as they may not cover all cases. We tested the hypothesis that training on a variety of tasks with such feedback would help the model solve more tasks than its base version. Our test results support this hypothesis.

For training, we used the DAPO algorithm in conjunction with verl and Uni-Agent. `verl` is responsible for calculating the loss function, gradients, and updating model parameters on the GPU. `Uni-Agent` connects the RL trainer with the agent and the task execution environment. For each attempt, it launches an isolated environment, manages the agent's operation, and collects the trajectory of its interactions with the model and tools. After the attempt is completed, the result is evaluated, and a reward is calculated. Trajectories and rewards are passed to `verl` for training. This approach allows integrating custom agent harnesses and using them for both training and evaluation.

In our case, the reward was binary: 1 for successfully passing regression tests and 0 otherwise.

At each step, we selected 16 tasks and ran eight attempts to solve each. For model updates, DAPO selected groups that contained both successful and unsuccessful attempts. Such a comparison provides a signal about which solutions should be encouraged. Groups with identical rewards across all attempts were discarded, and other tasks were selected instead.

In the synchronous scheme, we have to wait for all attempts to complete before updating the model. To improve GPU utilization, we used Colocate Async RL. In this scheme, the same GPUs alternately generate responses and update the model. Completed attempts are accumulated in a buffer. When enough data is collected for the next training step, generation is paused, and the GPUs are freed for parameter updates. Then, the updated weights are transferred to the generator, and the process continues.

Task Examples

The benchmarks and reinforcement learning use tasks of similar complexity. Examples:

  • Implementation of btrim(). The PostgreSQL 17 tree lacks an implementation of the built-in SQL function btrim(). It needs to be written in C and registered in pg_proc.dat to be callable from SQL. The function removes characters from a specified set from both ends of a string: for example, btrim('xyxtrimyyx', 'xyz') should return 'trim'. Variants for text and bytea are required.

  • Compatibility of the orafce extension. In the function dbms_random.string(option, len), the handling of an unknown single-byte mode needs to be corrected. For instance, dbms_random.string('w', 10) should generate ten uppercase letters instead of an error. Meanwhile, a multi-character mode like 'uu' should be rejected, and existing modes should retain their behavior.

The best quality was achieved with the sequence CPT => SFT => RL. In the SFT contribution check on the 27B model, the average proportion of successful attempts in solving PostgreSQL 17 tasks increased from 32.6% after CPT to 39.1% after CPT + SFT. Reinforcement learning added another 10.7 percentage points on PostgreSQL 17 and 20.5 percentage points on PostgreSQL 18. SFT taught the model to work based on successful examples, while RL improved the results through independent attempts and feedback from tests.

The improvement also transfers beyond PostgreSQL. SWE-bench Verified and Terminal-Bench 2.0 tasks were not used in our SFT and RL. This demonstrates the transfer of acquired skills to fixing other software projects and working in the terminal, even though reinforcement learning was performed on PostgreSQL tasks. Analysis of SWE-bench episodes indicates that the main improvement is related to the agent's work organization. After RL, the median number of turns decreased from 34 to 21, and the proportion of attempts where the model made a modification to the reference solution file increased from 76.3% to 94.0%. The model began spending less time on exploration and more frequently managed to make and verify a fix within the given budget.

What Didn't Work

We tried the MetaRL approach, where we trained the model to learn from its own mistakes to extract benefits not only from successful examples, but this did not improve the metric.

In this article, we do not discuss the agent wrapper, which is crucial for improving solution quality. Recently, research on this topic has emerged, for example, at the SIGMOD 2026 conference - DBCoocker. But we will cover this another time.

Conclusion

Thus, we have managed to fine-tune a small open-source model to a quality comparable to the frontier models we tested. Specialization in PostgreSQL also proved beneficial in other development tasks.

Returning to the point about implementing a spectacular case at the beginning of this article, our next goal is to verify whether such a small model can develop a full-fledged extension for PostgreSQL and another DBMS.
