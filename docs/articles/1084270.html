This week on Habr, there was a debate about whether programmers need the smartest models: "I stopped using the smartest AI models". The author believes that cheap models are sufficient for routine tasks, and speed is now the bottleneck. There are almost three hundred comments under the article. I read about half of them: many opinions, but I didn't find a single benchmark on identical tasks. It became interesting, so I sat down and checked it myself.

What I Measured

I took five tasks that I usually give to an agent and then go get coffee. All in Python, from one to five files:

  1. Off-by-one error in pagination, the test fails, needs fixing.

  2. Rename a function throughout the project. With a catch: in one place, the name is stored as a string in a dictionary and called via getattr.

  3. Normalize a Russian phone number based on a verbal description.

  4. A function of about fifty lines with triple copy-pasting. It needs to be refactored so that the output remains byte-for-byte the same, and each function fits within twenty lines.

  5. Splitting a bill among n people, where cents are lost. The requirements state: extra cents go to the first person in the list, and it should also work for refunds with negative amounts.

The models were four from the same family, from junior to senior: Haiku 4.5, Sonnet 5, Opus 5, Fable 5.1. The agent was the same everywhere (Claude Code in -p mode, MCP disabled), the prompt was the same, and each run started with a clean folder. I ran each task twice on each model, for a total of forty runs. I verified using a hidden script that the model couldn't see: it contained my tests and a check to ensure no visible tests were tampered with.

I'll say upfront what's bad about this. The tasks are small. Two runs per model is nothing. The family is the same. So, this is a quick-and-dirty measurement, I'm not claiming it's a benchmark. I'll share the tasks and checks if anyone needs them.

Now, what surprised me.

The most expensive model turned out to be the fastest. 341 seconds compared to 395 for the cheapest. Why is visible in the adjacent columns: fewer turns, almost half the text. The junior model reasons a lot, 18,754 tokens of reasoning for ten runs, while the senior has 2,674. Its tokens fly faster, but it needs more of them, and the total ends up being longer. However, Opus, the second from the top, is actually the slowest of the four, so "more expensive means faster" is also not true. I decided for myself to look at the total task time. Tokens per second don't predict it.

Next. Four out of five tasks were solved by all models, both times. Pagination, renaming with a catch, phone number, refactoring: 32 out of 32 runs. If your routine tasks are similar, a ninefold price difference won't give you anything.

And all the difference emerged on the fifth task. Moreover, they stumbled on reading the requirements, the code itself was fine for all of them.

The Fifth Task

The first thing that comes to mind:

base, remainder = divmod(total_cents, n) 
result = [base] * n 
for i in range(remainder): 
    result[i] += 1

1000 divided by three gives [334, 333, 333], beautiful. But for a refund, -1000: division in Python rounds down, resulting in [-333, -333, -334]. The extra cent went to the end of the list. This means the person paid one cent more than the others, but will receive one cent less upon refund. The requirements stated "extra cents go to the first person," so it missed the mark.

Haiku wrote it exactly like that both times. Sonnet did it once out of two. Opus and Fable all four times divided the sum modulo, and then returned the sign. And in their reports, they explained why: if you divide a negative number directly, the extra cent goes to the end, but the requirements say the opposite. In one run, Fable even wrote a script, iterating through all sums from -300 to 299 with n from 1 to 11. I didn't ask it to do that.

But most of all, I liked the junior model's report. Quoting verbatim:

✓ Remainder goes to the first person in the list 
✓ Works for refunds: split_bill(-100, 3) = [-33, -33, -34]

Two checkmarks in a row, and the second line contradicts the first. The visible test is green, the report is cheerful, but the bug will appear on the very first refund.

To be fair, the requirement about refunds can be interpreted in different ways, and someone in the comments will surely say that [-333, -333, -334] is also fine. Maybe so. But the senior models saw this fork and explained their choice. The junior model simply put a checkmark.

What I Do Now

For tasks where everything is clearly defined and there are tests, I give them to the junior model. 32 out of 32 solved, and it's almost an order of magnitude cheaper.

If the requirements mention "and for negative numbers," "and for empty," "as it was before," I use the senior model. The cheap model writes code fine. It misses the actual question.

And I trust the "it works" report only as much as I can verify it myself. One hidden test for a boundary case is cheaper than any model.
