According to statistics, among ordinary desktop computer users, the most common graphics card has 16 GB of video memory. According to GaugeDB surveys, such cards occupy 27.21% of the market. I have an NVIDIA GeForce RTX 4070 Ti SUPER with 16 GB of GDDR6X video memory, which currently costs $900. Until now, the main problem was that it was impossible to run an LLM agent on a graphics card of this class that would be smart and fast enough. If you run a smart model like Qwen 3.8 27B (Dense architecture), you get 10-20 tokens per second. And for comfortable work of a coding agent, you need 100-150 tokens per second.

But recently I came across 2 models: Tiel-Coder-35B-A3B-GGUF-MTP (specialized for coding) and Cyber-Tiel-Coder-35B-A3B-GGUF-MTP (an uncensored abliterated model that doesn't refuse to write exploits and perform active hacks on anything you ask). And what else is noteworthy about them? Firstly, they use MTP (Multi-Token Prediction) technology, which allows the LLM to predict several next tokens at once instead of one, providing a 20% inference speed increase. Secondly, they use the MoE (Mixture of Experts) architecture, which allows achieving the quality of a large model by performing computations with only a part of its parameters for each token. The token generation speed increase is +200-450%. Thirdly, it's Sharp Template, an optimized Chat Template (Jinja) with a system prompt that forces the LLM to spend fewer tokens on reasoning and answers without losing necessary information. It reduces inference by 59%, ultimately doubling the coding agent's performance.

As a result, on my graphics card, I run the following versions of these models: Cyber-Tiel-Coder-35B-A3B-MTP-UD-Q2_K_XL.gguf and Tiel-Coder-35B-A3B-MTP-UD-Q2_K_XL.gguf, and the launch parameters look like this:

This is a very good start, but as you can see, the context window is only 65535 tokens, which is not enough for agent work in coding. For this reason, I use 3 approaches.

Firstly, I don't use heavy coding agents like Codex or Claude Code, because out-of-the-box, with minimal interaction, they consume 10 to 14 thousand tokens for the system prompt, etc. That is, 15-20% of the context is consumed immediately, and local models lose context more easily, and such large system instructions distract them even more from the task the user formulates. I use the Pi coding agent; it requires 1.5 thousand tokens for its operation, which is 10 times less than Codex or Claude Code, significantly impacting the capabilities and quality of work on a user's local graphics card. Secondly, I never ask the coding agent to attempt a major code change directly. I start a new session with the command '/new' and ask the coding agent to write a plan.md file that describes what needs to be changed in the code to implement my task. This way, my 65535 token context window is sufficient because, essentially, I break the task into two phases: planning and implementation. Consequently, if the task is not too large, after creating plan.md, I clear the coding agent's context window with the '/new' command and ask it to make code changes based on plan.md, and upon completion, document the results in plan.md.

Thirdly, for very large plan.md files, I use my SKILL called subtask4llm-pi, which breaks down the task into no more than 10 subtasks and executes them sequentially. Each subtask is launched in a separate instance of the coding agent, where only what pertains to the subtask is passed, and its 65535-token context window will be almost empty. The results of the subtasks are aggregated into the main Pi instance and do not overflow its main context window, which is responsible for coordination, planning, and verification. You can install the skill by running the command "npx skills add https://github.com/evgenyigumnov/subtask4llm --skill subtask4llm-pi". There is also a version for Codex - subtask4llm-codex. By the way, if anyone wants to add support for Claude or help in any other way, send pull requests to https://github.com/evgenyigumnov/subtask4llm.

Fourthly, I use the approach of Robert Martin, the author of "Clean Code," who recently stated that he stopped reading code generated by coding agents. He achieved this by imposing strict constraints on the LLM. Using these constraints, one can compensate for the fact that the models used are heavily quantized to the UD-Q2_K_XL level. This means they make more errors than 4-, 6-, or 8-bit models. To create these constraints, I propose using AGENTS.md, which controls the size of each generated file, enforces writing unit tests, clearly formulates decomposition and responsibility in the code, and ultimately requires running tests. Since we don't pay for each token on a local graphics card, we can painlessly go through a couple of extra iterations when the model sees its mistakes and corrects them. Here is a basic example of an AGENTS.md file for this:

# AGENTS.md

## Code Writing Rules

- Maximum size of a single code file - 300-500 lines. If a file becomes larger, perform decomposition.
- The main principle is a single, cohesive responsibility per module.
- Do not sacrifice logical coherence or code readability to adhere to arbitrary line count limits.
- Separate files based on their functional purpose, not just line count.
- All functions must be covered by unit tests.
- When adding or modifying functionality, as well as fixing bugs, be sure to add corresponding unit tests.

## Pre-submission Check

- All tests and builds must pass without errors or warnings.
- Do not weaken checks or remove tests to pass testing successfully.

## Main Rule

**Never commit changes without a direct user request.**
