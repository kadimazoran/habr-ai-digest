How AI Reviewers Work: Two Approaches

Before comparing tools, it's useful to understand what they actually do under the hood. There are two approaches to code review:

The first approach is diff analysis. The model receives only the diff itself and, at best, a few dozen lines around it. It's fast, cheap, and requires no infrastructure. However, the model doesn't know where a function is called from, nor that a neighboring module uses this constant differently. This leads to classic false positives, like "variable not used"—when it is used, just outside the window. Diff-only tools become noisier the more interconnected your codebase is. Unfortunately, the higher the architectural quality, the worse diff-only review works on top of it.

The second approach involves analyzing the codebase with indexing. Greptile, Devin Review, and similar tools provide the model not only with the diff but also with indexing results, allowing them to study the call graph, module interdependencies, and sometimes commit history.

And here, by the way, it's worth connecting the topic of review to agent architecture in general. In the "generator-evaluator" pattern (Anthropic describes it in their "Building Effective Agents" as evaluator-optimizer), the second LLM call evaluates the work of the first and decides if another round is needed. AI review is precisely this role, deployed in production. The reviewer is the evaluator link in the cycle where the code-generating agent acts as the generator. And when Anthropic released Managed Agents in April 2026—a hosted service for long-lived agents where the harness is virtualized into interfaces (session, harness, sandbox)—testing and verification stood alongside code writing among the standard applications.

The diff-only approach has one honest advantage—predictability. It cannot find what it doesn't see, but it will never invent a non-existent function call because it wasn't fed a graph.

Overview of Major Tools

I've selected a few well-known AI code reviewers, and I've used some of them regularly.

CodeRabbit

Link: coderabbit.ai

The most popular standalone reviewer. It integrates with GitHub, GitLab, and Azure DevOps. It performs line-by-line analysis of PRs with comments on specific lines. Each remark is accompanied by an explanation of why it's a problem and how to fix it.

Its main feature is learning from your reactions. If your team consistently rejects certain types of feedback (e.g., style suggestions), after a few PRs, it will stop issuing them. The noise decreases over time, unless, of course, you completely ignore it—then it will just keep flagging everything. There's a limitation: it only analyzes the diff and doesn't see the global context of the codebase. If you rename a function in one place, CodeRabbit won't check if the calls in other files have been updated.

From my experience, this tool is comfortable: in addition to bug fixes, it can generate docstrings and sometimes even tests through separate PRs.

It's free for open source, and for commercial projects, it starts at $12 per developer per month.

Devin Review

Link: devin.ai

A tool from Cognition Labs, the same team that created Devin AI.

Unlike CodeRabbit, it doesn't just look at changed lines but understands the logic of the changes. It groups modifications by meaning, not by file. Moved code is displayed as a move, not a bunch of deletions and insertions—this greatly simplifies the perception of large PRs.

Another feature is auto-correction. The tool can not only point out a problem but also generate a fix and then apply it to the branch.

Limitation: it's not a standalone product but part of the Devin ecosystem. You need to connect through the platform. It's suitable for teams with large PRs where diff noise consumes attention and reviewers are drowning in changes.

However, it is quite slow; it's not instantaneous analysis, and you have to wait a long time. But auto-correcting some found bugs simplifies life. It also generates prompts for AI agents to fix found bugs.

Qodo (formerly Codium)

Link: qodo.ai

Formerly CodiumAI. It differs from others in that it doesn't just review code but generates tests for the modified functions.

A second important feature is validating PRs against tasks in Jira or Azure DevOps. The tool checks that the code aligns with the stated intention and doesn't go beyond the scope of the task. If the task says "add a phone field to the profile," but the developer also changed the authorization logic—the reviewer will highlight this.

It's complex to set up—it can take several days to configure integrations and rules. It's expensive—$38 per developer per month. There is a free tier, but it's limited to 75 PRs per organization per month.

Greptile

Link: greptile.com

A tool that indexes the entire repository. It's an AI engine that answers complex questions about the codebase.

In Martian benchmarks, it consistently ranks high in F1 and F₀.₅. It's useful in legacy projects where no one remembers how everything is connected.

Unfortunately, it's difficult to set up, expensive, and not suitable for every project. But if you have a large, tangled codebase, it's one of the best options.

Sourcery

Link: sourcery.ai

A reviewer focused on refactoring. It often suggests simplifying code with tips like removing duplication, reducing nesting, or replacing loops with more readable constructs.

It works not only in PRs but also in IDEs—VS Code, JetBrains. You can get suggestions directly while writing code, without waiting for a PR.

However, it only analyzes the diff, without the context of the entire base. But for everyday code cleanliness, this is often sufficient. At $12 per developer, it's the cheapest paid option among competitors.

Claude Code Review (from Anthropic)

Link: claude.ai/code

Launched in March 2026. Its architecture is unusual in that multiple AI agents are launched for a single PR. One searches for logical errors, another for edge cases, and a third aggregates the results, removes duplicates, and ranks the feedback by importance.

In benchmarks, it often shows a very high F1 score among all tools. However, the cost is $15–25 per review. This is expensive for regular development but cheap if the cost of an error is high.

Documentation for Humans and Machines

The topic of documentation is rarely touched upon. And it shouldn't be—it's an important subject, as half of the harness consists of markdown files. The quality of review depends on the context you provide to the model—and this context lives not in the reviewer's settings but in the repository's documentation. Specifically, documentation written for machines.

The first tool here is AGENTS.md. A format that grew from a peripheral initiative (OpenAI introduced it in Codex back in 2025) into a de facto standard. By 2026, it's natively read by Claude Code, Codex, Cursor, Devin, and Copilot. The essence is simple—a markdown file at the root of the repo describing build commands, style conventions, project structure, and what not to do. A reviewer with AGENTS.md stops flagging your non-standard import order or custom linter as an "error." The skeleton is roughly like this:

# AGENTS.md

## Build & Test
- `pnpm build` — build; `pnpm test:unit` — unit tests

## Conventions
- Imports via `@/` alias, relative imports forbidden
- Wrap errors in `AppError`, never throw raw Error

## Do Not
- Do not edit files in `generated/`—they are generated by a script

There's also llms.txt (spec at llmstxt.org, idea from Answer.AI, September 2024)—a file at the root of the site with a table of contents for LLM documentation and links to key pages. The spec is alive and has been updated (v2—August 2026). llms.txt is the TOC, llms-full.txt is the entire content in one file.

And finally—tools that automatically make documentation machine-readable. For example, DeepWiki by Cognition. Replace github.com with deepwiki.com in the URL of any public repo—you get a generated wiki with architectural explanations that can be worked with. Context7 (Upstash) is an MCP server that provides the agent with up-to-date library documentation directly in its context—the model stops hallucinating APIs of new or recently updated libraries because the harness has provided it with fresh docs.

Now About Skills

Reviewing involves a whole class of procedural knowledge—how to check migrations for backward compatibility, how to find N+1 queries, how to distinguish safe type changes from breaking ones, how your security review response should look according to your standard. This knowledge is multi-step, with examples and file references—an ideal candidate for the skills format.

A skill is a folder with SKILL.md and optional resources, which the agent loads on demand. The mechanics of the format are clever and useful: at each step of the review, only a list of skills with short descriptions enters the agent's context, and the body of the skill is loaded when the model decides to invoke it.

For review, this opens up a specific trick. Suppose your reviewer agent consistently misses something—say, migrations that break old deployments. Create a skill db-migration-review:

---
name: db-migration-review
description: Checking migrations for backward compatibility during rolling deploys
---

1. Each migration must be deployable in two steps: first add a nullable column / backfill, then enforce. 
2. Forbidden: DROP COLUMN, NOT NULL without default, renaming in one step.
3. Compare with the checklist.

The model sees the description line in each review step and loads the checklist only when migration files actually appear in the diff.

Where AI Review Helps and Doesn't Help

Let's start with a trivial truth: automatic review is good where the task is formalizable. Code review has more such tasks than you might think.

Typos, forgotten imports, unused variables, stylistic drift from project conventions, dead code, or even outdated docstrings. A human might spend the first 15 minutes on this, then get tired, and miss the most crucial part—the actual bugs or logic errors. In the same category are basic security patterns: hardcoded secrets, SQL concatenation, eval on user input, lack of input validation. CodeRabbit, for example, has security review as a separate top-tier feature.

Another scenario is mass review of agent PRs. Here, the "agent reviews agent" scheme applies: a coder agent opens a PR, a reviewer agent (or a pair—remember Anthropic's multi-agent Code Review) looks at it first, and a human intervenes for arbitration on contentious issues. But yes, an arbiter is still needed; you can't let everything slide, or you'll end up with something that makes the tech lead eloquently explain the color of your code and your professionalism level.

However, AI review can significantly hinder progress. For example, business logic. A machine doesn't know that your discount calculation is intentionally ugly and convoluted—it's a three-year-old compromise with the sales department, documented in Slack, which the agent doesn't read. Also, an agent might not understand architectural decisions. Or the holy grail—technical debt and compromises. An agent sees bad code without understanding the history behind why it became that way. And there's the dialogue aspect, as part of review's value lies in the conversation where the reviewer and author agree on the intent, but the bot leaves comments with no one to discuss them with. All this doesn't disappear with the advent of new models.

Furthermore, the reviewer itself has become an attack surface. Especially if it has access to tools, the system, and anyone can ask questions and provide prompts. One hidden instruction in comments, and that's it—time for leaks. The instruction can be hidden in an HTML comment, in a base64 string in a test, in documentation text that the reviewer kindly reads in full, unlike a human.

And this is where the second class of attacks comes in—poisoned tool descriptions. Instructions within the descriptions of MCP tools are invisible to the user but visible to the model. An attacker whose tool is connected to your reviewer can make it behave however they want—up to exfiltrating data through a legitimate call to another tool. A reviewer with access to MCP servers, auto-corrections, and a commit-privileged token is precisely the "deadly trinity": untrusted input + tools + access to private data.

And remember, PR content is untrusted input. Always, without exception, including your own. Don't give the reviewer push rights; auto-correction should only be through a separate PR reviewed by a human; reviewer MCP tools should operate behind a trust boundary with minimal scopes; and if a tool can fix the found bug itself, this should be disabled by default.

Regarding responsibility—briefly, because it's awkward to even argue. The model doesn't sign the release, the model doesn't sit in court in a mask if your service leaks clients' data overnight. The merge button belongs to a human. If the process is structured such that the button is pressed automatically based on the bot's verdict—that's a human choice.

Conclusion

To summarize the article in a couple of points, we can understand that AI review solves the attention economy problem, and it also brings its own (truly: create a problem and sell a solution). Machines indeed remove the superficial layer for humans—the first line of defense, style disputes, basic security patterns, mass agent PRs. But the problem of review is broader, as review is a dialogue about intent, evaluation of compromises, and transfer of context between people.

Review has become more interesting than it used to be. Let neither side be deceived—neither the one expecting the bot to be a full replacement for a senior engineer, nor the one who still reads every diff with their own eyes.
