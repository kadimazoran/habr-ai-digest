What happens when you take a hundred-page clinical guideline and ask an LLM to turn it into an interactive disease model? At first glance, the task seems simple. In practice, it turned out to be much more complicated.

I am developing an application that transforms clinical recommendations into a structured representation of a disease: a pathogenesis graph, a knowledge graph of medical and biological entities, a timeline, several ways to visualize a set of knowledge, training materials, and a link from each statement to the original text.

The project is already in the final stage before release, so I want to talk not so much about the interface as about how I solve the problem of reliable structured generation of medical knowledge using LLM.

To avoid being unsubstantiated, I will provide examples using real data from clinical recommendations for obesity, which the Ministry of Health publishes via its open API Ministry of Health of Russia clinical recommendation or the document itself. Everything that follows in the article is the result of the application's pipeline processing this text.

First, I tried to do everything in one request

The first version was as simple as possible.

For small documents where the resulting graph fit into a dozen entities and relationships, this scheme worked stably; the model managed to fit the entire result into one response, and it was valid. But as soon as I moved to real clinical recommendations of hundreds of pages with dozens of pathogenesis stages, entities, and relationships between them, everything started to break down in several directions, and I will explain which ones next.

1. Result size. A knowledge graph can contain dozens of entities and dozens of relationships, and each entity and relationship has mandatory fields, including source information. As a result, the final JSON became very large and easily approached the model's response size limits.

2. JSON truncation. If the model truncated the response in the middle, we received not just incomplete text, but an invalid structured object. Asking the model to continue turned out to be not the best solution; continuation is already a separate generation, and the integrity of the result has to be restored additionally.

3. Entity and relationship desynchronization. A more interesting problem appeared within the graph itself: when the model simultaneously generates entities and relationships, it can create a new entity right during the construction of a relation. For example, there are entities E1, E2, E3, and among the relationships, E2 → E7 suddenly appears, and E7 is not defined anywhere. This is no longer a JSON format problem, but a problem of the graph's integrity itself.

4. Semantic hallucinations. And here's the most important part. LLMs have a vast amount of general medical knowledge, so the model can build a relationship that looks absolutely logical from a biological perspective but is not confirmed by the specific document. For a medical application, this is much more serious than a regular generation error.

Therefore, I divided the generation into stages

Instead of one large request, a pipeline was created where each stage is a separate model call with a separate, narrow task.

This is not a continuation of a single conversation with the model, but independent stages with a predefined input and output structure, each subsequent stage receiving the verified result of the previous one.

1. Graph — macro-level first

The first stage builds the pathogenesis structure of the disease stage, the sequence of processes, transitions, temporal dependencies, and clinically significant events. Here, the model does not try to build the entire knowledge graph simultaneously; its task is only to understand the disease development structure.

For example, for obesity, a chain of 13 stages is obtained:

  1. hereditary predisposition

  2. environmental and lifestyle factors

  3. energy imbalance

  4. disruptions in the gut-brain axis and microbiota

  5. changes in adipose tissue

  6. chronic inflammation of adipose tissue

  7. insulin resistance

  8. cardiometabolic risk factors

  9. clinical picture

  10. associated diseases and complications

  11. diagnosis

  12. treatment

  13. weight maintenance and dispensary observation

2. Entities — first, we fix the entity space

The next stage separately extracts entities, genes, proteins, hormones, cells, organs, biomarkers, medicinal substances, and physiological processes. Each entity is assigned a stable code, for example:

{ “code”: “E17”, “type”: “protein”, “name”: “…” }

After this, an important restriction appears: we first create a closed set of allowed entities, and only then allow the model to build relationships between them.

3. Relations — the model no longer creates nodes on the fly

During the relationship building stage, the model receives an already formed list of codes, for example, E1, E2, E3, E4. Relationships like E1 → E2 or E3 → E2 become permissible, but E1 → E9 will be rejected by the system if E9 is not in the entity list.

This seems like a simple restriction, but it significantly changes the task. The model no longer has to answer two questions simultaneously: what entities exist and what are the relationships between them. The first question is already answered in the previous stage; only the second remains. This reduces the space of permissible solutions before the next step.

4. Evidence — link to the original document

The existence of two entities does not yet prove that a relationship between them actually exists. Therefore, significant statements receive provenance — a link to the original text. For example:

{“entity”: “obesity_genes”,“name”: “Genes regulating body weight”,“quote”: “many genes have been identified that encode the function of various aspects of body weight and metabolism regulation”,“source”: { “section”: “1.2”, “paragraph”: 1, “sentence_start”: 3, “sentence_end”: 3 }}

As a result, the user can follow the chain: graph → statement → source → original text. This is one of the key parts of the system: the LLM should not become an independent source of medical truth; it is used only to extract and structure information from the original document.

Credibility and Importance are Not the Same (Confidence ≠ Importance)

I also distinguish between two characteristics that are easily confused.

Confidence — how directly the original text supports the statement.

Importance — how significant the information is for understanding the disease or clinical practice.

These are different axes, and one cannot be automatically derived from the other.

For example, in the text of the recommendation, oncological diseases are simply listed comma-separated among the complications of obesity — "DM 2, CVD, oncological diseases, osteoarthrosis, etc." without a separate analysis of the mechanism. The confidence is medium, but clinically, this is one of the most significant complications, with high importance (major).

And the role of brown adipose tissue thermogenesis is described in the text as a hypothesis, with low confidence (low), evidence type (hypothesis), and for the main pathogenetic chain, it is a secondary detail, with low importance (minor).

How evidence type (evidence_type) differs from evidence level (evidence_level).

These are two different fields, and they should not be confused.

Evidence type (evidence_type) — the model's own assessment of how the original text formulates the statement. Possible values are established fact (established), probable statement (probable), or hypothesis (hypothesis). The model determines this from the wording in the text, for example, "it is proven that..." gives established, and "it is assumed that..." gives hypothesis.

Evidence level (evidence_level) — this is not a model assessment, but the official evidence scale from the clinical recommendation itself, the Level of Evidence (LOE, from 1 to 5, where 1 is the strictest) and the Strength of Recommendation (SOR, from A to C). This scale is used by the Ministry of Health in all clinical recommendations, and doctors are well acquainted with it. It is already indicated in the original document for some statements, and the model simply extracts and transfers it to the data structure, without assessing anything itself.

So, if a statement has an evidence level (LOE 1, SOR A) — it means that the clinical recommendation itself classifies it as the most proven. And if the field is empty, it means the document author did not assign such an assessment to this particular statement, and we rely only on the evidence type (evidence_type) determined by the model from the text wording.

Validation, starting with regular code

Here, I deliberately did not try to solve everything with another LLM right away. The first level of validation is performed by regular code and checks JSON schema compliance, mandatory fields, ID uniqueness, correctness of from/to, absence of duplicates, and links only to existing entities.

That is, the system checks that:

E1 → E2 ✅

E1 → E7 ❌

if E7 does not exist.

This may seem obvious, but for structured generation, such checks are very important. And most importantly, they do not require a neural network at all. If an error can be reliably detected by regular code, there is no point in spending tokens on an LLM.

The next level — AI semantic verification

This is where what I am now ready to connect to the pipeline begins, but I am not yet presenting it as a fully completed part of the system. I already have separate prompts for checking two different classes of errors.

Checking stages (stages) and entities (entities)

Elements have a quote (quote) — a verbatim fragment from the source. AI checks:

  • whether the quote (quote) actually supports the description (description/summary/label);

  • whether the model has amplified the statement;

  • whether the evidence type (evidence_type) and confidence (confidence) match the strength of the quote;

  • whether the description contains details not present in the source.

For example, if the source says, "A is related to B," and the generation states: "A causes B." The source only records the relationship between A and B, without asserting causality, while the generation already attributes a cause-and-effect relationship to this link. This is no longer just a structural error, but a semantic amplification of the statement.

For such cases, the check should distinguish at least four statuses: supported (supported), overstated (overstated), unsupported (unsupported), and type_mismatch (type_mismatch).

At the same time, the AI receives an explicit restriction:

Do not infer what should be based on general medicine. Evaluate strictly the correspondence of the statement to the provided evidence (evidence).

This is fundamentally important. I do not want the checking model to start using its general medical knowledge as a source of truth itself.

Checking relations (relations)

For relations, there is now a different type of check. The model checks the internal consistency of fields: does the relation type (relation_type) match the textual name of the relation (relation_label), does the effect (effect) align with the relation type, do confidence (confidence), evidence type (evidence_type), evidence level (evidence_level), and importance (importance) contradict each other, and are there any obviously risky combinations.

For example, relation_type: associated_with together with relation_label: "causes" — this is a clear contradiction, or conversely, relation_type: causes together with relation_label: "is associated with" — also.

But there is an important limitation here. If a relation contains only a reference to the source, and not the source text itself, the AI cannot honestly confirm that the specific relation is actually present in the document. Therefore, I deliberately separate the check of internal consistency from the check of correspondence to the original text.

Next step — checking the relation along with the source text (relation + source text).

This is the next stage that I am connecting to the pipeline. The logic is as follows: relation → source reference → small fragment of the source text → AI verification.

Instead of sending the entire document of millions of tokens to the model again, the backend can retrieve only the necessary fragment and a few surrounding sentences. Then the model's task becomes much narrower: does this specific fragment support this specific statement and this specific type of relationship?

For example, if the relation states: "A causes B," and the source only says, "A is related to B," the check should determine that the source does not confirm causality. This is much closer to actual evidence verification, and this is precisely why I do not want to pretend that one LLM checking another LLM automatically solves the hallucination problem.

Why I don't consider LLM the ultimate source of truth.

I do not expect one model to be able to build a medical graph without errors. Therefore, the architecture is gradually moving towards this scheme:

And here another important layer appears: medical editorial review. The doctor must have the ability to change a relationship, delete an erroneous one, add a new one, change the relation type, correct an entity, and see the source of the change. As a result, AI becomes not a "source of truth," but a tool that significantly speeds up the creation of the first structured layer of knowledge, while professional verification remains with the specialist.

Why this is important at the scale of medical knowledge

If we look at a single disease, we can imagine the manual work of a doctor or a group of specialists. But when it comes to thousands of diseases, this approach becomes practically unfeasible. This is where generation can provide a different scale:

The doctor no longer starts from a blank canvas; they receive the first structured version that can be checked and edited. In the future, I see this as a professionally editable medical knowledge base, where AI accelerates the initial construction, and specialists gradually verify and improve the result.

One set of knowledge — several ways to study it.

A graph is not necessarily the best way to represent information for every task, so the same set of knowledge can be presented in different ways:

  • Graph — for exploring relationships between entities;

  • Path — for sequentially following a cause-and-effect chain: factor → mechanism → change → manifestation → complication;

  • Timeline — for understanding the development of a pathological process over time;

  • Blocks — for studying individual mechanisms and compact groups of information.

These are not four different datasets, but different projections of a single knowledge model.

What the user sees

The interface is built on React and React Flow. The user can explore the general graph.

Select a node and see related entities, open connection details, view evidence, go to the original text, and see the highlighted fragment on which the statement is based.

Generation proceeds in stages and displays progress via WebSocket. Instead of an infinite loading indicator, the user sees what exactly is happening within the pipeline.

Why generation takes so long

There is another engineering problem — cost. For one document, the full pipeline can process ~3.2 million tokens on average. Generation can take about 12-15 minutes, and the cost of one full build is currently about 150 ₽ (everything depends on the model and its pricing policy), even with caching and query optimization. Therefore, it is obvious that the full pipeline cannot be run (user opens disease → generation starts → 150 ₽) for every user.

Therefore, the generation result becomes a separate artifact

Instead, clinical recommendation → generation pipeline → versioned knowledge graph → cache → and from the cache, the result is distributed to multiple users. A result created once can be used as many times as needed. This also allows storing the version of the original clinical recommendation and the version of the graph built on its basis, and if the recommendation is updated, a new version can be built.

What I learned in the process

The main conclusion was not in a specific prompt; reliability here is achieved by architecture. Instead of a "document → LLM → huge JSON" chain, it becomes document → structure → entities → limited domain → relationships → evidence → code validation → AI semantic verification → doctor's verification.

Moreover, not all stages need to be performed by AI. If a problem can be solved by regular code, it's better to solve it with regular code. If semantic understanding is required, then it makes sense to use an LLM. And when it comes to a professional medical database, the final responsibility for content correctness should remain with the specialist.

This is precisely why I am not setting myself the goal of "how to make LLM absolutely error-free" — such a goal likely simply does not exist. It is much more realistic to build a system in which an error becomes detectable, verifiable, and correctable.

Conclusion

I do not consider LLM as medical truth. I consider it as one of the components of the pipeline: LLM extracts → system limits → code checks structure → AI checks semantics → doctor checks content.

As a result, the graph becomes not a replacement for clinical recommendations, but an interactive layer on top of them. The user can not only see that "the system believes that A is related to B," but also ask "why?" and go directly to the place in the original document on which this statement is based. And the doctor will be able, in the future, not only to use the ready-made graph but also to correct, supplement, and develop it.

This is exactly the model of interaction with medical knowledge that I am currently building in my application.
