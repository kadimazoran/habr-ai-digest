More than 7000 Claude Code sessions.

Some of them I create myself, some are launched by robots on a schedule, some are launched from my voice recordings (a separate session is created for each of my voice recordings).

At some point, the thread of control over all this began to be lost. I no longer understood what was happening on which computer and in which session.

This article is about how I selected and configured dashboards to control sessions, which ones I kept, and which ones didn't suit me. All figures are real (as they say, based on real events).

How it all started

In general, a Claude Code session lives its own life. Don't you have that? You open it, give it a task, and go to sleep. In the morning, there are 100-500 new lines in the sidebar, and it's unclear which ones are working, which ones are waiting for some decision from me, which ones seem to be done, and how much it all cost me.

When there are ten sessions, it's easy to keep in mind. When there are thousands - no chance.

1. The first dashboard shows what I have in general.

It collects transcripts from all machines and all accounts into one table with text search.

At the last snapshot, for example, there were 7451 sessions in the pool:

  • 3497 human (3009 mine, 263 and 224 by my colleagues);

  • 3954 service, i.e., launched by robots;

  • 6 machines, 5 accounts.

Each row has a "Continue" button that opens the corresponding old session. This is very useful for me: I can easily see what was done and easily find sessions by searching.

And it's very telling, it turns out that robots create more sessions than humans. I somehow thought it wasn't the case.

2. "Who creates sessions": the robot panel

I needed to figure out which robot created how many sessions. I created a separate dashboard for this task:

Result:

  • 20 robots on schedule;

  • 286 sessions created by them;

  • 262 of them (91%) were created by one robot: a test "dry run" of the inter-machine bus, which only wrote to the log every 25 minutes.

In general, I corrected the situation here.

3. "What's working now"

Not everything has to be an HTML page. Most often, I want to understand what's working right now, and this is easily solved with a command in the terminal that prints the finished text:

📟 СЕССИИ · NATALY-WIN-NB · 22:03
🟢 РАБОТАЮТ: 1
✅ ЗАКРЫЛОСЬ за 12ч: 0
🔴 ЖДУТ ТЕБЯ: 4
  1. 🔐 БРАУЗЕРНАЯ РЕЛЬСА КРАСНАЯ на узле ... - 10 дн
  ...
Ответ: + <id> = да · NO <id> = нет

4. Sessions where I need to respond or make a decision

A session that has stopped and is waiting for my "yes". Or "no". I used to overlook such sessions in the general mass.

But now I've set up a watchdog for myself that checks the sessions on its machine every 15 minutes and reports who is waiting and how many are waiting.

5. Background sessions

This is my favorite dashboard.

Each background session ends with a return code. Code 0 means "everything is fine".

However, code 0 is not actually indicative.

Example from a real panel:

Session "restore re-indexing timer" · 20 minutes · return code 0 · status done. Inside the log: You've hit your monthly spend limit.

That is, the session worked for twenty minutes, hit the limit, did nothing, but reported that everything was okay and done.

An example of how I check the status. At one snapshot of 34 background sessions:

  • 18 finished with results;

  • 8 still in progress;

  • 8 require attention

6. Daily ledger: what happened that day

Sometimes you need to answer the question "what did we do on October 1st". The robot collects data for each day from seven free sources: session transcripts, commits, retrospectives, decisions, commissioned research, posts.

The keyword is "free": the assembly is done without a single LLM token, with pure code. For example, for October 1st: 43 different sessions, 197 calls, of which 95 were robotic, 27 commits to the knowledge base, 28 retrospectives, 4 decisions.

7. Autonomy: how many questions were asked in vain

My sessions ask me questions via Telegram. I thought I needed to track not only how many of these questions there were, but also how many of them are no longer relevant, meaning no one has answered and the question has lost its meaning.

Example for 30 days:

  • 57 questions;

  • 40 are irrelevant, which is 70%;

  • within one week, 23 out of 23 became irrelevant.

42% of questions are cases where the session asked me about something it could have solved itself.

Questions about login and two-factor authentication become irrelevant in 100% of cases: I simply don't have time to respond in the session on time.

I have made changes to the rule: now the session decides everything itself, except for money, irreversible deletion, legal signatures, and secrets to third parties. I trust it more and more.

8. Subscriptions

I spend about $2000 a month on subscriptions to various LLMs. The logical question is: how much of this do I actually use. I now have a dashboard that collects information for each subscription, how much I paid and how much I used from that subscription.

9. System health

A separate task counts all assets: scripts, scheduler tasks, skills, databases, hooks, dashboards. At the last snapshot: 10,665 assets, 23 are not working correctly, 35 are disabled, 322 robots on schedule, overall score 98 out of 100.

10. Routine registry

This is less of a dashboard and more of an inventory: what routines are on each machine, which ones worked during the week, which ones are idle, which ones can be moved to one server.

11. Grouping by tasks

The robot sorts my sessions into task groups (job search, content, infrastructure, research) and puts an icon in the header.

Dashboards I've redone or deleted

First, I made "Session Health" on each machine. But then I combined them into one dashboard.

I made a dashboard about the "Agent Fleet" with a process counter. But I don't need it at all. Maybe for now.

General board of waiting sessions - very inconvenient. It's more convenient for each employee to look at their own, rather than picking out their sessions from one general dashboard.
