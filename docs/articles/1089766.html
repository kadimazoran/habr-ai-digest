"How many GPUs does it take to run a 70B model?" It seems like a simple division problem: just take the model size, divide by the memory of a single card, and round up. A service built with this calculation works perfectly for one tester. But then the first ten users arrive with large documents, and it grinds to a halt.

The model is just one occupant of the GPU memory. Alongside it lives the KV cache for each dialogue, which we'll discuss shortly. Outside the GPU, there's the network between cards and servers, the CPU that distributes requests, and the disks from which everything is loaded. And over the last two years, racks consuming over a hundred kilowatts and models with a trillion parameters, of which only a small part is active per token, have been added.

This is a rough estimate, as the inference engine and auxiliary buffers also consume memory. But the order of magnitude is immediately clear. The memory bandwidth will be useful a bit later when we get to response generation.

Now let's add users. To avoid re-reading the entire dialogue at each step, the model stores keys and values for each token already processed. This is the KV cache, and its size is calculated directly from the model configuration. Llama 3.1 70B has 80 layers, 8 heads for keys and values, and a head dimension of 128. Keys and values are stored separately, with each number taking 2 bytes. Multiplying this out: 2 × 80 × 8 × 128 × 2 bytes gives about 320 KB per token.

A third of a megabyte sounds harmless. But a single dialogue with a full context of 128,000 tokens takes about 43 GB. And ten users, each uploading a document of 32,000 tokens, will occupy about 107 GB, which is three-quarters of the size of the weights themselves.

The weights occupy a fixed amount of space, while the cache grows with each new dialogue. Under load, it's the cache that consumes memory. The GPU's compute units might be half-occupied, while new requests are already waiting in the queue.

Weights can be compressed. In FP8, the same 70B model will take about 70 GB, but you'll need to verify the quality after quantization for your specific tasks. You can use a smaller model. If neither of these options works, the model is split across multiple cards, and from that point on, the network becomes a factor.

One Response, Two Different Loads

While the user waits for a response, the GPU operates in two very different modes. First, there's prefill. The model reads the entire request at once and populates the KV cache. There's a lot of computation here, but it parallelizes well. Then, decode begins, and the model generates the response one token at a time. Each subsequent token depends on the previous one; the computation per step is small, but it requires reading all weights and the entire accumulated cache.

Therefore, the service can slow down in two ways. If the first word appears after ten seconds, look at the queue and prefill. If the first word arrives immediately, but the text crawls afterward, you're hitting decode limits and the memory bandwidth from the table above. MLCommons, in its tests, measures these latencies separately: TTFT (Time To First Token) and TPOT (Time Per Output Token).

The modes also interfere with each other. A new request with a long document arrives, its prefill consumes GPU time, and for everyone currently receiving a response, the text momentarily freezes. In large systems, prefill and decode are increasingly separated onto different GPUs, as NVIDIA Dynamo does. This comes at the cost of network bandwidth, as the KV cache needs to be transferred from one card to another.

Splitting the Model: Within and Between Servers

If the weights don't fit on a single card, the model is split. There are two main methods, and in real-world configurations, they are often combined. With tensor parallelism, each layer is split across multiple GPUs; each card computes its part of the matrix, and then they exchange results. With pipeline parallelism, cards are arranged in a pipeline: the first computes the initial layers, the second continues.

It's also possible that no splitting is needed. If the model fits on a single card, you can place a copy on each and distribute different requests to them. The entire service will handle more users, but the response time for a specific query won't improve.

Let's start with memory, as it usually runs out first.

Tensor parallelism is most dependent on the network: cards synchronize a couple of times per layer, and for a 70B model, this means over a hundred exchanges per token. Within a server, GPUs are connected via NVLink, and for the H100, this provides 900 GB/s total in both directions, or 450 GB/s in each. Between servers, data travels through network adapters. In a DGX H100, each GPU has its own 400 Gb/s InfiniBand adapter, which is about 50 GB/s in each direction. In equivalent units, the difference is about ninefold.

In real-world operation, speeds are usually lower than in specifications. DeepSeek, in its V3 report, indicates 160 GB/s over NVLink versus 50 GB/s over InfiniBand for its H800 cluster, and according to the developers, this is a measurement in one direction. The NVLink on the H800 is also limited, so the gap is about threefold.

With new generations, the gap hasn't closed. For Rubin, NVLink 6 provides 3.6 TB/s per GPU in both directions, meaning 1.8 TB/s in each. The ConnectX-9 network adapter is rated at 1.6 Tb/s, which is 200 GB/s. Again, about a ninefold difference.

NVIDIA took a different approach starting with the Blackwell generation. Instead of boosting the network to match NVLink, it extended NVLink across the entire rack. In the GB200 NVL72, and now in the Vera Rubin NVL72, seventy-two GPUs are interconnected just like eight cards within a standard server. The boundary where the slow network begins has moved from 8 cards to 72. We believe this is the most significant hardware change in the last couple of years, more important than the increase in teraflops. A model that previously required nine servers and slow inter-server networking now resides entirely within a single rack.

It's worth keeping this in mind, especially if you rent GPUs in the cloud. When you rent a card, you're also renting its place in someone else's topology. Two H100s in the same server with NVLink and two H100s in different servers behave differently, even if the pricing might look the same. The network between nodes can also vary: besides InfiniBand, Ethernet with RDMA (RoCE) is used; Meta, for example, trained Llama 3 405B on such a network. Before renting for a distributed model, ask your provider how the cards are connected within a node and what connects the nodes.

MoE: Memory of a Giant, Computation of a Middleweight

While we were calculating a dense 70B model, many large open-source models have switched to Mixture of Experts (MoE). Inside such a model are many "experts," individual blocks, and only some of them are activated per token. DeepSeek-V3 has 671 billion parameters, of which 37 billion are active per token. And in MLPerf Inference 6.1, Lambda, in the open category, launched Kimi K2.6, an MoE model with a trillion parameters.

This presents an unpleasant asymmetry for the infrastructure. Computation is required as if for a 37B model, but all 671B parameters must be stored because it's unknown in advance which expert will be needed for the next token. Experts are distributed across different GPUs (this is called expert parallelism), and each token is sent to where its required expert resides. Communication is constant and follows an "all-to-all" pattern, so the network again comes to the forefront. With MoE, a single number in the model name is no longer sufficient. The total number of parameters indicates the memory required, while the number of active parameters indicates how quickly the model will respond. We would always specify both.

In their V3 report, DeepSeek describes their operational configuration. For processing incoming requests (prefill), a minimum of 4 nodes and 32 GPUs are needed; for generating responses, 40 nodes and 320 GPUs. The weights themselves, in FP8, fit even in a single server with eight H200s, but for user traffic, DeepSeek deploys the model like this.

Why Does a Server with GPUs Need a CPU, RAM, and NVMe?

It's easiest to analyze this using the DGX H100 as an example, because NVIDIA publishes its full specifications. Besides eight GPUs, it has two 56-core Xeons, 2 TB of RAM, and eight 3.84 TB NVMe drives for data cache. The RAM is more than three times the video memory, and the disks hold nearly 31 TB.

The CPU performs tasks without which the accelerators would be idle. It receives requests, tokenizes text, manages the queue, and feeds data to the GPUs. If the CPU can't keep up, the GPUs will appear underutilized in monitoring tools, leading to the mistaken conclusion that there's excess capacity.

Disks are needed at startup to load weights into video memory. 140 GB is a significant amount, and the more frequently the service switches models, the more often a cold start occurs. However, in the last year or two, RAM and NVMe have found more important work: they store the KV cache that doesn't fit into video memory.

Imagine a user returning to a dialogue after ten minutes. Or a hundred people asking questions about the same long document. Recalculating the cache means re-running prefill, and it's simpler to retrieve the ready-made cache from a lower tier. NVIDIA Dynamo can offload it from video memory to RAM, and from there to local disk. At CES 2026, NVIDIA showcased a dedicated storage platform for such cache using NVMe with BlueField-4 DPUs, with shipments promised for the second half of 2026.
