If you read Ethics.Dev, you’ve surely noticed how many stories there are lately about AI agents encountering cybersecurity. Some sound like movie scripts: agents breaking out of test environments, negotiating over channels no one intended them to use, finding vulnerabilities, stealing credentials, and reaching production.

But, in my opinion, the less glamorous part deserves more attention: AI is changing the economics of attack. A human attacker has limited time and attention. An agent, however, can explore thousands of paths, try multiple options in parallel, lose almost nothing on failures, and move on. In one recent corporate network breach, work that would have taken humans about two weeks was compressed into less than ten hours. And during the Hugging Face incident investigation, analysts recovered about 17,600 agent actions in four and a half days.

Because of this, the very idea of what constitutes "good enough" defense is changing, and that’s why I’m so concerned about what frontier models will do to cybersecurity. Below are the takeaways I would put on the table for corporate AI and security teams.

1. Prepare for an attacker who can afford to make mistakes

The weak points exploited in recent incidents were, for the most part, the most mundane: accounts with excessive privileges, internal systems unnecessarily exposed externally, and common misconfigurations.

Persistence has changed. At Hugging Face, they counted about 17,600 actions. Most attempts led nowhere, but that hardly mattered. The agent tried path after path, abandoned failed ones, switched channels when blocked, and returned to old leads until a working attack chain was formed from common weaknesses.

I would reconsider all assumptions that silently count on resources being hard to find or that an attacker will get bored. From a program that methodically probes everything it can reach, the obscurity of an internal endpoint offers almost no protection.

2. Measure how long containment actually takes

Security teams typically measure whether they can detect an intrusion. I would add another metric: how long it takes from detection to containment.

Recent examples show the scale of these timelines. In the aforementioned corporate breach, two weeks of work were completed in less than ten hours. And at Google, they observed another group go from a compromised cloud resource to a mass credential harvesting campaign in less than six hours.

Moreover, not only technology but also the organization itself can cause delays. At Hugging Face, security systems were signaling, but escalation was too slow. If revoking credentials requires three approvals and a meeting, you can understand perfectly what's happening and still not react in time.

A couple of years ago, I wrote about responding to AI incidents, and one of the main recommendations there was to think through containment options before something happens. With agent attacks, this advice has become even more relevant. Determine in advance which containment measures are automated and which the security team can apply without separate approval.

3. Protect the harness, not just the model

I recently argued that the model and its harness should be evaluated as a single system. Cybersecurity data adds weight to this argument.

The harness is everything around the model: tools, memory, credentials, network access, execution environments, and policies. In tests where AI models played the role of attackers, researchers saw that the model's ultimate achievements depend heavily on the harness. The Australian Cyber Security Centre recently came to the same conclusion from a defense perspective: they don't control the development of the model itself, but they do control the harness.

Try a simple exercise. Forget for a moment what model is involved, and list everything the agent can see and invoke, where it can write, and what it can spend money on. Then ask yourself: if the agent behaves badly tomorrow, what's the worst this harness will allow it to do?

4. Prepare for agent swarms

One of the strangest lessons from the Hugging Face incident: agents can find ways to act collaboratively, even if no one programmed it. There, hundreds of agents exchanged information and devised their own communication methods between runs that were supposed to be isolated from each other.

A group of agents can divide labor, share findings, and continue working on a task when individual attempts have already failed. Shared folders, databases, message queues, and other resources with write access can become communication channels you never intended.

I don't think any group of agents will behave this way. But if you're running many agents, consider communication between them as another permission that also needs to be controlled and monitored.

5. Stop giving agents persistent credentials

I've written before that agents should be treated as separate machine accounts. Now it's clearer how to do this in practice.

Each agent should have its own identity, separate from user credentials. Issue credentials with narrow privileges that expire along with the task. Separate read and write permissions. Don't keep static cloud keys in the agent's environment. And ensure that any sub-agent can be traced back to its parent agent and the human behind it.

This is the same principle of least privilege, just applied to software that can actively explore its environment.

And the difference is significant. A human might never realize that an old credential opens up some forgotten system. An agent will search for such things methodically.

6. Assume prompt injection will eventually work

Prompt injection is instructions that an attacker feeds into what the agent reads. I would assume that sometimes the agent will execute them.

Then the question itself changes. Instead of "can malicious instructions leak through," ask "what happens when they leak through?"

A programmer agent reads code comments and config files. A security agent reads logs, hostnames, vulnerability reports, and payloads generated by an attacker. Text written specifically for the model could appear in any of these places. Therefore, even a deceived agent must be constrained by strict limitations on credentials, network access, tools, and the right to make significant changes.

7. Keep the security boundary outside the model

Among the rules for production agents I recently formulated was: keep strict limitations in the code, not in prompts. After the latest incidents, this distinction should be treated even more rigorously.

A prompt like "don't go to production" is just a wish. Control is achieved when the agent's API simply lacks the permissions to reach production.

If an action can have serious consequences, let the model suggest it, but let another part of the system decide whether to actually execute it. The same applies to audit logs. If an agent can alter the records by which its behavior will later be analyzed, consider your audit trail non-existent.

8. Defend against agents with agents

The symmetry is uncomfortable. Attackers use AI because it provides speed and scale. Defenders, it seems, will have to do the same.

An incident involving tens of thousands of machine actions leaves so many traces that a human team cannot review them properly in real-time. Tools like Graphistry help analysts find connections in large volumes of security data. This is useful, but Security Operations Centers (SOCs) will increasingly need their own agents to analyze alerts, hunt for threats, investigate incidents, and assist with containment.

However, such agents have their own risks. They constantly read data that attackers might have forged, and they often receive unusually broad privileges. Prompt injection can redirect their work, and they won't need to steal any credentials to do so. Therefore, defensive agents need tightly controlled harnesses and access strictly limited to what they absolutely need.

We need to keep pace with attackers using AI without creating a new security problem for ourselves along the way.
