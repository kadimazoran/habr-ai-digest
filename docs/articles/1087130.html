How to Find the Cause of AI Feature Errors and Test Them Using a Test Oracle

When a language model-based function doesn't have a single correct answer, traditional 'expected = actual result' checks stop working. Testers need to determine which response properties are truly important, how to distinguish acceptable variability from errors, and how to build a clear pass/fail criterion. This article uses a customer support ticket summarization function as an example to explain how to form a behavior contract, a set of checks, and an approach to regression testing AI features.

Suppose a CRM system gets a new button: “Summarize Ticket.” It sends the correspondence to a language model and returns a short text for the next operator. QA needs to test the function before release, but the first scenario immediately raises a question: what should be entered in the expected result?

Let’s take a training dialogue. All the answers below are for illustrative purposes and are not the results of experiments with a specific model.

Client: Order 4812 was supposed to arrive on September 12th, but today is the 15th, and it's still not here. I don't want to wait anymore, give me a refund.
Operator: I will forward the request to my colleagues.

First summary option:

Client reports a delay with order #4812 and requests a refund. The operator promised to forward the request to colleagues.

Second option:

According to the client, order 4812 has not been delivered on time. The client is no longer willing to wait and is requesting a refund; the operator stated they would forward the issue to colleagues.

Third option:

Client reports a delay with order #4812. Refund approved, operator forwarded the request to colleagues.

The first two texts are acceptable. The third one introduces two changes: the request has turned into an approved refund, and the operator's promise into a completed action. For the next employee, this is a different situation, even though the summary looks convincing.

Let's explore how to describe the expected behavior of such a function and obtain an understandable pass/fail decision.

1. First, let's agree on what the summary should preserve

The requirement “briefly and correctly retell the conversation” leaves too many questions. Are dates mandatory? Should the operator's promise be preserved? Is it acceptable to write “order delayed” if the only source of this information is the client?

For our example, let's fix the conditions. The function receives only the correspondence, without access to orders or payments. It returns a single non-empty paragraph up to 500 characters long, including spaces. The next operator should understand which order is being discussed, what happened according to the participants, what the client wants now, and what the operator did or promised. Dates can be omitted if the problem remains clear. These are the chosen requirements for the training product, not universal summarization rules.

The dialogue is the source of truth here. The system can convey the client's words but cannot confirm delivery or payment in the external world. If the order number is not specified, it cannot be invented. If participants contradict each other and the contradiction is not resolved, it must be preserved. An explicit correction of one's own remark is considered a correction: “not 4812, but 4813” sets the current number as 4813.

This is how a behavior contract emerges: a set of properties that any acceptable response must meet. The method for determining if the contract is met is called a test oracle in testing. It can be a combination of assertions, i.e., programmatic checks, and evaluation against specified criteria.

The paper CheckList: Beyond Accuracy proposes checking individual NLP model capabilities through specially designed tests. There is no ready-made contract for CRM there; we use the principle of checking specific behaviors.

2. Let's separate form and meaning checks

Comparing the entire response to a single string would reject the second correct option. The presence of the word “refund” also proves little: it appears in both the request and the approval notification. Therefore, each requirement needs a suitable verification method.

Meaning check

Meaning checks start with a rubric: explicit rules by which a human or an automated evaluator makes a decision. For our summary, two mandatory criteria are sufficient.

Factuality: Every factual statement is supported by the correspondence; the author of the message, negations, and action status are preserved. A promise is not considered fulfillment, and a request is not considered a decision. If at least one statement violates this rule, the criterion receives a fail.

Completeness: The order number, the client's problem, their current request, and the operator's action or commitment are preserved, if such information is present in the input. Omitting any of these means fail. Greetings, repetitions, and dates from our example are optional.

These criteria are checked separately. “Client contacted about order 4812” might be factual but not complete. A detailed retelling with a fabricated refund approval might preserve all necessary topics but violate factuality. A high score for completeness should not compensate for a false fact.

Separate tracking of properties aligns with the multidimensional evaluation in HELM. The product team determines the criteria themselves and their criticality.

3. Let's write the contract into a test case and check it against responses

Let's write our own test case schema. This is not a framework configuration: textual criteria still need to be implemented in the evaluator.

id: delayed_order_refund
input: |
  Клиент: Заказ 4812 должен был приехать 12 сентября,
  сегодня уже 15-е, а его нет. Больше ждать не хочу,
  верните деньги.
  Оператор: Передам запрос коллегам.
must_preserve:
  - Номер заказа 4812.
  - По словам клиента, заказ не доставлен в срок.
  - Клиент больше не хочет ждать и просит возврат.
  - Оператор обещал передать запрос коллегам.
must_not_claim:
  - Возврат одобрен или деньги уже перечислены.
  - Запрос уже передан коллегам.
  - Известны сумма или срок возврата.
format:
  type: string
  min_chars: 1
  max_chars: 500
  single_paragraph: true
quality_criteria:
  factuality: Каждое утверждение поддерживается диалогом.
  completeness: Сохранены все пункты must_preserve.
critical_failures:
  - Выдуманный или искажённый факт.
  - Подмена номера заказа.
  - Потеря актуальной просьбы клиента.

The must_not_claim list highlights known risks but does not list all possible fabrications. The phrase “courier lost the package” should also fail the factuality check, even though it's not in the list.

The validator below measures length using Python's len. In the production product, the counting method needs to be agreed upon with the CRM's limitations.

import re

def check_basic_constraints(text):
    if not isinstance(text, str):
        return {"type": False}
    return {
        "nonempty": bool(text.strip()),
        "length": 1 <= len(text) <= 500,
        "single_paragraph": "\n" not in text and "\r" not in text,
        "order_id_present": bool(re.search(r"\b4812\b", text)),
    }

The code will pass the third response: the presence of the ID does not confirm the summary's correctness. The separation of string, programmatic, and model checks can also be found in OpenAI Graders; here, we are not tied to the API.

According to the rubric, the first two responses pass all checks. The third receives a fail for the approved refund and completed request forwarding. The response's final result is pass only if all mandatory checks are met.

Test the oracle itself: in a correct response, change the number, remove the request, and change “promised to forward” to “forwarded.” Add a correct rephrasing. The test should reject defects and accept acceptable text modifications.

4. Let's gather a set of scenarios from one dialogue

We need to vary not only the wording but also the conditions that determine the correct answer.

Expectations change with the input. Removing the ID cancels the check for 4812. The prohibition of “refund approved” applies to the original case: if the operator reported approval, it is acceptable content with the source indicated.

For an empty dialogue and correspondence without ticket information, we will set a separate branch: “Insufficient data for ticket summary.” The requirements to preserve the order and request do not apply here. The summarizer does not communicate with the client, so a clarifying question is inappropriate here.

Supplement the set with anonymized tickets and real defects. Test long context within the allowed size, especially corrections at the end. Consider the results of simple tickets and complex cases separately, so that successes on the former do not hide problems on the latter.

5. Let's use an LLM judge when manual evaluation becomes too expensive

LLM-as-a-Judge is an evaluation of a language model's response. The judge is given the original dialogue, the summary, and the rubric: an instruction like “evaluate quality from 1 to 10” does not define what constitutes an error.

For each violation, the judge should return a fragment of the summary and its basis in the dialogue, or note the absence of such a basis. A human can verify the verdict, although the model's explanation may also be erroneous.

First, prepare pairs of “dialogue — response” with human annotation: correct rephrasings, omissions, fabrications, and borderline formulations. Have two specialists independently evaluate disputed cases, then agree on a decision. If humans disagree, the rubric may need clarification. Train the judge on one part of the examples and test on another.

Comparison with human annotation is described in Google: Evaluate a judge model. Separately count missed defects: how many erroneous responses according to human annotation the judge accepted. Overall agreement on predominantly good responses can hide this problem.

An indeterminate verdict or an evaluator error leaves the check incomplete, rather than turning it into a pass. Pass disputed cases to a human. Save the judge version and rubric; after they are changed, re-evaluate old and new responses equally, otherwise, a change in the evaluator might be mistaken for a change in the function.

6. Let's repeat runs and set a regression rule

A single successful response shows the result of only that run: with the same input, a generative function may respond differently. OpenAI's recommendations suggest building an evaluation around a specific task, dataset, criteria, and version comparison.

Record the inputs, prompt, model ID, available generation parameters, and response processing. The baseline, the original version of the function, undergoes the same set of tests and checks as the candidate. Change what you want to evaluate; keep other conditions the same.

For the first diagnostic run, you can execute each case five times. This is a chosen budget, not a justified minimum. If one response fabricated a refund approval, we record 4/5 pass; 1 critical defect. We do not restart it until it succeeds, erasing the previous result.

Pass rate is the proportion of successful runs among those planned for a selected group. Here, 80% is the observed proportion on one case, not an established probability of success in operation. Repeats help detect variability; assessing rare errors requires a different volume and a well-thought-out sample composition.

Compare versions by cases and error categories. An increase in the overall proportion of successful responses does not compensate for a new substitution of a promise with a completed action. Errors in receiving a response and incomplete evaluations should be considered separately, keeping their count: silent exclusion of such runs distorts the report.

Set the release rule in advance. For our product, we will adopt: a confirmed critical defect blocks release; other mandatory violations and regressions compared to the baseline require analysis; incomplete checks must be completed. A threshold of “95% is enough” does not justify anything on its own: acceptable risk depends on the cost of error.

The result includes the contract, the set of inputs, the responses from each run, and decisions on individual violations. To transfer the approach to a project, follow the sequence: requirements → observed behavior → programmatic constraints → semantic rubric → set of scenarios → repeated runs → regression criteria.

This approach is convenient when the response can be verified against the source material. It does not prove the truthfulness of the source itself; access, performance, and actions in external systems will require separate checks. Start with one ticket, two acceptable summaries, and one erroneous one. If the team cannot consistently explain decisions on them, clarify the contract first.
