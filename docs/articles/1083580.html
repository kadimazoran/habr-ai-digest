A phone isn't always suitable for quick notes. You have to take it out, unlock it, open an app, and type something. It's especially inconvenient when you're busy with another task and don't want to switch context entirely.

That's why I started looking at what's available on the market for creating voice notes that automatically turn into text. The main criteria were high-quality Russian speech recognition and the ability to wear the device on my wrist. I bought PLAUD and quickly realized that the gadget itself only solves half the problem.

I can press a button and say:

Work. On Monday at 3 PM, check Exchange backups, remind me an hour before.

PLAUD will save the recording and create the text just fine.

But then I still have to open the app, find the right recording, read it, and manually create a task in Microsoft To Do. This means instead of one action, I still get several.

I wanted something different:

press button → say thought → forget → task automatically appears in To Do with category, deadline, and reminder.

As a result, I assembled a small system on a Raspberry Pi Zero 2 W.

What you'll find in the article

Using my system as an example, I'll show you:

  • How to extract deadlines, reminders, and task categories from spoken language.

The First Version Turned Out Too Expensive

Initially, I made the most obvious option.

Codex itself accessed PLAUD via the connected MCP and executed a request like:

List my recent Plaud recordings

It worked perfectly. I sent a request — the agent got the recordings and returned the result.

But then I looked at the token consumption.

One very simple request:

list my recent Plaud recordings

consumed:

16 901 tokens

Even though the final result consisted of literally a few recording titles.

The reason is quite obvious: not only my prompt was passed to the agent.

The context included:

  • Codex system instructions;

  • descriptions of available tools;

  • MCP tools;

  • the list_files call;

  • the PLAUD response;

  • agent context;

  • the final response.

This is fine for manual work.

But running such a construct every 5 minutes is already a questionable idea.

288 runs per day just to check if a new recording has appeared.

Main Architectural Change

After this, I divided the system into two parts.

All mechanical operations are performed by regular Python:

get list of PLAUD recordings
↓
compare IDs with SQLite
↓
get only new transcriptions
↓
save them

And the LLM is used only where text meaning is truly needed.

That is, now:

Python → PLAUD
Python → SQLite
           ↓ only new texts
          Codex

If there are no new recordings:

Codex is not launched at all.

This turned out to be an important architectural decision for the project.

Getting Recordings from PLAUD Without Codex

PLAUD MCP provides several useful methods:

list_files
get_file
get_note
get_transcript

First, Python calls:

list_files

and gets something like:

{
  "id": "of_...",
  "name": "2026-09-16 13:44:54",
  "created_at": "2026-09-16T10:44:54",
  "duration": 8000
}

The key field here is id.

It's perfect for deduplication.

If such an ID doesn't exist in SQLite yet, the Raspberry gets the transcription:

get_transcript(
    file_id,
    block="transaction_polish"
)

I prefer transaction_polish because PLAUD already cleans up the recognized speech a bit.

If the polished version is not available, you can use the regular one:

transaction

The Raspberry doesn't download the audio itself at all.

SQLite as a Small State Machine

For this kind of automation, it turned out to be very convenient not to try to do everything in one huge script.

Each recording has a state.

The main chain:

waiting_transcript
        ↓
pending_ai
        ↓
ready_todo
        ↓
synced

There are also terminal states:

done
note
question
ignored

For example, a recording:

Work. Create a test task for integrating PLAUD and Codex.

gets the state:

pending_ai

after classification:

ready_todo

after successful Microsoft Graph POST:

synced

And the phrase:

Report. Ordered cables, they've all arrived.

can be classified as:

done

and will be added to Microsoft To Do as already completed — this will be useful in future work reports.

The Most Unexpected Part — Categories

I quickly got used to starting notes with a keyword:

Work.
Hobby.
Personal.
Health.

And I started using the first word as a Microsoft To Do category.

For example:

Health. Go to the dentist.

becomes:

Health: Go to the dentist

and the task gets a real Microsoft category:

Health

In Microsoft Graph, this looks something like this:

"categories": [
  "Health"
]

And Then Speech Recognition Intervened

Of course, STT doesn't always hear a word the same way.

I got variations like:

Health
To health
Zdrovye (misspelling)
Zdarova (slang/misspelling)

If you create a category from the first word, after a while, Microsoft will have:

Health
To health
Zdrovye
Zdarova

which would quickly turn into a mess.

Therefore, I added normalization.

Important: it applies only to the first word.

The rest of the task is never touched by fuzzy matching.

Exact → Alias → Fuzzy

The algorithm is as follows:

first word
    ↓
exact match
    ↓
alias
    ↓
fuzzy match
    ↓
new category

For example:

Health
→ exact
→ Health
To health
→ alias
→ Health
Zdrovye
→ alias/fuzzy
→ Health
Khobiy (misspelling)
→ fuzzy
→ Hobby

How to Distinguish a New Category from a Regular First Word

There's another problem: the first word in a voice note doesn't always mean a category.

Suppose a recording:

Go to the doctor.

The first word is Go.

Obviously, you don't want to create a category Go.

So the rule is now as follows.

If there's an explicit separator, a period or comma — meaning you said the first word and paused slightly, resulting in a transcription like this:

Car. Buy antifreeze.

Here, the word Car will be a new category that is automatically created.

Result in To Do:

Car: Buy antifreeze

If there's no separator:

Car buy antifreeze.

the system first looks for Car among existing categories.

If such a category doesn't exist — the task is still created, but without a category.

That is:

Go to the doctor
→ regular task
→ category=None

This significantly reduces the number of false categories.

Microsoft Graph

For integration, standard Microsoft Graph with delegated permissions is used.

The main permission:

Tasks.ReadWrite

To manage Outlook master categories, the following was needed:

MailboxSettings.ReadWrite

Authorization is done via Device Code Flow.

The Raspberry stores the MSAL token cache, so you don't need to re-enter your password with every launch.

A client secret is not required for this scenario.

Fault Tolerance

I specifically avoided doing:

get PLAUD recording
↓
call AI immediately
↓
POST to Microsoft immediately

The problem with this approach is that with any error, it becomes unclear at which stage everything stopped.

For example, the recording was already processed by AI, but Microsoft Graph returned an error. Or the task was created, but the system crashed before it could save the result.

Therefore, SQLite was placed between all stages. This allows you to calmly handle:

  • lack of internet;

  • temporary PLAUD error;

  • exhausted Codex limit;

  • Microsoft Graph error;

  • Raspberry reboot;

  • unfinished transcript.

If the AI is temporarily unavailable, the recording simply remains in the state:

pending_ai

If Microsoft Graph doesn't respond:

ready_todo

As a result, an error at one of the stages does not mean the loss of the recording: it remains in the database and can be processed on the next run. The database itself will also be useful — for example, you can build your own interface on top of it with search, filters, and history viewing.

Deduplication

The main key:

PLAUD recording_id

In SQLite, this is the PRIMARY KEY.

Additionally, after successfully creating a Microsoft task, the following is saved:

todo_id

Therefore, a repeated pipeline run should not create another identical task.

Automatic Launch

A small shell script is responsible for orchestration:

run_pipeline.sh

It performs:

1. ingest_plaud.py

2. SELECT COUNT(*) 
   WHERE status='pending_ai'

3. If count > 0:
      classify.py
   else:
      Codex NOT launched

4. SELECT COUNT(*)
   WHERE status='ready_todo'

5. If count > 0:
      sync_todo.py

This is a rather important point.

Every 5 minutes:

PLAUD list_files

But AI is called only when there are actually new notes.

systemd

The service is a standard oneshot.

Timer:

[Timer]
OnCalendar=*:0/5
Persistent=true
AccuracySec=30s

This means the launch occurs at:

05
10
15
20
...

of every hour.

What's on the Raspberry

The structure is roughly like this:

/opt/plaud-todo/
├── .venv/
├── config/
│   ├── plaud-todo.env
│   └── msal_cache.json
│
├── data/
│   ├── state.db
│   └── pipeline.lock
│
└── scripts/
    ├── ingest_plaud.py
    ├── classify.py
    ├── sync_todo.py
    └── run_pipeline.sh

.venv/ — Project's Python environment.
Contains the interpreter and libraries for working with PLAUD MCP, Microsoft Graph, and Microsoft authorization. Scripts are run via Python from this environment.

config/plaud-todo.env — Integration settings.
Specifies the registered Microsoft application ID, the To Do list name, and the time zone for deadlines and reminders.

config/msal_cache.json — Microsoft authorization cache.
Used by the MSAL library to obtain tokens without manual login on each run. Created during initial authorization and updated as the system runs. Contains sensitive data.

data/state.db — SQLite state database.
Stores PLAUD recordings, transcripts, classification results, categories, errors, and created task IDs. Statuses indicate the stage of each recording: awaiting transcript, classification, sending, or already processed. It also stores a checkpoint for detecting new recordings.

data/pipeline.lock — Lock file.
Used by the flock command to prevent two pipeline runs from executing simultaneously. Created automatically. The lock is held by the running process.

scripts/ingest_plaud.py — Getting recordings from PLAUD.
Accesses PLAUD MCP, finds new recordings, and retrieves their transcripts. First requests the processed text, and if necessary, the original. Saves data to SQLite and transitions ready recordings to pending_ai. Does not download audio files.

scripts/classify.py — Semantic analysis of notes.
Takes up to 20 pending recordings from SQLite and sends their texts to Codex. The model determines the recording type, formulates the task title, extracts the date, time, and reminder. The script checks the JSON response and saves the result. Task-type recordings get the status ready_todo.

scripts/sync_todo.py — Creating tasks in Microsoft To Do.
Reads the processed results, determines the category from the first word of the transcript, and normalizes it using exact matches, aliases, and fuzzy matching. If necessary, it creates a Microsoft category, adds it to the title, and sends the task via Graph. After successful creation, it saves the todo_id and the synced status.

scripts/run_pipeline.sh — Overall launch script.
Acquires a lock and sequentially runs recording retrieval, classification, and synchronization. Before classification, it checks for pending_ai: if the queue is empty, Codex is not launched. Similarly, the sender is launched only if there are ready tasks.

PLAUD MCP and Codex CLI authorization is stored separately in the user's home directory, from which the service runs. Scheduled execution is provided by plaud-todo.service and plaud-todo.timer in /etc/systemd/system/. During classification, a tmp/ directory is also created for Codex's temporary JSON response.

Codex also does not run as root.

Task Analysis: Weekly Reports

This combination has another application: tasks can be used to prepare short reports.

Over the week, Microsoft To Do accumulates a history: what was planned, what was completed, what remains pending. If this data is passed to Codex or ChatGPT — via a connected tool or a regular export — you can get a ready digest.

For example, ask:

Summarize my work tasks for the week: what's completed, what's in progress, and what's planned next. Group by topic, remove duplicates. Separately highlight blockers, if they are specified in the notes. Prepare a short version for the daily stand-up that can be told in a minute.

For the daily stand-up, it's enough to change the period: what was done yesterday, what I plan to do today, and where help is needed. For the weekly report — to get an overall picture of the projects.

Here, the fact that the original transcription is saved in the tasks comes in handy. A short title might be "Check backups," while the notes will contain details: which server, what exactly to check, and why.

For this, during the testing phase, I set up a local MCP server on my PC for Codex to interact with Microsoft To Do, based on the @mag-cie/mcp-microsoft-todo package. Through it, Codex gets tasks directly, so you can ask in the chat to analyze completed tasks, compile a weekly digest, or prepare a short summary for the daily stand-up. In the future, I plan to move this functionality to Raspberry Pi, creating automatic reports in OneNote.

What Went Wrong: Authentication

On paper, the scheme looked simple: authorize PLAUD, authorize Codex, get a Microsoft Graph token — and you can start writing the integration. In practice, authentication was one of the unpleasant moments of the project, mainly because the Raspberry Pi works headless, and the OAuth flows of different services assume a browser on the same machine.

PLAUD OAuth and localhost, which turned out to be the wrong localhost

PLAUD MCP was installed with the command:

npx -y @plaud-ai/mcp@latest install

The installer found the Codex configuration:

Codex Desktop /home/one/.codex/config.toml

and started OAuth.

The problem appeared at the callback. PLAUD used the address:

http://localhost:8199/auth/callback

But my browser was open on Windows, and the OAuth listener itself was running on the Raspberry Pi.

As a result, after authorization, the browser tried to open:

localhost:8199

on my Windows computer, not on the Raspberry. PLAUD MCP on the Pi didn't receive the callback, and OAuth timed out.

The solution was SSH port forwarding:

ssh -F NUL -L 8199:127.0.0.1:8199 one@10.1.9.149

The chain then looked like this:

Browser Windows
     ↓
localhost:8199
     ↓ SSH tunnel
Raspberry Pi:8199
     ↓
PLAUD MCP OAuth listener

PLAUD OAuth tokens were saved locally.

Codex: Device Code Suddenly Required a Phone Number

The next problem was Codex itself.

I wanted to use authorization via ChatGPT, not an OpenAI API key. This was crucial: an API key would mean separate usage-based API billing, whereas Codex via ChatGPT uses the limits of my ChatGPT workspace.

When trying to go through the standard headless authorization via Device Code, the browser at some point sent me to:

auth.openai.com/add-phone

and required adding a phone number.

The problem was that the desired country was not in the list.

However, on Windows, I already had Codex Desktop normally authorized under the same ChatGPT workspace. Therefore, I used the existing Codex authorization on the Raspberry and transferred the authorization file to:

/home/one/.codex/auth.json

After that, I restricted the permissions:

chmod 600 ~/.codex/auth.json

Check:

codex login status

yielded:

Logged in using ChatGPT

This means the Raspberry started using ChatGPT authentication specifically, without an API key.

Microsoft To Do: Personal Account Required a Slightly Different OAuth Scheme

My Microsoft To Do is on a personal Microsoft Account, not in a corporate Entra tenant.

Therefore, the App Registration was created with support for personal Microsoft accounts, and the authority used in MSAL was:

https://login.microsoftonline.com/consumers

The application works as a public client:

Allow public client flows = Yes

A client secret is not needed here at all.

Initial Graph permission:

Tasks.ReadWrite

Later, when I added automatic category creation, the following was also needed:

MailboxSettings.ReadWrite

For the Raspberry, Device Code Flow turned out to be convenient here. The script output something like:

To sign in, use a web browser to open the page
https://www.microsoft.com/link
and enter the code XXXXXXXX

I opened the page on my PC, entered the code, and the Raspberry received the token.

After that, re-login is no longer required — MSAL automatically tries to refresh the access token from the cache.

In the end, there were three independent authentication mechanisms

PLAUD
→ OAuth token
→ ~/.plaud/tokens-mcp.json

Codex
→ ChatGPT auth
→ ~/.codex/auth.json

Microsoft
→ OAuth/MSAL
→ /opt/plaud-todo/config/msal_cache.json

And the systemd service must run as a user:

User=one
Group=one

and not as root.

Otherwise, the service simply won't see the user's PLAUD/Codex credentials.

All sensitive files ultimately received 600 permissions.

The Main Takeaway

The most useful part of this project for me was not the AI itself.

The first version was literally:

give the agent all the tools
and ask it to do everything

It worked.

But it turned out to be expensive and excessive.

The final architecture, on the contrary, is maximally boring:

Python does deterministic things.
SQLite stores state.

It was after this that the system began to resemble not a demonstration of neural network capabilities, but a normal, continuously operating service.

press button → speak → forget.
