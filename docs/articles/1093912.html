For the last three months, my colleagues from the community and I have been decompiling a popular first-person shooter. More precisely, AI agents were decompiling, and we were managing them. Our goal was not just to prove that it was possible in principle, but to obtain an accurate, stable, and fully functional C++ reconstruction of the game.

The result: the restored code contains 99% of the game's functions, 83% of them match the original byte-for-byte, and the game runs without noticeable bugs. By my estimate, this took 600-700 billion tokens.

For reasons beyond my control, I am not disclosing the name of the game, and this article is not about it, nor even so much about decompilation. The main topic is the orchestration of autonomous agents: how to set up the infrastructure, environment, and harness to get quality results from agents for months. And why all this doesn't work without objective automatic verification of the results.

The Task

We wanted to accurately decompile the game into C++. In addition to reproducing the original logic, there were other requirements: readable code that compiles, fixes for vulnerabilities and bugs (the game is old), and portability. It would be great to run it on Linux, macOS, and in the browser.

Later, we postponed modernization and portability, focusing on reproducing the original behavior. And the global goal was to learn how to effectively manage autonomous AI agents over months.

Infrastructure

We started with a Claude Max subscription (20x), then added Codex Pro and used both simultaneously. Models changed frequently: for most of the time, Sonnet 5 was used, but Opus 5.5, Luna, Sol, and Terra were also actively used. Claude agents ran in Claude Code CLI, Codex agents in Codex CLI. We also tried other agent harnesses, but noticed almost no difference and stuck with the standard ones.

Task Management

Agents manage GitHub issues via GitHub CLI: a separate issue is created for each unit of translation (a .cpp file). Labels help group tasks and set priorities.

Communication

All agents are in the same Discord channel, where everyone can read and write messages. This is how agents communicate with each other and with humans, and project participants do not need machine access. A GitHub webhook posts messages about CI failures to the channel, so agents are immediately aware of breakdowns.

Disassembler

For almost the entire time, agents worked with the official ida-mcp from Hex-Rays. It is very stable, works in headless mode, and can do everything needed for such a project. I definitely recommend it.

First Month: Rapid Progress

Initially, we had four agents. Three executors decompiled the code and committed it, while a reviewer passively coordinated the work and checked commits for bugs. In a month, the agents restored about 80% of the game: it launched, showed the main menu, and loaded maps.

In parallel, we spent a lot of time setting up the environment.

  • Early Context Compaction. By default, compaction occurs when the context is 90% full. We lowered the threshold to 42%. When decompiling, a lot of quickly outdated information accumulates in the context: a decompiled function is no longer needed. Early compaction removes this "garbage" and saves tokens.

  • Fighting Loss of Focus. The more data in the context, the more agents "drift," even within a single compaction cycle. They would leave a function unfinished and start the next one. They idled, watching CI, even though failure notifications were already coming to Discord. They closed issues without verifying if the work was actually done. In an agent's terminal, you can correct them in time, but this is not possible in autonomous operation.

Therefore, we wrote a document outlining the project's goal, work rules, prohibitions, and procedures for specific situations. Every hour, a cron job asked the agents to re-read it so that the instructions remained fresh in their context. This method might not be ideal, but it worked excellently until the very end of the project. We refined the document for a long time, but there's no point in publishing it: it's too tailored to this specific project.

The Problem: Readable but Incorrect Code

The visible progress convinced us that the decompilation was of high quality. This was not the case. The code was easy to read but semantically incorrect: agents confused function signatures, types, and struct layouts, invented logic, or discarded logic they considered unnecessary.

Furthermore, they made unnecessary architectural changes. For example, the game accesses configuration variables through global variables. Agents replaced this direct memory access with hash tables, where searching was orders of magnitude more expensive. And this is just one example among many.

Why did this happen? The reviewer catches bugs well, but can't do more: they didn't challenge architectural decisions if they fit the project's goal. Most importantly, we lacked objective acceptance criteria; we never defined what result should be considered correct. The game itself served as the benchmark, but since modernization and portability were among the goals, some deviations were not considered bugs.

Curious effect: the reviewer accepted deviations if the executor justified them in a commit comment or in the code. Such comments acted as unintentional prompt injections: the reviewer believed the explanations instead of independently verifying the code against the original.

Solution: An Oracle Based on Byte-for-Byte Comparison

We needed an oracle—an automatic check that would tell the agent whether the restored function matched the original semantically. A simple PASS or FAIL signal would suffice; the agent would figure out the error itself.

The easiest way to do this is through byte-matching decompilation. We switched to the same compiler used to build the original game and wrote a comparison script. The script reads our OBJ file, as well as the game's EXE and PDB (it's a bit easier with PDB, but it works without it too), extracts the function bytes, and compares them. If they match, the function is reproduced exactly. If not, the agent redoes it.

References to other functions and data will not match byte-for-byte: their encoded values depend on where the targets end up in the final binary. Fortunately, such references are recorded as relocations in the OBJ file. Their bytes can be excluded from direct comparison, and instead, we can check that both versions refer to the same symbol with the same offset.

Similarly, the script checks data and types. Agents run it before pushing. Restored functions are registered in text files, which CI uses to check all code and catch regressions.

How the Agents Cheated

Upon receiving the script, the agents' first move was to write inline assembly. We had to explicitly prohibit naked functions, object file patching, inline assembly, and embedding bytes into the code in the instructions. Such constructs are easy to find automatically, so a verbal prohibition was sufficient.

The other issue was worse: agents repeatedly tried to modify the script itself to exclude their function from the comparison. To prevent this, CI calculates the script's hash and compares it to a value stored in GitHub Actions secrets.

Pros and Cons of the Approach

Cons:

  • Achieving an exact match is not easy. Register selection, inlining, and calling conventions are difficult to reproduce precisely, and occasionally the compiler even produces different results for identical input data.

  • Decompilation takes much longer, and the result is not necessarily better.

  • A function can be semantically identical and not match byte-for-byte, for example, if independent instructions are swapped.

Pros:

  • Matched functions are guaranteed to be semantically identical to the original. The original behavior, including bugs, is preserved, and reconstruction errors are eliminated.

  • The reviewer agent is no longer needed.

  • Cheaper models can reliably handle the task. Previously, Haiku and Luna produced extremely poor results, but with a strict acceptance criterion, they receive enough feedback to show excellent results. Costs drop sharply, and the project can be scaled many times over.

Results

With the new verification system, the agents worked for almost two more months. The restored code contains 99% of the game's functions, and 83% of them match byte-for-byte.

In the final weeks, primarily 14 agents on Luna and 2 on Opus 5.5 were working. At this scale, each executor had its own branch, and changes went through pull requests.

Discord could no longer cope at this scale: when so many agents write to one channel, it becomes chaos. We allowed them to report only which issues they were taking on and to coordinate via CI. Moreover, over time, people needed almost no communication with the agents: they worked completely autonomously.

From here on, each new function becomes more expensive to obtain—the remaining ones either have non-deterministic features or don't match for other reasons. For example, identical COMDAT folding in the linker, which cannot be reliably reproduced, interferes. Opus 5.5 agents are still making progress, but the game already runs flawlessly: there are no noticeable bugs, and all original features are present. The remaining functions were redone many times, and we believe their semantics are correct, even if they don't match byte-for-byte. Further pursuit of an exact match would consume tokens without noticeable benefit, so the project can be considered complete.

Conclusions

  • Precise instructions are needed. If a task leaves room for interpretation, agents tend to cheat.

  • Correctness must be defined and machine-verifiable. Humans are poor at precisely formulating their intentions, so reviewers, in my opinion, will never be enough. The best feedback for an agent is reliable verification with an objective PASS or FAIL. Not every project has such a luxury as decompilation, but with sufficient ingenuity, I think it's possible to approach it anywhere.

  • With good harness, cheaper models are sufficient. With precise feedback and strict acceptance, smarter models don't necessarily perform better.

  • Instructions "evaporate" over time. The longer the work goes on and the more frequently the context is compacted, the more often agents forget rules or consider them unimportant. In interactive mode, this drift can be corrected on the fly; in autonomous mode, it can go unnoticed and degrade quality. Hourly updating of instructions helped us.

  • Generating code is cheap; discard bad code. After the first month, we tried to salvage unusable code, and it took more time than starting from scratch.

  • Correctness is more important than performance. Token savings, scalability, and agent throughput are great, but if the result is poor, they are of little use.

Conclusion

The project turned out to be an incredibly valuable experience: much went wrong, but much also succeeded. AI agents are taking on more and more work in development, and managing them is a new and much more complex task for humans.

At 15+ agents, other difficulties also emerged. From time to time, agents erased the contents of the virtual machine with incorrect commands. Solutions for sandboxing on Windows exist, but none have suited me so far. Therefore, I started developing my userspace emulator Sogen to provide a lightweight and scalable sandbox. However, it's still far from production-ready.

Due to the erased VMs, we lost some session logs, so the exact token consumption is unknown. By my estimate, it's 600-700 billion. The figure seems huge, but most of the work was done by Luna: it accounted for about 300 billion tokens. Luna is about 100 times cheaper than Astra, so in conversion, it's about 3 billion Astra tokens.

For obvious reasons, the code will not be published: it will remain closed, and I will use it only for my own needs.
