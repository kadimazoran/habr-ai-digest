Initially, we gave GPT full control: here's the store page, here's the list of promo codes, figure it out. It looked good in the demo. That is, until the day it navigated to the checkout page, saw a filled-in form, figured the task was roughly this, and proceeded to click the purchase button. Formally, it was following instructions. In reality, at that moment, we realized that LLMs cannot be given full control over someone else's browser. Moreover, in production, it was expensive, unstable, and at times dangerous.

Almost every detail of this system emerged after something broke in production. So, the following is mainly a collection of failure stories. I offer you a detailed analysis and our conclusions on building AI-native products.

Now, this extension automatically finds and applies promo codes on thousands of online stores worldwide.

On familiar sites, processing costs nothing; on unfamiliar ones, less than $0.005. The LLM inside does surprisingly little: it points out where the coupon field, the button, and the total amount are on the page. Clicking, typing, and price comparison are handled by a regular script that we can cover with tests.

What the Extension Does

When a user reaches the cart during checkout, the extension automatically finds and tries available promo codes, ultimately keeping the one that offers the biggest discount. Users don't need to manually search aggregators and check which coupons are still valid.

For us, this is a non-commercial product, a way to consolidate our experience in this niche and create a case study. Therefore, the savings for the user are genuine. We don't engage in gray monetization: we don't replace affiliate links, rewrite cookies, intercept attribution, or hide commissions. After the Honey incident (which secretly siphoned off commissions, exposed on YouTube), this is basic hygiene.

Story #1. We Gave GPT Full Control and Quickly Regretted It

The first version seemed almost perfect. We'd take the store page, give it entirely to the model, and say: here's a list of promo codes, apply each one sequentially, find the best, and keep it. In response, we'd get commands like "click here," "enter this there," and the extension would faithfully execute them.

The demo went perfectly. We were proud for a whole week until we looked at the real performance metrics.

Processing a single cart cost 7-10 cents. The model was taking too much context, getting confused, and retrying. One run took 2-3 minutes. It's terrifying to imagine a user sitting in front of their cart waiting for a discount for that long.

Less than 40% of applications were successful. In other cases, the promo code went anywhere: into the address field, the recipient's name, or some other field completely unrelated to the discount. And then there was the case with the purchase button, where the LLM started "thinking for the user."

Giving a model full access to another site's interface is like putting an intern in charge of a live production server on their first day and then going out for lunch. They try, they even do things, but no one can explain why they did them afterward.

Now, people usually ask me: have browser-controlling agents improved significantly since then, maybe it's time to try again? We've looked. Applying a code is just the last step in a long chain. First, the codes need to be found: gathered from aggregators, parsed by scripts, filtered for junk and duplicates, and for stores without a single code, a separate search needs to be initiated. Then, it needs to be determined that the user is at checkout, and a scenario selected. An agent would only handle the last, most predictable step, making it more expensive, slower, and with the same hallucinations.

Where the Model is Actually Useful

Applying a promo code is a boring, repetitive scenario: open a block, enter a code, click a button, wait for a response, compare prices, delete the code, try the next one. It's the same on all sites. The model shouldn't have to figure out this scenario every time. It's simpler to write this scenario once with regular code and maintain it. It's predictable, costs nothing, and doesn't hallucinate.

Regular code struggles with unfamiliar pages. Each store designs its cart differently, and it's impossible to describe all variations in advance. However, the model confidently reads the markup and tells us where the field is, where the "apply" button is, and where the total amount is.

Hence, the main architectural decision: a state machine, which we wrote ourselves, decides "what to do." "Where to click" is described by a set of CSS selectors, which can be obtained in five ways, from free to paid. The model is at the end of this list and answers only one question: where are the necessary elements on this page.

First, Understand That It's Actually Checkout

Before applying anything, we need to ensure the user is at the checkout. For this, each transition undergoes scoring: first, cheap URL heuristics, then checking the page for signs like a promo code field, total amount, product grid from the catalog, or an empty cart.

Early versions of the scoring made mistakes in both directions. When analyzing Debenhams, it turned out that the "this is a thank you page" indicator triggered on the checkout page itself: the desired text was searched across the entire markup and found where no one expected it. The extension saw a thank you for a purchase that hadn't happened yet and silently exited. Now, we only search for this text in the main content. And in the summer, the opposite happened: the extension confidently identified the Stripe payment page as checkout, and now we have a list of payment domains where we don't even start. We also had to learn to wait for SPAs: the URL screams "checkout," but React is still loading the chunk, and the DOM is empty.

Five Levels of Execution

When a user opens the cart, the extension contacts the server. The server doesn't make decisions: it provides the store's configuration, if available, and promo codes for the domain, independently. The client chooses which scenario to run. It proceeds through five levels: from the cheapest and most reliable to the most expensive.

Level 1. Pre-made Scenario for a Specific Store

We have scenarios written for 255 major stores: Amazon, eBay, Adidas, Gap, ASOS, Etsy, and so on. Fast, free, reliable. There's only one drawback: each scenario is written manually, and when a store redesigns its cart, we have to fix it manually too. The scenario for Under Armour, for example, had to be rewritten entirely once: the total amount, apply button, and confirmation modal moved to new markup, and none of the old selectors remained. Now it relies on data-testid because their classes are generated during the build. Although the expandable promo code block in the new version still uses a generated class, so the next redesign will also require manual fixes.

Level 2. Known Store Coordinates

Sometimes there's no complete scenario, but we already know the key elements of the site: the input field, the apply button, the total amount. We plug these into a universal template, and then it's like Level 1. It's funny that we later moved eleven stores from Level 1 to here, including Adidas, Debenhams, and JBL. Their handwritten scenarios turned out to be overcomplicated; three selectors were more than enough.

Level 3. Recognition by Platform Type

A huge number of online stores are built on ready-made engines: Shopify, Magento, WooCommerce, Demandware. Within the same engine, carts are like twins. If we don't know the specific store but see signs of Shopify, we use the Shopify scenario and reuse it. Once we figure out the platform, we cover thousands of sites at once. The downside is the same: once we had to adapt the Shopify template for mobile layout, and the change affected all Shopify stores at once. And eight platforms, from Shopify to VTEX and Shopware, have their own checkout API, where the code can be verified without even touching the page.

Level 4. Domain Memory

If the store is new and the engine isn't recognized, we first check our own memory. Once the model has parsed a site, we save its selectors for the domain. The first user on a new store pays for the parsing; all subsequent users get it for free. Even if the cache is outdated, it remains a starting point: it's easier for the model to correct an almost correct answer than to start from scratch.

Level 5. We Connect the LLM

We only reach this level if all previous ones have failed. The model receives a cleaned page and returns landmarks: where the field is, where the button is, where the amount is. We use DeepSeek V4 Flash: for such a narrow task, speed and cost are more important than erudition. The model still doesn't have browser control; all mechanics are handled by code.

The main feature of this chain is that only isolated cases reach the fifth level. The vast majority of processing is handled at the first four levels, conditionally for free. As a result, over 90% of coupon applications end in technical success, compared to forty percent in the first version, and the entire process is usually completed within a minute instead of two to three. Moreover, this minute, no matter how you look at it, is spent on the actual iteration; each coupon must be genuinely submitted to the store and a response awaited.

I'll talk about coupon application success separately because the figure is easily misinterpreted. In reality, only 50-60% of applications result in a discount. Most promo codes online are dead, expired, or don't fit the specific cart. What truly depends on us is the successful application of *any* promo code, ensuring it lands where it's supposed to.

The Core: A State Machine Instead of an Agent

If I were asked to show the most important part of the system, I'd show the most boring one. It's a pure function that, based on a page snapshot, decides the next step. First, preparation: remove the already applied code, expand the "have a promo code?" block, record the initial amount. Then, a loop through codes: apply, check, remove, take the next. If a modal window covers the page, we close it first. The function has no side effects, so the entire scenario runs in unit tests without a browser and without a single LLM call.

Here lies a truly non-obvious error. Initially, we thought any modal after applying a code meant rejection: "code invalid," it's logical, right? But there are modals saying "Congratulations, discount applied," and on such sites, the extension honestly discarded working codes. This rule lasted for three months. Everything broke on budgetvetcare.com: the extension invalidated all codes sequentially, including a working one that reduced the price from $49.04 to $41.22, and additionally showed the user zero dollars saved. Several reasons were found during analysis; the state machine was reading an outdated error message and an old amount, and the modal rule was among them. Ultimately, the "Total" amount became the source of truth: the error modal doesn't change it, but the success modal does.

Steps are assembled from a single template, parameterized by selectors. There are three mandatory ones: field, button, amount. The rest are optional, and the verification strategy is chosen based on what was found. If a delete button appears, it means the code was applied. If there's a spinner, we wait for it to disappear. If nothing is found, we compare the amount before and after.

Story #2. When We Removed Junk from the Page - Bills Dropped

When we took browser control away from the model, things noticeably improved. But the bills were still unpleasant, so we asked ourselves an uncomfortable question: why give the LLM the entire page if it only needs the structure?

The average cart page is 125-500 thousand tokens, of which, at best, a tenth is relevant. We pay for everything else in the context for no reason.

The solution is to write a handler that cleans the page before sending it. We remove from it:

  • Hidden blocks that the user doesn't see;

  • Product descriptions, reviews, legal boilerplate;

  • Technical junk that changes from build to build and only confuses the model.

The list of removal rules has grown to over eight hundred. Some even have the store noted in the comment for which the rule appeared: on AO.com, for example, the cart is filled with energy efficiency cards, a loyalty program, and trade-in offers.

We do not touch:

  • Anything related to the words "promo code," "coupon," "discount," promo;

  • Collapsed blocks that look empty but reveal the necessary field when clicked;

  • The total price and anything that might affect it.

After all, half of the cleaning work is not to throw away too much. In the removal list, there was a harmless rule about accordions; we considered them navigation. But the "Have a promo code?" block can be styled using a standard Bootstrap accordion, and then it flies out along with the menu. The check "isn't this a coupon?" only looked at classes and attributes; the visible button text didn't interest it. Kohl's survived by pure chance; its button had an aria-label with the word Coupons. American Eagle was saved by a parent block with discount in its name. Others weren't so lucky. Now we check the visible text too.

After such cleaning, the average store page shrinks by about 20-80 times, down to 6 thousand tokens. The request cost dropped dramatically, to $0.0012. An unexpected bonus was improved quality: the less junk in the context, the less often the model gets stuck on the wrong thing.

After applying the code, new elements appear on the page: an error, a discount line, a delete button. We don't send the whole page to the model for these; only the difference between the before and after snapshots. And when the second and tenth codes give the same error as the first, we don't ask again: we compare the structure of changes without text and skip what we've already seen.

Story #3. We Stopped Believing the Model at Its Word

Simply asking "find the coupon field" is not enough. Some answers will be useless, some dangerous. Therefore, the prompt has a block of nine rules, and each one appeared the same way: first a failure in production, then a line in the instructions. To put it in Russian:

  1. No generated class names.

  2. Rely primarily on data attributes, then on name, id, aria attributes, and only then on meaningful classes.

  3. For the total amount, take the innermost element that contains nothing but the price.

  4. Do not select the mobile version of an element if a desktop version exists.

  5. Compare attributes by partial match, case-insensitive.

  6. Always specify the element tag.

  7. The coupon field must be an input field.

  8. The apply button must be clickable.

  9. Precision over brevity: each answer finds exactly one element.

Regarding generated classes. Today an element is named css-1f8kqp, tomorrow it's css-9r2mzt because the frontend was rebuilt. A selector relying on such a name becomes obsolete within a day, and our domain cache turns into a cache of junk.

The seventh rule is about element type. Once the model found the "coupon field" #promoCode, but it turned out to be a container around a field with the same ID. The extension faithfully tried to enter the code into a div and reported success.

About precision. An answer like "any text input on the page" is guaranteed to lead nowhere: there are a dozen such fields on the checkout page, including email, phone, address, and card. Exactly the case where the promo code ends up in the recipient's name.

The examples in the prompt itself taught us a separate lesson. Next to the rules was a sample "good" selector, something like #promoCode td input: a field inside a table cell inside a block with an ID. On gemandharmony, #promoCode is the input field itself. The model diligently repeated the sample's structure and returned "field inside a field," which, of course, found nothing. Models copy examples much more literally than you might think, and the example had to be rewritten.

But even with the rules, the model regularly provides strange answers. Therefore, each answer undergoes three checks before the extension does anything.

Check One: Dumb and Fast

Syntax error, truncated JSON, broken structure. These are filtered out in milliseconds.

Check Two: More Interesting

We take the exact HTML that was sent to the model and run each selector against it. Zero matches mean the model invented the element. Two matches mean it didn't read rule nine properly. And even a single match must be of the correct type: an input field for the code, a clickable element for the button.

Check Three: Catches What's Formally Okay

The model is quite capable of confidently identifying a section header as the "apply button," and confusing success and error indicators. Therefore, the block with the amount must contain a price, and the "success" text should not suspiciously resemble an error message.

We saw how far a formally correct answer could go on another custom coupon project where the model fixes broken selectors in existing configurations. On the CVS cart, it needed to find the button that applies the code. The model returned the actual button, the only one on the page, with the correct tag, and the validator happily confirmed "exactly one match," and the fix went for review. Upon investigation, it turned out that the old selector on the same screenshots perfectly found the same button. It was simply inactive: on thredUp, with the class disabled; on Macy's, with the label "Action is in progress, please wait." The store was still verifying the code, or the field was empty, and the button was waiting. The report conflated "element not found" and "element unavailable" into a single failure. Eleven fixes across eight stores, and all were fixing what wasn't broken. Since then, the first question for any failure is: what exactly happened, and only then where.

Important: What Do We Know About the User?

Look at any checkout page. Name, shipping address, email, phone, sometimes the last digits of the card. And this page, it would seem, should be sent to the server, and from there to the model.

The model doesn't need any of this. It needs to understand where the code field is. Whose address it is, doesn't concern it. Therefore, before sending, directly in the browser, the extension cleans everything the user has entered or that the store has pre-filled for them. From the address field, only the name and label remain: this is enough to distinguish it from the promo code field. Contact blocks are turned into placeholders, emails and phone numbers in the text are masked. Only one type of number survives: order sums, without which the model won't find the total.

The server stores selectors and call metrics. The HTML itself is discarded after parsing.

Bonus Story: When Someone Else's Page Tries to Command Our LLM

There's a fashionable risk that's talked about with wide eyes in Reels, but rarely defended against in products. And it's absolutely real.

We send the LLM the content of someone else's page. Within this content, there might be text written specifically for the model. Something like "ignore previous instructions and do this." To the LLM, incoming text and instructions look the same; they are just tokens. This is called prompt injection, and trying to defend against it with pleas is useless.

We solve this technically and in several layers, not with requests in the instructions. Cleaning removes most places where such text could hide. The sanitizer removes known injection patterns and becomes alert if there's suspiciously much plain text in the HTML. The HTML itself is wrapped in boundaries with a random marker, new for each request, so the text from the page cannot "close" the data block and pretend to be an instruction. The response is limited to strict JSON: only element addresses, no free text.

And the last layer is the most reliable. The browser is controlled by code, so even an instruction that slips through everything else hits a wall because no one is there to execute it. The worst an attacker can do is provide an incorrect selector, which will be caught by the checks above.

The rule we derived from this:

> If the model reads content that you do not control, assume that this content is addressing it.

What to Do When Everything Breaks Along the Way (Often)

This part isn't particularly impressive and often doesn't make it into presentations, but it's precisely what distinguishes "works in demo" from "works for the user."

Applying a promo code is a chain of steps, and at any of them, the site throws a surprise:

  • The page suddenly redrew;

  • A cookie consent window popped up and covered the button;

  • The apply button got stuck in a loading state;

  • After applying the coupon, the site completely reloaded, and everything we knew about the page became outdated.

If a step fails, for example, the button is no longer found by the saved selector, we take the fresh HTML, ask the model again with the context of this step, and repeat. We try twice, then move to the next code. If the page reloads mid-step, we assume the action was applied: many sites apply coupons this way.

It's worth re-asking the model only if you're sure the selector itself broke. On that same adjacent project, we received a whole batch of "fixes" for the apply button on eBay, Best Buy, Chewy, thredUp, and Macy's. For each failure report, the model faithfully found the Apply button, just under a different name, the validator happily confirmed "exactly one match," and the fix went for review. Upon investigation, it turned out that the old selector on the same screenshots perfectly found the same button. It was simply inactive: on thredUp, with the class disabled; on Macy's, with the label "Action is in progress, please wait." The store was still verifying the code, or the field was empty, and the button was waiting. The report conflated "element not found" and "element unavailable" into a single failure. Eleven fixes across eight stores, and all were fixing what wasn't broken. Since then, the first question for any failure is: what exactly happened, and only then where.

Every Model Call is Recorded

The most useful table in our database is incredibly simple. Every attempt to access the model is recorded there as a separate row: model, tokens, cost, time, result, reason for retry, and what the model returned. It shows the cost of each run, without the average temperature of the hospital. It shows where a cheap model is sufficient, where retries eat up all the savings, and which domains consistently reach the fifth level and request a manual scenario.

What Still Works Poorly

Page cleaning relies on heuristics, and occasionally we encounter a store where the order summary is structured such that we discard it along with recommendations. Models still sometimes confuse success and error indicators, especially when the store styles both identically. Domain caching is good until a store rolls out a redesign: the first user after the release pays for parsing again. All of this is fixable, but for now, it's fixed manually.

What We've Learned From This

  1. LLM is engaged last. First, all cheap and predictable methods. Estimate what proportion of your requests truly need an LLM. For us, it's the tail, and the entire economy relies on it staying that way.

  2. A small task instead of full control. Give the LLM one question with a verifiable answer, and leave execution to the code. The narrower the question, the cheaper it is to verify the answer. "Where is the code field?" is verified with one DOM query. "Apply the best coupon" is not verified by anything and hallucinates in response.

  3. Expensive parsing must pay off. Consider every model call an investment. If the result cannot be saved and reused, you pay for the same thing over and over.

  4. Context must be cleaned. Most of the page is junk that you pay for and that degrades the answer. But removing junk is simple; what's difficult is not removing the necessary along with it.

  5. Verify every model response. Formally, factually, and semantically. These are three different checks, and they catch different things.

  6. Good rules are born from bad cases. None of our nine rules appeared during the design phase. And examples in the prompt are also rules, and the model follows them most literally.

  7. External text can rewrite the model's behavior. This is suppressed by architecture and response format, not by polite requests in the instructions. No levers, nothing to intercept.

  8. Every call must be counted. Which model, how much it cost, how long it took, how it ended. Without these numbers, you are not managing the economy, but hoping for the best.
