I have several Claude subscriptions, and Claude Code runs almost all day: I write myself, agents are running in parallel. The five-hour limit expires at the most inconvenient moment, the weekly one long before the end of the week. After that, everything is the same: open the terminal, log out, log in with another account in the browser, return to the session, and remember where you left off. At some point, I got tired of doing this manually.

Thus, ccswap was born – a Go daemon for macOS and Linux. When the current account approaches its limit (or when I ask), it logs Claude Code into another one. Running sessions pick up the new account in about half a minute, without restarting anything. Below is how it works, what I stumbled upon, and why you should use it with your eyes open: Anthropic has rules that directly concern this endeavor.

Why Not Proxies

The first thing that comes to mind is proxies like CLIProxyAPI. Claude Code sends requests to a local address, the proxy holds tokens for multiple accounts and decides on its own whose behalf the request will be sent.

I lived like that for a while. The project is large and active, and it solves its task – to provide subscriptions as an API to any clients. I needed something else, and for my case, proxies had three drawbacks.

It sits in the middle of every request. All Claude Code traffic, with code and tokens, goes through yet another server. It needs to be set up, updated, and fixed, and when it's down, Claude Code doesn't work at all.

Claude Code stops being the only client. Through the proxy, any program that speaks the OpenAI, Gemini, or Claude API can consume the subscription. To allow such requests, CLIProxyAPI by default disguises them as Claude Code: it substitutes its user agent and headers and changes the system prompt. This is stated in its own config.example.yaml (option disable-claude-cloak-mode, default false). And in the Claude Code terms, it is stated that the OAuth login for a subscription is intended for Claude Code and other native Anthropic applications, and third-party developers are not allowed to pass requests through Free, Pro, and Max credentials and act as intermediaries for tokens. Anthropic also reserves the right to apply these restrictions without notice.

The prompt cache is shared across accounts. By default, CLIProxyAPI distributes requests to accounts in a round-robin fashion. Anthropic's cache is not shared between organizations; each subscription has its own organization. If adjacent requests in the same session go to different accounts, each one re-reads the context without a cache. It is possible to bind a session to an account in CLIProxyAPI (session-affinity), but it is disabled by default. ccswap also resets the cache, but only once per switch, and tries to switch less often.

I don't need to distribute requests. I need Claude Code to be logged into another account at the right moment. Therefore, ccswap doesn't touch requests at all: it replaces what Claude Code stores as its login, and Claude Code itself communicates with Anthropic without changes. This doesn't make ccswap blameless; its relationship with Anthropic's rules is discussed below in a separate section. This is my opinion, and it's not for everyone: if multiple people need shared access, that's a job for Anthropic's team plans, not personal subscriptions, and ccswap is not suitable for that.

Where Claude Code Stores Tokens

A login in Claude Code is a JSON with the key claudeAiOauth: access token, refresh token, access token expiration time, and scopes. It is stored like this:

In the same JSON, next to claudeAiOauth, there are other keys, such as mcpOAuth with MCP server logins. ccswap doesn't touch these: it only changes the value of claudeAiOauth, keeping everything else byte-for-byte. If you overwrite the entire entry, you will lose the MCP logins.

The most pleasant discovery: a running session re-reads tokens on its own. After writing, all open sessions switch to another account; for me, this takes about half a minute. There's a price too: the prompt cache starts anew on the new account; I'll get back to that.

ccswap stores tokens for other accounts itself: on macOS in the keychain (service ccswap), on Linux in 0600 files in its own folder. They get there through the usual claude auth login, which ccswap runs in a temporary folder, so ccswap never sees the password.

The Refresh Token Works Once

This limitation leads to almost all the solutions within ccswap.

When the access token expires, the client exchanges the refresh token for a new pair, and the old refresh token immediately becomes invalid. There are three consequences.

You cannot refresh the tokens of the account currently in Claude Code. If ccswap uses up the refresh token stored by Claude Code, its own next refresh will fail, and Claude Code will be logged out. Therefore, ccswap only refreshes accounts that are not currently in use, about 10 minutes before their access token expires.

You cannot copy the login to a second machine. The same tokens on two machines will last until the first refresh: the machine that refreshes second will receive an invalid_grant error. When I needed to transfer an account to a server, this led to a separate command, which I'll discuss below.

You cannot lose the response to a refresh. The request was sent, the response was lost – the old token is already invalid, there is no new one, the account will have to be logged in again. Therefore, ccswap does not cancel the refresh request halfway, saves the new pair before it's used, and if saving fails, it keeps it in memory until the next attempt.

This is also where I got burned. One day I restarted the daemon using launchctl kickstart -k to pick up a new version. With -k, launchd kills the running process with a SIGKILL signal, and it doesn't have time to write anything. It was fine that time, but since then, the daemon is only restarted via ccswap daemon install, which stops it gracefully.

Switching and Claude Code Locks

Claude Code rewrites tokens not only on login: it refreshes them itself, and there can be multiple sessions. To prevent two sessions from refreshing simultaneously, it uses locks – empty folders created via mkdir. Whoever finds such a folder waits.

ccswap acquires the same locks in the same order:

  1. ~/.claude/.oauth_refresh.lock (considered abandoned after 60 seconds);

  2. ~/.claude.lock (also 60 seconds);

  3. ~/.claude/.storage-write.lock (15 seconds).

It waits no more than 10 seconds for all of them. If it doesn't get them, the automatic switch is postponed to the next daemon cycle, and a manual ccswap use returns an error and suggests retrying in a few seconds. ccswap does not go online while holding the locks. It saves the current tokens to itself, reads the entry again (in case Claude Code managed to rewrite it), writes the tokens of the desired account, and immediately releases the locks.

A catch that didn't surface immediately: a session that read tokens before the switch might write the old ones back over the new ones. Therefore, ccswap doesn't delete the copy of the account tokens immediately after switching to it. It remains without updates until this account has been active in Claude Code for two minutes.

And a simple safeguard: if Claude Code's access token has less than 6 minutes left to live, ccswap doesn't switch. Otherwise, you might hit a moment when Claude Code is refreshing, and you save a copy with an already expired refresh token.

Who is Currently in Claude Code

The login in Claude Code changes even without ccswap: you type /login, Claude Code refreshes the tokens. The daemon checks whose login is currently in the entry once a minute.

There are two methods. The first is fingerprinting: ccswap remembers the SHA-256 hash of the refresh token that it put there itself or has already identified, along with the account name. If the hash matches, the account is known, and there's no need to go online. The second is to ask for the profile: GET /api/oauth/profile with an access token returns the email. The profile is needed approximately once after each token refresh in Claude Code because the refresh token changes during this process.

The first bug related to the profile was found not by me, but by Ruslan when he installed ccswap. Adding an account failed with "Anthropic did not provide the login account name." The email in the profile response is in account.email, but I was reading email_address: that's the field name in the response of the code exchange during login, and I carried over the name without looking.

If Claude Code hasn't been run for a long time and its access token has expired, the login cannot be identified until Claude Code refreshes it itself. ccswap waits in this case. Sending any message to claude is sufficient.

How Much Limit is Left

ccswap gets limits from GET /api/oauth/usage: the five-hour window, the week, and weekly windows by model (Opus, Sonnet), each with a percentage and reset time. It queries the active account every 5 minutes, and others every 30: their numbers only change if you use them elsewhere.

I also had an incident with this endpoint. 429 errors are received for each account separately, and not just because of ccswap: the same address is hit by Claude Code hitting its limit and other tools. The first version queried more often and thus hit 429 errors so frequently that the daemon often didn't know how much was left. Now, after a 429, ccswap waits for Retry-After (no more than an hour) and doubles the interval for that account, but not beyond 10 minutes. It gradually speeds up again: every 30 consecutive calm responses, the interval is reduced by a quarter.

With outdated numbers, discipline is needed. ccswap will never switch to an account for which the data is old. Waiting a few extra minutes is cheaper than switching to an account that is actually also empty.

Hook and False Positives

Polling every 5 minutes is too long if a session hits the limit right now. Therefore, ccswap daemon install adds a StopFailure hook to Claude Code settings. When a session stops due to an API error, Claude Code launches ccswap signal and passes the event. If it's a rate_limit and the message mentions the limit and reset time, the daemon considers the current account exhausted for an hour and switches immediately.

Some of my agents work with their own token (CLAUDE_CODE_OAUTH_TOKEN), bypassing the login managed by ccswap. I intended to distinguish them by environment variables: ccswap signal skips the event if it sees such a token. It didn't work. In practice, the hook runs without CLAUDE_CODE_OAUTH_TOKEN, ANTHROPIC_API_KEY, and ANTHROPIC_AUTH_TOKEN; there's simply nothing for the check to see. The agent hit its account limit, the hook triggered, and ccswap moved my Claude Code away from a perfectly functional account.

These sessions cannot be distinguished directly, so the signal now checks against the numbers. The message indicates which window has ended (You've hit your session limit, weekly, or the model name). Fresh data shows this window below 80% – meaning the limit has been reached by someone else, and the signal is ignored. Old data – first query the limits, then decide. A signal within a minute after switching relates to the previous account, which ccswap also skips.

When and Where to Switch

Default rules:

  • leave an account when its five-hour window reaches 95% or its weekly window (including the weekly model window) reaches 98%;

  • select the first suitable one: enabled, not waiting for a new login, data is fresh, all windows are below thresholds; higher priority first;

  • return to an account with a higher priority when its windows drop 10 points below the thresholds;

  • at least 10 minutes between automatic switches, unless the current account is completely exhausted.

Within the same priority, two strategies are used. fill-first takes the account with the most available space. cache-aware first uses what will expire soon: the account whose weekly limit resets earlier. However, switching resets the prompt cache in all running sessions, and the re-read context also consumes the limit. Therefore, while the cache is warm, cache-aware only switches within a priority for a significant benefit: a reset within 24 hours and at least an hour earlier than the current account. ccswap judges whether the cache is warm by the time of the last write to Claude Code transcripts (~/.claude/projects), without reading the content. After an hour without requests, the cache expires anyway.

The Shift Page

The daemon has a local page (ccswap web, default 127.0.0.1:8318). Ruslan made the first version, and it looked like the CLIProxyAPI panel. Before publication, I redid it from scratch using a metaphor that is the essence of ccswap: accounts work in shifts.

At the top is the account currently in use: five-hour and weekly limits with precise reset times. Next to it is a forecast of who will replace it and approximately when. Below is a daily feed: who was using Claude Code, who is resting until reset, who needs a new login. The forecast is the consumption rate over the last hour, projected to the threshold. If there is less than 15 minutes of data or the window resets earlier, there is no forecast at all.

The page is assembled without a bundler and loads nothing from external sources: HTML, CSS, JS, and fonts are embedded in the binary, and a strict CSP prohibits it from accessing anything else. By default, the daemon listens only to 127.0.0.1. To open the page from another machine, you need to explicitly allow an external address in the settings, and then with a read-only key, you can only view it: changing settings is only possible from the machine itself or via an SSH tunnel.

Migrating an Account to Another Machine

Since tokens cannot be copied, a command is needed for migration. ccswap migrate export work -o work.ccswap packages the account into an encrypted file (AES-256-GCM, key derived via HKDF from a one-time 160-bit code) and prints a code. The code does not appear in the file or the log.

I wanted to guarantee two things: that under no circumstances would the same login be active on two machines, and that under no circumstances would it disappear silently. While exporting, the account is frozen: the daemon does not refresh its tokens and does not switch to it. It is removed from the source machine only after the file is written. Importing immediately updates the tokens, so a second import of the same file will receive an already invalid login. The most unpleasant part is when it's unclear whether the command "delete on your end" reached the daemon. In that case, ccswap does not delete the file and writes after what time to check ccswap list and what to do in each outcome.

Miscellaneous

  • Terminal Interface: ccswap tui.

  • Linux Server: the daemon runs as a user systemd service, and on a server without a browser, login is done by inserting code. Ruslan runs Claude Code on a server via T3 Code, so ccswap can respond to the part of the CLIProxyAPI that T3 Code reads to display limits.

  • Limits from Another Machine: ccswap remote gets numbers from another ccswap and doesn't ask Anthropic twice about the same account. Only numbers are transferred; tokens remain in place.

  • Languages: English and Russian. A new language is a single JSON file; no code changes are needed.

Separately about the load. When I had many agents running and the load average was over a hundred, the daemon didn't respond for several minutes. The culprit turned out to be the ProcessType key with the value Background in the service description for launchd: macOS sends such processes to the end of the queue. I removed it, and it worked.

Anthropic's Rules

This needs to be stated directly, not in fine print.

Anthropic's Terms of Use prohibit sharing an account: "You may not share your Account login information… You also may not make your Account available to anyone else." You cannot add other people's accounts to ccswap, only your own, on your own machines. Section 3 of the same terms prohibits access "through automated or non-human means, whether through a bot, script, or otherwise" (except for API keys and cases explicitly permitted by Anthropic) and bypassing "any of our systems or protective measures."

On the Legal and compliance page for Claude Code, there are two more points relevant to ccswap:

  • Pro and Max limits "assume ordinary, individual usage of Claude Code and the Agent SDK," and switching to another subscription when the first one runs out could be interpreted as exceeding these bounds;

  • OAuth login is intended for "ordinary use of Claude Code and other native Anthropic applications," and developers are not allowed to "collect, store, or intermediate Claude.ai credentials or session tokens."

ccswap is a program that you run yourself on your own system. Login is done through claude auth login, Anthropic's own flow. You store your own account tokens on your system; ccswap only sends them to Anthropic; nothing is sent to the authors. But ccswap is not a native Anthropic application and uses tokens itself: it refreshes tokens of inactive accounts and queries limits. Whether this is considered "storing credentials" according to these rules, Anthropic's text does not say. This is the main risk: Anthropic reserves the right to take action without notice. I have not found any explicit permission or prohibition from Anthropic regarding multiple subscriptions for one person.

I use ccswap myself and consciously accept this risk. I advise you to do the same, or not use it at all.

How to Install

go install github.com/Dudude-bit/ccswap/cmd/ccswap@latest
ccswap daemon install
ccswap adopt work
ccswap login personal

adopt adds the account currently in Claude Code, login adds the next one via the usual Claude Code login. Pre-compiled archives for macOS and Linux (amd64 and arm64) are available in the releases. All commands and the requests ccswap makes to Anthropic and how often are described in the README and in the document on how it works.

The project is in Go, MIT license, about 600 tests, CI runs them on Linux and macOS. Co-author is Ruslan: Linux support, polling intervals, the first version of the page, the cache-aware strategy, ccswap remote, interface translation, and the new TUI. He also was the first to install ccswap himself and found where it breaks.

What interests me most is for whom it won't work: Claude Code updates frequently, and the way it stores logins is not a public interface. If something breaks, an issue with the output of ccswap doctor will be more helpful than a star.
