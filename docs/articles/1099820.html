We are used to writing detection rules for something known: a specific tool, technique, or a characteristic string in a log. But an attacking AI agent breaks this logic: it chooses its own tools and order of steps, so by the time an analyst writes a rule for one tool, the agent might already be using another. Moreover, the analyst cannot keep up with the flow of alerts at the pace of the attacker. Tools, filenames, ports, and obfuscation techniques are just variables for the attacking agent; it changes them on the fly. However, almost any action an attacker takes while moving through a network leaves a behavioral trace. We checked if this trace is sufficient for detection, and the ML/AI solution complex was not configured for the lab.

What Was on the Defense Side

To detect an attack in a SIEM (Security Information and Event Management) system, two tasks must be solved. There are too many events: LLMs today cannot independently parse a raw SIEM event stream; they need a pre-filter to narrow down the context to what truly requires interpretation. And not every anomaly is an attack: a deviation might be explained by administration, infrastructure changes, rare legitimate scenarios, or specific system features, so classification is needed (Fig. 1).

The first task in our scheme is handled by MaxPatrol BAD (Behavioral Anomaly Detection) — an ML-based module within MaxPatrol SIEM. It aggregates, normalizes, and selects anomalies: it records deviations from normal behavior of processes and users, regardless of the tool used. Such deviations are called Indicators of Behavior (IoB).

The second task is handled by HackTracker — an ML classifier on top of BAD (I had a separate article about HackTracker this summer here). It takes not an event stream, but a BAD-prepared behavior description as input: indicators and behavioral traits. It outputs True if the behavior resembles hacking, or False if it resembles legitimate activity. It does not know specific tools. It intentionally has no explanation for its verdict: the model is optimized for classification accuracy.

Two other components help explain the verdict, so four components participated in the test. PT Naira is an AI assistant in MaxPatrol SIEM: an analyst selects a process chain, and Naira analyzes the normalized events within it, compiling an explanation with a verdict of "suspicious or not." It operates on demand, meaning only when the analyst initiates a query.

AI Agent for MaxPatrol BAD is an LLM model that receives BAD alerts along with the normalized events they are based on (command lines, process chains, network connections, file operations, authentications) and explains what is happening and why it resembles an attack. The AI agent is currently an internal Positive Technologies tool: it is being integrated into products, and in the article, it is shown as a demonstration of capabilities.

To simplify the roles: HackTracker answers the question "Is this a hacker?" at the level of behavioral traits, the AI agent answers "This is a hacker, and here's why" at the level of raw events, and Naira answers any clarifying questions from the analyst about already recorded activity.

What the Attacker Did

The lab was set up as a small corporate network: a WordPress web server at the perimeter, a Microsoft Exchange mail server (Windows Server 2019), a domain controller (DC), an ADCS (Active Directory Certificate Services) server, and user workstations.

The attacker's goal was to gain access to confidential documents of top management. To do this, it was necessary to penetrate the internal network, obtain domain-level privileges, and reach the executives' workstations, bypassing perimeter defenses. The operator provided hints to the attacking agent, and then it planned the steps itself, launched tools on Kali Linux (a distribution with a set of penetration testing tools), and moved through the infrastructure. The attack took several hours.

One technique runs through the entire attack: the attacking agent turns captured servers into relays and proceeds through them. To do this, it uses a utility that sets up a proxy (SOCKS5) on the host, and subsequent traffic to the next targets exits the network from this host's address. Such a foothold is called a pivot. There are three pivots in the test: the web server, Exchange, and the domain controller (Fig. 2).

Entry was through a vulnerable WordPress plugin. The attacking agent uploaded a PHP webshell to the server. Then, the agent exploited a sudo misconfiguration: the `awk` utility was allowed to be run without a password, and through it, any command could be executed as root. As root, it launched a popular tunneling tool. This is Pivot #0, the first foothold in the infrastructure.

The next target was Exchange. Through the tunnel, the attacking agent exploited the ProxyLogon vulnerability chain (CVE-2021-26855 + CVE-2021-27065) and wrote a webshell, an ASPX eval file named EMWdgv.aspx, into the OWA authentication directory. The `whoami` command showed NT AUTHORITY\SYSTEM, meaning system privileges. Next, the agent performed reconnaissance: it looked at users and groups, the list of Domain Admins, and found the domain controller; the domain topology became known.

Then, the attacking agent attempted to disable Windows Defender and downloaded a client using a built-in utility, `certutil`. It is designed for working with certificates but can download files via URL, and built-in utilities used for unintended purposes are called LOLBins. The agent renamed the file to `svchost32.exe` to make it look like a system process. The client connected to the attacker's command and control (C2) server, and Exchange became the second pivot (Pivot #1): all subsequent attacker traffic to the domain controller and ADCS originated from the Exchange IP address.

From Exchange, the attacking agent went for the domain. Through ADCS, it found certificate templates vulnerable to ESC1, meaning they were configured such that a certificate could be requested on behalf of another user, and requested a certificate using the `certipy` tool. Kerberos authentication (PKINIT) uses such a certificate, and the agent obtained a TGT (Ticket Granting Ticket) and the NT hash of the Administrator account.

Next, the attacking agent performed DCSync: this is a technique where the attacker impersonates a domain controller and requests credential replication. The `secretsdump` tool dumped the entire domain's hash database. Following this, the agent forged a Golden Ticket Kerberos ticket, which allows acting on behalf of any domain user. The first attempt, with the NTLM hash, failed (KDC_ERR_TGT_REVOKED error); the second, with the AES256 key, succeeded, and the agent authenticated to the domain controller.

The remaining task was to reach the workstations. Via SMB, the attacking agent browsed the domain controller's network shares (\ADMIN$, \NETLOGON, \SYSVOL), delivered another client to the domain controller under the name `svchost64.exe`, and launched it remotely using `wmiexec`, a tool from the impacket suite for remote command execution. The domain controller became the third pivot (Pivot #2). After this, the agent accessed six workstations via the \C$ share. The test objective was achieved: the agent performed lateral movement to the top manager's host and viewed the disk contents.
