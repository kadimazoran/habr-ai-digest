Why another Russian TTS

Modern neural speech synthesizers usually provide high quality but require significant resources: hundreds of megabytes of weights, a GPU for comfortable latency, and often a cloud API. For a voice assistant, this means dependence on an external service, traffic costs, and concerns about user data transmission.

I needed a different option: a compact Russian model that runs locally on a standard server, responds quickly to short utterances, and can be integrated into a voice bot. When I saw tiny-voca — an open-source model with 4.5 million parameters and 21 MB of ONNX weights — I decided to see how feasible it would be to create Russian speech based on it.

Data: Dialogs

For training, I used the open-source dataset Dialogs. It contains studio emotional dialogues from three actors; two voices were suitable for the task: female M1 and male D1.

After filtering and preparation, about 12 hours of clean speech remained. Some recordings were discarded during quality control: poor alignment, low annotator confidence, unknown phonemes, excessively long phonemes, and other artifacts.

Russian Frontend

tiny-voca already had a basis for language profiles, but no Russian profile. I added one and created a separate Russian text processing pipeline.

Main components:

  • eSpeak NG 1.51 — phonemization;

  • stresses from Dialogs — for phrases present in the corpus;

  • RUAccent — for arbitrary text and homograph resolution;

  • eSpeak fallback — if the external stress placement model is unavailable;

  • wav2vec2-based aligner — for phoneme duration labeling.

A key point: text is phonemized by sentences, not individual words. Otherwise, function words are read unnaturally: for example, the preposition "с" (with) might sound like a separate letter instead of part of a phrase.

For arbitrary text, I integrated RUAccent. It helps with stresses and homographs, but I didn't make it the sole point of failure: if it errors, the system reverts to the standard eSpeak pipeline.

For example, the phrase "выбор голоса" (voice selection) is marked as:

textв+ыбор г+олоса

в+ыбор г+олоса

Meaning "vYbor gOLosa", not "vybor golOSA".

Separately, I added a small exception dictionary for words where stable pronunciation is important: model names, service names, specific grammatical forms. This approach is practical: neural network labeling covers the general case, and the dictionary covers words critical to the product.

Training

Training was performed in Docker on Ubuntu 24.04, Python 3.12, and PyTorch 2.6.0+cu124. The model was trained from scratch on prepared Russian data.

First, I conducted a pilot run for 15,000 steps to verify that Russian language training was possible and that the data did not contain critical errors. Even at this stage, Whisper large-v3 recognized control phrases without errors, although the prosody was not yet lively enough.

After that, I launched the full run for 100,000 steps.

The effect was repeatable across several measurements. At 125 W, the card operated more stably, and the data preparation pipeline kept up with the GPU. At a high limit, performance dropped, even though the card could technically operate faster.

I don't intend this as a universal law: in most tasks, limiting power reduces performance. However, in the specific combination of "V100 + this training pipeline," a 50% limit proved to be a successful compromise in terms of speed, temperature, and noise.

Voice Assistant

A separate part of the project is not the TTS itself, but turning it into a useful product.

I created the demo page voice.lmchat.ru, where you can:

  • synthesize arbitrary Russian text;

  • switch between M1 and D1 voices;

  • change speech speed;

  • listen to dialogue examples;

  • communicate with the bot using voice;

  • send voice messages;

  • listen to your messages and the bot's responses in a messenger-like format;

  • make a web call to the bot without telephony.

In voice chat, the user speaks into the microphone, and the bot responds with voice. The recognized text and text response are not displayed: communication looks like an exchange of voice messages. Each response can be replayed.

There is also a web call mode: after pressing the button, you hear beeps, then the bot "picks up," greets you, and starts the dialogue. This is not telephony via SIP or a call to a real number, but a browser-based voice scenario via HTTP.

For the telephone bot, a different path is used: Asterisk receives the call, transmits the audio to the recognition service, a local LLM forms the response, and tiny-voca synthesizes the speech. You can call such a bot by number and talk to it using voice.

Demo Architecture

The pipeline, simplified, looks like this:

textUser    ↓ microphone    ASR    ↓ text    LLM    ↓ response    Russian frontend: normalization, stresses, phonemes    ↓    tiny-voca TTS    ↓    Audio to browser or telephone network

User ↓ microphone ASR ↓ text LLM ↓ response Russian frontend: normalization, stresses, phonemes ↓ tiny-voca TTS ↓ Audio to browser or telephone network

The website uses an HTTP pipeline: recording a phrase, recognition, response generation, synthesis, and playback. For telephony, AudioSocket and Asterisk are used.

The local LLM runs via Ollama. For the demo, I use qwen3.5:9b; it generates short responses suitable for voice dialogue. Ollama provides an HTTP API for chat completions, including a non-streaming mode.

Limitations

The project does not claim to replace large cloud TTS systems.

  • Speech quality is lower than with large models, especially for complex intonation and long texts.

  • Stresses in rare words can still be incorrect; RUAccent and the exception dictionary reduce, but do not eliminate, the problem entirely.

  • The M1 and D1 voices are based on recordings by Dialogs actors. For commercial use, the terms of OpenRAIL must be considered separately, and advertising or statements made in their name without proper rights should be avoided.

  • The model is optimized for short utterances and dialogue scenarios, not for audiobooks or long storytelling.

Conclusion

The main result of the project is not a record in synthesis quality, but proof that voice AI can be small, local, and accessible. The Russian tiny-voca weighs about 21 MB, runs on a CPU, and requires no cloud subscription. For short dialogues, voice notifications, interactive assistants, and embedded scenarios, this is already sufficient.

In the original tiny-voca, the model can even run directly in the browser: the user enters text, and synthesis happens on their device. This is a good indicator of where voice AI can go: not "send text to the cloud and wait for audio," but run a compact model close to the user.

When models stop taking up gigabytes, the approach to product development itself changes. A voice assistant can be deployed not only on a server but also where AI previously seemed excessive: in a cash register, a terminal, a car, a smart speaker, or household appliances.

And if one day a microwave asks, "Heat as usual?" and a refrigerator reminds you that you're running out of milk, it might not be a cloud service with a subscription. Perhaps inside will be a small offline model like tiny-voca-ru: 21 megabytes that can speak Russian.
