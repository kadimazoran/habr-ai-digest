How I gave an agent four repositories and saw what's fundamentally invisible in the code.

The hype around AI coding hasn't bypassed anyone. If you don't use AI tools in your work and life, your skills are becoming obsolete week by week and with every new model release. At the same time, this hype has flooded the internet with tons of SaaS solutions, the underbelly of which is scary to look into.

And it's not about the low qualifications of those who build these projects – the technical background of the guys is often more than decent. It's about speed: the pace of releases and decisions leads to tons of half-baked ideas because in this race, you have to grab your piece of the pie.

The concept doesn't change: first, quickly cobble together an MVP from what you have, release it, get feedback. Go through the most important stage – from nothing to something tangible – as quickly as possible. But if the project takes off, then you can rewrite it for all needs: with the right technologies, with the right approaches and patterns.

Let the solution architects throw stones at me :)

And who will rewrite all this? Who will have the context of a huge vibe-coded project? People, of course. Who will also use AI – but with an understanding of the context and existing problems.

Reverse engineering of everything vibe-coded will begin: documentation, data flow descriptions, lots of different diagrams – to design everything as it should be.

And the clearer these diagrams, composition, and structure are, the easier and faster it will be to rewrite everything onto the right track.

Let's imagine: we have a SaaS, vibe-coded in a couple of hours, that turns podcasts and videos into clips for social media.

We made it, released it – and the project really took off. The first users started coming in, the hype began. And immediately, something else starts: a mountain of bugs, user requests, resource utilization problems, things breaking for people. We rush to fix bugs with agents – new bugs appear. And so it goes in a circle.

And neither the agents nor we – the technical specialists who manage these agents – have enough context of the entire system.

Next, I tested this on a live project: I assembled such a SaaS from four repositories, gave it to an agent to restore the architecture, and then rewrote the core from Node to Java according to all the rules – with layers, types, JPA, and DTO. Spoiler: the code became many times larger and objectively better, but all five architectural problems remained in place. One of them even got explicitly entrenched in the code during the rewrite. I could only see it on the diagram.

The Guinea Pig: ClipCast

To avoid talking in circles, I built such a project for real. Meet ClipCast: a SaaS that takes a podcast or video and cuts clips from it for social media.

Four separate repositories, exactly as it usually looks:

  • clipcast-web - Web studio: login, workspaces, projects, clips, comments. React + TypeScript (Vite)

  • clipcast-api - Core: authorization, workspaces, projects, media upload, API tokens. Java 21 + Spring Boot

  • clipcast-transcriber - Worker: media → transcript. Python

  • clipcast-clipper - Worker: transcript → clips, external AI call. Node.js

Plus Postgres and Redis, everything is brought up with one command:

docker compose up --build

Open any of the four repositories separately – and everything looks fine.

  • You open clipcast-api – excellent Spring Boot, everything by the book.

  • You open clipcast-transcriber – a small, neat Python worker of 50 lines.

  • You open clipcast-clipper – the same small Node worker.

  • You open clipcast-web – typed React.

But here are the questions that none of these repositories answer:

  • Who writes to the clips table anyway? (Spoiler: not what you think.)

  • How many services maintain a connection to the same database?

  • What will happen if the transcripts schema is changed?

  • Which API endpoints are not protected by authorization?

  • Which endpoints are not called by anyone at all?

It's still possible to keep this in mind across four repositories. With twelve – no longer. And the agent, who is fixing another bug, doesn't get this context at all: they see one repository and their prompt.

Next – exactly the experiment for which everything was conceived.

Step 1. Get a token in Viaduct

Viaduct is a completely free tool where I keep the architecture: C4 model (systems → containers → components), HTTP contracts, broker channels, ER diagrams, PlantUML sequences, and Magic flows (playable data flows through the entire system).

Key for this article: it has an MCP server. This means the agent can not just "look at a picture" but read and write the model with tools.

Create an API token:

Create a token and then copy the config for the agent with it and ask the agent to set up its MCP connection.

Step 2. Connect the MCP server to the agent

I work in Claude Code, so the command is:

claude mcp add --transport http viaduct https://c4.quietgrid.com/api/mcp 
--header "Authorization: Bearer $VIADUCT_TOKEN"

Check that the agent has actually connected – the simplest call:

c4_whoami

If your username comes back in response – everything is fine, the agent is connected to the architecture.

Next, execute:

claude mcp list

The full set of tools that the agent receives is approximately what a live architect uses:

  • reading: c4_project_context, c4_search, c4_get_element, c4_list_docs, c4_list_technologies

  • model writing: c4_create_element, c4_update_element, c4_upsert_connection

  • documentation and flows: c4_upsert_doc, c4_upsert_sequence, c4_upsert_data_flow

I'll highlight a small detail that turned out to be important: Viaduct has a skill (viaduct-architect) – a set of rules on how exactly to model. That an endpoint is kind=endpoint with a method and contract, and a topic is kind=channel under a broker, not "another endpoint". That connections can only be between elements of the same C4 level. That technology is an ID from the catalog, not "Redis" as a string.

Without these rules, the agent draws a mess of "Service A communicates with Service B". With them – you get a model that's not shameful to show to the team.

Step 3. Ask the agent to document the project

Now for the most interesting part. The prompt is essentially one:

Scan the code in ~/clipcast-demo (4 repositories: clipcast-web, clipcast-api, 
clipcast-transcriber, clipcast-clipper) and document the architecture in Viaduct: 
create systems for each service, endpoints, broker channels, connections between services – including hidden ones. 
Mark hidden connectivity separately; it should be noticeable on the diagram.

And the agent starts working: reads pom.xml and controllers, worker.py and worker.js, schema.sql, docker-compose.yml, package.json – and in parallel, uploads it to the model.


Let's wait for the agent to create everything in the project.

After 12 minutes, the agent fully documented all repositories.

What was achieved

In Viaduct, there is now:

  • 1 Actor - Studio User

  • 5 Systems, 1 of which is the external OpenAI API

  • 16 endpoints on the API – with methods, paths, request bodies, and all response statuses, not just the successful ones

  • 2 broker channels for Redis: media.uploaded and transcript.ready – with message schemas

  • 9 tables in Postgres with columns and types

  • documentation for the system and for each significant container

  • PlantUML sequence diagram for the main scenario

  • Magic flow "Upload → Clips pipeline" of 9 steps – the entire path of a file from upload to ready clip

And now, what it was all for

When the model was assembled, the diagram revealed what was spread across four repositories in the code.

1. Three services write to the database, not one

clipcast-api – seems to be the only entry point to the data. But clipcast-transcriber maintains its own psycopg2 connection to the same database and performs INSERT INTO transcripts. And clipcast-clipper maintains its own pg pool and performs INSERT INTO clips.

In the code, these are two inconspicuous files db.py and db.js, each five lines long. On the diagram – three arrows converging on a single Postgres, and two of them are labeled "directly, bypassing the API".

A consequence that is completely invisible from the code: any schema migration in the Java service silently breaks the other two services in different languages. Hibernate with ddl-auto: update will happily change the schema itself.

2. The pipeline is half on events, half on HTTP

The entire chain is built on Redis pub/sub: media.uploaded → transcript → transcript.ready → clips. But the clipper's finalization is sent via a direct HTTP call POST /internal/clips/ready.

This was once a quick fix. In the clipper's code, it's a single line of fetch. On the diagram, it's a separate arrow that breaks the symmetry of the entire rest of the flow – and you immediately want to remove it.

3. Internal webhook without authorization

/internal/clips/ready checks nothing at all: neither authorization nor that the projectId belongs to the caller. Anyone who can reach the port can mark someone else's project as ready.

4. Dead code that no one dares to delete

GET /api/legacy/ping – an old health-check. There is no calling code in any of the four repositories. The agent marked it with the tag dead-code.

5. Hardcoded API address in the frontend

const API_BASE = 'http://localhost:4000' – without environment variables.

The main idea

None of the five points is "bad code." Each individually is a reasonable compromise made at a time when speed was essential. The problem is that all of them together exist only between repositories, and you can only see them on the map of the entire system.

What this gives in practice

Now I have a system map, and it's not in one person's head.

  • For me as a technical specialist: I see which strings to pull. Not "it needs refactoring," but specifically: remove two direct database connections, close /internal/*, replace the HTTP notification with an event. Priorities have become visible.

  • For agents: this is the missing context. When I give an agent a task "add an endpoint for downloading a clip," they can first read the model and find out that the clips table is written by a completely different service in another language. Without this, they would have simply added an INSERT to the Java service and created a third writer to the same table.

- For new people on the project: onboarding means opening the diagram and playing the Magic flow, not reading four repositories in a row.

___

Prompt advice that really affects the result: don't write "document the project." Ask to document specific things – endpoints with contracts, channels, database connections – and separately ask to highlight what looks suspicious. The difference between "drew boxes" and "found three arrows into one database" is exactly in this prompt phrase.

___

Extraordinary times require extraordinary solutions. We won't stop vibe-coding – and we shouldn't. But if we generate code ten times faster than before, we'll have to update the map of this code ten times faster too. It won't be possible manually anymore.
