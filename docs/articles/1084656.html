I recently read an article about 'Cost per Task' and how the cheapest model in a lineup can surprisingly outperform the smartest one in terms of cost per solved task. I fully agree with the conclusion, but I want to add something that wasn't in that article: it's not just about the model itself. It's about what happens after the model writes the code.

For the past eight months, I've been building an agentic wrapper where the model doesn't just write files; it has to prove that what it wrote actually works. Here's what I found: if you attach an honest verification loop to a weak model, it confidently outperforms a strong model operating in a 'write and report' mode.

Below are the numbers, architecture, and pitfalls.

The Problem: Models Lie, Not Maliciously

The classic scenario of agentic coding looks like this:

  1. User: 'Make a calculator'

  2. Model writes index.html

  3. Model: 'Done! The calculator works, buttons handle clicks, all operations are supported.'

  4. User opens the file. The 'equals' button does nothing.

Point 3 is key here. The model didn't lie intentionally. It read its own code, ran inference on it, and generated the most probable text continuation, which is a success report. For a language model, 'I read the code and it looks correct' and 'I ran the code and it works' are indistinguishable states because, in both cases, the context contains the same program text.

A smart model makes mistakes less often. But it makes them just as confidently, which is worse because you stop checking.

The conclusion I reached is this: don't try to make the model smarter. Make it so that a success report is physically impossible to generate without actually running the code.

Architecture: Three Mandatory Loops

Loop 1: Files Are Written Only by File System Tools

The first thing I forbade the agent was writing files via the shell.

// Forbidden
bash("mkdir game && echo '...' > game/index.html")

// Mandatory
Write(file_path="game/index.html", content="...")

The difference isn't cosmetic. A command like `echo` writing to a file returns exit code 0 almost always, even if you wrote the file to the wrong directory, in the wrong encoding, or to a mounted volume that will disappear in a second. The shell reports success without being accountable for anything.

My `Write` tool resolves the path relative to the project root, creates parent directories automatically, and returns not 'ok', but a structure in response:

{
  "path": "C:/Projects/game/index.html",
  "bytes": 14203,
  "refs": ["sprites/hero.png", "audio/hit.wav"],
  "missing_refs": ["audio/hit.wav"]
}

The `missing_refs` field is half the benefit. The agent learns about a broken asset reference at the moment of writing the file, not three steps later when the user sends a screenshot of a blank square.

Loop 2: Execution Is Mandatory, Reading Code Doesn't Count

The second loop is the sandbox. If you wrote a page, you'd better open it in a real engine, get the console output, and a screenshot.

The key rule I hammered into the system prompt, which yields the greatest quality increase, is:

Verification means you have seen a state change. Reading the code and concluding that it 'should work' does not count. If you cannot verify, state it directly and stop.

The last sentence here is more important than the first. Without an allowed exit path of 'cannot verify,' the model, under pressure to verify, starts hallucinating verification, which is strictly worse than the original situation. A legitimate way to say 'I don't know' is needed.

In practice, this is a single call that opens the page, takes a snapshot of accessibility with all clickable elements, runs a scenario, and returns a verdict plus console output:

{
  "opened": true,
  "console_errors": ["Uncaught TypeError: op is not a function"],
  "interactions": [
    {"click": "button[data-k=7]", "display_after": "7"},
    {"click": "button[data-k=plus]", "display_after": "7"},
    {"click": "button[data-k=eq]", "display_after": "7"}
  ],
  "verdict": "FAIL: equals did not evaluate"
}

This `display_after` is the real verification. It's the DOM state after a real click, not the model's opinion of what it would be.

Loop 3: No Hooks in the Product for Testability

The most non-obvious restriction, which I didn't arrive at immediately:

The agent is forbidden from modifying the delivered file to make it verifiable. No debug globals, no exports added 'just to see'.

A model that needs to prove its functionality will very quickly invent the following trick: it attaches the state to `window`, reads it via `eval`, and shows you a green checkmark. The verification is honest. However, the product the user receives now has a debug hook they didn't ask for.

The module's scope should be unreachable from `eval`. This isn't a testing problem; it's a correctly written module. You must prove behavior as the user experiences it: read the rendered DOM, interact with the interface, and for animations, compare two frames pixel by pixel.

const a = snapshot();          // frame 1
await sleep(400);
const b = snapshot();          // frame 2
const diff = pixelDiff(a, b);  // greater than zero means something is moving

Zero in the diff means `requestAnimationFrame` isn't running, regardless of how convincing the render code looks.

The main takeaway isn't that 88% is greater than 73%. The main point is this: a cheap model with a loop (73%) outperforms a strong model without a loop (42%), while costing nine times less.

The weak model takes more iterations. Let it. An iteration costs cents, while a false success report costs you half an hour of manual debugging and, more importantly, undermines trust in all subsequent reports.

The line with the local 14B is the most interesting to me. 61% with zero marginal cost and not a single byte of code sent to someone else's cloud. For a production monolith, this is the only acceptable configuration in principle.

Pitfalls I Stepped On

Own HTTP server for static files. I set up a local server, pointed the preview there, and got a white screen because it was a different origin, and the frame refused to embed it. Plus, the process survived the session and permanently occupied the port. Static files should be served by the preview's built-in router, and a real server should only be started for a real backend.

Paginated file reading. The agent read files in chunks of 100 lines. A four-thousand-line file turned into fourteen overlapping reads, each re-entering the context on every turn. Reading the entire file in one call is cheaper than reading it in parts fourteen times. It's counterintuitive until the first measurement.

Complete file rewrite to fix one function. Streaming a large file takes minutes, and if the connection hiccups halfway through, nothing is saved, and you start over. Patching broken lines point-by-point lands in seconds and survives anything.

Chain of `eval` calls for a single question. 'How many items in the list?' call. 'And after clicking?' call. Fifteen round trips where one script running the entire scenario would have sufficed. Batch aggressively: if subsequent actions don't depend on each other's results, they go in one go.

Mental arithmetic. The model calculated the product of nine numbers and gave 2,882,880, then 720,720, while the correct answer was 2,227,680. Any arithmetic more complex than adding two numbers must go to the interpreter, and the response should be what the program printed. This is also verification, just in a different domain.

What This Implies

The industry is currently competing on model intelligence, which is understandable because intelligence is easily measured by benchmarks. However, on a real engineering task, the quality difference between a 'smart' and a 'dumb' model is less than the difference between one that 'verifies its work' and one that doesn't.

The verification loop is pure wrapper engineering. It requires no retraining, no new weights, and no waiting for the next release. It requires forbidding the agent three things (writing files via shell, reporting without execution, modifying the product for tests) and giving it one honest tool that actually opens, clicks, and returns console output.

After that, you can take the cheapest model in the lineup. Or even a local one that doesn't send your code anywhere.
