The task was simple: build a personal compute unit at home for coding agents and minimize dependence on cloud limits as much as possible. I like Codex and Claude Code, but I don't want to constantly hit limitations, let alone pay $100 or even $200 a month for more expensive plans. So, I decided to see how far I could push with what I already had.

I tried to select hardware for the experiment with minimal investment: Core i7-4790, 32GB DDR3, ASUS Sabertooth Z97 Mark 2, and two RTX 3060s with 12GB each. No NVLink, and no CUDA P2P between the cards. However, in total, I have 24GB of VRAM and a desire to squeeze every last drop out of them.

In my specific situation, this setup was logical: a significant portion of the hardware was free (my old computer), and the notable purchases were a second RTX 3060 12GB and a large sound-dampened case. Therefore, I wasn't comparing a 'new expensive server versus a subscription,' but a one-time upgrade of an existing PC against monthly payments for higher cloud limits.

At the same time, I don't equate local Qwen with Codex or Claude Code. Cloud neural networks have a higher ceiling for the most complex multi-step tasks. But for most of my scenarios, a local 27B model is more than sufficient.

There's another very significant advantage: privacy. The model itself runs entirely on my server, so source code, prompts, and context don't need to be sent to a third-party LLM provider. This is convenient for internal code, configurations, technical logs, and other sensitive data. Of course, this statement is only true if the OpenCode wrapper, plugins, and connected tools are also not configured to send this data externally.

At the same time, speed was not an end in itself for me. I didn't want to achieve a beautiful tokens-per-second number at the cost of a noticeable loss in quality, switching to overly aggressive quantization, or cutting down the long context. The goal was precisely the opposite: to maintain a sufficiently high-quality 27B model and a large context, but to make the two 3060s work as efficiently as possible.

Initially, Qwen3.8–27B Q4 worked, but with a truly long context, generation dropped to about 9–10 tokens/s. After a series of experiments on the same two graphics cards in a controlled test with ~120K input tokens, I achieved 28.16 tokens/s, and in a real OpenCode session, an average of 39.6 tokens/s according to server logs. The working scenario is most important to me: the model should not just run, but be fast enough to use comfortably every day.

An important disclaimer upfront: this article is not about a new algorithm. All the core mechanisms already exist in llama.cpp. This is a practical review of which setting combinations actually worked on specific old home hardware, and which didn't, and why.

2. Where I Started

As a starting point, I took a fairly basic configuration: a standard Qwen3.8–27B Q4_K_M from ggml-org, full server context of 131,072 tokens, Flash Attention, Q4 KV-cache, and standard layer distribution of the model between two GPUs. This wasn't a deliberately slowed-down model, but my actual first working version: it fit into memory, launched stably, and already allowed me to use it via OpenCode.

Below is the initial launch command. By the end, you'll see which parameters actually changed. The path to the GGUF, of course, depends on where the model is located on your specific PC or server.

Why Q4_K_M and 128K in the first place? I didn't need a benchmark record, but a sufficiently large model for code with a context that doesn't end after reading a few files and a couple of long logs. A coding agent quickly accumulates source code, search results, test outputs, and its own history, so a 16K or 32K mode didn't suit me initially.

docker run --rm --gpus all 
  -p 8080:8080 
  -v "$HOME/models:/models:ro" 
  ghcr.io/ggml-org/llama.cpp:server-cuda13-b10991 
  -m /models/Qwen3.8-27B-Q4_K_M.gguf 
  -sm layer 
  --fit on 
  --fit-target 512 
  -c 131072 
  -np 1 
  -fa on 
  -ctk q4_0 
  -ctv q4_0 
  --host 0.0.0.0 
  --port 8080
