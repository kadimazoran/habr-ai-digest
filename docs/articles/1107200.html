Input tokens exceed 922,000 tokens. Your messages resulted in 1,674,813 tokens — this error kicked off a story that spanned six months. We have a self-hosted OpenWebUI with an internal assistant for a small team: files, documents, and minor engineering tasks. Initially, I wrote a filter to clean up tool results from the history. Then I realized I was patching the wrong place and moved agent execution to a separate service using OpenAI Agents SDK and Codex SDK. Along the way, I also stumbled upon the streaming Responses API.

About versions right away. On April 21st, we migrated production from 0.8.12 to OpenWebUI v0.9.1, on the same day it was released, and I wrote the filter for it. Everything said below about OpenWebUI internals refers to v0.9.1. The pilot with a separate agent was launched in July on v0.9.5, and at the end of July, production moved to v0.11.0. I later checked the call order in middleware against the current main (commit b0e6098, also tag v0.13.3, November 9, 2026) — I'll note one difference along the way.

April: One `read_file` for 66,871 Characters

Everything came down to Native Function Call. As soon as I enabled it, each tool call result started traveling to the model along with the entire history, in every subsequent request. In an internal test on April 21, 2026, the day of that very update, one read_file returned 66,871 characters. Eleven tool calls summed up to 129,972 characters, roughly 32,000 tokens. After a few turns, the request exceeded the limit, and that infamous error about 1.67 million tokens arrived.

The model's behavior was worse. It repeatedly decided that something needed to be checked or corrected again, called the tools again, and the context grew again. It ended with the user canceling the task.

Where to Cut

Looking at the interface, it's easy to think the HTML needs cutting: a tool call appears there as a collapsed block <details type="tool_calls">, and it's indeed located in chat_message.content. I delved into the middleware and the database, and the picture turned out to be different. The actual data is stored in chat_message.output — a structured array of results. The process_messages_with_output function, even before the inlet filter is called, expands output into the standard OpenAI format: assistant with tool_calls, followed by role=tool messages with the full content. That's where those 66,871 characters resided.

Outlet wasn't suitable. It triggers after the response is saved, and in v0.9.1, it only writes the modified content back to the database. It doesn't touch the output field, from which the role=tool messages are generated. (In v0.11.0 and the current main, outlet can already save modified output, but I didn't have that in the spring.) Inlet remained: it receives the expanded list of messages and can rewrite it before sending it to the model.
