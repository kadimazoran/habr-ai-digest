From Concept to Real Load

Initially, the autonomous agent was launched in test environments (over 800 databases) in cron mode with periodic ticket scanning — it continues to operate there.

In the first half of May, the load was low, but then we gradually started enabling the full processing cycle and added new alerts that generated tickets. This led to a snowball effect of tasks. From the second half of May to the beginning of June, the monitoring system created thousands of tickets per day due to high fragmentation, disk space shortages, and scheduled shutdowns.

The agent not only withstood the load but also showed impressive results. Below are the dry numbers and live examples:

  • 10,182 tickets processed in 30 days — a growth of +2426% compared to the previous period;

  • 99.6% automatically closed (StatisticsHandler). The system's autovacuum could not cope with fragmentation → the agent handled it forcibly.

Three Handlers in Operation: Example Breakdown

StatisticsHandler, the VACUUM/ANALYZE Flagship

StatisticsHandler is our flagship. It closed 9671 tickets in a month. Of course, we found and fixed bugs during debugging, but now it works stably, and we haven't seen any failures. It checks the master, monitors the load, finds dead rows, and performs VACUUM/ANALYZE. We deliberately did not optimize the code; we just let it run and watched — and it didn't fail. However, we still check the logs daily just in case.

DiskSpaceHandler, Disk Cleanup with LLM Planning

When tickets indicate a lack of space, the agent connects via SSH, analyzes the usage, and uses LLM to generate a safe cleanup plan (only allowed patterns, protection of system catalogs). Then, it performs file deletion or truncation.

Automatic cleanup of Pangolin logs (ticket anonymized):

📊 Diagnostics: occupied up to: 92% (8.5G), after: 3% (277M).
✅ Status normalized. Ticket closed.

PlannedMaintenanceHandler, Scheduled DB Stops and Starts

The agent extracts dates, hosts, and action types from the ticket text, checks for approval in comments, saves the task in a JSON scheduler, and at the right time, executes systemctl stop/start. Then, it closes the ticket with a full report.

LLM Analysis: The Agent Itself Suggests What to Automate Next

We added a weekly task to the agent — analyzing open tickets using LLM. The model (GigaChat) categorizes tickets by topic, looks for recurring patterns, and suggests new handlers. Over several weeks, we identified three stable clusters:

  • Initial DB setup (tickets CORESUP-55751, -55321, -54515, etc.) → potential ProvisioningHandler.

  • Backup requests (CORESUP-55070) → BackupHandler.

  • Incorrect data cleanup requests without specified coordinates → auto-clarification via LLM (planned).

Currently, we use LLM in the agent for:

  • extracting the host with verification against the current registry, mountpoint, dates, and times from free ticket text (fallback when regex fails);

  • determining the presence of time indicators in planned maintenance tickets;

  • generating a disk cleanup plan (DiskSpaceHandler);

  • categorizing tickets by topic (disk, vacuum, performance, configuration);

  • forming recommendations to the administrator if automatic cleanup did not free up space.

Next plan: teach the agent to create a detailed comment in the ticket indicating the causes of the problem (from logs) and specific recommendations for developers, in case of constraint violations, long lockups, and so on.

Migration of Typical DBA Tasks from Pipeliner to the Agent

Previously, many routine operations (updating statistics, log rotation, checking disk space) were performed using Ansible scripts launched from Pipeliner (an analog of Jenkins). The result: queues, dependency on slave availability, and overhead.

Now, we are gradually migrating these tasks to the agent. They are executed directly via SSH or SQL, without intermediate layers. Result:

  • execution speed has increased by two times or more;

  • dependency on CI/CD infrastructure eliminated;

  • unified logging and control through the agent's event stream;

  • ease of adding new scenarios without task configuration.

We plan to fully migrate Pangolin version updates and other routine operations to the agent, leaving Pipeliner only for complex orchestrations.

Interactive Mode: Chatbot and Manual Tools

In addition to the autonomous scanner, the agent is available as a chatbot via Streamlit WebUI. Users can directly invoke tools, bypassing ticket creation. Among the most popular:

  • Download DBMS logs from the host with optional AI analysis of errors (GigaChat highlights critical events).

  • pg_profile: reports and snapshots, an analog of AWR for PostgreSQL/Pangolin.

  • AI report analyze_pangolin_ai collects metrics from Prometheus and generates conclusions on CPU, memory, disks, and locks.

  • Install or uninstall pg_profile on the host with confirmation and DB restart.

  • Put/remove host(s) under monitoring via integration with Pipeliner (requires confirmation).

All tool calls are logged in the same event stream as autonomous handlers — the picture is as complete as possible.

Savings were achieved through:

  • priority use of regex (more than 95% of StatisticsHandler tickets do not require LLM);

  • built-in caching (llm_analysis_cache.py, TTL 30 minutes);

  • caching of Pangolin versions and other metadata.

The autonomous agent remains economical: less than 260 tokens per processed ticket.

Second-Line Support: How It Works Today and What's Next

The agent has taken the position of second-line support. Typical tasks (VACUUM/ANALYZE, disk cleanup, scheduled shutdowns) are resolved fully automatically. If the agent fails (no data, error, requires architectural solution) or the ticket contains complex logic, the task is transferred to a specialist with the NO_AUTO_RESOLVE flag. The employee sees all agent attempts in the event stream and can make a decision.

  • 99.6% automation in StatisticsHandler, the agent is ready for scaling to the entire DBA team.

  • 24-fold increase in load without an increase in manual labor, saving >500 man-hours per month.

Development plans (upcoming quarters):

  • Implementation of ProvisioningHandler and BackupHandler — based on identified LLM patterns.

  • Intelligent comments in tickets — the agent will analyze logs for constraint violations and provide developers with the exact error cause and recommendations.

  • Parameter clarification via LLM for requests without explicit coordinates (e.g., "fix the database" → clarify which one).

  • Full migration of remaining Ansible scripts to the agent (Pangolin updates, extension management).

  • Efficiency Dashboard — a showcase with KPIs, trends, and disk overflow prediction.

All described improvements are already in progress.

Conclusion

The autonomous DBA agent, which we built as an R&D experiment, handled 10,000 tickets in a month. It didn't crash, freeze, or make mistakes (well, almost — 3% of tickets were handed over to humans). The monolithic architecture with ThreadPool and targeted LLM proved more reliable than we expected.

We didn't build a super-infrastructure, didn't deploy Kubernetes, didn't write microservices. Just cron, Python, and a couple of handlers. We're moving forward: preparing an efficiency dashboard and new handlers. If you're interested, share your thoughts in the comments!
