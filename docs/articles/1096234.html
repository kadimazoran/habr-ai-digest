We tested how the agent edits files in 250 team sessions. It wrote to files via shell about 590 times, even though it had edit and write tools. 442 of these writes were due to a single phrase in one skill. We've accumulated many such stories during the development of Veai CLI.

Veai CLI works in the terminal, like Claude Code and Codex. Its first public version is out today. Anthropic, OpenAI, Google, DeepSeek, GLM, and Qwen models are available through it with a single subscription and without a VPN, and you can pay with a Russian card.

First, we'll explain who needs Veai CLI, what it can do, and how it differs from Claude Code, Codex, OpenCode, and Koda CLI. Then, in the "Under the Hood" section, we'll explain how it's built and what challenges we faced. Pricing and installation are at the end of the article.

Who Needs This

There are many good terminal agents, but connecting to them from Russia is difficult. Claude's subscription in Claude Code only provides Anthropic models, and ChatGPT's subscription in Codex only provides OpenAI models. Both subscriptions require payment with a foreign card, and you have to use a VPN to work with them.

Models from other providers can be connected in these agents via your own API key or gateway. There are also aggregators like OpenRouter that offer both Claude and GPT with a single key. However, OpenRouter accepts foreign cards, AliPay, and cryptocurrency; Russian cards are not suitable for it.

We developed Veai CLI for developers who:

  • want to work in the terminal with top Anthropic and OpenAI models without a VPN and a foreign card;

  • choose a model for a specific task and don't want to be tied to a single provider;

  • run multiple agents in parallel and want to see what each is doing;

  • work in a company with its own model gateway or a local model.

What Veai CLI Can Do

Models from Different Providers in a Single Subscription

You can switch models using the /model command directly in the chat. You can start a task on Opus, check the solution with GPT, and delegate routine tasks to Qwen or GLM. The subscription includes many models, among the top ones: Opus 5.5, GPT 6.1 Sol, Gemini 4 Argon, GLM 5.3, Qwen 3.8 Max, and DeepSeek V4.1 Flash.

A minute of work costs the same for all models on the plan. However, smarter models usually respond slower, thus consuming more minutes for the same task. It makes sense to assign complex tasks to powerful models and routine tasks to faster ones.

If you don't want to choose a model yourself, there are two modes:

  • auto directs to a pre-selected model and deducts half a minute for each minute of operation;

  • autopilot selects the model for the task based on price-performance ratio and can change it between turns. Minutes are counted by model operation time, as usual, but with a constant four-fold discount: a quarter of a minute is deducted for each minute of operation.

Your Own Gateway or Local Model

With the /custom-provider command, you can connect a corporate gateway or a local model. The agent will work through them, while other CLI features remain available.

Sub-agents and Background Tasks

The agent can divide work among sub-agents: while one runs tests, another analyzes a pull request, and you can proceed with your next task. Long-running commands also go to the background. You can start a development server or a build process and continue working.

Here's an example. We asked the agent to run tests in a three-module project and fix any failures. The agent launched three forks, i.e., three branches of the current chat, one for each module. A panel showing their status appeared below the chat.

You can open any fork and see what it's doing right now: what task the main agent assigned it, what tools it's calling, and what the commands output.

Upon completion, the fork sends a report: what was done, which files were affected, and what remains unchecked. In the cluster-api module, all 160 tests passed, and the fork made no changes. It also notes that tests were run with formatting checks disabled, so their results are unknown.

If a fork requires permission for a command, a request appears in the main window. It shows which fork is asking and why:

Each fork and sub-agent consumes minutes independently. Three parallel forks consume minutes three times faster than one.

Quick Questions Without Disturbing the Agent

The /btw command works just like in Claude Code: it asks a question about the current chat while the agent continues its work. The answer is constructed only from what's already in the chat; tools are not executed. /btw also sees command results from the current turn if they have arrived, but it doesn't see the answer the model is still writing or the command still executing. The answer appears in a separate window, and the question doesn't enter the main agent's history or disrupt it. Below, the agent is cleaning up the MCP server list, while we ask which servers are also useful to connect.

Permission Modes and Model Selection on a Single Wheel

Pressing Shift+Tab opens a wheel, similar to weapon selection in games. It allows switching between permission modes, models, and reasoning levels.

There are four permission modes:

  • normal asks about dangerous commands recognized by the parser and commands that couldn't be parsed. It executes python -c, node -e, and scripts without asking; there's a paranoid mode for those;

  • paranoid asks about any command if it's not sure it's only reading;

  • no prompts (YOLO in the interface) asks nothing;

  • I'm away also asks nothing and responds to agent's questions by stating you are away, allowing the agent to continue until the task is complete. Dangerous commands are not blocked in this mode, so only enable it where permissible.

Agent Configures Itself

To connect an MCP server or write a rule, you don't need to read the documentation. Just type in the chat: "Connect MCP server context7". The CLI documentation is included with it; the agent will find the relevant section and modify the config itself. After reloading the configuration, the server appears on the /mcp screen with its tools.

Management from Telegram

You can connect to a running session from Telegram and give tasks to the agent without being at your computer. Permission requests and agent questions arrive as cards with buttons. This works through your own bot.

Under the Hood

This section is for those who have already worked with Claude Code, Codex, or OpenCode and know what prompt caching and tool invocation are.

Why pi

When building your own agent, there are three paths: write the loop from scratch, fork a large existing agent, or take a small core and extend it with plugins.

Writing from scratch is time-consuming, and the loop where the model calls a tool and gets a result is already well-implemented many times over. A large agent immediately brings along others' architectural, interface, and prompt decisions. We chose the third path: pi by Mario Cechner.

The author calls pi a minimal agent that can be adapted to one's workflow. In the post about pi, he lists what the core lacks and will not have: sub-agents, plan mode, MCP, background bash, built-in to-dos, and permission requests. By default, pi operates in YOLO mode, meaning it executes any command without confirmation. The core has four tools: read, write, edit, bash. The system prompt along with tool descriptions is less than 1000 tokens.

This suited us. Almost all behavior, including the terminal interface, is defined by TypeScript extensions with hooks at each stage of the loop. We don't fork the engine: pi is included as a fixed dependency; product behavior resides in our extensions. In a few places, extensions selectively override the engine's behavior, but we don't have our own modified copy of pi, and we don't need to port upstream updates.

The wrapper launches the engine with flags like --no-extensions --no-skills --no-context-files, so your personal pi packages and the .pi/ folder in your project do not affect Veai CLI. AGENTS.md, CLAUDE.md, .veai/rules, and skills are loaded by our loader, including skills from other agents' folders: .claude/skills, .cursor/skills, and others.

Why Not OpenCode

Many use OpenCode as a base and connect their own models to it. For example, this is how src code works in SourceCraft CLI.

OpenCode has plugins, and they offer many capabilities. A plugin can replace the built-in bash with its own tool, and experimental hooks allow rewriting the system prompt and messages before querying the model. However, plugins barely change the interface: they can add text to the input field, execute commands, and display pop-up notifications. A sub-agent panel, mode wheel, and /btw window cannot be created this way. We would have to modify the application itself, and OpenCode has a client-server architecture and a large codebase, meaning every change would need to be ported during upstream updates. We needed to change both agent behavior and the interface, so we chose a small core.

What We Wrote Ourselves

For pi, there are already packages for sub-agents, background tasks, MCP, and web search. We started with them, but replaced most of them with our own: they didn't meet our standards for quality of work or interface usability. We wrote our own sub-agents and forks, command and background task management, permission system, rules and skills, Telegram integration, status bar, mode wheel, notifications, and built-in documentation for self-configuration.

Where ready-made packages worked well, we kept them and wrapped them with our own config and interface. These include the MCP client (pi-mcp-adapter), web search (pi-web-access), user prompts, and task lists (rpiv-ask-user-question, rpiv-todo). Connecting your own provider is based on an MIT-licensed package. We fixed one issue in it: the package declared model capabilities that were never checked.

Sub-agents and Forks That Hit the Cache

First, we tried the open-source package pi-subagents. It assembled the command line for the child process and included only its own extensions. The sub-agent lacked web search, project rules, and a permission policy, meaning its capabilities differed significantly from the main agent. Furthermore, forks in it did not hit the prompt cache.

The price is heavily dependent on the cache. For Anthropic, reading from the cache costs 0.1 of the base input token price, and writing costs 1.25. The cache only triggers on a byte-for-byte identical prefix. If the sub-agent's system prompt differs by even one line, or if the tool list has one less tool, the entire history of the main agent is charged anew, and at the write rate.

On the Veai subscription, minutes are counted by model operation time, and the cache helps here too: Anthropic notes that it reduces request processing time. With your own key, the cache saves money directly.

Therefore, we have two types of delegation:

  • subagent launches a new agent with an empty context. It's needed when an independent perspective is important, for example, for reviews;

  • fork creates a branch from the last completed turn of the main agent. A fork has the byte-for-byte same system prompt, the same tool schemas in the same order, the same model, and the same reasoning level. It receives past reasoning turns in their original form: for Anthropic, these are signed reasoning blocks; for OpenAI, encrypted reasoning elements. For OpenAI models, the fork also passes the same prompt_cache_key as the main agent. This is a hint to the provider that increases the chance of hitting the cache, but doesn't guarantee it.

The model and reasoning level are inherited by the fork from the main agent; they cannot be set independently. If you change the model on the wheel, there's no cache history for the new model, and the fork's first request will incur the cost of writing it.

The difference is visible in a test run on Sonnet. In the fork's first request, 17,234 tokens of history were read from the cache, and only 639 new tokens were not found in the cache. Through this run, we caught a bug: in the TUI, the child process lost one tool and missed the cache entirely. In that case, all 17,873 tokens would have been charged at the write rate. Now, the main process explicitly passes the list of active tools to the child.

What else is worth knowing about sub-agents:

  • There are no nested sub-agents. The fork and subagent tools remain in the child agent's schema to ensure the prefix matches, but their invocation is rejected with an error.

  • If the limit of parallel sub-agents is reached, a new launch is rejected. The model receives a denial and decides what to stop itself. A hidden queue for the model performed worse.

  • If a sub-agent finishes its turn and doesn't report back, the CLI reminds it to report, and after several reminders, terminates it with an error.

/btw is implemented using the same mechanism. It has the same tool schemas as the main agent, but invocations are blocked until completion. Therefore, the prefix matches and is taken from the cache.

Terminal and Background Tasks

In pi, bash is synchronous. The author intentionally decided this and suggests tmux instead of background processes. This is insufficient for a product: the agent needs to start a development server or a long build process and continue working.

We replaced bash with a similarly named implementation featuring a shared task manager and added bash_output and bash_kill. A command can be immediately run in the background. Output is written to a file, allowing the agent to later read the log tail or wait for the result for a specified time.

The waiting time is set by the model itself using the timeout parameter. By default, it's 120 seconds, with a maximum of one hour; both values are specified in the tool's description. If the command exceeds this time, the CLI does not stop it: it detaches and continues running in the background. The model receives a message with the task ID and knows it will be notified upon completion.

We did not use open-source implementations and abandoned several ideas:

  • pi-background-tasks stores utility files in .pi/tasks within your project. We didn't want to clutter the repository.

  • In oh-my-pi, a command automatically goes to the background based on a threshold that the model didn't set and isn't aware of. This is an unexpected change in behavior for the model. With us, the threshold is always what the model itself specified or saw in the tool description.

  • We wrote and discarded a detector for commands stuck waiting for input. Its heuristic based on a question mark `?` at the end of a line triggered on regular log lines.

To ensure the agent doesn't forget about a running task, the CLI reminds it about the active background task at 4, 8, and 30 minutes. There was also a race condition within the engine: a notification about a background task completion could arrive simultaneously with your message and intercept the turn. We fixed this in our extension, without modifying the engine. When you send a message, the extension sets a flag, and notifications wait for the turn to begin.

Permissions Without an LLM Classifier

There are no permission requests in pi, so we developed the permission system ourselves. Bash command parsing proved to be the most challenging part.

Regular expressions are useless here: env FOO=1 timeout 5 bash -c "rm -rf ~" hides a dangerous command behind innocuous wrappers. Therefore, the CLI parses the command into an abstract syntax tree and resolves wrappers (env, sudo, timeout, xargs), bash -c, substitutions like $(...), and trap up to eight levels deep. We ported the logic and lists of dangerous commands from Codex (Apache-2.0) and the cc-safety-net and Dippy projects (MIT).

The CLI prompts the user if the nesting is deeper than eight levels, if the command contains eval, if the command name is not a literal ($CMD, $(which rm)), if the script comes via pipe, and if the command could not be parsed.

Before release, we conducted a review with attempts to bypass the rules. For example, we found /bin/r? -rf ~ (glob in program name), bash <<< (command via here-string), .gi?/config and .GIT (bypassing the .git folder protection via glob and case sensitivity). We closed these bypasses.

The check has limitations. It protects against model errors but is not a sandbox: we lack OS-level isolation. In Codex, the sandbox is enabled by default on macOS, Linux, and Windows. In Claude Code, it's disabled by default, enabled with the /sandbox command, and doesn't work on Windows without WSL2.

The CLI checks protected paths only for write commands it recognizes: sed -i, redirects, tee, cp, and mv. The CLI doesn't separately recognize python -c, node -e, or scripts that the agent writes and executes itself. Therefore, for example, python -c "open('.git/config','w')" would pass without a prompt in normal mode.

On Windows without Git Bash, the bash tool executes commands in PowerShell. The model is aware of this: the tool description asks it to write in PowerShell syntax. The permission policy does not yet have its own PowerShell parser.

We intentionally introduced two limitations:

  • The permission mode cannot be set via a project file. Otherwise, a cloned third-party repository could disable your confirmations.

  • We abandoned the LLM classifier for dangerous commands. It is non-deterministic and adds latency to every command.

Rules and Task List Outside Session History

Rules are loaded from AGENTS.md, CLAUDE.md, and .veai/rules. Each rule is delivered to its specific location: the system prompt, a user message, upon invocation of a specific tool, or when reading a file matching a path pattern.

Rules for the system prompt are collected at the beginning of each user turn and do not change during the turn. If you modify such a rule, it will be included in the prompt from the next turn, and the cache for that turn will restart.

Other rules arrive when their trigger is activated: your message, the result of a required tool, or reading a suitable file. The engine hook adds such a rule before the model query at the end of the context as a separate hidden message. It operates on a copy of the context, so the rule is not in the session history and does not bloat it.

This approach has a cost for the cache. For Anthropic models, the engine places cache points on the system prompt, the tool list, and the last request block. The last block is often the hidden insertion. Therefore, writing to the cache ends with the insertion, and it's no longer there on the next request. The system prompt and tools are always read from the cache, while for the history, a match with the previous entry is not guaranteed.

Similarly, the list of active tasks is added to the end of each request. It is not stored in history, and the model sees the current list even if it created it a hundred turns ago. After context compression, the system prompt rules and the task list will be in place for the next request, while other rules will arrive again upon new trigger activation.

Interruptions the Model Understands

pi removes interrupted assistant messages from the request. You pressed Esc in the middle of an edit, the model didn't know about it, and on the next turn, it "finished" what you had just stopped. Now, the CLI inserts the marker [Request interrupted by user] into the history, and the model sees where it was stopped.

How One Phrase in a Skill Led to 442 Shell Writes

Let's return to the story from the beginning of the article. We analyzed 250 sessions recorded during development and counted how the agent modifies files. About 280 edits were made via edit, about 222 via write, and about 590 via shell: heredoc and cat >>, cat >, Python scripts, and sed -i. 442 of these were appends to a single note. The cause was the phrase "append to the note after every answer" in a skill from our own repository.

We rewrote the phrase and added an instruction to the CLI prompt to modify files using edit and write. This way, modifications are visible as file changes. Via shell, they would appear as regular successful commands.

Telegram Without Our Server

Telegram integration works through your bot, created in BotFather. Our servers are not involved: the CLI itself communicates with the Bot API. However, the chat with the bot is stored by Telegram and is not protected by end-to-end encryption.

Each session corresponds to a separate thread in a forum group, and the thread is deleted after the session ends. If you reply to a card in both the terminal and Telegram, the first reply is counted. If multiple CLI processes are running, new messages from Telegram are picked up by only one of them. When it finishes, another takes over this role.

Currently, you can connect to already running sessions from Telegram, but new sessions can only be launched in the terminal.

Cache Warming

This section is primarily for those working with their own Anthropic key. Veai subscription models are not warmed, and subscription minutes are not spent on warming.

Anthropic's cache lives for five minutes by default. If you spent longer thinking about a response, the next request will again incur the cost of writing the entire history. Anthropic describes two ways to avoid this: a one-hour cache, where writing costs 2× instead of 1.25×, and warming with a short request.

The warming mechanism is taken from the pi engine; we've enabled it in the CLI settings and documented it. When 90% of the cache's lifespan has passed, but no later than 10 seconds before it expires, it repeats the last request with a response limit of one token. Such a request is charged as cache reading plus one output token.

Warming only triggers if the expected savings are at least $0.05. It's calculated as: the cost of re-writing the entire history minus the cost of reading, multiplied by the probability that the actual request will arrive before the cache expires, minus the cost of warming itself. While the agent is working, this probability is one. When idle, pi's authors, based on their measurements, assume it to be 15%.

The setting has three values:

  • off: warming is disabled, this is the default value;

  • streaming: the cache is warmed while the agent is working on your request. This is useful when the agent waits for a long build, tests, or a slow tool for more than five minutes, and the context is large and the model is expensive. When the request is completed, warming stops, and no later than one hour later;

  • idle: the cache is warmed for up to 30 minutes after the last request, while you think about the next message.

Warming also stops when the conversation takes a different direction: you switch to another branch or session, or the context is compressed. It's enabled with the command veai config set cacheWarming streaming (or idle). The one-hour cache is enabled by the environment variable VEAI_CACHE_RETENTION=long.

Warming works for Anthropic models with your own key. Custom providers via /custom-provider and Claude models with a fixed reasoning budget are not warmed.

Windows

We had to deal with Windows separately.

  • We initially attributed the slow cold start to Node. It turned out that the antivirus scanned every file upon first opening. At startup, over a thousand files were opened, stretching the cold start to tens of seconds. We bundled dependencies into several bundles, and now only 127 files are opened at startup instead of 1237.

  • The installer installs its own version of Node and does not use the system version: it might be incompatible or non-standardly configured.

  • Task completion notifications are delivered via Windows system notifications; on other OSs, they use terminal escape codes, notify-send, or osascript. Notifications are not displayed while the terminal is in focus.

Pricing

Veai subscription is billed by the minute. A minute is defined as the pure API operation time of the model: while the provider processes the request, including waiting in its queue, and while the model generates a response. Requests that end in an error are not billed. While you are reading code or thinking about a task, and the agent is executing commands and tests, minutes are not consumed. Usage depends on the model and its response speed, the size of the chat history, and the number of sub-agents: each makes its own requests to the model.

How to Try

First, register at app.veai.ru. The trial period lasts 30 days and includes 200 minutes; no card is required. If you plan to work only with your own key, you can skip this step.

Veai CLI works on Windows x64, macOS (Intel and Apple Silicon), and Linux x64 with glibc.

Windows, PowerShell:

irm https://veai.ru/cli/install.ps1 | iex

macOS and Linux:

curl --proto '=https' --tlsv1.2 -fsSL https://veai.ru/cli/install.sh | sh

If you don't want to run the script blindly, open it at the same link and read it.

Then, run veai, execute /login, choose to log in with your Veai account, and set the model with the command /model.
