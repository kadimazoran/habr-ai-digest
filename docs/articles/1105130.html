Vibe coding vs. a hundred shards: how I built Terox in a couple of days

When a service runs on a hundred PostgreSQL shards, even the question "where is the record with this ID located?" can easily turn into iterating through dozens of connections. Entities are distributed using consistent hashing, and rare operations on heavily loaded tables require careful monitoring of lock_timeout, statement_timeout, and connection pools. I'm a backend developer for high-load services, formerly a DBA. Our standard migrations are rolled out automatically. But when a change requires special control on a heavily loaded table, I don't want to rely solely on the developer having checked the script and not forgotten anything. Thus, after a couple of days of collaboration with AI, Terox was created – a CLI that searches for data across a set of shards, switches to the found one, and rolls out complex SQL via dry-run, canary, and batches. At work, I have PostgreSQL. More precisely, I have PostgreSQL many times over: different services, environments, clusters, and hundreds of shards.

A little context about me: I'm currently a backend developer for high-load services, and before that, I was a DBA. So, databases aren't an abstract storage behind an ORM for me, but I also don't have to manually carry each ALTER TABLE to servers on a flash drive.

Our services roll out standard migrations themselves along with deployments. But there are rare operations on large and constantly loaded tables that require a separate plan: creating an index, validating a constraint, heavy DDL, or a change that needs to be performed in small stages. Here, it's important to choose the right moment, limit the lock wait time, set statement_timeout, not occupy the entire connection pool for too long, and stop after the first problem.

It's dangerous to perform such operations based on the principle "the developer looked at the SQL, it seems okay." A person can check the script and forget lock_timeout, confuse a shard, or miss partial application. I wanted a tool to remember these rules, not a person at the terminal. Terox was created precisely for such manual operational tasks and diagnostics – not as a replacement for automatic application migrations.

The common question "on which shard is this record located?" sometimes turned into a small quest:

  1. find the right host;

  2. recall the port and database name;

  3. open psql;

  4. execute the query;

  5. make sure the record isn't there;

  6. move to the next shard and strengthen one's character.

You can use pgAdmin, but first, you'll have to manually set up a hundred connections through the interface. For each, fill in the host, port, database, user, and TLS parameters, don't mix up the shard number, and neatly organize everything into groups. This is fine for a few databases. But when there are hundreds, it becomes a long, monotonous job that will have to be repeated with every configuration change. You could create a collection of shell aliases. You could keep a file with connection commands nearby, which over time starts to look like an infrastructure family tree.

All these methods work. The problem is that I didn't need another way to connect to PostgreSQL. I lacked a tool that understood entities at a higher level: service → storage → one, several, or all shards.

At some point, I stopped copying another connection string, sat down with AI, and started building such a tool myself. We made the first useful version in a couple of days. Thus, Terox was born – an interactive CLI client for working with sharded PostgreSQL clusters.

The name turned out to be a bit cosmic. The work still mainly consists of SELECT, but now it at least sounds like we're managing a fleet.

Why psql and pgAdmin weren't enough for me

Let me preface this by saying: psql is excellent. pgAdmin also solves its tasks. Terox doesn't try to replace either of them.

But for a regular client, the unit of work is a connection. In a sharded system, the unit of work is often a whole set of connections.

I regularly wanted to do things like:

  • execute a single diagnostic query on all shards;

  • see the results in a single table and not lose information about which shard the row came from;

  • quickly switch to the shard where the data was found;

  • compare the table schema between shards;

  • view locks, long transactions, and table sizes across the cluster at once;

  • apply a single migration with clear timeouts and see the status of each shard;

  • not confuse staging and production on a Friday evening.

The last point is especially important. Friday evening is a distributed system where the internal voice plays the role of consensus: "maybe on Monday?"

Why not a loop around psql

The most obvious option looks something like this:

for shard in $(seq -w 1 128); do 
  psql "host=pgbouncer-shop-rs${shard}.example.net ..." \
    -c "select * from items where item_id = 424242"
done

And this is a normal solution for a one-off task. Problems begin when such a loop becomes a daily tool: you need to limit parallelism, cancel already running queries, not lose errors from individual shards, combine different sets of columns, separate reads from writes, and each time check that the loop isn't looking at production with unexpected permissions.

Terox grew not from the idea "let's replace psql," but from the desire to build this wrapper once and then work with the concept of a set of shards, rather than connection strings.

One config instead of a connection directory

In Terox, hosts and databases are described using templates. In the examples below, names, addresses, and data are synthetic – internal infrastructure shouldn't be published – but the commands and client behavior are real. For example, a conditional 128 shards can be written like this:

max_rows: 100
fanout_concurrency: 8
query_timeout: 7s
statement_timeout: 5s
lock_timeout: 500ms

services:
  shop:
    storages:
      prod:
        host_template: pgbouncer-shop-rs{p1:03}.example.net
        db_template: shard_{p}
        port: 6432
        user: readonly
        password_env: TEROX_SHOP_PASSWORD
        count: 128
        sslmode: verify-full
        prod: true
        migration_role: app_writer

{p1:03} becomes 001, 002, …, 128, and {p} becomes the zero-based position number. The host and database name can be numbered differently.

fanout_concurrency is more important here than it seems. It prevents the client from simultaneously rushing to all 128 shards and causing a load test that no one asked for. The client's query_timeout limits the entire call to a specific shard, and the server-side statement_timeout and lock_timeout limit the work already within PostgreSQL.

After that, you can immediately open the entire cluster:

terox -t shop/prod/all

Or select the service, storage, and shard through a menu. The prompt always shows the current context, the production badge, read/write mode, and statement_timeout.

shop/prod(all) [prod ro st=5s] =>

If a query goes to the wrong place, even though it's all written directly in the prompt, the tool at least honestly tried to help.

Fan-out without manual fan-out

A query to all is executed across the selected shards, and the results are combined. Terox adds a shard column, aligns columns by name, and separately shows errors from individual targets.

Our entities are distributed across shards using consistent hashing. This is convenient for the system, but not always convenient for humans: with a single key, you can't just estimate on a piece of paper which of the hundred shards the record is on. To get an accurate answer, you need the current ring, virtual nodes, and the same routing logic that the application uses.

And sometimes the task sounds quite mundane: "find the object with this ID and see what's happening with it." Iterating through a hundred connections manually is a great way to turn a one-minute check into a hobby.

For this, Terox has ind:

shop/prod(all) => ind items item_id = 424242
┌──────────┬───────┐
│ shard    │ count │
├──────────┼───────┤
│ shard_37 │ 1     │
└──────────┴───────┘
found on 1/128 shard(s)
→ shop/prod(shard_37)

Terox iterates through the selected shards, shows where the data was found, and if there's only one matching shard, it automatically switches to it. The next query is then executed in the correct place – without copying the host, reconnecting, or playing "guess the shard."

And if there are multiple matches, you can select the desired shard manually:


s shard_37

For frequent scenarios, there are commands like count, locate, grep, saved queries with parameters, and exporting results to CSV/JSON. History is stored separately for each service: queries from one context don't pop up with the up arrow in another.

The editor supports multi-line input, wrapping long lines, live autocompletion for schemas, tables, and columns. There's also automatic layout correction: if you type a meta-command in a Russian layout, Terox tries to understand what your fingers remembered better than your head.

What happens inside fan-out

Simplified, the query path looks like this:

selector all / 0,1,5
        │
        ▼
expanding the list of physical shards
        │
        ▼
queue with fanout_concurrency limit
        │
        ├── shard_0: READ ONLY + SET LOCAL statement_timeout
        ├── shard_1: READ ONLY + SET LOCAL statement_timeout
        └── shard_N: READ ONLY + SET LOCAL statement_timeout
        │
        ▼
combining rows + shard column + individual errors

For each shard, the pool is created lazily: until the database is accessed, there's no connection. Within a single shard pool, no more than two connections are allowed – the second is needed so that background autocompletion doesn't block user queries. At the same time, the number of simultaneously processed shards is limited precisely by fanout_concurrency.

Each shard has its own client deadline. A slow or unavailable shard doesn't erase successful results from others: an error remains tied to its target and is displayed separately. Ctrl+C cancels the general context, so already running queries are interrupted, and those not yet started don't begin. Upon exit, the manager closes all created pools and prevents the background goroutine from creating a new connection after closing.

Reading on each shard occurs in a real PostgreSQL READ ONLY transaction, not just determined by parsing the SQL text. The result is limited by max_rows so that a random wide SELECT doesn't consume terminal memory; full export of large selections uses streaming reads.

Diagnostics that are usually pieced together

Gradually, the client has accumulated commands that I constantly need when troubleshooting problems. activity, blockers, locks, and longtx show activity and locks; sizes and statements --skew help see imbalances between shards; diff <table> compares schemas, and doctor --all collects a general health check. For individual queries, there's explain, advise, and lint.

This is not a replacement for monitoring or a pocket DBA. Rather, it's a shortcut from "something is slow" to a proper question that can then be taken to metrics, logs, and query plans.

For example, lint will warn about DELETE without WHERE, LIMIT without ORDER BY, suspicious Cartesian products, or NOT IN with nullable values. The heuristics can be wrong. But they don't get tired and don't think: "oh well, the query is small."

Writes must be enabled consciously

Reads in Terox are performed in READ ONLY transactions. By default, the client operates in ro mode, and write queries are rejected.

To enable writing, you must explicitly execute:

	write on

When switching services or storages, write mode is reset. This is a simple protection against the situation "I thought I was still on the test cluster."

If a migration_role is specified for the storage, writes get it via SET LOCAL ROLE. A regular transactional migration is wrapped approximately like this:

begin;
set local role app_writer;
set local statement_timeout = '5s';
set local lock_timeout = '500ms';

-- migration body

commit;

Here, LOCAL is important: settings live within the transaction and don't leak to the next PgBouncer client.

DROP DATABASE is unconditionally forbidden. Yes, the user is an adult. But the client, running on a hundred shards, is also an adult and has the right to refuse to participate.

Migration is not just "send SQL a hundred times"

Let me emphasize again: standard versioned migrations travel with the service automatically. The mode below is for exceptions where the developer consciously manages the rollout on heavily loaded tables and needs to see each stage.

There is a separate mode for migrations:

	migrate add_column.sql

Without --allowed, this is a dry-run: Terox shows the exact SQL, the rollout plan, and static analysis warnings. Actual application is launched separately:

	migrate --allowed add_column.sql

For large clusters, there's canary, batches, and resuming interrupted rollouts:

	migrate --allowed --canary add_column.sql
	migrate --allowed --batch 10 add_column.sql
	migrate --allowed --resume add_column.sql

A checksum prevents an already started migration from an altered file from being continued unnoticed.

There is, of course, no general transaction across 128 PostgreSQL servers here. Atomicity operates within each shard: one might have already performed a COMMIT when the next returned an error. Therefore, by default, the first error cancels targets that have not yet started and are executing, the report clearly shows partial application, and --resume continues only from uncompleted shards. This is precisely why migrations must be idempotent, and canary and small batches are more useful than heroism.

There is a separate unpleasant class of operators: CREATE INDEX CONCURRENTLY, REINDEX CONCURRENTLY, VACUUM, and other commands that are forbidden to execute within a transaction. For them, the usual wrapper with SET LOCAL and server timeouts cannot be applied. Terox recognizes such SQL, loudly indicates that execution will be unprotected, and on production requires a client-side migration_timeout and separate confirmation.

I wanted the dangerous path to be not impossible, but noticeable. Except for DROP DATABASE. That path already has enough independent tools.

Where is the vibe coding here

I actually did most of Terox in collaboration with AI. Not in the sense of "wrote one prompt and went for coffee." I drank coffee nearby.

The work looked something like this:

  1. I described a specific pain point from my work process;

  2. we found a minimal behavioral model;

  3. AI suggested an implementation;

  4. I checked the code, ran tests, and tried the scenario manually;

  5. another edge case turned into a new test.

This is how details emerged that rarely make it into a slick first demonstration:

  • correct closing of all connection pools on exit;

  • Ctrl+C that exits the prompt but cancels the active query;

  • wrapping long SQL to fit terminal width;

  • multi-line pasting;

  • secure history without passwords and with a separate file per service;

  • backup of the config before installation;

  • strict checking of unknown YAML fields;

  • protection against leakage of session-scoped state during transaction pooling;

  • tests for concurrent pool closing and race conditions.

AI greatly accelerates such a cycle. It quickly finds the right places, writes repetitive tests, suggests structures, and doesn't complain about another request "and now consider this too."

There's also a downside: it can implement a flawed idea quickly, neatly, and in twelve files at once. Therefore, code generation speed is not the same as decision-making speed.

One of the useful principles turned out to be simple: first formulate the invariant, then ask for code.

For example:

  • after exiting, there should be no connections left;

  • read-only should be enforced by PostgreSQL, not just a regular expression;

  • context switching must disable writes;

  • sensitive SQL should not end up in history;

  • a partial error on shards should not look like complete success;

  • dry-run should not suddenly become apply due to a convenient default value.

With such rules, the conversation with AI becomes engineering work. Without them, it turns into a very productive surprise generator.

What Terox cannot do for you

Terox doesn't make any SQL safe. Static analysis is a heuristic. The real security boundaries are still created by role permissions, READ ONLY transactions, TLS, timeouts, and rollout discipline.

It doesn't replace application migration systems, monitoring, backups, or understanding query plans. It doesn't fix sharding architecture. It doesn't know the business logic of the data.

And, unfortunately, it cannot determine if you really need to execute a query on all 128 shards. It just does it very well exactly where you asked it to.

What has been achieved

From a local pain point, a tool has grown that I find convenient to use every day:

  • a single config describes services, storages, and shard templates;

  • a single query can be executed on a selected set of targets;

  • the result preserves the origin of each row;

  • diagnostics are aware of the multi-shard context;

  • reads are protected by READ ONLY;

  • writes are enabled explicitly;

  • migrations get dry-run, lint, transactional wrapping, timeouts, and phased rollouts;

  • the CLI remains a regular local binary without a separate server.

The first version appeared in a couple of days precisely thanks to AI. But Terox became useful not because the code was written quickly. It became useful when the fast code started to be constrained by clear rules, tests, and real-world scenarios.

For me, this is normal vibe coding: not "not understanding what's happening," but quickly turning one's understanding of a problem into a working tool.
