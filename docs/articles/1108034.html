Need to Make a Notebook

On May 26th, ёPRSTCON took place. Among other topics, we discussed automatic parsing of scanner findings, the application of language models in cybersecurity, agent protection, and secure development in an agent environment. After such discussions, dozens of links usually remain on slides and in various chats. This time, we agreed to compile them into a repository.

The first commit appeared on May 27th. The main list had 99 entries and an additional 11 links to thematic collections. On June 2nd, I presented the list on Habr as a continuation of ёPRSTCON.

Two directions immediately stood out in the list. In one, AI helps find vulnerabilities, parse security system alerts, analyze executable files, and gather threat intelligence. In the other, tools protect models, applications, and agents from injections, leaks, and unwanted actions. As the list grew, separate categories emerged within each direction.

Star Tweet

In July, @KanikaBK wrote:

In my perception, after this post, the repository with the list became noticeably noisier. The collection of public projects was retold as a suddenly opened arsenal that should make all CISOs panic. Perhaps it should, if they hadn't previously encountered how agents are changing cybersecurity.

A "starfall" occurred, and on July 26th, the list occupied tenth place in Trendshift's daily Python projects ranking. In September, another wave of attention arrived: on September 23rd, I marked in the channel the crossing of the 1,500 stars mark.

For each request, we have to check the source repository, project renames, forks, uptreams, and licenses. Sometimes, a claimed scanner turns out to be a set of instructions for an agent, and a tool promising local operation sends all its source code to an external model provider. Neuro-Slop from Both Sides

We started receiving requests with similar characteristics regularly: a repository created yesterday, one large commit, an impressive README, and bold promises. Familiar pattern? Yes, the robot invasion begins with GitHub.

I also contributed to this. When I ran dozens of open-source projects through rust-in-peace, some maintainers also called it neuro-slop. And some accepted PRs and thanked me as a top contributor to Ginux.

The first commit sometimes contains yesterday's experiment, and sometimes a whole serious project previously developed in a private repository. Based on the repository's age and the README's smoothness, it's easy to err in either direction. I didn't want to reject based on a formal criterion.

I accepted the participation of agents as a given: they create projects, write documentation, and submit requests. Therefore, they should also help with parsing. In the "Creator's Manifesto", I wrote about how the decreasing cost of code increases the importance of selection, trust, and proof of practical benefit. With my own list, I had to test these predictions in practice.

With agents, I could read the implementation in more detail: trace data transfer, parse error handling, and compare promises with code. I wouldn't have had enough time to perform such checks for each request alone.

How We Check Candidates

The check begins with a few questions. What does the user install, and where does the analysis happen? What data goes out? Is a paid account and API key required? What happens if the model is unavailable? Is there another interface through which control can be bypassed? Do the tests check the protection mechanism itself or just its interaction with a mock? You know how agents love to present wishful thinking as reality.

We are all a little bit Terminators when it comes to mocks.

We pay particular attention to promises of protecting logs from tampering, offline operation, and mandatory rule enforcement. We look for how this is implemented in the code and separate the verification results from the author's promises. Currently, we examine external candidates without running their code, installers, or automation scripts on our work machines.

Static analysis allows us to understand the tool's architecture. Evaluating a detector's effectiveness and finding bypasses requires separate tests. I conduct these for tools that pique my interest. For instance, based on the analysis of Anthropic's defending-code-reference-harness, rust-in-peace was born. After all, this is a "notebook" to keep interesting tools at hand when the idea to "code something" arises.

I make the final decision. The checking agent can also make mistakes: a couple of times, they pointed out incorrect formulations or unsuitable tools in the list to me. Therefore, I established a rule to periodically "sift" through the entire list line by line.

We Accept Poorly Formatted PRs

For useful candidates, I started offering a choice: fix it yourself, or we'll accept the PR and then fix the wording ourselves. An incorrect category, a promotional description, or an error in generator interaction is easy to fix if the tool itself is good. The author doesn't need to deeply understand our JSON format.

It's important to me that authors continue to participate and contribute interesting things. Therefore, whenever possible, we accept the original PR while preserving authorship, and then make our own edits. If we moved an entry ourselves, we might indicate a co-author. For an agent, these edits take little time.

Before merging, we still check changes in the repository, especially in CI automation. We make a separate decision about including or excluding a tool and explain it to the author.

For substantive but too-young projects, we created WATCHLIST.md, a list of candidates with notes for re-evaluation. On August 4th, I already wrote about this practice. This allows us to preserve a find and give it time to develop, while maintaining stricter selection for the main list.

As of the current snapshot, the candidate list contains 276 GitHub repositories. We periodically check their development, migrations, and new usage evidence. We move growing projects to the main list and remove abandoned or irrelevant ones. We try to notify the original PR about the move: it's gratifying for the author to know their work hasn't been forgotten.

Security of the Review Itself

During the review, the agent reads others' READMEs, comments, and configuration examples. These might include instructions to execute a command, modify a CI script, upload a file, or transfer data. This creates a risk that the agent might execute them as part of its task. I didn't want to get too bogged down with sandboxing (though I should already).

Therefore, we treat external text as untrusted data. Commands from INSTALL.md and suggestions to "just check this Action" require a separate decision to execute. It turned out to be for good reason.

After including Lumi Eggcracker in the candidate list, we were offered in PR #69 to add a check for a synthetic execution report, named receipt, to the CI. The author of the project prepared an example report, a schema, and a verification program.

The catalog didn't need this integration: the check only verified compliance of the author's example with the author's schema. We have no grounds to declare this an attempt to introduce a backdoor or attribute malicious intent to the author, but it's unknown how an agent would behave in such a situation without additional restrictions.

What's Being Tried on the Watchlist

It's interesting to see what the "young generation that will erase us from the face of the earth" is up to. In the WATCHLIST snapshot from November 14th, there are 276 GitHub repositories. Of the 269 with comparable creation dates, 235, or 87%, appeared in 2026. The median among the 270 available repositories is 14 stars.

For the diagram, candidates were categorized by their primary task. Each repository is counted once.

"Who allowed this?" In CTRLRun, confirmation is tied to a specific action; in SpendShield, spending is limited. During review, we first check if the agent can bypass the restriction through another interface. Sometimes, they are also given a tool to approve their own expenses.

"What am I installing with this skill?" clonepeek lists the locations from which the repository can execute code; mcpsum fixes MCP definitions and notes changes. In such projects, I'm more interested in the list of checks and skips than a big A+ in the report.

"What did the agent actually do?" memory-blackbox tracks the origin of memory entries; aaesverify checks the integrity and signatures of reports. It's easy to get carried away with cryptography here: the signature can be flawless, but the entry itself might be erroneous. SHA-256 of a hallucination also has the correct length.

"How to grant access without a key in the prompt?" Keyrelay passes a secret to a specific command; browser-bridge separates credential input from the tab controlled by the agent. We check who ultimately gets the secret and where it can be sent.

What Remains After Six Months

I regularly check the list to see what interesting things have appeared. Some projects lead to their own developments, while others provide ideas for existing ones.

With agents, I was able to access the code of a much larger number of candidates and analyze them in more detail. Authors responded to feedback, fixed projects, and returned. So, the list proved beneficial on the other side of the PR as well.

We started with an agreement to compile links after ёPRSTCON. Now, the list is accompanied by hundreds of discussions, a queue of candidates, and regular revisits to previously reviewed projects.

Use the list, submit your projects, correct our mistakes, and return with updates. Before submitting, read CONTRIBUTING or give it to your agent. I publish observations and project news in "AiKyn".
