A code agent in a small project usually finds the right file with a very confident air. This is pleasant right up to the moment when it changes the wrong counter, alters the module's behavior, and reports that the task is complete. Confidence is free, regressions are too.

In the test example, we need to add a weekly limit to a small module. The agent finds the method, adds a counter, and even writes a test. Then it turns out that the limit is counted per user, a rejected attempt should not consume quota, and a negative limit should remain an error. In the code, this is scattered across the model, tests, and an old comment.

This is not necessarily the model's fault. I gave it the code, but not the intent.

Below is an overview of the SDD practice for a small repository. Not RAG, not a corporate knowledge base, and not a new religion with a folder naming committee. Just four short files that help the agent understand the project before the first change.

What is called semantics here

Code answers the question “how it is done now”. It answers the questions “why”, “what cannot be broken”, and “which two similar words mean different things” worse.

By project semantics, I mean a small layer of agreements:

  • a domain dictionary;

  • invariants that must survive refactoring;

  • public contracts;

  • boundaries of a specific change.

This is similar to Spec-Driven Development, but on a smaller scale. The GitHub Spec Kit documentation describes SDD as a process where intent is captured before implementation and refined in several steps [1]. I am not suggesting copying the entire workflow. For a small project, it is enough to make the intent accessible to the agent and link it to the tests.

Minimal set of files

Place the following structure next to the code:

agent-context/ 
  index.md 
  domain.md 
  contracts.md 
  features/ 
    weekly-limit.md

This is not documentation "just in case". Each file has one job. If a file does not help select source code or make a decision, it is a candidate for deletion, not for another subsection.

The mini-example contains all four files, tests, and ready-made instructions for the agent. It models a module with a weekly quota.

# domain.md 

- The weekly limit is counted per user, not per API key or IP address. 
- A rejected attempt due to the limit does not consume quota. 
- The week starts on Monday at 00:00 UTC.

These three lines are more useful for the agent than another retelling of app/limits.py. The first sets the aggregation boundary, the second defines behavior on refusal, and the third is a time rule. All three should be verifiable by tests.

How to collect context in an evening

You shouldn't start by generating documentation with the model. Otherwise, you'll quickly get a neat retelling of package-lock.json, which nobody needs. I would look at five things:

  1. the entry point and module tree;

  2. the dependency file and the test run command;

  3. the public API or CLI;

  4. two or three illustrative integration checks;

  5. the last non-trivial feature in the change history.

From these, you can assemble navigation, module names, and the external contract. But the meaning of the rule "refusal does not consume quota" cannot be reliably extracted from the code. It must be written by someone who knows the domain.

The filter is simple: if a statement can be restored from the source code without loss, do not copy it into agent-context. Provide the path to the module in index.md. If, after refactoring, the statement must still be true, it belongs in domain.md or the feature specification.

How the agent uses this

Do not send the entire repository in the first request. The context window is not a warehouse where you need to stuff all the boxes before moving. Give the agent a short route:

Before making a change, read agent-context/index.md. 
For the task about limits, read domain.md, contracts.md, and 
features/weekly-limit.md, then open the sources and tests named there. 

First, match each readiness criterion with a test. If a criterion has no 
match, add or change a test. Do not change the public contract without 
updating contracts.md.

The benefit is not in a magical prompt. The route forces reading the rules first and then limits the search to the relevant part of the repository. If the agent suggests changing the result type, it sees that this is no longer a local fix.

What to automate and what not to

For a small project, two rules in a PR are sufficient:

  • the public API has changed - update contracts.md;

  • an invariant has appeared or changed - update domain.md and the test.

It only makes sense to automate the obvious: for example, comparing the generated OpenAPI with the committed schema. You should not set up CI that requires rewriting documentation after renaming a variable. Otherwise, the context will become a ritual that everyone bypasses with the expression of a person updating a password in a corporate VPN.

The specification for a one-time feature can be deleted after merging. If it contains a permanent invariant, move it to domain.md or contracts.md. Spec Kit also does not prescribe a single fate for specification artifacts after requirements change [2].

Where this approach ends

Four files will not replace an architectural review, will not make the agent's code safe, and will not resolve conflicting requirements. They will also cease to be convenient if dozens of teams change one repository simultaneously.

Here you can already look towards OpenViking. This is a context database for agents that combines knowledge, memory, and skills in a virtual file system. In it, the agent first reads the short abstract of a directory, then the overview, and only then the source materials. The idea is close to our index.md, but the scale is different: instead of four files, there is a server, indexing, and a separate context storage layer [3].

For a pet project, I wouldn't set up OpenViking just so the agent could find two tests. It's like calling a crane to move a stool. But when the context lives longer than one feature, the agent has memory between sessions, and there are already many sources, such a system becomes a sensible next step.

But until then, you don't have to start with RAG, a dependency graph, and an autonomous orchestrator heroically orchestrating two Markdown files. First, you should answer one question: can a new person understand in ten minutes what to read before changing the limits? If not, the agent will also have to guess, only faster.

First version checklist

  • [ ] index.md leads from task type to sources and tests.

  • [ ] domain.md contains only terms and invariants.

  • [ ] contracts.md captures externally observable behavior.

  • [ ] The active feature has readiness criteria and task boundaries.

  • [ ] Each important criterion is covered by a test.

  • [ ] The PR includes a question: has the contract or invariant changed?

This is enough for the agent to get not "the whole project", but its working model. And then tools should only be added where four files are truly insufficient.
