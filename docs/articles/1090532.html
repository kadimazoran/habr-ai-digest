A Little About Myself

My name is Danil, I'm 23 years old. A year ago, I graduated from university. During my studies, I touched both frontend and backend, but ultimately realized that I felt more comfortable on the backend.

I particularly enjoyed Go. It has a pleasant feel: here's a struct, here's a function, here's an error – deal with it. Without the feeling that the language will suddenly pull another magical abstraction out of its sleeve. Predictability, strictness, static typing, a compiler instead of an interpreter, convenient work with concurrent and asynchronous code, automatic garbage collection, solid performance – all these factors influenced my attitude towards the language.

Where the Idea Came From

I have a habit: periodically browsing Habr and reading articles about everything. If I encounter an unfamiliar technology or concept, I dive deeper: documentation, Google, ChatGPT, source code. Recently, I stumbled upon an article by T-Bank about the problems of configuration libraries in Python: a zoo of formats, implicit type conversions, secrets, and other joys.

I could have just finished reading and moved on, but I was unexpectedly struck by the desire to write my own library. First, I decided to see what we currently have in Go:

  • Viper – a well-known heavyweight that can do a lot, but might seem excessive for a small service.

  • cleanenv and envconfig – concise libraries well-suited for environment variables and .env files.

  • There's koanf – a fairly flexible option, but with its own setup and boilerplate.

In short, everything necessary was already available. And that's precisely why, of course, I wanted to write another configuration library. Because otherwise, what kind of programmer would I be if I hadn't written my own implementation of a bicycle?

What I Wanted to Achieve

Before starting, I wrote down a few requirements for myself:

  1. No tons of settings. Ideally, I want to write something like Load(&cfg) and get a ready-to-use struct with all fields populated by corresponding values from a file.

  2. Support for different formats. .env, JSON, YAML, TOML, INI, and environment variables.

  3. Cascading loading. For example, take a base config, overlay a local one on top of it, and then environment variables on top of everything.

  4. Minimal number of tags. I didn't want to manually tag every field with ten tags.

  5. Support for clear validation. required, default, checking for unknown keys, and the ability to write custom validation.

  6. Handling secrets. Database passwords or API tokens shouldn't accidentally end up in logs just because someone did fmt.Println(cfg).

On paper, it all looked quite harmless. And then I decided to test how well an agent could assemble all of this.

Where the Agent Started Doing Something Weird

The first few hours easily create a dangerous illusion: if the agent writes code, runs tests, and says everything passed – then everything is fine. However, this is not the case. It can indeed program quite well, but sometimes it can solve a problem in such a peculiar way that you can't help but laugh.

Below are a few of the most illustrative cases.

"I Don't Know Why the Field is Empty, But We'll Fix It Now"

The repository contains a directory with examples of library usage. I asked the agent to create an example that combines all five supported formats into one scenario. It did, ran it, formatted everything, tidied it up, and confidently reported to me:

Error fixed, 100% of tests pass successfully

But when I decided to run the code myself, for some reason, one of the configuration struct fields turned out to be empty in the output. The configuration looked something like this:

type DatabaseConfig struct { 
 Host string
 Port int
 User string
 Password string
 Database string
}

Database turned out to be empty. I didn't dwell on it for long and wrote to the agent, "Everything... redo it." It quickly fulfilled my request, the example worked as it should, all fields were non-empty in the output, I was pleased, made a commit, and then decided to see what had actually changed since the last commit.

It turned out that in the configuration file, the key was not named DATABASE (like the struct field), but NAME. Instead of finding the reason for the mismatch and correcting the example, the agent decided that the library desperately needed a synonym system. The decoder gained behavior like this: if the struct contains a field Database, first look for DATABASE, and if it's not found – look for NAME. Moreover, the agent decided that this was an excellent opportunity for other cases as well. The README gained a new library "feature": automatic recognition of commonly used synonyms like SERVER, HOST, PORT, and other keys. That is, I got a working example with the error fixed, a confidently stated report of "100% successful tests," and along with it, a new concept of a configuration synonym dictionary that no one asked for.

The AI did solve the problem, but not in the way I wanted.

"This is 12-Factor Application!"

When I asked the agent to tidy up the README, I mentioned that the library could work with environment variables set directly at the operating system level. For me, this was just one of the library's capabilities. For the agent – the beginning of a grand philosophical discussion. It decided that it was essential to tell me about the 12-Factor Application, and the README gained text stating that the library fully complies with the 12-Factor principles, is magnificently standardized, and suitable for absolutely everything.

I deleted this piece of text, but during the next README edit, the agent added it again. And this happened several times. At some point, I felt like I wasn't editing the README, but fighting with some particularly stubborn marketer. Moreover, the agent, apparently, clearly remembered that we had discussed 12-Factor before, and considered this information so important that it tried to cram it into the text at every convenient opportunity.

I had to explicitly say:

Do not add 12-Factor Application to the README anymore.

And only after that did it give up. And here, again, emerged that "smart tag recognition using synonym search," about which, after every README edit, another mention appeared, which I had previously deleted.

"Since We're Writing a Config, Let's Make It Kubernetes-Ready"

I asked the agent to add support for another configuration loading scenario and, at the same time, to make the interfaces more uniform. Instead of simply changing the interface, the agent decided that the configuration should become as universal as possible. A bunch of abstractions appeared, everything got interfaces, the agent became obsessed with clean architecture and started accompanying everything with factories, builders, etc. The code looked decent, but I caught myself thinking that the code resembled Java. This was the moment when the agent didn't make a technical mistake; it simply over-performed a non-existent task too well. Fortunately, the request to simplify the solution helped the agent reorient itself and get rid of unnecessary abstractions.

I liked this case even more than the others because it clearly illustrates one feature of working with agents: sometimes the problem isn't that the model can't program, but that it agrees too easily with your wording and starts optimizing the solution for all possible future scenarios simultaneously.

What Was the Result

In the end, we got a full-fledged, lightweight, and modular library for working with configuration in Go – goconf. It allows you to assemble application settings from multiple heterogeneous sources in one line: .env files, JSON, YAML, TOML, INI, and system environment variables with deterministic cascading priority (where OS environment variables always have the highest weight).

The main focus is on developer convenience. The library supports the zero-boilerplate concept: it automatically builds hierarchical key paths for nested structures, eliminating the need to manually tag each field. At the same time, a strict validation system works under the hood: from checking types, required fields, and default values to catching typos in configs and supporting custom validation via the Validator interface. For security, a special generic type Secret[T] is implemented, which guarantees that passwords, tokens, and private keys will never accidentally leak into logs, the console, or serialized JSON.

The project is currently released in a test mode under version v0.1.0 because my opinion alone is clearly not enough to confidently claim the creation of a production ready level library. I invite everyone interested to the project's repository. I will gladly accept your Issues and Pull Requests.

I'm particularly interested in feedback on the library's architecture: what can be simplified, where the solution is overcomplicated, what formats should be added. And if you find another greeting from Antigravity in the code – be sure to let me know. Perhaps I haven't noticed it yet.
