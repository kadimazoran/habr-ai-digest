Previously, we discussed the FAIRouter library, which routes requests to the most suitable executor. Currently, executors can only be language models (LLMs), but we plan to add tools and agents in the future. In that article, the question of how the router decides who gets the task was only touched upon briefly. Therefore, we decided to dedicate a separate article to the mathematics behind it, breaking it down step by step: from task features to feedback training.

The project was based on a simple formula that evolved through practical testing. Most of the solutions described below emerged as a natural response to the limitations of the first version. In this article, we will show the development path of the library. Schematically, the routing of a single task can be depicted as follows.

The overall system logic is shown in Figure 2.

A task arrives as natural language text. First, a specification is extracted from it, i.e., a description of what the response should be: length, structure, style, language, and so on. Then, a vector representation of the task is constructed, and this vector is passed to all routing objects. Each object returns a logit, i.e., an unnormalized score of how well it can handle the task. The top K are selected, and a probability distribution is built from their scores using the softmax function with temperature, and an executor is chosen randomly according to this distribution. The choice is saved so that after user feedback or an automatic critic, a gradient can be calculated across the entire chain to update the executor vectors and the critic's projection matrix (more on this below).

The temperature is calculated for each object separately and is inversely proportional to the square root of the number of ratings it was trained on. The more statistics an object has, the lower the temperature, and the closer the sampling result is to argmax, i.e., choosing the best object according to the system. Thus, the balance between exploration and exploitation is regulated automatically. The group temperature is the average temperature across the top K objects. The decision-making process is recorded in the database: which objects participated, the cost and time estimates for each, and the quality rating from a human or automatic critic, as well as actual billing data and time measurements.

We have divided the article into eight parts: the first six describe the operation of the router and judge, the seventh covers the experiment, and the eighth outlines future development directions. Below, we will examine each part.

Selection Time

The selection itself takes milliseconds: features are calculated in 0.02 ms, and selection among 54 candidates takes 0.3 ms. The main time is spent on a single call to the language model, which extracts the specification from the task; for gpt-4o-mini, this takes 1–3 seconds. The judge's response evaluation is performed after the executor's response, in parallel in the C# version and sequentially in the Python version.

There are fast routers that select a model in 70–500 ms, with a median of about 95 ms. However, they do not extract the task specification, so they cannot replace this step. To speed this up, we plan to use our own classifier trained on "query, task" pairs. It will provide the same specification in tens of milliseconds, no longer than 0.1 s, and a version using small models, such as our distilled sbert, in 3–10 ms.

Part 4. Sufficiency Threshold

The score exchanges quality for cost without any restrictions. However, in practice, a different rule is often needed: find those who can handle the task, and among them, choose the cheapest and fastest. There is no point in overpaying for a strong model when an average one will suffice. For this, a threshold is set, i.e., the minimum probability that the response will satisfy a human.

Content Evaluation

Form alone is not enough, as a table with fabricated numbers can easily pass the form check. Therefore, content is evaluated separately from form, based on eight criteria, each from 0 to 1: factual accuracy, completeness, adherence to instructions, correctness of reasoning and calculations, expert depth, structural completeness, quality of sources, and practical applicability. Features not related to the task are not included in the average.

Factual accuracy is calculated based on a list of verifiable statements that the judge extracts from the response (no more than 12). For each statement, the probability that it is true is estimated. This is provided by the judge model or an external verification function if connected:

The verification function receives a statement and returns the probability of its truth or a "verification failed" mark. Thus, an external source, such as a legal database, can be connected to the factual assessment. For references to documents, a single probability per statement is not enough, as three different questions arise: does the document and the specified location within it exist, is the named edition in effect, and does the document say what is attributed to it in the response. The first two questions are checked against the database without a model; the third requires comparing the document text with the thesis. Currently, the function receives the statement as a string, and the parsing of the reference to the number, edition, and thesis is performed by whoever connects the verification.

Therefore, for references to regulations, standards, contracts, rules, and scientific articles, a separate type of statement with these three checks is planned. The score for references will be displayed in the breakdown as a separate line, rather than being averaged with other factual information. A similar approach to statement verification was used in the ExplainitAll library, in its Python and C# versions, and it is also planned to be implemented in the evaluation system.

Part 8. Not Just Language Models

Executor as a Vector

It is worth noting that none of the formulas in Parts 1–6 use the fact that the executor is a language model. The router needs four things: the task vector , the candidate vector , cost and time predictions, and feedback on the result. Feedback is provided by a human or the judge from Part 6, and the judge evaluates the completed response without looking inside the executor. Thus, the algorithm is essentially universal, and a candidate can be any executor with a call cost and execution time: a search service, a code interpreter, a call to an external system, an MCP, or an entire agent with its own step-by-step chain.

For tools, only the method of estimating cost and time changes; expression (9) calculates cost by tokens, while for a tool, it is usually fixed per call or depends on data volume. For an agent, cost and time are summed from steps, so it is more convenient to predict them from the log as an average for similar tasks. The capability filter works the same way: if a tool cannot generate tables, it will not be included in the candidate group for a task requiring tables.

A tool is selected the same way as a model, if it is registered as a candidate, via the execute delegate. Suppose in an agent scenario, one of the steps requires an internet search. Then, "deep search of 3–5 pages" and "quick search of one page" are registered as separate candidates with their own costs and speeds. For a diploma preparation step, the router will assign the task to deep search; for a purchase step, to quick search, and will refine based on feedback where each option is justified. The breakdown of the query into steps and reformulation of search queries is handled by the agent superstructure; in our case, it is MAS. FAIRouter, however, selects the executor for each step, whether it's a model or a tool, but currently does not configure tool parameters.

With the increase in the number of heterogeneous executors, there is an opportunity to develop the scheme further. The temperature (13) is the same for the entire group and describes the candidate's familiarity as a whole, not in specific task areas. For several models with similar strengths, this is sufficient; however, tools and agents are structured differently: a DSL (domain-specific language), for example, is strong in a narrow class of tasks, and it is useful to know its familiarity in each area separately. Therefore, we associate further research with a more complex task selection problem.

State of Research

The plan for future work includes comparing LinUCB and Thompson sampling with the current FAIRouter scheme, with an ε-greedy strategy, and with selection based on temperature over ridge regression. The model from Part 7 is being made more complex: 10–20 candidates with real costs, human evaluation only on a portion of moves and with a delay, the appearance of a new strong and cheap model in the middle of a run. After that, testing on the RouterBench dataset is planned, where the answers of all models are known for each query.

Language model routers based on LinUCB have already been published, for example, by PILOT (Panda et al., 2025) and Poon et al. (2025). Therefore, we see novelty not in the application of LinUCB itself, but in its integration with task specification, a judge based on form and content features, a sufficiency threshold, and also in extending this scheme to tools and agents.
