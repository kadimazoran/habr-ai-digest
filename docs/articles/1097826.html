Introduction

Hi everyone! My name is Dina, I'm a Java developer with about six years of enterprise experience. Since April, I've been working on a pet project with an AI agent: it wrote the code, I set tasks and watched the tests. Everything was going well: tests were green, scenarios were closed, and then I opened the project and realized I didn't clearly understand how the main scenario worked: from request to finished video. This article is about how I regained understanding of my own code.

The Problem: Code Appears Faster Than Understanding

Neural networks write code astonishingly fast: what would take a day by hand, the agent types in minutes. But in this speed, it's easy to miss one detail: if you didn't write the code, but only watched it, your involvement isn't as high.

Imagine that before AI agents, you were told: "From today on, you won't write code. Features will be done by another developer, and you'll only review their pull requests." I haven't met a developer who, while reviewing a PR, delves into it so deeply as to know the code better than the author. Involvement is still lower.

With agents, we've all found ourselves in this role.

Now, situations like this are possible: a colleague generated a lot of code and quit. A new person comes in their place, opens the project, and doesn't understand where to start.

I became that colleague to myself: in my pet project, I generated code with incredible speed, and didn't spend much time on review. Involvement decreased, but it wasn't noticeable at the moment.

Cognitive Debt

This problem has a name – cognitive debt. The term itself has been around for a while: for example, in a 2025 MIT Media Lab study "Your Brain on ChatGPT" about how AI assistants affect essay writing. In development, it was popularized by Margaret-Anne Storey, a professor at the University of Victoria. Her idea was picked up by Simon Willison and Martin Fowler.

Technical debt lives in the code: workarounds, bad architecture, lack of tests. Cognitive debt lives in people's heads: the team stops understanding what the system does, why it's designed that way, and how to change it safely. The code itself might be perfectly clean.

I like to compare it to a loan: if you don't understand what the neural network generated, you haven't sped up your work, you've taken out a loan. You'll have to pay it back later, when something breaks in the code that no one understands. And you'll pay with interest.

Storey describes a student team she supervised. The team worked together, under the professor's supervision, and still by the eighth week, they couldn't make even a simple change without breaking something in an unexpected place. At first, they blamed technical debt, but the issue was different: no one on the team could explain why certain decisions were made or how parts of the system were connected. Cognitive debt accumulates unnoticed, even when everyone is trying.

There are numbers too. In January 2026, Anthropic conducted a randomized experiment: 52 developers, mostly juniors, were learning an unfamiliar asynchronous Python library, Trio. Half performed the task with an AI assistant in a chat window. On a test of the material just learned, the group with AI scored an average of 50%, while the group without AI scored 67%. The lag was most significant in debugging questions. Meanwhile, the AI only sped up the work by about two minutes, and even this acceleration was statistically insignificant.

The most interesting part of this study isn't the average numbers, but how people worked with AI. Those who completely delegated code writing to it scored less than 40%. Those who first generated code and then asked questions to understand it, or asked for explanations along with the code, scored 65% and above. And this was with a regular chat. The authors themselves believe that with agents like Claude Code, which write entire code blocks, the effect will likely be even stronger.

My Personal Experience

I'll tell you how not understanding the code became a point of no return in my project.

It happened during spec generation. I was following a process where the agent itself breaks down the story into scenarios, writes tests, then code, then refactors and conducts a review. At each step, it adds a report of its work. At some point, I calculated the volumes:

  • product code: about 3,150 lines;

  • agent specs and reports: 13,260 lines, 4.2 times more than the code;

  • just the progress file for the second story: 5,821 lines, 1.8 times more than all the product code.

I physically couldn't read such a volume. The agent generated specs that I stopped understanding, and it took the wheel: it became the main pilot consulting me, not the other way around. I only saw green tests and closed scenarios, but control was lost.

Method: Linear Walkthrough and Interactive Explanation

I took the idea from Simon Willison's chapters "Linear walkthroughs" and "Interactive explanations" from his guide Agentic Engineering Patterns. Claude Code wrote him a word cloud utility, but the phrase from the report about "placement along an Archimedean spiral" didn't explain anything to him. A linear walkthrough helped understand the code structure, but not the algorithm itself. However, an animation showing how each word tries to find its place and moves along the spiral finally made the algorithm understandable.

It's important that these are two steps: first a text walkthrough, then an animation that builds upon it. I adapted them for my pet project Avatar – a service that generates video through a paid API of an external provider.

Stack: Java 17 and Spring Boot on the backend, React and TypeScript on the frontend, Postgres (H2 locally), Gradle build. The architecture is clean: domain, usecase, adapters. The code is written by Claude Code, and the walkthrough and animation were also done by it.

Step 1. My Prompt for Linear Walkthrough

Read the source code of [path to video generation module].  Plan a linear walkthrough: in what order should the code be explained so that someone who didn't write it understands the entire path from the video generation request to receiving the result, including errors and timeouts.  Write the walkthrough in walkthrough.md.  Insert code snippets using shell commands (grep, sed, cat) directly from files, not by retyping them manually. Explain not only what the code does, but also why it's designed that way.  

The requirement to insert code using commands, not retyping, is key. This makes it much harder for the agent to accidentally "improve" a quote or invent a line that isn't in the code: under each quote, there's a command, and you can run it yourself.

Step 2. Prompt for Interactive Animation

Read walkthrough.md completely.  Based on it, create the result-flow.html page, which animatedly shows how video generation works in my project: which components are involved, how the application waits for the result, what happens on error, retry, and timeout. Use dummy data and simulated time, no real API calls. Add a scenario switcher (success, error with retry, timeout), pause, speed control, and step-by-step forward and backward mode. At each step, show the state of each component and which code snippet is currently executing.  

I specifically added error and timeout scenarios. In asynchronous code, the most confusing part isn't the happy path, but what happens when something goes wrong.
