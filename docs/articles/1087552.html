Currently, the Jev model from Typesafe is widely discussed. I've decided to release my model in CMF format for personal use (License:apache-2.0), which has been operational on the gateway for a long time.

How does it work? For example, a user writes that their card hasn't arrived. The application needs to select card_arrival and route the request to the appropriate handler, or write a Go function. Decisions must be made as quickly as possible. There are many such decision points: selecting an agent tool, determining the topic of a request, its complexity, sending a document for verification, determining task complexity and type.

For these tasks, I've published CMF Decision: a model that makes decisions based on reconstruction error. The encoder, trained skills, and confidence rules are all in one .cmf file. New skills can be added using your own examples, and unfamiliar cases can be passed to a pluggable oracle-model that acts as a teacher.

In Cortiq 0.8.0, the same file runs on CPU, Apple Metal, and Vulkan. On an RTX PRO 4000 Blackwell, the full local path took 1.10–1.24 ms.

Below is how this mechanism works, what the results are compared to Jev and Laya, and how to run the model or add your own task.

First, a Decision, Not a Response Text

In the usual scheme, we ask a generative model to write a category name and then parse the response. Here, the local path works differently:

  1. The encoder translates the text into a feature vector.

  2. Each trained topology attempts to reconstruct this vector.

  3. Reconstruction errors are compared. The topology that best fits determines the class.

  4. Confidence and novelty thresholds decide whether to accept the answer or refuse.

Resonance here means the correspondence of the input signal to a trained topology: the smaller the reconstruction error, the better the correspondence. There is no separate trainable network predicting the number of the required topology.

In the current CMF Decision, the class topology is its average vector and a set of directions in feature space. We subtract the mean, sequentially remove components along these directions from the remainder, and calculate the squared norm of the remainder. The smallest error wins. This is the same selection principle I use in the Resonance Routing patent — US 19/452,440.

Practical implication: for a new skill, it's not necessary to retrain the entire encoder. You can train individual topologies on your own examples and package them together with existing skills.

Why a Separate Format for This?

CMF here is not just another weight file extension. The container consistently stores:

  • encoder and tokenizer;

  • descriptions of skills and allowed responses;

  • topology parameters;

  • calibration and decision-making rules;

  • data for integrity checks and skill training.

There's no need to separately transfer the category dictionary, classification script, and threshold file, hoping their versions will match. The file is opened by the Cortiq engine via both CLI and HTTP API. No conversion to another format is needed for GPU.

The finished model is 304.5 MB and contains three skills for BANKING77, CLINC150, and MASSIVE. This is a starting set, not a format limitation to three tasks.

The model can even be run on a mobile phone and used as an API gateway, with high decision speeds of about 20ms per decision (depending on the phone model). Android App

High Confidence Does Not Mean an Answer for Every Request

In a production system, it's useful to be able to refuse. For example, on BANKING77, the model accepted 90.62% of requests; among the accepted answers, 97.24% were correct.

This is a different metric, not a replacement for the 93.34% in the table. If complex cases are sent for review or to an oracle, you need to look at both the accuracy of accepted answers and the proportion of locally handled requests.

What About Comparing with Local Laya?

Laya also makes decisions without generating responses. Here, we can remove the network from the comparison: both models are run on the same Apple M4. CMF uses Metal, Laya uses MPS. The oracle is disabled. We compare the trained CMF skill with Laya's base English model, feeding it all 77 options at once.

On all 3,080 BANKING77 examples, the trained CMF skill achieved 93.34% with a median of 3.10 ms. Laya, which received descriptions of all 77 labels without retraining, achieved 35.65% and 917.59 ms.

In CMF, the task is already saved in the skill; Laya reads the options with each request. The practical implication here is to train a permanent decision point once and then use it locally many times.

This is a stress test with a large number of options, not Laya's full potential. Its author recommends pre-filtering a large list of candidates; a multilingual model is provided for long inputs. These modes were not tested here. Different training also does not allow us to declare a universal victory for one architecture. The new measurement does not replace the individual CPU/GPU series below.

To avoid limiting ourselves to short label names, we pre-selected three test queries for each class — 231 in total — and gave Laya two training examples per label. This configuration did not work reliably: 206 out of 231 responses fell into one label, with accuracy dropping to 1.73% compared to 35.50% with short descriptions on the same queries. This is not Laya's "usual accuracy," but a failed mode with a long list of examples. Increasing the token limit does not inherently make the model suitable for such input.

What Did Porting to GPU Achieve?

I accelerated not only the resonance core but the entire local path from text to decision: feature preparation, encoder, reconstruction, and final selection. The tables below do not include model loading, network, or external oracle.

On Apple M4, the median decreased by 14–26%: to 2.28–2.58 ms depending on the dataset. CPU and GPU were tested sequentially on the same texts; the Mac remained a regular workstation during this time.

On RTX PRO 4000 Blackwell, in a continuous series, it was 1.10–1.24 ms: 14–20 times faster than the native CPU path on the same server with a Xeon E5-2690 v4. First, CPU benchmarks were calculated, then a series of warmed-up GPU requests.

The graph panels have different scales and query submission modes. These are CPU/GPU comparisons within each benchmark, not an M4 vs. RTX performance ranking, nor a measurement of server performance under parallel load.

The Most Unexpected: Pauses Also Affect Speed

If a CPU benchmark is run between requests on the RTX, the graphics card has time to idle and reduce memory frequency. In a separate diagnostic on 400 examples of each dataset, the Vulkan median was already 3.40–8.57 ms, not around 1.2 ms. The logs showed reduced memory frequencies corresponding to this. We did not forcibly change frequencies or power limits.

On M4, there's another peculiarity: Metal shares the GPU with the desktop. The median may improve, while rare delays may worsen. In one of the additional continuous series on MASSIVE, Metal turned out to be slower than the CPU.

Therefore, the CPU remains the default option, and the GPU is explicitly enabled. For a specific application, it's worth checking not only the average throughput but also rare requests after pauses. All modes, p95/p99, and memory measurements.

What Exactly Was Optimized?

The main gain came not from porting each small operation to the GPU individually, but from organizing the entire computation:

  • weights and intermediate data remain on the device;

  • encoder and reconstruction are performed in a single command submission, without CPU waiting between layers;

  • some operations are combined to avoid writing and reading unnecessary intermediate arrays;

  • sequential update of the remainder during reconstruction is preserved, including for non-orthogonal bases.

Computations remained FP32: without retraining or switching to FP16. Across all 10,554 examples of each full run, the selected classes and refusal decisions matched. This is preserving quality after optimization, not a new improvement in model accuracy.

Optimization comes at the cost of memory. In the HTTP check of the published 0.8.0, the process occupied about 808 MiB RAM on M4/Metal and 648 MiB RAM plus 522 MiB VRAM on RTX/Vulkan. These are snapshots after requests with three loaded skills, not peak consumption. We do not have comparable memory data for Jev servers.

What About API Speed?

In a previous client measurement, Cortiq via HTTPS had a median of 70–79 ms, and Jev via OpenRouter had 346–392 ms. These numbers include network latency; servers, parallelism, and sample size varied. They cannot be divided by the local 1.2 ms to declare the resulting number as model acceleration.

A useful practical conclusion is simpler: fast local selection can be placed next to the application and avoid adding a network call for every handled task.

How to Try It

For a first look, there's a CMF Decision interactive demo on Hugging Face Spaces. Enter a query, select a skill, and see the decision, confidence, and reconstruction errors of the top three candidates. No installation or API key is needed; the demo runs on CPU, without an oracle.

Ready-to-Use Service Without Installation

If you don't want to deploy the model yourself, you can use the allaigate Routing API — a ready-made routing service based on the CMF format. Get an API key on the website and connect the service to your application according to the documentation. You don't need to download the model or configure a server for this.

Local Launch: One Installation, One File

Rust 1.88 or newer is required. Install the latest version from crates.io:

cargo install cortiq-cli --locked

Download the model and make the first request:

curl -fL -o cortiq-decision.cmf 
  https://huggingface.co/infosave/cmf-decision/resolve/main/cortiq-decision.cmf

cortiq decide cortiq-decision.cmf --skill banking77 \
  -p "I still have not received my new card"

In this control example, the model locally selects card_arrival. No cloud API key is needed for local decisions.

GPU support is already included in the standard installation. On Apple Silicon:

CORTIQ_DECISION_DEVICE=metal cortiq decide cortiq-decision.cmf \
  --skill banking77 -p "I still have not received my new card"

On a machine with a hardware Vulkan driver:

CORTIQ_DECISION_DEVICE=vulkan cortiq decide cortiq-decision.cmf \
  --skill banking77 -p "I still have not received my new card"

If you have multiple graphics cards, add CORTIQ_DECISION_VULKAN_ADAPTER with a unique part of the desired card's name. The same device selection works for cortiq serve; /healthz shows the actual adapter. GPU errors are not masked by an imperceptible fallback to CPU.

Adding Your Own Skill

Suppose you now need to distinguish between delivery, billing documents, and subscription cancellation. Prepare train.jsonl: one phrase and its label per line. Here's a fragment of the format, not a complete training set:

{"text":"My parcel has not arrived yet.","label":"delivery"}
{"text":"Where can I download my invoice?","label":"billing"}
{"text":"I want to cancel my subscription.","label":"cancellation"}

Different examples are needed for each label. One line per label does not create a working topology. Below is a small complete set on which the commands in this section were tested; it's for getting acquainted with the tool, not for evaluating quality on real requests.

Describe the meaning of the options in question.json:

{
  "instructions": "Choose the support department for this customer request.",
  "criteria": {
    "delivery": "Delivery, shipment tracking and missing parcels",
    "billing": "Invoices, receipts and billing documents",
    "cancellation": "Cancelling subscriptions and membership renewals"
  }
}

Add the skill, verify the new file, and use it:

cortiq decision add-skill cortiq-decision.cmf --skill support \
  --train train.jsonl --question question.json -o support.cmf

cortiq decision verify support.cmf

cortiq decide support.cmf --skill support \
  -p "Please send me a copy of the invoice for my last payment."

The verified result for this example is billing. Old skills remain in support.cmf; the original file is not overwritten. On the small training set, the skill has certified: false: statistical reliability cannot be obtained from a few successful requests.

If you need a separate model with only your skill, use instead of add-skill:

cortiq decision train --encoder cortiq-decision.cmf --skill support \
  --train train.jsonl --question question.json -o support-only.cmf

You can configure both the data and the topology size: --k sets the number of directions per class, --calibration is a separate calibration set. Verify the results on data that was not used in training or parameter tuning. For a JSONL file test.jsonl with text and label fields:

cortiq decide support.cmf --skill support \
  --input test.jsonl --bench --out predictions.jsonl

API and Oracle for Unfamiliar Cases

The local server starts with a single command:

cortiq serve cortiq-decision.cmf

By default, it listens only on 127.0.0.1:8080. Until keys are created, a local control request looks like this:

curl -s http://127.0.0.1:8080/v1/route \
  -H 'Content-Type: application/json' \
  -d '{"input":{"text":"I still have not received my new card"},"taxonomy_id":"banking77"}'

There is also a typed protocol state + questions, familiar from Jev/OpenRouter: /v1/decisions and /api/alpha/decisions. Skills are answered locally, and for an unknown contract, you can explicitly allow querying the oracle. API request examples and settings.

As an oracle, you can connect, for example, MiMo‑V2.6-Flash. Stop the previous server and run the version with a budget limit:

export OPENROUTER_API_KEY="<your OpenRouter key>" 

cortiq serve cortiq-decision.cmf --state ./decision.state \
  --oracle xiaomi/mimo-v2.6-flash --oracle-budget 1

Handled requests are still resolved locally. Only uncertain cases may go to the cloud; oracle responses are cached. The quality and GPU latencies shown above were measured without the oracle — MiMo's results are not attributed to them.

For training via the server, you need a key with the appropriate permission. You can create it before starting the server:

cortiq decision keys create --state ./decision.state \
  --account demo --plan developer --learning-allowed

After creating the key, pass it in the Authorization: Bearer <Cortiq key> header. In keyless mode on loopback, oracle responses are cached but do not train the model.

Self-learning is not an immediate replacement of weights with an LLM response. Examples are accumulated, a separate topology candidate is trained, and it is compared with the current version on control data. An accepted update can be saved as a new CMF version or rolled back. The immutability of other people's weights is checked separately from quality: a new candidate may still start winning against old classes on some requests. Learning and rollback mechanism.

What's the Result?

For me, the main result is not a single impressive latency figure. A trained skill has become a portable artifact: it can be added to CMF, tested, run alongside an application, and transferred from CPU to GPU without repacking the model.

For mastered tasks — a short local path without response generation and without paying for a cloud API. For new tasks — custom examples and trainable topologies. For uncertain cases — explicit refusal or an oracle with a specified budget.

This is the direction of CMF Decision: not to force a universal generative model to solve an already mastered decision point anew each time, but to save such decisions in skills managed by the developer.
