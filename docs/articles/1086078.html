I view Jev as a model for rapid decisions, not another chatbot. You can feed it a market state snapshot and typed questions, and in return, get scores with probabilities. Such a mechanism can be integrated into a trading system that continuously analyzes the order book, checks signals, and manages orders.

In this article, I will break down how such a high-frequency trading (HFT) loop works: where the model's work ends and regular code begins, how to ask questions to Jev, what checks to implement before sending orders, and how to measure system quality.

About Jev in brief

The model was released by TypeSafe AI. Its founder is Diogo Almeida, one of the researchers behind ChatGPT and InstructGPT. Jev does not generate free-form text or explain its reasoning. Instead, it answers pre-formulated questions in a specified format: selecting an option, returning a number, or assigning a score.

According to TypeSafe, the cost is $0.042 per million input tokens, with output tokens being free.

As an example, I present a working market-making bot on Monad. It reads the MON/USDC order book on Kuru, queries Jev on each block (approximately every 300ms), and places a limit order one tick closer to the market price. According to the repository, it gained over a thousand stars in three days, with some decisions arriving in as little as 81ms.

The decision-making mechanism itself does not constitute a trading system. It requires data collection, feature calculation, action policy, risk management, order execution, and performance monitoring. Jev should only be responsible for a portion of the evaluations within this loop.

1. What is Jev and why I consider it for HFT

TypeSafe calls Jev a "System 1" model – the fast, intuitive part of thinking, in Daniel Kahneman's terminology. The idea is that many decisions within a program don't require lengthy reasoning: you need to determine which category an object belongs to, assess urgency, or understand if an order flow resembles informed trading.

It's easier to understand how Jev works with this visualization:

A language model typically converts input data into a sequence of tokens, then outputs text that the program must parse. Jev receives the market state and questions with pre-defined response formats. It returns structured values and confidence in them – without free text, parsing, or JSON correction.

I use three response formats:

  • Noul returns a number between 0 and 1. For example: "How likely is the order flow to be toxic?" - 0.83.

  • Choice selects an option from a list, which can have up to 255 items. For example: trending regime - 0.63, mean reversion - 0.22, chaotic - 0.15.

  • Score evaluates a state on a given scale. For example: "How suitable is the market for quoting on a scale of 0 to 3?" - 2.3.

All three formats can be combined into a single call. Questions are evaluated in parallel and independently; I assume that adding more questions barely increases latency. The speed is related to two features:

  1. Jev is not an autoregressive model: it doesn't generate tokens one by one but calculates probability distributions for response options in parallel. Therefore, six questions might take roughly the same amount of time as one.

  2. The model is trained using RLCD (Reinforcement Learning for Calibrated Decisions). According to TypeSafe's description, it calibrates probabilities to actual outcomes, not human preferences. On average, higher confidence should correspond to higher accuracy.

The context window is 32,000 tokens. This is sufficient for a compact market snapshot and recent trades, but not for loading an entire strategy. Jev provides narrow assessments, and the rest of the logic is handled by code.

Where Jev fits into the latency budget

In co-located infrastructure for stock trading, latencies are measured in microseconds. I don't consider Jev for such scenarios: they require Field-Programmable Gate Arrays (FPGAs) and C++.

Blockchain stacks have a different pace. Monad blocks appear approximately every 300ms, Solana slots around every 400ms. Jev can fit into such a cycle along with order execution. For tactical assessments – such as market regime, flow toxicity, or strategy selection – the horizon is typically seconds.

2. Architecture: the model assesses, the code decides

The main principle of the entire system: Jev should not manage the trading bot entirely. It is assigned specific assessments, and the code handles the rest of the work.

Do not send the model a request like "Look at BTC and tell me what to do." To answer, it would have to simultaneously reconstruct the market state, estimate probabilities, account for fees and risk, choose a position size, and guess execution rules.

It's more reliable to divide responsibilities:

  1. The code collects data and calculates the state.

  2. Jev assesses features that are difficult to describe with a set of hard rules.

  3. The policy in the code matches assessments with thresholds and selects an action.

  4. The executor sends or cancels an order.

  5. Hard risk constraints can prohibit an action at any stage.

All precise calculations remain in the code: average price, spread, imbalance, realized volatility, position size, drawdown, VWAP, and queue position. There's no need to pay for a model call to perform arithmetic.

You can ask Jev, for example, about the market regime, the informativeness of aggressive flow, the quality of a trading opportunity, or execution degradation. Each question should be atomic. If an assessment depends on multiple factors, it's better to break down the request into separate questions and combine the results in the code with specified weights. When priorities change, you only need to adjust the coefficient, not rewrite the prompt.

The hard constraint layer always has the final say. The model can suggest an action, but it cannot override position limits or emergency shutdowns.

3. Setting up Jev from scratch

Below, I follow the official TypeSafe quick start guide.

Step 1. Apply for access

You can leave a request for access at typesafe.ai. I note that some users get access the same day.

Step 2. Install the official skill

The skill helps the agent call Jev correctly:

npx skills add typesafe-ai/skills --skill typesafe-ai

In Claude Code, two commands are needed. Simply adding to the marketplace is not enough – you also need to install the plugin:

claude plugin marketplace add typesafe-ai/skills
claude plugin install typesafe@typesafe-ai

Step 3. Create an API key

The key is created in the TypeSafe dashboard. You can then pass it to the client via an environment variable:

export TYPESAFE_API_KEY="your-key"

Step 4. Install the SDK

For Python, version 3.10 or newer is required:

# Python
pip install typesafe-sdk

# TypeScript
npm install @typesafe-ai/sdk

# Rust - for the execution layer
cargo add typesafe-ai-rs

In the example below, the lines with questions are left in English, as in the original.

Step 5. Execute the first request

The client reads TYPESAFE_API_KEY and by default connects to jev-latest:

from typesafe_sdk import Choice, Noul, Score, TypeSafeClient

client = TypeSafeClient()

state = {
    "mid": 3.4127,
    "spread_bps": 3.5,
    "imbalance": 0.71,
    "realized_vol_5m": 0.034,
    "inventory": -120,
    "aggressive_buy_ratio": 0.63,
}

response = client.system_one(
    state=state,
    questions={
        "regime": Choice(
            instructions="What market regime does this state describe?",
            criteria={
                "trending": None,
                "mean_reverting": None,
                "chaotic": None,
            },
        ),
        "toxic_flow": Noul(
            instructions="Is aggressive flow likely informed rather than noise?",
        ),
        "quote_environment": Score(
            instructions="How favorable is this state for providing liquidity?",
            legend={
                "0": "Do not quote",
                "1": "Marginal",
                "2": "Standard",
                "3": "Excellent",
            },
        ),
    },
)

For HFT, I recommend connecting directly to the API – via POST https://api.typesafe.ai/v1/systemone. Any intermediate gateway adds network latency, which can be critical under strict latency limits.

You should also fix the model version and record it with each response. Confidence thresholds are tuned for a specific version; an unnoticed model update can disrupt their operation.

4. State snapshot and batch of parallel assessments

Two key components are the state engine and the assessment batch. The state engine is regular deterministic code. On each block, it generates a compact snapshot of less than 400 tokens.

It can include:

  • Price: mid, microprice, and returns for 1, 5, and 30 minutes.

  • Order Book: spread in basis points, depth at three levels, imbalance, and queue position.

  • Order Flow: aggressive buy and sell volume, trade and cancellation frequency.

  • Volatility: short- and medium-term realized volatility, comparison with 24-hour regime.

  • Other Exchanges: divergence from a benchmark exchange, basis, and funding.

  • Position: inventory, unrealized profit or loss (PnL), drawdown, and position holding time.

  • Execution Health: fill rate, rejections, slippage, and the last ten latency values.

I highlight three rules:

  1. The snapshot must be dense and numerical: input tokens incur a fee.

  2. Timestamps require special discipline. Each field must only consider data available before the decision point.

  3. You must save each snapshot along with the decision and subsequent outcome. These records will become calibration data.

A single "buy or sell?" question is fine for a demonstration, but in a production system, I would send a whole batch of assessments in one call. In my estimation, batching provides approximately a 12x cost saving compared to individual requests:

response = client.system_one(
    state=snapshot,
    questions={
        "regime": Choice(
            instructions="Regime?",
            criteria={
                "trending": None,
                "mean_reverting": None,
                "high_vol": None,
                "crisis": None,
            },
        ),
        "direction": Choice(
            instructions="Bias next 10 blocks?",
            criteria={"up": None, "down": None, "neutral": None},
        ),
        "toxic_flow": Noul(
            instructions="Is aggressive flow informed?",
        ),
        "liquidity_stressed": Noul(
            instructions="Book thinner than 24h norm?",
        ),
        "quote_environment": Score(
            instructions="Favorable to provide liquidity?",
            legend={"0": "No", "1": "Marginal", "2": "Standard", "3": "Excellent"},
        ),
        "inventory_pressure": Score(
            instructions="Urgency to cut inventory?",
            legend={"0": "None", "1": "Mild", "2": "Skew hard", "3": "Reduce now"},
        ),
    },
)

Six assessments in one request – one latency. I estimate the cost of such a batch at approximately $0.00001 per block.

The code then applies thresholds and selects an action. A conditional example:

def compose_action(ans, snap, limits):
    if snap["drawdown"] > limits.max_drawdown:
        return KILL

    if ans["toxic_flow"].noul > 0.6:
        return PULL_QUOTES

    if ans["liquidity_stressed"].noul > 0.7:
        return WIDEN

    quote = ans["quote_environment"]
    if quote.score >= 2.0 and quote.confidence > 0.80:
        skew = inventory_skew(ans["inventory_pressure"].score)
        return quote_both_sides(skew=skew)

    if quote.score >= 1.0:
        return quote_wide()

    return STAND_DOWN

Three principles are important here:

  • Thresholds are set in the code, not delegated to the model.

  • Different thresholds can be set for different actions, considering the cost of error.

  • The fractional Kelly criterion (2p − 1), limited to a quarter, is only meaningful with a reliably calibrated probability p. In my opinion, applying it to probability logarithms from a standard LLM without calibration is pointless.

5. Continuous loop, risk engine, and emergency mode

Now we can assemble a loop that justifies round-the-clock operation.

The core mathematics of market making has been known for about half a century, so its place is in deterministic code. On each block, the pricing engine calculates the reservation price and spread using the Avellaneda-Stoikov model:

reservation price r = mid − inventory × γ × σ² × (T − t)
half spread      = γ × σ² × (T − t) + (2 / γ) × ln(1 + γ / κ)

Jev only answers the question that the formula cannot answer on its own: is it worth quoting at all under current conditions?

The full loop looks like this:

  1. Receive a new block event via WebSocket newHeads; in case of failure, use a fallback polling mechanism.

  2. Read the Level 2 (L2) order book: best bid and ask prices, depth.

  3. Assemble a deterministic state snapshot of less than 400 tokens.

  4. Get a batch of six Jev assessments in a single call.

  5. Formulate an action in the policy engine.

  6. Calculate the reservation price and spread using the Avellaneda-Stoikov model.

  7. Check hard risk constraints. If violated, any action is canceled.

  8. Cancel old quotes and place new limit orders that add liquidity.

  9. Record the result, account for fills and PnL, update the position, and proceed to the next block.

Each stage is a separate module with its own failure conditions. At module interfaces, manual assembly often turns into lengthy debugging, so I pre-define and verify component interactions.

Two conditions are particularly important:

  • Do not trade on stale data. If Jev doesn't return before the next block, you must skip the cycle, not send a quote based on an old snapshot.

  • Account for fees in advance. In the jevons critique project fork, an estimate is provided showing that naive cancellation and re-quoting on every block costs approximately 428 MON per hour with a 3.5 basis point spread. The system will have to account for a wider spread, less frequent re-quoting, or the real advantage of a directional signal. I recommend repeating this calculation for your network and strategy before placing real orders.

Hard risk limits

The risk engine should not delegate limits to Jev. Before each order, regular code checks at least:

  • maximum position and order size;

  • daily loss and maximum drawdown;

  • maximum inventory holding time;

  • age of market data;

  • leverage;

  • number of API errors;

  • maximum decision latency.

Each limit must be checked independently of the model's assessment. For example, you can check if a file with the execution result exists or if a metric has dropped below a set threshold.

Fallback scenario

For continuous operation, a pre-defined plan is needed for delays, low confidence, or model unavailability:

State

Action

System operational, high confidence

Normal trading

System operational, low confidence

Reduce position size or refrain from entering

Response not received before the next block

Skip the cycle; do not place stale quotes

Jev unavailable

Switch to a deterministic fallback algorithm

Hard limit breached

Halt trading, close positions, and send an alert

With such a plan, the system can be considered autonomous. Without it, it only functions until the first network failure.

I would consider blockchain stacks with block-level update frequencies for independent developers – Monad via Kuru, Solana DEX platforms, and Hyperliquid – as well as prediction markets with wide spreads of 200–500 basis points. The 300ms cycle is irrelevant to the microsecond trading of major US stocks.

6. Calibration and applicability limits

You need to test not only whether Jev guessed the price direction correctly but the entire trading policy as a whole.

I propose comparing four variants on identical data, features, costs, and limits:

  1. manually written rules;

  2. a system with a leading LLM;

  3. a system with Jev;

  4. Jev with confidence thresholds that allow the model to abstain from making a decision.

For each variant, you should measure Sharpe and Sortino ratios, maximum drawdown, win rate, slippage, adverse selection losses, cost per million decisions, and coverage rate.

A separate research question is whether the confidence filter helps: does Jev perform better when it skips dubious situations than when it is forced to answer every query? If the model is calibrated, such a filter should improve portfolio quality.

Calibration also needs to be verified. If the model estimates an 80% probability of an increase, do events with such an assessment actually occur about 80% of the time on your specific venue? To check, compare predicted probabilities with actual frequencies and calculate the Brier score, log loss, and Expected Calibration Error using the saved "snapshot - decision - outcome" triplets.

RLCD calibrates responses on TypeSafe's data, not yours. If the reliability curve deviates from the actual frequency, I would apply Platt scaling at the policy level.

What Jev can do – and what not to expect

Jev can:

  • return typed decisions with calibrated probabilities in 70–500ms;

  • assess dozens of independent questions in parallel with the latency of a single question;

  • accept up to 255 response options and a context of up to 32,000 tokens;

  • operate within a blockchain cycle with a 300ms interval;

  • replace some fuzzy rules, classifiers, heuristic assessments, and market regime detectors;

  • participate in Kelly criterion calculation after calibration checks;

  • execute a batch of assessments on each block for $10–25 per month – this is my estimate for the specified configuration, not a universal price.

Jev cannot:

  • generate text or design a trading strategy;

  • solve interdependent questions in a single call: each is evaluated separately, dependency requires a second request;

  • compete in the microsecond range;

  • replace market data collection, numerical calculations, exchange connectivity, or hard risk constraints;

  • guarantee TypeSafe benchmark results on your workload;

  • turn a losing strategy into a profitable one.

Jev can make individual decisions faster and cheaper. You still need to find and validate your trading edge independently.

Conclusion

Jev is not just a smarter language model, but a different type of tool: a decision engine that returns structured assessments with probabilities within a single blockchain cycle.

A working system doesn't ask Jev to "trade." It calculates everything calculable with regular code, sends a compact market snapshot, receives a set of atomic assessments, and passes each action through confidence thresholds and hard risk constraints. The price and spread are calculated by deterministic code; the model helps assess what is difficult to express with a formula.

I chose Jev not because it's the newest model on the market. I separate the system into deterministic calculations and probabilistic assessments, and then check if a calibrated model is suitable for the latter part. Records of decisions and their outcomes are needed not only for auditing: they help me check calibration and improve the system.

I pose this question to the developer: wait several seconds for a text response from a chat model, or ask six typed questions and get assessments before the next block?
