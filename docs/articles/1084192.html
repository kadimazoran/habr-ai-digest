One paragraph, one lost condition

Source:

Export is available on the Pro plan with two-factor authentication enabled. The link to the archive is valid for 30 days. The service does not save the original text.

Suppose, in response to a request to shorten the text, the following version was produced:

Export is available on the Pro plan. The link to the archive is valid for 30 days. The service does not save the original text.

It reads smoothly. The condition about the plan remains, the validity period hasn't changed, and the promise not to save the original text is also in place. The condition about two-factor authentication has disappeared. The user will buy Pro, open the export, and discover a requirement that the instructions remained silent about.

In the payment example, the list would be very short: "Anna received 30,000" and "Boris received 50,000". It immediately highlights the error that the list of names and sums misses.

Loss of negation and its inversion

These are useful signals: in a long instruction, it's hard to catch every changed digit. But a signal relates to a specific check. A zero return code does not make the entire new text correct.

There is also a less obvious detail in the output: for replacing 30 with 90, the changed field is zero. The difference lies in lost and added. If you only look at changed, you might miss the discrepancy detected by the program. With the --no-additions flag, any addition of an extracted element results in a return code of 1, even if there are no losses.

How to catch a known condition

Let's return to the export. If an important phrase is known in advance, it can be explicitly protected. In protected.txt, we will write:

with two-factor authentication enabled

Add the file to the comparison:

humanizer-facts diff before.txt after.txt --protect protected.txt --no-additions --json

Now the check returns code 1. The lost list includes an entry of category protected with the value "with two-factor authentication enabled".

Such a signal indicates that the protected wording has disappeared and points to the location for manual verification. However, the following example shows why it cannot be given the final word:

Export requires the Pro plan and two-factor authentication enabled. The link to the archive is valid for 30 days. The service does not save the original text.

The phrase has been rephrased, but all four assertions from our table are in place. The protected string in its previous form is no longer present. If you demand its literal presence, you will have to reject this edit as well.

Therefore, protected should be read as "check this place." If the condition has disappeared, return the text for editing. If it has been preserved in a different wording, accept it after comparison. Otherwise, instead of an editor, you'll get a comma guardian.

The most useful work happens before the model request

Here is the prompt for our paragraph:

Make the text simpler. Preserve the four assertions: 
1. Export requires the Pro plan. 
2. Two-factor authentication must be enabled for export. 
3. The link to the archive is valid for 30 days. 
4. The service does not save the original text. 
Do not add new features or promises.

The list here serves two purposes: it sets the task for the editor and remains with us for accepting the result. It is also useful when editing by a human.

What to check before publishing

Save the source. Write down the conditions, deadlines, negations, and relationships from it: who pays whom, who has access to the function, what needs to be done in advance. After editing, compare each point with the new version. Checking numbers and some other elements can be entrusted to a utility; assertions on which the reader's action depends should be read in full.

For a short text, this is a few lines next to the draft; for a long one, it's a list to return to after edits. If the source itself is contradictory, comparing versions will not fix it: it only answers the question of what has changed.
