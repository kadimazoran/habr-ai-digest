Habr, hello! My name is Nikita, I am a Rust developer.

On a stream, I heard a question: "How important is code quality in the era of AI?" Then they asked if all this struggle for quality still makes sense.

The speaker categorically disagreed. He talked about how an agent sends green pull requests, passes all checks, but the code still contains garbage. For example, inconsistency in class names. And you have to figure out how else to limit the dummy so that it notices such problems itself and understands that it's time to refactor.

I listened to this and experienced cognitive dissonance. I don't have such problems with agents. I specifically ask AI to find bugs, analyze questionable solutions, improve tests, and refactor. It works quite well.

I often see similar complaints on Habr and other platforms. People are quite harsh towards "vibe coding." Sometimes, just mentioning that you used an agent is enough to have your professional incompetence discussed.

We successfully wrote bad software even without AI. Temporary solutions remained in production for years, and the code in some projects was feared to be touched. We even repeated: "If it works, don't touch it." I fundamentally disagree with this approach. Now there is a dummy that can help sort all this out. So why, with such capabilities, do we continue to get bad software?

I wanted to understand what's going on and who's to blame. Although, as an old joke goes, the main thing in an investigation is not to blame yourself.

The dummy can find errors, after all

The dummy can help with a bug that occurs only on rare occasions. You can discuss with it what cases are missing in the tests and supplement old checks.

At Meta, they created TestGen-LLM, which supplements existing tests. New tests were collected and run, and then it was checked whether the coverage increased. Suggestions that passed automatic selection were reviewed by engineers. According to the authors, they accepted 73% of such recommendations into production.

When refactoring, you can first discuss why so much different logic has accumulated in one function and how to separate it. And give one-type edits in a bunch of files to a properly configured agent.

In the Stack Overflow survey for 2026, about 58% of respondents who answered the question about using AI used it for tests, and 64% for debugging and refactoring. For code generation in a familiar area, it was about 69%.

It works, let's take the next task

Here you are adding a feature with the dummy. It wrote the code, you looked at it, tried the usual scenario. It works.

You could linger and see what happens if the request is sent twice. Or if the neighboring service doesn't respond. The agent can help with that too. At the same time, look at the code itself: is it clear what it does, and how easy will it be to change?

But there's a temptation to close the task. The new button can already be shown to the user, and you can report that everything is ready. We'll notice the benefits of refactoring when we go back to this code. You'll check a rare scenario, make sure everything is okay, and then show the same button at the demo.

If, after each such result, you immediately take on the next feature, then from the agent we will mainly get more features. We'll leave the checking and refactoring for that wonderful day when we sort out the rest. And in the wonderful future project_name, there will be no bugs and the code will be perfect.

The business needs a feature by Friday

A manager can sincerely worry about quality. When users complain, support can't cope, and developers fix the last release instead of the next one, quality immediately becomes very important. It would be desirable for this to be noticeable when planning, otherwise it will be like that phrase about forgotten ravines.

With a new feature, it's clear what will be shown to the client on Friday. With refactoring an old module, the conversation is more difficult. You explain that later it will be easier to add new features. In response, they might ask why you can't finish the current one first. The old module works for now, right?

Refactoring requires time now. And how much it will save on future tasks, you still have to try to estimate when these tasks are not even in the plan yet. The client is already waiting for the new feature.

The client pays to solve their problem. If they need a new capability, the answer "we have a feature freeze, we'll deal with technical debt first" might not satisfy them. They might go to a competitor who already has this capability while we tidy up the code.

The authors of a study on dealing with technical debt compared how managers and developers assess it. Managers believed they supported this work more often than developers felt. Minor fixes were encouraged, while major overhauls were often postponed: there was a lack of clear explanation of benefits and a suitable way to redo everything. Developers ultimately didn't have time for this.

This study was published before the widespread use of agents. Now, working on an old module with AI is easier. But if the plan for Friday includes a new feature, then the dummy will be busy with that too.

AI can be compared to a supercar. A professional will reach the finish line faster, while a beginner will crash on the first turn. Moreover, they will reach this turn much faster than they expected.

By "beginner," I mean those who make decisions too. You can manage development for years and accept the first working version from an agent as a finished product.

Do it like we do here

In an old project, the same solution is copied in several places. You bring the agent: "Look how we do things here, and add more." It might repeat the error that was in the sample. And then we show the result, saying, "This is what your AI wrote."

In an experiment on broken windows and technical debt, 29 developers extended systems with varying amounts of old problems. In more neglected code, participants more often added new things: duplicated functionality, chose unclear names.

In a November 2026 preprint, they checked whether agents repeat vulnerabilities already present in the project. They were shown safe and vulnerable versions of existing code. In the latter case, similar vulnerabilities appeared more often in new changes. The request to follow the existing style amplified the effect.

With the same agent, we could have analyzed the old solution and fixed the error in all its copies. But such a task wasn't even set: we asked for another feature, and we got it.

A million lines are easier to sell

Compare two fictional headlines:

I rewrote a million lines from one language to another in 10 days with AI agents.

And the second:

AI helped me refactor a codebase.

I would open the first one out of curiosity, at least. Why did they rewrite it, how did they manage it, what did they break, who did they leave it to? A million lines are already in the headline, but no details yet.

With the second one, you still need to figure it out. Maybe they renamed variables. Or maybe they removed a problem that made every new feature take a week to develop. Until you explain what changed, it's not very clear why you should read it.

And here, while thinking about it, I remembered an objection myself. You can also write about bugs like this:

AI found a vulnerability that had been hidden in the code for ten ten years.

I would read something like that too. And if you can get root on the server through this vulnerability, add "SHOCKING!" to the beginning of the headline. You can also talk about bugs loudly when there's such a story.

But such bugs are not found every day, at least not yet. In normal work, you're more likely to figure out why the page crashes with an empty list, or fix a filter that didn't account for one of the conditions. Users need these fixes, but the headline "AI helped fix the filter" is, to put it mildly, not catchy.

At the same time, someone might be calmly fixing old bugs with the dummy, bringing the project in order, and not publishing anything about it. We just won't know about it. Then we'll see the loud stories and decide that everyone is just generating more services.

And if you yourself constantly read about "rewrote over the weekend," you also want to try. It's clear that you can show off and boast about something. For ordinary refactoring, you still have to figure out how to tell about it. And make sure they read past the headline.

And where am I in all this investigation

In someone else's PR, you can quickly spot a problem and explain why it's not okay to do it that way. But if I myself need to release the same change by Friday? How thoroughly will I delve into it, and what will I consider sufficient verification?

The business primarily pays us for the functionality the client expects. There is often not enough time for testing and refactoring. So we task the dummy with the next feature, and leave the old problems for later.

It seems to me that we are using AI's capabilities for improving quality less than its capabilities for accelerating development. In this investigation, we have, after all, come to ourselves, which I congratulate us all on.
