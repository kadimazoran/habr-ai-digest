It so happened that I completely missed agent systems. I decided that it was worth filling this gap and catching up. The less understanding, the greater the appetite, so I decided to blindly start with an ambitious task – to transfer project development under the control of agents. My enthusiasm cooled down a bit during the work process, and I want to share the first results. Perhaps you can help me point out my blind spot or start using agents if you haven't already :)

Philosophy of Application

In my daily work, I use LLMs to write short code snippets: where the input and output can be clearly isolated, but honestly, even here problems arise. My first attempt to trust the result without verification led to about 4 hours of human effort for the function "Split period into chunks." I was extremely disappointed: people commit generated code to the Linux kernel, create entire projects, and I broke down on a simple function. Then I returned LLM to the status of "search facilitation tool" and returned to the dogma "you still have to think."

Several months passed, and I successfully used LLMs in automation, but I still hadn't approached code generation. I build my work on the premise that the main thing in development is the transformation of business coordinates into algorithmic ones. Writing code itself is the routine that helps relax and clear your head: familiar tools, familiar problems, and an absolute guarantee of results. It turns out that a development agent doesn't solve my problems, but only removes the part where I relax, which doesn't make me very happy. Therefore, I decided that the place for LLM in my task-solving pipeline is precisely the part where coordinates degenerate: at the stage of transforming business requirements into architectural ones.

The most valuable thing in completing a task is finding out that the solution was based on incorrect assumptions. This converts the cost of all previous stages into the cost of error detection, increases the cost of achieving the result by introducing cognitive biases among participants, and most importantly, wastes our time. For large teams with small individual contributions, this is acceptable; for productive teams with a small number of participants, it is very expensive.

An agent is an LLM with the ability to do something. I decided to treat it like an employee – competencies and expected results of activity should be described. I used to call this a job description, now it's a technical specification for agent development. Here's a small digression about expediency: eliminating task returns to development lacks transparency at the tracker level. "It seems there's some problem with this task" – this is our feeling when we hear about a certain part of the system often enough. To translate this signal into a measurable metric means entrusting all our incoming noise to a system that will be our intuition. Or, to devise a model that analyzes artifacts significant to our intuition: business priorities, employee morale, development artifacts, tracker events. All this is far from me; I want to test the applicability of the tool and create a practical implementation that doesn't depend on the LLM's "mood" on a given workday. Setting a two-week deadline, I got to work.

Technical Details

I wrote about 3000 lines of code in Python, which I dislike. Writing the main functionality took me one full evening, and then the work continued in the background: one day was spent on debugging without team involvement, one day on testing interaction with project participants, and one day on release to production. It turned out to be something between an agent and automation, but the result impressed the whole team. I was satisfied, and I consider the experiment successful.

The essence is as follows: the IssueTriage agent receives the task ID via FastAPI. Then it forms a context: using YoutrackMCP, it downloads the task content, images, and comments. The next step is interaction with the LLM agent, which studies the feasibility of the task (the project description includes the current team with roles). If the task cannot be implemented under the current circumstances, it will leave a comment with a specific marker that is not visible to the user but has human-readable content.

Next is a check for ambiguity: if there are double meanings in the task, it adds a comment with possible interpretations and a question addressed to a team member.
