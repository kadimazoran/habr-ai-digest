Average metric hides failure in a rare segment: checking an ML model on slices

Accuracy has increased, and the queue for manual review has decreased – it seems the new ML model can be released to production. However, behind the improvement in overall metrics, a serious drop in quality on individual data segments might be hidden. Using the example of an ad classifier, we'll explore how to identify such problems, check the model on slices, and determine the criteria for its readiness for release. Let's analyze ML errors.

Let's imagine an ad service.

Before publication, listings go through a classifier: suspicious ones go to a moderator, and the rest proceed.

The team connects a new partner feed and prepares a new version of the ML model for release.

On the test set, accuracy increased from 93% to 95.5%, and the number of listings sent for manual review decreased from 136 to 113.

For the product, this looks like two improvements at once.

However, on listings from the new feed, the model started detecting only 8 out of 20 violations instead of the previous 16. Another eight violations on the same set slipped past the manual review route.

The outcome depends on whether other controls catch them, but for a release decision, overall accuracy alone is no longer sufficient.

This is a simulated product scenario, not data from a live service. The numbers and both prediction versions are provided below in reproducible code. They are useful for demonstrating the verification procedure, which can then be applied to your fully labeled dataset.

Here:

  • TP — correctly identified violations.

  • FN — missed violations.

  • FP — clean listings mistakenly sent for review.

  • TN — clean listings that the model did not send to the moderator.

Accuracy = (TP + TN) / N, and Recall = TP / (TP + FN).

Across the entire set, even recall increased: from 80% to 80.9%. The manual review queue for these 1000 listings decreased by 23 positions: the number of positive predictions is TP + FP. But in the partner feed, the number of missed violations increased from 4 to 12.

The new model unloads moderators and worsens control precisely where the new data source appeared. The release decision requires evaluating both effects.

This is not a peculiarity of accuracy. Aggregated precision, recall, or F1 can also hide deterioration in a specific group.

For moderation, FN means a violation that the model did not send for review, and FP adds work for the team and delays a legitimate seller. When choosing a metric, one must determine the cost of each outcome and the available moderation capacity. Google details the meaning and limitations of classification metrics.

Published case: toxic comment classifier

Researchers at Jigsaw conducted a similar check on two publicly available versions of the Perspective API classifier.

They evaluated the models on a corpus of 1.8 million comments; 450,000 of them were labeled with mentions of specific groups.

On short comments mentioning gay or lesbian individuals, the BPSN AUC metric for the first version was 0.57, while for the version after correcting the training data, it was 0.82.

BPSN AUC compares the scores of non-toxic comments from this slice with toxic comments outside the slice: a low value indicates a risk of false positives at a general threshold.

These are results of offline model evaluation in a study, not a measurement of moderation errors in an active service.

The case demonstrates a different type of failure than our partner feed: here, legitimate comments suffer, potentially receiving excessively high toxicity scores.

The authors also found that the correction helped shorter comments more and did not fully resolve the problem across the entire corpus.

This means that after correction, it is useful to re-check not only the selected slice but also groups adjacent in length and content.

Our 93% and 95.5% from the beginning of the article are illustrative numbers; the Jigsaw study does not confirm them.

Recalculating results for each listing

The code below works with the standard Python library. It does not train a model: two columns of predictions define the results of conditional versions A and B.

In a production project, these columns should be obtained from the models on the same set of listings. Here, we are checking the comparison procedure, not the training method.

from collections import defaultdict


def segment(name, positives, negatives, a_tp, a_fp, b_tp, b_fp):
    rows = []
    for i in range(positives):
        rows.append((name, 1, int(i < a_tp), int(i < b_tp)))
    for i in range(negatives):
        rows.append((name, 0, int(i < a_fp), int(i < b_fp)))
    return rows


# Row fields: source, confirmed_violation, prediction_A, prediction_B.
rows = (
    segment("main", 90, 810, a_tp=72, a_fp=40, b_tp=81, b_fp=20)
    + segment("partner_api", 20, 80, a_tp=16, a_fp=8, b_tp=8, b_fp=4)
)


def evaluate(data, prediction_column):
    counts = defaultdict(int)
    for _, actual, pred_a, pred_b in data:
        predicted = (pred_a, pred_b)[prediction_column]
        counts[(actual, predicted)] += 1

    tp = counts[(1, 1)]
    fp = counts[(0, 1)]
    fn = counts[(1, 0)]
    tn = counts[(0, 0)]
    n = tp + fp + fn + tn
    return {
        "n": n,
        "positives": tp + fn,
        "tp": tp,
        "fp": fp,
        "fn": fn,
        "tn": tn,
        "accuracy": (tp + tn) / n if n else None,
        "recall": tp / (tp + fn) if tp + fn else None,
        "precision": tp / (tp + fp) if tp + fp else None,
    }


for name in ("all", "main", "partner_api"):
    part = rows if name == "all" else [row for row in rows if row[0] == name]
    for model, column in (("A", 0), ("B", 1)):
        m = evaluate(part, column)
        print(
            name, model,
            f"n={m['n']}", f"positives={m['positives']}",
            f"TP={m['tp']}", f"FP={m['fp']}",
            f"FN={m['fn']}", f"TN={m['tn']}",
            f"accuracy={m['accuracy']:.1%}",
            f"recall={m['recall']:.1%}",
            f"precision={m['precision']:.1%}",
        )

For your own dataset, instead of the segment() function, you will need rows in the format (source, confirmed_violation, prediction_A, prediction_B).

Add a listing ID and its creation timestamp. This allows you to verify that both versions received the same input and that the labeling was available for every listing, not just those that the old model sent for moderation.

In the demonstration, the predictions are already binary.

If the models return a probability or score, the threshold for each version is chosen on a separate validation set and fixed before the final comparison.

For analyzing the trade-off between the moderation queue and missed violations, PR curves are useful.

With a rare positive class, a PR curve can be more informative than an ROC curve. Google: ROC, AUC, and PR Curves.

Labeling only reviewed listings will hide missed violations

The quality of evaluation depends on the source of truth. If a moderator only sees listings selected by the current model, then for the remaining listings, there is no confirmed class.

It is incorrect to equate "not reviewed" with "no violation": it is precisely among the unreviewed items that potential FNs are found.

Therefore, in our scenario, the test set is fully labeled regardless of the decisions of either model.

In practice, a team can organize selective review of listings from both routes and maintain the probability of selection.

If primarily suspicious listings are reviewed, raw proportions on the labeled set will not be an assessment of quality across the entire stream. With different selection probabilities, evaluating the overall metric will require weights; the absence of labels in part of the stream requires a separate check of assumptions.

This is a variant of the selective labels problem: the system's decision determines for which objects a label actually appears. It is studied, for example, in work on selectively observable labels; a study on the interaction of automatic and manual moderation considers the simultaneous selection of listings and the human queue.

There are two more data quality checks here. Fix the version of moderation rules: if they changed during the data collection period, identical listings might have received different labels.

And in case of disputes, check the consistency of decisions made by several moderators. A larger number of rows won't help if the target class itself is defined inconsistently.

Slices are chosen based on product routes

If slices are not defined in advance, one can always find a group where the candidate looks bad due to randomness. For an ad service, I would start with routes that use different input data or carry different error costs:

  1. Listing source: main interface, partner API, batch import.

  2. Product category, if categories have different rules or error costs.

  3. Client version and listing completion format: free text, structured attributes, short text.

  4. Intersections of source and category, if there are enough labeled violations in each intersection.

The first list should be based on known product routes, not on searching for the most striking drop after calculation.

For each slice, you need N, the number of violations, the error matrix, and the slice's proportion in the stream.

If the test set is collected with a deliberate overrepresentation of violations, its precision and queue size cannot be transferred to real traffic without adjusting for class prevalence.

The study by Oakden-Rayner et al. on hidden stratification shows that significant subgroups may not be labeled as separate classes.

The authors studied medical images and found noticeable quality differences in important subgroups. This is a good reason to look for domain-specific meaningful slices; the numerical results of the study cannot be declared a typical effect for other tasks.

There is another risk: a small slice yields an unstable proportion. In our example's partner API, there are only 20 labeled violations; one additional missed violation would change the recall by five percentage points.

A drop from 16 to 8 detected violations is visible in the raw counters, but for a release decision, estimates of uncertainty and new observations will be needed.

Versions should be compared on paired listings; for such an evaluation, one can use paired bootstrap in SciPy. If one seller created many listings, grouping by seller must be preserved during resampling.

The interval will not fix a biased sample, incorrect labeling, or a slice chosen after reviewing the results.

The release threshold is tied to risk and queue size

A single table in the report is insufficient if the decision is still made based on overall accuracy.

For our simulated service, the product owner and moderation team could agree on conditions in advance:

  • overall accuracy must not be lower than the current version's accuracy;

  • for the partner API, the model must detect at least 75% of confirmed violations on a separate test set;

  • the manual review queue must not exceed the available capacity of moderators for the expected traffic volume;

  • the comparison is conducted on a single fixed test set; thresholds for models are chosen on a separate validation set and fixed before the final check;

  • if there is insufficient labeling for an important slice, the team increases the test set and does not treat a noisy estimate as proof of improvement.

According to these rules, model B fails the check: in the partner API, it detects 8 out of 20 violations, or 40%, against a requirement of 75%. The 75% figure is for illustration only; it is not an industry standard.

In a production system, the threshold is derived from the acceptable number of missed violations, the consequences of a violation, and the capacity of manual review.

If the test set does not reflect future traffic, the expected queue and violation rate for the target population are recalculated separately.

Conditions can be automated: check the absolute minimum metric on a slice and the change relative to the current model.

It is precisely these two types of thresholds that TensorFlow Model Analysis supports.

The tool does not decide for the team which slices and thresholds are important; it makes the agreed-upon rule reproducible.

If the overall test passes, but a new route fails, there is an intermediate solution: keep model A for it, send its listings for enhanced manual review, or postpone the feed's connection.

The choice depends on whether listings can be routed by source, whether the queue can handle the additional load, and whether a separate threshold for the feed will create unexpected effects.

These options require measurement, not automatic application after a single table.

Failure on the partner feed requires separate investigation

A poor metric on a slice does not indicate the cause. For the partner API, I would check four hypotheses:

  • listings from the API contain different texts, categories, or attribute omissions;

  • moderators applied a different version of rules to partner listings;

  • the feature processing pipeline transforms API fields differently than main interface fields;

  • the chosen threshold creates an unfavorable trade-off between missed violations and manual review volume for the feed.

Order of checks:

  1. download the eight additional missed violations by model B with listing IDs;

  2. compare texts and attributes before and after processing;

  3. re-check disputed labels;

  4. compare the score distribution by source.

Only after this should a fix be chosen – labeling, transformation, model, or threshold. Its quality will need to be measured on new data: selecting a solution based on the 20 positive listings already reviewed will create an inflated estimate.

In other products, a slice might describe groups of people, not data sources. Then, quality analysis also involves fairness of decisions. Equal recall by itself does not prove system fairness: criteria related to the specific decision and its consequences are needed. Google: Evaluating Bias and Fairness.

Release report supplemented with slice size and error cost

On 1000 simulated listings, model B increased accuracy from 93% to 95.5% and reduced the number of items sent for manual review from 136 to 113. In the partner API, it missed 12 out of 20 violations instead of 4. The increase in the overall metric and the reduction in the queue coexist here with a specific product risk.

In the release report, I would keep the overall metric, the error matrix for pre-selected routes, the number of labeled violations, the expected moderation queue, and the acceptance criteria for each critical slice side-by-side.

Row-by-row predictions for both versions allow returning from percentages to the listings where the models diverged. Without this step, a table with a nice overall accuracy does not explain which cases the new version stopped noticing.

Conclusions

  • Overall accuracy increased from 93% to 95.5%, but on the partner feed, recall dropped from 80% to 40%. The release check should show both results.

  • For each important slice, original error counters, the amount of labeling, and an assessment of the consequences of a missed violation or false positive are needed. A single percentage without the slice size is misleading.

  • Slices and acceptance criteria should be defined before the final model comparison. If a critical route fails the threshold, its release requires a separate decision.

  • The cause of the drop is determined by examining listings where versions diverged, and the fix is verified on new data. A poor metric by itself does not explain the cause.
