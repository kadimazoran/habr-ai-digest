Most 1C integrations with external systems I've had to support are set up the same way: a procedure of several hundred lines in the configuration or an external utility parses JSON and fills a document. It works until someone touches either the source or 1C. After updating a standard configuration or adding a new field in the source, it needs fixing, and usually, only the person who wrote it can do it.

I tried describing the integration not with code, but with data. The integration settings store the direction, method, rules for "where to get → where to put," and small handlers for things that cannot be expressed by rules. All of this lives in an extension, while the standard configuration remains supported.

The next step turned out to be more interesting: if the integration is described by data, this data can be proposed by an AI assistant. The user writes the task in words, inserts a sample message, and shows a sample object from their database, and the assistant compiles a draft of the settings. Below, I'll break down what it receives as input, what it returns, where it makes mistakes, and how these are caught before writing to the database.

1. The Problem: Integration as Code

An integration "in code" has three weak points:

  • Updates. Modifying the standard configuration removes it from support or turns every update into a comparison-merge.

  • Opacity. To understand why a price appeared in an order, you need to read the procedure.

  • Number of Sources. Website, CRM, email with price lists, bot, clinic software: each requires its own integration with its own errors and logging.

2. The Approach: Integration as Data

The extension has four entities:

  • Integration Settings: direction (receive/send), method, message identification key, 1C object.

  • Property Definition Rules: path in message → attribute or tabular section, method for finding reference values.

  • Event Handlers: short procedures for things not expressible by tables.

  • Message Log: each incoming and outgoing message, status, error, retry.

The extension's HTTP service receives a message, finds the settings by method, applies the rules, and writes the result to the log. The configuration remains unchanged.

3. What the Assistant Receives

Three inputs:

  1. Task Text. For example: "The website sends an order. Create a Sales Order, find the customer by phone, if not found, create one, find items by SKU."

  2. Sample Message. The actual JSON of the order.

  3. Sample Object. An existing document from the database. Metadata (attributes, tabular sections, types) is taken from it, as well as which fields are actually filled in this database.

The sample is important: the same task in different 1C configurations (like UT and UNF) maps to different attributes, and a verbal description cannot convey this.

4. What It Returns

  • Integration direction and method name (e.g., inSalesOrder);

  • A table of rules "JSON path → attribute";

  • Search rules: nomenclature by SKU, partner by phone;

  • An object formation handler.

A simplified example of a handler (for the article):

Procedure OnObjectFormation(Message, Object, Refusal) Export
	Data = Message.Data;
	Object.CustomerOrderNumber = Data.number;
	For Each ItemRow From Data.items Do
		NewItemRow = Object.Items.Add();
		NewItemRow.Nomenclature = FindBySKU(ItemRow.sku);
		NewItemRow.Quantity = ItemRow.qty;
		NewItemRow.Price = ItemRow.price;
	EndDo;
EndProcedure

5. Why the Response Isn't Executed Blindly

The assistant's response is loaded into a form where it can be viewed in its entirety. Then, a person checks the rules and runs a test processing: it constructs an object based on the sample message but does not write anything. Only after this is the integration enabled.

6. Pitfalls from Real-World Scenarios

I recorded a minute-long video on a live database, and the assistant made mistakes where a human without context would also err:

  • Direction. Until the explanation stated that the message was incoming, it proposed an outgoing integration. This is fixed with a single phrase in the task.

  • Types. "Expected Array for path customer": in the example, the customer was an object, but the rule expected an array. This is visible during test processing.

  • Search Key. Searching for a customer by name instead of phone. Syntactically correct, semantically wrong. Only a human can catch this, so verification is mandatory.

7. Execution

The extension's HTTP service, a queue, a log, retries on error, and duplicate protection by message key (for an order, it's the order number from the website). Resending the same message does not create a second document.

8. Sources Other Than Websites

The mechanism doesn't know what a "website" is. It needs the message format and the 1C object. Therefore, it can also be used to describe: emails and attachments, files in a folder (price lists, supplier invoices), Telegram bots and forms, niche CRMs, clinic and salon software, any service with an API. And the reverse direction: statuses and balances from 1C to external systems.

9. Limitations

  • OAuth2, request signatures, and certificates require a developer.

  • Deeply nested arrays and non-trivial transformations are handled by procedures, not rules.

  • The responsibility for mapping lies with the human: the assistant proposes, the human approves.

Conclusion

An AI assistant handles routine tasks well: matching fields, suggesting searches, writing handler templates. It performs poorly on tasks not present in the input data: direction, business meaning of a key. Therefore, the "propose → show in full → test → enable" scheme seems correct for 1C, where an integration error turns into an accounting error.
