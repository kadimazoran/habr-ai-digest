Hi, I'm Vika. I've studied the open descriptions of 424 companies and products to understand what everyday tasks can be delegated to a personal AI agent in Russia: shopping, payments, delivery, or device control.

The connection method is secondary to me. Whether it's API, MCP, A2A, or another option: what matters more are the operations the service provides to the agent and under what conditions.

The main conclusion: in my sample, connections for businesses are significantly more numerous than for personal tasks.

  • 232 services have 312 connections. A single service may have multiple connections.

  • 233 connections are primarily intended for businesses, and 50 for personal tasks. Of these 50, 17 have confirmed official standalone access.

  • 10 personal connections claim actions with a physical result: ordering, transportation, or device commands. Half of these were created by third-party developers.

I was particularly interested in the second half of the process – whether an agent could proceed from search to action and verify the result. My focus was on orders, transportation, and device control, but I also considered digital tasks.

Finding a product, assembling a cart, and buying are different capabilities

Lenta: Get information. The API provides access to stores, products, prices, and availability. Authorization is not required. Order placement and payment are not confirmed in the published set.

VkusVill: Prepare a purchase. The vkusvill_cart_link_create method is responsible for generating a cart link. Authorized users have access to order history and personalized offers. I did not find methods for order placement and payment deduction in the published set.

Delovye Linii: Create a shipping request. The API allows creating requests and requesting modifications. For example, canceling a delivery from or to an address requires verification and may be rejected. A payment link does not yet signify a completed payment.

Sellers Have APIs. Buyers Haven't Been Invited Yet

Through the Ozon Seller API, one can manage products, prices, and shipments. But I need a buyer agent. The existence of Seller API does not grant it the ability to place an order in my account.

B2B and B2C here denote the service's purpose: for companies and sole proprietors, or for individuals. This is not the right to access the API. I also categorized 29 additional connections under data and development.

Of the 50 personal connections, 17 have official standalone access. These include 14 services, such as VkusVill's public MCP tools, Lenta's catalog API, Yandex Disk, and Smart Home.

Standalone access means no mandatory corporate contract or paid connection plan is required. An account, brokerage account, identification, OAuth, and program setup might still be necessary. The remaining 33 connections have additional conditions or unclear access procedures.

Difficulties arise even before the first request

Across the entire sample, there are 28 connections with official standalone access, including the 17 personal ones. The remaining 284 require additional conditions or clarification of access.

191 connections require corporate access, a seller's portal, or a partner role. In 80 cases, approval, separate authorization, or administrator setup is needed. Paid access and self-hosting are also encountered. Conditions can overlap.

The audience threshold is marked for Aviasales Search API and its dependent MCP. This refers to obtaining one's own access to the Search API, not automatically to a user of someone else's hosted MCP or other service APIs.

I did not count the cost of goods, delivery, or transaction fees as connection fees. OAuth by itself does not imply restricted access. What matters is whether a user can obtain the necessary rights for their task.

Many actions, but most remain within digital services

The assumption that most APIs only read information was not confirmed. Based on documented capabilities, I divided the 312 connections into five groups:

  • For 77, only information retrieval is confirmed: search, comparison, reading, calculation.

  • 8 prepare a cart, draft, or link for continuation.

  • 186 allow modification of digital data: sending messages, publishing content, editing entries.

  • 34 allow placing an order for goods, transportation, booking, or sending commands to devices.

  • For 7, there was insufficient information.

I did not count search as an action. Uploading a file via the Yandex Disk API is a digital action with a verifiable result. The Yandex Smart Home API allows sending commands to devices or launching scenarios. A physical result is possible here without any purchase.

Among connections primarily intended for personal tasks, such actions are claimed by 10 connections to 9 services. Yandex Smart Home is counted twice: API and third-party MCP.

Five MCPs were created by third-party developers. Four use internal APIs or browser automation; the Smart Home MCP uses the official API. The authors of the Pyaterochka MCP explicitly describe reconstructing requests for web client operations. However, it is incorrect to label all third-party MCPs as a result of reverse engineering.

The breakdown resulted in 214 APIs, 97 MCPs, and one A2A. Of the MCPs, 34 are official, and 63 are third-party.

A2A was found for Albato Copilot: an external agent can create, check, and run automations. Access is partner-based: an address and token are provided by a manager, and a user session is required separately. This is the only confirmed example in my sample, not in all of Russia.

How I counted

One entry in the registry corresponds to a pair of "service and protocol." API provides programmatic access to service functions, MCP provides tools to the agent, and A2A allows addressing another agent. The connection type is secondary to me: access to the desired action is more important. The programmatic tool, in this case, needs to be configured and, where required, authorized.

I checked the API and MCP capabilities of the same service separately. I did not sum up API methods or server instances. Products from the same holding company were counted separately. Some services fall into multiple categories: 424 profiles result in 432 placements.

I assigned the primary audience and the strongest confirmed result to each entry once. Additional scenarios and conditions may overlap. Carts, drafts, preliminary orders, and personalized offers were considered preparations: they can modify data but do not complete the task.

For 192 services, open connection confirmations were insufficient. "Not confirmed" does not mean "forbidden" or "non-existent." Sources included official documentation and descriptions from third-party connector authors; I did not test the functionality or reliability of the connections.

What to check before connecting

Before connecting, I would check five things: personal access, separation of read and write permissions, operation confirmation, protection against duplicate orders, and a method to verify the result.
