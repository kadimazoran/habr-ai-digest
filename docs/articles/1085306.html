Why Candidate Caching Was Needed

Every time a user sends a request, the recommendation system performs a large amount of computation. First, it collects candidates – items that might potentially suit the user. They come from various sources:

  • items similar to the user's recent interests;

  • items from familiar authors;

  • fresh items;

  • promotional content;

  • items from product quotas.

Then, the candidates undergo ranking, and the final output is formed from them. This scheme provides high-quality recommendations but requires significant computational resources: the more candidates reach the ranking stage, the higher the latency – request processing delay – and the higher the CPU consumption. Therefore, large recommendation services hit hardware limitations.

It's worth clarifying why this dependency exists. Ranking is designed such that the model calculates a score for each candidate separately, so its cost grows linearly with the number of input objects. A hundred extra candidates in one request mean a hundred extra model passes, multiplied by the entire service's request flow. Meanwhile, only a few items make it into the output: the rest are only needed so the model can choose the best ones from them.

This leads to a natural question: can we reduce the number of candidates entering the ranking stage without compromising recommendation quality?

The hypothesis is simple. Adjacent requests from the same user are often similar: between two feed openings, a person doesn't have time to completely change their interests. This means that most of the strong candidates for the next request were already found in the previous one. If this is true, they can be computed once, stored for a short time, and reused in several subsequent requests.

What the Output is Composed Of: Streams and Selectors

Before discussing caching, we need to describe the two levels at which candidate selection is organized.

The upper level consists of streams. Our recommender is divided into several independent streams: one is responsible for the main personalized content, another for fresh objects, a third for content from important authors, and a fourth for promotions and product guarantees. Each stream collects candidates and ranks them independently, and the results are combined into a single output at the end.

The lower level consists of candidate selectors, which operate within the streams. It is the selector that fetches data from the source and brings back a list of items. They will be mentioned frequently throughout the text, so let's break them down separately.

Types of Selectors

Selectors can be categorized into several types – the type of selector determines whether it can be replaced by a cache.

  1. Item-to-item. These find items similar to those the user has recently interacted with.

  2. Source-to-item. These select items from authors the user has shown interest in.

  3. Vector-based. These operate using HNSW indexes on embeddings. HNSW is a structure for fast approximate nearest neighbor search in vector space: it builds a multi-layer graph that allows reaching similar objects in logarithmic time instead of a full database scan.

  4. Non-personalized. These operate based on a data snapshot that is periodically updated and provide the same set of items to all users within a given context.

  5. Product-based. These are responsible for special pools – warm-up, promotions, and editorial selections. They bring a small number of candidates, but these candidates must appear in the output due to product commitments.

The difference between types also dictates the caching strategy. A non-personalized selector based on a snapshot is best suited for cache replacement: its output rarely changes anyway. Heavy personalized selectors are the main optimization target because they consume the largest share of computations. And mandatory product-based selectors should not be replaced by a cache at all: the risk of violating guarantees is higher than the benefit from a few dozen candidates.

Why Candidates Can Be Reused

We tested the hypothesis about the similarity of adjacent requests using data. If we take two consecutive requests from the same user within the same stream, the system often finds almost the same set of candidates – and performs the same work a second time during re-ranking.

These graphs should be interpreted as follows: they don't allow using the same set of candidates indefinitely, but rather show at what horizon reuse is safe. In the short term, candidates are sufficiently stable. In the long term, the set becomes outdated: the user performs new actions, new signals appear, the context changes, and fresh items should also appear in the output.

Complete overlap between adjacent requests doesn't happen, and that's normal. Some sources update independently of the user: fresh content appears, snapshots are recalculated, product pools change. Plus, the user themselves manages to watch or scroll through something between requests. Therefore, the question is not whether the sets of candidates coincide, but whether their overlapping part is large enough to save on it.

This leads to the requirement for the cache: it must be small and short-lived. The goal is to temporarily store only that part of the candidates that is highly likely to be useful again.

Idea: Cache Top-K Candidates

The basic scheme looks like this. After a regular request, we take the top-k candidates with the highest scores from each stream and store them in Redis.

The idea is that for the next request, a significant portion of the selection process doesn't need to be repeated. The candidate set is assembled compactly, from three parts:

  • candidates from the cache;

  • candidates from reactive selectors – lightweight versions of regular ones that capture fresh user signals;

  • candidates from mandatory selectors that cannot be replaced by a cache.

This way, we stop re-ranking a significant portion of low-scoring candidates. These are precisely the ones that contribute a noticeable portion of the computational load, even though they rarely make it into the final output. At the same time, caching does not eliminate ranking: candidates from the cache are still re-scored in the current context. What changes is not the final model, but the number of objects that reach it.

Here, it's worth mentioning two key parameters that require balancing:

  1. Cache size k. The smaller it is, the fewer candidates enter the ranking, and the higher the CPU savings. But with too small a k, there might not be enough good candidates – especially if the user quickly exhausts the saved list. In product metrics, this will manifest as a drop in engagement, conversion, or consumption time.

  2. Cache TTL. A long TTL increases the proportion of requests that can be served from the cache. However, recommendations become less reactive. A short TTL is safer for quality, but the savings are smaller.

Simply put, too small a k or too long a TTL harms recommendation quality, while too large a k or too short a TTL eats up the performance gains.

Reactive Selectors: To Prevent the Cache from Making Output Inert

The main risk of caching is that recommendations stop noticing the user's fresh actions. A person watches a new video, subscribes to an author, becomes interested in a new topic – and the system continues to work with the list compiled before that. Therefore, in cached mode, reactive selectors always work alongside the cache: lightweight versions of regular ones that consider only new signals that appeared after the cache was written.

Different levels of reactivity are needed, depending on the selector type:

  • item-to-item – to new user events;

  • source-to-item – to new author signals.

The advantage here lies in the volume of work. A full item-to-item selector goes through the user's entire interaction history and searches for similar items for each object in it. The reactive version only takes events that occurred after the cache was written – and not many of them accumulate within a short TTL. The logic is the same, but the input is an order of magnitude smaller.

The composition of selectors in cached mode needs to be configured carefully, and mistakes can be made in either direction. If too many candidates are added from reactive selectors, the caching benefit will decrease – we will simply return to ranking what we removed. If, conversely, some selectors are not included in cached mode, product guarantees can be violated.

There is no universal configuration here: it depends on the product specifics of a particular recommender. It needs to be selected through A/B experiments – we tested cache size, TTL duration, and selector composition in cached mode, while simultaneously monitoring CPU savings and product metrics.

Implementation Details

Technically, the candidate selection stage operates in two modes:

  1. Normal, without cache. This is enabled when the cache cannot be used. This happens for three reasons: the cache doesn't exist yet for this user and context, it has expired by TTL, or the stored candidates have been exhausted. The stream then operates as before: it launches the full set of selectors with normal quotas.

  2. Cached. This is enabled if a fresh cache is found for the user and the current context. A separate selector configuration is used for this: the cached_candidates selector is added, and heavy selectors are replaced by lightweight versions – for example, instead of a full item-to-item selector, its reactive version is used.

The proportion of requests that fall into the second mode is the hit rate – the main metric of the mechanism's effectiveness: it shows on what portion of the traffic we are actually saving.

The cache key consists of the user and the recommendation context – the type of recommender, platform, and product surface. The value contains the timestamp of writing and the sets of candidates for each stream: item identifiers along with their scores.

One candidate occupies about 20 bytes plus overhead. The total Redis memory usage is determined by three factors: the size of k, the TTL value, and the number of contexts we cache. The first determines the length of each list, the second – how many lists are active in memory simultaneously, and the third – how many lists are created per user.

Results

At the time of writing, two recommenders have been switched to cached mode – VK Video and VK Clips. We achieved savings by offloading recommender replicas, which reduced the consumption of not only CPU but also other resources: RAM, NVME, LAN. The cost was the scaling of Redis clusters in MDB – part of the saved hardware went there.

It's important to understand that switching a recommender to cache is not just flipping a switch. A custom configuration is selected for each recommender: which selectors are replaced by cache, which get reactive versions, which remain untouched, as well as the values for k and TTL.

The magnitude of the gain strongly depends on the parameters of a specific recommender, and here's why the numbers vary. The first reason is the proportion of uncached traffic. In VK Video, half of the RPS comes from the doc2doc surface, i.e., the "See also" block under the video. Candidates for it are selected for a specific video, not for the user, so the "user plus context" key doesn't work for this surface: the saved list would have to be created for each "user – video" pair, and there would be almost no reuse. The second reason is that different recommenders have different numbers of candidates in non-cached mode, and where there are already few, there's not much to reduce.

Conclusion

Candidate caching eliminates redundant work from the recommendation system without altering the core ranking model. We save strong candidates after a request, reuse them for a short period, and supplement them with fresh signals from reactive selectors.

The main engineering idea is not to cache recommendations entirely. Only the result of candidate selection is cached, and only the top-k candidates make it into the cache. Such a list is short enough for noticeable savings and stable enough during the cache's lifetime for reuse to remain safe. The final output is still built considering the current request context.

And the saved hardware becomes a resource on which new recommendation mechanics can be launched.
