Hello, Habr! I'm Artem Gambitsky, co-founder of the Flowwow marketplace.

Four months ago, we allowed colleagues without an engineering background to deploy AI-generated applications to production. Since then, we've received over 260 projects from 150 people, and none of this code has been reviewed by a programmer.

Yes, we could have banned AI altogether and left development solely to professionals. But for us, that path would have been a dead end. It's foolish to take away a tool that already helps people do their jobs, and suppressing initiative doesn't align with our principles at all. It made more sense not to fight reality, but to provide the process with safe rails and clear rules of the game.

We expected the vibe coders to crash production, but the problems came from a different direction. For example, builds started failing all at once when we approached 200 runners on a single machine and exhausted the kernel key quota. And during a planned update, the network hung on hundreds of docker interfaces, leaving the entire machine without DNS.

Next, we'll discuss how our sandbox is set up, what we've learned over these four months, where we made mistakes, and what the outcome has been.

Why Bother?

Vibe coding in the company started spontaneously and chaotically. Some people built applications and landing pages for themselves, others automated routine tasks, and some integrated AI-generated interfaces into their department's processes. Projects lived on laptops and questionable virtual machines that only their author knew about.

Development teams don't take on such local requests, and rightly so: a tool for saving one department's time loses out to any task affecting revenue in terms of prioritization.

Yet, the need remains.

It's the same story with hypotheses: the path from idea to MVP through the backlog takes weeks, while a prototype built by a product manager in a couple of hours can be shown to the team immediately via a link. This saves a lot of time on testing these theories.

We didn't want to ban vibe coding, but leaving it as it was was dangerous. The question came down to the classic "you can't ban it, you can lead it." Thus, the Flowwow Product Sandbox was born.

How It All Works

The sandbox lives separately from the marketplace infrastructure: its own machines, its own domains, its own deployment. Projects don't touch the main platform code. The project author creates a repository from our template, which already contains all the rules for the agent and texts, the design system, and protective hooks. Then, the AI agent refines requirements, writes a specification, an implementation plan, logic, and tests, submits the result for review by a sub-agent, and shows it in a local preview. After that, a self-hosted runner builds the image, our Deploy API launches the container, and within a minute, the application is available on its subdomain within the corporate VPN.

Under the hood, there's nothing exotic: Traefik, Deploy API on FastAPI, a separate docker-agent, SQLite, cron, and systemd timers. All this is hosted on a virtual machine with 8 vCPUs and 32 GB of RAM for 20,000 rubles per month.

Each project's container gets half a core and 512 MB of RAM. On a typical template stack (Node 24, Fastify, better-sqlite3), such a container can handle 500–1,000 requests per second: about 500 RPS for an API that reads from SQLite, and about 1,000 RPS if it's static SPA. But in reality, the loads are much more modest. One of our most visited projects gets 5–10 thousand visits daily and peaks at around 60 RPS. It's still a long way from hitting all its limits.

Two hundred running containers occupy 9–10 GB of memory, which is an average of 50 MB per container. Therefore, the virtual machine can handle up to 500 similar projects.

These figures are partly due to the chosen stack. The pre-configured agent defaults to lightweight tools: Fastify instead of NestJS, FastAPI instead of Django, SQLite instead of a separate Postgres, a lightweight front-end instead of server-side rendering on Next.js. It will only use a heavy framework if the author insists and justifies why they need it.

The code for all projects is mirrored daily to a separate private repository, and the data for all projects is stored in an S3 bucket. If the author deletes the repository or leaves the company with their account, their creation will remain.

By default, there is no access to internal corporate data. However, if an application requires it, this is separately approved through the information security department: a user account is created for the project, granting read-only access to a specific list of tables from the requested Flowwow database.

Run, Forest, run!

The sandbox is only accessible via the corporate VPN; it does not accept incoming connections from the outside. The cloud runner cannot reach it, so the build is done by a self-hosted runner directly on the virtual machine. Project code primarily resides in authors' personal accounts, and the runner is registered there only at the repository level. As a result, one runner per project. We launched the sandbox with this solution four months ago.

While projects were in the dozens, there were no problems. By the end of August, there were 165 runners, and we observed that two-thirds of the occupied memory and half the disk space were held by their fleet. A huge chunk of resources was consumed by processes that were simply waiting for work!

The solution was found in open source: chimera — a complete rewrite in Rust of the GitHub Actions protocol. One daemon holds all machine registrations as tasks within its process: each polls the broker for a long time, and workers appear only when a job arrives. We forked this runner, polished it for our needs, and migrated all projects to it.

After the migration, two hundred runners now live in a single process using 100 MB, compared to the previous 13 GB.

Virtual Ceilings

The entire sandbox is equipped with monitoring systems and alerts. If something goes wrong, the disk, memory, and processor warn about it in advance. However, during operation, some of the established ceilings presented us with unpleasant surprises.

For example, we didn't anticipate such rapid growth in the number of projects. In the four months since the sandbox's existence, Flowwow employees have registered 262 projects and performed around 5,000 deployments, and this number continued to grow geometrically.

At the start, we limited the docker network pool to 256 addresses, thinking we'd hardly reach such numbers on a single machine. This misconception turned out to be very pleasant. Upon discovering the approaching limit, we added a second pool with 2048 networks. Along the way, we learned that the order of pools in daemon.json doesn't matter: docker sorts them by base address. Now we're waiting for the first pool to run out.

It got even more interesting with the Linux kernel key quota. By default, each user has only 200 keys in the keyring, and all runners worked under a single account and held one key each.

At the 198 out of 200 mark, builds started failing with unable to create session key: disk quota exceeded, and user agents, seeing the word "disk," suggested cleaning the disk. It had nothing to do with it. We first increased the quota, and then migrated to chimera, where the entire fleet uses one system unit instead of two hundred.

We've dealt with infrastructure limits, but the main question remained—the security of the code generated by neural networks…

Agents and Security

Security in the sandbox is built around an unusual threat model: there's almost no attacker. There's an honest colleague who wants to do good, and a neural network that sometimes hallucinates, executes rm-rf in the wrong directory, or goes to read .env "just in case." Therefore, making the sandbox secure was a key task: to give people freedom to experiment, but to exclude even accidental harm to the infrastructure. We built layers of protection as follows: the deeper you go, the fewer opportunities the agent has to change something.

The first layer is instructions. A short AGENTS.md in the template acts as a table of contents: "if I do X → read Y" and 14 invariants that must not be violated. These are basic guidelines for the agent: how to solve the task and what boundaries not to cross. It loads detailed contracts (security rules, design system, red-teaming policy) when it gets to them, rather than keeping them in context all the time.

The second layer is hooks. On PreToolUse, there are six blocking hooks: destructive-command, git-destructive, git-no-verify, command-injection, secret-leak, and working-directory. On PostToolUse, there's an API key leak detector. We took five out of seven from the AnastasiyaW/claude-code-config repository and adapted them so that the same scripts understand different agents. Thanks to this, it won't be able to exit the current project folder and try to delete something nearby. The key detail why bypassing these rules won't work "head-on" is that the hook runs as a separate process, not as a child of the checked command. The agent can set permissions like CLAUDE_ALLOW_X=1 in its environment as much as it wants—the script simply won't see this variable.

But hooks live in the project repository, and the neural network can edit them if it wishes. Therefore, for us, this level is only basic protection against accidental mistakes.

The third layer is the server. The author fully owns their Dockerfile, but not how the image is launched. The server provides the container start parameters itself—they are read from internal platform rules, not received from a webhook. A user cannot set their own limits or obtain root privileges. A new version of the container is first launched alongside the old one, passes checks, and only then receives traffic.

The fourth layer is regular code review. All sandbox projects are connected to our common security console. AI regularly analyzes the generated code for vulnerabilities and, if found, prepares a full prompt for the agent. The author only needs to insert it into a new session. A person who doesn't read code gets a vulnerability fix without ever looking at the source code.

This multi-layered control allows us not to worry about the security of the infrastructure. Well, or at least worry a little less.

Technical Support

Despite the influx of projects from colleagues without technical backgrounds, the sandbox support team is not overwhelmed with help requests. And much of this is due to the approach itself: we initially designed it so that a person only gets involved in extreme cases.

The author's agent acts as the first line of support. It's trained on all typical problems that other sandbox users have encountered. Moreover, it can retrieve and read the tail of its container's logs (via API, the request is signed with HMAC, secrets in the response are redacted). Therefore, the agent fixes most problems itself.

If the AI gives up, it asks the user to write to the support channel. There, a general sandbox bot responds, which is in the thick of things on the virtual machine. It operates under a separate user with limited privileges and communicates via a personal socket with its own API. It checks the status of containers, logs, and deployment history for the relevant project or group of projects. Then, the bot responds if it has figured out the problem, or escalates the task to a human.

At the end of each day, the bot automatically trains on threads with resolved user issues where a support employee was involved, so that it can handle these questions independently in the future. It also selects the slowest project once a week and generates an email to the author with recommendations for optimization. Judging by the reaction, authors respond quite promptly and friendly to such mailings.

What's Being Built and What Survives

Four months have shown that the sandbox works exactly as we intended. The catalog of created projects includes product MVPs, tools for automating routine tasks, and seemingly random things. But it's precisely these spontaneous experiments that help people get their first hands-on experience with vibe coding without fear of breaking or crashing something.

The tasks being solved are absolutely diverse. Some people build a dashboard for Flowwow's offline stores to monitor category dynamics and plan fulfillment in real-time, without queues to analysts. Others create a tool for analyzing competitors in new markets, and still others, a unified request window for procurement and warehouse supply.

However, not all services are destined to live for months. A project might be built to test a single wild hypothesis, for a short promotion, or for a two-week sprint, and then be quietly shut down. A prototype that lasted a week is not a failure. A failure is when it waits for its turn in the backlog for a year and dies there.

What the Company Gained

The main change is not technical. We've moved from chaos on personal laptops and nameless virtual machines to a manageable system. All projects are collected within our environment, standardized, regularly checked for security, and access is granted systematically, not from memory.

A service in the sandbox is not required to remain a one-person project. The owner can invite any colleague as a co-author: they get access to the repository, work with their agent, and deploy on par with the author. A third of the sandbox users, in addition to their own project, also participate in others. This is how we've learned to gather vibe coders into packs, and we'll soon hold Flowwow's first internal product hackathon based on the sandbox.

Vibe coding hasn't eliminated engineering. It has moved it from the vibe coder's code to the platform on which that code lives.
