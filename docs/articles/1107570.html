It's no secret that language models lie, and they do so very convincingly, often with details. A year ago, if you asked an LLM for a link to a study, you'd get an article that no one had written. If you asked about a library method, the model would describe its arguments, even though such a method didn't exist. The world is still fighting this: models are tied to knowledge bases, equipped with skills, and prompted with 'answer only based on context.' This helps only partially. Fabrications still seep in where the model lacks facts.

But what if we turn the question inside out? Are there tasks where plausible fabrication is needed in itself? Yes, and quite a few, for example: test data for programs, populating game worlds, traps for hackers. I'll focus on the latter.

The Problem

In security, fake servers (called honeypots) have long been used. An attacker enters, leaves traces, and reveals themselves. The first problem is that an empty trap is immediately obvious, and filling it with configs, logs, and admin notes has to be done manually. A model, however, can produce such content quickly and in any quantity.

The second problem is more subtle, but anyone who has connected a model to their programs has encountered it. For a program to talk to an LLM, it needs a plugin, API, MCP server, or at least a wrapper. Meanwhile, in Unix, an interface has existed for half a century that all programs understand, from `ls` in '71 to Windows Explorer. It's called a file. Connect the model as a regular disk, and `find`, `grep`, `du`, file managers, and any scripts will immediately start working with it, without even realizing who they are dealing with.

From these two ideas, an experiment was born. I created a file system where there are no real files: the model invents folders and everything within them the moment they are accessed. Next, I'll explain how such a disk is structured, where `find` gets lost on it, what `grep` found instead of passwords, and how a second AI, acting as a hacker, believed a non-existent server five times in a row.

How a Non-Existent Disk Works

FUSE allows you to write a file system with an ordinary program. The Linux kernel receives a request like 'show what's in the folder' or 'read the file' and forwards it to your code. Whatever your code responds with, the program sees. I used the `mfusepy` library (which works with `libfuse3`) and wrote a class with two main methods. One is triggered when someone reads a folder, the second when someone opens a file.
