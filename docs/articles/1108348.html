1. Introduction

Large language model inference infrastructure is traditionally optimized for throughput and latency: KV cache, CUDA graphs, batching, quantization, parallelism. These components form the "skeleton" of the system and define its performance limits. However, often overlooked is the layer that determines quality rather than speed: sampling parameters. These are the rules for selecting the next token from the logit distribution at each decoding step.

The shift in priorities is understandable: these parameters do not affect the inference core, memory, or the number of requests served. But their underestimation comes at a high cost: a system that is perfect in terms of throughput and latency, with uncalibrated decoding, can fall into repetitions, break off reasoning, lose response format, or, in RAG scenarios, generate plausible but unsubstantiated claims. Formally, it "works," but it is not combat-ready.

This article breaks down sampling parameters in clear and simple terms – their mathematical nature, interaction, and role in different modes (chat, reasoning, RAG) – using the example of OpenWebUI + vLLM, where parameters are managed dynamically depending on whether search or reasoning mode is enabled.

2. Basic Concepts: Logits, Distribution, and the Act of Selection

2.1. Logits

A language model does not output a ready word. At each step, it receives the text written so far x1:t ("I love to drink hot... in the morning") and returns a vector of logits – one number for each token in the vocabulary. The vocabulary (V) of modern models typically ranges from tens of thousands to two hundred thousand tokens, so there are as many logits at each step. A logit zi​ is simply a number that indicates how much the model "leans" towards token i (e.g., "tea" - 10 points, "coffee" - 9 points, etc.). This is not yet a probability: logits can be negative, large, small, and their sum is not tied to anything. Their absolute values depend on the model's internal normalization, so logits cannot be directly compared between different requests.

2.2. Probability

To obtain a probability distribution over the vocabulary, the softmax operation is applied to the logits:

About probability distribution

Why is the weight of token i equal to exp(zi)? Because logits can be negative, but weights cannot (a proportion cannot be negative). It preserves the order and emphasizes the difference. If z1 > z2​, then exp⁡(z1) > exp⁡(z2). Moreover, the difference in logits turns into a difference in magnitude: a logit that is 1 greater gives a weight e times larger. The model, as it were, "amplifies" its leader.
Correspondingly, the total weight of all tokens is the sum of exp(zi).

Now, each pi​ is the probability that the next token will be token i, and all pi​ together sum to one. It's important to remember: this is the model's estimate, not the "truth." If the model is confident (e.g., after "The capital of France is - "), the distribution has a pronounced peak at the word "Paris." If the context allows for many equally valid continuations, the distribution becomes flat, and probabilities are distributed among dozens of candidates.

2.3. Decoding

Generation is a cycle (simplified):

  • the model outputs a probability distribution over the vocabulary →

  • one next token is selected from it →

  • the token is added to the context →

  • the model is run again →

  • the next token is selected →

  • and so on until a stop condition (special end token, length limit, stop string).

The key operation at each step is selecting one token (x̂) from the distribution. There are two fundamentally different ways to make this selection:

  • Deterministic (greedy / argmax): the token with the highest probability is always chosen. The same context always yields the same answer.

  • Stochastic (sampling): the token is chosen randomly according to the distribution, x̂ ∼ p (chosen randomly according to distribution p). It is this mode that sampling parameters adjust.

2.4. Sampling Parameters

Sampling parameters are a set of rules that transform the original distribution p before selecting a token. Each rule answers a specific question:

  • Temperature – how "sharp" or "flat" to make the distribution overall.

  • Top-k – how many of the most probable tokens are allowed for selection.

  • Top-p (nucleus) – what proportion of the total probability mass to retain, discarding the tail.

  • Min-p – how probable a token must be relative to the leader to remain under consideration.

  • Typical sampling – how "typical" in terms of information content a token's probability should be.

  • Repetition penalties (repetition / frequency / presence penalty) and DRY – how to adjust the logits of already encountered tokens or fragments.

  • Mirostat – how to maintain a target level of generation "surprise" over the long term.

A fact that is often overlooked: these rules are independent as concepts, but not independent as operations. We will elaborate on this below.

There's a subtlety here that is often missed. Each parameter can be defined on its own: to explain temperature, you don't need to know what top-p is, and vice versa. In this sense, they are independent as concepts – each represents a separate, self-contained recipe for transforming a distribution.

But in a real pipeline, they are applied sequentially, and the result of each step becomes the input for the next. This is what "not independent as operations" means: top-p operates not on the model's original distribution, but on the one that resulted after temperature. Therefore, the meaning of top-p changes depending on Temperature, even though the definition of top-p itself does not mention temperature.

In vLLM (V1 sampler), the order of application is fixed and described in the official documentation of the vllm.v1.sample.sampler module: first, penalties are applied (penalties), then within the sample method – temperature, then min-p, then top-k and/or top-p, and finally – the sampling itself. Source: https://docs.vllm.ai/en/v0.14.0/api/vllm/v1/sample/sampler/

2.5. Why Default Values in vLLM Are Actually "Disabled"

Quite often, you see logic like this: "The documentation says top_k = -1, top_p = 1.0, min_p = 0.0 – so these are neutral values, let them be." At first glance, this seems reasonable: default values are usually perceived as "average settings" that the VLLM developers chose as a safe compromise. But in the case of sampling parameters, this is not true – and this is where one of the most common mistakes in production lies.

2.6. What These Values Actually Mean

The default values in vLLM are not "average settings" but flags to disable the corresponding filter:

  • top_k = -1 means "consider all tokens," i.e., do not filter by count.

  • top_p = 1.0 means "consider all tokens," i.e., do not filter by probability mass.

  • min_p = 0.0 means "disable relative threshold," i.e., do not filter by comparison to the leader.

Let's consider a specific case with all sampling parameters disabled (I suggest you guess what will ultimately happen yourself).


In vLLM, a temperature of one is a neutral value: it neither compresses nor stretches the distribution; you simply sample from the distribution the model provided, without modifications. Let's analyze:

  • Temperature is neutral – the distribution does not change.

  • Top-k is disabled – no tokens are discarded by count.

  • Top-p is disabled – no tail is cut off by mass.

  • Min-p is disabled – no relative threshold is applied.

Result: you are sampling from the full, unchanged distribution over the entire vocabulary. Every token – including those with a probability of 0.0001 – has a non-zero chance of being selected. This is "pure sampling": no filters, except possibly penalties (which are applied earlier and to logits, not for cutoff).

Next, we will discuss four sampling parameters and analyze an example with parameter conflicts.

3. Sampling Parameters: The Four Main Ones

Let's break down the four parameters that are most common in configurations: temperature, top-k, top-p, and min-p.

3.1. Temperature

Temperature divides all logits by T before softmax:

Logits are "scores" that the model assigns to each token. The difference in scores determines how much more probable one token is than another. Temperature is a regulator that stretches or compresses this difference. Dividing by T < 1 stretches the difference, making the leader even more dominant. Dividing by T > 1 compresses the difference, making all tokens more "equal."

Consequently, the higher the temperature, the more stochastic the token selection becomes, and the more diverse – but less predictable – the response. The lower the temperature, the closer the generation is to deterministic, and the higher the reproducibility. For tasks where accuracy and reliance on sources are important (e.g., RAG), low temperature is preferred; for creative tasks, high temperature is preferred.

3.2. Top-k

Top-k keeps only the k tokens with the highest logits, assigning zero probability to the rest:

Top-k is a strict counter: "take exactly k best candidates and cut off all others, regardless of how confident the model is." If k=50, then exactly 50 tokens will always participate in the selection – whether the distribution is sharp (where 2-3 leaders are actually competing) or flat (where dozens have a chance). The threshold here is not probability, but position in the sorted list.

3.3. Top-p

Top-p sorts tokens by decreasing probability, accumulates probabilities from top to bottom, and stops at the first token where the cumulative sum reaches p:

Top-p is no longer a counter, but a "probability mass budget": "keep as many tokens as needed so that they collectively account for pp percent of the model's confidence." With a sharp distribution (the model is confident), 95% of the mass is accumulated by 2-3 tokens – and top-p keeps 2-3. With a flat distribution (the model is confused), the same 95% is accumulated by dozens of tokens – and top-p keeps dozens.

3.4. Min-p

Min-p keeps tokens whose probability is not less than a relative threshold tied to the leader's probability:

Min-p is a "threshold relative to the leader": "keep tokens that are not too far behind the most probable one." If the model is confident (p max​ is high), the threshold p min⁡ * p max⁡ becomes high – and min-p cuts aggressively, leaving only close competitors to the leader. If the model is confused (p max​​ is low), the threshold drops with it – and the nucleus expands, allowing more alternatives. Here, unlike top-p, the threshold is not absolute but relative: it scales with the model's confidence.

min-p is an attempt to solve the main weakness of top-p: sensitivity to temperature.

5. Dynamic Adjustment of Sampling Parameters

The inference engine sets a safe baseline and boundaries, while the application layer (in our case, OpenWebUI filters) gets the right to dynamically override parameters depending on the query context, which is unavailable to the engine.

5.1. Why Static Configuration Is Insufficient

The hierarchy of priorities in vLLM (request → server launch parameters → model's generation_config.json → defaults) and in OpenWebUI (model → account → chat) allows for flexible parameter management but doesn't account for the query mode. The same engine serves RAG, where the model must follow extracted documents, reasoning, where it must explore the solution space, and creative tasks. Fixing parameters at the engine level means depriving the application of the ability to switch modes; leaving it all to the user means getting irreproducible configurations. Dynamic overriding at the application level bridges this gap: the inlet() filter sees tool_ids and mode flags before sending the request and can consistently set parameters that will go to the engine as parameters for a specific request.

5.2. Policy for Modes

The key idea is a policy table that associates each mode with a consistent set of parameters, rather than individual "knobs." For three modes, the policy might look like this:

  • RAG enabled: low temperature (≈0.15), moderate top_p (≈0.9), top_k = 20 – the model should rely on documents, not "fantasize." Reasoning, if also active, does not change these values: reasoning should not lead away from the sources.

  • Reasoning without RAG: slightly higher temperature (≈0.3), top_p ≈ 0.8, top_k = 20 – some variability is allowed, but coherence should be maintained.

  • Neither RAG nor reasoning: parameters are not overridden; default values at the model or engine level are used.

  • And so on (everything is limited only by your imagination)

It's important to note that these are approximate figures, and the actual numbers will vary depending on the chosen model. The code below is also demonstrative.

5.3. Implementation

Go to Open WebUI → Admin Panel → Functions → Create:

""" 
title: Dynamic Sampling Policy
author: tnv
description: >
    Dynamically selects sampling parameters based on query mode:
    detects RAG presence (via tool_ids) and reasoning (via flag in
    chat_template_kwargs) and overrides temperature, top_p, top_k
    and penalties with a consistent set. Logs decisions, is idempotent,
    and passes the request through unchanged on error.
version: 1.0.0
icon: *
"""

import logging
from typing import Optional

from pydantic import BaseModel, Field

logger = logging.getLogger(__name__)

# Mode -> consistent set of parameters.
POLICY = {
    (True, False): {"temperature": 0.15, "top_p": 0.9, "top_k": 20,
                    "presence_penalty": 0.0, "frequency_penalty": 0.0},
    (True, True):  {"temperature": 0.15, "top_p": 0.9, "top_k": 20,
                    "presence_penalty": 0.0, "frequency_penalty": 0.0},
    (False, True): {"temperature": 0.3,  "top_p": 0.8, "top_k": 20,
                    "presence_penalty": 0.0, "frequency_penalty": 0.0},
    (False, False): None,  # do not override anything
}


class Filter:
    class Valves(BaseModel):
        priority: int = Field(default=0, description="Execution order")
        log_decisions: bool = Field(default=True, description="Log decisions")

    def __init__(self):
        self.valves = self.Valves()

    def _rag_is_active(self, body: dict) -> bool:
        tool_ids = body.get("tool_ids") or []
        return any("rag-search" in str(t) for t in tool_ids)

    def _reasoning_is_active(self, body: dict) -> bool:
        kwargs = body.get("chat_template_kwargs") or {}
        if kwargs.get("enable_thinking") is False:
            return False
        if kwargs.get("enable_thinking") is True:
            return True
        if kwargs.get("reasoning_effort"):
            return True
        return bool(body.get("reasoning"))

    async def inlet(self, body: dict, __user__: Optional[dict] = None) -> dict:
        try:
            rag = self._rag_is_active(body)
            reasoning = self._reasoning_is_active(body)
            policy = POLICY.get((rag, reasoning))

            if policy is None:
                if self.valves.log_decisions:
                    logger.info("sampling policy: rag=%s reasoning=%s -> default",
                                rag, reasoning)
                return body

            body.update(policy)

            if self.valves.log_decisions:
                logger.info("sampling policy: rag=%s reasoning=%s -> %s",
                            rag, reasoning, policy)
            return body
        except Exception:
            logger.critical("sampling policy filter failed; passing through", exc_info=True)
            return body

The provided filter is not "another setting on top," but a minimal framework for a dynamic sampling policy. Its value lies not in specific numbers, but in architectural decisions that are easily transferable and scalable to any stack.
