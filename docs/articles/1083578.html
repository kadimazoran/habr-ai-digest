What the model produced in one go

The llm output = seven files, and this is a build system:

logic.cjs: contains pure functions: event routing, admission calculation, response formatting, API validation. They are extracted from n8n nodes specifically for testing without n8n;

build.cjs - this is the builder itself: it reads the live workflow export, embeds functions into codenodes, adds 15 new ones, writes the finished JSON, and keeps a backup of the source (and refuses to overwrite it if it differs = protection against overwriting);

test.cjs: contains 16 tests on a real webhook payload;

README.md: this is a file "ANALYSIS OF THE COMMENT BRANCH" of 38 KB, where the model itself identified its shortcomings.

Final JSON: all original nodes without changes + 15 new ones. Imported inactive, webhook paths preserved.

Architecture in 60 seconds

```json
Webhook (Direct and Comments come into the same Meta stream)
  └─ IG: Route Events (Code)     — distributes igEventKind: direct / comment
      ├─ direct → old Direct branch (untouched)
      └─ comment → One At A Time (loop, batch of 1)
            → Prepare (admission: on/off, test-gate, blacklist, 7-day window)
            → Eligible? → Claim (Redis INCR — atomic comment_id acquisition)
            → First Claim? → Record Pending (log in Redis)
            → AI Agent (models and tools common with Direct, separate memory per node)
            → Prepare Reply (tag cleaning, fallback, 900 character limit)
            → Send Private Reply → Validate API Result → Record Accepted
            → back to the loop for the next comment
```

I want to explain three decisions separately, which in my opinion are the strongest in this build:

1. Private Reply is addressed by comment, not by user. Request body:

```json
{
  "recipient": { "comment_id": "18120835172314431" },
  "message": { "text": "Reply to client" }
}
```

One comment = one private reply, 7-day window, no public reply under the post. Continuation of the conversation - only when the person writes in direct, and this is already a separate execution of the old branch, not a tricky transition between agents.

2. Deduplication via Redis INCR, not GET-SET. If two executions hit the same comment simultaneously, both will see "key not found" and both will send a reply. INCR is atomic: 1 - mine, 2+ - already taken.

3. The philosophy of "we won't send twice" is more important than "we will definitely send." An error after capturing a comment blocks auto-repeat: the key remains in Redis - meaning the agent won't write a second time, you'll have to sort it out manually. A conscious exchange of delivery guarantee for absence of duplicates, so to speak = for an atelier agent, this is the right exchange.

By the way, a pleasant bonus confirmed by a live run: the comment author ID and the Direct sender ID are the same)). This means the memory key XXX_ig:{userId} is common to both branches: comment - private reply - person writes in direct - agent remembers what the comment was about. More on this in test run 1.1, where I almost buried this beautiful scheme with my own output.

Audit: where the hidden "flaws" were hiding

I didn't believe any green checkmark - skepticism or distrust, and simply fear :-) I reviewed the rebuild from sources (matched the output JSON byte for byte, except for random IDs), 16 tests, syntax of all Code nodes, and most importantly, ran the function directly from the JSON simulating n8n inputs. Results: the build is honest, all original nodes are untouched. But there were findings:

Finding (number)

What's the "catch"

1

The branch prompt = a copy of the Direct prompt of 12,000 characters with VERDICT/TASK/STAGE tags. A separate scenario for "+"/price/date of birth is in the ANALYSIS (!), but not included in the JSON; the agent would reply to the comment "as in direct," including technical tags.

2

With test mode disabled, users from the Direct blacklist would receive replies under posts because the "Blacklist" node is not executed on the new route... meaning a client banned in direct would receive care in comments.

3

Response cleaning catches [TASK:NONE] but misses [END_DIALOG] (tag without a colon). Technical garbage will reach the client's private message.

4

Private Reply is set to Graph API v25.0, while in the client's workflow, direct nodes run on the proven v22.0 (a minor thing, but still).

5

The hardcoded business account ID was taken from the test data and did not match the real one from the live webhook = with this constant, 100% of real comments would be silently discarded.

6

The allowlist was compiled from the Direct "Test Account" node ID, but the real test user was not included; in the fixture, the model concatenated the username with someone else's ID, and as a result, it would be like this: the agent silently ignores the comment = and not a single checkmark would turn red.

Separate honesty about myself: after run 1, I put forward one hypothesis: the commenter ID and the direct ID live in different spaces, shared memory will not work. Run 1.1 killed it in five minutes: I wrote in direct and in comments from the same account, and as a result: the IDs matched to the last digit. Hypothesis withdrawn. Moral of the story: constants from fixtures and beautiful theories are verified only by live runs, and this is true for both the model and the auditor.

Code: what ultimately went into "battle"

Event Router - this is the very first node after the webhook. Compact version of the production version:

```js
const accountId = String(entry.id);
const chatId = String(v.from?.id || '');
const commentId = String(v.id || '');

// Only our business account — REAL ID from live webhook, not from fixture
if (accountId !== '17841479739340657') continue;
// Echo loop (don't reply to ourselves) and empty author
if (!chatId || chatId === accountId) continue;
// IDs — only digit strings: JSON number > 2^53 is silently rounded
if (!/^\\d+$/.test(chatId) || !/^\\d+$/.test(commentId)) continue;

// Live text, FEED/REELS posts, not a nested reply, not a deletion
if (typeof v.text !== 'string' || !v.text.trim()) continue;
if (!v.media || !['FEED', 'REELS'].includes(v.media.media_product_type)) continue;
if (v.parent_id || v.verb === 'remove' || v.verb === 'delete') continue;
```

Admission (Prepare, production version) - a config that closed findings 1, 2, 6 in one move:

```js
const config = {
  commentsEnabled: true,
  testMode: false,                     // production mode: reply to everyone
  allowedUserIds: ['936850522443774', '826426153486930'],      // test gate for the future
  blacklistedUserIds: ['1344359104565035', '1686784379107626'], // blacklist from Direct
  activePrompt: SHORT_BRANCH_PROMPT  // ~1.3K characters instead of a copy of ~12K
};
```

And inside prepare, three lines that are worth the entire admission system:

```js
const allowed = config.commentsEnabled === true &&
  (!config.testMode || config.allowedUserIds.includes(j.chatId)) &&
  !(config.blacklistedUserIds || []).includes(j.chatId);
```

Response cleaning before sending = the model knows markdown, and NEIZYAGRAM knows plain text:

```js
text = text.replace(/```[\s\S]*?```/g, '')                    // code blocks
  .replace(/\b([^\]]+)\)((https?:\/\/[^)]+))\)/g, '$1: $2')   // [text](url) → text: url
  .replace(/\b[A-Z_]{2,}(?::[^\\\]]*)?\b/gi, '')                // [TASK:NONE] and [END_DIALOG]
  .replace(/\*\*(.*?)\*\*/g, '$1').trim();
if (!text || Array.from(text).length > 900) text = FALLBACK_TEXT;  // Instagram limit
```

Yes, by the way, the last line is the very protection that fired in run 2: the agent crashed, but I still received a polite placeholder in direct instead of silence or raw technical garbage. The protection did exactly what it was written for.

Three runs

Run 1. Everything is green... BUT... zero result

I imported it, left a comment under a reel on the test account. The execution is green, nodes have checkmarks, but it ended at Comments: Eligible?. No reply in my private message.

Well, that happens in n8n: execution didn't crash = it honestly fulfilled the design, which didn't match the intention. I read the input of Eligible?, and there's a ready verdict: skipReason: DISABLED_OR_NOT_ALLOWLISTED. The model's test gate was built from the Direct "Test Account" node ID = my real test user was not on this list (finding number 6 in the table above). At the same time, finding 5 from the table surfaced: the hardcoded account ID from the fixture does not equal the real one from the webhook = the guard with that constant would have dropped everything.

It's fixed not by debugging, but by reading one line of skipReason and editing the config (Prepare v2 above). About half an hour)

Run 1.1. Five minutes that killed my hypothesis

I write in direct and in comments from the same account. I look at the router's output: sender.id in Direct = 1385828923330271, chatId of the comment = 1385828923330271. Perfect match. The hypothesis about "different ID spaces" is dead, shared memory is legitimate, the model's architecture turned out to be more accurate than its "auditor's" output. Super).

Run 2. Bad request - and the "bomb" I planted myself

I write the second comment. Gate passed, keys acquired, agent processed, sending... and... damn:

```text
Failed to send private reply to comment 18120835172314431
for account 17841479739340657: Bad request - please check your parameters
```

Two failures in one execution.

First, the AI agent itself. The fallback model mode was enabled in the branch code, but the second model itself was not created and therefore the sub-node was not connected. The agent crashed, and the protection kicked in: in Prepare Reply, an empty and non-standard response is replaced with a placeholder. I received a polite "Hello!✨ Thank you for your comment..." in direct - instead of emptiness or raw JSON. The protection did exactly what it was designed for.

Second - the sending. Meta rejected the request itself. The Community node swallows the raw Graph API response, showing only "Bad request" - there's nothing to diagnose, I'll use curl. And the reason turned out to be funnier than any bug: the client's credit card was in the node, and I was testing on my own test account. The client's token physically cannot respond to my account's comments = Meta saw a "stranger" and politely sent me away with a 400.

Here it is, the very "safe sandbox" I chose at the beginning, so as not to break anything for the client. The decision was correct, but its execution was not: by moving the build into isolation, I forgot to move the context - the credential should have moved with it. The first "bomb" that I didn't account for was laid by my own hands. The AI has nothing to do with it.

Run 3. Victory)

Correct credential in the node, fallback model connected - and the chain went through: admission - acquisition - log - agent - sending - validation - result recording. The private reply arrived in direct.
