Why a New Notation Was Needed

Each generation of computing technology has its own scarce resource that engineers learn to measure and optimize. Big-O notation provided a common language to assess how an algorithm's memory and time requirements grow with increasing input size. Later, this approach was adapted for other bottlenecks: API calls per unit of time, outbound traffic, and cloud resources, which were crucial for a company's economic viability. For large language models, the scarce resource is the token.

Complexity analysis methods have been applied to AI before, but almost always in the context of training: the cost of training a model. How many tokens a model consumes for each response to a query within a given workload is a different question, and until now, it lacked its own terminology. Big-T Notation aims to create this. 

What the Approach is Based On and How Much to Trust It

The framework is based on research from Flexpa and the MIT CSAIL lab. They studied how LLMs search and retrieve information, as well as the experience of using model routing, caching, and input data serialization.

A brief digression for those who (like me) need a refresher on Big-O notation

Big-O is a way to describe how the runtime (or memory) of an algorithm grows as the input data increases. It's not the exact time in seconds, but the nature of the growth. For example, the notation helps answer the question: how many times longer will a function take to execute if the number of elements increases from 10 to 1,000,000.

Big-T Notation

n - is either the number of requests, the size of each request, or both simultaneously

k - is the number of model calls per request

a - is the depth of the agent tree (chain)

Big-T notation, similar to Big-O, helps classify workloads by how token consumption grows with increased usage, task complexity, or agent autonomy.

The author honestly admits that the notation they propose is not a formal mathematical system; it lacks theorems and proofs. The input values are not precisely defined—they can represent the number of requests, the volume, or both.

Let's examine the complexity classes presented by the author as a ladder. For easier understanding, I've added an example to each class, as if it were about employees rather than AI agents.

The Ladder of Complexity Classes

The key metaphor of Big-T is a "ladder" of classes, ordered by the rate of token consumption growth:

  • T(1) — Constant. The model is not called for every request (e.g., cache, static response) — analogous to O(1).

    Example:

    To prevent new guests and employees from repeatedly asking for the Wi-Fi password, the answer is posted as a sticker on the door. No employee is bothered, and the question never reaches them. No matter how many people ask, the employee's time spent is constant.

  • T(log n) — Sub-linear growth. This is a class that organizations often overlook: a properly constructed RAG where deterministic filtering (e.g., using SQL, embedding search) prunes excess data before it's sent to the model. The author provides an example: compressing data volume from ~240,000 to ~19,000 tokens via SQL filtering and reducing a million-item corpus to a few hundred relevant tokens during search.

    Example:

    An assistant receives a request like "find the contract with client X." Instead of sifting through all the archive folders, the employee goes directly to the correct cabinet, shelf, and folder. Even if the archive grows from 1,000 to 100,000 documents, the employee finds the necessary one in a few steps because they searched systematically, not by brute force.

  • T(n) — Linear growth. This is the baseline assumption for most budgeting models: tokens grow proportionally to the number of requests. A hidden fixed overhead is noted, such as loading the agent's entire tool catalog into context with each call, even if no tools are used. However, it's crucial to ensure that fixed costs don't eventually exceed the useful payload.

    Example:

    A typical first-line support operator: a new client means a new call; double the clients mean double the working hours. A fair, direct proportion with no surprises.

  • T(n·k) — Multiplicative growth. 'k' is the invisible multiplier: "deep thinking" models can consume hundreds of thousands of tokens for a few hundred tokens of visible output. Another driver is tool compatibility: if the output of one step cannot be directly passed to the next, the agent re-evaluates the entire accumulated context at each step. A five-step chain can cost 10–20 times more than achieving the same result through a single generalized call.

    Example:

    A support agent with a poor memory: before each new client message, the operator re-reads the entire conversation from the beginning, including everything the client has already said. Additionally, they "think aloud," verbalizing their doubts before giving a short answer. Visually, it's the same dialogue as a regular operator, but in reality, each message takes significantly more time than it appears.

  • T(n·k·a) — Agents as a growth multiplier. The depth of the agent tree ('a') is added. A developer working with multiple agent windows, where sub-agents within each window perform a list of tasks, consumes n×k×a tokens, where *a* is the depth of the agent tree.

    Example:

    A senior support operator has three assistants, and they pass every client request to all three "just in case." Each hierarchy level replicates the work model from T(n·k). The task is the same, but now it's multiplied by the depth of this coordination tree, even though from the client's perspective, they asked a single, simple question.

  • T(∞) — Unbounded growth. Production systems without cycle interruption, where token consumption is theoretically unlimited.

    Example:

    An initiative-taking employee who is never told when to stop and whose budget is not monitored. They could spend a week trying to solve a simple problem using thousands of inefficient methods, and no one would raise an alarm because there's no deadline, no limit, and no one to say "enough."

Let's look at an example of how user requests are processed in Yandex AI Studio, with a screenshot from a webinar on token billing. 

On the left, we see the user's question ("When are bridges raised in St. Petersburg in 2026") and a single response. From the outside, it appears as a single model interaction. This is how the complexity class concealment, mentioned by the Big-T author, works: the interaction format doesn't reveal how much is actually happening internally.

The colors, by the way, denote different SKUs (price points) for requests, corresponding to the price list:

  • purple — incoming request tokens and partially cached tokens;

  • green — outgoing model response tokens;

  • orange — tool tokens passed to the model as a result of calling a tool.

    Step 1 — basic T(n): request + full tool catalog. You pay for input tokens and cached tokens

    The Responses API sends not only the user's message to the LLM but also the entire list of available tools—websearch, filesearch, mcp_tool1—with their schemas, even if not all are ultimately needed. This is precisely the "hidden fixed overhead" within T(n): each call carries the entire tool catalog, regardless of what will actually be used.

    Step 2 — LLM decides which tools to use. You pay for tool calls and their consumption

    The first model interaction returns not an answer, but three tool calls. Three tools perform the work in parallel, each with its own counter for the request unit and the volume of processed data.

    Step 3 — Second model interaction: re-reading the updated context. You pay for tool tokens

    This is the point where n=1 (a single user query) is multiplied by k=2. The results of the tools are returned to the model along with the context.

    The three results (text from web search, file list, "OK" from mcp) are not sent directly to the user; they must be sent back to the LLM, along with the original context (message, instructions, tool outputs), for the model to generate a coherent natural language response. This is the second full pass through the model for a single user query—exactly what the Big-T author describes as "at each intermediate step, the agent returns, interprets the result, and makes a new call, reloading the context." Only here it happens once, so the multiplier is moderate, but it exists. Imagine a situation where tools operate sequentially, passing information between each other, and there are not 3, but significantly more.

    Potential transition to T(n·k·a)

    The caption under the diagram states: "tool calls occur in a loop based on the LLM's decision." This is an important detail—if the results of the first round were insufficient (e.g., file search didn't find the required file), the LLM could initiate another round of tool calls instead of stopping at one. Then, n=1 user request would turn not into a fixed k=2, but into a variable loop depth—potentially T(n·k·a), where 'a' is the depth of these "call → result → call again" iterations.

    Step 4 — LLM outputs the solution in the specified format. You pay for output tokens 

    Thus, even a well-designed agent call with parallel tool invocations at least doubles the number of model passes and adds separate counters for each tool. This complexity is hidden behind the flat dialogue interface that the user sees.

Five Levers for Savings

In notations, it's important to distinguish between the dependency class and the multiplier. The former affects the nature (shape) of the dependency, while the latter affects the slope. Understanding the dependency graph allows for a visual representation of the effect of proposed tools.

Questions to help identify optimization opportunities:

What complexity class does this workload belong to? 

This is an architectural decision, and it can only be changed at the architectural level. Complexity classes themselves are neither good nor bad; they simply reflect where the system's complexity lies.

How cheaply is it executed within its class? 

Note that quality is an input requirement, not a comparison parameter. That is, the models you choose between must be capable of handling the task.

Solutions for data compression, routing between models, caching, and serialization are about manipulating the coefficient, not the Big-T class: they make the same action cheaper but don't change how token consumption scales with increasing load. In this sense, Big-T behaves like Big-O, which also ignores constants.

However, there's a crucial difference. Big-O typically has a small range of constants—asymptotics are interesting precisely because they stop solving anything as 'n' grows. Tokenomics is different: the price range per token between model versions of the same generation can be 5–20 times, so "simply" optimizing the coefficient can save the budget by an order of magnitude—without a single architectural change.

Reference Architecture: The Token Efficiency Pipeline

The five levers form a pipeline where each layer reduces the load for the next, and the effective Big-T complexity decreases as the request moves through the stack:

  1. Deterministic preprocessing — SQL filters, regex, structural transformations. Helps reduce complexity to T(log n).

  2. Cache check — semantic cache and prompt prefix cache. On a hit, the response is returned in T(1), bypassing lower layers.

  3. Model router — classifies task complexity and directs it to an appropriate model tier.

  4. Prompt architecture — serialization optimization, deduplication of system prompts, output format constraints.

  5. Inference (model query) — only the necessary minimum of tokens reaches the model.

  6. Output mode selection — direct response for simple tasks; code generation for batch operations. This reduces the multiplicative factor by shifting the main workload from expensive LLM inference to executing generated code.

All six layers are covered by cost monitoring tools: telemetry, tagging, budget thresholds—without conscious data collection on consumption, no layer can be measured, and thus optimization is difficult to assess.

Self-Assessment Checklist

Big-T proposes a self-assessment across seven areas:

  1. Visibility. Do you know token consumption broken down by models, workloads, and costs?

  2. Model Router. Do you direct each task to the cheapest model capable of solving it?

  3. Prompt Hygiene. Does every token sent perform useful work?

  4. Caching Strategy. Have you reduced the cost of frequently recurring workloads to a constant using a cache?

  5. Cost Allocation. Can you attribute token costs to specific teams and projects?

  6. Abstraction Audit. Do credit-based (points) or seat-based contracts obscure the cost of individual workloads?

  7. Governance Model. Do you have automatic limits and budget thresholds?

Is Big-T Worth Considering?

Pros. The vocabulary is genuinely useful: even a non-rigorous notation provides a common language for the team to discuss "this workload is multiplicative, and that one is linear" instead of the vague "AI is expensive." The observation about concealment is truly important: the token consumption class of an agent system isn't visible in the request itself but is only revealed in post-factum billing, which the actual price list confirms literally.

Cons. The analogy with Big-O is elegant but flawed: Big-O has rigorous mathematics, while Big-T's "n" is a deliberately imprecise variable, as the author admits. Much of the content covers what practicing ML/platform engineers already intuitively know: cache stable prompts, route by models, monitor hidden "thinking" tokens. It's a positional and, to some extent, marketing document rather than a scientific work, with a market objective—to stake a claim on terminology.

Conclusion

Big-T is not a rigorous notation in the spirit of Big-O, but an attempt to give the industry a common vocabulary for discussing how token costs grow with increased usage, complexity, and agent autonomy. As a checklist for architectural reviews, it's a practical tool: it forces explicit questions like "what is the complexity class of this workload and is it justified by the value it brings?" before it becomes a surprise on the provider's bill.
