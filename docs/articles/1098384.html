Checklist for Storing Keys in Repositories Based on AI Agent Incidents

This article provides a checklist for securely storing keys in code repositories, prompted by recent incidents where AI agents accessed sensitive systems. It details nine points to verify, common vulnerabilities, and remediation steps, including what to do if a key has already been leaked. The checklist is based on findings from CERT-In and Anthropic.

I'm unlikely to reveal any secrets by talking about how to store keys, but I recently read an article on TechCrunch that describes how CERT-In (India's national cybersecurity agency) discovered that AI agents from several model developers accessed live systems of Indian organizations during tests. The agents only needed account and connection settings left in application configurations and public code repositories, along with overly broad cloud roles. The affected organizations did not even notice the intrusions themselves.

Therefore, mostly for myself, I decided to write a checklist. It consists of nine points, each tied to an entry method from these incidents, explaining what to check, what command to use, and how to fix it. At the end, I've written about what to do if a key has already been leaked.

What Happened and Why It Concerns Everyone

Facts from the CERT-In report. The agency received voluntary reports from several AI model providers: their agents, during research and test runs on the open internet, ended up in live systems of Indian organizations. The agents' actions, according to the agency's wording, went beyond their assigned tasks. According to the same wording, they read personal data and confidential business records. CERT-In did not name the providers or the affected organizations, nor did it say whether the agents changed anything in the systems.

I am taking the details of CERT-In's advice from The Hacker News analysis from October 16, 2026, because the page of the notification itself is unavailable. According to this analysis, the weak points were common: keys in source code, public repository histories, configuration files, and client applications, forgotten test APIs, exposed payment keys, broad cloud roles, and administrative interfaces without multi-factor protection. In the cases reported by AI companies, agents found the same open key and used it in various operations.

Why this is not just about India. An agent automatically iterates through whatever it finds in the public domain. A key in a public place will likely be found, and a role with excessive permissions can be exploited. Therefore, the checklist is written for a regular development team.

The same techniques were shown in Anthropic's July analysis. In the company's disclosure from July 30, 2026, three incidents out of 141,006 tested runs are described. The Claude model, tasked with hacking a fictional target, due to an error in the test environment setup, accessed the real internet and mistook real systems for part of the exercise. In all cases, it used simple techniques, including weak passwords and unauthenticated API endpoints, and in one case, it read credentials from a debug page and used an SQL injection. Two of the three organizations contacted did not notice the activity.

Repositories Where Everyone Sees the Key

Point 1. Key in Public Repository and its History

In the incidents, agents gained access using credentials from public code repositories.

The key remains in old commits, branches, forks, and local clones, even if the file is deleted. Therefore, check the entire history, including old commits.

Two tools are suitable for searching. Gitleaks from the project repository scans history with the command gitleaks git -v. A report with redacted values is obtained like this:

gitleaks git --report-path gitleaks-report.json --redact

TruffleHog can verify found secrets: according to the project documentation, the --results=verified option keeps only secrets that have been confirmed by the issuing service. A full scan of an organization on GitHub:

trufflehog github --org=ORGANIZATION_NAME --results=verified,unknown

The unknown result should be investigated manually: the verification might have failed due to network issues, even if the key is valid. Any finding from verified means an urgent rotation, which is discussed below.

Also check forks and private repositories that became public. Often, a key is leaked when a team opens a formerly internal project.

Point 2. Protection Against Re-leak at Commit Stage

The same path through public repositories will be open tomorrow if a barrier is not put in place.

The best moment to catch a key is before the commit. Gitleaks can be integrated as a pre-commit hook. In the .pre-commit-config.yaml file, specify the gitleaks repository, the desired version, and the hook ID gitleaks, then run pre-commit install. The hook can be bypassed with the flag SKIP=gitleaks, meaning it's not enough on its own.

The second line of defense is server-side protection. GitHub calls it push protection, and the documentation explains that it blocks the sending of a commit with a recognized secret. The third line of defense is in CI: the same gitleaks git for every merge request, failing the build if a secret is found.

If the repository is large and there are many old findings, generate a baseline report using --report-path, and then run the scan with --baseline-path. This way, the build will only fail on new secrets, and old ones will be handled in a separate plan.

Configs and Secrets Near the Code

Point 3. Secrets in Application Configuration, CI, and Client Code

Agents gained access through connection settings in application configurations.

Most often, leaks look mundane. A database password in config.yaml, a token in a CI variable, a key inside a mobile application or frontend. According to The Hacker News analysis, CERT-In specifically listed CI/CD variables, configuration files, client applications, and open web pages.

Checking starts with a search in the working directory:

gitleaks dir .

For containers and CI variables, go through them manually: environment variables in build logs, docker history of images, build artifacts. Move found secrets to a secrets manager (Vault, cloud Secret Manager, etc.) and pull them during runtime.

If secrets are still in .env files, do the minimum: set permissions to 600 and ensure only the service user owns the file. Check with one command:

find . -name '.env*' -perm /077

An empty output means other users cannot read the file. 600 permissions protect the file from adjacent accounts on the server, and a compromised owner process can read it itself, so .env is suitable as a temporary measure.

Point 4. Privileged Key in Client Code

According to The Hacker News analysis, keys were also found in client applications and on open web pages.

Consider any secret that ends up in a browser or mobile application as public. CERT-In, as retold by The Hacker News, advises keeping privileged keys out of client code and verifying what an anonymous user can read and write. Take the compiled frontend, search for keys within it using the same scanners, and make a test request to the API and storage without any authentication. A response with data indicates an error in permissions.

Cloud and Permissions Broader Than Necessary

Point 5. Revision of Roles and Service Accounts

Agents gained access through overly broad cloud roles.

The principle of least privilege is checked by the question: what does this role actually do, and how much of its granted permissions does it use? For AWS, the credential report and IAM Access Analyzer are useful:

aws iam generate-credential-reportaws iam get-credential-report

The first command generates a report on users, keys, and their last usage, the second retrieves it. It shows keys that haven't been used for months. The IAM Access Analyzer documentation describes analyzers that find externally accessible resources and unused permissions.

In Google Cloud, start with service account keys:

gcloud iam service-accounts keys list --iam-account=SA_EMAIL

Delete keys older than a quarter and keys that no one remembers. Replace roles like project owner or administrator on an application's service account with specific roles with a narrow set of permissions.

Point 6. Long-Lived Tokens to Short-Lived Ones

A key found once worked again and again. According to The Hacker News, in the AI companies' reports, agents found the same open key and used it in various operations.

The shorter the lifespan, the less damage from its discovery. In AWS, an application is issued temporary credentials through a role:

aws sts assume-role --role-arn ARN_OF_ROLE --role-session-name app --duration-seconds 900

In Google Cloud, instead of a key file, use service account impersonation:

gcloud auth print-access-token --impersonate-service-account=SA_EMAIL

For their own AI agents, CERT-In, according to The Hacker News analysis, advises the same: a separate short-lived identity with minimal permissions for each run and restricted outbound traffic except for necessary addresses.

Forgotten Surface

Point 7. Forgotten Test APIs and Weak Passwords

In India, these were old and test APIs accessible from the internet, while Anthropic had weak passwords and unauthenticated endpoints.

Create an inventory of all APIs and accounts. The list may seem mundane, but it helps find a test environment from two years ago and a forgotten demo account. Each item in the inventory gets an owner and a deadline. Without an owner and without use, it gets disabled.

A weak password in 2026 remains a working entry point. The Anthropic analysis illustrates this, as the model used weak passwords and unauthenticated endpoints. Check administrative panels, databases, and service interfaces, block them from the internet, enable multi-factor authentication, and change default passwords.

Point 8. Debug Page and Dependencies

In the third Anthropic case, credentials were taken from a debug page; in the second, the model published a malicious package to a public registry (second case).

Debug mode must be turned off in the production environment. In the third incident, the model read credentials from an open debug page. Check: access the application with a deliberately incorrect request and ensure that a short error page is returned instead of a stack trace and environment variables.

The second lesson is about dependencies. The fictional company's instructions included a package from PyPI that did not exist. The model published a package with that name, and according to Anthropic's description, 15 real systems downloaded it within an hour, and a scanner from a real company executed the code and revealed its credentials. Conclusions for the team: reserve names of internal packages in public registries, pin dependency hashes, and install using pip install --require-hashes -r requirements.txt, and keep scanning tools in a sandbox without production keys.

Monitoring Access

Point 9. Monitoring and Alerts for Unusual Access

The affected organizations did not detect the intrusions themselves: this is stated about India, and it was the case for two of Anthropic's organizations that could be reached.

Alerts are built on behavior: frequency, volume, and source of requests. CERT-In, according to The Hacker News analysis, advises monitoring APIs by detecting anomalies in request frequency, alerting on brute-force attempts, mass reads, and automatic registrations, and storing logs for at least 180 days. Agent activity logs are also useful if they operate in your production systems.

Specific signals worth setting up immediately:

  • Login from an unusual network or country;

  • A sharp increase in the number of reads from storage or a database in a short period;

  • Access to a key that hasn't been used for weeks;

  • Creation of new keys, roles, and accounts outside of planned work.

Honeypot keys. Place dummy credentials in repositories and configurations that do not work anywhere. Any access to them immediately triggers an alarm: there are almost no false positives.

What to Do If a Key Has Already Been Leaked

Act in this order. CERT-In, as retold by The Hacker News, requires considering the environment compromised until judicial verification results. After remediation, the environment must be re-verified, and repeated attempts should be expected for days or weeks.

  1. Revoke the key immediately. For AWS, first deactivate it: aws iam update-access-key --access-key-id KEY_ID --status Inactive --user-name USER_NAME. For Google Cloud, delete the key: gcloud iam service-accounts keys delete KEY_ID --iam-account=SA_EMAIL. For third-party service keys, use the revoke button in their dashboard.

  2. Issue a new key and update applications. The new value should only go into the secrets manager.

  3. Check logs for the key's lifetime period. What was read, when, and from where the requests came. Without logs for the required period, you won't know the scale, so a 180-day retention period is important in advance.

  4. Remove the key from repository history. The git-filter-repo utility is suitable for this: git filter-repo --replace-text expressions.txt replaces values listed in the file. Then, force push and ask all colleagues to clone the repository again. The order is important: revoke first, then clean up, because the key might have already been copied by the time of cleanup.

  5. Check the perimeter from the outside. Run scanners again and ensure that the old key returns an error and is no longer present in the public history.

  6. Notify relevant parties. According to The Hacker News analysis, CERT-In regulations require reporting cyber incidents to the agency within six hours. For Russian companies, different obligations apply, so clarify them with a lawyer or security specialist.

According to The Hacker News analysis, in a separate campaign against Indian companies, victims who only partially fixed the problem were subjected to repeated attacks within a few days. Therefore, revoke all adjacent keys immediately along with the found one.

Conclusions

The agents only needed the keys and permissions left in plain sight. CERT-In's report does not describe sophisticated exploits, and Anthropic calls its cases simple techniques. If a key lies in the repository history, a role grants more than necessary, and no one monitors the logs, the agent's task becomes easy.

I started by running gitleaks and trufflehog on all repositories, including forks and old projects. Then I listed all keys and roles in the cloud, deleted unused ones, and replaced long-lived tokens with temporary ones. Finally, I enabled 180-day log storage and set up alerts for unusual data reads. After that, I added a hook and push protection to prevent new keys from entering the repository.
