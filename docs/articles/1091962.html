Investigating an incident involves a chain of interconnected decisions. First, you need to determine when the problem started, then understand which systems it affected, verify the initial hypothesis using metrics, logs, or traces, and finally, bring together all the collected data to establish the most probable root cause.

We built an agent workflow following the same pattern. Each step is responsible for its part of the investigation and passes the result to the next.

This structure works well until the final answer turns out to be incorrect. And then, it becomes almost impossible to understand at which stage everything went wrong. The first stage might have chosen the wrong time interval. The next might have prioritized the wrong suspect. And one of the subsequent stages might have missed a mandatory request and still produced a plausible summary.

This is exactly what we encountered when testing a multi-step agent workflow for incident investigation. A full pipeline run showed that a failure had occurred somewhere, but didn't reveal where. Furthermore, each such run took a long time, consumed tokens at all stages, and produced different results from run to run.

Therefore, we changed our testing approach, borrowing a principle from hardware bring-up: enable one stage, verify it with a clearly defined control check (gate), ensure it passes consistently, and only then connect the next one.

In this article, we will explain how this approach helped us localize failures to a specific stage, control the cost of each test run, and discover a problem where we least expected it – in the evaluation mechanism itself.

Why the final answer doesn't reveal where the workflow broke

The investigation pipeline consisted of a fixed sequence of stages:

  1. Determine the incident's time interval.

  2. Identify the most likely suspect and assess their priority.

  3. Corroborate the hypothesis with independent data from another data plane.

  4. Consolidate the evidence and formulate the answer.

Each stage receives the output of the previous one. Therefore, a flawed decision at the beginning of the workflow can affect all subsequent stages.

This is a typical compound AI architecture: the workflow itself is deterministic, but a non-deterministic model operates within each node.

If the final answer is incorrect, a full end-to-end run doesn't allow for a definitive cause. An early stage might have passed incorrect context forward. A later stage might have misinterpreted correct context. And the final answer might appear convincing while hiding an error in one of the intermediate stages.

Full runs also make the development cycle quite expensive:

  • Each stage consumes tokens and can generate multiple tool calls.

  • A full run takes minutes, not seconds.

  • With the same input, the next run might produce a different result.

The usual cycle of "run workflow, read execution log, change prompt, and run again" doesn't provide enough data for conclusions. A single successful result could mean the change worked, or it could be just a lucky outcome in a non-deterministic system.

We needed a way to localize failures without replacing the actual behavior of previous stages.

Starting with one stage and gradually adding more

The approach is built incrementally. At level N, we truly run stages 1 through N and stop before stage N+1.

Incremental approach. Step-by-step debugging is incremental. Previous stages at each level continue to execute live, while subsequent stages remain disabled until the current level consistently passes verification.

The cycle looks like this:

  1. Truncate the pipeline after the stage currently being tested.

  2. Run it and verify against a predefined success criterion.

  3. If the check fails, fix the current stage.

  4. Repeat the run until the stage consistently passes verification.

  5. Add the next stage and repeat the cycle.

This is not the same as testing each stage with fixed test data. If stage 3 depends on stages 1 and 2, it must handle the real variability of their results. A cached ideal result from stage 2 would simplify testing stage 3, but wouldn't reflect the workflow it would encounter in production.

Therefore, previous stages continue to run live. We save time and resources by cutting off all stages after the one being tested, including the branching of tool calls they generate.
