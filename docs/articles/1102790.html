There are many debates now about whether developers will be needed in the era of vibe coding. Even among developers, the opinion is gaining popularity that they have now become "meat proxies" between tasks and AI.

The introduction of AI into development often begins with a simple requirement: use agents and release features faster. But questions quickly arise: who checks how the agent understood the task, what decisions can be entrusted to it, and how to ensure that the new feature hasn't broken existing ones? In my projects, I've encountered both rapid delivery of working results and regressions, as well as multi-hour agent work cycles. Using these examples, I'll try to break down what requirements, limitations, and checks are needed for working with agents, and how this experience can be used in a team, and I'll also touch on how the role of developers is shifting in the era of AI agents.

How Requirements Affect Agent Decisions:

After some time developing projects through such vibe coding, one might get the impression that code and its quality can be neglected.

Contrary to popular belief, vibe coding doesn't mean that the code and architecture will be of low quality. As an example, I created a demo banking application:

https://github.com/Atreides07/DemoBank - The solution was generated in a couple of days from scratch and represents an example of a banking application in Flutter (without a backend, only a client application, but a demo HTTP client is present).

I set requirements for performance, feature reusability, and design system, and also organized result verification. I deliberately didn't specify the architecture, structure, etc., and the result was the following:

Modular layered architecture by features — feature-first, with Clean Architecture and ports-and-adapters principles.

  • Features: accounts, history, analytics, fines, and other services are separated into packages.

  • Layers: UI displays data, Cubit manages the scenario, repositories work with API and cache.

  • Domain: models, monetary rules, and common contracts are separated from Flutter, HTTP, and SQLite.

  • DI: dependencies are passed through constructors and assembled in application wrappers.

  • UI State: BLoC/Cubit with unidirectional data flow.

This is a practical adaptation of Clean Architecture: UI and API adapters can be in the same feature package, and separate use case classes are not created for simple calls.

AI Does Not Provide Instant Results

When discussing AI implementation, I often encounter the expectation that a textual description of a task will immediately turn into a ready-made change, often citing Lovable and its analogs as examples. In practice, you need to account for the time it takes to gather and clarify requirements, implement, test, and fix.

In the case of DemoBank, the time distribution turned out to be as follows:

≈27 hours 13 minutes - total Codex work on responses and solutions, including commands, builds, checks, and test runs.

A lot of time was spent on performance tests on a 10,000 ruble Android phone.

≈19 hours 20 minutes - actual occupied time, if overlapping agent work is counted only once.

This does not include my time investment (about 2-3 hours).

Even this small example shows that rapid code generation is only one stage of the process. For a team, it's more useful to measure the time from task assignment to accepted change, including reviews and refinements.

So, if an agent can write tests, design architecture, and write quality code, where is the developer needed?

Code and Development Process Quality.

The requirement "use AI and release changes faster" by itself does not define a new workflow. The team needs to understand who checks the interpretation of requirements, who makes technical decisions, and what checks are mandatory before merging. For example, an agent might implement a function that passes existing tests but violates a business scenario not covered by them. Analyzing such an error should lead to a specific change in the process: clarifying requirements, adding a check, or revising the acceptance procedure. Responsibility for the accepted change remains with the team, regardless of who wrote the code.

Before AI, I had to manage developers who asked to write all requirements at once. The need for clear requirements is normal. But even a detailed task description doesn't eliminate ambiguities, contradictions, and subsequent changes. A developer needs to be able to notice them and discuss the consequences with the business.

This is particularly noticeable when working with AI: an agent can implement a chosen interpretation of a task, including an erroneous one. Therefore, it's important to verify initial assumptions before they turn into a large volume of code. Part of the implementation work can be delegated to the agent, but the team must retain responsibility for the meaning of the requirements, technical constraints, and acceptance of the result. For this, you can use the same OpenSpec: document the change goal, requirements, behavior scenarios, and technical decisions in related documents.

In any case, when working with agents, the team needs to explicitly distribute responsibility for task assignment, technical constraints, and change acceptance. One person can combine multiple roles, but for each decision, there must be a clear responsible party.

For example, the product owner and analyst will agree on the expected behavior. The module owner checks the impact of the change on their contracts and constraints. Before implementation, the developer can check how the agent understood the task, what assumptions it made, and what questions remain open. This approach allows for discussing the specific interpretation of requirements before they appear in the code. The team determines what evidence is sufficient for acceptance.

By AI Harness, I mean the agent's working environment: project context, available tools, action limitations, automatic checks, and the process of transferring the result to a human.

For a specific task, the agent needs a goal, acceptance criteria, affected modules, applicable solutions, and a method for verifying the result. For parallel work, it's necessary to separately coordinate changes to common contracts, data schemas, and infrastructure. Isolated branches help separate work but don't eliminate semantic conflicts between solutions.

Rules and context also require an owner. Changes to interfaces and architectural decisions must be accompanied by updates to the corresponding documents within the same change, otherwise the next task will start with outdated assumptions.

Quality Gate.

The quality of code and projects in the AI era is much more important than before. As the codebase grows, automated checks become even more critical. Throughout my career, I've seen many projects with low test coverage, yet they managed to maintain a decent code and project quality for years through slow, thoughtful development and designing the codebase based on SOLID/DDD principles, even without TDD. However, SOLID, DDD, and TDD solve different design and development problems, but applying architectural principles does not replace verifying system behavior.

Checks that influence change acceptance must be run automatically and be mandatory for merging. A prompt like "run tests" might help the agent, but it doesn't guarantee this condition is met.

In one of my projects, the agent's work cycle continued for 40 hours until I stopped it manually. This case showed that the condition "continue until checks pass successfully" requires additional limitations. For such a cycle, a budget for time and expenses, as well as stopping conditions, must be defined in advance. For example, repeating the same error without new results should lead to an analysis of the cause. Upon stopping, the agent should report which checks are failing and what correction methods it has already tried.

If the cycle was forcibly stopped before achieving the result, an analysis of the causes must be conducted, and changes made to the process. Perhaps the task was misunderstood, perhaps the project map couldn't be read, or the map was outdated. Perhaps the chosen execution model was too weak for the chosen task. Instead of manually making corrections each time, one should think about how to fix the root problem so that the agent doesn't make such mistakes again. Expected results should be derived from agreed-upon business requirements, contracts, and invariants.

The Problem of Large Codebases, or Is Large Context Needed?

When working with a large codebase, the agent needs to find relevant components, contracts, and constraints. Increasing the context window expands the amount of available information, but it doesn't guarantee its correct use. For example, the Lost in the Middle study (https://arxiv.org/abs/2307.03172) showed the dependence of response quality on the position of the necessary information in the context for the studied models and tasks. Therefore, it's useful to check how well a specific agent handles your project's tasks. A module map, up-to-date contracts, and related ADRs help gather context for a specific change. Their value is determined by whether they allow finding the necessary information and considering constraints.

When working with agents, it's useful to define in advance where the up-to-date description of each aspect of the system is located. For example, an API contract can be stored in TypeSpec, and OpenAPI, reference documentation, and client code can be obtained through generation. Then, a change in a parameter or response format is made in one source, and the consistency of derived artifacts is checked in CI.

ADRs, in turn, store the rationale for architectural decisions and a link to the contract. If a decision is revised, the previous entry is marked as superseded and linked to the new one. This helps the agent distinguish current constraints from project history.

However, formal API descriptions are not enough to verify all guarantees. For example, a mandatory idempotency key can be described in the contract, but the absence of a double refund must be checked by a separate scenario. Therefore, the agent needs an up-to-date contract, applicable solutions, and verifiable behavioral requirements.

If the agent misses an important ADR or business rule, the reason must be investigated: the document might not have been included in the context, might contradict other instructions, or might not have been specific enough. After that, the context selection can be corrected, the documentation clarified, or an automated check for the corresponding constraint added.

Working with Architecture and Domains:

Continuing the example above, there are cases where an agent might make an incorrect architectural decision. For example, imagine a situation where an online store has a separate Order Management module (orders, items, cancellation conditions) and a Payments module (payments, protection against duplicates, refunds, interaction with the payment provider, etc.). If the project map is poorly defined, the agent might decide that the Order Management module can directly call the payment service API for cancellation. This would be dangerous because refunds would not be logged in the payment module's journals, leading to financial losses and/or other business problems. Such a workaround can occur even if your context is clearly defined.

And here, all your DDD design experience can be useful for separating domains. Additionally, you can and should define constraints in the development cycle with review by another model, but it's even better to use ready-made tools:

Architectural rules can be enforced by automated checks. For example, allow the orders module to access the public interface of the payments module, but prohibit dependencies on the payment system's API. Such rules are checked using the specific language's tools and architectural analysis tools (e.g., ArchUnit, ArchUnitNET, dependency-cruiser, etc.). The need to include the corresponding module in the implementation increases the chances that ADRs and MD files of the module will also be included in the agent's context.

However, it's important to understand the verification boundaries here. For example, a prohibition on dependencies between modules won't detect a direct HTTP request to the payment provider through a common network client. Therefore, it's useful to separate constraints: structural checks to control allowed dependencies, access settings to limit the ability to contact the provider, and behavior tests to verify that the refund goes through the intended scenario and that a corresponding entry appears in the payment module's journal.

Therefore, architectural review should cover dependencies, system behavior, and the relevance of the documents describing them.

Where to Start?

If you want to integrate AI into an existing large project with accumulated legacy, it makes sense to start with a limited class of tasks – for example, small enhancements in one module. On these, you can set up a workflow: task assignment, agent implementation, automatic checks, and review. It's equally important to agree within the team on who clarifies requirements, who makes technical decisions, and what checks are mandatory before merging. For the agent cycle, time and cost limitations are also needed.

Therefore, in my experience, the quality integration of AI into teams with established development processes is less painful: there is already up-to-date documentation, automated checks, and a clear process for accepting changes. If this is not the case, development may even slow down initially, as some effort will have to be directed towards project preparation and process setup.

In some projects, introducing an agent without quality requirements creates an illusion of acceleration due to rapid code generation: new features appear faster, but unnoticed regressions accumulate along with them, and subsequent changes require more and more time.

Therefore, the result of implementation should be evaluated by the total time from task assignment to accepted change, the cost of fixes, and the quality of the released product.
