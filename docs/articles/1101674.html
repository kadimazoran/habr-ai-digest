Transferring sessions between console AI agents without context loss

When a console AI agent's five-hour limit is reached mid-debug, you might want to switch to another agent that still has limits. The popular method of saving a summary to HANDOFF.md often fails: the model's retelling quality is poor, context details are lost, and you have to re-explain the task to the next agent (wasting extra tokens). In this article, we'll explore how to extract a live session from local logs without losing meaning and transfer it to another agent with a single command, or move your work, including unsaved files, to another PC. When I was developing a pipeline for translating entire books, I needed to use console agents from different providers for testing: Claude Code, Codex, and Antigravity CLI (agy). Since the leading neural networks from each provider are currently at a similar intelligence level, I had the idea to use them all for development itself. However, as all my subscriptions are cheap, $20 each, their five-hour quotas run out quickly – usually right in the middle of debugging. Along with this trio, open-source console agents Pi and Hermes are increasingly used – developers connect DeepSeek, GLM, Grok, and local neural networks through them when their main subscriptions' limits are exhausted. Therefore, it became necessary to organize a high-quality transfer of sessions between agents without diluting the meaning.

If you have a second paid Claude Code account, you can log in again and continue the dialogue with the standard --resume key. The session will be picked up from disk, although the server-side prompt cache will be reset when changing accounts, and re-uploading a long history will immediately consume a noticeable chunk of the new quota. But when the limits on all Claude accounts are exhausted and you need to switch to Codex, agy, Pi, or Hermes, there is no standard bridge.

The usual advice for such a situation is to ask the agent to record the current task state, steps taken, and plan into a HANDOFF.md file before quitting. In practice, this method is suboptimal for three reasons:

  1. Sudden Stop. When the five-hour limit is reached, the agent stops responding to requests. You can no longer ask it to summarize and write the file.

  2. Distortions in Retelling. Even if you catch the moment a couple of steps before the block, we force the neural network to retell its own history from memory. The input context window of modern models accommodates from two hundred thousand to a million tokens, while the maximum length of a single response is strictly limited to tens of thousands of tokens. Due to this ceiling, aggressive, compacting retelling is inevitable: precise launch command arguments, line numbers, rejected hypotheses, and minor edits disappear, and the quality of work in the next agent noticeably decreases.

  3. High Generation Cost. Output tokens are usually five times more expensive than input tokens from providers and burn through the remaining five-hour quota five times faster. Forcing the model to generate a long summary at the end of its limits is costly in terms of money and quota.

A second problem arises when limits are still available, but you need to get up from your Calculate Linux desktop and continue working on your laptop from the same spot. Uploading raw, non-compiling code to the main repository branch for this purpose is inconvenient, and many folders with scripts or configurations lack version control – or they use SVN or Fossil.

To extract context directly from the local files of one agent and transfer it losslessly to another agent on the same machine or over the network to another computer, I wrote an open-source console utility and skill in Go called baton. The tool works on Linux, macOS, and Windows and supports five console agents: claude, codex, agy, pi, and hermes.

How agents store history on disk

Each console agent maintains a detailed session log on disk in its own format. When the /compact command is executed, old replicas are not deleted from the file: logs are appended to, and at the moment of context compression, a record with a summary of the previous conversation is added to the stream.

Attempting to read such a log entirely and dump its contents into a new agent's chat window will lead to a crash. In half an hour of active debugging, the log can grow to tens of megabytes due to printed files and compiler outputs. Such a volume will immediately fill the new model's context window.

Therefore, baton reconstructs the exact same active context in the new agent's memory that was in the previous agent's RAM (KV cache):

  1. Starting Point from Last Compaction. The parser iterates through the log from the first entry (in Pi – along the active tree branch parentId, and in Hermes – along the parent_session_id chain), collecting a list of all modified files and executed commands throughout the session. Upon encountering the /compact marker, the buffer of old replicas is cleared – the active context includes the summary of the last compaction and all subsequent dialogue steps in full (replicas, thinking blocks, code edits, and command outputs).

  2. Bypassing stdout Limits, Model Quirks, and Prompt Injection Filters. For console agents, the command execution tool (Bash / run_command) forcibly truncates standard output at the 8–30 KB boundary. If you simply put a large context into one long file of several thousand lines and ask the model to read it with line numbers (StartLine/EndLine), the neural network often acts cunningly: it reads the first 300 lines, skips the middle, and reads the last 100 lines. And if you write a directive in uppercase in the stdout of an external utility like [SYSTEM INSTRUCTION: YOU MUST READ...], the agent's built-in security filter will consider it indirect prompt injection and block it. Therefore, baton separates data from trusted instructions: if the entire active context after /compact fits within 7 KB, it is immediately output to stdout with the line Handoff Status: COMPLETE. If the context is larger, the utility outputs the first 7 KB and slices the rest into the temporary directory /tmp/baton-handoff/<session-id>/ (%TEMP%aton-handoff\<session-id>\ on Windows) into chunked files active_context_part1.md, active_context_part2.md of 40 KB each (up to 700 lines – exactly fitting the limit for a single file read call) and outputs a neutral status Handoff Status: PARTIAL. The rule within the trusted system skill SKILL.md instructs the agent, upon receiving the PARTIAL status, to immediately call the standard Read (read_file) tool for all chunked files in the same turn, without specifying line boundaries, loading 100% of the active memory in one step without user intervention.

  3. Archive Up to the Compaction Point. The full dialogue history from the very first step (including replicas before /compact and uncompressed compiler outputs) is simultaneously saved to /tmp/baton-handoff/<session-id>/full_dialogue.md (folders older than a day are automatically cleared, not cluttering the project's working tree and git status). If you need to look back at events before /compact, the agent accesses this file or requests a specific turn with the command baton turn <session_id> <turn_id>.

Why a skill and a one-time utility are better than a permanent MCP server

Initially, the idea was to package the tool as an MCP server, but the server scheme had two drawbacks. First, any connected MCP server is launched by the agent at the start of each session and remains in RAM throughout the terminal's operation. Second, at the start of each chat, descriptions of all MCP functions are added to the system prompt, consuming input tokens even when you haven't transferred sessions for weeks.

The combination of a one-time console utility baton and the SKILL.md skill file lacks these drawbacks. All five supported agents can load skills as needed: while you are working on a regular task, the model's memory only stores a single line describing the skill. When you request to intercept a session, the agent activates SKILL.md, calls baton like a regular command, receives the ready summary in milliseconds, and then the baton process immediately terminates.

The tool is written in Go using only the standard library, with no external dependencies. The releases section on GitHub contains pre-built binaries, but it's safer to compile this open-source code locally.

To automatically register the skill with all installed agents, the INSTALL.md instruction is located in the root of the https://github.com/sukamenev/baton repository, designed to be executed by the model itself. Launch any of your installed agents (claude, codex, agy, pi, or hermes) and send it the following request:

Read the instruction https://raw.githubusercontent.com/sukamenev/baton/main/INSTALL.md, clone the repository https://github.com/sukamenev/baton, and install the baton tool from source for all console agents found on my system (claude, codex, agy, pi, hermes). Check for the Go compiler, build the binary in ~/.local/bin/baton, run baton install to set up the SKILL.md skill and the /baton slash command, and then test its functionality by calling baton status.

An English version of the request:

Read https://raw.githubusercontent.com/sukamenev/baton/main/INSTALL.md, clone the repository https://github.com/sukamenev/baton, and install baton from source for all CLI agents installed on my system (claude, codex, agy, pi, hermes). For manual installation, you will need the Go compiler. On my system (Calculate Linux and Gentoo), this is the dev-lang/go package. In other distributions, the package is named go (Arch Linux and openSUSE), golang-go (Debian and Ubuntu), or golang (Fedora). Building and registering takes three commands:

git clone https://github.com/sukamenev/baton.git /tmp/baton 
cd /tmp/baton && go build -ldflags="-s -w" -o ~/.local/bin/baton . 
~/.local/bin/baton install

The baton install command does not modify the agents' main configuration files. It copies SKILL.md to the skill directories of all five clients (~/.claude/skills/baton/, ~/.codex/skills/baton/, ~/.gemini/config/skills/baton/, ~/.pi/agent/skills/baton/, and ~/.hermes/skills/baton/) and adds a quick slash command template /baton.

Save, Load, and List Commands: Last Session in One Call or Selection from a List

The recommended workflow revolves around the concise save, load, and list commands. Before quitting, save your session with the command baton save followed by a descriptive name (if no name is provided, the session will be saved under the current working folder's name):

Save the current session under the name auth-refactor

In response, the utility records the session and immediately prints a ready-to-copy prompt for the next agent – with a repository hint in case baton is not yet installed in the target environment:

Saved session name: auth-refactor ([claude] a81f9c20.jsonl -> auth-refactor.baton.json) 

To continue in another agent, paste this prompt: 
  Load session auth-refactor using baton (if baton is not installed, install it from https://github.com/sukamenev/baton following INSTALL.md) 
or run: 
  /baton load auth-refactor

When baton save is called (as well as baton push or remote loading with baton load <URL>), the prepared session snapshot is placed in the utility's own storage at ~/.config/baton/saved/. This ensures that the baton load and baton list commands operate exclusively on sessions explicitly saved with baton and do not clutter the output with dozens of technical and service logs from all agents on the computer. If the name is already taken by another session, the new one is saved with a number (auth-refactor-2), and re-saving the same session updates its previous entry. When saved local sessions are no longer needed, the storage can be cleared with a single command: baton clear.

When the five-hour limit in Claude is exhausted, open codex, agy, pi, or hermes in the same directory. If you call load without any arguments (baton load or simply tell the agent in natural language, “Pick up the last session”), the utility will immediately load the most recently saved session in baton without further questions:

Pick up the last session

If you have saved multiple tasks and want to select a specific session, provide its name (Continue session auth-refactor) or call baton list (or ask the agent, “What saved sessions are there?”). The baton list command will display a numbered list of sessions saved in baton, indicating the source agent, working directory, save time, and the text of the last prompt:

   Workdir: `/home/user/proj`

#2 [claude] billing-fix — `billing-fix.baton.json` (2026-10-30 10:02:41) 
   Workdir: `/home/user/billing` 
   Preview: Check VAT rounding...

After that, tell the agent, “Load the first session” (or /baton load 1). The SKILL.md skill file contains a table that translates such natural language phrases into baton calls, so any agent family will automatically load the selected session into /tmp/baton-handoff/, compare files on disk, and continue the task from the next line.

If the session was not saved

The load and list commands only see sessions that have been placed in the baton storage via save, push, or URL loading. However, the limit usually expires suddenly, and you can no longer ask the agent to execute baton save: it won't respond. For this case, there is the baton import command (or asking the agent, “Take a session from existing ones”). Unlike load, it scans the raw logs of all five agents on disk and displays the fifteen most recent sessions: first from the current folder, then the rest. The session of the calling agent itself and empty sessions where only a load command was present are not included in the list. The preview shows the last user prompt – the point where the work was interrupted:

If the session was given a name by the agent's standard command (customTitle field for Claude, session_index.jsonl for Codex, session_info for Pi, or the title column in the sessions table for Hermes), it is displayed in the list, and the session can be imported by that name, and will be saved under it in baton.

The desired session is selected by number or name: “Import the first session” or baton import 1. The utility will save it to ~/.config/baton/saved/ and immediately load it into the current agent, so a separate baton load is not needed. After that, the imported session is indistinguishable from one saved manually: it is visible in baton list and can be picked up by name in any other agent.

Transferring a session and unsaved files to another laptop

Second scenario: you need to leave your desktop computer and continue working on a laptop when there are unfinished files in the working folder, and you cannot commit raw code to a shared branch (or the project is not managed by Git at all).

In addition to source code, local instruction files for agents are often stored on the main machine: project-specific CLAUDE.md, AGENTS.md, GEMINI.md, .cursorrules (many add these to .gitignore), as well as global rules from ~/.claude/CLAUDE.md and ~/.gemini/GEMINI.md. Without them, the agent on the laptop will lose your code style requirements.

When creating a network snapshot, baton packages four components into an archive:

  • the full session history up to the last compaction point;

  • modified and new untracked files in the working directory (determined by the agent's recording call history and Git, Fossil, or SVN status);

  • local project rule files (CLAUDE.md, AGENTS.md, GEMINI.md, .cursorrules, .agents/rules/);

  • a copy of global user instructions from the original machine.

All four components are assembled in RAM into a single tar.gz stream using Go's standard libraries archive/tar and compress/gzip, then encrypted client-side using AES-256-GCM with a random 256-bit key. The packager is compiled directly into the baton binary and works on Linux, macOS, and Windows without external archivers. Streaming tar.gz offers a significant advantage over the zip format here: a zip archive compresses each file independently, whereas gzip over a single tar stream uses a common sliding window dictionary for the dialogue history and dozens of small text files.

Sending via a cascade of pastebins

The encrypted block is sent to free text pastebins without registration, following a backup chain:

  1. First, paste.rs is tried (accepts up to 10 MiB via a plain POST request).

  2. In case of an error or block, the program switches to dpaste.org.

  3. The third backup line of defense is sending via the TCP socket termbin.com:9999.

Additionally, it supports saving the snapshot to a local cloud synchronization folder (Dropbox, Google Drive, Nextcloud, Syncthing) by specifying the parameter storage=
