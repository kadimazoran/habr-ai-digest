Architecture Explained Simply

The main idea: offload the brains and generation to a subscription-based IDE (Antigravity / Claude Code) via the MCP (Model Context Protocol), and keep all memory, search, and storage local on the machine via stdio transport.

The stack turned out to be minimalist:

  • Language: pure Python 3.12 (without LangChain, LlamaIndex, or other wrappers over wrappers).

  • Database: ordinary SQLite with WAL (Write-Ahead Logging) mode enabled.

  • Transport: MCP server via standard input/output streams (stdio). No running web servers or open ports.

  • Search: hybrid (dense vectors on numpy + sparse lexical Okapi BM25), stitched together via Reciprocal Rank Fusion (RRF).

Vectors are stored directly in SQLite as binary BLOBs (float32 type). Each chunk uses about 128 floating-point numbers, which is only about 512 bytes. The entire database of 72,450 chunks across my 18 projects totals 110 megabytes on disk and consumes exactly 0 megabytes of RAM at idle.

Three Bugs They Don't Mention in Articles

When you read articles about RAG, everything usually runs in three lines. In reality, I stumbled upon three problems that took a lot of nerves to debug.

1. On-the-fly Dimension Mismatch (128 vs 384)

During initial chunking and indexing, I ran the documents through a local provider with a dimension of 128. But the default fallback configuration for FastEmbed was set to 384.

On the very first query, SQLite threw a ValueError: Embedding dimension mismatch: stored=128, query=384.
