"I asked ChatGPT about your company - it named three competitors." If you work with websites, you've heard this phrase more than once. Even if your site is at the top, traffic from search is good, and conversions are fine. A neural network either doesn't know about you or provides information about the company based on data from two years ago.

The first reaction is to rewrite texts, add expertise, and create an FAQ. We've been through this: the hypothesis of "not enough content" seems logical but is rarely confirmed. The neural network doesn't answer based on your text, but on what reached it. And this is where things get interesting.

When we ran our site through queries to various models and examined what their infrastructure actually receives, the picture was prosaic. Some AI crawlers do not execute JavaScript. For a website built in the browser, this means one thing: an empty framework reaches the model instead of an article. The user sees a beautiful page, but the neural network sees an empty file.

In this article, we will explore how AI systems read websites, where content gets lost on the way from the server to the model's response, and what can be checked and fixed.

❯ A neural network doesn't browse the site – it gathers context

To understand why a site might be invisible to AI, it's helpful to understand how a model gets information in the first place. Many imagine the process like this: a user asks a question, the neural network "visits" the site and reads it like a human in a browser. This is not the case.

A neural network works through a retrieval layer – a separate search pipeline that, before generating an answer, finds documents on the topic, chops them into fragments, and selects the most relevant ones. These fragments are fed into the model's context, and it builds its answer with source links based on them.

This leads to two practical conclusions. First, the criterion for inclusion in the answer is not its position in the search results, but the page's suitability for fragment extraction. The robot doesn't look for "the whole page," but for a paragraph that can be cut out and inserted into the answer. Second, to extract something, that "something" must physically exist in what the server returned.

Different robots visit websites, and they behave differently. GPTBot and OAI-SearchBot work for OpenAI, ClaudeBot for Anthropic, there's PerplexityBot, and there are Yandex robots serving Alice and the "Neural" mode. And here's the key point: not all of them can execute JavaScript. Some crawlers take the HTML as returned by the server and stop there.

For a classic server-rendered site, this is not a problem – the text is already within the HTML. For a site that is assembled in the browser from JavaScript, this is a death sentence: the original response contains no headings, no text, no prices, no addresses.

❯ Three layers where content gets lost

When we broke down the path from the server to the model's response into stages, it became clear that failure can occur at three levels. And they need to be fixed in the correct order: first access, then rendering, then signals. If you mix up the order, you'll be polishing texts that never reach the model.

Access: who the server allows in

Before reading a page, a crawler must obtain it. And the server might not let it in. Check three things. First – robots.txt: are AI robots blocked there? This is common: site owners haven't touched the file for years, but during a CMS update, directives were added that block new bots. Second – WAF and bot protection: they can return 403 or a CAPTCHA not only based on request frequency but also on user-agent, and "unwanted" robots are filtered out along with spam. Third – logs. If your server logs show no visits from GPTBot or ClaudeBot, it means they either didn't reach the site, or they were blocked at the entrance.

Separately about the popular advice "block GPTBot so the model doesn't learn from your content." It's important to understand the mechanics here. Robots acting on a direct user request may not comply with robots.txt rules: providers themselves warn that the file may not be applied in such cases. This means a closed door doesn't provide the protection you expect, but it guarantees you won't appear in responses.

Rendering: an empty framework instead of a page

The second layer is the very one that makes the site "invisible" while live traffic is fine. The difference between rendering types is crucial here.

CSR, client-side rendering: the server sends the page skeleton and scripts, and the browser fills in the content. This is the common scheme for SPAs built with React, Vue, or Angular. For a bot without JavaScript support, such a page looks like an empty template. SSR, server-side rendering: the page is assembled on the server and arrives with the text already present. SSG: pages are generated in advance during the build. ISR: static content is updated as needed. In any of these cases, the HTML already contains content ready for extraction – this is what AI crawlers expect from a website.

You don't have to completely switch your stack. Practice shows that a targeted approach solves the problem: pre-render critical data. Prices, contacts, service descriptions, key paragraphs of descriptions – anything the neural network should be able to quote must be in the initial HTML. The rest can be loaded by scripts, as before.

Checking this is simple: open the page's source code in your browser (not the inspector, but the actual server response source) and look for the text you want to see in the model's answers. If the text isn't in the source, it won't be in the neural network's response either.

Format: llms.txt, markup, and response speed

Let's start with llms.txt – a file that has been talked about a lot in the past year, often confused with robots.txt and sitemap.xml. The difference is fundamental: robots.txt controls access, sitemap lists URLs for indexing, and llms.txt explains the site's purpose – what kind of project it is, which sections are primary, and what to quote first. It's a markdown file in the site's root with a brief map of key pages. There's also an extended version, llms-full.txt, for more comprehensive content.

The standard appeared in September 2024, and on August 10, 2026, it received its second version – the first revision ever. Major players are adopting the file: Anthropic, OpenAI, Perplexity, Cloudflare, and Stripe publish their llms.txt. Google has also added it to its developer documentation. However, the file is not a mandatory requirement: Lighthouse checks won't fail if the server honestly returns a 404.

But there's a nuance to keep in mind: the presence of the file doesn't guarantee its functionality. The format is easily broken by incorrect structure, broken links, or missing mandatory sections. The problem is so widespread that we've analyzed it separately: three out of ten llms.txt files are broken, and owners are unaware.

In addition to llms.txt, classic machine-readable markup also works: Schema.org helps systems accurately extract facts about companies, products, and services. And also – server response speed and uptime. If a page is served slowly or is periodically unavailable, the chances of it being included in the response decrease: the retrieval layer will more easily pick up a neighboring source that serves the same information quickly and stably.

❯ Checking the site through the eyes of a neural network

Theory is useful when it can be tested on your own project. We've compiled a set of simple checks that we ran on our own pages. No special software is needed – a terminal and a browser are enough.

First check: a request from a bot's perspective. Take the URL of an important page and request it with the user-agent that an AI crawler uses:

curl -A "GPTBot" https://example.com/page | head -c 2000

See what's in the response. If the first two kilobytes contain a heading, text, and key data – the server is delivering content. If you see a framework of tags and connected scripts, but no text – you've found the cause. Repeat this for the URLs used by other robots: each provider has its own set of user-agents, published in their documentation.

Second check: source code vs. DOM. Open the page and compare two things: the source code of the server response and the final page structure in the inspector, after scripts have executed. The difference between them is exactly the content that is available to the browser and inaccessible to some crawlers. It's useful to assess not only the fact of the discrepancy but also the volume: if the source code is empty, but the interface displays an article of ten thousand characters, you have a primary problem.

Third check: logs. Look at your web server logs and search for bot visits by user-agent. This will show you who actually reaches your site, how often, and which pages they request. If AI bots don't appear in the logs at all – go back to the access layer.

Fourth check: llms.txt validator. If the file already exists, run it through a validator: it checks the structure (title, description, sections), size, and correctness of links. A file that exists but fails validation is no better than a missing one.

Fifth check: test in the model itself. Ask the neural network several questions about your topic and see which sources it names and uses. Keep two nuances in mind: each model has its own set of sources, and answers vary from run to run – one query proves nothing. Ask the same question at least three times and note what changes.

❯ What to fix in the infrastructure

Once the cause is found, the fixes fall into a clear sequence from simple to complex.

Access. Tidy up robots.txt: remove accidental blocks, ensure desired robots are allowed. Configure security rules so they don't filter out AI crawlers along with spam. If the site is behind a proxy or CDN, check filtering at that level too.

Rendering. Choose a strategy for your stack. If your site uses server-side rendering, you're already ahead; just ensure critical blocks are actually in the HTML and not loaded lazily. If it's client-side, gradually move towards server-side rendering: start with the most important pages. A small server is sufficient for this: a test environment can be set up in a couple of minutes, allowing you to run checks without affecting production.

Speed and stability. Fast server response and stable uptime are underestimated visibility factors. Caching and a CDN in front of the site help here, as does monitoring: it's important to know about unavailability before users report it. Static files, like llms.txt and llms-full.txt, are conveniently served from object storage – for example, from S3 storage in Timeweb Cloud, which offloads file serving from the server.

Files and markup. Add llms.txt with a correct structure, and if necessary, the extended version. Check Schema.org markup. Update publication dates and authors on pages so systems have fresh content signals.

In short, the entire block of fixes boils down to one idea: there should be no technical intermediary between your content and the neural network that silently breaks the transmission. For teams managing their own infrastructure, this is familiar logic: what's visible in monitoring is controlled; what's not visible breaks quietly. ❯ How to measure results

You've fixed it – now you need to see if it's better. Three metrics have become established in AI optimization practice: Citation Rate – the proportion of your queries for which you are cited in the answers. Share of Voice – the ratio of your mentions to competitor mentions for a selected group of queries. Brand Mention Rate – how often the brand is mentioned in answers, even without a link to the site. Measure them manually or semi-automatically, but regularly: for five to ten business-critical queries, with several runs for each.

Separately about traffic. OpenAI adds the `utm_source= ` label to links in search citations: `chatgpt.com` – such transitions can be filtered in analytics. Note: there may be no label in embedded links within a conversation, so a "zero" result in the report doesn't necessarily mean there are no transitions.

And most importantly – don't fool yourself with a small sample size. Models are non-deterministic: the same query at different times yields different answers. If you were mentioned once out of one – it's not a result, but a coincidence. Three runs of ten queries – that's a start.

❯ Checklist

Check your site against the points – from simple to complex. A full pass takes one evening.

  • Check robots.txt: is it blocking AI robots?

  • Look at web server logs: are AI crawlers visiting?

  • Make a request with a bot's user-agent and examine the response

  • Compare the source HTML with the DOM after rendering

  • Ensure prices, contacts, and descriptions are in the source HTML

  • Determine the rendering strategy for key pages

  • Check TTFB and set up availability monitoring

  • Add llms.txt, and if necessary, llms-full.txt

  • Run the files through a validator

  • Check Schema.org markup on important pages

  • Update publication dates and authors of materials

  • Set up AI traffic tracking using UTM tags

  • Measure Citation Rate for five to ten queries, with at least three runs

  • Repeat measurements in a month and compare

❯ Summary

A neural network doesn't "see" a website. It receives what its infrastructure gives it – and works only with that. Therefore, optimization for neural networks begins not with texts, but with the layer where content can get lost: access, rendering, and response speed. Texts come into play later, when a fragment actually reaches the model.

The good news is that almost all of this can be checked manually in a reasonable amount of time: one terminal command, one log walk-through, one file in the site's root. The bad news is that the problem isn't visible from the outside: the page looks great for you, for users, and for traditional search. It's just that a third party repeatedly receives an empty framework and goes to competitors.

Start with one page. Run it through the checklist and see what comes back in response to a bot's query. It will be easier from there: you'll know exactly what to fix.
