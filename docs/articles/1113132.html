Code Prepares Data, Model Diagnoses

Pavel Vasiliev, a DevOps specialist at the MWS Octapi integration platform, shared how he automated the search for error causes. Through the platform, corporate systems exchange data, and when a request fails, it can be difficult for users to determine which specific service caused the error. Previously, support engineers had to search for relevant entries in logs, find the request ID, and examine its path in Jaeger, a system for analyzing operation sequences.

Pavel decided to involve a language model in this process. However, feeding it raw logs and traces didn't always yield correct results. The model might confuse services and point to the wrong error source. Therefore, the developer redesigned the analyzer's architecture, adopting the Exoskeleton approach. Its principle is that the code performs the main preparatory work, and the model receives already filtered data and interprets it. The expert divided the analyzer into eight layers and moved some instructions from the prompt into the program logic.

The model is used in two stages. First, it helps understand the user's request, and then it analyzes the prepared information and generates a diagnosis. Other operations are performed by the code. For example, it determines the processing scenario, searches for logs and traces, selects records for analysis, and verifies the model's conclusions.

Using an example, Pavel showed that the program first extracts parameters using regular expressions and selects the appropriate scenario. If the user provided a trace ID, the analyzer immediately proceeds to parse it. If a log file was attached, the program searches for the relevant ID within it; otherwise, the full scenario is initiated. If necessary, the model can recognize a request for a specific keyword, after which the program forms a query to OpenSearch and searches for matching records. The search considers the request address, response code, and a five-minute time interval before and after the event.

Next, the analyzer connects to Jaeger. It finds the incoming call, checks its address and status, and saves the information in the Evidence Ledger, an investigation log. No more than five records with error indicators are selected for the model; they are sorted by duration to show the longest operations first. This allows the model to see not only internal service calls but also the response received by the user.

Before sending data, Guardrails, an information protection layer, is activated. It removes parameters from URLs and masks personal data, email addresses, phone numbers, tokens, secrets, and internal identifiers. For recognizing full names, Pavel used the Natasha library; other values are processed by regular expressions. According to him, the rules were tested to ensure sensitive information did not reach the model. Some masked values can be restored after analysis, but this does not apply to secrets and tokens.

In the main stage, the model receives the prepared information and explains the possible cause of the error. In the demonstration example, it considered the operation name, request address, response status, call duration, and timeout indicator.

However, even prepared data does not guarantee a correct diagnosis, so the next layer, grounding, links the model's output to a specific trace record. If the model points to a service that returned an error, the program searches for the corresponding record and checks its presence in the investigation log. If confirmation is found, the link remains in the response; if not, the conclusion is considered a hypothesis. In the final stage, the analyzer generates the result for the user. When the error source cannot be identified, the system directly states this, rather than presenting a guess as a confirmed diagnosis.

Initially, the expert created the tool for first and second-line support engineers. Later, the analyzer was added to the Octapi portal so that clients themselves could initiate diagnostics. The user sends a request and receives a response with links to logs and traces, without needing to understand Jaeger themselves. A support engineer, in turn, can copy the ready explanation into their response to a ticket. According to Pavel, after changing the approach, the diagnostic accuracy nearly doubled, even though the model itself remained the same.

The analyzer also began to filter out conclusions that were not supported by data. This experience showed that accuracy depends not only on the model's capabilities but also on the information provided to it. The expert believes that models should be used where ordinary code is insufficient, and their conclusions should be further verified by programmatic means.

 

Sandboxes for AI Agents in Kubernetes

The second report was presented by Matvey Kolesnichenko, a Go developer at MWS DevRails. He discussed how to organize a secure environment for AI agents in Kubernetes and which architectural solutions are suitable for different tasks.

An agent can execute commands, read files, and access services, but code generated by a model cannot be considered trusted. If it runs in a shared cluster, insufficient isolation could grant it access to others' data, secrets, and resources.

The expert identified three components for such a system. The first isolates the code from the host kernel, the second manages the sandboxes, and the third is responsible for launching and executing tasks.

How to Isolate Agent Code

Standard containers use a shared Linux kernel. This is sufficient for running applications, but when executing untrusted code, the level of protection may be inadequate.

Micro-virtual machines, such as Kata Containers, provide stronger isolation. They run applications with a separate kernel but require hardware virtualization. A compromise option is gVisor, which intercepts system calls and handles them in its own layer, reducing interaction with the host kernel. It runs on standard Kubernetes nodes but also has limitations and does not guarantee absolute security.

RuntimeClass allows connecting different isolation mechanisms in Kubernetes. It enables selecting the execution environment for a specific pod without changing the rest of the application's configuration. However, isolation alone is not enough for complete protection; it is also necessary to restrict the agent's network access and control access to secrets.

Who Manages the Sandboxes

The second component is responsible for creating and terminating sandboxes. Ready-made tools can be used for this. For example, Agent Sandbox adds objects and controllers to Kubernetes for managing isolated environments. It has a number of pre-launched sandboxes, which can reduce waiting time when launching an agent, but secret management needs to be organized separately.

OpenSandbox offers a more comprehensive set of tools. It combines sandbox management and task execution, provides SDK, CLI, and MCP server, and also supports network policies and secret management. When choosing this platform, it's important to consider the compatibility of additional features with the isolation mechanism being used.

For a large number of agents, Matvey considered Agent Substrate. Its idea is to separate the agent's state from computational resources: an actor stores the agent's data and state, while a worker provides resources for task execution. When an agent is idle, its state is saved, and resources are released. Upon a new request, work can resume on another worker. This approach saves resources but requires a separate system for state management and storage.

How to Run Tasks and Protect Secrets

The third component, often called Harness, manages task execution. It determines when an agent needs a sandbox, monitors its operation, and processes the result. The expert believes that for many cases, it's more convenient to write a custom orchestrator adapted to the specific team's tools and processes.

Protecting keys and tokens is a separate challenge. An agent doesn't necessarily need to be given real secrets; instead, it can send a request with a conditional identifier, and a special service will substitute the actual value when the request exits the sandbox. Network restrictions are also best enabled by default, allowing access only to necessary addresses.

The choice of architecture depends on the system's scale. For a small team, Agent Sandbox with separate task and secret management mechanisms might suffice. OpenSandbox is suitable for those who need a broader set of ready-made tools, and Substrate is worth considering for a large number of agents that are often idle. Custom development offers more control but requires independent support for all components.

 

Can Tokens Be Saved with a Recommender Model?

In the third report, Ruslan Pegov, a developer at MWS, discussed an experiment using one language model to advise another. The idea was to connect a cheaper model to the agent's workflow and assign it the preliminary selection of tools. The main model would retain the ability to independently decide whether to follow the advice or not.

The experiment arose from a practical problem. The team actively uses neural networks in development, including for code work, testing, and information retrieval, but token consumption and model usage limitations become a separate factor. Therefore, the developer decided to test whether an additional model could help reduce costs without sacrificing quality.

For the experiment, a plugin was used that received the description of the current task, information about completed steps, and a list of available tools. It did not pass the main model's full dialogue to the advisor but formed a concise context. Based on this context, the advisor suggested an action, such as reading a specific file or using a tool. The main model received the hint but chose what to do next itself.

Initially, a simple task involving rounding sums in a balance chart was investigated. The main model was used for this, and cloud and local models were tested as advisors. Some runs showed savings, but the variance in results was so large that it was impossible to confidently speak about the advantage of any particular option.

The experiment was then complicated by adding work with Kafka and integration tests. The agent needed to run checks in containers and select tools in a more complex sequence. In this scenario, some models showed more interesting results, but not all options proved useful. The advisor could not only help but also suggest an incorrect action that increased resource consumption or worsened the outcome.

The developer also checked how much the main model actually followed recommendations. In one run, 26 suggestions were sent, 15 of which coincided with the main model's actions. This does not allow us to claim that the hints directly influenced the choice, as the model might have reached the same decision independently.

Timeouts became a separate problem. In one experiment, the advisor could not prepare recommendations within the set time limit. After disabling the reasoning mode, it started to comply with the limit. This showed that when evaluating savings, it's necessary to consider not only tokens but also delays, model settings, and their operating conditions.

Based on the experiments, Ruslan did not recommend using weak advisor models for all tasks indiscriminately. For simple scenarios, there was no noticeable effect, and in some cases, the additional model increased execution time or resource consumption. He considers using advisors for complex tasks with many steps, business constraints, and tool choices a more promising approach.

However, the final decision should remain with the main model. In one test, the developer prohibited it from deviating from the advisor's recommendation, and in some cases, the task was not completed at all. This confirmed that it is risky to completely delegate action selection to a weaker model.

Conclusions

Integrating AI into engineering practices requires not only selecting the right model but also designing the environment in which it operates. In one case, diagnostic quality was improved by preparing data and verifying conclusions; in another, agent security is ensured by a combination of isolation, network policies, and secret management; and in a third, resource savings depend on how justified the use of an additional model is.

In all three scenarios, AI does not replace engineering infrastructure and operating rules. It becomes part of the process, the effectiveness of which is determined by the tasks assigned to it, the constraints set, and how the results are verified.
