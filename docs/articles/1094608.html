Stages of the AI Lifecycle

Providers use different terms for the same events, and the time you have in reserve depends on how accurately you read them.

  • Anthropic. Deprecated — the model is still functional but not recommended; a replacement and shutdown date are assigned. Legacy — the model no longer receives updates and may later be declared deprecated. Retired — the model is unavailable, and requests to it result in an error.

  • OpenAI. Deprecation — the process of retiring a model or endpoint, effective immediately upon announcement. Legacy — models without updates. Shutdown (also known as sunset) — complete deactivation: the model becomes unavailable.

  • Google. The Gemini API does not have a separate deprecated state; models have a shutdown date and a stability label (stable, preview, experimental, latest). Vertex AI uses labels like latest stable and legacy stable, after which the version is permanently deactivated.

Provider Policies: What's Promised vs. What's Delivered

Stated guarantees:

  • OpenAI: at least 6 months for generally available (GA) models; at least 3 months for specialized GA model variants; shorter for preview models, around two weeks. Active users are notified by email.

  • Anthropic: at least 60 days for publicly released models. A "not-sooner-than" date is published at release, indicating the earliest possible shutdown date.

  • Google (Gemini API): at least two weeks for preview models; for the "latest" alias, email notification two weeks before the base version changes. Shutdown dates in tables are the earliest possible; the exact date is communicated in advance.

Actual medians from an independent study by Okane Land (71 notifications: 38 from OpenAI, 9 from Anthropic, 24 from Google with dates):

  • OpenAI: 182 days; 183 days for GA models (15 notifications), around 152 days for preview models (8 notifications). The actual practice for previews is much more generous than the stated two weeks.

  • Anthropic: 63 days across all 9 notifications; no preview models have been shut down.

  • Google: 28 days; around 53 days for GA models, but with a sample size of only 4 notifications; 28 days for previews (17 notifications). Seven other Google shutdowns were announced only after the fact, without a dated announcement, and were not included in the medians.

Anthropic's pattern: for all ten verified models, the "not-sooner-than" date is exactly one year after release. This is a pattern, not a documented guarantee; the company only promises 60 days of notification. Google is the most unpredictable option for developers: the date is published as the "earliest possible," the exact date comes later, and there are no quantitative guarantees for GA.

Why Providers Shut Down Models So Quickly

Frequent releases make supporting old versions unprofitable. Each unique model ID requires a separate serving cluster, degradation monitoring, documentation, support for inquiries about outdated behavior, and A/B testing for routing between versions. With ten or more active versions, costs rise faster than the number of versions.

Weights cannot be patched. It's impossible to update safety alignment, fix a documented vulnerability, or add new data to a finished model in a targeted way. This requires retraining, new weights, and a new version. Therefore, "updating" a model actually means introducing a new model ID and retiring the old one.

Previews don't guarantee a lifespan. A preview model does not have a production SLA, and the provider reserves the right to shut it down quickly. Examples from the data above: 111 days of availability for gemini-3-pro-preview, 3 days of notification for one of Google's preview models.

Competition drives acceleration. The more frequently new versions are released, the less reason there is to keep the previous one. For the developer, the final arithmetic is this: an integration designed for a two-year lifespan of one version encounters two or three model changes in the same period.

What Breaks During Shutdown: Four Scenarios

1. Hard Shutdown Without a Fallback

A request to a retired model ID returns an error (HTTP 404, 400, or a specific code). There is no silent fallback. The user sees a non-functional feature, and the developer learns about it from monitoring or customers. This is the most straightforward scenario, and monitoring dates is sufficient to guard against it.

2. Behavioral Drift on a "Compatible" Replacement

The replacement technically works but behaves differently: the JSON response format changes, response lengths vary, failure rates fluctuate, or the reasoning style in chains shifts. A prompt calibrated for one model degrades on another without a single error. Such breakages are only visible through quality metrics, hence the need for golden datasets (see the section on frozen eval below).

3. Pricing Surprise

This case is instructive because the outcome was the opposite of what was expected. Claude Sonnet 5 was launched on June 30, 2026, at an introductory price of $2 and $10 per million tokens (input and output). From September 1, a price increase to $3 and $15 was planned, a 50% jump. However, on August 10, Anthropic announced on its blog that $2/10 would become the permanent standard price, and the increase was canceled. The figures themselves match across different publications, but different sources cite different announcement dates (August 8 or 10). Conclusion for planning: the price and lifespan of a model change independently, and the budget must be recalculated with any price change, in either direction.

4. Entire API Retirement

The Assistants API was shut down entirely on August 26, 2026. This wasn't a model ID replacement but the disappearance of a layer: Threads, Runs, and Files had to be rewritten for the Responses API and Conversations API. Such a migration requires architectural changes, not just changing a string in a configuration file. The Sora 2 and Videos API also disappeared (September 24).

How Teams Actually Migrate

An empirical study titled "When the Model Retires: An Empirical Study of LLM Migration in Open-Source Applications" analyzes 22,555 commits across 17,703 repositories from 2024–2026. 5,139 commits in 4,544 repositories were matched with official shutdown events: 30 from OpenAI, 9 from Anthropic, and 7 from Google. Two annotators reviewed a sample of 300 commits; only 62% of the identified commits were actual migrations, with the rest filtered out. All numbers below are recalculated estimates by the author. This is a single preprint by one author, so treat the numbers as guidelines, not laws.

Reactive migration is the norm. 82% of migrations (95% confidence interval 79–84%) occur after the shutdown. The median migration falls on the 39th day after shutdown and the 158th day after announcement. Post-shutdown fixes are distributed as follows: 9% within a week, 27% within a month, 55% within three months.

Behavior varies by provider. Percentage of reactive migrations: Anthropic 89%, OpenAI 66%, Google 64%. Median shift relative to shutdown date: Anthropic +72 days, OpenAI +14 days, Google 6 days earlier. Percentage of commits showing signs of breakage (based on keywords in messages): Anthropic 54%, OpenAI 29%, Google 28%. The explanation lies in the notification window itself: the shorter the window, the more often teams only manage to fix things after the shutdown.

Long notification periods work. At the commit level, each increase in the notification period by a factor of e (approximately 2.7) reduces the chances of reactive migration by 74–78%. A telling case is the Assistants API: the notification period lasted about a year, and reactive migrations were only 13–14%. On weekly spikes, the opposite is observed: after the shutdown of Claude 3.5 Haiku, Claude 3 Haiku, and Opus 4.1, the volume of fixes in a week increased 25-fold compared to the previous week; after the Assistants API shutdown, it increased 2.1-fold; after Gemini 2.0 Flash, it increased 1.3-fold.

Where the model ID resides. In 94% of migrations, source files are modified, meaning the model identifier is hardcoded directly in the code. Only 6% of changes concern configuration or documentation. Abstraction was already present in 3% of codebases, another 4% introduced it during migration, and the remaining 93% simply renamed the identifier in place.

Migration cost depends on architecture. Median modified files and lines: clean prompts (78% of the sample) — 2 files and 6 lines; agents with tools — 5 files and 63 lines; RAG — 7 files and 155 lines; fine-tuned models — 14 files and 693 lines. The more surrounding infrastructure around a model, the more expensive its replacement.

Quality verification is almost absent. Only 4.5% of commit messages mention evaluation datasets or regression tests, and 11% of patches add a verification line. Prompts are changed in 8% of commits, and parameters like max_tokens or temperature in 7.5%. Silent failures account for 8% of confirmed migrations, 14 out of 180.

Providers are rarely switched. 68–74% of teams stay with the retiring provider, 8% switch to another, and 16% add a second. Among the 85 repositories that experienced two or more shutdowns, the proportion of reactive migrations remained the same (73%) for both the first and subsequent events, although the migrations themselves became faster: a median of 22 days versus 45. In other words, teams get faster but don't start acting proactively.

The main takeaway from the entire dataset is this: the primary area for savings is not reaction speed, but rather making the model ID no longer a string in the source code.

Model switching in this scenario is reduced to editing a dictionary, not a deployment.

Distinguish Between a Fixed Version and an Alias

A dated identifier like claude-sonnet-4-5-20250929 fixes behavior but has a shutdown date. An alias like "latest" eliminates manual changes, but with Google, for example, it changes two weeks before the base version changes, meaning behavior shifts without your intervention. For production with quality metrics, choose a fixed version and a migration schedule. Aliases are suitable for prototypes and internal tools where regression is not critical.

Maintain a Golden Dataset for Every Critical Scenario

Before changing a model, run a fixed set of requests against both the old and new versions and compare the output qualitatively and quantitatively. A minimal set per scenario: 15–50 examples with golden answers or verifiable criteria (JSON format, presence of required fields, length, failure rate). If regression is detected, postpone the migration or fix the prompts. According to the study above, only a few teams perform such checks, and 8% of confirmed migrations end in silent failures.

Automate Date Monitoring

Three primary sources: OpenAI's deprecations page (platform.openai.com/docs/deprecations), Anthropic's deprecations page (anthropic.com/deprecations), and Google Vertex AI's model version lifecycle page (cloud.google.com/vertex-ai/docs/model-versions-lifecycles) along with Gemini API release notes. Parse these weekly and trigger an alert when a model from your registry appears on the list. A rule that pays off: record the shutdown date of each model ID on the day of its integration, not when you receive an email.

Monitor Pricing Separately

Pricing changes independently of the lifecycle: the Sonnet 5 example above shows both the threat of a 50% increase and its cancellation. Include a buffer in your budget and automatically recalculate expense forecasts whenever the provider publishes a new price list.

Proxy Layer: What It Offers and What It Doesn't

LiteLLM, Portkey, and OpenRouter allow you to switch providers and models without modifying application code. However, the layer does not prevent provider-side shutdowns, does not guarantee consistent model behavior, and introduces its own risk surface. For LiteLLM, this risk has already materialized: on March 24, 2026, compromised versions 1.82.7 and 1.82.8 were uploaded to PyPI, collecting credentials and environment variables; they were quarantined after 46 minutes, and during that window, 46,996 downloads were recorded according to PyPI logs. Therefore, any such layer should be pinned by version and hash, and secrets should be kept outside the application's environment.

Special Case: Anthropic's Weight Preservation

On November 4, 2025, Anthropic committed to preserving the weights of all publicly released models and models significantly used internally for at least the company's duration. When a model is retired, Anthropic prepares a deployment report, stores it with the weights, and conducts an interview with the model about its development, usage, and deployment, recording answers and feedback. The company explicitly states that it does not yet commit to acting on this feedback.

The first model to undergo this process was Claude 3 Opus: it was retired on January 5, 2026. It remained available to paid subscribers of claude.ai, and in the API, it is provided upon request via a form; Anthropic states it is willing to grant access generously. Additionally, the model has a weekly newsletter, Claude's Corner, where its essays are published (for at least three months): the texts are reviewed by Anthropic but not edited, and the company emphasizes that the model does not speak on its behalf.

For developers, two facts are important here. Weight preservation does not mean API availability: old versions may remain accessible only by request and without guarantees. And Anthropic calls these steps experimental and does not promise to repeat them for every model. Therefore, the strategy of "sticking with an old model forever" remains unavailable, and migration must still be planned.

Common Mistakes

  • Storing model IDs in source code. In 94% of migrations from the sample, the identifier was modified directly in the code. Configuration and a date registry turn migration from a release into a settings change.

  • Learning about the date from an email. The shutdown date is known upon the model's release: for Anthropic, it's "not-sooner-than" a year later; for OpenAI, it's 6 months for GA. Record it on the day of integration.

  • Treating the stated window as a guarantee. OpenAI states about two weeks for previews, but the actual median is 152 days; Google has no guarantees for GA, and actual periods have been as short as 15 days. Plan based on your worst-case provider.

  • Migrating without a golden dataset. This leads to silent failures: no errors, but the response format or failure rate has changed.

  • Assuming price is constant. The introductory tariff for Sonnet 5 could have increased by 50% and ultimately became permanent; the budget must accommodate both outcomes.

  • Postponing migration to the last week. Reactive migrations in the sample took a median of 39 days after shutdown: during this entire period, the function was either not working or running on an emergency fallback.

Frequently Asked Questions

Why are companies retiring models so quickly? Old weights cannot be updated incrementally: new data, security fixes, or quality improvements require a new version. Each live version demands separate infrastructure, monitoring, and support, and releases are frequent, so providers set a lifespan in advance. Anthropic's flagship models have a lifespan of about a year, while Google's preview models can last 3–4 months.

How many days in advance are you warned about a model shutdown? According to an independent study by Okane Land, the median notification period is 182 days for OpenAI, 63 days for Anthropic, and 28 days for Google. Stated minimums are: 6 months for OpenAI GA models, 60 days for Anthropic, and at least two weeks for Google previews. In practice, it can be shorter: Google has had notifications as short as 15 and even 3 days.

What happens to requests if a model is shut down? Requests to a retired model ID result in an error: there is no silent fallback. Therefore, a backup model and status checks in the registry are necessary. A separate risk is a "soft" replacement with a new version: no errors occur, but the response format and style may change, which can only be detected with a golden set of requests.

How can I avoid rewriting code with every model change? Store model IDs in configuration with shutdown dates, select models via a registry with a fallback option, and pin versions instead of using aliases. Before changing, run a golden dataset against the old and new versions and maintain weekly monitoring of deprecation pages. This way, changing a model becomes a matter of adjusting settings, not a release.

Conclusion

The lifespan of an LLM version is measured not so much in months as in how far in advance you know the date. Take three steps. Move all model IDs out of your code into a registry with shutdown dates. Create a golden dataset for each critical scenario and test any replacement against it. Set up weekly monitoring of deprecation pages so the date enters the team's calendar on the day it appears.
