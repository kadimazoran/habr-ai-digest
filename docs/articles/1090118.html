In the first part, I talked about how we went from simply copying code between MODX and ChatGPT to a proper subject-oriented interface for the CMS. The agent stopped seeing the site as a jumble of files and database rows and gained the ability to work with resources, chunks, TVs, and their dependencies. At some point, this was enough to set tasks almost as I would set them for a developer, without detailed instructions on where exactly to go and which line to change.

The next step was obvious. If the agent had already figured out the problem and found a solution, why should I take its code, connect via SSH, make a backup, upload the fix, run checks, and then browse the site to see if anything nearby broke? I wanted to simply write "See why the form stopped sending, fix it, and check" and get back not a ten-point instruction that I would have to execute myself, but an already fixed site.

This is where the second part of our project began. Giving write access turned out to be quite simple. SSH, physical files, logs, a browser, and several utility tools were added to MODX MCP. Much more time was spent ensuring that after the "fix it" command, I wouldn't be hovering over the agent's shoulder, watching what exactly it was about to mess up.

SSH unexpectedly gave up first

Who would have thought. The technology is ancient, everything has been invented long ago, it works everywhere. The agent also needs little from it: read a file, check the error log, execute php -l, run a build or some diagnostic command.

It turned out that humans and agents use SSH somewhat differently. A human usually connects to the server and stays there for a while. They look at something, think, smoke, execute the next command. The agent, however, breaks down the same task into many short operations: reads one file, accesses a second, searches for a string in the project, checks the log, clarifies the PHP version, runs a check, rereads the file. When there are several such tasks, and several sites are hosted on the same hosting account, the number of connections grows rapidly.

On one of the hosting providers, this quickly led to blocks. We had to communicate extensively with support and explain separately what an AI agent is, why it's accessing SSH at all, and where such a large number of short connections come from. Thankfully, they understood us, but the blocks themselves didn't disappear. In three days, we received them three times, each time for about six hours, and we could only wait for access to be restored. Adding our IP to the whitelist wasn't possible, as that option simply doesn't exist there.

After the third time, it became clear that negotiating with the hosting's security further was pointless, and we had to change the way we worked with SSH. Before connecting, our wrapper asks OpenSSH itself where exactly it intends to connect:

effective_config="$("$REAL_SSH" -G "$@" 2>/dev/null || true)"

The effective configuration is obtained using the command.

resolved_host="$( printf '%s\n' "$effective_config" | awk '$1 == "hostname" {print $2; exit}' )"

The resolved hostname is extracted.

resolved_user="$( printf '%s\n' "$effective_config" | awk '$1 == "user" {print $2; exit}' )"

The resolved username is extracted.

resolved_port="$( printf '%s\n' "$effective_config" | awk '$1 == "port" {print $2; exit}' )"

The resolved port is extracted.

Binding restrictions to a site turned out to be incorrect. We might have three different domains, three entries in the SSH configuration, and one real user on one server. The provider, of course, doesn't care how nicely we named these projects.

Therefore, the connection pool is built by the actual address, and the resulting key is also cleaned before use in the directory name:

pool_key="$( printf '%s@%s:%s' \n "$resolved_user" \n "$resolved_host" \n "$resolved_port" | \n tr -c 'A-Za-z0-9._@:-' '_' )"

The pool key is generated by combining user, host, and port, and then sanitizing it for use as a directory name.

Next, the standard ControlMaster is used so that ten agent commands don't turn into ten new authorizations:

SSH_OPTS=( \n -o ControlMaster=auto \n -o ControlPath="$CONTROL_PATH_TEMPLATE" \n -o ControlPersist=1h \n -o ServerAliveInterval=60 \n -o ServerAliveCountMax=3 \n)

SSH options are set to enable connection sharing and keep-alive.

You'd think that's all. But during the first connection, two processes could almost simultaneously see that the main connection didn't exist yet, and both started creating it. We had to separately block even this small section:

if ! master_alive; then \n  exec {bootstrap_fd}>"$pool_root/master.lock" \n  /usr/bin/flock "$bootstrap_fd" \n \n  if ! master_alive; then \n    acquire_slot \n    "$REAL_SSH" "${SSH_OPTS[@]}" "$@" & \n    ssh_pid=$! \n \n    for _ in $(seq 1 100); do \n      if master_alive; then \n        /usr/bin/flock -u "$bootstrap_fd" \n        exec {bootstrap_fd}>&- \n        wait "$ssh_pid" \n        exit $? \n      fi \n \n      if ! kill -0 "$ssh_pid" 2>/dev/null; then \n        wait "$ssh_pid" \n        status=$? \n        /usr/bin/flock -u "$bootstrap_fd" \n        exec {bootstrap_fd}>&- \n        exit "$status" \n      fi \n \n      sleep 0.05 \n    done \n  fi \nfi

This code implements a lock to ensure only one process creates the master SSH connection.

Parallel commands also had to be limited. By default, eight concurrently executing commands are now allowed per actual SSH account, and for this hosting, we set a limit of two.

After another redesign, we specifically tested the most problematic scenario: when an SSH connection isn't ready yet, and we simultaneously launched 12 commands. The result was one SSH authorization and no more than two concurrently executing commands.

We didn't invent anything new here, of course. ControlMaster, flock, and concurrency limits existed long before ChatGPT. What's funny is that the hosting's limitation, which I might not have noticed for years during normal work, the agent found almost immediately.

SSH was kept for diagnostics, and file writing was moved separately

When SSH stopped disconnecting, a more serious question arose. If the agent has access to a regular command shell, it can technically change a file in any way: using sed, cat, Python, Perl, or even a PHP script on the fly.

Our SSH wrapper itself is not a sandbox and does not parse every command executed. It handles transport, connections, and concurrency. According to our rules, production files are changed via site-file, not via ssh, scp, rsync, or a conveniently found sed.

We could have left the entire sequence of actions to the model's discretion and instructed it to first read the latest file, show the difference, save a copy, reread it after writing, and for PHP, always execute php -l. But I wanted this order not to depend on how carefully the agent read its own instructions at a particular moment.

Therefore, a separate tool, site-file, was introduced for physical files. Through the standard file channel, the content of some items is not even given to the agent for reading. For example:

HARD_BLOCK_FILES = { \n  "config.core.php", \n  ".env", \n  "auth.json", \n  "credentials.json", \n  "composer-auth.json", \n  "core/config/config.inc.php", \n} \n \nHARD_BLOCK_GLOBS = ( \n  ".env.*", \n  "*.pem", \n  "*.key", \n  "*.p12", \n  "*.pfx", \n)

A list of files and globs that are hard-blocked from access.

.git/, .ssh/, .codex/, .agents/, .site-manager/, node_modules/, MODX utility directories with configuration, logs, sessions, packages, and several other places where the agent has no business being for normal site operation are also blocked.

Importantly, this refers specifically to the standard file channel. SSH itself technically remains standard SSH and has the permissions of the system user. Therefore, the rule "production physical files are read and changed via site-file" is also enshrined in the agent's general instructions. Otherwise, this whole construction would quickly turn into a very expensive way to call cat.

Escaping through something like:

../../.ssh/id_rsa

is also not possible. Path normalization in the actual code looks like this:

def normalize_rel(value: str, *, allow_root: bool = False) -> str: \n  value = (value or "").strip().replace("\", "/") \n  \n  if value in ("", "."): \n    if allow_root: \n      return "" \n    fail("Путь не указан") \n    \n  if value.startswith("/"): \n    value = value.lstrip("/") \n    \n  p = PurePosixPath(value) \n  \n  if p.is_absolute() or ".." in p.parts: \n    fail(f"Небезопасный путь: {value}", 5) \n    \n  rel = p.as_posix() \n  \n  while rel.startswith("./"): \n    rel = rel[2:] \n    \n  if not rel and not allow_root: \n    fail("Пустой путь")    \n  return rel

The initial `/` is treated as a path relative to the site root, and attempts to go up via `..` are blocked.

There is also an intermediate category. Files like .htaccess, index.php, php.ini, PHP files, core/, connectors/, and some other sensitive areas sometimes need to be changed, so completely blocking them is pointless. But regular writing to them is no longer allowed and requires a separate --allow-sensitive flag.

As a result, the agent has SSH, but this does not mean that SSH automatically becomes a standard editor for the entire server.

First, we look, then we write

According to our rules, normal operation with site-file put starts without the --yes flag. The tool reads the current version directly from the production server again, calculates checksums, and shows the difference:

print(f"PATH: {rel}") \nprint( \n  f"BEFORE: {'exists' if before_exists else 'new'} " \n  f"size={len(before) if before_exists else 0} " \n  f"sha256={sha256(before) if before_exists else '-'}") \nprint(f"AFTER: size={len(after)} sha256={sha256(after)}") \nprint_diff(rel, before, after, before_exists)

The output shows the file path, its status before and after the change, and their checksums.

Without --yes, this is where it ends:

if not args.yes: \n  print("PREVIEW ONLY. Для применения повторите с --yes.") \n  return

The preview mode is indicated, and the user is prompted to repeat with `--yes` to apply changes.

Technically, nothing prevents calling the command with --yes immediately, so the "look first, then apply" order is dictated by the agent's rules. The tool itself still rereads the latest version and shows the difference immediately before writing. This means it changes the file that is currently on the production site, not a copy that the agent saw at some unknown time.

If the change is applied, the previous version of the file is saved first, along with its parameters:

manifest = { \n  "format": 1, \n  "site_id": site_id, \n  "created_at": datetime.now().astimezone().isoformat(timespec="seconds"),    \n  "operation": operation,    \n  "path": rel,    \n  "before_exists": before_exists,    \n  "before_mode": mode or None,    \n  "before_size": len(before) if before_exists else 0,    \n  "before_sha256": sha256(before) if before_exists else None,    \n  "before_file": str(before_file.relative_to(bundle)) if before_file else None, \n}

A manifest is created to store information about the previous file state.

The new content is also not written directly over the working file. First, a temporary file is created in the same directory, the necessary permissions are set, and only then does it become the main file:

def write_remote(cfg: dict, rel: str, data: bytes, mode: str) -> None: \n  target = remote_path(cfg, rel) \n  parent = str(PurePosixPath(target).parent)    \n  tmp = parent + f"/.mcp-write-{uuid.uuid4().hex}" \n  \n  cmd = ( \n    "set -e; " \n    f"mkdir -p -- {q(parent)}; " \n    f"cat > {q(tmp)}; " \n    f"chmod {q(mode)} -- {q(tmp)}; " \n    f"mv -f -- {q(tmp)} {q(target)}" \n  ) \n  \n  run_ssh(cfg, cmd, input_bytes=data, check=True)

The remote file writing process involves creating a temporary file, setting permissions, and then moving it to the target location.

After writing, the file is read from the server again. The checksum must match the version that was intended to be written. For PHP, php -l is additionally executed.

You can immediately add a check for the required page using --check-path, but here we have two different levels of checking. From site-file, a short site-check is called with --no-baseline. It's needed to quickly ensure that the page itself still opens without an HTTP error after writing. Console and network problems are also collected in the report, but not compared with the saved baseline. A full check for new errors is run separately, discussed below.

If the checksum doesn't match after writing, PHP fails the check, or the mandatory page check fails, the previous version is restored:

try: \n  write_remote(cfg, rel, after, write_mode) \n  \n  exists2, verify, _ = fetch_bytes(cfg, rel) \n  \n  if not exists2 or sha256(verify) != sha256(after): \n    raise SiteFileError("Проверка sha256 после записи не прошла") \n    \n  if PurePosixPath(rel).suffix.lower() == ".php": \n    php_lint(cfg, rel)    \n    \n  if args.check_path: \n    site_check(args.site_id, args.check_path) \n    \nexcept Exception as exc: \n  print(f"ERROR AFTER WRITE: {exc}", file=sys.stderr) \n  print("ROLLBACK: восстанавливаю предыдущую версию.", file=sys.stderr) \n  restore_previous(cfg, rel, before_exists, before, mode) \n  raise

The `try-except` block handles potential errors during writing and performs a rollback if necessary.
