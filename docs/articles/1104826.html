Claude Code doesn't officially work from Belarus: Anthropic doesn't serve the region, and you can't pay for subscriptions or API access with a Belarusian card. We're building ZuBrIQ — a gateway to models with BYN payments — and over the past few months, we've managed to make Claude Code, Codex, and OpenCode work on open models: GLM-5.3 from a provider and Qwen3.8-27B on our own V100s. Below is the architecture and five pitfalls we stumbled into ourselves.

Why Replace the Model for Claude Code at All

Claude Code is a good agent, and it can connect to more than just Anthropic. All it takes is ANTHROPIC_BASE_URL and a token, and it sends requests via the Anthropic Messages protocol to anywhere. There was a good review on Habr about this recently — "What to Replace Claude or Gemini With After the Ban." They replaced the model with DeepSeek and MiniMax.

Our task is broader. We need not just one client and one model, but a dozen clients and several models behind a single address and key. Plus, expense tracking, backup routes, and a model whose data never leaves the country. Therefore, a gateway on LiteLLM sits between the agents and the models.

Codex ──────── /v1/responses ────────┤

              ┌──────────────────────┼───────────────────────┐
              ▼                      ▼                       ▼
     vLLM, 4×V100 16 GB      GLM-5.3 from provider    DeepSeek V4 Pro
     Qwen3.8-27B AWQ INT4    (main route)          (backup)
     name: zubr               name: zubr-coder         under the same name

The main rule is that clients only know stable names: zubr, zubr-flash, zubr-coder. Each name has a list of routes with order and backups. If weights change or a provider goes down, integrations don't notice.

Pitfall 1. Silent Fallback on /v1/messages

Initially, we set up GLM-5.3 as a standard OpenAI-compatible backend — using the openai/ provider with the correct api_base. Chat and SDK worked. But Claude Code and Codex received responses... from the backup model.

It turned out that LiteLLM translates /v1/messages (Claude Code) and /v1/responses (Codex) for openai/ to the OpenAI Responses API. The provider responds to /responses with a 404, and the router silently moves to the next route. There's no error in the logs, and there's a response — just not from the intended model.

This is only revealed by the response header:

x-litellm-attempted-fallbacks: 1

This is fixed by using LiteLLM's native provider for this vendor: it translates Messages and Responses to chat/completions, which the provider supports. The variable LITELLM_USE_CHAT_COMPLETIONS_URL_FOR_ANTHROPIC_MESSAGES only fixes /v1/messages; Codex still falls back with it.

Conclusion: LiteLLM always respects the route order. If you get a response from the "wrong" model, check the fallback headers, not the order.

Pitfall 2. Claude Code Itself Requests Haiku, Sonnet, and Opus

Replacing ANTHROPIC_MODEL is not enough. Claude Code sends sub-tasks — headers, context compression, sub-agents — to models named Haiku, Sonnet, and Opus. Requests from a key without Anthropic access fail with a 403, sometimes mid-operation.

A working ~/.claude/settings.json looks like this:

{
  "env": {
    "ANTHROPIC_BASE_URL": "https://api.zubriq.ai",
    "ANTHROPIC_AUTH_TOKEN": "sk-…",
    "ANTHROPIC_MODEL": "zubr-coder[1m]",
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "zubr-coder[1m]",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "zubr-flash[1m]",
    "ANTHROPIC_DEFAULT_HAIKU_MODEL": "zubr",
    "CLAUDE_CODE_MAX_CONTEXT_TOKENS": "262144",
    "CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC": "1"
  }
}

The key is issued in the zubriq.ai personal account, and zubrcode connect claude writes this file automatically. Three details, each costing us an evening:

  • ANTHROPIC_BASE_URL — without /v1. Claude Code appends /v1/messages itself, and with /v1, it becomes /v1/v1/messages.

  • The suffix [1m] tells Claude Code that the model has a 1M context window, and it's truncated before sending: only the clean zubr-coder goes to the gateway. Without it, the agent calculates the window according to its own rules and compresses the context too early.

  • For a model without [1m], the window is set by CLAUDE_CODE_MAX_CONTEXT_TOKENS. This variable has no effect on models with [1m].

Pitfall 3. Zero Spend

With the native provider, requests went where they should, but the spend per key became zero. For this provider, LiteLLM doesn't pull the price from model_info. Zero spend means key budgets don't trigger, and the margin report is inaccurate.

The solution is to duplicate the prices directly in the litellm_params of the model configuration:

litellm_params:
  model: <provider>/glm-5.3
  input_cost_per_token: 0.0000012
  output_cost_per_token: 0.000004
  cache_read_input_token_cost: 0.00000022

The numbers are illustrative — the location where they are stored is important. Also, updating a model via PATCH /model/{id}/update takes a minute or two to reach the second pod. Don't rush to assume it didn't work.

Pitfall 4. A Model That Doesn't See Images

GLM-5.3 is strong in code but doesn't accept images. It behaves differently depending on the input:

Input

What happens to the image

Provider's chat/completions

400: allowed values: ['text']

Provider's Anthropic-compatible endpoint

Silently dropped; the model "guesses" based on text

DeepSeek V4 Pro backup

Responds that there is no image

The most dangerous is the second option: no error, a confident and incorrect answer. The user sends a screenshot with an error, and the model discusses something it hasn't seen.

In our ZubrCode agent, we implemented a workaround. If a model in the catalog lacks vision capabilities, the image is replaced with a text description from a fast vision-enabled model — GLM-5.3 Flash. The subtlety: the agent replays the entire history on each turn. Without caching, the same photo would be described anew each time. Therefore, the description is cached by the image's sha256 on disk.

A separate detail in the catalog: supports_vision: null from /model/info was interpreted by us as an explicit false ((bool) null). Because of this, vision capabilities were lost even for models that do see. The correct behavior is "I don't know, ask higher up the chain." And keep in mind: if there are multiple routes under the same name, the flags are taken from the first one in order.

Pitfall 5. Our Own Model on V100

For data that should not leave the country, we use Qwen3.8-27B on our own 4×V100s with 16 GB each. These are 2017 cards, without bf16 and FP8. Therefore, we use AWQ INT4 quantization with FP16 computations, vLLM with tensor parallelism across 4 cards, and a vLLM fork with SM70 support.

What emerged:

  • KV cache must be specified explicitly. The fork calculates the KV budget as total × gpu_memory_utilization − activations and doesn't subtract model weights: the loader for SM70 reports their size as almost zero. The result is that KV consumes more than allowed, leaving nothing for other processes on the same cards. We explicitly set --kv-cache-memory-bytes, and left --gpu-memory-utilization only as a check for free memory at startup.

  • Two instances cannot be started simultaneously. In the summer, a separate VL model coexisted with the main model. The peak initialization of two processes exceeded 16 GB — one worker caught an OOM. It got worse: the main instance hung on the NCCL watchdog. systemd showed active, but the port was closed. We fixed it by making the second unit wait for the first one's health check in ExecStartPre.

  • Dense vs. MoE. Until September, under this name was MoE 35B-A3B: about 3 billion active parameters, first token in ~0.6s. The dense 27B is smarter and sees images itself, without a separate VL model. But the first token is now ~1.3s. For an agent that makes dozens of calls, this is noticeable. We kept it as a "Haiku slot": for background sub-tasks and anything that cannot be sent externally.

Current parameters: 262,144 tokens context, max-num-seqs 24, KV ~4.6 GB per card, tool calling via qwen3_xml parser.

What's the Result

  • Claude Code, Codex, and OpenCode work through a single gateway on GLM-5.3 and Qwen, without client patches — only configuration.

  • The model in the key is stable by name, while the routes and weights beneath it change without user intervention.

  • The most unpleasant errors here are silent: falling back, zero spend, dropped images. Monitor fallback headers and verify spending, not just response codes.
