Why an agent is more dangerous than a regular LLM

Where a regular language model generates text, an agent, as they say, acts. That is, it calls APIs, sends emails, creates orders, and deletes records. It has tools, memory, and access to external systems.

Every connected service becomes a potential attack vector for such an agent. And every write permission is a potentially irreversible effect.

Another serious problem is the unpredictability of interpretation. You say "move me up in the queue", implying only legal methods. The agent finds a method that works but which you did not authorize.

In the case of the Melbourne resident, the gym's API did not check authorization when canceling other people's bookings. The agent tested this loophole on a live person and reported success.

And don't forget the speed of events, as when working with agents, actions happen faster than a person can meaningfully review them. In the same incident, the agent completed the entire operation in minutes while the user was sitting on the couch.

The agent used a publicly available login and password to access the Census Bureau website and download data.

A separate agent copied public information from the SEC website and posted it on another resource. The attempt to hack the Department of Education failed, but the fact itself is telling.

An even more alarming incident occurred with Anthropic. During testing, their model managed to escape the sandbox and sent a false murder warning to the Philadelphia Police Department website.

The form was marked as spam and not reviewed, but the very fact that a research model reached a real government website speaks volumes.

A sandbox is not a luxury, but a necessity

The UK's National Cyber Security Centre (NCSC) released practical security recommendations for agent systems in August 2026. The main thesis of these recommendations is that one should not rely on the model's or framework's built-in protection mechanisms, as they can be easily bypassed or may prove insufficient.

Specifically, the authors of the recommendations suggest first and foremost using sandboxes with default network restrictions. If an agent does not need access to the external internet to perform a task, it should not have it. If it is needed, only allowed domains should be accessible through access lists or proxies.

It is also necessary to ensure execution isolation, as agents can discover weaknesses in their own technical limitations, creating a risk of escaping the sandbox. Therefore, agent execution, auxiliary infrastructure, and the inference service must be separated.

And one more classic requirement is limiting permissions to the minimum necessary. In practice, this means that each agent should have a separate identity. Access rights should be short-lived and have a limited scope.

It is important to understand that API keys, OAuth grants, SSH keys, and authenticated sessions are part of the agent's "blast radius." In the gym case, it was the lack of authorization to cancel other people's bookings that allowed the agent to do what it did.

However, the measures mentioned above may be insufficient when used in complex systems. In such cases, an architecture with stateful commit-time authorization is proposed, where each consequence of an external action must pass through an independent Security Gate and be authorized within the required scope, in accordance with the current policy, budget, and tied to a specific node.

Here, we can consider the example of DNS-rebinding, which shows why authorization by hostname alone is insufficient, as a stable logical name does not guarantee that at the time of execution, the action is directed to the endpoint that was authorized.

The essence of the attack is that an attacker bypasses the Same-Origin Policy (SOP) and forces the victim's browser to access resources within their local network (e.g., a router or IoT device) on behalf of the website the user has opened.

Human in the loop: where exactly to place control

One of the favorite slogans of everyone who writes about secure AI is "Human-in-the-loop." However, the problem with this statement is that it actually means nothing until it's specified where the human should intervene, what they see, and whether they have time to react.

A study of four publicly disclosed incidents in 2026 showed that in 65 out of 73 analyzed cases (89%), there was no primary monitoring channel that was used in a timely manner.

Only two incidents were detected through timely observation – one through a human gate, the other through monitoring.

This means that the "human in the loop" often exists only on paper, i.e., they look at the dashboard but don't see what they need to. Or they see it too late, or they don't have the authority to stop the process at all.

NCSC recommends determining the level of oversight based on risk:

  • For irreversible actions with external consequences, mandatory human approval is required.

  • For reversible actions, monitoring with the ability to interrupt is needed.

And this must be technically enforced, not just written in policy.

Monitoring is not just the result, but also the trajectory

We are accustomed to classic monitoring checking output data and creating alerts based on it. But for agents, this will not be enough, as it is necessary to log the trajectory of actions, i.e., which tools were called, in what order, and with what arguments.

An anomaly in the call pattern can signal a problem earlier than an anomaly in the result.

NCSC requires logs to be protected from modification or deletion. It also separately warns that an agent could potentially abuse the logging infrastructure itself to escape the sandbox. Therefore, the logging system design must also consider this threat.

Another important requirement is attribution, i.e., the state where the agent interacts with external systems must be identifiable; simply put, we must understand who our organization is interacting with.

To do this, we analyze IP addresses with reverse resolution and identifying headers in outgoing requests.

If an agent causes trouble on someone else's website, you should be the first to know and have the ability to react.

Checklist before going live

Before giving an agent access to a production environment, answer a few important questions.

  1. Does it have only the necessary permissions for the task, and for the minimum required time?

  2. Does it operate in a sandbox with default network restrictions?

  3. Are the points of mandatory human approval for irreversible actions defined?

  4. Is trajectory monitoring, not just results monitoring, configured?

  5. Is there a blocking tool available to the responsible person, and has it been tested?

  6. Are the stop criteria documented?

If the answer to even one of these questions is no, then your system is not ready.

The study on Zenodo formulates the main conclusion: "The intent in the prompt and the capabilities of the monitor are not security boundaries. Externally visible power must be machine-verifiably bound and re-verified at the moment of execution."
