My name is Alina, and I am the Head of Web Applications at EXANTE. I am responsible for the technical strategy of web projects, delivery efficiency, and the development of engineering processes within teams, as well as leading several initiatives, including AI transformation.

When we started working with AI, it was important for us not to limit ourselves to individual tools for developers. We wanted to build an autonomous pipeline that could take on entire parts of tasks and assess how this approach increases team productivity and reduces the time from task assignment to a finished result. This is how Codey came about — an AI agent system that independently goes through a significant part of the journey from a Jira task to a working feature.

We started implementing it six months ago, and during this time, we have achieved the following results:

  • 250 tasks have gone through the system;

  • 75% of them were completed successfully;

  • Codey handles 7% of the total number of tasks in teams where it has been implemented;

  • Typically, it takes about 30 minutes from the start of writing code to deploying a feature environment.

For AI to become part of the real development process, one strong model is not enough. High-quality requirements, prepared projects, measurable checks, and clear system operating rules are needed.

From Individual Automations to an AI Developer

We started with small automation tools: AI review and analysis of affected modules based on changed diffs. They accelerated individual stages after code writing but could not independently complete the entire cycle — from parsing a Jira task and exploring the codebase to implementation and checks. I discussed this stage in a previous article.

Therefore, the next step was Codey — a system that independently explores code, creates a plan, writes the implementation and tests, verifies the result, and fixes identified problems.

Currently, Codey works well with projects in Node.js, React, and Python. We started with local frontend and UI tasks and then moved on to full-stack changes affecting both frontend and backend.

Today, we use the system in all projects within my department: from internal CRM and back-office systems to client-facing services, including the user personal account, the trading web terminal, and the desktop application.

How Codey Works

Architecturally, Codey is an AI agent orchestration layer developed by us. By an AI agent, we mean a model that operates in a connected execution environment, is assigned a specific role, and has access to necessary tools. Environments like Claude Agent SDK, Codex, and OpenCode allow agents to work with repositories, files, and the terminal. Codey connects them into a single process: it distributes roles and stages, initiates checks, returns work for refinement, and synchronizes results with Jira, GitLab, and CI.

How Tasks Enter Codey

The first scenario is integrated into sprint planning and depends on the stage of Codey's implementation. Initially, the team manually selects well-described tasks and marks them for transfer to the system. In teams where the process is already established, Codey and developers work with a common backlog: the system by default picks up suitable tasks, and the team marks tasks with `AI skip` that should be handled by a human for specific reasons. Gradually, we aim to extend this approach to all connected teams and projects.

The second scenario starts in Slack. The client describes a request, and Codey helps navigate the system, clarifies details, and forms a Jira task. The system then executes it, creates a merge request, and returns to the same chat: it notifies the client, invites them to review the result, and provides a link to the feature environment.

When Codey receives a task from Jira, it identifies the related GitLab repositories. For each project, the following is pre-configured:

  • which repositories to direct the task to;

  • which automatic checks to run;

  • who to assign as a reviewer;

  • how to deploy the feature environment and link the necessary frontend and backend versions.

Thanks to these settings, Codey knows how to guide a task through a specific project's process and prepare the result for team review.

Roles in the AI Agent System

Six main roles work on a task:

  • Researcher explores requirements and the codebase;

  • Planner creates the plan;

  • Developer writes code and tests;

  • Reviewer checks the quality and correctness of changes;

  • QA runs tests and technical checks;

  • Verifier compares the result against the mandatory requirements of the plan.

The system uses different models for different roles. If the Reviewer or automated checks find a problem, the Developer is assigned the task for refinement.

After submitting the result, the team conducts a review. Codey considers feedback on code and business logic from the merge request and Jira task, makes changes, and re-runs checks.

To prevent tasks from getting stuck in a refinement loop, Codey performs no more than three iterations. If the feedback is not addressed, the task receives an `AI failed` status; the result is added to statistics and the system's self-improvement loop. If necessary, execution can be restarted manually.

Checks and Error Handling

After creating a merge request, Codey runs the project's quality gates: tests, linters, security checks, and AI review. If a problem can be fixed, the task is returned for refinement. If a check cannot be run due to project settings, Codey creates a Draft merge request and indicates which checks were not completed.

Most often, the `AI failed` status is related to a lack of context, changes in multiple interdependent repositories, or initial tasks in a new project or technology stack.

Team Verification of Results

For each merge request, Codey identifies affected modules and indicates in Jira which parts of the product need to be considered during regression testing. After successful checks, the frontend and backend are deployed to a separate feature environment where the client can test the entire feature.

If the result meets expectations, the client clicks Confirm. Then, the task undergoes team review and is included in the release build. Product acceptance, final decisions, and responsibility for the release remain with humans.

Business Challenges

Quality of Task Assignment. Codey, like any development participant, cannot perform a task effectively without clear requirements. Therefore, we have introduced Jira task templates with mandatory descriptions of the acceptance flow and expected checks, including requirements for unit and integration tests.

Team Trust in Codey. Initially, we suggest starting with routine tasks or refactoring, which are always subject to specialist review. As successful results accumulate, teams move from manual selection to a common backlog for Codey and developers, marking exceptions as `AI skip`. This allows for gradually building trust and providing the system with more context.

Shift in Load to Review and Refinement. At the start of implementation, some of the workload shifts to these stages: the developer needs to understand not only the task but also how Codey interpreted and implemented it. We reduce this load with more precise task descriptions, detailed rules for each project, and multi-level automatic and human reviews.

Infrastructure Costs. Separate backend feature environments increase infrastructure costs. To control expenses, we limit the lifespan of environments and use truncated test databases.

Technical Difficulties

System Universality. Different projects have varying architectures, codebase structures, technology stacks, and development rules. It's impossible to give agents a single set of instructions and expect consistently high-quality results.

Therefore, for each project, we maintain a profile describing the architecture, codebase structure, build and testing commands, and local development rules. For repetitive tasks, Codey has skills at three levels: global, language-specific, and project-specific. The system generates new skill variations based on accumulated patterns, but they are first verified and only then connected to the pipeline. This allows adapting Codey's behavior to the context of a specific project.

Quality of Changes. For this, projects needed a simple and reproducible setup, clear check commands, and mature quality gates. Tests, linters, security checks, and AI reviews in CI stop problematic changes before they create additional load on the team or reach production.

Selecting AI Models for Different Roles. We select AI models based on regular benchmarks. To do this, we observe how different combinations of models, roles, and tools perform a set of universal tasks. Then, we compare the solve rate — the proportion of solutions that passed mandatory checks and received an assessment comparable to human review, as well as the speed and cost of execution. For independent evaluation, the result is not passed to a model of the same family for review.

Benchmarks have shown that using a single most powerful model for all stages does not always yield the best results. For some roles, a simpler model may be more effective than a complex one: it can follow the plan more accurately, less often overcomplicate the solution, and complete the task faster. Therefore, we regularly review the distribution of models among roles based on test results. Following the latest tests, we have already transitioned some roles to Codex models.

Continuous System Improvement. For systematic improvement of Codey, we use a Learning loop: it analyzes logs and problematic sessions, identifies recurring errors, and forms hypotheses. Each change is verified on the same benchmark and only enters production after measurable improvement.

In one such cycle, we tested 20 hypotheses and kept nine. Additionally, we consider feedback from developers and testers. In parallel, we optimize working with code and context: RTK reduces the output volume of commands, and the AST index speeds up the search for relevant modules.

What's Next

In the near future, we will continue to develop Codey in several directions:

  • automatic analysis of the general backlog: the system will suggest suitable tasks itself, and the team will exclude those that cannot be handed over to AI;

  • development of the Learning loop: continuous analysis of human comments in merge requests and using this feedback for automatic improvement of the engine;

  • expanding coverage: connecting new clients and departments, projects, technology stacks, and systems to Codey;

  • connecting additional context sources — documentation, Jira, and work communications — and developing Codey as a foundation not only for development but also for analytical and product-oriented task refinement;

  • transitioning to feature delivery, so that changes from Codey reach production faster after mandatory checks.

Conclusion

Over six months, we have become convinced that an AI developer can be part of the workflow. To achieve this, it's not enough to simply connect a powerful model to development: high-quality requirements, prepared projects, measurable checks, and clear system operating rules are needed.

The next step is to transfer the full cycle of working with a portion of tasks to Codey: from their assignment to production release, while maintaining defined rules and risk control.
