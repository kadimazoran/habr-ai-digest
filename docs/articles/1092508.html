So, what's happening with PLC programming?

At first glance, the task is similar. There's a language, variables, conditions, timers, and function blocks. Why not ask a model to write a control algorithm for a pump or conveyor?

You can ask, but it's not that simple yet. More and more specialized tools are appearing that read PLC projects, explain LAD, generate code in ST, and in some cases, even start compilation themselves. But working with them still has its nuances.

In this article, I've tried to figure out what AI tools for PLC code represent today, what they actually do, and where all this is heading.

First Experiments with AI and PLCs

I remember about three years ago stumbling upon one of the first videos experimenting with writing PLC code using AI. It was Jakob Sagatowski's video, where he tried to solve PLC programming tasks using ChatGPT. He asked it to write a PID controller in ST, logic with a delay, and a block for TCP/IP string transmission in TwinCAT. He also asked questions about development languages and environments.

I was still working at an integrator company back then. We wrote software for controllers and SCADA systems and were already experimenting with AI ourselves. The interest was purely practical: if the model helps write code in other areas, why not try to entrust it with part of our work?

But after that video and my own experiments, I was left with the feeling that it was too early for serious work with PLCs. Getting an explanation or a code template was already possible. But expecting the model to understand the task and provide results that could be safely transferred to a project was premature. A lot had to be verified, and the confidence of the answer didn't always help.

Universal models of that time were significantly limited in the context window they could consider in a single request. There are also fewer available training examples in our field: source code of industrial projects is rarely published as freely as Python or C++ code.

And PLC programming differs from application development not only in the number of available examples.

For example, a pump control block lives within a project: its data types are declared somewhere, the equipment library is connected, and tasks are configured; somewhere, interlocks and commands from the HMI are formed. The program runs cyclically, timers and function blocks retain their state between calls. Writing a fragment that looks correct is only part of the job. You also need to understand how it will work with everything else.

Therefore, it seemed to me even then that a more specific approach was needed here: train models on automation examples, give them the documentation for a specific platform, and access to the project structure. And then verify the result in an engineering environment. Knowing just the syntax is not enough for this.

From Code Analysis to Project Work

The first tool with such capabilities that I encountered was PLC Copilot. At that time, it only worked with projects for Rockwell Automation controllers from Studio 5000. It was primarily an assistant for analyzing existing programs: you upload the project, ask questions about the code, and get explanations and hints. It helped understand the logic, but it didn't go through the entire process from project modification to result verification.

This already seemed more useful than a regular conversation with a model. There was no need to manually copy individual networks and try to explain how they were connected; the tool worked with the uploaded project. For a program inherited from another engineer, such help can be quite useful. Especially if the comments stopped around the same place where the complex logic began. However, the software's capabilities were still quite modest, and I wanted much more: help in writing new logic, making changes, and verifying the results.

I didn't return to PLC Copilot for about six months and only in early September 2026 did I decide to look again at what had changed. And I saw that much of what was only dreamed of had already appeared: the developers added support for other engineering environments, announced code generation, and expanded project work capabilities.

When I decided to see if PLC Copilot had competitors, I found more than a dozen specialized solutions. These include standalone applications, AI functions within source code management platforms, and built-in assistants from PLC manufacturers.

What AI Tools for PLCs Can Do Now

Capabilities have also expanded. Explaining existing logic, finding connections between blocks and tags, preparing documentation, generating ST, and converting between ST and Ladder are all found in various tools. Some already connect to the engineering environment, make changes to the project, start compilation, and fix errors based on its results. Others claim to assist with HMI and equipment configuration. The set of functions depends on the product and the supported platform.

Increasingly, developers are positioning such tools as agents. The transition from assistant to agent is quite specific here: from explanations and hints to executing a chain of actions – read the project, modify the block, compile, and fix found errors. The model receives feedback from a real engineering environment. Although successful compilation, of course, doesn't mean the conveyor will move where it should.

I chose five examples to show different approaches: analyzing an uploaded project, working through a repository, bridging to an IDE, and proprietary solutions from engineering environment manufacturers.

Copia AI and Copilot

Copia AI uses projects from Copia Source Control and DeviceLink backups. The manufacturer claims code explanation and documentation, fragment generation, and conversion between LAD and ST.

The main difference in approach is the context source. AI works with the program from the source control system. For example, you can prepare a description of a selected version and then compare it with a change.

There is no public pricing for Copia AI/Copilot. The documentation suggests contacting a Copia manager to connect Copilot to a subscription and get trial access conditions. The duration and limitations of such access are not publicly disclosed. You can also request a demo.

PLC Assist

PLC Assist focuses on Structured Text and feedback from the compiler. According to the documentation, CODESYS V3.5 SP18+ and TwinCAT 3.1+ are supported. TIA Portal is currently listed as coming soon.

A local bridge connects to the IDE: a Python script within CODESYS or a separate Windows application for TwinCAT. It reads the project structure, applies changes, and sends compilation results to a cloud agent. Necessary code fragments, as indicated by the developer, are sent to the AI provider.

It also claims to show changes and fix errors based on the standard compiler diagnostics.

This is already quite close to a programmer's usual work with an agent: add an output to a block, consider the existing interface, build the project, and fix any errors that arise.

However, successful compilation only confirms what the environment has checked. Whether the new diagnostic signal works correctly will have to be figured out separately.

On the pricing page, Pro is listed at €24 per month and Power at €49 per month. Power offers 2.5 times more AI usage. There is a free Trial tariff with limited usage: code generation and verification, connection to CODESYS and TwinCAT, and library documentation are available. The trial period and exact limits are not specified.

The agent can generate PLC code, create HMIs, and configure devices considering the project. It also claims to read electrical schematics in XML and AML and generate project structure from a machine description.

This means Siemens is looking beyond a single function: the agent should work with related engineering data. A station description can become the basis for a program, tags, and configuration.

What's Behind the Chat Window

Externally, many such products look similar: a project, a request field, an assistant's response. But their practical value is determined by what happens between these elements.

If we generalize the approaches reviewed, we get four parts. Their specific implementation by manufacturers may vary.

The first reads the project. It extracts blocks, networks, variables, types, calls, and available configuration. For ST text, this is one task; for graphical LAD or FBD, it's another.

The second selects the context. If the question concerns a single valve, you need to find its block, the calling program, the data type, and the library documentation. Simply passing more text to the model is not always a good way to help it understand.

This can involve source code search, dependency graphs, and documentation search. One approach is called RAG: along with the question, the model receives the found materials.

The third part transforms the answer into a modification of an engineering object or an import file. It's necessary to preserve the project structure and show what exactly will be changed.

The fourth initiates checks and returns the result. First, it's format and compilation, then block tests and simulation, if the tool can handle them.

For an engineer, a useful result looks something like this: here's the change, here's the project version, here are the compiler messages, here are the executed scenarios. The phrase "I've checked everything carefully" can be included, but it shouldn't replace this set.

Why There Are Still Many Difficulties

Industrial Projects Are Rarely on GitHub

A machine's program may contain knowledge about the customer's technology, equipment, and processes. It's usually not possible to simply post such a project publicly along with the enterprise's libraries and documentation.

In general, the limitation of public data for training models in PLC programming is a known issue. For example, the authors of the research on training AI to write ST code also note the lack of open examples and consider fine-tuning models with feedback from the compiler.

For tool developers, the task is clear: supplement the model's knowledge with documentation and project context. But even within a project, not everything is equally reliable. A comment might be from a previous version of the algorithm, and a variable name might be from equipment that has long since been replaced.

ST Can Be Different

The label "supports Structured Text" still says little about compatibility with a specific project. Language extensions, types, libraries, environment version, and target platform are important.

Suppose the AI suggests calling a drive control block. The name looks quite convincing. It remains to find out if such a block exists in the installed library.

If it doesn't exist, it's a relatively convenient error. The compiler will likely help detect it. It's more difficult if the block exists, the call is valid, but the model misunderstood the purpose of an input or the conditions for executing a command.

Therefore, a single request like "write code for Siemens" is not enough. The model needs to be told the TIA Portal version, the PLC model, and the libraries used in the project. Otherwise, it might suggest functions or blocks that are not in that project.

Ladder Logic Needs to Be Read and Reassembled

ST can be passed as text. LAD and FBD contain a connection graph: branches, connections, block parameters, and execution order determined by the environment.

In a screenshot, some of this information might be missing. An adjacent network is not in the frame, a variable is declared elsewhere, a program call is on another screen entirely. Therefore, explaining a picture and analyzing a structured export offer different possibilities.

And then the result needs to be returned to the IDE. A list of instructions by itself doesn't yet become a graphical program that the environment can import and display.

When converting LAD to ST and vice versa, it's necessary to check that the behavior is preserved, including block states and calculation order. Matching variable names is too weak a criterion here.

The Program Doesn't Know the Entire Installation

From the code, you can see that a signal is used as a start enable. But from a variable name alone, it's not always clear what sensor it represents, how it's connected, and what should happen if communication is lost.

You need the electrical schematic, the I/O list, the algorithm description, and the operating mode requirements. If these materials contradict each other, the tool should notice the contradiction.

For example, the description requires manual alarm reset, while the existing code automatically clears it after the signal is restored. The current behavior can be explained by the program. Deciding what it should become requires referring to the requirements.

The model's confidence doesn't resolve this dispute.

Compilation Doesn't Verify the Technological Process

The compiler checks the program within its capabilities. It doesn't know if a restart is allowed after power restoration or how the installation should behave when a sensor fails.

To test a block, you can set input sequences and observe outputs and states. For equipment, you need to consider the object's response: a command changes the mechanism's position, the position changes the sensor signal, the signal affects the next command.

Successful compilation doesn't mean the program correctly controls the equipment. The generated code needs to be tested in normal and emergency modes. It's important to understand which situations have been tested and which are still outside the scope of the tests.

Where the Model Itself Runs

The phrase "runs locally" needs clarification. The computer might host the interface, the bridge to the IDE, the project, or the model itself. These are different parts of the system.

In PLC Assist, the documentation explicitly describes transferring necessary fragments to the AI provider. Therefore, before choosing a solution, it's worth finding out what leaves the workstation, where the history is stored, and which components require an external connection.

For an isolated site, this is a practical question. If cloud requests are not possible, the model, documentation search, and verification tools must run within the available infrastructure.

What Can Be Done Right Now

There are still many limitations, but practical tasks for such tools already exist. If we combine the capabilities of the reviewed products, we get a list like this. Of course, the specific set depends on the tool and the supported environment.

  • Analyze existing programs. Get explanations of logic, find start conditions and interlocks, search for connections between tags and blocks. Especially useful when the project was inherited from another engineer.

  • Prepare documentation. Compile descriptions of blocks and algorithms, add comments, and gather materials for project handover.

  • Write new logic. Get templates in ST and other supported languages, and in some products, convert Ladder to ST and back. Then, verify the result in your environment.

  • Make changes and fix compilation errors. Tools that connect to an IDE can modify the project, start building, and use compiler messages for the next attempt.

  • Assist with HMI and equipment configuration. Such support goes beyond writing PLC code, although it's currently found only in some solutions.

In the near future, I expect a closer connection between these functions: modifying a block will be accompanied by updating related tags, HMIs, and documentation. Another interesting direction is the automatic preparation of test scenarios and running simulations so that the assistant can check the program's behavior and use the results for corrections.

When Will a Regular Universal Agent Be Able to Do This?

After this selection, the question arises: how long will it take before an agent like Codex or Claude Code gains access to the engineering environment and can perform the same actions? And it definitely will happen, I'm sure of it.

There are already ready-made mechanisms for such connections. For example, TIA Portal Openness is an interface through which another program can interact with TIA Portal. It allows, among other things, to start compilation and get a list of errors. Based on this, an AI agent can be connected, which will start compilation after its changes and fix code based on compiler remarks.

A possible path is an adapter that provides the agent with understandable operations: read block, find references, prepare change, compile. This is an architectural option, not a statement that all listed environments already connect to universal agents out of the box.

For providing operations, MCP (Model Context Protocol) can be used, for example. It describes the interaction of AI applications with external tools and data. But the adapter still needs to know the specific IDE's API, limitations, and formats.

And CODESYS already has such a tool – the official CODESYS Development System MCP Server. Through it, AI can read projects, create and modify blocks and data types in ST, start compilation, receive error messages, and access library documentation. Furthermore, the manufacturer already reports successful connection of Claude Desktop.

This results in a fairly clear scheme: the agent plans the work, the adapter performs operations in the environment, the compiler and tests return results, and the engineer evaluates the changes.

Where All This Is Heading

I think the capabilities of universal and specialized tools will converge. And competition will gradually shift to the quality of integrations and verification.

A scenario like "paste ST into chat and get another ST" is relatively easy for a universal tool to reproduce. Much more work is involved in reading different project versions, preserving graphical networks, correctly using libraries, and verifying changes.

IDE manufacturers can develop built-in agents around their own objects. Independent developers can connect multiple platforms, repositories, and enterprise documentation. Universal agents can use available engineering adapters. All of this can coexist.

Therefore, I wouldn't set a deadline by which separate PLC products will become obsolete. Some of their functions may turn into integrations for various models. But working with engineering formats, libraries, and testing will remain.

The engineer's role will also change. More attention will need to be paid to algorithm specification, context selection, change verification, and reproducible tests. Knowledge of the technology is especially useful here: it allows you to notice a problem that the compiler won't see.

In my article about a Modbus client, I already wrote that AI helped create the application, but I still had to explain and verify the engineering scenarios myself. With PLC code, the logic is similar. There's just more context around the program, and the result needs to be evaluated based on the equipment's behavior.

AI has already reached PLCs. Now it's interesting to see how well it will master the part of the job that is usually called by the short word "commissioning."
