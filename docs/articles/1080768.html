Every few years, developers are buried again.

First, visual builders were supposed to replace us. Then no-code. Then low-code. Then auto-generation of CRUD. Then Copilot. Now, it seems, the final boss has arrived in the form of large language models, which can whip up a backend, frontend, Docker Compose, migrations, OpenAPI, Kafka, PostgreSQL, Redis, authorization, tests, README, and a compiler on the side in an evening.

And if you open any social network, you'll see everywhere: 'I made a SaaS in 20 minutes,' 'the neural network wrote me an app,' 'one prompt replaced a development team'... It all looks like the profession truly belongs in a museum next to punch cards and floppy disks, as now an ordinary internet user can conjure up enterprise software, a banking mobile app, and a taxi aggregator. And all this just in the morning.

But the more I work with AI tools, the less I believe in the disappearance of developers. And not because AI is stupid. Quite the opposite – AI writes code well now. But to avoid discussing the topic abstractly, I'll tell you one illustrative story. I'll deliberately take the most modest scale possible: no backend, no Kafka, and no eight services. One frontend. To be completely honest, it will be one search screen. We'll see everything there.

At first, I was impressed by the beautiful code

Once, a colleague showed me a generated application. It had: Next.js, authorization, tables with filters, forms with validation, charts, a dark theme. Everything started with one command and looked better than half of what I had done manually. He showed it, of course, not just for fun. After the demonstration, he pompously said: 'In a year, we won't be here anymore.'

I didn't argue, although I understood he was mistaken. But where exactly? Where exactly does it break? The code was written not badly, so I couldn't find fault here. Then I thought, where does what the model does for me end, and what I will have to do begin, no matter how many tokens I spend?

I took a similar task – an interface for booking consultations – and after a dozen minutes, I got a working application. True, then I spent half a day figuring out why the search sometimes shows results not from the query typed in the field, but that's not what we're talking about. I wrote a detailed prompt, then ran it additionally through GPT: stack, folder structure, that server state lives in react-query, that forms are needed with react-hook-form using zod, that components are assembled according to these and those rules, what approaches we use, and so on.

The result was an expert search, a profile page, a calendar of slots, a booking form, a history of these bookings, an admin page, skeletons, empty states, toasts. Everything assembled on the first try, no type errors, the application worked.

Honestly, I was impressed.

It would have taken me several days manually, and that's only with a ready-made design and description of business processes. But then I started typing in the search field...

And got upset

Here's the code the model generated (slightly shortened, but the mechanics are untouched):

function ExpertSearch() {
  const [query, setQuery] = useState("");
  const [experts, setExperts] = useState<Expert[]>([]);
  const [isLoading, setIsLoading] = useState(false);
  useEffect(() => {
    if (!query) return;
    setIsLoading(true);
    fetch(/api/experts?q=${query})
      .then((r) => r.json())
      .then((data) => setExperts(data.items))
      .catch(() => setExperts([]))
      .finally(() => setIsLoading(false));
  }, [query]);
  ...
}

Looks okay, right? There's a loading state, error handling, a dependency in useEffect, a finally block. I would have passed this in a review if I were reading quickly. And I did.

We type 'm', 'ma', 'mar' – three requests are sent. The responses arrive in the order the server responded, not in the order we asked. If the response for 'm' is delayed and arrives last, it will overwrite the results for 'mar'. One thing in the field, another in the list.

This bug is as old as useEffect itself, and it's in the React documentation in a separate section. The model knows about it, because when asked 'Is there a race condition here?', it answers correctly and immediately.

It's a shame it didn't have a reason to ask itself about it. I asked for search, I got search. What's to complain about, right?

Nearby, setExperts will also be called after the user leaves the page. No one is going to cancel requests, of course, so when typing quickly, five are flying in flight.

And here's another example.

const { data, isPending } = useQuery({
  queryKey: ["experts", query],
  queryFn: ({ signal }) => searchExperts(query, signal),
  enabled: query.length > 1,
  placeholderData: keepPreviousData,
});

There's no race condition here. Except it's not because we fixed it, but because it became impossible, as the result is tied to the query key, not the order of responses.

And this – not identifying a specific error, but a place where an entire class of errors can be made impossible to occur – I consider the main skill in working with generation (to see and know these places).

Are we sure we're still needed?

I found this bug by disabling the network in devtools.

const handleSubmit = async (form: BookingForm) => {
  setIsSubmitting(true);
  const booking = await api.createBooking(form);
  toast.success("Бронь создана");
  setIsSubmitting(false);
  navigate(/bookings/${booking.id});
};

If createBooking throws an exception, setIsSubmitting(false) is never executed. The button remains disabled, the spinner spins, the user waits, then reloads the page and loses the filled form. An unhandled reject hangs in the console, which the user doesn't see.

This is the most common bug in generated frontend that I've encountered.

The model writes a scenario where everything worked out: the request was sent, the response arrived, the redirect happened. States that the interface enters on its own – network failed, user double-clicked, left the screen mid-way, returned from background after twenty minutes with a dead token – are not included in this scenario.

It's fixed either with try/finally or useMutation, which itself manages isPending and error.

But before fixing it, you have to notice it. And it's only noticeable if you deliberately break it.

Upon booking cancellation, I, as a developer, was taken aback. The model made an optimistic update: click – and the booking immediately disappears from the list, the request goes in the background. Looks nice.

But what will we do if the request fails?

Return the booking to its place silently? The user will think the interface is glitching. Show a 'notification'? What if the user has already switched to another tab and won't see it? Leave everything as is and hope for the best? You shouldn't do that (but, by the way, they do). Ask 'Retry'? What if they don't understand what it's about?

There's also the issue of debouncing the search. The model decided to set it to 300 milliseconds. But where did 300 come from? Who decided that? For searching ten experts, you can do without debouncing at all, and if the backend request is heavy, even 600 might not be enough.

There is no answer to any of these questions in the code. The answer lies somewhere in the realm of how people use the screen, in discussions about the cost of a request and who we are willing to 'upset'. The model lists options well (I later asked and got a reasonable list of compromises), but choosing between 'sometimes we shortchange the user' and 'sometimes we slow down' is, forgive me, not a technical decision.

Then came the minor, but telling, details.

lodash – entirely for the sake of two functions. It significantly affects the bundle size, and in the code, it looks absolutely normal: one import line. The modal opened without a focus trap and didn't close with esc, and half of the clickable elements were divs with onClick. This can be checked in 30 seconds – just navigate the screen with the Tab key. But you have to do it. You have to check.

After that evening, I established an order

This is the sequence in which I open files. It developed historically, but in such a way that most really costly errors are found.

First, I look at where the state lives. Server data in useState? That's future pain: you'll have to synchronize manually, and all race conditions will come from there. Filters not in the URL? This means the link to the filtered list cannot be sent to a colleague, and this will be discovered in six months.

Then I look at all side effects and always ask myself: 'What if there's no response at all? What if the component is already unmounted? What if the response is NOT WHAT we expect?' Usually, that's where all the interesting stuff is found.

Then I look at states other than loading and success. The model always does these two. But empty result, partially loaded data, server validation error, double-clicking the button – almost never.

And at the end, we always look at the bundle, dependencies, configurations.

An hour and a half for a screen versus 3 days of manual work – it's an excellent deal, in my opinion! But it should be a real 1.5 hours of reading, not 5 minutes of looking at a diff.

What has really changed

The creation of an MVP version has become cheaper.

Previously, between 'there's an idea for a screen' and 'there's a working screen that can be poked at,' it took a day or two. Now – an hour! I manage to review many more options before agreeing to something. I started making two or three layouts and choosing, instead of defending the first one because time had already been spent on it.

But the cost of errors in decisions has not decreased. It has rather increased.

Previously, it was difficult to accidentally introduce 5 ways of doing the same thing. Now you can create your own useFetch next to react-query in an evening, three different ways to show an error, one button component with twelve props, because with each generation I asked to 'add a variant'.

Previously, to create a mess, you had to work hard, but now the mess is generated for free. But the same person who did it before will be cleaning it up.

Final conclusion

The code is written faster than if I wrote it myself, and, in fact, that's mega cool. But none of the bugs I spent time on were code bugs.

The first was about the difference between 'looks right' and 'is right'. The second about states that the interface enters on its own when no one is looking. The third wasn't even solvable in the editor because it required deciding what exactly we want as behavior.

And here's what seems most important to me. All of this is one frontend: one application, one developer, one evening of generation. Moreover, the frontend is the most honest part of the system because bugs are visible to the eyes. The search showed me the wrong people? I noticed it. The button died? I noticed it. I didn't even need logs, devtools and my own curiosity were enough.

Now let's complete the picture with what I started the article with. To this application, 8 generated services are added.

  • Between them, Kafka with events that arrive twice and not in the right order.

  • A saga of three steps, which has a state 'payment processed, but booking already canceled due to timeout'.

  • Migrations, command idempotency, distributed locks that are released half a second earlier than needed.

And all this was also generated in an evening, also assembles on the first try, and also looks absolutely normal when reading.

Only there, no one will notice anything with their eyes anymore. A race condition in useEffect affects one user and is immediately visible. But a race condition between two services is a second booking for the same slot and a call to support a month later.

Errors in such a system do not add up, but multiply: each service is plausible individually, and the interaction, which is not in any single file, is broken. There's nowhere to read it, because it exists only in the mind of the person who holds the entire system.

This head is currently our job.

Although, I don't think it's forever. Models have grown so much in a year that I've stopped predicting, and a race condition in useEffect is quite deterministic, it can be caught statically, it's just that no one has really taught it yet. But for now, someone has to disable the network in devtools and see what happens.

So, the most useful habit I've acquired this year is not the ability to write prompts, but not to trust a working demo until I've tried to break it.
