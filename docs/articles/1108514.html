Hello, Habr! Artificial intelligence systems are being implemented everywhere. Therefore, specific threats are emerging, directly targeting AI infrastructure and the information security of systems that use it. Ensuring the confidentiality, integrity, and availability of data is becoming a paramount task for both programmers and users of such systems.

It is important for companies to integrate AI securely. Therefore, before implementing ML models, it is necessary to understand how to secure the data on which the model will be trained and with which it will subsequently work.

Among other things, an AI attack can be aimed at the model, training and fine-tuning data, as well as interaction mechanisms with it – prompts. This opens the door to new AI security threats, such as:

  • Prompt injection – injecting malicious instructions into a prompt that lead to unintended behavior of the LLM.

  • Jailbreaking – bypassing the model's built-in restrictions and exploiting its behavioral "gray areas.".

This article does not cover all methods for secure information handling during AI system training, nor is it a guide to AI implementation. The main goal is to introduce the reader to basic methods of ensuring confidentiality, using simple language and a humorous D&D analogy for enthusiasts.

Data Security in AI Systems

Let's consider the main approaches to ensuring data confidentiality for model training and integration.

Data Encryption During Storage and Transmission

Basic step – store datasets (e.g., databases with personal information, large user data) in encrypted form. Standard symmetric encryption algorithms (AES, GOST – "Magma", "Kuznechik") are used for files or DBMS. When transferring datasets between nodes (e.g., between client and server, or between distributed components of an ML system), communication channel protection (TLS, VPN) is used – this protects data from interception.

Data Anonymization

Working with personal data of individuals or data sensitive to disclosure to third parties involves the need for anonymization to reduce the negative consequences of such data leakage. Main approaches:

  • Deletion or masking of identifiers – names, numbers, addresses.

  • Pseudonymization – replacing real identifiers with artificial ones. For example, a random ID is used instead of a name, and there is a separate mapping dictionary that is stored securely.

  • Data generalization – for example, instead of the exact date of birth, the year of birth or age range is indicated.

  • Removal of rare characteristics – features that can be used to identify a person.

Anonymization allows data to be used in research without revealing personal identities. This approach is particularly useful when a model works with general corporate information with different access levels: anonymization will prevent employees from seeing what they are not authorized to access.

With pseudonymization, consistent replacement (linkage) is used if it is necessary to preserve links between records. Thus, the same original identifier receives the same designation in all related data. For example, the same replacement of an IP address in network logs allows correlating events from one node and analyzing its interactions with others without revealing the original address. However, it is better to work carefully with this approach: the more links are preserved, the more useful the data is for analysis – and the more information remains with the person trying to restore the original objects. Cryptographic masking using hashing plays a similar role. This approach preserves important links – the correspondence of different records to one object and the distinction between different objects in the corresponding records.

It is important to remember regulatory requirements: GDPR in Europe, HIPAA in the USA, and 152-FZ in Russia impose strict norms on personal data processing. For example, 152-FZ requires mandatory anonymization in specific cases (upon achievement of the processing purpose, for research purposes, upon request from the Ministry of Digital Development).

Differential Privacy

Allows publishing aggregated data or training a model such that adding or removing a single record does not affect the final result (almost). Mathematically, differential privacy adds controlled noise to query results or gradients during training, making it impossible to restore the original data with high confidence. There are two main approaches:

  • Adding noise to the model's output. This prevents an attacker from determining whether specific data was used in model training (Membership Inference Attacks). For example, instead of the exact number 34.2, the DP algorithm might return 34.7 or 33.8, while the noise's impact on overall statistics remains minimal.

  • Injecting noise into the training process itself. This helps protect the system not only from Membership Inference Attacks but also from Model Inversion Attacks – attacks aimed at extracting original data by reverse-engineering the model (e.g., reconstructing a face image from model predictions). In this approach, the model becomes "blind" to individual records and learns only general, stable patterns.

Federated Learning and Homomorphic Encryption

When a dataset is distributed among multiple participants, they can jointly train a model without revealing their data to each other. Algorithms based on encrypted information exchange protocols allow computing a common result (e.g., model weights) without revealing the original data of each party. This means that data can be processed without knowing its content.

In some cases, homomorphic encryption is used, which allows performing computations on encrypted data (e.g., searching an encrypted database without revealing either the query or the found value). However, homomorphic encryption has very high computational complexity and requires powerful hardware.

For aggregating model updates in federated learning, Secure Aggregation is used – a protocol where the server receives only the sum of updates but does not see the contribution of each client individually. This is computationally cheaper than homomorphic encryption and does not reduce model accuracy.

Data Integrity Protection: Cleansing and Poisoning Detection

Data can not only be stolen but also poisoned with the aim of distorting the model's results – this is called Data Poisoning. To prevent such situations, data cleansing is performed: noise and anomalies are removed, and regular regression testing and attack simulations are conducted to identify vulnerabilities before they affect the production environment.

If poisoning is detected, dataset versioning (DVC – Data Version Control) can help roll back quickly. Keep a history of dataset changes and control versions – this will allow you to restore a "clean" version and continue working without losses.

Infrastructure Security

We have discussed direct tools for protecting data in AI systems. But they can be useless if the corporate infrastructure itself is not adequately prepared. If an attacker gains access to the training server, even the most advanced model trained on perfectly anonymized data will be compromised.

Below are equally important principles for ensuring basic security for AI implementation.

Principle of Least Privilege

Employees and systems are granted access only to the data minimally necessary to perform a specific task. This reduces the attack surface and the damage from a potential compromise of a single account.

Infrastructure Isolation

Training models on sensitive data should not occur on a general corporate cluster where test environments and marketing emails are running. The infrastructure for model training must be strictly isolated – this implies network segmentation, dedicated clusters, restricted external access, and full control over all components.

Infrastructure Monitoring

Intrusion Detection Systems (IDS) monitor for network attacks, and tracking resource consumption anomalies helps detect hidden attacker activity. Sudden abnormal CPU/GPU load, suspicious disk or network interface activity can be signs of a malicious script running or an attempt to steal a model. Such solutions are combined to ensure protection at all system levels.

Additionally, it is worth organizing monitoring of mass API requests to the model and unusual usage patterns – this will help detect exploitation attempts or data leaks through external interfaces in a timely manner.

DLP Systems and AI Request Control

Data Loss Prevention (DLP) systems can detect attempts to transmit confidential data in requests to external AI services (e.g., cloud LLMs). This is particularly relevant when using B2B solutions where data leaves the company's perimeter.

Physical Security

Do not forget about the physical level: server rooms where training data and model weights are stored must be in a controlled zone with limited access, video surveillance, and climate control systems. If an attacker gains physical access to the equipment, all software protections may become useless.

Code Obfuscation

Protection of the model itself after training deserves special attention. This is not about data encryption, but about obfuscating (making complex) the model's code and using methods to protect neural network weights. This makes it difficult to analyze and reproduce the model even in case of infrastructure compromise, but it is not encryption in the classical sense.

Conclusion

Of course, many other problems can arise during AI implementation, but it is very important to pay attention to data security, especially if you are training a model on corporate information.
