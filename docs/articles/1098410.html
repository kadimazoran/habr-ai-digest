Where It All Began

Full-stack Dart entered my life 5 years ago – I quit my job to develop my own studio. I assumed it would be better to choose one stack as a specialization and develop within it. (I don't think so anymore.)

I already knew a little Flutter and believed in it strongly. (And I still do.) That's why I was particularly drawn to the then-emerging Serverpod – I remember the first projects were on version 1.1 or 1.2. Their slogan was "missing server for Flutter," and the main feature was code generation for the contract between the server and the application: this applied to both models and API methods.

I thought this innovative approach would be my competitive advantage, allowing me to build applications faster and better. All my assumptions turned out to be wrong: a monostack rather limited me, and taking the first steps in business while simultaneously reinventing the wheel turned out to be a catastrophically difficult endeavor. Don't do that))

Nevertheless, I was an adventurer and chose my own path. At first, I simply built projects on Serverpod, but very soon my inclination for optimization began to manifest. I really disliked that for every request from the application, a separate endpoint was needed, errors had to be handled within it, and a response formed.

I also didn't like that for each model in the application itself, a separate repository with a lot of logic appeared. At that time, I didn't understand application architecture very well, and it all turned into a terrible mess.

But what horrified me most was that every developer on every project did things a little differently, and the same problems repeated across different projects…

That's when the idea of DartWay was born – to develop a single, universal methodology for application development.

But it took a long time from the birth of the idea to its clear implementation. I recall my first sketches – it was excruciating pain.

For example, I tried to create a mechanism where all models were stored in a single pool and accessed through some terrible extensions on enums – in every widget where they were needed.

DartWay's Idea and Philosophy

The most important thing to understand about DartWay is that it's a terribly opinionated framework. It dictates literally everything – from the logic of interacting with the backend to variable naming and folder structure.

DartWay was born from one simple hypothesis: for every problem, there can be found such a universal and flexible solution that 99% of projects can use it and not worry about it.

Experienced developers, accustomed to their own methodologies or disagreeing with my approaches, might not like this very much. But I'm not creating the framework to please everyone. The goal is simple – to maximally accelerate and simplify the launch of reliable mobile applications.

And the main challenge is how to ensure functional flexibility and the implementation of any client requests within a strict structure and using unified mechanisms.

What is key to this in DartWay.

1. Strict Backend Contract

The client can only send models to the server and receive them – more precisely, DTOs. All requests go through the same pipeline.

On the backend, this includes authorization checks, validation, database operations within a transaction, response formation, and additional updates, broadcasting updates via sockets to all subscribers.

On the frontend, all server responses are also processed by a unified repository and distributed to subscribers.

Thanks to this, a specific feature doesn't need to think about who else its updates affect – this is handled by the central repository and subscriptions.

How it looks. A feature consists of several classes in a shared package that compiles for both the server and the application:

final class ListNews extends DwListRequest<NewsPost> with _$ListNews { const ListNews(); @override List<DwLiveChannel> get channels => const [ DwLiveChannel(DartwayExampleChannel.news), ]; } final class PublishNews extends DwActionCommand<NewsPost> with _$PublishNews { const PublishNews({required this.title, required this.text}); final String title; final String text; }

On the server – one handler per call: who can call it, what it does, and who will know about it:

DwCallHandler.command<PublishNews, NewsPost>( access: AppAccess.staff, handle: (ctx, command) async { final me = await ctx.profile; final row = await ctx.db.newsPosts.insert( NewsPostRow( authorProfileId: me.id!, title: command.title.trim(), text: command.text.trim(), createdAt: DateTime.now(), ), ); final post = (await ContentObjects.news(ctx.db, [row], author: me)).single; ctx.publish(AppChannels.news, post); return post; }, ),

In the application – a live list and a button that won't publish twice:

ref.watch(dw.request(const ListNews())) // AsyncValue<List<NewsPost>> onTap: dw.action((_) => dw.command(PublishNews(title: title, text: text)))

An employee publishes a news item – it appears for everyone who has the list open, in its place, without reloading. An error is returned as a code and displayed in the user's language. A repeated command is executed once. No endpoint, no route, no client method, no cache was written for this. Under the hood – POST /dw/<Type> for each type and one socket /dw/live for live channels.

2. Strict Application Structure Rules

Strict instructions on the structure of a Flutter application, feature architecture, and responsibility boundaries. Separation of logic from UI is not a recommendation but a set of rules checked by the linter and scripts. Cyclic dependencies and uncontrolled file growth are excluded.

This is what a feature looks like in the project template:

lib/app/profile/ profile_page/ profile_page.dart ← the only public file of the feature logic/ profile_change.dart profile_page_commands.dart widgets/ avatar_picker.dart profile_settings_widget.dart identity/ ← nested feature, same rules profile_identity_section.dart logic/identity_change_controller.dart widgets/identity_change_sheet.dart

dartway check ensures it stays that way: a feature has one public file, you can't access others' logic/ and widgets/, there are no cycles between features, a file longer than 350 lines is a reason to split it. A violation looks like this:

lib/app/home/home_page.dart imports the internals of app/profile/profile_page (lib/app/profile/profile_page/widgets/avatar_picker.dart) — only the public file of a feature may be imported from outside it

It is precisely because of these rules that I don't worry about the code written by agents. The worst that can happen is a local sub-optimality within a 500-line feature. The project structure and architectural correctness are guaranteed.

3. Ready-Made Foundation and Modules – and Yet Flexible

My biggest pain has always been code repetition between projects. We implemented authentication in one project. Then in two more. Then we found a bug or added a feature in one of them – and we start manually porting the fix to all projects. It's terrible.

The other extreme is ready-made packages. How many I've seen, they all have the same problem: only one scenario works, you can't change literally anything except button colors. As a result, on the very first project, you have to fork and modify it for yourself.

I am convinced that the main advantage of DartWay is the balance between ready-made solutions and flexible customization. The framework covers all the main tasks: authentication, repository, WebSockets, server operations. But everywhere there are callbacks and parameters to solve any project task.

For example, login. Accounts and login methods are the framework's responsibility: it knows that someone has logged in and with what phone number or email. But who this person is for the project – their profile, role, what to do with their data upon deletion – is decided by the project in callbacks:

DwAuthConfig( // how to deliver the code – SMS, email, custom gateway deliverCode: (ctx, kind, identifier, code, accountId) async { ... }, // profile is created along with the account, in the same transaction onAccountCreated: (ctx, accountId, kind, identifier, origin) async { final profile = await ProfileChanges.create(ctx, accountId, origin); ctx.publish(AppChannels.admin, await ProfileObjects.profile(ctx, profile)); }, // delete person's data or leave a "tombstone" – decided by the project onAccountDeleting: (ctx, accountId) async { ... }, )

The framework grew out of the studio's needs: everything must work as the client wants – which means no compromises. Any behavior can be configured, any task can be solved.

And a separate level – the template. Many things are not hardcoded into the framework's packages but are implemented in the project template: they are ready for use but do not restrict editing and customization in any way.

Most recently, I created a nice dashboard in the admin panel. Now, every new project will have the same out-of-the-box.

It was precisely this flexibility that I lacked in Serverpod – and this led to the decision to abandon it.

Why I Abandoned Serverpod

For over three years, my team and I built projects on Serverpod, and the first version of DartWay was based on it – essentially, DartWay was a module for Serverpod.

It was convenient at the start – to have a ready-made foundation. And Serverpod was very good in this role: a decent implementation of the server, ORM, and contract generation, very high-quality documentation, and no bugs. As a framework for a project, I can still recommend it. But as a foundation for DartWay, it began to limit me.

I'll describe the main points – as an illustration of how differently the same issues are resolved at the framework level.

Module Architecture

Serverpod provides ready-made modules for authentication and chats. But all models within them are located inside the module – and the project cannot add a new field to the user class or its own message type in the chat.

Therefore, none of my projects could use their modules without modifications: we copied them and edited them. During this time, the framework itself moved forward by a dozen versions, and we couldn't update.

In short, a nightmare. In the end, I first abandoned their chats, then created my own authentication.

In DartWay, the user model belongs entirely to the project and can be freely modified to suit its needs. The framework only manages access tokens and authentication providers, and connects to the project's model through a couple of typed callbacks – as in the login example above.

The result – 100% flexibility.

Model and API Contract

Serverpod's main feature is generating mirrored models for the backend and frontend. Mirrored, because they are still different classes, even though they have the same name. I don't know why they went this way, but the approach has two unpleasant effects.

Cannot share business logic. Since they are different classes without a common ancestor, you cannot simply add an extension and implement unified validation on the frontend and backend. As far as I know, a solution for this has appeared in the latest release, but I haven't looked into it in detail yet.

Unified model list for the application and server. At first, this seemed like a huge advantage: no duplication, the same classes, everything is great. But the deeper I delved into mobile development and architecture, the clearer I understood that the approach was incorrect.

ORM models that are stored in the database should not leak into the application: the set of fields in them does not match the use cases and user permissions.

Serverpod has workarounds for this – converting a model to its public version or marking individual fields as server-only. But each time it was an individual solution, and I wanted a unified, universal approach.

Therefore, in the new DartWay, models live only on the server. The contract between the application and the server is placed in a shared package and consists of DTOs – separate entities for each scenario of interaction between the application and the server.

Why It Took So Long

Abandoning Serverpod had been brewing for a long time. I understood that it limited me and created difficulties, but I was intimidated by the need to rewrite such complex modules as the HTTP server, ORM, and contract generation. With the development of neural networks, everything changed…

The New DartWay – On Agents and For Agents

Since the beginning of 2026, I started delegating many development tasks to neural networks, and by mid-year, I practically stopped touching the code manually.

Now I am firmly convinced that the only real future process is development in Dark Factory mode, where agents handle development completely independently, including code reviews and acceptance testing.

It is for this future that I am now building DartWay. The framework, which was created to control the quality of work by juniors, has become the ideal constitution for agents.

A Week Without Serverpod

This is how the story with Serverpod ended. On September 13th, on impulse, I asked Claude to prepare a plan, we discussed the details for about an hour – and the next day the new version of DartWay was ready: its own server directly on dart:io and its own ORM on top of postgres. It took a few more days to migrate projects, and by September 19th, Serverpod was no longer used anywhere.

The most surprising thing is that everything worked immediately. I don't recall a single bug related specifically to the rewrite.

A Constitution for Agents

I can trust neural networks with so much thanks to DartWay. For a couple of years, I developed it as a methodology: many non-obvious solutions that together reduce complexity, eliminate risks, and make development simple and controllable.

The main thing is that the architecture is checked by a machine, not a human. Code is verified against sources, migrations against the schema, structure against rules. An agent won't break the project by the third feature.

And security by default: a handler won't run without an access rule. Each subscription requires an authenticated user and rules for its channel; a channel for which no rule is written will deny everyone.

Therefore, I have no flaky bugs. Data, server, authorization – all from a single request. Even login via Google and Apple worked the first time. This is not the merit of the neural network, but of the methodology within which it operates.

Out of 658 commits to the framework, 458 were co-authored with Claude – and the code in projects using it is also written by agents. For them, DartWay has three things:

  • Toolkit – 22 skills for an agent: how to add a feature, write a migration, test. Recently, it was reduced threefold: it's also harmful for an agent to read unnecessary things.

  • Law of Synchronicity – API, example, template, documentation, and migration notes change in one PR. Based on these notes, the agent updates projects themselves.

  • Decision Log – every architectural decision is recorded with its reason. The agent reads why it was done this way, rather than guessing.

Conclusion

What's Next

The framework is still 0.x, and I don't hide it. Releases are published in the stable branch, and the project transitions to a new version with a single command dartway update – following those very migration notes. Our live products run on it.

The nearest focus is on autotests: their quantity and accuracy. And the development process itself: fewer code review cycles and fewer tokens per task.

I am concerned not only with the code of the packages but also with the entire application creation process. Therefore, around the framework, I am building DartWay Studio – a ready-made development factory with AI agents. Just like with the framework, I am working through all the product development processes to make application creation simple and transparent. Studio is currently in closed beta.
