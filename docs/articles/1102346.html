What is Claude Code?

The tool's history is shorter than its current scale might suggest. Claude Code appeared on February 24, 2025, as a research preview alongside Claude 3.7 Sonnet – a terminal utility to which engineering tasks were delegated. It read files, executed commands, and corrected code based on the output. The agent was released to the public on May 22, 2025, simultaneously with Claude 4, and over the following months, it gained features that now seem standard: a VS Code extension, checkpoints, Agent SDK, background agents, Opus 4.6 mode with a million-token context window, and headless mode for CI.

By the spring of 2026, it became clear that the terminal was no longer its sole domain. On April 14, Anthropic released a completely redesigned desktop application for Mac and Windows. The main innovation there is a sidebar with sessions instead of a chat list. Internally, it's called Mission Control: developers see all active and recent sessions in one list, filter them by status, project, or environment, and arrange the terminal layout, diffs, and previews by drag-and-drop to suit their workflow. The shift's purpose is that the application was designed for multiple parallel sessions, assuming the human acts as a dispatcher, not an operator.

To establish a baseline: Claude Code exists as a CLI in the terminal, a VS Code and JetBrains extension, a desktop application, and a web session. The core essence is the agent that takes on tasks holistically; the wrapper is secondary. There is no free tier; access starts with a Pro subscription for $20 per month. And, as per the laws of capitalism, Anthropic dictates its pricing and rules, and there's always something to criticize.

At the end of 2026, Routines were added to the suite – cloud procedures on Anthropic's infrastructure. At night, they analyze bugs, find outdated documentation, and react to GitHub events via webhooks. At first glance, it's just automation. But architecturally, it shifts the effort from "pressing buttons" to "configure and forget": now you can actually go have tea while Claude Code fiercely tackles your favorite repository.

Dynamic Workflows and Parallel Sub-Agents

If the desktop application and Routines change where and when Claude Code operates, then dynamic workflows define the very nature of its actions. Formally, it's a JavaScript script that Claude writes for a specific task and which then executes in the background, spawning dozens, or even hundreds if necessary, of sub-agents within a single session. Each sub-agent gets its piece of the work, and the script manages the loop, branching, and intermediate results – unlike regular sub-agents where everything settles in the parent model's context window and can overflow it.

These workflows are tailored for finding bugs in a codebase, security auditing with independent verification, migrating thousands of files, and exploring unfamiliar code. That is, if a task requires not one pass, but several independent attempts with cross-verification, the script runs all variants in parallel. We are wired differently: we try options sequentially and discard them on the fly until we reach a working one.

The most prominent example is Bun, which Jared Sumner rewrote from Zig to Rust. The creator of Bun assembled a dynamic workflow to port the codebase – approximately 750,000 lines of Rust – and completed it in eleven days from the first commit to the merge; 99.8% of existing tests passed. One workflow determined the correct Rust lifetimes for each struct field in the Zig code, another wrote `.rs` files as behaviorally identical ports of `.zig` files, hundreds of agents worked in parallel with two reviewers per file, and then a correction loop ran builds and tests until a clean state was achieved. Sumner estimated that even a team of engineers familiar with the codebase would have taken a year for such a task. He himself didn't expect the approach to work and tested it on a pre-release Claude Fable 5.

To be fair, regressions still appeared after the merge, and Sumner is a professional engineer, not just a casual vibe-coder.

The downside to this power is quite specific and measured in tokens. Anthropic explicitly warns that dynamic workflows can consume significantly more tokens than a regular session and advises starting with a limited task to gauge consumption. Sub-agents eat their share: according to independent measurements, with several parallel agents, the Pro or Max quota can be depleted ten times faster. Anthropic estimates the average daily consumption per developer at around $13, but with five simultaneous agents, the amount easily reaches $50–65.

Access to dynamic workflows requires Claude Code version 2.1.154 or higher and a paid plan; on Pro, they are enabled by a separate line in /config.

What to Do If You Want to Try

If you've decided to try it out – here's what you should know about the key features. Even if Claude Code doesn't work out for you, much of this is applicable to alternatives like OpenCode.

The first step is simple installation. On macOS, Linux, and WSL, it's a single command: curl -fsSL https://claude.ai/install.sh | bash. On Windows via PowerShell, it's irm https://claude.ai/install.ps1 | iex. For package manager enthusiasts, Homebrew and WinGet are available. After installation, check the version with claude --version and run claude in your project directory. On the first run, a browser will open for OAuth authorization; the token will be cached, and you won't need to log in again.

The next step, often skipped (and for good reason), is the /init command. It prompts Claude to scan the repository and generate a CLAUDE.md file: a starting document listing build commands, tests, project conventions, and everything else you would otherwise have to explain to the agent in every session. If the project is complex, go through the generated file manually: remove unnecessary parts, add what Claude couldn't infer from the code – specifics about working with branches, non-standard environment variables, or pitfalls already encountered.

CLAUDE.md, AGENTS.md, and llms.txt: How to Give the Agent Context

CLAUDE.md is more or less clear, but in 2026, there are two more mechanisms that solve the same problem in different ways. And they shouldn't be confused.

AGENTS.md is an open format, essentially a README for AI agents, supported not only by Claude Code but also by Cursor and other tools. It resides in the repository root and contains commands for building, code style, allowed and disallowed patterns. Claude Code reads AGENTS.md starting from version 2.1.277. If a project lacks CLAUDE.md, it automatically uses AGENTS.md instead. The format differs from CLAUDE.md only in its name and what is transferred between agents. If your team has some members using Cursor and others using Claude Code, AGENTS.md eliminates duplicate instructions in two files. Notably, Anthropic resisted this standard for a long time, but in September 2026, they finally learned to read it – first through mods, then integrated into the core.

# AGENTS.md

## Setup commands
- Install deps: `pnpm install`
- Start dev server: `pnpm dev`
- Run tests: `pnpm test`

## Code style
- TypeScript strict mode
- Single quotes, no semicolons
- Use functional patterns where possible

You can also look at other examples, such as AGENTS.md from AIR – a Python web framework advertised as "designed for AI." It contains instructions for working with HTML layouts, minimal application code, routing rules, templating, forms, SSE, databases, common patterns, and dependencies. In essence, it's an excerpt from the developer documentation with notes and code style – something between CONTRIBUTING.md, README.md, and the docs themselves.

llms.txt and llms-full.txt is a standard from Answer.AI, proposed in September 2024 and widely adopted since. llms.txt is an index: a regular markdown file with links to documentation that the agent scans to decide what to read next. llms-full.txt is the full text of the documentation in a single file, downloaded once and kept in context. The logic is simple: agents have token limitations, and it's more efficient for them to read one file than to visit twenty links and parse HTML. Claude Code doesn't automatically pick up these files like CLAUDE.md, but you can place them in the project root and explicitly ask the agent to read them – or connect them via an MCP server like llms-txt-mcp, which indexes the content and returns only relevant fragments. For projects with extensive documentation, this saves context and reduces the chance of the agent inventing non-existent APIs.

# Documentation index for MyLibrary

## Getting started
- https://mylib.dev/docs/installation.md
- https://mylib.dev/docs/quickstart.md

## Core API
- https://mylib.dev/docs/api/client.md
- https://mylib.dev/docs/api/auth.md

## Examples
- https://mylib.dev/docs/examples/basic.md
- https://mylib.dev/docs/examples/advanced.md

How to assemble llms-full.txt? Concatenate all documentation pages into a single file – markdown, rST, or any similar format. The standard helps with both navigation and reading: the agent immediately sees the section map instead of wandering around the site.

It's best to place these files on the documentation website – as done in the django-modern-rest project: https://django-modern-rest.readthedocs.io/llms.txt and https://django-modern-rest.readthedocs.io/llms-full.txt.

Context7: Up-to-Date Documentation Without Hallucinations

The problem Context7 solves is familiar to anyone who has worked with LLMs in code, where the model only knows what was in its training data. If a library was released yesterday or recently updated drastically, Claude hasn't heard of it. Or if it has, the code examples will be from last year's version where the API has already changed. Context7 is an MCP server from Upstash that pulls up-to-date documentation and code examples directly into the agent's prompt.

Connecting to Claude Code is straightforward. The simplest way is to run npx ctx7 setup --claude: the CLI will configure the MCP server, perform OAuth authorization, and install a skill that triggers automatically when you ask about libraries. The second option is a plugin: in Claude Code, run /plugin marketplace add upstash/context7 and /plugin install context7@context7-marketplace, then restart and access it via /mcp. The plugin doesn't require local Node.js and doesn't read API keys from environment variables – authorization is done through the browser. If you need headless mode or CI, manual setup via claude mcp add remains an option.

After installation, you can type "use context7 for Prisma query examples" or simply "use context7," and the agent will fetch the documentation for the relevant library. A nice detail: if you know the library ID, specify it directly – use context7 with /vercel/next.js for app router setup – and this skips the name resolution step. For the first two hours, this is more than enough to understand how much less nonsense the agent generates when it has up-to-date examples in front of it, rather than fragments from its training.

What else have we missed? Don't ask the agent to "write something useful" and don't give it your entire backlog. Take one specific task with precise criteria and conditions, start a session, let the agent work, and – this is important – review the result using git diff. Claude Code can check its own work, but it doesn't replace code review, and you should always spend time looking at where it makes mistakes, where it overcompensates, where it does more than you asked. Even if you're short on time, run a reviewer agent for good measure.

The next level is working with sub-agents. In Claude Code, they are created as markdown files with a YAML header in the .claude/agents/ directory: describe the agent's role, available tools, and operating mode. For the first time, one sub-agent is enough, one that only reads code and prepares reports, without the right to change anything. This reduces the chance that one careless call will break or delete something extra, and at the same time shows how the agent architecture in Claude Code is structured. Then you can create orchestrators, reviewers, testers, and documentation writers.

In the first two hours, it's easy to not notice your weekly limit melting away – especially if you leave Opus as default and start a couple of background processes. Start with Sonnet – you can switch models with the /model command; for routine tasks like "read code, run tests," it's more than sufficient. Run /usage and /context to see where the limit is going: most often, it's consumed by MCP servers with their tool descriptions or background tasks you forgot to close. And don't forget about security; you should limit the agent's access to environment variables and don't give it permission to write outside the working directory without explicit confirmation. Sub-agents, if there's an orchestrator agent, don't need write and file creation permissions – leave only read access. Anthropic explicitly recommends auto mode in the documentation, stating that it re-checks risky actions in advance.
