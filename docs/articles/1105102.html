As I've said, the formula "Agent = LLM + Harness" sounds simple, but it's actually quite accurate. Harness refers to everything involved in making AI work and directly solve tasks, including all the bells and whistles like skills, context, integrations, and multi-agent logic. So, in today's world, if you're going to use AI, do it smartly – and OpenCode can help with that.

Claude Code and Codex set the bar, but they come with different costs for freedom. Claude Code is a proprietary harness tied to Anthropic's models; other models are connected via a gateway at ANTHROPIC_BASE_URL. Codex CLI is LLM-agnostic through its Open Responses API but remains an OpenAI product. OpenCode takes a third position: MIT license, 75+ providers, local models via Ollama or vLLM, and full control over which model acts as the orchestrator, coder, reviewer, or tester.

How to Install, Log In, and Configure

Now, let's move on to installation and configuration. There are a couple of interesting points I encountered myself.

OpenCode is installed globally via npm (or through a VSCode extension, which automatically installs OpenCode). There's a nuance here: the current v2 branch lives under the @opencode/cli package, while the old opencode-ai is now legendary, the 1.x line.

npm i -g @opencode/cli
opencode --version

There are also alternatives: brew install anomalyco/tap/opencode-v2, bun install -g --trust @opencode/cli, or installation via the official script curl -fsSL https://opencode.ai/v2/install | bash.

Now, let's talk about integrating a custom provider, in our case, the OpenAI-compatible gateway BotHub: https://openai.bothub.chat/v1. You can create an API key at this link.

The configuration uses the @ai-sdk/openai-compatible package and the baseURL exactly as specified in the service's documentation. Here's what a minimal example might look like:

{
  "$schema": "https://opencode.ai/config.json",
  "provider": {
    "bothub": {
      "npm": "@ai-sdk/openai-compatible",
      "name": "Bothub Gateway",
      "options": {
        "baseURL": "https://openai.bothub.chat/v1"
      },
      "models": {
        "gpt-6.1-sol": { "name": "GPT-6.1 Sol" },
        "claude-sonnet-5.5": { "name": "Claude Sonnet 5.5" },
        "claude-opus-5.5": { "name": "Claude Opus 5.5" },
        "glm-5.3": { "name": "GLM-5.3" },
        "glm-5.3-flash": { "name": "GLM-5.3 Flash" }
      }
    }
  }
}

The keys are the model IDs for the API (and the list of models is available at this link).

But where do you put the API key? You could put it in the config or via an environment variable, but it's much safer to use the opencode auth login command.

In the list of providers, find your provider (in this case, Bothub Gateway). This way, credentials are not saved in a file or an environment variable.

Now, about a problem I encountered. OpenCode runs on Bun. And Bun's native fetch, to put it mildly, is strange about HTTP_PROXY and HTTPS_PROXY: in some scenarios, it reads them; in others, it ignores them. When installing plugins via npm chains, it might crash with an error fetch() proxy.url must be a non-empty string. The reason is type incompatibility between @npmcli/agent and the node:http polyfill in Bun: the agent returns a URL object, while fetch expects a string. It looks like a bug, and it is.

A separate issue is socks5://. Bun doesn't handle this; it needs the http:// format. And even if you do everything correctly, NO_PROXY with localhost and 127.0.0.1 is mandatory, otherwise the TUI might go through the proxy and get stuck in a loop of its own requests.

So, it's better to remove all proxies or at least convert them to HTTP/HTTPS format. I personally spent a lot of time on this because it works poorly with proxies.

unset HTTP_PROXY HTTPS_PROXY ALL_PROXY NO_PROXY
opencode service restart
opencode

Before building the orchestrator and sub-agents, make sure everything works and requests are being sent.

Primary and Subagent – What's the Difference in Practice

In OpenCode, agents are divided into two types: Primary – this is the one you interact with directly. You open the TUI, select an agent (or it's selected by default), and there it is. Subagent – this is the executor that the primary agent calls itself, through delegation or via @mention. It operates in a child session with its own context, and only returns the result to the main chat.

By the way, OpenCode already comes with four built-in agents: build and plan are primary, while general and explore are sub-agents. They can be overridden, but in our configuration, we're just adding our own without touching the built-in ones. Why not, sometimes the standard build is more convenient than a custom orchestrator.

I was guided mainly by the news. GPT 6.1-Sol is a good orchestrator (not too expensive and smart enough), Gemini 4 Argon as an architect is chosen for the desire to test, and it's also good for research and architecture planning. As a coder – the good old Claude, Claude Sonnet 5.5, the latest at the time of writing. As a reviewer – Opus, because it's expensive but smart. I decided to test GLM-5.3 for vulnerability auditing (I tried not to use the top 1-2 flagship models, but various ones, including open-source ones). For documentation – the cheap GPT-6 Luna. And for tests – GLM-5.3 Flash, even though it's a flash model trained on the main model's responses, I don't need more for tests.

The most important thing is that only the Coder has editing rights. If multiple agents or sub-agents can edit files, chaos ensues: the orchestrator might fix something, the reviewer might rewrite something, and in the end, the diff grows to an indecent size, and it's unclear who exactly made the change. Therefore, in my scheme, edit: allow is only for the coder and docs. The coder is the executor; their job is to write code. The documenter's job is to write documentation. Others either advise or check.

reviewer and security have bash: allow. This sounds a bit strange: can't edit files, but can run commands? But that's the point. The reviewer needs to be able to run a linter, view git diff, and check if tests pass.

Permissions as a Technical Prohibition

An instruction like "don't do git push" can be written in the prompt. The model will likely obey it. But it might not – especially if the task is ambiguously formulated or the context pushes it towards "completing the work." A technical deny cannot be bypassed, and that's its main advantage. Here's how it looks in the config:

"permission": {
  "bash": {
    "*": "ask",
    "git status": "allow",
    "git diff *": "allow",
    "git commit *": "deny",
    "git push *": "deny"
  }
}

Anything not explicitly allowed asks for confirmation. Anything denied is denied at the harness level. It's convenient that rules can be specified precisely, for example, git diff * is allowed, but git commit * is not.

Markdown Agents – An Alternative to JSON

By the way, it's not mandatory to keep all agents in one opencode.json. They can be moved to separate markdown files: .opencode/agents/<name>.md. The filename becomes the agent's name, the YAML frontmatter is the configuration (model, mode, permissions), and the file body is the system prompt. This is convenient when prompts are long and you want to version them separately from general settings. Plus, if you work in a team, such files can be committed to the repository, and everyone will have the same agents.

---
description: Reviews code for quality and best practices
mode: subagent
model: anthropic/claude-sonnet-5-5
temperature: 0.1
tools:
  write: false
  edit: false
  bash: false
---

You are in code review mode. Focus on:

- Code quality and best practices
- Potential bugs and edge cases
- Performance implications
- Security considerations

Provide constructive feedback without making direct changes.

Calling Sub-agents

In my system, the orchestrator receives a task, breaks it down, and calls the required sub-agent via @mention or through the internal delegation mechanism. As a last resort, you can operate sub-agents yourself. In the TUI, it looks like a regular conversation, but a child session with a clean context is launched under the hood. The parent agent only sees the result, which saves tokens and doesn't clutter the main context.

However, not all sub-agents are available for calling from any primary agent. This is regulated in the configuration via permissions at the agent level, but in my current setup, I haven't tightened it – the orchestrator already knows who to call. If needed, you can deny calls to specific sub-agents, but that's fine-tuning for a particular workflow.

Next, it would be logical to talk about how to add skills and MCPs. For now, check that your agents are visible in /agents and that each one responds to a simple query. If something is wrong, it's likely due to the model ID or permissions.

Skills, Commands, MCP, and Plugins

Agents are configured, permissions are granted, you can start. But an agent system isn't an agent system without MCPs and skills. Without them, the structure is straightforward. But it's these components that turn a basic harness into a full-fledged system.

Skills: Instructions Loaded On Demand

Skills in OpenCode (and in AI agents in general) are a way to package a repeatable algorithm or instructions into a separate file and not carry it into the system prompt every time. It works simply: you place SKILL.md in .opencode/skills/<id>/, the agent sees the skill's name and description, and the full text is pulled only when the task actually requires it. Importantly, this saves context – and context is not infinite in agent work.

It looks something like this:

---
name: code-review
description: Sequence for checking a diff before merging
---

1. Examine the changed files and their related calls
2. Check error handling and edge cases
3. Identify potential regressions in dependent code
4. Verify against project conventions
5. Provide criticality-based feedback

The format, at first glance, is simple, again markdown with a prompt. But behind this simplicity lies an important distinction: a skill doesn't have its own tools and permissions; it inherits everything from the agent that called it. That is, if the reviewer is forbidden from editing files, then the code-review skill within it also won't be able to edit files. Furthermore, it allows separating instructions and code style, and the AI agent will take this into account.

Commands: Pre-defined Sequences

Commands are steps you've already performed manually and don't want to repeat. They live in .opencode/commands/ and are invoked via /name. A classic example is /fix-bug: examine the bug → find the code → cause → solution → confirmation → changes → tests → diff. All this is written in one file, and the agent doesn't need to be explained every time the order of operations.

The difference between a command and a skill is that a command is executed explicitly, while a skill is pulled automatically based on its description. Also, a command usually sets a strict order of steps, while a skill is more of a set of rules applied situationally. By the way, both can be versioned along with the project, which sounds reasonable for teamwork.

You can also create them using files in .opencode/commands. For example, you can create a file .opencode/commands/review.md with the following content:

---
description: Review code for correctness
agent: plan
model: anthropic/claude-sonnet-5-5#high
---

Review $ARGUMENTS. Report bugs first.

Commands support argument positioning:

Compare $1 with $2.

Or calling shell commands:

Summarize these commits:

!`git log --oneline -$1`

There is much more functionality; you can read in more detail in the documentation.

MCP: External Tools

MCP servers are a separate story. In my configuration, exactly one is connected, context7, and it's remote:

"mcp": {
  "context7": {
    "type": "remote",
    "url": "https://mcp.context7.com/mcp",
    "enabled": true
  }
}

Why is it needed? Context7 pulls the latest library documentation directly into the agent's context. This is useful when working with a framework that changes faster than your knowledge of it is updated. Local MCP servers (type: "local" with command) are connected similarly, only instead of a URL, you specify the launch command – this is often needed for GitLab, Jira, or internal APIs.

It's worth remembering that MCP is not always the best approach. If the task can be solved with a script or a regular HTTP request, there's no need to bring in MCP just for the sake of a trendy term. It's justified when a structured interface to an external system is specifically needed.

Plugins: Extending the Harness Itself

Plugins are about OpenCode itself. My configuration includes opencode-wakatime, which tracks work time directly from the TUI. It's installed automatically by Bun on startup if listed in "plugin": [...].

Notably, plugins are one of those areas where versions diverge painfully. Plugins written for v1 will not work on v2; they need to be adapted or a v2-compatible alternative must be found.

Building an agent system in OpenCode is an architectural task, not just choosing models, because, as I've said, AI is LLM + Harness. Although, I admit, choosing models is the most enjoyable part of the process. Additionally, it's worth remembering that agent systems are young and constantly evolving.
