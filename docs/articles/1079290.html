Let's go! My name is Prokhor, and I lead the 'Explore' agent team – a deep research mode in Alice AI chat.

Let me remind you what we're talking about, in case you've never used Deep Research: it's a special operating mode that creates a unique plan to solve a user's task, performs hundreds of searches based on your query, can visit websites (even with dynamic JavaScript content), write and execute Python code (for complex calculations), work with downloaded files, and so on. All this is to provide the best answer to your complex queries, for example: 'Plan a two-week trip to Dagestan for me by car with children.'

Over the past year, the agent has gone from its first prototype to production – along with it, the quality of responses, operating speed, and GPU consumption have changed. Ruslan Iliev, the agent's product manager, was responsible for the product side: he formulated the product goals, defined the set of tools and validation queries, and then led the launch from a closed waitlist to 100% production. How we got here – through a discarded prototype, dozens of wrapper layers, and a couple of painful lessons – I will tell you in order. Welcome!

From Search in Reasoning to a Full-Fledged Agent

The 'Explore' agent didn't appear immediately: it all started with an attempt to teach the 'Reasoning' mode to work with fresh data from the internet. Simple search gradually turned into a full-fledged agent cycle – with tools, its own strategy, and infrastructure for long queries. Let's break down this path step by step.

Reasoning + Search

It all began in the spring of 2025, after the release of DeepSeek-R1 and the general boom in reasoning models. At that time, I was tech-leading the rollout of the 'Reasoning' mode in Alice AI, and the question arose: how to add search results to it for queries requiring fresh data from the web?

As a result, we created a simple RAG pipeline with multi-query search, where the LLM itself generated the queries. Despite the simplicity of the solution, users loved this mode for the quality of answers to complex questions. After the first success, we decided to go further.

Agents! Agents!

A couple of months later, the hype around agents began. I remember walking around the booths at ICLR, and everyone was talking about them. We already had our first successful experience, so it was time to create a full-fledged Deep Research – we called it the 'Explore Mode'.

The timing was super opportune: Alice AI was just starting a major infrastructure build-out for ATS (Agent Transport System) and Agent SDK (Python, Go, C++...). And our mode is a classic agent, because it involves multi-turn query execution. An answer can take minutes (the first version took 30 minutes or more to respond).

If you're wondering why a separate infrastructure for agents was needed, it's simple. We needed a guarantee of execution for long queries with hundreds of tool-calls, tracing, logging, scaling, alerts, and all that we're accustomed to for regular Alice AI queries. Colleagues have already written about ATS on Habr.

The team was short on people, and we, of course, wanted to move fast. So, we agreed not to train large LLMs until we hit their quality or performance limits. We focused on developing wrappers around LLMs, context engineering, and auxiliary models.

Interestingly, the founder of Manus later arrived at the exact same conclusion: 'I was training models from scratch for information extraction and semantic search. Then GPT-3 and FLAN-T5 appeared – and my models instantly became obsolete.'

We assembled the first prototype based on the CodeAgent approach: the model calls tools by generating Python code. The metrics were immediately decent: FRAMES – 75, SimpleQA – 81, GAIA – 26 (low on GAIA because the agent couldn't work with files then). But we rejoiced for a short time.

First Big Fail: We Discard the Prototype Entirely

The problem emerged when we started thinking about how to bring CodeAgent to production. The code generated by the model needs to be executed in an isolated sandbox. At the same time, we really wanted the sandbox to have internet access, for example, to use open APIs. This means it would have to live outside the internal network. All the agent's tools, on the other hand, live inside the network. In short, it turns out we would have to implement tool-call forwarding from the external network to the internal one. Doesn't sound safe.

And then we got lucky: at the end of July 2025, an open-source model with truly good function calling was released. Two weeks later – and the agent was rewritten to a classic function calling loop. Another week – and the CodeAgent metrics were surpassed. The infrastructure was simplified many times over, and security audits ceased to be a pain. The first architecture was thrown away, and we never regretted it.

Harness and Scaffolding

Everyone is writing about DeepResearch agents now, and almost everyone is talking about the same thing – about the harness. Our colleagues from Yandex have already described how they built a DeepResearch agent using corporate data and codebase, and recently colleagues from Sberbank released a detailed analysis of their pipeline.

We solved the same problem from a different angle. If colleagues moved 'agentness' into a managed pipeline, we went the route of a classic agent with tool-calls: the model itself holds the strategy, and around it are dozens of wrapper layers. And each layer appeared not out of love for beautiful architectures, but out of a very specific pain. But first, let's talk about terms.

A decent model with a great harness beats a great model with a bad harness.

Eddie Osmani, Google Cloud AI (Agent Harness Engineering)

Harness (wrapper) is everything that turns a 'bare' LLM into an agent: orchestration, tool-use loop, context and memory management, retries, verification, sandbox, observability.

Nearby is the word scaffolding – 'construction scaffolding': prompt templates, tool schemas, pre-defined steps.

The terms are often mixed up. For us, it's convenient this way: scaffolding is the defined structure (design-time), harness is the execution engine (runtime).

What We Got in the End: Agent Architecture

So, after moving to function calling, the agent began to grow wrappers. At its core is the same classic agent cycle: the model calls tools until it decides that the research is complete. The strategy is also held by the model itself: it builds a plan, updates it as it goes, and decides where to dig next.

Adding Wrappers and Learning to Cut Them

Let's look at a few cases for clarity.

Case 1. One wrapper over search → +9 pp on BrowseComp. Raw search returns ten snippets of ~500 tokens each. A good half of them are garbage that overloads the context and leads the model astray. We placed a relevance classifier between the search and the model: each snippet gets a 'yes', 'partial', or 'no' verdict. Only relevant ones are included in the context.

Case 2. Files and multimodality → +8.5 pp on GAIA. We taught the agent to work with PDF, CSV, XLSX, and images: a code sandbox for tables, VLM for images, RAG for large documents. Of course, growth is expected for a benchmark with files, but the point is that a wrapper for working with files is still needed, and the quality of work with them largely depends on it.

Case 3. Advanced reasoning tool. We created a separate reasoner tool. It added +5 pp to our benchmarks, but with the release of newer models, it started to interfere – we got rid of it. It turned out this isn't just our private pain, but a pattern that already has a name:

99% of the work is done by the model itself. We don't need a complex framework around it.

Browser Use, The Bitter Lesson of Agent Frameworks

This is a reference to Richard Sutton's Bitter Lesson: methods that scale with computation eventually win over manual add-ons. Each wrapper component is essentially a patch for the current model limitation. With a new release, this assumption becomes obsolete. Therefore, the consensus among practitioners (Anthropic, Cognition, Browser Use, Ramp) sounds unexpected: the harness should not only be expanded but also regularly trimmed, re-measuring the benefit of each component with each model release.

Infrastructure: An Agent That Thinks for Ten Minutes

Our agent became the first Alice AI mode that can think about an answer for several minutes. Sometimes more than ten. During this time, anything can happen: the user closes the tab and goes for coffee (and will look at the result from their phone), sockets break, services are deployed, something temporarily fails.

Now for some math. One research task involves hundreds of tool and service calls, and each of them sometimes fails. Every tenth user would wait ten minutes and leave with nothing. Frankly, not a great product.

The solution is to add checkpoints. Remember the guarantee of executing long queries for which ATS was built? Here it is in action! The agent's state is saved after each tool call: if the pod crashes for maintenance during the fifteenth minute of research – it's not a problem, progress is not lost, the agent wakes up on another pod and continues from the same point.

Does it work? We tested it rigorously: 11 production experiments with pod shutdowns. Nevertheless, the main exam happened on its own – and we passed it successfully.

The Main Exam: Victory Day

May 8, 2026, Friday, 10:00 AM. We are in our Moscow office. Anxiety on our faces: production is almost down, we urgently need an additional 50 GPU cards because about 100,000 people have started using the 'Explore' agent, and the GPUs were designed for a much lower load.

By May 9th, we launched a promotion: the 'Explore' agent helps find information about relatives who participated in the Great Patriotic War in open archives. A person writes down what little they know: name, year of birth, a snippet of family history. The agent accesses open archives – OBD 'Memorial', 'Podvig Naroda', 'Pamyat Naroda' – matches documents, and in a few minutes compiles a biographical summary: combat path, awards, service location. Manual search takes hours.

The announcement was made in advance, and people started using it even before the holiday itself. We expected a surge. But not like this. We sit in the meeting room, there are no GPUs to get. Pasha, the lead of a neighboring team, saved us: 'We can give up 100 cards from the functional model, but for one day.' As a result, we took about half – this was enough to handle the load.

People found their relatives. It seemed to be the most meaningful day of the agent's work.

And then began the long journey of improving the harness with the goal of optimizing GPU consumption.

Harness is Also Money

The wrapper is not just about quality, but also about money. Every token in the context and every extra model call is GPU time, which means it affects the number of users we can serve on the existing hardware. Here's what we did:

  • search snippet processing was handed over to a trained classifier instead of an LLM;

  • we call tools only when it genuinely advances the research;

  • plan generation was moved to a lighter model without loss of quality.

As a result, the cost per query decreased by 6.6 times in three months.

More users – faster responses with the same quality.

What's Next

If we try to formulate the main lesson of this year, it is this: the harness decides, but it also becomes obsolete the fastest.

Models are released every couple of months, and each release devalues part of the wrapper (hello, reasoner tool). Re-measuring and reconfiguring dozens of components manually for each new model takes weeks of work. Therefore, our next big step is auto-adaptation of the harness: new model as input → auto-selection of prompts and wrapper → auto-measurement on benchmarks → rollout. We want model switching to be a pipeline, not a month of manual reconfiguration.

And of course, we continue to improve the quality and speed of the agent itself. Where to grow is clearly visible in the benchmark graph above.

And here's what I suggest you take away from this article:

  1. Before blaming the model, check the harness; the leverage is there. Our cases provide +5 to +9 pp per component.

  2. Harness is not only about quality but also about economics. The cheaper the wrapper, the more users on the same GPUs.

  3. Models change, and the harness changes with them. Therefore, it's better to keep the harness simple so that at each release, the benefit of each component can be re-measured and outdated parts can be cut.
