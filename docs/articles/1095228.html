My voice AI administrator, Aika, already had a voice, a conversation script, and a working page. It lacked a face. I wanted to add one while keeping Yandex Realtime: let the new service receive the finished audio and sync lips to it.

I tried Simli and Anam. The face appeared, but along with it, I had to deal with the pause before the response, starting video on iPhone, and mobile internet. And with the second character, Eva, it turned out that the portrait's persuasiveness depends not only on the face but also on what's behind it.

Claude Code wrote the code, and Codex generated some appearance options based on my technical specifications. The solutions, selection, and live phone testing were mine.

At the end of September, Google showcased Gemini Live with an avatar — Habr already has a review of this approach. My task was different: the voice engine was already working, and I didn't want to switch from it just for a face.

What was the input

Aika talks to website visitors directly in the browser. The browser maintains a WebSocket connection with our FastAPI server, and the server maintains a session with Yandex Realtime. This is a "speech-to-speech" interface: I don't need to separately assemble a chain of recognition, text model, and synthesis.

I discussed why Yandex instead of OpenAI in my previous article. For this story, one thing is important: the server sends audio to the browser in chunks of PCM16 at 24 kHz, as pcm_chunk events. PCM16 is uncompressed audio where each sample takes 16 bits. In normal voice mode, the browser plays it.

The task: add a face that syncs its lips to this audio while the response is still being received.

A face given someone else's voice

I didn't need a new pipeline of recognition, language model, and synthesis. I only needed face animation. Both services I tried have such a mode: you provide your audio, the service renders a face to it and returns audio and video via WebRTC — a real-time media transmission technology.

The response is still generated and voiced by Yandex. The avatar service is responsible for the visuals and their synchronization with the audio.

The first technical detail is the frequency. Yandex, in my configuration, provides 24 kHz. Simli needs 16 kHz, and for Anam, I used the same format as in their JavaScript example. Anam's frequency is set by a parameter: 16 kHz here is our integration's choice, not a universal service limitation.

Audio arrives in chunks — pieces of varying lengths. If you start resampling from scratch with each chunk, the result depends on where the boundary falls. Therefore, the fractional position and the last sample are carried over to the next chunk. In this example, AVATAR_RATE is 16000:

const resampler = {
  pos: 0, prev: 0,
  reset() { this.pos = 0; this.prev = 0; },
  run(int16, inRate) {
    const n = int16.length;
    if (!n) return new Int16Array(0);
    const step = inRate / AVATAR_RATE;
    const out = new Int16Array(Math.ceil((n - this.pos) / step) + 1);
    let p = this.pos, k = 0;
    while (p < n - 1) {
      const i = Math.floor(p), f = p - i;
      const a = i < 0 ? this.prev : int16[i];
      out[k++] = Math.round(a + (int16[i + 1] - a) * f);
      p += step;
    }
    this.pos = p - n;
    this.prev = int16[n - 1];
    return out.subarray(0, k);
  },
};

Verification: the same signal was processed entirely and then cut into pieces of random length. The maximum difference was zero.

This only confirms that chunk boundaries don't change the result. The quality of resampling itself is a separate issue: there's no proper filter before downsampling here, so components above 8 kHz can cause distortions in the remaining range. The seam problem was thus closed, and there's still room for improvement in resampling quality.

The service key does not reach the browser. The page requests a short-lived session token from our server via POST /voice/avatar-session. The server checks the origin — the source of the request — and limits issuance: 6 tokens per hour per IP and 30 per hour in total.

If obtaining a token or starting video fails, the page reverts to voice mode. Eight seconds are allocated for the token request, and fifteen for the SDK launch call. An important detail: a successful SDK launch doesn't mean the first frame has appeared yet. In hidden video mode, a line with the error reason is displayed, and the voice call continues. The face here is a decoration, not a condition for conversation.

Anam has two more important commands. After sending the last audio fragment of a remark, call endSequence(). When interrupted, call interruptPersona() and the same endSequence(): the first stops the avatar's current speech, the second closes the input audio sequence. The end of audio transmission doesn't mean the avatar has finished playing it.

Simli vs. Anam

I compared what I could launch on my accounts: Simli's previous generation face and Anam Cara-4. This is a service choice for my task, not a comparison of the best models from both manufacturers.

Creating a Simli next-generation face in my account returned a 403 with a message about the GS Faces limit, so the face was created via the previous generation endpoint. For both services, we used the same source portrait, the same voice, and the same page.

I almost compared apples and oranges regarding connection speed. In one Simli run, the first frame was captured approximately 11 seconds after the "Connecting to video..." status. For Anam, the status changed after 0.9 seconds, but the image only appeared in the logs after 2.7 seconds. Looking at the status, it seems one speed, but looking at the frame, it's another. Therefore, there's no common "connection time" row in the table: I didn't conduct identical measurement series until the first frame.
