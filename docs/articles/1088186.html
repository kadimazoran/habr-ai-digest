BB is an open-source MIT-licensed program where Claude Code, Codex, Pi, and ACP agents work in a single window. In 7 months, the repository has gathered about 4,000 stars. The key feature of BB isn't the window itself, but how its interface is extended by plugins, with new plugins being recognized without restarting the program.

Recently, I made a video about BB. In it, an agent, using just 20 minutes and two prompts, created a plugin that transcribes call recordings, extracts agreements with deadlines, and drafts a client email. The video focused on the user benefits, while this article will dive into the code to explain how it all works. Everything below is verified against the get-bb/bb repository as of late September 2026.

The idea behind BB is based on two layers. At the bottom are the agents you already have, each running in its own environment with its own tools and settings. At the top is a single window that communicates with them. To understand how one window manages different agents, let's start by looking at what processes are launched.

The Server Stores, the Daemon Executes

The command npx bb-app launches the launcher, which then starts two Node processes: server and host-daemon. The server is written in Hono, listens on 127.0.0.1:38886 by default, and stores all state in SQLite, in the file ~/.bb/bb.db. The daemon manages the machine's primitives, such as files, git, terminals, and agent execution. The desktop application built with Electron is merely a shell that launches the same bb-app and displays the server's web interface.

The direction of communication is noteworthy. It's not the server that reaches out to the daemon; instead, the daemon itself opens a WebSocket connection to the server and receives commands like turn.submit. This allows a second machine to connect to BB without open ports: a one-liner curl .../install.sh is generated in the settings, which installs the daemon as a launchd or systemd service, and the daemon receives its machine key. The server, in this context, is a role rather than a separate computer, and the same daemon runs on the server machine as on the others.

Since the daemon and server don't always update simultaneously, the protocol between them is versioned. Currently, the contract specifies HOST_DAEMON_PROTOCOL_VERSION = 220. If the versions diverge, the daemon automatically downloads the appropriate build, verifies its SHA-256, and restarts. This is important for the second machine, as it eliminates the need for manual updates after every server release.

A server can have multiple clients: a React 19 web interface, an Electron window, the bb CLI, an SDK, and an Expo mobile app. They all communicate with the same /api/v1 endpoint, so a thread started in the browser can be continued from a phone or terminal. Let's explore how agent responses reach all of them.

The thread is stored as a log: the events table is append-only, and each event has a sequence number within the thread. When the daemon sends a new batch of events, the server inserts them and broadcasts a changed notification via WebSocket. The WebSocket itself doesn't contain the data; instead, the client marks its interface state as stale and fetches the timeline via HTTP. This "notify, then fetch" pattern is simpler than streaming because the client doesn't maintain its own copy of the thread, which could diverge from the server's.

Its Own Protocol, and ACP is Just a Dialect

To ensure that events in the log appear consistently, BB must communicate with agents that have vastly different interfaces. For this, it employs its own provider bridge protocol. The daemon launches a separate bridge process for each agent and communicates with it via JSON-RPC 2.0 over standard input and output. The bridge is part of the provider plugin, which the daemon downloads from the server and verifies the hash of before launching.

I expected BB to be built on top of ACP, the Agent Client Protocol from Zed, but that's not the case. ACP in BB is just one of the dialects that the bridges translate into BB's native protocol. The table below shows how each agent is launched:

Normalization occurs in two steps. First, the bridge translates the agent's native stream into a small set of events: open turn, open element, append text, close element, report token consumption. Then, the assembler within the daemon assigns identifiers to turns and elements, manages their lifecycle, and stitches together token streams into 100ms chunks. The protocol documentation summarizes this separation with a single phrase: "the bridge knows the dialect, the runtime knows the timeline."

The bridge provides the signature and icon for each element, so the core doesn't need to maintain tables of tool names for Claude or Codex. A new agent can be added without modifying the core or the interface.

BB also doesn't impose a single model for permissions. During the handshake, the bridge reports the approvalEnforcedBy field. For Claude Code, this is set to provider, meaning Claude's own permission engine makes the decisions, and BB integrates via the canUseTool callback. For Codex, Pi, and ACP agents, it's set to runtime, indicating that BB itself enforces the policy. Anything not resolved by the policy is presented to the user as a uniform request, regardless of which agent initiated it.

Skills are managed similarly. The daemon collects all skills into a single directory and passes it to the bridge via the skills/configure command. The bridge then translates these skills into the agent's native language. For Claude Code, a Claude plugin is dynamically generated with a symlink to the skills directory. Codex receives skills/extraRoots/set, Pi gets the --skill flag, and ACP agents have the list of skills with their paths appended to the instructions. Consequently, a skill added once to BB is visible to any agent.

Environment plugins determine where an agent actually runs. The built-in git-worktree creates a separate worktree for each thread, while project-checkout operates directly within the project's checkout directory and prevents branch changes if there are uncommitted modifications. The most interesting option is modal-sandbox, which registers not a directory but an entire machine. BB launches a Modal sandbox, installs its daemon there, and then interacts with it as if it were any other computer.

I particularly liked how this layer is tested. The repository contains recorded sessions of real agents performing scenarios like approval, interruption, and compaction. The command pnpm parity replays these sessions through bridges of old and new code versions and compares the timeline output line by line.
