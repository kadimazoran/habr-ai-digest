Where It All Began

My name is Sergey Ladygin, and I'm a developer.

Claude Code announced the Agent Teams feature. One session becomes the team lead, assigning tasks and collecting results. The other agents are teammates, separate Claude Code sessions, each with its own context. They pick tasks from a shared list where tasks have dependencies, and they communicate directly with each other.

The feature is enabled by the environment variable CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1.

I also had a personal pain point: retrospectives in my teams were inefficient. I decided to try building my own service and, at the same time, create a system where agents could work like a full development team. Thus, in March 2026, I began developing a service for team retrospectives – Scruma, which I'll refer to as the "project" from now on. The stack is standard: Go, Next.js, PostgreSQL, Docker.

First, Claude and I put together a comprehensive technical specification: how I envisioned such a service, its capabilities, and its screens. Then, we broke down the spec into tasks, and I ran one task at a time in a single session. At this stage, we finalized the stack, architecture, and rules.

Claude delivered results so quickly that I couldn't keep up with reviewing and accepting them. Eventually, I realized that I myself was the bottleneck in this process.

Then we thought about how to make it so that it could check results itself and write tests for them. This is how QA emerged: it checked tasks in the browser, described test cases, and wrote tests for them. For tests, Playwright has ready-made agents – Playwright Test Agents: a planner, a generator, and a healer. Along with QA, DevOps appeared – to make changes to the environment and rebuild it. And also a high-quality local environment where the entire functionality can be tested.

This is how I built an autonomous process from task assignment to working implementation.

/weekly - once a week. I run it on Mondays. The analyst role reads the strategy, the hypothesis backlog, and the previous report. It collects metrics: attendance, database views, errors for the week. It compares what was promised a week ago with the actual outcome and writes a report. Then it shows me a summary with suggestions and stops: it doesn't launch anything or spend anything without my response. The analyst records the reason for rejection and considers it in future suggestions. After my response, it updates the backlog and suggests running executors on approved tasks. Next week, the subsequent /weekly will check if the task yielded the promised effect.

/implement - for each task. This is launched for an approved product task. The session begins with the tech lead role: it breaks the task into subtasks and manages it through the roles – architect, backend and frontend, DevOps, QA, documentation. At the end, the tech lead commits, followed by PR and CI. All I have to do is accept the result and release the version. This path is detailed below.

These are the two points where I make decisions: in /weekly I approve the plan, and after /implement I accept the result. Everything in between is handled by the roles.

After several iterations, I went even further: now /weekly, after approving the plan, automatically launches /implement for each task. This means several development teams are working on the project simultaneously, each with its own task and set of roles. The output from each team is a PR.

For specific cases, there are additional teams. /bugfix is a short pipeline for defects: tech lead, developer, DevOps, QA verification. /triage is the product on-duty agent: it analyzes errors from Sentry and logs and suggests what to fix. /marketing handles promotional texts and measures their effectiveness.

The most useful part of this table is the right column. Agent roles work best when prohibitions are formulated more strictly than responsibilities. A QA engineer who fixes issues themselves stops finding them: bugs are fixed silently and don't make it into the registry.

However, a prohibition stated in text doesn't always work. The tech lead's prompt explicitly states: "You must not implement tasks yourself or write code; you must decompose tasks for teammates and monitor their execution." At the end of March, I gave them a small task, and they decided it would be faster to do it themselves. They did it – worse than a frontend developer would have.

The skeleton of a role prompt looks something like this (highly simplified):

You are the QA engineer for the <project name> project. 1. Verify changed files against the spec and solution. 2. Static checks: go vet, go test, tsc, lint. 3. Browser: ONLY changed functionality, screenshots in testing/screenshots/. 4. Integration tests for affected modules. ## What is forbidden - Do not fix bugs yourself. If you find one, describe it in testing/bugs/, one file per bug. - Do not test the entire service: there is a separate team for that. ## Report What passed, what needs fixing (file and line number), test case statistics.

The real file is 119 lines long, but the structure is the same: context, order, prohibitions, report format. Order and prohibitions are the most critical parts.

The Journey of a Single Task

Tech Lead Decomposes. Reads the spec, asks me questions, breaks the task into subtasks, creates a team and a task list with blocked_by dependencies. Does not write a single line themselves.

Architect Writes the Solution. An ADR file in docs/decisions/: what endpoints, what migrations, what WebSocket messages, what components. Then distributes the specification to backend and frontend. For a trivial task without new APIs, the architect can be skipped. Backend or frontend can be skipped if the task doesn't touch that layer. DevOps, QA, and documentation – never.

Backend and Frontend Work in Parallel. Each in their own file area. Each concludes with a "Test Impact" block: which test plans were changed, which test modules need to be run, which scenarios are under suspicion.

Control Point. Without the "Test Impact" block, the tech lead does not pass the task further but returns it to the developer. This inexpensive rule has saved the most time: QA runs tests only on affected modules, not the entire regression suite.

DevOps Rebuilds the Environment. docker compose up -d --build, checks logs and service health, notifies QA "environment is ready".

QA Verifies. Compares the result against the spec and solution, runs static checks, uses Playwright MCP in the browser to test only the changed parts, runs integration tests for affected modules. If tests fail due to changed behavior, the sub-agent healer fixes them. If new functionality is added, the planner updates the plan, and the generator writes new tests. Finally, QA updates test cases and the coverage map.

Documentation. README, project map, API statuses.

Tech Lead Collects the Result and Commits. Then PR, CI (vet, tests, types, linter, trial image build), tag, release.

A Week Later. The on-duty agent monitors production, the analyst compares the hypothesis with the facts.

All of this is recorded in the tech lead's prompt – the /implement command. The skeleton looks like this (highly simplified):

You are the tech lead for the <project name> project. You must not implement tasks yourself or write code; you must decompose tasks for teammates and monitor their execution. Task: $ARGUMENTS ## Instructions 1. Decompose the task into subtasks with dependencies. 2. Create an agent team and a task list with dependencies (blocked_by). 3. Migrations, handlers, services, tests, Test Impact block. - frontend: awaits spec. The real file is 100 lines long. The main part is the block about the mandatory pipeline: three stages must never be skipped – DevOps, QA, and documentation. The block is in caps; I've only moved lines:

NEVER skip pipeline stages. Even if the task affects only frontend or only backend – the full cycle is mandatory: Development → DevOps (rebuild) → QA (browser testing) → Docs - DevOps ALWAYS runs after development completion (backend and/or frontend) – without a rebuild, QA cannot test in the browser - QA ALWAYS performs browser testing via Playwright MCP – this is not optional - Docs ALWAYS checks and updates documentation

The caps appeared after a mistake. In March, after implementation, the tech lead forgot to pass the task to DevOps. QA opened the browser, saw the old version, and returned the task with the words "nothing done." I had a one-on-one with the tech lead, and they corrected their prompt themselves.

Code Review: Built into the Process

There is no separate code review stage in this pipeline, and this is a conscious decision. I believe that reviews should be integrated into the development process itself: defining the architecture to follow in advance and setting limitations. This avoids the loop of "write code → review → fix → review again," which otherwise repeats several times per task.

Classic code review is designed for human-written code and has two goals. The first is control: not everyone in the team is equally experienced. The second is knowledge dissemination: through reviews, the team learns how things are conventionally done and why something is done a certain way. With agents, both goals are achieved differently.

Control – Before the Code. The architect defines interfaces and contracts before others start working. Prohibitions are recorded in each role's prompt. For the frontend, for example: "No hardcoded colors, spacing, radii, shadows, font sizes. Any HEX/rgba in component code = error." In a regular review, this comment would have to be written over and over again.

Verification – Automatically. Some rules are enforced by tests: violate them, and the build fails. CI on PR runs go vet, tests, type checking, linter, and trial image builds. QA verifies the result against the spec and solution, not arguing about style.

Knowledge – in Files. A review comment to an agent is useless: they won't remember it for the next task. Therefore, what is conveyed in a human team through reviews is recorded by me in ADRs and "pitfalls." The agent reads them before making changes.

My method of verification has also changed. I read diffs less often now, but I always read ADRs before merging. Verifying the solution is more important to me than verifying every line.

Knowledge Layer: What Lies Beside the Code

An agent doesn't remember past tasks, so the team's memory resides in files. I adhere to the GitOps approach: everything that can be described in code is described in code and stored in git. Besides the application, this includes infrastructure, monitoring, alerts, and dashboards. With agents, this provides a multiplicative boost. The agent can see the entire system, from code to alerts. It changes any setting the same way it changes code: edit in a branch, PR, CI, release by tag. Everything that has changed remains in the git history, and the next agent can read it.

Here's what's in the repository besides the application code.

  • Spec – the vision. Read by the tech lead and architect. It is not a source of facts about the product.

  • ADR – memory of decisions: what was decided, which options were rejected and why. Written by the architect; any agent reads it before making changes; I read it before merging.

  • Pitfall Map – a folder with failure diagnoses, verbatim: what the failure looks like, how it differs from similar ones, why it cannot be "simplified back." The root project file contains a table: "feature, file, main thing that breaks."

  • Feature and Coverage Map – a table: screen, functionality, covered by which test, which solution. Each row indicates which role updates it.

  • Test Cases and Test Plans – one file per case, sequential numbering. Plans by module – input for the test generator.

  • Strategy, Hypothesis Backlog, Weekly Reports – the basis of the weekly cycle. The strategy explicitly states: "The strategy lives in files, not in agents' memory: decisions not recorded here or in backlog.md do not exist for the next cycle."

  • Infrastructure Configuration – compose files for local and production stacks, gateway and proxy configs. During a tagged release, CI copies them to the server along with the new code version.

  • Monitoring Configuration – telemetry collector, logs, traces configs, and alert rules. An alert is a file in the repository, not a checkbox in the interface.

  • Grafana Reports – dashboards described in JSON: technical service status and business metrics. The analyst collects the weekly report from business dashboards.

Where to Start

The most frequent question after my posts about agents is "Where do I start?" I'll answer with the repository structure, because the process lives in it, not in people's heads or prompts.

Everything is in one repository. An agent sees only what is located next to the code. Wiki, task tracker, browser dashboard, Miro diagram – these do not exist for it. Therefore, everything is in my repository: code, tests, documentation, tasks and hypotheses, database schema as migrations, deployment and service configs, dashboards and alert rules as files, MCP connections to the browser, error tracker, and metrics, and everything needed to run the project locally with a single command. There are no secrets in the repository: environment variable examples are in .env.example, actual values are substituted in CI/CD.

How it's organized. Simplified, without details:

CLAUDE.md / AGENTS.md    Project map: stack, structure, conventions, pitfall map. .claude/commands/        Roles as slash commands, one file per role. .claude/agents/          Test sub-agents: planner, generator, healer. .mcp.json                Agent connections: browser, errors, metrics (tokens from env). backend/                 Service, migrations = DB schema, unit tests. frontend/                Application. configs/                 Gateway, email templates, Grafana (dashboards, alerts), telemetry. docs/spec.md             Spec - the vision. docs/decisions/          ADRs, one file per decision. docs/dev/                Pitfalls, one file per feature. docs/features.md         Feature and test coverage map. docs/api/                Endpoint contracts and their statuses. docs/runbook/            How to start the server, restore backup, configure email. docs/business/           Strategy, hypothesis backlog, weekly reports. specs/                   Module test plans, input for test generator. testing/                 Module integration tests, test-cases/, bugs/, screenshots/. .github/workflows/       CI on PR, release by tag, landing page deploy. docker-compose*.yml      Local stack, production, corporate edition. Taskfile.yml             task up / build / test-integration-<module> / check. .env.example             All variables with comments, no values.

Document Formats. The formats are simple, and agents maintain them more accurately than humans.

Feature map – a table by screen:

| Functionality         | Test                        | Document            | |-----------------------|-----------------------------|---------------------| | Registration by email | ✅ auth/registration.spec.ts | ADR on authorization | | Password change       | ❌                          | ADR on password change |

ADR – one decision, one file, must include rejected options:

# NNN. Decision Title ## Status: accepted / superseded by decision NNN ## Context: what problem are we solving, what is being removed from the live system. ## Decision: what we are doing - API contracts, migrations, messages. ## Alternatives: what was considered and why it was rejected. ## Consequences: what changes, how it is verified. ## Test Impact: which test plans and modules are affected.

Backlog task – a hypothesis with expected effect and status, which is not closed as "done" until the effect is compared with the fact:

| ID    | Hypothesis               | Expected Effect     | Confidence | Status               | |-------|--------------------------|---------------------|------------|----------------------| | B-001 | Guide for frequent query  | +N search entries   | medium     | done, awaiting measurement |

Test case – one file, sequential numbering, status changed by QA:

# TC-001: Email Registration Module: auth · Priority: critical · Status: pass ## Preconditions ## Steps ## Expected Result ## Actual Result

Monorepo or Multiple Repos. For a project of my size, a monorepo is suitable: backend, frontend, landing page, configs, and documents in one place; the agent sees everything from a single root. If the project is large and services live in their own repositories, a meta-repository works: it contains rules, roles, documents, and the map, while service repositories are placed alongside. The principle is the same: the agent has one root from which everything is visible.

Local Launch is Mandatory. task up starts the entire stack: database, email mock, gateway, monitoring. The QA role and integration tests run on it. If the project cannot be launched locally with a single command, the QA role cannot verify anything, and the entire pipeline reduces to "code written."

Order of Implementation. If starting from scratch, I would proceed as follows:

  1. Project map and spec – before the first commit.

  2. Two to three roles as file-commands and a mandatory stage order.

  3. Browser-based QA and integration tests as a transition condition, with a report on test impact from the developer.

  4. ADRs and pitfalls as mandatory output for each task.

  5. Weekly cycle with plan approval and a product on-duty agent.

None of these steps require a specific model or tool. My roles have moved between Claude Code and Codex with minimal edits because they live in ordinary markdown files.

Conclusion

If I had to distill it down to one takeaway: the process for agents is about roles with prohibitions, two decision points for humans, and memory stored in files. Everything else is detail.

  • Prohibitions work better than responsibilities: "don't write code," "don't fix," "don't touch the environment."

  • Verification is built into the pipeline as a transition condition. A developer doesn't hand off a task without a test impact report; QA doesn't take a task without a rebuilt environment.

  • Code review is integrated into the process: architecture and constraints are defined before coding, so there's no "write – get feedback – fix" loop.

  • Memory resides in files: decisions, pitfalls, coverage map. Without it, agents repeat old mistakes.

If you're building a project with agents and after a couple of months it starts repeating old mistakes, begin with prohibitions and mandatory stages – it's the cheapest fix. If you're a team lead of a human team and thinking about integrating agents, start with the project map and ADRs: they will be just as useful for humans.
