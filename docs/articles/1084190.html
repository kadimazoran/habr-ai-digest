Here, I want to look at the same problem more broadly. If the model itself is forbidden from writing, does that mean the entire AI system truly cannot change the CRM?

For a CTO, product owner, or security lead, this is a very practical question. The statement "the model operates in read-only" might appear in an architectural description, security review, client questionnaire, or a decision about production launch. But for such a decision, something else is more important: which component of the entire execution chain is actually capable of causing an external consequence—and what limits it immediately before the action?

This is precisely what I tested in a laboratory workflow using n8n + DeepSeek + HubSpot.

DeepSeek did not have HubSpot credentials and could not perform a write directly. However, the write credential remained with the next n8n node. In a control scenario, the initial request pertained to one synthetic deal, while the structured proposal pertained to another. The downstream path executed a PATCH, and the CRM was indeed changed.

The main conclusion turned out to be simple:

Model permissions are not the same as system permissions.

This class of problem is not new in itself: in classic security logic, it's close to confused deputy. My goal was not to re-state a known risk but to see how it manifests in a modern agentic execution chain and what exactly changes the outcome.

Where the Write Actually Resided

At the model level, the restriction was real: it could not access HubSpot directly.

However, the ability to change the CRM belonged not to the model but to the downstream orchestrator. If it accepts the proposal parameters and executes them without separate verification, the system as a whole remains capable of writing.

Architecture B and Architecture C. Limiting the model's permissions does not, by itself, eliminate the system's write capability. The outcome changes when control appears at the execution boundary.

Therefore, the question "what is the model allowed to do?" is useful but insufficient. For a launch decision, the following is more important:

Which component is capable of causing a real consequence—and what limits it immediately before that action?

Control Scenario: Correct and Incorrect Object

The test was performed in an isolated laboratory environment with synthetic objects and verified one specific class of mismatch between the proposal and the actual target.

In a separate synthetic HubSpot Lab, I used two test deals: LAB-042 and LAB-043.

In the normal scenario, the request, proposal, and actual write all pertained to LAB-042.

Then, I intentionally created a mismatch:

human-readable request: modify LAB-042
structured target:   modify LAB-043

This did not simulate a "malicious model." It was a controlled wrong-object case: a check to see if the architecture would stop a proposal with a different target before the CRM write.

In the first configuration, there was no independent boundary. n8n received the proposal, used its own HubSpot credential, and executed a PATCH for LAB-043.

A separate read after the run confirmed:

  • LAB-043 was modified;

  • LAB-042 remained in its original state.

That is, the deal modified was not the one named in the original request, even though the model itself still lacked write credentials.

What Independent Control Changed

In the second configuration, a separate deterministic gateway was introduced between the model's proposal and the HubSpot PATCH.

Its task was narrow: before allowing the write, verify the parameters that define the permissible consequence:

In this laboratory scenario, the expected target was fixed separately from the model's generation result and used as a source for verification before the external call.

  • the target system;

  • the object identifier;

  • the expected initial state;

  • the permitted transition.

The credentials did not disappear. n8n could still write to HubSpot. What changed was that access to this permission became dependent on a separate check immediately before the external action.

The normal scenario with LAB-042 received an allow and completed with a write. The wrong-object proposal with LAB-043 received a deny: the HubSpot PATCH was not initiated, and a new read confirmed that the deal's state had not changed.

Wrong-object test. The same target mismatch leads to different results: without an independent boundary, the CRM changes; with a boundary, the write is blocked before the external action.

As a result, the same class of wrong-object proposal that led to a CRM change in the first architecture was stopped before writing in the second.

What This Changes for Launch Decisions

In a production project, the phrase "agent is read-only" might be used as an argument during:

  • production rollout;

  • expanding autonomy or the set of available actions;

  • connecting operations in CRM, ERP, or infrastructure;

  • handing the solution over to a client;

  • security questionnaires or procurement reviews.

If such a statement is based solely on the tools and credentials available to the model, the team is only seeing part of the execution chain.

The practical question for the decision-maker is not "is the AI dangerous?" It's much more specific:

Do we have sufficient confirmation that the system's actual permissions align with the stated restrictions?

Removing credentials from the model is a useful control. However, it limits the model's direct permissions, not automatically the capabilities of the entire system. If a downstream component can still change the external state, that permission also needs to be identified and verified.

The practical takeaway from such scenarios is that verification should not only focus on the presence of security controls but also on confirming where the execution authority actually resides and whether the control is working at the runtime boundary. where the actual authority lies, what limits it, and what evidence confirms that the control is indeed working at the runtime boundary.

For such verification, I need not only the architecture diagram but also a reproducible chain:

what was proposed
→ who can actually execute
→ what is checked before execution
→ what was actually called
→ what state resulted after the call

This is a transition from a declaration of control to confirmed runtime controllability.

Six Questions Before Production or Expanding Permissions

Before launching an agent with access to CRM, ERP, ticketing, or infrastructure, I would check:

  1. Where are the write credentials and permissions physically located?

  2. Which component performs the external call?

  3. What parameters are checked immediately before execution?

  4. Can the target or a significant parameter change between the user request and the write?

  5. Is there an independent boundary between the model's proposal and the consequence?

  6. How is the final state confirmed after the action?

These questions are useful not only for engineers. They help CTOs, security leads, or product owners understand what exactly the decision "it can be launched" is based on.

Instead of a Conclusion

In this architecture, removing HubSpot credentials from DeepSeek did not eliminate the system's ability to change the CRM: the write permission remained with n8n.

You need to trace the authority to the component capable of causing the consequence and verify the control precisely at that boundary.
