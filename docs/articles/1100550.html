From Assistant to Agent: Who Presses the Button?

Let's, as is tradition, clarify the concepts to perceive the difference between an AI assistant and an AI agent equally.

An assistant responds to a request: explains an error, suggests code, generates an SQL query, or advises on server configuration. Even if the advice is incorrect, the consequences usually arise only after a person decides to follow it.

An agent can take the next step independently: open a terminal, execute a command, modify a file, call an API, use a browser, check the result, and continue working. If the first method didn't work, it can try the second—and then the third. It is this autonomy that makes it useful. And it is precisely this autonomy that complicates control. There is one inaccuracy here! Usually, the user deals with an agent application, not the agent directly, but for simplicity, they call it an agent. This simplification was also used for this article.

While AI writes code in a chat, everything is relatively simple and harmless. It suggests a solution, the human checks the code and initiates its execution. The process changes significantly when there is no human between the suggestion to do something and the execution of the task. This is the main difference of the agent approach, where the boundary shifts towards action.

That is, the implementation of an agent is primarily about expanding access rights. And it needs to be checked through boundaries, auditing actions, and the ability to roll back.

Checklist: Ten Questions Before a Project Pilot

1. Where are the boundaries of the agent's actions?

The most important question. The agent must have a clear and technically enforced limit: which directories, hosts, services, and commands are accessible, and which are not. It is desirable for workflows to be executed in an isolated environment (sandbox) rather than directly in the production environment.

What to check when choosing an agent: access model description, documented limitations, ability to configure the scope of action, behavior when attempting to exceed boundaries.

2. Where is the data stored and who has access to it?

By definition, an agent works with your content: repositories, documents, logs, results. For any company, this is not an abstract issue. If you are choosing between a foreign and a Russian environment, check not the country of the brand, but legally significant aspects: where the servers are physically located and data is processed, who the operator is, what happens when requests are transferred to external services.

What to check: data processing policy, storage jurisdiction, contract with the operator.

3. How does the agent handle secrets?

Passwords, tokens, API keys, private configurations—things the agent sees during its work. The question is not whether the agent is "honest," but how the architecture prevents unintentional disclosure.

What to check: restrictions on handling secrets, no transfer in external calls, logging without revealing values.

4. Can a human intervene in the process?

In a corporate environment, a "human-in-the-loop" model is needed: observability of actions, the ability to stop execution, mandatory confirmation for destructive and external actions.

What to check: operating modes (e.g., Ask / Plan / Agent), plan approval mechanism, ability to intervene at any step.

5. Is it visible what the agent is doing at every moment?

The agent should not operate as a "black box." Observability is ideal—in the same terminal or browser where the team works.

What to check: action log, display of executed steps, session reproducibility.

6. How does the agent verify its own results?

A mature solution is characterized by the agent verifying its work with all available tools. It runs tests, opens pages, executes commands, analyzes output.

What to check: is there verification in the pipeline, what happens when verification fails, how the agent reports unconfirmed results.

7. What does the agent do in case of errors?

The worst-case scenario is an infinite retry loop where the agent repeats the same thing, deviating further from the goal and consuming resources. The correct behavior is to stop after several unsuccessful attempts and request clarification from the user.

What to check: attempt limit, stop criteria, quality of the error message.

8. How dependent are you on a specific model?

An agent application is a combination of an execution environment and an LLM model. It's worth understanding if you are tied to one model, if it can be replaced or added. This question is particularly relevant for organizations with requirements for operating within the Russian environment.

What to check: list of supported models, configuration mechanism, licensing terms, possibility of on-prem installation.

9. Does the agent integrate with your tools?

A corporate agent should work where the team already works: files and folders, terminal, browser, network, repositories, etc. If for every action you need to switch to "export/import to chat," instead of an agent, you'll get an expensive consultant.

What to check: the range of environments the agent works with, support for your formats and systems, absence of "shims" for basic operations.

10. What about the legal aspects and reputational risks?

Contract with the developer, data processing, responsibility for decisions made with AI involvement, ability to prove the origin of the result.

What to check: contract, privacy policy, registers/licenses, if applicable, procedure for handling sensitive data.

Important: The feature set itself guarantees nothing. It's best to check each item on the checklist in your own infrastructure and with your own data. But if the developer has, at least at the architectural level, secured boundaries, controls the non-disclosure of confidential information, and has a clear logic for handling errors, it significantly reduces the number of "surprises" after production.

How It All Works in Practice

Let's still look at all the processes with a real example, otherwise, the checklist looks detached from reality and somewhat theoretical. As the test subject, we have Duade—an agent application designed to work in the Russian environment and even in a completely closed environment.

How Boundaries Are Defined

In Duade, workflows can be executed in isolated sandboxes, and potentially destructive or external actions require user confirmation. At the same time, the "sandbox" itself is not a magical protection and a guarantee of effective work. Effectiveness will depend on the configured setup and available resources, and security will directly depend on what actions are allowed outside of it. That is, the boundary of what is permissible is embedded in the solution's architecture; the agent is not assumed to have unlimited access to the entire infrastructure.

Human in the Loop

In Duade, work is organized as a joint session between the user and the AI. The user sees the agent's work in the terminal and browser, switches between "Agent, Plan, Ask" modes, and can intervene at any stage. Before a complex task, the agent generates a plan and a to-do list. In our team, there are developers who spend several days working on the plan with Duade, building the solution architecture and detailing the responsible stages. The agent writes code quickly, and working through a detailed plan allows for error-free code. Thus, in scenarios with increased control requirements, an additional "step" is added, where work begins only after full plan approval. This approach allows choosing the agent's degree of autonomy for a specific task.

Verification

Today, everyone knows that a confident AI answer is worthless without verification; a statement that a task is completed does not mean it is completed even well.

Before reporting task completion, Duade runs tests, opens web pages, "looks at them with its eyes," executes commands, and analyzes the received data. Before reporting completion, the agent checks the result with available tools and reports on the testing. This does not mean that Duade never makes mistakes and always delivers only excellent results. Let's not idealize it )) Yes, tests may be incomplete, and verification may not cover all possible scenarios. But there is a fundamental difference between "I wrote the code" and "I ran the code, checked the result, and can explain exactly what I checked."

Secrets

Duade has several simple built-in rules: passwords, tokens, API keys, and 2FA codes cannot be output to chat, logs, commits, or files; files with embedded credentials cannot be created. If a password is required for an operation or a step, the user enters it in the terminal; the agent does not request, substitute, or record it. The agent does not have the rights to reproduce secret information in any way.

Errors

Errors are a normal part of working with an agent; it's just like with people. It can misunderstand the task, encounter an unavailable resource, or a million other reasons why something went wrong.

Duade has stop criteria: if the agent encounters the same error two or three times, whether it's a failed test or an unavailable service, it doesn't repeat attempts in a loop. It stops, explains what went wrong, and asks for clarification. This behavior avoids the so-called retry loop, which drifts further from the goal and consumes resources.

Where the System Runs and What Models It Uses

For corporate implementation, not only the agent's functions are important, but also where the system is deployed, how models are connected, and what data leaves the working environment.

Duade supports installation on Windows, macOS, and Debian/Ubuntu Linux. For isolating workflows, Docker with SSH access can be used, and for specific scenarios, a local service with a web interface is available. This allows organizing work in an environment familiar to the team. However, it's important to remember that the mere presence of a desktop application does not determine the data route; it depends on the configuration, the chosen model, and the method of its connection. For some reason, even in development environments, people don't always realize that the agent's installation location and the model's operating location are far from the same thing.

If the application runs on an employee's computer, but requests are sent to an external API, the data still leaves the local environment. Therefore, when choosing a configuration, the entire chain must be considered: from the agent's working environment and tools to the model, network connections, and results storage. Duade works or provides corporate clients with the ability to organize work with their own LLM, in which case data is processed on Dumeit's servers and does not leave the Russian Federation's perimeter. The client can choose any other LLM and connect it to the agent via API; in this case, one must consider the provider's terms. For a completely closed environment, an on-prem installation option is provided, where data does not leave the corporate perimeter. This is the safest, but also the most expensive solution.

But let's return to the main idea of this article, which is that any autonomy of an AI agent's operation must be primarily controllable

Implementation must begin! Abstract testing may not always help identify subtle model issues. It's best to start launching your first AI agent with a small pilot: take a real work task, limit available resources, define success criteria, and decide in advance under what conditions the experiment should be stopped. If the agent handles it, its scope of application can be gradually expanded.

After all, it's pointless to aim for an agent that never makes mistakes. The goal can be stated as building a more efficient work process by implementing an AI agent in an environment where the agent's actions are safe and controlled.
