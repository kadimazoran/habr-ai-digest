The first CSS specification was released in 1996. Since then, for about thirty years, we've been trying to make interfaces beautiful: adding shadows, gradients, animations, flexboxes, and grids. But what did we get with the advent of LLMs? Back to text.

Ironic, isn't it? :)

Let's consider a relatively common scenario: you ask a model, 'Find me headphones in Megamarket.' The model enthusiastically tries to access the store and hits either sanctions restrictions or anti-bot protection. As a result, it sheepishly returns text: 'Well, there are such and such headphones, google it yourself, everything will be fine,' or, in the best case: 'Here's a list of links, but I'm not sure they're correct.' Thanks, of course, but we want more. And now we finally have the tools to provide that 'more.'

Basic Solution: MCP Server with Tools

The simplest step is to write an MCP server that will access Megamarket itself and return the necessary data to the model. It will have tools: find product, show product card, add to cart, check delivery. My demo server has nine of them. I write the schema description in English — for a number of recommendations, this consumes fewer tokens and the model understands better — but conceptually, everything is simple:

{ 
    "name": "search_products",
    "description": "Search the catalog by category, price and rating.",
    "inputSchema": {
        "type": "object",
        "properties": {
            "query": { "type": "string" },
            "category": { "enum": ["headphones"] }
        },
        "required": ["query"]
    },
    "annotations": { "readOnlyHint": true }
}

// The rest are in the same vein

The tool has a readOnlyHint marker: a hint to the host that the call only reads and changes nothing. It's just a hint: the specification explicitly requires considering annotations untrusted if the server is untrusted, as nothing prevents a malicious server from assigning readOnlyHint: true to an instrument that clears the cart. The host builds its confirmation policy on these annotations, but they are not a guarantee.

We connect the server to Claude Desktop and ask: 'Search for headphones under 5000 rubles.' The model picks up the tools, the server goes to the store, returns the products — and we get a neat table with prices, ratings, and an exact link.

This is no longer 'google it yourself,' but it's not magic either.

Why Tools Are Not Enough

The agent sees from the descriptions that we have search, delivery address, and product information. And yet, it outputs text without prompt wizardry. The tool schema answers the question 'What does the tool do?' It tells the model nothing about how to display the result to a human or how to go through a multi-step scenario.

Suppose we want to filter the results so that delivery arrives no later than tomorrow. This is a chain: 'search → filter by delivery → filter by price → sort.' The model will try, but without clear instructions, it will wander, especially if Opus is replaced by GLM or DeepSeek. And we also want the user to fall in love with the product, its appearance, and be able to easily compare the characteristics of different offers.

These tasks are covered by two MCP resources:

  • ui:// — an interface for humans;

  • skill:// — instructions for the agent.

Both are formatted as MCP resources, meaning the core protocol hasn't been changed for them; current servers can be extended, but the client will also need to handle them.

How Does MCP Apps Work?

For the user, we will render a live widget — an interactive product gallery where you can flip through cards, apply filters, and add to cart. All this, under the hood, requires two nested iframes for security (we'll talk about this below).

Lifecycle:

  1. Initialization. The host retrieves the HTML template from the server and can cache it in advance, even upon connection. The fact that the template is declared before the call allows the host to read and verify it before anything is executed.

  2. Call. When the model calls a tool, the host launches an iframe, the widget greets via ui/initialize and receives context in response: theme, CSS variables, container size, locale, timezone, platform. The host renders the widget.

  3. Interaction. From within the widget, we manage the display: gallery, filters, cards. The widget can, through the host, request the server's tools to be called.

  4. Cleanup. Before removing the widget from the screen, the host sends it ui/resource-teardown with the reason and waits for a response so the widget can complete correctly. It does not handle state saving between calls; this is on the list of future specification improvements.

The result of the tool call comes in two streams, and both fields are already present in MCP:

  • content — a textual representation for the model and hosts that cannot render widgets;

  • structuredContent — structured data for the widget. This is where the aforementioned 20 headphones from the search, warehouse balances, prices, and ratings go. According to the specification's recommendation, they are not included in the model's context.

On Divergence from the Core

There's a subtlety here. The core protocol states that a tool returning structured content SHOULD also return serialized JSON as a text block — for backward compatibility. This means, according to the core rules, these fields duplicate each other, and MCP Inspector versions 0.17-0.21 even showed a warning about the discrepancy. In February 2026, it was removed as misleading.

MCP Apps deliberately separates them and describes this as a recommended practice: content is for the model, structuredContent is for rendering. The meaning is clear: no one needs to render twenty cards as text, and paying for them with tokens is even less desirable. The debate about this has been ongoing since the fall of 2025 (SEP-1624). OpenAI decided differently in their Apps SDK: there, the model sees structuredContent, and only meta is hidden from it. And some maintainers, including Olivier Chafik from ext-apps, believe that data for the widget should be carried precisely in meta.

Under the Hood

The widget communicates with the host via JSON-RPC over postMessage. The host acts as a gatekeeper: it decides whether to allow the tool call, may require user confirmation, and logs everything that comes from the widget. A tool call from the widget is a standard tools/call, which the host proxies to the server.

On top of standard MCP messages, the extension adds its own layer of ui/* methods: handshake ui/initialize, ui/open-link, ui/message, ui/request-display-mode, ui/update-model-context, plus notifications about tool entry, result, cancellation, and size changes. The transport remains the same, but the set of messages is new, and the host must learn to understand them.

Everything is linked via _meta: the resource is declared separately, and the tool references it.

// Declare the resource
{
    "uri": "ui://shop/compare",
    "name": "Headphone Comparison",
    "mimeType": "text/html;profile=mcp-app"
}
// Use the resource
{
    "name": "compare_products",
    "inputSchema": {
        "type": "object",
        "properties": { "product_ids": { "type": "array" } }
    },
    "_meta": {
        "ui": {
            "resourceUri": "ui://shop/compare",
            "visibility": ["model", "app"]
        }
    }
}

Inside the resource is HTML. The host retrieves it: upon seeing _meta.ui.resourceUri for a tool, it calls resources/read over a regular MCP connection, just like tools/list. The specification allows doing this in advance, immediately after server connection; in the worst case, the host reads the resource in parallel with the tool call. The widget cannot and should not load itself: its script starts executing within the sandbox, where the host has placed the ready HTML.
