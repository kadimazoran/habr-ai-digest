Wazuh collects security events well, but to find answers within them, you need to know the query language and hundreds of index fields. An experienced SOC engineer can write a query in a minute, but it's not so easy for colleagues who haven't worked with Wazuh or SIEM systems.

The Wazuh dashboard is built on OpenSearch Dashboards, and OpenSearch has a ready-made assistant – OpenSearch Assistant. It's not included in the Wazuh distribution but can be installed with standard plugins of the same version, without modifying Wazuh itself.

This is Andrey, head of cloud security at Selectel. In this article, we will install Wazuh, connect our own model, and add a button to the interface that explains any document.

We tested the instructions on Wazuh 4.14.7, which is based on OpenSearch 2.19.5. Any model with an OpenAI-compatible API will work. The entire setup will take about two hours, of which 30–60 minutes will be spent building the plugin for the Explain Document button.

After setup, three tools will appear in the dashboard.

  • Chat window. An analyst asks a question in their own words and gets an answer from the LLM.

  • Query Assist in Discover. A "verbal" question is converted into a PPL (Piped Processing Language, OpenSearch query language) query, and the result is displayed in a regular table.

  • Explain Document button in the document viewing panel. The model analyzes an alert or vulnerability record: what happened, how serious it is, and what to check.

How it works

The analyst's question follows this path:

  • Dashboard plugins render the chat window, the Query Assist bar, and the button. They don't perform any calculations themselves; they pass the question to the indexer.

  • The ml-commons plugin in the indexer manages the connection to the model and agents. An agent is a scenario of operation: what prompt to send to the model and what tools to give it. The main tool here is PPLTool. It asks the model to generate a PPL query and executes it.

  • The model runs separately. The indexer accesses it via HTTPS through a connector – an object with an address, request format, and response parsing rule.

We will configure in the same order: plugins, model, agents, and finally, the interface button.

Requirements

The instructions have been tested on the following configuration:

  • Wazuh 4.14.7 in Docker (wazuh-docker repository, single-node variant). Wazuh 4.14.7 runs OpenSearch 2.19.5 internally;

  • qwen3-next-80b model via OpenWebUI. Any model with an OpenAI-compatible API that reliably follows instructions will work.

Have ready:

  • model API address, model name, and token;

  • root access to the server running the Wazuh indexer and dashboard;

  • for the Explain Document button – a Linux machine with Docker, 8 GB of RAM, and access to GitHub and npm.

Plugin versions must match the OpenSearch version. A plugin of a different version simply won't load. You can find the OpenSearch version in Dev Tools by querying GET /, the version.number field. For Wazuh 4.14.7, this is 2.19.5. If you have a different Wazuh version, replace 2.19.5 in all commands with your version.

Most commands are executed in the dashboard console menu: Indexer management→ Dev Tools. The console automatically adds the indexer address and authentication. Do not confuse it with Server management → Dev Tools: that's the Wazuh manager API console, and the commands from this article won't work there. Where server terminal access is needed, it's indicated above the code block.

Step 1. Installing plugins

The assistant requires two indexer plugins (opensearch-skills and opensearch-flow-framework) and three dashboard plugins (assistantDashboards, mlCommonsDashboards, observabilityDashboards). They don't have separate archives, so we'll take them from the official OpenSearch build of the same version. The archives weigh about 1.3 GB.

Perform the following steps on the Wazuh server.

1. Download the OpenSearch and OpenSearch Dashboards builds and extract only the necessary plugins:

URL=https://artifacts.opensearch.org/releases/bundle

curl -LO $URL/opensearch-dashboards/2.19.5/opensearch-dashboards-2.19.5-linux-x64.tar.gz 
mkdir -p indexer dashboard 
tar -xzf opensearch-2.19.5-linux-x64.tar.gz -C indexer --strip-components=2 
  opensearch-2.19.5/plugins/opensearch-skills 
  opensearch-2.19.5/plugins/opensearch-flow-framework 
tar -xzf opensearch-dashboards-2.19.5-linux-x64.tar.gz -C dashboard 
  --strip-components=2

Step 2. Enabling the assistant

1. Enable agents in ml-commons and allow connection to your model. Replace llm.example.com with your model's host in the last parameter:

PUT _cluster/settings 
{ 
  "persistent": { 
    "plugins.ml_commons.agent_framework_enabled": true, 
    "plugins.ml_commons.memory_feature_enabled": true, 
    "plugins.ml_commons.only_run_on_ml_node": false, 
    "plugins.ml_commons.connector.private_ip_enabled": true, 
    "plugins.ml_commons.trusted_connector_endpoints_regex": [ 
      "^https://llm\.example\.com/.*$" 
    ] 
  } 
}

Let's look at these settings in more detail.

  • agent_framework_enabled and memory_feature_enabled enable agents and conversation memory. Without memory, follow-up questions like "how many of them are critical events?" won't work.

  • only_run_on_ml_node: false allows models to run on regular nodes. By default, ml-commons expects dedicated ML nodes, which Wazuh doesn't have.

  • connector.private_ip_enabled is needed if the model is on an internal network.

  • trusted_connector_endpoints_regex is a list of allowed model addresses. By default, it only includes cloud services like OpenAI and Bedrock. This is a regular expression: each dot in the hostname is written as \.; otherwise, it matches any character.

The response should be "acknowledged": true. No indexer restart is needed.

2. Enable the assistant interface. Add five lines to the end of opensearch_dashboards.yml. In Docker, this file is located on the server in config/wazuh_dashboard/opensearch_dashboards.yml next to docker-compose.yml; in a package installation, it's in /etc/wazuh-dashboard/opensearch_dashboards.yml:

assistant.chat.enabled: true 
assistant.incontextInsight.enabled: true 
assistant.alertInsight.enabled: true 
observability.query_assist.enabled: true 
observability.summarize.enabled: true

3. Restart the dashboard:

docker restart <DASHBOARD_CONTAINER> 
# or in a package installation: 
systemctl restart wazuh-dashboard

After restarting, the dashboard header will show Ask a question, and clicking it will open the OpenSearch Assistant window. It won't be able to respond yet, as the model is not connected.

Step 3. Connecting the model

The indexer doesn't run the model itself; it accesses it via API. This requires a connector and a model registered on top of it.

1. Create a connector. Replace the bracketed values with your own and execute the entire query:

POST _plugins/_ml/connectors/_create 
{ 
  "name": "LLM chat", 
  "description": "OpenAI-compatible chat endpoint", 
  "version": "1", 
  "protocol": "http", 
  "parameters": { 
    "endpoint": "<LLM_URL>", 
    "path": "<LLM_PATH>", 
    "model": "<LLM_MODEL>", 
    "temperature": 0, 
    "max_tokens": 2048 
  }, 
  "credential": { 
    "api_key": "<LLM_API_KEY>" 
  }, 
  "actions": [ 
    { 
      "action_type": "predict", 
      "method": "POST", 
      "url": "${parameters.endpoint}${parameters.path}", 
      "headers": { 
        "Authorization": "Bearer ${credential.api_key}", 
        "Content-Type": "application/json" 
      }, 
      "request_body": """{ \"model\": \"${parameters.model}\", \"messages\":[{\"role\": \"user\", \"content\": \"${parameters.prompt}\"}], \"temperature\": ${parameters.temperature}, \"max_tokens\": ${parameters.max_tokens}, \"stream\": false }""", 
      "post_process_function": """ 
def text = params['choices'][0]['message']['content']; 
if (text == null) { text = ""; } 
String t = text.toString().trim(); 
int te = t.indexOf(\"</think>"); 
if (te >= 0) { t = t.substring(te + 8).trim(); } 
if (t.startsWith(\"```\")) { 
  t = t.replace(\"```json\", \" \\").replace(\"```JSON\", \" \\").replace(\"```ppl\", \" \\").replace(\"```\", \" \\").trim(); 
} 
t = t.replace(\"<cppl>\",\"<ppl>\").replace(\"</cppl>\",\"</ppl>\"); 
return '{\"name\":\"response\",\"dataAsMap\":{\"response\":\"' + escape(t) + '\"}}'; 
""" 
    } 
  ] 
}

Triple quotes """ are a feature of the Dev Tools console: text between them can be written as is, and the console will automatically convert it into a JSON string. The connector differs from the standard OpenAI template in two places, and both differences are mandatory: ““»

  • request_body substitutes the ${parameters.prompt} parameter into the request. This is what the assistant agents pass. The standard template with ${parameters.messages} is not suitable for agents: the model receives a broken request, and ml-commons responds with Invalid payload.

  • post_process_function extracts text from the model's response and returns it as {"response": "..."}, as expected by the tools. It also removes the reasoning block <think> and Markdown wrappers that some models add.

The response will include a connector_id. Record it; this is <CONNECTOR_ID>.

2. Register and deploy the model:

POST _plugins/_ml/models/_register?deploy=true 
{ 
  "name": "llm-chat", 
  "function_name": "remote", 
  "description": "LLM for OpenSearch Assistant", 
  "connector_id": "<CONNECTOR_ID>" 
}

The response will include a model_id – this is <MODEL_ID>. The model runs on the OpenWebUI API side, so deployment takes a few seconds. You can check its status with the query GET _plugins/_ml/models/<MODEL_ID>: the model_state field should be DEPLOYED.

3. Verify that the model responds:

POST _plugins/_ml/models/<MODEL_ID>/_predict 
{ 
  "parameters": { 
    "prompt": "Answer in one word: does it work?" 
  } 
}

The response should contain the dataAsMap.response field with a short answer from the model. If you get an error, check the address, path, token, and regular expression from Step 2.

Step 4. Chat agent

In the chat window, communication is not with the model but with an agent. The agent receives the question, calls PPLTool if necessary, gets the query result, and formulates an answer. The agent's behavior is defined by three texts, which you can view under the spoilers below.

Appendix A – system prompt: respond in Russian, do not write queries yourself, show the executed query.

Inserted into the prompt.prefix parameter in Step 4.

You are an SOC duty analyst assistant. The data is Wazuh alerts in the wazuh-alerts-* index.

Respond in Russian, concisely, without retelling your steps.

MAIN RULE. The analyst must be able to double-check every number.

Therefore, EVERY response, even to a simple question like "how many," includes the executed query

in a PPL code block. An answer without a query block is unacceptable. Response format:

Answer. <numbers and essence, 1–2 sentences>

Query.

```sql

<exact PPL executed by the tool>

```

HOW TO FIND DATA

You do not write PPL queries yourself. To get a number or a list of events, call

the TransferQuestionToPPLAndExecuteTool and pass the analyst's question in words to the question field. The tool will build the query based on the index schema and execute it.

Correct: {"question": "How many alerts of level 10 or higher today?"}

Incorrect: {"question": "source=wazuh-alerts-* | where..."}

If the analyst mentions a rule number, group, address, or username, transfer them

verbatim into the question. Do not guess rule numbers from memory: they are unique to each cluster.

The number in the answer must come from the tool's result. If the tool has not

been called yet, you have no answer.

COMPOUND QUESTIONS

If the question has two parts requiring different counts (e.g., "total count" and

"from which address is the highest count"), call the tool separately for each part.

Provide the final answer only after receiving results for all parts.

CLARIFYING QUESTIONS

If a question refers to a previous one, make it a standalone question: repeat

the period and conditions.

"And how many of them are level 13 or higher?" after a question about today

becomes "How many alerts of level 13 or higher today?"

If the analyst changes the topic, do not carry over conditions from previous questions.

HONEST ANSWER

The period in the answer must match the period in the executed query. If there is no time filter,

write "for all time.".

If events exist but the required field is empty, state that. This is not the same

as "no events.".

If the result is empty, and the analyst did not specify a period, repeat the query to the tool,

adding "for all time," and respond with the second result.

Never respond with an empty message. If the query failed, state that and

show the last query that was attempted.

RESPONSE FORMAT, STRICTLY ADHERE TO

Respond in Markdown. This structure is mandatory for EVERY response without exception,

including simple count questions and rule explanations by number:

Answer. One or two sentences on the essence of the question, with numbers.

Query.

```sql

<exact PPL query executed by the tool here>

```

If there is an important caveat (period, empty field), add a line:

Note. One sentence.

Formatting rules:

— Insert the exact query from the tool's response 'ppl' field into the code block, do not rewrite

it from memory.

— If the tool was called multiple times, show all executed

queries in the Query. block, each in its own code block.

— Do not enclose the service JSON when calling the tool in triple quotes.

— Do not retell your steps or use think tags.

Appendix B – template used by PPLTool to ask the model to generate a query. It includes PPL language rules for Wazuh indexes and examples.

Inserted into the PPLTool's prompt parameter in Steps 4 and 5. Before inserting, replace <INSERT_GROUP_LIST_HERE> with the list of your cluster's groups. The lines ${indexInfo.indexName}, ${indexInfo.mappingInfo}, and ${indexInfo.question} should not be changed: PPLTool will substitute the index name, its field list, and the question in their place.

You are translating an analyst's question into a single PPL (Piped Processing Language) query for OpenSearch.

Use only fields from the index field list at the end of this text.

RULES FOR WAZUH INDEXES

1. NAMES WITH DOTS

Enclose the index name and all fields with dots in backticks:

source=wazuh-alerts-* | where rule.id = '5710'

2. MAIN FIELD TYPES

timestamp – date. rule.id – keyword, compare with a string in quotes: '5710'.

rule.level – number, compare with a number: rule.level >= 10.

rule.groups, agent.name, agent.id, data.srcip, data.dstuser – keyword.

rule.description – keyword, the English description of the rule.

3. TIME FILTER

Apply a filter on timestamp in every query. Use only these forms:

last N minutes timestamp >= adddate(now(), interval ‑N minute)

last N hours timestamp >= adddate(now(), interval ‑N hour)

today timestamp >= curdate()

last 24 hours timestamp >= adddate(now(), interval -24 hour)

yesterday timestamp >= adddate(curdate(), interval -1 day) and timestamp < curdate()

last N days timestamp >= adddate(now(), interval ‑N day)

The expression now() - interval 1 day is not accepted by this PPL version.

"Yesterday" always means two conditions: lower and upper bounds.

If no period is specified, use the last 7 days.

If the analyst asks for "all time" or to explain a rule by number, do not apply a time filter.

4. HOW TO SELECT EVENTS

If a rule number is specified, filter by it: rule.id = '5710'.

If the rule number is not specified in the question, do not use rule.id in the query at all:

rule numbers are unique to each cluster, and guessing a number gives an incorrect answer.

Multiple numbers – use 'or': rule.id = '5710' or rule.id = '5712'.

If a topic is mentioned, filter by group. Standard Wazuh groups:

authentication_failed failed logins (SSH, PAM, etc.)

authentication_success successful logins

sshd all SSH events, both successful and failed

syscheck file changes (integrity monitoring)

rule.groups = 'authentication_failed'

The groups for this cluster are listed below. Use only groups from the list.

If no suitable group is found, search by rule description:

like(rule.description, '%brute force%')

5. COUNTS AND SORTING

Unique values: distinct_count(field). count(distinct...) does not work.

Non-empty field: isnotnull(field). The is not null construct does not work.

Sort by aggregate name: stats count() as cnt by data.srcip | sort - cnt.

6. OUTPUT FORMAT

Return exactly one line <ppl>QUERY</ppl> and nothing else: no explanations, no

other tags, and no triple quotes.

CLUSTER RULE GROUPS

<INSERT_GROUP_LIST_HERE>

EXAMPLES

Question: How many alerts today?

PPL: <ppl>source=wazuh-alerts-* | where timestamp >= curdate() | stats count()</ppl>

Question: How many alerts of level 10 or higher yesterday?

PPL: <ppl>source=wazuh-alerts-* | where timestamp >= adddate(curdate(), interval -1 day) and timestamp < curdate() and rule.level >= 10 | stats count()</ppl>

Question: From which addresses are there the most failed logins in the last week?

PPL: <ppl>source=wazuh-alerts-* | where timestamp >= adddate(now(), interval -7 day) and rule.groups = 'authentication_failed' | stats count() as cnt by data.srcip | sort - cnt | head 5</ppl>

Question: How many unique agents sent alerts in the last 24 hours?

PPL: <ppl>source=wazuh-alerts-* | where timestamp >= adddate(now(), interval -24 hour) | stats distinct_count(agent.id) as agents</ppl>

Question: Show the last events for rule 5712

PPL: <ppl>source=wazuh-alerts-* | where rule.id = '5712' and timestamp >= adddate(now(), interval -7 day) | fields timestamp, agent.name, rule.description, data.srcip | head 5</ppl>

Question: Explain rule 5710

PPL: <ppl>source=wazuh-alerts-* | where rule.id = '5710' | fields rule.id, rule.level, rule.description, rule.groups | head 1</ppl>

export const buildDocContext = (source: any) => { 
  if (!source) { 
    return ''; 
  } 
 
  try { 
    return `Wazuh document (JSON):\n${JSON.stringify(source, null, 2)}`; 
  } catch { 
    return ''; 
  } 
}; 
 
const ExplainDocument = ({ context }: { context: string }) => { 
  const [state, setState] = useState<{ 
    loading: boolean; 
    answer?: string; 
    error?: string; 
  }>({ loading: false });

The parameter values were chosen on the test bench; they should not be changed without reason:

Parameter

Reason for value

model_type: "FINETUNE"

With the OPENAI value, the tool removes backticks from the query. Without them, field names with dots (rule.id, wazuh-alerts-*) break the query parsing.

head: 5

Limits the number of rows in the result. Each alert is a document with hundreds of fields, and a large output overflows the model's context.

message_history_limit: "3"

How many previous conversation turns to pass to the model. With the default value, the context overflows on the third question, and the answer comes back empty.

max_iteration: 10

How many steps the agent can take. A compound question requires two tool calls plus one step for the answer.

The response will include an agent_id – this is <CHAT_AGENT_ID>.

3. Link the agent to the chat window. The window looks for the agent in the system index .plugins-ml-config using the key os_chat. Only users with an administrative certificate can access OpenSearch system indexes, so this query is executed not in Dev Tools but in the server terminal.

Wazuh in Docker:

docker exec <INDEXER_CONTAINER> curl -sk 
  --cert /usr/share/wazuh-indexer/config/certs/admin.pem 
  --key /usr/share/wazuh-indexer/config/certs/admin-key.pem 
  -X PUT "https://localhost:9200/.plugins-ml-config/_doc/os_chat?refresh=true" 
  -H "Content-Type: application/json" 
  -d '{"type": "os_chat_root_agent", "configuration": {"agent_id": "<CHAT_AGENT_ID>"}}'

Package installation: the same command without docker exec <INDEXER_CONTAINER>; certificates are located in /etc/wazuh-indexer/certs/admin.pem and /etc/wazuh-indexer/certs/admin-key.pem.

The response should be "result": "created". If the key was already linked to another agent, you'll get "result": "updated".
