In the previous article about skillmem — local memory for code agents — I talked about how someone else's README could become a user rule, and how we fixed it in 0.10. At the time, the code had passed two independent reviews, and I thought the vulnerability was singular and closed.

Yesterday, 0.11.0 was released. In between: forty rounds of review by two models from different sides (one on the Claude side, the other on the GPT side), each reading the code hostilely and tasked with reproducing findings as a team, not through reasoning. Below is what came of it and why I no longer trust any "clean" review until it's backed by another.

Stop Rule

"Review until there are no errors" is non-terminating: fresh eyes will always find something in any module. We agreed on this: stop when neither of the two reviewers reproduces any P1/P2 (data loss, incorrect answer, trust boundary violation, crash on real input) for two consecutive rounds. P3s accumulate in the issue for the next release.

The rule was met in rounds 39-40. We didn't get there directly.

Three Waves of Findings

Wave 1 (Rounds 1-18): Initial Audit. Six P1s, all outside the Stop hook everyone was looking at. HTTP-/write intercepted someone else's entry, /learn wrote public skills without permission, body files were shared across different databases, trust could be granted by any process, kind was a path traversal in export. Fixed, then three rounds spent fixing what the fixes broke.

Wave 2 (Rounds 19-23): Release Rehearsal. I wrote the release requirements and gave them to the same reviewers. A rehearsal of init on a config copy found that moving the venv doubled all hooks — recap would run twice per session. Then a chain reaction: config backups named by the second overwrote each other; they were created with 0644 permissions next to the file containing the OAuth account; the Codex backup was not byte-for-byte. Eleven P2s in the installation code that "worked."

Wave 3 (Rounds 24-40): Fresh Eyes on the Core. The most interesting part. Every time a reviewer received a module that no one had re-read from scratch, they found 1-3 old P2s inherited from main:

  • HTTP server with multiple agents: 409 on conflict quoted headers of someone else's private entries. Backlinks of a public entry returned the slug of someone else's private one. /search, /list, /recall paginated results *before* the visibility filter — 110 of someone else's entries, and your own entry returned as an empty 200, even though /get found it.

  • import-vault followed symlinks like *.md outwards and put the target text into the database — ~/.zshrc, for example. Attachments and packs had already rejected this case; notes had not.

  • skills rm <pack> deleted all project entries for the pack, including the owner's author note.

  • The Windows scheduler did not carry environment variables, which launchd/cron/systemd did.

  • And my favorite: scrub — a function that hides secrets before writing — was not idempotent. An already substituted [secret redacted] would match again on each rewrite and grow into [secret redacted] redacted]. The hash changed, owner approval was removed. Restoring a dump over the same database silently removed approvals.

Every Second Fix Introduced a Regression

This is the main thing I learned. The fix for search displacement went through four iterations, and each was caught by the next round:

  1. Candidate window 5 → filter after limit: five hidden rows displace their own.

  2. Window 100: one hundred hidden rows — same issue.

  3. No limit, cursor up to N visible: without LIMIT, SQLite sorts all matches before the first row, and a wide SELECT pulled all bodies through sorting — 20 seconds per request on a database of 9 thousand rows.

  4. Narrow pass + bodies only for selected: 52 ms without filter, 73–87 ms with filter. Done? No: the predicate was given to both the master and the HTTP master, which started ranking on an unlimited pool — a different top-5 than in the CLI, for five out of six requests.

The fifth iteration — the master follows an unfiltered path, and the test "HTTP master == S.search", which failed on the previous commit. Only then did the round become clean.

If there had been no review after the first fix, we would have shipped a 20-second /search with the confidence that we had closed the leak.

What's Worth Repeating

  • Two reviewers from different sides, not one. Models err differently; the overlap in their findings over 40 rounds was noticeably less than the union.

  • Strict report format: P1|P2|P3 · file:line · what · evidence (command + output). "Seems like a race condition here" is a P3, not a gate.

  • Reviewer does not write code. Twice during the review cycle, a reviewer violated read-only mode (editing pyproject.toml, a file next to the working clone) — check git status after each round.

  • Each fix is a new round, even a one-liner. Especially a one-liner.

  • Define the stop rule in advance, otherwise the cycle will either not end, or end when everyone is tired.

Cost: a day of machine time and ~350 tests instead of 221. Result for 0.11.0: the trust boundary is closed equally on HTTP, MCP, CLI, and hooks, and every line of the release notes was verified by the team before being written. What remains P3 is in issue 0.11.1.
