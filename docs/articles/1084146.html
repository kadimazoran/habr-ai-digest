Completion Does Not Prove AI Agent Result Quality

An AI agent can complete a run, return correct JSON, and pass automated checks. However, the team might still not have a usable result.

This is not a paradox, but a confusion of different states. "Request completed" refers to the environment's operation. "Artifact exists" indicates the presence of material. "Result accepted" means a responsible person has confirmed compliance with the original task. Separate checks are needed between these states.

Format Does Not Equal Content

Let's imagine a task where the agent must prepare a map of sources, a system description, a list of contradictions, and a development task. The response contract requires four fields. The agent returns them, and the JSON parses successfully.

But inside the fields, there might be paths to files that no one has created:

  • source_map: output/source_map.md;

  • system_context: output/system_context.md;

  • findings: output/findings.md;

  • task_pack: output/task_pack.md.

The schema is validated, but the documents are missing. Another run might return headers and phrases like "material will be added later." The text is not empty, but the artifact is absent. Yet another run might terminate after preparing part of the package due to environment limitations.

If all three cases are recorded as the same fail, the report won't indicate what needs fixing. Did the environment, format, result completeness, or requirement quality break?

Completion Gate Should Come Before Quality Assessment

Before assessing content, I use a separate completion gate, which is a check for artifact completeness. Its purpose is not to decide if a document is good. It should determine if there is anything to evaluate.

Checks proceed sequentially:

  1. The request completed without a timeout or process crash.

  2. The response contains content.

  3. The structure can be parsed.

  4. Mandatory fields comply with the contract.

  5. Returned values or links lead to existing, non-empty artifacts.

  6. These artifacts are not placeholders and do not consist of empty sections.

Only after this do requirement checks begin: assertion sources, mandatory sections, known contradictions, security constraints, and compliance with the user scenario.

This way, a technical failure is not masked as a poor understanding of the task, and a correct format is not accepted as a finished result.

A Green Test Only Checks Its Own Question

Automated checks are useful, but their limitations must be visible. A checker might confirm the presence of four headers and overlook empty text. It might require an exact word and reject an equivalent phrasing. It might repeat the same erroneous interpretation from which the agent assembled the response.

There is an even earlier risk: tests might be written based on an outdated specification. In the project, there's a new contract, an old wiki page, a prototype, and a support email lying around. The agent chose the old version, and the tests meticulously checked precisely that.

Therefore, the chain must preserve provenance:

source or decision → rule → user scenario → test or manual check → proof of implementation → user acceptance testing (UAT).

If the source or decision changes, related rules, scenarios, and tests become obsolete. An old green result cannot be automatically carried over to a new version of the context.

Independence is More Important Than the Number of Agents

Multiple agents retelling the same set of information do not create an independent check. They might simply arrive at a common misconception faster.

It is more reliable to maintain a log of evidence coverage: which facts are already presented, which are repeated, which sources conflict, and what evidence is missing. The discussion ends not after a fixed number of replies, but when mandatory facts are covered, and unresolved conflicts are escalated to the solution owner.

This is not a vote for truth. In case of conflicting sources, the system should preserve both versions, show the area of divergence, and stop where human authority is required.

Textual Retelling Does Not Replace the Original Artifact

A requirement might originate from a screenshot, a recording of a conversation, a video, or an interface state. A transcription is useful for searching but remains a derivative representation.

For verification, you need:

  • the original artifact;

  • an exact pointer to the fragment;

  • a derivative description;

  • a transformation method;

  • known losses.

If the requirement is "the user sees a save confirmation," an API test alone is insufficient. The observable interface state must be checked. If the solution is extracted from a video, the final check must lead back to the time fragment of the original.

The Author Should Not Solely Accept the Result

An agent can prepare a solution, change the format, and explain why a test passed. But it should not simultaneously be the sole author of the result, the author of the criteria, and the release authority.

Before acceptance, a human checks:

  • the criterion appeared before implementation;

  • the test relates to the original scenario;

  • fixes and deviations are visible;

  • the limitations are understood by the person who will use the result;

  • the residual risk has been accepted by a named owner.

This is not a rejection of automation. The executor, deterministic checks, and human acceptance answer different questions.

What to Store in the Report

Instead of a single success percentage, it is useful to break down the reasons:

  • the environment did not complete the request;

  • the response could not be parsed;

  • the format was restored by external code;

  • the complete artifact did not pass the criteria;

  • the result was rejected by a human;

  • the result was accepted within agreed boundaries.

This way, the team sees where the next step lies: in the environment, contract, model, check, or specification.

A completion gate does not make a model smarter or evaluate content quality. It prevents mistaking the absence of a whole verifiable artifact for a poor result, and a formally correct object for completed work. First, the system must produce a whole artifact. Then, external code checks the agreed-upon properties. After that, a human decides if the result can be used.
