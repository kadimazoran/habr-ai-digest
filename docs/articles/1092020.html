What is AigisSAST

AigisSAST is a console security scanner for AI-generated code. About 3,000 lines in pure Python, without a single dependency and without the cloud: your code never leaves your machine.

pip install aigis-sast
aigis scan

Inside:

  • Python is parsed using AST, not grep. This is why cursor.execute(f"... {user_id}") is different from a harmless f-string in a logger.

  • 21 rules for typical AI mistakes: tokens (OpenAI, Telegram, GitHub, AWS, Stripe, etc.), passwords, database connection strings, committed .env, SQL and shell injections, eval, pickle, JWT without signature verification, CORS *, debug=True, verify=False, tokens via random, FastAPI endpoints without authorization, XSS, secrets in VITE_*/NEXT_PUBLIC_*, root in Docker, exposed database ports.

  • Each finding is explained in human-readable terms: its dangers, how to fix it, and ready-to-use code.

  • Secrets are masked (7312************) to prevent keys from leaking again through CI logs.

  • Russian and English: language is taken from the system, switchable via --lang en.

Each finding has a clickable link to the file and line on GitHub, GitLab, or Bitbucket, so you can get to the relevant spot with one click.

It Also Fixes Things

aigis fix --dry-run   # show diff
aigis fix             # apply changes

It moves keys to .env and .env.example, adds .env to .gitignore, changes verify=False to True, yaml.load to safe_load, random to secrets for tokens, disables debug, hides database ports behind 127.0.0.1, and adds necessary import statements. It doesn't automatically touch SQL injections or JWTs: without understanding the application logic, it's easy to break things.

'But I Deleted the Key'

The most common scenario: someone notices a token, deletes it in the next commit, and feels relieved. But the old version of the file lives on in the git history, visible to anyone who does a git clone.

$ aigis history
  [CRITICAL] AIG001  7312************  (Telegram bot token)
      bot.py  ·  commit 402c92b from 2026-09-14  ·  deleted, but remains in history
      ↗ https://github.com/you/bot/commit/402c92b...

In CI, it's integrated with a single command aigis init: findings appear in the Security → Code scanning tab and directly in pull request diffs.

Round 1: 126 AI-Generated Projects and 2,012 'Passwords'

I started with repositories that showed clear signs of AI generation: .cursorrules, CLAUDE.md, 'vibe coded,' 'built with Cursor/Bolt/Lovable.' The median was three stars, typical pet projects.

The first run was embarrassing: 2,012 hardcoded passwords. I started analyzing them manually, and almost all of it turned out to be noise: test passwords, hashes in lock files, your-key-here, ${DB_PASSWORD}, variables like hashed_password and ACCESS_TOKEN_EXPIRE_MINUTES, translations where password meant 'Пароль' (Password).

After refinement, 138 findings remained, and real keys weren't lost: I added a test for each corrected case. Manual annotation showed a precision of about 60–70% for secrets. This is an honest figure, not a marketing one.

The most valuable aspect of this round wasn't about other people's bots, but about my scanner. 16,378 findings, with about 30 being real. The noise came from:

  • translations in VPN panels: "newPassword" = "Nueva Contraseña" — this is a label for a field;

  • vendored vue.js, where emptySlotScopeToken = "_empty_" sounds like a token only by name;

  • example values in OpenAPI ("password": "secret");

I also found a real bug: aigis history loaded the entire git log -p into memory, crashed with OOM on large histories, and silently wrote an empty report with code 0. For a security scanner, there's no worse bug: seven repositories were almost marked as 'clean.'

I fixed everything. The history is now read as a stream, and in case of a git error, the scanner honestly exits with code 2. On one popular VPN panel, there were 37 findings, now 3; on another, there were 29, now 7. The actual embedded bot token remained in the report, which was the whole point.

Why I Didn't Check Any Keys

I was constantly asked: 'Why not just call getMe on Telegram and see if the token is alive?'

Because that would be using someone else's access. A request with someone else's token authenticates you as the bot owner, regardless of whether the method is 'read-only.' Normal security research works like this: find a key by format and context, inform the owner of the file and line (without the key itself), and leave the verification and revocation to them. Therefore, all the numbers above mean 'looks like a real key,' not 'the key works.'

I never accessed any third-party service, bot, database, or panel, nor did I use any found keys. The scanner only reads public code and masks secrets. I'm developing this project for the community's benefit: to get AI code into production with fewer vulnerabilities and for owners to learn about leaks before malicious actors do.

What I Learned

  1. AI makes mistakes not randomly, but according to patterns. Secrets in code, f-strings in SQL, CORS *, debug=True, endpoints without Depends(...) — these are the same errors across thousands of projects.

  2. Finding is easy, staying silent is hard. Most of the time was spent not on making the scanner find things, but on preventing it from shouting about everything. Of the 193 tests, most are about what not to find.

  3. A deleted key is not a deleted key. If it got into a public repo, you need to revoke it, not just delete it with a commit.

  4. A silent failure is worse than a false alarm. A scanner that crashes and says 'all clear' is more dangerous than no scanner at all.
