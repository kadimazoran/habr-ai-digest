Offline Deployment: Local Repo and Transfer

The stack only needs internet during the build phase. After all Python packages are downloaded to offline_packages/, the project can be moved to an offline machine and deployed from a local repository. This part is about creating a dependency snapshot and restoring the stack on a clean Debian 12.

Why is this needed?

The standard pip install open-webui requires internet and resolves dependencies anew — today it might install one version, tomorrow another. This is unacceptable for an offline machine: pip will either fail with "no internet" or (if the cache is partial) install incompatible versions.

Local repository (offline_packages/) solves both problems:

  • Version pinning — requirements.lock contains an exact list of packages (transformers==5.5.4, torch==2.11.0+cpu, etc.), not "free" ranges.

  • Offline operation — all .whl files are stored locally, pip install --no-index --find-links=./offline_packages does not access PyPI.

  • Reproducibility — an identical environment can be created on any machine with the same OS/Python.

What goes into the repository: only Python packages. Models, llama.cpp/stable-diffusion.cpp binaries, scripts, HTML — are transferred separately (via tar of the entire project folder). offline_packages/ is an addition, not a replacement for the "entire project folder".

How make_offline_packages.sh works

The script takes a snapshot of the current venv and downloads all packages to offline_packages/:

  1. pip freeze > requirements.lock — pins the exact versions of everything installed in venv.

  2. pip download -r requirements.lock — downloads wheels for each package.

  3. --only-binary=:all: — ensures that .tar.gz (sdist) are not downloaded. If a package doesn't have a wheel, the script will report it now, not on the offline machine.

  4. --extra-index-url https://download.pytorch.org/whl/cpu — the key point: torch is taken from the CPU index (version +cpu), not from PyPI (CUDA version with nvidia-*).

  5. Fallback to sdist — if a package doesn't have a wheel, the script will download .tar.gz and warn that the target machine will need gcc, python3-dev, and for tokenizers — rustc/cargo.

  6. Verification — compares the number of files with the number of packages in requirements.lock. If it's less, it warns.

Why --extra-index-url and not --index-url. With --index-url, pip searches only on the PyTorch index and won't find open-webui (it's not there). With --extra-index-url, it searches everywhere: open-webui on PyPI, torch on the PyTorch index. At the same time, torch==2.11.0+cpu (the +cpu suffix) unambiguously indicates the CPU version, and CUDA won't be pulled in.

About the "no wheel" fallback. In 99% of cases for the open-webui + torch stack on Debian 12 x86_64, all packages have pre-built wheels. The fallback is a safeguard: it's better to find out about sdist now (when there's internet and python3-dev can be installed) than to get error: command 'gcc' failed on the offline machine.
