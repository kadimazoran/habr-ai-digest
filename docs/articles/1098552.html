EmbeddingGemma 2: How to switch from 768 to 512 coordinates and save memory on RTX 5090

EmbeddingGemma 2 has an output projection with a rank of 512, even though the standard embedding contains 768 coordinates. We used QR decomposition of this projection to map vectors into a 512-dimensional space while preserving cosine similarity. We then compared QR variants with standard MRL dimensionality reduction. Experiments were conducted on an RTX 5090, evaluating search quality on SciFact and FiQA, measuring memory and latency for exact FAISS search on MS MARCO corpora up to five million documents, and the conversion time for an existing database. On five million documents, QR-direct reduced the process peak memory from 15.88 to 11.11 GiB. The total latency for a single query changed from 36.19 to 34.80 ms, and for a batch of 32, from 50.62 to 44.97 ms. This article explains the transformation, the variants compared, and the conclusions drawn from these experiments. The RTX 5090 testbed was rented through the GPUGO catalog. Read more

Five million 768-dimensional embeddings in FP32 occupy 15.36 GB. On an RTX 5090 with its 32 GB of VRAM, this is almost half, and that's just for the coordinates. The search index requires additional overhead memory, and if the model runs on the same card, it will need space too.

EmbeddingGemma 2 offers a way to reduce this volume. The model's last linear layer transforms 512 numbers into 768. In exact arithmetic, its outputs lie within a 512-dimensional subspace: a different basis can be chosen for their storage, keeping 512 coordinates while preserving cosine similarity.

We tested what this yields in practice. For five million documents, the peak memory of the exact search process decreased from 15.88 to 11.11 GiB, approximately a 30% reduction. However, the total query latency improved much more modestly: from 36.19 to 34.80 ms in single-query mode. Below, we will break down the transformation, check the quality, and see where the time savings go.

For the experiments, we rented a testbed with an RTX 5090 from gpugo.ru. The configuration was selected from the catalog.

Why a vector of 768 numbers can be stored in 512 coordinates

In the fixed EmbeddingGemma 2 checkpoint, the last linear layer of the text part of the model has a weight matrix W of size 768×512 and operates without bias. Subsequently, SentenceTransformers averages the token states without padding and normalizes the resulting vector to unit length:


512D token states → token RMSNorm → Linear 512→768

                      → masked mean pooling → L2-normalization

This scheme has two useful properties. First, the linear projection can be moved after averaging: in exact arithmetic, mean(W h) = W mean(h). This possibility is already noted in the Transformers implementation. Token RMSNorm remains in place, before averaging: the equality does not hold for it.

Second, a linear layer cannot transform 512 independent coordinates into 768 independent directions. Checking the weights revealed a rank of 512 and a condition number of about 11.64. The outputs are recorded in 768 numbers but still lie within a 512-dimensional subspace.

To store them more compactly, we use the reduced QR decomposition W = Q R. The matrix Q defines an orthonormal basis for the output subspace, and R allows obtaining coordinates in this basis.

Why QR preserves cosine similarity

Token RMSNorm normalizes the states of individual tokens before the linear layer. Let's denote the average of these states by x. Then the standard embedding is normalize(W x).

The decomposition is as follows:


W = Q R

Q: 768×512, orthonormal columns

R: 512×512

full representation: e = normalize(W x)

512D representation:   z = normalize(R x)

The columns of Q are mutually perpendicular and have unit length. Multiplication by such a matrix preserves lengths and dot products. Therefore, in exact arithmetic, the cosine between z vectors matches the cosine between the corresponding full embeddings e.

A given normalized 768D vector can be transformed into this basis by the expression normalize(e @ Q), if the vectors in the batch are row-wise. The basis is taken from the model weights; it does not need to be trained on the corpus, as with PCA. However, the original 512D token states cannot be stored instead of embeddings: the W head defines the learned metric WᵀW, which ordinary cosine similarity between these states does not preserve.

The factorization itself is standard. We were interested in whether the result would be preserved in the model's actual computational path and how much memory could be freed up.

What variants were compared

The new basis can be used in two ways. QR-convert transforms already calculated Full768 embeddings: texts do not need to be re-encoded. QR-direct immediately obtains a 512D vector by applying R after pooling.

For comparison, we also used standard dimensionality reduction. EmbeddingGemma 2 is trained with Matryoshka Representation Learning, or MRL: useful signal is preserved in the first coordinates. We can take the first 512 or 256 numbers of the standard output and re-normalize the vector.

Pool768 is used to separately test the consequences of moving the linear layer after pooling. In Pool768 and QR-direct, this layer is computed in FP32, whereas the standard head operates in BF16. Therefore, not only the dimensionality but also the numerical path changes. All stored vectors were uniformly converted to FP32 and L2-normalized.

QR-convert, QR-direct, and MRL512 have the same storage volume. However, MRL discards part of the original coordinates, while QR changes the basis of the full output subspace. Standard MRL prefixes are not preserved after such a change: the first 256 coordinates of a QR vector cannot be considered MRL256.

The actual process takes more: CUDA context, FAISS overhead structures, and temporary memory are added to the coordinates. Therefore, we measured both the array size and the peak memory of the entire process. For the latter, we used NVML: torch.cuda.memory_allocated() and memory_reserved() do not cover all FAISS memory.

For measurements, we used MS MARCO. We used nested prefixes of the original corpus: 100 thousand, 500 thousand, one, and five million documents. All six representations were calculated for actual texts; a small corpus was not duplicated to reach the desired size.

We searched using FAISS's GPU IndexFlatIP. This is an exact brute-force search by dot product, which for unit-length vectors is equivalent to cosine similarity. Each index was built in a separate process, without the text encoding model loaded.

On five million documents, the median observed peaks over three rounds were 15.88 GiB for Full768 and 11.11 GiB for QR-direct 512D. The coordinate array decreased by 33.3%, while the process peak memory decreased by 30.0%. Overhead costs do not decrease proportionally to dimensionality.

What happened to the quality

In the proof above, we consistently specified exact arithmetic. The model operates differently: in BF16, each multiplication and pooling operation rounds values. The standard output is no longer strictly required to lie within the W subspace, so QR-convert does not provide bitwise exact recovery.

Across all query-document pairs in SciFact and FiQA, the maximum cosine error for QR-convert was around 1.5×10⁻⁵. For QR-direct relative to Full768, it reached 2.3×10⁻³: here, both the order of operations and the head's precision change.

To assess the impact of these discrepancies on search, we used the full test sets from BEIR:

  • SciFact: 5183 documents and 300 queries;

Why the context was kept at 8192 tokens

For quality assessment, we kept the documents whole. A limit of 256 tokens would have reduced encoding costs but would also have altered the input texts.

Actual lengths were calculated with prompts, titles, and special tokens, without truncation. For MS MARCO, the median was 76 tokens, with a maximum of 962; only 0.0668% of passages exceed 256 tokens. For SciFact, the proportion of documents longer than 256 tokens is already 61.14%, and for FiQA, it is 19.96%. A single short limit would truncate these corpora differently.

The main limit was explicitly set at 8192 tokens, according to the checkpoint card. The maximums for SciFact and FiQA were 1901 and 3545 tokens, respectively, so all documents from the three corpora fit entirely. With dynamic padding, 8192 sets an upper bound, not the length of each batch. Separate checks with 256/512/8192 confirmed the influence of context on quality. All results above refer to full texts.

Details of memory and latency measurements

In memory measurements, we used FP32, disabled TF32, and 1024 MiB of FAISS temporary memory. The observed peak covers index building and subsequent queries. NVML was polled every 5 ms, so a very short peak might have been missed by the monitor.

For measurements of search on a pre-built index, we used 992 queries from a fixed thousand in the official MS MARCO dev split. This allows comparing B=1 and B=32 without an incomplete last batch. For each variant and corpus size, we conducted three rounds with shuffled run order. Within a round, we repeated the time measurement three times. The base seed for samples and shuffles is 42.

All 144 Flat measurement rows passed checks against CPU Flat and FP64 scores with a tolerance of 2×10⁻⁶.

How to convert an already calculated database

For a ready FP32 database, QR-convert is suitable. Embeddings can be read in chunks, multiplied by Q, normalized, and written to a 512D file. After this, the index will need to be rebuilt. Texts do not need to be re-encoded by the model.

The basis is constructed once for a specific model version. Example for a loaded SentenceTransformer:


import torch

head = st[0].auto_model.language_model.embedding_projection

assert head.bias is None

W = head.weight.detach().cpu().double()

Q, R = torch.linalg.qr(W, mode="reduced")

# Fix sign convention.

signs = torch.where(torch.diagonal(R) < 0, -1.0, 1.0)

Q = (Q * signs.unsqueeze(0)).float()

R = signs.unsqueeze(1) * R

def compress(vectors768, Q):

    assert Q.device == vectors768.device

    return torch.nn.functional.normalize(

        vectors768.float() @ Q,

        dim=-1

    )

The matrix Q needs to be transferred to the GPU beforehand, once. Along with it, we save the model revision and the weight hash. Documents and queries must use the same basis: a 512D query in the QR basis cannot be sent to an old 768D index. When switching services, both the index and query transformation need to be updated.

How long did it take to convert five million vectors

In a separate CPU measurement, the conversion read 15.36 GB and wrote 10.24 GB. The observed RSS peak was about 1.30 GB.

A total of 126.78 seconds was recorded, including writing, flushing, and final fsync. Multiplication and normalization took 11.58 seconds. The main part, 108.95 seconds, was occupied by writing with flushing. Reading and copying required 4.32 seconds, with an additional approximately 1.94 seconds for creating the output array and overhead work outside specific timers.

The input file was pre-read, so it could remain in the OS file cache. The cache was not cleared, and this result does not characterize reading from a cold NVMe. The 126.78 seconds also do not include prefetch (4.21 s), separate result verification (199.87 s), or index rebuilding. The maximum coordinate error relative to the saved GPU QR-convert was 3.13×10⁻⁷.

What can be applied in your own projects

For a ready FP32 database, we would start with QR-convert. On SciFact and FiQA, it preserved nDCG@10, Recall@100, and the ordered top-10 for all 948 queries, and texts did not need to be re-encoded for conversion. On your own database, you should still test your own queries, especially for close scores near the top-k boundary.

In a new service, you can test QR-direct, which immediately outputs a 512D vector. In our experience, it matched Pool768 on per-query metrics but differs from the standard numerical path. MRL512 is also a viable option: it has the same storage volume and almost the same search cost. Our data does not demonstrate QR's superiority in relevance.

The results also have limitations. We tested FP32 storage of text embeddings and dense exact search. Encoder weights do not decrease with basis change, nor do the costs of its intermediate activations. Quality was assessed on two English retrieval tasks; the multimodal path was not measured. MS MARCO was used for scale and speed, without conclusions about relevance on the selected prefixes.

Coordinate quantization and product quantization (PQ), which encode parts of the vector separately, will require their own experiments: basis rotation may alter their behavior.

If the task is to fit the index, look at the peak memory of the entire process. If you need to speed up the service, measure the full query. In our case, 512 coordinates instead of 768 provided about a 30% saving in search process memory, and the gain in full latency depended on the corpus size and batch size.
