AI Has Partially Accelerated Development. What About Everything Else?

AI helps write code and test ideas faster, but accelerating development doesn't mean accelerating the entire system. What happens to testing, reviews, metrics, and engineer growth. Read more

A developer used to spend three days on a task, and now handles it in one day with AI. It seems productivity has tripled. But after development, the task still needs to go through review, testing, integration, and deployment. If these stages haven't sped up along with code writing, only one part of the system has become faster.

In recent years, AI has significantly changed my work. I no longer manually write another mapper, simple CRUD, or spend hours deciphering an unfamiliar API. I can quickly build a prototype, try a new library, or test a hypothesis. This truly accelerates development.

The problem begins when the speed of writing code is mistaken for the speed of the entire product development.

Accelerated One Part of the Pipeline

Let's imagine a simple team. Previously, a developer completed a task in three days, after which another day was spent on verification.

With AI, a developer finishes in one day:

For a single task, everything looks good: instead of four days, it took two.

But now imagine several developers constantly sending new tasks to the next stage. They started writing code two to three times faster, while testing capabilities have barely changed. Very soon, the queue will simply shift. Previously, development was the bottleneck. Now, it becomes reviews, testing, analytics, requirement approvals, or deployment.

This doesn't mean accelerating development is pointless. It means that local acceleration of one stage cannot be automatically considered the same as accelerating the entire system. AI can increase the productivity of an individual developer and simultaneously increase the amount of unfinished work for the entire team.

Code Became Cheaper, Verification – Not So Much

This is especially evident in code reviews. Just a few years ago, a pull request with several thousand lines usually meant several days of work for the author. Now, an agent can modify dozens of files in a short session.

Generating two thousand lines of code has become significantly cheaper. Proving that these two thousand lines work correctly – not so much.

The reviewer still needs to understand what exactly has changed, check architectural decisions, find missed scenarios, and ensure the new logic doesn't break the old. A PR with 60 changed files might take the author a couple of hours of work with an agent. But the person on the other side still has to reconstruct the context of the changes.

Of course, reviews can also be delegated to AI. Then you get a system like this:

AI #1 writes code
       ↓
AI #2 does review
       ↓
AI #3 generates and runs tests
       ↓
Developer clicks Approve

And here arises the question: what exactly did the human approve with their Approve? If one agent wrote the implementation, another checked it, and a third fixed the identified issues, the developer interacts less and less with the code itself. In the short term, this might be faster. In the long term, there's a risk of losing understanding of the system.

As my colleague says:

Excessive use of AI leads to degradation.

It's not about the tool, but about the measure. Understanding someone else's code is a skill that weakens without practice.

Testing Hasn't Disappeared Either

AI already helps well with testing: it can suggest test cases, write unit tests, find obvious edge cases, or prepare data. But generating tests and independently verifying a product are not the same thing.

The model works with the context it's given. If an important scenario is forgotten in the requirements, there's no guarantee it will restore it on its own. If several components work correctly individually, it doesn't mean the user can complete the entire scenario. Humans also make mistakes. The difference is that the task of verification as a separate process doesn't disappear just because AI now helps write code.

This is particularly noticeable when reviewing test assignments. Sometimes, based on the results, it's quite easy to assume that the candidate asked the model to create test cases: the structure is neat, there are many scenarios, the wording sounds professional. But upon closer inspection, it turns out that several important cases are missed, and some checks exist more for quantity than quality. A plausible result doesn't necessarily mean a good result.

Ideas Have Also Become Cheaper to Produce Along with Code

AI accelerates not only development. Previously, even a simple prototype could take several days. Now, a person can come up with an idea in the evening and have a working interface and backend by morning. This is a huge opportunity. More people can experiment, create their own products, and test hypotheses. But here lies the same problem.

Creating a product has become cheaper. Making it good – not so much. Therefore, the reduction in development cost inevitably means not only more good products, but also more raw ones.

When an application can be assembled over a weekend, the temptation arises to monetize it immediately. Meanwhile, security, error handling, support, proper testing, and even the user problem itself might be left for later.

As a result, the amount of software produced grows faster than users' ability to discern which of it can be trusted.

We Are Measuring Output Instead of Outcome Again

A separate question is how to even understand if AI implementation in a company is working. The most accessible metrics are easy to measure:

  • how many employees use AI tools;

  • how many requests they sent;

  • how many tokens they spent;

  • how many lines of code they generated;

  • how many tasks they closed.

All these metrics can be useful for evaluating tool usage. But by themselves, they say almost nothing about its value. A team might start spending ten times more tokens. This only proves that the team started spending ten times more tokens.

The number of tokens used is activity, not result.

Even the number of closed tasks doesn't necessarily show the effect. Let's imagine:

AI Usage
       ↓
Development Time ↓ 30%
       ↓
Review Time ↑ 40%
       ↓
Number of Returns ↑
       ↓
Lead time to production ≈ unchanged

At the developer level, AI works perfectly. At the system level, the gain is already unclear.

Therefore, I am more interested not in the question "how much code a company writes with AI," but in what happens next:

  • has the lead time from task to production decreased;

  • has the review time changed;

  • how many changes are returned for rework;

  • has the number of defects changed;

  • does the team deploy changes more often;

  • has the hypothesis testing time decreased;

  • and ultimately, has the product result changed.

Tool usage and tool benefit are different metrics.

If AI Writes Simple Code, Where Will Experienced Developers Come From

There is another problem, the consequences of which will not be immediately apparent. Most of my experience didn't come from books. I wrote bad code. Made unsuccessful abstractions. Saw queries without necessary indexes, read explain analyze to understand how a query works (believe me, it wasn't easy before). Observed how a solution that seemed beautiful today became difficult to maintain a year later. Some mistakes led to code rework. Some led to production issues. Sometimes the consequences of an error quickly explained why a certain practice exists. This is how experience gradually builds up.

I remember one such mistake better than others. I divided data between microservices based on how they looked at the time, not on how they were used. The boundary ran through the middle of a user scenario: part of the entity remained in one service, part moved to another.

As long as the functionality was minimal, it didn't interfere. A year later, almost any change affected both services, support questions required looking into two databases, and we maintained consistency manually. At first, it was tolerated, then the boundary had to be moved anyway, along with the accumulated data. There's a lot written about where to draw boundaries, but I only understood it then.

Previously, the path looked something like this:

      ↓

      ↓

      ↓

      ↓

      ↓

Now, the lower part of this path is automated the fastest. Companies are less interested in paying a person for simple CRUD, mappers, or another integration if an agent can do most of this work.

This is rational for business. But the question arises: if juniors no longer write simple code, where will middles (and later, seniors) come from in a few years, who can understand when AI has written complex code incorrectly?

An AI Operator Must Also Come From Somewhere

There's often an answer to this question: the developer of the future won't write code but will manage agents. I don't argue, but a good operator must understand when the agent makes mistakes.

Why does one developer look at a query and immediately think about the data size in the table and the index, while another doesn't? Why does one notice a potential race condition, while another calmly accepts a PR? Why does one see that a new abstraction will become a problem in six months?

Not because the first writes better prompts, but because they have already seen similar situations. Experience comes from one's own mistakes and their consequences.

You can read as much as you want about how a query without an index can crash a database, but your own slow query in production, latency graphs, and user support calls create a completely different level of understanding of the problem.

If most of these decisions are made by an agent, the question arises where the future engineer will gain this experience. And here, the problem of juniors becomes not just social. Yes, it becomes harder for a person after university to get their first job. But for the industry, something else is more important: a junior is not a cheap senior. It is one of the stages of becoming a future senior. If this stage is removed, the consequences will only manifest in a few years.

AI Creates Comprehension Debt

The concept of technical debt has long existed in development. We make a compromise now and understand that someday we will have to pay for it: redesign the architecture, remove a temporary solution, or rewrite a complex part. With AI, another type of debt is increasingly appearing – comprehension debt.

The system works, tests pass, the code is already in production, but the team doesn't fully understand why it's structured that way. For example, an agent changed 30 files, added caching, several database indexes, and a new abstraction. After several iterations, the tests are green. The PR was reviewed by another agent, a human looked at the main changes and clicked Approve. It seemed everyone was happy.

Three months later, a production problem arises. Now the team will have to figure out these 30 files anyway. Only they will do it during an incident and possibly for more than a day.

The cost of understanding has not disappeared; it has simply been postponed. This is especially dangerous for code where the cost of error is higher than usual: payments, personal data, infrastructure. I wouldn't be surprised if some modern products already contain solutions whose authors cannot quickly answer where sensitive data is stored, which fields end up in logs, and who has access to them.

It Seems Code Will Become Crafted

Once, I had a wild thought: what if in 10 years, "written by a human" will be perceived similarly to a hand-built car?

It sounds like developer snobbery, but there's no particular value in a human manually writing a mapper that an agent can correctly generate in five seconds. But behind this joke is another question: if code production becomes practically free, what is the value of an engineer then?

The value becomes the ability to say:

I understand why this system works this way. I know its limitations. I can explain the decisions made. And I am ready to take responsibility for its consequences.

Then a good engineer might indeed write less code than today. But they will have to understand no less.

AI is Still Useful

Despite all that has been written above, there is a huge class of work that can be accelerated. Writing a mapper. Preparing a migration. Generating repetitive tests. Deciphering an unfamiliar API. Finding several solution options. Quickly trying a new library. Building a prototype and understanding if it's worth continuing at all. The ability to make cheap mistakes during the research phase is especially useful. Previously, I might spend several days studying a new technology before realizing it wasn't suitable. Now, a few hours are often enough: give the model context, build a small prototype, look at the limitations, and discard it. And this is an excellent result.

The problem doesn't start when a developer uses AI. It starts when the generation speed is confused with the speed of value creation.

We have learned to produce more code, PRs, prototypes, and products. Now, the processes around development must learn to cope with this volume: verify, discard the unnecessary, maintain system understanding, and grow people capable of distinguishing a good result from a convincing-looking one.

The cheaper code creation becomes, the more expensive the ability to verify, understand, and be responsible for it becomes.
