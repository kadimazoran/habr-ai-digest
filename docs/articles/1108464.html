What Was Compressed in Research

In the paper Selective Context, EMNLP 2023, text fragments were evaluated based on how unexpected they were for a language model. The most predictable ones were removed. The method was tested on scientific articles, news, and dialogues: models generated summaries and answered questions.

Hidden text

Selective Context is a method for compressing input text by removing the most predictable fragments. Selection operates at the token, phrase, or sentence level.

An auxiliary language model estimates the probability of each token given the preceding text. These probabilities are used to calculate unexpectedness: the harder a fragment is to predict, the higher its score. Fragments with low scores are removed at a specified proportion; the remaining text is passed to the main model.

When context was reduced by 50%, memory usage decreased by 36%, inference time by 32%; BERTScore decreased by 0.023, and faithfulness metric by 0.038. Compression halved processing time by about a third, with a slight loss in quality according to the chosen metrics.

For practical tasks, specific errors are important. An answer where the model missed an exception to delivery rules can maintain high similarity to the reference and change the store's revenue when calculating the price.

In LLMLingua, EMNLP 2023, a smaller model selected which parts of the prompt to keep. The token budget was distributed among the instruction, examples, and question; the text was compressed considering the connections between tokens.

In LLMLingua-2, Findings of ACL 2024, the compressor was trained to classify tokens: keep or remove. Training data was prepared using GPT-4. When selecting, the model considers context from both sides of the token. The method was tested on five benchmarks, including MeetingBank and LongBench.

The compressor worked 3–6 times faster than comparable methods; the entire cycle, from compression to obtaining an answer, accelerated by 1.6–2.9 times with prompt reduction by 2–5 times.

The preserved words are taken from the source, but removing a negation or part of a condition changes the meaning of the rule. Such losses are checked separately: how much shorter the text became and how accurately the model performs the task are two independent questions. The degree of compression is selected based on the specific task, model, and language, balancing savings with errors.

What Exactly Are We Compressing

A prompt includes instructions, source data, example answers, and sometimes conversation history. During manual editing, repetitions are removed and cumbersome wording is shortened while preserving the task conditions. An example with a rare exception requires attention: if the condition is not described anywhere else, it will disappear from the request along with the example.

An automatic compressor selects which fragments to keep to fit within the token budget. Summarizing a document with another model requires a separate request and carries the risk of losing details.

Let's compare three versions of instructions for calculating delivery in a hypothetical store. The rules include a free delivery threshold and exceptions for express and oversized orders; these are useful for checking which conditions are preserved when shortening the prompt.

The order amount amount_after_discount is the amount after all discounts. Standard delivery (delivery="standard") costs 390 rubles. For orders of 5000 rubles or more inclusive, standard delivery is free. Express delivery (delivery="express") costs 790 rubles for any order amount.

How to Calculate Savings

The cost of a request includes input and output tokens — each at its own rate. Excluding cache, the calculation looks like this:

Request cost =

(input tokens × price per 1 million input tokens

+ output tokens × price per 1 million output tokens) / 1,000,000

Let's compare two prompts with a hypothetical example. The original has 2000 tokens, the shortened one has 1200; both answers take 600 tokens. An output token costs four times more than an input token.

In units of input token cost, we get:

A: 2000 + 600 × 4 = 4400

B: 1200 + 600 × 4 = 3600

Input was reduced by 40%, request costs — by approximately 18%. If a short instruction causes a longer answer or requires a repeat request, savings will decrease.

We add the compressor's work to the expenses. The cost of a one-time document compression will be distributed among the requests that use its short version. If new context is processed before each request, compression is paid for each time. For manual editing, we consider the time spent preparing and checking the template.

Caching also affects the comparison. If a long prefix is read from the cache, and the short version is sent for the first time, the costs depend on the conditions for processing cached tokens. We will save counters for cache reads and writes, and compare the cost with actual charges or our tariff prices.

To compare versions, we will calculate the cost of a result that passed all checks:

Cost of accepted result = (expenses for all requests + expenses for automatic compression) / number of accepted results

The numerator will include unsuccessful attempts. For all versions, we will set the same response correction rules and repeat request limits in advance. If no result is accepted, the cost cannot be calculated using this formula.

In the delivery example, the instruction must return the correct price and valid JSON. A variant that lost the rule about oversized orders is not suitable for work, regardless of token savings.

Conclusions

What I managed to find out:

  1. The prompt can be shortened without noticeable loss of quality, but the acceptable degree of compression depends on the task and the model. Conditions require attention: in the delivery example, removing the word "standard" changes the rule.

  2. Versions must be tested on identical data, including exceptions and missing fields. Repeat the A/B test on one model; then expand a successful small test with new cases.

  3. Calculate savings based on the cost of the accepted result. The calculation includes input and output tokens, compression, repeat attempts, and cache. Fewer tokens in the prompt are only part of this calculation.
