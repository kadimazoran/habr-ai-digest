Even during peak load, users must receive a concise answer in seconds. To achieve this, we, the Alice AI Search team, adapt the entire fast answer pipeline—from custom architecture pre-training to online RL training on user behavioral signals.

In this article, we will break down how generative answers work in Search and discuss the main improvements in the June release: how we accelerated answers using short info-contexts, why we combined Encoder-Decoder with a sparse MoE architecture, and how training on real user signals affected the product's quality and usage.

Furthermore, we have made the model trained from scratch, Alice AI‑T5-35B‑A0.6B Base, publicly available, with the limitation that external users can access inference via Hugging Face Transformers, while optimized production inference is currently only available within Yandex.

How Alice AI's Fast Answer Works

Alice AI's Fast Answer is built on the same infrastructure as Alice's chat response. Its structure was detailed in a separate article, so here we will briefly recap the essence:

  • First, the query goes to a model that accesses various types of search—for example, text and image search—and gathers the information needed for the answer.

  • All text documents are processed by the next model, which keeps only the parts relevant to the query—we call these info-contexts (IC).

  • In the final stage, ICs along with images, videos, and other found materials are fed into a model that generates Alice AI's final answer.

Next, we will delve into the key changes at each stage.

Agentic Search Stage

By Nazar Pogosskiy and Nikita Semyonov

Search provides LLMs with up-to-date facts and details that might not be present in the model's weights. The retrieved documents contain much more text than is needed for a specific answer, and each additional token in the context increases generation time.

A human typically opens the top search results and selectively reads the necessary parts of the found documents. A language model works differently: it processes the entire provided context sequentially. This, on one hand, helps the language model gather complete information, but on the other hand, requires significant computation. To adapt Search to these specifics, six months ago, Yandex introduced the Agentic Search initiative. The main goal: to optimize search technologies for all Alice AI family models.

One of Agentic Search's tasks is to retain only the fragments in the retrieved documents that genuinely help form the answer. Below, we explain how we trained an extractor model for this purpose and how it accelerated generation.

The Info-Context Extractor Model

For this task, we trained a "tiny" BERT-like model with 80 million parameters from scratch. The training dataset included 4 trillion tokens from our corpus. We then fine-tuned the model to determine the relevance of each token in a document. The annotations for this were collected using open-source LLMs. This gave us a cold-start version of the extractor that already performs well on the task.

However, relevance to the query alone is not enough: we need the minimal context that is specifically useful for our generative model. For instance, the model might have already learned some information during its training—passing such fragments in the context is unnecessary; they only increase its length and slow down generation.

Pretrain Stage

By Anton Viktorov

To achieve the required response speed, we need a fast architecture that excels at processing input context when analyzing retrieved documents.

Our previous model had an Encoder-Decoder architecture, which performed well on text and RAG tasks. We wanted to improve it by adding MoE layers, which significantly increase model capacity and knowledge volume without a proportional increase in computational cost.

Among current large open-source models, we didn't find common Encoder-Decoder MoE architectures. The closest examples from major research teams are NLLB-MoE, Switch Transformer, and FLAN-MoE, published between 2021–2023. This led to the idea of trying to train a modern hybrid of these architectures.

Alice AI‑T5-35B‑A0.6B is an Encoder-Decoder model with a sparse MoE architecture.

The model was trained on 15T tokens from our proprietary dataset for the UL2 denoising task, with context extension from 8K to 128K at the end of training using YaRN. The dataset was significantly improved compared to the last open-source release, but colleagues will discuss this in a separate post.

We used Muon, which orthogonalizes matrix weight updates using Newton-Schulz iterations. In our experiments, it outperformed Adan and AdamW.

Alignment Stage

By Dmitry Kalashnikov

SFT: Laying the Foundation for Response Patterns

In the SFT stage, we teach the model various patterns, establish response structures, and define basic behavioral principles for different query types. This is where specific skills and behavioral patterns are formed, which can later be further enhanced during RLHF.

Therefore, one of the main goals of SFT is to assemble not just a large dataset, but one that thoroughly covers real user scenarios. Real Search queries form the basis of the dataset. To ensure diversity, we use a system of stratified bins. Queries within these bins are distributed across various domains and segments: for example, education, medicine, e-commerce.

How We Obtain Answers for SFT

The era when reference answers were entirely human-written is gradually fading. Today, for creating SFT data, we use generation and rewriting pipelines with the help of more powerful models, including earlier versions of Alice.

Essentially, we employ Rejection Sampling: multiple answers are generated for a single user query from different systems and configurations, and our task is to select the best one among them.

But the question arises: how do we choose the best answer? We have about a dozen rule-based and model-based quality signals at our disposal for evaluating candidates. There are universal criteria—such as usefulness and factual accuracy—as well as those specific to certain segments and product scenarios. For instance, in the e-commerce segment, one criterion was the practical applicability of the answer, while in the education segment, it might be checking the rule-based correctness of the answer.

Why isn't the best answer determined by a single universal metric? The set of signals and their relative importance can depend on the specific task. Using these evaluations, we rank the generated answers and select the highest-quality candidates for the training dataset.

However, Rejection Sampling works well as long as a sufficiently high-quality answer is present among the generated candidates. But in complex segments or for "rejects" (user dislikes), this is not always the case.

In such situations, we use a separate Critique & Revision pipeline.

For each unresolved query, we gather specific requirements in the form of rubrics and feed the current answer to a judge model. It analyzes the answer based on the given criteria and generates criticism: what exactly is wrong with it and what needs improvement. This criticism guides the modification of the answer, after which the model generates a new, improved version.

RLHF: Pushing the Quality Ceiling

The core of our RLHF pipeline is the GRPO algorithm, or more precisely, its modification GSPO.

After each RL cycle, we use the generations from the new model for the next training iteration. These augment the SFT dataset, and SbS annotation of new answers allows us to update the reward models. Thus, model improvement simultaneously enhances the quality of data and training signals for the next cycle.

This approach allows us to continuously improve our answers: establishing patterns at the SFT stage, adapting them to a specific model, and using it for further improvement of signals and SFT.

VeRL and Encoder-Decoder

A year ago, our primary RLHF algorithm was DPO, implemented on Yandex's internal training framework. However, GRPO was becoming the standard in LLMs. VeRL was one of the popular training frameworks. However, it is primarily designed for decoder-only architectures: during the rollout stage, the framework uses specialized inference engines, particularly vLLM. Therefore, for our Encoder-Decoder architecture, colleagues adapted an internal version of VeRL, creating a custom rollout using the internal inference library.

The transition to online RL reduced the time for one RL experiment cycle severalfold, and the model, after the transition, almost immediately surpassed the previous one with a 60% win rate. After adding the answer generation and rewriting pipeline, the new model surpassed the previous one with a win rate of over 70%.

Online Signals

Even a good set of offline metrics doesn't guarantee that we've accounted for everything that affects the usefulness of an answer for a real user. Therefore, we additionally use online signals—information about user interactions with Search.

How long did the user spend reading Alice's answer? Was the information received sufficient, or did they continue searching after the answer? These and many other signals help assess how well Search solved the user's task. Their aggregate is considered in the Proficit metric—one of the key online metrics by which we evaluate how successfully Search has solved the user's task.

To optimize answers for Proficit, we model this signal by training a separate reward model. We then use it as one of the signals in RLHF alongside offline rewards. The key challenge in this task is that online signals from real users are often very noisy, as users can interact with the product chaotically. Because of this, a training dataset consisting of simple "query—answer—Proficit value" samples does not allow for training a high-quality reward. To combat noise, we use aggregation (we are interested in answers shown for the same query multiple times), filtering, and pairwise training formulation, and we also stratify pairs by user device (behavior on computers and mobile devices differs).

In the training dataset, we form contrasting pairs of answers for the same task and determine which one was more useful based on user signals in terms of Proficit. This way, we reduce the influence of random actions by individual users—for example, when someone gets distracted while reading or leaves a page open.

The resulting reward captures user preferences that are difficult to define with a set of rules. For example, thanks to the reward, the model learns to identify the likely intent of a user's query and immediately provide the necessary information, placing explanations and additional details below. If a user successfully solves their task, they are more likely to return to Search with a new query. We see this connection in A/B experiments with major Alice updates: as the proportion of successfully solved tasks increases, so does the number of new user search sessions.

Ultimately, in an ablation A/B experiment, the trained reward model showed a statistically significant increase in Proficit and SPU (sessions per user).
