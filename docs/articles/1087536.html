The junior's clumsy code used to be useful. A strange JOIN, variables tmp2 and data_new, three nested ifs where one would suffice. Following such traces, the reviewer could immediately see where the person was struggling and go check precisely there.

With an assistant, this signal is gone. The PR comes in neat: normal names, docstrings, error handling, tests for the happy path. It looks just like the work of someone who understands what they are doing. However, the error might be in a single line, and you can no longer find it by appearance, so you have to look at everything.

Juniors close tasks faster with AI, but this only increases the senior's workload.

Generating Became Cheaper, Checking Did Not

Here are two descriptions for the same PR. The first: "Here's the code." The second: "I chose this algorithm because the input is no more than a couple of thousand records; I ran it on an empty list and on duplicates; it will break if the API starts returning paginated responses." The code is the same. In the first case, the reviewer has nothing to check except the code itself, and they solve the task anew: they read the documentation of the called API, run tests, think about parallel requests. In the second, they have something to build on: run the same empty list, see what happens with three thousand records, open the API documentation on pagination. The model will, of course, write such a description too, and you shouldn't take its word for it. The benefit is that it can be quickly double-checked.

When the only thing between the task and the result was the prompt, the intermediate steps (hypothesis, discarded options, how it was tested) are simply absent, and the reviewer will have to reconstruct them.

It's Especially Painful in Infrastructure

Suppose a service has an SSE endpoint behind nginx. Events arrive in the browser in batches, with delays, and if the backend goes silent for more than a minute, the stream breaks: proxy_read_timeout defaults to 60 seconds. A junior asks the model and brings a fix:

location /api/stream/ { 
 proxy_pass http://backend;
 proxy_buffering off;
 proxy_read_timeout 3600s;
}

If the batching is caused by nginx buffering, this config fixes both symptoms.

But what did it change along with it? With buffering turned off, nginx sends the response to the client synchronously, as it receives it, and a slow client keeps the upstream open while reading (and if the backend uses one worker per connection, then the worker too). This is not important for SSE; the connection lives long anyway. But if proxy_buffering off was set not in this location, but in server {}, all regular responses will go the same way. And proxy_read_timeout limits the pause between two reads from the upstream, so nginx will now only interrupt a truly stuck upstream after an hour of silence.

Perhaps the backend should have sent keepalive comments every half minute, and left the timeout as is? Where did these lines end up, in the location or higher? How was the effect measured, and how to roll back? Buffering, by the way, can be turned off by the backend itself, with the header X-Accel-Buffering: no for the relevant responses, without touching the config (it doesn't change the timeout in this case).

If the answer to all this is "the model suggested it," the reviewer goes to the nginx documentation and figures it out themselves. They do the task a second time, and then explain why the first version was dangerous.

What I Would Change

I wouldn't ban assistants. AI significantly speeds up the work for a strong engineer precisely because they can verify the answer, and that's what juniors need to be taught.

It makes sense to change the requirements for submitting work, and these are long-known requirements that were simply managed without before. The task should be accompanied by assumptions and how the result was verified: a test, EXPLAIN, a query on staging, metrics before and after, and for infrastructure, also a rollback plan. All of this should be verifiable without the model. And the chunks should be small: a PR with a thousand generated lines cannot be reviewed in a reasonable time.

There's also a very simple test: close the chat window and ask the author to explain the solution verbally. Why this timeout, what happens after a restart, what happens on an empty input. As long as the author cannot answer these questions without the open chat, the senior will have to check the task for them.
