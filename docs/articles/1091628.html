Where It All Began

I'll Start by Telling You About Myself

I'm someone who somehow ended up in IT. I'm not a programmer, I'm not an engineer. My experience is exclusively around projects and products. I worked for a software vendor for a long time and saw how projects should and, most importantly, shouldn't be done, across various types of businesses.
I'm also a musician, I regularly perform my own material, and until January 2026, I performed with a pre-assembled, calibrated, and learned setup of hardware synthesizers.
This is the so-called Dawless format, where you create music without using a computer.

But in January 2026, I had to sell everything, for reasons not important, it just happened.
And I started looking for solace in Ableton, thankfully I've been using it since I was 17, so getting back into it wasn't difficult.
I bought an AKAI APC 40 MK1 controller and started trying to play live.

This is where I hit a snag. All the plugins I came across were mainly designed for mouse-based work in the studio. This means they clearly lack performability. Yes, you can set up the perfect sound, automate everything down to the smallest detail, and record a track. But for live performances, where you play or improvise, this is no longer suitable.

Here We Get to the Main Topic. I Installed Claude Code

First Steps

In short, my impressions in the first few days were: it felt like I was given a magic wand, and all I had to do was say the right spell to get the desired result. That's how impressed I was. Everything I had wanted to do before but couldn't due to lack of skills became accessible to me.

The first thing I made was a drone synthesizer, I immediately went all out—16 oscillators, mutual modulation of several types, modulation by incoming audio signal, an effects block.
It was done in about a day. I tested it a bit, found a few bugs, but it didn't really grab me.

Then I made a delay, then something else (I don't remember the exact chronological order anymore)

First Grand Idea

And then I decided to create a super-ultimate synthesizer that generates any sound based on a text prompt to an LLM. But not just generating audio, but assembling a patch that would suit that description.
When I somewhat grasped this idea, I realized I needed to create a specific set of modules for the synthesizer to build any sound from them. I needed oscillators, LFO generators, envelopes, filters, effects, and so on. The initial list came out to about 40 modules (I don't remember the exact number now).


My process looked like this:

  1. Discussed the list of modules with DeepSeek, refined and expanded it. A rough plan was made on how to implement them. I perceive it as a very well-read, top-student: it does a lot of things correctly, but can make mistakes in some global aspects.

  2. Claude criticizes everything written by other LLMs to shreds, saying it's clearly written by a dilettante: everything needs to be done differently.

  3. The final technical specification is created, and we start working.

The Idea I Brought to This Task

Before this, each of my plugins was a separate entity with its own hardcoded audio path. The modules inside were repeated, but you could only build something new from them by creating a new plugin from scratch.
Here, I decided to flip the scheme. The sound is described not by code, but by a connection diagram: which blocks to use (oscillators, filters, saturation, delays, reverb), how to connect them, and what to modulate with what. The diagram is saved in a text format, a JSON patch. A language model can write text. This means the model can "assemble a synthesizer" from a phrase like "cold rusty drone at dawn," all that's left is to create an engine that executes this diagram.

But the local LLM required further fine-tuning and a quality dataset (I had one collected, but it clearly needed validation and corrections). Therefore, I decided to postpone the local version and simply connected the DeepSeek API, which, with a pre-prompt, was good at creating patches.

How the Other Plugins Came About

Next, I decided not to bother with these super-ideas involving LLMs anymore, and at this point, I realized I had a universal constructor for any synthesizer or effect I needed.

This is Where Work with Rules for Claude Began

The main rule was maximum reuse of all components. My idea was that if we improve something in one synthesizer, it should improve in all of them. But then the question arose: if we break something somewhere, it breaks everywhere, so review rules were created—touched the common core—tests for all plugins.
Then a separate sub-agent reviewer appeared, which accumulates tasks during the day and, on command, runs at night to perform a review—to avoid spending the daily token limit.

Thus Began the Plugin Creation Marathon

Everything was more or less done according to one scheme:

  1. Discussion

  2. Writing the first version of the technical specification

  3. Rewriting the technical specification

  4. Implementation with preliminary verification:
    Each plugin was tested even before the interface was created, as one of the rules stated—the core does not depend on JUCE. Pure C++, which compiles with any compiler and is tested without VST wrapping. Essentially, several sound examples were generated; if everything was suitable, we moved on; if not, we refined it.

Improving Sound Quality and Workflow

When there were more than 10 plugins, I started to wonder—do they sound good? After all, they were made by AI, and I didn't want them to sound like the simplest plugins.
Thus, the audit was born.
It took about two weeks: the first week was for the audit itself, the second for fixing what was found. To properly guide the AI, I delved into the topic of "How to make plugins sound better."

As a result, the following plan was developed:

  1. First, investigate, don't fix anything. Until there are facts, don't touch the code.

  2. Study how others do it. Claude analyzed 18 sources, from scientific articles to FabFilter's approaches: how to combat digital dirt in saturation and distortion.

  3. Set up a measurement bench and take measurements "before" any edits. Now, these measurements are verified by CI.

  4. Go through the entire core step by step. Each finding is recorded with numerical indicators, not with the word "seems."
