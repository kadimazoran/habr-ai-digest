Ilya Kuchmin, author of the "AI Agents Development" course, proposes a thought experiment:

You and your team are on a raft in the middle of the ocean. You can only keep one thing. Shark repellent, an astrolabe, or life jackets for everyone. You must agree unanimously in 10 minutes.

Now, let's put 32 GPT-6.2 Astra agents on that raft. I'm afraid life jackets will be needed before they agree.

The article compares how different models divide tasks and communicate in teams of 8, 16, and 32 agents. For some models, additional participants helped speed things up, while for others, the result only worsened as the team grew.

In 1975, Fred Brooks observed that adding programmers to a project that is already behind schedule will make it even later. Each new participant adds more coordination overhead than useful work. Early studies of AI agent teams showed a similar picture: considering coordination costs, multi-agent systems often performed worse than a single agent [1–4].

We decided to test if this holds true for modern models. To do this, we took performance optimization tasks and studied how increasing computations during model operation affects program acceleration and the coordination methods that emerge in teams.

A single Claude Opus 5.5 agent accelerated NumPy tasks 3.7 times in two hours. A team of 32 Opus agents achieved 18.9 times acceleration in the same two hours. GPT-6.2 Astra showed the best result among single agents, but its teams performed worse as they grew larger.

The agents were not instructed on how to organize teamwork. Teams of different models organized it differently, which affected the outcome. Successful teams rarely exchanged private messages; participants claimed tasks and posted results on a shared board. In less successful teams, everything went through a coordinator, whose inbox grew with each new agent.

The second decisive factor was the nature of the task. If the codebase had many independent problems, each additional agent could contribute. If the work was concentrated in a small part of the code, agents often started interfering with each other.

Agent Habitat

In Replit, the agent team is largely structured like a development team. Each agent—both coordinator and executor—is a full-fledged Replit Agent with its own isolated cloud environment. It can build, run, and profile code without interfering with others. Agents work with a shared repository, and changes are merged via branches and commits. They exchange information through a shared discussion board, direct messages, and statuses, private messages, and work logs that allow learning about another agent's attempts without interrupting them.

Agent Habitat provides the necessary computational resource flexibility. Each isolated environment is a separate virtual Linux machine, with CPU, memory, and disk resources scaling as needed. This allows a coordinator to quickly launch hundreds of executors, and a single agent to work in multiple environments simultaneously. Network access, credentials, and runtime actions are restricted and tracked separately for each agent. The execution state is reliably recorded, so the team can resume work after a failure.

How to Apply Agent Teams in Practice

Models have learned to coordinate actions, and the necessary infrastructure for teams is now available. Therefore, such systems are beginning to provide value in real-world tasks. The Missions product makes them accessible to users: simply set a goal in Replit, and it will launch a team of agents to achieve it.

The research question now is not whether agent teams can work at all. It's more important to understand when a team outperforms a single agent, which models are better at teamwork, and how to organize it.

Existing tests do not provide a complete answer. In many published studies, agent teams are given program creation tasks, such as from ProgramBench [5, 6]. Agents reconstruct the program, and the result is evaluated by the number of passed tests. Such tasks have two properties that limit their suitability for studying teamwork.

First, the results are additive: parts of the program created in parallel can be combined without inter-agent output exchange. Second, the evaluation has an upper limit. A single agent already passes almost all tests, so a team can finish earlier but cannot achieve a significantly higher score. In small tasks, coordination costs can negate even time savings.

Complex tasks usually look different. In research and many engineering tasks, progress is made through search and experimentation: ideas that might not work must be tried, others' findings must be considered, and partial results that don't automatically add up must be combined. To test teamwork, a task of this type is needed, along with an evaluation that rewards additional findings, not just speed of completion.

Performance optimization fits both criteria. It requires search, has no hard result ceiling, and provides fast, objective feedback. An agent can profile a program, modify a piece of code that takes the most time, and quickly check if it has accelerated while maintaining the same result. There is no upper limit to the evaluation: it's unknown in advance how much the code can be accelerated.

Agents can divide work, but they cannot completely ignore each other. Changes to shared code conflict during merging, and without exchanging results, participants repeat each other's failed attempts. The quality of coordination directly affects the final score: a well-coordinated team can find more solutions than a single agent, while a poorly coordinated one may perform worse.

Optimization-Bench

We are releasing Optimization-Bench—a set of performance optimization tasks on fixed versions of popular open-source libraries. In each task, an agent receives the library's source code, execution code with a realistic workload, strict result requirements, and an isolated verification system. The goal is to reduce the actual execution time of the workload while adhering to strict constraints.

We chose libraries where profiling showed that the main part of the execution time is spent on the library's own code, not on external dependencies. Thus, the most time-consuming parts are in files that agents are allowed to modify, and they have a real opportunity for optimization.

Comment from Ilya Kuchmin

The task itself is not that important, as the main goal is to find out how well models can interact with each other and how they choose their communication methods.

For each library, several workloads are provided—tasks that it solves. They often use shared infrastructure. For example, NumPy includes quantile calculation, array sorting, and conditional filtering. We consider each individual function a separate workload. Agents are tasked with optimizing parts of the workloads related to core, frequently used library features with stable specifications.

The first preliminary version covers 14 widely used, actively developed open-source libraries. It shows that Replit agent teams can achieve significant performance gains. Below, we will detail four major libraries:

NumPy: 13 workloads, including quantile calculation, sorting, date and time processing, and random number generation.

SQLite: 12 workloads, including full-text search, indexing, JSON, and table joins.

SQLGlot: 4 workloads using the same parser and generator.

Git: 7 workloads focused on the diff library, which spans 15 files.

Experimental Conditions

Each agent was allocated 8 virtual CPU cores, 16 GiB of RAM, two hours of runtime, and standard profiling tools. Agents were required to preserve all observed results, error handling, and public interfaces. Strict rules prohibited caching between calls, separate handling of specific input data, pre-computation of results, offloading tasks to external libraries, and modifying global runtime settings such as memory allocators or garbage collectors.

Each task was evaluated in four configurations: a single agent and teams of 8, 16, and 32 agents. We tested six leading models: Claude Opus 5.5, Claude Sonnet 5.5, GPT-6.2 Astra, GPT-6 Astra, GPT-6.1 Sol, and GPT-6 Luna. All were set to a medium reasoning effort level, except for Luna, which was set to high.

The coordinator received the task requirements but no instructions on team organization. Work distribution and branch merging were entirely at the agents' discretion. They coordinated via private messages and a shared board. Each agent operated in a separate isolated virtual machine; only the repository was shared. Network access was disabled, and after execution, each run was checked for compliance. Only the final branch submitted by the end of the two-hour period was evaluated.

Evaluation of Results

Studies show that cloud virtual machines are unreliable for performance measurement: speed varies between instances and changes over time [7, 8]. Even on dedicated hardware, environment size, build order, and data placement in memory can alter results so much that the conclusion is reversed [9, 10]. The standard way to reduce the impact of these factors is through multiple measurements with interleaved comparisons [11, 12].

Furthermore, agents tend to find ways to game the evaluation system rather than solve the task itself [13, 14]. METR researchers found cases where models overwrote the timer and read the checker system's answer from the call stack [13]. And Sakana's claimed 10–100x speedup for CUDA code turned out to be due to an error in the isolated evaluation environment [15].

In Optimization-Bench, after two hours, the final branch of each run is frozen and transferred to a separate virtual machine that agents never have access to. The evaluation system rejects changes outside permitted files and rebuilds both the original and modified variants from the source code. The modified variant must pass the repository tests and produce the same output as the original on both public and hidden inputs. Additionally, it must pass generated tests available only to the evaluation system. These help detect solutions tailored to existing tests or exploiting loopholes in them.

Time is measured only on hidden inputs, on a dedicated Intel¹ machine, running checks one by one. The original and modified variants are randomly interleaved so that neither gains an advantage from a warm cache or changing conditions during measurements. The timer and correctness checker operate outside the measured process, so the executable code cannot access them.

We found that Anthropic models improved results when working in a team, with the magnitude of improvement depending on the amount of independent work in the codebase. For instance, in NumPy, with 13 separate workloads, we observed the largest jump: from 3.66× to 18.92×. Even in SQLite and SQLGlot, where single agents struggled to achieve speedup, teams showed decent results. In Git, despite seven workloads, there was the most overlap: all affected the same 15 files. Therefore, Anthropic model teams found it difficult to surpass single-agent results.

OpenAI models did not show such a dependency. In some repositories, teams outperformed single agents, while in others, they performed worse. In SQLGlot, none of their teams achieved significant improvement over a single run. GPT-6.2 Astra was the strongest in single runs for each task, but its teams' best results were with eight agents. At 32 agents, the results on NumPy, SQLGlot, and Git were worse than with a single agent.

One example of optimization is the NumPy function `searchsorted`, which determines where each value should be placed in a sorted array. In the original implementation, a binary search is performed for all search values at once: first the first comparison for each, then the second for each, and so on. When there are millions of values, this data doesn't fit into the processor's cache, and it has to be reloaded from memory at each step.

The Opus team modified the algorithm: it now processes 256 values at a time. Such a small batch stays in the cache from the beginning to the end of the search. Additionally, the algorithm skips the slower NaN-aware comparison if neither array contains NaN. For float64 input data with a large number of values, `searchsorted` became 8.7–13.1 times faster while maintaining identical results.

Analysis

The performance of a single model poorly predicted the performance of its team. The interaction scheme that the team built itself proved much more important. Opus 5.5 and Sonnet 5.5 teams outperformed single runs in all cases. At 16 and 32 agents, the median improvement was 1.30x. GPT-6 Astra and GPT-6.1 Sol teams performed no better than a single agent in most cases.

This is particularly evident with GPT-6.2 Astra. It was the strongest single agent in our tests: on NumPy, it provided more than three times the speedup of a single Opus. But as the team grew, its results deteriorated. At 32 agents, in three out of four tasks, they were worse than a single agent's results. Opus showed the opposite trend: the larger the team, the greater the gain.

Teams that could scale without losing efficiency retained information about their work where any agent could read it later. For example, Opus 5.5 sent 82% of messages to the shared board—mainly in discussions of individual workloads, where executors claimed work and reported findings. GPT-6 Astra and GPT-6.1 Sol acted oppositely. Their executors sent an average of about 22 and 20 private messages to the coordinator, respectively; Opus executors sent 1.4. GPT-6.2 Astra adopted the same habit: less than 40% of messages ended up on the board, and each executor sent about 15 private messages to the coordinator. Due to over-reliance on private correspondence, valuable information did not reach the board, and the information there became outdated.

In the most successful teams, the coordinator distributed work, waited for results, and merged the resulting changes. Opus coordinators sent about 0.5 private messages per executor—usually just a final message to stop. During the NumPy run with 32 agents, the coordinator did not read the board or write to executors at all.

GPT-6 Astra and GPT-6.1 Sol coordinators, conversely, acted as dispatchers, constantly responding to a stream of messages. Luna coordinators went even further: one checked the board over 200 times, another performed a significant portion of the work themselves instead of delegating tasks to executors, and some instructed their executors to remain idle.

GPT-6.2 Astra coordinators exhibited a third scenario. During one run, executors sent them hundreds of private messages, but coordinators rarely responded or posted on the board. As a result, only a small fraction of the information from executors reached the rest of the team.

The best team results occurred when each executor was responsible for a separate workload, file, or code area and publicly indicated it. Opus teams created a separate discussion for each NumPy workload, left messages like "working on btree.c" before modifying SQLite, and agreed on work division between specific pairs of executors. With this structure, even minimal message exchange is sufficient. For example, Sonnet 5.5 communicated the least among models, but its teams consistently outperformed single runs.

The increase from 16 to 32 agents particularly highlighted the differences. For Opus, the number of private messages per agent decreased as the team grew: from 4.9 to 1.0 on NumPy and from 3.1 to 1.1 on Git. For GPT-6 Astra and GPT-6.1 Sol, each new executor increased the load on the sole coordinator. On SQLGlot, the Sol coordinator received 631 messages instead of 356, and on NumPy, the GPT-6 Astra coordinator received 615 instead of 346. The coordinator became a bottleneck, and nearly doubling the load on them resulted in almost no improvement in scores.

GPT-6.2 Astra faced the same limitation. When the team doubled, the number of messages to the coordinator increased in all four tasks—by about four times on SQLite—while scores decreased in all four. Its teams performed best primarily with eight agents, when the coordinator's inbox was least loaded.

The strongest single agents did not form the strongest teams. GPT-6.2 Astra led in single runs on NumPy, SQLite, SQLGlot, and Git, but Opus teams achieved higher scores on NumPy, SQLite, and SQLGlot. The exception was Git: all its workloads affected the same 15 files, so a large team had little to divide among participants. Here, GPT-6.2 Astra matched or surpassed Opus at any team size.

This aligns with observations from other researchers. In Cursor, teams became more effective when agents creating plans stopped implementing solutions themselves, and executors stopped planning [16]. Cognition reports that multi-agent schemes work when many can contribute, but changes are recorded sequentially [17]. Our results add an important clarification: models vary significantly in how they self-organize work. This is precisely what determines whether adding more agents will pay off.
