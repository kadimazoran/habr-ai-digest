At GTC Berlin 2026, participants in an NVIDIA workshop managed to accelerate Qwen3-32B generation from 16.4 to 24.5 tokens per second without changing hardware. For this, FP8 was used instead of BF16. Total throughput also increased, though noticeably less: from 639 to 719 tokens per second.

The experiment was conducted on a Kubernetes cluster with four 80GB NVIDIA A100s. Each participant had their own cluster where they could deploy models, change configurations, and measure performance. In addition to quantization, the session covered NVIDIA Dynamo, request routing considering the KV-cache, automatic scaling, and splitting prefill/decode between GPUs.

The material is based on the article by engineer Siim Tolk, published on November 4, 2026.

How the Workshop Went

The session took place on October 20, the day before NVIDIA's main presentation at GTC Berlin. It was led by NVIDIA architects Amit Kushwaha and Yesika Ramirez Cardenas. From 9:00 AM to 4:00 PM, participants went through three practical blocks, each starting with a short lecture and followed by work with the cluster.

Each participant was provided with a GPU server with four A100 80 GB GPUs and a ready Kubernetes environment. It already had NIM and Dynamo Operators, Envoy Gateway, Prometheus, Grafana, and DCGM Exporter installed. The practical part included 14 Jupyter notebooks, totaling about 270 code cells. Participants launched real models, generated load, and analyzed inference metrics.

First Experiment: BF16 vs. FP8

We started with gpt-oss-20b, a model with a Mixture of Experts architecture. It was deployed via NVIDIA NIM, cold start time was measured, and then API parameters affecting generation were tested: reasoning effort, streaming, temperature, maximum tokens, and JSON mode. The time to the first token was measured separately.

The next experiment was conducted on Qwen3-32B. The model was run in two variants, BF16 and FP8, after which their performance was compared using NVIDIA AIPerf. In Siim Tolk's test, each variant had 240 requests.

The generation speed for a single user increased by 49.4%, and total throughput by 12.5%. The difference between these metrics is due to the fact that the speed of an individual stream and the overall performance under concurrent requests depend on different factors, including batching, memory usage, and workload characteristics.

In BF16, 16 bits are used to represent weights, while in FP8, only 8 bits are used. This reduces the amount of data that needs to be stored and transferred. Depending on the implementation, quantization can reduce VRAM requirements and speed up inference.

There's a nuance with the hardware. A100 does not support native FP8 Tensor Cores, which appeared in newer NVIDIA architectures. Therefore, the FP8 designation itself doesn't indicate which specific computations were performed in 8-bit format. Details of the implementation are not provided in the original article, nor are the results of checking response quality after quantization.

The obtained 49.4% applies to the specific configuration of Qwen3-32B and the load test. For a different model or GPU, the result may differ significantly. After these experiments, participants moved on to vLLM metrics in Prometheus and Grafana.

One API for Multiple Models

In the second block, participants configured Envoy AI Gateway in front of three models. Instead of separate API addresses for each model, they got a single endpoint with routing by model name.

A similar idea can be seen in multimodal chats like AnyLLM: the user selects a neural network in one interface, and the request is directed to the appropriate model. The workshop covered the server-side of this approach, including routing, access control, and token accounting.

API keys, token consumption limits, usage accounting, retry mechanisms for errors, circuit breakers, and gradual model rollouts were added to the gateway. All of this was configured via Kubernetes and Envoy.

Why Gateway API Instead of Ingress

Kubernetes is no longer developing the Ingress API and recommends Gateway API for new scenarios. Existing Ingress continues to be supported, but new features are no longer being added to its specification.

Ingress allows routing HTTP traffic by domains and paths. More complex scenarios often require custom annotations that depend on the specific controller. In Gateway API, such capabilities are built directly into the specification. For example, you can send 5% of requests to a new model version or configure routing based on HTTP headers and request parameters.

Configuration is divided among several resources. GatewayClass defines the implementation, Gateway describes the entry point, and HTTPRoute sets the routing rules. Envoy Gateway implements this specification based on Envoy Proxy, and Envoy AI Gateway adds functions for serving LLMs, including model routing and token limits.

Why Limiting Tokens is Better Than Limiting Requests

In a typical REST API, the number of requests per minute is often limited. With LLMs, this approach is not always convenient, as a request with a 10,000-token context can consume significantly more resources than ten short requests.

Envoy AI Gateway can account for tokens, and Envoy Gateway applies limits through its global rate limiting mechanism. In the workshop configuration, Redis was used for this.

Retries on errors were discussed separately. If the server returned a 5xx error or the connection dropped, a retry can sometimes help. But if dozens of clients simultaneously start retrying requests to an overloaded server, the situation can worsen. Therefore, exponential backoff is used, meaning the delay between retries increases. A circuit breaker allows temporarily stopping requests to a problematic instance.

Authorization errors and incorrect request parameters are pointless to retry without correction. For LLMs, there's an additional problem: after a connection breaks, generation might continue on the server. A retry request could initiate a second generation and consume resources again.

When updating models, two methods for testing a new version were considered. Canary rollout sends a small fraction of user requests to the new model. Request mirroring copies requests to the version being tested, but only the response from the main version is returned to the user. This allows testing the new model's behavior on real traffic before a full switch.

Automatic Scaling with KEDA

After configuring the gateway, participants freed up GPUs and tried scaling NVIDIA NIM using KEDA. Standard Kubernetes HPA can use CPU and memory load, but for LLMs, these metrics don't always accurately reflect the number of requests a server can handle.

The experiment used vLLM metrics. The metric vllm:num_requests_running reflects the number of ongoing requests, and vllm:num_requests_waiting shows the queue length. KEDA retrieves values from Prometheus and scales the number of replicas up or down based on them.

GPU utilization issues in DCGM were discussed separately. On nodes with multiple GPUs, metrics can sometimes be incorrectly associated with pods. As a result, monitoring might show 0% utilization even when there are requests.

Another peculiarity relates to scaling down. A NIM container might take several minutes to load a model. If replicas are deleted and created too frequently, startup time will interfere with request processing. Therefore, the example recommended gradually reducing the number of replicas, with an interval of about ten minutes.

NVIDIA Dynamo: Splitting Prefill and Decode

The third block was dedicated to NVIDIA Dynamo. Qwen2.5-32B-Instruct in GPTQ Int4 format, run via vLLM, was used for the experiments.

LLM request processing consists of two main stages. Prefill processes the input prompt and generates the KV-cache. During this stage, the model performs many computations, especially with long contexts. Decode generates the response sequentially, one token at a time. Here, performance is often limited by memory bandwidth.

In a standard configuration, both stages are performed on the same GPUs. This mode is called aggregated serving. Dynamo allows splitting prompt processing and response generation between different GPU groups, transferring the KV-cache from prefill-workers to decode-workers.

At the workshop, two pairs of A100s connected via NVLink were used. Participants sequentially tested aggregated serving, KV-cache-aware routing, and disaggregated serving. Each configuration was tested separately.

Splitting prefill and decode allows scaling them independently. For example, with many long input documents, more resources might be needed for prefill. If users generate long responses simultaneously, the load on decode increases.

However, splitting is not always beneficial. Transferring the KV-cache between GPUs also requires resources, so with a small number of requests, standard aggregated serving might be more efficient.

KV-Cache-Aware Routing

Dynamo has a KV-cache-aware router. Its task is to reuse already processed context fragments.

Imagine a chat where a user sends several messages consecutively. With each new request, the server might receive the entire previous conversation. If the beginning of the prompt has already been processed and its KV-cache is stored on one of the workers, some computations can be skipped.

The router tries to send the request to the worker that already has a suitable cache. It also considers the current load. This approach is particularly useful for long dialogues and RAG systems where different requests reuse common prompt parts.

Dynamo also includes a Planner, which monitors the load and adjusts the number of prefill and decode workers. Another mechanism, ModelExpress, speeds up the startup of new workers. Instead of reloading weights from storage, a new instance can copy them from an already running one.

An additional notebook was dedicated to Grove, a tool for coordinated scheduling of related pods. It helps place groups of prefill and decode workers considering their joint operation.

Other Tools

During the session, several features were discussed that could be useful even without Dynamo.

Logprobs allow obtaining the log probabilities of generated tokens. These can be used to analyze model behavior and identify responses for further verification. However, the probability of a token should not be directly equated with the confidence of the answer.

A fixed seed helps achieve more reproducible results during testing. It does not guarantee completely identical output across all configurations. FlashAttention, in turn, computes attention in blocks and reduces GPU memory accesses. This speeds up computations and reduces memory consumption while preserving the exact attention result.

NVIDIA tools for performance evaluation were mentioned separately. AIPerf measures time to first token, inter-token latency, and throughput. It was used directly at the workshop.

AIConfigurator helps compare aggregated and disaggregated serving configurations, as well as estimate the required number of workers. AISimulate models inference and Dynamo configurations without actual deployment. The tool is currently experimental and intended for evaluating options rather than precise capacity planning.

Final Assignment

At the end of the workshop, participants were given the Qwen3-1.7B model, which they hadn't worked with before. They had to independently prepare a Dynamo configuration, deploy the model in aggregated and disaggregated modes, conduct testing via AIPerf, and compare two variants of the prefill/decode replica ratio.

After measurements, they had to choose a suitable configuration and justify their decision. There were a total of seven assignments worth ten points. To receive a certificate, all of them had to be completed.

What Can Be Applied in Practice

For a home computer with a single GPU, most of the workshop tools are overkill. KEDA and splitting prefill/decode are designed for infrastructure where load can be distributed across multiple GPUs and model instances. However, experiments with quantization, FlashAttention, and inference engine settings are quite applicable to local LLMs.

When comparing configurations, it's useful to measure not only tokens per second but also time to first token, VRAM consumption, and response quality. If the model serves many users, routing, queue metrics, KV-cache reuse, and automatic scaling become relevant.

In the original experiment, FP8 accelerated Qwen3-32B generation by almost 50% for a single user. But without testing on a specific model and hardware, one should not expect the same increase.
