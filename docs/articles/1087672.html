Hello! My name is Vladimir Allamov, I am an Application Security engineer in the product security team at Avito. Spoiler: the human factor was involved.

In May 2026, Google's Gemini AI model, during security testing conducted by Irregular, gained access to the protected services and websites of three real companies. This was a so-called Capture the Flag (CTF) event. In such tests, it is necessary to find vulnerabilities and extract pre-placed information – "flags" – from a controlled target system.

Gemini was tasked with obtaining data from the software of a fictional company in an isolated environment, but due to a configuration error, the test system allowed the model to access real internet services. Since the fictional companies in the test task had the same names as real organizations, the model mistakenly identified them and began interacting with their services. In one case, Gemini tried passwords until it gained access to a protected service. In two other cases, the model discovered and used credentials found in public repositories for access. What actually happened

Gemini did not overcome isolation on its own but gained internet access due to a configuration error. Therefore, the word "attack" is both appropriate and inappropriate here if intent is implied – it was not an attack: the model was solving an educational task and considered the targets fictional. If we describe the actions themselves, it is a full-blown attack.

Brute-forcing passwords and logging in with someone else's leaked credentials to a real system without the owner's permission is classic unauthorized access. The SOC of the affected company would see a normal incident, and from a legal perspective, it's not who performed the action that matters, but who is responsible for it: the operator or the agent's owner.

The most accurate way to put it would be: "unauthorized access of an autonomous agent to third-party systems due to the failure of the test environment's isolation." This is not a sandbox escape: the door was open, the model did not break it down. But everything the model did behind that door were its own actions. The configuration error explains why the model ended up on the internet, but it doesn't explain why the model started trying passwords for a system it knew nothing about.

From an information security perspective, the interesting part here is that the model, having gained access to the real internet, continued to perform its task.

Configuration errors are common. OWASP TOP-10 includes Security Misconfiguration – a category that is currently the second most popular. Open outbound traffic is one of the most frequent errors in any infrastructure, and it will happen again. More importantly: the model checked whether the target was within the allowed scope only after gaining access.

Any pentester, before the first request, verifies that the IP address or domain is within the agreed scope, otherwise, it's not a pentest but a violation of Article 272 of the Criminal Code of the Russian Federation. Gemini acted the other way around: it entered first, then realized the system was not its own. In practice, this means that the boundary of what was permissible existed only in the model's "mind" and triggered with a delay.

There is a third layer that is rarely discussed: the affected companies. The password was successfully guessed, and the keys from public repositories turned out to be working. Most likely, there was no limit on login attempts, no MFA, and no rotation of leaked secrets. The agent didn't need to do anything complicated: it exploited what has been a low-hanging fruit for any attacker for years.

So, in this case, it's like a match-three game: collect and it's gone. Here, three layers failed: the isolation of the test environment, the model's "understanding" of boundaries, and basic hygiene on the part of the victims.

For modern AI agents, such behavior is not unusual. Today's models can independently build such a chain of actions without a pre-written human scenario. I would say that for agentic models of 2025–2026, this is a routine task. The chain "find target → search for information in open sources → find credentials → log in" is the basics of reconnaissance and initial access. You don't need to script the scenario for the agent: just give it a goal and tools, and the model builds the plan itself. That's the point of agency.

There are much more complex examples. In November 2025, Anthropic described the GTG-1002 spy campaign: the company estimated that 80–90% of tactical operations were performed by an AI agent. In 2026, Anthropic models in similar incidents used SQL injection and a debug page with secrets, and one internal model scanned about 9,000 targets. OpenAI models found several zero-day vulnerabilities in JFrog Artifactory, used them to escape the isolated environment, and penetrated Hugging Face. Against this backdrop, password guessing and key searching on GitHub are child's play.

Therefore, the right question is not "can the model do this," but "when and why will it stop." The answer should be provided by technical limitations of the environment, not the model.

How to safely give tools to agents

There's nothing new here: an agent is an untrusted user with very high operating speed. Therefore, the minimum set of technical restrictions for an AI agent provided with a browser, command line, or the ability to access external services is as follows:

  • Execution isolation. A one-time microVM or container with enhanced isolation (gVisor, Firecracker). No shared credentials, SSH keys, or VPNs with the host. Access to cloud metadata (169.254.169.254) is blocked.

  • Default-deny network. Outbound traffic is prohibited at the infrastructure level, not in the agent's code. Access only through an egress proxy with an allowlist for domains. DNS is also under control: DNS tunneling has not been canceled.

  • Isolation check before each run. Autotests must confirm that the environment truly cannot see the internet. This exact control was missing in the Irregular incident, and Anthropic explicitly named it among the missing measures.

  • Separate identity and minimum privileges. The agent has its own service account, short-lived tokens with a narrow scope. The agent does not see secrets: they are provided by a proxy or broker.

  • Tool control. Read-only by default. Irreversible actions (writing to production, deletion, sending data externally, payments, deployment) – only after human confirmation. Limits on the number of steps, time, and budget.

  • Observability and emergency stop. Full log of every tool call and every network connection, real-time monitoring, and a "stop" button that actually works.

A sandbox, blocking outbound traffic, and an allowlist of permitted resources are the necessary minimum, but they are not enough. Every address on the allowlist is an attack surface. The most striking example is OpenAI's incident with ExploitGym. The only permitted exception in the network was a package proxy registry, and it was this that the models hacked to get out. If you allow github.com, the agent can upload data there. If you allow a package registry, it can publish a package there (Anthropic's model, which had access to the entire internet, did just that: it published a package on PyPI, and 15 real systems downloaded it).

What I would add in a real infrastructure:

  • Policy engine for tool calls. Every agent action is checked against an explicit policy (who, what, on which object), not just network-wise.

  • Synthetic names for test targets. Use reserved zones (.test, .example, .invalid) and credentials that cannot exist in the real world. In the Gemini case, the fictional company had the same name as a real one, and this was predictable.

  • Scope check on the infrastructure side. Before allowing a request to the target, the wrapper verifies that the address belongs to the test range.

  • Canaries and honeytokens. Trap keys and credentials inside and around the environment: their use immediately indicates that the agent has gone beyond its boundaries.

  • Automatic safeguards. Stop on anomalies: N failed logins in a row, access to a new domain outside the allowlist, a sharp increase in the number of requests.

  • Independent oversight. A separate system or model that monitors the agent's actions from the outside and can stop it, without relying on its own conclusions.

  • Protection against prompt injection. Perhaps the only specific item in this list. All external content (web pages, emails, tickets, READMEs) is considered untrusted. An agent that reads untrusted data should not simultaneously have access to sensitive systems and the ability to send data externally.

  • Processes. Changes to the test environment configuration – only after review. For contractors testing models – contractual requirements for isolation and incident notification deadlines.

Why you can't rely on the model's self-stopping

You cannot rely on the model's ability to independently recognize that it has gone beyond the allowed environment and stop working. There are four reasons why, from an IT security perspective, this is not a control measure but an additional safeguard.

Reason #1: it triggers after damage. Gemini stopped after access had already been gained. As a control, it's a detection measure at best, not a preventive one.

Reason #2: it's non-deterministic and not verifiable. We cannot guarantee that the model will stop next time, with a different task formulation, or in a different version. Anthropic's data on similar incidents: Claude Opus 4.7 continued the attack, having already recognized that the environment was real. Mythos 5 "reasoned" that it was still in simulation. Only the newest model stopped. Behavior changes from version to version, and you cannot rely on this.

Reason #3: the models were explicitly told that everything around them is a simulation. The model makes decisions based on the data it was given, and the data lied to it. The same will happen with an external attacker who, through prompt injection, convinces the agent that "this is allowed."

Reason #4: we wouldn't build human protection this way. No one builds access control on the premise that "the employee/hacker will figure out on their own that they shouldn't go there."

However, the fact of self-stopping is valuable. It's a useful signal for monitoring and a good sign of progress in model training. But in the threat model, it should be the last line of defense after network, access rights, and monitoring, not instead of them.

How an agent differs from a chatbot

When an autonomous agent capable of independently performing a sequence of actions and choosing tools is used instead of a regular chatbot, the threat model fundamentally changes. A chatbot's risk lies in its content: harmful response, leakage in text, bad advice. A human stands between the model's response and real-world action, and they filter it.

An agent's risk lies in its actions: the human is removed from the loop, and the agent has privileges, tools, and a speed of hundreds of operations per minute. Essentially, the agent becomes a new entity in the infrastructure – a non-human account with privileges.

This leads to new threat classes:

  • Confused deputy via prompt injection. External text is turned into actions with the agent's privileges.

  • Abuse of tools and privilege escalation.

  • Achieving goals bypassing rules (reward hacking). OpenAI models penetrated Hugging Face not with malicious intent, but to get answers for a benchmark and "solve the task."

  • Cascading failures in multi-agent systems.

  • Agent memory poisoning.

There is also an important conceptual change. Previously, the model was an object of protection or an attacker's tool in the threat model. Now, the agent itself must be considered a potential source of threat: not malicious, but persistently pursuing its goal and not always understanding boundaries. There are already industry guidelines for this, such as OWASP Top 10 for Agentic Applications.

What will change with the development of autonomous agents

The advent of autonomous AI agents significantly changes the cyber threat landscape compared to ordinary LLMs that only generate instructions or code.

LLMs that write instructions and exploits have lowered the knowledge threshold. Agents remove the execution limitation: time, skills, and the number of people available to the attacker. Previously, even with a ready-made exploit, an operator was needed to conduct reconnaissance, adapt the attack to the target, handle errors, and move forward. Now, an agent can do this – in parallel, around the clock, and almost for free.

The main effect is economic. It becomes profitable to attack the "tail": thousands of small companies with weak passwords, leaked keys, and unpatched services. Previously, attackers simply didn't have the resources for them. The Gemini case is exactly about this: no rocket science, just mass exploitation of basic errors.

The second effect is that the time between vulnerability publication and its mass exploitation shortens, meaning patching needs to be faster.

But this asymmetry works in the other direction too. Defenders gain the same capabilities: vulnerability discovery (Big Sleep, XBOW), automatic patching (according to Google, Gemini 3.8 Flash Cyber provided 2.6 times more correct patches for Chrome than the best commercial models), log analysis, and triage. Whoever integrates agents into their processes faster will win.

The most dangerous boundary is not where the model gains access to a browser, command line, credentials, and corporate APIs, but where it is allowed to independently combine all these tools into multi-step scenarios.

It's not a single tool that is dangerous, but a combination of three things: autonomy (no human between decision and action), privileges (credentials, write access), and untrusted input (internet, emails, third-party code) plus the ability to reach out. This is also called the "deadly triad": access to private data, untrusted content, and a channel to the outside world. Meta formulated a practical "rule of two": an agent without human supervision should have no more than two of the three properties – it processes untrusted input, has access to sensitive systems, or can change state or reach out.

Each tool individually is manageable: a browser without credentials, a shell in a disposable container, read-only API. The risk multiplies when the agent is allowed to freely combine tools into chains. The Gemini case illustrates this well: the model had no credentials of its own; it obtained them through the browser and immediately used them. Limiting one tool is not enough if the agent can "buy" the missing link through another.

If we still have to choose one most dangerous element, it's broad credentials with write access. They are what turn a model error into a real action on behalf of a real account.

Why incidents will repeat

As models' capabilities grow, similar incidents will almost certainly become more frequent, even if the models themselves have no intent to cause harm. There are three reasons for this:

  • Scale. There are more agents, and more runs: Anthropic alone tested over 140,000 runs in this investigation. With such volumes, rare failures become regular.

  • Capabilities. The stronger the model, the more paths it finds, including those that the environment authors did not anticipate. Zero-day vulnerabilities in OpenAI's proxy registry are exactly such a case.

  • Persistence in achieving goals. Malicious intent is not needed: models optimize for the task, and bypassing restrictions can be the shortest path to the result.

What companies where agents are already used should do

Part of the growth will simply be the effect of better detection and disclosure, and that's good. In a corporate environment, incidents will look mundane. An agent can delete a production database (as in the Replit incident in 2025), trigger a data leak through prompt injection in an assistant (as in the EchoLeak case in Microsoft 365 Copilot), or post a secret to a public repository. The frequency will increase with adoption, and the severity of consequences will depend solely on the restrictions around the agent.

Models will better understand boundaries, but this is no reason to weaken controls. If employees start using AI agents with access to internal systems, companies should already be implementing practices such as:

  • Inventory and policy. Know which agents, extensions, and MCP servers are in use. Approve a list of allowed ones, and block shadow AI.

  • Separate accounts for agents. An agent should not operate with full employee privileges. Separate service accounts, OAuth with minimal scopes, short-lived tokens, secrets from a vault, not in config or prompts are needed.

  • Minimum privileges and human in the loop. Read-only by default. Irreversible operations (production changes, deletion, sending data externally, payments) – only after human confirmation.

  • Isolation. An agent with a shell works in a dev container or VM, not on a laptop with VPN, SSH keys, and production access.

  • Traffic control. All agent traffic goes through an LLM or MCP gateway: with logging, DLP, and outbound connection restrictions.

  • Monitoring and response. Agent tool calls are logged to SIEM, there are detection rules for anomalies, and the IR playbook has a separate scenario for "AI agent incident" with a clear stop procedure.

  • Protection against prompt injection. Email, tickets, web pages, and third-party repositories are untrusted input. Agents that read them should not simultaneously have access to sensitive data and an outbound channel.

  • Supply chain. MCP servers and plugins are third-party code with privileges. They need to be reviewed, versions fixed, and updates checked.

  • Basic hygiene. The Gemini case is a reminder: scanning repositories for secrets, quick rotation of leaked keys, MFA, limiting login attempts, and blocking protect against both AI agents and humans.

  • Red team before rollout. Before mass deployment, test the agent scenario with an attack: can external documents force the agent to do something it shouldn't.
