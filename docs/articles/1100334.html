tbook Four Months Later: Readers, Dictionaries, and v2 of the Format

In July, I wrote about searching for a foreign language e-reader and the birth of the TBook format. Half of that article was about getting cheap LLMs to produce alignment without positional drift. Four months have passed since then. An app has been released on Google Play, a desktop reader for three OSs has appeared, along with offline dictionaries, an online converter with a shared library and a Telegram bot, a GUI converter with ready-made binaries, two dozen reports on translation quality experiments—and most importantly, the second version of the format. You are reading a novel in English, click on an unfamiliar word—and the reader highlights something completely different in the translation. The file is valid: the check said "everything is fine." It was precisely these cases that made me rework tbook.

In the first article, I described how I created a book format with a ready-made translation and word-by-word alignment: you click on a word in the original, and you see the sentence translation with the correct highlighting. Everything works offline because the book already contains the translations. In four months, an Android app on Google Play, a desktop reader, offline dictionaries, a web converter, a shared library, and a local GUI have grown around this idea. And on September 29th, the second version of the format was released. Here's what has changed for the reader—and why improving the models alone wasn't enough.

From Experiment to Everyday Reader

Android. TReader has reached version 1.14. It now includes an e-ink mode without animations, English word transcription with a choice of American and British pronunciation, and text-to-speech for words or sentences. Bilingual mode displays the original and translation mixed, in two columns, or line by line. Settings, help, and the tour are available in nine languages;

Desktop. TReader Desktop is built for Windows, macOS, and Linux. Inside Tauri v2: Rust handles the book, search, and dictionaries, while Svelte 5 renders the interface in the system WebView. The binary is about 6 MB. It also features translation on click, transcription, bilingual mode, text-to-speech, footnotes, images, tables, and search. On Linux, .deb, .rpm, and .AppImage are available; the macOS build is not yet notarized, which complicates the first launch.

I would gladly cooperate with macOS/iOS developers to release versions for iPhone and Mac.

Both readers open v1 and v2 books, so there's no need to migrate your old library.

Dictionaries. A tap answers "what does this word mean here," but a learner also needs a dictionary entry: part of speech, gender, pronunciation, other meanings, and forms. For this, .tdict was introduced—an SQLite file that readers download separately and then use offline. It contains three tables: metadata, dictionary entries, and word forms. When searching, the lemma takes precedence over form matches: this way, the exact word isn't lost among similar results. The data comes from Wiktionary via kaikki.org and is distributed under CC BY-SA 4.0. All 20 directed pairs between English, Russian, German, Spanish, and Italian have already been compiled. The desired pair can be downloaded from the internal translation server within the app; you don't have to download the entire collection.

Conversion Made More Accessible

The open-source local converter is still available. However, building from source and using the local LaBSE aligner requires Go, Python, and a model of about 1.8 GB. That's why the web converter was introduced: upload EPUB or FB2, select the language and model, monitor the task, and get a .tbook file. The same converter from the open repository runs in the background. The result can be added to the shared library with search by books and languages; a Telegram bot allows searching the catalog.

The Converter Learned to Remember the Book

Previously, Irene could become "Ayreen," "Irin," and "Iren" within a few chapters: the translator processed small text chunks and forgot previous choices. Now, the converter pre-compiles a glossary of names and terms and passes it with each request. It can be built before translation and manually corrected via --only-glossary—this was added by Nikita Pimkin (NikPim), the first external contributor. Thank you!

Measurements helped determine the size: 40 entries covered 61.9% of term mentions in the test book, and 300 entries covered 97.2%. Gender tags were added for characters. On text the model didn't know beforehand, correct agreement improved from 45.2% to 97.6%.

The glossary is compiled separately for each translation language. This is important: if you send Russian name variants in a request for German, the model might obediently carry them over into the German text. And previewing via --only-glossary gives a chance to correct a heroine's name before it spreads across hundreds of sentences.

Alignment has also changed. The local LaBSE on CPU handles the bulk of sentences, with LLM refining about 4% of complex cases. The hybrid mode is 5–8 times faster than pure LLM alignment with better word coverage. Separate idiom processing taught the aligner to link gave up with "бросил" (quit) as a whole, not just through up: on the tested novel, the proportion of working taps increased from 79% to 96%.

Coverage figures require caution: a word might be highlighted but still lead to the wrong place. Therefore, aligner variants were compared based on what the user sees when tapping, not just on link completeness. This is especially noticeable for idioms: if gave up was split into two independent parts, the highlighting is formally present, but the meaning is lost.

Translation proofreading, punctuation normalization for Russian, German, and French, and new providers have been added: gonka, Claude via local CLI, Ollama, and llama.cpp. You can now choose between cloud and local models, although their quality varies. About two dozen experiment reports are located next to the converter as GitHub issues: useful changes underwent blind comparison, and ideas that lost were not hidden. More steps in the pipeline do not guarantee a better result.

Why .tbook v2 Had to Be Released

In September, I compared nine format variants on a single corpus. Only 62.6% of taps in v1 produced clean highlighting. This is the result of a specific test, but the reasons were in the format's design. v1 assembled a page from sentences, so a segmenter error could break a word. Word links could be mixed up, and the file would still pass structural checks. Numbers were not recognized as tappable words at all. Adding a language required recompiling chapters.

I also tested other approaches: SQLite, binary representation, an overlay on EPUB, and alignment directly within the reader. The latter reproduced only 47.5% of old taps. The choice fell on the familiar ZIP with JSON, but with a different text and link model. In the tested set, none of the 132 numerical tokens in v1 were tappable—a minor detail until you try to read an address or date.

In v2, I changed four things.

The paragraph is stored whole. Sentences became ranges within it: "text": "Hello. Goodbye.", "sents": [[0, 7], [7, 15]]. If the segmenter makes an error at the boundary, the page text remains intact: the reader no longer stitches it together from chopped phrases. Segmentation affects translation but doesn't corrupt the original on screen.

Each language has its own overlay. The original text resides in the book's skeleton, while translations and links are in separate files by chapter and language. For example, text/ch1.json contains the original chapter, and gloss/ch1.ru.json contains the Russian translation. A new language can be added without rewriting the skeleton. In the test, an eight-language book decreased from 6.96 to 3.55 MB; a single-language book decreased from 2.19 to 1.30 MB. Repeated ranges for each word are no longer stored in the archive: the reader calculates them when displaying text according to the general rule in the specification.

Each translation token has its own link. For example, 0 points to a single original word, [5, 6] points to two at once, null indicates an unknown link, and [] means a word added by the translation. These last two states cannot be mixed: "I don't know" and "I know there's no pair" are different assertions. This is also important when migrating an old book: you cannot retroactively assign it confidence that wasn't present in the original data. For languages and expressions requiring finer markup, the format has additional fields, but the converter doesn't fill them automatically yet.

The file reports what was checked. The old q metric measured coverage but looked like a quality score. In real books, 75–88% of cells had q = 1; even 16 erroneous Chinese sentences received a one. Now, the book stores the translation status, check results, and the list of checks that were run. If a judge only looked at suspicious phrases, the rest are not marked as checked. The reader can distinguish between "passed check" and "no one looked."

Archive entry hashes detect file corruption, alignDigest detects discrepancies between links and their checksum. Bookmarks rely on identifiers derived from chapter and paragraph content, so they can survive re-conversion. But no hash proves that the translation is semantically correct. It only prevents the verifiable data from being imperceptibly replaced or corrupted.

Old books continue to open. On an eight-language book, migration from v1 preserved the previous result of 836,496 out of 836,600 taps—99.9876%. The remaining 104 cases involved words that v1 had split in the middle. This is the percentage of behavioral preservation, not the percentage of correct translations.

Several Mistakes That Taught a Lot

Over the summer, about two dozen reports on hypothesis testing accumulated, including blind comparisons of variants. The most useful findings were unpleasant.

A powerful model corrupted correct data. On "The Name of the Rose," I fed it 72 suspicious sentences. After 32 minutes, it broke 49 correct alignments. Dictionary checks flagged Latin and Occitan, which the German-Russian dictionary couldn't evaluate; the pipeline interpreted "I don't know" as "error."

More coverage turned out worse. The new aligner increased the coverage of significant words from 97.84% to 99.57%, but blind comparison twice favored the previous version: extra links led to incorrect words. A more cautious algorithm that only fills gaps helped. Even with the words it restored, 15.6% of links are erroneous. For the reader, it's important that the correct word is highlighted, not how many words are highlighted.

Context can also interfere. One preceding sentence reduced proofreading accuracy from 87.1% to 80.0%; two sentences yielded a better result than either option. Therefore, the tool now rejects --context 1. And when changing models, two valid batches turned out to be translations into Chinese instead of the desired language—16 out of 544 sentences. Now, the language is checked separately.

Quality can also be lost after translation. A typography pass altered the text before verdict assembly. Verdicts were searched for the previous string, and 977 French cells went into the book without the required remarks. When preparing v2, the order of operations was changed: first, the check results are saved, then quotation marks and spaces are corrected.

Even after marking v2 as Final, a real file was found on which the migration failed: a footnote marker 10 simultaneously fell into an exception and a link. On October 20th, the converter had to be fixed and the specification clarified. This is what working with the format looks like after release.

What's Next

v2 already has places for idioms, split expressions, and word parts; now, we need to learn how to fill them and display them in readers. The aligner currently outputs character ranges, which are translated into v2 tokens when writing; direct alignment in tokens will eliminate an extra step. For the apps, full interface localization and improving macOS installation remain. But the main principle has already emerged: if the system doesn't know something, the book should honestly show it. A valid file and a good translation are not the same thing.
