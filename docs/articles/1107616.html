A couple of days ago, I posted on LinkedIn about AI development and received a rather unexpected comment from a development lead – he was extremely skeptical about AI development.

And the reasons for this skepticism are, in general, understandable. I see many people who tried AI tools a couple of years ago, when these tools were just being invented, and were not impressed with the quality – they ended up with genuine AI slop (from the English word "slop" – refuse, garbage), and have held that opinion ever since. The code seems to compile and even pass tests, but it's written completely differently from how your team usually does things, it repeats the worst parts of the project, and falls apart at the first edit.

Almost a year ago, I left my position as CTO at the carsharing service Citydrive to fully immerse myself in agent-based development, and over this past year, I've come to the conclusion that most often, the model isn't to blame, but rather the repository that wasn't prepared for the agent. In this article, I'll explain why it's so difficult for an agent to write good code in such a repository and what needs to be done to prevent slop from appearing there anymore.

A Hundred Comments on a Pull Request

I'll start with a story that happened long before any agents. Once, in 2019, I was leading the development of "VK Taxi," where we were building a taxi service directly within the social network app using the VK Mini Apps platform. The project was purely frontend, the code was written by me and one other developer, and at some point, we hired a third – a quite capable developer who, however, was used to working with completely different conventions than we were.

We didn't have any written rules, of course, so we left a lot of comments on his first pull requests. Once, we left him a record-breaking hundred comments on a pull request of about fifteen hundred lines. And no, the code was generally understandable and functional, it just completely deviated from the practices we decided to adhere to in this repository going forward. With each pull request, the comments became fewer, and after about ten, they could be counted on one hand.

But there was also a part of the approaches that he had no way of knowing about. Some of them we had already developed but kept only in our heads, and some we had abandoned after trying them once and getting burned, but there were no artifacts left in the repository about it. Only a part of the team's decisions was visible from the code, and everything else lived in meetings, in the smoking room, during breaks, and at shared lunches in the cafeteria.

A Newcomer Who Arrives for the First Time Every Morning

Now imagine that this developer resets every morning. Yesterday, he received his hundred comments and fixed everything, but today, having completely forgotten everything, he again submits code that doesn't comply with any of your agreements. Well, an agent is essentially the same newcomer, only reviewing the same mistakes day after day is a rather dubious and unrewarding task.

It's important to understand that the model itself has no memory, and with each request, the agent sends it the entire conversation history. When the context fills up, the agent compresses the conversation, and detailed instructions from the beginning of the session can get lost. And it doesn't keep the entire project in its head; it only sees what it has found and read itself.

And here's what this leads to in a typical project:

  • let's say you have a hundred modules, you write the last ten perfectly, and the ninety old ones are legacy code that you're gradually removing. The agent knows nothing about this and will take one of the old ones as a sample, perhaps the very first, the worst one;

  • integration tests in a Java project have historically been in their own folder and are connected via a profile, and the entire team has long been running them as mvn test -P integration. The agent will run a regular mvn test, Maven will write No tests to run followed by BUILD SUCCESS, and the agent will calmly decide that the tests are green;

  • newly written data is read from the master because it might take time for the write to reach the replica. A newcomer will be corrected during review once, but the agent will step on the same rake in every new session.

It's also important to understand here that the agent's errors are no longer syntactic but semantic. The code compiles, looks correct, and passes simple tests, but it's built on a false assumption – the agent misunderstood the business logic, didn't ask clarifying questions when the task was unclear, or simply missed an edge case. And finding such an error is much harder than a build failure, as it can easily be missed during review.

It turns out that onboarding an agent is exactly the same as onboarding a newcomer, except that from session to session, it only remembers what is written in the repository files, so you have to teach it through the repository itself.

Record What the Team Knows

A long time ago, I started working at Mail.ru Group, and like every newcomer, I was given an envelope with a one-page letter containing useful information – it had the intranet address, a temporary email password, the floor where tech support was located, and where the cafeteria was. Essentially, this was my AGENTS.md – a file in the root of the repository that the agent reads at the beginning of each session and which Claude Code, Codex, and other agents now understand.

And it should look exactly like that A4 sheet, meaning it should be a cheat sheet for a newcomer of a couple of hundred lines, not a fifty-page wiki page. It contains what's needed for almost every task and what the agent won't find in the code itself:

  • what this repository is and what it consists of – in five lines;

  • where things are located and which folder to go to for what;

  • build and test commands;

  • agreements that the team has in their heads;

  • a glossary of terms that only your team uses.

At the same time, there's no point in documentation that just rephrases the code. Sooner or later, it will diverge from the code, and you'll shoot yourself in the foot by creating two sources of truth, when you have only one source of truth – the code that runs in production.

The best way to gather all the knowledge accumulated by the team is to ask the agent to collect all the comments on pull requests from the last year. You'll then just need to review this list and keep what's still relevant, and the agent will stumble on these pitfalls much less often.

And if the agent made a mistake not in a rule, but in a multi-step task, for example, in how you enable a feature flag, and does the same thing next time – that's a reason to write a skill, i.e., an instruction that the agent loads when it needs it. There's no point in sitting down and writing a skill from scratch: it's better to complete a typical task with the agent and ask it in the same session to compile everything you did and describe it step-by-step in the form of a skill.

Let the Agent See the Result of Its Work

It's good practice for a developer to test and debug code after it's written, and the agent should follow exactly the same practice, but for this, it needs a full environment where all these checks can be performed. If the project is small and can be deployed locally, the agent will do it locally, and the key here is to give it clear and understandable instructions on how to build and deploy this project.

Of course, it would be great if you had a single console command that builds the entire project, but if the build is a chain of commands, that's also not a problem; the important thing is that it produces the same result every time. In this case, you can record this chain as a console script, because the agent reads the instruction text anew each time and might interpret it slightly differently, while a script always executes the same way.

If the project is too large to build entirely locally, you'll need a preview stand – a separate environment where your branch works together with the entire project. Vercel, Netlify, GitLab with its Review Apps, and Argo CD can set up such stands for pull requests, and all that's left is to teach the agent to retrieve the dynamic address of the stand from the pull request. And then it will test what it has written itself – ping endpoints and see how the data in the database has changed, or open a browser and click through everything according to test cases.

Check, Don't Ask

Any rule in AGENTS.md for an agent is a request, not a guarantee, because it might not follow it, or it might lose it when the context is compressed. Therefore, anything that can be checked by a program should be checked by a program, and here the same practices that we've used for years when we wrote code manually apply:

  • test first, then code. When a test fails, the agent is tempted to adjust the test to the code, and to prevent this temptation, you need to do the opposite – ask it to write the test first, and then the code;

  • linters that explain how to fix. The same rule about master and replica can be written as a line in AGENTS.md, or you can write a linter rule that won't allow reading from the replica immediately after writing. And if the text explains why this is not allowed and how to fix it, the agent will quickly understand what needs to be changed;

  • hooks. Claude Code can run the linter itself after each file change, whether the model wants it or not, and the agent will find out about the error immediately, not from the reviewer;

  • CI, without which you can't merge. A pull request cannot be merged until all mandatory checks have passed, and the agent should not be able to bypass this barrier, so CI configurations and tests are changed only with the approval of their owners from CODEOWNERS. And all checks should take 20–30 minutes, otherwise CI will destroy all the speed that agents bring.

Reviews have also changed. Previously, a developer closed three to four tasks a week, but now they can close three to four a day, and it's physically impossible to read all this code line by line. Therefore, one agent writes the code, and another reviews it in a fresh session, because the one who wrote it remembers what and why they intended to do, and checks the code with the same context with which they wrote it. Human attention is needed where decisions made are difficult to reverse – for database schemas, access rights, security, and architecture, and to avoid searching for these places in a 20,000-line diff, the agent should itself put key decisions in the pull request description.

Don't Let the Agent Break Everything

Everything you can do yourself in your terminal is also available to your agent, and if it breaks something, you'll be responsible because the agent acts in your name. At the same time, you should fear not so much the agent itself, but malicious code, for example, from an infected library that the agent will install and run with your permissions. You can protect yourself from this at various levels, and their reliability varies greatly:

  • the most reliable is when the computer running the agent simply has no access to production;

  • in a sandbox or container, the agent can be allowed to do anything and not confirm each of its commands, because it won't touch anything outside of it;

  • everything related to production, the agent does only after your permission – it stops, shows the command and its risks, and does nothing until you say "yes." And this is not based on a request in AGENTS.md, but on hooks that check each command even before the agent executes it.

Where to Start Today

To understand how the agent navigates your repository right now, ask it about the part of the project that you know best:

Where in this repository is the code that handles <what we are looking for> located? Show the files and briefly explain how it works.

And see what search commands it ran, what files it opened, and how many loops it had to go through to get the answer. Everything it searched for too long or found incorrectly will become the first lines of your AGENTS.md.
