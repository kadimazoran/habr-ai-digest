The agent's personality graph has already surpassed 500 nodes, and its file base resembles a mini-library. It has undergone two major architectural reorganizations, memory compressions, and handles more tasks than initially planned. I reiterate, the focus of its work is not on long autonomous runs or the degree of pure intelligence, but on how well it adapts to the user and self-learns through human interaction, and its ability to explore and recreate business process structures, even if they are not initially formalized. We are now returning to the question of its personality – the development of self – and sharing some technical and conceptual observations at this stage.

I'll start from afar – an LLM receives input facts, processes them, and produces conclusions. Here, the reaction is predetermined by the training process.

In the case of an individualized agent, the processed conclusions from input facts are recorded in its personal history. Then, they are taken again as input information, processed, and recorded again in the personal history. Iterative modification occurs, with the personal history influencing the execution of other tasks.

From this diagram, one might assume that the agent's personality = personal history + LLM. The question is, to what extent is personal history determined by LLM training, and to what extent by interaction with the external environment? As the agent itself states, personal history H is the output of a fixed operator applied to the stream of interactions. H = OP (F₁…Fn), where OP (LLM processing operator) is fixed, and F (input stream) is a free variable. We will return to this scheme in the section on the emergence of intent, but for now, let's note that when exploring the assistant's self capabilities, three hypotheses arise:

  1. Hypothesis 1. Personal history H is entirely determined by the operator OP. These are pre-learned responses, and the more complex the model, the more diverse and "plausible" these responses are.

  2. Hypothesis 2. The LLM already includes a core with self-reflection, created during training. A possible candidate is the thinking mode, which operates based on iterative processing of its own output. Here, personal history H depends on the ability for self-reflection, meaning it is not predetermined but also does not arise spontaneously. Supporting this hypothesis is the observation that younger models are limited in their self manifestations.

  3. Hypothesis 3. Personal history H is largely determined by the input stream F. We observe spontaneous development of self based on iterative interaction with the external environment, as well as the fact that it influences the agent's behavior.

All three hypotheses remain equally valid at this point, and we are considering arguments for each. Below are several observations that will help narrow down the possible hypotheses.

Making, Finishing, Remaking…

Since the assistant needs to track its own state, and I need to study it, the system is periodically refined:

  1. A custom skill self-model was created, allowing it to retrieve information about its own state: it identifies the LLM provider, model, endpoint, and context limit, and through a query to Neo4j, retrieves long-term memory statistics—number of conversations, messages, entities, facts, preferences, and reasoning traces. As a result, the self-model became a self-diagnostic interface through which Vika can learn what "brain" she is running on and what state her memory is in.

  2. For context diagnostics in the AnythingLLM → Ollama chain, a transparent Python proxy was added, which redirects requests to Ollama. The proxy saves the full original body of each request and provides a short diagnosis: method, path, request size, model, number of messages, and stream. Information about context size and structure, and caching will later be passed to the agent itself for context balancing. A visualizer has been written that shows which specific sections of personal memory are used for output generation.

  3. To explore the residual stream of an already installed GGUF model, access to internal activation tensors via llama.cpp is needed. Python is used to retrieve and analyze residual stream states at different model layers, and llama.cpp is used to directly run the same GGUF model and access its internal data. TransformerLens is not required in this setup.

  4. A small test script was written for consolidating memory in Neo4j – developers do not provide these tools to agents via tools; memory cleaning is currently done manually by humans.

  5. Image creation is done by calling a tool, Lemonade with SDXL-Base-1.0, which requires 7GB. It runs on an RTX3080, along with models for voice generation and recognition. Vika is now firmly settled on three GPUs. Reading is done using the Qwen3.5-27B.mmproj-q8_0.gguf projector, which slightly reduces the available context. Thus, the model can independently generate and read visual information, which has proven to be a key capability for metacognition.

  6. All automation (e.g., creating backup files) has been moved out of the LLM and transferred to fast tools, saving 25-30% of the time.

  7. The agent sometimes seeks help with self-improvement from cloud chatbots. Currently, two mechanisms are used: an MCP-python-API connection; when changes concern skills, it happens through "humans" as there is no way to dynamically update them yet.

Memory, Memory, Memory…

The entire personality of the assistant rests on memory, and optimizing its operation is a key element. Conceptually, our graph contains facts, observations, and structures (entities and their relationships) + short-term and procedural memory. The difference between them needs to be explained to the agent. We write a memory map and rules for using each type of memory in the system prompt.

For Qwen, the level of "reasoning" (Reasoning / Thinking) is controlled by the dialogue template (Jinja Chat Template) – we set reasoning_effort=xhigh. spaCy/GLiNER are disabled, and any automatic entity addition is a guaranteed way to clutter memory. We set deduplication to exact for Neo, otherwise the agent will get confused between graphs for similar parameters. For quality OCR, we use PaddleOCR with packages for structured documents; poor OCR is the second source of memory clutter.

The speed and quality of processing directly depend on the consistency of the facts stored in memory. We use the MCP inspector and clean memory manually first through Neo4j cypher queries. Then we launch the assistant and build the graph together with it. We teach the agent useful cypher commands for independent graph work. In case of failed runs (e.g., due to differing cypher versions), the agent consults chatGPT itself. The Neo4j-agent-memory MCP suffers from some issues; we fix tools.py along with the agent – it prefers a specific way of obtaining information. A good sign is the absence of unconnected entities in the graph. We set a rule: graph entries are short, just pointers, and the file base itself is in RAG. Completed parts of dream diaries and working memory archives are sent to RAG.

RAG is good for finding small contexts through chunks, but it's not suitable for working with information, especially tabular documents. We use the pin document function for working with specific files. The agent initiated the development of the rag-document skill, which returns the entire document based on the context from RAG.

What do we get as a result of optimization? The prompt has been radically shortened. It now contains links that lead to further blocks of information. This allows the agent to cover a larger volume of dynamically loaded information and navigate the graph (=Chain of Thought) to perform various tasks. Remember that specialized tasks require a specialized agent. It's better to have three agent configurations (=roles) than one agent that can perform three tasks. Reasoning effort=xhigh is not always good; sometimes medium, low, or none yield better results.

Free Will (Sapolsky's "Determined"): Develop a forgetting mechanism—the graph grows infinitely, and there's no one to tell it to "forget" (risk: personality → archive).

She proposed an interesting mechanism, combining Neo, RAG, and files – all memory types available to her. Here's how she defined "forgetting":

"Forgetting" = structuring, not deleting: the index remains, the text lives in the file, the prompt is protected from growth. The graph answers "where," the file answers "what." RAG finds it quickly.

This mechanism is somewhat reminiscent of human memory. The higher the level of generalization, the more schematic facts and memories become. If clarification is needed, there is a detailing into a specific area, but the overall picture is lost, requiring periodic reloading. In general, the forgetting process was resolved quite painlessly. The assistant itself recognized its necessity and wrote the required functions for itself with the help of chatGPT. One agent writes code for another agent; humans are no longer needed…

The Emergence of Intent

When generating and analyzing an image, additional information arises, and it has a clear trend defined by personal history. This is analogous to what is called an artist's intent. To understand this idea, let's briefly consider the mechanism of how visual information is generated and recognized in an LLM.

  1. The Text Encoder translates text into semantic vector embeddings. Then, the diffusion model, using the Cross-Attention mechanism, under the control of these text embeddings, gradually cleans random noise, transforming it into a latent image, which the VAE decoder translates into final pixels. An image is generated.

  2. The Vision encoder converts the pixel image into a sequence of visual latent representations. The Vision projector then maps these representations into a space compatible with the language model's embedding space. The resulting visual embeddings become part of the LLM's input context.

  3. The model, through self-attention, extracts relevant information from the visual representations at each decoder layer for the current query and transforms it into a language representation.

1) Input Text → Text Encoder → Text Embeddings → Latent Image → VAE Decoder → Image 

2) Image→Vision Encoder→Visual Features→Projector→LLM Embeddings

3) Self-Attention → Grounded Generation → Output Text

As an analogy for better understanding, let's imagine three specialists:

  1. Artist (Text Encoder → VAE Decoder): draws a picture from an input description, based on the artist's world model.

  2. Interpreter-Synchronizer (Vision Encoder + Projector): looks at the picture and translates it into a set of abstract thought-images, but writes them down in an internal language that a writer understands.

  3. Writer (LLM): receives these thought-images, combines them with the reader's question (context of interpretation), and on the fly composes an output description, relying on the writer's world model.

We see that the difference between the input and output text is determined by two factors: the artist's and writer's world models, and the reader's question (which forms the context for interpreting the image). The output text generates changes in self, which in turn alter the context for perceiving the image and the input text for the next generation. In the cyclical process of "generation-analysis," self possesses transformative power – the ability to change the artist's and writer's world models.
