In the previous article, I tested Jev on text-based tasks: classification, answer confidence, long context, and noisy input. On October 14th, TypeSafe announced Jev 1.14 and opened up experimental capabilities: images, a new box question type, and extended context. I wanted to see what could be done with them in practice and where errors arise.

Through a quick series of experiments, I managed to test object detection by description, cat and dog breed classification, image-based questions, finding bank details on documents, and queries with dozens of photos. All computations together cost about $2.6.

The most illustrative result came from the task "find the cat among dogs." With 32 and 96 photos, the model failed to select the correct photo from the middle of the array each time. After changing the query structure—the same pictures, the same order—it answered correctly in all tested cases. Below, I will explain what exactly changed and why the first result was easily misinterpreted.

What You Can Now Ask Jev

If you missed the previous article: Jev is TypeSafe's model for structured solutions. You provide data and questions, and in return, you get values of specified types. choice selects an option from a list, score evaluates on a scale, noul returns the probability of a "yes" answer. choice and score have probability distributions and a confidence score. A brief description of the approach is in the TypeSafe documentation.

With images, box is added: you can ask to find a cat's head, a person in red glasses, or the recipient's IBAN on a document. The response is four coordinates for a bounding box as fractions of the image width and height, along with confidence. One question returns one box. Description of box.

Three questions for one photograph. Blue indicates Jev's bounding boxes and their confidence. All three boxes look accurate, although the confidence for the cat on the right is only 0.12. Low confidence by itself doesn't necessarily mean an error.

Images can be provided in the query data, instructions, and even in the descriptions of answer options—for example, by using a photo as an example for each class. For images and box, the header TypeSafe-Danger-Zone-Images: true is required; developers currently mark these capabilities as experimental. Working with images format.

The announcement contains an interesting detail: Jev 1.13 was already multimodal, and now this capability is available to users. Extended context is also supported in 1.13; box is only available from 1.14. Developers have enabled experimental features via separate API headers and explicitly state they are not yet ready to recommend them for production.

Jev 1.14 itself also claims minor improvements in various areas, especially in language support. Here, I've focused on images and long context. All results below were obtained on October 15, 2026, using jev-1.14.0; cross-lingual improvements and quality differences between versions were not tested in this series.

The practical utility of the score is still evident: some boxes can be accepted automatically, while others are sent for further processing. If the Object is Not Present

In the pet photos, I asked about a plane, a giraffe, a bicycle, and other absent objects. A bounding box was returned for them as well. This behavior is directly described in the documentation: box does not have a "not found" response.

Therefore, noul was used alongside—a question about the object's presence. On 150 positive and 40 negative examples, the results were completely separated: for present objects, the probability was not lower than 0.91; for absent objects, it was not higher than 0.21. The box's own confidence score separated them less effectively: for one box of an absent object, it reached up to 0.80.

In a query, this looks like this—a fragment of the questions field, assuming the photo is already passed in state.photo:

{
  "present": {
    "type": "noul",
    "instructions": "Is there a cat in `photo`?"
  },
  "location": {
    "type": "box",
    "instructions": "the cat in `photo`"
  }
}

In this test, the negative examples were simple. With occluded objects, silhouettes, or similar items, there might be more errors. But even here, it's clear why using only the box's confidence score to check for presence is a weak solution.

If There Are Multiple Identical Objects

In synthetic scenes with apples, the query "the apple" usually selected one apple. With three apples, there were many misses, and the median confidence dropped from 0.69 for one apple to 0.19 for three.

The clarification "the leftmost apple" helped: correct boxes were found in 100% of responses with two apples and in 92% with three. For each quantity, there were only 12 different scenes with three repetitions, so this is a preliminary observation. It highlights the value of an unambiguous target description.

2. Documents: Finding a Line is Easier When Magnified

Initially, the task looked promising. On simple synthetic payment documents, Jev found the IBAN line, although the box was often vertically misaligned. After expanding the box up and down to the height of the line, the target detail was found within the box in 98–100% of responses. The model did not confuse the payer with the recipient.

This result has two significant caveats: there were only 15 documents with one and 15 with two IBANs; the criterion for a usable crop was established after reviewing the responses. With a strict IoU ≥ 0.5, the results were only 27–47% depending on the question. Expanding the box seemed like a useful technique worth further investigation.

The next series was more challenging: 1100×1556 pixel pages with paragraphs, a table, details, and distracting numbers. Each page had zero to 12 synthetic IBANs. Each page was tested in its clean form and with rotation, blur, and noise, and JPEG compression simulating a scan.

Here, the success criterion was fixed before the run: after vertical expansion to the line height, the box must cover at least 80% of the target IBAN and less than half of any other. The area of the original box was also limited to prevent the "entire page" answer from being considered a success.

On a full page, the model often returned boxes that were two to three lines high, shifted by about one line. Then, the same page was cut into four horizontal strips with a 60-pixel overlap, each enlarged 1.4 times. The responses were translated back to the page coordinates.

What if we ask for "first IBAN," "second IBAN," and so on? This approach proved weak. The correct i-th detail was found in approximately 11% of cases on a full page and in 31–37% within a strip. Even with an additional noul "is there an i-th IBAN?", all details were found on only 18 out of 60 non-empty pages after cropping. There were also many extraneous boxes.

Therefore, the next experiment would be structured as follows: strips → OCR finds candidates → Jev localizes the candidate by its text. This series tested the last link with ideal candidate text. The entire pipeline, including reading and verifying details, still needs to be measured.

3. Classification: Embeddings Proved to Be Strong Competitors

For classification, Oxford-IIIT Pet was used: 37 breeds of cats and dogs, with 10 test photos per breed.

Jev received a list of breeds with short descriptions like "name—cat/dog breed." Gemini Embedding 2 calculated the similarity between the photo's embedding and the embeddings of the text descriptions of the classes. This is a zero-shot comparison, meaning without training examples.

One-shot was also tested separately: one example photo from the training set was added to the description of each option for Jev.

Analyzing the errors was more interesting than overall accuracy. All 25 errors in color questions related to figures of medium size. There were no errors for small or large figures. In each erroneous answer, the model chose the color of a figure of the same shape but different size. This means the difficulty arose in selecting an object by relative size.

The counting situation is different: the exact count was poorly guessed both from the image and from the text. If an error of one is allowed, both versions yield 96%. The model was often close to the answer, but that's not enough for precise counting.

And the 100% on long numbers requires careful reading: the model chose from four pre-set options, differing by one digit. The font was 16–22 pixels, scenes were synthetic. Free-form text recognition without options was not tested by this.

In one query, photos of dogs and one cat were provided. The task was to select the photo with the cat. Sets of 8, 32, and 96 images were tested, with the cat placed at the beginning, middle, or end. For each combination—12 queries.

The result resembles information loss in the middle of long context. But with 32 photos, all 12 errors pointed to the adjacent position. This suggests checking what exactly the model failed to do.

In the second version, the same photos in the same order were provided as an object with random names. Answer options referred to paths like photos.<name>—without a sequential number.

After this, all answers became correct: 8, 32, and 96 photos, any of the three cat positions. The confidence for all these answers was 1.0.

The set of 96 photos occupied about 117 thousand tokens, with a median response time of about seven seconds. For 8 photos—about 10 thousand tokens and 0.6 seconds.

This experiment suggests that in the tested task, the model did find the cat in the middle of the set. The reason for the failure of the first scheme cannot be definitively established: the data structure and the method of referencing the image changed simultaneously. The dual numbering might have confused the model; the option with a single unambiguous numbering was not tested separately. With 96 photos, probabilities were more spread out, and explanations solely based on a shift of one unit are insufficient.

For my own queries, I would choose named images. And the 12 successful answers per combination would be considered a good pilot result for now, worth testing with more complex searches.

When combining all long variants, accuracy dropped by an average of 4.8 percentage points, with a 95% interval from −9.6 to −1.1. Confidence dropped by 0.10 [−0.16; −0.05]. For the middle position, the estimated accuracy drop is 8.9 p.p. [−17.8; −2.2].

This aligns with observations from the previous article: extraneous text degrades results, especially if the useful fragment is in the middle. Here, the filler was neutral, and at maximum length, some sentences were repeated. Long real documents might behave differently.

A Few Details for Those Who Want to Replicate

According to the TypeSafe pricing, one million input tokens cost $0.042, with output being free. In these measurements, a 640×480 image occupied approximately 870 tokens—about $0.00004. Therefore, even a broad overview test was inexpensive. A full query costs more: it includes instructions, answer options, and possibly example photos.

It's best to check image sizes in advance. The documentation specifies sides from 256 to 1568 pixels and a separate area limit. However, on the day of measurement, the API rejected not only 256×256: 279×400 and 256×1000 also received 400 Invalid image dimensions, although they were within the area limits. 280×280 and 280×400 were accepted. For these tests, the minimum side used was 280 pixels. This observation pertains to the specific API at the time of testing.

In the queries, I explicitly specified jev-1.14.0: box on 1.13 returned a 400 error in testing. Fixing the version also helps reproduce results and confidence thresholds.

What I Want to Test Next

From this series, I would first continue the experiment with documents: take real or more diverse annotated pages and measure the entire chain from OCR to the bounding box of the desired detail. It is now clear that the image scale significantly affects the result, and iterating through objects by number yields too many omissions and extraneous boxes.

With photos, a useful set of capabilities has already been developed: finding an object by description, checking its presence, and selecting more confident answers. For each operation, there are measurable limitations—and the option to change the query or processing when the quality is insufficient.

The story with the cat among 96 photos particularly illustrates why analyzing failed responses is important. One result looked like a failure of long visual context, while re-testing showed that the model saw the correct image. The method of pointing to it turned out to be a significant part of the task.
