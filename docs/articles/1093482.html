When writing a typical HTTP API in Go, using context.Context quickly becomes a habit.

A request comes in, you get r.Context(), pass it to the service, then to the repository, and to all external calls. If the client disconnects or the timeout expires, related operations are canceled.

For most backend tasks, this is exactly the behavior we want.

Why continue executing an SQL query if no one needs the result anymore? Why keep a connection to an external API if the user has closed the page?

But when an LLM is added to the system, this familiar logic doesn't always work as expected.

Imagine a SaaS that analyzes documents. A user uploads a PDF, clicks a button, and waits for the result. The backend extracts text, sends it to the model, receives a structured response, and saves the analysis result.

As long as it all fits within a single HTTP request, the architecture looks perfectly normal.

Problems arise when the user closes the tab five seconds after sending the document.

What should happen to the task now?

Why the Usual HTTP Context Isn't Always Suitable Here

Let's start with a simple example.

func (h *Handler) Analyze(w http.ResponseWriter, r *http.Request) { result, err := h.analyzer.Run(r.Context(), r.Body) if err != nil { http.Error(w, "analysis failed", http.StatusInternalServerError) return } json.NewEncoder(w).Encode(result) }

The code is simplified, but the idea is familiar.

The Handler receives a request and passes its context to the service. The service uses the same context to call the LLM provider.

In Go, the context of an incoming server request is canceled when the client connection closes, an HTTP/2 request is canceled, or ServeHTTP completes. This is the standard behavior of net/http. Go Packages

Now let's imagine a sequence of events:

12:00:00 POST /api/analyze 12:00:01 Backend sent request to LLM 12:00:05 User closed tab 12:00:05 r.Context() canceled 12:00:06 Backend stops waiting for response

At the Go level, everything looks correct.

The context is canceled. The external HTTP request, if the client library correctly supports cancellation, should complete.

But here's the question: what happened on the LLM provider's side?

The answer depends on the specific API and at what stage the operation was canceled.

Perhaps the provider also stopped generation.

Perhaps the request had already started executing, and some tokens were spent.

Perhaps the result was formed, but the backend didn't receive it.

From a local context.Canceled, it's impossible to reliably determine which of these events occurred.

This is where the problem lies.

We've canceled waiting for a response, but not necessarily the work or costs in the external system.

Canceling an HTTP Request Is Not the Same as Canceling a Business Operation

I believe this is the main distinction to consider when designing AI services.

In a typical CRUD API, a user sends a request, the backend performs a small operation, and returns a result.

Even if the connection is interrupted, you can often simply retry the request or check the resource status.

In an AI application, the situation is more complex.

Suppose a user initiates a contract analysis.

It takes 40 seconds to complete. During this time, the system calls the model, gets the result, validates it, and saves it.

If the user accidentally refreshes the page after twenty seconds, should the analysis stop?

I would answer: not necessarily.

If the user explicitly clicked "Cancel Analysis," that's one event.

If the browser lost connection, that's entirely different.

But if all the work is tied to r.Context(), we are effectively equating these events.

This results in the transport layer controlling the lifecycle of the business operation.

For simple, short requests, this is fine.

For a long-running, paid AI task, this behavior is worth reconsidering.

Why Goroutines Don't Solve the Problem

The first solution that comes to mind looks something like this:

go func() { ctx := context.Background() result, err := analyzer.Run(ctx, input) if err != nil { log.Error("analysis failed", "error", err) return } repository.Save(ctx, result) }()

Now the work doesn't depend on the HTTP context.

The user can close the tab, and the goroutine will continue performing the analysis.

This seems like a solution.

But we've just traded one problem for several others.

First, what happens when the application restarts?

If the container stops, the goroutine disappears with the process.

Second, where is the information about the running operation stored?

How does the user know the task is still running? How to avoid restarting it? How to restore processing after a failure?

Third, how to limit the number of such goroutines?

If users simultaneously launch several hundred analyses, the application might create as many concurrent calls to the model.

And finally, who is responsible for retries, limits, cancellations, and cost accounting?

A goroutine by itself is not a background task execution system.

It merely allows code to run concurrently.

What About context.WithoutCancel?

Go has a more refined way to detach a context from its parent's cancellation. Since Go 1.21, context.WithoutCancel is available.

ctx := context.WithoutCancel(r.Context())

The resulting context retains the values of the parent context but does not inherit its cancellation or deadline. It does not have an automatic cancellation mechanism itself. Go Packages

This is useful for some short operations.

For example, when you need to guarantee an attempt to send a small audit event after an HTTP request completes.

However, I would not use WithoutCancel as a universal solution for LLM tasks.

It does not guarantee work persistence across process restarts. It doesn't provide retries, doesn't limit concurrency, and doesn't create a resilient task state.

Furthermore, along with the context, you can preserve request-scoped values, although for background execution, it's often better to explicitly pass the necessary data: user ID, organization, and trace ID.

Most importantly, if you detach long-running work from cancellation, it still needs its own timeout.

ctx, cancel := context.WithTimeout( context.WithoutCancel(r.Context()), 90*time.Second, ) defer cancel()

This is safer in terms of limiting execution time, but the problem of reliable recovery remains.

For long-running business operations, I would prefer not to create a working context from the HTTP context at all.

AI Analysis as a Separate Entity

In my opinion, a more reliable model starts with a rather simple change.

We need to stop considering document analysis as a continuation of the HTTP request.

The HTTP request merely creates a task.

The task itself exists separately.

The architecture becomes this:

 HTTP API | v Create AI Job | v PostgreSQL | v Worker | v LLM API | v Validate Result | v Save Result

The external API might look like this:

POST /api/ai/jobs Idempotency-Key: 1b7c4e... HTTP/1.1 202 Accepted

The response:

{ "job_id": "8c2f...", "status": "queued" }

After this, the frontend can get the status via:

GET /api/ai/jobs/8c2f...

Now, closing the tab no longer means an automatic loss of the task.

The user can return later and get the already completed result.

At the same time, 202 Accepted means the system has accepted the request for processing, not guaranteed successful completion.

True guarantee begins with the fact that the task record is reliably saved.

Can We Get By With Just PostgreSQL?

For a small AI SaaS, I wouldn't rush to add Kafka, RabbitMQ, or a separate orchestration system immediately.

If the application already uses PostgreSQL, it might be sufficient at the first stage.

For example, you can create a table:

CREATE TABLE ai_jobs ( id UUID PRIMARY KEY, tenant_id UUID NOT NULL, idempotency_key TEXT NOT NULL, request_hash BYTEA NOT NULL, status TEXT NOT NULL, payload JSONB NOT NULL, result JSONB, attempts INTEGER NOT NULL DEFAULT 0, run_token UUID, lease_until TIMESTAMPTZ, created_at TIMESTAMPTZ NOT NULL DEFAULT now(), UNIQUE (tenant_id, idempotency_key) );

Here, the purpose of the fields is more interesting than the fields themselves.

status shows the task's state.

attempts allows limiting the number of retries.

lease_until helps detect stuck tasks.

run_token is needed so an old worker cannot overwrite the result of a new run.

And idempotency_key protects against duplicate creation of the same operation.

Payload is shown here as JSONB for simplicity. In a real service, I would separately consider document storage, deletion timelines, and access to sensitive data.

Why Idempotency Is Especially Important Here

Imagine the frontend sent a request to create an AI task.

The backend saved it in PostgreSQL.

But the connection broke before the client received a response.

The user clicks the button again.

Without idempotency, the application might create a second task and resend the same document to the model.

As a result, we'll get two analyses and potentially two paid operations.

Yet, the user only wanted to perform one.

Therefore, the client must provide a stable Idempotency-Key that doesn't change when resending the same logical operation.

The backend checks the pair:

tenant_id + idempotency_key

If the task already exists, it returns its ID and current status.

It's important to consider one more detail.

The same key should not allow substituting request parameters.

Therefore, it's useful to store a fingerprint of the original data.

If the key is the same but the request content is different, it's more correct to return a conflict, e.g., HTTP 409.

Otherwise, idempotency will gradually turn into a source of hard-to-explain errors.

How Multiple Workers Can Pick Up Tasks

For PostgreSQL, there's a quite convenient mechanism: FOR UPDATE SKIP LOCKED.

It allows multiple workers to select available rows without waiting for tasks already locked by other workers to be released.

PostgreSQL directly notes the applicability of this mechanism for queue-like tables, although for ordinary consistent selections, such behavior is not suitable. PostgreSQL

A simplified query to get a task might look like this:

WITH picked AS ( SELECT id FROM ai_jobs WHERE ( status = 'queued' OR ( status = 'running' AND lease_until < now() ) ) AND attempts < 3 ORDER BY created_at, id FOR UPDATE SKIP LOCKED LIMIT 1 ) UPDATE ai_jobs AS j SET status = 'running', attempts = j.attempts + 1, run_token = gen_random_uuid(), lease_until = now() + interval '3 minutes' FROM picked WHERE j.id = picked.id RETURNING j.id, j.run_token, j.payload;

This is only part of the implementation. A full-fledged queue would require handling exhausted attempts, backoff, indexes, and concurrency limits.

But the scheme itself solves an important problem.

Multiple workers can safely pick up different tasks.

At the same time, the row lock is held only within the short transaction of acquiring the task.

We don't keep an open PostgreSQL transaction for the entire 40 seconds the LLM is running.

After acquiring the job, the worker makes the external call independently.

The Worker Must Have Its Own Context

And here context.Context reappears.

Only now it doesn't manage the HTTP request, but a specific attempt to execute a background task.

For example:

func (w *Worker) process(workerCtx context.Context, job Job) error { ctx, cancel := context.WithTimeout( workerCtx, 90*time.Second, ) defer cancel() result, err := w.llm.Generate( ctx, job.Payload, ) if err != nil { return err } return w.repository.Complete( ctx, job.ID, job.RunToken, result, ) }

This code shows the idea, not a ready-to-use production worker.

Specifically, saving the result is better done with a separate, limited context when you need to preserve state after the main attempt completes. Also, lease renewal and shutdown handling are not shown here.

But the main difference is already visible.

The HTTP context is responsible for the HTTP request.

The worker context is responsible for a specific execution attempt.

And the lifecycle of the task itself is stored in PostgreSQL.

Now, the cancellation of one connection doesn't destroy the state of the business operation.

What Happens If a Worker Crashes?

Suppose a worker picked up a task and set:

status = running lease_until = 12:03:00

After that, it sent a request to the model.

The container terminated 20 seconds later.

There will be no callback from it.

But after the lease expires, another worker can pick up the task and retry the execution.

This is how a failure recovery mechanism appears.

However, there's a subtlety here.

The old worker might not die but simply take a very long time to execute the request.

For example, it lost the database connection but continues to wait for the external provider's response.

Meanwhile, the lease has expired, and another worker has already picked up the task.

Now, both might potentially try to save the result.

This is precisely why run_token is needed.

Task completion should be conditional:

UPDATE ai_jobs SET status = 'succeeded', result = $3, run_token = NULL, lease_until = NULL WHERE id = $1 AND run_token = $2 AND status = 'running';

If the task already belongs to another worker, the UPDATE will not change any rows.

The old run won't be able to overwrite the new one's result.

For long operations, the lease usually needs to be periodically renewed, and only if the current run_token matches.

But even this scheme doesn't solve one of the most unpleasant problems of AI integrations.

Exactly Once Ends at the External API Boundary

Consider the situation.

The worker sent a request to the LLM.

The model performed the work.

The provider sent the result.

The worker received the response but crashed before saving the result to PostgreSQL.

After the lease expires, another worker will retry the task.

At our database level, everything looks correct.

There's still only one task.

But on the provider's side, two calls might have been made.

And if both calls were billed, the costs might also be doubled.

This is a standard problem in distributed systems: a local PostgreSQL transaction cannot atomically commit the execution of an external LLM API.

In effect, we get at-least-once execution with protection against duplicate result acceptance.

We don't guarantee exactly one execution of the external call.

If a specific provider supports idempotency on its side for the relevant endpoint, it might help. But such a guarantee must be checked separately, not assumed by analogy with other APIs.

And here, it's important not to promise the user or the business more than the system actually delivers.

One saved task doesn't necessarily mean one billed request to the model.

AI SaaS Needs to Distinguish Two Costs

I think it's useful here to distinguish two entities.

The first is the cost of executing operations with the LLM provider.

The second is the cost we charge the user within our product.

These are not necessarily the same.

If the provider performed two attempts due to a worker failure, we might pay for both.

But the user should not automatically be charged twice for one ordered analysis.

Therefore, I would separate accounting at the level of:

AI Job +-- Attempt 1 provider_cost failed / unknown +-- Attempt 2 provider_cost succeeded

And link user billing to the logical business operation and a predefined pricing policy.

For example, you can reserve a limit when creating a task, finally deduct it after accepting the result, and release the reserve upon unsuccessful completion.

It's also worth storing the attempt history separately.

Otherwise, it will be difficult later to explain why LLM API costs increased, even though the number of completed user tasks hasn't changed much.

Cases with an uncertain outcome are particularly unpleasant.

When a worker times out, we can't always reliably say how many tokens the provider actually spent.

Therefore, unknown is sometimes more honest than failed_without_cost.

Why Not Just Retry Any Error?

After introducing a queue, the temptation arises to make a universal rule:

error → retry

But not every error means the request should be retried.

Temporary provider unavailability and an incorrect user document require different handling.

If the model consistently receives a payload that fails mandatory validation, three retries usually won't improve the situation.

However, if the provider returned a temporary availability error, a retry might be justified.

Timeouts after sending a request to the provider should be treated separately.

In this case, we might not know if the operation completed on the other side.

Therefore, before retrying, it's useful to consider not only the error type but also the execution stage, the provider's deduplication capability, and the expected cost of a retry.

For expensive tasks, automatic retries might have a separate policy altogether.

And this is another reason why executing an AI task is better kept in an explicit orchestration layer rather than hidden in an HTTP handler.

How Then to Show Generation to the User?

This is where the objection usually arises.

For some AI applications, streaming is important.

Users want to see the response immediately, not wait for the task to complete in the background.

But streaming and task lifecycle don't have to be the same thing.

You can maintain an asynchronous model and organize event delivery separately.

For example:

POST /api/ai/jobs | v Job created | v Background worker | +----> Result storage | +----> Event stream | v Frontend

The frontend can subscribe to execution events via SSE.

If the connection breaks, the subscription ends.

But the task itself will continue to execute according to its policy.

The user will reopen the page, get the current status, and, if necessary, resume viewing the result.

However, there's a technical nuance here too.

If we want to restore not just the final result but specifically the stream of intermediate events, these events need to be stored somewhere, or there needs to be a mechanism for replaying them.

SSE itself doesn't make the stream durable.

And for a small service, I would first implement saving the final result and regular polling.

I would add streaming only when the product truly needs it.

User Cancellation Should Be a Separate Operation

Now let's return to the situation with the closed tab.

In the described architecture, losing the connection no longer automatically cancels the task.

But the user might still need a "Cancel" button.

For this, it's better to have an explicit endpoint:

POST /api/ai/jobs/{id}/cancel

It shouldn't just look for some CancelFunc in the memory of a single application instance.

It's better to record the cancellation intent in the task's state.

For example:

cancel_requested = true

The worker periodically checks this state and stops work when permissible.

If the LLM call is already in progress, the worker can try to cancel the outgoing request.

But even here, you can't promise that the provider will definitely stop generation or not issue a bill.

Therefore, at the product level, it's worth distinguishing between canceling a user task and successfully canceling an external execution.

These are different events.

What Metrics Are Truly Interesting Here

After transitioning to background AI tasks, ordinary HTTP metrics become insufficient.

The latency for the task creation endpoint might be 30 milliseconds.

But this says nothing about the user receiving the result only a minute later.

Therefore, I would separately look at queue wait time, execution duration, number of attempts, and the proportion of tasks completed without retries.

It's even more important to see cases of recovery after lease expiration and situations with unknown outcomes of external calls.

For AI SaaS, an interesting combination of metrics emerges:

jobs_created jobs_accepted job_retry_rate lease_expired_count provider_attempts provider_unknown_outcomes cost_per_accepted_job

With the last metric, we return to product economics.

If the cost of one model call decreases, but the number of retries increases, the total cost of the finished result might not improve at all.

Therefore, comparing providers solely by token price is also insufficient here.

Do We Need to Complicate Every AI Endpoint Like This?

No.

If the application generates a short response in a couple of seconds and this response doesn't need to be saved, a regular synchronous HTTP call is perfectly justified.

The user closed the connection, the operation is canceled. This is expected behavior.

I wouldn't create a durable job for every model call just because an LLM is used internally.

The boundary appears when an operation has at least a few properties: it's long-running, expensive, the result needs to be saved, the user might return to it later, or retrying the execution could cause problems.

In other words, it's not about whether AI is used.

It's about whether the operation is a self-contained business task.

What's the Bottom Line

In the familiar Go backend model, we often tie the lifetime of work to the lifetime of the HTTP request.

This is a good model for many ordinary APIs.

But a long-running AI operation can have its own lifecycle, its own cost, and its own recovery rules.

In such cases, I would separate three levels.

The HTTP request is responsible for creating the task and getting its status.

The worker is responsible for a specific execution attempt.

And the database stores the state of the business operation independently of both.

Then, context.Context remains a useful tool for managing execution time and canceling specific operations.

It simply ceases to be the sole source of truth about the task's existence.

In my opinion, the most interesting part of production AI lies here.

We start with a familiar API call to the model and quickly arrive at questions of idempotency, reliable delivery, transactional boundaries, distributed execution, and cost accounting.

That is, to ordinary backend problems.

Only now, a retry error might cost not a few extra milliseconds, but real money.

How do you handle long LLM operations: do you keep them within the HTTP request or immediately move them to separate jobs? I'm particularly interested in how you handle cases where the provider has already completed the request, but the worker failed to save the result.
