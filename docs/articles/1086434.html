What the Customer Actually Requires

Over the past year, large enterprise companies' requirements for generative AI protection have changed significantly. Initially, it was a short list of tasks for a "ChatGPT proxy." Now it's a multi-page matrix with over 500 formalized requirements: standard tasks first, then requirements for AI agents, MCP, 152-FZ, model supply chains, and so on. This is no longer a request for a filter. It's a request for a control loop.

CISOs no longer ask if the system can "catch jailbreaks." They ask where the control point is, what happens if the analyzer fails, whether confidential documents leak to an external model even in masked form, and who will see at three in the morning that a service account has burned through the monthly token budget.

The requirements matrix can be divided into two parts, with the second part being much stricter than the first.

Part I - Initial form. This is where the analysis usually begins: general characteristics, model catalog, basic security pipeline, agent protection, PII anonymization, roles and limits, API, classification and routing, MCP Gateway.

Part II - Additional requirements. Here, the Customer thinks like a risk owner: deployment options, fail-closed, shadow AI, model supply chain, ML Red Teaming and regression, performance, gateway protection itself, data localization, AI agents on the endpoint, and so on.

How Are These Requirements Grouped?

The first layer is the control point. The LLM/AI Firewall must be placed in the traffic path: API gateway, transparent proxy, sidecar, browser plugin, thick client on the endpoint. The connection should not break the operation of AI agents and assistants. It is important to detect "Shadow AI," when employees use public AI chats bypassing the gateway. AI traffic must be subject to the same regime as the rest of the corporate channel.

Here also arises the requirement for separating areas of responsibility:

  • gateway to models,

  • gateway to tools (MCP),

  • agent on the endpoint,

  • control of code generated by AI.

The refusal of any layer must be an explicit risk, not an "unnoticed simplification of the project.".

The second layer is the model catalog. The public name seen by the client and the specific deployment behind it are different entities. Behind one name lives a pool: local vLLM, GigaChat, external provider. Each entry has a mode, entry and exit cost, cache cost, context limits, RPM/TPM, and a mandatory placement label: local or external model. Without this label, the router has no right to make data access decisions.

The minimum set of providers: Anthropic, OpenAI, DeepSeek. In practice, Customers immediately add GigaChat, YandexGPT, Ollama, vLLM, llama.cpp.

For security, two points are also critical: prohibiting training on transmitted data (where the provider supports it) and allow/deny lists of models at the organization, team, and key levels.

The third layer is the security pipeline. This is not a single classifier, but a large pipeline with a clear order of steps, separate reactions to each check, and an audit event for each trigger. First, normalization and rules, then small models, then a judge for disputed evaluations. Separate requirements for Russian morphology, homoglyphs, indirect injections from files, emails, RAG, and tool results, parsing office formats, OCR, and speech.

Through the ML Red Teaming scanner, the Customer wants to implement a regular loop for checking the resilience of internal AI models: text attacks, visual insertions and hidden layers in images, voice instructions in audio, multi-step scenarios, and attacks through tool results. The set of probes must be expandable with custom cases, not just vendor-supplied, and the verdict must be based on a fixed methodology and a judge model so that the pentest can be repeated after changing the model, system prompt, or knowledge base. The scanner must not just achieve a percentage of reflected attacks on a public benchmark, but link each probe to a threat class and immediately feed it into the LLM/AI Firewall policy: what to block, what to mask, which route to close. If a finding lives only in a report and does not become a gateway rule, then the ML Red Teaming scanner can be considered useless.

The fourth layer is data. Here, the Customer speaks the language of 152-FZ. INN, SNILS, passport, insurance policy, special categories, checksums, a stable placeholder for the entire session, and reverse substitution in the streaming response are needed. Masking must cover the dialogue history and summary, otherwise the model carries away an entity found three turns ago. Secrets and corporate categories are handled by the same mechanism as personal data.

The fifth layer is people, teams, and money. Customers require a hierarchy of "organization - team - user," two-level RBAC, and login only through the corporate directory, without local accounts that are later never revoked. A person can be part of several teams, but each request belongs to exactly one: it is determined by the key, and based on it, available models, quota, and budget are calculated. Otherwise, the investigation gets stuck in a common pool of tokens where it's impossible to understand whose loop it is.

The budget here is a control mechanism just like the access policy, not a report for the finance department. The ceiling is set in the accounting currency for the organization, team, and individual user; the team limit can be detailed internally; the individual quota overrides the general one. RPM, TPM, and cost checks are performed before calling the model: if money or frequency is already exhausted, the gateway denies with a clear warning and reset time, rather than breaking the connection.

Why Controlling LLM Token Consumption is Important

In procurement, this block is often hidden in the limits section, and for good reason. A token is simultaneously a unit of cost, a unit of risk (anomaly indicator), and a unit of inference load. If the LLM/AI Firewall does not count it before calling the model, it does not manage risk, and CISOs and CIOs cannot explain why the payment bill has quadrupled.

A model that thinks for a long time internally and maintains a hidden chain of reasoning consumes money (tokens) faster than a dozen ordinary tasks. The model card needs different rates: separately for input text, for response, for reuse of already paid context, and for internal reasoning. Without this breakdown, the platform report shows the incorrect cost, and the CFO will see discrepancies in the bills before the information security service notices a strange spike in the logs.

The counter must check the quota before accessing the AI model. Otherwise, prompt-based DoS or a looped AI agent can quickly spend money and "muffle" local inference. It is necessary to set a contract ceiling within which the team lives within its budget, a user or service key cannot take another's limit, the model has its own RPM/TPM, a single request has a length limit. At the same time, the individual quota overrides the team quota.

For a CISO, what's more important here is not a pretty graph, but the system's behavior at the moment of failure. Exceeding the limit should return a clear error: which limit, how much is spent, when it resets. A connection break without reason leads to circumvention. An example of an anomaly indicator: a nighttime spike in token consumption by an account that is used little during the day. Therefore, alerts at 80% of the quota should go not only to the team owner but also as an event to the SIEM.

There is another detail that Customers start including after the very first agent pilot. The budget for an AI agent's session is calculated as the sum of all nested calls, not as the cost of the first reply. Otherwise, a tool in a loop bypasses any "chat quota.".

Request Redistribution: Cost, Complexity, Confidentiality

The most frequent request is classification and routing of requests to an AI model. The Customer explicitly states: the LLM/AI Firewall itself must choose the AI model for each request.

The selection criteria are fixed in the requirements as follows:

  • task class ↔ model capabilities;

  • confidentiality level ↔ allowed deployment (internal or external models);

  • cost and availability.

The decision must be deterministic and verifiable with a test request. The model can change in the middle of a dialogue if the task or data classification changes.

Let's break it down.

Redistribution based on token consumption

This is not a rule like "send it where there's still quota left." Blindly transferring to a live loop is precisely what breaks protection.

If, when using an "expensive" AI model, limits on frequency, volume, or money are reached, the request can be moved to the next link in the chain, but only if the access table allows it. If the task is simple ("cheap"), it cannot be kept on an expensive model just because it has quota. If internal AI models are overloaded, confidential data must still not go to external models. Availability in this architecture never overrides classification.

The chain usually looks like this: powerful local model, then a lighter local one, then a Russian cloud, then an external provider. Each transition is permitted only by policy and data class.

Redistribution based on task complexity

The task class is set by configuration, not by user habit. For example, a brief summary of a meeting protocol should not be sent to an expensive external model just because it's the first in the chat list.

It is important to differentiate between code generation, data analysis, text compression, knowledge base response (RAG), image processing, tasks with long internal reasoning, and so on in requests to the model.

The model card must be machine-readable: what modalities it accepts, what context window it has, whether it can reason, where it is physically located, how much input, output, and internal reasoning costs. An important caveat from the requirements: routing rules are administered without restarting. Otherwise, IT security cannot quickly shut down an expensive loop after an incident or limit exhaustion.

Redistribution based on request confidentiality

Three levels are strictly defined:

  • Confidential or restricted data (Restricted) must not leave the perimeter in any form, including after masking. Only local (internal) AI models are used.

  • Anonymized or masked data (Masked) can be sent to an external loop only after entity replacement (masking) and only to those providers explicitly permitted by policy, with a prohibition on training on this data.

  • Public data goes through a list of allowed models.

The classifier does not look at a single user replica. The evaluation includes the current input, dialogue history, derived session context, and what the tool returned. If the detector is unsure that it has found all sensitive fragments, Masked is elevated to Restricted. This can only be relaxed explicitly, with logging of the name of the person who accepted the risk.

Internal requests marked "internal only" do not go to an external model because it is smarter. The decision is made for each turn, so the model in the dialogue can change. A person starts with a public question, then inserts a fragment of a contract. In this case, the router must move the session to the local loop and preserve the agreed substitutions. If the substitution map lives only in the memory of one deployment, changing the model breaks both protection and the meaning of the response.

What This Implies

As organizations move from individual experiments to corporate AI platforms, the requirements for an LLM/AI Firewall rapidly become more complex. Customers are no longer satisfied with a proxy that passes requests to a model, counts tokens, and blocks a few known jailbreak scenarios. An LLM/AI Firewall is expected to be a full-fledged control loop capable of considering the user, team, application, model, data source, dialogue history, and AI agent actions.

These requirements are becoming not only more numerous but also more diverse. A single policy must simultaneously consider data confidentiality, allowed model deployment, request cost, task complexity, performance limits, agent rights, and logging requirements. The system must control not only the text of requests and responses but also the content of files, RAG search results, images, audio, tool calls, and data exchange via MCP. Furthermore, policies must be applied to each step of the chain, including intermediate model calls and nested AI agent actions.

Traditional security tools are insufficient for such a loop. WAF, IAM, DLP, API gateways, and SIEM remain important infrastructure components, but they do not understand the semantics of prompts and model responses on their own. They can check request format, destination address, access rights, or the presence of known patterns, but they cannot determine that a seemingly harmless instruction is actually trying to change system rules, extract hidden context, bypass a restriction, or force an AI agent to perform an unauthorized action.

Therefore, an LLM/AI Firewall analyzes the meaning and context of the interaction. Its tasks include detecting prompt injection and jailbreaks, controlling sensitive information leaks, detecting dangerous output, countering excessive agent autonomy, verifying tool results, and protecting against OWASP Top 10 for LLM Applications scenarios, including supply-chain risks, vector representation vulnerabilities, and unlimited resource consumption.

Thus, the LLM/AI Firewall is transforming into a risk management mechanism for the entire AI request lifecycle. Its value is determined not by the number of individual functions, but by how consistently it links semantic analysis, access policies, routing, masking, agent control, budgeting, auditing, and response. This is precisely why the requirements for such solutions continue to grow: corporate AI needs not only access to models but also a managed, verifiable, and secure environment for their application.
