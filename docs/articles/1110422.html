Don't start with a prompt. Start with a process

The work of a system analyst rarely boils down to a sequential execution of clearly defined tasks. Usually, everything starts with a task in Jira containing product requirements. Sometimes these are enough to understand the direction of work, but more often, you need to clarify details, find context, communicate with related teams, and check if all scenarios are accounted for.

Our analyst's workflow consists of several stages:

At each stage, there are tasks requiring expertise and tasks that can be formalized. An architectural decision cannot be made by an analyst, but checking a document for compliance with internal agreements, finding similar solutions in the project history, or preparing a draft technical description are quite realistic scenarios for automation. Therefore, we started with specific recurring tasks, not with the idea of implementing AI in all processes at once.

From a chat to a working tool

We use a corporate tool called OpenCode. It allows not only sending individual requests to the model but also building stable workflows with an agent. First, let's cover the key concepts:

  • Agent — an assistant that receives a task, accesses sources, processes information, and provides a result. For example, it studies the codebase and documentation, compares them, and prepares a draft of changes.

  • Skill — an instruction for a specific task. If we regularly update a technical solution, it's enough to describe the procedure and sources once, and then the agent only needs to be told which document to check.

  • Command — a quick way to launch a pre-prepared scenario. For example, to analyze changes in a commit and briefly describe them.

  • Agents.md — a file with basic instructions and project context: system architecture, available resources, and operating rules. The agent doesn't need to gather this information anew with each request.

As a result, instead of an endless dialogue with the neural network, we get a repeatable process that can be launched as needed. Now we need to figure out which tasks are worth automating.

Where AI truly helps an analyst

We create skills for different stages of work: some are already available to the team, and some are being tested. Tasks with clear rules and small contexts are best automated.

1. Find historical context: what we already know but forgot

Before starting a new task, it's useful to check if we've done something similar before. Sometimes a project returns after several years. During this time, the code might have changed, processes might have been disabled, and solutions might only exist in discussion history.

Searching manually through Jira, documentation, and repositories is time-consuming. That's why we are developing a skill that collects historical context: past tasks, discussions, and the current implementation in the code. The analyst receives not a ready-made solution, but a starting point: what has been done, what are the limitations, and what needs to be checked.

2. Use AI as an opponent, not the author of the solution

This principle seems particularly important to me. At the design stage, we don't ask the agent to invent a solution from scratch: first, the analyst forms a hypothesis based on system knowledge and business context, and then tests its robustness with the help of AI.

The agent acts as a reviewer and asks questions that are easy to miss when working alone:

  • What if the external system is unavailable?

  • What happens if the timeout is exceeded?

  • What alternatives have we not considered?

  • What edge cases have been left out of the main flow?

This way, we get a different perspective on the task: the agent is not limited by our experience.

3. Relieve the routine of formatting and initial verification of technical documentation

Automation is particularly noticeable here. We work with Docs-as-Code: solutions are stored in repositories, changes are made via pull requests, and formatting adheres to agreements and templates.

The agent knows the document structure, section requirements, and formatting rules, so it can:

  • prepare a draft solution based on accumulated context;

  • check the document for compliance with agreements;

  • find typos, duplication, and logical gaps;

  • create a diagram from a description or text from a diagram.

However, the generated document is not the final artifact: it is reviewed and refined by the analyst.

4. Simplify review

We sometimes have quite extensive technical solutions that go through several discussion stages. Once, within a pull request, we received 411 comments. And although this is more of an exceptional case, it clearly shows why even small process improvements can matter.

We created a skill that sorts reviewer comments. Some questions already have answers in the document, others require cross-referencing with the code, and some are genuinely open and could change the decision. The agent prepares draft responses, but the analyst publishes them and makes the decisions.

5. Keep documentation up-to-date

A familiar situation for analysts: a solution is approved, development is completed, but the documentation diverges from the actual implementation. During implementation, clarifications arise and names change, while the team has already moved on to the next project.

We have automated the entire process of updating documentation, leaving the final say to the analyst. The agent compares the technical solution with the code and tasks, identifies discrepancies, and provides a list to the analyst. The analyst confirms which changes actually need to be made, after which the agent updates the document. This way, the documentation reflects the current state of the system.

If an agent can do so much, why is an analyst needed?

This is a logical question when automating more and more tasks. AI creates documents, builds diagrams, analyzes code, and finds inconsistencies. What is the value of a system analyst then?

For me, it's in the responsibility for the result. The agent will suggest solution options, but the analyst chooses the appropriate one: they know the system context, implicit agreements, and business constraints. The analyst is also responsible for the quality of input data and verification of the result. The more tasks we delegate to AI, the more important the ability to evaluate its work becomes.

There's also a downside: if you rely too much on ready-made answers, you might stop understanding the details. Therefore, we use AI not to replace thinking, but to enhance it. Our main practice: first, we form our hypothesis, then we test it with the agent. This preserves expertise while reducing routine work. How not to turn automation into another job

Creating an agent is only half the battle. It's important that it simplifies work, not adds complexity. During our experiments, we identified several principles.

  • Break down tasks into small iterations. One skill — one task. If it grows and performs multiple operations without intermediate checks, it's better to split it into separate scenarios.

  • Record intermediate results. A project can last for weeks, and agreements can change during this time. We store key decisions, discussions, and the current status in the project's external memory. This way, we don't have to reconstruct context from an endless chat with each new session.

  • Don't reinvent automation. If colleagues are solving similar tasks, their approaches should be combined. We store skills, commands, and instructions in a shared repository, divided by areas.

Initially, everyone created tools for themselves. But it turned out to be more effective to test common scenarios on similar tasks, conduct reviews, and share proven solutions. This is how local experiments become common team practice.

What's next?

AI in system analysis is not a replacement for humans, but an opportunity to understand where expertise is needed and what can be accelerated. Without quality sources, clear rules, context, and manual verification, automation doesn't work.
