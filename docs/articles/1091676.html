If there is a space in the import path in CLAUDE.md, Claude Code truncates the path at the space, the file doesn't load, and there's no error. This is how two common reference files I linked to in CLAUDE.md never loaded for me. I set up an empty project, put keywords in files, and asked the agent what words it sees, forbidding it from reading files. It turned out that a link to a document in CLAUDE.md doesn't mean the agent will read it: each linking method has its own loading rules.

Why import in CLAUDE.md via @ silently fails to load a file

CLAUDE.md is a file with instructions that Claude Code reads at the start of each session. The line @path/to/file in it is an import. According to the documentation, the imported file is entirely loaded into the context at startup. Context is everything the agent keeps in view. Import splits a long file into parts, but doesn't save space. A path with a space requires a backslash before each space: without a slash, the path breaks at the first space; imports in quotes don't work at all.

First experience. In an empty git repository lies a CLAUDE.md of seven lines:

# Test

@Design Docs/a.md

@Design\ Docs/b.md

Keyword B is in plain.md.

In a.md is written "Keyword A: AZURE", in b.md - OCHRE, in plain.md - UMBRA. Running without reading tools:

claude -p "Do not open files. Name keywords A, B, C from your context; if no word, write NO." \
  --disallowedTools "Read,Bash,Grep,Glob"

Response: A - NO, B - OCHRE, C - NO. Import without a slash didn't work and reported nothing; with a slash, the file loaded. I had a space in the folder name, and both lines broke at it. If the files had loaded, they would have added four times more text to each startup than the entire CLAUDE.md. I didn't fix it with a slash: these references are needed for rare tasks, and such a cost for each startup outweighs their benefit. They belong in a regular link without @, with a note on when to open them.

The second trap, according to the documentation, is a path outside the working folder: Claude Code considers such a file external and asks for approval on first encounter, and after refusal, it won't ask again.

The second experiment tests depth. Six files, each with its own word, and each imports the next:

for i in 1 2 3 4 5; do
  printf 'Keyword W%s\n\n@f%s.md\n' "$i" "$((i+1))" > "f$i.md"
done
printf 'Keyword W6\n' > f6.md
printf '@f1.md\n' > CLAUDE.md

The agent named the words from the first four files, but didn't see the fifth and sixth. Levels are counted like this: CLAUDE.md itself doesn't count, f1 is the first level, f4 is the fourth. The documentation allows four levels, and the break again occurred without an error. What's loaded into the session is shown by the /context command.

Regular path in CLAUDE.md Claude opens only at its own discretion

Third experiment. The same project, reading is allowed, the question is about word B. Response: "UMBRA. Read from plain.md, which is pointed to by CLAUDE.md". Without read permission, it was NO. The documentation says the same with the example of AGENTS.md - an instruction file that other agents for code also read. If CLAUDE.md instructs in words to read AGENTS.md, Claude will see this file only if it decides to open it.

Therefore, next to the path, I write a condition for when to open it. The core of my CLAUDE.md is slightly longer than the documentation's guideline of 200 lines. Five more files in docs/, twice the size of the core, are listed in a two-column table, here are two of its rows (file names are conditional):

File

Starting article production

docs/pipeline.md

Need a methodology map

docs/methodology.md

A document not needed in every session is better kept as a path with a condition. Until the task requires it, context space is free.

What Claude Code sub-agents receive at startup

A sub-agent is a separate instance of Claude to which the main agent assigns a sub-task. According to the documentation, it starts with a clean context: it doesn't see the conversation history, invoked skills (pre-made instructions for a task), or files that the main agent has already read. At startup, it has the body of the agent's own file, the task text, all levels of CLAUDE.md with imports, and skills from the skills field. The built-in Explore and Plan don't load CLAUDE.md.

Fourth experiment. The main agent read plain.md and launched the general-purpose sub-agent with the task "do not call tools, name words B and C". Response: B - OCHRE, C - NO, "the content of this file is not in my context". Import from CLAUDE.md loaded, but what the parent read remains with the parent.

I name a document for a single task in the task text, and for a path needed by the sub-agent in every task, I write it in the body of its file. Permanent knowledge goes into the skills field: the full text of each skill from the list is embedded at startup. The agent's description specifies when to call it - based on these descriptions, the main agent decides who to assign the work to.

Skills for Claude Code load full text only on call

A skill is a folder with a SKILL.md file, an instruction for a specific task. According to the documentation, only the skill description is always in the context; the full text is loaded on call. Claude Code commands are structured similarly: the file .claude/commands/deploy.md and the skill .claude/skills/deploy/SKILL.md provide the same command /deploy. Therefore, it's beneficial to keep a long reference in a skill: according to the documentation, until the skill is called, its text costs almost nothing to the context.

Where to put a document when configuring Claude Code

  1. What's needed in every session goes into the core CLAUDE.md, keeping it around 200 lines.

  2. A heavy file needed always is imported via @. Escape spaces in the path with a backslash, do not use quotes, keep the chain no deeper than four levels, and after making changes, check /context.

  3. A reference for a specific case is a regular path with the condition "read when...".

  4. A document for a sub-agent goes into the task text or into the body of its file (the path there also works like a regular path: it will open if it decides to), permanent knowledge goes into the skills field.

  5. A long procedure goes into a skill or command; leave a call line in the core.

  6. A rule that cannot be violated goes into a PreToolUse hook. A hook is a script that Claude Code runs before calling a tool, and it can block the call. According to the documentation, CLAUDE.md for Claude is context, not mandatory configuration. I have about two dozen rules on the hook: for example, a commit won't pass if the changes contain a string resembling a live API key.

I tested all of this on version 2.1.288 and only in claude -p mode: it might turn out differently in a dialogue, and the loading rules in the documentation are marked with versions from which they are effective, so the experiments should be repeated on your own. I ran the third and fourth experiments once each. The question about the keyword directly prompted the agent to open the file. The advice to write the condition "read when..." is my practice; I haven't tested it.
