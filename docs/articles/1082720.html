A week ago, I released skillmem — local procedure memory for code agents. In the past day, there have been eleven releases: from 0.9.3 to 0.10.5. Not because I had nothing better to do, but because I sat down to test my own product and found eleven things that needed fixing. This post is about what exactly — almost every point applies to any tool that lives within an agent's loop.

The Beginning: 4083 Sessions in a Day

It started with a harmless question: is everything working? I looked into the hook logs and saw that the Stop hook had triggered 4083 times in a day, whereas the day before it had triggered six times.

The mechanism: a hook on Stop asks the model to summarize the session using claude -p. The child process is a full Claude Code session, and on its Stop, it triggers the same hook. There's no bottom. In a day: 3901 phantom sessions, gigabytes of transcripts on disk, ~286 million cache tokens subscribed, and garbage summaries like "session is empty, please provide text" kept appearing in my context on the next start.

The most annoying part: we've had this bug before — on 09.09, and it was closed with three safeguards. When the project was renamed, the hooks module was moved, and all three were lost: the env flag in the child process, the slot semaphore, and --strict-mcp-config. I brought back one first, then, after understanding it, all of them.

A lesson worth hanging over the desk: any hook that launches an agent must mute itself in the child process. And if you're rewriting a module where safeguards existed, transfer all of them, not just the ones you remember.

Next — On the List

0.9.3 — anti-recursion (env with a refusal flag for the child process) plus a test to ensure the flag actually reaches it. The old test only checked "if the flag is set externally — stay silent," so the regression passed the green tests.

0.9.4 — frequency limit. It turned out that Stop in Claude Code triggers after every response, not when the session closes: on a normal workday, this means calling the model on every turn and a lot of nearly identical notes. Plus: the mark is set on an attempt, not success (otherwise, a failing model buys a new call on every turn), the return code is checked (otherwise, the error text "usage limit reached" longer than 100 characters was saved as memory and overwrote a good summary), and the slot semaphore was returned.

Also there — a small but pleasant find: the child claude -p now launches with --no-session-persistence, and phantom transcripts don't appear at all. Gigabytes of garbage are no longer reproduced.

0.9.5 — four silent defects found by external review:

  • recall for NotebookEdit was dead: the hook read file_path, but Claude Code for notebooks sends notebook_path;

  • 7793 notes out of 7793 were without session binding — the writer puts source_session in frontmatter, but the importer only knew originSessionId;

  • the MCP guard lied with numbers: it counted all servers, not the intersection with the standard, and could say "12 out of 10 connected";

  • the ledger of shown records lived in the shared /tmp, where a machine neighbor could create a file in advance and mute someone else's recall.

0.9.6 — races for the final summary. Slow Stop and SessionEnd overlapped, and the old result overwrote the final one. A note now stores the transcript volume it was made for, and whoever read less doesn't overwrite. Plus an honest budget: Claude Code raises the SessionEnd budget to the hook's timeout, but no more than 60 seconds — meaning the final call should ask the model for less.

0.9.7 — trust boundary (more on this below), plus skillmem recap and skillmem hooks-status. The latter appeared from a simple observation: hooks are designed to mute their errors to avoid breaking the session — which means a hook that quietly died looks exactly like a hook that has nothing to do. Now there's a command that shows launches, skips, failures, and the last line of each.

0.9.8 — a missed turn no longer reads the transcript. The limit check was placed after counting file lines, meaning on each missed turn, we read the entire transcript in vain. On my machine, this means files up to 59 MB and 840 MB in total.

0.9.9 — publishing a summary became compare-and-swap: checking freshness and replacing the file were two steps, and a Stop that passed the check before SessionEnd wrote the final overwrote it afterward. The base is re-read within a short lock — milliseconds, not a model call.

0.10.0 — trust boundary, the biggest piece. There's a separate post about this, in short: each record has an origin (owner/agent/imported/derived), trust is granted only by the owner with the skillmem trust command, editing an approved record's text removes approval, and anything unapproved is mixed into the agent's context within a marked "data, not instructions" frame. The transcript summarizer runs without any tools (--tools "" + --strict-mcp-config), and if the CLI doesn't know these flags, the summary isn't made at all. It closes the path "external README → agent memory → user rule.".

0.10.1 — it turned out that three manifests (including server.json for the official MCP Registry) still advertised version 0.9.2 — meaning anyone who installed us through the registry would get a version with that very recursion.

0.10.2 and 0.10.3 — two ends of one defect, and it wasn't me who found it, but CI. The test failed on all OS, and the test was right: FTS queries were cut by spaces, so /work/analysis.ipynb turned into a single phrase token and found nothing. And the tool-recall hook passes the file path to the query. On a standard installation pip install skillmem (without semantics), recall for Edit/Write/NotebookEdit was completely dead — locally, this was hidden by the embedder. Digging deeper: the index itself discarded tokens shorter than three characters, so db, py, js, ci were absent from all records.

Second lesson for the wall: keep a run without optional dependencies in CI. We had one, and only because of it did the defect surface.

Also there, I caught my own mistake in migration: rebuilding the index on a live database (8917 records) takes 66 seconds, and init_schema is called by every hook with a 10-second timeout. Migration now only sets a flag; the heavy work is done by a nightly job or skillmem reindex-lexical.

0.10.4 — found during testing a real installation on Ubuntu: a clean database reported that it needed re-indexing. On a fresh install, doctor would scare people for no reason.

0.10.5 — Dockerfile in the repository and honest serverInfo. MCP directories collect the container to evaluate the server, and if their AI build fails, the server doesn't appear in the directory search. Our own build is more reliable than guesswork: the image is 297 MB, initialize responds with the actual version, tools/list returns all 9 tools via stdio. Before this, the server presented itself with SDK version 1.30.0 — a version the package never had.

The loop that justified itself: Requirements → review by another model → implementation → review → deploy. Moreover, each reviewer's assertion was checked by the team on a live system, not taken at face value: one out of six checked turned out to be incorrect (the bug had already been fixed during development).

The Result

214 tests, and each safeguard is verified by reverting the fix — I break the fix, the test turns red, otherwise the test doesn't count. Cross-platform compatibility is verified not by declaration, but by installation: macOS and Ubuntu from PyPI, Windows in CI.

pip install -U skillmem
skillmem init            # Claude Code: hooks on five events + 9 MCP tools
skillmem init --codex    # same memory for Codex CLI
skillmem hooks-status    # what hooks actually did: launches, skips, failures

If you are on 0.9.0 –0.9.2 — update. There's recursion there, and it's costing you quota.
