Vibe Coding <> Documentation?

What happens if an AI programmer gets context not from its own chat, but from the project's functional and architectural model?

For the past couple of months, I've been working on several applied tasks.

  • An analyst agent that helps identify the business process functional framework of ERP systems. Our specialization is replacing one ERP system with another, and such work begins with identifying the As Is in the outgoing system and modeling the To Be in the new one. The more completely we identify existing functions and model them in the new system, the more reliably the transition can be carried out.

  • An agent – a presale manager. It helps the project manager prepare a commercial proposal based on unstructured customer documentation and project methodology. A task that previously took about two weeks was supposed to take about an hour in the experiment.

  • Process assistant — an experiment where an employee interacts with a "zoo" of corporate systems through a Telegram bot. For example, a project manager launches a new project, the bot suggests a suitable process, then creates a counterparty in 1C and a project in Redmine itself. And we tested all this without classic integration via HTTP services or APIs. Pure nocode

Each lab work ends with a YouTube video and the appearance of another folder. At some point, the volume of the three projects reached about 1.7 GB. What if in a few months I want to change something in each of these agents?

I'll open the project folder in Cursor. I'll see the code. I'll see Markdown files. And, most likely, I'll see a rather large chat where I was self-forgettingly giving the agent valuable instructions until it started producing the desired functionality.

In general, it's my fault. I already have experience with "laboratory" vibe coding: I don't set the task to immediately get an industrial product, but explore the question "can this also be done?". Therefore, I envy experiments where a blogger throws a task at an agent and goes away for the weekend, and on Monday they are already receiving money from the first clients. True, without details about the project.

But after several such experiments, it became clear that the next question should be different:

What will happen if vibe coding starts to create not only the program but also its documentation?

And not in the sense of writing a few more Markdown files.

I decided to try to make the documentation and functional model of the project created simultaneously with the code.

Task for the current lab work

Combine the speed of AI agent programming with full documentation of improvements using ERP-tools.

Intermediate task - We have a 1C version of ERP-tools where the project team works. Now we need to release a simplified web version of the program with key artifacts so that the customer can monitor their project in the browser.

There is also a star task.

In fact, the current project is a "2 in 1" project: we are creating a project that creates another project.

As always, there is a video version for YouTube and RuTube, where you can see the agent's real work.

Markdown has already taught us one important thing

For development with agents, it is now completely normal to use Markdown files.

They store system rules, requirements, architectural decisions, instructions, project descriptions, and individual skills. The agent can read them, and some tools already allow connecting such knowledge through MCP and other connectors.

But we have another advantage

ERP-tools is a database where functional model artifacts are stored not in text files, but in separate entities and relational links. And ERP-tools can describe ERP systems - the most complex and gigantic types of software, and md files are definitely powerless there.

Therefore, the project began with the creation of an MCP server — an extension for 1C with which Cursor will communicate — and a system prompt that explains to Cursor the methodology of the five ERP-tools artifacts and the rules for working with them.

That is, we decided to test the hypothesis:

What if the AI programmer's external context is not a set of Markdown files, but a structured project model in a specialized database

At the time of writing, not all necessary objects have been created yet, but we can already talk about some success in the lab work. The first interfaces and application commands exist.

Project Preparation

First, we created a new project in ERP-tools — ERPToolsWeb.

Then we created a Cursor user and assigned them as the project manager — so that they would have read and create rights within the project.

After that, we created an empty extension and saved it in XML. Here we had to help Cursor a bit — it always makes mistakes when creating an extension from scratch.

We don't present the agent with a fait accompli:

"Here's the repository. Do whatever you want."

We are trying to build a managed loop in which the agent suggests, gets context, works within the given framework, and leaves behind not only code but also architectural traces, while people control and make decisions.

What's wrong with regular vibe coding

Before starting the experiment, I asked Cursor to list the problems of vibe coding itself.

It turned out to be a rather familiar list.

The data model drifts

Each AI agent session solves the task locally. If there is no general description of the model, the agent easily adds new entities and attributes, not realizing that a similar object already exists.

Model errors surface late

The agent implements exactly what is described. If there is a gap in the description, it can quite accurately code this gap.

The agent does more than requested

This is one of the main sources of regressions in vibe coding. The model "improves" adjacent code "at the same time," renames, refactors, and sometimes changes what it was not asked to change at all.

Access rights are scattered across the code

After 30-40 functions, it's hard to tell who can do what. If each session invents its own way of checking roles, architectural chaos and potential security issues gradually emerge.

When making changes, it's unclear what they affect

After a few months, neither the human nor the model remembers where a specific rule is implemented and what adjacent requirements are related to the same function.

Knowledge lives in the chat, and there's nothing to check the result with

This is the result of Cursor's output, but of course, it all depends on the ability to ask questions...

The context of vibe coding is often a correspondence history. A change of session, developer, or just a long break almost nullifies the understanding of the project.

If two or more vibe programmers work on the same project, each of them starts to live in their own context. However, a complex corporate application requires a large number of common solutions, libraries, data models, and rules.

Architectural Decisions

Therefore, we didn't start with code. We started with architectural decisions — rules intended for both Cursor and the team.

ERP-tools uses a requirement of type "Architectural Decision." Externally, it really resembles a Markdown file: both contain text — there is a name and a detailed description. But in one case, you need to read the entire file, and in the case of a database, the text is in a special place, and you don't need to read the entire table.

The requirement has a status model — from "Not approved by the customer" to "completed," and within it, there is a separate approval by the architect and project manager.

We fixed the rule: architectural decisions are recorded in the database and require approval in ERP-tools.

And the main rule of the system prompt:

Cursor cannot fulfill a requirement that has not been approved by people.

Cursor criticized this rule and called it bureaucracy that slows down execution.

But later, it noticed itself:

"As the team grows, the benefit increases: auxiliary steps that seem like bureaucracy to an individual become the meaning of the process for the team."

It seems to me this is an important observation. For one vibe coder, approval really looks like an unnecessary stop. For several developers, it's already a synchronization mechanism. And what if a vibe coder works on several projects simultaneously?

Of course, I didn't invent architectural requirements — I asked Cursor to create them, it tweaked MCP, and created about two dozen requirements that can be read and agreed upon. Previously, I started projects with the team: "Create a website that..."

We spent a few minutes agreeing on the project's file structure — and at this moment, someone would really want to say, "Why are we doing this? Start burning tokens on code!"

But this is precisely the point of the experiment.

We don't want to hand over the project to the agent's mercy for a second. We want the agent to program within the agreed model.

After agreeing on the initial decisions, Cursor deployed the project, created the file directory, and started loading Django — that is, executing the directives of the agreed requirements.

Metadata Objects

The first small battle was synchronizing terminology: in ERP-tools, an entity is called "Users," while Django uses User. Such things seem trivial until you start building a system where several models need to speak the same language.

In ERP-tools, metadata objects are the basis of navigation. Inside an object, there is a list of attributes indicating data types, including references to other metadata elements. Once again — we are not inside the ERP-tools configurator. We are in Enterprise mode working on a Project. Other teams are working on other projects nearby. No one interferes with anyone.

The traditional "Code" and "Name" did not cause problems. But the other attributes required separate consideration.

We decided that a meaningful attribute should be justified by a requirement — functional, and sometimes non-functional. This is exactly how we do it on ERP implementation projects — all "gaps" must be fixed by a created Requirement, not just a phone call.

The reason is very simple. Cursor easily adds what it considers useful to the Django model. Therefore, we came up with a rather interesting rule:

AI can freely generate implementation, but should not freely invent the business model — at most, suggest and advise

Creating ten requirements with only a name takes a few minutes.

However, in six months, this can be very useful context: any project participant will see why a particular attribute exists in the model. We have a small life hack — the 1C database is in front of us, and we just need to select the attributes needed in the browser.

In vibe coding from scratch, the stage of drawing the metadata object model, attributes, possible functions — this is probably a multi-day job specifically within ERP-tools — far from the frantic programmer.

Migrations

When we prepared the first table for migration, we had to make another decision. The agent, as it turned out, is itching to start programming everything that's poorly attached.

Therefore, the system prompt included a rule: any task in Cursor must be controlled.

To do this, the agent creates a roadmap item, formulates a proposal as a note, and waits for permission. ERP-tools already has a separate mechanism for this — the "Roadmaps" directory and associated "notes."

From the perspective of the project manager, and also the "mechanic" himself — the programmer who controls an agent with practically unlimited capabilities, this is no longer bureaucracy, but reasonable precautions.

The agent proposes. It is allowed. Only then does it act.

Function

The first table "Users" is ready. Now the most important thing — functions. In our methodology, a function is a completed user action on a metadata object. I am deliberately repeating this definition because "function" can easily accommodate anything. Here we are talking specifically about user behavior.

A business process is a container for functions, and a function answers a simpler question:

What exactly should the user be able to do in the application?

For example, we have the "Users" table. One of the functions is "Create User."

This is a fairly simple directory, and the most valuable thing in it is a correctly formulated name. For a person, it immediately sets the meaning.

And then it turned out that such a function doesn't exist, and the first user should be created simultaneously with the Account, and then Users should be invited to the account.

Therefore, we skip the creation of the second metadata object, Accounts, and the general function "Registration of the account administrator and a new account" here.

For an LLM, a good name also saves context: the model doesn't have to read a long explanation of what a function means if its name is already formulated accurately enough.

Instruction

The next question was more interesting and actually key.

Could the LLM itself come up with an instruction for the function and figure out what needs to be done at the first step and what at the last?

Cursor managed.

It built a sequence of actions: find the necessary directory, click "Create," fill in the required attributes, and finally save the object. But there was no magic here at all. We had previously fixed the composition of the metadata object and the requirements for its attributes.

The LLM simply performed this work, taking into account the known rules, and turned them into a sequence of user actions. That is, it did the work of a regular analyst acting according to the rules.

After designing the instruction, Cursor asked for permission to perform the task through the "Notes" mechanism.

I gave permission — and it went to program.

In about 10 minutes and about 8 million tokens, it completed the implementation of a separate, not complex function (for reference — in 1C ERP, there are an average of 700 not complex functions for users. The main difficulty is that there are 700 of them).

Then, according to the agreed scenario, it tested it. And even provided each step of the instruction with a picture of the user's actual actions (because this is part of the prompt methodology). This is where what we started the experiment for begins.

Upon completion of the function programming, we received not only code. We received a complete instruction for working with the function. We programmed and documented the system's Function

And the requirements reflected in the instruction received the final status "Completed by inclusion in the instruction" — this is how ERP-tools works.

This results in a chain:

Function ↓ Metadata Object ↓ Attributes ↓ Requirements ↓ Instruction ↓ Approval ↓ Code ↓ Testing ↓ Visual Instruction

And this, perhaps, is the main result of the lab work.

Vibe coding begins to create documentation not after programming, but simultaneously with programming.

What about access rights?

Calm down.

Rights should also not appear in the agent's head. In ERP-tools, there is a separate place for them — access profiles, and the rights themselves are assigned directly to the function: who can perform it.

This leads to another important thing. When Cursor implements a new function, it should not independently decide who gets access to it.

This decision is in the project model, and in our project, the role model is quite rich and works with RLS by project and account. And later, Cursor recommended adding a new attribute "Account" to the working tables, although there was "Project," which has "Account" as the owner, but Cursor convinced that a separate attribute would speed up the work. We recorded this in a Non-functional requirement (as it's a security issue), added a new attribute to the Metadata Object in ERP-tools, and performed a migration. That is, we discussed it in the chat, it created the necessary changes in ERP-tools, I approved the new requirement, and it changed the migration.

There was also a case of change — adding a new attribute to the table, and you know what — it not only added it but also updated the instruction, as this field now needed to be filled in on the form, and I didn't ask it to do that!!!

Context

Now we can move on to the most interesting technical question. How does Cursor get all this knowledge? MCP allows it to access ERP-tools with requests.

If we are designing a specific function, we can get the associated metadata object, its attributes, and requirements. At the same time, for project work, general architectural decisions and non-functional requirements are also needed.

At first glance, it might seem that we have simply replaced Markdown files with a database. But the experiment showed an important difference. We don't need to load all the documentation into the context every time. We can request exactly the piece of the model that is needed for the current task.

Cursor even suggested performing each new task in a new chat — it was also worried about the experiment's progress, like its colleague ChatGPT.

And measurements on a comparable task showed an interesting result: instead of about 8 million tokens, about 4 million were used. This is not a benchmark or a universal figure — it's the result of a specific experiment. Whether it's a lot or a little — I don't know.

But the direction seems logical. The less irrelevant context, the less the agent has to keep old decisions, old attempts, and chat history in mind.

Therefore, ERP-tools plays another role here:

It is not only a documentation repository. It is a context management mechanism for an AI programmer.

Development Cycle

Thus, a fairly simple cycle has formed. We don't ask the LLM to write the entire application at once — like trendy bloggers with unknown super-applications.

  • First, we form the model.

  • Create an object.

  • Define its attributes.

  • Fix requirements.

  • Create a function.

  • Describe what the user should be able to do.

  • Then we ask the LLM to suggest an implementation based on this model.

  • After verification, we allow programming.

  • After implementation, we get a test and a visual instruction.

And this is starting to resemble not a chat with a programmer, but a production line. And the process involves thoughtful work by specialists, not the reckless rush of a programmer tasked with destroying hated tokens at any cost.

Non-functional Requirements

Non-functional requirements work similarly. If Cursor asks a question, for example, about access rights, design, performance, or other system properties, we don't leave the answer only in the chat.

We ask the agent to formulate the proposal as a requirement. After that, the requirement is approved in ERP-tools and remains forever.

Thus, the decision ceases to be part of a temporary conversation with the model. It becomes part of the project. This is a very important boundary. And several times during task execution, Cursor said that the given solution violates the architectural contract — meaning it really keeps this data in context.

The chat is where the agent thinks. ERP-tools is where the adopted decision becomes part of the project, where people look and visualize the application, which gains more and more functionality with each hour

Functional Requirements

According to our methodology, a functional requirement is a requirement that can be demonstrated in an instruction and that typically defines the execution of a specific step by the user. This fits well into the new scheme.

  • The function describes a completed action.

  • Requirements explain what exactly should happen in this action.

  • The instruction shows the action to the person.

  • And the code implements it for the system.

Documentation

So, the initial goal of the lab work was simple: to understand if the main principle of vibe coding could be changed so that the system simultaneously receives and generates documentation along with programming.

Of course, almost all modern vibe coders have already come up with the idea of external context.

System prompts, skills, Markdown files, MCP connectors to trackers and knowledge bases are used. Therefore, the idea of external memory for AI itself is not new.

Our experiment is different. We tried to use not a collection of text files for this role, but an already existing structured model of a corporate application, which was created for other purposes — to describe the functionality of ERP systems.

  • Markdown stores descriptions.

  • ERP-tools stores the model.

In Markdown, you can write:

"The object has an "Assigned To" attribute."

In ERP-tools, this attribute is part of the model object, has a type, is linked to requirements, functions, and other objects.

Cursor can create another huge Markdown file after development and write in it how the application is structured. Formally, there will be documentation.

But who will read it? I personally find Markdown documents difficult to read. "Why read them — LLM lays it out softly, but sleeps hard"

In ERP-tools, a person can look at the project model from different angles: through functions, objects, requirements, rights, instructions, business processes — perhaps a couple more lab works — and we will work like Tom Cruise in the movie Minority Report.

And we have a full-fledged Query Console, which helps to assemble data in the desired format.

Technical Level: Why We Need DevInfo

There is another, more technical level.

ERP-tools has a DevInfo information register that allows generating "injection code" — a special tag that Cursor can insert into the code near the requirement implementation location.

Cursor records which file was changed. Why is this needed?

Imagine that after six months, an architect sees a suspicious piece of code. The usual question:

"Why is this here?"

In our scheme, you can ask the reverse question:

"What requirement led to the appearance of this code?"

This is where traceability appears:

Requirement ↕ Function ↕ Instruction ↕ Code

You can go from requirement to implementation. And you can go from strange code back to its basis. This is especially interesting for systems that are intended not just to be written, thrown at the customer and run away, and then developed for many years.

However, the approach is still controversial. Such tags add service noise to the code, require discipline, and are not always needed during active refactoring.

But for stabilizing and subsequent maintenance of a complex corporate application, such a link can be very useful.

Graphical Schemas

There is another interesting result. Cursor quickly figured out how to create graphical schemas within ERP-tools in our "1C" format and BPMN.

That is, the agent can work not only with text and code. It can create and edit visual project artifacts. This is another argument in favor of the fact that a structured project model can be more useful than a collection of Markdown files.

In fact, Cursor has become an analyst with whom any question can be discussed — the prompt taught it the methodology, and the connectors allow it to request and record any information. I haven't forced the poor Cursor to write technical specifications within Requirements yet (as I force analysts), but there will be no doubt — it will do it.

Several Vibe Programmers

Now let's return to the original problem. What happens if several AI programmers work on the same project? In the usual scenario, each agent has its own chat. Each accumulates its own context. One agent knows why a certain decision was made yesterday. The second doesn't know about it.

A third might even suggest doing everything differently. And most likely, each developer will create their own Monolith, the resulting program will be 3 monoliths, i.e., with 3 microservices — because this is a way to justify violating the DRY principle.

In our scheme, the common context is external and highly organized. Architectural decisions are agreed upon. Functions are defined. Requirements are linked to objects. Rights are in the model. Instructions are part of the project and linked to requirements.

And honestly, it becomes clear — what does this system even do?

Therefore, the agents can be different, but the project model can be common. This results in the following structure:

                  ERP-tools (common context) ┌──────────┼──────────┐ ↓ ↓ ↓ Cursor Cursor Cursor agent 1 agent 2 agent 3 ↓ ↓ ↓ code code code └──────────┼──────────┘ ↓ Git

This is more like a development pipeline than a conversation with one smart programmer.
