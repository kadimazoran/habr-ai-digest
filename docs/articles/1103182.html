How I Did It Before: Software 2.0

Six months ago, 'making an AI that plays a game' meant one thing to me: reinforcement learning (RL). A neural network looks at the screen, presses buttons, gets rewards for points scored, and thus learns from millions of attempts. This is how Atari game-playing networks were once trained. I didn't succeed then.

In this project, I went through the same process again, more carefully, and recorded every run. The agent saw a downscaled screen, could only move the paddle in small steps, and trained for about a day on a laptop's CPU: 17 million steps, approximately 17 hours of pure training. The average score increased and got stuck at 7-8 thousand points. It never cleared the first round of bricks; it sometimes reached the second round via a bonus capsule. I changed the reward, let it train from convenient positions, and increased the number of evaluation games. The edits helped a little, but it didn't go further.

All the training code was written by Claude, a large language model (LLM), acting as a programming assistant. It prepared the environment, reward calculation, and result verification. It found bugs and suggested edits. But all this was within the method I chose. The AI for me was a trainable network, and I used the LLM as a tool to create it. Now I understand that this is exactly Software 2.0 according to Karpatsky: the programmer 'sets up datasets and training goals.' When I tweaked the reward and starting positions, I was programming exactly like that.

Why it was so difficult for the agent became clear later. The bounce direction depends on the impact point: if you move the paddle within ±12 pixels of the ball's center, the angle changes from about 20° to 160°. On a screen halved in size, the ball turned into a blurry spot, and the paddle only moved in small steps. It was difficult for the agent to both notice this mechanism and use it. The agent itself didn't figure this out. I hinted at what the bounce depends on, and only then did we measure it. We later redid the vision and control, but didn't finish training the new run.

How It Worked: Software 3.0

Then I tried a different approach. A separate session of the same LLM was given not the task 'write code for training,' but a 'body' and a goal. The body was an emulator: it ran the old DOS game on a modern computer from the very beginning. The researcher could look at the screen, press keys, move the mouse, and return to saved game moments. The goal was stated as: 'figure out how to play yourself and write a player program.' I named the game and explained how the result would be verified. I didn't give hints on how to play.

The model was the same, Claude Opus 5.5. Its role changed, and with it, the conditions: precise mouse control, full frame instead of downscaled, save states for experiments.

And here's what I realized when I rewatched the presentation. My program here was no longer code, but text: a one-page assignment and a description of the body. The LLM, the very interpreter Karpatsky talked about, read it. And it wrote a completely ordinary player code, which doesn't need any LLM to play. Software 3.0 wrote Software 1.0. I controlled its work through the assignment: I explained the goal, the rules, and how we would verify the result.
