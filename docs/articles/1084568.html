The core of a basic agentic harness is a simple loop: an LLM receives a task, selects and calls a tool, the result is returned to the context, and then the model decides what action to take next. The loop continues until the model decides the task is complete.

This loop is correct, but naive. One pilot in a good fighter jet can win a dogfight, but no one conducts an entire air operation like that. Real operations have mission planners who, even before takeoff, determine which sorties need to be flown; squadrons performing independent tasks in parallel; fuel limits and a bingo fuel signal after which you need to return to base; flight recorders that allow you to reconstruct the course of each sortie; and finally, post-mission debriefings to determine if the mission was truly successful.

None of this replaces the pilot. All of this creates an infrastructure around them, thanks to which the system as a whole remains fast, safe, easy to debug, and measurable.

The same happens with agents. In this article, we will take the basic agent loop and sequentially add typed tools, DAG and parallel execution, multi-level memory, verification, role separation of Planner / Worker / Critic, multi-dimensional budgets, and tracing – and then connect it all with a thin orchestrator.

The entire experiment is built around one question:

How to turn a simple agent loop into a reliable system capable of planning, acting, recovering from errors, and proving that it has done everything correctly?

End-to-End Example

In the original series, the author starts with a minimal agentic harness – a loop where the model receives a task, calls a tool if necessary, returns the result to the context, and continues until the task is completed. We haven't translated a separate article about the basic version, so we'll only provide the starting point here, from which the architecture will be built further.

def run_agent(goal: str, llm_provider, budget: Budget | None = None) -> AgentState: state = AgentState(goal=goal, budget=budget or Budget()) system = build_system_prompt() consecutive_errors = 0 while state.status == "running" and state.budget.has_room(): state.budget.steps_used += 1 user = build_user_prompt(state) t0 = time.time() raw = llm_provider.complete(system=system, user=user) latency = int((time.time() - t0) * 1000) result = validate_proposal(raw) if not result.ok: consecutive_errors += 1 state.trace.append(Step( index=state.budget.steps_used, thought="(parser)", action={"type": "invalid", "raw": raw[:200]}, observation=f"VALIDATION_ERROR: {result.error}", latency_ms=latency, )) if consecutive_errors >= 3: state.status = "failed" continue consecutive_errors = 0 proposal = result.parsed action = proposal["action"] if action["type"] == "final": state.status = "done" state.final_answer = action["answer"] else: tool = TOOLS[action["name"]] try: obs = tool.fn(**action["args"]) state.budget.tool_calls_used += 1 except Exception as e: obs = f"TOOL_ERROR: {type(e).__name__}: {e}" state.trace.append(Step( index=state.budget.steps_used, thought=proposal.get("thought", ""), action=action, observation=obs, latency_ms=latency, )) return state

Throughout the article, we will build an agent to compare cities. After receiving a list of cities, it generates a report comparing population and time zones and provides a brief text description of each city.

The task seems almost ridiculously simple, but it was chosen for a reason.

Each request for one attribute for one city is independent of the others. Therefore, the task for three cities naturally breaks down into nine tool calls, which can potentially be executed simultaneously.

The final report, on the other hand, depends on the completion of all these calls: before compiling it, you need to wait for each result. This means we no longer have a flat sequential list of steps, but a real dependency graph.

Furthermore, the result is easily verifiable programmatically: for example, to ensure that each requested city is indeed present in the final report.

Finally, the cost of tools varies greatly. Getting population and time zone is a simple dictionary lookup in memory, while brief city descriptions and final aggregation require LLM calls. This creates a realistic budget pressure for execution.

For reproducibility, the data retrieval tools read from a small test dictionary CITY_FACTS, so the entire notebook can be run without network access. Components with LLM can work with either the real Anthropic model or a deterministic mock.

This brings us to the first primitive.

Pluggable "Brain"

Almost every component we're going to build ultimately calls an LLM: the planner, the summarizer, the aggregator, the critic. If you hardcode this call to a single SDK, the entire harness becomes poorly testable and tied to a specific provider.

Therefore, first, let's define a base class that abstracts the API details of different LLM providers:

class LLMProvider: # Shared interface. Subclass to plug in a different backend. def complete(self, system: str, user: str, role: str = “default”) -> str: raise NotImplementedError async def acomplete(self, system: str, user: str, role: str = “default”) -> str: # Wrap sync call in a thread; works for any SDK. return await asyncio.to_thread(self.complete, system, user, role)

For testing and debugging, we also implement a MockProvider that returns deterministic responses based on the role: a reference plan when asked to plan something, a template one-line description when summarizing, and a pass/fail verdict based on rules when checking a result.

This allows us to separate two fundamentally different problems during development: "Is my orchestration broken?" or "Did the model just fail to make a good plan?"

Thanks to the mock provider, all experiments in this article can be reproduced on any machine without relying on the behavior of a specific model.

Typed Tools

In the basic harness, we manually validated tool arguments. This approach quickly becomes unworkable: each new tool duplicates validation logic, the LLM doesn't see a formal schema and has to guess the argument structure, and errors turn into arbitrary strings that make it difficult for the model to understand what exactly needs to be corrected.

Instead, we describe the arguments of each tool with a Pydantic model and use a single definition for all tasks:

@dataclass class TypedTool: name: str description: str args_model: type[BaseModel] # Pydantic model defining the arg schema fn: Callable[..., Any] cost_hint: float = 0.0 # relative cost for budget accounting def schema(self) -> dict: """Shape expected by Anthropic/OpenAI tool-use APIs.""" return { "name": self.name, "description": self.description, "input_schema": self.args_model.model_json_schema(), } def run(self, raw_args: dict) -> Any: args, err = self.validate_args(raw_args) if err is not None: raise ValueError(err) return self.fn(**args.model_dump())

This solution immediately provides several benefits: runtime validation, JSON Schema for arguments, documentation, and a point for accounting relative cost via cost_hint. The same argument schema can be used when describing tools for both Anthropic and OpenAI, even though the external wrapper for their APIs differs: Anthropic uses input_schema, while OpenAI uses parameters within function tool.

The description of each field in Field(..., description=...) becomes part of the tool catalog that the Planner receives. Thus, a single schema serves both for validation and for explaining to the model what arguments the tool accepts.

But most importantly, where exactly the error occurs.

If the arguments are incorrect, we find out before running the tool. This is especially important for expensive operations and actions with side effects.

A bad plan should fail fast – be rejected at the validation stage, not crash somewhere deep within a database query.

Full-fledged frameworks and APIs converge to this approach in one form or another: LangChain tools, Anthropic's tool use, and OpenAI's function calling.

Our registry will have four tools with three cost levels:

  • get_population() and get_timezone() are practically free: they are simple dictionary lookups, so we set cost_hint=0.1 for them;

  • summarize_city() performs one LLM call per city, so its relative cost is higher – cost_hint=1.0;

  • Finally, aggregate_report() performs the most token-intensive synthesizing call: it compiles all received data into a final Markdown report. We set cost_hint=2.0 for it.

It's worth noting one important detail here: the last two tools themselves call the LLM.

To the Worker, all tools look the same, but some of them are wrappers around additional LLM prompts. In other words, the LLM call is encapsulated within the tool, not a separate step type.

Therefore, such internal calls can be cached, rate-limited, or even switched to a different model independently of the rest of the harness.

A Plan is a Graph

The basic harness performed one action per iteration. This approach works as long as the steps are strictly sequential, but our task involves nine independent requests whose results converge into one final aggregation:

A regular while loop would execute these operations one by one. A Directed Acyclic Graph (DAG) explicitly describes dependencies and allows the executor to concurrently run everything that is ready to execute right now.

Therefore, instead of asking the LLM for the next action at each iteration, we ask the Planner to build the entire graph at once. In other words, the model declares the task structure before execution begins.

But the Planner is also an LLM, which means it can hallucinate not only data but also the plan structure: for example, refer to a non-existent node ID or create a cyclic dependency that will never resolve.

Therefore, the first thing we do with the received plan is validate it, before spending tokens and resources on executing a demonstrably broken graph.

def ready_nodes(self) -> list[PlanNode]: """Nodes whose deps are all DONE and are themselves PENDING.""" out = [] for n in self.nodes.values(): if n.status != NodeStatus.PENDING: continue if all(self.nodes[d].status == NodeStatus.DONE for d in n.deps): out.append(n) return out

ready_nodes() is the heart of the execution scheduler: at any moment, this function returns a set of nodes whose dependencies are all met.

For the task with three cities, the Planner creates ten nodes: nine data retrieval operations with empty dependency lists – all ready for concurrent execution – and the final aggregate_report, which depends on the completion of all nine.

Parallel Execution of the DAG

The Executor performs a level-synchronous traversal of the DAG: it computes the set of ready nodes, launches them concurrently using asyncio.gather, marks each as completed or failed, and then repeats the process until the work is finished or further progress becomes impossible.

MAX_CONCURRENT = 5 # cap concurrent tool/LLM calls async def execute_dag(dag, tools, on_step=None): semaphore = asyncio.Semaphore(MAX_CONCURRENT) async def run_node(node): node.status = NodeStatus.RUNNING async with semaphore: try: # Sync tools run in a thread pool so other nodes can proceed node.result = await asyncio.to_thread(tools[node.tool].run, node.args) node.status = NodeStatus.DONE except Exception as exc: node.error = f”{type(exc).__name__}: {exc}” node.status = NodeStatus.FAILED while not dag.is_done(): ready = dag.ready_nodes() if not ready: break # remaining nodes depend on FAILED ancestors await asyncio.gather(*(run_node(n) for n in ready))

Here, two small architectural decisions do the main work.

First, asyncio.to_thread moves our synchronous tool functions to a thread pool. Therefore, we don't have to rewrite each tool as async def or tie the entire harness to an SDK with a native async API.

Second, asyncio.Semaphore limits concurrency. Without a semaphore, a large set of ready nodes could launch dozens of concurrent LLM calls, quickly hitting rate limits and causing a sharp increase in costs.

We deliberately do not build a full-fledged dynamic scheduler with work stealing, priority queues, and other complex mechanisms. For agent tasks like ours, where each node is an API call lasting from hundreds of milliseconds to several seconds, level-synchronous execution is sufficient to gain most of the benefits.

With sequential execution, wall-clock time is approximately equal to the sum of operation latencies. With concurrent execution, it is determined by the critical path of the DAG and the MAX_CONCURRENT limit; without concurrency limits for a single independent layer, the time approaches the latency of the slowest node plus the time for final aggregation.

Remember Only What's Necessary

Naive agents put everything into the prompt: the full conversation history, the results of every tool call, data from all previous tasks.

This approach breaks for two reasons. First, we pay for tokens that the model likely won't even need. Second, the model's quality noticeably decreases when the task's goal gets lost among irrelevant text.

Therefore, production agents use multi-level memory, partly inspired by cognitive science.

  • Working memory is a constantly present "draft" in the context: the current goal, a brief description of the plan, and the last few results.

  • Episodic memory stores the results of previous runs and is retrieved when a past task is similar to the current one.

  • Semantic memory contains background facts that are retrieved in the same way but are not tied to a specific agent run.

But the main rule is never put everything into the context at once. Instead, we retrieve the top-k memories most similar to the current goal and assemble the context within a strict character budget:

def build_context(working: WorkingMemory, store: MemoryStore, budget_chars: int = 4000) -> str: """Assemble working memory + retrieved memories, respecting a char budget.""" pieces = [working.to_prompt()] used = len(pieces[0]) # Episodic first (past similar tasks), then semantic (facts) for kind in (”episodic”, “semantic”): for m in store.retrieve(working.goal, k=3, kind=kind): snippet = f”[{kind}] {m.content}” if used + len(snippet) + 1 > budget_chars: return “
”.join(pieces) + “
(...truncated at budget...)” pieces.append(snippet) used += len(snippet) + 1 return “
”.join(pieces)

Episodic memories get priority over semantic ones: experience and mistakes from similar past tasks are usually more useful than general facts.

If the budget runs out, truncation is explicit, not silent. In other words: context must be actively assembled, not passively accumulated.

For similarity calculation, MemoryStore supports two backends:

  • The first is the Jaccard similarity coefficient. It's practically free and well-suited for a tutorial example, but it doesn't work well with paraphrasing. For example, the phrases "famous landmarks of France" and "Paris is famous for the Eiffel Tower" have almost no words in common, although they are semantically closely related.

  • The second option is full sentence embeddings: the all-MiniLM-L6-v2 model converts text into 384-dimensional vectors, so paraphrased fragments end up close to each other in vector space.

MemoryStore first tries to use embeddings, and if the model is unavailable, it falls back to Jaccard.

To quantitatively assess the effect of this replacement, a full benchmark is needed – we will return to this in a separate article.

Trust, But Verify

Agents can produce coherent, confident, and yet incorrect answers.

Without separate verification, a report might, for example, silently omit one of the cities and be sent to the user as if nothing happened. And a regression would go unnoticed until a human accidentally reads the result.

But different checks have different costs. Therefore, we arrange them in a hierarchy: first, the practically free deterministic structural checks; only then, the LLM judge for subjective quality assessment, which already requires tokens and money.

The rule is simple: always perform the cheap check first and only resort to the expensive one for results that passed the first level.

def verify_report(report, goal, required_cities, provider) -> Verdict: det = deterministic_check_report(report, required_cities) if not det.passed: return det # Cheap tier caught it — don’t bother the LLM # Deterministic passed → escalate to LLM judge for subjective quality return llm_judge_report(report, goal, provider)

If a demonstrably incomplete report is passed here – for example, only for Paris, although three cities were requested – it will be rejected at the deterministic level:reason = "Missing cities: ['Tokyo', 'New York']".

Not a single token was spent on evaluation, and the reason string is specific enough for the replanning step – or a human – to immediately understand what went wrong.

This two-stage scheme underlies many production evaluation pipelines: first cheap filters, then expensive checks only for those results that passed them.

Equally important is the separation of responsibilities: the Worker creates the result, the Critic evaluates it. The generator should not check its own homework.

Meet Planner, Worker, and Critic

A single prompt that simultaneously plans, executes actions, summarizes results, and critiques its own response tends to confuse goals: planning constraints seep into the style of the final text, and the "planning part" becomes difficult to isolate, complicating both testing and replacement.

Therefore, we will divide the work among several specialized agents. Each will have a short system prompt and one clearly defined contract.

  • Planner receives the goal and schemas of available tools and returns a DAG in JSON, which we validate before execution.

  • Worker receives the ready DAG and simply executes it.

  • Critic receives the original goal and the completed report and makes a verdict.

The catalog of actually available tools is directly inserted into the Planner's system prompt, so it can only refer to existing tools:

PLANNER_SYSTEM = """You are a Planner agent. Given a GOAL, produce a dependency graph of tool calls that will satisfy it. Output ONLY JSON in this shape (no prose, no markdown): {”nodes”: [{”id”: “...”, “tool”: “...”, “args”: {...}, “deps”: [...]}, ...]} Nodes may run in parallel if their `deps` are empty or already satisfied. The final aggregate_report node must depend on all upstream fetch/summary nodes. Prefer id “aggregate” for that capstone node (any unique id is acceptable). Available tools (name and schema): <<TOOLS_JSON>> """

If you connect a real model to the Planner, the plans are usually structurally correct but may differ in style and details. If the orchestrator later needs to find a specific node – for example, the final aggregate_report – it's cheaper to ask the model to use a predictable ID in advance than to write code that parses all possible variations of its response.

This division is similar to how production systems are structured: planners in the style of AutoGPT, Worker agents like SWE-agent, and evaluation via LLM-as-a-judge. At the same time, our implementation remains compact enough to be read in its entirety.

Since all three roles work through a unified interface LLMProvider.complete(..., role=...), replacing the Planner model or substituting the Critic with a mock implementation can be done with a single line.

Fuel Gauges and Failure Modes

The basic harness had a single limitation – the max_steps counter. But the number of steps poorly reflects the agent's real limitations.

Steps might still remain when tokens are already depleted. You can stay within the token budget but exhaust the tool call limit. And a hung network request can consume the entire wall-clock time limit without increasing the step counter at all.

Therefore, BudgetMulti simultaneously tracks four resources:

  • tokens;

  • tool calls;

  • wall-clock execution time;

  • estimated cost in dollars.

Execution stops as soon as at least one of these resources is exhausted.

But the most useful metric here is a single number. pressure shows how close the agent is to exhausting the most strained of its budgets. For each resource, we calculate the fraction of the limit already used, and then take the maximum:

def pressure(self) -> float: return max( self.tokens_used / self.max_tokens, self.tool_calls_used / self.max_tool_calls, self.elapsed() / self.max_wall_seconds, self.cost_usd / self.max_cost_usd, )

This single number controls graceful degradation: at pressure < 0.7, the full pipeline is executed, including the LLM judge; at pressure > 0.9, the orchestrator skips the expensive Critic and uses only deterministic checks; at 1.0, execution stops with partial results.

Production agents can use a similar signal to switch to cheaper models, reduce retrieval depth, or request user confirmation.

However, budgets alone are not enough. The second component of operational stability is understanding that not every error requires the same reaction:

  • Rate limit or timeout is a temporary error: here, retries with exponential backoff and jitter are appropriate, so that multiple agents don't retry requests synchronously.

  • Validation error is an improper tool use: we return a structured error to the LLM so it can correct the arguments itself.

  • Unknown entity is missing information, so retrying the same request is not just useless but harmful: if the model invents a city name, each repeated attempt will end with the same error. The correct action is to replan the task without this entity.

  • Policy violation is a fatal error, for which execution should be stopped immediately.

A small function classify_error() maps error strings to these four classes, and the recovery policy is determined by the error class, not by blind retries.

The Flight Recorder

When an agent fails, an append-only log of structured events is needed to answer questions: what happened and in what order, how long each step took, which role consumed tokens, and whether budget pressure increased before something went wrong.

Each event in the Tracer contains identification – step ID and parent ID, linking a Worker step to its originating plan; semantics – the role and the action performed; execution and cost metrics – latency, tokens, cost, and a snapshot of budget pressure at the time of recording; and for Critic events, also the verdict.

The schema is intentionally flat and unexciting: a list of JSON-serializable dictionaries that can be saved to a file, sent to OpenTelemetry or LangSmith, or used to directly build matplotlib plots.

For true observability, a proprietary format is not needed – a suitable schema is enough.

Latency by steps and roles immediately shows that the summarize_city() and aggregate_report() nodes determine the main part of the wall-clock time, while lookup operations are almost imperceptible.

The main time is spent on LLM calls – which is why their concurrent execution is so important.

Budget pressure increases monotonically over time and sharply increases during the aggregator stage. If it crosses the degradation threshold of 0.9 before the Critic starts, the trace itself explains why the LLM judge was skipped.

Finally, the token distribution by role shows where the budget is spent – on planning or execution. In this task, the main share falls on the Worker due to the numerous summarize_city() calls.

Putting It All Together

When all primitives are ready, the Orchestrator becomes almost boring. It assembles context from memory, asks the Planner to build a DAG, passes the DAG to the Worker along with a callback function that records an event in the trace and deducts the budget with each tool call, checks for errors, verifies the result with degradation depending on pressure, saves the result to episodic memory for future runs, and returns a RunResult combining the report, verdict, DAG, trace, and budget state.

The only new behavior it adds is the replanning loop. If execution fails with an error of class missing information, the Orchestrator sends the error context back to the Planner instead of blindly retrying. The number of such attempts is limited by the max_replans parameter.

The essence of the method fits into a few lines:

for attempt in range(self._max_replans + 1): dag = self.planner.plan(goal) if attempt == 0 else self.planner.replan(goal, dag) await self.worker.execute(dag, on_step=on_step) if dag.any_failed(): failed = (n for n in dag.nodes.values() if n.status == NodeStatus.FAILED) if any(classify_error(n.error or “”) == ErrorClass.MISSING_INFO for n in failed) 
 and attempt < self._max_replans and budget.has_room(): continue # informed re-plan, not a blind retry return RunResult(..., status=”failed_execute”) break # success # Pressure-aware degradation: skip the LLM judge if budget is tight if budget.pressure() > 0.9: verdict = deterministic_check_report(report, required_cities) else: verdict = self.critic.judge(report, goal, required_cities)

What We're Still Missing

We started with a basic agent loop and gradually added infrastructure: typed tools, DAG, memory, verification, role separation, multi-dimensional budgets, and tracing.

Importantly, these components do not form a monolith. They can be changed independently: add a new tool – and the Planner will receive its schema; tighten verify_report() – and subsequent runs will be checked according to new rules; replace the LLM backend – and the rest of the architecture will remain the same. It is this composability that allows us to keep the Orchestrator thin and the entire harness extensible.

However, we are still far from a full production system. Memory is stored within the process, whereas in real systems, embeddings are usually moved to an external store like Chroma, Weaviate, or pgvector. Tool results are considered trusted here, although in production, they should be treated as untrusted data and separated from instructions to reduce the risk of prompt injection. Irreversible actions should go through human confirmation, and actual token consumption is better obtained from SDK metadata rather than estimated by text length.

But there is a more important limitation.

A single successful run only shows that the harness can work. It says nothing about how stably the system handles different tasks, how often it makes mistakes, how much its operation costs, and where exactly it degrades.

To answer these questions, we need not a new component of the agent itself, but a separate eval harness. But that's already the subject of another article.
