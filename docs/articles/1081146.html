I won't reveal a secret by saying that ordinary keyword search is no longer very helpful. For neural networks to answer accurately, relying on your corporate knowledge bases, they need to "understand" the meaning of the text. And this is more complex than just searching for exact letter matches.

In this article, we will break down how vector databases are structured, why modern RAG doesn't work without them, how they differ from familiar relational databases, and how to choose the right tool for your project.

Relational vs. Vector Databases

Let's start with the familiar – traditional (relational and non-relational) databases. For simplicity, let's take a relational one. The concept of such a database will be understandable to those familiar with Excel spreadsheets. Data in such a database has a strict structure and is clearly typed. There is a list of tables, which will have columns (fields) and rows (objects). Each cell contains information with strict criteria: the "date" column will only contain a date format, and you cannot enter a name into the "age" column.

Since the data has a very predictable form, it's easy to search through it. For these purposes, indexes are built or separate SQL queries are written. For example: "I want all products over 1,000 rubles," "Show all users under 40," "Give me all Mercedes cars." You provide part of the data and a selection criterion (greater than, less than, equal to) as input, after which you get the result in the expected format.

Relational databases are called relational because of the relationships. Tables in them are linked to each other by certain fields. So, you can search for objects in one table based on a filter from a related column.

As for vector databases – in addition to the original information, they store its vectors. Vectors are arrays of numbers. They are not "human-readable," but they carry a mathematical imprint of the meaning of the stored data. Texts close in meaning, numbers close in magnitude, images similar in content – all of them will have similar vectors. To facilitate navigation, metadata (creation date, source of acquisition) and tags are also attached to the object.

How are these vectors obtained? You didn't enter them. This is not a simple transformation with a couple of formulas – the data is processed through an embedding model.

An embedding model (embedding) is a special neural network that translates text, audio, or video into mathematical quantities and places them in a multidimensional space in this form. Semantically similar data receives close numerical values (like GPS coordinates: Moscow and Ryazan will have close coordinates, while Moscow and Sydney will have distant ones).

The size of such a vector is fixed. The longer this array of numbers (typical dimensions are 768, 1024, or 1536), the more accurately the model captures nuances of meaning, but the more memory is required for storage and the slower the search becomes.

And here's a strict rule: the same model must always be used for indexing (writing to the database) and for searching. Otherwise, the "coordinates" will not match. Remember how difficult it is to navigate your colleague's creative mess, in which only they manage to be productive and find the right things – another person's model will not understand the logic of yours in the same way.

For example, you upload a photo of a black cat. The model will process it into vectors containing semantic features like "cat," "black," "sitting" – you don't even need to add keywords for further searching.

Why does it do this? The peculiarity begins during the search. You make a query: "Show me all images of dark-colored domestic animals." The query also goes through the embedding model, turning into a vector, after which the system searches for vectors mathematically closest to it. Your photo didn't have an explanation that a cat is a domestic animal, and black is a dark color. But you will get it in the results of this query. The model "knows" the relationships, that cats live with people and that black is clearly darker than white.

That is, the key difference is how the database stores data and how it can work with it later. A traditional database stores exact characters and can perform exact queries (it won't return "cat" for the word "cat"). A vector database "understands" the data before saving it. Therefore, for the query string "dog," it will return a dog, a hound, a Labrador, and a puppy.

Why Vector Databases Are Needed in the Era of LLMs

The functionality of conventional databases is insufficient when it comes to integrating artificial intelligence into business processes.

Semantic Search is Required. Search by exact matches is not enough. For example, a user writes: "how to reset password," and the knowledge base article is titled "Account Access Recovery." Relational databases can search by keywords – and won't find it. You can add full-text search (e.g., PostgreSQL tsvector, Elasticsearch), and this will increase the chances, but the user's question still lacks enough words. A search by meaning, by the semantics of the question and the semantics of the objects in the knowledge base, is needed. For a vector database, "reset password" and "access recovery" will be very close.

Context Window Limitation. If your knowledge base contains tens of thousands of text files, you won't fit them into the model's limit, for example, 128K tokens. And let's not forget about the rational use of limits. Some mechanism is needed to rank objects by relevance when full-text search is not feasible. A traditional database can rank results by the accuracy of matches. But if the query and the answer are only close in meaning, it's not helpful. A vector database, "out of the box," will understand the meaning of the data. This meaning has its own vectors, which can be similar to the vectors of other objects. This results in a more specific data selection that can already fit into the prompt.

Multimodality. You cannot put an image, video, or text file into scalar databases. You can put a path to a file on disk, a download link, or a byte array of the file content there. This further complicates (or even makes impossible) searching by meaning, even if you know the correct keywords or the breed of the cat in the picture. By the way, vector databases can now combine two search approaches: for example, "here is a document, find similar ones, but only from documents from 2024 and with the tag legal." We see both a request for semantic search and strict metadata constraints.

Format Flexibility. Relational databases prefer data uniformity, as we discussed earlier. But a vector database doesn't care as much about the original format, because in the end, everything is converted into a universal data type – a mathematical vector.

How Data Is Prepared and Searched

Before moving on to choosing databases and building a RAG architecture, let's synchronize on terms and understand how data is actually stored in the database and on what principle the system finds it later.

Text is rarely uploaded to the database in its entirety. If you try to process a huge document through a model at once, the meaning will be blurred, and the result may not fit into the neural network's context limit. Therefore, before vectorization, the text undergoes chunking – cutting it into small fragments. To avoid breaking the thought in the middle of a sentence during this division, these pieces (chunks) are made overlapping, with a small overlap. These are what are sent to the embedding model, converted into vectors, and stored in the database.

When you make a query, the system needs to understand which of the millions of chunk vectors are similar to it. For this, the system uses similarity metrics. Most often, cosine similarity is used for texts, which estimates the angle between vectors: if they "look" in the same direction, their meaning coincides. Sometimes Euclidean distance (the classic straight-line distance between points) or dot product is used – a faster method that, with normalized vectors, gives a result analogous to cosine similarity.

However, comparing a query with absolutely all entries in a large database is too slow and expensive. To provide answers in milliseconds, vector databases use approximate search algorithms. They sacrifice a tiny fraction of accuracy for a colossal increase in speed.

This works through special search indexes. For example, the popular HNSW index builds a network of short paths: the algorithm doesn't check each vector sequentially but quickly moves through major semantic nodes. This is a very fast method, but it requires a lot of RAM. If resources are limited, databases use other approaches: the IVF index pre-divides vectors into clusters (regions) and searches for matches only within the relevant one, and the PQ method simply compresses the vectors themselves – similar to compressing photos, where the file becomes much lighter at the cost of losing minor details.

Hybrid Search and the RAG Pipeline

Vector search is good at capturing meaning, but sometimes it misses exact names, product codes, or rare terms. For example, the error code "ERR-4412" might be "misunderstood" by the model.

For such cases, hybrid search is used, which combines semantic similarity (vectors) and keyword matching (like in the exact search we are familiar with).

In modern realities, vector databases are most often used in conjunction with large language models. The classic RAG (Retrieval-Augmented Generation) pipeline consists of two main stages:

  • data preparation (indexing): original document → chunking → processing through embedding model → saving vectors to the database;

  • query processing: user question → translating the question into a vector using the same model → searching for the nearest vector chunks in the database → passing the found texts and the original question to the LLM → generating the final answer by the neural network.

Overview of Tools and Solutions

Each step of RAG is usually handled by a separate component of the vector search infrastructure. To avoid getting lost in the multitude of technologies, let's examine the available solutions as a unified path – from specialized engines to hybrid databases and embedding models themselves.

Specialized Vector Databases

These are systems initially designed for one task – to perform the "find the most similar" search as quickly as possible. They work with vectors "out of the box" but differ in their infrastructure approach.

Pinecone.io

A turnkey cloud service that is ideal for getting started. The scheme is simple: create an account, set up an index, upload vectors, and immediately perform searches. There is minimal work with servers, scaling, and maintenance. The downside is that it's paid, and your data physically resides with an external provider.

Qdrant

A fast open-source database with convenient metadata filters (date, tags, tenant_id). You can run it yourself or use their cloud. Qdrant is often chosen when strict self-hosted control and security are important. A nice bonus is the built-in mechanism for easy data migration from other services (e.g., from Pinecone).

Weaviate

Another open-source representative. Its strength lies in its focus on hybrid search (where the model considers meaning + keywords) and ready-made modules that help vectorize data themselves.

Milvus (and cloud Zilliz)

A solution for very large volumes: millions and billions of vectors. If you have a small FAQ, this would be overkill. But if you are building corporate search on a huge data corpus, it's worth considering.

Chroma

An extremely lightweight and user-friendly database for prototypes, pet projects, and tutorials. It's convenient to test an idea in an evening. For serious loads, people usually move to something more powerful sooner or later.

Vector Search within Familiar Databases

You don't always need a separate "vector empire." Sometimes it's easier to add vector capabilities to where the data already resides.

PGVector

A familiar extension for PostgreSQL for many. You add a column with vectors and an index for similarity search to the same Postgres database. It's convenient to start: one stack, familiar JOINs, transactions. But with very large volumes, specialized vector databases are usually stronger.

You can easily launch PostgreSQL with the pgvector extension installed and configured by renting cloud databases in Selectel. This will save you from having to manually administer the database server.

After connecting the extension, you can create a table with vectors:

CREATE TABLE documents ( id bigserial PRIMARY KEY, title text, content text, embedding vector(1536) );

And then search for documents closest in meaning to the query vector:

SELECT id, title, content FROM documents ORDER BY embedding <=> :query_embedding LIMIT 5;

In this example, the operator <=> is used for searching by cosine distance. PGVector supports several types of distances and corresponding indexes. We have already discussed the tool in more detail in this article.

Elasticsearch/OpenSearch

If a powerful search engine is already running in your infrastructure, it makes sense to leverage its vector capabilities. The result is an effective hybrid: the system searches for both exact word matches and deep meaning.

MongoDB Atlas Vector Search

The most natural and seamless path for teams whose services are already deeply integrated with the MongoDB ecosystem and store their main documents there.

Practical advice: if PostgreSQL is already running in production and the data volume is moderate, start with PGVector. Switch to a separate vector database only when you genuinely hit limits in scale, speed, or specific selection requirements.

Embedding Models

A vector database itself only stores sets of numbers. But special neural networks – embedding models – convert the original text into these numbers. There are two conceptual paths here.

Cloud APIs

OpenAI embeddings – the most familiar path. Send text via API – get a ready-made vector. Simple, but paid and dependent on an external service;

Cohere – especially useful if your RAG works with a large volume of multilingual (non-English) texts, where the model shows high accuracy.

Own Open-Source Models

Options like BGE, E5, or other models from the Hugging Face repository (via the sentence-transformers library). The main advantage is that it's free, and confidential data never leaves your secure environment. The disadvantage is that you need your own server (preferably with a GPU) and self-maintenance.

RAG rule: the model used to index data and the model used to vectorize user queries must strictly match. If you decide to change the embedding model, you will have to recalculate the entire database.

Example Pipeline: What a Typical Stack Looks Like

For this entire system to work stably in production, a database alone is not enough. A classic corporate search architecture with AI usually looks like this:

  1. original files (documents, PDFs, images) are stored in S3-compatible storage;

  2. a message broker (e.g., Kafka or RabbitMQ) receives updates so that the system indexes new documents asynchronously, without overloading the main service;

  3. a separate microservice retrieves text, cuts it into chunks, and converts it into vectors via API (OpenAI, Cohere) or local open-source models (e.g., BGE);

  4. the vector database stores the prepared vectors along with metadata and provides fast search through them;

  5. the backend receives a request from the user, vectorizes it, requests similar chunks from the database, and "glues" them together with the original question;

  6. the LLM generates the final, human-readable answer based on the received and filtered context;

  7. the logging system tracks search speed, relevance of results, and API costs.

Where and How Vector Databases Are or Can Be Used

Knowing the advantages and specifics of vector databases, you can guess the ways to use this tool. For example, searching large knowledge bases – corporate documents, historical communication data with counterparties, product documentation. You can set up more complex product catalog searches – find a similar dress from a photo.

Speaking of products. Let's recall marketplaces with their recommendation systems. Or online cinemas. As a user, based on your purchases/views, you can be converted into text, and therefore into a vector. This means your vector can be compared with product vectors, and similar items can be suggested.

Or customer support – instead of an FAQ tree, search a solutions database. This will increase relevance to the query, and consequently, customer satisfaction.

On the topic of support: you can simplify working with bug reports by detecting duplicates – not cluttering the database with similar ones, but merging them. Or simplify procurement by merging similar orders.

There are also code writing or learning assistants that developers love. After all, code files are just text documents. Cut them into chunks and go.

For rational token usage, you can connect vector databases for long-term agent memory – they will store important dialogue facts as a set of vectors.

The technology can also be useful in fraud detection, and therefore in its prevention. If the history of interaction between a client and a product resembles a fraudulent scenario, it can be recognized even if the fraudsters change their script.

Problems and Pitfalls

As with any relatively new tool, vector databases have their own problems and complexities in operation.

The main bottleneck of vector databases is the quality of RAG. What and in what form gets into the context, how the data is prepared, how it is processed – all this determines the correctness of the answer. If the database search returns garbage due to a low-quality RAG flow or its parts, this garbage will enter the model's context – it will rely on it when answering. That is, even with formal correctness of operation, the result will be unsatisfactory.

The process of indexing data, converting it into vectors, is a black box of your system. If the meaning is misread, it will be difficult to figure out the problem. Perhaps the data was poorly prepared, or it was incorrectly ranked by the model. Maybe the vector calculation failed. In general, it's a brain-racking quest.

When processing data, chunking is an important step that can potentially cause problems. If you choose the same chunk size, you might encounter sections cluttered with meanings from neighbors. If you chunk by sections or paragraphs, you might stumble upon document peculiarities – if you chunk Tolstoy this way, you can quickly fill the context with one paragraph.

Where there are neural networks, there will be hallucinations. The RAG approach reduces them, but no one is perfect. You still need to constrain the model by refining prompts. For example, "answer only based on the context.".

Among other things, the quality of search and, consequently, the answer can suffer from multilingualism. Embedding models are trained primarily in English. If your data is in another language, the model will have to translate first. This will increase its resource consumption and likely introduce some semantic losses.

Unlike familiar scalar databases, there is also the problem of data relevance. A card catalog will be the same regardless of who requests data from it. But if you operate with meanings, then when changing the embedding model (the reader of this data), you will need to re-index all the data. Otherwise, the vector in the database will no longer correspond to the document content. If the data volume is large, this can become a significant problem. In particular, the bills for the embedding model's work at this stage alone will not please you.

Data security in multi-tenancy systems is highlighted as a separate problem. If you don't want data to be mixed between consumers, you need to mark it separately in the metadata. In other words, each piece of information needs to be "signed." The search will then combine the scalar approach with a strict match on this signature in the metadata and semantic vector search.

It's worth mentioning some legal issues of working with vector databases. For example, problems with storing personal data – in the original text, in a scalar database, you can replace or delete full names, phone numbers, and passport numbers. In a vector, this is impossible – regulatory documents must take these specifics into account.

Don't chase after technological sophistication and trends. If you have a small knowledge base, full-text search might suffice – the vector database infrastructure would be too heavy. If your database is mainly used for strict queries (e.g., accounting), a scalar database will perform better and be cheaper, and easier to maintain.

Do not implement vector databases where they are objectively not needed. If you have a small knowledge base or the search in your application is based solely on exact queries, a classic relational database or Elasticsearch will handle the task better and cheaper.

As with any issue, the choice of tool should depend on goals and resources. But they are very helpful in working with LLMs – without them, a chatbot will confidently lie, based on a cloud of tags it could gather in an infinite knowledge base. A vector database provides a foundation for the correct formation of the answer context, and therefore more accurate and specific information within it.
