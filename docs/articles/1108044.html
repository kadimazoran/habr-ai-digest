This section describes Common Params.

Parameters in this category largely overlap across all utilities: llama-cli, llama-completion, llama-server. Where there are differences, relevant comments are provided.

For each parameter, its name, template, and a brief description from the official llama.cpp help are given first, followed by a more detailed explanation.

----- common params -----

-h, --help, --usage

print usage and exit

Comment:

Displays help for all main parameters: parameter names in short and extended forms, brief parameter descriptions, possible values, default values, OS environment variable names for some parameters, and in some cases, links to the project's GitHub with descriptions/discussions of specific parameters.

--version

show version and build info

Comment:

Shows information about the current version and specific build data. For example, you can check if the current build supports CUDA.

--license (parameter absent in newer versions)

show source code license and dependencies

Comment:

Displays the license information for the main llama.cpp package, as well as other packages used within llama.cpp.

-cl, --cache-list

show list of models in cache

Comment:

Shows a list of models from the disk cache. Models are downloaded and cached when the “-mu, --model-url MODEL_URL” parameter is specified. If you download models yourself and access them via a direct disk path, this list will likely be empty, and this parameter may not be useful for you.

--completion-bash

print source-able bash completion script for llama.cpp

Comment:

Outputs a bash script to the console. Executing this script will enable your terminal to: suggest parameters for llama-cli, auto-complete flags with TAB, etc.

-t, --threads N

number of CPU threads to use during generation

(default: -1)

(env: LLAMA_ARG_THREADS)

Comment:

Number of CPU threads to use for generation. In theory, more threads lead to faster processing.

Note: Generation performance is often limited by memory bandwidth. Beyond a certain number of threads, performance gains diminish, and excessive threads can even slow down generation. This should be tested on your specific configuration and model. There's also a notion that for Ryzen processors, it's better to specify the number of physical cores, while for Intel, the number of logical cores.

Default: “--threads -1” (auto-select).

env: LLAMA_ARG_THREADS - OS environment variable where you can specify this parameter's value for the current session.

-tb, --threads-batch N

number of threads to use during batch and prompt processing

(default: same as --threads)

Comment:

Number of CPU threads for processing incoming prompts and batches of tokens (prefill). If not specified, it defaults to the value of “--threads”. This is similar to “--threads” but specifically for token generation and overall llama.cpp operation, whereas this parameter concerns only prefill.

Note: Generation performance is often limited by memory bandwidth, so performance gains diminish after a certain number of threads. Prompt processing scales well with threads, so theoretically, a higher number of threads is optimal for “--threads-batch” than for general “--threads”. However, this needs to be tested on your specific configuration and model.

Default: “--threads-batch -1” (auto-select).

-C, --cpu-mask M

CPU affinity mask: arbitrarily long hex. Complements cpu-range

(default: “”)

Comment:

Specifies the use of specific CPU cores via a hexadecimal bitmask.

Example: “--cpu-mask 0xF” (0xF = 1111, use CPU cores 0, 1, 2, 3).

Default: not used (mask not specified).

-Cr, --cpu-range lo-hi

range of CPUs for affinity. Complements --cpu-mask

Comment:

Specifies the use of specific CPU cores within a given range. This is an alternative way to specify CPU affinity compared to “--cpu-mask”, using familiar decimal notation. Both parameters can be used simultaneously: “--cpu-mask” + “--cpu-range”.

Example: “--cpu-range 0-7” (cores 0 through 7, total 8).

Default: not used (not specified).

--cpu-strict <0|1>

use strict CPU placement

(default: 0)

Comment:

Literally, “use strict CPU placement”. Works in conjunction with “--threads/--cpu-mask/--cpu-range”. Without strict mode, threads specified by “--threads” can move freely between CPU cores at the OS's discretion. With strict mode, each thread is rigidly assigned to a specific core. Potential benefits include lower latency and more optimal cache utilization. The main advantage of affinity is preventing threads from migrating between CPUs and losing cache state. However, this is theoretical; in most cases, the latency difference is negligible. Moreover, strict mode can sometimes be detrimental; for instance, if another process occupies one of the assigned CPUs, the current thread cannot move to a free CPU and must wait.

Default: “--cpu-strict 0” (disabled).

--prio N

set process/thread priority: low(-1), normal(0), medium(1), high(2), realtime(3)

(default: 0)

Comment:

Sets the priority of the llama.cpp process in the OS scheduler. Higher priority grants llama.cpp more CPU time when competing with other processes. This only affects CPU contention; on an idle system, there's virtually no difference.

Possible values:

  • (-1) low - background mode, llama.cpp yields to other processes.

  • 0 (normal, default) - llama.cpp competes with other processes on equal terms. The best choice for most scenarios.

  • 1 (medium) - llama.cpp receives slightly more CPU time than other processes.

  • 2 (high) - llama.cpp receives significantly more CPU time, while other processes receive less.

  • 3 (realtime) - llama.cpp receives maximum priority. This can cause system processes to lag; not recommended for general use.

For medium(1), high(2), and realtime(3) priorities, administrator privileges may be required; otherwise, llama.cpp will simply ignore the directive.

Default: “--prio 0” (normal).

--poll <0...100>

use polling level to wait for work

(0 - no polling, default: 50)

Comment:

Determines how long a thread actively waits for new work after completing a current operation (polling). Examples:

“--poll 0” - the thread goes to sleep immediately. Minimal CPU load, but slightly longer wake-up time.

“--poll 100” - the longest active wait. Near-instantaneous wake-up, but higher CPU load and power consumption.

The difference is usually very small, milliseconds per token, and may only be noticeable with small and fast models.

Default: “--poll 50”.

-Cb, --cpu-mask-batch M

CPU affinity mask: arbitrarily long hex. Complements cpu-range-batch

(default: same as --cpu-mask)

Comment:

Same as “--cpu-mask”, but for batch processing. Allows specifying the use of specific CPU cores via a hexadecimal bitmask.

Example: “--cpu-mask-batch 0xF” (0xF = 1111, use CPU cores 0, 1, 2, 3).

Default: not used (mask not specified).

-Crb, --cpu-range-batch lo-hi

ranges of CPUs for affinity. Complements --cpu-mask-batch

Comment:

Same as “--cpu-range”, but for batch processing. An additional way to specify CPU core affinity within a given range. Unlike “--cpu-mask-batch”, it uses familiar decimal notation. Both parameters can be used simultaneously: “--cpu-mask-batch” + “--cpu-range-batch”.

Default: not used (not specified).

--cpu-strict-batch <0|1>

use strict CPU placement

(default: same as --cpu-strict)

Comment:

Literally: “use strict CPU placement”. Works in conjunction with “--threads-batch/--cpu-mask-batch/--cpu-range-batch”. Without strict mode, threads specified by “--threads-batch” can move freely between CPU cores at the OS's discretion. With strict mode, each thread is rigidly assigned to a specific core. Potential benefits include lower latency and more optimal cache utilization. The main advantage of affinity is preventing threads from migrating between CPUs and losing cache state. However, this is theoretical; in most cases, the latency difference is negligible. Moreover, strict mode can sometimes be detrimental; for instance, if another process occupies one of the assigned CPUs, the current thread cannot move to a free CPU and must wait.

Default: “--cpu-strict-batch 0” (disabled).

--prio-batch N

set process/thread priority: 0-normal, 1-medium, 2-high, 3-realtime

(default: 0)

Comment:

Same as “--prio”, but for prompt and batch processing threads (prefill). Higher priority grants batch threads in llama.cpp more CPU time when competing with other processes. This only affects CPU contention; on an idle system, there's virtually no difference. In high(2) priority mode, llama.cpp prefill might run slightly faster, but other processes in the OS will run slower. In realtime(3) mode, llama.cpp prefill will preempt all other processes, including system ones, causing the OS to become sluggish.

Possible values:

  • 0 (normal, default) - llama.cpp prefill competes with other processes on equal terms. The best choice for most scenarios.

  • 1 (medium) - llama.cpp prefill receives slightly more CPU time than other processes.

  • 2 (high) - llama.cpp prefill receives significantly more CPU time, while other processes receive less.

  • 3 (realtime) - llama.cpp prefill receives maximum priority. This can cause system processes to lag; not recommended for general use.

For medium(1), high(2), and realtime(3) priorities, administrator privileges may be required; otherwise, llama.cpp will simply ignore the directive.

Default: “--prio-batch 0” (normal).

--poll-batch <0|1>

use polling to wait for work

(default: same as --poll)

Comment:

Same as “--poll”, but for batch processing. Determines how long batch threads actively wait for new work after completing a current operation (polling).

Examples:

--poll-batch 0 - the thread goes to sleep immediately. Minimal CPU load, but slightly longer wake-up time.

--poll-batch 100 - the longest active wait. Near-instantaneous wake-up, but higher CPU load and power consumption.

The difference is usually very small, milliseconds per token, and may only be noticeable with small and fast models.

Default: “--poll-batch 50”.

-c, --ctx-size N

size of the prompt context

(default: 0 - loaded from model)

(env: LLAMA_ARG_CTX_SIZE)

Comment:

Context length. Usually, the model's context length is specified (if memory allows). A larger context length requires more memory to operate. It often makes sense to specify a smaller context size for short chats or single requests, such as function/tool calls.

Default: “--ctx-size 0” (uses the model's value).

env: LLAMA_ARG_CTX_SIZE - OS environment variable where you can specify this parameter's value for the current session.

-n, --predict, --n-predict N

number of tokens to predict

(default: -1, -1 = infinity)

(env: LLAMA_ARG_N_PREDICT)

Comment:

The number of tokens the model will generate. Generation stops (abruptly cuts off) when this number is reached. If this parameter is not specified, or if “--predict -1” (default) is used, text will be generated indefinitely or until an end-of-sequence token is encountered (if one exists for the model). Only newly generated tokens are counted; prompt tokens are not included.

Note: An end-of-sequence (EOS/EOG) token is a special token used during training to mark the end of texts, teaching the model when to stop generating. End tokens can vary between models. Examples include: <|endoftext|>, <end_of_turn>, , <|im_end|>, etc.

Default: “--n-predict -1” (infinite or until end-of-sequence token).

Important: For llama-completion, there's an additional value for this parameter: “-2 = until context filled”. This means generation will stop when the specified context length is reached (see “--ctx-size”).

I'm currently unsure why this option is only available for llama-completion. It might be due to the different operational modes of the utilities: llama-cli and llama-server typically operate in a conversational mode (backend optimized for this), whereas llama-completion works exclusively in a single-message generation mode (one-off call).

env: LLAMA_ARG_N_PREDICT - OS environment variable where you can specify this parameter's value for the current session.

-b, --batch-size N

logical maximum batch size

(default: 2048)

(env: LLAMA_ARG_BATCH)

Comment:

Batch size in tokens. Used for the incoming request (prefill - prompt, message, or message chain). If the prefill is large, it will be split into batches for sequential processing. Batching is done to save memory during computations.

Default: “--batch-size 2048”.

env: LLAMA_ARG_BATCH - OS environment variable where you can specify this parameter's value for the current session.

-ub, --ubatch-size N

physical maximum batch size

(default: 512)

(env: LLAMA_ARG_UBATCH)

Comment: Similar to “--batch-size”, but specifies the “physical” batch size (microbatch) that is actually sent to the CPU/GPU. For example, if “--batch-size 2048” and “--ubatch-size 512”, then the “logical” batch of 2048 tokens will be split into physical batches of 512 tokens, which are then sent for computation to the CPU/GPU.

Important: The value of “--ubatch-size” must not exceed “--batch-size”; otherwise, this parameter is meaningless, as the initial batch size is set by “--batch-size”, and “--ubatch-size” only helps by splitting the batch before sending it to the CPU/GPU and cannot be larger than the original batch size.

Default: “--ubatch-size 512”.

env: LLAMA_ARG_UBATCH - OS environment variable where you can specify this parameter's value for the current session.

--keep N

number of tokens to keep from the initial prompt

(default: 0, -1 = all)

Comment:

Number of tokens from the initial prompt to retain when the context overflows. The older tokens from the rest of the conversation will be discarded. When the context (“--ctx-size”) is full, llama.cpp starts trimming tokens from the beginning of the conversation, a process called context shift. The “--keep” parameter allows you to preserve the beginning of the dialogue, for example, to keep the system prompt entirely, and context window trimming will only start after the specified value.

Example:

[n_past, n_left, n_discard - internal llama.cpp variables, calculated during operation]

--ctx-size 4096, --keep 200, context is full (n_past = 4096).

n_left = 4096 - 200 = 3896 (first 200 tokens are not touched).

n_discard = 3896 / 2 = 1948 (half of the remaining 3896 are discarded - the earlier 1948 tokens).

When the context fills up again (n_past), the context shift repeats.

If “--keep -1”, the entire initial prompt is preserved.

Default: “--keep 0” (no preservation).

--swa-full

use full-size SWA cache

(default: false)

Comment:

Some models, like Gemma2/3, use Sliding Window Attention (SWA) instead of full attention across the entire context. By default, llama.cpp optimizes the SWA cache and stores only the necessary (limited) attention window, which significantly saves memory. If “--swa-full” is specified, the full-size SWA cache is enabled without optimization. A full SWA cache can theoretically provide better quality and compatibility/stability but requires significantly more memory to store the entire KV cache.

Default: not used.

-fa, --flash-attn [on|off|auto]

set Flash Attention use (‘on’, ‘off’, or ‘auto’, default: ‘auto’)

(env: LLAMA_ARG_FLASH_ATTN)

Comment:

Enables/disables Flash Attention. FA is a more efficient method for calculating Attention. It's faster, consumes less memory (especially with large contexts), but may yield slightly different results (either better or worse; in most cases, differences are negligible). Additionally, “--flash-attn” should be enabled if cache quantization (V, “--cache-type-v”) is used during model inference; it's also recommended (though not mandatory) if K cache quantization (“--cache-type-k”) is used. See below for KV cache quantization (“--cache-type-k” and “--cache-type-v”).

Default: “--flash-attn auto” (auto-select).

env: LLAMA_ARG_FLASH_ATTN - OS environment variable where you can specify this parameter's value for the current session.

-p, --prompt PROMPT

prompt to start generation with; for system message, use -sys

Comment:

The prompt text, the first message from the user. Not to be confused with the system prompt, which is set using the “-sys/--system-prompt” and “-sysf/--system-prompt-file” parameters.

--perf, --no-perf whether to enable internal libllama performance timings (default: false)

Comment:

Enables internal performance timings for the libllama library (llama.cpp): load time, prompt eval time, eval time, tokens/s, etc. Can be used for benchmarking or debugging.

Possible options:

“--perf” - enabled (default).

“--no-perf” - disabled.

Default: “--perf” (enabled).

-f, --file FNAME

a file containing the prompt

(default: none)

Comment:

Loads the prompt from a file. Used instead of specifying the prompt directly in the llama.cpp request via the “--prompt” parameter.

Default: not used.

-bf, --binary-file FNAME

binary file containing the prompt

(default: none)

Comment:

Loads the prompt from a file in binary mode, byte by byte, as is, without text conversion. Rarely used, but may be necessary for passing raw data in cases of rare source text encodings, special characters, etc., to ensure the prompt is passed exactly as is.

Default: not used.

Whether to process escape sequences. Applies to prompt text and some other string parameters.
