If this decision isn't made explicitly, it will still be made by default, and most often not in favor of system stability.

The Core Idea

The experience of resolving the situation described above can be summarized by one main thought: the stability of an LLM agent depends not on the number of constraints in the prompt, but on how clearly the boundary between the algorithm (and its relevant code) and the model is drawn and fixed, allowing the model to operate independently and autonomously within its conceptual space.

This boundary itself is not a new concept. Anthropic defined it back in December 2024 in "Building Effective Agents." In a workflow, the flow is controlled by predefined code, whereas with an agent, the model directs the flow. This idea has been reiterated many times since, including in recent Russian-language texts. For example, the article "From Talkative LLM Agents to Controllable Systems" on Habr, published a month ago, emphasizes that models should not be tasked with what code can do more accurately and reliably. The most well-known specific case of this boundary is query routing: first, a cheap heuristic or model, then escalation based on a confidence threshold. This pattern is called cascade routing and is discussed in detail, including production specifics – threshold drift with model updates, attacks on the router via specially crafted queries. There's no point in rehashing it here.

The essence is that we need to consider the question of where the boundary is fluid and how to maintain it.

First. The Asymmetry Rule

To begin, let's focus on the direction in which a decision is allowed to change, setting aside the question of who makes it. A classifier assigns a query to a category. It then turns out that the query is more complex than initially thought. Revision is necessary in this case, but only in one direction. The category can be elevated to a more stringent and costly processing, but it can never be lowered.

An elevation error and a lowering error belong to different categories. An incorrect elevation is an execution error: more resources are spent than necessary, but the basis of the answer remains valid. This can be corrected at a later stage. With an incorrect lowering, the basis of the answer is silently replaced with a weaker, insufficient one, but the recipient of the result is unaware of this. It's impossible to verify this substitution retroactively because the answer looks like any other and is stated with the same confidence. These two errors cannot be compared on any scale; they are incomparable (like comparing the cost of an extra step to the cost of taking a step in the wrong direction).

Furthermore, model confidence should not be confused with task simplicity. The classifier's confidence threshold indicates how convinced the model is of its interpretation, not how simple the situation actually is. Allowing high confidence to lower the category substitutes one for the other: a system that is confident takes the place of a system that is correct. Therefore, the decision to elevate remains with the code – a simple rule based on the detected complexity. The model is only trusted with the signal "complexity is higher than expected," not with the right to lower the category itself. Make an exception once, and asymmetry ceases to be a rule. It becomes a recommendation that is easily bypassed in the next prompt version. Each elevation is logged along with the initial and actual category. This is necessary not only for auditing individual responses. It also serves as a metric for the classifier's quality: if the proportion of elevations for a specific query type increases from release to release, the category definition has become outdated and no longer reflects reality.

Second. Undetectable Error

The second place where the boundary is often lost is in errors that the asymmetry rule does not resolve. Suppose a result is obtained without a single technical failure, but it is factually incorrect. The query executed, the plan passed checks, there are no execution errors. Yet, the number is wrong because the join was built on the wrong key, or the filter applied was not what the user intended. Neither syntactic checks nor the execution plan will catch such an error. From their perspective, nothing is broken.

The first natural impulse is to catch such an error with another check, by calling an arbiter model. The unreliability of this approach is well-documented – it's a known limitation of the LLM-as-judge pattern: the judge is also a language model and can also make mistakes. This leads to the perennial question: what to do? The answer is simple – make the result itself verifiable. The generated data query is returned along with the answer, not hidden behind a debug flag. Even those who don't read the code benefit from this – a specialist can always reconstruct what was asked. And those who do read the code will immediately spot an incorrect join. If the answer relies on a metric definition from a common catalog, that definition is explicitly stated in the answer text. There should be no raw number that cannot be verified. And this is again a decision at the code-model boundary, as it is the code that can provide the user with the means to verify the answer.

Third. Refusal as a Code Decision

The third place (and this point is far more important than the previous two) is the decision to refuse. It might seem natural that deciding whether to respond should also be up to the model: it understands language, and it's easiest for it to detect that a question is inappropriate or illegitimate. In practice, this is not the case. In descriptions of "safety routers" or unified input filters, it's often overlooked that refusal is not a single operation with two outcomes: allow or block. It involves several logically distinct reasons for not responding. Each has its own specific verification mechanism. Empty or unreadable input is a form defect, not a content defect. Code recognizes it before any model even looks at the question. A query that is inherently illegitimate is a different type of defect: the form is fine, but such a question should not be asked in principle. This is also handled by a hard rule, even before classification. The third case is a question for which the system simply has no data. The question itself is fine, but it has nothing to tie into within the domain, and this is only discovered after an attempt to make such a connection. Reducing all three cases to a single "refused" response means erasing the distinction between the fundamental right to ask a question and the system's ability to handle requests of that type. Yet, this is precisely the information needed when analyzing individual incidents.

Therefore, the reason for not trusting the model with refusal decisions is not the unreliability of classification itself, but the fact that these categories are logically different. A model given a single general command like "refuse inappropriate requests" will inevitably conflate different reasons. And a refusal that can be bypassed by rephrasing is not a refusal in substance, but merely noise in the system's behavior, and here there is no boundary decision to be made. A good refusal, therefore, names both the class of the reason and the level at which the decision was made. Formulations like "the system cannot answer" are insufficient for this. This is not just about transparency for the user, but more about diagnostic capability for the developer: if the number of refusals of a certain class increases, it immediately becomes clear where to look for the cause – in the rule set, in the data domain definition, or in the user questions themselves that the system cannot yet handle.

Conclusion

All of the above essentially represents the same check applied at different depths – the question of who makes the decision at a given point and why it is them, and not someone else. The practical takeaway for your own system is simple. If a decision can be reduced to enumerable structural features, then it belongs to the code. If the decision actually consists of several logically distinct questions – it's not enough to draw the code/model boundary once. You also must not collapse these different questions into a single general reaction – whether that reaction is made by code or by the model.

Postscript

In your project, there may be more boundaries and potential points of failure than described, but one thing is important – for an engineer, searching for a boundary is coupled with searching for a mechanism to maintain it.
