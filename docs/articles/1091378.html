Why a Regular Test and an Agent Test Are Not the Same

In a static benchmark, the model receives a question and returns an answer. The environment does not affect the result: the answer is compared against a reference. An agent works differently; it:

  • explores the repository,

  • edits files,

  • runs the compiler and tests,

  • installs dependencies,

  • creates child processes,

  • reads results and modifies the solution,

  • repeats this cycle until success or timeout.

At each step, the agent depends on the environment. If there isn't enough memory, the package installation will fail. A slow CPU will delay compilation and tests, meaning the agent will complete fewer iterations within the allotted time. The environment here is not a passive shell but part of the problem-solving process.

Therefore, two agents with different limits are essentially taking different tests, even if they use the same model and tasks.

What Anthropic Discovered

Anthropic ran Terminal-Bench 2.0 on Google Kubernetes Engine and noticed two interesting things: the results did not match the official leaderboard, and up to 6% of tasks failed due to pod errors. Most of these failures were unrelated to the model's ability to solve the task.

The reason turned out to be the way limits were applied. Starting with version 2.0, Terminal-Bench specifies recommended CPU and RAM for each task. However, specifying resource limits and enforcing them uniformly are different things.

What do I mean? A container has two separate parameters: guaranteed resources and a hard limit, exceeding which forcibly terminates the container. In Anthropic's configuration, both parameters were equal to the task specification.

There was no buffer, and even a brief spike in memory consumption would kill the container due to OOM. However, the official Terminal-Bench leaderboard is calculated on a different sandbox provider. It is more lenient: it allows temporary exceeding of limits for stability. The same specification on different infrastructure yielded different results.

Experiment: Six Configurations

To assess the scale of the effect, the team ran Terminal-Bench 2.0 in six configurations: from a strict 1x, where the task specification serves as both guarantee and ceiling, to a variant with no limits at all. The model, agent, and task set were identical in all runs.

The results fall into two groups.

  • From 1x to 3x, environment reliability increased, not the result. The proportion of infrastructure errors decreased from 5.8% to 2.1% (p < 0.001), but the overall success rate varied within the noise margin (p = 0.40). The data shows that most tasks that failed at 1x would have failed anyway: the agent hit the limit before finding the correct path to the solution.

  • After 3x, resources began to help solve tasks. From 3x to the configuration without limits, infrastructure errors decreased by another 1.6%, and success rate increased by almost 4%. Success rate here grows faster than errors decrease: the agent gains the ability to use approaches that simply don't work without resource buffers.

The outcome between the extreme points: +6% to success rate, and the proportion of infrastructure errors dropped from 5.8% to 0.5%.

The main finding was replicated on other Anthropic models: the effect recurred, only the magnitude differed. The picture for models from other companies is likely similar, but this has not been rigorously tested.

The effect was also tested on SWE-bench: 227 tasks, 10 runs each, memory up to 5x the base. Success rate again monotonically increased with RAM, but less so: the difference between 1x and 5x was 1.54%. This is expected, as SWE-bench tasks are generally less resource-intensive. However, resource allocation still affects the result here.

Resources Change What the Benchmark Measures

The key takeaway is that not only the magnitude of the increase matters, but also its nature.
