Why a Prompt Isn't a Boundary

Over four years, prompt injection has not been reliably eliminated, and there's reason to believe a definitive solution may never emerge. In the latest OWASP State of Agentic AI Security and Governance report, prompt injection is linked to six out of the ten OWASP Top 10 categories for agentic applications. Help Net Security, in its analysis of the report, explains the reason in one sentence: "There is no reliable way to mark some of these tokens as commands and others as data." The model perceives the system prompt, user query, and external text as a single stream. Anything that enters the context can potentially control the agent.

The 2025 version of the report cataloged theoretical threats. The 2026 version introduced real CVEs and incidents: OWASP tracking lists 53 agentic projects, 28 of which are coding agents. Popular frameworks already have dozens of advisories: 57 for n8n, 22 for Claude Code, 15 for AutoGPT. The frameworks remain the same, but now they are being seriously exploited.

Prompt filters also do not protect against supply chain issues. A compromised LiteLLM package in March 2026 was downloaded nearly 47,000 times in three hours. A boundary is needed between the agent and what it retrieves from package registries.

The market has responded with LLM Firewall products. Llama Firewall checks prompts with the PromptGuard 2 model on 22 million parameters and statically analyzes generated code via CodeShield. These are useful tools, but they filter text and code. A similar assessment is provided by Innostage's analysis.

An LLM acting as a regulator inherits the vulnerabilities of the model it's trying to protect, from prompt steering to jailbreaking. Ideco explicitly states that nine out of ten OWASP threats for agentic systems remain outside the coverage of a classic LLM firewall.

Simon Willison proposed a useful framework: the lethal trifecta – access to private data, interaction with untrusted content, and an external communication channel. An agent that combines all three properties becomes an exfiltration tool after a single injected prompt. Meta (recognized as an extremist organization, banned in the Russian Federation) expands on this idea with the Agents Rule of Two: without human oversight, an agent is allowed a maximum of two of the three properties. Both approaches address access levels and communication channels. Such limitations cannot be expressed through prompts.

For a diagnostic read-only agent, the boundary can indeed be maintained at the API server. A ServiceAccount with read-only permissions is sufficient, as discussed in the analysis of a cluster-aware agent. However, we will now discuss agents that take action: writing to databases, calling APIs, and applying manifests. For them, the boundary drops three levels below the text.

The manifests below are educational. They are compiled from Kubernetes documentation (RBAC, ServiceAccount, ResourceQuota, NetworkPolicy) and the Kubernetes SIG's Agent Sandbox project documentation. The Claw Patrol configuration is based on the project's reference guide. All three sources demonstrate a common principle. Names and versions need to be adapted to your environment, and before going to production, add timeouts, retries, and monitoring.

Three Layers of Isolation

Runtime: Execution Sandbox

At least three teams have independently arrived at similar architectures: Anthropic with bubblewrap and seccomp in sandbox-runtime, Google with a pool of pre-warmed sandboxes on GKE, and Kubernetes SIG with the Sandbox CRD on top of gVisor and Kata. In CNCF materials: "AI sandboxing is having its Kubernetes moment."

The common principle formulated there is containment first: a policy failure should not extend beyond strictly defined boundaries. This formulation was proposed by the sandbox vendor Edera, and it's in their interest to promote it. However, three independent implementations already exist under this approach.

Anthropic's Mythos Preview model, in its own security research , discovered a 27-year-old vulnerability in the OpenBSD TCP stack in about a thousand runs and for less than $20,000. When a system is capable of such feats, it's too late to list everything it's forbidden from doing in policies. The only option left is to limit the surface area it can reach.

The author of the material describes the current setup as: "Thousands of workloads use a single shared kernel without structural isolation." Workloads on a shared kernel are isolated by policies and the assumption that everything is written without errors. Browsers solved a similar problem long ago: tabs were separated into processes, and a failure in one tab no longer affected others. The promise of this approach is to localize failures.

The Kubernetes community has formalized this idea into a separate primitive. The Agent Sandbox project from Kubernetes SIG introduces the Sandbox CRD: one Sandbox corresponds to one isolated pod for the agent, with gVisor or Kata running underneath. For gVisor, one line is sufficient:

apiVersion: agents.x-k8s.io/v1beta1
kind: Sandbox
metadata:
  name: report-agent
  namespace: agents-report
spec:
  podTemplate:
    metadata:
      labels:
        app: report-agent           # network policies from layer 3 will hook onto this label
    spec:
      runtimeClassName: gvisor     # all kernel isolation is here
      containers:
      - name: agent
        image: registry.example.com/agents/report:1.4.2
        resources:
          requests:
            cpu: 300m
            memory: 700Mi
          limits:
            cpu: 700m
            memory: 1500Mi

The lifecycle, storage, and identity of the Sandbox are defined by separate fields. The full list of parameters is provided in the project documentation. The label in podTemplate.metadata.labels will be needed in the next step: network policies use it to determine which pods to apply rules to. Resource requests are chosen considering the quota at the next level – it's sufficient for five pods.

gVisor or Kata: Performance Trade-off

gVisor places a userspace kernel between the container and the host, intercepting system calls. If a container escape does occur, the attacker lands in the sandbox's userspace kernel, with another barrier remaining before reaching the host. Kata Containers achieves the same goal through hardware virtualization.

These approaches have different performance costs. The gVisor guide shows where the overhead comes from: CPU and memory operations are usually performed almost as fast as in a regular container, while system calls, network, and file operations are noticeably slower. If the agent primarily performs computations and waits for an LLM response, the difference may be negligible. However, for workloads with frequent file and network operations, it's worth testing Kata separately.

There's a second factor: cold start time. At KubeCon NA 2025, Google identified kernel-level isolation as mandatory for agentic scenarios and demonstrated a pool of pre-warmed sandboxes. In this setup, a new environment is ready in less than a second – the company claims up to a 90% improvement compared to a cold start. These figures were obtained in GKE, but the principle of a pre-warmed pool is platform-independent.

Anthropic provides another example. In Claude Code, a sandbox with an egress proxy reduced user confirmation requests by 84%. When the environment is reliably isolated, an agent can be granted more operations in advance – and users have to intervene less often.

The entire layer relies on a single statement from the same material: "A reliable sandbox requires both file system isolation and network isolation." File system isolation without network isolation leaves a channel for exfiltration. Network isolation without file system isolation doesn't protect data from corruption. In the open-source sandbox-runtime, this is evident in the Linux primitives: bubblewrap and seccomp filters are used, the network namespace is completely removed, and egress goes through a bridge to a host proxy with an allow-list of domains.

gVisor is measured on synthetic benchmarks and classic services, but no vendor has public measurements for agent profiles yet. Long inference pauses and bursts of file operations between them don't fit well into such a profile. Therefore, it's better to choose between gVisor and Kata based on your own traffic.

A minimal measurement scheme: run one agent on one task in three runtimes – runc, gVisor, and Kata – and perform fifty runs each. Compare the p95 wall-clock time of the task and the number of system calls using strace -c. If the difference between runc and gVisor gets lost in the inference time variance, there's no longer a choice to be made.

Pod and ServiceAccount: Identity and Permissions

The evolution of this pattern is well illustrated by the open-source project kagent. Initially, all agents ran in a single runtime. Then the team moved to the model: "each agent runs in a separate Pod, with its own Service and ServiceAccount."

The reason is not just failure isolation. A Pod assigns a separate identity to the agent: ServiceAccount becomes the subject of RBAC, NetworkPolicy is applied based on Pod labels, and the namespace allows limiting resource consumption with quotas. As a result, the agent ceases to be an anonymous process within a shared runtime and becomes a distinct cluster object – with a name, permissions, and resource limits.

For a single agent, the following set is usually needed:

apiVersion: v1
kind: ServiceAccount
metadata:
  name: report-agent
  namespace: agents-report
automountServiceAccountToken: false   # do not mount by default; enable for pods needing API access selectively
---
aspiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: report-agent-role
  namespace: agents-report
rules:
- apiGroups: [""]
  resources: ["configmaps"]
  verbs: ["get", "list"]               # exactly what the task needs
---
aspiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: report-agent-binding
  namespace: agents-report
subjects:
- kind: ServiceAccount
  name: report-agent
  namespace: agents-report
roleRef:
  kind: Role
  name: report-agent-role
  apiGroup: rbac.authorization.k8s.io
---
aspiVersion: v1
kind: ResourceQuota
metadata:
  name: report-agent-quota
  namespace: agents-report
spec:
  hard:
    requests.cpu: "2"
    requests.memory: 4Gi
    limits.cpu: "4"
    limits.memory: 8Gi
    pods: "5"                         # limit for spawning sub-agents

Synthesis from official documentation: RBAC, ServiceAccount, ResourceQuota.

This set includes two important settings:

  • automountServiceAccountToken: false in ServiceAccount. If the agent does not interact with the Kubernetes API, it does not need a token. A token inside a Pod is an unnecessary target: with successful injection, it can be used to access the API on behalf of the agent. The Role can still be kept as a limiter in case such access is needed later. In that case, the token is explicitly enabled – via automountServiceAccountToken: true in the specific Pod's specification. By default, it is not mounted, and any exception is visible in the manifest.

  • Namespace. It's better to allocate a separate namespace for an agent or a small pool of agents. The Kubernetes RBAC guide notes that boundaries within a single namespace are weaker than between namespaces. Therefore, permissions should be granted granularly: use RoleBinding instead of ClusterRoleBinding where possible, and avoid wildcard rules.

The limit here is set more by economics than security. A service might run for days, while an agent often lives only a few seconds or minutes. Load comes in waves, with sub-agents appearing right during task execution. If a separate Pod is maintained for each of them in advance, resources quickly become idle.

In the CNCF article, Lin Sun describes an alternative – agent-substrate. Instead of a Pod for each agent, this uses a pool of worker Pods (WorkerPool CRD). The template (ActorTemplate) describes the agent's environment, including the image pinned by sha256, and the gVisor runtime; logical agents (Actor) are launched on available workers.

In the CNCF example, six agents fit into one worker Pod because they were not running simultaneously. The point of the approach is that the Pod becomes the unit of execution, not a permanent deployment unit for each agent.

agent-substrate is worth looking at, but it's too early for production: the article refers to version v0.0.6 from a single vendor.

This direction is confirmed externally: InfoQ analyzed the discussion as a trend, and Google announced Agent Sandbox and Agent Substrate on its platform. Agent identity is being decoupled from the pod, just as service identity was once decoupled from machines.

Egress: Where and What the Agent Can Do

Even a well-isolated agent with minimal privileges remains a risk if it's allowed arbitrary outbound traffic. In the "Memory Theft" article mentioned in the introduction, data was exfiltrated through a chain of seemingly harmless link clicks.

Therefore, the network layer begins with a basic rule: enable default-deny for the agent's namespace and then allow only necessary outbound traffic.

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: agents-report
spec:
  podSelector: {}
  policyTypes: ["Ingress", "Egress"]  # deny everything in both directions
---
aspiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: report-agent-egress
  namespace: agents-report
spec:
  podSelector:
    matchLabels:
      app: report-agent
  policyTypes: ["Egress"]
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: agent-egress
    ports:
    - protocol: TCP
      port: 3128

This is a basic scheme from the NetworkPolicy documentation: first, a general denial, then specific allow rules. For the allow rule to work, the agent's Pod must have the label app: report-agent. For Sandbox, this is specified in podTemplate.metadata.labels; for Deployment, it's in template.metadata.labels. If the label is missing, the second rule will not select any Pod, and the general default-deny will remain in effect for the agent.

DNS – The First Exception to Default-Deny

The first rule blocks all outbound traffic, including requests to kube-dns. However, a Pod typically doesn't report this directly: DNS names simply stop resolving, and logs show timeouts when accessing both the LLM API and internal services. Therefore, allowing DNS traffic to kube-system is not optional but mandatory.

But NetworkPolicy can only restrict traffic by IP addresses and ports. This is insufficient for an agent: it connects via HTTPS to domains, and the set of such domains can change depending on the task. Therefore, typically only one egress is allowed from the Pod – to a proxy gateway, which then handles HTTP(S) traffic and applies rules at the domain level.

This scheme is described in the CNCF material from F5: all agent outbound traffic goes through NGINX acting as a forward proxy, allowed domains are specified in an allow-list, and iptables blocks attempts to bypass the proxy directly.

The proxy solves more than just the filtering task. It shows exactly where the agent is connecting externally. Without this control, teams are often reluctant to allow agents into production: it's impossible to verify which external services the agent is calling and what data it might be transmitting outside the cluster.

Rules for Protocols and Operations

The domain allow-list only answers the question of where the agent can connect. However, this is insufficient when the agent has access to a production database: it's crucial to restrict the actions themselves – what queries it can execute and what objects it can operate on.

This requires control below the network level, at the protocol level. The open-source project Claw Patrol from Deno parses PostgreSQL, ClickHouse, Kubernetes API, and HTTPS traffic, and then applies allow/deny rules using CEL to the fields of the parsed request:

# read the reporting catalog - allowed
rule "reporting_read" {
  endpoint  = postgres.prod
  condition = "sql.verb == 'SELECT' && sql.tables.all(t, t.startsWith('reporting.'))"
  verdict   = "allow"
}

# writes to prod - only with human confirmation
rule "prod_writes" {
  endpoint  = postgres.prod
  condition = "sql.verb in ['INSERT', 'UPDATE', 'DELETE']"
  approve   = [human_approver.oncall]
  reason    = "writing to prod DB requires confirmation"
}

Rules are described in HCL, and conditions within them are written in CEL. Endpoints – for example, postgres.prod – and users or groups that can approve requests are declared in separate blocks within the same configuration file.

Available fields, such as sql.verb, sql.tables, k8s.verb, and http.path, as well as the exact syntax, depend on the Claw Patrol version. Before implementation, the configuration should be checked against the current reference guide.

Secrets are not transmitted through this channel. The agent only receives a placeholder, and the gateway substitutes the actual credentials when connecting to the target system. These credentials are not present in the agent's context – meaning they cannot be extracted from its memory, logs, or working directory.

Access policy is stored as code in Git. User rough-sea describes their setup: "In our configuration, all security policy is described in a single file, stored in Git, controlling access to 14 Kubernetes clusters, ClickHouse, PostgreSQL, and about a dozen other HTTP APIs." This claim cannot be independently verified, but it indicates the scale for which the approach is designed. According to Deno, Claw Patrol grew out of their own experience: the tool is needed to allow ops agents into production without giving them persistent credentials.

The caveat here is the same as with agent-substrate: the project is young, backed by a single vendor, and there are no public measurements of the overhead for parsing PostgreSQL protocol yet. Before placing such a gateway between an agent and a production database, two things should be checked:

  • How it behaves with long COPY operations.

  • What happens to active and new connections if the gateway becomes unavailable.

Where This Boundary Doesn't Work

In the Claw Patrol discussion on Hacker News, user oulipo2 asks the obvious question: why add a layer that prevents the agent from writing to SQL when you can simply give it a read-only account? They also point out the weakness of any policy built as a blacklist: "I understand the idea of a 'centralized registry,' but it's easy to miss something, and agents are good at bypassing restrictions: 'Ah, DROP TABLE is not allowed – I'll just delete all rows,' and so on."

If an agent is forbidden from DROP TABLE but allowed DELETE, it can delete all rows and technically not violate the rule. This is less an argument against Claw Patrol and more a reminder of the limitations of deny-lists in general.

Blacklists and Bypasses

A read-only account and gateway rules solve different problems:

  • An account defines what the agent cannot do in principle.

  • A gateway introduces operations that require separate human confirmation.

If choosing only one mechanism, it's more sensible to start with the account: it's simpler, more reliable as a basic barrier, and doesn't depend on the completeness of the rule list. A gateway is needed where the agent truly requires write access, but certain actions must still remain under human control.

The same logic applies lower down the stack. A single HTTP proxy can be easily bypassed if the agent can launch a child process: for example, call psql directly and not go through the HTTP layer. This scenario is also pointed out in the project description.

Therefore, the gateway must inspect the protocol itself, not just HTTP. At the same time, direct network access must be removed from the sandbox – for example, by assigning it a separate network namespace, as sandbox-runtime does. One layer closes the bypasses of another; a single boundary, at whatever level it stands, can almost always be bypassed.

Shadow AI Outside Kubernetes

The three technical layers only work for agents that have already come under the platform's purview. If an agent runs outside this boundary, there's simply nothing to protect.

According to OWASP data, only 37% of organizations have implemented policies for discovering and accounting for shadow AI. NetworkPolicy applies to Pods based on labels, but a label only appears on a Pod that someone has intentionally deployed into the cluster. A script on an analyst's laptop, launching an agent with production credentials from environment variables, will not fall under these rules.

This problem is solved at a level above Kubernetes manifests: through agent inventory, controlled access issuance, and rules that prevent the use of production secrets outside the approved boundary.

Auditing, Exploitation, and Requirements

Every agent call passes through the gateway and leaves a record. The NGINX OTel module creates a span for the external request, and the trace goes to SIEM or Grafana. In Claw Patrol, the audit log on the gateway serves the same purpose. This results in an action log that would otherwise have to be collected by a separate project.

There is only one important caveat. As CNCF writes, "observability must follow the logical agent, not the underlying Pod." A Pod is a temporary entity: it can terminate, be recreated, or serve multiple tasks. Therefore, traces and audit logs need the logical agent's identifier, not just the Pod name.

The tools here are the same as for regular multi-tenancy: network policies, quotas, and auditing. For people and teams, we discussed them in articles about isolation layers in a shared cluster and Gatekeeper policies. In VK Cloud's Managed Kubernetes, network policies, quotas, and auditing are available out of the box. RuntimeClass with gVisor and the Agent Sandbox CRD are not included in the service: like in other managed clusters, they need to be installed separately.

Regulatory requirements are gradually converging with what this boundary provides inherently. Obligations for high-risk systems from Annex III, including Article 26 of the EU AI Act, have been moved by Digital Omnibus to December 2, 2027, and for AI within regulated products to August 2, 2028. Article 50 on transparency applies from August 2, 2026. The deadline has shifted, not the content. Paragraph 2 of Article 26 requires that specific individuals with "the necessary competence, training and authority, as well as the necessary support" are responsible for human oversight of high-risk systems. Authority here is on par with competence and training: it's not enough to appoint a responsible person on paper; they must have the ability to intervene in the system's operation. A gateway with a rule requiring operation confirmation provides this capability in practice. Paragraph 6 specifically requires automatically generated logs to be stored for at least six months, unless EU or member state law specifies otherwise. It is more logical to build such a boundary before December 2027, not after.

Incident notification deadlines are shortening: DORA allows four hours, the RAISE Act – 72. Without a gateway log, it's difficult to even reconstruct the incident within four hours. Relying on application logs alone is not an option: a compromised agent will only log what it deems necessary. It cannot control the gateway's recording.

In Russia, requirements for AI agent isolation are not yet a separate category. However, such a boundary fits into familiar measures for certified systems: segmentation, access control, and security event logging. NetworkPolicy and the egress gateway handle segmentation; ServiceAccount with a narrow Role and the sandbox handle access control; the gateway's audit log handles event logging. If an agent accesses a system classified as a critical information infrastructure (CII) object, there's also an obligation to notify the State CERT about an incident: for significant CII objects, the deadline is three hours, for others, 24 hours.

Pre-Launch Checks

The API versions in these manifests have different statuses. networking.k8s.io/v1 and rbac.authorization.k8s.io/v1 are stable groups available in any supported Kubernetes cluster. agents.x-k8s.io/v1beta1 is a beta API from the Agent Sandbox project. Its CRD does not appear in the cluster automatically: in a managed environment, it also needs to be installed and maintained independently.

Before setting up a full environment, three short checks are sufficient.

Verify ServiceAccount's Actual Permissions

kubectl auth can-i --list 
--as=system:serviceaccount:agents-report:report-agent

This command will show the effective permissions of the ServiceAccount after applying the Role and all existing bindings. Sometimes it turns out that the agent has access to extra actions due to inherited ClusterRole or overly broad RoleBinding.

Verify Egress is Truly Closed Access the agent's Pod via kubectl exec and run curl to a domain not in the allow-list. If the request succeeds, the policy is not working or did not select this Pod. It's convenient to check the cause in this order: does the CNI support NetworkPolicy, does the Pod have the required label, is the namespaceSelector for kube-system correct. For example, Flannel itself does not enforce NetworkPolicy: the Kubernetes object will be created, but traffic will continue to flow without restrictions.

Check for Runtime Availability. kubectl get runtimeclass. This command will immediately show if the runtime for gVisor is installed in the cluster. It's best to find this out before specifying runtimeClassName in the manifest: otherwise, the Pod might remain in Pending or fail to start due to a missing RuntimeClass.

Minimal Production Boundary

If you can only implement one of the three layers, start with the network. The sandbox protects the host, RBAC protects the cluster, but data leaves the company over the network. "Memory Theft" would have passed through the first two layers, as would the database deletion in the Replit incident. A default-deny and egress gateway can be set up in a day: they don't require CRDs or a different runtime. A cluster where the CNI actually enforces NetworkPolicy is sufficient.

The complete boundary looks like this:

  • Runtime: RuntimeClass with gVisor or Kata.

  • Deployment Unit: a separate Pod per agent, its own ServiceAccount without token auto-mounting, a narrow Role, a namespace with ResourceQuota.

  • Network: default-deny for ingress and egress, egress only through a gateway with an allow-list, protocol-level rules for accessing databases and Kubernetes API.

In the Replit scenario, the DELETE operation would have been blocked by the gateway rule requiring write confirmation. The attempt itself would have been logged in the audit log even before the investigation began.

Agents are becoming another class of cluster tenants. In the July CNCF column, they are referred to as "non-human platform consumers with their own access, scope, and governance needs." There will be thousands of them, and they will live for minutes.

Agents will still end up in production – in one form or another. Therefore, what's more important is: what exactly will prevent an agent from accessing a system if it makes a mistake, receives malicious instructions, or tries to bypass restrictions?
