Large models for code have always been constrained by video memory. To run, they require tens of gigabytes of VRAM, preferably without compression. The startup PrismML has attempted to solve this problem using ternary quantization in the new Ternary Bonsai 2.5 27B model. In its most compact form, Bonsai occupies 5.93 GB. According to the company, it solves 75.6% of SWE‑bench Verified tasks, compared to 80.6% for Qwen3.8 27B, upon which it was based.

In reality, slightly more memory will be needed for launch, and the figure itself requires several important caveats that were not highlighted in the news announcement. In addition to the 5.93 GB for the model weights, the graphics card needs another 1–3 GB for the context window and the runtime environment, so it won't fit entirely into a 6 GB card.

What is a Ternary Model and Where Does 5.9 GB Come From?

According to the Hugging Face card, each model weight takes one of three values: -1, 0, or +1. For every group of 128 weights, there is a single common multiplier (or scale) in FP16 format, which helps restore their correct "size" during calculations.

To prevent the model from losing precision due to rounding, especially on rare but critical value spikes, the weights are mathematically "shuffled" (rotated in the Hadamard basis) before compression, evenly distributing outliers across the group. The engine quickly restores the data to its original form during runtime. A pure ternary weight carries approximately 1.585 bits of information.

Including overhead data, the card indicates an effective figure of 1.76 bits per parameter, resulting in 5.93 GB in PTQ1_0 format. Direct arithmetic without overhead would yield about 5.3 GB; the difference is accounted for by the aforementioned scale multipliers and metadata.

Out of the 27 billion parameters, 24.35 billion are for the language part, 0.47 billion for "vision," and 2.54 billion for input embeddings and the output layer (the accuracy of the latter is not disclosed by the card). For comparison, the original model in standard BF16 format would occupy about 54 GB (two bytes per parameter), meaning the developers achieved a ninefold compression.

Now for the caveat. The most compact PTQ1_0 format (the 5.93 GB) only works in a modified version of llama.cpp from PrismML itself; support for the main code branch is still undergoing verification. The standard llama.cpp will only run a heavier two-bit variant, Q2_0. Its exact size is not specified, but it weighs significantly more.

Furthermore, running even this version requires a recent llama.cpp (build no older than b11556). If an older version is used, the program will load the model without any errors, but the output will become incoherent. The situation is similar for Apple: a separate two-bit MLX package weighing 8.86 GB (including the vision module in standard FP16 precision) is used, which also requires its own loader and a modified kernel.

What Remains After Compression

The models were run in reasoning mode with a high effort level (xhigh) and sampled using parameters from the Qwen 3.8 card (temperature 1.0, top‑p 0.95, top‑k 20). Compared to Bonsai 2 at the same size, there is a 14.8 point increase on SWE‑bench and 39.3 on AppWorld. In comparison to the initial Qwen 3.8, the biggest drop is on Terminal‑Bench 2.1, a decrease of 10.7 points, meaning the ternary version loses the most on long terminal sessions. On τ³‑Bench, it is 1.1 points higher than the base, but this is likely measurement noise.

Speed and Memory

PrismML promises a speed of 291 tokens per second on H100 and 204 on RTX 4090 with MTP. On H200 and B200, it's around 300. On NVIDIA cards, this technology provides a 1.5–1.8x speedup, but with a couple of conditions. The necessary draft head is only available in special files with the suffix mtp (it's not in the base weights), and the MTP kernels themselves are still considered experimental ("in testing") and have not been tested on Metal, SYCL, or NPU at all.

The model's context is declared up to 262,000 tokens, for which memory will have to be paid. Judging by the documentation from the previous version of Bonsai 2 (the architecture hasn't changed in 2.5, so the calculations remain relevant), the KV cache in standard FP16 consumes 64 KiB per token—that's about 6.3 GiB for every 100,000 tokens.

If cache compression is enabled with the variable BONSAI_KV4=1, the consumption drops to 18 KiB per token (1.8 GiB per 100,000). In reality, on a graphics card with 10 GB of memory, the model will occupy about 9.5 GB with automatic parallelism, and if strictly limited to one thread (‑np 1), it will occupy about 7.8 GB. So, owners of 8 GB cards will find it a bit tight. For smooth operation, it's better to have 10–12 GB of VRAM.

For a normal launch, it's important to note that the ‑min‑p parameter must be reduced to 0 instead of the default 0.05, and the response length limit should be set no lower than 16,384 tokens—otherwise, the model will simply cut off generation mid-reasoning. It also does not support the low-effort mode (low).

Conclusion

As of now, without a disclosed measurement protocol (neither a specific agent nor a step limit has been named), the 75.6% SWE‑bench score remains solely a marketing figure from the vendor. The claimed 5.93 GB and high speeds are also tied to a custom llama.cpp fork and specific presets.

However, from a legal standpoint, everything is clean: the model weights are released under the permissive Apache 2.0 license, although the commercial use conditions of the base Qwen3.8 27B should still be verified separately. And the release itself reflects a general industry trend. Developers are increasingly trying to fit agent models with billions of parameters onto ordinary consumer graphics cards, squeezing the maximum out of compression.
