A new language model can appear in the morning, be at the top of several leaderboards by evening, and be replaced by the next version in a couple of weeks. For a team using LLMs in a product, this raises the question: when to update and how to do it without undue risk to users and development.

At Pervaya Forma, an AI agent assists in the development pipeline: it works with code, tools, and reviews. We regularly review the set of models in this pipeline. In recent weeks, we updated Muse Spark from version 1.2 to 1.3, added Gemini 3.8 Flash, and prepared a quick rollback for it to the previous model. We will explain how this process works.

Why Public Model Evaluations Are Not Enough

Public benchmarks allow us to notice a new model, understand its positioning, price, context window size, and claimed capabilities. That's where their role in our process ends.

A leaderboard answers a generalized question: how did the model perform on a specific set of general tasks and a particular rating methodology. In a product, the question is: "Can this model perform our tasks no worse than the current one, work with our tools, and not create additional operational problems?"

In our understanding, a developer agent should be able to parse a repository, use tools, make careful changes, detect regressions, and maintain stability over a long session. A model might appear strong in an open benchmark and yet perform worse in one of our critical scenarios.

There's also a more general risk: public tests eventually become known to development labs, and they retrain their models to perform better. Furthermore, a model's behavior depends on the prompt, provider, invocation mode, and surrounding infrastructure. Therefore, we perceive public results only as a signal for candidate selection. And then the selection process begins.

First — A Model Pool and Rollback Capability

Now, let's explain how the AI assistant at Pervaya Forma works. It's not tied to a single model. The pipeline has a pool of providers from which a model is selected based on assigned weights. For specific cases, you can manually request a particular model.

This approach solves several problems simultaneously:

  • it allows for gradual introduction of new models;

  • it prevents the product from becoming dependent on a single provider;

  • it provides an opportunity to compare models on identical scenarios;

  • it simplifies rollback if a problem is discovered after activation;

  • it helps consider quality, speed, cost, and availability in conjunction.

When a new model passes verification, we don't remove the old version from the configuration. It's put into a dormant state: it doesn't participate in normal selection but remains ready for return. As a result, rollback is a change in the pool composition in the configuration, which is significantly simpler.

This detail seems minor until an incident occurs. At the moment when a quick return to the previous state is needed, having a pre-prepared model noticeably reduces the cost of an error.

Deployment Doesn't End with Configuration Change

Simply adding a new model to the pool is not enough. After deployment, you need to verify that the agent is actually using it, that the system hasn't fallen back to a previous state, and that there are no hidden errors in the logs.

After updating Muse, we set up a separate live probe:

  • sent a request through the relevant route;

  • confirmed via technical data that the response came from Muse Spark 1.3;

  • checked for any signs of fallback;

  • ensured there were no new errors in the exception logs.

Such a probe takes little time and protects against a common situation: the configuration looks correct, but the actual request is handled by the previous model or a backup provider for some other reason.

This is a mandatory part of model changes for us. An agent's response by itself does not yet mean that the rotation was successful.

Gemini 3.8 Flash Case: Rollback Prepared in Advance

During the same period, we added Gemini 3.8 Flash to our catalog. The model has a context window of 1 million tokens and a response limit of up to 32,768 tokens. It was included in the pool with a specific weight. Gemini 3.7 was kept in a dormant state so that it could be quickly restored by changing the pool composition if necessary.

After deployment, we performed a probe with an explicit request for Gemini 3.8 Flash and checked three things:

  • the agent received a response specifically from the new model;

  • fallback did not occur;

  • technical logs remained clean.

The order of operations is important here. The rollback must be ready before the new version starts serving production requests. If the previous model is kept in a prepared state, the replacement ceases to be an irreversible event.

What Actually Breaks During Rotation

Changing a model often seems like a simple configuration edit. In practice, the quality of rotation is also determined by the infrastructure around the model: provider selection rules, session state storage, error classification, blocking mechanisms, and observability.

Over a week of analysis within our pipeline, several characteristic problems emerged.

Manual Provider List Lagged Behind Actual Configuration

One mechanism used a manually maintained list of cloud providers. When the pool composition changed, this list did not include some of the current providers: 5 out of 10 providers in the frontier pool did not fall into the correct category.

As a result, an unhealthy provider could be selected again instead of being temporarily excluded. In the analysis, 19 out of 28 failure traces were related to such a provider being repeatedly returned to the pool.

We changed our approach: provider characteristics are now determined from the live configuration. The general rule here is: The logic for selection and failure protection must rely on the same data source that defines the composition of the active pool.

Otherwise, the configuration and protective mechanisms will inevitably begin to live separately over time.

Unknown Error Did Not Block the Problematic Route

In another case, one type of error was classified as "unknown." The system did not consider it sufficient grounds to temporarily exclude the provider and selected it again in the next step of the same task.

In measurements, this led to 29 failures in 15 calls. Processing the scenario took about 6.5 minutes instead of approximately one minute.

After analysis, this type of error was reclassified to a category that blocks the provider for 15 minutes. This doesn't mean the error disappears on its own. However, the system stops repeating the same unsuccessful route and gets time to recover or switch.

Session Remembered the Wrong Provider

Another problem is related to session state. The system saved the provider from the configuration at the start of a turn, not the one that actually generated the response. After a failed request, the next turn could return to the already failed route.

In one analysis, this caused three consecutive interruptions within a single task. The conceptual fix was: the session should be tied to the provider that actually responded. But such a problem can only be detected when the logs show both the expected configuration and the actual request route.

A Model Might Silently Not Participate in Selection

There can be a quieter failure. A new provider is added to the configuration, but a necessary parameter is missing for it in the relevant pipeline. As a result, it is not selected, and there might be no explicit error.

This is why we don't consider documentation and configuration diffs sufficient confirmation of readiness. Every new provider undergoes a live probe after activation.

Conclusion

LLMs are updated faster than teams can safely change the surrounding infrastructure. Therefore, it's useful to treat new models as candidates in a managed process and not rush to update based on the first news.

We use a small set of our own scenarios, comparison with the current model, a pool with prepared rollback, and technical verification after deployment for this. We separately ensure that routing, fallback, session state, and error classification keep pace with the actual configuration.

This approach doesn't promise that every new model will be better, but it guarantees that changing a model remains a verifiable and reversible action.
