B&R process automation after sanctions, without magic and rituals: how to replace a dead controller with a mini-PC, keep the original racks, and not rewrite the project. Driver for Intel I226 network cards, real-time gateway, kernel for the task, and testing on real hardware.

In the first article, I talked about how I was left alone with two hundred car washes. It was about why it all worked out. Here it will be about how exactly, with the specifics that were asked for in the comments.

First, some context to understand where everything came from. Our car wash automation project is written in Automation Studio, which is B&R's development environment, and it runs on a B&R controller. When it became clear that controllers and modules could no longer be bought, we started migrating projects to regular PCs. For new car washes, this has been debugged since 2022: about a hundred facilities run on mini-PCs, and instead of B&R racks, they have racks from another manufacturer, using Modbus TCP. The project remains the same, only reconfigured for new modules.

But this won't work for the old car washes. They have original B&R racks, and they communicate with the controller via POWERLINK. This is a hard real-time protocol with a cycle of two milliseconds, and it wasn't there for show: the PLC counted the flow meter pulses and generated dispenser pulses on it. On such facilities, it's usually the controller that dies, while the racks live on and are ready to serve for another ten years. It's a shame and expensive to replace them, buying a controller is also expensive; a used one through gray import costs from half a million to three and a half million rubles, and that's for each failure. This article is about this case: how to put a mini-PC instead of a controller and not touch the racks or the project itself.

What We Keep and What We Change

We keep all the installed hardware. The cabinet, B&R X20 module racks, wiring, sensors, actuators – everything stays as is. We only change the "head," and here lies the main trick. The project logic is executed on the PC by ARsim, B&R's official runtime simulator. In Automation Studio, any project can be run through ARsim, and few people realize that it can not only simulate peripherals but also communicate with real hardware via Modbus TCP. So, the project doesn't need to be rewritten. The logic, visualization, remote desktops – all of it remains untouched, only the I/O configuration changes.

ARsim has its limitations. First: it only supports physical I/O via Modbus TCP, no POWERLINK. The second became apparent during implementation: ARsim is 32-bit, and it reserves buffers for each Modbus station. In the 2019 project, there are ten Modbus devices (vacuum cleaner couplers and lighting), and with just seven stations, it hit the address space limit. 2038 MB out of 2048 were occupied, leaving no room for visualization, and the runtime restarted. There's a third limitation regarding continuous operation, but we've resolved it on our end, and I won't go into detail here. The first two are overcome with a single trick: a gateway is placed between ARsim and the real hardware, and the project retains exactly one Modbus station.

Why not connect POWERLINK directly to the PC without any gateways? I settled this question even before starting work by digging into the installation files of Automation Studio itself. On the B&R panel PCs used in our car washes, POWERLINK resides on a separate interface card; on compact controllers, it's in the FPGA. In the catalog of almost two thousand modules, there isn't a single entry for "standard processor," only x86 PCs. The POWERLINK driver for such a PC is included in the delivery, but only one, and it's tied to a specific chip, the Intel 82574L. ARwin, the industrial version of the runtime for Windows, requires an old PCI slot, a proprietary card, and a licensed USB key. So, the racks can only be kept with their own bus master; there are no other options.

What the PLC Handled and What the PC Handles Now

Before writing anything, I went through the project and analyzed what actually required millisecond precision. It turned out to be almost nothing. The car wash logic runs fine with polling every few hundred milliseconds; we left that for the simulator. However, two areas are critical for real-time operation: counting flow meter pulses, as customer billing depends on it, and the 100-millisecond pulses for the dispensers. This is what the PLC previously handled within its two-millisecond cycle, and this is what has been moved to the gateway, which runs on a dedicated PC core with the same cycle time.

The gateway handles exactly what was in the controller's cycle: ten free-running 32-bit pulse counters (the PLC calculates the difference, and the polling frequency doesn't affect the count), eight pulse generators for dispensers (the PLC specifies "X pulses per minute," and the gateway generates them), an I/O mirror, scale conversions, and node diagnostics. In numbers, for the 2019 racks, this means 184 signals: every two milliseconds, 152 bytes from the racks and 43 bytes to the racks. The gateway then provides the processed data via Modbus TCP, appearing to ARsim as a standard Modbus station.

There are actually two gateways. The first is new; it translates POWERLINK to Modbus TCP and pre-processes data for channel logic, including the counters, pulses, and scales. The second is our standard one, used since 2023 on all car washes with mini-PCs, which aggregates devices already on Modbus TCP into a single table. The project in Automation Studio is reconfigured relative to this unified table. The configuration for Automation Studio is not drawn manually. There's a generator: it reads the rack descriptions and signal mappings from the original 2019 project and generates everything at once – a single Modbus station, polling blocks, over three hundred variable mappings, a table for the aggregate gateway, and an address map for the POWERLINK gateway. These items cannot diverge as they share a single source. The migration is verified by two separate scripts: one compares the map with the original project based on the physical module channel, not the variable name, and the second directly compares two Automation Studio projects, without trusting the map at all. For 2019, it resulted in 202 POWERLINK channels and 329 Modbus variables, with zero discrepancies and zero losses.

Hardware and System

Mini-PCs with two or more Intel network ports: my test benches used I210, while the machine deployed to the site had six I226-V ports. The specific model isn't critical. What's important is having multiple processor cores with separate caches, so at least one core can be dedicated entirely to real-time tasks. The operating system is Ubuntu, with a custom-compiled kernel: vanilla 6.8 with the PREEMPT_RT patch, HZ=1000, configured for core isolation and interrupt handling.

Now, about what usually raises questions: ARsim is a Windows program. On Linux, it runs via Wine, without a virtual machine, and it has a peculiarity that's good to know in advance. ARsim behaves like a real runtime and assigns its threads to the highest-priority CPU core. And that highest-priority core is precisely the one I isolated for the gateway. As soon as ARsim occupied it, the core utilization jumped to 50%, and the two-millisecond cycle became unstable. Initially, I tried to block it in various ways, with a patch for each launch method, but nothing worked: blocking one path, it found another. Only by separating everything using cgroups did it work. The gateway resides in its own group, with only that group having access to the isolated core, while the system, user session, and containers get the remaining cores. I verified this not by reading configs, but by attempting to load the cycle core with every known method. All were blocked, and core utilization dropped from 52% to 6.5%. Interrupts from the network card connected to the racks are also routed to this isolated core. The openPOWERLINK kernel driver takes over this card entirely; the standard Linux network stack cannot see it. The second card is the regular local network of the car wash, through which ARsim communicates with the gateways via Modbus TCP.

Once again, to avoid confusion: there is no separate PLC on this PC. ARsim executes the logic, and our gateway communicates with the racks through the control node of the open POWERLINK stack, running on top of our own network card driver.

Scripts That Hold It All Together

Assembling such a system once on a test bench and making it work reliably on-site without constant supervision are different tasks. The latter is achieved through scripts; without them, this would be a demonstration, not a solution.

The deployment is fully scripted and offline: a single installer sets up any PC from the kit, which contains everything – kernel packages, stack source code with patches, drivers for both card families, and services. All checks that could halt the installation are performed before any changes are made. If Secure Boot is enabled, the installer stops because our kernel and driver are not signed. The kernel for isolation is selected based on the cache topology from /sys, not a hardcoded number. The port for POWERLINK is selected by PCI slot and remembered along with the MAC address. This is crucial: on a machine with six identical ports, assigning a local network port to the bus means losing access to the PC, along with the PC itself. A separate service transfers the card to our driver in the correct order; the order is important here, as I'll explain later.

Three things ensure its longevity. The gateway doesn't crash when the link is lost; instead, it restarts the stack internally and honestly reports "rack not present" to the PLC. The gateway process itself is managed by systemd. And a separate watchdog monitors ARsim: it restarts the simulator if it crashes, restores the correct bootloader after an ARsim reinstallation from Automation Studio, and recently, it also verifies via handshake that its OPC UA server is responding, not just holding the port open. All of this is done in Bash and Python, nothing extraordinary, but it's precisely what allows us to install a mini-PC at a car wash and leave.

Why openPOWERLINK Doesn't Work Out of the Box

An open-source implementation of the protocol exists, called openPOWERLINK, and on paper, it's exactly what's needed. In practice, it runs into three issues.

The stack is abandoned. The latest version, 2.7.2, was released in 2019. It doesn't compile with modern Linux kernels (6.x), and the community rarely responds to questions.

It lacks drivers for modern network cards. To maintain the cycle time, the stack doesn't use the standard Linux network stack but interacts directly with the Ethernet controller via its own kernel-space driver. Pre-built drivers are only available for older Intel and Realtek chips. The I225 and I226, currently found in most mini-PCs, belong to a different family. In Linux, they are served by the igc driver, which is structured differently, and the stack has nothing for it.

And the kernel has moved forward. Over the years without support, calls that the stack relies on have disappeared or changed. In total, ten patches were needed, about twenty kilobytes: for the 6.x kernel API, for the removed struct timespec, for sched_setscheduler which is no longer exported, for the stack's virtual interface that wrote the MAC address directly into a structure field and received kernel warnings for it at every stop. Two more patches addressed real-time defects within the stack itself, which will be discussed separately, and two more concerned module lifecycle: unloading with active threads and kernel thread leaks if the stack failed to start.

So, the choice was: either find a specialist who simultaneously understands the Linux kernel, real-time, network card drivers, and industrial protocols, or do it ourselves. I couldn't have done this alone; I lacked the depth in this specific area. I did it with AI; I'll discuss the roles below.

Driver for I226

We took the driver from the stack itself as a basis, the one originally written for the I210 card, and ported it to the I225/I226 family. The MAC, DMA, interrupt, and 1588 clock registers match, so the timers, descriptor rings, and three MSI-X vectors were transferred almost verbatim: the new driver has 3343 lines and differs from the original by a few hundred. However, there are three areas where the cards are fundamentally different, and each required separate analysis.

First, the scheduler. On the I210, frame transmission at precise times was maintained by a Qav shaper with a 32-nanosecond step. The I225/I226, instead, has a full 802.1Qbv scheduler in nanoseconds: each of the four queues has "gates" with open and close times, a base time, and a cycle length. A queue with unprogrammed gates transmits nothing at all, silently, without a single error in the log. A zero cycle length and zero base time mean "scheduler off." Nearby is a trap for transmission buffer sizes: the default value, from which the port started, left zero bytes for the queues, and the card would again fail to send any frames. All of this was found even before the first hardware run, when the driver was compared line by line with the reference igc kernel driver, and the code now contains direct warnings.

Second, timings. Ethernet Energy Efficient (EEE) is disabled before the PHY reset: entering and exiting sleep mode on 100BASE-TX takes tens of microseconds, which falls directly within the two-millisecond cycle. PHY delay compensation is taken from the actually negotiated link speed, not from an assumption: the card supports 2.5 Gbps, the POWERLINK segment runs at 100 Mbps, and if the speed isn't checked, a misnegotiated link remains invisible. There's also a subtlety with the scheduler horizon. It ends at the current Qbv cycle of one second, and a frame targeted beyond its boundary is sent immediately unless marked as the first frame of the next cycle. At our two-millisecond cycle, this is exactly one frame per second, and without the mark, it would be sent half a millisecond earlier than scheduled. This was also caught by comparing with igc, before hardware testing.

Third, resilience to silent hardware. The driver had places where an unresponsive PHY or a frozen hardware semaphore could hard-lock the kernel, including during module unloading. All such waits are limited by the number of attempts, and each logs a warning. Upon unloading, the transmission path is returned to the state after reset, so the card is presented to the standard igc as expected. We encountered an issue with the I210: after our driver, the card remained in forced mode, and the standard driver then failed to bring up the link.

Two Real-Time Defects in the Stack Itself

These two issues are not related to the I226; they concern the stack itself and were only discovered on hardware, on a test bench with an I210 card and a real rack. Every few minutes, the cycle would stall for exactly half a second, 502–517 milliseconds, and a node would go into an inactive state. Half a second turned out to be the stack's default behavior: after five consecutive delays, the master enters PreOperational1 and waits there for 500 milliseconds. The delays themselves stemmed from two defects.

The first was in the I210 driver's timer handler. Upon startup, it enabled system clock overflow among the card's interrupt sources, which occurs once per second. The handler, upon seeing this bit, exited prematurely without checking the cycle time. A cycle coinciding with the overflow was lost, the timer was not reset, and delays occurred in batches of five, precisely the threshold after which the network exits the operational mode. The second defect was the margin for preparing cycle frames: in the stack, it's 150 microseconds, or 7.5% of the two-millisecond cycle. On a standard PC with an RT kernel, this is barely enough. I increased it to 500. This doesn't affect the wire, as frames are still sent by the card at hardware time. After both fixes, we had 44 minutes without a single delay, zero node disconnections, and zero lost pulses on 224,273 fronts, which I measured by shorting an output to its input on the rack. Before the fixes, there were about seventeen disconnections per hour. Both fixes have been applied to the I226 driver as well.

How It Was Done and How It Was Tested

First, about the roles, to be clear. The idea itself—replacing the controller with a PC while keeping the racks, placing gateways between ARsim and the hardware, and offloading signal processing previously done by the PLC to them—is mine, and the architecture of the entire scheme is also mine. However, the code was written together with AI, and a significant portion of it is AI-generated: the kernel, the driver, stack patches, gateways, project reconfiguration. I didn't sit with an editor typing registers manually, and I won't pretend otherwise. My job was different: setting tasks, verifying results, and iterating. The test bench with a live car wash is also my work, because real-time cannot be verified by just looking at code.

The first check was even before hardware testing: the line-by-line comparison of the driver with the reference igc, which I've already mentioned. Thirteen errors were found, five of which were critical for transmission. The commit for that day ended with: "Builds clean against 6.8.0-rt. Not yet run on hardware — the card goes in tomorrow." The card was installed in the mini-PC, and on September 13th, the very first run with a real rack behind a coupler yielded 297,766 cycles without a single skip and without any losses according to the coupler's own counters.

On the calendar, it took three weeks, not counting the first night on-site. August 26th: decision made. By September 5th: stack compiled for kernel 6.8 and master brought up on I210. September 7th: real-time defects analyzed. September 8th: first project commit. September 10th: I226 driver written. September 13th: it worked with a real rack for the first time and on the same day, the deployment package was compiled and tested in a virtual machine. September 15th: second test bench set up. September 17th: first site visit. The code itself—kernel, driver, gateways, and reconfiguration—took three to four days of pure work time. Everything else was the test bench, and there, everything was done manually. B&R rack behind the coupler, mini-PC, wires. I poked inputs, watched if the indicator lights on the correct modules lit up, connected outputs to inputs to check if the signal passed through the gateway back and forth and reached the project. I pulled the patch cord, disconnected the rack's power, killed the gateway, killed ARsim, and watched how everything recovered.

Four things discovered on the test bench through errors are worth mentioning.

A device should not confirm itself. The rack's software simulator initially wrote the same number to all channels, and a one-byte shift in 55 out of 64 analog connections was simply invisible. Once unique values were fed into each channel, the shift immediately surfaced.

The arbiter must be external. B&R couplers count lost frames themselves; these counters are read via SDO and cannot be influenced. If the count is zero after hundreds of thousands of cycles, then it's zero. The second external device is a separate PC on the same segment that listens to SoC frames with kernel timestamps. This is how I distinguished master delays from observer delays: the gateway's cycle counter must increase by exactly thirty thousand per minute, and if the observer sees a half-second pause while the counter is full, the delay is with the observer. What exactly the observer measured, I'll explain below, in the section on test runs.

Testing should be done by attempting to break it, not by reading configuration. A telling case: if the rack is powered on after the gateway, the driver re-requests interrupts, they land on shared cores with default priority, and within five minutes, 271 lost cycles accumulate. We found this precisely with this test and fixed it by binding interrupts after each stack startup, hence the startup order in the deployment scripts. Priorities turned out to be crucial: card interrupt threads at 95 and 90, cycle thread at 80, stack event thread at 79. By default, PREEMPT_RT gives interrupt threads a priority of 50, which is lower than the thread waiting for their events, and this single inversion caused network failures. What turned out to be irrelevant was also verified by instruments: firmware is not to blame (hwlat, SMI zero), the scheduler is not to blame (cyclictest, maximum 61–72 µs). However, nohz_full, which is usually recommended for real-time, is detrimental here: the stack makes a system call every two milliseconds and pays for each entry into the kernel.

And the longest investigation was not about our code at all. On the second test bench, a node would drop out strictly on schedule: after 10.5 seconds, then after 12.5, and so on. When the period is regular, it's a hint in itself that some ten-second timer is ticking somewhere. ftrace showed that the card's timer fires exactly every 2.000 ms, but the handler remains silent for half a millisecond when simply reading a register. I wrote a small program that reads the card's register from user space, and it showed freezes of 350–770 microseconds in series, with the adjacent Realtek also freezing at the same microseconds. This meant the entire PCIe bus was freezing. In each such window, there was an ACPI event, and according to DSDT tables, it led to the integrated graphics. The i915 driver would put the GPU to sleep after ten seconds of inactivity, and each such transition would freeze the PCIe behind the south bridge for five milliseconds. This is fixed with a single udev rule that keeps the GPU in D0. Everyone doing real-time on a consumer mini-PC should remember this: the subsystem you're looking at might not be the culprit at all.

The longest part in terms of time was not the coding but the test runs. Overnight, for eight hours, on two different machines: 7 hours 47 minutes and 13.9 million cycles on the mini-PC with I226 (which later went to the site), and 8 hours 05 minutes and 14.56 million cycles on the second test bench with I210 after fixing the graphics issue. We monitored three things: frame skips according to the coupler's counters, frame interval exceeding the cycle time, and the stability of the OS kernel under load (no freezes, no leaks, no timing degradation by morning). The result: zero skips and zero node disconnections.

The frame interval, as observed on the wire, stays at 2.00 ms, with a maximum of 2.335 ms; no interval exceeded 2.5 ms. However, the timestamp is set by the regular PC's kernel, and some of this jitter belongs to the observer itself. The jitter is paired: one interval is longer, the next is exactly as much shorter. This is not the coupler's merit but a property of the master. The cycle timer is set on the card's own clock as "previous target plus two milliseconds," and the SoC leaves the card at the hardware launch time on the same clock. The grid on the wire belongs to the card; the program only needs to prepare frames 500 µs before the deadline, the margin I increased from 150 µs. A delay within the margin doesn't reach the wire; beyond the margin, the frame is sent late, the master considers it a cycle error, and five consecutive errors drop the network into PreOperational1. The coupler has its own limit: the SoC must arrive within the cycle plus a tolerance for SoC loss. Each violation adds eight to the counter, each clean cycle subtracts one; the threshold in B&R configuration is 80. A node drops out after approximately ten consecutive violations. The gateway reads this counter from the coupler via SDO, and it remained zero throughout all test runs.

Live Car Wash: What the Test Bench Couldn't Catch

Then came the live car wash. It wasn't about indicator lights anymore, but about signals that needed to be processed according to the project logic: the flow meter counts, the dispenser dispenses, and the billing matches. It didn't work from the first site visit, and the reason deserves a separate explanation because it's precisely the boundary beyond which a simulator cannot prove anything.

In the eleventh slot of the rack, there's an X20ZF0000, a dummy module without any signals. However, the dummy module has an address on the internal X2X rack bus. In Automation Studio, there's no description file for it, and the built-in openCONFIGURATOR silently removes it from the network configuration: this results in 23 module configuration objects for 24 stations. The coupler addresses each module's configuration by the index "0x2100 plus X2X address" and refers to the data layout in frames by the same indices. Consequently, the configuration of the twelfth module was mapped to the dummy module's address, and everything after it to other modules. Communication occurs, inputs up to the dummy module match the panel, but all outputs after it are dead, and the power monitor at the end of the rack reports zeros. The same rack worked for years with the standard PLC, meaning the dummy module was present in its coupler configuration. It was lost precisely during the transfer through openCONFIGURATOR and the CDC file.

The second trap cost a whole day. Three consecutive corrected configuration files had no effect whatsoever. It turned out that the coupler stores its configuration in its flash memory, and the openPOWERLINK configuration manager only reloads it when the configuration date and time reported by the node do not match what the master expects. The date in my edits remained unchanged, and the line "CFM node 1: result 6" on each startup meant not "loaded" but "nothing to load." Guesswork consumed the day. A probe helped: directly on-site, I added reading arbitrary node objects via SDO to the gateway and outputting them to the log. It revealed two things immediately. The dummy module's address contained the configuration of the adjacent output module, and the configuration date in the coupler matched the expected date, meaning none of my edits had reached it. The mechanism was proven the same day on a small test rack: a configuration with just a new date went through the path "written, node reset, operational mode," and the probe read the new date from the node.

The fix is a script that compares the number of stations from the map with the number of objects in the configuration, inserts the missing station, shifts subsequent configurations and 27 layout references, and updates the date. The check "number of stations equals number of objects in file" and "date is new" takes a minute and is now on the checklist before any site visit. From the second visit, the rack worked entirely: phase voltages of 230/229/228 volts on the panel, outputs after the dummy module accept commands, dispensers pulsed, and the car wash then operated for clients. Why the test bench missed this is also clear: the main rack on all test benches was a software node simulator; only the small rack was real, and it had no dummy modules. The simulator accepts any configuration. The real coupler does not.

Already on the operational car wash, two more effects emerged that don't occur on a B&R controller and are useful for anyone running ARsim under Wine. First: under load on three cores of the system (remote desktop, USB servicing, graphics driver polling HDMI output), the OPC UA server within ARsim once froze. The process was alive, logic was running, the bus was clear, but port 4840 accepted connections and remained silent, causing the station panels to lose communication with the PLC. This is fixed by restarting ARsim, which is why the watchdog now checks the OPC UA handshake, not just the process existence. Second: the project includes code that, each cycle, first clears visualization elements and then repopulates them. On the PLC, this works without consequences, as visualization cannot interfere with the task cycle. However, in ARsim, the task is a regular Linux thread; the OS can preempt it precisely in this window, and an element on the HMI disappears for a second. Race conditions within the cycle, which don't occur on the PLC, are possible here, and such code is better rewritten so that the visualization is published by a single copy operation.

Economics

A used B&R controller costs from 0.5 to 3.5 million rubles, and that's for each failure. A mini-PC is one to two orders of magnitude cheaper. Development took three weeks of one person's calendar time, including three to four days of pure coding, and it's done once: the solution is then replicated to sites via scripts.

Scope of Application

  • The 2019 generation of racks, where I/O is entirely on POWERLINK, has been debugged. On facilities from 2015–2018, eight frequency inverters are also connected to the same bus; they will need to be addressed separately.

  • The end-to-end delay ("rack input → logic reaction → rack output") has not been measured separately. The gateway handles all millisecond-level timing, and the logic suffices with polling in hundreds of milliseconds, so in practice, it's not an issue, but I don't have the exact figures.

  • One kernel defect during driver unloading on the test bench could not be reproduced, but it recurred on-site: stopping the gateway once completely froze the machine. The rule is now simple: the driver and bus configuration on an operational site are changed only by rebooting; we do not unload the driver on the fly.

  • The longest pure test runs were eight hours on the test bench and twenty-four hours on the live car wash, totaling 43 million cycles without a single skip. There is no multi-month statistical data yet.

From the software side, the scheme uses no custom code where it's not necessary: logic is executed by B&R's standard ARsim, and the system communicates with native modules via an open protocol through an open stack. Specifically for this task, a driver, gateways, surrounding scripts, and the operating system itself were created—a real-time kernel with core isolation and interrupt distribution.

Conclusion

The outcome is as follows. A dead B&R controller is replaced by a mini-PC; the racks and the project remain. The project code is not rewritten—logic, visualization, remote desktops remain as they were—only the I/O configuration is changed to match the gateway's aggregate table. Three weeks of work by one person versus millions for each failure and versus a new automation project at each site. Dependence on a vendor that no longer exists in the country has been eliminated.

Regarding AI, without exaggeration: I don't know how long it would have taken a good specialist to create such a driver—a week, a month with debugging—and I won't guess. It's not about the volume of code. It's about the task sitting at the intersection of fields that rarely coexist in one mind: the Linux kernel and its real-time compilation, network card drivers with their schedulers, an industrial protocol with a hard cycle, B&R environment and its configuration. Finding a specialist for all of this at once is difficult, and waiting is long. AI assembled the stack in three to four days. Moreover, if I had known in advance what we would encounter and provided a precise specification immediately, it would have taken a day. But no one knows that in advance, and it would still have been impossible without feedback from the hardware: the longest part here is not the code, but the test runs and on-site debugging. And I'll be honest: half of the defects found during this time were our own, and almost every one was found by measurement or by attempting to break it, not by reading the code.
