Without actual exports, you can prepare a comparison: save the accounting conditions, match the addresses, and check the disputed pages.

What fields to save in URL exports

In both exports, you need to save the page addresses and the conditions under which these addresses were included in the list. A column with links is not enough for comparison: you need information nearby that allows you to reconstruct the check.

You will need:

  • An export of pages from the Search Console AI report with impressions, period, country, and applied filters. You also need to specify which report and search type were used.

  • An export of URLs from monitoring for the same period and region. For each check, you need the service, AI function, question, check time, and found link.

  • Information about URL parameters, redirects, and canonical addresses of pages where discrepancies are found.

The domain can be replaced with the same conditional designation in both exports, preserving paths and parameters. Based on this data, you will identify common pages, pages only in Search Console, and pages only in monitoring, calculate group sizes, and specify the denominator for each share. Then, check the reasons for discrepancies on specific URLs.

For each list, it's worth separately recording what counts as a page inclusion: a link impression, a link in a saved response, or another event. Mentioning a brand without a link should be kept as a separate indicator. Otherwise, different items will end up in the same comparison row: the company's presence in the text and a link to its page.

It's convenient to collect comparison conditions in a table before calculations. It should include the period with timezone, country, service, AI function, questions, and filters. An unspecified condition is better marked as unknown than reconstructed from memory. For a row with an unknown region, you cannot silently substitute the region of a neighboring check.

How to match parameters, redirects, and canonical URLs

For each original URL, you need to match the address by which the match will be checked, keeping the original link in a separate column. This will allow you to return to a specific transformation and check why two addresses were merged or left separate.

The order of comparison should be fixed in advance:

  • Save the URL in the form it came from each source.

  • Check for redirects and record the final address along with the redirect chain.

  • Check the canonical address information for the page and note where it was obtained.

  • Parse URL parameters and determine which variants are acceptable to merge in this comparison.

  • Assign a common address for comparison to the page and record the basis for the transformation.

Parameters cannot be removed by a single rule without checking their purpose. For example, in a conditional comparison, two URLs differ only by a parameter. Before merging them, you need to open both addresses and check the content. The mere external similarity of links is not a reason to consider them the same page.

If the final and canonical addresses differ, it's useful to save both. For a disputed pair, you need to indicate which address was chosen for comparison and why. Unverified canonicalization cannot be used as a ready explanation for a discrepancy.

After processing, you should have two results: a comparison of original URLs and a comparison of addresses after confirmed transformations. This will show which differences disappeared after checking the links. Each disappeared discrepancy can then be linked to a specific rule, rather than a general data cleaning note.

How to count the intersection of two page lists

After matching addresses, you need to identify common pages and pages found by only one source. Within each list, remove duplicate matching addresses: multiple observations of the same page should not result in multiple pages.

For each page in the combined table, two indicators are sufficient: whether it is in Search Console and whether it is in monitoring. Based on these indicators, you will get three groups:

  • Pages found by both sources.

  • Pages found only in Search Console.

  • Pages found only in monitoring.

The sizes of the groups should be shown in absolute numbers. Next to each share, you need to write the number of pages it is calculated from. A statement about matching lists without a denominator leaves too many interpretation options.

In all calculations, the numerator is the number of common pages; the denominator depends on the question.

How to find out why a URL is only in Search Console or only in AI response monitoring

For each one-sided match, you need to reconstruct the conditions under which the URL was included in the respective list. It's more convenient to check one page at a time, keeping the original records from both sources side-by-side.

If a page is only in Search Console, first check if the corresponding service and AI function were included in the monitoring scope. Then, compare the period, region, and set of questions. If there is no suitable check in monitoring, the absence of the URL cannot be recorded as a missed link in the response.

If a suitable check exists, the next step is to open the saved response. You need to find out if it contained a link to the disputed page and under what address. If a link is present, check if it made it to the export and if it was merged with another URL during processing.

For a page found only in monitoring, the process starts with the saved response: which service provided it, for what question, and when. Then, compare the Search Console report settings and look for the original, final, and selected-for-comparison addresses. Record each checked option in a table so that repeated checks don't start from scratch.

It's useful to describe the absence of a row literally: the address was not found in such-and-such export with such-and-such filters. The wording about an error should be reserved for cases where a specific violation of expected behavior is found. For example, in a conditional check, a link is present in the saved response, but the processor missed it. This is already a verifiable defect in link extraction.

How to confirm an error in monitoring AI responses links

The conclusion about a monitoring error should be tied to a specific stage: receiving the response, extracting the link, processing the address, or exporting the result. For each disputed URL, it's worth saving the original record, the expected result, and the actual result.

A confirmed explanation must have a verifiable basis: a saved response with a link, a redirect chain, information about the canonical address, or check settings. If the explanation relies solely on assumptions, it should be left without an established cause. This way, a confident diagnosis based on a single missing address won't appear in the results.

Search Console and AI response monitoring cannot be considered interchangeable sources. The reason for a discrepancy must be determined by specific URLs and check conditions.
