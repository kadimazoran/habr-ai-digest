The Case of Overthinking: Why Thinking Too Much is Harmful

In this investigation, we explore the performance of Qwen3.8-27B models with different quantization levels (BF16, 8-bit, 4-bit) on a Mac Studio. Contrary to initial assumptions, increasing reasoning effort (reasoning_effort=xhigh) did not improve performance for quantized models, especially in coding tasks. Instead, a medium reasoning setting (medium, thinking_budget=2048) yielded better results for 4-bit and 8-bit models, demonstrating that more thinking doesn't always equate to better quality, particularly when specific artifacts like compilable code are required. The study suggests that for tasks demanding concrete outputs, models need to finish thinking and start producing, rather than getting lost in excessive deliberation.

In the previous investigation https://habr.com/ru/articles/1075706, we looked into the speed of the local Qwen3.8-27B on a Mac Studio. The conclusion was quite harsh: for interactive work, radically speeding up a 27-billion parameter model can be achieved primarily by reducing the size of its weights, i.e., through quantization. In conjunction with DFlash2, the 8-bit version reached 38 tokens per second.

But that was only the first question.

Responding quickly and working well are not the same thing. Especially when the model needs to analyze an incident, adhere to a strict format, write, and debug code, rather than just retell a text.

I wanted to find not the fastest version of Qwen3.8-27B, but a model that could be realistically used every day: so as not to wait a minute for a response and receive very convincing nonsense in return.

It seemed the plan was obvious. We take BF16 as the quality benchmark. We compare 8-bit and 4-bit to it. And to ensure the quantized versions don't lose out on complex tasks, we enable the maximum reasoning level for them — reasoning_effort=xhigh.

This was a perfectly logical hypothesis.

And it turned out to be incorrect.

A Brief Look at the Setup

Tests were performed on a Mac Studio (2025), Mac15,14: Apple M3 Ultra, 32-core CPU, 80-core GPU, 512 GB unified memory, and 2 TB SSD.

Why BF16 on such a machine doesn't turn into lightning, how decode limitations work, and why DFlash2 helps has already been explained in a separate article: https://habr.com/ru/articles/1075706. DFlash2 here is not an independent model but an assistant for speculative decoding: it proposes a block of future tokens, and the target model verifies them. The authors of DFlash2 describe it as a block-diffusion draft model, not a replacement for the main Qwen (model card).

This means that in the test, the quantization of the target model was changed, not the entire rest of the pipeline.

What to Consider Quality, Not Impression

Asking another LLM to evaluate responses is a bad benchmark. We then simply replace one probabilistic judgment with another and call it measurement with a serious face.

Therefore, I wrote a Python benchmark for the local oMLX API. It contains 28 quality requests for each model.

Seven tasks tested reasoning, instruction following, and analysis:

  • inventory, schedule, and reliability with retries;

  • strict JSON and a specified Russian format;

  • incident analysis and calculation of vendor TCO.

Another 21 requests were for development: seven tasks, each in three reasoning profiles.

This is an important distinction. In real development, an answer like "generally correct, but didn't meet the contract" is not an almost finished result. It's work that needs to be redone manually.

Clue #3: xhigh Turned Out to Be a Bad Development Manager

The initial hypothesis sounded reasonable: the stronger the quantization, the more carefully the model should be made to think. Therefore, 4-bit should be given xhigh, and perhaps even make it the default.

At xhigh, everything got worse. But 4-bit failed the most: one out of five C# tasks and none of the two SwiftUI tasks.

At medium / 2048, 4-bit and 8-bit passed all 7 out of 7 development tasks. In the C# LRU cache task, 4-bit was also faster: 19.94 s compared to 25.21 s for 8-bit and 57.53 s for BF16.

This is the central result of the investigation.

To compensate for quantization, a smaller model doesn't need more thinking time. In this stack, it needs less freedom to go into endless deliberation and to be prompted for the final code faster.

What Exactly Was Breaking xhigh

The problem wasn't that the model chose the wrong algorithm. In several cases, it didn't reach a result at all.

The most illustrative example is the strict TCP port parser. This is not the most complex task in the set: it requires correctly handling null, empty strings, spaces, +80, Unicode digits, overflow, the range 1...65535, and returning a strictly defined C# class.

In xhigh, BF16 and 8-bit went into long deliberation but did not produce the final Solution. The code didn't reach the compiler — there was nothing to check there.

After switching to medium / 2048 and low / 1024, both models passed all 13 out of 13 hidden tests for this task. In the full set, all three models, including 4-bit, solved all five C# tasks in both medium and low modes.

The story with SwiftUI is similar. Some xhigh failures were not errors in filtering or validation but violations of the output contract: the model didn't provide import SwiftUI, added a forbidden import, or didn't reach the final View.

For 4-bit in xhigh, there was also one actual compile error: System.StringBuilder instead of System.Text.StringBuilder. But this doesn't explain the entire difference. The main problem was that excessive reasoning consumed tokens and destroyed the transition from analysis to final code.

The paradox is that xhigh looked like a "do it more carefully" setting, but it actually became a bad development manager. It forced the model to recheck edge cases for too long but didn't control the simple and main deliverable: return compilable source code with the correct API.

Fewer Bits — Less Thinking? Yes, But With the Right Formulation

The tempting conclusion is: "the smaller the model, the less it needs to think." Based on this experiment, it accurately describes the practical configuration for 4-bit.

Whether this is true will be shown by the ongoing development by my AI team on Qwen3.8.

Why this happens is likely due to several reasons:

  1. xhigh generates too long an internal chain and leaves fewer chances for a precise final answer.

  2. Quantization changes the generation trajectory; with long reasoning, a small deviation can accumulate to a point where the model no longer returns to the task contract.

  3. In the oMLX API chain, reasoning sometimes ended up where the benchmark expected only code. For automation, this is not a "format peculiarity" but a real integration error.

The first and third points were directly observed in the results. The second is a reasonable hypothesis that still needs to be verified with repeated runs, not an established fact.

This is precisely why the setting cannot be chosen on a "more is better" scale. It must be chosen based on the task.

Verdict: Quality Was Not Found Where It Was Sought

We started with a clear logic: BF16 — maximum quality, 8-bit — a compromise, 4-bit — almost certainly a quality trade-off for speed. And if the trade-off is too great, reasoning needs to be added.

The experiment revealed a more interesting picture.

  • Quantization to 8-bit and 4-bit provided a huge speed gain and showed no catastrophic degradation on the selected set of tasks.

  • Quality cannot be measured solely by the external impression of the text: code must compile, and the response must adhere to the contract.

  • Maximum reasoning did not become a safeguard for quantized models. In programming, it turned out to be one of the causes of failure.

  • For 4-bit, the best mode was not xhigh, but medium / 2048: all 7 out of 7 development tasks with minimal time among the three models.

My current working configuration for development is Qwen3.8-27B-4bit + DFlash2 + reasoning_effort=medium + thinking_budget=2048. I am not discarding BF16: it remains the control model and a reserve for tasks where errors are particularly costly.

The main takeaway here is not about 4 bits. It's about how we are accustomed to configuring LLMs.

More thinking does not mean more quality. Especially if the task requires not beautiful reasoning, but a specific artifact: valid JSON, working code, a compilable screen, an accurate API call.

The model should not just think for a long time. It should finish thinking on time and start doing.

What to Check Next

The case is not yet closed. The next stage is to increase the evidence base:

  • correct the incident judge so that it accepts both justified sets of evidence;

  • repeat the set several times and add independent tasks;

  • test real tasks from work projects in an isolated harness;

  • separate pure TG/PP/TTFT from end-to-end wall time and run speed tests in blocks by model;

  • separately test long context, tool use, and tasks where errors are particularly costly.

Only after this can we confidently say where BF16 truly justifies its slowness, and where 4-bit has already become not an experiment, but a working standard.
