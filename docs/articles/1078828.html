In the first part, I built an assistant that listens to calls, distinguishes voices, writes transcripts, and stores meetings in a knowledge graph in Obsidian. All on my Mac, nothing goes to the cloud. A month and a half of daily work has passed since then, and it turns out that recording a meeting is the lesser half of the task. The greater half is ensuring that after a month, you can extract the truth from these records, not what the model invented based on them.

This part is about how the graph lives for weeks: what it stores, how it doesn't lie, what the night does to it, how search answers from it, and how a meeting can be forgotten entirely. There will be little code, but a lot about how it works.

Three Layers and No Database

I described the scheme in the first part—I'll briefly remind you. The graph is a folder with markdown files that Obsidian opens:

Meetings/2026-07-17_1400_Payment Provider.md   ← episodes, raw data
People/  Systems/  Teams/                       ← entities, backlinks
Cores/                                          ← cross-cutting themes: status + history
Dossiers/                                          ← ready-made summaries on topics
Meetings-archive/2026-07-17 14-00 — …/             ← same for Finder

This is the same three-layer scheme of "episodes → entities → communities" as in graph memory systems like Graphiti or Zep, just without a graph database. Files. It works with grep, git, any editor, and most importantly—the files are owned by a human, not by code. If I stop developing the project tomorrow, the folder will remain readable.

An example from the demo graph: a meeting about choosing a payment provider creates a node Cores/Payment Provider Selection.md, containing a status line "Decided 17.07 — ЮPay." and below it, a history with links to the meetings where this decision was reached. People (Maria Sokolova, Igor Vetrov) get their own nodes with backlinks to meetings. Everything else in this article is about how these files don't turn into a mess.

Rule Number One: A Fact Lives with "From" and "To" Dates

The first thing I realized in a month: nothing is ever final in work meetings. A decision is made on Wednesday, canceled on Friday, and two weeks later they return to the first option. If the graph only stores the last state, it lies about history. If it stores everything, it lies about the present.

Therefore, each core has two sections. "Status" is overwritten by each meeting, and the superseded status moves to "History" with a note of the date it was active from. A fact gets "from" and "to" dates. A dash in the status is not considered a status; re-processing the same meeting adds a clarification to its line, rather than creating a second one.

This sounds obvious, but models don't want to do it. They want to write a nice summary. I had to make the prompt boring and strict.

Rule Number Two: Every Line of History Leads to a Replica

The most unpleasant discovery I made one evening: I noticed that the graph confidently quoted people, and the quotes looked plausible, but they weren't in the transcript.

The mechanism was as follows. Live minutes, which the model writes every two and a half minutes during the meeting, were appended to the same file that was later used for quote verification. The second-pass model found "confirmation" in the text of the first. Fiction was confirmed by fiction. Three external reviewers (more on this below) found four loopholes of the same origin: the "who said it" field was taken from the model's response, not the transcript; the parser didn't know the pipeline format; the replica header wasn't considered a boundary; notes the model writes to itself during the meeting (the "Co-thinking" section) were signed as human replicas.

A separate circle added a fifth: the parser took any short word before a colon as the speaker's name, and lines like "Summary:", "Decisions:", "Attendees:" ended up in the "speakers" list. In total, this fix involved six review rounds.

Now, the source of a fact is only the transcript: "who" and "when" are read from the replica line, the quote is verified against the text, and if the replica is missing—the fact goes without a signature, not with an invented one. The model can interpret, but it cannot assign an author.

A side lesson: three different loopholes had the same cause, and treating them individually was a mistake. After a second Critical error in the same fix, I completely removed my parsing heuristic and put a single parser next to the transcript renderer. This became a project rule: a second Critical error in the same fix means stop, look for an existing mechanism, not a new patch.

Dossiers: A Layer Between Search and the Graph

The question "what's our final decision on topic X?" is the most frequent. Searching the graph returns a dozen snippets from different meetings, and the model reassembles the answer each time—and each time slightly differently.

A dossier is a ready-made summary on a topic: status, history, what's decided, what's open, who's involved, with links to nodes. A topic cluster is the core plus its neighbors by links: meetings, documents, adjacent cores. The boundaries of topics are set by the user themselves by placing links. No graph clustering algorithms were needed—the hierarchy already exists.

At night, a local model rewrites dossiers whose source composition has changed. Each dossier has a fingerprint in its header: a list of sources and their modification times. If it matches the current one, the topic is not touched. On a normal night, only a few out of dozens of topics are rebuilt. Once a week—a full run, because incremental updates gradually shift the boundaries.

Search looks at the dossier index first and only delves into the graph for details. The index is lexical, based on word stems with prefix matching, without embeddings: it works even if Ollama is not running.

What I took from other works: the idea of community summaries from GraphRAG, incremental updates and two-level search from LightRAG, invalidation by event, not schedule, from Graphiti. The recursive abstraction tree from RAPTOR was not needed: the tree is already drawn by links.

Night

At 04:15, the night processing starts: morning brief, core revision (checking for duplicates and contradictions between topics), dossiers, optional cloud revisions, duplicate file deletion, memory measurement. During the day, all this would interfere with meetings because there's only one model and one machine.

Several night rules that emerged after incidents, not from theory:

  • A live meeting is more important than the night. If a call starts at seven in the morning, the night step hands over the model to the meeting and waits. Previously, core revision continued to share the model with live prompts during meetings, and recording was interrupted.

  • Night ends at night. The processing has a time limit, and all steps, including tail steps, adhere to it. Previously, deduplication and measurement went beyond the limit and woke up the model in the morning.

  • "Ok" only when the work is done. A night without a single graph doesn't turn green—just like a revision that ran in vain. A literal example from today: the Claude CLI was updated overnight, the binary changed underfoot, seven cloud revision topics failed with an exec error, and the night reported success because each topic caught an exception and wrote "failure" to a service file. Now, before the first topic, there's a probe claude --version; the broken CLI has its own return code, and the night status is honestly red.

  • A laptop with a closed lid sleeps, and this is not a malfunction: the system's monotonic clock stops, while the wall clock continues. The difference is recorded in the status as "slept," and a night where only late steps failed gets the status "slept," not "failed."

The Cloud Edits a Copy, Not the Graph

The local model retells accurately, but doesn't see connections: one decision cancels another, a deadline has passed, two nodes say different things. A large cloud model sees this. By default, the cloud is off. Flip the switch—and at night, Opus goes through the dossiers and cores again.

The first version of the rule "cloud edits the graph itself" cost me the notes of one meeting. The revision took a long time, a live meeting happened in parallel, the pipeline recorded it in the graph, and the rollback of the failed revision returned the "before" snapshot and deleted what was recorded. Since then, the cloud edits a sandbox: a clone of the graph snapshot where its CLI lives. Transferring back happens under a lock, conflicts are resolved in favor of live work, the cloud version goes into quarantine, deletions are not transferred at all, and executable zones like Obsidian plugins are never transferred. Transcripts, minutes, and the "Author's Edits" section are not touched by the cloud under any settings.

Two writers in one folder without a lock always means data loss, it's just a question of when.

Search: Blocks Instead of Files and Three Surprises

Graph search combines two signals: lexical (stemming, IDF, freshness) and semantic (bge-m3 via Ollama). Individually, neither is sufficient: lexical captures internal identifiers that a vector can't distinguish, semantic bridges the gap when the question is phrased with different words.

Three surprises emerged along the way.

First: one vector per file for the first 12,000 characters works for a node, but for a transcript, it reverses the result—decisions are made at the end of the meeting. On the work graph, 325 files were longer than the limit, and 63% of the content wasn't indexed at all. Now, the file is split by headings into blocks, each block carries its path "File → H1 → H2" into the embedder, because a block like "Well, let's do it this way" doesn't mean anything on its own.

Second: Ollama silently truncates the bge-m3 input to about 12,300 characters despite the stated 8192 tokens. Verified by binary search: a unique marker appended to the end doesn't change the vector.

Third: iCloud marks elements in its container with a "hidden" flag, and the standard walker with the "skip hidden" option silently skips them. On the work graph, "People," "Systems," "Meetings," and almost all documentation were hidden this way: the index saw 546 files out of 1172. Search no longer looks at the flag at all: service folders are filtered by name.

I measure quality with an end-to-end loop: search → synthesis on a closed set of questions with expected facts, generation temperature is zero. The block index and document role weight (raw data is muted, summaries are boosted) increased the proportion of facts included in the answer from 11 out of 14 to 14 out of 14 on the full index. There was also a negative result: the requirement "transfer abbreviations and codes verbatim" seemed like an improvement on one run and turned out to be a regression as soon as the temperature was fixed. The instruction pushed the model to quote instead of honestly saying "unknown." I reverted it.

Memory Hygiene

The graph as memory degrades quietly. An audit in late August found 626 broken links and seventeen person nodes that were actually diarization labels: "Interlocutor 3," "Speaker 2." Different people from different meetings were merged into one file with a hundred incoming links.

Rules after the audit: a diarization label is not a person and doesn't get a node; node names are compared by a key without punctuation, parentheses, and hyphens, so "Ivan (Ivanov)" and "Ivan Ivanov" are the same node; line breaks within a link from the model's response are merged during writing, otherwise the link is dead for Obsidian. At night, a script-doctor without a model checks the health of each graph: broken links, labels among people, orphans, duplicates. The morning brief shows a summary.

Two Meetings in One Minute

This is a separate chapter of suffering. The transcript name and the recording name are taken from the same timestamp. While the timestamp was minute-based, two meetings in one minute (daemon crash and restart, two recordings from a phone consecutively, reprocessing) silently overwrote each other or merged into one.

Now the timestamp includes seconds, recording files are opened in "create only" mode, and a collision is a visible error, not silent truncation. Next to each meeting is a small service file that remembers the exact timestamp and hashes of the transcript and minutes. When a meeting is renamed by topic, the file moves with it. This saved us from a scenario that three external reviewers independently found: if the transcript was renamed to a name already associated with an orphaned service file of a neighboring meeting, someone else's recording silently became ours.

If this sounds like a lot of work for a rare case, it is. But each such rarity happened on my machine.

Forget a Meeting

A privacy promise is worth little if a meeting cannot be removed. Audio is deleted automatically after two days, while everything else lives forever and in six places: the transcript and its derivatives, the meeting folder in the archive, the meeting node, a copy of the transcript in the documentation, history lines in cores, and links in dossiers and people nodes. A person who needs to remove one conversation shouldn't have to remember all six.

The "forget" script creates a plan: what to delete, what to rewrite. A history line referencing the forgotten meeting is removed entirely along with the fact derived from it. A link in connected text is replaced with a note, not leading to emptiness. By default, the script only shows the plan; deletion requires explicit consent, and edits to surviving nodes are backed up. And it honestly states what it can't reach: copies already uploaded to iCloud or Time Machine, and files held by other participants.

Today's audit added a seventh location: a copy of the audio in the import folder. Now that too is removed with the meeting.

Recordings Not Just from Mac

Two things have been added in the last week. The "External Recording" tab: phone voice recorder, someone else's call recording, Zoom export—drag and drop the file, and it goes through the same pipeline as a live meeting. A copy lives for two days and is deleted along with the audio source in the archive; text sources remain. A failed file is not deleted or re-processed every two minutes but waits for a "Retry" button.

And an iPhone companion that listens immediately: open the app, recording is already in progress. If opened during a call, the microphone is busy with the call, and the app honestly waits: as soon as the call ends, it will start recording automatically if it's still open. A minimized app won't wake up on its own, but if you return within half an hour, recording will start upon return. No one can record the call itself on an iPhone: this is a platform feature, not an app weakness. Calls are recorded by the Mac.

Second Heads

About the process without which none of this would hold together. Every code change before merging is read by external models: GLM and DeepSeek via API, sometimes Codex. Not as a "second opinion for the sake of it," but as an acceptance team with a rule: as long as a round brings Critical errors, we continue to the next round; the first round without Critical errors closes the topic.

This is long (a round takes 10–15 minutes) and constantly unpleasant. Today, two heads independently found the same race condition in my own fix: I moved file copying to the background to avoid freezing the interface, and the scanner started picking up incompletely written files. It was fixed not with a patch, but with the very template already present in the project: a copy under a hidden name and a single atomic rename. Without the second head, this would have gone into release.
