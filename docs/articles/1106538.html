By my rough estimates, a similar task can take about an hour to an hour and a half instead of half a workday. Moreover, part of the agent's work is done in parallel with my other tasks.

Why You Can't Just Ask an Agent to Write Tests

It might seem that working with an AI agent is quite simple: get a task from development, understand the requirements, describe them to the agent, ask it to write autotests, and run them. If the tests are green and the code looks architecturally sound, the task can be considered complete.

In practice, it's a bit more complicated.

AI agents are indeed quite good at writing code now. They can study an existing framework, understand the architecture, find similar tests, and implement new scenarios based on existing patterns. But they might test something completely different from what we expect.

Let me give you an example from my own experience. My project has a feature for publishing documentation structure to a Git repository. If a section is removed from the structure during a re-publication, the corresponding file should also be deleted from the repository.

The agent wrote the test test_update_structure_removes_orphan_doc_file. The scenario seemed logical enough:

  1. Publish the structure with two sections: overview and setup.

  2. Re-publish the structure, but this time without setup.

  3. Clone the Git repository.

  4. Verify that the setup file no longer exists.

This looks correct: we're not just checking the API response, but the actual state of the Git repository after the operation. However, the agent missed an important detail: before deleting, it never checked if the setup file actually existed in Git. The document's existence was confirmed via the REST method get_repowiki_docs(), but this method might return document metadata without directly accessing the Git repository's content.

It turns out that if, due to an error during the first publication, the setup file never appeared in Git, the test could still pass successfully. After all, the file was indeed absent after the re-publication. But in this case, the business rule for deletion was not checked at all. It means the test checked the final state of the system but did not confirm the initial state. Without this, it's impossible to reliably verify the transition from the state "file exists" to the state "file deleted".

Interestingly, the developer agent didn't even find this problem during its self-check. It tries to assess if the test can detect an error but limits itself to analyzing its logic without performing experimental checks. The problem was discovered by another AI agent — the reviewer. After correction, the test gained an additional step with repowiki_repo_clone() as clone_before. Now, before re-publishing, it checks if the file physically exists in the Git repository. Only then is the deletion performed and the final state verified.

Situations like these clearly show why it's not enough to simply delegate test writing to an agent. Clear requirements, acceptance criteria, and a separate mechanism for verifying the result are needed. I gradually arrived at this approach when I started using Specification-Driven Development (SDD) and OpenSpec.

Instead of immediately sending an agent to write code, I first assign a separate agent to research the task, prepare a specification, and create an implementation plan. Then, I review them myself, and only after that does test development begin. Writing tests is just one of the stages. The entire process, from task research to result verification, is divided among several specialized agents.

How the Multi-Agent Process Works

In practice, it all starts like this: I open Claude Code and give the main agent the task number from Jira. I don't need to run each agent myself, describe the sequence of actions, or manually transfer results between them. The main agent — the orchestrator — is responsible for this.

How does it know which agent to run and what actions to perform? The repository contains a file named CLAUDE.md, which describes the operating rules, available specialized agents, and their areas of responsibility.

Currently, four main agents are involved in my process. To make it clearer how the orchestrator distributes work, here's a shortened configuration snippet from CLAUDE.md:

The presence of opsx:archive for the reviewer doesn't mean automatic archiving after their verdict. The orchestrator first presents the conclusion to me and requests a decision on further actions.

From Task to Specification

Suppose a developer gives me a task to fix a defect in the API. I send its number to the orchestrator and ask it to prepare automated coverage.

The first to get involved is the test-planner. It researches the task, studies existing tests, the framework's architecture, and available documentation. If necessary, it consults Jira and other context sources. Its goal is not to write code but to understand what behavior needs to be tested and how best to integrate new tests into the existing framework. To do this, the planner uses OpenSpec and creates a separate change — a set of artifacts describing the upcoming modifications.

The main files I work with are:

  • proposal.md — why the changes are needed, what problem they solve, and what they affect.

  • design.md — the technical approach to implementation, decisions made, and constraints.

  • task.md — specific implementation steps that the developer agent will follow.

After completion, the change also stores verification results and the reviewer's conclusion. For example, here's the structure of one of the archived tasks:

qa-report.md contains the results of QA checks, and review.md contains the implementation conclusion. Thus, the repository stores not only the initial plan but also information on how the result was evaluated.

After preparation, the planner validates the change using openspec validate strict <slug>. However, even successful specification validation doesn't mean the plan is automatically accepted. This is where I come in: I study the proposed scenarios, check if the agent understood the task correctly, if there are any missed cases, and if the solution aligns with the test project's architecture. If I have questions about business logic, I clarify them with the developers. If I see shortcomings in the plan, I send it back for revision. Only after approval does implementation begin.

From Specification to Autotests

The next participant in the process is test-qa-writer. It receives the prepared OpenSpec change and implements the tests, focusing on task.md, requirements, and existing framework patterns.

The important thing here is that the agent doesn't have to re-interpret the original Jira task every time. It already has an approved plan, technical constraints, and criteria for evaluating the result. As it works, the agent marks completed items in task.md and then performs a self-check of the implementation. However, as the example in the previous section showed, the implementer's self-check is not enough. An agent might miss its own error even if it carefully analyzes the written code. Therefore, the next stage is a separate review.

Review and Decision on Further Actions

After implementation, the orchestrator passes the result to the test-reviewer agent. Its task is to check how well the written tests match the specification, whether architectural agreements have been followed, and if the checks can indeed detect the declared defects. The reviewer analyzes the code and OpenSpec artifacts, formulates remarks, and issues a conclusion. Importantly, they do not execute the tests themselves: their review is based on analyzing the implementation and requirements. There's an interesting nuance here: the developer and the reviewer might use the same language model. The separation of roles doesn't make the review completely independent, but it allows evaluating the result from a different perspective and with different criteria. It was this reviewer who discovered the problem with checking the setup file deletion, which I mentioned earlier. After the review is complete, the orchestrator returns to me with the conclusion and asks me to decide on further actions. If the remarks are justified, the implementation is sent back for revision. If there are contentious points, I study them further and clarify requirements if necessary. If I'm satisfied with the result, I authorize proceeding to the next stages.

This means the reviewer agent doesn't make the final decision for me. It provides information based on which I can make a decision. For me, this is one of the key features of the process: I've delegated a significant part of the engineering work to the agents, but I haven't transferred the responsibility for the final quality to them.

Checks, Documentation, and Merge Request

After the implementation is approved, the work isn't over. It's necessary to ensure that the tests not only comply with the specification but also behave correctly during execution. For this, actual test runs and additional checks for their sensitivity to errors are provided. For example, one can intentionally change an expected value in an assertion and check if the test actually detects the discrepancy. This is not full-blown mutation testing of the service implementation but an additional way to check how meaningful the written assertions are. I will discuss this mechanism in detail separately, as it has its limitations.

After the necessary checks and my confirmation, the work with the OpenSpec change can be completed: the specification is archived, and the results are passed to the next agent. The docs-writer is responsible for updating documentation. It receives information about the changes made and updates the affected project documentation pages. The final step is preparing a Merge Request with the implemented autotests.

As a result, the task leaves behind not only code but also a history of decisions made: why changes were needed, what scenarios were planned, what was implemented, and what remarks arose during the review. Moreover, the described sequence is not a rigid pipeline. For small tasks, individual stages might be redundant, so the process can be simplified. The main thing is not to lose track of requirements and control over the result.

What Remains for Me

The diagram might suggest that agents now perform most of the work. In a sense, this is true, at least when it comes to writing code. But my role isn't just to provide a task number and wait for a ready Merge Request. I still need to understand the requirements, assess risks, determine coverage adequacy, and analyze the results. I simply spend more time on design and verification now, rather than on the direct implementation of each test. Additionally, while the agents are working on the code, I can focus on other tasks: manual, non-functional testing, defect analysis. This change, in particular, has been more significant for me than simple time savings. But for now, all of the above sounds like a rather abstract scheme. Practice: How Agents Covered CRUD Tags

So far, I've mainly discussed the process's structure. But drawing a diagram with several agents is one thing, and seeing how it works on a real task is another.

As an example, I'll take a task to expand the REST API for working with Git tags. This involved adding tag creation and deletion, as well as extending the response of the existing tag list retrieval method. At the time the task was assigned, I already had three autotests for GET /tags. They checked for the presence of tags in the list, an empty list, and requests to non-existent repositories. However, the checks were limited to the name field. For POST /tags and DELETE /tags, there was no automated coverage at all. The task seemed quite standard: study the API contract, extend the client, prepare fixtures, and write positive and negative scenarios. But it was precisely here that the advantages and limitations of my approach became apparent.

What the Planner Proposed

I handed the task over to the orchestrator, which then launched tests-planner. The agent researched the existing coverage, studied the API contract, and prepared the OpenSpec change test-may-001-tags-crud. The first thing I liked about the planning result was that the agent didn't just list the methods to be covered. It divided the work into several areas: extending response models, adding client methods, preparing test data, positive scenarios, negative checks, and verifying the actual state of the Git repository.

For instance, for tag deletion, it wasn't enough to check that the API returned 204 No Content. The planner included a check for the tag's absence not only in the subsequent GET /tags response but also directly in Git via git ls-remote. This is an important detail. If the API uses caching or returns outdated data, checking only through another REST method might give a false impression of the repository's state.

## What Changes## GET /tags — retrieving the list of tagsExpand existing GET /tags coverage:- Verify the full set of response fields:`name`, `commit`, `message`, `author`, `date`. - For an annotated tag, verify the tag author's data (tagger). - For a lightweight tag, verify the use of the target commit's author. - Ensure `commit` contains the target commit's SHA, not the tag object's SHA. - Verify the presence of created tags in the list.### POST /tags — creating a tagAdd tests for creating Git tags:- 201 — successful creation of lightweight and annotated tags. - 409 — attempting to create a tag with an existing name. - 400 — non-existent target revision. - 400 — invalid input data and exceeding limits. - 404 — non-existent repository or a repository of another project. - 401 — request without authorization.### DELETE /tags — deleting a tagAdd tests for deleting Git tags:- 204 — successful deletion of an existing tag. - Verify the absence of the deleted tag in GET /tags and in Git via `git ls-remote`. - 404 — deleting a non-existent tag. - 404 — attempting to delete the same tag again. - 404 — non-existent repository. - 400 — invalid tag name.### Environment LimitationsOn the current dev-stand, it's impossible to reliably check:- 403 — Git hook rejection of the operation. - 409 — concurrent update of a Git reference. - 403 — operation forbidden for a role below Developer.These scenarios should be documented as coverage limitations, without substituting full checks with imitations.

In task.md, the agent broke down the implementation into specific steps. For example, creating a tag required checking the creation of lightweight and annotated tags, reusing names, non-existent target revisions, field length limits, and handling operations without authorization.

For deletion, it included successful operations, re-deletion, non-existent tags, invalid input data, and access restrictions. The planner also separately noted scenarios that are difficult to reproduce on the available test environment: Git hook rejection, concurrent reference updates, and certain permission restrictions. This is also part of planning. It's not enough to just list all possible checks; one needs to understand which ones can actually be automated in the existing environment.

From Plan to Implementation

After the specification was approved, the orchestrator handed the work over to test-qa-writer. The agent extended the Tag model, added tag creation and deletion methods to the REST client, prepared the necessary fixtures, and implemented the test scenarios.

As a result, the coverage was distributed across three modules:

  • test_content_tags.py — retrieving the list of tags and verifying additional fields.

  • test_content_create_tag.py — creating tags, validation, and negative scenarios.

  • test_content_delete_tag.py — deleting tags and verifying the operation result.

In the final version, pytest collected 30 test scenarios, including parameterization: four for GET, eighteen for POST, and eight for DELETE. Part of the GET coverage existed before the work began — the agent extended it rather than creating it from scratch.

One of the illustrative scenarios is the successful deletion of a Git tag. Here, the agent didn't just check the HTTP status 204 No Content. First, the test creates a tag via API, then deletes it, and verifies the result in two ways: via GET /tags and directly via Git.
