AI Agent Didn't See My Code: Worktree, Task State, and Access Control in VECTA

Project files were on disk, but the AI agent received an empty working copy. The cause was found in Git: the sources hadn't been committed yet, and worktree was created from HEAD. Using VECTA as an example, I'll break down what needs to be built around a coding agent: snapshots of current files, restoring events after disconnections, access rights, and result verification. I'll explain how to manage a task from another device, why worktree doesn't replace a sandbox, and what not to promise regarding cost limits. Read on.

During one of VECTA's checks, the agent received an almost empty project. Yet, the files were present in the source folder. The user could see them, open them in the editor, and expected the agent to start working with them.

The reason turned out to be more mundane than model issues: the repository had an empty initial commit, and the files hadn't made it into Git yet. We were creating the task's working copy from HEAD. From Git's perspective, everything happened correctly. From the user's perspective, the tool lost the project.

This case clearly shows what needs to be built around a coding agent. Simply launching a CLI and displaying the output in a chat is not enough. We need to define which version of the project the agent receives, who is allowed to manage it, what the human will see after reconnecting, and relative to what they will view the diff.

My name is Andrey, I develop VECTA at Aterna and use AI agents in development itself. VECTA is in closed beta. It's a workspace for projects and tasks: the agent performs work on a connected computer, and a human manages the task via desktop or browser, including from a phone. Below, I'll discuss several solutions and limitations of this architecture. I don't have comparative performance benchmarks with other products yet.

Why a Second Terminal Isn't Enough

In many cases, it is sufficient. tmux, SSH, and separate worktrees allow you to maintain multiple agent sessions without an additional product. If you work on one machine, remember the purpose of each session and analyze changes yourself; such a configuration is perfectly reasonable.

My interest begins in a different scenario. One project is on my home computer, the second on my work laptop, the third on a machine in the office. They have different tools and capabilities. An agent on one of the machines requests permission when I'm already offline. Later, a colleague connects to the project: they need requirements, previous decisions, and the result, but they will be working on their own task.

Here, it's useful to link the discussion, execution, and verification to a persistent entity called a "task." Then, from my phone, I open the specific solution required of me. From my laptop, I return to the diff of the same task. I grant my colleague access to the working context, not a collection of forwarded messages.

The approach itself is not new. Habr has an analysis of the Orca and Pi Agent combination and experience building a process on top of Vibe Kanban. Orca documents mobile management and multi-host operation. Therefore, having a phone, browser, or multiple agents is not an argument for VECTA in itself. For me, the subject of work here is more specific: to make the path from a task in an existing project to a verifiable result on a chosen machine understandable.

Where the Work is Performed

The system has three main layers.

Layer

What it does

Common desktop and web interface

Displays projects, tasks, discussions, permission requests, and results

API

Verifies access, stores server state and events, connects clients to connected machines

Runner on the selected computer

Prepares the working copy, launches the connected agent, and transmits execution events

The desktop is built on Electron, with a shared interface with the web client. The Runner is written in TypeScript, and the API in FastAPI. The browser client does not run a local CLI on the phone. It communicates with the management layer, and execution remains on the selected machine.

This way, a weak laptop or phone can be used to manage work performed on another computer. However, computational resources are not moved anywhere. For local execution, the machine must be turned on, the runner must be running, and the network must be accessible. A local model still requires adequate memory and a suitable accelerator.

A remote desktop solves part of this problem differently. It doesn't have the universal limitation of "only two devices"; multi-user solutions exist. And VECTA also depends on the network. The difference is that the unit of management becomes the task with its history and actions, not the computer screen. I don't have comparable traffic and latency measurements yet.

Worktree Copies a Commit, While a Human Works with a Folder

Let's return to the empty project. The problem can be reproduced without VECTA and without a model. In a separate temporary folder, we'll create a repository with an empty initial commit, add a file, but not commit it:

demo_dir="$(mktemp -d)"git init -q "$demo_dir/source"git -C "$demo_dir/source" -c user.name=Demo 
  -c user.email=demo@example.invalid commit -q --allow-empty -m initialprintf 'export const answer = 42;
' > "$demo_dir/source/app.js"git -C "$demo_dir/source" worktree add -q -b agent "$demo_dir/task" HEADtest -f "$demo_dir/source/app.js" && echo 'source: app.js exists'test ! -f "$demo_dir/task/app.js" && echo 'worktree: app.js missing'

This is expected Git behavior. However, a tool connected to an existing project must clearly define its contract: does it work with the last commit or with the current folder content?

For a new, isolated task in VECTA, a snapshot of the current permissible files is now prepared. This includes regular tracked files with their working content and non-ignored untracked files. The original working files, staging area, and user's branch are preserved.

This immediately introduces a second problem: what to show in the diff. Suppose, before launching the agent, the user has already modified the authorization form. If the task result is compared with the previous HEAD, these changes will appear as the agent's work. Therefore, the prepared state becomes a separate baseline for the task. Subsequent changes are compared against it.

In its implementation, this uses standard Git mechanisms: a separate worktree, its index, tree objects, and a service reference called baseline. VECTA does not implement its own version control system. However, the preparation does add Git objects and service references to the repository, so the statement "changes nothing in Git at all" would also be incorrect.

When resuming an existing task, the snapshot is not recreated. Otherwise, a more recent source folder could overwrite work already done by the agent.

Why Not Just Copy Everything?

The source folder might contain .env files, keys, dependencies, symbolic links, and custom Git filters. Preparing a working copy itself becomes an operation that needs to be restricted.

Currently, it has exceptions for known sensitive paths and files, file type and link checks, and size limits. Custom Git filters are not supported for such snapshots: they can execute commands. If a change in source files is detected during preparation, the operation fails instead of producing a mixed state.

This is not a universal secret scanner. If a token is written in a regular config.ts file, the filename alone won't indicate that it shouldn't be transmitted. Such a mechanism also doesn't replace an atomic file system snapshot.

The approach has a compatibility cost: some projects will require different environment preparation. For example, dependencies excluded from copying won't appear automatically in the new working folder. The repository needs an initial commit; the absence of commits and an empty initial commit are different cases here.

Closed Tab and Stopped Agent: Different Events

Managing from a phone requires more than just a narrow interface. Mobile networks drop, tabs go into the background, and the user returns minutes later. During this time, the agent might have finished or stopped to request permission.

If the client only receives new events after reconnecting, an unpleasant situation can occur: the last event has already happened, there will be no new ones, and the screen will forever show "working."

In VECTA, task events have a sequence. Upon reconnection, the client sends cursors, the API selects stored events after them, and returns them in sequence order. Access to the workspace and task visibility are re-verified. The identifier sent by the client is not considered proof of rights.

The simplified logic looks like this; this is an explanation of the algorithm, not a ready-to-use public API client:

client reports: for task T, the last event has sequence = Nserver verifies access to Tserver selects stored events for T with sequence > Nclient applies events, skipping already processed ones

The catch-up delivery is limited by the number of tasks, events, data volume, and sending time. This is a safeguard against an infinite response to a slow client, not a promise to restore an arbitrarily long history with a single request. Interface reconnection also does not mean automatic process restoration after a computer shutdown.

A separate contract is needed for the stop button. Sending a signal to the process and ensuring it has completed are different actions. In the runner, stopping waits for confirmation of completion; if it's not received, an error is returned. Resources cannot be freed and changes accepted as if the process had already disappeared.

Worktree is Not a Sandbox

Separate working folders help two tasks avoid directly editing the same files. They do not isolate the operating system. Processes can compete for memory, ports, external databases, and other shared resources. File-compatible changes might be semantically incompatible.

In VECTA, access is considered at several levels:

Level

What boundary it sets

Workspace participant

What data a person sees and what actions they can perform

Connected machine

To which assigned tasks the runner can send events

Agent process and its tools

With what environment and permissions the work is executed

The server has roles of owner, operator, and observer. Checks are performed in the API, not just by hiding buttons. Rights to control the computer are checked separately. Therefore, inviting a colleague to the workspace should not be described as an unconditional transfer of control over all connected machines.

Before launching an agent process, internal VECTA variables are excluded from the environment, except for explicitly passed allowed task tool parameters. This protects VECTA's own credentials in this channel, not a promise to remove any third-party secrets from the environment, files, or provider settings.

Real isolation of the file system, processes, and network depends on the adapter, provider, and OS. A confirmation dialog does not turn into a sandbox just because the user clicked "allow." Similarly, agent text cannot be considered a trusted command or permission to act.

General Context Does Not Mean Infinite Model Memory

The project saves tasks, discussions, and documents. A colleague with appropriate access can review the history and manage a separate task. This is useful when you need to transfer not only code but also the reasoning behind decisions: what has already been tried, what changes were rejected, what remains to be checked.

However, the history in the product and the context of a specific model call differ. Models have window limitations, and adapters have different session continuation mechanisms. Switching agents does not mean transferring its hidden state or full internal context to another model.

Documentation of an existing project and instructions help the agent orient itself. The Marketplace skills allow reusing work instructions and pluggable capabilities. But a skill does not gain the right to bypass task permissions. Connecting an MCP server or another executable tool expands the trust surface; a useful description does not automatically make such a tool safe.

The choice of model also does not equalize connections. The ability to get text from a compatible API, access to file tools, running a terminal, and browser automation are different capabilities. Support for a local or Russian provider needs to be checked for a specific connection and scenario, not by the presence of a logo in a list.

"Done" is Verified Outside the Agent's Response

Let's take a typical task in an existing application: after changing the authorization form, the submit button stopped fitting on the phone. The prompt "fix the responsiveness" is too vague. It's more useful to fix the screen width, the expected scenario, the affected files, and constraints, for example, not changing the authorization API.

After the agent's work, you need at least a diff, test results, and a browser preview of the scenario. In VECTA, these tools are located next to the task. But the built-in browser itself doesn't prove the application's correctness, and the model's message "tests passed" doesn't replace the actual result of the run.

There's also the technical aspect of the browser: a project preview should not give the page arbitrary access to all local machine services. Therefore, permission to open a specific preview cannot be substituted for general permission to the entire loopback. In the project, this class of errors is specifically checked by a real Chromium and test HTTP services.

Acceptance remains an independent action. Even if multiple agents work in parallel, a human or a clearly configured verification process is needed to decide whether the changes meet the task requirements. The number of sessions is not a metric of product readiness.

Task Budget Does Not Equal Guaranteed Provider Bill

In the interface, we want to offer a simple setting: limit the time, tokens, or cost of a task. At the integration level, this becomes inconsistent.

In the current runner, a monetary limit for local CLI tasks is allowed for Claude Code, and a token limit for Claude Code and Codex. This reflects the available reports from these adapters. For unsupported accounting types, the runner returns an error, suggesting a time limit or a different agent. Managed modes have a separate quota mechanism; it should not be mixed with this list.

There's also a reporting delay. If the provider reports consumption after part of the work is done, a local pause cannot retroactively cancel already spent tokens. Therefore, such limits should not be presented as a universal financial safeguard with a cent-by-cent guarantee. Unknown cost should remain unknown, not turn into zero.

The practical result is more modest and useful: consumption is tied to the task, supported limits are available, and a long series of improvements is not lost outside the workflow.

Model and Execution Location are Chosen Separately

VECTA has local execution with connected agents, a managed VECTA Auto model, and a separate VECTA Cloud mode. The names can be easily confused, so it's more important to describe where the files are located and where the tools are executed.

In Auto, the model is provided through an approved VECTA account, and work with the local project is performed on the selected computer. This mode does not require separately installing coding CLI or adding your own provider key.

Cloud allows working through a browser without a constantly powered-on personal computer, but in its current version, its scope is limited: dialogues and creation of text files or code. This is not an automatic migration of a local repository into a full-fledged cloud development environment.

Local execution also does not mean that data never leaves the machine. The API handles synchronization of tasks and events, and an external model provider receives data passed to it by the agent. Using a local model changes the model channel but does not, in itself, turn the entire system into a completely autonomous local installation.

What Can Be Tested Now, and What I Haven't Measured

For preparing a new working copy in the repository, there are separate regression tests on actual temporary Git repositories: untracked files after an empty commit, saving the staging area, excluding protected files, reopening a task, Git hooks, filters, and modifying source code during preparation. This is more specific than checking if a function returned the expected object.

However, the existence of these tests does not prove that all combinations of OS, models, and projects work identically. I also haven't measured the acceleration relative to Orca, Cursor, or the SSH with tmux combination, nor have I conducted a load test for twenty people collaborating. These claims cannot be derived from the presence of corresponding screens in the interface.

Currently, my task in VECTA is to enable a person to continue full development of existing projects from different devices and maintain control: over the initial state of files, permissions, costs, and acceptance of results. This approach needs to be tested on completed tasks, including failed runs and recovery after failures.
