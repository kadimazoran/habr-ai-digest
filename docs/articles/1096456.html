Hello! This is Danil, a TypeScript developer on the Platform V DataSpace team at SberTech.
DataSpace is a platform module for visual (low-code) business application development and data management. It provides a GraphQL API for working with databases. We've been developing the product for several years, but now, due to the rapid development of AI and MCP, a predictable task has emerged: connecting this API to AI agents via the Model Context Protocol (MCP).

MCP is needed so that an AI client can discover tools, understand their input parameters, and call external systems through a standard protocol. At first glance, GraphQL is well-suited to serve as a source of MCP tools: the schema already describes types, input arguments, and the form of the result, but it doesn't answer the main question: 'what part of the API and with what level of freedom should be exposed to the agent?'.

In DataSpace, the scenario turned out to be as follows:

  • there is a GraphQL API on top of the data model;

  • there is an AI agent that needs to perform application actions;

  • an MCP adapter is needed between them;

  • the backend team wants to maintain control over the contract, types, and security.

The question turned out not to be whether GraphQL can be connected to MCP. It can. What's more interesting is: what form should the MCP adapter for a GraphQL API take?

In this article, I will discuss several variants of such adapters and our choice: generating MCP tools from pre-prepared GraphQL operations.

What kinds of MCP adapters for GraphQL exist?

It's possible to adapt GraphQL for MCP in several ways. The main difference is the level of freedom the agent receives.

A Tool for Arbitrary GraphQL Queries

Example implementation: Microsoft Fabric API.

The most flexible option is to create an MCP tool that accepts a GraphQL query and variables:

execute_graphql( 
  query: string, 
  variables?: Record<string, unknown>
)

The agent or MCP client forms the query itself, selects fields, and passes variables. Along with this flexibility, the model takes responsibility for the correctness of the GraphQL query: field selection, naming, rules for working with null, and variables. The selection set remains dynamic, the API surface is broad, and the backend team analyzes the executed queries.

This approach gives the agent maximum freedom and is well-suited for research, local development, prototyping, exploring an unfamiliar schema, or creating developer tools where it's important to quickly start working with an arbitrary GraphQL API. One universal tool is enough to get started, so a prototype can be assembled quickly.

Tools from Schema and Root Fields

Example implementation: parob/graphql-mcp.

In this variant, MCP tools are created from the root fields of the Query and Mutation types. The agent receives a ready-made set of tools with names and arguments close to the root fields.

This format is simpler than the tool for arbitrary queries and allows quickly exposing a significant part of the API via MCP. The GraphQL schema already contains enough information for automatic tool construction, making the approach convenient in the early stages of development. However, the set of tools follows the GraphQL schema. Often, it is broader and more detailed than the application contract we want to provide to the AI agent.

Tools from Fixed GraphQL Operations

Example implementations: Apollo MCP Server, WunderGraph Cosmo MCP Gateway, GraphQL Hive MCP plugin.

Here, an MCP tool corresponds to a pre-written GraphQL operation. The agent selects the tool and fills in the variables. The GraphQL operation text is defined in advance by the developer.

Structurally, a GraphQL operation is close to an MCP tool: it has a name, input variables, a selection set, and a result form. The developer can read it, review it, and check it against the schema.

Operations can be stored in a repository, discussed in pull requests, checked against the GraphQL schema, and used as an allowlist for the API surface available to the agent. This gives us a predictable selection set, clear auditing, and full control by the backend team over the API contract.

The set of operations becomes a separate artifact that the team can maintain along with the code. Therefore, the approach is well-suited for production scenarios, enterprise APIs, and sensitive data. It also fits well with dynamic GraphQL gateways: Apollo, WunderGraph, and Hive. They collect available operations at startup and immediately provide an MCP API for them.

Code Generation from GraphQL Operations

Example implementations: our generator, labd/graphql-codegen-mcp-tools-poc.

This is an evolution of the operation-derived approach. GraphQL operations remain the source of truth. Based on them, TypeScript types, Zod schemas, MCP tool declarations, and helper code for tool registration are generated.

Lab Digital is developing a similar idea in graphql-codegen-mcp-tools: GraphQL operations are marked with MCP directives, pass through GraphQL Code Generator, and are transformed into tool descriptions.

Code generation is particularly useful when the MCP server becomes part of the product. In the generated code, you can see which tools have appeared or disappeared, which fields have become mandatory, how enum values have changed, how the result form has changed, and what tool descriptions the model will see.

All these changes can be reviewed locally and in CI before the agent calls the tool. However, the approach also has associated costs: the project gains an additional step – code generation, and you'll need to maintain the generator configuration along with the rest of the code.

Code generation provides type safety, reduces manual work, adds data validation via Zod, and allows for diff generation.

We chose this particular option – fixed GraphQL operations and code generation in TypeScript/Zod – because we needed an adapter where GraphQL developers continue to describe and validate the contract using familiar GraphQL operations, and the agent receives a limited set of MCP tools instead of the entire GraphQL API.

Overall Workflow

The generator takes the following as input:

  • GraphQL schema;

  • a set of pre-written operations;

  • configuration;

  • a list of plugins;

  • tool descriptions and annotations, custom scalar settings;

  • TypeScript and Zod generation settings.

The code generator invokes a set of plugins and creates dataspace-graphql.ts: TypeScript types, GraphQL documents, Zod schemas for input and output data, and MCP tool descriptions. The template MCP server imports this file, registers the tools in McpServer, and uses the default handler, which calls the appropriate GraphQL operation in DataSpace and returns structuredContent.

During startup, the server works with the generated TypeScript module with a known set of tools. Work with the schema, operations, and schema sources happens before the MCP server starts.

Why all in TypeScript? We chose it as a simple and convenient language for DataSpace consumers and for our low-code platform as a whole, of which DataSpace is a part, along with other solutions for automation, process orchestration, data model design, and report generation. The generated TS module is placed alongside the template MCP server code, and custom tools can be added there as well.

Let's see how this looks with a simple operation: from a single GraphQL query, we get TypeScript types, Zod schemas, and an MCP tool.

Demo: Searching Clinics by City

The DataSpace demo model describes a medical domain: clinics, doctors, patients, schedules, appointments, and addresses. For this example, we'll limit ourselves to searching for clinics by city.

The GraphQL operation itself looks like this:

query searchClinicByCity($cityName: String!) { 
  searchClinic( 
    cond: """ 
    it.address.city.$upper $like ${cityName}.$upper + '%' 
    """ 
  ) @strExpr(string: $cityName) { 
    elems { 
      id 
      name 
      address { 
        city 
        street 
      } 
    } 
  } 
}

The operation developer pre-defines the DataSpace cond, the @strExpr directive, and the set of clinic fields. The agent passes one parameter – cityName.

Example response from the GraphQL API:

For each GraphQL operation, the code generator creates Zod schemas for variables and responses:

  cityName: z.string(), 
}).strict(); 
export const SearchClinicByCityQuerySchema = z.object({ 
  searchClinic: z.object({ 
    elems: z.array(z.object({ 
      id: z.string(), 
      name: z.string().nullable(), 
      address: z.object({ 
        city: z.string().nullable(), 
        street: z.string().nullable() 
      }) 
    })) 
  }) 
});

Next, the MCP tool description is generated:

export const SearchClinicByCityToolDefinition = { 
  name: 'SearchClinicByCity', 
  document: SearchClinicByCityDocument, 
  inputSchemaObject: SearchClinicByCityQueryVariablesSchema, 
  outputSchemaObject: SearchClinicByCityQuerySchema, 
  config: { 
    title: 'SearchClinicByCity', 
    description: 'Search clinics by city name', 
    annotations: { 
      title: 'SearchClinicByCity', 
      readOnlyHint: true, 
      destructiveHint: false, 
    }, 
    inputSchema: SearchClinicByCityQueryVariablesSchema.shape, 
    outputSchema: SearchClinicByCityQuerySchema.shape, 
  } 
} satisfies ToolDefinition 
 
export const allMcpTools: ToolDefinition[] = [ 
  SearchClinicByCityToolDefinition, 
  // and other tools 
];

The server imports the generated module and registers the tools in McpServer:

const mcpServer = new McpServer(); 
 
for (const tool of allMcpTools) { 
  mcpServer.registerTool(tool.name, tool.config, defaultMcpHandler(tool)); 
}

After startup, we open @modelcontextprotocol/inspector and see the GraphQL operation as a regular MCP tool.

Calling SearchClinicByCity with the parameter cityName = "Moscow" returns a structured response. A text fallback is necessary for MCP clients that do not support structuredContent. The inspector uses outputSchema to validate the MCP server's response.

Not many agents these days pass outputSchema into the LLM context.

From this simple example, the main point is clear: the agent doesn't write GraphQL. It selects a tool and fills in variables, while the selection set, DataSpace condition, types, and result form are already fixed in the operation.

Where mistakes are easy to make: null, omitted, and default

We decided to use the MCP contract (JSON Schema) as an early check of the request form, rather than as a complete copy of GraphQL input coercion. We allow conscious simplification of certain GraphQL flexibilities. The GraphQL API remains the final source of truth, and JSON Schema and Zod schemas reflect it for the agents.

Let's take a small example:

input ClinicSearchInput { 
  cityName: String! 
  district: String 
  limit: Int! = 10 
}

There's a slight nuance that null and omitted are different things. The default value applies only to omitted, but not to an explicitly sent null. This behavior is preserved in the MCP generator.

This leads to the following rules:

  • required in JSON Schema is only set for Non-Null fields without a default value;

  • GraphQL's nullable type is reflected as the ability to pass null;

  • omitted does not need to be replaced with null;

  • we decided not to transfer GraphQL's default values to Zod via .default(...), so that the MCP layer does not become a second implementation of GraphQL input coercion.

A practical rule for the agent: do not send null instead of an unknown or missing value – use it only if there is an explicit need to set the value to null.

In GraphQL, for the type [[Int]], you can pass the value 1, and input coercion will convert it to [[1]]. For simplicity, we decided to abandon this semantics in JSON Schema. We specify an explicit list with full nesting.

GraphQL input objects do not accept fields that are not in the type, and the MCP layer can catch this before calling the GraphQL API. In JSON Schema, additionalProperties: false is set; for Zod, this is .strict().

GraphQL enums map well to JSON string enums and z.enum(...):

enum SortDirection { 
  ASC 
  DESC 
} 
const SortDirectionSchema = z.enum(['ASC', 'DESC']);

Basic scalars map as expected. Custom scalars are more complex. Their business semantics cannot be reliably inferred from the name. DateTime, Decimal, JSON, UUID, and internal domain scalars require explicit configuration or a conservative fallback to number, string, or boolean.

It's also best to be cautious with recursive GraphQL input objects. JSON Schema can describe recursion through $defs and $ref, but it's better to check support in the specific MCP client and validator.

In addition to the schema and operations, it's useful to provide the generator with descriptions that are understandable to the agent:

  • for the operation and tool, so the agent can better choose the right tool;

  • for input fields, especially if the field name doesn't reveal the business meaning;

  • for enums and their values;

  • for tool annotations;

The less the agent has to infer at the API contract level, the higher the chance it will be useful at the business task level.

When a Tool Should Be Higher Level Than a GraphQL Operation

Not every good MCP tool should be a direct mapping of a single GraphQL operation.

Suppose there's a task: find available slots for a doctor. In the data model, the schedule might be stored as busy intervals. For a human, it's clear: take the work schedule, subtract the busy intervals, filter out past times, and return the free windows.

But for an agent, this application logic might be too much. It could make mistakes with interval boundaries, mishandle time zones, return a slot over an existing booking, or confuse appointment durations. In such cases, it's more useful to create your own TypeScript handler on top of a GraphQL operation. GraphQL still handles data retrieval, while the TypeScript layer transforms it into a result more convenient for the agent.

const doctorFreeSlotResponseSchema = z.object({ 
  elems: z.array(z.object({ 
    doctorScheduleId: z.string(), 
    beginDate: z.string(), 
    endDate: z.string() 
  })) 
}) 
server.registerTool( 
  'SearchDoctorFreeSlotsInPeriod', 
  { 
    title: 'SearchDoctorFreeSlotsInPeriod', 
    description: 'Returns hourly free slots for a doctor schedule in the requested period', 
    inputSchema: SearchDoctorScheduleByDoctorIdAndPeriodQueryVariablesSchema.shape, 
    outputSchema: doctorFreeSlotResponseSchema.shape, 
    annotations: {destructiveHint: false, readOnlyHint: true} 
  }, 
  async (args, extra) => { 
    const response = await execute(SearchDoctorScheduleByDoctorIdAndPeriodDocument, args) 
    const structuredContent: z.infer<typeof doctorFreeSlotResponseSchema> = { 
      elems: findDoctorFreeSlots(response.searchDoctorSchedule.elems) 
    } 
    return { 
      content: [{type: 'text', text: JSON.stringify(structuredContent)}], 
      structuredContent, 
    } 
  } 
)

In this example, the input schema from the generated GraphQL operation SearchDoctorScheduleByDoctorIdAndPeriod is reused. However, the result is different: instead of raw schedules and busy intervals, a ready-made array of free slots is returned. The findDoctorFreeSlots function encapsulates the application logic: it takes the doctor's schedule, considers already busy intervals, and collects free slots. For the agent, this logic becomes part of the tool's contract, not a task to be figured out each time.

The point is to give the agent a tool at the task level, not at the API CRUD level. The generator, in this case, doesn't close off the system. It provides a base layer: types, operations, Zod schemas, handlers, and registration, and alongside it, you can manually write application tools, reusing the same GraphQL client, authorization, context, and generated types.

Security

The fixed operations approach helps reduce the API surface that the agent receives. If an operation doesn't have a certain field, the agent cannot simply add it to the query. The set of available tools and GraphQL operations is known in advance. MCP annotations like readOnlyHint and destructiveHint help the agent and client choose tools more carefully, but actual permission checks are performed on the DataSpace side:

  • RBAC, ABAC, and RLS on the DataSpace side;

  • JWT of a service account or a specific user;

  • additional security predicates at the operation level;

  • limits and checks that do not depend on the model's behavior.

The MCP server can call the DataSpace GraphQL API with the JWT of the original user or with the JWT of a service account. The choice depends on the access model. For example, an RLS rule can restrict search results to the current user's data. In this example, a regular user sees only records with their email, while a user with the manager role sees all records:

{ 
  "name": "searchPerson", 
  "body": "...", 
  "pathConditions": [ 
    { 
      "path": "searchPerson", 
      "cond": "it.email == ${jwt:email} || 'manager' $in ${[]:jwt:realm_access.roles}", 
      "description": "Select all records for managers; otherwise select the current user's record" 
    } 
  ] 
}

An RBAC rule solves a different problem: it doesn't filter the result but prohibits the operation itself if the user doesn't have the required role. For example, creating a clinic can only be allowed for an administrator:

{ 
  "name": "createClinic", 
  "body": "...", 
  "checkSelects": [ 
    { 
      "conditionValue": "'administrator' $in ${jwt:roles}", 
      "typeName": null, 
      "description": "Only administrator can create clinic" 
    } 
  ] 
}

In DataSpace, the security model is initially built around fixed operations. Therefore, MCP tools based on operations do not create a separate layer of restrictions but transfer the existing access boundaries to MCP: the agent works only with a predefined set of operations, the composition of which can be explicitly verified.

What We Achieved

There are several ways to connect GraphQL and MCP:

  • An MCP adapter for arbitrary queries is good for API exploration and rapid development scenarios.

  • MCP tools derived from the schema and root fields help quickly expose the API via MCP.

  • For a manageable API surface, we chose tools based on operations. Code generation makes this approach more controllable. The agent works with a pre-prepared set of operations: it selects a tool and fills in variables. GraphQL developers, in turn, retain control over the operation body, selection set, and result form.

The approach is not tied only to DataSpace; it can be adapted for other GraphQL APIs. It even seems possible to adapt the generator for other languages. For example, generating Pydantic models for Python. And in the near future, we plan to develop more flexible tool configuration. Ultimately, GraphQL operations become a common contract: developers manage the composition and permissions of GraphQL operations, and the agent works with a predictable and explicitly defined set of MCP tools.
