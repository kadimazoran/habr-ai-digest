What we will check

Hello! I'm Evgeny Stepanenko, a lead QA engineer at Ozon. I'll show you how to juggle API responses.

Let's say we're adding a task filter by status to a task tracker: "New," "In Progress," "Blocked," and "Completed."

In this example, we'll focus on UI testing: we'll check how the interface displays filtering results, loading, and errors.

We need to check:

  • Tasks loaded. Their titles and statuses are displayed. A blocked task shows the reason for blocking, while others do not.

  • Nothing found for the selected statuses. A message appears as per the mockup.

  • The response has not yet arrived. A loader is displayed.

  • The request failed. The user sees an error message and a retry button.

The frontend filter is already ready, but the staging environment only has a few tasks with the status "New."

To check other states, you can create tasks with the required statuses and fill them with data. However, you can't get a loading error this way. Instead, we'll prepare several API responses and substitute them in the browser. This allows us to check task display and error handling without changing the data on the staging environment.

What data to prepare

Mocks in testing allow you to check a feature even if the necessary data is not available on the staging environment. We substitute the backend response and see how the interface handles it. This approach is called mocking.

When the user applies a filter, the application sends POST /api/tasks/search with the selected statuses in the request body. Let's prepare a response with two tasks – a new one and a blocked one:

{
  "items": [
    {
      "id": 1,
      "title": "Prepare report",
      "status": "new"
    },
    {
      "id": 2,
      "title": "Approve mockup",
      "status": "blocked",
      "block_reason": "Waiting for designer's response"
    }
  ]
}

items contains the tasks that match the filter. The block_reason field is only present for the blocked task.

We'll use this mock as a basis. For each scenario, we'll change what affects the check: data, HTTP status, or response delay.
