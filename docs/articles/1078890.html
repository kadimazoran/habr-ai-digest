How to connect agents to Google Workspace

Actually, there are quite a few ways to connect - as many as three. The first, simplest way is your provider's connector, like Claude or ChatGPT. Everything works with a connect button there.

But this method is limited. I use Claude the most, so I'll explain using its example. Claude Code can use connectors in cloud sessions and in local sessions via Claude Desktop. Claude Code CLI, which runs in the terminal, no longer sees the claude.ai connectors. If you only use the UI and don't install open-source agents, then the connector is really the best option. Everything that follows is not for you.

The other two methods are an MCP server or an API. At the time of writing, I concluded that the easiest way is to use the API with a custom CLI wrapper.

Google has released official MCPs, but there are nuances. There's a very small set of methods. Calendar doesn't have access to contacts (People API). And the Drive MCP didn't work for me at all. Perhaps in some time, MCPs will be perfected, but for now, we have what we have.

There are many 3rd party MCPs and CLI tools. In general, you can use them. But you know, it's not worth the effort. There might be bugs, something might be missing, and at the same time, they'll clutter your context with a bunch of unnecessary methods. I simply asked the agent to write its own client for my specific requirements. It's faster now. And then the agent calls this CLI as a regular command in the terminal, which is enough for it.

How Google Cloud authorization works

The main thing to understand and accept is that Google Cloud is not designed for individual users. It treats everyone like a company.

Google does not support PAT (Personal Access Token). You might think: just give me a token, like most other services do, I'll grant it permissions and the agent will use it. Profit!

But Google doesn't allow that. You have to create a project, an application within it, a client within that, and so on. As if you were creating a service for thousands of people. Then, you yourself log in to your application as an external user and get permissions.

As an authorization mechanism, Google offers OAuth. What this means from a practical standpoint:

  • Our MCP or CLI client needs to create a link on accounts.google.com. We open it in a browser.

  • This link contains all the necessary information - for which application and what permissions we are requesting, as well as to which link to send the result.

  • As a user, we look at the permissions to grant and click OK in the browser.

  • After that, Google redirects the browser to the callback link we provided. In our case, this is a local address on the computer where our client has started a small web server and is waiting. The link doesn't provide a token, but a one-time code.

  • The client itself, without the browser, exchanges this code for tokens with a direct request to Google.

If you are setting up an agent on a server, you will need to set up an SSH tunnel to localhost to handle the callback link.

You might also see two other types of credentials besides the OAuth client. These are API Key and Service Account. You can ignore them. An API Key does not identify a user and is used for technical requests to the project. A Service Account only gains access to personal data through an organization administrator in the corporate version (like a secretary), and doesn't work at all for personal accounts.

Basic explanation of Google Cloud entities used

  • Project. A container for APIs, access settings, limits, etc. By default, you have one project, "My First Project".

  • Google Auth Platform. A set of interfaces that contains "application" settings. An application is an entity to which the user grants access. One project is one application. The application has a name and several other parameters - a link to the homepage, privacy policy, etc. Fill in anything, I put a link to my GitHub everywhere.

  • Client. A set of credentials associated with the platform (Desktop, iOS, etc.). This means an application can have different clients. A client has an ID, which Google uses to understand which client the user is connecting from.

  • Scopes. A set of specific permissions for what can be done. For example, "Allow reading email".

Here is the JSON downloaded from the Clients page. The secret here isn't particularly secret: client_id is the identifier of your client, and client_secret confirms this ID. However, it doesn't grant access to the API on its own. Using client_id, we pass the consent screen.

{ 
  "installed": {
    "client_id": "1234567890-abc123.apps.googleusercontent.com",
    "project_id": "my-project-123456",
    "auth_uri": "https://accounts.google.com/o/oauth2/auth",
    "token_uri": "https://oauth2.googleapis.com/token",
    "auth_provider_x509_cert_url": "https://www.googleapis.com/oauth2/v1/certs",
    "client_secret": "GOCSPX-...",
    "redirect_uris": ["http://localhost"]
  }
}

The structure of OAuth tokens (this is how the python-google-auth library saves them; other clients may have a different format, but the set of fields is semantically the same):

{
  "token": "ya29.a0...",
  "refresh_token": "1//0g...",
  "token_uri": "https://oauth2.googleapis.com/token",
  "client_id": "1234567890-abc123.apps.googleusercontent.com",
  "client_secret": "GOCSPX-...",
  "scopes": [
    "https://www.googleapis.com/auth/calendar",
    "https://www.googleapis.com/auth/drive"
  ],
  "universe_domain": "googleapis.com",
  "account": "",
  "expiry": "2026-09-05T18:30:00Z"
}

Without going into the details of the OAuth protocol, the most important thing here is the refresh token. It's issued after passing the consent screen and is actually used to gain access. The token is a short-lived access token; it lasts for an hour, and the client re-issues it using the refresh token. Tokens are saved by your client (CLI or MCP).

How to configure an OAuth client

Everything is done in the Google Cloud Console (https://console.cloud.google.com/), mostly on the Google Auth Platform pages. Let's go step by step.

1. Google Auth Platform -> Branding

You need to fill in:

  • App name - any name.

  • User support email - just your email.

  • App domain: home page, privacy policy, terms of service - put your GitHub link everywhere. This is okay.

  • Logo - not needed.

  • Authorized domain - github.com.

  • Developer contact information - your email again.

2. Google Auth Platform -> Audience

  • User type: External. Internal is only available for corporate accounts, and only accounts from your organization can log in to the app. This is inconvenient if you have personal and corporate accounts.

  • Publishing status: In production. Testing issues tokens that expire after 7 days. In production provides an indefinite token. More precisely, it only expires if it's not used for six months, the access is revoked manually, or the account password is changed.

  • Verification: we don't do this, it's difficult, it's for real applications for external users.

3. Google Auth Platform -> Clients

Create a Desktop client. Desktop is important because it allows redirection to localhost after passing the permissions screen. Save the JSON with client_id and client_secret.

4. APIs & Services -> Library

In addition to the OAuth client, you need to enable the APIs themselves in the project that the agent will access. Search by name and click Enable: Google Calendar API, Google Drive API, Gmail API, People API (this is for contacts and people search in an organization). If you don't do this, the token will have permissions, but requests will fail with a 403 error.

5. First login

On the first login, after selecting an account, Google will show a warning screen "Google hasn't verified this app": the app is not verified, "Back to safety", and so on. Just keep this in mind.

Useful links

  • https://console.cloud.google.com/auth/overview - Google Auth Platform page (Branding, Audience, Clients)

  • https://console.cloud.google.com/apis/dashboard - APIs & Services page. Here you can view dashboards with request counts to various APIs, latency, and error codes. Also, in the Library section, you can enable the necessary APIs.

  • https://myaccount.google.com/connections - from the user's perspective: which applications have access to the account, and where access can be revoked.

  • https://developers.google.com/workspace - API documentation and official MCPs. You can give this to your agent.

Conclusion

I think you'll agree: the way agents connect to Google Workspace is sheer madness. However, it can be explained. Google Cloud makes money from corporate clients. The consumer segment should use connectors within the UI of ready-made applications.

And we, ordinary engineers, should be grateful anyway. The API exists in principle, and we can use it for free.
