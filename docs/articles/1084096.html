The work of a data engineer involves many repetitive tasks: fetching data from an API, checking its structure, transforming fields, and writing the result to storage. This is surrounded by configuration, tests, error messages, and documentation.

Such work is convenient to delegate to an Agent. For example:

Write an Airflow task graph: get data from the API, save it to S3, check the structure using Pydantic, and load it into storage. Add retries, logging, and tests.

The generated code needs to be reviewed, but starting from an empty file is no longer necessary.

This raises the question: if implementation can increasingly be obtained from a description, what will a data engineer be responsible for?

I would start by saying that writing code has never been the entire job. It's just that its result is very visible: here's the task, here's the change in the repository, here's the new processing.

The solutions that prevent the system from losing data, overwhelming the source with requests, or requiring overnight recovery are much less visible. These are what we should focus on.

First, you need to decide what should happen in case of failure

Let's say we have a daily load of 100 files. After loading, their content goes into a search index.

The implementation seems simple: delete old files, download new ones, start the index update.

Today, 40 files were loaded, after which the source stopped responding. The old dump is gone, and the new one is not yet complete.

Even if the index update doesn't start after the loading error, it won't bring back the previous dump. If the import does start, you'll have to figure out separately what it will do with an incomplete set.

In such a task, you first need answers to several questions. How do we determine that all expected files have arrived? When do we allow them to be used? What will happen on a rerun? Do we have a previous working version?

One possible way to structure the loading process:

  1. New files are saved separately from the active dump.

  2. Before publication, the completeness and content of the set are checked.

  3. Consumers switch only to the ready version.

  4. The previous version is kept for an agreed period for recovery.

This is not yet a complete architecture. You need to choose a switching method, define a retention period, and agree with the source on how to get the list of expected files. Simply comparing their quantity with yesterday's is not enough: today the source could have legitimately generated a different set.

An Agent can be tasked with implementing such a scheme. You can ask it to look for weaknesses and suggest alternatives. But first, someone needs to clarify the requirements and decide which guarantees are truly necessary.

The command "add retries" does not replace this work.

Suggesting a solution and making a decision are different tasks

A model can suggest intermediate storage, checksums, completeness checks, version switching, and saving the previous state.

The suggestions might be reasonable. But each of them needs to be applied to the system.

Suppose storing two dumps is too expensive. Or consumers read files directly, and there's no single switching point yet. Or the source doesn't provide a file list to check completeness. Or restoring yesterday's version is acceptable for a report but unacceptable for another dependent system.

These constraints need to be collected and passed to the model. Then, check if they were lost in the proposed solution.

Therefore, using an Agent for design is quite possible. There's no point in rejecting its suggestions just because a model made them. But it's also not worth accepting the answer as a ready-made engineering solution.

The client ultimately receives a working system, not a flawed answer in a chat. Someone must ensure that the system meets the agreements and organize recovery when it violates them.

Knowledge of SQL and Python is not going anywhere

From the reasoning "An Agent writes code," it's easy to draw the wrong conclusion: therefore, a deep understanding of code is no longer needed.

But how can you check it then?

You can get a Spark processing without understanding at what point data is redistributed between executors and how much it costs. You can accept an SQL query without looking at the execution plan. You can apply Kubernetes settings without understanding resource requests and limits.

In each case, the text will look convincing. This is not enough to evaluate its behavior on real data.

It's the same story with retries. It's important not only to check that they are configured. You need to understand if it's safe to repeat the operation, whether it will create duplicates, and whether it will increase the load on an already overloaded source.

Tests also require verification. For example, a successful load test doesn't answer the question of what happens after half the files are written. And checking the write structure says nothing about the completeness of the entire set.

Fundamental knowledge is needed not only for independent implementation. It is needed to notice a missed case, ask a precise question, and distinguish a working solution from a plausible one.

What to look for beyond an individual task

A data engineer doesn't work with an isolated SQL query or a task graph. There's a source, delivery, transformations, storage, and consumers. An error in one area can manifest in a completely different place.

For example, a loading task completed successfully. It read everything the source provided and wrote the result without exceptions. But the source provided only part of the data.

From the perspective of code execution, everything went according to plan. From the user's perspective, the report is incorrect.

Therefore, it's useful to separate two questions: did the processing complete, and did the consumers receive usable data.

For the second question, you need your own checks: data freshness, completeness, key uniqueness, acceptable values, consistency with other sets. The specific composition depends on the task. An empty table means a disaster somewhere, and a normal day without events somewhere else.

The same applies to observability. An error message helps to know that a task failed. To analyze the causes, you usually need additional information: what source was used, what period was processed, how many records arrived, and what code version transformed them.

And to assess the consequences, you need to know which reports, services, and other processes use this data.

This is not a reason to collect all possible metrics. First, you should determine what questions will arise in case of failure, and then ensure the ability to answer them.

Sometimes it's more useful to reconsider the requirement than to speed up processing

Imagine a table that updates every five minutes. The processing is expensive, so the engineer looks for ways to speed it up.

You can rewrite the query. Change data placement. Add resources. Ask the Agent to suggest a few more options.

But first, you should find out where the five minutes came from.

Perhaps the data is indeed needed with such a delay. Then the task is clear: ensure the required freshness at an acceptable cost.

Or perhaps this interval was set sometime without good reason, and the report is opened once a day. Then discussing the requirements can yield more than optimizing the code.

Similar questions arise with storage periods, the depth of historical recalculation, and the volume of collected data.

This is not a call to argue with every requirement. You need to understand its origin and consequences. Without this, you can conscientiously speed up processing that should have been simplified or removed long ago.

Cost is also an engineering constraint. The solution must fit not only within execution times but also within available resources, including the team's time for maintenance.

Where an Agent is useful beyond writing code

I would look at the entire change process: from the appearance of a task to checking the result in a working system.

For example, before fixing a load, you need to find related tables, read the source description, check dependent processes, and understand which tests will need to be changed. Part of this information gathering can be delegated to an assistant if it has access to the necessary materials.

When analyzing a failure, the work is similar: collect errors, code changes, information about recent runs, and dependencies between data. An Agent can be tasked with preparing such a summary and searching for possible causes.

Here it's important to separate established facts from assumptions. "Execution time increased after the change" and "the change caused a slowdown" are different statements. The latter requires verification.

Another application is preparing test cases. Not just "write tests," but a more specific task:

Find situations where a rerun will create duplicates, an incomplete set will be published, or restoring the previous version will be impossible.

The answer still needs to be checked, but it can help consider cases that were not included in the initial problem statement.

For such automation, I would start with reading, analyzing, and preparing changes. Restarting processes, deleting data, and recalculating history are separate actions with separate permissions and checks.

And I would evaluate the result based on the entire work time. If the model prepares a change in a minute that then takes two hours to untangle, the generation speed alone doesn't say much.

Is it mandatory to build Agents now?

No. Not every process needs an agent, and not every sequence of actions should be replaced by model reasoning.

For loading according to known rules, ordinary code and a scheduler may be sufficient. Adding Agents should solve a specific problem, not just make the system look more modern.

At the same time, the experience of a data engineer is useful even in agent systems. The questions are familiar: where is the state stored, can the action be repeated, how to limit the load, what to do after partial execution, and how to restore the sequence of events.

Therefore, transitioning to working with agents doesn't necessarily mean abandoning your previous specialty. But I wouldn't declare it a mandatory next step for all data engineers.

First, you should find a task where the model is truly useful. Then decide if an agent is needed for it.

What I would spend time on

SQL, Python, and the architecture of the systems used remain the foundation. Checking someone else's code without understanding the tool is difficult, regardless of who wrote that code.

The next layer is data processing design: state, retries, consistency, recovery after partial execution. It's useful to be able to explain not only the normal workflow but also the behavior during failures.

Separately – data quality and diagnostics. What violations do we check for, how do we learn about them, and can we identify affected consumers.

And also – requirements and cost. Why is the processing needed, what update frequencies are justified, how much do the chosen guarantees cost, and who will maintain all of this.

I would learn Agents along with these tasks: delegate implementation, information gathering, and searching for missed cases to it, and then check the result using familiar engineering tools.

The ability to write code doesn't become useless because of this. The way you work with it changes.

In the example with 100 files, it's not enough to show that the load completes successfully from start to finish. You also need to explain what will happen after the fortieth file, how the system will detect an incomplete dump, and where it will get the data for recovery.

This is what a data engineer is responsible for.
