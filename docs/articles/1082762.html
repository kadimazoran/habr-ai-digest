In the previous article, I ended by saying that the next part of the series would likely go beyond the Obsidian plugin itself, into Companion and MCP.

It did.

During this time, Vault Audit AI has acquired a separate server, an MCP interface for AI clients, a change proposal mechanism, and a second repository.

Then it became clear that the old name no longer adequately explained what was going on.

So, the project is now called Veynrel.

The plugin itself was not rewritten from scratch. Existing users don't need to reinstall anything, re-enter API keys, or rebuild the semantic index. I specifically tried to make the most technically boring rebranding possible.

However, things around the plugin have become noticeably more interesting.

Now, in a simplified form, it looks like this:

Veynrel

   | semantic duplicates
   | Ask your Vault
   | AI workflows

Veynrel Companion

In this article, I'll explain why I decided to build a separate Companion, why another layer was added between the agent and Markdown, why the MCP server can't directly rewrite notes, and how all this ultimately led to a full rebranding.

Also, closer to the end, there will be a rare innovation for my articles: I've finally added a button to the project that doesn't start another index but allows you to support development financially.

Why Vault Audit AI stopped being Vault Audit AI

When I started the project, the name was quite accurate.

There's Vault. There's Audit. AI is somewhere nearby.

The plugin gets notes, processes them through a model, and helps manage the vault.

Then MapReduce for large Vaults appeared.

Then automation for working with notes.

Then the semantic index, Similar Notes, semantic duplicate search, and Ask your Vault.

At some point, auditing became just one of the functions, but the name continued to pretend that it was the sole purpose of the project.

Continuing to call the project Vault Audit AI would be like naming an IDE "main.ts editor". It's not technically false, but the description is slightly behind reality.

Thus, the name Veynrel was born.

The most important thing here was not to change the text in the README, but to avoid turning the name change into a user migration.

Therefore, old technical identifiers are still encountered within the project.

For example, the plugin ID remains:

ai-knowledge-hub

Some of Companion's environment variables also haven't changed:

VAULT_AUDIT_COMPANION_DIR
VAULT_AUDIT_MCP_TOKEN

Sometimes vault_audit is also found.

This isn't a forgotten Ctrl+Shift+H.

If a string is already used in a user's config, storage key, or protocol, renaming it just for aesthetics is quite pointless.

It would result in a clean diff and less clean broken installations.

So, Veynrel became the new user-facing name, while old identifiers remain where they are already part of compatibility.

An existing user simply updates.

Settings remain in place. The semantic index remains in place. Hotkeys too. Companion continues to understand the same protocol.

In my opinion, a good rebranding should look exactly like this. Most of the complexity should remain the author's problem, not the user's.

Why was Companion needed at all?

As long as Veynrel lives only within Obsidian, everything is quite convenient.

The plugin sees the Vault, monitors changes, and maintains a local semantic index.

But this approach has an obvious limitation.

To ask something of the Vault, you need to open Obsidian and call a function within the plugin.

But I wanted a different scenario.

For example, I'm working in Codex and type:

Find everything in my Vault that I've written about MCP,
and show unresolved architectural issues.

Or:

Look at my project notes and find
where I've already described a similar idea.

Or even:

Suggest an update to README based on my notes.

Copying Markdown manually into a chat quickly becomes tedious.

It's especially funny after spending months writing semantic search, only to then manually search for the right note to paste into an AI client.

A layer was needed that could live separately from the Obsidian interface.

Thus, Veynrel Companion was born.

It's a separate Node.js service that maintains a persistent mirror of the relevant semantic state.

And here, the word "mirror" is crucial.

Companion does not open the Vault directory and does not directly access Markdown files.

It does not become a second owner of the notes.

And most importantly, it cannot simply overwrite a file while Obsidian is looking elsewhere.

Why I specifically prohibited Companion from writing to the Vault

At first glance, it could have been made much simpler.

Give the server the path:

/home/me/Vault

and then the usual:

readFile()
writeFile()

Done.

The agent reads notes, the agent writes notes, the demo looks nice.

And a future post is ready:

How I taught AI to work with Obsidian in one evening and spent the next evening restoring the Vault from Git.

The problem isn't just that the model might do something strange.

Obsidian itself has a state.

The plugin monitors files. AutoSync is working. The semantic index changes along with the notes. Some operations read the current file version, think for a while, and then try to apply the result.

If another independent process that writes Markdown whenever it wants is added on top of this, a second writer emerges.

And two writers to one knowledge base without a common concurrency control model look fun right up until the first race condition.

Therefore, the rule became quite strict:

Only Obsidian writes the Vault.

Companion receives the state from the plugin and stores it locally.

AI can read this state via MCP.

AI can even propose a change.

But Veynrel within Obsidian still applies it.

`propose_change` instead of `write_note`

This is one of the parts of the architecture I like most right now.

The most obvious MCP API would look something like this:

read_note
search_notes
write_note
delete_note

But if you give the model `write_note`, the previous section can be almost thrown away.

So, instead of a "change file" command, a different scenario emerged:

AI
 |
 | propose_change
 v
Companion
 |
 | stores proposal
 v
Obsidian
 |
 | user reviews diff
 v
Approve / Reject

The agent creates a proposal.

For example:

operation: replace
path: Projects/Veynrel.md
summary: Update Companion architecture section

Companion saves the proposal.

After that, Veynrel shows it to the user.

You can view the diff, reject the proposal, or approve it.

Only after approval does the plugin check that the note hasn't changed unexpectedly since the proposal was created and applies the operation.

This means MCP can participate in changing the Vault, but it doesn't own the Vault itself.

I like this option much more than simple CRUD.

AI gets the ability to do useful work, but the write boundary remains explicit.

What exactly does an MCP client see?

Companion currently provides seven tools:

vault_status
list_notes
get_note
get_chunks
search_vault
propose_change
get_proposal

The set is intentionally small.

I didn't want to turn the MCP description into a phone book of fifty almost identical functions.

vault_status allows you to understand if the mirror exists, how many notes and chunks it contains, and which generation is current.

list_notes returns known paths and metadata.

get_note reads the Markdown of a specific note. Large files can be retrieved in chunks.

get_chunks works with note segments from the semantic index.

search_vault does what this whole thing was initiated for.

The client sends plain text:

how I wanted to organize shared memory between agents

Companion builds an embedding of the query and searches for similar chunks.

The saved note texts are not sent for embedding again. The index already exists.

propose_change creates a change proposal, and get_proposal allows checking its status.

There is no approve_proposal in MCP.

This is also intentional.

Approval remains within Obsidian.

Where does Companion get its semantic search from?

This turned out to be another amusing twist.

When I wrote the semantic search for the plugin itself, I deliberately avoided a separate vector database.

For a typical Obsidian plugin, setting up Qdrant for a few thousand notes seemed a bit excessive.

So, Veynrel uses its own local LocalVectorStore.

And this solution hasn't disappeared.

But Companion is already a server.

It has Node.js, SQLite, and a completely different set of constraints.

As a result, SQLite became the persistent source of state, and on top of it, Qdrant can be enabled as a search accelerator if desired.

The key point is that Qdrant does not become the primary storage.

If it's turned off or lost, the canonical data remains in SQLite.

Veynrel
   |
   | sync
   v
Companion
   |
   +---- SQLite  <-- permanent state
   |
   +---- Qdrant  <-- optional derived index

For a small Vault, you can live without Qdrant at all.

If the mirror becomes large enough and linear search becomes annoying, an accelerator is available to connect.

I prefer this approach over a scheme where the disappearance of an auxiliary service suddenly means the loss of the main database.

And where is MCP in all this?

If we simplify greatly, MCP solves a rather mundane problem.

It gives AI clients a standard way to know:

what actions are available here and how to call them.

Without it, Codex would require one adapter.

Claude Code would need another.

Then another client would appear, and the developer would suddenly have a new hobby.

With MCP, Companion exposes one interface.

Then the client receives the tools and calls them as needed.

For example:

Codex
  |
  | search_vault("MCP security model")
  v
Veynrel Companion
  |
  | embedding query
  | vector search
  v
matching chunks

If the result is insufficient, the agent can request the full note via get_note.

If, after analysis, something needs to be changed, it creates a propose_change.

This means the model doesn't get a huge dump of the Vault into its context window, but rather the ability to gradually retrieve the necessary information.

This seems much more natural for a knowledge base.

Two tokens instead of one

Since the server can both synchronize state and serve data to AI clients, the next question quickly arose.

Why should an MCP client have the same rights as Obsidian itself?

It shouldn't.

Therefore, Companion has different credentials.

COMPANION_TOKEN is used by the trusted plugin for synchronization.

MCP_TOKEN is used by the MCP client.

If someone obtains an MCP token, it should not automatically grant them the ability to impersonate Veynrel and upload a new mirror state.

Companion does not accept equal token values on startup at all.

This might seem like paranoia on a local machine.

On a VPS, it's less so.

One Companion for both local and VPS

There is no separate "server version" of Companion.

The same code is run.

Locally, it might be:

127.0.0.1:27124

The plugin synchronizes to the same address.

Codex connects to:

http://127.0.0.1:27124/mcp

If you want to host the mirror on a VPS, you can install Companion there and hide it behind a reverse proxy:

Internet
   |
 HTTPS
   |
Caddy / Nginx
   |
127.0.0.1:27124
   |
Veynrel Companion

Companion itself does not terminate TLS.

I would not use plaintext HTTP for remote connections. It still holds a mirror of a personal knowledge base, and a bearer token doesn't become less secret just because it's in a nice JSON.

Why Companion had to be moved to a separate repository

Initially, the server lived directly within the plugin's repository.

It looked convenient:

veynrel/
├── plugin code
├── semantic/
├── companionSync/
└── companion/

One project, everything together.

Then the Obsidian Community Plugin review began.

The scanner saw Companion's Node.js code and, quite logically from its perspective, started explaining to me that `node:http` and `node:sqlite` are unavailable on mobile Obsidian.

It was right.

Except for one small detail.

This code was never supposed to end up in Obsidian at all.

The server and the plugin were simply in the same Git repository.

You could endlessly explain to the tooling where the mobile plugin ends and the standalone Node service begins.

Or you could establish a proper architectural boundary.

Now there are two repositories:

github.com/zinverno/veynrel

github.com/zinverno/veynrel-companion

The main repository retains `companionSync`, which is indeed part of the plugin.

The server itself lives separately.

After this, not only did the extraneous scanner warnings disappear.

The project's structure itself became simpler.

Companion now has its own dependencies, its own CI, its own tests, and its own lifecycle.

And, unexpectedly pleasantly, it can now be developed as a standalone service without pretending to be just a large subfolder of the Obsidian plugin.

The rebranding also turned out to be a backward compatibility test

Renaming a project sounds like a task of the level:

Find: Vault Audit AI
Replace: Veynrel

I quickly discovered why such operations sometimes end with a separate migration guide.

The old name appeared not only in the README.

It had made its way into package names, environment variables, storage keys, MCP identifiers, Qdrant prefixes, hash inputs, and historical fixtures.

Some could be renamed.

Some could not.

Some could be, but it offered no benefit other than risk.

As a result, each such identifier had to be classified before replacement.

For example, Companion's private npm package could easily be transformed from:

vault-audit-ai-companion

to:

veynrel-companion

But:

VAULT_AUDIT_COMPANION_DIR

remained.

Because it's already a user environment variable.

The same applies to some storage keys and protocol identifiers.

The principle turned out to be quite simple:

The brand can be changed aggressively. Compatibility should only be changed when there's a reason beyond a new logo.

As a result, Veynrel 1.8.0 updates over Vault Audit AI 1.7.0 without migrating user data.

There are suspiciously many tests again

In the previous article, I wrote about 698 tests.

Now, the main plugin has 849 tests.

Companion lives separately and has another 218.

And I stopped perceiving the number of tests as a competition with myself long ago.

It's just that almost every new boundary of the project creates a new class of unpleasant scenarios.

What if the note changed between proposal creation and approval?

What if the embedding provider returned NaN?

What if two requests simultaneously try to process the same note?

What if the semantic descriptor changed right during the search?

Most of these things never happen in a demo.

In a real main Vault, these are precisely the things that tend to happen.

The project's tradition continues.

What resulted in the end

After all this restructuring, Veynrel no longer looks like a single large Obsidian plugin to me.

It's more like two layers.

The first is located directly next to the notes:

Veynrel

It owns the interaction with the Vault.

It indexes, displays the interface, and applies approved changes.

The second:

Veynrel Companion

can live separately, maintain a persistent mirror, and provide controlled access to external AI clients.

MCP connects this layer to agents.

The most important thing for me here is that the boundaries have become sufficiently explicit:

Agent can read
Agent can search
Agent can propose

Agent cannot silently write Markdown

This limits some of the fancy demos.

However, it significantly increases the chance that I myself will agree to connect all this to my actual Vault.

And this test for the project still remains the main one.

The project now has support via Boosty

And one more change, not architectural at all.

Until now, Veynrel was just an open-source project to which I systematically dedicated my free time.

It remains that way.

The code is open under MIT.

Features will not be hidden behind a subscription.

Companion and MCP are also not turning into a paid tier.

But the project has long ceased to be a small weekend experiment.

There's a Community Plugin, a separate Companion, documentation, CI, tests, version compatibility, and periodic battles with problems I didn't even suspect existed yesterday.

Therefore, I've finally added the option to voluntarily support development.

Boosty: https://boosty.to/veynrel

There's a simple support level for the project there now.

No Veynrel Ultimate Enterprise Plus.

No "semantic search available with Pro plan".

If the project is useful to you and you want to help me continue developing it, this option is now simply available.

If not, nothing changes in your use of Veynrel.

What's next

In the previous article, I wrote that the next part of the series would likely go beyond Obsidian.

This has now happened.

But Companion and MCP are interesting to me for another reason.

When several AI clients start working with the same data, the next question quickly arises.

Why should each of them build its own memory, integrations, and context retrieval method around itself?

For now, Veynrel solves this problem only for one specific domain, Obsidian Vault.

But architecturally, more general ideas are starting to emerge here.

Storage is separate.

Agent is separate.

A controlled access layer between them is separate.

Where this will ultimately lead, I'd better not promise yet.

This project already has a bad habit of turning the phrase "I'll add a small feature" into a new repository.
