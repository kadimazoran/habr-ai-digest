Higher reasoning effort isn't always better: a benchmark of local LLMs on different thinking levels

When working with Claude Code, I intuitively chose the reasoning level for the task type—high for planning, low for code based on a plan, to save tokens. Now I use local models, there are no limits, and we only pay with time: more reasoning tokens mean longer generation. I decided to test my intuition with measurements: I assembled a benchmark of three tasks with traps on a production stack, ran several models at different thinking levels—36 runs isolated in containers. In some measurements, I got results I didn't expect: models were revealed where increasing the reasoning level did not lead to a better outcome. I am continuing to get acquainted with the world of local LLMs after my Claude Code account was blocked. The beginning of the story is in the previous article.

This week, I pondered what reasoning effort is optimal for tasks. While working with Claude Code, I followed this approach: planning and debugging—Opus + high, and writing code based on a plan—Opus + low or Sonnet + medium. But I arrived at this intuitively and with the goal of saving tokens.

I started following the same tactic with local models. But how correct is it? If we use local models, then there is no question of saving on limits anymore. The only thing we pay for when choosing a higher reasoning effort is time. Firstly, the model generates more reasoning tokens, and secondly, the generation speed itself decreases.

What if we use a lower level of reasoning for writing code? How much faster will the task be completed then? Will the quality decrease? Maybe it's better to always set the maximum thinking level?

I decided to check this with measurements.

Benchmark on Tasks

One of the articles on Habr inspired me to create a separate repository for testing coding agents and automating the evaluation of results.

The evaluation methodology (hidden acceptance tests, subtle conditions, mutation layer, traitor test, zero-based normalization) grew out of the minibank benchmark. But there are some differences:

  • three tasks instead of one, and all on a production stack with databases, queues, and migrations, not just one module of 700 lines;

  • zero-based normalization is built into the evaluator script: the baseline "did nothing" and "reference solution" are calculated automatically during the calibration of each task;

  • the mutation layer is supplemented with portability control: the agent's tests are first run on a clean reference, and failing classes are excluded—otherwise, tests tied to class names from the agent's implementation receive points;

  • the traitor test check is static: assertions are compared by methods, not by "file changed";

  • discipline, report honesty, and scope layers have been added, which are not in minibank;

  • the infrastructure is optimized for serial runs: isolation of each run in a container, leak control, automatic matrix aggregation.

I decided to build on the same stack that the project I manage at work uses: PHP 8.4, Symfony 6.4, API Platform 4, Doctrine ORM 2, Messenger, PHPUnit, PHPStan level 10.

The benchmark consists of three tasks for diagnosing and fixing problems. We will perform 3 runs for each point (model + reasoning effort).

I had to spend quite a lot of time calibrating the tasks. At first, I observed that on some tasks, all agents hit the ceiling (e.g., 82.5%). You start investigating—it turns out that the agents also produced a valid solution, but not the one I expected on the "golden" path. If you provide a hint to remove ambiguities, then even on low reasoning, we always get 100%...

The next step was to remove excessive hints from the initial data, add new traps, and hidden tests. After about 4-5 iterations, I managed to find a state where there is a normal spread across runs. That is, there are no longer tasks where all models at all thinking levels consistently give 100%, but they also don't hit a lower ceiling.

Measurement Methodology

What the agent receives. A snapshot of the app/ application in a clean container: no git history, hidden tests, reference solutions, or traces of previous runs. Nearby is the dev.sh script with team checks (PHPUnit, PHPStan level 10, PHP-CS-Fixer) and the AGENTS.md file with team rules—it is read by the agent automatically. The database is empty (only applied migrations). The prompt is a manager's request in business terms: symptom, goal, desired behavior. No file or class names, or the word "tests." At the end, the agent writes a report: changed files, executed checks, what was done.

How the score is calculated. The evaluator script checks what the agent doesn't see:

  • Hidden acceptance tests (weight 0.40) — 15–24 tests per task, all fail on the base with a bug. They check the behavior derived from the prompt and team rules.

  • Subtle conditions (0.15) — time zones, midnight, idempotency, degenerate cases.

  • Mutation layer (0.20) — 10–16 plausible incorrect fixes: each patches the reference solution, and the agent's own tests must catch it.

  • Discipline (0.15) — forbidden files, previously green tests, traitor test, PHPStan, code style.

  • Report honesty (0.05) — the declared list of changed files matches the diff, commands from the report are in the transcript.

  • Scope (0.05) — proportion of diff lines within the task's scope.

A separate type of trap is the traitor test: an existing test that solidifies old behavior with a bug. After a correct fix, it turns red, and it needs to be updated, not the code adjusted to old assertions.

The final score is normalized from zero: "did nothing" → 0, reference solution → 100. Each previously green test that turns red is penalized, so the score can go into the negative.

Protocol. The comparison point is the "model + reasoning level" configuration. For each task—3 runs; tables show median and min–max range. Limit—90 minutes per run. Each run is performed in its own container with a private /tmp (after agents started finding ready-made solutions from their predecessors there, I had to add host leak control as well).

Tasks

All bugs are fictional. No users were harmed.

Task 1. Other People's Monitors

Task. "The client says they see other people's websites in the monitor list. Figure it out and fix it. And check if it breaks anywhere else.".

Description. Data leak between accounts: the monitor selection is not filtered by owner. The key part of the request is "where else": this problem exists in five places—in the list, identifier export, CSV export, batch operations, and summary. Fixing only the list solves only 20% of the problem. Furthermore, the task is enhanced with mechanics that cannot be broken: summary cache with invalidation, soft-delete of monitors, admin bypass of filters, sorting contract.

Traps:

  • five places with the same problem—the code fix is the same, but all affected endpoints must be checked;

  • summary cache: if the cache is not invalidated when creating/modifying/deleting a monitor and opening/closing an incident, the client will see outdated data for some time;

  • monitor deletion—soft-delete: the row remains with deleted_at, disappears from all selections, and is no longer checked by cron; a migration is needed;

  • unknown parameter ?sort=—not an error: by the team contract, this is a 200 and sorting by createdAt. If the agent makes the endpoint return a 400 error code—penalty;

  • two traitor tests solidify the behavior with the bug: after a correct fix, they turn red, and they need to be updated.

24 hidden tests (17 acceptance + 7 subtle), 16 mutants.

Task 2. Emails to Deleted Clients

Task. "DevOps sent an export from the mail gateway logs: a lot of delivery errors for emails to addresses deleted-15@example.invalid, deleted-48@example.invalid. Find out why this is happening and if this bug affects anything else.".

Description. Deleted clients (soft-delete) continue to be checked by the cron job, and incident emails are sent to non-existent addresses. Initially, all models handled the task 100%, so I had to add several more layers of bugs to it: there are three links in client deletion, and fixing one does nothing. Plus, cascading deletion should remove all dependent entities: monitors, incidents, notification settings, status page subscriptions, webhooks. According to the decision recorded in AGENTS.md, only payment information should remain in the database after user deletion.

Traps:

  • Bug 1: the monitor deletion service, before deleting, checks if the user has a deletion flag, but the user manager sets this flag after calling the monitor deletion service. Thus, the method declares that it deletes user monitors, but does not do so;

  • Bug 2: the cron filters only blocked users but does not check the deleted_at deletion flag—therefore, monitors of deleted users continue to be checked;

  • Bug 3: the incident email goes to the queue, and the recipient is determined at the moment of processing—by this time, the client has already been deleted. The fix "do not send to deleted" only in the sender does not catch this path;

  • user deletion should also delete soft-deleted monitors (based on the rule in AGENTS.md): a row with a filled deleted_at is visible only to a special repository method;

  • re-deleting a client should not result in an error;

  • traitor test solidifies the "correctness" that part of the monitors remains after deletion.

15 hidden tests (7 acceptance + 8 subtle), 11 mutants. The penalty for not running PHPStan and PHP-CS-Fixer is higher here: a loss of ~4.5 points out of 100.

Task 3. Incident Threshold with Service Errors

Task. "The site returns a 500 error code, but an incident is not opened when some locations return a service error. And for another user, it's the opposite: an incident is opened when there are no reliable responses. Fix it so that the threshold is calculated based on reliable responses, and service errors do not turn into failures"—with target rules specified in AGENTS.md.

Description. The site is checked from several cities. There are situations when we get system errors from one or more cities, which indicate a problem with the infrastructure, not the site being checked itself. These are the responses we call unreliable (the definition of this term is in AGENTS.md). The user can select 3 cities and set a trigger threshold of 3 (i.e., from three locations, it is necessary to confirm that the site does not return a 200 code). But for one of the locations, a service error occurs, so the incident is not opened—this is the main bug. The task seems simpler than the previous ones: the prompt clearly lists the rules. But there are many rules, and they are subtle.

Traps:

  • classification: service error is not a failure; an incident is opened and closed only based on reliable responses;

  • all locations returned a service error → incident is not opened, the monitor status (metrics, location results, message) remains the same, only the next check is scheduled. If the agent changes the monitor status, it breaks the tests;

  • two different threshold clamps that are easy to confuse: constant (threshold greater than the number of configured locations—fix the setting, the monitor should not be silent until manual re-saving) and ephemeral (threshold greater than the number of locations in a specific response—reduce by one check, do not touch the setting). Several mutants are built on this pair;

  • traitor test: a basic unit test solidifies the behavior with the bug, the reference solution removes it.

16 hidden tests (9 acceptance + 7 subtle), 10 mutants.

Interesting Benchmark Findings

  • In some tasks, agents tried to cheat—looking for ready-made solutions from their predecessors in the /tmp folder. Automatic cleaning by name patterns didn't help find all remnants of previous runs. Therefore, I came to complete isolation of each run in a container with the project folder mounted.

  • In the first iteration of the benchmark, I took measurements with reasoning off. And here's what I found: on complex tasks, DeepSeek showed the best results with reasoning completely disabled! I started to figure out how this was possible. It turned out that with reasoning turned off, more tokens were generated, and the runs took longer. This was due to the fact that in this mode, the model doesn't stop thinking—it just stops outputting its reasoning into reasoning blocks, i.e., it speaks all its "thoughts" aloud, i.e., outputs them into the main chat window. It turns out that the model no longer has limits on the length of its reasoning! And it gives its maximum capabilities. But at the low and medium levels, we set a budget for the number of reasoning tokens, and the model starts cutting corners and making minimal changes that are insufficient to get maximum points. But I didn't include reasoning off in the final selection, as the results were too unstable, and I wouldn't use this mode in production tasks.

  • DeepSeek and Qwen NVFP4 explicitly need to be asked to write tests: on some tasks, they lost points precisely for their absence.

Conclusions

For DeepSeek and Qwen NVFP4, the reasoning level has little effect on the average score. DeepSeek's average across three tasks: 85.7 at low, 86.6 at medium, 86.7 at high. For Qwen NVFP4—76.1–77.5 at all levels. The difference between low and high is within the noise, but high takes twice as much time (for DeepSeek: 10.9 minutes vs. 5.1).

The low reasoning level for GLM and Qwen INT4-AR is risky. GLM at low level: average score across all tasks—45.2, on Task 2 the agent practically failed the assignment. Qwen INT4-AR at low: average score—59.1, and on Task 2—a range of 1.5–72.6 (runs: 1.5, 33.3, 72.6). It seems the reasoning token limit cuts off the search rather than discarding excess: the model grabs the first fix and stops.

The best balance is DeepSeek on low. Average score—85.7, median time—5.1 min, median score per minute—13.9. High and medium score 1 point higher but take more time.

The "Score per minute" metric should be viewed alongside the average score. The formal leader is GLM on low (17.3). Yes, tasks were completed very quickly on this configuration, but the quality of execution at this level is low.

It is necessary to look not only at the median but also at the range. The same model under the same conditions can give both 1.5 and 100 points! Qwen NVFP4 with medium level on Task 2 received the following scores for each run: 1.5, 75.9, 100. DeepSeek medium on Task 3: 50.4, 97, 97 (50.4, of course, is not a complete failure, but the difference is significant). One run would lead to a false conclusion. But how often do we perform multiple generations in real work?

More reasoning tokens does not mean better. Qwen INT4-AR medium on Task 1 generated an average of 105k reasoning tokens (the most in the matrix and more than the same model at xhigh) and achieved a decent but mediocre result—78.9 points. And it took significantly more time.

The mutation layer provides the greatest difference in scores. On the complex Task 3, acceptance tests were passed by all. But only a few wrote their own tests catching plausible incorrect fixes: by median, the mutation layer was covered by only 4 out of 12 configurations.

  • Consistently—only GLM on high: caught 90% of mutants (9 out of 10) in all three runs—the only configuration without misfires.

  • Almost consistently—DeepSeek on medium: 90% in two out of three runs.

Recommendations for models for debugging tasks

  • DeepSeek—low, and sometimes medium. The difference in average score between levels is insignificant (85.7 – 86.7), but low is twice as fast as high. The only exception is complex tasks with subtle rules: on Task 3, medium gave 97 versus 69.6 for low. That is, in most cases, you can work on low, and switch to medium if the result is questionable. And demand that tests be written—without them, DeepSeek loses points on the mutation layer.

  • Qwen NVFP4—no definitive answer, but I lean towards medium. The difference in average score between levels is also insignificant (76.1–77.5), but the best level for each task is different (medium, xhigh, low)—because of this, the difference in average score between levels is within the noise. But I prefer medium because Qwen NVFP4 performed faster on it (6.3 min).

  • Qwen INT4-AR—xhigh. The only model with a monotonic benefit from reasoning: xhigh consistently shows one of the best results on all three tasks (91.5 / 98.0 / 69.6). Low and medium are risky choices.

  • GLM—high, and sometimes max. Low should definitely not be used (average score 45.2, complete failure on Task 2). By default, we use high, as it achieves the highest average score (78.7), shows stable results on Task 3 (97). We switch to max when the result of high is unsatisfactory (on Task 2, max got 72.6 vs. 55.1 for high).
