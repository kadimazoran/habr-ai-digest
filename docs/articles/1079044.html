The "Everything is a Plugin" Principle

Plugin systems are one of the most successful, yet underestimated, architectural mechanisms in the JavaScript ecosystem.

Webpack calls plugins the foundation of its architecture and is itself built on the same plugin system available to users. Vite provides an extensible plugin API. Fastify builds a server application as a graph of nested plugins, and Avvio manages their loading order and shutdown. Linters, testing environments, editors, and many other development tools use a similar principle.

Plugin architecture has already proven capable of supporting vast ecosystems of independently developed extensions. However, it typically resides around the application: extending the bundler, dev server, editor, or framework. But within the application itself, components are still connected in familiar ways: through direct imports, shared service registries, dependency injection, and manually coordinated initialization and cleanup functions.

Cordis proposes taking the next step:

Transform the plugin system from an application extension mechanism into the primary method of application composition.

This is precisely how Cordis is used in DeepSeek Harness. The project explicitly states the Everything is a Plugin principle: model adapters, tools, session logs, the agent loop, and other parts of the system are plugins. Moreover, Cordis operates not only on the host side: the browser runs its own Cordis tree, where UI capabilities are also represented by dynamically loaded plugins.

Therefore, it's more accurate to consider Cordis not just as a backend plugin framework or another DI container. It is an application composition environment, equally applicable to frontend and backend components. Its task is to make the fundamental relationships within a complex system explicit and manageable:

what components exist; 
what they require; 
what they provide; 
what changes they own; 
when they can start; 
what should happen when the composition changes.

The scientific paper A Programming Paradigm for Spatiotemporal Composability formalizes the properties required for such an architecture, and Cordis implements them in TypeScript. Thus, Cordis is interesting not only as a convenient API for plugins. It offers to establish a self-contained architectural layer with its own model of composition, lifecycle, and correctness.

To see how this layer differs from a regular plugin system, let's first compare two models: an application extended by plugins, and an application built from them.

From Extensible Application to Application of Plugins

In a traditional plugin architecture, there is a privileged core:

The core defines the main behavior of the application. Plugins connect to predefined extension points and add optional features.

This model works well for editors, CMS, bundlers, and other extensible products. But it maintains a strict distinction between the "real application" and "add-ons."

Cordis's plugin-oriented architecture offers a different picture:

In this system, a significant portion of what was previously considered the core becomes ordinary components, subject to the common model.

DeepSeek Harness demonstrates a radical version of this approach: its architectural description lacks a privileged core that needs modification to extend the system. New functionality is added alongside other plugins, and registries, services, events, and the agent loop are also parts of the overall composition.

This doesn't mean the application lacks a stable foundation altogether. The foundation simply shifts. Instead of a large functional core, there's a relatively small composition runtime responsible for universal rules:

Component = 
    provided capabilities 
  + environmental requirements 
  + configuration 
  + owned effects 
  + lifecycle

Business logic remains within the plugins. The runtime doesn't need to know how search works, how the interface is built, or how the model is called. It needs to know how these capabilities enter the system, how they interact, and what changes each component introduces to the environment. This is precisely what allows Cordis to be called an additional architectural layer.

However, simply establishing such a layer doesn't explain why it's needed. Its value becomes apparent when the system evolves in multiple directions simultaneously, and the connections between its components become difficult to coordinate manually.

Why the Importance of Plugin Systems is Growing

Plugin systems existed long before Cordis. The novelty here is not in the idea of plugins itself, but in the scale of tasks and the speed of changes: products are accumulating features and integrations, and AI is reducing the cost of code creation, allowing a small group of authors to develop multiple directions simultaneously.

Architectural complexity is therefore increasing even without an increase in team size, and it becomes difficult to keep the full system model in mind. Connections between components need to be formalized at the system level so that each component can be understood and modified locally.

Plugin architecture addresses this problem by giving a component a limited context and explicit connection rules. In 2026, the Yandex Tracker team described such a platform for a product with 600,000 users. In the first beta month, teams created 25 plugins, some with the help of LLMs. Plugins connect only through defined extension points and operate within explicit permissions and isolation.

This year, the Cloudflare team described an AI code review system based on plugins: each plugin implements ReviewPlugin, has an explicit lifecycle, and receives only its own configuration. This is not a direct analogue of Cordis, but the principle is the same: stable interfaces and limited component context.

Partial Knowledge Instead of a Unified Architectural Center

The approach where a component doesn't need to know the entire system's structure dates back to David Parnas's work on information hiding. Cordis transfers this principle to runtime, managing component dependencies, effects, and lifecycles.

Imagine an application that includes search, analytics, authorization, an interface, an AI platform, and infrastructure. These areas can be developed by several autonomous teams or a small group of authors with AI assistance. The organization of work changes, but the need to understand the connections between components remains:

who publishes which events; 
who provides services; 
who depends on a specific implementation; 
in what order everything starts; 
what registrations each component creates; 
what will change when the configuration is updated.

As the system grows, a gap emerges:

application complexity                 grows 
number of components and connections   grows 
speed of changes                     grows 

ability to understand the whole system   decreases

Without a separate composition layer, the architecture becomes distributed across direct imports, bootstrap files, framework hooks, React contexts, DI containers, event buses, and implicit team agreements. A component might appear locally simple, but to modify it correctly, a developer has to investigate a large part of the system.

Plugin architecture proposes replacing some of this global knowledge with a local contract:

Plugin "Research" 

requires:
    search
    database

provides:
    research

configuration:
    strategy
    limits

effects:
    managed by the runtime

Complexity doesn't disappear. But it is partially relocated:

from developers' memory
        ↓
into an explicit composition model

This is one of the main sources of cognitive load reduction. The developer declaratively specifies dependencies, and Cordis determines the startup order and manages component lifecycles.

Contract Between Teams and Reduced Cognitive Load

In Cordis, a plugin's contract can become a boundary not only between components but also between teams. Each team can independently change the internal implementation of its plugin as long as it preserves its requirements and provided capabilities.

The process remains common, but the boundaries of responsibility become explicit:

Search Team:
    provides "search"

Research Team:
    requires "search"
    provides "research"

Interface Team:
    requires "research"
    adds interface slots

In the official Cordis guide, a service is defined as a named capability that one plugin provides, and others receive through ctx. The dependent component accesses the service via a context property—for example, ctx.tools, ctx.llm, or ctx.agents—rather than importing a specific implementation. The name of a required service is specified in inject; the runtime keeps the component in the PENDING state until all necessary dependencies are available.

A module helps organize source code, while a plugin contract makes explicit the conditions under which a component can be active in the current composition. This doesn't shrink a large system into a small one, nor does it eliminate the need for architectural design.

Cordis reduces the amount of global knowledge required for local modification.

A component's author only needs to understand:

  • the available Context;

  • declared dependencies;

  • provided services;

  • events and registries it connects to;

  • its own configuration;

  • effects not covered by standard Cordis means.

However, such locality is maintained only if common agreements remain not just in documentation but are automatically verified at runtime.

From Documented Assumptions to Verifiable Invariants

A significant portion of complex architecture errors arises from assumptions that exist only in documentation or team memory:

"this service always starts first";
"this event handler is always removed";
"the provider never disappears";
"another plugin won't register the same name";
"this configuration is always valid".

Cordis does not prove the correctness of business logic. It cannot establish that a search algorithm yields good results or that an AI-generated interface meets product requirements. But it allows certain compositional assertions to be verifiable:

required services exist;
plugin is not activated until dependencies are available;
loss of a dependency changes the lifecycle state;
service has an owner;
registration is tied to plugin lifetime;
configuration passes schema validation;
deletion of a component triggers its cleanup functions.

Composition checks in DeepSeek Harness are complemented by a registry of runtime invariants—conditions that must be met during application operation. Each package can register its own check in ctx.invariants under its npm name. If a condition is violated, the registry generates an error indicating the package to which this contract belongs.

Such checks should describe the meaningful behavior of the system. For example, they can verify that one event occurs only after another, or that related mutable data does not contradict itself. A simple check for the existence of a service or method is not considered an invariant.

Therefore, instead of stating:

Cordis proves application correctness,

it's better to say:

Cordis transforms part of architectural assumptions into explicit contracts and invariants, the adherence to which can be automatically verified during application operation.

How Cordis Works

The basic structure of Cordis is built around three entities. Context defines which services are available to a component, Service registers a service under a permanent name, and Fiber represents a loaded plugin instance and its lifecycle. Together, they allow tracking component dependencies and undoing changes made by it upon unloading.

At the core of Context is a container of named services. One component registers a service under a permanent name, and another declares that it needs this service.

A simplified component providing a service looks like this:

import { Service, type Context } from "cordis";

declare module "cordis" {
  interface Context {
    search: SearchService;
  }
}

class SearchService extends Service {
  constructor(ctx: Context) {
    super(ctx, "search");
  }

  query(text: string) {
    // ...
  }
}

export function apply(ctx: Context) {
  ctx.plugin(SearchService);
}

A dependent component accesses not the SearchService class, but the search service:

import type { Context } from "cordis";

export const inject = ["search"];

export function apply(ctx: Context) {
  ctx.search.query("spatiotemporal composability");
}

The declare module "cordis" block informs TypeScript that Context has a search service of type SearchService. This allows TypeScript to check accesses to ctx.search. The service itself does not create this declaration.

A real service registers the SearchService class during application runtime. When the component providing the service is unloaded, Cordis removes its registration.

But Context is not just a service container. It links a component's requirements to its effects: it defines available services and tracks introduced changes so that Cordis can undo them upon unloading.

Calling ctx.on() registers an event handler, and ctx.plugin() registers a child component. Services provide named capabilities to other components. For external resources, ctx.effect() is used: the function passed to it creates a resource and returns a cleanup function.

For example:

export function apply(ctx: Context) {
  ctx.on("request", handleRequest);

  ctx.effect(() => {
    const timer = setInterval(refreshCache, 10_000);

    return () => {
      clearInterval(timer);
    };
  });
}

Cordis associates all such registrations with the current plugin instance. Each loaded instance corresponds to a Fiber—a utility object that stores state and manages the plugin's lifecycle:

PENDING means the plugin is declared, but a required dependency is currently missing. If a dependency disappears, an active Fiber goes through UNLOADING and returns to PENDING; when the dependency reappears, it can be loaded again. In UNLOADING, the runtime calls cleanup functions. DISPOSED means the Fiber has been permanently removed. Calling fiber.dispose() completes only after the cleanup functions registered in Cordis are executed and child plugins are recursively unloaded.

This results in an ownership hierarchy:

Root Context
│
├── Plugin A Fiber
│   ├── service
│   ├── event handlers
│   └── child plugin
│
└── Plugin B Fiber
    ├── timer
    └── intermediate handler

This hierarchy forms the basis of the application's lifecycle.

Scientific Foundation: Spatiotemporal Composability

Cordis's design is based on the idea of spatiotemporal composability, described in the paper A Programming Paradigm for Spatiotemporal Composability. This is what the authors call a system's ability to safely add and remove components during operation. To achieve this, two independent tasks must be solved:

  1. track dependencies between components;

  2. completely undo changes made by a removed component.

The first task is called spatial composability, the second—temporal.

Spatial Composability

Spatial composability describes dependencies between components.

For example, the "Research" plugin might declare that it needs a search service and a database to function. Cordis activates it only when both services are available. If the search service then disappears, the plugin can no longer remain active, even if the database is still available.

Cordis treats the dependency graph not as a schema built once at startup, but as a living structure.

The official guide emphasizes that dependencies from inject continue to be tracked after loading. If a required service disappears due to the unloading or hot-swapping of its provider component, dependent plugins are also unloaded. When the service reappears, they are loaded again with the new implementation.

In the scientific paper, this is modeled through reactive effects: a component declares requirements for the context, and changes in the context cause the runtime to re-evaluate whether the component can remain active.

Temporal Composability

Temporal composability deals with the changes a component has made over time.

If a plugin:

added an event handler;
registered a service;
created a timer;
connected an intermediate handler;
added a child plugin;

then upon its removal, these changes must be undone.

Registrations made through the Cordis API are considered effects. For resources outside the standard APIs, ctx.effect() is used: the function passed to it creates a resource and returns a cleanup function. When the owning plugin is unloaded, the runtime calls these functions.

In the scientific paper, this is formalized through reversible effects: each context transformation is accompanied by an inverse operation tracked by the runtime.

Why These Dimensions Are Inseparable

Spatial composability determines under what environmental conditions a component can be active. Temporal composability determines how to undo the changes it introduced upon unloading.

required dependency disappeared
         ↓
component requirements are no longer met
         ↓
component is unloaded
         ↓
system undoes effects created by it

Without reactive dependency tracking, the runtime doesn't know when their structure becomes invalid. Without tying effects to owners, automatic reaction to changes in this structure leaves residual state.

The main theoretical step by the authors is to combine the tracking of effects and environmental requirements into a single Context abstraction. Thus, tracking requirements and rolling back effects become parts of a single dynamic composition model. On this basis, the authors formulate a meta-theory that transfers the properties of an individual component to a system of components with alternating execution. They also link the formal model to the Cordis core, declarative loader, configuration reconciliation, and HMR.

For a JS/TS framework, such a theoretical foundation is unusual. Of course, it doesn't prove the correctness of any application: formal results apply only within the given model and its premises. What's important is that Cordis's key properties are described not only as convenient API agreements but also at the level of operational semantics and meta-theory.

What's Innovative for the JavaScript and TypeScript World

Cordis's novelty lies not in individual mechanisms. Plugins, dependency injection, and dynamic services existed in other ecosystems long before it.

For example, OSGi has long provided Java applications with a dynamic service registry. Modules can publish and find services, as well as receive notifications about changes in the registry. The Declarative Services mechanism deactivates a component if a required service disappears and activates a new instance when a suitable replacement appears.

Therefore, Cordis cannot be considered the inventor of dynamic component lifecycles. Its novelty lies in the combination of several mechanisms into a single model:

Cordis combines reactive dependency management, effect ownership, hierarchical Context, configuration reconciliation, and formal descriptions of these properties.

It is particularly important that Cordis manages different types of effects uniformly. An event handler, a service registration, a tool, an intermediate handler, a child plugin, and a user-defined resource are all treated as different manifestations of one common idea:

a change belongs to the lifetime of a specific component.

The strength of the approach lies in a unified discipline that can be applied not to one subsystem, but to the entire running application. Therefore, Cordis's innovation is not in a single primitive, but in the combination of these mechanisms at the application level.

Client and Server: Unified Composition Model, Different Loading Mechanisms

One of Cordis's strengths is the same composition model for both client and server parts. DeepSeek Harness shows that Cordis principles can manage components on both sides of the boundary.

In a Node.js process, one Cordis plugin tree operates; in the browser, a second one does, where each UI capability is also represented by a plugin. The official description of the client architecture states this directly: both sides run Cordis, and React serves as a projection layer over the client context.

The same composition model, however, does not require the same module system. In a Node.js process, Cordis Loader can rely on standard loading mechanisms. In the browser, code can reach the application as part of the overall build, as a remote module, or as an artifact of a specialized module system. In all cases, it's useful to separate two responsibilities:

Loading Mechanism:
    finds code;
    delivers it to the browser;
    forms module exports;

Cordis Composition Environment:
    verifies plugin requirements for the environment;
    mounts and unmounts plugins;
    associates effects with their lifecycles;
    reacts to composition changes.

The boundary between these layers is crossed when the loader can return a module export suitable for mounting as a plugin. It can deliver the same code in different ways without changing the composition contracts.

Cordis doesn't need to own the specific method of code delivery. It manages the component's life after the loading mechanism makes the code available.

The three architectures below draw this boundary differently. A virtual registry generated by the bundler includes plugins in the application's shared module graph. Module Federation links the application with independently built and deployed remote modules. DeepSeek Harness builds its own module system tailored to the product's specific requirements.

Virtual Modules: Plugin Registry in a Shared Build Graph

The first option is to create a plugin registry at the build stage using a virtual module. This is a module that doesn't exist in the file system: its identifier and content are defined by the bundler's extension. The application imports this module like any other, obtaining the set of plugins known at build time.

This technique is not tied to a single tool. Virtual modules are supported by Vite, Rolldown, Rollup, esbuild, and Rspack. Their APIs differ, but the principle is the same: the generated module becomes part of the shared graph and is processed along with the rest of the code.

For example, a Vite plugin can find components by configuration, manifests, or file structure and create a registry that the application imports as a standard ESM module:

import { plugins } from "virtual:plugins";

The source file virtual:plugins does not exist. When the application imports this module, the Vite plugin handles the request: resolveId recognizes the virtual identifier, and load returns the generated source code. This code might contain static or dynamic imports of known plugins.

In this architecture, plugins are linked to the main application during the formation of its module graph—either during development or the final build. During the final build, a dynamic import of a plugin can be transformed into a separate chunk that the browser will load only when the plugin is accessed. This chunk remains part of the overall build: its content and address are determined along with the main application. Therefore, a plugin cannot be released or updated independently of the main application.

This scheme is relatively easy to maintain: the bundler sees all plugins and forms a single set of files from them and the main application. Plugins don't need to be deployed separately, and their versions don't need to be coordinated with the application at runtime. The cost is a shared build and deployment cycle: to add a plugin unknown to a previous build, the main application must be rebuilt, or a dynamic loader must be pre-embedded into the virtual module. In the latter case, delivery is handled not by the virtual module itself, but by an adapter generated by it.

Module Federation: Linking Independent Builds at Runtime

The second option is to build plugins as remote modules compatible with Module Federation and link them with the application at runtime. This architecture is not tied to a single bundler: official integrations exist for Webpack, Rspack, Vite, Rsbuild, Metro, and other tools.

On the main application side, you can use a bundler plugin or include the Module Federation Runtime as a standalone library. In the latter case, the Runtime registers remote builds, loads them, and returns exports via loadRemote. The project publishing the remote module still needs a compatible bundler integration to create the Module Federation artifact.

When registering a remote build, the main application can provide Module Federation Runtime with the URL of remoteEntry.js or mf-manifest.json. remoteEntry.js is not the MF Runtime itself. It's the entry point of the remote container, providing get and init operations. The manifest describes published modules, files, and shared dependencies; Module Federation Runtime reads it and determines the final entry point URL.

The general scheme looks like this:

The main application and the remote build can be built, updated, and deployed independently of each other. Module Federation Runtime links them at runtime and coordinates shared dependencies. The cost is a distributed contract of versions, caches, network failures, and initialization order. Module Federation handles the loading of the remote build and coordination of shared modules, but it doesn't answer questions about which runtime services a plugin needs, who owns its effects, and how to release those effects upon unloading. These tasks are left to Cordis.

DSH Client Module System: Specialized Loading Mechanism

The third option is to not use a ready-made remote module protocol but to build a module system tailored to the constraints of a specific product. This is precisely how the DeepSeek Harness client module system is structured.

Each DSH client plugin is compiled into a separate client.js file and is not included in the main Vite client build. The package specifies this file in dsh.client. The server takes only the plugins connected in Cordis and compiles a list of modules the browser will need. The identifier for each module is the npm package name.

Typically, client.js is not listed in index.html as a ready-made <script>. The server provides the browser with a list of modules and their addresses and revisions, and serves the files themselves on demand. When a module needs to be preloaded or used for the first time, ClientModuleSystem by default dynamically creates an asynchronous <script src="...">. The browser receives the file from the DSH server and executes it as a classic script, not an ESM module. Plugins marked with immediately are loaded at the startup of the client module system; others are loaded as needed.

Loading a file does not yet run the plugin. The script only registers a function that can create the module. ClientModuleSystem calls it upon the first access to the module, saves the obtained exports, and then reuses them. During hot-swapping, invalidate(id) removes the old factory and exports, after which prefetch(id) loads the new script and registers a new factory.

DSH does not replace Cordis Loader with its module table. The browser repeats the same separation of responsibilities as the server: the module system is responsible for bytes and module identification, while the same implementation of Loader included in the project manages waiting for services, activation, updates, and Fiber cleanup. Therefore, server and client plugins follow the same lifecycle model with different module acquisition mechanisms.

A custom system gives DSH control over delivery order, lazy execution, versions, source maps, and hot module replacement (HMR). But this flexibility makes all the listed mechanisms the project's own responsibility. The architecture note explicitly states that Module Federation was considered but rejected: the project needed a format for independently built plugin assemblies, which the considered Vite integration of Federation did not support.

In practice, the choice starts with one question: do plugins need to be updated independently of the main application? If not, a registry generated by the bundler is sufficient. If plugin builds must be updated and deployed independently, Module Federation provides a ready-made protocol. A custom mechanism, as in DSH, makes sense when the existing protocol doesn't support the required artifact format or loading model, and the project is prepared to maintain this system itself.

None of these mechanisms negate Cordis's tasks. They determine how a module's export appears in the browser. Cordis determines how that export becomes a running component and how its impact on the system disappears upon unloading.

What Microservices Explain

The code delivery method itself does not define the strength of the boundary between components. To understand what Cordis provides and cannot provide within a single process, a comparison with microservices is useful.

A microservice gains a strong boundary due to its separate process. If the process is stopped, the operating system frees its memory and local resources. There's no need to separately figure out which objects or timers belonged to it.

The process boundary is an expensive but reliable ownership mechanism.

Microservice
    identity      = process
    interaction    = network
    lifecycle    = deployment / shutdown

Cordis attempts to gain some lifecycle independence within a single process:

Cordis Plugin
    identity      = Fiber
    interaction    = services / events
    lifecycle    = mounting / unloading

However, the similarity ends where isolation begins.

A Cordis plugin runs in the same process and execution environment as other components. Therefore, Cordis itself does not isolate its failures: an infinite loop can halt processing in the entire process, and a memory leak can exhaust the process's available memory. Such a plugin also cannot be scaled independently of the application or implemented on a completely independent technology stack, like a microservice.

On the other hand, composition within a single process:

  • is significantly cheaper;

  • preserves local calls;

  • is suitable for small functional capabilities;

  • is suitable for many relatively small components;

  • does not require turning every architectural boundary into a network one.

Therefore, Cordis occupies the space between a regular module and a microservice:

module
   ↓
Cordis plugin
   ↓
microservice

Each level has its own cost and boundary strength.

What Kubernetes Explains

The technical history of Kubernetes shows why Kubernetes needed an explicit state model and independent asynchronous controllers. This helps understand two key ideas of Cordis Loader: reconciling desired and actual states, and explicit resource ownership. This is not about containers or cluster management, but about the model of managing composition within a running application.

A Kubernetes controller compares the actual system state with the desired state. The user describes the result, and the controller determines which actions will bring the system closer to it, and then re-checks the state.

Furthermore, Kubernetes explicitly describes ownership relationships and turns deletion into a managed process. An analysis of an object's full lifecycle shows how ownerReferences links a dependent resource to its owner, and finalizers delay physical deletion until the controller completes necessary cleanup.

Cordis Loader applies a similar principle within the application.

Instead of a sequence of commands:

load A
load B
stop C
restart D

a desired composition is specified:

A
B
D-v2

Cordis Loader compares the specified composition with the current plugin tree and determines which plugins need to be loaded, updated, or unloaded. The authors of the scientific paper describe this mechanism as a declarative component loader: the developer specifies the desired configuration, the system brings the current state into compliance with it, and can replace modules without a full application restart.

Cordis as an API Between Teams, AI, and Architecture

A plugin contract is particularly valuable not because AI code is necessarily worse than human code. Coding agents make new implementations cheap, but the cost of their integration, verification, and safe removal remains high.

If an agent edits arbitrary parts of the application, a change might affect the startup code, routes, registries, and overall state. A plugin contract localizes such changes: the agent creates a component with explicit requirements, capabilities, and configuration, and the host integrates it through a predefined composition protocol.

This creates an important balance:

The freedom of code generation within a component is combined with the strictness of its integration rules.

In this sense, Cordis can be viewed as an API between AI and application architecture. Just as a tool's API limits the ways an AI agent can interact with an external system, a plugin contract defines how a component created by the agent is embedded into the application's architecture.

AI's non-determinism should not extend to the architecture. A plugin contract doesn't guarantee that the generated code will be correct, but it makes its integration predictable: it allows checking dependencies, associates side effects with the component, and manages resource release.

Architecture as Mutable Runtime State

DeepSeek Harness provides an optional package @deepseek-ai/dsh-tool-cordis. When explicitly connected, it allows an AI agent to temporarily modify the set of plugins directly during application runtime.

The package registers Cordis management tools. With their help, an agent can view the current Cordis tree, create a temporary in-memory plugin, connect it, and then stop or remove it. Upon unloading, Cordis releases resources whose cleanup is registered via Context: it removes tools, event handlers, and services registered by the plugin, stops managed timers, and executes other disposers. Unloading completes only after this cleanup is finished. The plugin does not create project files or change its configuration; its runtime definition disappears after DeepSeek Harness restarts.

In other words, the user describes the desired functionality in a prompt, and the LLM generates JavaScript and, upon calling cordis_define, passes it as a string in the code.host field for the server-side plugin or in code.client for the part executed in the browser. This call checks the syntax and registers the package in the application's server-side memory. Then, cordis_run starts the server-side and, if present, the browser-side part of the plugin. If the experiment is successful, the plugin can be formalized as a permanent part of the project; if not, it can be removed.

In this mode, a plugin can be viewed as an architectural hypothesis:

This is no longer just hot reload. It's a speculative architecture where the application's composition itself becomes an object of experimentation. In fact, the main application defines the space of architectural degrees of freedom—the set of available services, events, and extension points—within which the LLM can propose and test new composition variants. The initiator of such an experiment can be either a developer or a system user.

What Cordis Does Not Guarantee

Managed lifecycle allows temporarily loading plugins, observing their behavior, and then unloading them. However, this does not mean that Cordis sees all their effects, knows how to reverse any action, or ensures safe isolation. Therefore, Cordis's boundaries must be explicitly formulated.

Plugin Contract Is Not a Security Boundary

Cordis manages dependencies, effect ownership, and lifecycles, but it does not isolate untrusted code. A plugin runs within the application's process and can access capabilities available to it as regular JavaScript code. Limiting CPU time, memory, module imports, file system, and network access requires a separate sandbox or capability layer.

Only Mediated Effects Can Be Managed

Cordis sees:

ctx.on(...)
ctx.plugin(...)
ctx.effect(...)

But a plugin can bypass Context:

globalThis.value = 1
setInterval(...)
externalLibrary.register(...)
fetch(...)
sendEmail(...)

The runtime cannot automatically know who owns an arbitrary change and how to undo it.

Fundamental rule:

ownership requires mediation

For Cordis to associate an effect with a plugin and undo it upon unloading, the effect must be created through Context or explicitly registered using ctx.effect().

Not All Effects Are Reversible

Local registrations can usually be removed:

register handler ↔ remove handler
add route            ↔ remove route
provide service       ↔ revoke service

Resources can be terminated:

open connection ↔ close connection
start timer   ↔ stop timer

But actions in the external world are often irreversible:

email sent;
payment made;
message published;
remote database modified.

For such actions, transactions, compensating operations, idempotency, consensus, and commit protocols are needed. Temporal composability does not guarantee that an external system can be returned to its previous state.

The Cost of an Additional Architectural Layer

Managed composition comes at the cost of a new layer of complexity. Some complexity moves out of component code and into the runtime.

Cordis adds:

  • a dynamic dependency graph;

  • a service namespace;

  • its own lifecycle;

  • new states like PENDING and UNLOADING;

  • the need to diagnose reasons for activation and unloading;

  • version compatibility rules;

  • state migration issues;

  • errors within disposers;

  • the cost of restarting dependent components.

In a simple application:

import { search } from "./search";

search();

is almost certainly better than a full plugin runtime.

A plugin model is justified when the system truly needs:

client and server extensions;
variable composition;
replaceable providers;
runtime configuration;
hot-swapping;
a long-running process;
capabilities generated by AI.

That is, the principle of Everything is a Plugin should not be turned into a universal dogma. It is useful where global connectivity is more expensive than a mechanism for managing component composition.

Conclusion

Cordis proposes viewing an application not as a once-built module graph, but as a living composition of components. Dependencies, effects, and lifecycles become part of a shared executable model for both client and server.

In systems with AI, this creates a new level of interaction with the architecture: the application defines the permissible space of changes, within which a developer or user via an AI agent can experiment with its composition.

Therefore, Cordis's main contribution can be formulated as follows:

Cordis transforms the plugin system from a program extension mechanism into a protocol that manages the appearance, replacement, and disappearance of its components during operation.
