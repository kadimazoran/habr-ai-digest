WebGPU provides direct access to modern graphics card capabilities, not just for rendering but also for general-purpose computing via compute shaders.

But how far can this be pushed in a regular browser? What happens when computations involve a full-fledged simulation with tens of millions of objects? We'll explore this in the article.

Background

For this experiment, we'll try to revive an evolution simulator written many years ago and rewrite its logic from CPU to GPU. I discussed this project in more detail in another article, but reading it is not mandatory – I'll retell the important points.

My cellular simulator was written in C# and structured quite naturally: a two-dimensional matrix of objects, a separate list of living cells, and a foreach loop that called their logic on each tick. A cell would look around, choose an action, and immediately change the overall world. This was enough to see populations emerge on the screen, competing and evolving.

The web version of that simulator allowed creating worlds up to 200 × 200. Let's try to raise the bar to 8192 × 4096. That's about 33 million cells, each of which can potentially be occupied by a living cell.

Let's Tackle Memory First

If we allocate just one 32-bit number for each of the 33 million positions, that's already 128 MiB. And one number isn't enough: we need to store the cell's age, species, energy, individual traits, and intermediate data required for calculating the world's next state.

On the CPU, it's convenient to group all this into a single object of type Cell. But at this scale, the familiar OOP approach becomes quite expensive. Add another 4-byte field to each position – potentially another 128 MiB.

In the GPU version, I divided the state into several arrays. One stores the primary information about the cell's content, while energy, individual traits, and species genomes are stored separately. Temporary data for a single tick also resides in its own arrays.

This division proved useful not only for memory savings. Different computational passes require different data: a shader that changes energy doesn't necessarily need to see the entire cell state, and a renderer doesn't need temporary requests for cell movement at all. As a result, the memory structure depends on how this data will flow through the GPU.

From Sequential Tick to Parallel

In the old version, the game simply took a list of living cells and called their logic one by one. A cell would look at its neighbors, choose an action, and immediately modify the overall world. The next cell would then see the result of the previous move.

This means the order of traversal subtly became part of the simulation's rules.

This approach cannot be directly transferred to the GPU. Thousands of cells can be processed simultaneously, and you cannot assume that one will necessarily finish before another. For example, two cells might simultaneously spot an empty position and both decide to move there.

Therefore, a single tick is now broken down into several sequential stages.

First, cells only make decisions and record their Intent – what exactly they want to do. The world's state itself does not change yet.

Then, Claims appear – requests for what the cells are competing for. If multiple cells claim the same position, the conflict is resolved separately according to a predefined rule.

Only after conflict resolution does the Apply stage begin, which actually modifies the world's state.

This requires more intermediate memory and several computational passes, but the result of a tick no longer depends on the random execution order of thousands of parallel threads.

How to Display 33 Million Cells

By this point, the world is alive and changing on the GPU. And here arises a rather natural question: why return it to the CPU at all, just for an image?

One could copy the state back to JavaScript after each tick and draw from there. But at such sizes, data exchange itself would quickly become a separate problem.

For this reason, there is no full CPU copy of the world in the new version. Rendering reads the necessary data directly from the GPU buffers, and JavaScript primarily handles the interface, camera, and command sending.

When zooming out significantly, another problem arises: an individual cell becomes smaller than a pixel. Drawing it as an independent object is no longer meaningful.

Therefore, the distant view is constructed from aggregated world sections. The further the camera, the less important a specific cell becomes, and the more important the overall picture is: population density, resources, and species distribution.

What We Got

To test, I tried to maximally load the simulation and fill the entire available world with cells.

Even in this mode, on my computer, the simulation calculates approximately 5–10 full ticks per second.

Of course, 5–10 ticks/s is not a universal characteristic of WebGPU. The speed depends on the graphics card, browser, simulation settings, and the number of living cells. But for me, the principle is more important: a simulation with tens of millions of active objects is quite feasible right in a regular browser tab.

Conclusions

When I started this remake, my main interest was to understand how large a living world could be simulated directly in a browser tab.

Judging by the result, tens of millions of objects is a perfectly workable scale. But to achieve this, it's not enough to simply port the old code to the GPU; you have to rebuild the data and computation logic itself for its operational model.
