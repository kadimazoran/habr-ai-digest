When I was once asked what inference is and what local model deployment looks like, I answered correctly but too generally: load weights, start runtime, expose API, connect application.

I understood the theory. But the honest answer was: I didn't have personal experience yet where all this goes from model files to a working user scenario.

A few days later, I gained that experience.

In two days, I needed to set up two local LLMs on NVIDIA DGX Spark, deploy a separate speech recognition model on a mini-PC with an AMD GPU, expose everything via persistent APIs, and connect it to the IskraBot AI agent platform within a corporate client's environment.

The task turned out to be a useful reminder: "the model launched" and "the AI function is working" are entirely different levels of readiness. Between them lie hardware and runtime compatibility, memory management, queues, long context, streaming output, tool calling, observability, and response quality on the real route.

In this article, I will break down this journey specifically as an engineering case: what had to be designed, what measured, which optimizations worked, which had to be rolled back, and why a functional check on 256,000 tokens still doesn't mean production-ready.

All data pertains to a pilot environment. The client is anonymized. Individual measurement results cannot be mechanically transferred to other hardware, models, and user scenarios.

Initial Task

The IskraBot multi-agent platform was already in place. The models needed to be hosted locally and connected to three compute services:

  • the main LLM for complex user requests;

  • a faster LLM for auxiliary and potentially simple tasks;

  • an ASR model for transcribing audio and video.

This resulted in the following diagram:

User
    │
    ▼
IskraBot: agent orchestration, history, tools
    │
    ├──► Main LLM ──► DGX Spark #1
    │
    ├──► Fast LLM ──────► DGX Spark #2
    │
    └──► ASR API ───────► Beelink / AMD Radeon / WSL2

The two Sparks used:

  • Qwen3.8-27B-FP8 as the main model;

  • Qwen3.6-35B-A3B-NVFP4 as the fast model.

For speech recognition — Qwen3-ASR-1.7B on Radeon 8060S in WSL2.

For LLMs, vLLM was chosen. It can launch an OpenAI-compatible HTTP server, allowing the application to call local models via the familiar /v1/chat/completions endpoint without needing a separate integration for each runtime.

This is an important architectural decision: a standardized contract separates the application from the specific inference implementation. The model, quantization, or server parameters can be changed beyond the API boundary without rewriting the entire agent layer. However, a compatible endpoint does not guarantee compatible behavior — especially in streaming and tool calling. We'll return to this.

Day One. Model Files Are Not Yet a Service

In casual conversation, "deploying a model" often sounds like "downloading and running it." In practice, a model in a repository is a set of artifacts:

  • weights and their format;

  • architecture configuration;

  • tokenizer;

  • chat template;

  • sometimes additional model code;

  • quantization metadata.

By themselves, they don't accept HTTP requests, limit parallelism, check keys, write useful metrics, or recover after restarts.

In an applied sense, inference is the execution of an already trained model on input data. But a local inference service is more than a single generate() call. Its minimal setup looks like this:

model artifacts
      +
compatible runtime
      +
GPU driver and compute stack
      +
HTTP API / streaming / auth
      +
healthcheck / logs / restart policy
      =
a service that can be connected to an application

The first engineering check, therefore, is not "does the number of parameters fit in memory?" but the entire compatibility matrix:

  1. CPU architecture;

  2. GPU generation and capabilities;

  3. CUDA or ROCm and driver version;

  4. support for specific quantization;

  5. availability of necessary kernels in the runtime;

  6. weights format and chat template;

  7. container image architecture.

In our case, Spark is an ARM64 system based on Grace Blackwell. According to the NVIDIA specification, it has 128 GB of unified system memory, shared between CPU and GPU. This allows working with large models in a compact form factor but doesn't eliminate competition for memory between weights, KV cache, runtime, and other processes.

The ASR setup was different: AMD Radeon in WSL2 and ROCm. This means the same phrase "run the model on GPU" hid two different stacks, different images, and different diagnostic methods. For WSL2, AMD has a separate installation path and compatibility matrix; transferring CUDA instructions to such a node is pointless.

As a result, reproducible containers were built, weights were moved to persistent storage, servers received API authentication, health checks, and restart policies. After this, the model could be considered not a one-off process in the terminal, but part of the integration pipeline.

With a security caveat: the built-in API key in vLLM does not protect all possible endpoints. The official documentation directly recommends considering this when publishing the server and, if necessary, placing it behind a reverse proxy. "Having a key" and "the service surface is secured" are not the same thing.

Memory: Weights Are Just the Beginning of the Formula

The next trap is to estimate memory consumption solely by the size of the weights.

For a rough engineering model, it's more useful to keep in mind:

process memory ≈ model weights
                 + KV cache
                 + working buffers and graphs
                 + runtime overhead
                 + memory of other processes

Weights are primarily determined by the number of parameters and the storage format: FP8, FP4, and so on. KV cache depends on the model architecture, context length, number of concurrently executing sequences, and its dtype. Working memory changes with prefill settings, CUDA graphs, and specific kernels.

This is precisely why the question "will the model fit?" is incomplete. It's more accurate to ask:

  • with what maximum context will it fit;

  • how many requests can it execute simultaneously;

  • what buffer will remain for the system;

  • will KV cache evictions or swap occur;

  • what will happen with two long requests at once.

Why the 256K Window Came at the Cost of Parallelism

The initial configuration worked with a 32K window. This was insufficient for real agent scenarios: system instructions, tool descriptions, history, documents, and intermediate results quickly consumed tens of thousands of tokens. The goal became a 256K window — more precisely, 262,144 tokens.

Both LLMs ultimately accepted 259,616 input tokens simultaneously and found four out of four control values. During this functional check, there were no OOMs or crashes.

This sounds like a victory. But the price was quite specific: for each model, only one concurrently executing sequence was allowed. Other requests waited in the queue.

This is one of the main takeaways from the case:

Context length is not an isolated quality parameter. It's part of the resource budget along with memory, parallelism, TTFT, and throughput.

On the main model, a joint run of 256K took 510.32 seconds, on the fast model — 243.62 seconds. The main model registered seven KV cache evictions, while the fast model had none. The minimum available RAM during the test was 20.24 GiB, with swap usage around 1.04 GiB.

vLLM, when lacking KV cache space, can preempt a request and later recompute part of its state. This maintains operability but degrades end-to-end latency; this effect is also described in the vLLM optimization guide.

Thus, the acceptance test proved: the servers functionally support long context. It did not prove that the user is willing to wait eight minutes or that the system can handle acceptable load from multiple users.

LLM Speed Is Not a Single Number

"How many tokens per second?" is a useful but insufficient question. In a user scenario, there are at least two distinct phases.

Prefill — processing the entire input context. It accounts for a significant portion of the time until the first token, especially with long requests.

Decode — sequential generation of the response after prefill. This is where output tokens per second are typically measured.

For the user, at least the following are important:

  • TTFT — time to first token;

  • decode speed;

  • total scenario time;

  • time in queue;

  • time for external tools;

  • stability of streaming output.

Therefore, optimizations were measured separately, and their percentages were not added together.

Faster Is Not Always Better

The natural next idea is to send simple and auxiliary tasks to the fast model, leaving the main model for complex requests.

Architecturally, it seemed reasonable:

request
  │
  ├── simple / auxiliary ──► fast LLM
  └── complex ──────────────► main LLM

The fast model did indeed speed up some instrumental tasks. However, it thrice failed to follow a short instruction. The alternative mode of the main model without thinking, in turn, failed to complete one parallel chat.

Both routing options were rejected, and the original backend was restored.

This was perhaps the most architectural moment of the entire effort. Optimization should not be applied to the model server in isolation, but to the product's objective function:

utility = response quality
          × probability of correct action
          × acceptable latency
          × operational stability

If a model responds three times faster but follows instructions worse or chooses the wrong tool, the system has not become more effective. It simply produces defects faster.

Integration Is Not Verified by a Test Prompt

After the OpenAI-compatible endpoint appeared, it's easy to assume the main work is done. For a regular chat, this is sometimes sufficient. For an agent, it is not.

The agent pipeline adds:

  • event streaming;

  • structured tool calls;

  • argument schemas;

  • re-turns after tool execution;

  • history and system instructions;

  • tool error handling;

  • protection against unwanted side effects.

In one short real chat, the agent made an unsolicited calendar entry, then canceled the created event. The event did not trigger, but the choice of action itself was a defect. Such a case would not be detected by a health check and would almost certainly not be shown by a single request like "write a poem."

In another test, the model incorrectly wrote the number 10,555 in words — "ten thousand five hundred five" — and on the next line, it effectively contradicted its own answer. We did not establish a causal link with MTP, quantization, or context: this would require a separate experiment where only one factor is changed at a time.

Here, it's important not to fall for the easy explanation. After performance tuning, any new error seems to be a consequence of the latest optimization. But temporal proximity is not causality.

ASR: A Fast Service Doesn't Guarantee a Fast User Turnaround

A persistent ASR service was launched on a separate node. In warm synthetic tests:

  • 20.9 seconds of audio were transcribed in 1.9 seconds;

  • 83.6 seconds — in 9.9 seconds.

WAV, WebM/Opus, and M4A/AAC formats were tested, as well as silence and corrupted files. However, long video revealed a limitation: attempting to send large chunks resulted in ASR failure.

The solution was moved to the application side: video was split into 60-second fragments with a 3-second overlap. Overlap reduces the risk of losing a word at chunk boundaries, although it later requires dealing with repetitions.

A video 28 minutes and 55 seconds long was processed in 150.96 seconds: 31 out of 31 parts, 18,223 characters of output.

This confirms the successful processing and retention of all parts, but not the complete accuracy of the transcript. Listening to the entire material, the quality of names, repetitions at seams, timestamps, and speaker diarization remained separate acceptance criteria.

More telling was a user request with 21 seconds of audio. The transcribe_file call itself took 2.03 seconds and correctly extracted the meeting time, three topics, and a control number. The full agent turn took 106.41 seconds.

Why? After ASR, the model still had to process the accumulated context, plan an action, call a tool, and generate a response. In two very short chats, each request to the main LLM contained 46,697 input tokens.

Hence, another practical conclusion:

A fast component does not guarantee a fast scenario. The user's critical path must be measured in its entirety.

Context Turned Out to Be a Separate Architectural Debt

46.7K tokens for a short utterance is an alarming signal. This sum could include system instructions, tool schemas, attached skills, history, and user data. At the time of work completion, the exact breakdown had not yet been determined.

Simply increasing the window from 32K to 256K in such a situation is insufficient. A large window postpones the overflow error but simultaneously:

  • increases TTFT;

  • consumes KV cache;

  • reduces possible parallelism;

  • increases the cost of each extra instruction block;

  • makes the queue more noticeable to the user.

The next logical step is to introduce a context budget and observability of its composition:

input context
    ├── system prompt
    ├── tool schemas
    ├── skills / policies
    ├── history
    ├── user documents
    └── tool results

For each block, its size, reason for inclusion, and loading policy are needed. Some instructions can be loaded only as needed, stable prefixes can be reused, and history can be compressed or relevant parts selected.

This is no longer vLLM tuning. This is the architecture of an agent application.

An Incident That Cannot Be Automatically Labeled OOM

After the main work, one of the Sparks froze. Under high pressure on unified memory, such a state seems plausible, especially after long contexts, KV cache preemption, and swap writes.

However, the saved data did not provide sufficient confirmation that OOM was the cause. Therefore, the correct incident record is not "the model crashed the server due to memory," but:

the node froze; OOM is a hypothesis, the cause is unconfirmed.

The difference seems bureaucratic only until the first incorrect optimization. If the cause is a driver, kernel, power supply, or another process, reducing the context might mask the symptom but not eliminate the defect.

This is precisely where the line between a pilot and production is drawn. In a pilot, you can prove that the system functionally works. Production requires reproducibility, monitoring, alerts, managed recovery, a load model, and confirmed SLOs.

What was confirmed:

  • reproducible service startup;

  • connection to the agent platform;

  • functional long context on both LLMs;

  • transcription of several audio formats and long video;

  • measurable improvements in individual parts of the inference path;

  • managed rollback of unsuccessful routing.

What could not be honestly declared production-ready:

  • target latency and concurrency were not yet agreed upon;

  • a single active request created a queue;

  • the quality of the long transcript had not passed full acceptance;

  • the causes of incorrect responses and unwanted actions were not localized;

  • the composition of the 46.7K mandatory context was not analyzed;

  • the cause of the node freeze was not confirmed;

  • part of the chunking change remained a pilot delivery.

The term "production-oriented pilot" is more accurate here than "production-ready."

How I Now Answer the Question "What Does It Mean to Deploy a Model Locally?"

Deploying a model locally means more than just loading weights onto a GPU.

It means:

  1. selecting compatible hardware, drivers, runtime, format, and quantization;

  2. transforming model artifacts into a persistent service with a clear API;

  3. calculating the memory budget for weights, KV cache, and working buffers;

  4. making an explicit trade-off between context, parallelism, and latency;

  5. testing prefill, TTFT, decode, and the full user scenario separately;

  6. ensuring that streaming and tool calling are correct specifically for the agent application;

  7. measuring quality after each optimization, not just tokens per second;

  8. adding health checks, logs, metrics, restart policies, and degradation scenarios;

  9. distinguishing between a successful launch, a working pilot, and proven production stability.

Now, behind the words "launch local inference," I see not general phrases, but quite physical things: minutes of waiting for the first token, KV cache pressure, requests in the queue, 31 audio chunks, rolling back a fast model due to quality, and an incident with an unconfirmed cause.

And perhaps the main conclusion is this: local inference is not a property of the model. It is a property of the entire system around it.

Checklist Before the Next Local Deployment

  • [ ] CPU/GPU architecture, driver, and runtime versions are documented.

  • [ ] Model, dtype, and quantization support are verified.

  • [ ] Weights, KV cache, and system memory buffer are allocated.

  • [ ] Maximum context and actual parallelism are determined.

  • [ ] TTFT, decode, queue, and end-to-end latency are measured.

  • [ ] OpenAI compatibility, streaming, and tool calling are tested.

  • [ ] Auth is not just for show; the entire API surface is secured.

  • [ ] Healthcheck, restart policy, logs, and metrics are in place.

  • [ ] Quality is tested on real scenarios after each optimization.

  • [ ] Tool side effects are tested in a safe mode.

  • [ ] For long audio, chunking, overlap, and result assembly are defined.

  • [ ] It is separately documented what the pilot proved and what it has not yet proven.
