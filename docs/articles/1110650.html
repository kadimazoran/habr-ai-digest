Model Context Protocol (MCP) allows an agent like Claude Code or Cursor to call external tools. I connected my short link service this way: the agent writes a newsletter or release notes and creates a link with UTM tags itself, and then checks its clicks. The server turned out to be small, about 360 lines in pure Node.js, without SDK or dependencies. But almost every line in it appeared after the model behaved in a way I didn't expect.

In the article, I will break down how such a server is structured and five solutions that turned out to be more important than initially thought.

Architecture: a thin wrapper

The service already had a REST API with a key. The MCP server contains no logic of its own: it accepts a tool call, makes a request to the same API, and returns the response. All validation, limits, and security checks remain on the API server.

Pros of this approach:

  • one place where the rules live. If you change a limit or a URL check, MCP clients will get the change immediately, no need to update the package;

  • the MCP server can be run locally via npx, it only needs the API key and address;

  • it's easy to test: it's just a mapping of "tool → HTTP request".

async function callTool(name, args = {}) { if (!API_KEY) { throw new Error( "API_KEY is not set. Create a key at https://linkbit.live/api-keys and set API_KEY to the slk_ value.", ); } switch (name) { case "shorten_url": return api("/api/v1/links", { method: "POST", body: JSON.stringify(args) }); case "delete_link": return api(`/api/v1/links/${args.id}`, { method: "DELETE" }); // ... 7 more tools default: throw new Error(`Unknown tool: ${name}`); } }

Transport: stdio and two message formats

The local MCP server communicates with the client via stdin and stdout using JSON-RPC 2.0 messages. According to the specification, each message is a single JSON line. But in case the client or a debugging utility sends a message in LSP format, with a Content-Length header, the parser understands both variants:

function takeJsonMessages(chunk) { const messages = []; let rest = chunk; while (rest.length) { const headerMatch = rest.match(/^Content-Length:\s*(\d+)\r?\n\r?\n/i); if (headerMatch) { const size = Number(headerMatch[1]); const start = headerMatch[0].length; const body = rest.slice(start, start + size); if (body.length < size) break; // message not fully received, waiting for the rest messages.push(body); rest = rest.slice(start + size); continue; } const nl = rest.indexOf("\n"); if (nl === -1) break; const line = rest.slice(0, nl).trim(); rest = rest.slice(nl + 1); if (line) messages.push(line); } return { messages, rest }; }

Two important details:

  • stdin arrives in chunks of arbitrary length. One message can be cut in half, and one chunk can contain three messages. Therefore, a buffer is needed, and the unprocessed remainder must be returned.

  • Nothing but the protocol can be written to stdout. One accidental console.log breaks the client's parsing, and it silently disconnects the server. All debugging goes to stderr.

There are few methods that are actually needed: initialize, tools/list, tools/call, and ping. Notifications (messages without id) do not need to be replied to.

Solution 1. Errors are tool results, not protocol errors

The most obvious way is to return API errors as JSON-RPC errors. But then the client often just shows the model "tool failed", and it starts guessing: retrying the call, changing arguments, apologizing to the user.

MCP offers another way: return a regular result with the flag isError: true. Then the error text gets into the model's context as data, and it can work with it.

try { const result = await callTool(name, params.arguments || {}); reply(id, { content: [{ type: "text", text: JSON.stringify(result, null, 2) }] }); } catch (error) { reply(id, { isError: true, content: [{ type: "text", text: error instanceof Error ? error.message : "Tool failed" }], }); }

I kept protocol errors only for what is truly broken at the protocol level: unknown method, unknown tool, invalid JSON.

Second consequence: the error message should be written for the model, not for logs. Not 401, but:

401 Unauthorized: API_KEY is invalid. Create a key at https://linkbit.live/api-keys

Upon receiving such a response, the agent usually doesn't repeat the request but tells the user where to get the key. The same applies to limits and forbidden URLs: a short reason and what to do next.

Solution 2. Annotations for dangerous tools

Tools in MCP have hints for the client: readOnlyHint, destructiveHint, idempotentHint, openWorldHint. Clients use them to decide when to ask for human confirmation.

{ name: "delete_link", description: "Permanently delete a short link. This cannot be undone.", inputSchema: { type: "object", properties: { id: { type: "string" } }, required: ["id"], }, annotations: { title: "Delete link", readOnlyHint: false, destructiveHint: true, idempotentHint: true, openWorldHint: true, }, }

destructiveHint: true is set for deleting and disabling links. Reading lists and statistics is marked readOnlyHint: true, which the client calls without questions. The phrase "This cannot be undone" directly in the description is also helpful: the model reads the description and asks the user again itself.

It's important to remember that these are hints, not protection. The client can ignore them. Real restrictions are the key's permissions and checks on the API server.

Solution 3. The model "corrects" URLs, the server must be predictable

Models like to rewrite URLs "as they see fit." Imagine: the user asks to "shorten the link and add utm_source=newsletter," but the URL already contains utm_source=partner. What should take precedence?

I decided that existing parameters in the URL are not overwritten, and the anchor #fragment is preserved. The link often comes from a finished campaign, and someone consciously set the tags in it. This is enforced by a test on the API side:

it("does not overwrite existing utm_* params", () => { const out = applyUtm("https://example.com/?utm_source=original", { utm_source: "other", utm_medium: "cpc", }); const url = new URL(out); assert.equal(url.searchParams.get("utm_source"), "original"); // old tag remained assert.equal(url.searchParams.get("utm_medium"), "cpc"); // new one was added });

And the same rule is written in the tool description: "Optional UTM fields are merged without overwriting existing utm_* params." The model reads the description and stops being surprised by the result.

General conclusion: if the model can pass extra or conflicting information, the server's behavior should be deterministic and documented. Don't expect the model to pass "correctly."

Solution 4. Partial success in batch operations

The shorten_urls tool creates multiple links at once. If one out of ten fails validation, throwing an exception is bad: nine links are already created, and the model will decide that nothing worked and restart everything.

Therefore, the API for a batch responds with an object containing two arrays, created and errors, and the MCP server passes it to the model as a regular result, even with an HTTP error:

const data = await response.json().catch(() => ({})); if (!response.ok) { if (data && Array.isArray(data.created) && Array.isArray(data.errors)) return data; // ... }

The model sees which links were created and which were not and why, and retries only the necessary ones.

Solution 5. Images are served as images

The get_qr tool returns a QR code. If you return base64 as text, the model gets several kilobytes of meaningless characters in its context. MCP has a content type image, and the client will show the image to the user:

if (mime.startsWith("image/")) { content.push({ type: "image", data: result.base64, mimeType: mime }); } content.push({ type: "text", text: JSON.stringify({ contentType: result.contentType, bytes: result.bytes }, null, 2), });

A short text block with the type and size follows: this is enough for the model to say "QR ready, PNG, 4 KB."

Connection

For Claude Code, the server is added with one command:

claude mcp add linkbit -e API_KEY=slk_... -e APP_URL=https://linkbit.live -- npx -y linkbit-mcp

For Cursor and Claude Desktop, the same is described in mcp.json. After that, you can write to the agent in plain text: "shorten the link with the slug spring and utm_source newsletter," "show clicks for the last link since January 1st."

What I would do differently

  • I would design API responses for the model from the start. Short error reasons and explicit partial success are useful not only for the agent but also for regular integrations.

  • I wouldn't write my own code unnecessarily. Without an SDK, the server turned out to be transparent, and I understood the protocol well. But for something more, with resources, prompts, and HTTP transport, the official SDK would save time.

  • I would test on multiple clients from day one. Claude Code, Cursor, and MCP Inspector can display errors differently and decide differently when to ask for confirmation.
