Why MAX

MAX is pre-installed on smartphones sold in Russia, and there are few AI bots in it yet – the niche is not overheated like in Telegram. It has also become easy for self-employed individuals to enter.

Since June 2026, MAX has had an open partner platform for the self-employed. Registration is at business.max.ru, type "Self-employed", confirmation via Gosuslugi. A self-employed individual is given up to two bots, and the bot card is moderated for up to 48 hours.

Only residents of the Russian Federation can create bots: self-employed individuals, individual entrepreneurs, and legal entities. This is worth checking before writing code.

What is useful to know about the Bot API in advance:

  • There are no built-in payments like Telegram Stars. We accept money via a link to an external payment system.

  • The API certificate is issued on the root certificate of the Ministry of Digital Development. It needs to be added to trusted certificates on the server, otherwise HTTPS requests will not go through.

  • The token is passed in the Authorization header without the Bearer prefix.

  • The webhook only accepts HTTPS on port 443. A 200 response is required within 30 seconds, so the request to the neural network goes into a background queue.

  • If the webhook does not respond successfully for 8 consecutive hours, MAX unsubscribes the bot itself. Without monitoring, you might wake up with a dead bot.

  • The limit is about 30 requests per second.

  • Check the secret in the X-Max-Bot-Api-Secret header to filter out unauthorized requests to the webhook.

Which models I chose

The bot has two families of models for text and one for images. Each family has three tiers – from cheap to the smartest.

Three tiers are not just for show. The top OpenAI model in the bot is 20 times more expensive than the lower one – both for input and output. If you give everyone only the flagship, a simple "translate a paragraph" will cost as much as analyzing a contract.

For images, I chose Nano Banana 2.1. It was released in October and, at the same resolution, is about a quarter cheaper than Nano Banana 2. The second version remained as a backup – in case the new one started malfunctioning.

The models are connected through a common provider layer. Adding a new family or replacing a model requires a new adapter and a line in the catalog; the business logic does not change.

Billing: how not to go into the red

This was the main engineering challenge. The price of a request to a neural network is unknown in advance: no one knows how many tokens the model will write in response.

The naive scheme "check balance → send request → deduct" breaks immediately. A user with a balance of 100 credits sends two heavy requests – from their phone and from their laptop. Both pass the check, both are executed, and the balance goes into the negative. The bot owner will pay for this deficit.

Therefore, each request goes through four steps.

1. Top estimate. We count input tokens through the vendors' APIs: OpenAI has a token counting endpoint, Gemini has countTokens. Output is limited by the max_output_tokens parameter. The model's reasoning is included in this same limit, so the model physically cannot spend more. The price = input tokens × input price + output limit × output price. This is an upper bound, not a forecast. The user sees it before sending the request.

It's simpler with images: a fixed price per image based on resolution plus input tokens for the prompt.

2. Reserve (hold). We reserve the amount in a single transaction in PostgreSQL. The balance check condition is directly in the UPDATE, so two parallel requests cannot pass the check simultaneously.

BEGIN; 

-- idempotency key = MAX update ID: 
-- repeated webhook delivery will not create a second hold 
INSERT INTO holds (idem_key, user_id, amount)
 VALUES (:update_id, :user_id, :hold); 

UPDATE wallets
 SET held = held + :hold,
 active_holds = active_holds + 1
 WHERE user_id = :user_id
 AND balance - held >= :hold
 AND active_holds < 2;

-- 0 rows updated → ROLLBACK 
-- and "insufficient credits" message
 COMMIT;

PostgreSQL locks the wallet row during the UPDATE. The second request waits and re-checks the condition, taking into account the first hold. I also limited the number of simultaneous requests to two – so one user doesn't clog the queue.

3. Deduct actual cost. When the model responds, we take the actual usage and deduct min(actual, hold). The remaining hold is returned to the balance. Usually, the actual cost is significantly less than the upper estimate, so the user overpays only temporarily.

4. Cleanup. If the process crashes mid-request, the hold will remain. It is released by a background task based on TTL. It is important that the timeout for the request to the vendor is shorter than the hold TTL – otherwise, the hold will be released while the model is still responding.

All money movements are written to an append-only journal. The balance can always be rebuilt from the journal, and you can find out where each credit went.

I tested race conditions on a real PostgreSQL, not mocks: tests launch parallel holds on one wallet and check that the balance does not go below zero.

The entire request path: money is reserved before calling the model, and deducted only after the response.

How a self-employed person can accept payments in 2026

I work as a self-employed individual, and here I encountered a surprise. The usual route through YooKassa no longer works: from December 29, 2025, it stopped sending self-employed checks to "My Tax".

Manually issuing checks is also not an option. When paying by card or SBP, a check must be generated at the moment of payment – this is required by the law on NP D (Part 3, Article 14, Federal Law 422-FZ). With a flow of small top-ups, you can't keep up manually.

As a result, I chose Robokassa with the "Robochecks SMZ" service. What's important for the bot:

  • checks are sent to "My Tax" automatically, for free;

  • payment by link – exactly what is needed in MAX without built-in payments;

  • there is a server-side notification of payment (ResultURL);

  • commission on the "Starter" tariff according to their calculator – 3.9% for cards and 2.7% for SBP.

Top-up looks like this. The user clicks "Top up" and selects a package. The bot sends a payment link. After payment, Robokassa calls ResultURL: we check the signature, credit the funds, and notify the user in the chat.

The ResultURL handler must be idempotent by account number. Payment systems repeat notifications, and without this, one payment will be credited twice.

Refund of unused balance is also automated: through the Robokassa refund API with check cancellation. Why it's needed – in the next section.

What's the result

The bot itself – dialogue, model selection, image generation – took less time. More time was spent on ensuring that money was accounted for honestly: no one goes into the negative, checks go to the tax office, and the balance can be returned.
