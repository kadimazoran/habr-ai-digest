A breakdown of the architecture of an AI agent for static code analysis: a local index on SQLite, 71 tools, a 30-turn tool-calling loop, and validators that we wrote and then removed because they falsely triggered on valid files.

The Problem Statement

Vibe-coding works great where all the necessary context fits into the prompt: a script, a landing page, a small service. But take a large legacy system — for me, it's 1C:Enterprise configurations, thousands of metadata objects, hundreds of thousands of lines of code, relationships defined not in code but in structure (attributes with types, document movements, event subscriptions, RLS in roles).

Let's do a rough calculation: even a 128K token window is about a hundred thousand characters of code. That means the model sees 1-2% of the base. The remaining 98% it constructs from training statistics — hence the classic picture: a neural network for 1C confidently writes code with an attribute that doesn't exist in this configuration and calls a non-existent method. The problem isn't that the model is stupid. The problem is that we're asking it to guess what can simply be read.

Hence the task: don't drag code into the model, but give the model tools to navigate the base itself and retrieve the necessary facts. This is essentially RAG, but not "find a chunk and insert it into the prompt," but a full-fledged agent with a tool-calling loop.

I built such an AI agent within a desktop 1C configuration analyzer (the project is open-source, link at the end). Next, I'll explain how it's structured, with numbers and pitfalls.

Local Index: SQLite + FTS5 + Offline Embeddings

The first fundamental decision: the index lives locally on the user's machine, not in the cloud. A codebase is a trade secret, and the requirement "transfer the entire repository to our service" kills the product on the spot.

How the index is structured:

  • Structured data — SQLite: metadata objects, attributes with types, forms, document movements, permissions and RLS restrictions, enumeration values. The agent performs real SQL queries on this index — this provides precise answers like "list everyone who references this attribute.".

  • Full-text search — FTS5. Fast, accurate, but only finds what matches by words.

  • Semantic search — a local multilingual embedding model (384 dimensions) builds vectors for each function and object. Indexing is done offline, on the user's machine, once when the project is connected, and then maintained in the background.

Why both searches, not just vector search: they compensate for each other's weaknesses. Vector search finds "check debt overdue" even if there isn't a single word from the query in the code. FTS finds the exact variable name that embeddings have smeared. The agent is responsible for deciding which one to use.

The call graph was a separate effort. Standard static analysis only catches direct calls like `Function()`. But 1C has many hidden connections: `Execute()` with a string assembled at runtime, notifications (`NotifyAboutChange` → `HandleNotification`), event subscriptions where the connection is defined in metadata, not in text. The graph accounts for all these channels — otherwise, the agent would answer "nothing will break if I change this procedure" to the question "what will break if I change this procedure," and a background job would break.

Agent Loop: 71 Tools, 30 Turns

Instead of a multi-agent relay (classifier → searcher → generator, where context is lost at each transfer) — a single agent with native tool-calling: the model itself decides which tool to call, gets the result, and decides further. The loop runs for up to 30 turns per question. This is an important number: with 8-16 turns, the agent consistently failed to reach a conclusion on complex questions — and we've increased it more than once (the history of constants still has the chain 8 → 15 → 12 → 16 → 30).

The arsenal consists of 71 tools, divided into four groups:

  1. Search and Typing: semantic search, literal search, entity resolution ("open posting document" → specific module), function passports with inferred types.

  2. Data: SQL to the local index (SELECT only), call graphs up/down, full-text and vector search.

  3. Edits: pinpoint patches, insertions, string replacements, function splitting — with a diff panel "original/revision.".

  4. Domain-specific: editing report schemes with semantic operations ("add column", "create variant", "add total") and web search on a curated whitelist of sites.

Engineering insights without which the loop would fall apart:

Verification Log. LLM doesn't remember what it did five turns ago: the agent re-queried the database with the same requests and contradicted its own conclusions. This is fixed with a log: each tool call writes a compact trace (tool + arguments + short result), and before the next query, a block is inserted: "you've already checked this: ...". We keep the last 40 entries, truncated at the boundary.

Tool Result Truncation. Raw SQL output of 500 lines kills context faster than it helps. Each tool has its own result limit, some have smart truncation (SQL is truncated at the string literal boundary, long articles are provided with a hint "re-read with filter by word X").

Tool Filtering by Topic. All 71 tool schemas are ~80 KB of text per request. When the question is about code, СКД (System of Collection of Data) tools are paid for and consume context in vain. Solution: tools have topics, the question has topics (based on word triggers, content of open files, and semantic routing via embeddings), and only relevant schemas are sent to the server. The same list of topics also automatically loads domain-specific reference books for the platform.

Turn Markers. At each step, the model sees "[SYSTEM] Turn N of 30, K remaining". 4 turns before the limit — a soft warning ("consolidate batches, don't start new branches"), 2 turns before — a polite request to honestly summarize findings instead of generating a half-empty response.

The Most Interesting Part: Edit Validation

The agent edits not only code but also declarative artifacts — for us, these are XML report schemas (СКД). And here's the main pain point: the model makes an edit that is structurally valid and yet doesn't open in the platform. The user saves the file, loads it into the configurator — and gets "Field not found.".

Therefore, a chain of checks after each edit, before the agent's response goes to the user:

  1. Tag convergence and section order — trivial, but necessary.

  2. Verification against the formal format model. We have the official XDTO model of the schema from the vendor's toolkit (8 files): nesting and element composition are checked against it, with class inheritance. Pitfall: class names in the model don't match XDTO names in XML (mapping table), and unfamiliar types from other namespaces are NOT an error, otherwise the check would force the model to rewrite a valid block three times in a row.

  3. Referential integrity — duplicate names and broken cross-references (data set link → non-existent set). This is not caught by tag convergence or the format model: the file is valid by both checks and still doesn't open.

  4. Query semantics within the schema — duplicate aliases in the selection list of one branch (the platform doesn't open this, and the grammar parser misses it — this is already semantics), broken reference chains like `Reference.TablePartAttribute`, multiplication of rows when joining with a table part.

Checks are divided into advisory (⚠️ in the tool's response — fix, but optional) and blocking (edit is not applied, agent must correct it).

And now the most valuable part — an honest list of checks that we wrote and then removed because they falsely triggered on valid files (calibrated on ~600 reference schemas from real configurations):

  • "duplicate dataPath" — exact repetitions are legal (97 files with "violations");

  • "double quotes in query" — in the language, this is an escaped quote, legal (159 files);

  • "output field does not exist" — virtual tables and reverse fields are not stored in the index (139 files).

The conclusion I drew is: "just validate against the spec" doesn't work. The format allows more than it seems, and your sample of valid files is always smaller than the real world. Calibration on hundreds of real files is a mandatory step, and the rule is simple: a check must not trigger on native, known-valid artifacts. Better advisory than blocking with a false positive.

Infrastructure Pitfalls

Briefly, but each point cost a day of debugging:

  • Interruption of long SSE streams. `CURLOPT_TIMEOUT` is the overall limit for the entire request, including stream reading. 45 seconds cut off long responses mid-transfer. Partial responses cannot be retried (you'll get duplicate text) — the request failed for the user. Fixed by a combination of numbers: stream timeout > worker window > time to clean up stuck tasks > client timeout, in strict ascending order. Cannot change one by one.

  • Atomic task acquisition from the queue — `SELECT … FOR UPDATE` before `UPDATE status='processing'`, otherwise overlapping workers process the same request twice.

  • Dialogue history overflow — after dozens of messages, response quality degrades. Compression: when the threshold is exceeded, old messages are collapsed into a summary, keeping the last N.

  • Mismatched retry markers. The client looked for one string in the error text, but a different one was actually thrown ("Connection with server X is interrupted") — due to the mismatch, the automatic connection interruption retry didn't work silently, and the user saw an error. A small thing, but it lived for a month as a "sometimes it doesn't work" bug.

A typical medium-complexity question goes through 6-12 turns: find object → read code → build graph → check attributes → answer. Complex ones ("rewrite the query that broke after the update and explain the data selection") — up to 20+. An example of a real case: the task "link payment orders to customer orders" — there's no direct attribute, the agent found a workaround through the invoice base documents and assembled a correct query with `ALLOWED` and checks for deletion marks. You can't write this by guessing — these are exactly the facts that lie in the index.

What this gives in practice: the AI assistant stops being "ChatGPT for 1C" and becomes a tool that answers based on your real codebase — all static analysis works locally and without the internet.

About the Project

Everything described is not an experimental toy, but the program MetaVision for 1C: AI, which has reached version 3.2 after a year and a half of combat edits on real configurations. What it includes:

  • static analysis of 1C configurations: 9 scanners for problematic code (performance, security, transactions, locks, and others), call graphs with hidden connections, semantic vector search;

  • loading not only the main configuration but also extensions (considering redefinition annotations) and external processing — the configuration that is actually running is analyzed;

  • AI agent interaction with code directly in the program: edits in two panels (original/revision with highlighted changes), editing report schemes with semantic commands and auto-checks, error analysis from a screenshot;

  • works on Windows and Linux, free; only the AI processing is paid for — based on balance, per use.

There are two editions with identical functionality, differing in whose models process requests:

  • Custom Edition — DeepSeek V4 and GLM models. The default option if there are no regional processing requirements for the code.

  • RU Edition — Russian models (Yandex Qwen3, Yandex DeepSeek V4) via Yandex AI Studio, on servers in Russia. Works from Russia without VPN, payment by Russian card or via SBP. The choice for those who want code processing to happen within Russian infrastructure.

It can be used not only in vibe-coder mode ("write me a function"). The second mode, which users ultimately value no less, is deep analysis: to take over someone else's configuration and understand in an evening how it works, find everyone who references an attribute before deleting it, figure out why a report is crashing, trace a call chain through notifications and subscriptions. Vibe-coding here is a special case, not the essence.
