Or an example of what happens if the role of package manager is entrusted to AI.

The short answer is: use templates.

A template is a general framework on the basis of which other projects with unique business logic can be developed.

A template is not necessarily Open Source. Projects can very well be hosted in a separate private company repository. But! By default, company management and employees must remember and understand that this template is developed using cloud models, and therefore, be prepared for copying, leakage, or publication.

As a result, we get a separation:

  • we work with templates in the cloud

  • for internal projects, we use corporate tools

Everything seems simple.

The only difficult part is how to develop the template in the long term?

What if the template cannot be packaged into a library? How to transfer changes in such a case?

Entrust the role of package manager to AI.

An example from personal experience.

pytest‑hardware‑template — a template for testing network, laboratory, embedded, and other physical equipment.

  • Copy the project.

  • Adapt it for your own needs using the skill ‘adapt‑internal‑infrastructure’.

  • When a necessary update appears, transfer a commit or a separate functionality of the template using the skill ‘adapt‑template‑change’.

As it turned out in practice, today even small local models are sufficient for high-quality transfer. If you have already made changes to the project, in case of a conflict, the agent will offer options on how to adapt the changes. The larger the model and the smaller the volume of changes, the better. The more clearly, but unambiguously and concisely, the architectural rules are formulated in AGENTS.md, the fewer questions FROM the agent and TO the agent will arise in the future.

The developer will only have to follow these architectural rules themselves:)

By the way, about architecture.

The pytest‑hardware‑template project was initially conceived NOT as a library, but specifically as a universal template.

But during development, parts became visible that, in the future, when a public API is established, would be convenient to transfer to a separate library.

At a minimum, it will help save tokens and time.

Therefore, for developers of the template and projects created on its basis, the documentation includes a special decision on the architecture and possible publication as a library.

Yes, it's not easy.

Sometimes even the procedure for approving the publication of a small piece of code in Open Source can take months.

An example from personal experience.

yaml‑test‑params — a library for dynamically generating test parameters from YAML configuration files.

The project was initially a small auxiliary module, about 200–300 lines of code. The approval process took a month. As a result, it became a library.

Is it worth the effort?

From the examples above, the main advantage that cloud models provided was ideas, features, architectural options that came from dialogue with the model.

It's good when you know what to ask.

But when the image of functionality is just swirling in your thoughts, you have to search, try out options.

As my own practice shows, the combination of large model sizes and the built-in search engines of cloud AI providers makes a tangible difference, which is worth rethinking internal company processes and project architectures for.
