Hello Habr! My name is Sergey Tretyakov. I am the product owner of MWS Data Scout, a service that describes database tables using large language models (LLMs).

In this article, I will explain why the task of documentation cannot be solved by simply passing the schema to the model, what layers of context we had to build, and which prompt block, contrary to expectations, only degrades the quality of work.

Problems with Table Descriptions

MWS Data Scout began with an experiment. We took the Resource Inventory system and tasked seven employees with manually describing its data marts.

Result after three months: 310 data marts.

Speed: about two tables per day per person.

Time spent: up to six hours per table.

Such high time costs are due to the complexity of finding answers to the questions "what is stored here and why": it is necessary to find the data owner, restore the system's history, understand how status_2 differs from status_new, and verify assumptions with SQL queries.

On the scale of MWS — our cluster alone contains over 600 databases — the data landscape cannot be described manually. It grows faster than people can document it.

When we started, AI agents for corporate data did not yet exist. The task was down-to-earth: to help an analyst who spends hours each time figuring out which of the forty similar tables contains the current data. We learned later that a ready-made layer of descriptions would also be useful for AI agents.

First Attempt: Passing the Schema to the Model

We started with the most obvious approach — we passed the data structure to the LLM: table names, column names, and data types.

The result was disappointing. The model simply rephrased what was already visible in the schema: "The table contains information about users, the user_id column is the user identifier." There was no new knowledge or business logic in such texts.

The problem is that a column name is a label that a developer once assigned. A technical field like status_2 could be a payment status, a delivery status, or a migration flag. This cannot be directly inferred from the schema.

Context Layers

To overcome this barrier, we began collecting context from all available sources:

1. Data Samples. We take 10 random records per table. This is not enough for analysis, but it is sufficient to distinguish a directory from a log and to see that the column contains not "some statuses," but specific repeating values.

2. Classification by Usage. We divide tables into types:

  • Log — events and monitoring;

  • Transactional — business transactions and ETL (including stage tables);

  • Directory — reference data with constant values;

  • Bridge — many-to-many relationships;

  • Summary — aggregates and summary metrics.

One needs to write about a log and a directory completely differently, so we determine the table class first.

3. Domain Affiliation. If a company does not have its own description of the subject area, we rely on industry standards. For telecom, this is eTOM (a telecommunications operator's process map); for finance, it is BIAN. As a result, the model correlates the table with a verified external business schema.

4. Own Glossary. If there is no ready-made industry model, the product itself builds a glossary of the subject area based on the data and maps tables to it.

5. Documentation. We connected parsers for Confluence, git repositories, and files (PDF, DOCX, XLSX, MD, TXT, HTML). Pages are divided into fragments, saved in Elasticsearch, and searched using a hybrid method — simultaneously full-text and vector search.

What Works in a Prompt and What Hinders

It would seem that the more context we give the model, the better the result should be. But experiments showed the opposite.

Testing Methodology

We took the same model and performed 1048 generations for 93 unique tables from three different sources. The quality was assessed by an automatic rater — a combination of LLM-as-a-judge and CatBoost on a scale of 1 to 5. The influence of prompt blocks was calculated using a paired t-test and fixed-effects regression.

We tested the following prompt blocks:

  • task — instructions on what needs to be done;

  • examples — samples of desired output;

  • output_format — strict specification of the format;

  • documentation — found documentation fragments.

The top two results are expected, but the bottom two are not. Strict format specification and adding documentation degrade quality. And we spent the most effort on extracting documentation!

Reason for the Problems

Both of these blocks add noise:

  • Documentation often contains outdated information, describes a neighboring system, or a different process. The model begins to blindly copy this information into the description.

  • The format specification distracts the model too much from analyzing the data itself.

Combinations of blocks behave even more interestingly. The best quality was achieved by combining context, examples, and documentation. But if the task block was added to this set, the overall score decreased. A block that is useful in itself starts to interfere in an oversaturated prompt.

The main conclusion: one cannot assemble a prompt based on the principle of "let's add everything we have." As a result, we moved to a prompt matrix. At the intersection of the table class and its business domain, a unique version of the prompt is created. A prompt for a financial directory and a prompt for a log of customer clicks are different entities that evolve independently.

Implementation Results

We tested the system on MTC's production databases. Automation results:

  • 8180 tables from 7 DBMS were fully described in less than 3 days.

  • Generation speed was about 25 seconds per table (instead of 6 hours of manual work).

  • About 80% of the documentation work is now fully automated. The team only needs to configure the domain and approve the result.

  • 95% of descriptions are accepted by analysts without any edits.

  • The productivity of one employee increased from 30 to 2000 tables per month.

Speed strongly depends on the volume of collected context. We processed a system with 634 tables in 33 hours, and another system with 4653 tables in just 1.75 hours. This is the net generation time, excluding human review.

In addition to texts, the system performs related tasks:

  • Builds ER diagrams. Including hidden relationships identified by analyzing data intersections (when relationships are not defined by foreign keys).

  • Generates business terms and synonyms.

  • Marks personal data (PDn).

Personal Data Security

Marking personal data is a critically important task with a high error cost. From May 2025, according to Law No. 152-FZ, significant turnover fines are provided for data leaks: up to 3% of annual revenue (up to 500 million rubles) for a repeated leak and up to 15 million rubles for an initial one.

The main danger is "forgotten" copies in legacy systems. Our product automatically searches for PDn across the entire landscape using LLMs and classic machine learning methods. Based on the ER diagram, we can see exactly where this data flows within the storage.

Important: masking of sensitive fields occurs at the network gateway before an AI agent can access them. The data itself never leaves the company's secure perimeter.

Technical Limitations

1. Data Sources. Out-of-the-box, there are over eight connectors to DBMS: Oracle, PostgreSQL, MS SQL, ClickHouse, MySQL, Greenplum, Hadoop. Lakehouse architecture is supported, and there is integration with DataHub and OpenMetadata catalogs. Results can be exported to Excel and JSON.

2. Cost and Infrastructure. Each LLM request costs money. Models are deployed within the company's network on dedicated servers with A100 and A40 GPUs. This is a fixed expense item and simultaneously a performance "ceiling" — scaling requires purchasing expensive additional equipment.

3. Optimization. To reduce costs, we are migrating simple tasks (e.g., PDn detection) from heavy LLMs to lightweight classifiers — from logistic regression to DistilBERT-class models. We train them on synthetic data generated by AI. This reduces response time to milliseconds and provides a stable, deterministic result.

MWS Data Scout for AI Agents

We created the product to help people find the information they need faster, avoid spending time deciphering tables, and not create duplicates. But with the advent of corporate AI agents, it turned out that they need a semantic layer even more.

Unlike a human, an AI agent cannot just "ask a colleague for directions." It can only work with information that is clearly and systematically documented.

Without clear descriptions, a glossary, and relationships, an AI agent works blindly: it confuses tables from hundreds of similar ones, interprets business metrics (e.g., "revenue") differently each time, joins tables randomly, and may accidentally disclose confidential data.

Conclusion

MWS Data Scout collects multi-layered context: data samples, table classification, domain affiliation, glossary, and documentation. In addition to text descriptions, the system builds ER diagrams, including hidden relationships, generates business terms, and marks personal data. Due to this solution, the productivity of one employee has increased from 30 to 2000 tables per month.

It is also important to note the work with AI. Agents can confuse similar tables, arbitrarily interpret metrics, randomly join data, and risk disclosing confidential information. Our product allows for the creation of a unified and accurate source of descriptions for all databases for other AI agents. At the same time, sensitive data itself remains within the secure perimeter.
