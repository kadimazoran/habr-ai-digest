At night, around 2 AM Moscow time, the server wakes up and starts a pipeline. First, the service goes to Telegram and downloads new messages from chats that the user has marked. An hour later, a second worker starts and turns these messages into memory: it chunks them, processes them through DeepSeek, organizes them into tables, and exports them to markdown files. By morning, the user has additional information in the second memory service.

The second memory service is not just a chat history. Six months later, you can ask, 'What budget did we agree on for the trip then?' and get an answer with a link to a specific message in a specific chat.

Strangely enough, almost all my work on creating the service was not in working with LLMs.

Why I Didn't Create a Vector Database

The standard approach for such a task is to load the chat history into a vector database and perform RAG. I consciously avoided this path.

Chat history is poorly divisible into fragments (chunks). A single fact can be assembled from a dozen replies across different chats, and chunking by 500 tokens breaks the history into pieces. A person might be called Sasha in one chat, Alexander in another, and have an obscure nickname in a third, leading the search to return five nearly identical fragments instead of a single piece of knowledge. The recency issue is even worse: an agreement made in March might be superseded by a change in June, and both versions remain in the index with equal weight.

I needed not fragments, but cards: people, projects, topics, facts, tasks, and the connections between them. And a mandatory link: from each fact back to the message from which it was extracted. A vector database doesn't provide this out of the box.

What I Ended Up With

The diagram turned out like this. Telethon fetches messages from selected sources (you can connect an entire folder or a specific chat). Each raw message gets an entry in the state table (pending, processing, processed, error). The scheduler picks up only those that are not yet in this table for the next run. This way, I don't pay twice for processing the same message.

I group messages by the key 'source:chat', sort them by date, and chunk them into groups of 100. Each chunk contains messages from only one chat, so the model sees a coherent dialogue. From a chunk, I assemble a transcript in the format [date] Sender: text, truncated to 30,000 characters.

Each chunk triggers one call to DeepSeek, which must return a strict JSON:

{
  "daily_note": { "title": "...", "summary": "..." },
  "topics":   [{ "name": "...", "summary": "...", "facts": ["..."] }],
  "people":   [{ "name": "...", "summary": "...", "action_items": ["..."] }],
  "projects": [{ "name": "...", "summary": "...", "action_items": ["..."] }],
  "links":    [{ "from": "...", "to": "...", "type": "related_to" }]
}

In the prompt, I include a list of the user's already known entities and ask the model to reuse their names. Without this, the same project would be named differently in each run, and the database would quickly turn into a mess.

When all chunks for a task are ready, the merge process starts. I look for entities using the key (user, type, canonical name). Repeated mentions don't create duplicates but update the summary. Facts and tasks are linked to entities, relationships go into a separate table, and each entry references the IDs of the original messages. This is the connection I need.

The final step is exporting to regular markdown files: Daily, Knowledge, People, Projects. I formatted the links between notes as [[wiki-links]], so the vault opens in Obsidian. The export is idempotent: before writing a block, I calculate its sha256, and if such a block has already been exported, it's skipped.

A finished card looks something like this:

# Trip to Antalya

## Update

We were planning a trip to Antalya in September, with a budget of around 350,000 ₽ for two.
[[Anya]] suggested the dates, [[Sasha]] clarified the details about the hotel and flights.

- Hotel: around 180,000 ₽
- Flights: around 70,000 ₽
- [ ] Clarify dates with Anya

The relationship isn't written to the file; it lives in the database. Each fact and task has links to specific messages. This keeps the files clean, and if needed, the source can always be retrieved.

Numbers

Currently, there are a few users. On average, each user has about 7 sources (3 folders and 4 individual chats). Even these, over a couple of months of testing, have generated tens of thousands of messages across 34 chats.

This resulted in 281 entities: 147 topics, 108 people, and 26 projects. Plus, 1815 facts, 184 tasks, and 133 daily notes.

In terms of tokens, it's currently 10.05 million: 3028 thousand input and 7027 thousand output. The responses are more than twice as expensive as the input because the JSON with the schema takes up a lot of space. At DeepSeek's rates, this is less than ten dollars for all messages. It's nice that personal memory costs pennies for small volumes.

One task (processing all new messages for a single user per run) takes an average of 205 seconds. The longest took almost 12 minutes. But since everything runs at night, 12 minutes is quite acceptable.

What Broke

Some Tasks Were Canceled Mid-Execution

The database contained the text cancelled - model changed to v4-flash. I changed the model on the fly while a task was executing. It turned out funny: some chunks were processed by one model, and others by a different one. The data wasn't corrupted, but it's better not to repeat this.

The Agent Responded "Nothing Found" Even Though Files Were Present

This was the most unpleasant bug because it looked like "memory is empty." It turned out that OpenClaw has a bug: the memory_search tool returns false null results while the internal search engine is working correctly. The cause is a cached memory manager. A forced re-indexing helps:

openclaw memory index --force

After this, I hardcoded the image version and forbade myself from updating it to 'latest': major versions change both the configuration schema and the internal database schema. I've been burned by this once before.

Telegram Sessions Don't Last Forever

A Telethon session can disconnect, requiring the user to re-authenticate. I created a separate flow with a code from Telegram and a message to the bot to "reconnect the account." In the dashboard, upon re-authentication, the chat list is rebuilt; otherwise, dead links to chats that are no longer accessible remain.

Telegram Itself Is Inaccessible from Russia

This is a separate headache. Initially, I set up WARP via sing-box, but the setup turned out to be fragile: either the tunnel would drop, or the speed would be terrible. Eventually, I switched to an MTProto proxy via Cloudflare Worker. I use the open-source Flowseal/tg-ws-proxy, which can wrap MTProto in WebSocket via a worker.

A separate story is how to monitor this. The first version of the check simply made a TCP connection and said "everything is fine," until users started complaining that messages weren't arriving. It turned out that the MTProto proxy doesn't respond to a plain obfuscated init: it waits for the client to send the first frame. I had to write a healthcheck that manually constructs the init according to the MTProxy protocol (SHA256 of random bytes and a secret, AES-CTR), sends req_pq_multi to the data center, and waits for resPQ back. It checks the entire path: listener, proxy, worker tunnel, data center. If any link fails, I receive a notification.

What I Would Do Differently

I wouldn't set 100 messages per fragment as a "universal" size. In practice, the night run includes about 20 messages per chat, and the limit is rarely hit. However, when a user first connects an old folder, it can receive up to two thousand messages at once, and then a hundred per chunk is just right. This means the parameter should be chosen based on the scenario, not "in general."

I would have introduced a metric "how many messages are still not converted into memory" for each user much earlier. Before that, I manually delved into Postgres and calculated the difference. Now, this number immediately shows who has problems.

And I wouldn't skimp on the connections. Initially, it seemed that links to messages could be added later. But it turned out that without them, it's impossible to debug or show the user where the memory came from. In the end, the connection turned out to be more necessary than I thought.

Instead of a Conclusion

The second memory for an assistant is not just about attaching a vector database. Boring things are important here: processing state, deduplication, idempotency, connections. The beautiful part (calling the LLM) takes about five percent of the work; the rest goes into infrastructure.

The project is alive, there are currently five users, and I honestly don't know what will break next. But that's precisely why I'm writing: if you have experience with personal memory, long-term context storage, or accessing Telegram from Russia, I'm interested in comparing our pitfalls. My project is called memory.tg, it's personal memory for Telegram.
