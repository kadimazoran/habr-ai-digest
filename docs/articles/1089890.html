The hardware and agent are the same as in the first part: MacBook Pro on M4 Max with 128 GB, pi 0.87.1 without extensions. The task is also the same: write the `minicalc` expression interpreter from scratch according to the specification, with 24 visible tests that the model can run, and 30 hidden ones it cannot see.

An important caveat about the comparison: the server is different, but the checkpoint is formally different too. The MTPLX build is the same Qwen3.8-27B in 4 bits, with MTP heads added and weights repacked for its own runtime. MTPLX simply doesn't work without MTP heads, and oMLX doesn't use them from this model. So, it's a comparison of the "server + build for it" combination, as it appears to the user.

Correction to the First Part: What is the "Default" Mode?

In the comments on the first part, it was correctly noted that Qwen3.8-27B defaults to `xhigh`, not `medium`. This is stated directly in the model's chat template: `reasoning_effort|default('xhigh')`. MTPLX substitutes `medium` itself — its code for this model sets `default_effort="medium"`, chosen by the MTPLX developers based on their own measurements on a coding task.

oMLX substitutes nothing: it only passes the reasoning level to the template when the client sends it. pi does not send it, so out-of-the-box, the model runs on its native `xhigh` on oMLX. To run other modes, I set them on the server side in the model settings `~/.omlx/model_settings.json`:

"Qwen3.8-27B-4bit": { 
  "chat_template_kwargs": { "reasoning_effort": "medium" }
}

And for the mode without reasoning — `"enable_thinking": false`.

What interested me most was `xhigh`. On MTPLX, it had 13 calls, 0 errors, 27k tokens, and 9 minutes until the first file. On oMLX, the agent did significantly more work. This no longer looks like the same answer that one server is simply outputting more slowly.

Where the 3-6x Difference Comes From

Before the first file, MTPLX took 9 minutes, and oMLX took 23 minutes. About 2.5 times longer. In agent work, MTPLX produced about 34 tokens per second; for oMLX, the estimate based on reasoning volume and time spent was around 13.

It's tempting to call this a pure gain from MTP, but the time to the file also includes processing the input context and depends on how much the model decides to think. These observations align with faster generation on MTPLX, but they don't measure the MTP contribution separately.

Further on, the trajectories diverge even more. On `xhigh`, oMLX produced 53k tokens and 41 steps, compared to 27k and 13 steps on MTPLX. In terms of tokens, the run is about twice as long; in terms of steps, it's over three times longer. These are overlapping parts of the same work, so they cannot be multiplied: 2.5 × 1.97 would give 4.9, not 6.4. Each extra step on a slower server costs more, hence the widening gap, but a precise breakdown requires splitting time by requests and tools, which I don't have. Perhaps oMLX just got an unlucky run: the same model on the same template isn't obligated to respond twice as verbosely.

Reasoning Mode on a Slow Server

On MTPLX, the difference between `medium` and `xhigh` was lost in the variation. On oMLX, in these runs, it's significant: `medium` finished in 37 minutes, `xhigh` in 93, and `low` in 72.

At 2.5 times faster than the native `xhigh` with the same test results, `medium` proved to be more efficient. For me, this is a reason to repeat the comparison: it's not yet possible to separate the influence of the mode from a lucky or unlucky run.

With `low`, the expected savings didn't materialize again — it lost to `medium` on both servers. The explanation "thought less, corrected more" seems plausible, but this table doesn't prove it.

Without Reasoning

The `off` mode didn't bring the task to a working state in any of these attempts, and the failures were different. On MTPLX, by 8.5 minutes, the code hadn't even imported. On oMLX, by 68 minutes, there was an infinite loop: the tests hung, and with them, the agent's work stopped — the `bash` tool in pi has no timeout, so I manually aborted the run. Comparing these times as solution speed is meaningless: there's no solution, and the oMLX wait also included the tests hanging.

In `smart` mode, MTPLX immediately ramps them to maximum, even before heating up. If macOS controls them, the speed under load drops by about a third, and generation drops by 30%. Memory

The second question from the comments: how much does all this consume, and what to do with 24 GB?

In this task, the agent generated 26–40k tokens per request — pi's system prompt and tool descriptions, the specification, code, and test output. The 262k window was filled to 10–15%.

The context for this model is cheap. Attention is hybrid: a full KV cache, which stores attention data for already processed tokens, is only present for 16 out of 64 layers. One token costs about 64 KB — 40k tokens is about 2.6 GB, and the full 262k window is about 16 GB. This is a calculation, not a measurement, and it's sensitive to cache format and unit rounding.

For oMLX, there's a measurement during the run: the process occupied 18 GB, peaking at 21 GB. For MTPLX, there's no separate measurement. According to its own memory plan, it's 20.7 GB for weights, about 3 GB for auxiliary buffers, and KV cache based on actual context — around 26 GB for this task. I wouldn't directly compare this to the oMLX process memory: one figure is measured, the other calculated.

On a Mac with 24 GB, it's more complicated. macOS allocates about two-thirds to three-quarters of the memory to the GPU, i.e., 16–18 GB. With such a budget, a dense 27B in 4 bits along with context no longer fits. I haven't tested this combination on a machine with this amount of memory. Among smaller options, there are 9B class models: for Qwen3.5-9B with MTP, the MTPLX team indicates a requirement of 16 GB or more. Another option by weight size is Ternary-Bonsai-27B in 2 bits, 8.5 GB. Their quality on this task has not been measured here.

What about Flash-Next?

In the comments, it was suggested to try Qwen3.8-Flash-Next: this is an MoE (mixture of experts) model, where only a small part of the weights is active for each token, so generation should be significantly faster. I haven't been able to test this yet.

Full 4-bit builds weigh 106–115 GB, and the GPU memory limit on a Mac with 128 GB is around 103–107 GB, so there's little space for them and the context. A more realistic option in terms of size is a reduced REAP build at 73.5 GB. I haven't gotten to it yet: downloading it on my channel would take about 17 hours. For now, it's a candidate for the next part, without speed and quality measurements.

Pitfalls

Default context window. oMLX limits the context to 32,768 tokens out of the box. This is barely enough for the agent: the task in the article generated up to 40k. The `max_context_window` parameter in oMLX settings should be checked immediately.

API Key. oMLX requires a key. In pi's `models.json`, you can enter it directly as text, but another option is more convenient: pi can fetch the key via a command — `"apiKey": "!command that prints the key"`. Then the key lives only in oMLX's own settings and isn't duplicated.

Built-in benchmark aborts work. This is the aborted run I mentioned in the first part, separate from the completed attempts above. In the admin panel, the built-in benchmark was launched, and it instantly unloaded the model, interrupting the agent's request. pi received a "Connection error" and hung until timeout.

SSD cache grows silently. With oMLX, the processed prompt cache on SSD is enabled by default and grew to 17 GB over a couple of days of testing. With MTPLX, I enabled such a cache for experiments — it grew to 51 GB in the same period. It didn't provide any speedup on this task in either case: within a session, the history is already kept in RAM cache.

Both servers on port 8000. If you run both, one will have to change its port. If the port is occupied, MTPLX enters "limited mode" and loses connection with its own server.

Running from DMG image. Like MTPLX, oMLX can be easily run directly from a mounted `.dmg`. It works until the image is unmounted.

My own methodological error. Once, I named the folder for the first oMLX run with a mode that wasn't in it, and the next `medium` run ended up in the folder with the already completed solution. It "solved" the task in 8 minutes — and this result had to be discarded.

Conclusions

  • MTP speeds up generation on this task, and the MTPLX combination finished 2.8–6.4 times faster than oMLX. However, I won't attribute the entire difference to MTP: the agent's trajectories diverged, and oMLX did significantly more work on `xhigh`. ChatGPT's advice to use oMLX as a "faster and higher quality" solution on this hardware was not confirmed — in terms of quality, the combinations were equal, and oMLX lost in speed.

  • In these runs, quality was determined by the model, not the server: in all completed modes with reasoning, both combinations passed 30 out of 30 hidden tests. This statement has not been verified on other tasks.

  • On a slow server, the reasoning mode is more important. `medium` on oMLX was 2.5 times faster than the native `xhigh` with the same result; on the fast MTPLX, this difference is lost in the variation.

  • Disabled reasoning did not bring the task to a working state on either server.

  • Quieter means slower, and almost one-to-one: switching fans to macOS control reduced RPM by about a third and generation speed by about the same amount. The `sustained` profile did not make it quieter.

  • For oMLX, I have one run per mode, so I won't claim that `xhigh` is always two and a half times more expensive than `medium`: repetitions are needed.
