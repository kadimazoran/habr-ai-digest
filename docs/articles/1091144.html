How it all started

The implementation of the project turned out to be very spontaneous. I was invited to participate in one of the internal team meetings to suggest solutions to a problem: another recognition tool was already in use, and its data showed discrepancies and constant errors.

I decided to prepare and sketch out an initial draft. It took two days — I tested it on everything available on the internet: enforcement orders, salary garnishments. The goal was precisely this narrow scope initially.

At the meeting, they showed my version and the version from colleagues in a related team. Mine fit a bit better — it didn't require sending data externally, worked within a closed environment out-of-the-box, and was tailored to the specific document types that were requested.

And then my meticulousness and desire to bring everything to an Excellent level — as much as possible for one person — kicked in. So, versions started flying: 1-2-5-10... I honestly can't say which specific version it is now — I didn't publish it on GitHub immediately, I developed and tested it locally.

A separate issue is a significant limitation: only LLM models within the perimeter. Everything that enters this perimeter is strictly confidential; transmission even to other employees is not allowed — let alone externally.

But, honestly, I was surprised by the quality of the models within this perimeter: yes, it's not fast — generation and processing speed is not what we're used to with subscriptions — but it's definitely possible to achieve good results. And I believe it's necessary: we remove all limitations and get an excellent tool without the fear of information leakage "outside".

A side effect of this architecture is that it's not tied to a specific model (any OpenAI-compatible gateway), so the project can be easily tested at home with Ollama and Qwen2.5-VL, which is what I did during development.

The project is currently in production and being tested by brave folks who weren't afraid to trust an enthusiast)

Next is the technical meat. For those only interested in the essence: scan at the input, verified details and registers for 1C at the output, we don't trust neural networks at all.

What was achieved in fact

The pipeline "scan → extracted and verified details → 1C/Excel registers":

  • 9 document types out-of-the-box: FSSP resolutions, enforcement documents (orders, court orders), salary garnishments, UPD/invoices, contracts, HR orders, powers of attorney, claims/lawsuits, acts of work performed. All these are isolated plugins; new ones are added as a folder, the core knows nothing about types;

  • any model via OpenAI-compatible API: corporate, local Ollama/vLLM, cloud if desired;

  • deterministic verification: check digits, sum arithmetic, statutory limits, chronology, cross-modal comparison with the source text (more on this below, it's the main part);

  • output: two JSONs per document (_Full — canon with audit, _Flat — flat record for 1C), a general register RegistryFull.json, and an Excel file;

  • CLI with meaningful return codes, JSON-RPC server for integrations.

The stack is modest: Python 3.9+, Pydantic v2, Pillow/PyMuPDF, openpyxl, optionally rapidocr.

How the pipeline is structured
