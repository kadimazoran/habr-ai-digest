What follows is how it grew from there: through three course changes (learning project became a product, Gemini CLI was replaced by Claude Code, a two-output router became a graph), one wall I hit at full speed, and a launch that didn't work.

What is this and why

I live in a village, in another country. The internet isn't available everywhere here. However, my phone is always with me – when I'm not at my desk, it's my entire computer. Perhaps it's professional deformation, but for me, it's long been a principle: if something can be done on a phone, I'll do it on a phone.

And then I need the most ordinary thing from the model. To summarize a long text. To find where I wrote about it. To extract dates and sums from a document. To answer a question based on my own notes. Things any model does without thinking.

Except it's not there. Not 'responds slowly' – no, not until the network appears.

This is the first half. The second is what I won't give away even with a working internet: correspondence, notes about people, clinic reports, NDAs. Not because there's a terrible secret, but because there's no need.

The result in both cases is the same: the task isn't done. Not slower – not at all.

The application I'll be talking about solves this in one way: the model runs on the phone itself. The engine is LiteRT-LM, a language model wrapper over LiteRT, the successor to TensorFlow Lite. The model is Gemma 4 E4B; for weaker phones, there's E2B. The file weighs about 3.4 GB and is downloaded once; after that, you need 2+ GB of free memory. In this mode, the conversation never leaves the device – it simply has nowhere to go. Below, there will be cloud models, MCP, and HTTP requests, so I'll state this upfront: all of this only appears after you yourself enter the key, server address, or list of domains. Until you enter them, they don't exist for the application.

And one more thing, because the phrase 'AI agent' conjures something with hands in your phone. The scenario I described doesn't require any tools: the model reads and responds, nothing more. What the agent can do and who decides what it's allowed to do will be discussed later, in the section about the graph.

Six weeks

First commit – March 2nd.

Then, in order: framework and architecture, LiteRT-LM engine and model management, memory and context, tools and OS integration, chat screen, background work, orchestration, stabilization, multi-session support, 'smart' pipelines, tech debt cleanup, pipeline visual editor rework.

Twelve phases. Two hundred seventy-six commits. Six weeks.

I listed this deliberately because the list looks strange. For a learning project, this is overkill. But I wasn't setting out to build an application; I was figuring out how development with an agent is done, and the application was the proving ground. The proving ground grew on its own.

What I learned in those six weeks, in short: the task must be set precisely, and each step must be verified. It sounds trivial until the first time. Gemini CLI was fond of stubs and tests that checked nothing. It happened more than once: task closed, report enthusiastic, but no implementation. It would create a class structure, and inside the methods, it would say, 'and then someday we'll add this.' A test was attached to it. Green.

The pace, meanwhile, was about what I expected. I had heard about what employers want these days, so twelve phases in six weeks didn't surprise me.

April 16th

By mid-April, I had figured out what I came for. And I was faced with a choice I hadn't planned for: I had an application that was too good to discard.

At this point, a learning project is supposed to be closed – it has served its purpose. I decided otherwise: to grow it further, into something more useful than a learning exercise. And on the same day, I switched tools, from Gemini CLI to Claude Code.

The main reason was those very stubs. Debugging what the agent had actually done versus what it had only promised was more expensive than writing it myself. Claude Code proved more reliable in this regard – it sometimes forgets important things too, but noticeably less often. Plus, there was more to grow and learn.

You don't need to remember the date; it's visible in the repository history. April 16th, right at the boundary of the twelfth and thirteenth phases. Before it: 276 commits; after: 1336.

How a router became behavior

It all started simply. There's a local model, there's a cloud model, and you need to choose between them based on the situation. A two-output router, an evening's work.

Then, each subsequent piece appeared not because I wanted to add features, but because the previous one broke. I'll tell you in order; this is the most useful part.

A model with 2-4 billion parameters falls apart on multi-step tasks. It doesn't respond slowly – it responds incorrectly.

The very first case was quite simple: comparing two facts. Or just finding two different facts within a single task. The model went to search with one query, asking about everything at once, and got garbage. It then built its answer on this garbage, and it sounded confident.

The same task works if you break it down into two searches, execute them sequentially, and compare the results. The difference isn't in the model's quality but in whether the step given to it was manageable.

Hence the first move: break the task into steps and give each step its own node. The model no longer needs to hold the entire task – the graph holds it. This is also where the separate decomposition node came from: not only humans can break things down in the editor.

A node that is supposed to output a structure sometimes doesn't. A router must return a class; a parser must return JSON. A 2B model sometimes forgets this, and the run fails entirely.

The second move is the validation gate. If the response can't be parsed, the node gets a second attempt, and the error text is literally placed in the prompt: not 'fix it,' but what exactly was wrong. By default, there are two such attempts; it's configurable from zero to four.

By the fifth node, the prompt carries everything that happened before it. A small model drowns in this, and the quality drops not where the error occurred but two steps after it.

The third move appeared almost on its own: context management at each node. You choose what exactly goes further, rather than sending the entire accumulated conversation.

Prompts need fresh values. Date, time, list of active tools, device language. Hardcoding them means lying on the very next run.

The fourth is variables in prompts, nine of them, substituted anew on each run.

The model cannot ask for clarification. Where a human would ask, it guesses, and ambiguity turns into a confidently wrong answer.

The fifth is the clarification question node. The run stops and asks.

Graphs became large and repetitive. The same pieces were copied from pipeline to pipeline.

The sixth is composition. A pipeline can be inserted into another pipeline as a node, and a set of tools with their limitations can be packaged as a skill.

There are ultimately fourteen types of nodes. This is where it stopped being just a router: the graph describes not 'where to go' but what's happening at all.

Who decides what the agent is allowed to do

I promised to return to this earlier – I'm returning because it's the first question asked.

Of the fourteen node types, only two can call anything: the tool node and the skill node. The output of a regular model node regarding calls isn't even analyzed – there's nothing to intercept. A pipeline consisting only of a model and an output cannot do anything other than respond with text.

Of the fifteen pipelines that come bundled, nine do not contain any such nodes.

Now, about everything that looks outward. A cloud model works only with your key: no key, no cloud node, nothing for the router to choose from. An MCP server is only one you've added yourself. The outgoing HTTP request tool isn't even shown to the model until you fill in the list of allowed domains; before that, it doesn't exist for it. Crash reports in the Play build are disabled by default, and if enabled, they contain neither prompts nor messages. There's also a separate build without proprietary dependencies: it doesn't have Firebase at all, and no toggles – nothing to report.

And when you finally assemble a graph that does something, all destructive and sensitive actions are paused and await your confirmation. This includes when a pipeline runs in the background triggered by an event – then confirmation comes via a notification.

Access to actions is a property of the graph you assembled, not a property of the application you installed.

The Wall

Next, about the place where I hit a wall at full speed.

The agent needs tools – to be able to not only speak but also act. In Android, there are AppFunctions for this: an application declares functions, another application finds and calls them. Exactly what's needed: to reach what's already installed on the phone.

At the time, I wasn't familiar with local Android AI and, without spending time studying this new Jetpack component, I immediately started implementing. I wrote the caller side, the callee side, argument parsing, dispatching. Nothing worked.

It was a long process. I reread the documentation, rechecked the manifest, changed versions, wrote minimal examples. Everything was done correctly – and it didn't work. This is the worst kind of debugging: when there's no error, but there's also no result.

Then I found out why. Any application can declare its functions – that side is open, and there are already enough guides on 'how to show your functions to Gemini.' The other side is closed. To find and call someone else's function, you need the EXECUTE_APP_FUNCTIONS permission, and it's declared in such a way that it's granted to pre-installed applications and system modules. An app from the Play Store won't get it – not on any stock image. My code was correct. The premise was incorrect – that the caller could be anyone, not just something pre-installed from the factory.

The workaround became MCP: tools that the agent fetches from the server, not from a neighboring application. It works, but it's not what I intended: the point of AppFunctions was to reach applications already installed on your phone.

Postponed until times when and if the permission is opened.

But the real cost wasn't the discarded branch.

From the same story, I learned that AppFunctions requires Android 16. And the minimum supported application version remained Android 16 for almost the entire project life. This cuts off everyone with older phones.

I only verified this assumption in August. It turned out that nothing required the sixteenth version: not dependencies, not the inference engine, not a single line of my code. The threshold dropped to Android 14, two versions down, and nothing broke.

The lesson here isn't about Android, and I don't like it. Jumping into implementation before studying the platform costs not debugging – it costs a discarded branch. And then the assumption that started it all survives its refutation and continues to charge you for months until you finally measure it.

Race and Checks

A separate expense, which is rarely written about: everything this is built on is constantly moving. Kotlin, Android Gradle Plugin, Hilt, Koog, the LiteRT-LM engine itself. You have to update, otherwise, in six months, you won't be able to build at all, but each update is a separate task, not a line in a config file.

Here are four things that explained this to me.

First: an update breaks not what was updated. I upgraded the Kotlin version – Hilt broke, related to metadata I hadn't touched. It's fixed by forcing a specific library version, which can only be found by looking at error messages in someone else's bug tracker.

Second: it works fine in debug, but it's bad for users. Long-term memory didn't work in release builds. In all release builds. The reason was the R8 optimizer: it considered the class I was accessing via reflection unnecessary and made it abstract. R8 doesn't work in debug builds, so everything was fine for me. The crashing release on flogger surfaced in exactly the same way.

This is perhaps the main difference from what you get used to in a learning project. You run a learning project yourself, on your own machine. The difference between 'it works' and 'it works for people' is a whole class of errors you won't see until you start releasing seriously.

Third: removing a button doesn't mean disabling a function. I removed the analytics toggle from the settings – and found that data collection didn't stop: the saved flag was older than the manifest and continued to be active. For an application that lists privacy in its description, this is not a minor issue. This is where the checks came from.

That lesson from the second week – set the task precisely and verify each step – eventually stopped being my personal discipline and moved into the build process. Now, one command runs everything at once: static analysis with type resolution, formatting, Android linter, test coverage threshold, architectural tests. Plus nineteen separate checks that I wrote for specific pitfalls: comparing generated files with sources, broken links in documentation, version discrepancies across four places. And instrumental tests on emulators in CI.

Discipline that you keep in mind works only until the day you're tired and want to finish the current task quickly. A check built into the build always works.

And here's an honest disclaimer, because otherwise, it sounds too smooth. Checks also need to be checked. Three of my build logic tests remained red after two merges – simply because they were in a separate build that the main team couldn't reach. Everything was green. The tests were failing.

And fourth, about default settings. Cloud providers are connected via a library that has timeout settings. I didn't touch them – they're reasonable by default, right? It turned out that a request to a frozen provider lives for fifteen minutes with these defaults: I measured it, and it was 900,033 milliseconds. For fifteen minutes, the application looks like it's thinking, even though no one has been there for a long time.

What turned out to be useful wasn't so much the fact itself as understanding which timeout was at play. You need to limit not the response length but the silence length: the socket timeout applies to each read, so it terminates a frozen provider and doesn't interfere with a long but live response. A limit on the entire request doesn't see this difference.

What resulted

Now it's forty-three phases and six months by the calendar. The application is on Google Play, the source code is open under Apache 2.0. I use it every day – and honestly, that's the only maintenance guarantee a solo developer can give without lying.

It's called Knotwork. I chose the name for the image of an intertwined pattern – a graph, nodes, connections. I still don't know if anyone reads it besides me.

Now, about the launch.

In early September, I wrote about it on r/LocalLLaMA, the largest community of people running models locally. The post got 13,000 views and a rating of zero. Three people commented. The actual discussion was with exactly one person. He said that without proper virtualization, he wouldn't keep an agent on a phone he uses every day; only on a spare one, as an experiment.

At first, I read this as a rejection. Then I reread it: this is the answer to the question I went there with. I was making an assistant for a person who doesn't expose their data externally – that is, for someone whose default setting is 'do not trust.' And I got exactly what that setting implies: it won't let the agent in until it can verify that it's locked down. Distrust doesn't stop at the network boundary.

What I have for this request, and what I don't.

I have. Every run writes a trace: which node received what, what it returned, which tool it called – this is visible in the run console. All destructive actions await confirmation. The HTTP tool doesn't exist without your domain list; the cloud, without your key; MCP, without your server. There's a build without proprietary dependencies; it doesn't have Firebase at all.

I don't. A build that has no network at all. The 3.4 GB model needs to be downloaded from somewhere; the INTERNET permission is in the manifest, and therefore, you check 'nothing is sent out' today by looking at the source code and taking my word for it, not by external verification. Tools run within the application process, without their own sandbox: the agent is locked down only as much as the application itself is locked down.

The option with manual model file download and no INTERNET in the manifest seems to be the cheapest way to respond to that person's words with action. I haven't done it yet.

The second half of the same thing is even funnier. One of the FOSS subreddits I was planning to go to next recently introduced a rule: applications made with significant AI involvement are banned there. About half of my commits bear the mark of the model; I don't hide this and contacted the moderators myself before publication. I still haven't received a response.

It's symmetrical. I went to learn agent development because the market started demanding it. I wrote an agent using an agent. And I encountered two communities, one of which rejected what I built, and the other – what I built it with. Both halves of the same activity were rejected.

Therefore, the question I came here with is not 'how to convince them.' Trying to convince is a bad goal, and unnecessary: their position is consistent, and I understand it. The question is project-related, and after Reddit, it became more specific.

What should a local agent demonstrate for someone with a 'do not trust' setting to install it on their primary phone, not a spare one? Is a build without a network and a full action log enough – or is isolation needed, which the application itself cannot provide, and then it's a platform issue, not mine?

I asked something similar in the thread there and didn't get an answer. It would be dishonest to present someone else's silence as significant, so I'll just ask again, here.
