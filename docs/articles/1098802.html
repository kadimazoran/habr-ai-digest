How four everyday use cases evolved into an agent-based investment office, and why humans remain in the loop

When terms like SDD, AI PDLC, or HG PDLC are mentioned, ordinary people often perceive these acronyms as distant from real life and belonging to the rigid corporate IT sphere. I will explain through a series of personal experiences (from simple to complex) how these abstract concepts are implemented for personal ideas and projects.

Case 1: An Agent-Filter for Long Articles

Analytical resources publish many lengthy texts. There isn't enough time to read everything. It's frustrating to spend an hour on an article that is either far-fetched or full of manipulation.

The decision was made to create the first personal agent with a single skill: formal logic (based on Chełpanov's textbook: reviewing argumentation, text correction, syllogisms, and logical fallacies). Upon receiving a link to an article, it performs three actions:

  1. Article summarization—a concise summary of the author's main points (not a retelling, but a reconstruction of theses).

  2. A list of logical fallacies—for example, hasty generalization, straw man, false dilemma. This exposes hidden manipulations.

  3. Three theses the agent agrees with and three it disagrees with, with justifications for each.

As a result, in one minute, I receive a report and decide whether to read the article, skip it as uninteresting, or flag it as manipulative.

This agent is the first tool with non-deterministic logic and initial skills.

Case 2: A Medical Agent with MCP—From a Stack of PDFs to a Living Map

You periodically get medical tests done, and the clinic sends a bunch of PDFs. If there are any deviations in the results, it's unclear whether something is wrong internally or if you had a mild virus last week that you managed on your feet.

The decision was made to create an agent to which all PDFs from the medical application are uploaded. The agent has:

  • the ability to recognize PDFs with Cyrillic characters and tables;

  • a persistent structured storage (a personal medical record structure defined by me);

  • the capability to form a hypothesis about one's condition based on the aggregate of analyses and conclusions from various doctors;

  • analysis of doctor's recommendations: how closely they align with this hypothesis;

  • recommendations on what additional tests would be meaningful to confirm the hypothesis, and what lifestyle and dietary changes to make.

The recognition skill didn't appear immediately: at first, I simply made the agent process PDFs from medical clinics. After the first successful attempt at reading and recognizing analyses, I asked it to formalize this as a skill—to be used later when new PDFs arrived. Thus, a one-time task turned into a reusable tool.

The agent tracks changes in indicators based on test results, not just looking at a current snapshot. It builds an overall picture: what is already improving, and what still needs work. It shows not a snapshot of current indicators, but the dynamics: improving, stagnant, or worsening.

Crucially, the agent does not replace a doctor. It essentially provides prompts for the dialogue to have with the doctor at the next appointment, and does not dispute prescribed medications. It records your history of taking them: when you started, when you stopped, and correlates this with the dynamics of indicator changes.

This agent was the first to use MCP—integration with a Xiaomi account: the agent pulls data from smart scales with bioimpedance analysis about body composition, from smartwatches about physical activities and cycling workouts. Plus, it recognizes Excel files where home observations are manually entered.

Incidentally, such an agent is like a Tamagotchi, motivating you to regularly feed it new health metrics.

Case 3 (Prototype): Multi-Agent Currency Exchange Rate Forecast

Before my vacation, I faced the need to buy currency for daily expenses. The exchange rate is volatile, and buying at the peak is frustrating.

This resulted in the first attempt at a multi-agent system. Agents are divided into pairs, with each pair working on a specific factor influencing the exchange rate: fundamentals, technicals, news. Within each pair, there's an optimist agent and a pessimist agent: the former gathers arguments for why the rate will rise, the latter—why it will fall. Each provides a conclusion in a formal structure with a probability corridor. When commanded to "give a forecast for 5 days," a judge agent sequentially calls sub-agents, analyzes their responses, and issues a final conclusion, citing the arguments that seemed most compelling.

Each sub-agent has its own set of information sources and its own set of aspects that can influence the exchange rate. These aspects do not always overlap between the optimist and pessimist; there are asymmetric factors (e.g., affecting only the rate's decline). If a competitive pair had mirrored factors, it would simply duplicate the same viewpoint.

I delegated testing to my wife: periodically asking for a forecast for a few days ahead and recording on the forecast date whether it came true. I couldn't test it systematically and for a long time due to a lack of patience, but the positive feedback was unexpectedly strong: she said she had never bought currency so effectively before, and the exchange rate difference alone managed to cover a significant portion of her vacation expenses.

The downside of such a system with a competitive structure is that it's impossible to verify it historically for confirmation: I don't have a historical dataset of all factors and news influencing the exchange rate. Plus, there's no way to confirm forecasts built on technical analysis results. This pushed me to work on the next case.

Incidentally, after launching, I learned about a similar project at BlackRock. In August 2025, the company's researchers published a paper on AlphaAgents—a multi-agent system for stock selection and portfolio construction. The general principle is similar: three specialized agents with different areas of responsibility—fundamental (financial statement analysis), sentiment agent (news and analytical ratings), and valuation agent (historical prices, volatility, technical analysis). Each agent provides an independent opinion, after which they engage in debate and reach a consensus, considering the given risk profile.

Case 4 (Main): An Investment Office of Agents

One of my hobbies is quantitative investing. The problem is well-known: research consumes an enormous amount of time. You either need to develop your own indicators or combine existing ones, and all these experiments are endless.

I decided not to search for the Holy Grail but to launch a portfolio of strategies, each satisfying my formulated intention, and collectively smoothing out market and model risks. This means a pipeline of agents is necessary for the rapid deployment of trading strategies into production.

As a result, I have a collection of agents that essentially replaces an entire investment office. For example, the research-stage pipeline consists of the following agents:

  • the "researcher" agent analyzes specified sources and looks for fresh ideas;

  • the "developer" agent builds Python notebooks based on the found ideas and optimizes them;

  • the "reviewer" agent checks the notebooks: correctness of calculations, optimization of computations, and so on;

  • the "risk analyst" agent calculates specified risk metrics and charts for the strategy and then awaits my decision.

Of course, I will never let such a system run autonomously. At key stages of the pipeline, I make the decisions, not the agents. Only after my approval, confirming the strategy meets the criteria, does the next set of agents activate, implementing the script on the live platform: development, review, testing, and all this is looped (the cycle repeats in case of errors or remarks).

Separate auxiliary agents exist: some update data used in testing, others generate reports on the portfolio, and a third group verifies that the live strategy and the research notebook have identical trades. They are invoked separately from the pipeline, in dialogue with an orchestrator agent.

For myself, I formulated the following principle for breaking down the pipeline (or PDLC process) into agents: first, I maximally decompose the process, and for each atomic step, I create an agent. They turn out to be simple and with clearly defined operating rules and desired outcomes.

It seems I have achieved a human-guided product development life cycle (HG PDLC)—an AI-agentized product development life cycle, where the product is a trading strategy, and a human coordinates the pipeline.

The most challenging part turned out not to be the code or orchestration at all. The hardest part is clearly formulating the desired outcome (the Spec from Spec-Driven Development, SDD), which the pipeline agents should achieve. The clearer the intention is formulated, the fewer revision cycles are needed after reviewing the results, and the more predictable the outcome. A vague specification leads to agents working "in vain": formally doing everything correctly, but not what is needed.

I want to specifically address issues of interaction with the agent: notifications and remote access. When an investment event occurs in a strategy (opening or closing a trade), I must receive a notification. I used Telegram before, but after its blocking in Russia, I found the ntfy app, which solely handles notifications. This tool also proved useful beyond trading strategies: the coding agent, which houses all my projects, writes to me through it for any project if work is completed in a dialogue session, an outcome is presented, or my reaction, choice, or even access confirmation is required. The notification arrives indicating which specific project requires attention.

The system runs at home, but I want to interact with the agents from anywhere. Therefore, I created a web interface for the agent: after receiving a notification, I log in through the browser, quickly type a response, launch it, and return to my tasks.

When the risk analyst runs a strategy over a large historical range, it takes a long time, and there's no point in waiting for the result. I set up publication of such reports to Google Drive: the agent finishes, notifies me, and uploads the report. I log in, review it, and say "okay, deploy to production" or "stop, we're not considering this strategy further."

The agent implements LLM memory with the task of constantly expanding the experience used in developing trading strategies: life hacks formed from analyzed external materials, strategy runs, code development across all used stacks. Everything is stored in a knowledge base, and all agents are required to consult it before starting work. This creates a feedback system: agents use lessons learned from previous iterations, including from other agents. Thus, each completed run improves the next one.

All backtests during strategy selection and optimization consider the real commissions of my current broker and exchange, and use the division of history into test and validation periods. A separate skill verifies the match between real trades and strategy trades in the backtest for the past period, to avoid discrepancies between what history showed and what is happening in production.

What was the result? Previously, deploying a strategy to production took several quarters: everything was done manually, in free time outside of work and family. Now, over 30 strategies have been deployed to production in one week. These are strategies that meet my specified intentions: defined requirements for profitability (threshold CAGR set), risks (maximum drawdown limited, Sortino ratio, daily VAR), trade frequency, profit factor, win rate, and so on. Strategies are validated in production with small capital, so it's too early to talk about any success, but what has been achieved by the pipeline is something I couldn't have imagined even a year ago.

Technical Notes

1. When upgrading agents at each stage, I try to use the simplest possible skills. LLMWiki can be organized on graph databases and RAG technologies, but I chose an accessible open-source LLMWiki skill using simple markdown files, specifically organized for knowledge storage: concepts, entities, generalizations, synthesis. I did the same with notifications: I didn't fight Telegram's blocking but opted for the simple ntfy application. And I organized the transfer of results to me for all coding agent projects by copying them to Google Drive into my folder for each project.

2. The coding agent I use for all my projects is opencode: a fully open-source agent under the MIT license, not tied to a specific model provider. I had to install both the Desktop version (which I use at home) and the CLI (which organizes a web server for remote web interface).

3. Several skills, common to all projects, live on top of the coding agent. The first: a skill based on Karpathy's approach: a set of techniques that make the agent work with code like a thoughtful engineer would, not an autocomplete with ambitions. The second: a token-saving skill: rules that reduce context consumption without loss of quality. The third is a skill for publishing materials from any project to Google Drive. The fourth is a skill for notifications via ntfy.

Conclusion

From a single skill with formal logic to an investment office of agents—four cases, based on which the terms SDD, AI PDLC, and HG PDLC turned out not to be corporate abbreviations, but an understandable approach. By clearly formulating the intention and detailing the stages (agents), results can be achieved even in personal projects.
