VLM Hallucinations in Zero-Shot Detection: False Alarms about Smoke and a Prompt-Level Solution

How I tried to solve the task of fire and smoke detection without training, using zero-shot detection on VLMs. I describe how it initially worked on videos with real smoke, but on clearly smoke-free streets, the model found "smoke" in 70% of my data: drawing bounding boxes on cars, signs, and traffic lights, sometimes with 0% confidence and a textual explanation that there was no smoke. Early detection of smoke and fire is a common and valuable task in urban video analytics. A camera can spot a fire earlier than people on the street or an operator. Training a separate detection model requires a dataset, labeling, and time, and fires in a frame look too different to cover all cases quickly. Therefore, when the number of detection scenarios in work projects grew, I decided to try a shortcut: ask a VLM (a language model capable of working with images) to find smoke using a text prompt in zero-shot mode, meaning without any task-specific training.

For the first model, I chose Qwen3.5-9B — a medium-sized VLM, around 9 billion parameters. The scheme is simple: input is a frame and the prompt 'find smoke, return bbox', output is JSON with coordinates. The detector is configured by a text description, which is the main advantage of this approach.

On test videos from street and panoramic cameras with real smoke, the system worked well. However, testing on clearly smoke-free videos (ordinary courtyards with parking, lawns, trees, people, shops) ended unexpectedly: false alarms in 70% of frames, up to 96% on some videos.

In the article, I analyze why this happened, which known prompt engineering techniques did not help, and how the problem was solved by changing a single prompt: the proportion of false alarms on problematic cameras decreased from 70% of frames to zero, and the FPR (false positive rate on negative frames) on an independent benchmark dropped from 10.6% to 0.6% with recall above 80%.

The main conclusion from the experiments is: the detection task consists of two decisions – 'is the object present?' and 'where is it?', and combining them into a single VLM response step and a single output format can cause false alarms when the object is not in the frame.

Test Data

Briefly, on what everything was measured. There are two sets:

  • Negative Sample — videos from real street cameras, mostly courtyards, about two thousand frames. The absence of smoke and fire in them has been verified manually, so every alarm on this set is false. It was on this set that all the "70% false alarms" and all prompt iterations were measured. Frames within the same video are highly correlated, so further on we look not only at the proportion of frames but also at the number of unique objects that triggered alarms.

  • Labeled Benchmark — thousands of images with manual annotations, selected for our domain: positives (distant smoke and fire over forests and fields, building and car fires, street smoke) and negatives with similar scenes. Recall, precision, and FPR were calculated on it. Prompt variations were selected on the negative sample and a separate small labeled set with real smoke, not overlapping with the benchmark. The benchmark itself was used only for final evaluation. The data is not academic but oriented towards real operating conditions.

The proportion of false alarms here and further is calculated per frame: it is the proportion of negative frames on which the model returned at least one detection. All measurements are greedy generation (temperature 0) without constrained decoding: the response format was determined solely by the text of the prompt, and the decoding scheme was not imposed.

Initial Prompt and Its Behavior on Negative Data

The initial prompt was typical for zero-shot detection:

Detect uncontrolled outdoor fire or wildfire smoke. Ignore chimney/exhaust
smoke, steam, fog, clouds, rain, snow, lens glare.
...
Output ONLY JSON in markdown code block:
[{"bbox_2d":[x1,y1,x2,y2],"label":"smoke"|"fire","confidence":0.0-1.0}]
If nothing matches: `[]`

The empty response `[]` in the prompt was formally allowed. However, on clean frames, the model almost never used this option.

What did it respond with instead? After analyzing the false alarms, I found that they all boiled down to about 50 unique, consistently present objects in the frame:

The hypothesis arose that the model wasn't "seeing smoke" but was marking anything that remotely resembled the fire and smoke examples from the prompt: vehicles that might emit smoke, bright red-yellow objects resembling flames, diffuse light spots resembling haze. An alternative explanation is language priming: the words fire, smoke, wildfire in the prompt itself increase the probability of semantically related objects in the response. Both remain hypotheses: it's impossible to determine from individual bounding boxes what specific visual features the model used.

The Model Can Say "No Smoke" — But Still Draws a Box

The most interesting part turned out to be the raw responses. In 21% of false detections, the model returned a bounding box with `confidence: 0.0` and simultaneously explained in text that there was no smoke in the frame. The response contradicts itself: one part asserts "no object," while another contains object coordinates. This shows that at least some errors are not due to an inability to recognize an empty frame but to a mismatch between parts of the generated response.
