Following my move from Claude Code to Codex on Habr, a debate arose: is dialogue history needed if Git, documentation, and specifications exist? I examined arguments, tools, and research. It turns out the problem is much broader.

In early November, I wrote on Habr about how, after the paid Claude Code organization was blocked, I switched to Codex and tried to preserve project history.

The code remained on my computer, the repositories didn't disappear. But over several months, dozens of conversations about architecture, bugs, experiments, and plans accumulated. Not everything made it into the documentation.

The built-in import in Codex proved inconvenient: out of 25 projects and 53 chats, about 50 sessions were transferred, but linking conversations to projects was unsuccessful. Eventually, I found Hansard and started accessing old history through search.

I thought that would be the end of the story. However, a debate began in the comments.

greenrus suggested storing decisions and plans in Git. mist56 reminded about skills, KB, and documentation, and then pointed out the amount of noise in old dialogues. becefi raised the issue of transferring reasoning state and differences between model protocols.

Other readers shared their own memory and agent management systems. And RouR wrote a separate article, "Context Should Be in the Repository, Not in the Chat," describing GRACE and doubled-graph.

I began studying these approaches and realized that we are often arguing about different tasks.

Preserving history, handing off unfinished work, and providing an agent with reliable knowledge are not the same thing.

Context is Not One Big File

Suppose a new agent opens an existing project for the first time. It needs to understand the architecture, constraints, and current state of work.

But information about this is scattered across different places.

Code shows what's implemented now, but doesn't necessarily explain why a particular architecture was chosen. Documentation might contain the reasons, if they were recorded and updated promptly. Conversation history preserves more details, but along with them, erroneous hypotheses and outdated information.

Therefore, the task is not to force the agent to read everything.

It's necessary to choose the appropriate source and determine how much trust can be placed in the information obtained.

Current Project: Documentation, Specifications, and the Code Itself

Here, critics of my initial approach have a strong argument.

A new developer doesn't start by reading the entire project history. They are given a map of the system, instructions, and a specific task. They study other materials as needed.

It's logical for an AI agent to do the same.

In a small project, AGENTS.md or CLAUDE.md, up-to-date documentation, ADRs, work plans, and tests are often sufficient.

But Git itself is not a memory system. It's version control: specifications, decisions, plans, and even session history can be stored in the repository. The content and currency of these materials are more important.

When There's Too Much Source Code

Navigating a large codebase is a separate problem.

Aider Repo Map generates a compact project structure map, considering token budget. The article "Codebase Intelligence for Agents" discusses searching and indexing a Rails monolith of over 3.5 million lines.

Structural navigation, symbol relationships, and semantic search allow you to avoid reading hundreds of files for a single change.

However, even a perfectly found code snippet doesn't necessarily explain the history of a decision.

How Not to Trust Outdated Documentation

Suppose an architectural document states that two modules are independent, but code has already introduced a link between them.

An agent might read the document and suggest a change based on outdated information.

OpenSpec and GitHub Spec Kit help organize work through requirements, specifications, and plans.

RouR, in his article, describes GRACE and doubled-graph, which maps declared architecture to the structure of actual code.

This check potentially allows detecting architectural discrepancies. But graph matching doesn't guarantee correct program behavior, and specifications and contracts require maintenance.

For a large project, this might be justified. For a small utility, it could be overkill.

The key here is not the choice of a specific methodology, but the principle: it's advisable to verify current knowledge against an independent source—code, tests, or execution results.

Historical Memory: Hansard and Deja-vu

Let's return to my own scenario.

The blocking of Claude Code happened unexpectedly. Many decisions existed only in previous conversations. I didn't have time to prepare a complete set of documents for migration in advance.

This is where Hansard came in handy. It allows searching through saved sessions of different agents, accessing them via Recall, and continuing work in another agent environment.

Example from NetRuleRouter

I am currently continuing the development of NetRuleRouter, a program for routing traffic through various connections.

While investigating a Windows TUN error with error code 5010, the agent reported:

Hansard confirmed TUF as a dedicated Windows laptop and a local copy of the repository on it.

After this, the agent indicated the need to check logs and the lifecycle of TUN/routes before changing the code. Information about the test laptop and the conditions for reproducing the error might not be part of the architectural documentation. However, they can be useful during diagnostics.

At the same time, I cannot yet claim that Hansard sped up the error correction. To conclude this, I would need to examine the Recall request itself, the sources found, and the impact of the information on subsequent actions.

This episode shows the potential benefit of historical context but is not yet a measure of the tool's effectiveness.

Why Deja-vu is Interesting

Another project is deja-vu by VShulcz. It indexes local logs of coding agents and provides search via CLI, MCP, and other integrations.

Particularly interesting are the features tied to development:

  • deja wip — restoring unfinished work;

  • deja blame — finding historical sessions related to files;

  • deja fix — searching for past actions after similar errors;

  • statuses of decisions, including rejected ones;

  • warnings about file changes after a found discussion.

The latter capabilities help not just find old recommendations but also assess how applicable they still are. For example, if a found fix relates to a module that was later rewritten, it's a reason to further verify the search result. And the absence of error repetition in an old log doesn't prove that the found action fixed it.

I haven't tested deja-vu myself yet. Hansard already covers my current needs, so I don't plan to install a second indexer just for a review.

When History Helps Specifications

An interesting detail: the deja-vu session recall extension is already included in the GitHub Spec Kit community catalog. Its submission was closed on November 5, 2026.

The extension uses current spec.md and plan.md to search old sessions: what was tried before, which decisions were rejected, and which files were changed.

However, being included in the community catalog doesn't mean the Spec Kit maintainers have verified or approved the quality of the extension's code. The catalog confirms the correctness of the entry's formatting, not the results of an independent audit. But the mechanism itself is interesting.

Specifications define the current task, and the archive helps avoid repeating experiments already conducted.

Here, history and documentation do not compete but complement each other.

Handing Off Unfinished Work and Coordinating Agents

Now, another scenario. Claude Code fixes a bug, executes commands, changes files. At this point, the limit is reached. You can ask it to prepare HANDOFF.md in advance, but if the work is already interrupted, this might not be possible.

For such situations, baton was developed, described in the article "Transferring Sessions Between Console AI Agents Without Context Loss." It reads existing logs, prepares materials for continuing work, and can transfer local changes between computers.

Hansard also supports continuing work in another agent. Therefore, such solutions should be compared not by the presence of a "Continue" function, but by what data is actually transferred: message history, tool results, changed files, work plan, links to sources. Moreover, a saved log is not equivalent to transferring the model's internal state. Thinking blocks, caching specifics, and different providers' protocols do not guarantee identical reasoning continuation.

Orchestrators have another mechanism. For example, LangGraph separates execution checkpoints from long-term knowledge stores. A checkpoint allows resuming a process from a known state. Historical memory helps reconstruct past experience. Both approaches can be used in one product.

When There Are Multiple Executors

In the comments, anikin-v described his practice: task work folders with plans, hypotheses, and intermediate results. The agent updates them itself or upon command.

Another part of his experience is particularly interesting. For long-term tasks, he sometimes uses a separate controller agent that doesn't write code. It monitors the plan, prepares tasks for executors, records results, and organizes work handoff. Essentially, it forms a small virtual team.

Similar problems are addressed by Beads and SpecWithCode, which aabyzov mentioned.

Another example is the multi-agent OpenIDE, which allows creating separate discussion branches, passing tasks to different agents, and returning verification results to the main conversation.

Here, it's no longer just about storing memory, but about managing context flows between executors.

However, structured handoff doesn't eliminate errors either. The controller might misunderstand a report, and a summary might lose a significant detail.

Automatic Memory: Recording Doesn't Mean Remembering

Between a full archive and manually maintained documents lie systems for automatic knowledge extraction.

Claude-Mem, kaeru, and skillmem use various mechanisms for saving observations, decisions, and reusable techniques.

But two problems arise here: when to access memory and how to determine the reliability of what's found.

The Cost of Memory That Isn't Used

In the article "Recording Doesn't Mean Remembering," the author described an experiment with MemShelf. After 38 days of system operation, the index and digests of 157 saved episodes occupied about 36.6 thousand tokens — 18.3% of a 200 thousand token window.

In another segment — over 30 separately analyzed days — the author found no calls to MemShelf and DocShelf MCP tools. However, he accessed the archive manually.

These measurements cannot be directly combined into a single effectiveness statistic. And the absence of MCP calls doesn't prove the uselessness of all memory: information might have entered the context through other means.

However, the problem is clearly visible. Constantly loaded memory can occupy a significant portion of the window without corresponding search benefits.

The developers of kaeru encountered a similar issue. They analyzed over 13 thousand log files; in one small observation, agents never used the optional suggestion to read saved reasoning over seven sessions.

Seven sessions are too few for general statistical conclusions, but the problem itself is understandable. An agent might have access to memory and not use it. Or, conversely, the system might inject history too often, consuming tokens and polluting the working context.

MCP provides a call interface. Hooks, instructions, and skills can manage the moment of access. But no mechanism guarantees the relevance of the result on its own.

Context Window Also Needs Control

In the paper Effective Context Engineering for AI Agents, Anthropic discusses history compression, tool result cleanup, selective file reading, and sub-agent work isolation.

This is not the same as long-term memory. Compression frees up space but can lose details. Cleaning command results reduces context size but sometimes requires repeated calls. Sub-agents allow not transferring all intermediate reasoning to the main session.

Therefore, increasing the context window alone does not solve the knowledge management problem.

What If Memory Preserved an Error?

Suppose an agent made a wrong conclusion and recorded it as useful experience. Later, another agent retrieves this record and takes it as confirmed. This leads to an accumulation of errors.

Therefore, it's useful to store not only the content of the record but also its source, date, status, verification conditions, and link to the current code.

It's especially important to distinguish between hypotheses, confirmed results, canceled decisions, and information with unknown reliability.

There's also a security issue. An old dialogue might contain instructions that once pertained to a different task or were obtained from an untrusted source. If an agent starts executing them while reading the archive, historical memory becomes a channel for transmitting unwanted commands.

Therefore, retrieved conversations should be treated as data about the past, not as new instructions for execution.

From Historical Discussion to Verified Solution

After familiarizing myself with various tools, I formulated a simple workflow for myself.

Suppose an agent finds an old discussion about fixing a TUN error. Applying the found solution immediately is risky. First, you need to establish the source and date of the discussion. Then, understand whether it was a hypothesis, a confirmed result, or a rejected option.

After that, compare the findings with the current code, documentation, and tests. Only after verification should you use the solution or discard it. If something important is established, the result should be recorded in the current work plan, ADR, or KB. This results in a sequence:

Find → Establish Status → Verify Relevance → Apply and Verify → Record Result.

Here, the archive and documentation serve different roles.

The archive preserves evidence of the past. The current knowledge base records information that the project can rely on now.

Moreover, the latter also requires verification and updates.

How to Tell if Memory is Actually Helping?

I studied most of the tools discussed through their documentation and authors' publications. I haven't conducted comprehensive comparative testing yet. And the question "found or not found?" is not enough for such a test.

The LongMemEval, ICLR 2025 research offers a useful foundation. Its criteria can be adapted to development:

LongMemEval itself is designed for the long-term memory of conversational assistants. Therefore, its results cannot be directly transferred to coding agents.

But more programming-relevant research has emerged.

VibeMemBench: Does Memory Actually Help Fix Code?

In September 2026, the authors of VibeMemBench proposed evaluating memory on real repository modification tasks. The study included 111 tasks from 90 repositories and 3634 historical work trajectories. Success was determined by executable tests, not just the accuracy of recounting the past.

The authors compared agents without memory, with directly provided prior verified experience, and with systems that had to independently extract this experience from history.

The result was telling.

Direct transfer of verified experience improved task performance for four out of five tested executors. However, in 11 out of 12 agent-memory system combinations, automatic experience extraction did not outperform the corresponding no-memory variant.

This doesn't mean memory systems are useless. The tasks in the benchmark were specifically selected for the utility of historical experience under controlled conditions, and specific implementations and models were tested.

But the study shows a significant gap between two capabilities:

Useful experience exists in history — and the system is truly capable of extracting it in time for the agent to perform the task better.

For me, this is the main argument for verifying not only the accuracy of Recall but also the final development result.

How to Test on Your Own Project

For a practical experiment, I would take a real project where different ways of solving a problem were discussed over several months.

I would provide one agent with the current repository and documentation. To a second agent, I would additionally provide the history archive. To a third, a pre-prepared verified summary.

Then I would compare the correctness of solutions, sources, token consumption, time, and manual preparation effort.

Handing off an interrupted session and the work of multiple agents would need to be tested separately: these are different tasks. Until such measurements exist, declaring one tool a winner would be premature.

It's wiser to choose a tool for a specific problem rather than based on the number of features.

And About Confidentiality

A local archive doesn't necessarily mean fully local processing.

If a cloud agent receives a historical fragment via Recall, it might send it to the model provider along with the query.

Furthermore, logs can contain configurations, working paths, internal information, and secrets.

Therefore, it's important to check what data is indexed, where it's sent, what is excluded from storage, and how records are deleted.

Similarly, placing documentation in Git doesn't guarantee its security or currency.

What I've Concluded

This story began with a simple task: after Claude Code was blocked, to retain the ability to continue development in Codex.

But thanks to the discussion, it became clear that a whole set of engineering problems lies beneath the surface of AI agent memory.

Dialogue history helps reconstruct past experiences. Documentation and specifications describe current knowledge. Work plans allow for task handoff. Orchestrators manage multiple executors. Automatic memory attempts to extract and store useful experience.

Each approach has its limitations.

An archive might return outdated information. Documentation might lag behind the code. A controller agent might make mistakes when preparing a summary. And an automatic memory system might diligently store information that no one uses.

Therefore, for me, the main question now is not how much data an agent can remember.

It's more important whether it can find the necessary information in time, verify it, and make the right decision.
