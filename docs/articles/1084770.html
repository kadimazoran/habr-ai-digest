Jev only answers "yes/no" or chooses from provided options. 16,000 calls: first a comparison with gpt-5.4-mini and gpt-5.6-luna on four open datasets, then several thousand real-world decisions in workflows. Where it wins, where it errs, and how to use it.

TypeSafe opened early access to Jev on September 15. The impressive numbers in the announcement were obtained by comparing it to a flagship model that generates text. However, most teams do not use flagship models for classification. Thousands of everyday decisions in workflows—whether to read a page, whether an email contains a request, what category an object belongs to—are already made by small, fast models: flash-lite class models, gpt-5.4-mini, gpt-5.6-luna. These are the ones Jev is supposed to surpass. I compared it against them.

Jev does not write text. You provide it with text and a question with fixed answer options, and it returns a probability for each option. A single call looks like this:

POST https://api.typesafe.ai/v1/systemone

{
  "model": "jev-latest",
  "state": {"text": "i am sorry that i was unable to get the full brunt of the comedy ."},
  "questions": {
    "sentiment": {
      "type": "choice",
      "instructions": "Is this movie review positive or negative?",
      "criteria": {"negative": "Unfavourable", "positive": "Favourable"}
    }
  }
}
{
  "answers": {
    "sentiment": {
      "choice": "negative",
      "probabilities": {"negative": 0.97, "positive": 0.03},
      "confidence": 0.93
    }
  },
  "usage": {"input_tokens": 336},
  "model": "jev-1.13.0"
}

From my laptop, this call took 850 ms and cost $0.000014: 336 input tokens at $0.042 per million. The output is free, as there are no output tokens. A choice type question can have up to 255 options. The response includes the probability of each option and a confidence score—the certainty of the chosen answer. A noul type question (as TypeSafe calls "yes/no" questions) returns a single number: the probability of a "yes" answer. Therefore, 0.05 means a confident "no," and 0.95 means a confident "yes." A single call can include multiple questions.

TypeSafe does not explain how confidence is calculated. It's not the maximum probability: in the example above, they are 0.93 and 0.97 respectively. However, selecting by maximum probability yielded the same pattern on open datasets with a difference within one percentage point. In this article, a "confident answer" means a value no further than 0.1 from either end of the range for "yes/no" questions, or a value of 0.9 or higher for choosing one option.

I spent two days and about 16,000 calls to figure out what Jev is useful for. First, I tested it on four open datasets for classification: two small OpenAI models answered the same questions. Then, on several thousand real-world decisions from workflows I'm involved with. I evaluated correctness based on what actually happened, not on another model's opinion.

Key Takeaways

— On short text classification, Jev matches or surpasses gpt-5.4-mini and gpt-5.6-luna on three out of four open datasets. It is 5–56 times cheaper, with a median response time under a second.

— Its probabilities can be trusted near 0 and 1. For tasks it handles well, confident answers were correct 90–100% of the time. In the middle of the range, performance is comparable to a coin toss.

— It works best with short inputs and clear class labels. The longer the input, the fuzzier the labels, and the more business logic in the question, the more accuracy and confidence drop simultaneously. When analyzing a full document, it underperforms the small model we currently use. No prompt fixed this.

— Therefore, it acts as a filter, not a complete replacement: it handles confident decisions at both ends of the spectrum, passing the rest to the model you already use.

Four Open Datasets

For testing, I randomly selected 300 examples from each of four open datasets: Enron spam—for spam detection in emails, AG News—for determining the sentiment of movie reviews, and Banking77—for identifying reasons for customer support inquiries. Each model received the same question and the same one-line description for each label. It was required to return the probability of each option: without this, a confidence-based selection cannot be built. Both OpenAI models were called via the Responses API with a reasoning level of low. gpt-5.6-luna is also included in TypeSafe's own evaluation leaderboard.

Jev takes roughly the same amount of time regardless of the task. LLMs slow down as the number of options increases because they record the probability for each one. All measurements were taken with 20 concurrent calls—as would happen in a workflow. However, Jev's latency tail isn't always so neat: with 100 concurrent calls, several requests out of every thousand took between 10 and 35 seconds.

Two notes on cost. The LLM bill includes output tokens, and the requirement to return the probability for each option is what makes calls expensive. For Banking77, this is about 700 output tokens per call, so a thousand calls to gpt-5.4-mini cost $3.81. If you only ask for the selected option, the bill will be several times lower, but then you won't have a confidence score to make decisions by. Furthermore, the cost difference depends on what you compare it to: 5–15 times less than gpt-5.6-luna, 100 times or more less than a model with intensive reasoning or an agent. We'll return to this.

For routing, the comparison was with the current classifier: these pages do not have their own subsequent outcome. For simple page types, Jev is indeed useful. It matched the actual outcome 96–98% of the time, and our current classifier 95–97%. Its probabilities barely changed: asking about the same page twice resulted in a difference of about 0.01. We placed it before the classifier as an exclusion filter: any page with P(yes) below a threshold, chosen using the method described below, is not sent to the model. The rest are processed as before.

We repeated five production runs with and without the filter. The outcome for all 1,005 pages remained the same, but the number of calls for routing decreased by 50–67%, for administrative pages by 45–74%, and for object lists by 8–13%. The last gain is modest because the classifier reads pages in pairs. A pair can be skipped only if both pages fall below the threshold.

Jev did not handle complex page types well. The question "Is there a value on the page for one of the 135 report lines?" requires distinguishing a mention of something from a specific value, and Jev triggers on the mention itself. To achieve our completeness, about twice as many data extraction tasks were needed. The probability for the same page could change by 0.5 between runs. A general-purpose LLM made the same mistake on the same question: it's a problem with the task, not the model.

The most interesting case was email. Currently, for every email in the general support inbox, an agent session is launched. It decides whether the email contains a request we need to handle. On average, this costs about 12 cents and takes 94 seconds. In most cases, the answer is "no." Given the same email and the same written rules, Jev matched the recorded outcome in 87% of cases. For emails where it was confident, the accuracy was 96%; these emails accounted for 69%.

However, some actual requests received a probability close to zero—a confident "no." For example, a standard request mentioning a third party was interpreted by the model as a change in rules. Therefore, there is no loss-free threshold here. There is a trade-off: if you discard everything below 0.03, 78% of non-request emails are eliminated, but along with them, 5 out of 231 actual requests in this set are lost.

These five cases are mainly short forwards from colleagues and emails where all significant information is in a photo, which Jev cannot read. If both types of emails are always sent to the agent, about one request out of 140 is lost among the rest.

Trust the Edges of the Range, Not the Middle

The value of this number is that at the range's boundaries, it corresponds to reality. On open datasets, 82% of answers came with a confidence of 0.9 or higher; 96% of these answers were correct. With confidence below 0.9, the proportion of correct answers ranged from 55% to 72% depending on the interval.

For our pages, this number is P(yes), so the two edges represent a confident "no" and a confident "yes." Both work: 82% of pages had a probability below 0.1, and only 0.3% of them were needed. 4% of pages had a probability of 0.9 or higher, and 97% of them were needed. The remaining 14% were in the middle, where the proportion of needed pages varied from 6% to 83% depending on the interval. A single threshold is not enough here. Therefore, trust the edges, and pass the middle to a model that can truly understand the content.

The page graph combines three filters: a total of 2,559 calls. From the routing filter, only 549 pages were included, which have their own subsequent outcome.

The discard threshold does not need to be chosen arbitrarily. Take all examples that are known to be positive, find the minimum P(yes) that Jev assigned to at least one of them, and set the threshold at half that value. Tune it on one part of the data, test it on another, and re-verify as new data emerges. Next month, you might encounter a true positive example with a probability lower than any you've seen before.

For our filters, I tuned the threshold on four out of five production runs and tested on the fifth, rotating the test run. On no split were pages lost. The resulting thresholds were 0.12, 0.065, and 0.025 for routing, administrative information, and object lists, respectively. They were calculated based on 187, 124, and 61 positive examples and allowed discarding 25% to 60% of pages.

The threshold is determined by your positive examples, not by the high confidence range, so it can be either above or below 0.1. For emails, this method discarded almost nothing: there is no useful loss-free threshold, only the trade-off described above.

What Others See

Three days after launch, most of the noise was still reactions to the announcement. In the Hacker News discussion, there are nearly 500 comments, but very few are from people who have actually called the API.

The debate is about how the results are presented. The "193 times faster" and "444 times cheaper" figures are obtained by comparing Jev to a flagship model that outputs text. "Cannot hallucinate" means the output is typed, not that it is correct. And TypeSafe's own evaluation leaderboard compares answers to the average result of GPT-6 Astra and Claude Fable 5.1, not to true answers. On it, Jev has 67.8% compared to 74.1% for the best LLM: it's not first in accuracy anywhere, but it is 200 times cheaper.

When one of the commenters called it "essentially a zero-shot classifier," the CEO replied: "Precisely." This is the most useful suggestion in the entire discussion. Within two days, open-source equivalents appeared on GitHub and Hugging Face, as well as a collection of 70 repositories.

Reports with measurements, where Jev and LLMs were run on the same task, are divided by task nature.

Short input, clear labels: Jev wins or shows comparable results. Near Here tested event announcements, comparing it with Mistral Small 4 and Gemini 3.5 Flash-Lite with high reasoning. Result: 48 correct answers out of 50 versus 42 and 43; none of the 13 real events were filtered out; 0.6s versus 2.9s and 3.4s; 4 cents per thousand calls versus 37 cents and $2.50. Vercel's CTO ran Jev on an existing classifier test that used Gemini 2.5 Flash Lite. Jev "won both in quality—reaching the test ceiling—and speed: 6 times faster."

HiringCafe evaluates resume-job description match against human labels: Spearman correlation of 0.79 at a cost of 2 cents per thousand calls versus 0.77 for DeepSeek V4 Flash at 14 cents and 0.72 for Gemini 3.1 Flash-Lite at 29 cents. Spam detection on 19,500 emails yielded 98.3% accuracy without fine-tuning—on par with a logistic regression trained on 15,000 of those emails. Calibration matches my observations: 0.1% spam at probability below 0.1, 99.9% at probability from 0.9, and 38% in the 0.5–0.6 range.

Classmethod's model router: 40 out of 40 at a cost of 2.5 cents per thousand calls; confidence is lower in the middle range of models. Every: detected 6 out of 7 intentionally introduced defects in 0.35s per fragment. Claude Fable 5.1 found all 7 in 8.8s.

Longer input, fuzzy labels, or reasoning-required decisions: Jev loses, and the fix is always the same. In a test on 2,000 phishing emails, Jev had 62.6% accuracy compared to 81.3% for Claude Haiku 4.5, with worse calibration and a result fluctuation of 5 percentage points solely due to question wording. Five narrow "yes/no" features combined with logistic regression yielded 95%, and Haiku on the same five features yielded 93%.

Samuel Sacco tested 800 examples of increasing complexity. Probabilities were overestimated at the lower end of the range and underestimated at the upper end. However, all answers with confidence of 0.9 or higher were correct; these answers accounted for 21% to 32%. His advice is to treat the number as an estimate and tune your own thresholds on several hundred labeled examples. I came to the same conclusion. In a poker study, answers were compared to a solver: 63% on random situations, 94% on simple ones.

Jev's weakest scenario on TypeSafe's own leaderboard is invoice processing: 61.8% versus 79.1%. This is the same full document analysis that failed for me.

Verdict

A filter. Jev is cheap and fast, answering only "yes/no" questions and questions with a single choice option. At the edges of the range, its probabilities correspond to reality. This is enough to place it before a classifier, but not enough to replace one.

Below the discard threshold on our data, it made no errors. Such examples bypass the classifier, and nothing changes further in the process. Our page filters thus discarded 25% to 60% of pages. Above 0.9, it is correct in 97% of cases on our pages and in 90–99.6% on each of the open datasets. Therefore, where most examples fall into the upper part of the range, you can act on Jev's answer and not call the classifier at all.

For pages, we didn't need this: only 3–9% of them receive such high values. But for the spam filter, the upper range is much larger. On Enron, 90% of examples received a confidence of 0.9 or higher with 99.6% accuracy—nine out of ten classifier calls are no longer needed. Everything in the middle is passed to the model you already use, as before.

The pattern held across all tests—mine and others'. Short input, clear labels: nearly perfect results and high confidence. Long input, fuzzy labels, or a rule requiring reasoning: accuracy and confidence drop together. The solution is to break down the question into narrow "yes/no" features and combine them in code. In the phishing test, this raised the result from 63% to 95%.

It is precisely at this limit of capabilities that one should pay attention. All of Jev's errors in these examples are related to long input, and TypeSafe's own notes state that accuracy decreases as state increases. If the next version can handle a whole page or conversation as well as the current one handles a single sentence, the filter will become a classifier even for complex tasks, and passing to another model will become the exception.

Tune both thresholds based on your own recorded results and test on data that was not used for tuning. Do not assign Jev questions that cannot be answered without comprehending the entire document. A question from the title can be answered with a single word. The main work is to determine where to draw the two boundaries.
