In the previous article, I talked about how our three-week RAG pilot for technical documentation stretched into three months. We intended to teach corporate AI to answer questions from engineers and managers, but instead, we discovered that we first needed to sort out our own documents.

We've made progress since then. We've built a knowledge base, set up search, prepared hundreds of test questions, and finally started testing the assistant on real engineering tasks.

The interim result is 84% correct answers on a test set of 188 questions. For us, this is a way to test a hypothesis: can the assistant handle the routine navigation of dozens of diverse factory specifications and reduce the number of inquiries to engineers regarding standard equipment parameters?

But overall percentages hide the most important thing – how exactly the system makes mistakes in complex engineering queries.

It turns out that AI can find the right document, correctly extract a number from it, and still make a mistake. It might refuse to answer a question for which all the source data is available in the base. Or it might not notice that the problem statement itself is flawed.

Today, we'll discuss how we test corporate RAG on real factory documentation, what tasks it stumbles on, and what errors we've already managed to fix.

From an Excel Registry to 27,000 Fragments

Let me remind you of the task. PSM produces power equipment, and we want a manager or engineer to be able to ask a question in plain language about a specific power plant and get an answer based on the technical documentation.

For the pilot, we chose the AGBa1000 gas piston power plant with a capacity of 1 MW.

In the previous article, I discussed 44 variants of its configuration. Here, 44 is a different number – the number of documents included in the test knowledge base: operating manuals, system descriptions, technical data sheets, and component manufacturer instructions.

Of these, 29 are PDFs, 12 are Word documents, and 3 are Excel files. Exactly half of the documents are in Russian, and half are in English. However, if we consider the search index volume, 94% of the fragments are in English: the large component manufacturer manuals are written in it.

The entire array was divided by the system into 27,007 search fragments.

And here, the first interesting task arose. Our engineer asks a question in Russian, but the answer might be in an English-language engine passport, in a table on the 150th page, or in a document whose name doesn't even contain the designation of our unit.

It's not enough to just upload files. The system needs to understand which documents relate to a specific configuration, be able to match terminology, and find applicable data.

In parallel, we pursued two paths. First, we integrated RAG search into an already operational corporate AI assistant so that employees could test it. Separately, we continued to develop a target RAG platform with stricter search and source verification mechanisms.

The solutions do not compete. The first allows us to get feedback now, while the second is intended to become a full-fledged tool in the future.

Measuring Quality, Not Just the Impression of an Answer

A big problem with testing language models is that they can talk very convincingly.

You can ask ten questions, get ten beautiful answers, and decide that the system works. But what if one of those answers confuses the generator voltage or the permissible gas pressure?

We decided to check specific technical facts.

We prepared several control sets with reference answers. These included questions about equipment parameters, operating modes, component documentation, and practical scenarios for operating the plant.

Parameters of the main measurement:

  • Object of verification: RAG search in the knowledge base of the AGBa1000 gas piston power plant (44 documents: manuals, system passports, service instructions from component manufacturers).

  • Evaluation methodology: automatic comparison of extracted numbers with the reference and verification of semantic consistency with found fragments by an independent model (this is an automated convergence test, not an expert acceptance).

Case #1. How Two Supports Became 161

Let's start with a classic data extraction task from a table.

In the AGBa1000 gas piston power plant, the electrical power of 1000 kW is delivered by a 0.4 kV generator in the base continuous load mode. Depending on the type of connection to the engine, the generator can have a single support bearing and a rigid flange to the flywheel, or two own bearing supports via a flexible coupling.

The tester asked a direct question:

“How many supports are required for the AGBa1000 station generator at 1000 kW in COP mode on gas fuel?”

The knowledge base contains the official technical letter from the generator manufacturer. It includes an applicability table where, for the power range of 800–1120 kW, gas drive, and COP mode, the execution is clearly indicated: 2 supports.

However, the assistant did not see this information:

AI Answer: “The provided technical documentation does not contain information on the number of supports for a 1000 kW generator.”

The user sent a screenshot of this document page to the chat. Based on the image, the model was able to recognize the line and corrected itself: “For the 800–1120 kW range in COP mode, 2 supports are required.” That is, the system lost the information in the text layer of the document but found it visually in the screenshot.

In another test, a more interesting situation occurred. During the automatic processing of this same scanned letter, the recognition module stumbled over complex layout: merged header cells and column separators shifted. As a result, numerical values from adjacent columns merged into one line.

The power range of 800–1120 kW turned into a fantastic 16,000–16,100 kW, and the design of 2 bearing supports, picking up the index from the adjacent column, transformed into 161 supports! Imagine the reaction of an engineer who is advised by a corporate assistant to include 161 generator supports in the station's design.

The cause of the error turned out not to be LLM hallucinations. The model conscientiously retold what the search index received. The problem arose at the very first stage, during the parsing of the scanned document. The factory archive is full of scans of letters, questionnaires, and drawings with merged cells and small footnotes. If the parser destroys the table structure, it no longer matters how smart your neural network is.

Conclusion: the quality of engineering RAG depends on the reliability of data digitization. Scanned tables cannot be fed to a general text parser "as is": they must either be indexed line by line with explicit preservation of column headers, or pre-validated by special table recognition models.

Case #2. AI Found Two Documents but Couldn't Connect Them

Now for a more complex task – correlating disparate documents.

The tester asked:

“What steps can be used to load the AGBa1000 gas piston power plant?”

In the station's operating manual, the assistant found a general requirement: load acceptance must be stepwise. However, the specific load step values are not regulated in the operating manual. The system honestly replied that it could not confirm the exact load step for the station.

At the same time, the knowledge base contained an official technical letter from the engine manufacturer with recommendations for the 16M33 family: a step increase of no more than 10% of nominal at steps up to 50% capacity and no more than 5% in the 50–100% range. But the model did not correlate this data with the station because the AGBa1000 power plant name is not mentioned in the letter.

The logical chain for an employee here seems obvious:

AGBa1000 Power Plant → Baudouin 16M33G6N0/5 Engine → Engine Manufacturer's Recommendations.

But this task hides an engineering boundary that caused a discussion within the working group.

Developers rightly noted that the model has no right to transfer component parameters to the finished product without confirmation. Baudouin's recommendations are for a "bare" engine on a factory test bench. The complete gas piston unit at the site includes a generator, turbochargers, a gas manifold with a specific supply pressure, and its own control system. The rate of load acceptance by the finished unit depends on gas quality, air temperature, and operating mode (in parallel with the grid or in an isolated island).

Testers, conversely, argued that the connection is already contained in the documentation and just needs to be discovered.

As a result, a more precise task was formulated. The assistant should be able to find confirmed links between equipment and components, but at the same time distinguish between reference recommendations from the engine manufacturer and guaranteed characteristics of a specific power plant.

What the assistant's correct answer should be:

  1. State that fixed load steps are not specified in the AGBa1000 operating manual.

  2. Indicate that the station is equipped with a Baudouin 16M33G6N0/5 engine.

  3. Provide reference recommendations from the engine manufacturer with a precise link to the letter.

  4. Clearly state the applicability boundary. Indicate that these figures apply to the engine, and the permissible load steps for the complete power unit are determined by the project and require approval.

Second conclusion: a folder of documents is not yet a base of engineering knowledge. Links between models, components, configurations, and documentation versions are needed. Without them, even correctly found information can be useless.

Case #3. We Asked AI About the Gas Power Plant's Fuel Tank

The third experiment particularly well illustrates the difference between information retrieval and task understanding.

The tester asked to calculate the continuous operating time of the AGBa1000 on a full fuel tank at loads of 50%, 75%, and 100%.

AI found the natural gas consumption for the corresponding modes: 161, 229, and 294 m³/h. Then it explained that the fuel tank volume was missing for the calculation and even provided formulas where it suggested dividing the gas reserve by the hourly consumption.

At first glance, it might seem that the system behaved cautiously: no data – so don't make it up. However, the system missed an error at the very initial stage – in the premise of the request itself.

Our unit operates on natural gas, which, according to the documentation, is supplied from an external pipeline. It fundamentally does not have and cannot have a "fuel tank." The request for the volume of a non-existent reservoir and the formulation of mathematical formulas became a gross defect in the answer. The system unconditionally accepted the user's false premise and began to build calculations on inputs that are not applicable here. Therefore, the engineer's first reaction would be different: what fuel tank are we even talking about?

Only after several clarifications did the user receive a practically useful answer: it is possible to consider connecting the station to the gas pipeline, after first checking the gas supply parameters and equipment requirements.

This leads to a paradox. The system correctly extracted fuel consumption, did not invent missing characteristics, and yet could not immediately help the user solve their problem because it did not point out the error in the request itself.

This case is particularly important for us because corporate AI is created not only for experienced engineers. It should be used by managers, service staff, and other specialists who do not always know the technical nuances and may formulate questions incorrectly.

If the assistant requires a person to understand the equipment design in advance and formulate tasks flawlessly, its practical value decreases.

Third conclusion: an AI assistant must notice erroneous premises. Sometimes the best answer is to explain why calculating using the proposed method would be incorrect.

How to Explain Contradictions in Documentation to AI

Testing RAG has led us to a problem that any enterprise faces – the quality of source data.

When engineers began preparing reference data and verifying the knowledge base, it turned out that different official factory documents could contradict each other.

Two illustrative examples:

  • Continuous mode power: the power plant passport indicates 1150 kW, while a recent engine manufacturer document states 1280 kW.

  • Maintenance schedule: the station's operating manual prescribes changing spark plugs every 1500 operating hours, while the engine manufacturer's service instruction specifies an interval of 5000 hours.

What should AI answer if two official documents in the base state different things?

Choose the more recent file? Take what appears more often? Average it?

None of these options are acceptable. The only correct behavior for the system is not to try to guess the "correct" figure, but to directly highlight the conflict:

“The AGBa1000 operating manual (Section 4, p. 18) specifies an interval of 1500 operating hours. However, the engine service instruction (Rev. 2024, Table 3) sets the regulation at 5000 hours. Engineer confirmation is required.”

We plan to use such search as a tool for initial documentation audit: the model can quickly highlight discrepancies in numbers across different files. However, resolving these inconsistencies still requires manual effort because the system does not and cannot know which of the conflicting specifications has been approved for a specific order.

What Has Been Fixed, and What Is Still in Progress

The results showed that a single universal accuracy assessment is not enough.

On Tables and Parsing (Case with 161 Supports)

  • What happened: The model produced a non-existent number due to column merging in a scanned PDF document.

  • Reason: The parser read the scan as continuous text, losing cell boundaries and the association of rows with headers.

  • What has been done: We switched to line-by-line indexing of structured tables. Each row is now saved in the index along with the table header as a separate semantic fact. In the main test, this increased the proportion of correct numbers in answers from 70.8% to 78.3%.

  • What is in progress: Line-by-line parsing solved the problem for "clean" files (Excel, well-formatted PDFs), but complex graphical scans with drawings and handwritten notes still cause failures. We are currently testing a separate layout analysis module that validates the grid geometry before sending it to OCR. A re-run of scans with manufacturer letters is planned for the next test cycle.

On Equipment Hierarchy (Case with Load Steps)

  • What happened: The system found requirements for the engine but did not link them to the complete power plant.

  • Reason: The knowledge base was a "flat" folder of files without metadata about the product composition.

  • What has been done: Added a graph of equipment connections to the index: the specific configuration of the station is linked to the makes of the installed engine, generator, and controller. Search can now pull up component documentation when querying about the station.

  • What is in progress: Configuring the fixation of applicability boundaries. The model should add a disclaimer: “Data is provided for the engine. The permissibility of load surges for the complete gas piston unit requires confirmation.” This mechanism is currently being tested on a control sample of questions.

On Semantic Context (Case with Gas Tank)

  • What happened: AI attempted to calculate the volume of a non-existent fuel tank for a station powered by a main gas pipeline.

  • Reason: Lack of verification of user's input premises. The model blindly searched for keywords "tank" and "consumption."

  • What has been done: Documented the problem and described scenarios of incorrect questions.

  • What is in progress: Developing a query validator. Before launching the RAG search, a module compares the key entities of the query with the station's design profile. If the question mentions a "fuel tank," but the product passport states "fuel – natural gas, supplied from the gas pipeline," the system clarifies this instead of trying to plug numbers into meaningless formulas.

So, Can RAG Be Trusted with an Engineer's Work?

Not yet, and it's fundamentally wrong to set the task that way.

Our goal in this pilot is to provide employees with a tool for quick and transparent navigation of factory documentation. For the tool to be used safely, it must meet three criteria:

  1. Applicability of Information: the answer must consider the actual equipment configuration instead of abstract numbers from the internet or passports of similar units.

  2. Source Traceability: any number in the answer must be accompanied by a direct link to the document, page, and section of the technical description, so an engineer can verify the fact in 10 seconds.

  3. Understanding Boundaries: if there is a gap in the documentation, a revision discrepancy, or a physically incorrect question – the assistant must directly state it, rather than trying to generate a plausible guess.

As long as the system does not guarantee the verifiability of every answer back to the original source, it remains an internal experimental service.
