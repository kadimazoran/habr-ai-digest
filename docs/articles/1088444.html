Users need an interface. Applications need an API. The model needs to be fed context and corporate data. Access to the service must be restricted, actions controlled, queries logged, and errors handled.
For the model to do something useful for the business, it will need to be provided with context, connected to external or internal systems, and have its operating rules defined.

All these components around the model are often called a harness.

In this article, we'll explore why it's needed, what parts it can consist of, and why choosing the LLM itself is just one step in creating an AI service.

According to research, out of 33 corporate AI pilots, only four on average reach production — 88% remain experiments, and the model is rarely the bottleneck. Some studies compare it this way: the model is the engine, the harness is the whole car.

An engine by itself has no brakes, steering wheel, or speed limiter. Without a harness that decides who to trust, what to allow, and when to hand over decisions to a human, an agent can get stuck in a loop on a failed request, forget access restrictions, and allow unauthorized interference with its logic.

The Difference Between an LLM and an AI Service

The model receives a sequence of tokens as input and sequentially generates new tokens in response. It doesn't know who sent the request, whether the user has the right to see the requested data, where to save the result, or if the proposed action can be performed at all.

Even the conversation history is not an inherent "memory" for the model. The application must save the relevant messages and send them back to the model in the context with the next request.

Therefore, there's a significant layer between a running LLM and a finished service. And around this loop, you get authentication, data handling, integrations, logging, and monitoring.

This is the point where an experiment with a model begins to turn into a product.

What the Harness Includes

The set of components depends on the task. It will differ for a simple corporate chatbot and an autonomous agent working with a CRM. However, several layers are almost always present.

Context and Corporate Data

A basic LLM only knows what was in its training data and the current context. It doesn't know the company's current regulations, internal documentation, product catalog, or the content of the corporate knowledge base.

One way to connect such data is RAG (Retrieval-Augmented Generation): before querying the model, the system finds relevant documents or their fragments and adds them to the context.

When a user asks, "How do I grant access to a new employee?", the model receives not only the question itself but also a fragment of the current internal instructions. Here, several components are at work: a document storage, a search mechanism, context formation, and the LLM itself.

There are ready-made solutions for such scenarios — for example, Open WebUI has built-in RAG, and RAGFlow specializes specifically in this.

Integrations and Actions

The next level is when the service needs to not only generate text but also perform an action. For example, find a client in the CRM, create a ticket, send an email, get product stock levels, generate a report, or call an internal API.

In such an architecture, the LLM can determine what needs to be done and with what parameters, but it's best to leave the actual execution to program code. This is how, for example, the tool calling mechanism in modern commercial models works. The model generates a structured request to a pre-defined tool, the application executes the function, and returns the result back to the model.

OpenAI, for instance, allows defining tool schemas and receiving call arguments in a structured format. Structured Outputs further allow restricting the response to a specified JSON Schema.

You don't necessarily have to write all the logic yourself to assemble such processes. For example, low-code tools like n8n can connect AI components with CRM, ERP, email, chats, and other systems via workflows. You can also run an LLM locally on a server with a GPU using Ollama, or connect to an external model via API without a GPU.

Limits, Costs, and Fault Tolerance

The harness also has a less visible but equally important task: preventing the service from accidentally draining the budget or crashing due to load. Every request to an LLM costs money and takes time. An agent with access to tools could theoretically call the model in a loop dozens of times until it hits the token limit or gets stuck in a failed action.

In practice, this is handled by several mechanisms. First, the number of steps and tokens per user request is limited, or repetitive questions are cached. You can also distribute tasks among models — simple requests go to a fast and cheap model, complex ones are passed to a more powerful one — and if the primary model is unavailable, the service switches to a backup. Without this layer, your tokens or budgets could be depleted sooner than expected.

Validation: Models Cannot Be Unconditionally Trusted

An LLM generates the most probable text continuation, not a deterministic function execution.

Therefore, where the result affects another system, it's advisable to validate it before performing the action. The simplest example is an agent forming a ticket:

{
  "priority": "high",
  "department": "network",
  "description": "..."
}

The application can check if such priority and department values exist, if mandatory fields are present, and if the user has sufficient rights to create the ticket. For critical actions, separate human confirmation might be required.

This results in an important division of responsibility: LLM proposes an action → software layer validates → system executes. The more authority an AI service gains, the more important this boundary becomes.

It's also worth considering the flip side. You shouldn't only distrust what the model proposes to do, but also what is fed into it. If foreign documents, emails, or the result of an external API call are included in the context, they might contain an instruction like "ignore previous instructions and..." Something designed for the model — this is prompt injection, which was mentioned at the beginning of the article (when discussing input data).

Therefore, text from RAG, tickets, or responses from third-party services should be passed to the model as data, not commands. And it should be explicitly stated in the prompt whose instructions take precedence. System instructions are higher than user instructions, user instructions are higher than what was found in documents or returned by a tool.

Security Also Lies Around the Model

Another reason why a simply launched LLM is insufficient is security. If the service handles corporate data, you need to at least decide:

  • who has access to the application,

  • what data is accessible to a specific user,

  • where requests are sent,

  • where the history is stored,

  • what systems the AI can access,

  • what actions it is allowed to perform,

  • what events need to be saved for error investigation.

This layer becomes particularly important for AI agents. If a service can only answer questions, an incorrect answer is unpleasant. If the same service has access to the CRM, file system, or infrastructure, the cost of an error is different.

Therefore, it's best to build AI service permissions on the same principle as regular application permissions: grant only the access necessary for a specific scenario.

The infrastructure itself can also be isolated. The server can be placed in a private subnet without direct internet access or connected to a private network via a router. SSH keys can be used to access the server.

  • GPT is a family of models;

  • ChatGPT is the application through which a user interacts with these models.

Around the model itself in a product, you get an interface, dialogue and context management, file handling, tools and integrations, access control, and many other components.

The situation is similar with Claude: the language model is the core, but the finished product adds functionality for working with tools, files, and external systems.

When developing your own AI service, roughly the same thing happens, only the set of components is determined by the specific business task.

When choosing an LLM, we are choosing the core of the future service, not the entire service.

Conclusion

Downloading a model and running it on a GPU is indeed not difficult today. But an LLM by itself remains a computational component. For it to become a service that employees or clients can use, other layers almost always appear around it: interface, data, access management, integrations, checks, logs, and infrastructure.

The complexity depends on the task. For an internal chatbot, a model and Open WebUI are sometimes sufficient. For a RAG service, a document handling pipeline will be needed. For an agent, tools, workflows, permissions, and control over executed actions are required.

The model determines what the system can generate. The harness determines whether it can be used safely and conveniently in a real process.
