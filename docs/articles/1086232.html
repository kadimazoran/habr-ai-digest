Every morning, I receive a GitHub trends digest about AI agents. Skills, wrappers, MCP servers, yet another "replacement" for something. In a month, 138 unique repositories accumulated, and I set some aside with a note "to try". Then I decided to check what exactly I was setting aside. It turned out that you can almost never understand from the description.

First, I sorted the first 40 by the lines from the digest. Then I counted the code in them. 25 out of 40 turned out to be platforms, although they looked like small things worth looking at in the feed. The most illustrative case: a repository presented as a skill for drawing diagrams. The instruction for the model there takes 137 lines. Below it lie 35,245 lines of its own renderer and 37,047 lines of tests.

Next is the method I eventually applied to all 138, what I found, and which of my own ideas the measurement disproved.

What and How I Measured

The feed covers 34 days, from August 15 to September 17, 2026. Of the 138 repositories, I downloaded and weighed 123. Another 10 weighed more than 250 MB each, so I didn't download them: the size itself is an answer here. Five were already deleted from GitHub by the time I got to them.

I didn't run any of this. An archive of the default branch is fetched with a single request to the GitHub API, without git clone and without installing dependencies. Then a Python script counts the lines. There's nothing else in the method, and that's intentional: code you haven't read yet shouldn't have a chance to execute.

I count four things separately. Code: everything executable. Prose: Markdown, text instructions, prompts. Tests: by file paths and names. And generated code that a human didn't write: zz_generated, *.pb.go, _pb2.py, *.gen.ts, and similar files.

The class of a repository is determined by the ratio of these numbers. If there is at least twice as much prose as code, and the code is less than 2000 lines, the product of this repository is text. Instructions for the model, and the code nearby serves as glue. I call this a prompt-class. The rest is divided by the amount of code:

The thresholds are intentionally rough. They need to distinguish three solutions: "I'll rewrite it myself," "I'll integrate it as is," and "I won't touch it." Line-by-line accuracy is not needed for this.

Generated Code Almost Ruined the Measurement

halfway through, one repository showed 2.12 million lines of code. I went to see where so many came from. A generator produced 521,227 lines, and a single file occupied 136,419 lines. No one writes or maintains this by hand; it's the output of a tool. After this, generated code began to be counted separately from handwritten code.

What's more curious is that the correction didn't move any repository from one class to another. The numbers became more honest, but the verdicts remained the same. This shows that the correction fixed accuracy and didn't adjust anything to fit a desired outcome.

Two more things that trip up any such count. Tests should be kept in their own column. stablyai/orca has 2,036,238 lines of code and 2,463,575 lines of tests, and if you add them, the repository on paper becomes twice as large as its product. I count Jupyter notebooks as files, not lines: .ipynb stores code, text, and output in base64 within a single JSON, and the line count in it means nothing.

There was also a completely mundane error. The while read loop over the list of repositories silently skipped the last line because there was no newline at the end of the file. 39 out of 40 passed, and the script reported success. Now I compare the number of results with the number of inputs before looking at the results themselves.

If you add the ten un-downloaded giants to the platforms, including NationalSecurityAgency/ghidra and sgl-project/sglang, you get 77 out of 138. That's 56%. More than half of what flashed in the trends over a month as an "interesting thing for an agent" actually turns out to be a codebase that is forked only with the intention of maintaining it.

A caveat: if you use such a repository as a ready-made package and don't plan to change it, the platform class doesn't concern you; the author maintains it. The weight becomes your problem the moment you want to "tweak it a bit." For skills and agent wrappers, this is almost always the case, which is why I measured.

Easy ones, i.e., prompt-class and small, totaled only 24. Half of them aren't even tools: lists of links, someone's notes, and one joke consisting of a single line of code. Portable skills that you can actually take and rewrite for yourself, I counted fewer than ten in the month's trends.

Who Owns the Engine Under the Prompt

The difference between "installing" and "taking an idea" is clearly visible in a couple of repositories that look identical from the outside.

latent-spaces/brag creates promotional videos about your project. Its main instruction takes 173 lines. There is zero product code of its own. The 525 lines that the counter recorded as code are an optional music annotation script, a linter for its own documentation, and the project's website. Each render goes through npx hyperframes, meaning it uses someone else's engine.

tt-a1i/archify draws architecture diagrams. This is the same skill from the beginning of the article: instruction of 137 lines, almost the same size. Below it are 35,245 lines of its own renderer, 37,047 lines of tests, and five JSON schemas.

The instructions are almost identical in size, but the architectures are opposite. The first repository asks the model to assemble the result entirely. The second asks the model for typed data according to a schema and builds the image with proven code. If the correctness of the result is important, the second approach is more reliable: the model is good at filling structures and bad at hitting precise formats. The question "who owns the engine under the prompt" separates these two repositories better than any description. If the engine is someone else's, you're installing that too.

What to do with a prompt-class if you like the idea? Rewrite it for yourself; it's an evening's work. That's how I turned blader/humanizer into the slopcheck linter. Humanizer is a prompt that asks the model to rewrite text without AI traces. I needed something different: a check without a model and without a network, which only reads text and returns an error code. Such a check can be put in CI.

The first version of my linter found 17 serious violations in the README of humanizer itself. I almost published this irony, but first, I checked the findings with my own eyes. All 17 turned out to be quotes. The README shows "before and after" examples, and the bad examples are there intentionally. Any document discussing AI text markers will trigger falsely. When quotes, tables, and code were excluded from the check, the same README yielded zero findings, and zero is the correct answer. The moral is general for any measurement tool: first, run it on a case where you know the answer in advance.

Without a license file, rights default to the author. The code can be read, but not copied. This category included, for example, ripienaar/free-for-dev with 137,746 stars, a well-known collection of free services for developers.

Then I opened a graph that is usually skipped. For 19 repositories, GitHub couldn't determine the license: the API returned NOASSERTION or an empty field. I read all 19 files. Eleven turned out to be standard MIT or Apache with modified headers. Three turned out to be AGPL. The remaining five open the source code but restrict usage: Fair Source, Elastic License 2.0, PolyForm, a custom text requiring written permission, and one more case, described below. In total, out of 19 "unidentified" ones, 8 cannot be used.

This last file is worth remembering separately. The first line in it says MIT. Below, a prohibition on commercial use is added. Such a file is no longer MIT, but a license scanner that reads the first line or trusts the API will mark the repository as free. This is bilawalsidhu/gods-eye-view: 218,774 lines of code and almost 38,000 stars.

And one more case for the collection. elder-plinius/CL4R1T4S collects leaked system prompts of other products and is published under AGPL. The author imposes copyleft on texts that he did not write.

The conclusion is simple: the license must be read in the file itself, to the end, not in the badge on the repository page. I subsequently added a license check by file text to my parsing tool, with tests for these specific cases. This is not legal advice: the table only shows which file is worth reading yourself.

Three Signs of Inflation That Didn't Work

During the analysis, I marked ten repositories by eye as suspicious without opening them. The picture consisted of three parts: a fresh account, the name of a well-known product in the title, and stars growing faster than they can be honestly earned. Within 24 hours, five out of ten disappeared from GitHub. Judging by the names, these were a miner, "free" builds of Acrobat and Total Commander, some kind of "optimizer," and a panel whose purpose I never got to see.

The deletions seemed to confirm my intuition, and the next step was obvious: turn the picture into an automatic check. I checked each sign on 28 normal repositories that I had already analyzed manually, against five marked ones that were still alive.

Star velocity doesn't differentiate. 24 out of 28 normal ones grow faster than the slowest of the marked ones. The fastest in the entire set was browser-use/jev-ultrafast, about 3,244 stars per day, and this is a real project from a well-known team.

Account age differentiates in reverse. Marked ones have older accounts: a median of 2,340 days versus 658 for normal ones. Several legitimate projects live in organizations created later than the repository itself.

Borrowed product name guesses correctly in half the cases. The sign triggers for 12 out of 138 and is correct in about six. Among the accused are openai/codex and deepseek-ai/deepseek-harness, meaning the owners of these products themselves.

The sample size is small, five versus twenty-eight, and the median for five values is noisy. However, it's enough for a conclusion. The check I was going to release should have differentiated at least on this data, where the answer is known in advance. It did not differentiate.

Later, I found an explanation for why age is misleading. vastsa/PI-Desktop was created in 2023, but the product in it is from 2026. Age is also borrowed: an old repository is repurposed for a new product, and the creation date starts working to build trust.

Then I reread the code of the five marked repositories that remained alive. I had to remove the mark from four of them. For example, the repository with someone else's brand in its name turned out to be an aggregator of free tiers for fifty-three providers, and the README explicitly states that it is not affiliated with the brand owner. All four marks were based on borrowed names, i.e., on a sign that I had already disproved myself by then. My intuition worked exactly like the check I was trying to derive from it: in about half the cases.

The result is more modest than desired. There is no check for inflation, and I didn't release it. The only reliable signal is deletion. It comes within 24 hours and takes the evidence with it: none of the five deleted ones have even a star count in my data, because by the time the script arrived, the pages were already returning 404.

And one more invisible thing. In a month, six repositories from the feed changed owners or names: santifer/career-ops became career-ops-hq/career-ops, basecamp/omarchy moved to omacom/omarchy. GitHub silently redirects old links. The link from the digest works, and the owner change is not visible. I later found the same pitfall myself: one of my private repositories was renamed, and the local remote kept pointing to the old name all this time.

The Verification Order I Adopted

Before installing anything from the trends, I now go through five steps. The first three take a minute.

  1. Read the license file to the end. I don't use code without a file; with copyleft, I only take ideas.

  2. Count code, prose, and tests separately, subtracting generated code. The class immediately suggests a solution: rewrite, integrate, or don't touch.

  3. For prompt-class, find out whose engine is under the prompt.

  4. Verify the owner and name via API against what's written in the link.

  5. Consider stars as proof that promotion has reached people. They say nothing about quality.

Measurement Boundaries

Lines of code are not a measure of quality. The measurement answers one question: what am I taking on for maintenance if I install it. This is one feed over one month, 138 lines, and the class thresholds were chosen by me. They can be moved; the numbers in the table will not change because of this. Default branches live their own lives, so each line describes a repository as of September 18-19, 2026. I did not download the ten largest repositories and recorded their size, without a fictional measurement.
