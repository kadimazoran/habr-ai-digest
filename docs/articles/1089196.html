The application runs locally via Docker, with the interface accessible in a browser. It connects to servers via SSH. The code is open-source under MIT, with no subscriptions. An API key is required for the agent; manual tools work without it.

Why I Made This

I needed to migrate several of my web projects to a new server. To ensure I didn't miss anything, I launched an AI agent on the old server and asked it to study the configuration and compile a document for the migration. Where the projects were located, how services were started, which config files needed to be backed up.

Then I thought: if the agent can study all this, why not entrust it with the setup as well? At the same time, I wanted to see what it was planning to do and have the ability to verify the results myself.

Thus, ssh-commander was born. On the left, you select the server; at the top, you switch between the terminal, files, and other sections. On the right is the chat with the agent. You can open a log, send a relevant snippet to the chat, and continue troubleshooting within the same window.

You can also run the agent directly on the server; that's how I started. I found it more convenient to consolidate connections and manual tools in one panel.

What the Application Offers

  • Terminal. Multiple tabs per server, command history, session recovery after page reload. You can send highlighted text or the last output to the agent with a single click.

  • Files via SFTP. Upload and download, editor with syntax highlighting, search, viewing growing logs. There's a disk space analyzer: you can navigate from a large directory down to specific files.

  • Docker. Containers, images, logs, start/stop, Compose, terminal within a container.

There are also sections for PostgreSQL and MySQL, Nginx, systemd, ports, and cron. A full list of features is available in the README.

The agent has memory for each server: a local file named MEMORY.md, which is loaded at the beginning of the next session. You can record where projects are located and how they are launched there. Writing requires confirmation. You can connect multiple servers to a single chat; each command shows which machine it is executing on.

An Example of Use: PDF, Free Space, and a Broken Backup

When the application was already running, one of the servers ran out of space. The agent found duplicate large PDFs and suggested freeing up almost 1.5 GB. It also suggested switching PDF handling to Yandex S3.

We removed the duplicates, then configured S3 integration and moved the documents there. When it was time to delete the PDFs from the disk that had already been transferred, it turned out there was no up-to-date backup of all media files in S3, even though backups were configured earlier.

The agent quickly figured out the cause. The synchronization broke when we deleted the duplicate PDFs: the backup process tried to delete the corresponding files in S3, but the service account lacked deletion permissions. The operation failed, and the backup stopped updating.

This means that before cleaning up the remaining local files, a problem with the backup was discovered. The agent linked it to our previous action and identified the missing permissions.

What the Agent Does Automatically and What Requires Confirmation

The agent can automatically read a regular file, view logs, list containers, or check free space. Writing to a file, restarting a container, or executing arbitrary shell commands requires confirmation. A banner appears at the bottom of the chat: you can expand the command fully, then confirm or reject it.

For read-only commands, there's a separate tool, exec_readonly, with an allowlist. Initially, I used a blocklist, but during testing, I found bypasses: for example, /bin/rm and m didn't match the checked name. Therefore, now only a limited set of commands passes automatically. Their flags are checked separately, and pipelines, redirections, and substitutions are prohibited.

Command

Will pass without confirmation

df -h

Yes

find /opt -name '*.conf'

Yes

find /tmp -delete

No: file deletion

sort -o /tmp/list.txt /etc/hosts

No: writing to file

Interpreters and network clients are not on this list. For complex commands, the agent can suggest using regular exec, requiring confirmation. Sometimes, even a harmless request has to be confirmed this way. For my tool, I consider this a reasonable compromise. Here is the filter and its tests.

For larger tasks, there's a planning mode. The model creates a plan based on already gathered information, without invoking tools. If fresh information is needed, it must be obtained before entering this mode. Approving the plan initiates the work but does not override the confirmation of individual changes.

Limitations

The agent might suggest an incorrect command. You must read it before confirming, and verify the result after execution. Backups are still necessary.

When working with an external AI provider, read files and logs are sent to it. Reading paths that resemble secret files, such as .env or private keys, requires confirmation. Recognized secrets are hidden in tool outputs. These are pattern-based checks; they might miss something and do not anonymize logs.

Prompt injection also remains a problem: a file or log might contain text with extraneous instructions for the model. Command checks and confirmations are still in place, but they cannot guarantee the correctness of the agent's suggestions.

The panel is designed for a single user, is accessible only on 127.0.0.1 by default, and is password-protected. SSH passwords, database passwords, and the API key are stored locally in plain text; the panel password is stored as a hash. The data/ and keys/ directories, along with backups, should be protected from unauthorized access.

How to Try It

You'll need Docker with Compose v2 on your computer and SSH access to a Linux server. On Linux or macOS, the ready-made image version 0.1.1 can be launched like this:

mkdir ssh-commander 
cd ssh-commander 
curl --fail --location https://raw.githubusercontent.com/lexuss1979/ssh-commander/v0.1.1/docker-compose.release.yml --output compose.yaml 
docker compose up -d

Open http://localhost:8080, set a panel password, and add a server. In the address field, enter the VPS IP or hostname. localhost here will be the address of the container itself.

For the agent, add an API key in the settings. There are provider presets and configuration for your own OpenAI-compatible API with tool-calling support. Costs are based on the provider's rates; the application includes token tracking and cost estimation per conversation. The screenshots use deepseek-v4-flash. I also use this model myself – it's very fast and inexpensive.

Installation, including on Windows, and first connection are described separately. If you want to look at the code: TypeScript, Node.js, and ssh2 on the backend; React and xterm.js on the frontend. There is a description of the architecture.
