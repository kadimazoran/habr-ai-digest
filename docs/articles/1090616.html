Neural networks write grammatically, which is precisely why their text is recognizable from the first line: em dashes, "it's not X, but Y" constructions, "it's important to understand," "let's break it down." I encountered this with a Telegram bot that converts voice messages into social media scripts and fixed the problem in three layers in one day. In this article, I'll break down how the bot's pipeline works, why prompt instructions weren't enough, why a second neural network pass also didn't save the day, and what ultimately solved the task. All code below is from a working repository; I've slightly simplified variable names.

What the Bot Does

The bot has one user: an author who runs a blog and doesn't want to sit at the keyboard. They dictate an idea, choose a format (story script, carousel, or post), and the bot sends back a ready-made text in their style. At the end of the text is a block with instructions for editors and SMM specialists: format, topic, what to do, deadline. When the author clicks "Accept," the bot asks for the deadline and sends a "TASK READY" card in a separate message, which can be immediately forwarded to the work chat.

The stack turned out to be as follows:

  • Python 3.11, aiogram 3 (aiogram>=3.17,<4);

  • Speech recognition: Whisper whisper-large-v3-turbo via Groq API;

  • Generation: Claude Sonnet 4.6 via official SDK anthropic, intent routing in free chat on Claude Haiku 4.5;

  • Storage: SQLite in a file on a Docker volume;

  • Deployment: one container on a VPS, deployed via Coolify on push to main.

Pipeline: From Voice to Text

Receiving Audio

The bot accepts voice messages, audio files, videos, and "circles" (short videos). It downloads the file entirely into memory and sends it to Groq; there are no intermediate files on disk:

file = await bot.get_file(file_id) audio_bytes = (await bot.download_file(file.file_path)).read() text = await transcribe_voice(audio_bytes, config.GROQ_API_KEY, filename)

The recognition module is about fifteen lines long:

async def transcribe_voice(audio_bytes: bytes, api_key: str, filename: str = "voice.ogg") -> str: result = await _get_groq(api_key).audio.transcriptions.create( file=(filename, audio_bytes), model="whisper-large-v3-turbo", language="ru", ) return result.text

The bot substitutes the filename based on the message type: voice messages are sent as voice.ogg, videos and circles as video.mp4, and for audio files, the original name from message.audio.file_name is used. The API understands the format of the bytes based on the extension.

There is no size check in the code, and this is a conscious laziness: Bot API does not give bots files larger than 20 MB, and the author does not dictate voice messages for half an hour. If they start, the bot will crash on get_file, and this branch will need to be added.

To the transcription, the bot adds a source label ([Voice], [Video], [Text]), and if the user sent a link, it first downloads the article using httpx and extracts the text with BeautifulSoup. All of this is placed into the FSM data as input_text.

States

The dialogue is maintained by aiogram's finite state machine. For each format, there are three states: input, selection of the number of frames or slides, and an editing loop:

choosing_format → storytelling_input → storytelling_count → storytelling_edit ─┐ → carousel_input → carousel_count → carousel_edit ─┤ → post_input → post_edit ─┤ ┌───────────────────────────────────────────────────────────────────────────↓ «Принять» → assignment_deadline → карточка → choosing_format

In the *_edit state, the author can send an edit by text or voice ("remove the third slide, add an example about work"), and the bot runs the current version through apply_edit with a low temperature. My FSM storage is MemoryStorage, so an unfinished dialogue is lost when the container restarts. This is tolerable for one user, but I'm already thinking about Redis.

Prompt Assembly

Prompts are stored in a single file prompts.py, weighing 64 KB. Each format is assembled as an f-string from three parts: general author context (who they are, tone, vocabulary, prohibitions, about 3 KB), format description, and rules against AI markers at the very end:

def get_carousel_prompt(slides: int) -> str: return f"""{AUTHOR_CONTEXT} ## ЗАДАЧА Сделай карусель из {slides} слайдов по теме из сообщения пользователя. ... {ANTISLOP_RULES}"""

The rules are intentionally placed at the end: on my texts, the model followed the last instructions noticeably better than instructions in the middle of a long prompt.

The block for assistant instructions is generated by the model itself, following a template from the prompt:

📋 ЗАДАЧА ДЛЯ АССИСТЕНТОВ: Формат: Сторителлинг ({frames} сторис) Тема: [одна строка] Что сделать: снять все кадры по инструкциям выше, смонтировать сторис, опубликовать пост Дедлайн: ___

The final "TASK READY" card is assembled by the code, not the neural network: the bot takes the topic from the state, the deadline from the user's response, and the checklist from the format dictionary. The neural network is not needed here, and its absence eliminates a whole class of errors.

Calling Claude

message = await _get_claude().messages.create( model="claude-sonnet-4-6", max_tokens=max_tokens, extra_body={"temperature": temperature}, system=[{"type": "text", "text": system, "cache_control": {"type": "ephemeral"}}], messages=[{"role": "user", "content": user_content}], )

The system prompt is passed as a list of blocks with cache_control because the author's context plus the format weighs several thousand tokens and is repeated in every request. The cache lasts five minutes, and the author usually generates and makes two or three edits in a row, so repeat requests read the prompt from the cache at a cost ten times lower than usual.

I adjusted the temperature for the task: generation structure 0.7, edits 0.3, cleaning 0.2. Why the temperature is passed via extra_body, I'll explain below; it's a separate story.

The bot splits long responses into messages using the ━━━━━━━━━━━━━━━━━━━━ delimiter, which the model places between parts of the script, and assembles chunks up to 4000 characters (Telegram limit is 4096). If one section is longer than the limit, it's split by lines.

The Main Problem: AI Markers

Early versions wrote cleanly and smoothly, but anyone who spends more than an hour a day on social media recognized the neural network in them. There were three groups of markers:

  1. em dashes where a human would use a period or comma;

  2. antitheses: "it's not X, it's Y," "not X, but Y," "the issue isn't X, but Y," "X, not Y";

  3. clichés and rhythm: "it's important to understand," "it's worth noting," triplets of adjectives, sentences of 30 words.

Layer 1: Rule in the Prompt

First, I wrote a strict checklist with "before/after" examples and put it in the group chat prompt. A couple of days later, it turned out that the carousel, post, and story generators didn't know about it at all: I added the rule in one place, but there are more than a dozen generation paths in the bot. The rule was moved to the constant ANTISLOP_RULES, which is appended to the end of each prompt, and the most important part was moved to the first heading in the author's context:

## MAIN WRITING RULE (must not be violated, check every sentence) No em dashes (—). No antitheses "it's not X, it's Y" / "not X, but Y" / "the issue isn't X, but Y" / "X, not Y". These are the two main AI markers.

It got better, but the model still slipped up regularly, most often on long scripts where the rule was thousands of tokens away from where it was writing the text.

Layer 2: Second Pass - Cleaner

Next idea: the finished text is sent to the same model a second time with a different system prompt. Its role is narrow, "editor-cleaner": remove markers and don't touch anything else. Key prompt lines:

This is the second pass: you clean, you don't rewrite from scratch and you don't shorten. ... Preserve all structure and formatting: headings, "Slide N", "Story N", icons 📌🎙🎬📝📷🎨🎯, separators ━━━, numbering, emojis, the "INSTRUCTIONS FOR ASSISTANTS" block. Length: the output text should be approximately equal to the input. Return ONLY the cleaned text in its entirety.

For antitheses, the prompt has "before/after" pairs and a separate phrase "check BOTH orders," because the model missed "X, not Y" more often than "not X, but Y." Temperature is 0.2, limit is 8000 tokens, so a long script isn't cut off in the middle.

The second pass caught most of the antitheses, but dashes continued to slip through. The reason is simple: a language model works with tokens, and "remove all U+2014 characters" is as soft a request for it as "write shorter." Sometimes it replaced a dash with a comma, and sometimes it inserted a new one itself in the rewritten sentence.

Layer 3: Deterministic Filter

Here I realized that a task with a verifiable result must be solved with code. Dashes are removed by regex, and this function is applied to every bot output:

_AI_DASHES = "—–―−‒"  # em, en, horizontal bar, minus, figure dash _AI_DASH_RE = re.compile(f"[{_AI_DASHES}]") def strip_ai_markers(text: str) -> str: if not text: return text text = text.replace(" -- ", " - ") return _AI_DASH_RE.sub("-", text)

Five characters were included in the set because the model uses not only the em dash: medium dashes, the minus sign U+2212, and even the horizontal bar U+2015 were encountered. Everything is replaced with a regular hyphen, so a range like "1–3" becomes "1-3" and doesn't break. I deliberately excluded ━ from the set; section separators and long message splitting rely on this character.

It's not possible to do this with regex for antitheses: "not X, but Y" cannot be mechanically transformed into something meaningful; the sentence needs to be rewritten. Therefore, the code only searches for antitheses:

_ANTITHESIS_RES = ( re.compile(r"это\s+не\s+[^,.!?\n]{1,40},\s*это\s+", re.IGNORECASE), # это не X, это Y re.compile(r"(?:^|[\s(])не\s+[^,.!?\n]{1,40},\s*а\s+", re.IGNORECASE), # не X, а Y re.compile(r"дело\s+не\s+в\s+[^,.!?\n]{1,40},\s*а\s+в\s+", re.IGNORECASE), # дело не в X, а в Y re.compile(r",\s*а\s+не\s+", re.IGNORECASE), # X, а не Y ) def _has_antithesis(text: str) -> bool: return any(r.search(text) for r in _ANTITHESIS_RES)

The [^,.!? ]{1,40} constraint keeps the match within a single sentence and prevents the regex from concatenating "not" from the beginning of a paragraph with "but" three lines down. False positives still occur, for example, with "it's not his job, it's the editor's job," which is precisely why the detector doesn't delete anything itself. It only triggers one targeted attempt to rewrite the text; a blindly deleted phrase would break the meaning.

The final function looks like this:

async def antislop_pass(text: str) -> str: text = strip_ai_markers(text) # deterministic, always, before everything else if not config.ANTISLOP_SECOND_PASS: return text try: cleaned = strip_ai_markers((await _generate_claude( text, get_antislop_pass_prompt(), max_tokens=8000, temperature=0.2)).strip()) or text if _has_antithesis(cleaned): # one targeted retry retry = strip_ai_markers((await _generate_claude(cleaned, get_antislop_pass_prompt() + "\n\nВ тексте ОСТАЛИСЬ антитезы «не X, а Y» / " "«это не X, это Y». Перепиши их напрямую, без противопоставления.", max_tokens=8000, temperature=0.2)).strip()) if retry: cleaned = retry if _has_antithesis(cleaned): logging.warning("antislop: antithesis still present after one retry") return cleaned except Exception: return text # dashes are already cleaned

The order here is important. The filter is applied first, so that in case of any API failure, the user receives text without dashes. After each model response, the filter is applied again because the model might return dashes in a rewritten piece. There is exactly one retry: if an antithesis survives two passes, it's almost always a false positive, and a third call would only waste tokens. Such a case is logged and handled manually.

The second pass can be disabled with the ANTISLOP_SECOND_PASS flag: then only the filter remains, and the user doesn't wait for an extra model call.

Paths That Bypassed the Filter

When the filter was ready, I went through the code and found six places that returned the model's text directly to the user, bypassing antislop_pass: advisor responses, text reviews, group chat replies, daily jokes for the team, topics and descriptions for YouTube. The second pass itself wasn't needed for them, but dashes slipped through there just the same. Now, every output from the model goes through at least strip_ai_markers, and in the group chat, where a quick response is needed, that's where it ends.

I implemented all three layers in one day, June 7th, in three consecutive commits. If I had started with the third layer immediately, I would have saved half a day: a requirement that can be checked by code should be checked by code, and prompts should be left for what cannot be checked by code, i.e., for voice, tone, and structure.

What the Filter Can't Do

Preserving formatting in the second pass relies solely on the prompt instruction; there's no programmatic check. If the model loses the instruction block one day, I'll find out from the user. It would be better to compare the number of markers 📌, ━━━, and lines "Slide N" before and after cleaning, and if there's a discrepancy, return the text from the first pass. In a neighboring module that cleans entire documents, such a check already exists: if less than 60% of words remain after cleaning, the piece is sent for a retry, and after the second failure, the original remains.

The code also doesn't check sentence length or clichés. Clichés could be caught by a dictionary, but their variations are endless, so I left that to the model.

Second Breakdown: Bot Died After Rebuild

In September, the bot stopped responding to all buttons at once, even though I hadn't touched the code: Coolify simply rebuilt the image. requirements.txt had anthropic>=0.40.0; during the build, SDK version 1.x arrived, and every call to messages.create(..., temperature=0.7) started failing on the method signature.

The API parameter itself still accepts it, so the fix took one commit: the temperature was moved to extra_body, which the SDK passes to the request body as is, and the SDK version is now limited to the range anthropic>=1,<2. Other dependencies (groq, httpx, beautifulsoup4) are still specified only with a lower bound, and the next such breakdown will come from them. The correct solution here is a lock file with exact versions, and it's the first item on my to-do list.

Storage and Deployment

Generation history is stored in SQLite. A separate database server is not needed for a single user, and the file on the Docker volume survives image rebuilds:

CREATE TABLE IF NOT EXISTS generations ( id INTEGER PRIMARY KEY AUTOINCREMENT, user_id INTEGER, username TEXT, format TEXT, topic TEXT, content TEXT, created_at TEXT DEFAULT (datetime('now','localtime')) );

I work with the standard sqlite3, not aiosqlite: each call opens a connection and goes into asyncio.to_thread to avoid blocking the event loop. New columns are added by migration via ALTER TABLE in a try/except block. It's primitive, but it works with a single database file and a single process.

Access to the bot is restricted by middleware with a whitelist of user and chat IDs; everything else is silently ignored and logged:

class AuthMiddleware(BaseMiddleware): async def __call__(self, handler, event, data): uid = getattr(data.get("event_from_user"), "id", None) cid = getattr(data.get("event_chat"), "id", None) if uid in self.allowed_users or cid in self.allowed_chats: return await handler(event, data) logging.info("Blocked update from user_id=%s chat_id=%s", uid, cid) return None

It's connected as dp.update.outer_middleware, so it triggers before any handler and before FSM.

The Dockerfile is short, but it has one non-obvious line:

FROM python:3.11-slim RUN apt-get update && apt-get install -y ffmpeg && rm -rf /var/lib/apt/lists/* WORKDIR /app COPY bot/requirements.txt ./requirements.txt RUN pip install --no-cache-dir -r requirements.txt COPY bot/ ./bot/ WORKDIR /app/bot CMD ["sh", "-c", "sleep 35 && python main.py"]

sleep 35 is needed because of how Coolify deploys a new version: a new container starts while the old one is still running. Two processes with the same token simultaneously call getUpdates, Telegram responds with a Conflict error, and one of them crashes. The pause allows the old container time to stop. This problem wouldn't exist with webhooks, but I didn't want to set up an HTTPS endpoint for just one user.

What I Would Do Differently

  1. I would have fixed the versions of all dependencies from day one using a lock file. For a bot with one user, "latest version" offers nothing but sudden crashes.

  2. I would have saved the original transcription in the database alongside the result. Currently, only the final text is written to the table, and when the result is unsuccessful, it's impossible to tell who is to blame: Whisper or Claude.

  3. I would have started with the deterministic filter, and added the prompt and second pass later. A regex for dashes can be written in five minutes and doesn't make mistakes.

  4. I would have written at least a couple of tests for strip_ai_markers and _has_antithesis. There are none now, and I checked the regexes by manually running them on texts where the model slipped up. I already have a set of such texts; now I just need to wrap it in pytest.

Conclusion

The bot has been working since May 2026, with 59 commits in the repository. The three-layer scheme can be applied to any text generator: the prompt sets the voice and structure, the second model pass rewrites what requires semantic understanding, and the code guarantees what can be formally verified. If you're doing something similar, start with the third layer.
