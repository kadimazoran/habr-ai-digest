I have a MacBook Pro 16 2019: six-core Intel Core i7, 16 GB RAM, and Radeon Pro 5300M with 4 GB VRAM. It already had Ollama, gemma3:4b, and gemma2:2b installed.

The idea seemed obvious: why spend cloud Codex on parsing a short traceback, summarizing a log, or a commit message? Let Codex offload such tasks to a local model, get the finished result, and only handle complex tasks.

I created an MCP server, connected it to Codex, ran identical tasks, and checked the exact token consumption. The integration worked. Savings - no.

On one simple task, the route through the local model used about twice as much cloud input as a direct Codex response.

Below is not an instruction on 'how to run a neural network in five minutes,' but an analysis of the experiment: what I built, where I erred in my initial hypothesis, and for what tasks a small local model was still useful.

What exactly I wanted to achieve

Not a second chat alongside Codex, but a local executor within the workflow:

  1. I assign a task to Codex.

  2. Codex understands the task is simple.

  3. It passes it to Gemma via a local tool.

  4. It verifies the response.

  5. It doesn't spend expensive cloud inference on the routine itself.

For delegation, I chose MCP. Codex supports local STDIO MCP servers: a process runs on the computer, reads JSON-RPC from stdin, and returns the result via stdout. Configuration is stored in ~/.codex/config.toml.

The server turned out to be small and without external Python dependencies. It has one tool - local_llm.

{ 
  "prompt": "What does this error mean?", 
  "context": "SMTPAuthenticationError: 535 authentication failed", 
  "mode": "classify", 
  "max_tokens": 160, 
  "temperature": 0 
}

The response includes not only the model's words but also measurements:

{ 
  "answer": "Incorrect username or password for the email server", 
  "model": "gemma3:4b", 
  "wall_time_ms": 6098, 
  "prompt_tokens": 71, 
  "output_tokens": 44, 
  "tokens_per_second": 9.52 
}

I don't log prompts and source code. Only the SHA-256 of the prompt, context length, model, time, and token count are saved. Otherwise, the 'local and private assistant' would imperceptibly turn into another source code repository.

First launch failed

Codex saw the server and tried to call the tool, but codex exec responded:

MCP tool call requires approval, but approval policy is never

The behavior is correct. An non-interactive process cannot show a confirmation dialog, so a new tool cannot be executed silently.

For a specific read-only tool, I explicitly allowed calls:

[mcp_servers.ollama-worker] 
command = "codex-ollama-worker" 
default_tools_approval_mode = "approve" 

[mcp_servers.ollama-worker.tools.local_llm] 
approval_mode = "approve" 
output_token_limit = 1200

After this, the chain worked: Codex selected local_llm, Gemma responded, and Codex read the structured result and returned the summary.

What 2B and 4B are capable of

I created eight small tasks. They are based on errors I encountered in a regular project:

  • hostname mismatch in TLS certificate;

  • SMTP 535;

  • extracting ports from Docker Compose;

  • path traversal when uploading a file;

  • an old entry permanently blocking a new one;

  • protecting a mailing list from duplicate submissions;

  • adding UNIQUE to a table with existing duplicates;

  • commit message.

Both models ran on CPU. Despite having a discrete Radeon with 4 GB VRAM, Ollama showed 100% CPU.

For simple transformations, everything was fine. Both models extracted external and internal ports, identified Redis as a dependency, understood SMTP 535, and wrote an acceptable commit message.

However, with a short security review, things got interesting.

I gave gemma3:4b this snippet:

target = Path('/srv/uploads') / upload.filename 
with target.open('wb') as output: 
    output.write(await upload.read())

The model mentioned directory traversal but primarily suggested replacing binary mode wb with text mode w.

This means the dangerous filename remained dangerous, and uploading binary files was additionally broken.

gemma2:2b performed slightly better: it correctly pointed out the user-provided upload.filename but then advised using Path.joinpath() or os.path.join(). These functions combine paths but do not sanitize ../../etc/passwd.

The models also failed on the logic of entries:

existing = await db.execute( 
    select(Enrollment).where(Enrollment.user_id == user.id) 
) 
if existing.scalars().first(): 
    raise HTTPException(400, 'Already enrolled')

The real problem: the query considers any existing entry. After the first enrollment, the user might permanently lose the ability to enroll further.

The 4B model, instead, suggested translating the Russian error message into English. The 2B model noticed that any enrollment is checked but explained it so confusingly that a ready-made fix could not be obtained from the response.

The conclusion on quality was simple: small models are suitable for mechanical text processing, but not for final security reviews and domain logic.

Why was the MCP route more expensive?

Because the local model does not replace the cloud pass. First, Codex must read the request and decide which tool to call. After the tool executes, Codex again receives the context along with the result and forms the final answer.

For a short task, this results in two cloud passes instead of one. The local model performs useful work in between, but its own work hardly subtracts anything from the Codex context.

Important: the numbers are taken from turn.completed events, not from interface percentages. Percentages are too coarse, and the server development itself was ongoing in parallel.

Can I run the entire Codex locally?

There is an OSS mode in the CLI:

codex exec --oss --local-provider ollama -m gemma3:4b

I tried that too. First, the launch failed because Codex requested thinking, and gemma3:4b does not support it. I disabled reasoning but got the following error:

registry.ollama.ai/library/gemma3:4b does not support tools

Even when the user request says 'do not call tools,' Codex acts as an agent and provides the model with available tool schemas. The installed Gemma 3 4B does not support this mode.

This means that on this machine, I got a working local MCP executor, but not a fully local Codex agent.

What makes sense in the end

My initial scheme was backward.

If cloud Codex has already started a turn, calling a small local model is not guaranteed to save limits. For a minor task, it might cost more due to the second cloud pass.

Savings only appear when a simple task is completed entirely locally – before contacting Codex.

A working division for my hardware looks like this:

Locally:

  • extract facts from logs;

  • compress long command output;

  • convert JSON or a table;

  • write a draft commit message;

  • classify a known error.

In Codex:

  • change code;

  • search for the cause of an incident across multiple layers;

  • work with migrations;

  • perform security checks;

  • make architectural decisions;

  • re-verify a questionable local response.

I kept the MCP server anyway. As a local tool, it works, returns measurable results, and can be useful for private preliminary processing. It would simply be untrue to call it a 'limit saving' after this experiment.

The next step is to create a local-first wrapper: the task first goes to Ollama, and only goes to Codex upon explicit escalation. This is the scheme that can be honestly tested for weekly limit savings.
