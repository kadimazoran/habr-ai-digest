Imagine hiring a confident mid-level developer for your team. But they weren't given access to the tracker, weren't shown the knowledge base, and were only told about architectural decisions once during onboarding. They are occasionally asked to Google something, sometimes assigned a small feature detached from the big picture, and then blamed for poor understanding of the task and company processes.

I see the same mistakes in startups, venture studios, and with non-technical solo founders, and, of course, in the bloody enterprise. Some even call themselves the trendy "AI-native" – although each of their employees works with a single agent in their own way, and knowledge sharing, if it happens, is due to someone's personal initiative in a private conversation.

Developers are bought Claude Code or Codex, and told to play around with it themselves. Management has heard that agents speed up development – the tool is provided, the box is ticked. But the delivery speed hasn't changed for some reason.

It hasn't changed because only one node was "automated" – the system within which it operates remained unchanged. Code is now generated at inference speed, but the sprint is planned as before.

Steinberger, in his article Shipping at Inference-Speed, describes a process where his productivity is limited by inference time and complex engineering decisions. He runs multiple tasks in parallel, maintains documentation for subsystems, has agents execute commands, and check their own results.

He is an excellent example of what an experienced solo developer achieves by reconfiguring their entire personal environment for agents. But the same article has an important caveat: some of his practices won't work in a large team.

For a single developer with a defined task, inference speed truly becomes the main bottleneck. But for a team as a whole, the bottleneck is the processes that generate these tasks.

Back in the pre-agent era, when I wrote about approaches to speed up my work using neural networks, I often heard:

What about high load?

in the context of applying these approaches to large systems – and I didn't understand how the size of the system could prevent assigning certain tasks to a neural network. Then it dawned on me: people imagined only one scenario for using models. Stuff the entire codebase into the context, ask the model to behave like a senior developer, and expect everything to be designed and work magically on its own, then be disappointed.

But neither a model nor a human works that way.

A person who knows a project well keeps routes in mind: they know where things are, where the contract is, whom to ask if the contract is silent. An agent needs exactly the same.

This route looks something like this:

intent or task -> acceptance criteria and risk boundaries -> routing to the correct context -> plan for non-trivial change -> isolated implementation -> mandatory local checks -> independent review and CI -> staging and behavior verification -> controlled delivery -> telemetry, conclusions, and documentation update

It's not required to remove the human from every node. Each segment should have a clear input, output, owner, and transition condition. Where the risk is low – the transition is automatic. Where the cost of error is high – human confirmation is needed. The agent executes the part of the process it's allowed to and transfers the verifiable result to the next gate.

Let's take a hypothetical example. The team is adding idempotency to payment creation. The task states a verifiable promise: two requests with the same key create one operation. The root instruction sends the agent to the API contract, the ADR on payments, and migration rules. The feature plan lists the affected components, the state in case of partial failure, and the rollback method. The agent modifies the code in an isolated environment and runs the happy path along with a repeated request, parallel requests, a failure after writing to the database, and a repeated migration run. A second agent or a human receives the initial promise, the diff, and the test results. CI re-runs the mandatory profile. On staging, the scenario is run on synthetic data. After successful verification, a human approves the result and the delivery of the compiled artifact to production.

The model writes code here, and reliability is ensured by the process around it: predefined criteria, the right context, isolated implementation, independent review, repeated checks, and a human decision on delivery.

Next, let's see what such a route is assembled from.

A single entry point is needed instead of an encyclopedia in one prompt

At the root of the project, a short file is needed that the agent reads before working. For Codex, it's AGENTS.md.

Anthropic's documentation states that Claude does not read Agents.md and needs a dedicated Claude.md, but in my experience, it reads it just fine if there's no alternative file. Moreover, AGENTS.md can be specified as an explicit entry point in the initial instruction or in that root Claude file if needed; there's no point in duplicating and maintaining a separate Claude.md with identical content.

The root file's task is routing. Inside, it's enough to describe the project's purpose and its boundaries, commands for execution and basic checks, the documentation map, rules for selecting a test profile, actions requiring mandatory confirmation, and the definition of a completed result.

It might look something like this:

# Working agreements - Read `docs/contracts/` and `docs/testing/api.md` before changing the API. - Follow `docs/workflows/migrations.md` for migrations. - Start non-trivial tasks with a plan in `docs/plans/active/`. - Update user-facing docs after any behavior change. - A task is done when the check commands and their output are attached. - Prepare report and instructions for an operator.

The rule is selected based on the type of change. A minor CSS tweak is handled by the linter and component tests; a payment contract requires the full testing profile.

This is also useful for humans – a new employee opens the same repository, follows the same routes, and quickly understands how things are done here. Good documentation for an agent almost always turns out to be good documentation for the team. And everyone suffers equally from implicit agreements.

Documentation lives in the repository

Documentation for agents is a shared, versioned, and maintained knowledge repository about product development. If agent documentation in your team is the responsibility of individual developers and each for themselves – there can be no talk of development standardization and quality control.

It's most amusing to see the lack of such standards in development studios that call themselves AI-first – product manufacturing is streamlined, and process and stack standardization is done, at best, based on ChatGPT's advice.

Currently, it's common to criticize non-technical people who have finally gained the ability to realize their ideas without computer science knowledge, for the technical quality of their products. However, such teams and studios contribute no less to mass sloppiness – if not more. Because it's much faster to churn out poorly maintainable projects with multiple hands.

When agent documentation is standardized for teams, internal processes also begin to change: knowledge stops surfacing in random links or internal workshops; code and documentation changes go through a unified review flow, and a new developer receives up-to-date documentation along with project access. The agent sees the status and scope next to the code and behaves consistently on each individual workstation.

The minimal structure of project documentation might look like this:

AGENTS.md docs/ architecture/ # subsystems and data flows contracts/ # APIs, schemas, external commitments decisions/ # ADRs and the reasoning behind them plans/ active/ # in-flight changes completed/ # finished plans with outcomes research/ # verified research notes testing/ # test profiles and selection criteria workflows/ # repeatable processes operations/ # runbooks, diagnostics, rollback

The specific directory names may vary – the purpose of the documents and the clear structure of their interconnections are important.

In my own and client projects, besides general documentation, I distinguish several main types of documents specific to working with an agent.

Master Plan

The master plan defines the project's direction: goal, boundaries, architectural principles, major stages and phases, external dependencies, key risks, and what is consciously not being done.

This document is usually created in a new project that starts from scratch and research. When the necessary data is collected, the boundaries and scope become clear, and the final form is formed – at least at the current stage of project understanding – the master plan consolidates all this and provides a basis for quickly creating subsequent documents.

It's best to search for and study information for the main project direction within a single session and, within the same session, prepare the master plan. If the research you are conducting doesn't fit within the session's context or starts to blur it – save intermediate results in separate documents – later they can be used as context building blocks for brewing the overall picture in the master plan.

Feature Plan

A feature plan describes a specific change: current and desired behavior, affected components, invariants, migration, failure scenarios, and readiness criteria.

Such a plan is usually a description of a process that should lead to a specific result. It's acceptable for this document to be extensive and cover more than one feature. With a large volume, it's divided into phases – each with its own start conditions and its own completion and acceptance criteria; but they all work in one direction: to create new end functionality, perform major refactoring, or stabilize a part of the system.

ADR

Or Architecture Decision Record – stores the reason for a decision, considered options, and consequences. An ADR is needed to explain and document a decision made on the fly, for example, with new data. It may differ from what is written in a specific feature plan, or deviate from the general outline of the master plan – the ADR records why, how, under what conditions it was decided, and why it is important. It is simultaneously a firm fixation of knowledge and one of the tools for process flexibility.

A document must have a lifecycle

The docs/ folder by itself standardizes nothing and, without a process, quickly turns into a dump of MD files.

Every important document should have at least a scope, status, owner, last checked date, and a condition under which the document needs to be reviewed. Four statuses are sufficient: draft, active, superseded, archived.

Updating documentation is part of defining readiness. If a change has altered a public contract, a mandatory command, an architectural invariant, or an operational process – the task is not complete until the corresponding document is updated.

However, documenting everything is unnecessary and harmful. The directory structure, dependency list, and function signatures will be read by the agent from the repository itself. Document what cannot be understood from the code:

  • intent;

  • constraints;

  • reasons for decisions;

  • dangerous exceptions;

  • acceptance criteria;

  • known operating modes and their application conditions.

Conflict of sources is also resolved explicitly: tests show the recorded expected behavior, code shows the actual implementation, ADR explains the architectural intent, the active plan describes a change not yet completed. If they diverge, the agent stops, records the conflict, and escalates it to the owner – the machine should not be able to simply choose the most convenient version of truth.

Mechanical checks are moved to CI: broken links, missing mandatory fields, unknown owners, completed plan without a final status. The semantic relevance of a document is confirmed by the same owner who is responsible for the corresponding system behavior.

Where to store knowledge so that relocation doesn't cost weeks of work

Not in skills. There's a lot of mysticism around agent skills, although essentially they are just a packaging of a repeatable process: instructions, supporting materials, and sometimes scripts. OpenAI describes skills as a format for reusable workflows with progressive context loading.

Skills work well when the task is truly repetitive: fixing a specific class of pipeline failures, preparing a migration according to an accepted template, compiling release notes. But storing all company memory in them is pointless.

Firstly, a specific agent system may change its format, loading rules, or behavior after an update. Secondly, the provider may become unavailable to a specific team, region, or account.

Here the author describes all the pain of migrating from Claude Code skills to Codex after Anthropic started blocking accounts by region more carefully.

The main problem was with skills. Over the past few months, I've become deeply involved with skills for internal systems, some of which duplicated each other.

Redoing the skills took two and a half days. The difficulty was that there are no perfect skills for some internal systems yet. For example, for our version control system, there are three skills with different strengths and weaknesses. And with three different authors.

over time, the entire zoo of skills turns into a mess and needs cleaning up.

The last quote particularly resonates with me because that's exactly how documenting skills feels. It seems more correct to document approaches rather than specific skills.

And a skill instruction that was well executed by one model is not guaranteed to be executed as well by another. Commercial models are updated, old versions are eventually retired – what worked stably with GPT-5.5 in 5.6 starts to fail or is ignored altogether.

Therefore, I distinguish layers of documentation here:

  • project knowledge, invariants, and mandatory policies live next to the code;

  • a repeatable workflow can be formalized as a skill;

  • critical and deterministic actions are implemented by a script or check;

  • an adapter for a specific agent only connects the general source and its tools.

If, when migrating from Claude Code to Codex, you have to manually transfer hundreds of rules – this is not a good reason to clean up the old stuff at the same time, but rather an indication that the knowledge is too tightly coupled to one runtime.

And a separate skill also needs to be tested. The tasks it should work on, the tasks it shouldn't, expected inputs and outputs, forbidden actions. Before changing the model or version of the agent wrapper, these checks are run again. The fact that a new model is "smarter" can backfire.

Where to store knowledge so that relocation doesn't cost weeks of work

When starting a project in an unfamiliar area, it's reasonable to delegate research and design assistance to a powerful model, and well-specified implementation to cheaper and faster ones.

"Smart" ones write documentation, "dumb" ones handle implementation.

The assessment of who to delegate what to should consider:

  • cost of error;

  • volume and heterogeneity of context;

  • reversibility of change;

  • quality of automatic verification;

  • complexity of the architectural solution.

A simple model can excellently implement a routine adapter according to a precise contract. A powerful one will be needed for complex refactoring or quality review.

Encapsulate the environment

When an agent can run commands, install dependencies, and modify files, a reproducible environment must become part of the contract.

Many teams don't standardize this at all. The project runs on the host machine, outside a container with a defined configuration – and breaks already at the build stage because local library versions don't match. Now imagine that a developer, without thinking, asks an agent to fix this without rails, it adapts the project to their local library version, and this "fix" along with the feature goes for review. How happy everyone will be is unnecessary to imagine: time is spent fixing stupidities, and the culprit, naturally, is the stupid agent that doesn't understand development.

Containers are necessary because they provide isolation, portability, and the reproducible result that is so important for process standardization.

  • the environment is set up by a documented command or set of commands;

  • dependency versions are fixed;

  • external services have reproducible test replacements;

  • state is safely created and cleaned;

  • accessible directories and network paths are limited;

  • the same set of checks is performed locally and in CI;

  • a failed launch does not affect the developer's machine.

Somewhere, this requires compose with a database, a queue, and a mounted source code so that changes are picked up without rebuilding. Somewhere, a lightweight devcontainer will suffice. Somewhere, a separate remote sandbox will be needed.

A container, however, is not a magic bullet in itself. Incorrectly set security boundaries – mounted directories, privileged mode, Docker socket, or excessive network access – again expose the agent to the host or internal infrastructure, and this also needs to be monitored.

Tests verify the task's promise

An agent that has written code and reported readiness has not proven that the task has actually been completed. Proof comes from passing checks against a compliance matrix and tests created during the phase planning stage.

In my practice and documentation, I distinguish 3 levels of check strictness:

  1. Strict check with a full test run – before merge or delivery.

  2. Local and integration checks of the feature itself and the immediate area of change, without a full run – to ensure that the implementation works and does not break the directly affected parts of the system.

  3. Full YOLO – the "vibe-code" mode, acceptable in small projects, experiments, and early development stages – when there's too little code to put everything on rails and you can just push feature after feature, discard and rewrite entire layers of the project.

But even a good and reliable run of tests and matrices is not a 100% guarantee that: a) everything is done; b) everything is done correctly. For work to be considered ready for human acceptance, a second opinion is needed.

Cross-checking

The joke goes: if you mention in Claude Code instructions that the result will be checked by Codex, the default quality of self-checks and, consequently, the output will significantly increase. How well this actually works is hard to say. But the principle of a second opinion is one of the most useful practices, especially for resource-intensive tasks.

A working cross-check usually looks like this:

  1. The implementer agent, a simpler and cheaper model, receives the task, context, and the right to modify a limited, defined area.

  2. The checker receives the initial requirements, code, and test results. They do not see the first agent's report.

  3. They essentially perform a review, looking for specific classes of problems: missed requirements, hacks, security flaws, lack of tests, inconsistent documents.

  4. Observations are formed into a fix plan.

  5. The fix plan is passed to the implementer.

Sometimes another iteration of checks and fixes is needed, and the task is completed. But sometimes, even after a repeated fix plan, the weak model cannot cope with the task; in such cases, it's appropriate to hand over the finishing touches and "tidying up" to the same "smart" model that did the review – it has not much left to do, and the consumption of precious tokens will not be as high as for the full implementation of the task by the same smart model. This creates a kind of literal senior-junior relationship.

For risky changes, cross-planning is useful: one "smart" model creates a plan, another tries to break it before implementation begins. The conclusions from this are naturally drawn by a human, and the decision on what the final plan will look like remains with the human.

When you can't let AI into production

Short answer: never (you can't). Direct access with the right to change a running system is excluded.

All necessary principles were invented before AI: least privilege, separation of duties, auditing, reproducible artifacts, and rollback are still relevant.

Practical boundaries are as follows:

  • the agent does not receive universal production keys;

  • the agent does not connect to the production host via SSH;

  • the agent does not bypass CI/CD and does not deliver a locally built artifact;

  • the agent does not change infrastructure, secrets, or permissions on its own decision, even on dev or staging.

It is permissible for the agent to see production data. It can assist with diagnostics through existing monitoring infrastructure. Building magical monitoring on an agent that freely roams production and decides what's happening there is a bad idea.

An agent can prepare a change, open a pull request, create a migration plan, or even initiate a pipeline, if initiating does not grant the right to bypass production gates. The decision to apply a high-risk change remains with a human in a separate controlled loop.

You can let an agent play around in other environments. Staging accepts an already verified release candidate, and it's almost live there. However, staging should not be a dumping ground for any agent's result: dev is for that.

How to tell if automation is really working

The number of generated lines, tokens spent, subtasks closed by the agent, and pull requests opened – are not indicators of value in themselves. A fast generator increases the review queue along with the amount of garbage in it.

As an example, in Ghostty, the review queue at some point became so bloated that Mitchell Hashimoto at the beginning of the year rewrote the change acceptance rules. According to him, previously even a bad pull request required time and effort from the author, and agents removed this natural limiter. As a result, bad issues and PRs increased by about tenfold. Now, random AI-generated pull requests are closed immediately, and those who continue to flood the project with junk are blocked permanently.

If you automate a separate development node, giving developers access to code generation systems in a fragmented way, it will only speed up tasks through that node – and increase its idle time. How quickly tasks are generated, how they move the project and work forward – that's what needs to be covered by metrics. How much time passes from a ready task to production, how long it waits at individual gates, how often it's returned for rework, and how many changes after delivery require fixes or rollbacks.

The entire system around development must move at the same pace. If your tasks are planned once a week or two, it doesn't matter how quickly they are completed – the planning procedure itself limits the possible delivery volume.

The quality of tasks is also an important factor. If everything works faster at all nodes, but the project is still stuck on the roadmap, you might be bogged down in optimization, or something in this pipeline is broken, and all the speed is going not into moving forward, but into stopping leaks and patching holes.

If developers are generating code faster, tasks on the board are flying one after another from column to column, and the delivery time hasn't changed – you've found the process bottleneck. That's what needs to be automated – or figure out what's broken there.

Where to start

A universal agent orchestration platform is not needed at the first stage. It's enough to take one repeatable type of change and run it through the full route.

In the beginning, you can ask yourself questions:

  • Have we documented critical instructions and provisions?

  • Is this documentation accessible to everyone in a single repository?

  • Does this documentation work regardless of which agent works on it?

Then, take one small subproject, or invent one within it, or identify a type of task that seems more optimizable than others – and make sure that all questions are answered with a confident "yes".

If something exists only as a prompt request, it is not automated. A process known by one developer is not standardized. If something goes wrong, and documentation needs to be transferred to the specifics of another agent – supported documentation does not yet exist in the project.

Claude Code, Codex, and other agents indeed radically speed up development. But at what cost – depends on how responsibly you implement them. A purchased license changes exactly one stage of the process, while the production system needs to be rebuilt by hand.

Automation begins where every task gets a reproducible and verifiable route. The agent understands the intent and finds exactly the necessary context. It works in a limited environment, proves the result with tests, and passes independent gates. It cannot expand its authority unilaterally. The acquired knowledge returns to the shared repository, so the next developer and the next agent start from a non-zero point.

Then, the team's ability to safely deliver changes accelerates. The output of an individual developer is just one of the indicators here.

Until this happens, no matter what agents you give your team, you have automated code generation – but not development.
