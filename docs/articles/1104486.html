The Problem: QA Knowledge Lives Everywhere Except Where It Can Be Found

Imagine a typical QA day. A task comes in: an empty category storefront on pickup. QA opens the code, logs, Jaeger, and messages the development team in chat. Two hours later, it turns out it's not a bug. The storefront gets availability from the cache, the cache updates every few minutes, and the mock inventory on the environment was intercepted by a live proxy with the wrong priority.

Knowledge acquired. And where is it now?

  • In this QA's head;

  • In a chat thread that no one will find in a week;

  • In a comment on a task, searchable only by task ID;

  • In the best case, on a wiki page that someone will write someday.

A month later, another QA gets a similar task and spends the same two hours. And the AI agent we entrusted with testing spends them every time: it has no memory between sessions.

We have no issues with corporate documentation: we have EvaWiki, which contains requirements and process descriptions. But EvaWiki is about the product, not about testing. It doesn't contain entries like "on the main test stand, the fresh gift doesn't appear in the search results, check the online scenario on test-qa" or "before checking, wait five minutes for the availability cache to update." This is working QA knowledge, and it needs its own home.

What is MKP

MKP (Multi Knowledge Platform) is an internal platform for testers and analysts: a knowledge base and smart document search.

MKP has two types of bases.

evawiki — the integrated EvaWiki base. It's a single instance, comes out-of-the-box, and updates itself daily. Through MKP, you can only query it: creating and editing EvaWiki documents must be done through a separate EvaWiki MCP.

markdown — team-specific testing bases. There can be any number of these. They store testing architecture, test run results, found bugs, and workarounds. Documents can be created, updated, deleted, searched by meaning, and retrieved by number.

You can interact with the platform in three ways:

  • web interface with sections like "Chat," "Documents," "Runs," "Users," and "Profile";

  • REST API for integrations;

  • MCP for AI agents: Cursor, Claude Code, Codex, and anyone else who supports MCP.

Permissions are unified across all access methods. Users log in with a username and password, while REST and MCP use their personal API key. No access to the base means the operation is rejected through any channel.

How MKP Searches

Under the hood, it uses RAG, but not the most naive implementation. The platform combines several techniques:

  • hybrid dense/sparse retrieval — semantic search combined with keyword search. This is important for QA: our queries often contain identifiers like GetExists, is_pickup, CMA-14699, which pure vector search tends to miss;

  • multi-query — the model reformulates the query in several variations;

  • reranking — retrieved fragments are further ranked;

  • parent-child retrieve — we search using small fragments but return the context of the section from which the fragment was taken.

The response always includes three things: the formulated answer, sources (document, score, snippet), and a trace_id for diagnostics. Sources are fundamentally important to us. QA and the agent must see what the answer is based on and be able to open the original document.

Permissions and Roles

There are two roles: admin (users, models, prompts, splitters, base creation) and user (operation within granted permissions). Permissions are granted for each base separately: read — search and read, write — also create, update, delete, and run processing.

A tip from the platform's documentation that we adopted as a rule: create a separate user with the minimum necessary permissions for each AI agent or integration. A catalog team agent doesn't need write access to the payments team's base. An administrator has a convenient "Disable UI Login" switch: a technical user operates only via MCP and cannot log into the interface.

How a Document Enters Search

A saved document is not immediately available in search: the platform must first process it.

While the document is being processed, its status is processing. After processing, it becomes published and becomes searchable. If processing fails, the document gets an error status, and processing is restarted. When a published document is updated, it goes through processing again, and the new edits only become searchable after that.

How We Integrated MKP into QA Workflow

MKP itself is a good platform with smart search. But if documents are added manually, in six months it will become another wiki that no one updates.

So, we did it differently: the AI agent writes knowledge into the base during the QA's regular work.

We have a QA kit, which we will definitely cover in the future, a repository with rules, skills, and automation that QA uses with Cursor and Claude Code. Now, MKP is integrated into this kit, and every QA query to the agent goes through the knowledge base.

This is no longer just a wiki. It's a knowledge base on steroids. QA works on a task in real-time, and the AI helps them: answers questions, accesses code, DB, and logs, and verifies hypotheses. Everything discovered during the process is structured by the agent and stored in the project's knowledge base. On the next task, another QA uses this. Their agent finds colleagues' knowledge, tests faster and more accurately, and adds what they learned to the base themselves. Testing improves with every task.

The agent reads its domain's bases and eva-wiki, and writes only to its own four. It cannot see other domains. Several teams within the same domain (e.g., catalog and product card) write to the same set of bases. Which team wrote a document is visible via the `team` field in the metadata. MKP knows the specific author by API key: each has a unique key, and the agent writes under the key of the QA it's working with.

Before Testing: The Agent Remembers First

Previously, the agent started a task from scratch. Now, before showing the QA a test plan, it must perform four searches:

  1. Was there a retest. `get_document` by exact IDs <task>-test-plan and <task>-test-result. Missing these for a new task is normal.

  2. What was caught on similar issues. A semantic query to `outputs` based on functionality. Without the task ID, otherwise the search will pull documents from the same task and drown out semantic search.

  3. What the team knows about the service. A semantic query to the team's QA-wiki, e.g., catalog-wiki. This contains what QA and agents have accumulated: environments, mocks, how to test correctly.

  4. What the product says. A semantic query to the integrated eva-wiki, i.e., corporate documentation: requirements. If it's empty, the agent searches for the document directly in EvaWiki via its separate MCP: a fresh document might not be in the daily copy yet.

After Testing: The Agent Writes

At the end of the task, the agent makes several entries:

  • to `outputs` — the full test plan, full result, and the comment sent to Tracker. No summaries or abbreviations;

  • to `daily` — the day's entry and the updated index table of contents;

  • to `wiki` — a new stable fact if one emerged. For example, "on this environment, the search proxy returns 403, a static mock is needed.".
