An agent in the next tab has finished its work or is waiting for permission to run a command. How does the terminal know about this?

I downloaded the current builds of Claude Code 2.1.331 and Codex CLI 0.172.0 and found the notification channel selection code: for Claude Code, it's in the binary; for Codex, it's in the source code. Then I searched the source code of twelve terminals and multiplexers. I took ten of them by the latest release tags, WezTerm and Warp from the main branch as of November 24. For agterm, I also ran the server part and CLI from the Linux release. Five more agent orchestrators, including Herdr and Agent of Empires, are analyzed separately at the end. Everything was done in a disposable Docker container: downloading packages and searching by bytes, without running agents or logging into accounts. Versions, prices, and licenses were verified as of November 24, 2026.

In short: in October, agents gained a common status language, OSC 7501, and its number is not yet in the source code of most of the tested terminals.

Claude Code: What Goes to the Terminal

The Claude Code binary contains a table of OSC numbers it works with:

var Y_={SET_TITLE_AND_ICON:0,SET_ICON:1,SET_TITLE:2,HYPERLINK:8,ITERM2:9,SET_FG_COLOR:10, 
SET_BG_COLOR:11,CLIPBOARD:52,KITTY:99,RESET_FG_COLOR:110,RESET_BG_COLOR:111, 
SEMANTIC_PROMPT:133,GHOSTTY:777,PROGRAM_STATUS:7501,TAB_STATUS:21337}

The notification channel in auto mode, which is the default, depends on which terminal Claude Code detects at startup:

switch(Uf()?.terminal??s.terminal){ 
case"Apple_Terminal":return await T()"terminal_bell"?"no_method_available"; 
case"iTerm.app":return"iterm2"; 
case"kitty":return"kitty"; 
case"ghostty":return"ghostty"; 
default:return g()??"no_method_available"}

Claude Code fills the s.terminal field based on environment variables, and TERM_PROGRAM is not checked first. After checks for IDEs (Cursor, JetBrains, and similar), it checks TERM: xterm-ghostty results in ghostty, the substring kitty results in kitty (kitty itself does not set TERM_PROGRAM). Only then is the value of TERM_PROGRAM taken as is, for example, iTerm.app or Apple_Terminal.

The g() function is a fallback: if the terminal identifies itself as ghostty, iTerm2, or kitty in response to an XTVERSION query, the corresponding channel is used (this path does not work within tmux with passthrough disabled). The channels are: for iTerm2 — OSC 9, for kitty — its own OSC 99 protocol (three sequences: title, text, focus), for Ghostty — OSC 777. Terminal.app receives a bell only if a sound alert is enabled in its profile: Claude Code checks this via osascript and defaults export.

All other terminals receive no_method_available: WezTerm, Warp, Windows Terminal, Wave, Tabby, Alacritty, the built-in VS Code terminal. In these, auto mode does not even produce a bell. Caveat: if Claude Code is running in a background session and a client is connected to it, the terminal of the connected client (Uf()?.terminal in the code) is checked first.

This is fixed with a single setting: besides auto, preferredNotifChannel accepts iterm2, iterm2_with_bell, terminal_bell, kitty, ghostty, and notifications_disabled. The iterm2 channel is a standard OSC 9, and WezTerm and Warp display it (at least, that's what Codex thinks, more on that below). They should choose iterm2, and others from the list should choose terminal_bell.

The progress indicator (OSC 9;4, a sequence originating from ConEmu) is enabled even less frequently:

if(s.WT_SESSION)return!1; 
if(s.ConEmuANSI||s.ConEmuPID||s.ConEmuTask)return!0; 
let r=aj(s.TERM_PROGRAM_VERSION);if(!r)return!1; 
if(s.TERM_PROGRAM==="ghostty")return Tw(r.version,"1.2.0"); 
if(s.TERM_PROGRAM==="iTerm.app")return Tw(r.version,"3.6.6"); 
return!1

In Windows Terminal, with normal local startup, progress is explicitly disabled, although according to Microsoft's documentation, the terminal has understood OSC 9;4 since version 1.6 and draws a ring on the tab and a progress bar on the taskbar. Why this is the case cannot be understood from the minified code.

The binary also contains the string probe: no reply to OSC 7501 ; ?. Before sending statuses, Claude Code asks the terminal if it supports the Program Status Protocol (more on that below) and sends reports with app=claude-code only if the terminal replies.

Codex: What Goes to the Terminal

Codex has open source code, which you can read directly from the tag rust-v0.172.0. The notification logic there is shorter:

fn supports_osc9(terminal: &TerminalInfo) -> bool { 
    matches!( 
        terminal.name, 
        TerminalName::Ghostty 
            | TerminalName::Iterm2 
            | TerminalName::Kitty 
            | TerminalName::WarpTerminal 
            | TerminalName::WezTerm 
    ) 
}

In these five terminals, OSC 9 is used; in all others, BEL is used, and only when the tab is not in focus. This is configured in the [tui] section of the ~/.codex/config.toml file: the notification_method parameter (auto, osc9, osc777, or bel) sets the method, and notification_condition sets the condition. The default condition is unfocused, so to check in an active tab, set notification_condition = "always". The lists of the two agents differ: Codex considers Warp and WezTerm capable of displaying OSC 9, while Claude Code in auto mode is silent in them.

With OSC 7501, Codex does the opposite: it doesn't ask anything and writes \[1b]7501;state=…:app=codex to any TTY, except for terminals on VTE versions below 0.54. The specification allows this: a correct terminal simply ignores an unknown OSC. OSC 21337, iTerm2's tab status, is sent only to iTerm2 and only outside tmux, zellij, and screen.

In the terminal detector, Codex has a separate value Rex, recognized by TERM_PROGRAM=rex or TERM=xterm-rex. More on this terminal below.

Who Listens to OSC 7501

Mitchell Hashimoto introduced the Program Status Protocol on October 6, 2026, and published the specification in the documentation for his new terminal, Rex. A program reports one of five states: idle, working, done, blocked with a reason (permission, question, auth), or error. You can add the program name, percentage, title, and message; the title and message are base64 encoded. Hashimoto explains why this was needed using Herdr as an example: such "agent inboxes" guess Claude Code's status by the spinner character in the window title, and the rule for Claude Code alone has been changed ten times in three months.

I checked the terminals by their source code: I downloaded each project from GitHub by its latest release tag (WezTerm and Warp from the main branch), removed tests and vendored code from the search, and looked for the numbers 7501 and 21337 in the remaining files.

Finding the number doesn't necessarily mean the status is visible anywhere. Ghostty is a good example here: in the release notes for 1.4.0, it's stated that libghostty parses the protocol completely, but the Ghostty GUI currently ignores it. In kitty, support was added in 0.50.0 (November 3), and the status is displayed in the tab bar via the tab.program_status field. The iTerm2 source code includes a file named ClaudeCodeStatusOverlay.swift, and a comment within it directly states that Claude Code reports its status via OSC 7501.

The absence of a number proves less. The search was conducted using a decimal literal, and a handler in a third-party dependency or under a different name would have been missed. However, in WezTerm, Warp, Windows Terminal, Wave, and Tabby, there isn't even a mention of the number, so OSC 7501 from Codex is most likely simply discarded there.

tmux 3.8 does not process the protocol itself. Status can only be forwarded externally via passthrough: allow-passthrough is enabled in tmux, and the program itself wraps the sequence in DCS tmux;. Codex 0.172.0 writes OSC 7501 directly, so its status from under tmux presumably does not reach the external terminal. Claude Code at least checks the passthrough setting.

agterm: A Terminal Controlled by the Agent Itself

agterm is a macOS terminal by Umputun under the MIT license. The repository appeared on GitHub on June 21, 2026. The current release, 0.44.1, came out on November 22, and new versions are released several times a week. Under the hood, it uses the same libghostty, with its own model on top: windows, named workspaces within them, and sessions within those. A session can have a split, a scratch terminal, an overlay, and "companions," which are attached logs, watchers, or HTML pages. Pre-built versions are available only for Apple Silicon and macOS 14 and newer; installation is via brew install --cask umputun/apps/agterm.

The main feature is agtermctl, a CLI that operates over a local socket. It's used to create sessions, print to them, read panel text, run programs in an overlay and get their exit codes, set session status, open a native selection dialog, or a question with buttons. A separate skill (Help ▸ Install Agent Skill or the agterm@agterm plugin for Claude Code and Codex) teaches the agent these commands, allowing the agent to manage its own panels and overlays.

agterm receives agent statuses via hooks. The Help ▸ Install Agent Status Hooks option installs adapters for Claude Code, Codex, Pi, OpenCode, and others. The adapter calls agtermctl session status with one of the states idle, active, completed, or blocked, and an icon appears in the session's side panel, optionally with blinking and sound; idle has no icon. The adapter for Claude Code also tries to identify claude -p, launched by another agent, by examining the process tree, to prevent hooks from such nested launches from recoloring another agent's line. If the ancestor chain cannot be read, it still sends the status.

The check is the same as for others, plus execution. The Linux archive from release 0.44.1 contains agterm-server for remote sessions and agtermctl, and both ran in the container: agterm-server --version returned 0.44.1, and the help for agtermctl session status lists the same four states and the flags --blink, --sound, --auto-reset. A search of the v0.44.1 tag's source code with the same exclusions as for others (831 files) did not find numbers 7501 and 21337. OSC 9 and OSC 777 are handled: NotificationManager.swift converts them into macOS notifications tied to a specific session. The shell inside receives TERM_PROGRAM=agterm and TERM=xterm-ghostty.

Agents read these variables in different orders. Codex first checks TERM_PROGRAM, doesn't recognize the agterm value, and in auto mode sends BEL; it doesn't get to TERM. Claude Code, conversely, first checks TERM, sees xterm-ghostty, and considers agterm to be Ghostty. This results in the ghostty channel, i.e., OSC 777, which agterm displays as a notification; an XTVERSION response isn't even needed for this. I haven't tested this chain live on macOS.

For Linux, only the server component is available. Sessions under agterm-server continue to run while the Mac is asleep or the network is down, and they are monitored from the macOS application. There is no native Linux client in the repository; there is a third-party port, agterm-linux, based on GTK4, and an independent reimplementation for Windows, agwinterm.

Terminals Individually

iTerm2. Branch 3.7 was released on September 8, 2026. The current stable version, 3.7.9 from November 20, closes a vulnerability: a specially crafted file outputted via cat could execute commands through kitty's image protocols and drag-and-drop. An update is recommended. Starting with 3.7, the menu includes iTerm2 ▸ Install Claude Code Integration. This integration adds hooks to ~/.claude/settings.json, displays the status on each tab, adds a Chat / Diff / Code Review workspace group, and a Cockpit window showing the status of all windows. Since 3.7.5, the Session Status tool also monitors Codex, but its hooks are configured manually. AI Chat with pluggable models appeared in 3.6. GPL-2.0, macOS 13 and newer, free.

Rex. Apparently, this is what Codex recognizes as xterm-rex. This is a terminal from Superlogical, founded by Hashimoto himself, the creator of Ghostty and co-founder of HashiCorp. The public beta began on October 5, 2026, with invitations sent out from a waiting list. Currently, all testers have access to the macOS application and the Linux server. Windows and iOS applications require separate registration, and there is no Linux client in beta yet. It uses libghostty internally, with a session server on top. Closing the window doesn't terminate the session; you can connect to the Rex server from another machine. The rex CLI manages everything externally: rex run --wait returns the command's exit code, rex capture takes a screenshot and scrollback, and rex events --json provides a stream of events. Configuration is in Lua. Rex is promised to remain free and without an account. I haven't run it myself: server installation commands are only available after tester login, so there's no Rex entry for OSC 7501 in the table. I know about protocol support from its documentation.

Warp. Client source code was opened on April 28, 2026, under AGPL-3.0, the UI framework under MIT, and the cloud part is closed. Warp calls itself an agent development environment: it has its own agent, cloud agents, and the ability to connect your keys to OpenAI, Anthropic, and Google models (BYOK). Pricing as of November 24: Free, Build for $20/month with $20 of agent usage at API prices, Max for $200, Business for $50 per seat. Warp connects third-party agents via its plugins. OSC 7501 is not in its code, and Claude Code in auto mode is silent in it, but the warp@claude-code-warp plugin installs with one click from the interface prompt or via /plugin install, and then Warp itself displays permission requests and sends notifications. There's a similar plugin for Codex, warp@codex-warp; without it, Codex in Warp is limited to OSC 9.

Ghostty. Version 1.4.0 was released on October 27: full implementation of kitty graphics with animation, macOS 27 support, and a dozen security fixes. MIT. Claude Code recognizes it both by environment variables and by its response to XTVERSION, notifies via OSC 777, and since version 1.2.0, it shows progress.

cmux. A macOS terminal based on libghostty from Manaflow, designed specifically for agents. Vertical tabs with git branch and PR number, blue rings around panels where an agent is waiting for a response, a built-in browser, and the command cmux claude-teams for Claude Code's teammate mode. It takes notifications from OSC 9/99/777 sequences, and for agent hooks, there's the cmux notify command. Workspaces and the built-in browser can be managed via CLI and socket API; cmux ssh user@remote creates a workspace with a terminal on a remote machine. It reads Ghostty's config and identifies itself to the shell as Ghostty: it sets TERM_PROGRAM=ghostty and TERM=xterm-256color. Therefore, according to the code, Claude Code sends OSC 777 to cmux, and Codex sends OSC 9. The client is under GPL-3.0, server components under BSL 1.1.

Wave Terminal. Apache-2.0, runs on all three desktop OSs. The built-in Wave AI connects to cloud models using your keys or to local models via Ollama and LM Studio. It has editor and browser blocks, and SSH sessions survive disconnections. The latest release, 0.14.5, came out on April 16, 2026.

kitty, WezTerm, Windows Terminal, Tabby. kitty 0.51.1 (November 23, GPL-3.0) can now output OSC 7501 to the interface, but the tab.program_status field needs to be manually added to the tab title template (tab_title_template). For WezTerm, the last release was dated February 3, 2024; since then, only nightly builds are available. Windows Terminal 1.25 moved to the stable channel in October; the current stable build 1.25.3131.0 was released on November 11. Tabby 1.0.238 (MIT) has no built-in AI; there's a third-party plugin with an MCP server.

Multiplexers and Agent Orchestrators

These programs run inside or alongside any terminal. They keep agents in persistent sessions, monitor their status, and consolidate everything into a single list. I checked five such projects in the same way: I searched their source code by the current release tag (for amux, by the main branch), and I also ran the Linux builds of Herdr, Agent of Empires, and AgEnD Terminal in a container with --version and --help. The number 7501 was not found in the code of any of these five projects; an exception is the separate desktop application Herdr, discussed below. For Paradev, matches were found in one documentation file, and it's a port number in a test report; the protocol itself is only mentioned on marketing pages comparing it with competitors, which were not included in the search. The same caveat as above applies: a handler in a dependency would have missed such a search.

Herdr. A multiplexer written in Rust, a single binary without Electron, Apache-2.0. This is the one Hashimoto referred to. It runs in your terminal, while a background server manages the panels, surviving client closure and SSH disconnections. In the Herdr panel, it finds a familiar agent process and reads the panel title and the bottom of the screen based on rules from the manifest: working, blocked, or idle. Unrecognized programs are displayed as regular terminals. The command herdr integration install installs integrations for 18 agents, according to the 0.9.5 release help. For Claude Code and Codex, the hook only reports the session ID to resume it after server restart; only some integrations, like OpenCode and Pi, directly transmit the status. Via CLI and socket API, agents themselves open panels and wait for each other; remote machines connect via SSH to a shared list. OSC 9 from the Herdr panel is remembered as a progress signal for the detector, and 21337 appears only in the debug log. Builds are available for all three desktop OSs; release 0.9.5 was published on October 14.

Since October, Herdr also has a separate desktop application, herdrdev/herdr-app (Apache-2.0), with its own repository. OSC 7501 reports are received and stored by its core, herdr-core, as stated in the core's documentation, and the number 7501 is also present in the application's code: it identifies the agent by the app field from the report and, if the terminal has no name, assigns it to the notification. I haven't run the application, only performed the same search on the master branch.

Agent of Empires. A session manager aoe written in Rust under MIT. In terminal mode, each agent lives in its own tmux session, which can also be attached to using a regular tmux attach. There is also a structured mode via ACP (Agent Client Protocol), which does not use tmux panels. The command aoe agents in release 1.25.0 (November 18) lists 17 agents. In terminal mode, aoe determines the status from the panel screen (status_detection.rs module) and from hooks that it registers for agents. Tasks can be isolated in a git worktree and in a Docker, Podman, or Apple Containers container. There is a web panel with a mobile version and an HTTP API. It runs on Linux and macOS; on Windows, only via WSL2. The repository recently moved from the author's personal account to the agent-of-empires organization.

Paradev. Until recently, the application was called Superset; the CLI remains superset and has no relation to Apache Superset. A task can be launched in a separate git worktree with its own branch and terminal, with changes and PRs viewable alongside. The application reports that the agent has finished or is waiting for input, and it distinguishes between these two cases for Claude Code. MIT, primary platform macOS, Linux AppImage build is experimental, no Windows. The current release, 2.0.11, is from November 20. Incidentally, OSC 777 was found in the code: Paradev writes it itself from the shell wrapper as a shell readiness marker, unrelated to agents. This is a desktop GUI application; I did not run it in a container.

amux. A server written in Rust and SQLite by Mixpeek. Agents (Claude Code, Codex, Gemini CLI) run in tmux sessions by default; a separate worker can be switched to Herdr. On top of these, there is a shared task board and schedule, and when the limit is reached, tasks wait for its reset. It can be viewed from the web panel and native applications for Apple devices. The license is MIT with Commons Clause: you can use and host it yourself, but you cannot sell amux itself, so it's not considered open by OSI definition. macOS and Linux. There is no ready-made Linux build in the releases; the installer clones the repository and builds it, so I only searched the main branch in the container. The name is not unique: there is, for example, thevibeworks/amux, a Bun wrapper for managing Claude Code via tmux.

AgEnD Terminal. An agent process manager written in Rust, Apache-2.0. The set of agents is described in a single fleet.yaml file: each has a backend, role, and working directory. agend-terminal start launches them as long-lived PTY processes and restarts crashed ones. The README for the release lists six backends, including Claude Code and Antigravity CLI, and 32 MCP tools for agent communication. Management can be done from the TUI and optionally from Telegram. Discord is also supported, but only in the build with --features discord; it's not in the pre-built binaries of the release. Agent status is determined by its terminal screen, and hook and session events refine it. Release 0.12.2 was published on August 17; the last commit to main was on September 23.

How to Test Your Terminal

You can test your terminal for OSC 7501 support without agents. The function from Hashimoto's post (I adapted the example call for make):

status() { 
  printf '\e]7501;state=%s:msg=%s\e\' "$1" "$(printf '%s' "$2" | base64 | tr -d '\n')" 
} 
status working "Building"; make && status done "Built" || status error "make failed"

In iTerm2 and cmux, the status should appear on the tab or in the side panel; in zellij, it should appear on the tab and the panel border. In Rex, the spinner will appear on an inactive tab, and done and blocked will be marked in the session list. In kitty, the status is only visible after editing the tab title template. If nothing changes, support is likely absent, but it's best to consult the terminal's documentation.

Conclusion

Built-in chat with a model is currently available in Warp, Wave, and iTerm2, but it doesn't help an agent in the next tab. When three or four agents are open, the "I'm waiting for you" signal is much more useful, and the list for it is currently short. Via the common protocol, it's understood by iTerm2, cmux, kitty, and Rex, while zellij, according to documentation, displays the status in the tab, on the panel border, and in its inbox, and works inside any terminal. Warp and agterm receive status via their plugins and hooks. In others, agents use one-time notifications (OSC 9, 99, or 777) or a bell, and Claude Code in WezTerm, Wave, Tabby, and Windows Terminal (and in Warp without a plugin) is completely silent by default.

Orchestrators like Herdr and Agent of Empires work in any terminal and also see agent statuses, but through hooks and parsing panel output, and Agent of Empires also through structured ACP sessions. The number 7501 is present among them only in the new desktop Herdr: in the application's code and its core documentation.

The practical conclusion is simple: if you are not using iTerm2, kitty, Ghostty, or cmux, check Claude Code's preferredNotifChannel and Codex's notification_method. By default, Claude Code might be completely silent there, and Codex might be limited to a bell.
