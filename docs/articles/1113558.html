Do Not Use XHigh Under Any Circumstances

I made my first mistake on the very first evening: after paying $200, I cranked the intelligence slider to maximum, to Neon XHigh mode (labeled Extra High in the interface). Do not repeat this. It was XHigh that turned the fast editor into a source of pain.

When I ran the logs from the first week through scripts, there were exactly zero actual program crashes. However, all 37 ten-minute freezes occurred on XHigh, with zero on Neon High. XHigh had four times more turns (1,215 vs. 289), but even in the extended sample of 110 chats, it froze about 20 times more often (3.05% vs. 0.15%).

Neon's hidden reasoning and response share a single generation ceiling (65,536 tokens). On a bloated chat or a batch of images and videos, XHigh enters a long reasoning cycle, slows down on contexts of 350K+ to a median of 63.8 tok/s, and hits a 10-minute timeout. Sub-agents by default copy the parent model, so one enabled XHigh brings down the entire chain.

The code quality for my tasks shows minimal difference, and according to Artificial Analysis measurements, XHigh consumes 50-72% more tokens. Disabling it in favor of Neon High immediately provides 33-42% quota savings.

Three More Client Issues That Can Be Fixed With Rules

Besides XHigh, my logs revealed three more client issues. All three are cross-platform and not tied to Windows.

Disconnections on long writes and false Model unavailable banner. In the first week, I had 218 unexpected EOF disconnections (199 on XHigh, 19 on High) when trying to write a long file in a single call. The Google server did not go down. Regular text in chat streams in chunks and lasts 3-5 minutes, while the write_file argument or a long inline script in run_command accumulates in JSON entirely.

While the model is writing a large file, there's silence in the connection. At the silence cutoff (~60 seconds on Google's frontend and ~40-42 seconds on my route), the stream breaks, and the client retries the request nine times in a row, burning quota. This is doubly problematic with Russian due to the two-byte Cyrillic characters in UTF-8.

To rule out random network glitches, I ran an A/B test within the same connection. A control write of ~15 KB of Russian text in a single call failed 3 times out of 3 exactly at 41-42 seconds.

As soon as I configured splitting writes into chunks of up to 4-5 KB of Cyrillic (using Append: true or a skeleton + edit_file), up to 6-7 KB of code, and up to 3-4 KB of inline script in run_command, four test runs (31 write steps, 62 KB of text and HTML) completed without a single disconnection.

Two Habits That Ruin the Cache. The internet often warns that above 200K tokens, the Antigravity cache falls apart. This was not confirmed by my logs: on Neon High, I ran 97 turns above 200K and up to 350K, and the average cache hit rate stayed in the 85.7-93.7% range without a single disconnection.

Forced compression by the client itself kicks in around 500K, so on High, `/compact` at 350K-400K is usually sufficient.

However, two everyday habits actually impact the cache. Switching modes (Medium, High, XHigh) mid-chat instantly resets the cache (0 out of 85,906 tokens in the measurement) because they are different model IDs within the client. And pauses longer than five minutes increase the miss rate from 0.5% (on pauses less than a minute) to 18.5% for pauses of 5-7 minutes and 21.3-34.9% after 7 minutes.

Hidden Rule Truncation at 24,000 bytes and Windows Quirks. The client has a hard limit of 24,000 bytes per file, which silently truncates the end without warning. This affects both AGENTS.md and any skill file SKILL.md (the Adobe team encountered the same problem in repository #665).

I found three skills on my end that were 25-32 KB, where the endings with checks were simply cut off, plus the overall budget of 20,000 tokens for all active rules adds to the pressure.

I keep each file under 20 KB, and move heavy tables to the `references/` subfolder. On Windows 11, I also set the syntax for old PowerShell 5.1 in the rules (where `&&` and `??` operators fail), updated Python beyond the WindowsApps stub, and added a check for `worktreeConfig = true` in `.git/config`. These problems do not exist on macOS and Linux.

Three Practical Tips and a Ready-to-Use Rule Set

In addition to setting limits, three short rules have helped me in my daily work:

  1. Assign light roles to different models. In my setup for sub-agents dealing with images and video, I assign the light `flash` model, and for small, one-off edits, I open a separate chat on `Hydrogen` (8 turns in my logs ran at a median of 107.8 tok/s without a single failure).

  2. Provide fresh documentation directly in the context. Without internet access, Neon is more prone to making up details (13.9% hallucinations in the AA-Omniscience v1.1 test on Artificial Analysis), but with fresh source code or documents in the context, it works very accurately.

  3. Curb the tendency for excessive code and radical changes. Neon sometimes rewrites unnecessary files or tries to delete a failing test just to achieve a green build. I've forbidden it from touching tests and integrated the open-source Ponytail rules in `full` mode. Even two lines in `AGENTS.md` demanding a minimal diff without excessive wrappers provide a basic effect.

To avoid rewriting these limitations manually, here is a basic rule block that you can copy directly into your `AGENTS.md` or `.gemini`:

Basic rule block for AGENTS.md for Antigravity (copy and paste)
## Antigravity & Gemini 4 Neon Guardrails
- Default effort: `Neon High`. Never switch effort level mid-chat (resets KV cache).
- Subagents for screenshots/video: use `flash`, never `XHigh`.
- Avoid SSE `unexpected EOF` silence cliff:
  - <= 4-5 KB (~80-100 lines) per `write_file` for Cyrillic / Russian Markdown / HTML (split with `Append: true` or skeleton + `edit_file`).
  - <= 6-7 KB (~140-160 lines) per `write_file` for ASCII code.
  - <= 3-4 KB for inline scripts in `run_command` (write longer scripts to a file first).
  - Strictly one large `write_file` per turn.
- Keep every rule file (`AGENTS.md`, `rules/*.md`) and every `SKILL.md` under 20 KB (hard silent truncation at 24,000 bytes; move large tables to `references/`).
- Run `/compact` around 350K-400K on `Neon High` (120K on `XHigh`).
- Windows 10/11 only: `run_command` uses Windows PowerShell 5.1 (no `&&` or `??`), verify `python` is not `WindowsApps` stub, check `.git/config` for `worktreeConfig = true`.
- Never weaken or delete failing tests or working features just to make a check pass; prefer the smallest complete diff without speculative wrappers.

I hope Google will also address these client-side issues in upcoming patches. I'd like to see a short ping within a long file write, a simple yellow warning for files heavier than 24 KB, and a proper Diff Viewer.

Is It Worth Switching from Claude Code?

If you need a mature out-of-the-box tool without fiddling with configs, Claude Code is still more reliable: you don't have to split writes into chunks and worry about the hidden 24 KB limit for skills.

I've stayed with Antigravity because of the Gemini 4 Neon and native client combination and the economics of the $200 subscription. Disabling XHigh and a short rule block in `AGENTS.md` removed the main bottlenecks, and for now, I see no reason to return to Anthropic.
