A large language model doesn't know how a specific information base is structured. It cannot see configuration modules, active extensions, user rights, or document data until it gains controlled access. Therefore, the practical task isn't just choosing a model. It's about gathering relevant context for it, limiting its actions, and incorporating result verification. Let's explore how this process works in an AI assistant for 1C and where a specialist is still needed.

Why a Regular Chat Isn't Enough

If you paste a separate BSL code snippet into a chat, the model can explain it or suggest changes. However, in a real database, the cause of an error is often outside that snippet. A method might call other procedures, an extension could alter document behavior, and the result might depend on specific user data and rights.

A developer typically reconstructs this context manually: searching for methods, tracing call chains, checking extensions, and reproducing the situation with data. An AI assistant can speed up this search if it can obtain the same information through its tools. The model doesn't need unrestricted access to the entire database. For each task, it requires a limited set of code and data.

How the Assistant Gets Configuration Context

To analyze code, the program creates a local index of modules from the main configuration and active extensions. This index is used to find procedures, functions, and related code fragments. Index creation is performed in read-only mode and does not alter the working configuration.

The user formulates a question in natural language. For example:

Why does the project change when this document is posted?

To answer, it's not enough for the assistant to find a line with the word "Project." At the process level, it needs to identify the posting handler, retrieve called methods, check active extensions, and correlate the code with the document's attributes. Fragments relevant to the current task are passed to the model, not a full configuration dump in one request.

What Happens During Error Analysis

A typical analysis can be represented as a sequence of actions.

The user specifies the problematic document, operation, or code section and describes the observed behavior.

The assistant retrieves the object's metadata and finds related modules in the local index.

It traces the call chain to gather methods that might affect the outcome, including intercepts from extensions.

If the task requires data, the tools read the user's accessible attributes, movements, or log entries.

The model forms a hypothesis and displays the code or data it's based on. A specialist verifies the output and decides if changes are needed.

This sequence is crucial for verifiability. An answer like "it seems the error is in the posting handler" is not very useful without the method name, related intercepts, and the observed value. The more precisely the assistant shows the basis for its conclusion, the faster a developer can distinguish a plausible hypothesis from a confident model error.

Checking Extensions After an Update

Updating a standard configuration introduces a specific class of risks. A vendor method might have changed parameters or internal logic. A code fragment copied into an extension might be outdated. Multiple extensions could intercept the same method in an incompatible order.

For initial checks, the solution uses the "Intercepts" report. It helps find changed or missing methods, outdated copies of standard code, and potential conflicts. In recent versions, scenarios for re-posting documents and register movements have been added to these checks.

Based on the identified issue, a task description for correction can be prepared and sent to the chosen AI client. The assistant can also retrieve the current code of the standard method and prepare the modification transfer. This reduces the mechanical part of the work but doesn't confirm practical correctness. A changed method might reflect a new business rule that cannot be mechanically transferred to an extension.

Therefore, the result is first tested on a test database. This requires at least loading the extension, syntax checking, and reproducing the original scenario. For critical sections, regression tests and document movement reviews are added.

Why Code Changes Require Separate Permissions

Reading configuration and modifying extensions carry different risks. Thus, the ability to create and change extensions is enabled separately for each database and is only available to users with the MCPFullAccess role. Extension versions are saved, allowing rollback to a previous state.

When working via a terminal server, employees run their own program instances. The assistant works with the databases and permissions accessible to a specific employee. This doesn't replace the company's internal access model but avoids granting all team members identical privileges solely for an AI tool.

For a pilot, it's reasonable to separate environments. In the production database, limit access to reading and diagnostics, and prepare changes in a test copy. Deployment to production should follow the standard review and release process.

One-Off Reports Without Separate Development

Not all data-related questions require configuration changes. An analyst might need a one-time selection or a report with familiar settings. Such a task can be described in words:

Show sales by counterparties and months, add a filter by organization and a chart.

The solution can generate an external 1C report in ERF format. This requires the configurator to be installed and appropriate permissions. After creation, the user receives a standard external report where they can change the period, filters, and available settings.

The main risk here is not with the file format but with the meaning of the indicators. Terms like "sales," "revenue," or "balance" can have multiple interpretations within a specific database. A specialist must verify data sources, filters, and calculation methods before using the result in a management decision.

Diagnosing User Requests

Support requests often start with phrases like "the document won't post" or "the numbers don't add up." Before analyzing code, a specialist has to gather context: which document is open, what are the user's rights, what related objects exist, and what is recorded in the registration log.

The assistant can obtain this information through available tools and prepare a more precise problem description. For diagnostics, connection can be limited to read-only access. This mode is also organizationally useful: it separates fact-gathering from actions that modify data or code.

The AI Client Can Be Changed

Tools for accessing 1C are not necessarily tied to a single chat client. The current version supports ChatGPT, Codex, Claude Desktop, Claude Code, DeepSeek Harness, Kimi Code, and Kimi Work. The latter three are available in Russia without a VPN, and connections to databases for them are configured automatically.

For a team, this means the model and interface can be chosen based on the task and corporate restrictions. However, changing the client doesn't eliminate the need to verify permissions, the composition of transmitted data, and the quality of the result. The same set of tools doesn't guarantee identical behavior from different models.

What Data Goes to the External Provider

When using a cloud-based model, data necessary for the request is transmitted to the external provider. This must be considered before connecting a production database, not after the first incident. Organizations should define acceptable data categories, the account for connection, and the list of permitted scenarios.

The solution includes anonymization of supported personal information. When this function is enabled, attachment transfer is disabled. However, organization names, product lists, and amounts are not changed. Consequently, anonymizing personal data doesn't automatically make every request secure. Commercial information and the context of business operations must be evaluated separately.

• Use a separate 1C account with the minimum necessary permissions.

• Separate scenarios for reading, diagnostics, and extension modification.

• Review the contractual terms and data storage settings with the chosen AI provider.

• First, connect a test or anonymized database and document the result verification process.

How to Conduct a Pilot and Get Measurable Results

It's easier to start a pilot with a repeatable task for which the standard process is known. For example, checking extensions after an update. The team can compare the assistant's results with manual checks and see not only the time saved but also any missed issues.

Before launching, it's advisable to document several metrics:

• how much time manual searching for changed methods and intercepts takes;

• how many issues the assistant finds and how many are confirmed by the specialist;

• what issues the assistant misses;

• how many edits are required in the prepared task or code;

• whether the modified extension passes existing checks on the test database.

Such a pilot answers the practical question: at what stage does the tool save time for this specific team. For some, it might help find code faster; for others, it might be useful for diagnostics, while extension creation might prove too risky for the initial stage.

The Specialist's Responsibility Remains

Access to code and data makes the model's response more relevant but doesn't turn it into proof. The assistant can find related methods, prepare a report, or suggest a change. The developer and analyst remain responsible for the practical meaning, completeness of verification, and deployment to the production database.

The most beneficial scenario occurs where the model reduces search and mechanical preparation, while the process retains rights, versioning, and a test environment. These limitations precisely determine whether an AI assistant can be used in daily 1C work.
