TL;DR

  • The time to dive into context is now primarily spent during the review phase.

  • If you accept code just because it works, you can accumulate debt that the team doesn't even notice.

  • It's worth either reducing the amount of manual review or automating repetitive checks.

In a conversation with a client about AI development, I heard the opinion that reviewing code generated by agents creates a huge cognitive load—you have to keep many details in mind simultaneously to understand the work and assess its quality.

I myself have almost never felt this. I think it's because I started using AI tools for development back in the beta version of GitHub Copilot and got used to small tasks, small commits, and short feedback loops.

The models back then struggled with large tasks. I broke problems down into parts, read and corrected the results, and gradually immersed myself in the code and its limitations. As the models' capabilities grew, I simultaneously learned to understand where they could be trusted.

Today, a model can generate a large amount of code at once. But the time needed to dive into its context does not automatically decrease along with the code writing time. If understanding is no longer formed during implementation, all this load accumulates and falls on the person when they receive the finished result.

It seems to me that because of this, people might start accepting code they are unfamiliar with simply because it works, thereby accumulating "cognitive debt" they don't notice themselves. To break this cycle, you need to either reduce the load during code, architecture, and documentation reviews, or remove the human from routine repetitive checks altogether.

1. Time to dive into context shrinks to the review stage

When a developer wrote code themselves, they had to read surrounding code, translate requirements into implementation, and fix failing tests. In the process, they understood why a particular structure was needed and under what conditions it might break.

That is, the code writing time was simultaneously the context immersion time. Even if the understanding remained incomplete, the developer still gradually formed a working model that could be relied upon for the next solution.

When implementation is delegated, the person immediately receives a ready result. Now they have to go in the opposite direction: analyze the code and tests to restore the intent, initial assumptions, and exceptions. Work that was previously distributed throughout the development process now has to fit into the short review window.

DORA describes this as shifting time from generation to verification and directly emphasizes the difference between these tasks.

“Verification is a fundamentally different cognitive task than creation.”

This diagram shows at which stage the main work occurs. If the same amount of code is generated faster, it doesn't mean the entire task speeds up proportionally: the person still has to immerse themselves in the context separately.

If, within the same deadlines, more changes are taken on at once, people have to constantly switch between unfamiliar contexts. For an individual developer, this results in cognitive load, and at the team level, it leads to review queues and additional rework.

In this article, by backpressure at the review stage, I mean a situation where progress is hindered by people's ability to understand and review the incoming stream of changes. If the volume of generation grows and the time for context immersion shrinks, this pressure only intensifies.

2. Debt taken consciously, and debt that goes unnoticed

When we talk about technical debt, we usually mean a trade-off between release deadlines, performance, and the cost of future maintenance. For example, a team might consciously postpone fixing duplicate implementations to release a product faster.

When describing conscious technical debt, Martin Fowler specifically emphasizes this point.

“The team knows that it is taking on debt.”

If the team understands what exactly they have postponed and what it might cost, paying off such debt becomes a decision that can be discussed. But technical debt can also be unintentional. Here it is important to distinguish between a conscious compromise and a gap in understanding that passes through review unnoticed.

Cognitive debt is the lack of a common understanding within the team about how the system behaves and how changes will affect it. Here I am considering situations where the team accepts code without fully realizing that such a gap even exists.

Let's imagine a hypothetical function to prevent double charging. Payments through the interface go through, tests with retry attempts are also green, but no one has checked what will happen with a retry after a record is lost or if two requests arrive simultaneously.

By contract here, we mean the behavior and set of conditions that the implementation must meet. For example, one request should not lead to two charges. Knowing the contract itself is not the same as understanding the specific conditions under which the implementation actually adheres to it. If you accept the result simply because it works, the team might not even notice what exactly has been left unchecked.

Postponing analysis under pressure of deadlines and the need to approve changes faster can be quite conscious. But this doesn't mean the team understands the scale and consequences of the gap left behind. Story separates these two points.

“Even when such a decision is made consciously, the resulting debt accumulates unnoticed.”
— Margaret-Anne Storey

Later, someone shortens the retention period for payment records to reduce data storage costs. A reviewer who doesn't understand the connection to retry attempts might miss an erroneous change. Cognitive debt degrades the quality of subsequent decisions: it can lead to increased technical debt or the later discovery of an existing problem.

The diagram shows one of the possible scenarios where the team accepts code before they have time to understand it. Cognitive debt doesn't disappear, turning into technical debt. Lack of understanding and erroneous code that it allows to be missed can coexist.

3. Team speed is limited by the slower verification stage

To avoid accumulating cognitive debt, you need to understand how many changes the team can process while still having time to understand them and perform necessary checks. When generation becomes fast enough, it is the verification throughput that begins to limit the team's work speed. Microsoft's recommendations on system bottlenecks state this principle:

“A system can only process data at the speed of its slowest component.”
— Microsoft

Let's apply this principle to reviews. Assume that generation and delivery do not create other bottlenecks, and the incoming stream of changes is sufficient to fully load the review process. Each change passes automated checks, and only changes requiring human assessment go to manual review. Both stages can process different changes in parallel. Let's assume that units of change and quality criteria are the same.

If we express the throughput of both stages in terms of the number of changes processed, the team's speed, limited by the review stage, can be approximately represented as follows. This is a bottleneck model that helps understand what exactly should be improved, not a formula derived from measurements of real teams.

team velocity ≈ min(human review velocity, automated review velocity)

Here, velocity means the number of changes that meet the same quality criteria, not just the number of approvals. Rework and waiting can reduce actual throughput. If generation or delivery are slower, they also need to be considered when looking for bottlenecks.

Let's imagine a hypothetical team where each change requires manual review. People can review eight changes per day, and automated checks can handle twelve. min chooses the smaller value, so min(8, 12) = 8. Even if automation can handle twelve changes, the team can stably deliver about eight per day if people can only review eight.

Where does this manual review throughput—eight changes per day—come from? It can be calculated from the time available for review and the average time per change.

H = available time for manual review per day
C = average review time for one change requiring human assessment
p = proportion of all changes requiring manual review

human review velocity = H / (p × C)

Suppose the team has 240 minutes per day for reviews, and one review takes an average of 30 minutes. Each change requires manual review, so p = 1. Plugging in the values: 240 / (1 × 30) = 8. We get a throughput of eight changes per day.

Now, suppose only half of all changes require manual review, i.e., p = 0.5. If H and C remain unchanged, we get 240 / (0.5 × 30) = 16. People review eight of these sixteen changes, spending 8 × 30 = 240 minutes. The denominator p × C is the average manual review time per change among all changes.

Therefore, the result shows the total number of changes that the available manual review throughput can support, not the number of reviews people perform directly. Since automated checks still only process twelve changes per day, the team's speed is now min(16, 12) = 12, i.e., approximately twelve changes per day.

C includes reading code, restoring context, verifying assumptions in architecture and documentation, and analyzing exceptions. The more time it takes to understand unfamiliar context and deal with complex conditions, the higher C becomes. If the available review time H and the proportion of changes requiring manual review, p, remain the same, an increase in C means the team can handle fewer changes.

Therefore, I believe that cognitive load can be inversely related to team speed. Here I link cognitive load to throughput through the time required for understanding and assessment. I am not claiming that there is an exact inverse relationship between any numerical indicator of psychological load and team speed. The point is that cognitive load limits team speed when manual review becomes the bottleneck.

Returning to the initial condition where each change requires manual review. Suppose that by reducing the effort for context immersion, a review of the same quality can now be done in 15 minutes. H remains 240 minutes, p is one, and C decreases: 240 / (1 × 15) = 16. If the time for one review is halved, the manual review throughput doubles. With unchanged automated check throughput, the team's speed can increase to about twelve changes per day.

If the team size and available time do not change, there are two main levers on the manual review side—C and p: you can reduce the cost of understanding and assessment or reduce the proportion of changes that require direct human involvement. If a certain stream of changes does not require manual review at all, this stage should simply be removed from the throughput model, rather than trying to divide by zero.

4. Reduce the cost of context immersion

The first direction is to make the necessary manual review less labor-intensive. C increases when, with each review of code, architecture, or a document with requirements, people have to reconstruct the goal of the changes and the assumptions embedded in them from scratch.

I would define the contract even before implementation begins, and link the finished result to the system's behavior before and after the change, failure scenarios, and verifiable outcomes. The contract should fix observable behavior, conditions that must be met, and who can read or modify what data.

In the payment example, a simple message that tests have passed is not enough. It is much more useful to understand which retry scenarios have been tested, how lost records and simultaneous requests have been accounted for, and which decisions still remain open. Explanations should lead directly to the relevant code and actually executed tests—this way, context restoration requires less effort.

You can also reduce the amount of information you have to deal with at once. Implement one small part of the requirement, understand it, test it, and only then commit. If you first generate several small pull requests—review and merge requests—and only read them all later, the time for context immersion will again be shifted to the very end.

The diagram shows how understanding is formed between small implementation steps. The context of the current small change becomes the starting point for the next one.

The cognitive debt already accumulated will still have to be paid off. Time is needed for joint analysis of code and design, searching for missed assumptions and failure scenarios, and correcting erroneous implementations. If the system's behavior and initial assumptions are fixed in code, documentation, and tests, you won't have to reconstruct all this context from scratch for the next task.

In the ALPS Writer Plugins that I maintain, I have incorporated criteria for breaking down work into parts and verifying results against contracts. Long-term decisions are recorded in Architecture Decision Records (ADRs), and implementation explanations link request processing and failure scenarios to specific code and tests.

The mere existence of documentation does not mean the system is understood by the team. Maintainers must be able to explain behavior that is important for future changes and incident response. Small changes and understandable verifiable results help maintain this understanding.

5. Remove people from routine checks

The second direction is to stop requiring the same manual review for every change. If people have to repeatedly re-read conditions that can be checked automatically, p remains high.

If reviews constantly have to check which modules might depend on each other, these dependencies can be controlled by architectural tests. If reviewers repeatedly ensure that the same request is not processed twice, regression tests can check that subsequent changes have not reintroduced this problem. If such decisions are accumulated in the verification infrastructure (harness)—work instructions, tools, and verification environments—they can be reused.

In my target scenario, if the agreed-upon contract is sufficiently checked automatically, repeated human approval is no longer required. People get involved where new product behavior needs to be defined, a contract needs to be changed, high-risk conditions need to be assessed, or assumptions that automation cannot confirm need to be verified.

An agent's statement that everything is fine is not enough to abandon manual review. It must be clear what exactly was checked, and the results of the check must be available to a human. Otherwise, the process simply starts to pass unfamiliar code faster.

Automating checks is not the same as maintaining the necessary understanding of the system. People don't necessarily have to read every implementation detail, but the team still needs to define the goal and quality criteria and take responsibility for subsequent changes.

Until this transition is complete, the flow of new work entering the process should be controlled. Reducing the number of incoming changes itself does not reduce the cost of understanding a single review. The freed-up time is better used to improve explanations, contracts, tests, and tools—then throughput can increase in the future.

After automation, the complexity of the remaining manual reviews needs to be re-evaluated. Eliminating routine changes can reduce p, but simultaneously increase C, because people will be left with more complex decisions. Therefore, it is worth looking at the actual review time and its quality. Automated checks also require costs for tools and operation, so it is useful to evaluate CTS-SW—the cost of delivering one unit of software to the user—to understand if the overall cost has decreased.

Let's summarize

AI reduces code writing time, but people may still need separate time to dive into context. If you accept a working result while ignoring this gap, you can accumulate cognitive debt—and the team may not always understand what specific knowledge they are lacking.

Demanding approval of changes even faster under the same pressure is unlikely to solve this problem. With unchanged quality, you either need to reduce the effort required for manual review or remove people from routine repetitive checks. In my opinion, this is precisely the main task for increasing team speed after code generation is no longer a bottleneck.
