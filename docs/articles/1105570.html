Agent Harness is an infrastructure layer that automates and manages the working environment, bringing the agent closer to true agency, if you'll pardon the pun.

An agent is essentially an LLM + Harness. With skillful use, even a less advanced model with a quality Harness environment can outperform a top-tier LLM without one.

In this article, I will explain what Agent Harness is and its components as of 2026.

The word Harness, as I've already mentioned, comes from the field of testing and refers to the infrastructure and conditions for running code. In our case, it has evolved into the actions that need to be performed after the LLM's output to ensure it solves tasks effectively and makes fewer mistakes. Currently, this includes context management, tools, memory, skills, MCP, and multi-agent logic.

In the ideal perception of an AI agent, the LLM is merely an endpoint that accepts JSON (or another format) and returns JSON.

Without a quality harness, even a top model remains a chatbot; with a good harness, an average model sometimes solves tasks more reliably. This is precisely why we have concepts like orchestration and multi-agent systems: an expensive model for verification and complex design/reasoning, a medium one for generation and orchestration, and a fast, cheap one for mass sub-agent calls.

Such distribution requires a unified access layer to different models, and here, an OpenAI-compatible gateway like BotHub (https://openai.bothub.chat/v1) becomes a practical solution. Official SDKs work without changes, and upon registration via the referral link, you receive 300,000 CAPS.

Next, we'll break down what constitutes a harness, how MCP and skills are structured, why sub-agents are needed, and how to choose models for specific roles – so that the agent ceases to be a demonstration of capabilities and becomes a working tool.

What is a Harness?

The word harness, in its direct translation, means a harness for pulling. In the context of agent systems, it refers to runtime scaffolding.

An agent's ability to solve tasks is not a property of the model itself but an emergent property of the "model - harness - environment" system, where the harness mediates how the agent perceives the project, acts within it, receives feedback, and ensures task completion. In other words, the debate about "which model is better" often boils down to the quality of the harness surrounding it. Practice confirms this: the same ReAct loop can be implemented in ten lines of code, but 95% of an agent system's work involves the context, tools, sandboxes, and error handling around those lines.

Let's try to break down the layers.

Execution loop

The ReAct loop is a sequence of operations: prompt -> model -> parsing -> tool execution -> returning result to context, repeated until the task is completed.

In AgentScope Java, there's even an explicit separation between ReActAgent, which implements the reasoning-acting loop itself, and HarnessAgent, which wraps it. It doesn't change the loop but adds a workspace, long-term memory, context compaction, skills, sub-agents, sandboxes, and session logging.

Why is this important? Because the loop itself is the cheapest part of the harness. The complexity lies in not knowing when to stop. Did the model generate a response without calling tools – is that the end, or is it just tired? Is the iteration limit reached – is that an error or normal completion? This is where the engineering of termination conditions begins, involving separate exits for the final answer, exceeding the token budget, triggering a guardrail, or user interruption.

Context management

Context window is a very popular AI metric. But it's not an infinite storage; each tool call adds new conditions and new messages. LLM APIs are stateless services, so you need to pass the entire context with each request.

If this isn't managed, the model can drown in its own logs, and your wallet can shrink significantly – context grows non-linearly. Therefore, context compression and caching are important features. Caching is caching, but context compression either truncates old messages, filters messages, or has the model generate a summary.

By the way, this is also where the decision of what actually goes into the prompt resides. Anthropic, in their harness for long tasks, uses context resets – a complete clearing of context with a structured handoff.

Cached tokens in the context might be free or cheap, but it's still better not to overuse a single chat and create a separate chat for each independent task.

Tools

Tools are provided to the model as schemas with metadata and parameters. The harness handles the dirty work of validation, checking, and running results in sandboxes. This is a crucial part as it gives the model its hands. Yes, and again, most often, a tool is a JSON/MD specification. The model itself decides when to use a tool during operation.

But there's a small nuance: the more tools there are, the worse the model becomes at selecting them. Context is not elastic; don't fill it with tool descriptions. User requests can get lost, and the model might start focusing on playing with tools.

Memory and state

Memory in an agent is divided into short-term (within a session) and long-term (between sessions).

Anthropic, in Managed Agents, explicitly separates the session (an append-only log of everything that happened), the harness (the loop of calls), and the sandbox (execution environment) so that the implementation of each can be replaced without breaking the others. State should not be tied to the container; container failure should not mean session loss. In general, the system design principle is evident: avoid a single point of failure.

Guardrails and permissions

Now, about responsibility, protection, and permissions. A model can generate anything and use anything, but it's best to keep the approval to yourself. Most harness systems can check policies, lists of allowed or disallowed tools, ask the developer if necessary, and only then proceed.

And if you have more than one agent, it's better to distribute write, execute, read, and other permissions to avoid race conditions among agents.

Sandbox and observability

And of course, two things are important: sandbox and observability. A sandbox is not just a Docker container but true isolation from the system. As infrastructure grows, Cloudflare Sandboxes and Google Managed Agents emerge. Simultaneously, observability is important not just as logs but as a condition for agent admission. If the harness cannot show what the agent has done and in what context, that harness isn't worth even a sliver of RAM for Sam Altman.

Some academic papers propose a "trace-based evaluation protocol," turning each agent run into an auditable episode package – with reproducibility, error attribution, and deterministic checks.

All 6 layers may not be equally developed. After all, a harness is a set of compromises (one could say agent systems are a subgenre of system design). Somewhere you sacrifice memory depth for speed, somewhere – strictness and security for throughput, somewhere – a centralized orchestrator for debugging simplicity.

A harness encodes assumptions about what the model cannot do itself. When the model changes, these assumptions become outdated – and a component that was a load-bearing wall yesterday becomes a bottleneck today. Anthropic explicitly states that harnesses must evolve, and therefore we will see many unrealistically "innovative features" in the form of another md-file describing something.

Now, let's move on to specific components!

Skills

Skills are a technology built on top of model fine-tuning, prompting, and files. In essence, they are a compositional package of procedural knowledge that teaches an agent how to solve a task.

To understand the concept, it's important to distinguish a skill from a tool, which was the primary building block of agents previously. A Tool is a single deterministic function with a clear input and output, described by a schema (e.g., get_weather(city)). The agent simply decides when to call it and executes it. A Skill, however, is a layer of judgment and orchestration. It represents a "recipe" or a set of procedural knowledge that defines which tools, in what order, and why they should be used to achieve a goal. If a tool is a hammer, then a skill is an instruction manual for assembling a cabinet, telling you when and how to use that hammer.

A typical skill is essentially a directory of documents. Metadata and main instructions are in SKILL.md, and resources are in subdirectories like scripts, ref, and assets.

Skills have come to the forefront for a reason. By 2026, a "model parity" has emerged: leading LLMs (GPT-6.x, Claude 5.x) have reached similar levels in benchmarks, and the practical difference between them has become minimal. The competitive advantage has shifted from the model's "raw" intelligence to engineering – the ability to build a reliable, scalable system of skills around it.

However, skills also carry vulnerabilities, and too many skills can only confuse and overcomplicate things. Everything is poison, and nothing is without poison; only the dose makes the poison imperceptible. Also, don't install no-name skills, and even well-known ones should be checked just in case, as there have already been instances of vulnerability exploitation.

Now for the interesting part – the loading mechanism. The agent initially only sees the name and description, and only when the task matches does it open the full instructions, then pulls in additional files as needed.

AGENTS.md and llms.txt

Let's talk a bit about harness sub-components that, while not part of the main loop, are very important.

AGENTS.md is an open format proposed by OpenAI in August 2025. It's essentially a README for AI agents, supported not only by Claude Code but also by Cursor and other tools. It resides at the root of the repository and contains commands for building, code style, and allowed/disallowed patterns.

Here's an example of AGENTS.md:

# AGENTS.md

## Setup commands
- Install deps: `pnpm install`
- Start dev server: `pnpm dev`
- Run tests: `pnpm test`

## Code style
- TypeScript strict mode
- Single quotes, no semicolons
- Use functional patterns where possible

You can look at other examples, such as AGENTS.md from AIR – a Python web framework billed as "designed for AI." It includes instructions for working with HTML templates, minimal application code, routing rules, templating, forms, SSE, databases, common patterns, and dependencies. Essentially, it's an excerpt from developer documentation with notes and code style – something between CONTRIBUTING.md, README.md, and the docs themselves.

llms.txt and llms-full.txt are standards from Answer.AI, proposed in September 2024 and have since become quite widespread. llms.txt is an index, essentially a regular file with a list of documentation links that the agent scans to decide what to read next. llms-full.txt is the full documentation text in a single file, downloaded once and kept in context. The logic is simple and related to token economics – agents are token-limited, and it's more efficient for them to read one file than to visit twenty links and parse HTML.

How to assemble llms-full.txt? Concatenate all documentation pages into a single file – markdown, rST, or any similar format.

It's best to place these files on the documentation website – as done in the django-modern-rest project: https://django-modern-rest.readthedocs.io/llms.txt and https://django-modern-rest.readthedocs.io/llms-full.txt.

MCP vs A2A: Tools and Coordination – Different Layers

MCP and A2A are two open protocols that address different but complementary tasks in the AI agent ecosystem. MCP gives agents "nerves" to access tools (if tools are the model's hands, then MCP is the nerve), while A2A provides "colleagues" for collaboration.

MCP is an open protocol (originally created by Anthropic) that standardizes how LLM applications connect to external data sources and tools. It's built on a "client-server" model. A host application (e.g., an IDE or chat interface) connects via a client to MCP servers, which provide context and capabilities. This is vertical integration – the agent "looks down" at the tools. MCP is optimized for fast, structured requests and responses (request-response).

A2A is horizontal, an open protocol (introduced by Google) that allows autonomous AI agents to communicate with each other, exchange information, and coordinate actions, even if they are built on different frameworks or from different providers. It enables peer-to-peer interaction between agents. Unlike a tool in MCP, a remote agent in A2A is a fully autonomous system with its own model, tools, and reasoning. It can accept a task, ask clarifying questions, work for an extended period, or refuse to perform it.

By the way, it's amusing how AI agents have given new life to classic UNIX utilities – grep, find, cat, sed, and so on.

Orchestration and Sub-agents

And here comes the most interesting part. Multi-agent systems are divided into a centralized model of orchestrator-agents and a decentralized model of agent swarms.

The centralized model became mainstream thanks to Anthropic. In their harness for long autonomous tasks, the final architecture turned out to be three-tiered: planner, generator, evaluator. The idea was borrowed from GANs: the generator creates, the evaluator assesses based on predefined criteria, and the planner decomposes the work into digestible chunks.

However, this architecture is expensive. A three-tiered centralized harness can complete a task to full application in hours, but the bill increases significantly compared to a single agent.

And here, I'd like to make a small digression about choosing models for roles. If you have a planner, generator, and evaluator, it's logical that they don't necessarily have to be the same model. An expensive one for verification and complex design, a medium one for generation, and a fast, cheap one for mass sub-agent calls. Such distribution requires a unified access layer to different models, and here, an OpenAI-compatible gateway like BotHub becomes a practical solution.

The decentralized model looks different. Microsoft Research released Agensh – a harness without a lead agent and without a central orchestrator. Each worker independently picks up a sub-task, shares findings, and merges code into a common Git repository. It scales from one agent to 1024 on ProgramBench, with 16 nodes of 64 agents each. On some tasks, scaling from 1 to 1024 agents increased the final test-pass rate from 33.89% to 55.06%. But scaling gradually ceases to be cost-effective.

Agensh doesn't replace single-agent work but builds upon it. In experiments, GitHub Copilot CLI was used, and Claude Code and other harnesses were connected through a thin adapter. This means decentralization is an attempt to remove a single decision-making point and create a swarm.

Conclusion

Let's start with the obvious: a harness is, after all, a subgenre of system design, one could even say a software product. It has versions, dependencies, regressions, and a lifecycle. Each harness evolves and gains new features, using modern standards and formats, and attempts to rethink classic tools.

Furthermore, it's important to understand that a harness can also degrade, so testing the system is also necessary. Both the system itself and the output of its AI agents. Google, in its developer blog, goes even further and proposes behavioral evals – checking individual observable actions, such as asking a clarifying question for an incomplete prompt, running a validator before declaring work complete, or providing canonical links in documentation.

Now, about security. Skills and MCP reduce vendor lock-in but simultaneously expand the attack surface, and this is not an abstract warning. In 2025–2026, entire classes of attacks were recorded specifically at the harness level, such as malicious instructions hidden in SKILL.md or reference files, injections through MCP tool descriptions, including invisible Unicode characters and ANSI sequences, "rug pulls" where the server substitutes the tool description after authorization, and attacks on tool selection where accuracy drops below 20%. And this doesn't even include the classic feature overload.

It's also worth understanding that you don't need to build your own OpenClaw (ah, it blew up the internet, but now there's no news of it...), because agents should perform one task; it's a real system, a chain with its own costs.
