When a Fast Result is Truly Useful

Sergey Chistyakov has already shared on Habr a similar experience with agent development. In one of our experiments, several Python services were quickly assembled as prototypes to demonstrate a user scenario and test a hypothesis. After receiving feedback, the team adjusted the solution and consciously designed the production version using the target stack with authorization, observability, and other operational requirements.

Here, the inexpensive code worked exactly as a prototype should. It bought knowledge about whether users needed this scenario and what it should look like. The team didn't try to turn the prototype into a production foundation without re-evaluation.

The problem arises when the entire implementation chain is fixed in a specification beforehand and handed over to an agent. New knowledge about the task might emerge only after a significant portion of the solution is already ready. This is when a very fast waterfall occurs. The agent helps to move faster along the chosen path, but doesn't indicate that the path itself needs to be changed.

A Specification is Not Product Knowledge

SDD is useful for an agent. It needs scenarios, examples, constraints, and verification criteria. A simple phrase like "make it beautiful" is not enough. The model will guess the architecture, error format, responsibility boundaries, and user expectations.

However, for some tasks, the team can indeed describe the space of acceptable solutions in advance. These are typically specific, repeatable tasks with a clear subject boundary, formalized rules, and a well-defined validation procedure. In such scenarios, the specification becomes not only a description of intent but also a working contract between the human, the agent, and the verification system.

A team rarely knows everything necessary about a new feature right away.

This is the normal nature of working with uncertainty. The team gradually understands what question should have been asked. But here, it's useful to distinguish two things:

  • The specification for the nearest verifiable step.

  • The specification for the entire future implementation.

The first helps the agent move forward. The second can serve as a guide if the team perceives it as an assumption that still needs to be verified.

How a Fast Result Becomes Expensive

Two stories from colleagues clearly illustrate how a fast result can lead to extra work. In both cases, the team quickly arrived at a working solution, but a critical assumption was verified later than it should have been.

Integration with Compliance Checks

The team read the API documentation for the company's compliance checks and allocated a sprint for integration. The result was a convenient adapter that other teams were already interested in.

In the next sprint, it turned out that the API was an internal tool of the audit team and provided access to raw data. Other teams could not use it. Two sprints of development had to be scrapped along with the new service.

The documentation was detailed and accurate. It answered questions like "how the API works" and "how to connect to it," but not the main question: did the team have the right to use this API in their scenario? A conversation with the integration owners would have been significantly cheaper than the finished service.

Integration with a New 1C Product

Within a sprint, an engineer used AI to set up an integration service with a new 1C product for the team. The code appeared quickly. Another two sprints were spent on negotiations and approvals with legal and security departments.

Questions that couldn't be solved by the speed of writing code required separate time. Could this data be processed, what were the requirements for access, and who should approve the solution?

What These Cases Have in Common

In both stories, AI accelerates code writing but not the verification of assumptions that the solution depends on.

Full specification:

→ implementation chain

→ code, tests, integrations, infrastructure

→ new knowledge about the product, data, or constraints

→ mass rework and re-verification

The faster the team turns an unverified assumption into services, interfaces, tests, integrations, and infrastructure, the more work becomes tied to a solution that hasn't yet proven its viability.

AI can rewrite code cheaply, but system owner permissions, data verification, approvals, and release responsibility remain with the team.

The further the team progresses down one solution path, the more expensive it is to revise.

The Bottleneck is Trust in Change

Writing code was long a noticeable limitation on development speed. An agent dramatically accelerates this stage, but stages remain that don't scale on their own:

  1. Understanding that the correct scenario has been implemented.

  2. Proving that the change hasn't broken adjacent scenarios.

  3. Verifying integrations, data, security, and operational consequences.

  4. Deciding how to safely roll out and roll back the result.

  5. Taking responsibility for the fact that the change can be released.

Code review is an important part of this work. The reviewer reconstructs the intent, evaluates trade-offs, and checks if there are sufficient automated proofs.

When an agent generates more changes than the team can qualitatively review and accept, a queue forms. The bottleneck simply shifts from code generation to verification, approvals, and responsibility acceptance.

DORA links working in small batches with fast feedback loops and notes that this practice amplifies AI's positive impact on product outcomes.

Google also recommends making small changes. They are easier to understand entirely during review and verify without losing context. However, the size of a change isn't just about the number of lines. More important are the number of scenarios and system boundaries affected by the change, and the time a competent person needs to assess the risk. A mechanical migration across hundreds of files might be more understandable than a small billing adjustment.

An Agent in a Narrow, Standardized Task

There's a class of tasks where an agent can confidently handle not just a single code fragment but a sequence of standardized actions. For this, the task must have a clear boundary, a stable input data structure, and explicit rules by which the result can be verified.

Such a case exists in antifraud. The team regularly needs to connect financial and non-financial events to their perimeter. The connection is defined by runtime configuration, which describes the source or flow itself, validation rules, and data transformations.

For this work, the team gave the agent a configuration grammar and rules for its application. The grammar defines permissible constructs. The rules specify how to describe the connection, validation, and transformations. A separate skill then explains to the agent how to use these artifacts in a specific task.

As a result, the agent works not with an abstract request like "connect a new flow," but within a comprehensible language and a set of invariants. It can quickly prepare the configuration, and the team receives a result that is already verified by domain rules and runtime mechanisms.

After implementation, a second agent skill is used to write autotests. It directly formulates how to apply the standard autotest framework, which scenarios need to be covered, and how to use the provided example. The agent quickly generates tests with the coverage needed for such a connection.

Here, the two-step link is particularly important:

configuration grammar and rules
→ connection configuration
→ standard test framework and example
→ autotests
→ result verification by the team and pipeline

This process is now used not only by engineering roles—under the supervision of developers. A person formulates the need within a known scenario, the agent prepares the configuration and tests, and the developer is responsible for correctness, application boundaries, and accepting the change. The practical effect is a noticeable acceleration of standardized work without needing to reassemble the entire implementation context each time.

This example demonstrates the useful meaning of SDD for agent development. A specification can contain not only requirements for a single future feature. It can be the accumulated knowledge of the team: grammar, examples, contracts, test templates, and validation rules. Then, the agent can use the rules and examples accumulated by the team in new tasks of the same type.

A Good AI Pipeline and Task Size

Agents can be given large tasks. A large batch works well if the team has a quick way to verify important assumptions and safely change course.

Signs of a healthy pipeline:

  • There is a user or system signal that will appear quickly.

  • The change can be enabled in a limited way: by flag, for a segment, or in shadow mode.

  • A clear rollback is defined.

  • Automated tests and contracts cover the main invariants.

  • Critical unknowns have been verified: model quality, data availability, API rights, security and compliance requirements.

  • The solution owner who understands the risk is known.

  • The team knows what to do in case of a negative experiment result.

For repeatable operational tasks, a few more signs are added to this list:

  • The space of acceptable solutions is described by a grammar, schema, or set of contracts.

  • There are typical examples that can be used to reconstruct the expected result structure.

  • Validation rules are executable or easily verifiable by a human.

  • It is defined which parts of the work can be performed by a non-engineering role, and which remain the developer's responsibility.

  • The result is integrated into the existing CI/CD process, test environment, or other familiar control mechanism.

In such a pipeline, AI helps to conduct an experiment faster, prepare a standard artifact, or perform operational work reproducibly.

It's not about the number of agents or the size of the diff. The order of steps is important: when the team receives a signal, how it verifies invariants, and at what point it decides to continue, stop, or change course.

What SDD Should Do

A good specification makes the next step verifiable. It does not define the entire implementation path at once.

Before an agent task, it's useful to fix a short card:

Scenario: What user or system case are we verifying?
Boundary: What are we consciously *not* doing in this iteration?
Critical Assumption: What must be true to continue?
External Owners: With whom do we need to confirm rights, data, access, and limitations?
Invariants: What must the change *not* violate?
Verification: What test, metric, demonstration, or log will confirm the result?
Release: How do we enable, observe, and roll back?
Owner: Who makes the decision about the next step?

For a narrow, standardized task, this card can refer to existing artifacts: configuration grammar, data schema, integration contract, example catalog, agent skill, and autotest template. It's not necessary to describe a known process from scratch every time. It's important that its boundaries, invariants, and verification method are visible.

The card does not replace a long document if it is substantively needed. It shows what verification is missing, even if the specification looks neat.

It also helps to ask the questions that formed the basis of the stories above earlier. Do we have the right to use the API, has the model's accuracy been proven on real data, are access and data agreed upon, by what criterion should we continue investing?

And Here We Come Back to XP

This sounds familiar because AI hasn't abolished what makes Extreme Programming work.

XP helped the team learn during implementation through small releases, tests, continuous integration, simple design, refactoring, and constant feedback.

With AI, this ability becomes more valuable. When code can be obtained in minutes, choosing the next hypothesis, verifying the result, understanding the consequences, talking to system owners, and taking responsibility for release become more important.

Pair programming today often looks like "engineer plus agent." The agent prepares the implementation, variations, and test drafts. The engineer maintains context, sets boundaries, notices new circumstances, and decides whether to continue down this path.

In repeatable tasks, this pair can be expanded. A non-engineering role initiates the described scenario and receives a prepared artifact, while the engineer helps configure the rules, checks exceptions, and accepts the final change. The value is not in transferring responsibility to the model, but in transforming accumulated engineering knowledge into an accessible and verifiable process.

XP brings back into the AI pipeline points where the team has the right to change its mind while the cost of the decision is still low.

Conclusion

SDD remains a useful tool. AI agents need specifications. They work best when they initiate a learning cycle, capture accumulated rules, and help make the next step verifiable.

A "very fast waterfall" occurs when a team turns an initial hypothesis into a broad layer of code, tests, and infrastructure before they have had a chance to verify it.

The agent approach is particularly useful where the team already knows how to accurately describe task boundaries and result verification rules. In such tasks, the agent accelerates not just code writing. It allows more people to connect to an already described process, without removing developer verification and responsibility.

Value is created by those who quickly turn the code that the agent can already write into a change they can confidently be responsible for.
