A quality product only gains real value when people start using it. SaaS, a browser tool, or a mobile app needs a clear page, a path to a target action, and a way to attract people. For a product relying on organic search, a separate job begins: understanding queries, studying search results, preparing content, implementing it, and observing the outcome. AI helps at each of these stages, but between them remains the developer who transfers answers, refines tasks, verifies proposed paths against the project, requests text rewrites, and passes the result to an agent that modifies code.

This year, I tried to automate this work as much as possible. The result was three sequential approaches: a custom YAML orchestrator, an external workflow on Dify with Tavily, and an office of AI employees with distributed responsibility. SEO remained the task for which the orchestration setup was progressively changed.

First Approach: Describe the Process and Execute It

Orchestrix began as a local Django service. An external architectural chat generated a YAML file with steps, roles, instructions, and rules for data transfer. The service imported the description into a database, displayed it in the Django admin, and sequentially executed steps via the OpenAI Agents SDK.

For an SEO page, the chain included research, specification, JSON generation, language processing, review, correction, integration plan, and a final task for Codex. Each of the eight steps received a separate task and passed the result to the next.

Each step had its own contract. Below is a shortened fragment of the original YAML for the research role.

  slug: research
  title: Research
  order: 1
  agent_role: seo_researcher
  agent_instructions: |
    You create a compact SEO research brief for one page topic.
    Return markdown only.
    Do not generate SEO JSON. Do not write final page copy.
    Do not claim competitor pages were read unless fetched text is provided.

The instructions separated research from page writing. The description also included facts about the target project, such as the framework, actual routes, and content location. This is necessary because a specified file path might not be relevant to a particular repository.

The model call itself took a few lines. Below is a fragment without error handling or cost tracking.

agent = Agent(
    name=pipeline_step.agent_role,
    instructions=pipeline_step.agent_instructions,
    model=run.pipeline_instance.default_model,
)
result = Runner.run_sync(agent, prompt_text)

Infrastructure had to be built around this call: process instances, steps, runs, states, artifacts, and token usage records. Results were saved in the database and files. It was possible to view intermediate responses and re-run specific steps. Re-running deleted saved results for that step and subsequent ones to avoid artifacts from an old input version in the chain.

Saved results showed what task the model received and what it passed on. However, automation ended at the Codex Handoff preparation. Frontend implementation remained a separate task, the success of which depended on the completeness of the final task and the accuracy of project information.

This SEO example lacked live search, SERP analysis, and competitor text extraction. The chain could process provided context but did not gather fresh market data itself. Significant effort seemed necessary to implement a custom executor. It would require developing checks, result corrections, and integration, and the service itself needed separate maintenance. In the next attempt, I moved this infrastructure to a ready-made platform.

Second Approach: Externalize Workflow and Connect Sources

In Dify, the process was assembled from LLM nodes, code nodes, and external tools. Tavily added search and page extraction. A distinct stage for working with sources emerged between the future page topic and content generation.

First, the model generated research queries. Then, the search returned materials, a separate step selected sources, the tool extracted their content, and the next role analyzed the obtained texts. Only after this were the user intent map, entities, page specification, and SEO JSON constructed.

In the high-level workflow diagram, node names are grouped into semantic blocks.

Research queries
→ Tavily search → source selection → page extraction
→ source analysis → intent map → specification
→ SEO JSON → validation → correction → review
→ final processing → validation → output package
