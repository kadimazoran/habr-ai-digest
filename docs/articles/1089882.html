From Note to PDF: Why Another Application?

In the previous article, I discussed local RAG on Markdown and TXT: splitting text into chunks, embeddings, cosine similarity, several found pieces, and the model's answer. The source there is a range of lines. For a learning project, this is convenient. Open the file – and you can visually verify the address.

PDF is structured differently. It has pages, not lines in the usual sense. Extracted text may not match what a person sees on the screen: columns appear in an unexpected order, a table loses its structure, a caption ends up far from the image. Verifying the answer based solely on the extracted line is risky. A page as an image is needed. Nearby – a text layer to understand what the program saw.

The second difference is search. Instead of its own chunking and vector index, I used the PageIndex SDK local mode. In this scheme, PageIndex builds a tree-like index of the PDF and conducts agent-based search within the document. This is not a "fully local neural network." The index and files are local; model computations may be performed via an external API. Misrepresenting these concepts will spoil both the architectural solution and user expectations.

The scope is intentionally narrow. One user, one Streamlit process, one active PDF. The upper limit is 25 MiB and 500 pages. A readable text layer is required. No OCR. The application won't magically turn a scan from images into text.

The Path of a Single Question

The complete workflow:

Browser  │  ├─ API address + two models + key  │        └─ check: regular response + ping tool call  │  ├─ PDF upload  │        └─ PDFium: format, size, page count, text layer  │                 └─ PageIndex local: index in data/items/<fingerprint>/index/  │                          └─ active.json: active document  │  └─ question           └─ PageIndex chat → response + source tags                    └─ check doc_id and page number                             ├─ response text                             └─ source button → PDFium → page image

The code is split into three files. app.py contains the interface and operation script. reader.py handles PDFium, PageIndex, and response validation rules. storage.py is responsible for local paths, document fingerprinting, and atomic manifest writing.

Who trusts whom? The browser sends bytes and settings. The model returns text and links in its own format. Neither of these inputs becomes correct on its own. Therefore, the PDF is validated before indexing, the index profile before the query, and the source before the button is created.

Launching

You need Python 3.11 or newer, Git, and access to an OpenAI-compatible POST /chat/completions endpoint. The response model must support tool calls; otherwise, PageIndex cannot complete the workflow. The project uses PageIndex 0.2.22, Streamlit 1.64.0, pypdfium2 5.13.0, and PyPDF2 3.0.1.

On macOS and Linux:

git clone https://github.com/balyakin/pdf-desk.gitcd pdf-deskpython3.12 -m venv .venv.venv/bin/python -m pip install -r requirements.txt.venv/bin/python tests/make_demo_pdf.py.venv/bin/python -m streamlit run app.py --server.address 127.0.0.1 --server.port 8502

If you don't have python3.12, use your installed python3 version 3.11 or higher. For Windows, the commands are in the README.

The script will create data/demo-manual.pdf: three pages with warranty, its termination conditions, and support hours. The price is not mentioned. This is a small control document, not a search quality benchmark.

Open http://127.0.0.1:8502. In the sidebar, enter the API address ending in /v1, the model for indexing, the model for responses, and your key. For the tested DeepSeek setup, both models are deepseek-flash, and the address is https://api.deepseek.com/v1. Model names depend on the provider; do not mechanically transfer them to another subscription. External requests may incur costs.

The "Check Connection" button is worth pausing at. It does more than it seems.

Connection Check: Two Short Requests Instead of a Pretty Model List

Many applications call GET /models and consider the task complete. A list of models is useful. It doesn't guarantee that the selected model responds to requests or calls tools. Our chain needs both capabilities.

The first request goes to the document indexing model. The application asks for a short, plain response and checks that the content field contains a non-empty string. The second request goes to the response model: it's given the ping function without parameters and asked to call it. The tool name and JSON arguments are checked. The ping function does nothing with the PDF. Its purpose is to quickly catch an incompatible API before sending the document text.

The simplified validation structure from reader.check_connection():

ordinary = request({    "model": settings["index_model"],    "messages": [{"role": "user", "content": "Respond in one word: done."}],    "stream": False,    "max_tokens": 128,})probe = request({    "model": settings["chat_model"],    "messages": [{"role": "user", "content": "Call the ping tool to test." }],    "tools": [{        "type": "function",        "function": {            "name": "ping",            "description": "Safe connection check, no arguments needed.",            "parameters": {                "type": "object",                "properties": {},                "additionalProperties": False,            },        },    }],    "tool_choice": "auto",    "stream": False,    "max_tokens": 128,})

This checks the compatibility of a specific "model + address" pair, not a guarantee of successful indexing for any PDF. The timeout for trial HTTP requests is 15 seconds. The size of the read response is limited to approximately 1 MiB. Redirects are prohibited: if the address points to a redirect, the application requests the final URL. Only HTTPS is allowed for external servers; HTTP is permitted for localhost, 127.0.0.1, and ::1. URLs with credentials, query parameters, or fragments are not accepted.

There's a subtlety with Streamlit. The settings fields live outside the form: changing any of them triggers a redraw and resets the successful check status. You cannot check one key, then seamlessly replace it with another, and continue indexing under the old green indicator. The saved settings.json contains the address and model names, without the key. The key is only in the current session state.

The connection check itself does not touch the document. Text is sent to the provider only after a separate "Prepare Document" click.

PDF Validation: An Extended Name Still Tells Us Nothing

The Streamlit uploader limits files to 25 MiB and accepts .pdf. The server doesn't stop there. inspect_pdf() repeats essential checks: byte size, non-empty file, extension, ability to open the file with PDFium, page count from 1 to 500. For each page, PDFium extracts text and counts non-whitespace characters.

If the entire document has fewer than 20 such characters, the application stops with a message about the lack of readable text. Individual empty pages do not halt preparation, but the user receives a warning: they won't become a solid basis for text search.

For password-protected PDFs, there's a separate message. For an arbitrary byte sequence with a .pdf extension – rejection before calling PageIndex. It's not just about convenience. The external API should not receive garbage data after a superficial file name check.

PDFium is also needed at the end of the chain. When the user selects a page, read_page() opens the saved original PDF, retrieves the text layer, and renders the page into an image. The scaling factor is calculated from at least 2.0 and 1600 / max(width, height). This prevents the long side of the render from growing indefinitely. Human page numbering starts from 1; the page index in PDFium starts from 0. The code explicitly handles this conversion.

Why show both the image and the text? The image answers the question "What is written on the page?" The extracted text helps understand what went into the machine pipeline. The difference between them is a separate class of errors, especially with tables and complex layouts.

What Exactly Does PageIndex Do in This Application?

PageIndex describes itself as vectorless, reasoning-based RAG: a structural document index and model-based search without a mandatory vector database. In local mode, the SDK accepts a PDF, builds an index on disk, and provides methods for conversing with the document. "Local mode" here refers to where the index is stored and the SDK is executed. If DeepSeek is specified in its backend, DeepSeek performs model calls. PDF Desk files are not uploaded to PageIndex Cloud, but the document text is sent to the selected model API. For privacy, the boundary lies precisely here.

The client configuration in reader.make_client() has two independent parts:

backend = {    "base_url": settings["base_url"],    "api_key": settings["api_key"],    "timeout": 60.0,    "max_retries": 0,}client = PageIndexClient(    mode="local",    index={        "model": "openai/" + settings["index_model"],        "storage_path": str(storage_path),        "backend": dict(backend),    },    chat={        "model": "openai/" + settings["chat_model"],        "backend": dict(backend),    },    instructions="Respond in Russian based only on the selected document. ...",)

The openai/ prefix is a way for the SDK to route to an OpenAI-compatible backend. The original model name entered by the user is sent in the request to the selected API. The index and chat settings can point to different models, although the address and key are common in this version. There are no retries at the backend level: max_retries=0. An error should not be masked by a long, implicit series of calls.

During the first preparation, submit_document() indexes the PDF. In local mode, the operation is synchronous: after it, the application checks get_document(), the completed status, and the pageNum. Without these three conditions, a new document does not become active.

Indexing large documents is a separate story. Time and costs depend on the number of pages, PDF structure, model, and pricing. For the three-page example, everything worked out. The cost for a 400-page contract is not implied by this. We did not measure it.

Why There's No Custom Vector Search Here

In local-docs-ai, the search is intentionally transparent: text is split into chunks, embeddings are generated for each, and cosine similarity with the query is calculated. You can open the JSON index and see every vector. You can reproduce the ranking in ten lines of Python. Such transparency is valuable for learning.

A long PDF has a different cost of error. Imagine a 300-page manual: the word "warranty" appears in the table of contents, in the contract example, in the exceptions section, and in the appendix. The similarity of a small fragment to the query doesn't explain which section answers it. A structural index can use headings, page ranges, and document part descriptions for navigation. This is precisely the work I handed over to PageIndex, instead of building my own PDF parsing, fragment overlaps, and candidate selection heuristics.

This choice has a downside. PageIndex's behavior is harder to verify with a single arithmetic function. Indexing calls the model; SDK versions and the indexing model become part of reproducibility. If the answer is incorrect, you need to distinguish at least three situations: the required text is not in the extracted layer; the index or search did not guide the agent to the correct location; the model saw the location but misrepresented it. A single "show source" button helps with the last situation. It does not reveal all internal search steps.

And one more thing. "Without a vector database" does not mean "without state." The tree and auxiliary data are stored in data/items/.../index. They need to be linked to a specific PDF and model profile, survive interrupted writes, and be verified on the next launch. The code for this doesn't disappear; it's just different – not what revolves around an embedding model.

Index Fingerprint: One PDF Can Mean Different Data

A user uploads a file, builds an index, then changes the indexing model. The PDF is the same. Can the old index be reused? It's on disk. Conceptually, it's the result of a different profile, and silent reuse would be deceptive.

PDF Desk constructs the item_id from the SHA-256 hash of the PDF bytes, the API address, the index model name, and the PageIndex SDK version. These values are serialized into JSON with a stable key order, then hashed again. Schematically:

profile = {    "pdf_sha256": hashlib.sha256(data).hexdigest(),    "base_url": validate_base_url(base_url),    "index_model": index_model,    "sdk_version": sdk_version,}item_id = hashlib.sha256(    json.dumps(profile, sort_keys=True, ensure_ascii=False).encode("utf-8") ).hexdigest()

The fingerprint does not include the response model. This is intentional. Changing the chat_model alters generation and requires re-checking the connection, but it doesn't change the already built document structure. If you change the index_model or address, a new index is needed. If you only change the response model, the existing index can be reused.

The API key is also not included in the fingerprint. It should never be saved in the manifest. When querying, the application still compares the current index profile with the saved one, and the user must have a verified connection in the current session.

On disk, the structure looks like this:

data/    ├── settings.json    ├── active.json    └── items/        └── <item_id>/            ├── source.pdf            └── index/

active.json is a short manifest: schema version, ID, display name, sdk_doc_id, page count, and index profile. The display name doesn't become the file path. The original file is always named source.pdf inside the verified folder with a 64-character hex name.

Before using a saved document, load_active() checks the JSON form, profile, PDF existence, size limit, and fingerprint match with file bytes. If the data is corrupted, the application reports an error but does not silently delete the folder.

How to Replace the Active Document Without Losing the Old One

File system operations complicate even small projects. Writing a new active.json can be a single operation. Preparing the PDF and index is not. If the model interrupts indexing midway, the link to the previous document must remain functional.

Therefore, the sequence of actions is as follows:

  1. Validate the new PDF and settings.

  2. Calculate the new index folder path.

  3. Save the source PDF and build the PageIndex index.

  4. Ensure the SDK sees the document as completed and the page count matches.

  5. Only then, atomically replace active.json.

  6. After successful replacement, attempt to delete the previous document's folder.

The manifest is written to a temporary file in the same folder: JSON, flush, fsync, then os.replace. This protects the main JSON from partial writes during a normal process crash. The ability to read the old index in case of a new preparation failure is checked by a test. Temporary folder remnants are handled separately; active data is not deleted during a failed rollback.

There's also the "same PDF again" scenario. If the profile and bytes match, the program checks for an existing index and uses it. A repeated query or page navigation should not trigger re-indexing.

All this operates within a single process. threading.Lock prevents two operations from different tabs from simultaneously modifying the shared data/ folder. Two separate application instances with a shared folder will not synchronize using this lock. A multi-user service would require a different storage and locking architecture.

Response and Sources: Where Trust Ends

After preparation, app.answer_question() compares the active item_id and index profile, then calls reader.ask_pdf(). The query is limited to 2000 characters and cannot consist solely of spaces. The SDK receives the doc_id, includes citations=True, and returns raw text. Citations are extracted from PageIndex, after which the application validates each one.

The criteria are simple but necessary:

  • The citation's doc_id must match the active document;

  • page must be an integer, from 1 to the PDF's page count;

  • repeated references to the same page are removed.

A tag with a different page or document will not become a button. If the SDK discarded an invalid number before passing citations, the application additionally scans the raw response for tags and displays a warning. If there are no verifiable sources, the response remains text but receives a prominent message: it cannot be used without verification.

Citation tags are removed from the displayed text. During a live test, a small but visible error was found here: after removing the tag, a space remained before the period. clean_answer() now normalizes spaces before punctuation. It might seem like cosmetic work. In reality, it's a good indicator: the SDK, generation, and display chain was tested with a real response, not just a placeholder.

The strictest limitation remains. Checking doc_id and page proves that the link points to an existing page of the current document. It does not prove that this page contains every assertion in the response. The model might misrepresent a correct source. Therefore, the interface opens the original page next to the answer, rather than displaying "confidence 99%."
