Trusting an AI Agent with Your Server and Sleeping Soundly Without SSH

We are moving faster towards self-healing infrastructure. But when an incident does happen, it can take engineers a lot of time to gather information about server status. With 99.99% SLA, there are about 4 minutes left per month for downtime, every minute counts, and not automating this part of incident analysis is an unaffordable luxury. Technically, this can be done now: give the AI agent SSH and sudo. I decided to go a different way and built the Linux MCP daemon (mcpd): a server initially designed for AI agents. Instead of wrappers around standard utilities, it reads system status directly from the kernel and provides it to the agent through tools - there are currently 38 of them, and the list is growing. When root is needed, the agent can request it, but will only get it where you allow it, and within specified boundaries. The linuxctl utility in the style of kubectl turned out to be a separate interesting solution. Under the cut is the architecture, installation, connecting an AI agent, and permissions that only look safe. Read on.

When analyzing incidents, I increasingly use an AI agent: it quickly gathers information about the server — load, memory, disks, processes, logs — and correlates it with monitoring data to understand why the site is slow, what's filling the disk, or what crashed overnight. Based on its findings, I can ask the agent to solve the problem, which might require restarting a service, changing a config, or even kernel settings. Giving it SSH with sudo is not the safest path. I wanted to try a different approach. Let's see what came of it.

I wanted the agent to see the server through a set of understandable tools, get root only for what I allowed, and have every step recorded. And due to my great love for Kubernetes and its object model, I wanted to manage the operating system in the same way: represent it as a tree of objects — processes, disks, services, files — and work with them using familiar commands like get and describe. For this, I created the linuxctl utility. Thus, linux-mcp-daemon was born — the mcpd daemon and the linuxctl client. In this article, I will explain how it works, how to install it in a couple of minutes and connect an AI agent, and what pitfalls I stumbled upon along the way.

Existing Solutions and Their Problems

Before writing my own, I looked at what had already been done. The protocol for connecting tools to AI agents is MCP (Model Context Protocol), and there are plenty of Linux servers for it. They can be broadly divided into three types:

  • Remote shell with MCP sauce. For example, ssh-mcp and dozens of its forks: a "execute command" tool plus a whitelist. The problem is that the list usually only checks the first word of the command, and the command goes into sh -c, so ls; rm -rf ~ passes. The most thoughtful options like t11z's fork classify commands, ask for confirmation, and keep an audit log, but fundamentally it's still text command parsing. In essence, it's the same SSH, just with an illusion of control.

  • Read-only. For example, Red Hat's linux-mcp-server: dozens of diagnostic tools, including on remote hosts via SSH. It's safe, but you can't do anything, only look, and host access is still granted via SSH keys for the entire account.

  • Direct SSH. The agent gets everything the account can, and with sudo — even root.

None of the options I found met my needs. I want to build systems where an AI agent, knowing the service architecture, can independently gather information from all servers involved in an incident. This requires network access with authentication, not a local process on each machine, as well as user separation and root privileges granted through a single tool.

MCP in Brief

MCP is an open protocol over JSON-RPC. The agent connects to the server and asks what it can do. Two types of capabilities are important to us:

  • Tools — functions that the model calls itself when it deems necessary. Each has a name, description, and JSON schema for arguments. In the specification, they are called model-controlled. mcpd currently has 38 of them: processes/top, services/manage, files/read, and others.

  • Resources — data with a URI address that the application connects to the context, not the model (application-controlled). mcpd has 11 persistent resources (os://release, network://routes, devices://pci…) and 6 templates: service://{name}/status, file:///{path}, process://{pid}/{target}, etc.

There are two transports. With stdio, the client itself launches the server as a child process. Over HTTP, the server runs separately, and the client connects to it. mcpd is network-based: it runs on the server, and the agent connects to it via HTTPS.

The difference is not formal. In April, OX Security showed how dangerous stdio is: the client executes a command from its config to launch the server — and it will execute it, even if it's not the server but anything else. It's enough to substitute the config, and malicious code will run on the developer's machine. There's a flaw in all official SDKs, and Anthropic refused to fix the protocol. mcpd doesn't have this problem: the client doesn't launch anything on its own, and official SDKs are not used. The researchers' main advice — to run MCP processes in isolation and with minimal privileges — is implemented by default in mcpd.

How mcpd Works

The daemon is written in Go; it's a single static binary. Tools instead of shell. The agent doesn't execute commands; it calls tools with understandable names like group/command: processes/top, disks/usage, logs/journal-control, services/manage, files/read, and others; currently, there are 38 of them. For each tool, the server provides a description and a JSON schema for arguments, so the agent itself understands what the server can do.

Kernel-first. mcpd reads most data itself — from /proc, /sys, and systemd via D-Bus — rather than running ps, df, or systemctl and parsing their output. External programs are called only where a custom implementation would be worse: smartctl, traceroute, journalctl, dmesg, last, and find. For example, the systemd journal is stored in a binary format with compression, and a libsystemd library would require cgo and deprive us of a static binary. All of them are executed without a shell, with separate arguments.

Each call is a separate process under the user's name. The main mcpd process only accepts requests, checks the token, and verifies permissions. It doesn't execute the tool itself: for each call, a new short-lived process (worker) is launched under the Linux user with the same name as the mcpd user. The worker executes one command, returns the result, and terminates. User alice in mcpd corresponds to the alice account in Linux: what the kernel prohibits for them, the agent cannot do.

Root — per tool and with boundaries. In the mcp-sudo.yaml file, for each user, it's listed which tools they can call with privileged: true, meaning as root. And not just "can," but within what limits:

users: 
  logs:
    privileged:
      tools:
        files/read:
          allowed: true
          paths: [/var/log]        # root only within /var/log
        logs/journal-control:
          allowed: true
        network/curl:
          network:
            deny_private: true     # no localhost, 10/8, 169.254.169.254

For tools with paths, paths is mandatory: without it, the config won't load. If you want the whole disk, explicitly write paths: ["/"] so it's visible. If root is not granted, mcpd responds like this:

$ linuxctl tool files/read --path /root/.bashrc --privileged true
user mcp is not authorized to run files/read on path /root/.bashrc as root

TLS by default. On first launch, mcpd generates a self-signed certificate, and clients trust it by its fingerprint. An open HTTP option exists in the config but is disabled.

Everything is logged. Every call is written to the daemon's log (journald or docker logs): user, tool, arguments (secrets like tokens are redacted), and the result of the call. Calls that modify the system are marked audit and logged at any logging level.

My Test Environments

Everything below was tested on three installations simultaneously:

  • local Kubernetes in Docker Desktop on Mac — the main development environment;

  • VPS with Ubuntu 24.04 (1 CPU, 2 GB): mcpd via systemd;

  • the same VPS: mcpd in a Docker container on a neighboring port.

A change was considered ready only when it was deployed to all three and tested live. Several bugs only appeared on one of the setups.

Installation

On a server with systemd, it's a single command:

curl -fsSL https://raw.githubusercontent.com/nucleusv/linux-mcp-daemon/main/scripts/install.sh | sudo bash

The script downloads the release, checks sha256, creates configs without any users, sets up the first user mcp, and prints their token (once — only the salted hash is stored in the config) and the certificate fingerprint. There are also .deb/.rpm packages and a ghcr.io/nucleusv/linux-mcp-daemon image.

We verify from any machine with linuxctl installed (it's also available for macOS):

export MCP_SERVER=https://my-server:9091
export MCP_TLS_FINGERPRINT=sha256:...   # from install.sh output
export MCP_TOKEN=...
linuxctl get system os-release

OS Release Info:
PRETTY_NAME="Ubuntu 24.04 LTS"
...
Kernel Info:
Linux my-server 6.8.0-142-generic #142-Ubuntu SMP PREEMPT_DYNAMIC Wed Sep  2 14:24:27 UTC 2026 x86_64

linuxctl is a client in the spirit of kubectl: get, describe, create, update, delete over tool groups. It doesn't store the command list but reads the schema from the daemon each time, so a new tool on the server is immediately available in the client. explain shows which commands are available for a group and what they translate to (descriptions are shortened):

$ linuxctl explain disks
  get              -> tool disks/list
  get free         -> tool disks/free
  get usage        -> tool disks/usage
  get mounts       -> tool disks/mounts
  get partitions   -> tool disks/partitions
  get performance  -> tool disks/performance
  get health       -> tool disks/health
  describe <name>  -> template disks://{name}/stats

$ linuxctl get processes --sort_by mem --limit 3 --output table
PID   USER   COMM              STATE   PPID   RSS_BYTES   CMDLINE
967   root   dockerd           S       1      107339776   /usr/bin/dockerd -H fd:// --containerd=/run/containerd/containerd.sock
274   root   systemd-journal   S       1      65556480    /usr/lib/systemd/systemd-journald
813   root   containerd        S       1      63471616    /usr/bin/containerd

There is autocompletion for bash and zsh: Tab completes verbs, groups, flags for a specific tool, and even resource URIs like network://interfaces. Hints are also taken from the daemon, so each user sees only what they are allowed. How to enable it is described in the documentation.

$ linuxctl get disks <Tab>
free  health  mounts  partitions  performance  usage

Connecting the Agent

For Claude Code, it's enough:

export NODE_EXTRA_CA_CERTS=~/.config/mcpd/my-server.crt   # certificate from the server
claude mcp add --transport sse my-server https://my-server:9091/sse \
  --header "Authorization: Bearer <token>"

After this, the agent sees the server's tools and decides for itself which ones to use. Here's what it gets, for example, from processes/top (real output from the VPS):

top - 17:15:34 up 23:51,  1 user,  load average: 0.15, 0.06, 0.01
Tasks: 114 total,   1 running, 113 sleeping,   0 stopped,   0 zombie
%Cpu(s):  1.0 us,  1.9 sy,  0.0 ni, 96.1 id,  0.0 wa,  0.0 hi,  0.0 si,  1.0 st
B Mem : 2063577088 total, 509673472 free, 305860608 used, 1248043008 buff/cache
B Swap: 536866816 total, 536592384 free, 274432 used. 1552297984 avail Mem

    PID USER      PR  NI         VIRT         RES         SHR S  %CPU  %MEM     TIME+ COMMAND
  66914 mcp       20   0   1297649664    10428416     6569984 R   2.0   0.5   0:00.03 mcpd

This is not a call to top: everything is read from /proc, and %CPU is calculated the same way top does — by two measurements with an interval. Sizes are in bytes by default, so the agent doesn't have to parse 1.8G; for humans, there's human_readable. In the last line, you can see the worker process for this call: the mcpd process, started by the mcp user.

How an AI Analyzes an Incident

To test all this not just in words, I simulated a training incident on a test VPS: the my-service service writes a debug log without rotation, and it constantly grows. For the agent, I created a separate mcpd user agent. Root privileges were granted for exactly one action: files/update for /var/log/my-service.log. Everything else it does from its unprivileged account. Then, a normal conversation in Claude Desktop connected to mcpd.

In a couple of minutes, the agent made 20 calls: free space, directory sizes, log list, tail and head of the growing file, journal settings, processes, service code. Two calls were marked with a cross, and both are telling. For disks_usage with privileged: true, the agent requested root, and mcpd denied it: the user didn't have such permission. The agent didn't insist and continued without root. The systemd journal was not accessible due to the kernel: the agent user is not in the systemd-journal group.

The agent found the culprit, calculated the growth rate, honestly stated what it couldn't see without root, and didn't try to change anything without permission. Most importantly, it suggested cleaning the log itself rather than deleting it: the service keeps the file open, and after rm, the space wouldn't be freed anyway.

Permissions That Only Look Safe

The most important page in the documentation is not about installation, but about risks. Some permissions seem narrow but actually grant the agent full root privileges:

  • Writing to /etc (files/update with paths covering it). The agent can add itself to /etc/sudoers.d/, schedule a cron job, or create a systemd unit that will run as root.

  • Service management (services/manage). The permission applies to any unit, not just a specific one: the agent can stop ssh or mcpd itself.

  • Writing kernel parameters (kernel/system-control without a write_keys list). Via kernel.core_pattern, you can specify a program that the kernel will launch as root when any process crashes.

  • Reading the entire disk (files/read with paths: ["/"]). This includes password hashes from /etc/shadow and the private key of mcpd's own certificate.

  • The docker group for the OS agent account. This grants root privileges without any grants in mcpd: it's enough to launch a container with / mounted.
