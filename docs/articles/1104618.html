PROLOGUE

From Personal Practice to Corporate Implementation

At that point, I was already using agents in my own work: connecting different models, organizing mutual checks, accumulating experience between sessions. I had experience implementing corporate systems, so training and support were not new to me.

Now I had to assemble an analyst's workbench that would provide a different speed of creating software documentation. Along with the tools, I had to transfer the way of working: how to set a task, check the result, get help, and save the found solution for others.

As implementation progressed, roles and skills were added: canon owner, update releases, messenger support, and several memory levels. In the article, I will explain what problems required these solutions and what had to be reconsidered along the way.

Battle Test: Business Requirements Package Under a Deadline

The canon passed its battle test before it became a finished product. An analyst needed to deliver a business requirements package for a new payment product to the client: regulatory sources had been updated, and the work had to be done in parallel with other tasks. According to the analyst's own assessment, doing this manually would have taken more than two weeks — and there wasn't that much time.

We quickly assembled a minimally viable package: a business requirements template, roles, skills, and tools. For a week, I worked as the analyst's co-pilot: observing where the agent stumbled and correcting the canon directly for the task. The main effort was not in generating text, but in establishing trust in it: what template to use for the document, where to get the data, how to find conflicts and missing data, what to do if data was insufficient. Only after that did the agent stop filling in the gaps with guesses.

During this task, the agent started inventing data, and instructions alone were not enough: I lowered the temperature to 0.2 and top-p to 0.85. Other specialists on different tasks found a temperature of 0.6 with the same top-p sufficient. Generation parameters need to be selected based on the task type, but the main protection remains the sources, rules for handling missing data, and result verification.

We started the work on one model, but the subscription limit was insufficient for the entire volume, so we continued on another provider's model and returned to the first one after the limit was updated. The scheme was devised on the fly: the package had to be delivered on time, and the expensive connection was a solution under pressure of circumstances, not a recommendation for continuous work.

Each document was reviewed by the analyst who worked with the agent: acceptance remained their responsibility. I transferred their remarks into the instructions so that errors would not be repeated in subsequent documents. At the webinar, the analyst herself recalled the pace of work: "fourteen items... in eight working days. I don't know if that's fast or not." Later, for delivery to the client, the package grew to 17 business requirements: each document was reviewed and published in Confluence.

The main outcome of this race was not just the package. The canon, having withstood a real deadline, became a proven tool: subsequent specialists connected to already tested roles and rules, and their mistakes continued to improve the canon.

What I Brought to This Task

By then, I already had experience in developing and implementing ERP, integrating corporate systems, and managing development. I was accustomed to dividing work between departments: where data comes from, who makes decisions, to whom the result is transferred, and where rework occurs.

I learned classic development methodologies through practice: Agile with decomposition into sprints and user stories, Waterfall with phased gateways, task management in Jira. These are not textbook terms for me — I know how to break down a large task into short iterations with clear acceptance criteria, how to conduct planning and retrospectives, and where the chosen approach breaks down and why.

Later, AI implementation projects and my own experience working with agents were added to this.

In my own workspace, I used various applications and models, assigned agents to develop, research, and check each other's results. Gradually, my own roles, skills, tools, and memory between sessions emerged. Thanks to these developments, I approached the task of automating analysts' work with a set of solutions that I could apply and develop.

However, much of my personal practice depended on my involvement. When I set a task, I noticed the agent going in the wrong direction. I had to explain the error, decide when to connect another model, and when to stop another round of checks. Some rules were written down, while others I added as needed each time.

From personal experience, I understood that the quality of interaction with an agent begins with task setting and feedback. For a specialist's workbench, I wanted to go further — to ensure that a successful solution or a corrected error did not remain within a single conversation but was converted into the agent's experience, which it remembers and considers when generating conclusions.

This led to the task of creating a common work foundation: defining agent roles, establishing task execution methods, connecting tools, and organizing experience storage. The entry barrier for an analyst should not be a prompt engineering course, but a few connection steps: then they focus on the content of the documentation, and the entire framework and agent operating rules are handled by the canon.

Thus, I began to build a corporate standard for the analyst's workbench.

How I Assembled the Workbench Canon

Canon and Project Structure

The working title for the pilot was “Golden Standard”: a set of roles, skills, tools, and agent operating rules common to the entire department. Subsequently, this set came to be called simply “Canon”. It was intended to work independently of the project and free the specialist from self-configuring the workbench.

Preparation involved a few simple steps and a couple of prompts to the agent: give a command, go have coffee, and upon return, you get a ready-to-use workbench: the environment is deployed, dependencies and necessary libraries are installed, roles, skills, and tools are in place — you can immediately take on a task. Along with the framework, I introduced a unified standard for project directory and file structure so that specialists and agents could navigate materials according to common rules.

Initially, I proposed a simplified project structure with three layers: source data, working drafts, and released artifacts. This separated analysis materials from work results and assigned clear storage locations for the agent.

When colleagues-analysts joined the work, their practices and feedback influenced my choice of structure. An agent rarely produces a suitable result on the first try: a document goes through several iterations, remarks appear, source data is refined, and assembly is repeated. The project structure had to support this process.

We arrived at separate sections by document type and working directories for specific documents within them. The working text in Markdown and its assemblies in DOCX are stored side-by-side in subdirectories md/ and docx/. I established an explicit contract: all these materials are by default drafts. A successful file assembly does not change its status by itself.

For the approved release package, we allocated a separate directory. This contains verified and approved versions of documents. Thus, the current package can be downloaded and maintained as a whole, maintaining a single source of truth, without needing to assemble the required versions from working directories each time.
