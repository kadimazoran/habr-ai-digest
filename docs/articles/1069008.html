The Basics of Transformers and Why MoE Became a Breakthrough

Let's recall the origins: a standard transformer model consists of layers. Each layer contains matrices of numbers. The total count of these numbers across the entire model equals the number of parameters. Previously, more was considered better. A model receives some context as input, for example: "Hello! You are an engineer, complete the sentence that starts with the word 'peak'." The query travels through all 96 layers of the model and becomes part of the conversation context, landing in the model's 'notebook' – the KV cache. An important clarification: it's not the words themselves that are cached, but rather the model's computed representations of them.

And then the interesting process begins. The model doesn't blurt out the answer immediately but constructs it word by word (or rather, token by token), gradually passing it through ALL layers and refining the answer at each one. How does this refinement happen? Within each layer, there are two fundamentally different mechanisms:

  1. Attention – this is like an ADHD secretary. Small (about 1/3 of the parameters), it constantly checks the notebook, understands the input context, adds its own representations of what it deems correct, and passes them on. It does this 96 times!

  2. Feed-Forward Network (FFN) – this is, roughly speaking, a template repository. It's large (2/3 of the parameters) but useful. This part knows about peak load, peak power, peak rate, and even peak performance, but it can't look around; it can only multiply numbers received from the previous layer without knowing the conversation's context.

In the case of our sentence, during the answer generation process in the early layers, a filtering occurs: "Hold on, we're not talking about literature or cards, so it's either load or power, the later layers will figure it out." Then, another refinement happens: "Excuse me, but what rate? There's no mention of games or the stock market here."

…And so on, until the user sees, for example: "Hello! Here is your answer: the peak load on the system exceeds the nominal value."

But let's look at the economics of this answer. The word "load" cost us a full pass through all 96 blocks and all 175 billion parameters. All matrices, including knowledge of medicine, law, and Silver Age poetry, were involved in calculating a technical term. And this is for every word in the answer: approximately two operations per model parameter, with no discounts for simplicity. By the way, you paid as much for the word "hello" as you did for the word you were initially interested in.

Developers of the Mixture-of-Experts architecture thought: why should we engage the entire FFN repository on every layer if we can split this "fat" part of the model into dozens of small "experts," so that each token only activates a couple of them? The others don't disappear, but we only pay computation costs for those involved in the answer.

This is how it came to be that the number of parameters for MoE architecture networks is now denoted by a double figure: the total number of parameters represents what the model knows, and the active number represents the computational cost. For Qwen 3.5, it's 397 billion parameters of knowledge at the cost of 17B, and for Kimi K2.5 – a trillion at the cost of 32B.

For the end-user, this means that the same computation quality is achieved approximately seven times faster – this is the value demonstrated in the work by Google researchers. Since the release of this paper, it became clear that MoE is the future of architectures.

Where the Medical Expert Lives in MoE

So, MoE changed one thing in the architecture: instead of one FFN in a block, it added N small FFN experts plus a tiny router. Attention is already compact, so it's barely changed.

The process now works approximately like this:

  1. The token passes through attention almost like in a regular model. (I say 'almost' because describing the differences would require a separate article).

  2. The router looks at the hidden state (not the word itself, but those computed representations the model made) and selects the top-k experts out of N.

  3. The token is processed only by the selected experts – the remaining N-k are asleep.

  4. Their outputs are summed with the router's weights and become the layer's output.

But let's take a closer look at the router: a small layer with great power. It's the one that decides which expert to send the ferritin analysis results to, right?

Here, you'll face disappointment, even two. Look closely at the GIF above. Do you see a person in a white coat? I don't either. Because neither a code expert, nor a medical expert, nor a Silver Age poetry expert lives in MoE. The reality is simultaneously more mundane and more interesting.

When researchers (including the authors of Mixtral) looked at which experts the router was assigning tokens to, they found no thematic specialization. It turned out that experts specialize in token patterns: this one likes punctuation, that one – numbers, and this one prefers code indentation and Python keywords. It's that simple: syntax is much more distinguishable in this representation than medicine or law.

Now, pay attention to the caption below the GIF: unselected experts are not counted at all. It's not "counted and multiplied by zero"; their weights are not even read from memory. All of MoE's savings are based on this fact – it's their strength and simultaneously their biggest pain point.

One might think this scheme is as reliable as a Swiss watch! If only! It has its holes, like Swiss cheese.

As tokens pass through, they go to different experts, but they all need the same basic knowledge. This means they independently learn the same thing across their parameters.

The folks at DeepSeek understood this and refined the scheme: in addition to the routable experts, they introduced a single shared expert that is always active for every token. The logic is as follows: basic things (grammar, common words) are needed by everyone – there's no need to force each expert to duplicate them. Common knowledge is stored in the shared expert, while specific knowledge is in the routable experts, which can also be further subdivided.

However, knowledge duplication is not the main problem that MoE developers encountered on the path to the networks we see today.

Load Balancing: Headache #1 in MoE

Actually, the first paper describing MoE principles dates back to 1991. If you don't believe me, see for yourself. The authors then proposed a set of expert networks plus a separate manager network that decides which one to activate. However, they weren't striving for savings but rather to prevent different subtasks from interfering with each other during training, and this particular issue was hard to fix.

The first working approach to the problem and the router itself appeared in a later paper. Here's the thing: an expert that is chosen more often learns more and becomes better, which causes the router… to start choosing it even more often! Consequently, if there was little work for some exotic expert in the training set, new tasks won't be assigned to it because it hasn't shown any activity before. Meanwhile, a general-purpose expert will be working overtime.

A "dead" expert is bad not only because it's inactive; it also takes up VRAM space. Unacceptable! To engage the entire team, it was proposed to add balancing losses. This is a penalty to prevent corruption and favoritism: if the network sees that one expert is receiving more requests, it throttles it and forces the router to distribute tasks more evenly (Auxiliary loss). This solution is effective but not without flaws: all experts learn, the entire model capacity is utilized, but at the cost of the router sometimes sending a token to the not-so-best expert. To mitigate the impact of this on response quality, two more mathematical tricks are used: Z-loss and Aux-loss-free. But this is probably too complex a topic. I've left links for the curious and knowledgeable, and we'll move on.

So Why Do 17B Beat 70B, and Where's the Catch?

Let's return to the headline's premise. In short, dense models tightly couple computation with tokens: if you want more knowledge, you pay more computation for each token. MoE breaks this link: knowledge is 397B, but you pay for 17B because only the experts needed for the answer are activated. There's an empirical rule circulating in communities: MoE quality behaves similarly to a dense model at √(total × active) – for Qwen3.5, this is ~82B, and for DeepSeek-V3 ~157B. These are rough numbers, but the order of magnitude is correct: 17B active parameters honestly beat 70B dense. You can debate the precision of this folk heuristic in the comments.

But where's the catch? The catch is that with large batches, the free lunch disappears.

With a batch size of 1 (your local chat), everything is great and cost-effective. But on a server with a batch size of 256, each token has its own route – cumulatively, almost all experts are activated in one step, and all weights must be read from memory. The FLOPs advantage remains, but the bandwidth advantage disappears. Therefore, large and serious providers address this using expert parallelism, clever batch routing, quantization, which I've already written about, and offloading experts to the CPU.

MoE bills are in gigabytes. Expert selection happens for each token, and you can't predict in advance which ones will be needed, so all of them must reside in memory. Qwen3.5 in BF16 is ~794 GB of weights when operating "like 17B." You can't load only the active ones because after one token, different ones will be active.

Otherwise, MoE is a fair trade: memory in exchange for speed and capacity. Now, when you see "1T parameters" in loud announcements, you'll know that for each token, the model only utilizes a modest 32B. But how elaborately and elegantly it does it!
