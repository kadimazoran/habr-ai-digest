Hi Habr! For about six months now, I've been trying to get into backend development with Go. By day, I'm tightening bolts in an auto repair shop, and by night and on my commute, I'm sitting with code, trying to understand the runtime's inner workings.

At some point, there were just too many topics. Everything got mixed up in my head: slice headers, Swiss Tables, the GMP scheduler, escape analysis. Cramming articles from my phone on the go is not very effective, and going to real interviews is scary – I just couldn't articulate these concepts out loud. When you're asked about memory or goroutines in real-time, your mind goes blank, and your tongue gets tied.

I didn't want to create another checkbox-ticking To-Do list, so I decided to build something purely for myself: a Telegram bot that quizzes me on technical questions, listens to voice answers, evaluates them strictly, and makes me repeat what I'm struggling with. I eventually finished and deployed the project to a server. Below, I want to share how the backend is structured and what pitfalls I stumbled upon during the process.

Stack and Architecture

I didn't write everything in a single main.go file; I wanted to get used to a proper structure from the start. I divided the code according to Clean Architecture: domain models separately, use cases with scenarios separately, database interactions separately, and the Telegram layer with handlers separately.

The backend itself is written in Go 1.23 using the telebot.v3 library. The database is PostgreSQL 16 via pgx/v5 with a connection pool, and I manage migrations using golang-migrate. Session states and repetition queues are stored in Redis 7. For voice recognition, I integrated the Deepgram API, and DeepSeek evaluates answers via the Groq Cloud API. All of this runs in Docker Compose on a cheap VPS with Ubuntu.

├── cmd/bot/          # Entry point, dependency initialization
├── internal/│   
├── domain/           # Business entities (Question, User, Attempt)│   
├── usecase/          # Scenarios (interviews, mock, quizzes, progress)│   
├── repository/       # Storage implementation (Postgres + Redis)│   
├── delivery/telegram # Command handlers, inline buttons, and HTML rendering│   
└── ai/               # Neural network and speech recognition clients
└── migrations/       # Versioned SQL migrations

Many people write bots in Python, but this Go application consumes only 25–35 megabytes of RAM in production, starts up in a fraction of a second, and comfortably runs on a server for 200 rubles a month.

Voice Input and Why Deepgram

The whole point of the project was voice interaction, because in an interview, no one lets you write essays. Initially, I tried to set up a local Whisper instance, but on a cheap server without a graphics card, it completely maxed out the CPU at 100% with every audio message.

Ultimately, I switched to the cloud-based Deepgram with the Nova-2 model. It transcribes audio messages from Telegram (OGG/Opus) in less than a second, and importantly, it understands our Russian IT slang well. Words like 'goroutines,' 'mutex,' 'slice,' or 'generics' are not mangled into gibberish. The bot takes the voice message from Telegram, streams it to Deepgram, and then works with clean text.

Evaluating Answers and How to Tame a Neural Network

The main problem with neural networks is that they always try to agree with you. If you simply ask ChatGPT or DeepSeek, "How do you like my answer?", the model will almost always reply, "Great, excellent!", even if you've said something completely nonsensical.

To make it judge strictly, I compiled a database of 860 questions across 85 topics and for each question, I wrote down the benchmark criteria (key_points). The model works strictly according to a checklist:

You are a strict technical interviewer for Go.
Question: %s 
Reference Answer: %s 
Mandatory Key Criteria: %s 
Candidate's Answer: %s 
Your task:
1. Check for the presence of each mandatory criterion in the candidate's answer.
2. Assign an objective score from 1 to 10.
3. Specify exactly which criteria the candidate missed.
4. Provide a brief, strict critique without flattery.

Now, if a candidate says, "Well, a slice doubles when it overflows," but forgets to mention the 256-element threshold and the new formula from Go 1.18+, the model won't give a high score. Instead, it will point out exactly what was missed.

Spaced Repetition with Redis and Mock Interview Mode

Cramming questions one after another is useless, so I implemented spaced repetition using Redis. For each user, a queue of questions for a session is assembled. If you answer confidently with an 8–10 score, the question goes to the end of the queue. If you fumble the answer or score less than 6, the question will reappear in a couple of steps. All attempts and scores are logged in Postgres for later statistical analysis.

I also created a real interview simulation mode for different grades: you select from intern to senior, the bot compiles a pool of 10 questions, can ask follow-up questions during the answer, and at the end, provides a verdict: Hire or No Hire with a detailed breakdown of errors.

What Pitfalls I Encountered

The first pain point was HTML markup in Telegram. If the model returns code without backticks or a closing tag is lost somewhere, Telegram simply crashes with an error and doesn't send the message. I had to write a small sanitizer that catches Go code on the fly by keywords (package, func, :=) and carefully wraps it in <pre><code> with proper escaping.

The second problem was double-clicking buttons. If you quickly press an inline button twice, Telegram sends two callbacks in succession, and a race condition would start in Redis, creating two parallel sessions. I fixed this by instantly disabling buttons using EditReplyMarkup before the backend even starts making heavy database queries.

And regarding security: Docker containers do not run as root; a separate user, appuser, is configured, and in the docker-compose.prod configuration file, flags like read_only: true are set, cap_drop: ALL capabilities are dropped, and system folders are mounted as tmpfs.

For me, this bot became a real opportunity to stop endlessly reading theory and finally get hands-on experience with databases, caches, external APIs, and deploying to a server.
