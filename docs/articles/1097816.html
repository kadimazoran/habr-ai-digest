What the Patch Does

1. cuBLAS FP16 without Tensor Cores (ggml-cuda.cu)

The function ggml_cuda_device_is_cmp() has been added to ggml_cuda_mul_mat_cublas_impl. It identifies CMP cards by device name and caches the result. On CMP, the calls to cublasGemmEx / cublasGemmStridedBatchedEx / cublasGemmBatchedEx receive different parameters:

  • CUBLAS_COMPUTE_16F → CUBLAS_COMPUTE_16F_PEDANTIC;

  • CUBLAS_GEMM_DEFAULT_TENSOR_OP → CUBLAS_GEMM_DEFAULT.

The behavior is controlled by the environment variable GGML_CUDA_CMP_MODE: 1 forces the mode on, 0 turns it off, without the variable, auto-detection works. When triggered, the following line is written to the log:

ggml_cuda_device_is_cmp: device 0 treated as NVIDIA CMP: cuBLAS FP16 GEMM without tensor cores (PEDANTIC)

This switches the matrix multiplication method with weights in F16 (this primarily affects Whisper).

2. dp4a Emulation (common.cuh)

If compiled with -DGGML_CUDA_CMP_EMU_DP4A, the ggml_cuda_dp4a function, instead of __dp4a, executes four mad.lo.s32 instructions written in Inline PTX:

int r = c; 
asm("mad.lo.s32 %0, %1, %2, %0;" : "+r"(r) : "r"((int)(int8_t)(a      )), "r"((int)(int8_t)(b      )));
asm("mad.lo.s32 %0, %1, %2, %0;" : "+r"(r) : "r"((int)(int8_t)(a >>  8)), "r"((int)(int8_t)(b >>  8)));
asm("mad.lo.s32 %0, %1, %2, %0;" : "+r"(r) : "r"((int)(int8_t)(a >> 16)), "r"((int)(int8_t)(b >> 16)));
asm("mad.lo.s32 %0, %1, %2, %0;" : "+r"(r) : "r"((int)(int8_t)(a >> 24)), "r"((int)(int8_t)(b >> 24)));
return r;

Inline PTX is needed here because the compiler would fold a plain C expression back into dp4a. The Matrix-Vector Quantized Multiplication (MMVQ) and MMQ kernels without tensor cores are built on dp4a, and thus, primarily token generation.

What the Measurements Showed

1. INT8 tensor cores on CMP 50HX are not throttled, at least in MMQ. Variants B–D, which lack tensor cores entirely, process the prompt 3–4 times slower than the base version. Therefore, bypassing them is unnecessary.

2. FMA and dp4a are bottlenecks for generation. Token generation is limited by MMVQ kernels, which are built on dp4a and FMA. Comparing within the “Pascal branch,” moving from B to C (disabling FMA) gives a +55% increase in generation, and from C to D (dp4a emulation) another +16–23%.

3. Hence, variant E: the best of both worlds. We keep sm_75 so that MMQ goes through tensor cores, and remove FMA and dp4a. The result on Q4_K_M:

It is worth explaining separately why E outperforms A even in prefill. The -fmad=false flag affects all kernels: normalization, softmax, RoPE, dequantization, and flash attention. On CMP, all of these are limited by throttled FMA.

4. The larger the quant, the lower the generation, while prefill remains unchanged. Generation is limited by the weight size: 58 tokens/s on Q4_K_M versus 53 on Q5_K_M. Prefill is around 410 tokens/s in all cases.

What is clear from the CMP 50HX testing results:

  1. FMA is indeed throttled, and it's the main bottleneck. Compiling with -fmad=false is the cheapest and most effective step: the code doesn't change, only the compiler flag is needed.

  2. dp4a is throttled. Emulation by replacing four functions with mad.lo.s32 provides an additional ~20% to generation.

  3. cuBLAS FP16 is throttled. The PEDANTIC mode speeds up F16 models like Whisper by more than 3 times.

  4. INT8 MMQ on tensor cores works fine. Compiling for Pascal (61-virtual) reduces prefill threefold, so it's not necessary.
