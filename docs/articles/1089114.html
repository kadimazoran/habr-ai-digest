Finding the right object in a customized configuration, processing a single shipment for multiple sales, uploading bank statements from email, or correctly matching excise stamps with receipt lines – each of these tasks involves a specific workflow. The September selection from Infostart Marketplace includes five solutions that help automate such operations. We examine their capabilities, technical requirements, and limitations.

Two products in the review are primarily for developers: Pilot 1C collects context for AI work, and ConfigEditor combines configuration file viewing, code editing, and an AI assistant. The other three developments are for users of accounting systems: they help process electronic shipping documents, receive bank statements, and control the sale of marked cigarettes.

Pilot 1C: First Configuration Research, Then Code

When working with a universal language model, knowledge of 1C syntax is not enough. To suggest a suitable implementation, the assistant needs to understand the specific configuration: what objects exist in it, what attributes have been added, how relationships are structured, and where the necessary data is used.

Pilot 1C begins by collecting this information. The primary source is Analyzer 1C, from whose graph the assistant obtains information about objects, their composition, relationships, calls, and roles. If an object or relationship cannot be confirmed, Pilot can interactively request clarification from the developer.

Additional context is provided by Insight 1C. It shows what is actually used in the information base. This is useful, for example, when a configuration has several similar objects, but only one is populated with actual data. Documentation from the team in PDF, TXT, or Markdown can also be included: internal standards, regulations, and solution descriptions.

The process is divided into six stages: configuration research, requirement formulation, architectural design, technical specification preparation, code or change map creation, and development of verification scenarios. The results of each stage are saved separately, allowing you to return to a specific phase when reviewing the task.

In addition to the full development scenario, there are modes for inquiry, configuration analysis, and code review. You can work interactively with user clarifications or autonomously, in which case missing information is recorded as assumptions.

According to the product description, the result undergoes over 150 checks before being issued: from syntax and method availability in the selected platform version to execution context, queries, and compliance with development standards. Confirmed conclusions are separated from assumptions.

Applying changes and debugging remain the developer's responsibility. Pilot provides code and an insertion map but does not modify the information base on its own or launch 1C:Enterprise for live data verification. Test scenarios are generated in Russian Gherkin for Vanessa Automation, and task materials can be exported to Markdown and Word.

For full functionality, Analyzer 1C with a loaded configuration and access to the graph via MCP is required. The Pilot server is deployed via Docker. The working part can be hosted within the company's network, and the language model can be chosen separately, including a local server with an OpenAI-compatible API. The model is not included in the package.

Electronic Order by Sales: One Shipment, Multiple Documents

If goods for several sales are sent to a customer in one vehicle, the shipment details need to be consolidated into a shipping document. The extension for UT and KA adds the creation of an electronic order – a request – directly from the "Sales of Goods and Services" documents.

For a simple "one sale – one shipment" scheme, a command "Process EPD -> Electronic Order (Request)" appears in the document menu. A separate workspace is provided for combining multiple sales.

The user specifies the period, organization, and counterparty, then selects the posted sales. The list displays the warehouse, delivery address, amount, number of packages, weight, volume, and information about previously generated electronic orders.

Before combining, the extension checks that the documents belong to the same organization and counterparty, and that their delivery addresses match. The weight, volume, and number of packages are summed up. Weight and volume are calculated based on package characteristics or primary units of measurement. If data is insufficient, the user receives a warning listing the problematic items.

Before creating the order, you can specify the carrier, vehicle, loading and unloading times, and other parameters. Re-including a sale already linked to an active electronic order is blocked.

The result is a standard 1C document linked to the original sales. Further verification, signing, and sending are performed using the system's standard tools: the extension does not create a separate exchange mechanism with the EPD GIS.

The solution is intended for UT 11.5 and KA 2.5/2.6. The source material indicates tested releases; compatibility may need to be checked for other versions, as EPD mechanisms change.

ConfigEditor: 1C Files, Code Editor, and AI in One Window

ConfigEditor is a standalone desktop IDE for working with CF, CFE, EPF, and ERF files. It is designed for viewing configuration structure, analyzing modules, and editing code.

The built-in metadata explorer allows you to navigate to desired objects, modules, and forms. The Monaco-based editor supports tabs, syntax highlighting, and autocompletion for standard constructs and BSP. Multiple modules can be kept open simultaneously.

Syntax is checked during editing: errors are displayed in the editor and the status area. For example, when modifying a procedure in CF, some problems can be identified before exporting and running the result in 1C. An external EPF processing file can be opened, modified, and exported.

The integrated AI panel considers the open code. This allows you to discuss a specific BSL fragment or query with the assistant. Local Ollama and cloud AI with a personal account key are supported. With the local option, code does not need to be sent to the cloud service.

The product is in Beta, and its functionality is continuously developing. The program code is closed. The description states testing on several configurations, including Accounting, ERP, KA, UNF, UT, and ZUP.

Bank Statements: From Your Inbox to Your Accounting Database

Receiving a statement via email often involves several manual steps for the employee: opening the email, saving the attachment, switching to 1C, and uploading the file. The extension for Accounting 3.0 consolidates this process within the accounting system.

After installation, the processing is available in the "Bank and Cash Desk" section. The user selects the email account and configures rules for finding statements.

Two scenarios are supported: the file is attached to the email, or the email contains a download link. In the latter case, a link template is configured for the sender. The description provides an example for Sberbank. Files can also arrive in archives.

In manual mode, the employee initiates the search, reviews the found statements, and uploads them to the database. For regular work, there is a scheduled task "AZV Automatic Statement Upload," which runs on a schedule.

The solution has a specific limitation: it does not search for statements in subfolders of the mailbox. This should be considered when configuring rules for processing incoming emails.

The extension is intended for 1C:Accounting 3.0; the source material indicates testing on release 3.0.205.22.

Excise Stamp Price (MRC) from Mark: Price Control and Code-to-Receipt Line Matching

Cigarette packs of the same item can have different maximum retail prices (MRC). This price is contained in the excise stamp code of a specific pack, so a single price in the product catalog is insufficient for correct sales.

The "MRC from Mark" extension retrieves the price from the excise stamp code upon scanning and sets it in the receipt line. In UT, packs of the same item with different MRCs can be automatically separated into lines with VAT recalculation.

The second task is to maintain the correspondence between a specific pack and the receipt line. According to the development description, before printing, the standard mechanism may reallocate excise stamp codes among lines. If packs have different MRCs, a code inconsistent with the item's price may be sent to the fiscal registrar.

The extension matches codes with lines whose price matches their MRC before printing. The document itself is not rewritten; only the data transmitted to the fiscal registrar is adjusted.

The third mechanism blocks sales above the MRC. The cashier receives a message with the product name, sale price, and the maximum price from the excise stamp. By default, exceeding the limit is prohibited, although the settings allow for it to be permitted.

The source material includes results from testing on copies of a tobacco store's live databases. According to the data presented in the original article, 5,864 checks with tobacco products for August were analyzed on copies of the tobacco store's live databases; 64 operations were identified as sales above MRC. In 58 tested tobacco items, no discrepancies remained between the MRC of the code and the price of the transmitted item after processing. These are the results of a specific run, not a universal assessment for all databases.

The solution has been tested on Retail 2.3.26.13 and UT 11.5.22.182 on platform 8.5.1.1302. In Retail, it is designed for the new POS. The price is changed only for pack codes containing MRC: blocks, sticks, cigars, and codes without such data are not processed by this mechanism. After updating the configuration, it is recommended to check the extension's application.

What the Selection Shows

These five developments automate different areas of work, but the value of each can be described through a specific action. Pilot collects configuration information before development. ConfigEditor helps work with files and code. The EPD extension combines sales into a shipment. The statement uploader transfers data from email to 1C. MRC control links the sale price to the excise stamp code of a specific pack.

When evaluating such tools, not only functions but also application conditions are important: configuration version, infrastructure, completeness of source data, and automation boundaries. It is these details that allow you to understand whether the development is suitable for a specific workflow.
