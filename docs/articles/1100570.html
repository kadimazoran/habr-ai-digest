We encountered this in a voice assistant and investigated thoroughly: replaying battle queries and changing one factor at a time. The prompt was irrelevant. The model followed its own dialogue history, and below I'll show how we discovered this, the resulting metrics, and what to do if you're building an LLM chatbot, agent, or assistant.

Where It Occurs

The assistant listens to a call and suggests answers to the user on screen. In auto-reply mode, the model sees every speaker's phrase and decides whether a suggestion is needed or if the utterance should be skipped. For skipping, it has a special response NOOP, which the user doesn't see.

The task of "knowing when to stay silent" is more common than it seems. A bot in a work chat should only respond when addressed. A support bot should escalate to an operator instead of answering on certain topics. A voice assistant shouldn't interrupt for every "uh-huh." An agent should pause and re-ask before a risky action. The pattern is the same everywhere: a rule in the system prompt and a long dialogue where the model must repeatedly adhere to this rule.

What Went Wrong

On a test set of utterances, the model skipped 78% of unnecessary ones, which was our target. In real calls, the situation was different: the model responded to almost everything, including "uh-huhs," spoken thoughts, and long explanations from the other speaker. Suggestions overlapped, and the relevant one got lost among the unnecessary ones. The policy in the prompt was detailed, with examples of what to respond to and what not to, and its edits had an effect within the margin of noise.

How We Found the Cause

The first rule of LLM debugging is to reproduce the battle query byte for byte. This means exactly what went into the model: the system prompt, dialogue history, context, and parameters, not a similar prompt in a playground. Then, change one factor at a time and observe how the rate of correct behavior changes. We took labeled turns where a suggestion was needed and where it wasn't, and ran variations.

Why History is Stronger Than the Prompt

The mechanism is simple and somewhat frustrating. The dialogue history only recorded utterances where a response was shown, and turns where the model responded NOOP were not included: the user didn't see them, so they didn't belong in the history. It sounds logical, but after half an hour of conversation, the model sees dozens of pairs in the history like this:

user: Uh-huh. Well, look, here's the board.

assistant: [detailed response of three paragraphs]

This effectively becomes few-shot learning. Usually, it's enabled intentionally by placing a few examples in the prompt to set the response format. Here, we enabled it accidentally, and it taught the opposite: to respond elaborately to any utterance. Dozens of examples outweigh an entire paragraph of rules, creating a loop: the more the model responded unnecessarily, the more confidently it continued to do so. During a long monologue from the other speaker, the model with full history stayed silent in 4% of cases, while without history, it was 78%.

The same mechanism threatens any of the scenarios above. A bot that should only respond to direct questions might start responding to everything after a couple of dozen messages if only its responses are logged in history. An agent whose history contains only successful actions without clarifications might stop re-asking. An assistant that sees its past answers to similar questions might start rephrasing them instead of providing a new answer. If a model is "disobedient," look not only at the prompt but also at what the history is teaching it.

What Didn't Work

Before truncating the history, we tried gentler methods. The first was a line in the prompt: "past responses are not a template." Silence increased to 54%, but the model started skipping 10% of necessary responses. The instruction against examples lost again, and with a side effect.

The second option was to also log NOOP turns in the history, i.e., "utterance → NOOP" pairs, without showing them in the interface. This resulted in 52% silence with a loss of 1-7% of necessary responses. Better than the original, but worse than a short history!

The third was the heuristic "don't respond while the person is speaking." It removed 9% of unnecessary responses but lost 11% of necessary ones because real clarifications often sound like interruptions: "Why?" "What does that mean?" temperature: 0, as seen in the table, adds 5 percentage points and doesn't solve the problem.

Won't Responses Get Worse Without History?

The fear is understandable: history is needed so that responses consider what was said ten minutes ago. We tested this blindly. For 45 questions where a response was needed, we generated two answers each in two variants: with full history and with the last two exchanges. The conversation summary and user profile were identical. Eight agents on Claude evaluated the four answers in random order, and each saw the full history up to that point. Evaluation was on a scale of 1 to 5, plus flags for: rephrasing old information instead of answering new, contradicting history, hallucination.

The difference in average score is within the margin of error: two answers for the same question in the same variant diverge more than the variants themselves. However, two unexpected observations emerged. Full history doesn't protect against contradictions; in fact, it increases them because the model gets confused by its own past responses. Furthermore, full history encourages rephrasing: when asked "and the third code?" the model listed the first two again, and when asked "name one code from 3xx" it provided the entire range from 100 to 504.

Then we ran the same scheme on other types of conversations: a technical call, a customer support conversation, a bilingual call. The model skips unnecessary utterances in 62% of cases instead of 23% and responds to 98% of necessary ones, with blind evaluation showing no worse answers. The cost is rare omissions, about one in forty necessary responses. Almost all of these occur for short clarifications like "Uh-huh. Which ones?" and are random: if repeated, the model responds to them.

The Recipe

Reproduce the battle query byte for byte. Log the model's full input, otherwise debugging turns into guesswork based on the playground. A similar prompt behaves differently than the actual one, and you'll end up fixing the wrong problem.

Change one factor at a time and compile the results into a table. We would still be fixing the prompt if we hadn't run the variations consecutively. Seven rows in the table explained more than all the wording edits before it.

Calculate what the history is teaching. How many examples of desired behavior and how many of undesired behavior does it contain? If the model is supposed to stay silent sometimes, but there are no omissions in the history, you are clearly teaching it NOT to be silent.

Separate decision from response. The model can make the decision "to respond or not" with a short history, and generate the actual response with a full one. We managed with a single call using a history of two exchanges; this was sufficient for quality.

Measure on the real stream. Our test set was clean but lacked history, showing 78% where production yielded 16%. If tests don't include what the model sees in production, they are measuring a different system.

Pitfalls Along the Way

Regex with an honest comment. The "looks like a question" function searched for substrings how, what, and when anywhere in the phrase, so "so that" and "the fact that" were also counted as questions. Above it in the code was written:

// MEASUREMENT ONLY. NEVER use this to filter fresh speech.

The function was written for measurements but was then reused exactly where the comment prohibited it. Only the person opening the file sees the comment, while the function name is visible at every call site.

Intermediate recognition results. Speech recognition in streaming mode provides intermediate hypotheses that are later rewritten. We calculated the boundary for "this has already been processed" based on text length, including these, and sometimes cut off a phrase mid-word, so "Testi" instead of a question went into the prompt. The boundary should only be calculated based on the final text.

-1 in logs. The field "how many milliseconds ago did the person speak" is -1 if data is unavailable. The regex [^0-9]+(?P<x>[0-9]+) in the log query honestly extracted a unit from -1, resulting in a metric of 33% instead of 9%. The correct way is: (?P<x>-?[0-9]+) and a separate filter x >= 0.

What's the Result

Currently, the model makes the decision "to respond or remain silent" with a short history, while queries that the user sends themselves are processed with the full history. On the real stream, the model has become noticeably more silent, although less so than on the test stand, and we are still investigating this discrepancy. When we figure it out, I'll write a follow-up.

The main takeaway for me is this: dialogue history is also a prompt, and the most powerful one. If a model persistently does something contrary to its instructions, first check what examples it is following.
