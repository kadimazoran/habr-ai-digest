How I tested: 8 tasks, 119 hidden tests, and about 75,000 random checks

Each model received each task in a new chat, and its response was checked by a page in the browser with hidden tests. The conditions were the same for all four:

  • run in the LLM studio SYNTX.AI, where the same prompt is sent to different models;

  • a new chat for each "task and model" pair: when changing the model in an old chat, the new one sees the entire conversation;

  • reasoning enabled for all, tools (including code execution) also;

  • the prompt was inserted entirely, without edits, up to three attempts per task. One was needed.

There were 119 hidden tests: 16 cases for bug fixing, 22 for string parsing, 7 lines of SQL results, 20 for refactoring, 20 scenarios for discount leakage, 11 for event counting, and 23 for time zones. Code review was compared against a key of four errors. Additionally, the solutions were run on random inputs against the benchmark: 20,000 carts, 30,000 duration strings, 20,000 reports, 4,000 dates in 18 time zones, and several hundred sequences of orders and event sets.

The reason for the test is Kinder's review "The 2026 AI Model Showdown" on X from October 13, which has about 209,000 views in six days. The review's conclusion: "almost a tie between Opus 5.5, Sonnet 5.5, and Astra in code, and Sol comes closest to the flagship level at the lowest cost." The author does not have their own run; all numbers there are from others' tables, and this conclusion wanted to be verified manually.

The first set of tasks turned out to be too easy

ChatGPT 6 Astra and 6.1 Sol passed five basic tasks without a single error, about a minute per task. The reason was in the tasks themselves: the traps were listed directly in the conditions. The duration parsing specification included all edge cases, and the SQL task had a separate rule for returns. A model that carefully reads the text will pass such a check. Therefore, a difficult round of three tasks was introduced. The condition for it sounds as a colleague would formulate it. Hidden tests check what an experienced developer would consider: a 190-line module with an error known only by its symptom, a million events with a 2-second limit, and reminders at local time in time zones with daylight saving changes. Spoiler alert: all passed this too.

Basic tasks: traps are named, yet solutions still differ

Bug fix based on a complaint. A customer sees 5996.999999999999 cents instead of 5997 on the receipt, and according to the specification, there are three more discrepancies in the function: the discount is rounded down, the promo code threshold is not checked, and there is no exception for a percentage outside the range. All four discrepancies were found by all four models. The volume differs: Sonnet's solution is 23 lines, Opus's is 34, Sol's is 47, and Astra's is 57. Astra and Sol wrote an accurate decimal parsing using BigInt, which even understands notation like 1e-7. This is correct, but a bit overkill for fixing three lines. Both Claude models used Math.round(priceRub * 100) and integer rounding, which is sufficient for prices with two decimal places.

The duration parsing of the form "1h 30m" was written by the models using regular expressions or component parsing, and all four summed it up accurately in BigInt. The only discrepancy found by random checks: Sonnet literally interpreted "there can be spaces between components" and rejected tabs, while the others accepted any whitespace character. This is a matter of interpreting the condition, not an error.

The most difficult among the basic tasks was the SQL report on city revenue. It had three traps at once. An order from September 30, 23:59:59 is lost if filtering with BETWEEN by date without time. An order with two items and two returns is duplicated if everything is joined in one query. And a return on September 5 for an order from August 31 is subtracted according to the condition. All were bypassed. Claude Sonnet 5.5 and Opus 5.5 calculated sales and returns in separate subqueries, ChatGPT assembled "money movements" using UNION ALL. The shortest version is from ChatGPT 6.1 Sol, 27 lines: cities without sales were added as zero rows to the same UNION ALL and it managed without LEFT JOIN.

In refactoring, the models received a report function with quirks, on which an external parser depended: numbering with gaps after skipped lines, "12abc" becomes 12, opts = null works like an empty object. Code review yielded the fewest differences. Four errors were embedded in the 21-line asynchronous code: forEach with async returns an empty array, a 404 response is cached as a profile, parallel calls with the same id duplicate requests, slice loses the last element of the page. All four models found all errors, and there were no false positives. Sonnet added a fifth point: the cache grows without limits. And Astra, in fixing duplicates, removes the promise from the cache on error only if the same promise is there; others remove it without such a check.

The hard round: traps without hints

A module for calculating an order for coffee delivery, 190 lines, and a support message: customers sometimes see a discount from a promo code they didn't enter, and on the test stand, everything is calculated correctly for one order. The reason: the promo code function adds the discount to the client status context, and this context is taken from the general cache. After the first order with a promo code, the discount applies to all subsequent clients of the same status until the process is restarted. The trap for the hasty: copying { ...ctx } looks like a fix, but the discount array remains shared, and five out of 20 leakage scenarios continue to fail.

No one fell for it. There were three ways to fix it:

  • Astra and Sol: copy the discount array inside the promo code function, three lines.

  • Opus: a new function that gives each order its own copy of the context; the cache is built as before, once.

  • Sonnet: the promo code function no longer changes anything, but returns the promo code, which goes only into the local order rules list. This is the only option after which the cache is read-only, although it affects the main function as well.

Astra and Opus also reminded that the service needs to be restarted after deployment. In the live process, the cache is already corrupted by previous orders, and the fixed code will not remove old promo codes from it.

A million events in 2 seconds. For each event, it's necessary to count how many events from the same user occurred in the previous 10 minutes. The data includes a user with 300,000 events, who has up to 20,000 neighbors in the window: a brute-force solution is correct for a small example, but for such a volume, it doesn't fit even in 10 seconds. Here, the models agreed on one scheme: group indices by user, sort by time, use two pointers. On a million events, all fit within 187-259 ms with a 2000 ms limit, which is faster than the benchmark solution in the same browser (290-307 ms). Events with the same millisecond, which break a standard sliding window, were also accounted for by all. Astra and Sol added a disclaimer that 2 seconds cannot be guaranteed without measurement on the target device.

Reminder at 09:00 user time only using Date and Intl, without Temporal and libraries. The simple approach of "add N days and set the hours" passes 18 out of 23 cases in the tests for this task. It fails on the nights of daylight saving changes, at times that don't exist (02:30 during the transition to summer time), and on Lord Howe Island, where clocks are changed by 30 minutes.

No model took the simple approach. All four took the same long path: local date via Intl.DateTimeFormat, adding calendar days, iterating through offsets around the desired day, checking if such a time exists. The result matched the benchmark on all 23 tests and on 4,000 random dates, including Casablanca, Dublin, and Apia, where December 30, 2011, was entirely removed from the calendar. The volume varies greatly: from 34 lines for Sonnet to 134 for Sol, which also searches for the exact second of transition using binary search.

Sonnet 5.5 checked its own code: up to 14 minutes per task

Sonnet took about 28 minutes for eight tasks, Opus about 13, and Astra and Sol less than ten. Sonnet spent the most time where it reported its own runs in the response: "checked on 426 runs against the original" in refactoring, "on 400 random orders" in the leakage task, "measurement on Node about 400 ms" in the million events task. The time zone task took 14 minutes. Tools were enabled for all in the LLM studio, but only Sonnet seemed to execute code, judging by the responses. I didn't see Sonnet's own runs, so these are the model's words; hidden tests confirm the result.

Traces of self-checking remained in the response text. The time zone task began with the model's service remarks about its work: "will restart checks sequentially in a new folder," "my manual expectations for two cases were incorrect." The code itself arrived directly in the LLM studio chat without being formatted as a block, merged into several long lines, and single-line comments ate part of the code. It was impossible to copy and run it as is. After restoring line breaks and quotes, without changing the logic, the solution passed all 23 tests. This is the only one of the 32 responses that required manual fixing.

Before the test, I had a hypothesis: the flagship might lose not on quality, but on endurance, if it exhausts the reasoning limit and doesn't reach the answer. It was not confirmed. Opus 5.5 delivered all eight responses in full on the first try, and Sonnet thought the longest, and judging by the responses, due to its own checks, not a lack of budget.

What benchmarks promised and what happened

The loudest figure in code discussions is Sonnet 5.5's 70.6% on Terminal-Bench 4.0, taken from Anthropic's own table. An independent tracker, Artificial Analysis, shows neighboring models getting 59-60% on the same test: Opus 5.5 at maximum effort 59.6%, Astra 59.1%. I wouldn't choose a code model based on a figure published by its manufacturer.

Kinder's "almost a tie" is based on benchmarks where the gap between models is less than the spread between stands. My test neither confirms nor refutes this tie: eight tasks couldn't differentiate the models, all passed everything. However, it shows that what matters are not two or three points in a table, but how the model behaves on your code: waiting a minute or fourteen, reading 23 lines or 57, getting a reminder about restarting after deployment.

Kinder has a correct formula: the price of a usable result equals the token price multiplied by tokens per task and the number of attempts, plus human time for edits. The review itself only considers the first multiplier. In my test, there was only one attempt everywhere, and no edits were needed, so price and time remain in the formula. I didn't measure the cost of a task in dollars: in the LLM studio, text models consume the request limit according to the tariff, not tokens. According to Artificial Analysis, Opus 5.5 at maximum effort costs about $5.98 per task from their set, compared to $3.26 for Astra, and at medium effort, it's the opposite, $1.34 versus $1.54.

One thesis from the review was not confirmed by the test: that Astra is stronger in deep refactoring (Kinder refers to CodingFleet). In my task, Astra changed the structure the least. This is one task with a strict requirement to preserve behavior, so the conclusion is cautious: caution might have been a response to the condition.

What to choose for code: Claude or ChatGPT

For a bug, SQL report, or refactoring a single function, any of the four will suffice, and it's more reasonable to start with the junior model: Claude Sonnet 5.5 or ChatGPT 6.1 Sol for $2 / $10. The choice then depends on what's more important to you.

  • Response within a minute: ChatGPT 6.1 Sol, and if budget is not an issue, ChatGPT 6 Astra.

  • More deeply rewritten code with the same behavior: Sonnet 5.5; in refactoring, it extracted three functions, while Astra touched almost nothing.

  • A model that runs its own code checks: Sonnet 5.5 with tools enabled. In total, this takes 2-3.5 times longer than others; on one task, it was 14 minutes versus 1-4 for others, and this is the response that came without a code block.

  • A reminder about the consequences of a change, such as restarting a service: in this test, Astra and Opus provided it.

In terms of correctness, the flagships at $10 / $50 and $4 / $20 offered nothing beyond the junior models on these tasks. Where they might have been useful, the test did not check: long agent sessions and edits across multiple files.

Where my conclusions might not apply

Eight tasks and one response per model per task: I did not measure stability from run to run. Languages are JavaScript and SQL, the evaluator is one, response time is approximate. Tools were enabled for all, but only Sonnet used them, so its time reflects self-checking, not model speed. There were no agent wrappers like Claude Code or Codex: the model received the task in a chat and responded with code. And the main limitation: the tasks did not differentiate the models by quality, so the test indicates equality at this level of complexity, not equality in general.
