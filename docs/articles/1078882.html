In late March 2026, Figma opened its canvas to AI agents. Claude Code, Codex, and similar tools gained the ability to create and edit mockups via the Figma MCP server.

I decided to test how well Claude Code could transfer website designs into mockups and how much it would cost. To do this, I selected several landing pages and asked the agent to transfer them to the canvas—I tried providing either a screenshot or a website link. Each time, I observed the agent's steps, the number of tool calls, and the number of tokens (i.e., money) spent.

When interacting with Figma MCP, the agent essentially assembles the mockup using JavaScript. Claude Code generates code that, through the Figma Plugin API, creates frames and layers, setting their sizes, coordinates, colors, fonts, and other properties.

How the experiment was conducted

I selected three pages:

  • The hero section of Hermes Agent

  • The main page of PostHog

  • The first screen of Tailwind CSS

For the Hermes and PostHog websites, I provided the agent with a screenshot of the pages in the prompt. I also included a folder with images, logos, and other assets from the website in the agent's context. For Tailwind, I only gave the agent a link to the website: the agent was supposed to study the HTML and CSS, find the necessary assets, and capture the page in the browser itself.

I used the Opus 5 model with an effort level of high. For each session with Claude Code, I created a clean harness—without additional skills, memory, or plugins. This way, the agent could only use the Figma MCP during the session.

After each agent run, I calculated:

  • the cost of the entire session

  • the working time

  • the number of tool calls

  • the cost of MCP calls

  • expenses for analysis and intermediate checks

  • visual similarity to the original

After launching the agent, I did not interfere with its work and waited until the design was fully completed.

How I calculated tokens and cost

After each session, Claude Code saves a log in JSONL format. It records the agent's messages, tool calls, and the usage field for each model response. From usage, I took four values:

  • input_tokens—new input tokens

  • output_tokens—model response, including code and tool arguments

  • cache_read_input_tokens—context read from cache

  • cache_creation_input_tokens—context written to cache

In the "Tokens" line, I summed all four values. To calculate the cost, I used the Opus 5 tariff with hourly caching: $5 per million input tokens, $25 per million output tokens, $0.50 for reading from cache, and $10 for writing to cache.

Here is the main part of the script that converts tokens of one response into dollars:

PRICE = { 
    "input_tokens": 5.0, 
    "output_tokens": 25.0, 
    "cache_read_input_tokens": 0.5, 
    "cache_creation_input_tokens": 10.0, 
} 

def cost(usage): 
    return sum( 
        usage.get(token_type, 0) * price 
        for token_type, price in PRICE.items() 
    ) / 1_000_000

Let's break down each step the agent took to complete this task in detail.

What Claude Code does before assembling the design

Before assembling the mockup, the agent doesn't start by creating elements. First, it analyzes the photo or website link: block sizes, coordinates, colors, fonts, and image cropping rules. Based on the logs from the three sessions, I found that the analysis method heavily depends on the input data.

If only a screenshot is provided

In the tests with Hermes and PostHog, the agent only had a screenshot of the page. Therefore, it analyzed the image approximately as follows:

  1. It checked the file format and resolution using file and sips, and reduced large screenshots for general viewing.

  2. It cropped out the navigation, header, buttons, and other complex areas into separate images and opened them using an image reading tool.

  3. Using the Python library for image manipulation—Pillow—it read pixel colors, built masks relative to the background, and found element boundaries.

  4. It separately analyzed the attached SVG, PNG, and WebP files: their sizes, alpha channels, and the position of the visible part within the file.

  5. It rendered several font variations using PIL.ImageFont: comparing character widths and uppercase letter heights.

Here is a real fragment from the session when analyzing the Hermes website. First, the agent divided the 4070×2056 pixel screenshot into zones and took several color samples:

The agent checked the pixel colors at several pre-selected points in the image. First, it took two points on free background areas and got the same value (0, 46, 228). This is how it determined the main blue color of the page #002ee4. Then it checked points within the text and button: their color turned out to be (243, 243, 243), or #f3f3f3. The agent used these values when creating the background, text, and button in the mockup. Separate enlarged fragments of the screenshot helped it to more accurately examine fonts, element boundaries, and internal spacing.

To measure geometry, Claude Code built a mask: a pixel was considered part of an element if it differed significantly from the known background. Below is a shortened fragment of the script the agent used:

from PIL import Image 

im = Image.open("hero.png").convert("RGB") 
px = im.load() 
background = (0, 46, 228) 

def is_foreground(color): 
    return sum(abs(color[i] - background[i]) for i in range(3)) > 60 

def bbox(x0, y0, x1, y1, label, step=1): 
    min_x, min_y = 10**9, 10**9 
    max_x, max_y = -1, -1 

    for y in range(y0, y1, step): 
        for x in range(x0, x1, step): 
            if is_foreground(px[x, y]): 
                min_x, max_x = min(min_x, x), max(max_x, x) 
                min_y, max_y = min(min_y, y), max(max_y, y) 

    print(label, min_x, min_y, max_x, max_y) 

bbox(300, 650, 2100, 1300, "headline") 
bbox(300, 1390, 2100, 1520, "button") 
bbox(300, 1600, 2100, 1860, "terminal")

The script measured the visible boundaries of the headline, button, and other elements. Based on these coordinates, the agent determined their width, alignment, and distances between elements. It refined the dimensions of containers and internal padding separately using enlarged image fragments.

Along with the website screenshot, the Hermes agent received the original illustration file for the Hero section. To place it correctly in the mockup, it tried different sizes and positions, overlaying the result onto the original screenshot. The agent used a similar method to determine the position of background images for PostHog.

It turned out that analyzing a screenshot, as shown in the cost table, involves dozens of small iterations:

cropping → viewing → measuring → new hypothesis → another crop.

Fonts and decorative images required particularly many steps, where a single color and rectangular boundary were not enough for the agent.

If a link is provided

The Tailwind agent acted differently. First, it obtained the page's HTML, found the connected CSS files and assets, and then opened the site in a headless Chrome with a fixed window size of 1440×900. The Chrome DevTools Protocol was used to control the browser. Within the page, the agent traversed the DOM and for each visible node, it called two functions: getBoundingClientRect() and getComputedStyle().

Below is a shortened fragment of JavaScript from the session—I only removed the Chrome launch and WebSocket connection boilerplate:

(() => { 
  const out = []; 

  const walk = (element, depth) => { 
    const rect = element.getBoundingClientRect(); 
    if (rect.bottom < -60 || rect.top > 1450) return; 

    const style = getComputedStyle(element); 
    const text = [...element.childNodes] 
      .filter(node => node.nodeType === 3) 
      .map(node => node.textContent) 
      .join("") 
      .trim(); 

    out.push({ 
      depth, 
      tag: element.tagName, 
      x: +rect.x.toFixed(1), 
      y: +rect.y.toFixed(1), 
      width: +rect.width.toFixed(1), 
      height: +rect.height.toFixed(1), 
      font: `${style.fontFamily} ${style.fontSize}/${style.lineHeight}`, 
      weight: style.fontWeight, 
      letterSpacing: style.letterSpacing, 
      color: style.color, 
      background: style.backgroundColor, 
      borderRadius: style.borderRadius, 
      text: text.slice(0, 90), 
    }); 

    for (const child of element.children) { 
      walk(child, depth + 1); 
    } 
  }; 

  walk(document.body, 0); 
  return JSON.stringify(out); 
})();

In one pass through the page, the agent collected approximately 430 elements: their sizes, positions, fonts, colors, and border radii. For example, it determined that the headline was set in Inter font at 96×96 pixels. For the code panel and the card, the agent also obtained precise dimensions, spacing, colors, and shadows. All this data became the specification for further mockup assembly.

While working, Claude Code still decided to take a screenshot of the page. However, it used it only once, as a visual check. The agent obtained the main parameters not from pixels, but directly from the page.

This explains the difference in analysis cost. When working from a screenshot, the agent is forced to repeatedly test hypotheses, whereas a link allows for extracting most of the geometry and styles in a single DOM traversal.

During the work with the canvas, the agent generated 221.7 thousand output tokens. The native structure requires creating objects step-by-step and explicitly passing their properties. Since output tokens are more expensive than input tokens, long tool arguments significantly affected the final cost.

Screenshot verification

When verifying the Tailwind landing screen, the agent noticed that the description under the headline "Rapidly build modern websites…" wrapped differently than on the original site. It fixed the wrapping in the correct place, changed the width of the text block, and requested its screenshot again.

After creating a block, the agent took its screenshot and compared it with the original. The MCP function get_screenshot returned not the image itself, but a temporary link to a PNG file:

{ 
  "image_url": "https://www.figma.com/api/mcp/asset/...png", 
  "width": 1440, 
  "height": 900 
}

Then the agent downloaded the file and opened it separately:

curl -L -o screenshot.png "https://www.figma.com/api/mcp/asset/...png"

That is, the cycle looked something like this:

request screenshot → get link → download → open → correct element

During the Tailwind assembly, the agent also wrote a small JavaScript script to compare the result with the original. Both images were loaded into Canvas, after which the script iterated through the pixel arrays and counted noticeable color discrepancies:

let different = 0; 

for (let i = 0; i < reference.length; i += 4) { 
  const difference = 
    Math.abs(reference[i] - result[i]) + 
    Math.abs(reference[i + 1] - result[i + 1]) +

With each verification, additional commands were generated for downloading and opening the file. Therefore, part of the expenses for "work around MCP" occurred after the agent had already started assembling the mockup.

Conclusion

The main part of the expenses is related not to the creation of the mockup itself, but to how the agent obtains data, controls the canvas, and verifies the result. A link to the website proved to be more cost-effective than a screenshot: ready-made HTML and CSS allow for extracting structure, styles, and assets directly, without reconstructing them pixel by pixel.

It is clear that a mockup is only half the journey. In the second part, I will conduct the reverse experiment: I will provide Claude Code with the created mockups and ask it to turn them into working code.
