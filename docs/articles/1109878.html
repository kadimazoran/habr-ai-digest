AI generates code in minutes, but teams might not see the promised acceleration. After generation, there's still verification, fixes, testing, and release, which developers spend hours on. According to a SimpleOne study, 83% of teams already use artificial intelligence, but only 24% reported releasing changes made with its help into production systems.

Let's explore what hinders AI code from reaching release, what questions development leads have, and what a task looks like where agents handle everything from requirements to deployment on a test stand.

Code is Generated, But Not Released

The SimpleOne study polled 71 specialists: 46% development leads, 24% developers, 15% analysts, and 15% other roles. Of the companies, 71% of respondents came from organizations with over 1,000 employees, and 36% from those with over 5,000.

According to the survey results, 41% of respondents have individual employees experimenting with AI on their own initiative, and another 18% are conducting team pilots. Only 24% reported regular use in work tasks where results go to production.

Another 23% of respondents found it difficult to answer what proportion of AI-generated code and configurations reaches production. It's possible that changes are released, but no one tracks them separately. This makes it difficult for management to assess the tool's benefits based on completed tasks.

There's another telling point. Currently, 60% of respondents use AI for writing code and configurations. Generation has already sped up, but other development stages remain the same in many teams.

If You Generate Code, You'll Be Held Accountable

A development lead needs more than just a working prototype. Before release, they must assess the effort, ensure security compliance, and verify that the change addresses the original task. These three concerns are directly related to the barriers mentioned by study participants.

Does It Save Time?

Nearly half of the study participants (48%) expect development to accelerate by at least 1.5 times. Another 31% cannot assess the effect. If we only compare the speed of writing code, the gain might seem impressive, but preparing the context and correcting the result also take work time.

Suppose a typical modification took 16 hours. With AI, two hours were spent on task description, half an hour on generation, four hours on review, and another five hours on fixes. In total, that's 11.5 hours: a saving of 4.5 hours, or about 28% of the effort.

What if the agent misunderstands the requirements? Repeated fixes will take nine hours, bringing the total to 15.5 hours. Generation still took half an hour, but the savings practically disappeared. Therefore, the effect should be calculated for the entire accepted modification, adding model costs to the effort.

What Data Did the Agent Work With?

For a small code snippet, an agent might need only a few sentences. When working with an existing corporate application, it will need context: repository structure, project rules, test stand configuration, and information about tables and dependencies.

For example, a developer asks to fix an authorization error and provides the application logs to the agent. If sent in full, along with technical records, user identifiers, tokens, and other personal data could end up in the model. The risk of code or data leakage was named the main obstacle by 68% of participants, with another 23% citing regulatory requirements.

Before connecting the agent, the team needs to determine which repositories and test stands it can access, what data is allowed to be transmitted, and which models can be used. It's useful to keep a history of requests and changes: during incident analysis, it will help establish what information the agent used and who confirmed sending the result to the test stand.

How to Know if the Result is High Quality?

The quality of the result concerns 48% of survey participants. At the same time, 61% are willing to entrust testing to agents. This poses a risk: an agent might write the implementation and tests based on the same task description, making the same mistake in interpreting the requirements.

Suppose the support manager asks to show the percentage of tasks resolved on time. The system has several closing statuses, including canceled and rejected requests. The agent considers all closed tasks, writes a test for this calculation, and passes it successfully. A number appears on the screen that does not match the support service's operational rules.

Therefore, acceptance criteria must be agreed upon before generation. The process owner determines which statuses count as resolved tasks, and an engineer verifies the calculation against a reference set of records. Other agents can check the implementation against the specification and run scenarios, but disputed business rules and the decision to accept remain with the responsible specialist.

Let's Look at a Modification with Agents: A Dashboard in 17 Hours

At the SimpleGen webinar, a product owner demonstrated a task that the team took from initial concept to working functionality on a test stand. The broadcast covered the development session history, encountered errors, and the final result. The multi-hour generation itself was done in advance.

The goal was to create a dashboard for the support manager: a single screen with filters for period, group, and task type. It should display the request flow, processing speed, bottlenecks, and quality metrics. The manager can set target values, and if they are violated, the corresponding metric is highlighted.

The task required calculated metrics, multiple data sources, a separate goal reference, and access rules. Therefore, the team used SimpleGen, which helps develop solutions on the SimpleOne platform with the involvement of AI agents.

First, the agent tackled the requirements. It asked the author 28 clarifying questions: which statuses count as resolved, how to calculate the median response time, and whether to consider negative flow balance. Discrepancies with the test stand were also found. The initial setup mentioned three task tables, but the test stand had ten descendant tables that also needed to be considered.

A second agent reviewed the specification, after which the author corrected disputed points. A total of 11 iterations were required; 5.5 hours were spent on preparing and agreeing on the requirements. Then, the agents divided the work into 11 phases and 42 tasks with dependencies. Planning took another 1.5 hours.

Next, generation began by phases. One agent wrote code, another compared changes against requirements and the plan. Then, the team sent them to the test stand. Upon sending the first phase, the test stand returned an error twice: one reason was, in particular, a long Russian-language tooltip. The agent suggested changing the text, agreed on the edit, and retried sending.

Later, a conflict arose with the form that the platform automatically created along with the table. During an update, the agent attempted to recreate it. The team synchronized the test stand state with the repository and continued working with the existing form. Code review revealed other discrepancies: an incorrect default value, insufficient access rights to the report, and an erroneous signature.

Testing the finished dashboard was also entrusted to agents. They prepared a demonstration scenario and data, then ran the scenario in a browser. Out of 28 steps, the agent completed 25 in seven minutes; three more required actions related to authorization, which it cannot perform due to internal rules. During the run, an empty block and invisible tooltips for the goal fields were discovered. After agreement, the agent updated the specification, plan, code, and configuration.

Following an additional redesign, the team reassembled the change package and installed it on a clean test stand. The installation proceeded without conflicts, errors, or warnings.

In total, the modification took about 17 hours, including requirements preparation, planning, code generation, and result verification. During this time, the team went through 11 specification agreement iterations, implemented 42 tasks, and tested the dashboard across 28 steps of the demonstration scenario. After fixes, the change package was installed on a clean test stand without conflicts, errors, or warnings.

What Tasks Would Teams Give to AI Agents?

According to the SimpleOne study, only 23% of respondents use AI at all stages of the development lifecycle. The need for automation beyond generation already exists, although in practice, AI is connected to these tasks much less frequently.

The gap is most noticeable in testing: currently, AI assists 26% of participants, while 61% would entrust it to agents. For bug analysis, the figures are 28% and 54%, and for code review, 26% and 46%. The situation is reversed for code: AI writes it for 60% of participants, while only 46% would delegate it to an agent.

The dashboard story shows where additional value can be found. Agents helped clarify business logic, reconcile requirements with the actual test stand, verify changes, and identify defects during demonstration. At each stage, humans retained the ability to approve disputed decisions and check the results.

If a team is already generating code with AI, it's useful to take the last completed modification and record how much time was spent on setup, generation, review, fixes, and release. The code might have appeared in half an hour, but several days were spent on clarifications or verification. Then, the next step for connecting an agent will become obvious from your own numbers.
