When we started building the TozheBot platform, we had a rather unusual task. We didn't just want to create a "platform for AI agents." We wanted to build a system where classic security, circuit isolation, and protection against next-generation threats work not as separate components, but as a single fabric. As CTO, I had seen too many projects where encryption was present, yet data still leaked. Where multi-tenancy was declared, but isolation was just a filter in an SQL query. Classical Security with an Eye to the Future and Key Management

Technology Choice

When choosing a cryptographic foundation, we had two paths: use proven standards (e.g., AES-256-GCM) or take a risk and implement hybrid solutions with post-quantum resilience. The classic approach seems secure – until you consider the planning horizon. Data encrypted today could remain confidential for decades. The "store now, decrypt later" attack is not a theoretical threat: an attacker could intercept ciphertext today and decrypt it when a sufficiently powerful quantum computer becomes available. And with today's progress in this area, there's something to think about.

I had previously worked on hybrid algorithms, including implementing my own QuarkDash protocol, which showed good results for chats. It solves this problem by combining Ring-LWE post-quantum resistance with the performance of symmetric ciphers ChaCha20 and Gimli. Benchmarks showed a throughput of up to 2.8 GB/s and session establishment in less than 10 ms on standard hardware, even in a TypeScript implementation, which fits well within the platform's framework. This was critical for us: we couldn't sacrifice speed for security.

There is also a port for Go – which generally works even faster due to the language's specifics.

But it's not just about performance. QuarkDash's architecture allows deriving keys not only through classic exchange (as is done in chats) but also deterministically: from a master secret, salt, and version. This means we don't need to store the keys themselves in the database. Only metadata: salt, version, KDF parameters. Compromising a long-term key does not reveal past sessions – a property called perfect forward secrecy in cryptography.

In our KeyManager, this is implemented through the deriveKeys function, which adds four bytes with the version number to the salt:

And here we come to the challenge related to key rotation.

Key Rotation: When Security Meets Performance

Key rotation is a classic compliance requirement. But implementing it in a multi-tenant environment with millions of documents is a separate headache. If you rotate the key every 24 hours and re-encrypt all data immediately, you'll have downtime. If you don't re-encrypt, old data will remain on the vulnerable key.

We solved this problem through lazy migration and background re-encryption. The key is rotated on schedule, but data is re-encrypted gradually, in batches of 100 documents with a delay between batches. The process can be paused and resumed – progress is saved in the keyring document.

The most interesting part here is the interaction with the platform's core. By default, our API automatically decrypts fields in the afterRead hook. This means that during normal reading, we see plaintext, not ciphertext. But for re-encryption, we need the ciphertext itself – to determine the key version and understand if the document requires migration. We solved this through the request context:

// keyManager.ts: Getting raw ciphertext for re-encryption
// In reality, the context is a bit broader, but for understanding, we show
// only the most important part
const migrationReq = {
  user: undefined,
  context: { skipDecryption: true },
} as any

const result = await db.find({
  collection,
  limit: batchSize,
  where,
  sort: 'id',
  overrideAccess: true,
  depth: 0,
  req: migrationReq,
})

When skipDecryption is set, decryptHook returns the value unchanged – and we see exactly what's in the database. When updating the document, the context is no longer passed, so encryptHook triggers normally and re-encrypts the plaintext with the active key.

But that's not all the headache.

Drift Protection: Why Rotation Lock Isn't Paranoia

In a multi-tenant environment, it's easy to reach a situation where key versions accumulate faster than data migrates. For example, if every new user session triggers a rotation. After a week, we'll have 50 key versions, 49 of which contain data requiring migration.

To solve this problem, we built three levels of protection into KeyManager:

  • The first is a 5-minute cooldown for session-bound rotation.

  • The second is checking for pending migrations: if there are background tasks waiting, rotation is blocked.

  • The third is a limit on the number of versions (KEY_MAX_VERSION_DRIFT). If there are more than 50 versions, the system enters read-only mode for rotation – migration must be completed first.

// keyManager.ts: Checking rotation locks
// The example is also simplified to show the essence
// of implementing rotation locking
private checkRotationLock(): RotationLockCheck {
  if (this.explicitLock.locked) {
    return { locked: true, reason: this.explicitLock.reason ?? 'Explicitly locked' }
  }

  /* Pending migrations block rotation */
  const pending = this.getPendingJobs()
  if (pending.length > 0) {
    return {
      locked: true,
      reason: 'Pending re-encryption jobs in progress',
      details: { source: 'pending-jobs', jobs: pending.map(...) },
    }
  }

  /* Version drift - too many versions pile up = something is wrong */
  if (this.versionRecords.length > this.options.maxVersionDrift) {
    return {
      locked: true,
      reason: `Version drift exceeds KEY_MAX_VERSION_DRIFT (${this.options.maxVersionDrift})`,
    }
  }

  return { locked: false }
}

This is not just a technical precaution. It's a compliance requirement. Regulators want to see that the system can explain why a key wasn't rotated and provide an audit trail. Our checkRotationLock returns detailed information about the reason for the block, which is logged and accessible via admin endpoints.

Circuit Isolation and Zero Trust Architecture

Multi-tenancy: Why a SQL Filter Isn't Isolation

The most common mistake in multi-tenant systems is relying on the developer not forgetting to add WHERE tenant_id = ? to every query. I've seen this in dozens of projects: one missed filter, and one client's data leaks to another.

Our approach is contextual isolation. Every database operation is performed within the tenant's context, and this context is passed through: from the HTTP request to the tool call in the end AI agents. In agentRunner.ts, we explicitly extract the tenantId from the conversation and pass it into the tool execution context:

// agentRunner.ts: Extracting tenantId and creating context
// The tool physically does not receive data outside this tenant, even if the agent itself
// forgets to specify it
const tenantId = extractId(conversation?.tenant)

const toolCtx: ToolExecutionContext = {
  api,
  req,
  agentId: agent.id,
  conversationId: conversation.id,
  tenantId: tenantId!,
  userId: conversation.user,
  mcpServers,
  agentTools,
}

Every tool within the platform, whether it's create_lead, escalate_to_human, or a custom webhook, receives this context. This means that even if a tool attempts to access a collection without an explicit filter, the system can apply isolation at the executor level. This isn't just defense in depth – it's the principle of least privilege by default.

Why We Don't Use a Shared Key Pool for All Tenants

Returning briefly to the encryption issue. Another architectural choice: each tenant has its own set of encryption keys. This is more expensive in terms of management (metadata needs to be stored for each tenant), but it's critical for compliance. If one tenant requests data deletion (GDPR or 152-FZ), we can simply destroy their keys – and the data becomes unreadable. If the keys were shared, we would have to re-encrypt the entire database.

This approach also reduces the blast radius in case of compromise. If an attacker gains access to one tenant's keyring document, they cannot decrypt other tenants' data.

Naturally, this is far from everything related to classic security. It also includes protection against CSRF, XSS, SQL, and other classic attack types, but we are not covering them today as they have become basic.

On that note, let's move on to more modern threats.

AI Agent Security: Where Classic Approaches Break Down

Prompt Injection: Why Regular Expressions Are Just the Beginning

The first thing that comes to mind when protecting against prompt injections is regular expressions. "Ignore all previous instructions" is easy to detect. "Forget everything" too. But modern attacks have long moved beyond these obvious phrasings. The OWASP LLM Top 10 clearly indicates that protection must be multi-layered: from isolating untrusted content to semantic filtering.

In addition to tenant isolation, we've built a three-phase system that complements each other. The first phase involves heuristics based on regular expressions. They work instantly (0.1 ms) and catch about 30-40% of attacks. This isn't just a filter – it's the first line of defense that doesn't require loading an ML model and works even under resource constraints.

The next stage is trained ML models. I had previously experimented by creating the OGL-Mini library, so we used it as the basis for our future shield.

OGL-Mini: Why ONNX and Not an External API

The second phase is the OGL-Mini ONNX model, which I fine-tuned. It was trained on TF-IDF with 100,000 features and logistic regression. Latency on weak hardware is 3-7 ms. So why did I choose a local model instead of an external API like OpenAI Moderation?

The answer is circuit isolation. If every user request is sent to an external API for verification, we violate the principle of "data does not leave the circuit." Furthermore, an external API adds 100-300 ms of latency due to the network request. For a chatbot, this is critical. OGL-Mini runs on CPU with a latency of less than 10 ms – which is 10-30 times faster than going to an external API.

And most importantly – it's unconditional control. We can fine-tune the model on our data observed in monitoring. We can add new attack classes without waiting for an external provider to update their model. And we can guarantee that the model is available – even if the external API is down.

Lazy Loading: Why We Don't Block Application Startup

One of the most complex architectural questions is when to load the ML model. If loaded at startup, the service will be unavailable for several seconds. If not loaded at all, we lose the second phase of protection.

We chose lazy loading. On the first request, the model is loaded in the background, and the system continues to operate with regular expressions. Once the model is ready, it's integrated into the process. This ensures fault tolerance: even if the model fails to load, the basic protection continues to work.

// guard.ts: Lazy loading of OGL-Mini
// Basic check.
// The model must be available in the general circuit without isolation from other modules
function ensureGuardLoaded(): void {
  const status = getStatus()
  if (status.state === 'ready' || status.state === 'loading') return
  if (globalThis.__tozhebot_ogl_loading) return

  globalThis.__tozhebot_ogl_loading = (async () => {
    try {
      setStatus({ state: 'loading' })
      const mod: any = await import('hybrid-ai-guard').catch(() => null)
      // ... initialization
    } catch (err) {
      setStatus({ state: 'failed', error: (err as Error).message })
    }
  })()
}

PII Masking: Why Tokens, Not Deletion

The third phase is protection against personal data leakage. We don't just delete PII – we replace it with tokens. This is important because the model loses context if all names and phone numbers are removed from the conversation. Imagine: a client writes "My name is Elijah, my phone number is +7 999 123-45-67." If we delete this data, the model won't be able to create a lead.

We use stable tokens: the same name is always replaced by the same token within a session. This preserves context for the model but protects the data. After receiving the response from the LLM, we restore the original values:

// piiMasker.ts: PII masking with token preservation
export function maskPii(
  text: string,
  pii: { hasPII: boolean; entities?: PIIEntity[] },
): MaskResult {
  // Check if the model returned personal data to us
  if (!pii.hasPII || !pii.entities?.length) {
    return { sanitized: text, tokenMap: new Map() }
  }

  const tokenMap = new Map<string, string>()
  const valueToToken = new Map<string, string>()
  const counters: Record<string, number> = {}

  const sorted = [...pii.entities].sort((a, b) => b.start - a.start)

  let out = text
  for (const ent of sorted) {
    const key = `${ent.type}:${ent.value}`
    let token = valueToToken.get(key)
    if (!token) {
      counters[ent.type] = (counters[ent.type] ?? 0) + 1
      token = `[${ent.type}_${counters[ent.type]}]`
      valueToToken.set(key, token)
    }
    tokenMap.set(token, ent.value)
    out = out.slice(0, ent.start) + token + out.slice(ent.end)
  }

  return { sanitized: out, tokenMap }
}
