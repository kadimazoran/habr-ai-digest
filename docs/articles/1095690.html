They don't replace people. Reviews, answers to questions, and the final say in MR remain with the human, I'll show below where exactly. I give agents one-shot tasks: clear and limited enough to be solved in one pass without long correspondence: add a button, fix a form, prepare a draft of requirements, etc.

I've been working with AI agents for a long time, and I'm used to working with my harness (for those who don't know, this is the working environment around the model: project context, instructions, access, checks) locally. It has long been the working environment for the entire team; not a day goes by without it. But the local version lives on each machine, and I wanted to assign tasks to agents just like to people: in Jira. Thus, the server version appeared.

Next, two demo scenarios: a small front-end task and a more complex one for an analyst. Then I'll explain what's behind the Assignee field.

Case 1. One button and two merge requests

The button isn't the main thing here. I was interested in checking the entire process, from assigning the task in Jira to changes in code, documentation, and review in GitLab. Therefore, I took a small task: to add a button to copy details to the supplier card. In Jira, it's one line, without description or mockups.

I assign the AI Front-dev as the assignee, move the task to 'In Progress,' and a task automatically appears in the harness backend. In the card, you can see how the agent loads project instructions, studies repositories, selects the necessary ones, and decides to update the documentation as well. During the work, test logs, check results, and other artifacts appear.

The result: in the Jira task, there are two links to merge requests and the status 'For review.' The first contains project documentation with a description of the new button. The second contains the button itself: code in the project's style, a test, and the copying logic.

I switched to the branch and opened the form. The button appeared and copies the details to the clipboard:

It works, but it looks boring. No questions for the agent here: the task was a single line, without mockups or design requirements. To match the project's design, it needs Figma mockups or at least a more detailed description. But that's a separate conversation; it's not important for the test. After this, only the agent's MR review is left for me.

At first glance, the code looks fine, but the MR needs to be checked anyway. If something is not satisfactory, I can leave comments and change the Jira task status to 'In Progress.' Then the agent will automatically take the task again, see that the MR in the task requires revisions, read my comments, and make the corrections; the cycle will repeat.

Case 2. From business need to User Story

Now for a more complex task, and it's no longer one-shot. I describe the need as a customer might, briefly and without technical details: 'I want to find products that are running low directly from the stock analysis and immediately create a supply request for them.' In this case, I assign the business analyst agent and move the task to 'In Progress.'

The analyst reads the documentation and repositories (they only read the project's codebase) and stops: the task in the harness goes to 'Waiting for response.' The agent doesn't guess for me; it asks questions.

The questions are specific, representing implementation choices. For example, can the composition of goods in the created request be changed, or should only selected items be included? Should the stock threshold be specified as an integer, or should fractional values with up to six decimal places be allowed? For each question, the agent suggests a recommended option, and I can choose it or write my own answer.

After my answers, the analyst prepares a draft User Story in Confluence. I read it and decide that it's ready for development.

The original task now has a link to the User Story and two related tasks, Front-end and Back-end. Both are already in 'In Progress' status: they have been assigned to agent developers. I won't go into how they handled it here; the mechanics are the same as in Case 1.
A human is needed three times in this chain: to answer questions, to read the User Story, and to decide that it's ready for development. The agents did the rest.

How it works behind the Assignee field

Each assignee in Jira has a profile in the harness: role, model, instructions, and access. When I assign a task to such an assignee and move it to 'In Progress,' the server checks the assignment, creates a task, and puts it in the queue. Then, the work proceeds according to one of the two scenarios from the cases above.

First, the server gathers the context: task description, comments, related materials from Jira and Confluence, project instructions, and repository snapshots. Source versions are saved with the task, so it's clear later what requirements the result was based on. If there are significant gaps in the context, the task waits for human clarification.

The work is done in a separate environment. The developer agent prepares code, tests, and documentation. The analyst agent reads code but cannot modify repositories in this mode: their result is requirements. If human decision is needed to proceed, the agent asks a question through the backend. This pause was shown in Case 2.

For each repository, custom checks can be configured. For example, a linter, tests, build. For interface tasks, a run in a headless browser with screenshots can be added. Commands and results are saved in the task artifacts. If a check fails, the server requests a human decision: correct the command, improve the result, or approve skipping with a reason. If no mandatory checks are assigned for the repository, the MR is still created, but with a note about it.

Branches and MRs are published by a separate server component, not the agent itself. Before sending, it verifies the assignee's permissions, task relevance, source branch, and the commit to which the checks apply. For the analyst, the result is an unpublished draft User Story in Confluence. Merging or publishing the document is done by a human.

The task lives on the server: PostgreSQL stores the state and history, Redis distributes the work. Therefore, I can close the tab, return later, open prepared files, stop, or resume the task. The backend collects events, questions, artifacts, and token consumption. Hidden model reasoning is not saved: actions, commands, and results are visible, not 'what the agent was thinking.'
