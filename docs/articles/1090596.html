Hello ladies and gentlemen. My name is Vasilyev Stas and I, like many members of this wonderful community, am trying to learn how to effectively use LLMs and AI Agents in development.

It would be ethical of me to say that this material was co-authored with an LLM. Who, if not an LLM, knows and understands how best to talk to and work with it. I see the work of a developer and an AI agent not as a replacement for one another, but as a symbiosis: the human sets the direction, experience, and responsibility, and the agent expands the developer's capabilities.

By 2026, the capabilities of Large Language Models had reached such heights that the surrounding context for development no longer fully matched them, or it became cluttered very quickly, and the quality of work began to significantly decline. Then, on June 12, 2026, a group of engineers from Google Cloud announced the open format Open Knowledge Format (OKF), in which they proposed the concept of LLM-wiki to the world:

Knowledge bundle — a catalog of Markdown documents with YAML frontmatter, where at the beginning of each file there is a short metadata block in YAML format, containing the structured context necessary for the agent to work with the project.

The specification was so concise that it fit on a single page. The most important quality of this format was that the knowledge was equally readable by both Humans and LLMs.

An OKF document bundle consists of:

  • Simple formatting — readable in any editor, displayed on GitHub, indexed by any search engine;

  • Files only — can be sent as an archive, placed in any git repository, connected to any file system;

  • YAML preamble only — for a small set of structured fields that should be accessible for queries: type, title, description, resource, tags, and timestamp;

On July 24, 2026, the same group of engineers proposed an update to this format OKF v0.2 tackles agentic trust. OKF v0.2 introduced mechanisms that allow the agent to consider the origin, confirmation, and relevance of knowledge when using it. This does not eliminate hallucinations on its own, but it gives the agent additional signals by which it can evaluate the source.

New optional fields were added to YAML:

  • Provenance — where the data came from;

  • Trust — who created and who verified the information (human or algorithm);

  • Lifecycle & Freshness — document status and the date after which knowledge is considered outdated;

  • Attestation / Attested computations — whether the computation was performed in the declared manner;

When I was starting my journey into Agent Development, it often turned out like in the good old Soviet cartoon about Vovka and the Two from the Chest. The model performed all my tasks, but very often it performed them as it understood them. And this understanding was sometimes unexpected and non-obvious. All this does not mean that Models are bad and useless. It just means I don't know how to "cook" them correctly. And that means I need to learn how to do it. After numerous attempts to find a worthy recipe, I came across this very OKF, which greatly interested me.

I decided to create a small template for myself using the Open Knowledge Format methodology in the hope of keeping my projects clean and ensuring that the steam from burning tokens doesn't just go up the chimney, but also leads to higher quality, more productive work. In my current version, I practically don't use some of the v0.2 features, but I hope that further immersion into this specification will allow me to apply these ideas.

In my work, I use Opencode. I've tried various Agents, but settled on this one. And my template is primarily oriented towards Opencode's requirements, but adapting it for any other Agent will not be difficult. Over time, I plan to make the templates as universal as possible myself.

One of the main advantages of this approach to working with Agents is a clear information storage structure and Lazy-loaded. You don't store everything in memory; you get the information/data you need precisely when you need it. Google's own description of OKF directly includes the idea of progressive disclosure: an agent or human gets the ability to move through the knowledge tree gradually, without loading the entire bundle into context. And the very fact that project information is structured and recorded somewhere is half the battle.

What does it all consist of:

  • AGENTS.md — the entry point, a minimal project description, and workflow; it's not a knowledge base, it's a router to the knowledge base;

  • _*.md — thematic reference files (architecture, setup, CI, codestyle, security, testing, API, performance, release, and much more) — loaded on demand;

  • working directories — issue/, playbook/, pr/, analysis/, runbooks/, archive/

As a result of this approach, instead of one 500-line AGENTS.md file, we have a focused core of ~60 lines and over 25 thematic files that are intended to be loaded only when needed.

I tried to apply this idea in practice and create a separate knowledge bundle for Opencode. Its task is not to replace the project documentation, but to provide the agent with a structured project map and a set of specialized knowledge that can be accessed as needed.

Subdirectories contain findings/discoveries made during the work process: issue/, playbook/, pr/, archive/

Key principles:

  • Lazy loading (Lazy‑loaded) AGENTS.md is a table of contents, not an encyclopedia: the agent reads thematic files only when necessary;

  • Local file .opencode/ — I prefer to keep this bundle separate from the project's source code so that the agent's knowledge and the production repository have independent lifecycles, but nothing prevents you from storing it in Git alongside the project code;

  • Compliance with OKF v0.2 requirements: convenient Markdown + YAML frontmatter with trust signals (generated, status, sources);

  • Accessible to all. If you can view the file content, you can read OKF; if you can perform a git clone, you can distribute it.

  • Does not require additional tools. Does not require building, does not require a central registry. Consumers can add validators, but it is not mandatory;
