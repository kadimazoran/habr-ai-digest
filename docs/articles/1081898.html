— AI is everywhere now. I upload a document to a chat, and it answers everything correctly. We need to do the same for all documents.

I hear such dialogues more and more often when discussing new projects.

This means that the question "why is it difficult to do the same as in the chat, but for all documents?" is already commonplace and requires discussion.

I have been involved in industrial document processing and recognition systems for many years. When a system "succeeds" on one document, I try not to be enchanted by it. I try to think about how to make it a stream.

Modern AI models are indeed almost blurring the line between a question to a text document and a question to an image. It looks like magic.

But we need to figure out what to do with documents when the magic doesn't happen. I will try to generalize approaches to organizing document stream processing and reflect on what should not be forgotten when designing such a stream.

A couple of words about terms. The difference between them is becoming increasingly blurred, but I will still define what I am starting from in this article.

OCR (or classic OCR) — recognition engines (e.g., ABBYY, Tesseract, etc.) that are used to extract text from an image by converting pixels into letters and words without understanding the meaning of the extracted text.

AI models — a generalized name for LLM, VLM, and their combinations, when contrasted with classic OCR is required.

In general, in my article, I do not distinguish between VLM and LLM, but where it is required by the meaning, I will do so.

A prototype and a stream are different things

Let's go back to the document and the chat. We uploaded 20 documents to the chat for verification, and the model made a mistake in one. It doesn't seem scary — what's 1 mistake. But if there are 2000 documents, there will be about 100 mistakes. In a real system, the number of errors cannot always be predicted from a prototype, but for simplicity, let's assume the error rate is constant. And when there are even more documents, it turns into a full-fledged stream of errors alongside the main stream of documents. We need to do something with these documents. And first of all, we need to identify the erroneous documents. After all, the system cannot always understand that it has made a mistake. Some errors may be detected in other systems when document processing is considered complete. Moreover, detecting an error is not enough; it must be corrected, and document processing must be completed. This is how it turns out that when designing a document processing system, you almost always have to think about error handling as well.

But here it is important to talk about the cost of an error.

It is not always necessary to spend a lot of effort and time correcting errors in extracting attributes from documents that do not affect anything further. But if an error affects a payment, a legally significant action, or another critical process, a control mechanism is needed — automatic or manual. Moreover, the check does not necessarily have to be carried out at the recognition stage: it can be integrated further into the business process.

A simple example: a document has a full name and an email address; these attributes are needed to find the document in the electronic storage system. The system made a mistake in extracting the email. Is it worth spending time analyzing, repeating, and finding ways to control this error if there are only a few such documents and all that this error led to is a search by full name instead of email? And another situation: the document number was incorrectly identified, and an error occurred in the subsequent business process, leading to the wrong path for further document processing. As a result, this can lead to fines and reputational risks — such an error must be controlled in advance.

But sometimes, to understand where the error is, it takes a lot of resources to change the process (e.g., enable extended logging, collect copies of the entire document stream for future analysis, launch debugging processes, etc.). Sometimes it's easier and faster to leave such errors for manual resolution.

Depending on this, it is necessary to determine in advance which errors require changes in the pipeline and which are more reasonable to leave for manual processing or a separate scenario.

There is a more important question before OCR

In my practice, the task almost never ends with the words "we just need to get a recognized document." Data is always needed for something: to find a record, determine a route, check a condition, make a decision, launch the next process.

Therefore, when starting a recognition task, it is worth first understanding what the business intends to do with the data from the document. Sometimes the client comes with a document and a list of attributes:

"They are all here on the document — let's extract everything."

After analyzing the business process, it turns out that some of these fields are not used anywhere else. For example, the process requires transferring data to an external system to generate a response, and it turns out that the external system cannot process the attributes that the client asks to extract. Technically, they are on the document, the system can extract them, but here it is appropriate to ask the question "Can we, and why?"

Because if we decide to recognize them, everything else follows immediately: setup, quality assessment, checks, error handling, maintenance.

As a result, we spend resources on data that does not affect the outcome at all.

So, to the first question "What is the cost of an error?" we add a second one: "What measurable result will automation provide?"

And only after that, choose OCR, VLM, LLM, and everything else. Otherwise, the project justification quickly boils down to the phrase: "It's the 21st century." The argument is good until two numbers appear next to it — the cost of automation and the expected effect.

Sometimes, after such an assessment, automation has to be abandoned or its scope reduced. But it's better than spending effort and resources on a project that will not bring results.

The criteria can be different. Somewhere labor costs are important, somewhere speed. The effect can also be a reduction in errors or the absence of fines.

The main thing is that the result can be measured and that it is understood equally by both business and IT.

How much intelligence does a document need?

After answering the first 2 basic questions, you can move on to choosing the technology.

The mere fact that a model can solve a given task does not mean that it should be used to solve the task.

A simple example is document classification. You can pass the document text or even an image to the model and ask it to determine the type. When there are many types and few documents, this can be a good idea. After all, you don't have to spend time training a classifier for each type. But if there are only 2 types and there is a formal feature that easily determines the desired one, it is better to use classic tools.

And so at each stage of processing — if the task can be solved simply, there is no need to solve it complexly. As trite as it may sound, sometimes it's easier to put a barcode on a document than to construct a VLM + LLM combination to split the document stream. And it's not just about architecture. At the prototype stage, any additional processing step is practically unnoticeable, but in a stream, the time and cost of each operation are multiplied by the number of documents.

It is not necessary to choose one solution for the entire document stream. Somewhere, rules based on OCR are sufficient, somewhere a narrow ML model will work, and somewhere you cannot do without LLM.

Classic OCR has its limitations

If it seems that I am calling not to use AI, that is not the case. Classic approaches to data extraction have their limitations. They are mainly based on predefined algorithms and known document variations. As soon as an unknown document example appears or the rules for forming documents change, OCR needs to be reconfigured.

Changing algorithms and adding new templates can worsen the processing of "old" documents. A typical scenario: one document is fixed, but the overall recognition rate drops. VLM, in this regard, allows for less dependence on changes in formats and rigid rules. And modern approaches to software development using AI allow for faster analysis of large volumes of documents and testing hypotheses on the entire document array at once. They also allow for faster changes to code and algorithms. The practical effect here is not only in the quality of OCR but also in the speed of implementing changes. However, we will return to this later; there are pitfalls here.

When you need to build a system instead of just a model

The phrase "we use AI for document recognition" still says nothing about the solution architecture. For example, there may be a case where a document is sent to a model for text or structure extraction, and all other attribute extraction logic is written algorithmically. Or another option, where a document is sent to a model, and all logic is entrusted to it. There are many combined approaches between these options, but that's not the point now. The point is that even when all the logic could be entrusted to AI, architecturally, other blocks have to be added nearby. After all, the client almost always asks: "How well does the system recognize?" And here a quality control block appears on the diagram. Models cannot be fully entrusted with this task yet. Perhaps someday in the foreseeable future, but for now, we have to choose or combine different methods: reference books, mathematical checks, reference values from other systems, or manual validation.

"And why did it decide that way?"

Another question that often comes from business and support is: "And why did it decide that way?"

Even with classic OCR, the answer is not always obvious. Sometimes a 6 is mistaken for an 8, a 0 for an O, etc. We don't know why a particular option won within the algorithms, but we clearly see the processing chain.

  • Here is the original image.

  • Here is the result of preprocessing.

  • Here is what OCR returned.

  • Here is what the next stage extracted.

  • Here is what rule worked after that.

The administrator and developer can manage the system quite flexibly in terms of correcting algorithms, rules, etc.

In the case of a model, a document is fed into it, and the result is output. All intermediate working logic is hidden inside the model; it is quite difficult, if at all possible, to fix something pinpoint.

This means that it is better to add another architectural block — document lifecycle control. Its task is to provide more information about what happens to the document inside the system and to ensure that nothing is lost during processing. It must be possible to reprocess the document if the model does not give the desired result or if something went wrong outside the model. Documents should not "disappear" inside the system. If we sent 100 documents for processing, it should be clear what happened to each of them.

Finding an error is not enough

As the boss said in an old movie: "Strike while the iron is hot." It's not enough to detect an error — it needs to be analyzed and corrected. And for that, it needs to be reproduced. And explaining the error is not the final business result. It must be possible to reprocess the same document after correction in the system. This also requires a separate block from the architect. By the way, this block is common for both model processing and classic approaches. But there is still a difference. While there are still questions about the repeatability of results when processing documents with models, this risk must be "wrapped" in additional checks in advance. If, at the design stage of the system, you do not ask the questions: "What will we do if the document is processed incorrectly?", "How will we correct it?", "How will we bring it to the result?", — this is a reason to ask them.

When modifications become too easy

Next, I am stepping onto thin ice of general system requirements, not just OCR systems. But they logically follow from the above, so I will mention them. Especially since I already put a "bridge" here about the disadvantages of easy changes by development agents.

Let me remind you of the advantages first: module code is written quickly, hypotheses are tested faster, different algorithms and their combinations can be used when searching for attributes. A new document type or kind appeared — a new rule was quickly added.

Now for the disadvantages:

Another option appeared — another condition.

Then another one.

When the number of new document types becomes large or a wide variability of forms not previously checked is discovered, there are many conditions. At some point, without proper development, all this becomes a "lump" of code that is difficult to perceive as a whole and control. And even worse, when these changes start to contradict each other. It is tempting to make a local fix and get a quick result, thereby further complicating the code. Therefore, it is important to periodically review small fixes and replace them (if possible) with a more general fix.

This is especially characteristic of document recognition systems: each new document type or format can bring its own set of errors.

The ability to change quickly is "the base"

Another feature that an architect needs to remember is that models are changing rapidly now. The solutions chosen at the start of the project may change (and even several times) during the work on the project. It is risky to build an architecture such that replacing a key tool requires redoing the entire system.

On the other hand, you shouldn't rush to change everything as soon as a new version of a system component is released. And this is not only about the stage of a new project. The approach is the same for a production system.

A component should be replaced only when the benefit of replacement exceeds the overhead costs of implementation. The architect's task here is "basic" — to make the system easily modifiable.

Architecture is more important than the model

As models develop, the recognition task becomes increasingly accessible. Now there are more and more ready-made tools, and there is no need to build your own extraction technology from scratch. The entry threshold for various teams is lower. The task of specialists and teams involved in document processing is also gradually changing. Knowing a specific OCR engine and being able to configure it is still useful, but it's no longer enough. The team needs to understand the entire process: why data is extracted, what its value is for the business, what errors can occur, where additional control is needed, which tasks should be automated at all, and which tools should be used for this.

This requires a large set of tools: stream scanning systems, classic OCR tools, VLM, LLM, reference systems, etc. By combining these tools, you can assemble a suitable solution for a specific task, rather than forcing all tasks to fit the capabilities of a single technology. The focus shifts from the question "How to recognize it?" to the question "How to correctly solve this problem?" The emergence of AI models has not replaced previous technologies but has significantly expanded the set of available tools for solving problems. The architect's task should not be limited to choosing the best model (although this is undoubtedly an important task), but should consist in selecting the optimal set of tools to achieve business effects.

Therefore, a new project should not start with searching for the most powerful model, but with the question:

"What business effect will this automation bring?"
