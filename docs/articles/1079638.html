When an agent in production makes a mistake, the team's discussion follows a single scenario: "the model is dumb," "the prompt is flawed," "the provider has something wrong with their API." A particularly biting version of the argument is when all the code around the model is written by you: is the model to blame, or am I? I argued the same way until I started analyzing failures one by one, with logs and numbers. It turned out the agent wasn't failing because the model was bad, but for reasons that have names.

Three episodes from practice, all with green metrics.

  • When uploading a corpus of norms into the vector database, 34% of chunks were silently lost: 6861 points remained in the database out of 10,414, the upload log reported "no skips," and the golden set of questions was green – verification questions simply didn't hit the lost pieces.

  • Adversarial auditing found 14 defects; half were in my own evaluation tests. And all these tests were passing green.

  • My favorite from the same batch: the smoke test "no public PDF crashes the parser" was written using any() – if one out of three documents survived, the test was considered passed. An empty proof, not a check.

In all three stories, the model remained unchanged and wasn't retrained: the fix wasn't needed for it, but for the surrounding code – the database, the pipeline, my own tests.

Next, why this isn't bad luck, but a pattern. The visible failure is always the same: "the agent made a mistake." And behind it can be four different types of repair: model post-training, harness engineering, environment redesign, or benchmark repair. Harness is all the code around the model: prompts, context, memory, tools; there's no precise short Russian word for the term, "harness" is the closest equivalent. From the observed failure, it's not clear which of the four types of repair is needed – the article calls this the repair-assignment problem. The cost of error is not abstract: spending weeks on retraining or changing the model – the failure remains in place. By default, everyone chooses this most expensive and usually incorrect path: "the model is stupid – let's change it."
