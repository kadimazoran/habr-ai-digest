This story is about how a common task of searching for rare equipment on the secondary market turned into a full-fledged engineering investigation. As a result, I managed to teach a local 7B/8B class language model (Qwen) to bypass aggressive protection systems, obfuscated frontends, and network restrictions of an isolated sandbox. No paid search engine APIs, no proxies. Only Python, Playwright, and a pixel-logic approach. The article is written hot on the heels of our "technological breakthrough" with AI.

Prehistory and Pain: Why requests to large sites are a guaranteed ban.

The task seemed trivial: ask a local model in the Strata environment to find ads for a flagship mobile workstation in maximum configuration with a rare professional video card on a popular classifieds site. But modern large classified platforms have a simply ferocious bot protection system. An attempt to make a direct requests.get() or use standard BeautifulSoup instantly results in a banal "HTTP 403 Forbidden" or "HTTP 429 Too Many Requests". The WAF (Web Application Firewall) at the network level instantly blocked the model's work.

Then I tried to use a classic "intermediary" - to teach the model to search for ads through search engines (Google, Yandex, DuckDuckGo) with the operator site:domain.ru. But here too, I was met with failure! One search engine displayed a typical "You are not a robot" captcha, which a text script could not pass. The text HTML mirror of the second search engine hung indefinitely due to timeouts because of the network allow-list within the isolated Strata environment. The third search engine returned live HTML, which, upon parsing, turned out to be an empty JavaScript redirection stub.

The model repeatedly returned zero results, got confused in regular expressions, and broke URLs. It became clear: standard web scraping methods, if not dead, then require extremely non-trivial methods on the verge of foul play. The interaction architecture itself needed to be changed.

The Found Method: Direct Action Visual-Textual DOM Agent (Visual Web Agent).

Instead of trying to deceive the network at the raw packet level, I decided to ask the model to simulate a human at the pixel and logical levels. The method is based on "two pillars": emulation of a real system browser and parsing the DOM tree by "human" markers instead of relying on CSS classes.

Step 1. Browser "Invisibility Cloak" - Emulating System Edge.

Anti-fraud systems easily detect headless Playwright or Selenium browsers by specific flags (e.g., navigator.webdriver = true). Therefore, I asked the model to intercept control of the Microsoft Edge browser already installed in the operating system, and the model quickly assembled a Python script.

The script runs in visible mode (headless=False), using the system browser binary via the channel="msedge" parameter. Additionally, the --start-maximized and --focus flags are passed to the arguments, and the page.bring_to_front() method is called in the code. This forcibly pushes the browser window from the tray directly onto the screen, on top of all other windows. For protection systems, this looks like an absolutely legitimate page launch by a user. An 8-second pause ensures that all protection scripts have time to execute and the page fully loads.

Step 2. Victory Over Obfuscation: Parsing by Text Markers.

The frontend of large platforms is overloaded with hashed dynamic classes (e.g., .styles-module-root-XyZ12), which are randomly generated by the server and change with each site update. But here too, the model proved to be on top of its game and fundamentally began to ignore CSS selectors. The agent scans the DOM tree in one pass, clinging to semantic text markers:

  1. Finds a text node containing a currency symbol (or other price marker) - this becomes the fixation point.

  2. Moves up to the parent container and grabs the adjacent large text - this is the title.

  3. Extracts a link from the same block, validating it with a regular expression for the pattern _ {5,} (a unique digital ID of the ad in the URL tail of the card).

Step 3. Assembling Dispersed Data by Item ID (iid).

The architecture of modern marketplaces often separates data for optimization purposes: the seller's name and city may lie outside the compact card container. The local model itself found an elegant solution: it discovered that store profile links in the page code have a hard parameter linking them to the card (e.g., ?iid=, where is the unique ad ID). The script, immediately and completely independently optimized by the model, began to take a full text dump of the page, find matches by iid, and stitch together "product + price + city + seller link" pairs with 100% accuracy, completely eliminating line shifts in the report output.

As a result, I practically took on the role of an observer who just sat and watched "the artist create," receiving parsed ads and links at the end of the model's work!

Universal Prompt Container for Launching the AI Agent.

As a result, a simple and universal prompt container was "born" for launching the AI agent for the described task. So that your local (or cloud) model immediately understands this method and applies it to any other complex site without falling back to requests and trying to download the built-in Chromium (which often breaks the environment), you can use the following proven prompt container:

Start the "Direct Action Visual-Textual DOM Agent" mode. Your task is to find [what we are looking for] on the site [site name here].

Act strictly according to the algorithm:

  1. Do not use requests and do not try to download the built-in browsers of the Playwright library.

  2. Launch the browser in visible mode (headless=False), strictly specifying the use of the already installed Edge via the parameter: channel="msedge" (this will cancel downloading Chromium from the network).

  3. To prevent the window from remaining minimized in the tray, be sure to pass the flags: "--start-maximized" and "--focus" to the browser launch arguments, and after creating the page, call the page.bring_to_front() method to forcibly bring the window to the foreground on the screen above all other windows.

  4. Formulate a search URL with the query embedded within the link to open the results page directly.

  5. Wait for 8 seconds after loading to bypass protection systems and Cloudflare.

  6. Take a screenshot for visual control and OCR analysis.

  7. Ignore hashed CSS classes. Collect data (name, price, link) by traversing the DOM structure, clinging to text markers (currency symbols, card ID patterns).

  8. If the data is scattered in the DOM, take a full text dump of the page and match blocks by indices (e.g., via the Item ID of the ad).

Write the script code, execute it right now using the launch tool, and output the ready report with the ads to the chat.

Results: What did my "autonomous robot" bring in the end?

Despite the fact that during the process of dense interactive debugging of the script, the target site eventually issued a temporary "429" restriction on the sixth attempt, the model showed a high level of autonomy. It did not get confused, blocked new network requests (until the IP ban "unfreezes"), and collected the final structured report from the local data buffers already stored in memory.

The most interesting part: the AI agent exhibited elements of critical thinking. In one of the ads, the title indicated a top-tier video card model, but the model scanned the description text DOM and found the seller's line: "Video card: lower series with 16 GB". The model itself included a warning in the report: "Attention, contradiction in the specifications of the title and description, clarify with the seller." Thus, the model made me understand that the ad was not suitable for me, even if it formally "matched" the request.
