1. What an AI Assistant Consists Of and Why Backing Up Just the Database Isn't Enough

We'll use the Reg.ru services architecture as an example: source code is stored in S3, DBaaS PostgreSQL holds document versions, application rights, and dialogue history, while the API and handlers run in KaaS. Qdrant is deployed independently within the same Kubernetes as a StatefulSet with PVC and Persistent Volume. This is an application component, and its data and regular snapshots are the responsibility of the application team. Response generation is handled by an external LLM via API; embeddings are created by a separate model.

When a document is uploaded, the handler saves the original file, extracts text, splits it into chunks, and calculates embeddings. When a user asks a question, the application finds the chunks accessible to them and passes them to the language model. This method of adding sources to the context is called RAG — retrieval-augmented generation.

Components are updated independently. A file might already be in S3, even though the handler hasn't finished writing all the vectors. The database might store a new version of a document while the index still contains the previous one. If only PostgreSQL is backed up, after a failure, you'll be left with references to files and chunks that no longer exist.

The unit of recovery in this case is a consistent set of application data. This includes specific document versions, their metadata, the state of the index, and the versions of code and models that can work with them. Backing up each storage is necessary, but it doesn't ensure consistency between them.

2. What AI Assistant Data Needs to Be Saved in a Backup, and What Can Be Recreated?

Let's start with an inventory. For each component, we need to know if there's an independent source for its restoration.

Embeddings and indexes are at different levels. Saved vectors allow rebuilding the search structure without re-querying the model. If only PDFs remain, you'll have to re-perform text extraction, chunking, and vectorization.

For an application with an external LLM, copying the provider's model is usually not possible. We save the identifier of the model used, query parameters, prompts, and tests. If the provider removes this version, even a full application backup won't restore previous behavior. A pre-tested replacement option is needed.

For embeddings, it's crucial to save the model itself or guarantee access to the exact version. A new model with the same dimensionality might create a different vector space. Old document vectors and new query vectors then cannot be considered compatible simply because they have the same length.

Dialogue history is backed up with stable conversation_id, message_id, message order, roles, content, organization, and attachment links. During restoration, we compare the messages themselves and their sequence, not just the line count. User-confirmed messages after the backup point will be lost if not saved via WAL or a separate log. The correspondence needs its own RPO.

For an agent, we save the operation key before the first external system call. After rollback, this key must remain the same. If the provider supports idempotent requests, repeating with the same key returns the same result. If such support is absent, we first look for an execution receipt. Unknown statuses are escalated to manual reconciliation rather than repeating the action automatically.

3. When Is It More Advantageous: Rebuilding Data vs. Restoring from a Copy?

The choice depends on the acceptable downtime and the cost of rebuilding. The entire path to a ready service must be evaluated: file reading, parsing, embeddings, vector writing, index building, and verification.

Suppose the corpus has a million chunks, and the same pipeline processes 100 chunks per second in a test. This part alone would take about 2 hours and 47 minutes to rebuild. Deploying infrastructure and verifying the search will require additional time. This is a calculated example, not a measurement from a specific platform.

If each chunk averages 500 tokens, re-vectorization will involve 500 million tokens. At a rate of p rubles per million tokens, the cost of embeddings alone will be 500 × p. Separately, calculate computations, object reads, network traffic, and engineer time. API limits and retries also affect recovery time.

Now let's compare with a copy. Transferring a 100 GiB snapshot at an actual speed of 100 MiB/s will take approximately 17 minutes. This is just the transfer: then the snapshot needs to be loaded into the engine, the index readiness waited for, and verifications performed. Speed should be measured on the chosen platform, not taken from network interface throughput.

A rule of thumb: rebuilding is suitable if its verified time, including preparation and validation, fits within the RTO. RTO is the target time for service return after a failure. If rebuilding takes longer, save at least the embeddings, and for faster startup, also regular index snapshots.

We set RPO separately — the acceptable loss of recent changes. A consistent copy from six hours ago might be technically sound but still not meet product requirements. For documents, dialogues, and completed actions, RPO can be set separately, but restoration must account for dependencies between them.

4. How to Organize Backups in S3, PostgreSQL, and Kubernetes

For this example, we'll use KaaS for the API, handlers, and Qdrant; DBaaS PostgreSQL for application state; and Reg.ru S3 for documents. The external backup circuit from Figure 1 is assembled separately. Surviving the failure of the entire working circuit is not guaranteed by placing the second bucket in the same infrastructure.

S3

For files, we calculate the SHA-256 of the content and record it in the recovery directory. We don't substitute it with the ETag value: for example, in Amazon S3, the ETag of an object uploaded in parts is not a standard MD5 of the entire file.

We separate the working bucket and backup copies by access rights. The application account should not be able to delete copies. Versioning in the same bucket helps restore a previous revision but doesn't eliminate the general risk of site failure or compromise of administrative rights.

In the chosen scheme, we build copy protection on a separate backup circuit and independent rights, without relying on the native Versioning and Object Lock of the working S3. If the backup storage supports Object Lock, configure the mode and retention period: in Amazon S3, locking protects a specific version and doesn't prohibit new versions or delete markers. Support for this mechanism is confirmed for the chosen storage, and application-level revision naming itself is not WORM protection.

The retention period applies to the entire recovery set. A database dump is useless if the lifecycle policy has already deleted the file versions it references. Decryption keys must also remain accessible throughout this period.

DBaaS PostgreSQL

Reg.ru's documentation describes automatic daily backups of database clusters, retention for the last 7 days, and restoration to a new cluster of the same configuration. New copies are not created for a stopped cluster. A new cluster allows verifying the result before switching the application; then, we update connection parameters and secrets.

The platform's technical description also mentions PostgreSQL backups to S3 via barman-cloud and CloudNativePG with PITR support. This is a database mechanism: it doesn't automatically restore the S3 corpus and Qdrant index to the same logical version. Regular copies are supplemented by our own export of a consistent set to an external backup circuit.

For a small application, you can start with a logical dump. pg_dump creates a consistent snapshot of a single database, even if writes continue. It doesn't synchronize this snapshot with S3 and Qdrant.

Example of export and restore to a pre-created empty test database:

pg_dump --dbname=service=rag_source \
  --format=custom --file=postgres.dump

pg_restore --dbname=service=rag_restore \
  --exit-on-error --no-owner --no-privileges \
  postgres.dump

Here, rag_source and rag_restore are libpq connection profiles. Passwords are not included in commands or the article. During restoration, we intentionally do not transfer owners and SQL privileges: roles and minimal permissions are created by a separate, verified script. User application rights stored in tables are included in the dump.

If a lower RPO is needed, consider physical base backups and continuous WAL archiving or the corresponding managed database mechanism. PITR requires a suitable base backup and a continuous log chain up to the recovery point; a single logical dump is insufficient.

In the recovery plan, we record the actual available PITR window and the method for specifying the point for a specific cluster. The presence of PITR in the architecture does not replace client scenario verification. For independent restoration, we save the export, server and client versions, extensions, roles, and settings. Server configuration files are not restored via WAL.

Reg.ru KaaS and Qdrant on Persistent Volume

In the repository, we store manifests or Helm charts, configuration values, and dependency versions. We fix images by digest and ensure their availability independently of the source cluster. Secrets are restored from secure storage; base64 in YAML is not encryption.

An etcd backup saves the Kubernetes API state but not the content of all Persistent Volumes or external S3 or DBaaS. For stateful components, we back up data separately. CSI snapshots depend on driver support and storage availability after failure. Their creation itself does not ensure consistency across multiple applications.

In our example, Qdrant is backed up using the regular collection snapshot mechanism. For a test environment, one node is sufficient. In a distributed setup, you need to consider the composition of shards and nodes; a single local snapshot cannot be automatically considered a copy of the entire distributed collection. The ability to restore is verified for a specific version and deployment scheme. The snapshot file is moved outside the source node.

We will not save the working database directory by simply copying files instead of using regular backups. When recovering from a logical error or attack, the copy might contain the same error: a suitable point is chosen before the corruption and verified in an isolated environment.

We've covered what data and artifacts need to be saved for AI application recovery and how to organize backups in S3, PostgreSQL, and Kubernetes. However, having copies of all components doesn't guarantee they will be consistent with each other after restoration. For example, the database might contain a new document version, while the search index refers to an old one. Or the restored copy might grant the user access to documents they've already had their rights revoked for.
