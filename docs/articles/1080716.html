I long thought Claude Code was hardcoded to the claude.ai account. Turns out, it's not: it's a standard client for an HTTP endpoint, and where it sends requests is configured by two variables. I needed this for a mundane reason: my workplace introduced an internal LLM gateway, and all traffic to models must go through it. While figuring this out, I stumbled over every possible pitfall. Below is what Claude Code actually needs from the endpoint, how to connect it in three ways, how to test before launching, and what the errors you'll inevitably see mean.

I won't name services or routers—that's not the point. Everything below works the same with a corporate gateway, your own proxy, or any third-party endpoint, as long as it speaks the right protocol.

What Claude Code Asks from the Endpoint

Claude Code communicates using the Anthropic Messages API. It needs an HTTPS address that responds to POST /v1/messages, and a key. That's it. If the endpoint only offers an OpenAI-compatible /v1/chat/completions—it won't work directly with Claude Code; that's a different protocol. Check with your gateway administrator which format they have before configuring anything.

The second question to ask the administrator is: in which header do they expect the key. There are two options, and your answer determines which variable you'll set:

  • Authorization: Bearer <key> — then you need the ANTHROPIC_AUTH_TOKEN variable

  • x-api-key: <key> — then you need ANTHROPIC_API_KEY

If they don't specify, use ANTHROPIC_AUTH_TOKEN, and the check below will tell you if you guessed correctly. Half of all 401 errors in this topic stem from putting the key in the wrong variable, sending it to the wrong header.

Method 1. Variables in Shell

The quickest way, good for trying things out:

export ANTHROPIC_BASE_URL=https://llm-gateway.example.com
export ANTHROPIC_AUTH_TOKEN=sk-gateway-key
claude

The downside is it only lasts in that terminal session. Open a new tab, and Claude Code will go to claude.ai again.

Method 2. settings.json

The persistent option. The file is ~/.claude/settings.json (on Windows, it's %USERPROFILE%\.claude\settings.json), under the env block:

{
  "env": {
    "ANTHROPIC_BASE_URL": "https://llm-gateway.example.com",
    "ANTHROPIC_AUTH_TOKEN": "sk-gateway-key"
  }
}

Two points that aren't written in large font. First: if the same variable is set in both the shell and settings.json, settings.json wins. I spent an hour figuring out why my export wasn't working—this was the reason. Second: don't put your key in .claude/settings.json within a project. This file gets committed and sent to everyone who clones the repository. For projects, there's .claude/settings.local.json, which is in .gitignore by default.

Method 3. apiKeyHelper

If your key rotates or is stored in a secrets manager, instead of a static variable, you can specify a command that prints the key to stdout:

{
  "apiKeyHelper": "~/bin/get-gateway-key.sh"
}

The command must print only the key, without banners or logs, otherwise Claude Code will pick up garbage, and you'll get the cryptic "Your apiKeyHelper script is failing." The key from the helper is sent immediately in both headers, so the question of 'bearer or x-api-key' is irrelevant here.

Check the Endpoint Before Launching Claude Code

This is the main advice of the article. Don't launch claude until you've verified with curl that the endpoint is live and the key is valid:

curl -X POST "$ANTHROPIC_BASE_URL/v1/messages" \
  -H "Authorization: Bearer $ANTHROPIC_AUTH_TOKEN" \
  -H "anthropic-version: 2023-06-01" \
  -H "content-type: application/json" \
  -d '{"model":"claude-sonnet-4-6","max_tokens":32,"messages":[{"role":"user","content":"ping"}]}'

If your gateway expects an x-api-key, replace the Authorization header with x-api-key: $ANTHROPIC_API_KEY.

How to interpret the response:

  • You get JSON starting with {"id":"msg_ and containing "content":[...] — everything is working.

  • You get an error about an unknown model—that's also good: the address and key are correct, the gateway authorized you and only then denied the model. This means you need to find out how models are named on that specific gateway (see below).

  • 401 — the key is wrong or in the wrong header. Try the other header before contacting the administrator.

  • 403 with an HTML body like "403 Forbidden," and the gateway logs show no request—something is blocking you en route: CDN, corporate proxy, regional filter. This is not a Claude Code issue.

Only after a successful curl should you launch claude, send any message, and type /status. In the Status tab, you should see two lines: Base URL with your address and Auth token (or API key) with the variable name. If instead, it shows Login method with a claude.ai account—the variables didn't reach the process.

Model Names

Internally, Claude Code uses aliases opus, sonnet, haiku, and runs background tasks on the haiku class. If your gateway uses different names for models than Anthropic, or is missing some—specify the mapping:

{
  "env": {
    "ANTHROPIC_BASE_URL": "https://llm-gateway.example.com",
    "ANTHROPIC_AUTH_TOKEN": "sk-gateway-key",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "sonnet-name-on-gateway",
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "opus-name-on-gateway",
    "ANTHROPIC_DEFAULT_HAIKU_MODEL": "haiku-name-on-gateway"
  }
}

The line about haiku is particularly important: Claude Code uses this model for utility tasks, and if it's not available on the gateway, you'll get a 404 at the most unexpected moment, even if the main model is working. The ANTHROPIC_MODEL variable sets the default model for new sessions, and the --model flag overrides everything for a single session.

What You Lose by Leaving the claude.ai Gateway

I'll list them honestly, because you find out about them after the fact:

  • The claude.ai subscription is not used while a key variable is set. Traffic is billed by tokens to whoever owns the key, and subscription limits do not apply to it.

  • Remote Control and voice input are unavailable—they are tied to the claude.ai account.

  • Anything the gateway cannot forward (new beta headers, thinking, cache) will not work for you. Claude Code updates frequently; the gateway must keep up.

A Word on Common Errors

  • A warning at startup about two authorization sources, "auth may not work as expected." A key from a variable and a saved claude.ai login are active simultaneously. Either remove the variable or use /logout so only the key remains.

  • 401 invalid token. The key was not issued by this gateway or was sent in the wrong header. Refer to the table above.

  • Claude Code asks for login, even though curl works. Variables were not inherited by the process: new terminal, IDE started from a different shell. Move them to settings.json.

  • 400 mentioning thinking or adaptive. The gateway doesn't understand Claude Code's new parameters. This is an issue for the gateway administrator.

  • Timeouts on long responses. By default, a request waits 10 minutes; API_TIMEOUT_MS is in milliseconds if you need more. If going through a proxy—check that the proxy itself isn't cutting the connection earlier.

A Word on Proxies

HTTPS_PROXY and ANTHROPIC_BASE_URL are for different things. The former tells where to go externally, the latter—where to send requests. They can be combined: the base URL points to the gateway, and the proxy is needed because you can't reach the gateway otherwise. NO_PROXY excludes hosts by comma separation. If Claude Code "doesn't work over VPN," in nine out of ten cases the problem is that the proxy is set for the shell but not for the process from which the IDE is launched.

Instead of a Conclusion

Claude Code is a standard client, and you can direct it anywhere as long as it speaks the Messages API. But "can direct" doesn't mean "should trust": based on the gateway's response, you can check at least two things—what was returned in the model field and whether cache_read_input_tokens appears in usage on repeat requests.
