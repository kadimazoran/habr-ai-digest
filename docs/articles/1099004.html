We build business modules on ELMA 365: contracts, counterparties, correspondence, powers of attorney, bonds. AI agents are doing more and more of this work. They edit forms and scripts, run checks, write documentation and reports.

Sounds like an advertisement. But the first few weeks were different. Two agents worked in the same project folder simultaneously. One spent hours running the browser, the other quietly did its task. And a commit from either could pick up garbage left by its neighbor.

This is the first of seven articles. In it, I will tell you how we restructured our work so that agents bring value and don't break things. Spoiler: the main thing turned out to be not the models or the prompts. But the rules we wrote while stepping on rakes.

Starting Point: An Agent Does a Lot, But Not Everything

I have been managing IT for over twenty years. I am used to every employee having a zone of responsibility, access rights, and a clear process for submitting work. With agents, I initially forgot about this.

It seems like an agent is just a fast developer. Give a task, get a result. But an agent has no memory of yesterday's conversation. It doesn't know that another session is currently editing the same form. It confidently confuses servers if the variables in the settings are named poorly.

This is exactly what happened to us. There are two development servers. The variable names in the configuration have been historically mixed up: a variable with an "obvious" name points to the other server. The agent did the task on the wrong server several times in a row. In one case, it compiled and checked the fix entirely, and then it turned out that the server was wrong. I wrote something like, "You're confusing everything again." The work was redone from scratch, and on the correct server, the widget turned out to be structured completely differently.

After this, a separate line appeared in the agent's instructions: read the address, not the variable name. And the general conclusion: an agent needs not freedom, but a framework. Clear, written, verifiable.

Rule One: One Task — Its Own Project Copy and Its Own Log

The first framework is isolation. Since October, each task lives in its own branch and its own project working copy (git worktree). All working copies are located in a single service folder within the project. Working in the main copy is not allowed, only viewing.

This solves the problem of folder neighbors. Two agents no longer share drafts, temporary scripts, and exports. Each commit contains only its own work.

But there is a nuance that we recorded separately. A working copy isolates files. It does not isolate live objects on the server. If two agents edit the same process in ELMA 365, separate folders will not help them. Therefore, before editing on the server, the agent records which object it is "occupying" and checks if someone else has changed it.

The second half of the rule is the task log. It records every changed object: form, widget, process, file, test record, temporary access. And not just "what was changed," but how:

  • the state before the edit and the object version;

  • the method of editing: through the interface, API, or utility;

  • the result and what was actually applied to the server afterward;

  • what was created temporarily and how it was removed.

A screenshot by itself is not considered proof. An export or server response is needed. Unsuccessful and partial records also go into the log. Especially those.

Why so much bureaucracy? Because after two weeks, no one remembers who changed the button on the approval form and why. Neither a person nor an agent. But the log remembers.

Rule Two: Production Only for Reading

On October 15, I issued an unequivocal order. The production system is read-only. Agents do not save, publish, create, or delete anything there. Ever. Not even for "just checking."

Reading, however, is allowed and necessary. Users complain about documents that live precisely in the production system. The agent opens a record, a task, a process history, and sees the same thing a person sees.

To make "read-only" not a promise but a technique, the browser session in the production system sets a request filter. It only allows reading, login, and search, and cuts off everything else before the page even sends anything. After work, the saved session is deleted.

Fixes are collected and checked on the development server. They only reach the production system through the partner company's deployment process. For this, we maintain a registry: for each change, there is a card with the scope, steps for testing and production, and a list of checks that can be done in production in read-only mode.

This is slower than "quickly fixing in production." But production has a single, responsible path for changes.

Rule Three: "Published" Is Not Yet "Working"

This is where we stepped on the most painful rakes.

We added protection against repeated approvals to the contract and power of attorney approval processes. If a person has already approved a document at one step, they are not prompted a second time. Everything compiled, tests on stubs passed, publication was successful.

And then it turned out that a new contract failed at the very first approval step. Any new contract. The reason was in the platform's behavior, which was not present in the tests. The list of file versions returns only superseded versions. A file uploaded once has an empty list. The code did not account for this.

Fortunately, it was the development server. It was fixed the next day. But we strictly recorded the conclusion in the rules. Compilation, package check, stub tests, and reading the object after writing only prove their own validity. None of these checks replace going through the actual business process.

Now, after publication, the change has the status "published, verification not completed." To remove it, you need to:

  1. Re-read from the server everything that has changed, in the exact version that was published.

  2. Compare this with what was accepted before publication.

  3. Go through the affected process again, with fresh test data and real form buttons.

  4. Ensure that all temporary items have been removed.

And a separate line that I repeat most often: a "server responds" check is not proof. The import completion code is not proof. A completed child process is also not proof. "Compiled," "imported," "published," and "checked" are four different words, and the agent must distinguish them in the report.

For processes, we have a mandatory matrix of cases. Normal completion. Empty participant list. Repeated participants. Return for rework and resubmission. Cancellation. If the task touches files or users, this is supplemented by file replacement, reassignment, substitution. "Not applicable" without explanation is not accepted.

Rule Four: The Checker Is Not the Author

An agent who wrote the code is bad at seeing their own mistakes. Just like a person. Only an agent also writes very convincingly that everything is ready.

Therefore, the work is not accepted until an independent reviewer confirms it. This is a separate agent who did not do this work. They receive the exact version of the result and check it themselves. They do not re-read the author's report but write their own checks.

In the logs, this looks routine: author's tests, separate reviewer checks, and a note that everything passed on the exact version that was checked. If the reviewer made a mistake in their own check, that is also recorded, along with the corrected repeat.

Even merging into the main branch happens without me. But only if an independent reviewer has confirmed the exact version of the changes and the automatic build has passed. If the code changes after the check, the check is invalid.

This is not about distrusting agents. It's about the confirmation being tied to a specific result, not to a feeling of "it seems ready."

Episode: The Agent Stopped Before the Final Click

Now, two stories that, frankly, made me want to start the series.

First. We spent a long time figuring out if configuration changes could be made through files, not just the visual designer. The agent exported the solution, made edits, and tried to upload it back. The upload utility failed with the same error. The agent narrowed it down to the minimal request and prepared an email to the vendor's support with exact reproduction steps. This, by the way, is useful for anyone working with the same platform: a finding, not a complaint.

There was one more path. The same package could be processed through the configuration update wizard in the admin panel. The agent reached the step after which the actual application begins. And stopped. The protection mechanism of the session itself triggered, and the agent did not bypass it.

In its report, it was noted: left for a human, not an agent. If you want an answer to this question, a human must press the button.

A similar story happened with linking servers for regular deployment. The agent itself opened the necessary dialog and went through everything around it. A protection triggered on the access token field: agents are not allowed to put secrets into another system's storage themselves. It did not bypass it. It closed the dialog without saving and checked that nothing remained after it. In the report, it honestly wrote: this field must be filled by a human, I will finish the rest.

At first, I was annoyed. Then I realized that this is exactly the behavior I want. An agent can lead me to the button. But the button that changes the real system or leaves a secret in someone else's place, I press.

Episode: The Agent Checked the Task Against Reality

I like the second story even more.

We planned to switch to ELMA 365's standard deployment mechanism between servers. I wrote a detailed task. Its basis: the main development server is the source of truth, and changes are transferred from there to the test server. The task explicitly stated that the main server had recently been updated and was newer.

The agent did not immediately build the transfer. As a first step, it checked the platform versions on both servers. And it turned out that it was the other way around. The main server was more than a year behind the test server in releases.

What's more. The test server had months of manual modifications that were not on the main server. Transferring "as written in the task" would overwrite this work with an older version of the solution. And to a platform version for which this build had never been tested.

The agent wrote a report with the heading "contradicts the original task." It proposed two honest options: first, align the versions, or second, reverse the transfer direction. And asked me to decide which server to consider the source of truth. It did not decide for itself.

After this, I added another strict rule about that server. But the main point here is different. A human writes the task, and a human makes mistakes. A good performer first checks the input data against reality. I now expect the same from an agent as from a strong engineer: check what you are relying on before moving anything.

How an Agent Reports: "What We Need From You"

The agents' reports were terrible at first. Tables, file paths, version identifiers, log excerpts. I read them for a long time and in the end, I didn't understand the main thing: was anything needed from me or not?

In early October, I introduced a format that we kept forever. The report is short, in simple Russian. The first block is "What We Need From You": only actual decisions or actions, one line for each. If nothing is needed, it says so. The second block is "What Was Done," two to four short lines. No tables, paths, or internal names.

Along with the format came the rule about work distribution. The agent does all the technical work itself: commits, cleanup, repeated exports, checks, documentation. It does not send me a command "please execute." It does not ask "commit?". It only asks about real decisions: architecture, business choices, everything irreversible, and everything related to the production system.

Details, meanwhile, do not disappear anywhere. They go into the project documentation and the task log. Conclusions go into the chat.

The best effect was unexpected. When an agent cannot hide a problem in a table, it is forced to formulate it. "This field must be filled by a human" — one line, and it's immediately clear what to do.

"Finish It, Clean Up After Yourself, Explain the Essence"

This rule appeared simultaneously with the report format. Each task ends with three things, not one.

Finish It. Don't stop at the plan or half the result. If the remaining steps can be done by yourself, do them.

Clean Up After Yourself. Everything that the task created and that is not the result. Temporary files, test solutions and records on servers, saved browser sessions, exports. If something on the server was changed only for testing purposes, return it to its original state and prove it with a repeated export that matches the original byte for byte. If something cannot be deleted, say so directly.

The latter is more important than it seems. For example, in ELMA 365, you cannot delete a business process. This is a platform limitation, not agent laziness. The agent renames a dropped draft process with the note "not used" and records this in the report. An honestly left trace is better than a silent one.

Explain the Essence. A person needs meaning. What can be done now, what cannot and why, what remains.

A Constitution for Agents

We have several projects around ELMA 365. To prevent the rules from diverging, we have moved the common ones into a separate document, which we call the constitution internally. Each project refers to it and can add its own rules, only stricter, not softer.

If you rephrase it in simple terms, it will be something like this.

Who is the owner and what only they decide. There is a short list of things that the agent does not do without me. Writing to the shared development server, which we share with a partner. Any actions in the production system. Choosing where and when to release changes. Accesses and accounts. The owner's order permits exactly the action named in it, and nothing more.

Everything else, the agent finishes themselves. In October, I explicitly said: finish the work without waiting for me. On our additional server for experiments, agents can install and check anything within the scope of the task, without a separate permission each time. At the same time, the agent never opens a file with secrets and does not handle token values.

Approval without proof is not considered valid. You cannot write "checked" if the check was not observed. You cannot retroactively mark "passed" for old work that had no initial state. What did not happen is recorded as "did not happen."

The checker is not the author. I have already written about this above.

Stops are categorized. This is my favorite part. Without it, agents stop and ask for any reason. Therefore, each typical stop has a class and a method of handling:

  • network failure or service limits — wait and retry, don't ask me;

  • failed tests, merge conflict, outdated branch — fix it yourself, this is not a reason to stop;

  • no external proof — record what you tried to do, keep this item open, and continue with the rest of the work;

  • action requires my decision — state which rule was triggered, and continue working on what you can;

  • if the solution is already clear and only a human step remains — state exactly which step;

  • incident — escalate immediately.

This has significantly reduced the number of "can I...?" questions. An agent no longer asks permission to fix a failed test. And is not afraid to stop at a button that changes a live system.

What You Can Take Away From This

You don't have to build such a system entirely. Here's what I would implement first if you are just starting to work with agents in low-code or in regular development.

A separate working copy for each task. It's cheap and immediately eliminates a whole class of strange commits.

Production system read-only. Not by agreement, but by technique: a request filter or a role without write permissions.

Distinguish between "published" and "working." Let the report state exactly which check passed and what it proves.

Independent verification. A second agent who didn't write the code catches surprisingly much.

A report format that starts with "What We Need From You." You'll be surprised how much time it saves.

And the rule of the final click. Decide in advance which buttons only a human presses. Write it down. And be happy when an agent stops at such a button.
