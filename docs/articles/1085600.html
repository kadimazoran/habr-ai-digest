A practical breakdown of a solution using a real corporate FAQ bot.

A shift supervisor at a warehouse opens the corporate AI assistant and types in the chat: "What should be done if a driver is late with a delivery?" A few seconds later, an answer appears – clear, correct, with a link to the source: the logistics operations regulations. It can be downloaded.

Now, imagine the same employee asks another question: "How much do we pay carriers per kilometer?" There's nothing stopping them from asking this. What matters is what happens next. If the file with the rate schedule is in the same database as the regulations, the assistant will respond politely, accurately, and attach a download link.

This is the problem. We've solved semantic search and achieved good answers. But the next complex task is to ensure the assistant only answers based on what a specific person is permitted to know.

Briefly: What is RAG?

Large language models know a lot about the world and nothing about your company. They have never read your onboarding materials, contract templates, or incident reports from last quarter. Retrieval-Augmented Generation (RAG) closes this gap. The term appeared in a 2020 paper by Patrick Lewis and colleagues from Facebook AI Research, and the idea is simple. Before the model answers, the system retrieves (via vector search) the most relevant snippets from your own documents and passes them to the model as context. Then, the model generates an answer based on these snippets and can indicate the source of the information.

Under the hood, documents are split into fragments (chunks). Each chunk is converted into an embedding— a set of numbers, a vector that reflects its meaning—and stored in a vector database. When a question comes in, it's translated into an embedding in the same way, and the database returns chunks whose vectors are closest to it. This is why a query like "driver was late" finds a paragraph under the heading "Handling Late Arrivals," even though they have no common words.

The approach has spread rapidly. Morgan Stanley provided its financial advisors with a similar assistant, working on top of about 100,000 internal analytical reports and documents, and according to the company, over 98% of advisor teams use it. The same approach can be found almost anywhere there are more documents than people can remember:

  • Logistics and Transportation

  • Law Firms

  • Online Schools and Course Sellers

  • Medicine, Insurance, Banking, HR Departments, IT Support: anywhere people repeatedly ask the same questions to a mass of PDF files.

But Not Everyone Is Allowed to See Everything

Each of these organizations has an access hierarchy. A legal assistant should not be browsing client cases from another team. An online school support employee needs the return policy, but not the partner commission table. In the security department, an employee should know the instructions for their assigned sites and doesn't need to read the vulnerability report for other sites, let alone clients.

Moreover, boundaries don't always align with document boundaries. An employee handbook might be open to everyone except for one chapter—about disciplinary procedures and salary ranges—which only managers and HR should read. One file — two audiences.

Without access control, a RAG system erases all of this. It becomes the most effective data leak tool the company has ever implemented: it answers in plain language but also provides links to sources.

This isn't hypothetical. Microsoft Copilot implementations have encountered precisely this problem, termed oversharing—excessive access. The assistant respected existing permissions, but due to years of careless access granting in SharePoint, salary data, HR files, and strategic documents became accessible with a single query. Security vendors state it directly: AI didn't create new access issues; it made existing bad access trivially discoverable. OWASP now includes insufficient access control to vector stores in its Top 10 for LLM Applications (LLM08: Vector and Embedding Weaknesses).

The Good News: It's Still Just Data Segregation

RAG might seem like a new type of system, but at its core, it's a database query. "Find the five chunks closest to this vector" is a SELECT with an unusual ORDER BY. This means old data segregation rules still apply.

The main rule is to filter before the model sees anything. A system prompt like "do not reveal confidential information" is not access control. A language model can be persuaded to ignore instructions. Once a forbidden snippet enters the context window, it's too late. Only a document that was never retrieved is truly safe.

With this rule in mind, there are four common ways to segregate data:

  1. Physical Isolation: A separate database or deployment for each client or security zone. The strongest boundary and the most expensive. Suitable for regulated industries and different clients.

  2. Logical Partitions: One database, but a separate collection, index, or namespace for each role or group. Each query goes to exactly one partition; others are unreachable for that query.

  3. Metadata Filtering in a Shared Index: Each chunk carries labels like allowed_groups: ["hr", "managers"], and each search includes a filter by user groups. Flexible and granular. The weak point is that one missed filter in a single code branch is enough to leak everything. Pinecone and Oso offer good explanations.

  4. Authorization at Query Time: First, candidates are retrieved, then each is checked against permissions in the source system (SharePoint, Google Drive, an authorization service like OpenFGA), and only then is it passed on. Permissions are always up-to-date, but this is slower and more complex to implement for large volumes.

Real-world systems often combine several approaches. Our FAQ bot uses the second.

Our Approach: One Folder Per Role

In our project—a FastAPI backend with a LangGraph agent and PostgreSQL/pgvector—the rule is: a role is a folder, and a folder is a collection.

Example:

documents/

├── faq/ → general knowledge base for everyone

├── support/ → support team: regulations, escalation, return policy

└── management/ → managers: all of the above + salary ranges, disciplinary chapter.

A mapping in the configuration links roles to these collections ({"administrator": "faq", "support": "support", ...}). When an administrator manually starts indexing (chunking and vectorization), or it happens automatically, the system iterates through each folder and writes the embeddings of its files into that folder's own pgvector collection. A document from support/ will never end up in faq/.

This also solves the problem with the employee handbook. The client maintains two versions: a full one in management/, and a version without the sensitive chapter in the general folders. Editing happens where people already understand it—in the documents themselves, not in the code.

Why Folders Work Well

  • Clear Boundaries. Anyone can open the directory tree and see who reads what. No one needs to understand label combinations or policy files.

  • Familiar Interface for the Client. Business owners know how to work with files and folders. Deciding what a role sees means moving a file to a folder. The same structure maps to a shared drive like Google Drive or SharePoint, so the client can manage access in a tool they already use.

  • Robust Build-Time Isolation. The search engine for each query is created for exactly one collection, so a query cannot reach data from another role, even if the model requests it.

  • Simple Auditing. The question "what documents does support see?" is answered by the command ls documents/support.

And Where They Fall Short

  • Duplication. A document needed by three roles resides in three folders and is indexed three times. Copies diverge when someone updates only one of them. Compromise: more data in favor of simplicity.

  • One Role Per User. An employee who is simultaneously "support" and "sales" doesn't fit the scheme well—either a composite role or a shared folder is needed.

  • High-Level Segmentation. Access at the chapter level means manually preparing separate document versions.

For a small or medium-sized company with a few clearly defined roles, these costs are minor, and the clarity is invaluable. At the scale of a large enterprise with thousands of overlapping groups, metadata filtering or query-time authorization usually wins.

User Journey Step-by-Step

Here's what happens when an employee asks a question:

  1. Login. The user authenticates and receives a signed JWT with their ID and role. Blocked users are filtered out at this stage and with every subsequent request.

  2. Question. The message is sent to the backend with the token in the Authorization header.

  3. Collection Determination. The server looks up the user in the database and maps their role to a collection name. The role is taken from the server's own records. Nothing sent by the client can change it.

  4. Search. The output of the agent tool search_documents is returned only for this collection. From the perspective of this query, documents from other roles do not exist.

  5. Answer. The model writes an answer based on the retrieved chunks and streams it via SSE along with source links (filename and text snippet), which are displayed in the sidebar.

  6. Private History. Conversations are stored separately for each user, so no one can access another's chat by guessing its ID.

Access verification happens at step 3. By the time the model gets involved, the data has already been narrowed down to what this user is permitted to see.

The Invisible Leak: The "Download" Button

Source links are one of RAG's best features. Users trust answers they can verify, so in our source panel, you can click the filename and download the original.

But this button is also an easy way to leak data. It's tempting to make it a static link like /files/management/salary-bands.pdf, served directly from disk. Then, any user who guesses this URL or gets it from a colleague will download the file regardless of their role. The search will be securely locked down, but the download will be open to everyone.

We've specifically focused on the download endpoint:

  • Authentication Only. GET /documents/{filename} requires the same JWT as the chat. The frontend requests the file with the token in the header, converts the response to a blob, and triggers the browser's "Save As" dialog. The token never ends up in the URL, where it could leak into logs or browser history.

  • Within Role Folder Only. The server re-determines the user's collection (it trusts nothing sent by the client) and searches for the file only within documents/{collection}/.

  • Path Traversal Protection. Filenames are escaped. Anything containing .., directory/file separators, or absolute paths is rejected, and the final path must pass a strict relative_to(collection_root) check.

  • No Fact of Existence Leaks. A file that resides in another role's folder returns 404—just like a file that doesn't exist at all. A 403 response would confirm to an attacker that salary-bands.pdf actually exists.

  • No Special Cases. Even an administrator only downloads from their own collection. Every exception to the rule is a place where something can break.

  • Covered by Tests. Automated unit tests verify the standard scenario, failure on accessing another role's data, path traversal attempts, unauthenticated requests, and missing files.

The principle is: every channel through which data leaves the system needs its own check—the response, the snippet in the source link, the download, the chat history, and any logs.

Other Isolation Methods

If folders aren't suitable for your organization, consider these options:

  • ACL in Metadata within the Same pgvector Table: Each chunk is tagged with allowed groups, and each query is filtered by them. Works well when documents are shared among many overlapping groups.

  • Row-Level Security in PostgreSQL. Since pgvector lives inside Postgres, the database itself can enforce the rule "this session only sees rows belonging to its groups"—even if the application code forgets the filter.

  • ACL Synchronization from the Source System (Google Drive, SharePoint, Confluence) into chunk metadata, so the AI assistant inherits the permissions people already maintain in the data sources. The Copilot story serves as a warning here: bad permissions are inherited too, so check them first.

  • Relationship-Based Authorization (systems like Zanzibar, e.g., OpenFGA or SpiceDB) for complex "who can see what" graphs with checks at query time.

Conclusion

A RAG assistant is trustworthy only to the extent that the weakest path to data is secured. Choose a segregation model that can be explained in one sentence. Filter data even before the model sees any context. Then, repeat the same check for every other channel through which data leaves the system—especially for the "Download" button.

Our version in one sentence: your role is your folder, and everything outside it doesn't exist for you. This isn't the most flexible design, but the client's office manager can understand, verify, and maintain it simply by dragging files between folders.
