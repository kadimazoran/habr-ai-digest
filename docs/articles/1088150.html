How Minor Routine in Work Turned into a Set of Tools Used by Thousands of Designers

I made the first plugin for Figma without any grand idea. I was simply curious: how difficult is it to create your own plugin if you are a designer, not a developer?

I have over 10 years of experience in product design, currently leading a design team at Kupibilet, and I work in Figma almost every day. Code has never been my primary profession.

But at some point, AI tools reached a state where it became interesting to test: could I take a small idea and bring it to a working product myself?

Thus, the first plugin appeared.

The First Plugin Was Just an Experiment

CGrab: Color Palette from Image.

The mechanism is simple: you select an image, run the plugin, and it extracts the main colors and creates a frame-palette from them, which can then be used in the layout.

I didn't do any market research, of course. I just wanted to go through the entire process myself:

  • come up with an idea;

  • figure out how the Figma Plugin API works;

  • explain to the AI what exactly should happen;

  • launch it all within Figma;

  • publish it.

And at some point, it actually worked. For me, this turned out to be more interesting than the plugin itself.

Before this, the thought "it would be great if Figma could do this" usually ended predictably: either you look for a ready-made plugin, or you do it manually, or you just give up.

But here, suddenly, another option appeared:

create it yourself.

After that, it became hard to stop.

Most Ideas Started with Minor Annoyances

I didn't sit down in the morning with the task "today I need to come up with a new Figma plugin." Usually, it happened the other way around.

I would be working, performing the same action several times in a row, and at some point, I'd catch myself thinking: why am I still doing this manually?

For example, large Figma files. After some time, hidden layers, empty frames, forgotten groups, old layout fragments, and all sorts of junk after dozens of iterations inevitably appear there.

You can periodically go through the file manually. I decided to create Clean Hidden & Empty Layers.

The plugin goes through the page, finds hidden and empty layers, and helps to quickly clean them up.

It's a very small tool, and perhaps that's why I like it.

Launch → check → clean → continue working.

Without a separate process and without another task to keep in mind.

Smart Randomizer Appeared from Product Work

There's a classic layout problem.

You have neat data everywhere:

Ivan Ivanov
$100
12:00

Everything fits nicely, everything is perfectly aligned. But then, in a real product, a long name appears, a six-digit sum, or a city that takes up two lines, and the component suddenly stops being so perfect.

That's why I created Smart Randomizer.

It substitutes random data directly into text layers: names, cities, times, sums, numbers, and other values.

Then came various countries, languages, time formats, currencies, and number formatting.

And here I started using the plugin not just for speed. It's a convenient way to quickly stress-test the interface and see:

  • where text doesn't fit;

  • where Auto Layout breaks;

  • where numbers push adjacent content;

  • where a card only works well with ideal data.

  • to look at the layout with "real" data;

Of course, this doesn't replace testing. But it's a good way to stop designing a product solely for the hypothetical Ivan Ivanov.

Then I Started Packaging Almost Everything I Was Missing into Plugins

The pattern became quite clear.

If an action is regularly encountered in work and can be shortened, I try to create a tool.

Thus, ColorLab. appeared.

I periodically need to quickly adjust an image right while working on a layout:

  • brightness;

  • contrast;

  • saturation;

  • effects;

  • some quick visual experiments.

I don't always want to switch to other software for this.

Then Easy Palette appeared for working with palettes for light and dark themes.

And around this point, I noticed that my attitude towards the plugins themselves had changed.

With the first CGrab, I was thinking something like:

"Cool, it actually works."

After a few more plugins, I started treating them as small products.

Completely different questions arose: how will a person understand what needs to be done here? How many actions will they need? Is this setting necessary at all? Can another button be removed? What should happen immediately after launch? Is an instruction needed, or can the interface be made so intuitive that it's not required?

In the end, you're creating a small utility for Figma, but you're doing regular product design. It's just that the product itself is much smaller.

Perspective Quickly Reminded Me That Vibe-Coding Isn't Magic

Some ideas sound very simple until you start implementing them.

For example: "I want to change the perspective of a vector object."

Thus, Perspective. appeared.

At the interface level, everything is clear: there's an object, there are controls, you change values, and you get a new perspective.

But it's one thing to draw a few sliders. It's quite another to make all this work correctly with vector geometry within Figma.

And this is where the real friendship with vibe-coding begins.

Sometimes you describe a task, and after a few minutes, you get a quite workable solution. Other times, the AI writes very convincing code that doesn't work at all.

The familiar cycle begins:

  1. fix one problem;

  2. break another;

  3. change the approach;

  4. get a new bug;

  5. go back;

  6. gradually start to understand what's going on;

  7. ran out of tokens - no more vibe-coding;

  8. return to step 1.

Perspective well reminded me of one simple thing:

AI has significantly lowered the entry barrier to development, but it hasn't started thinking for you.

You still need to formulate the task properly, break it down into parts, understand what result you need, check corner cases, and notice when technically everything works, but it's inconvenient to use.

There's a lot in common with design work here. Except now your developer lives in the terminal and never gets tired of your edits.

WordGlue Appeared Because of Dangling Prepositions

One of my simplest plugins is called WordGlue.

I constantly work with text: interfaces, product screens, banners, presentations. And I was always annoyed by short prepositions and conjunctions that end up at the end of a line.

This is the type of problem for which no one would ever create a formal task. You just manually insert a non-breaking space. Then another. Then another.

At some point, I got tired of it.

Thus, WordGlue appeared.

It goes through text layers and automatically inserts non-breaking spaces where they are needed. You can process the entire file or only selected layers.

Later, I added support for multiple languages.

Figma is also gradually improving its text handling, but I still like my scenario: launch the plugin → click the button → done.

I know the necessary layers are processed, and I don't think about it anymore.

They don't have to do much. Sometimes it's enough to perfectly solve one annoying problem.

WordGlue, perhaps, best describes how I now view small tools.

And My Favorite: ShapeFlow

Now I'll return to the second plugin I created.

ShapeFlow: Organic Shapes Generator.

Now more than 20,000 designers use it. And it's still a bit strange to write that.

Initially, the task was as down-to-earth as possible. I wanted to quickly create blobs, waves, organic shapes, and abstract graphic elements directly within Figma.

Of course, you can draw all this manually. You can open a separate generator, create the shape there, export it, and come back.

But I wanted to just open a plugin and get the result right there.

So I made it.

I had no plan to gain tens of thousands of users. It was completely unclear if anyone other than me would use it.

But after publication, the numbers started to grow: first a few people, then hundreds, then thousands, tens of thousands. Now over 20,000.

And this, perhaps, is the most pleasant thing in the whole story.

You create a tool in the evening because it was convenient for you to use. And then, somewhere in another country, a stranger opens Figma and uses your thing in their work.

You have no idea what they are designing right now, but you've contributed a small piece to their workflow.

I really like that.

Why I Like Vibe-Coding Anyway

I don't consider myself a developer. And I never aimed to become one.

For me, vibe-coding is interesting for other reasons. It has significantly shortened the distance between two states:

"I have an idea."

and

"Let's see if it works at all."

Just a few years ago, the path for a small utility would have looked something like this:

  1. an idea appeared;

  2. described the task;

  3. found a developer;

  4. explained the mechanics;

  5. designed the UI;

  6. waited for the first version;

  7. started fixing.

For an idea the size of WordGlue, this is simply too expensive in terms of time and effort. Therefore, half of such things would have remained just ideas.

Now the scenario is different. You can open Codex/Claude in the evening, describe the mechanics, build the first version, connect it locally to Figma, and quite quickly test a real product.

Didn't work? No big deal.

Worked poorly? Redone.

Turned out to be useful? You can move on.

For me, this is where the most interesting shift occurred:

the cost of testing a small idea became much lower.

And the number of things I want to try immediately increased.

After This, You Start Looking at Your Work Differently

I've noticed that I now more often catch myself asking: why am I doing this manually?

If I repeat an action for the tenth time, maybe it can be automated.

If a scenario requires five steps every time, can it be reduced to one?

If you constantly have to leave Figma for another tool for one small operation, can it be moved inside?

Essentially, this is ordinary product thinking.

We constantly look for such problems in users: what is repeated, where a person wastes time, where there are too many steps, where there is unnecessary friction.

It's just that in this case, the user is sitting at your own laptop.

And 20,000 Users Aren't Necessary at All

ShapeFlow, of course, is the most prominent example. It's very pleasant to see 20K+ users.

But I wouldn't say that this specific number makes a plugin successful.

If WordGlue saves me time a few times a week, it's already useful. If Smart Randomizer helps quickly populate a screen with data, great. If the next plugin is used by a hundred people, but constantly, that's also a good result.

I generally like the idea of small tools precisely for this reason.

You don't have to immediately build a SaaS, invent a billion-dollar business, seek investment, spend a month choosing a niche, and build a huge roadmap.

Sometimes you just notice a small problem and create a small solution for it.

And then anything can happen.

Instead of a Conclusion

Lately, AI has given designers a rather interesting opportunity.

We can still do our main job: research, design, think about users, look at metrics, and create interfaces.

But alongside, there's another tool.

If something is missing, you can try to create it yourself:

  • a Figma plugin;

  • a small service;

  • a prototype;

  • an internal team tool;

  • an experiment that would have otherwise remained a note in Notion.

For the first version, you no longer necessarily need to find someone to write it for you.

But AI, at the same time, doesn't solve the most complex part of the work.

It doesn't know what is actually worth doing. It doesn't understand which problem truly annoys the user. It doesn't sense when an unnecessary button has appeared in the interface. It doesn't decide which function is needed and which is better to remove altogether.

This is where a person is still needed.

For me, vibe-coding hasn't become a way to become a developer. It has simply removed a rather large wall between:

"it would be great to do this"

and

"I've already made the first version, let's take a look."

And sometimes, you then go to Figma Community and see that twenty thousand people are using this first version.

Also not bad.

Don't be afraid to do small things. Not every idea has to become a big product, not every experiment has to bring money, and not everything has to work out the first time.

If something seems useful, try to build it. If something annoys you, maybe it annoys someone else too. Experiment, share your results, and create things that make someone's life even a little bit easier.

After all, sometimes it all starts with the thought: "What if I try?"
