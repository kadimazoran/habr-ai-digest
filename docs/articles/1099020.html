About Morse or Morse About

I thought for a long time about how to name the article, but I chose this particular title, fashionable, and perhaps already very annoying with the prefix AI. It is already clear that it will be about neural networks, but what does Morse have to do with it? I'll tell you now!

It is no secret to anyone that the Morse code is used literally everywhere where data needs to be transmitted over long distances through blizzards and storms, through thunderstorm noise, through... in short, even by tapping a spoon on a battery. Morse code saved lives, helped find lost ships and planes. Even now, for a ship captain or an airplane pilot, knowledge of Morse code is a requirement dictated by safety in extreme situations.

A long, long time ago, when Flash still reigned and I was young and handsome, I decided to create a cool Morse code program. You can read the full story here, if anyone is really interested. As a result of this experiment and a series of iterations for improvement, a decent application with a wide range of functionality was created, which still had room to grow.

Legacy Problems from Both Sides

My application project was written entirely by hand in Objective-C, maintained, and worked correctly, but had not been updated for various reasons for over 5 years. And the first task that needed to be addressed was launching the application. Literally everything in the project was outdated, from the interface to the system core. What to do if there is no time for the project? Use AI.

The first thing I did was port the project to pure macOS, as it previously used Catalyst, and there were enough problems with it even then. The second thing I did was port all the Objective-C code to Swift and start migrating from third-party libraries that relied on CocoaPods. And then I ported the core itself to Swift.

By the way, I had serious doubts that I could port the core to Swift, as all the signal generation was in pure C! And this was not done out of my whim, but because even Objective-C had incredible latency, and it was simply impossible to generate fast signals. By the way, this is what initially distinguished my program from others.

After porting to Swift, the interface was redesigned using SwiftUI, and then a series of major improvements and enhancements were made. Currently, not a single line of code remains from the old program; everything has been rewritten entirely with Claude, under my careful guidance and close attention.

A Few Words About Translations and AI

Previously, I translated the application manually for countries where application activity was highest, and China was one of them. I did the translation into Chinese manually, involving Chinese speakers, but we have a powerful tool in our hands!

But simply translating the interface is only part of the job, what about the App Store... it requires images, captions for them, and interface screenshots made in the native language. For this, Python files were created that launch the application and take screenshots at the right time and place. Next, each screenshot needed captions and a beautiful background; all this also took time, but the result was magnificent.

In addition to interface translations, there is such a thing as translating the Morse code table itself. The point is that some countries use their own Morse code tables, while others use international Latin letters. For example, Japanese Morse uses a syllabic alphabet, Chinese uses Unicode and abbreviations, and Indian and Thai have their own special combinations.

Without much thought, the application interface was translated into 60 languages worldwide, and neural networks do this very well, almost in the native language. They do it quickly, but you need to check their work. To avoid defects, I ran all translations through two competing neural networks, one from Claude, the second from Codex. The result was excellent translations for all 60 languages.

Thus, I ended up with literally 37! alphabets, which I had to work with for a long time, implementing the clever practices they use in my architecture. The integration is at the core level, as input from the key must also allow entering these tricky combinations. Even if they come from a telegraph key connected via an adapter.

Admin Panel and AI

Where would we be without an admin panel... In the old application, feedback was quite simple: when you clicked, it checked if the user could write to the developer in iMessage, and if not, an email was generated. I wanted to improve this experience as much as possible.

Therefore, a separate admin panel was created for product management: mailings, auctions of physical goods, promo codes, as well as direct chat communication with each user, with video and photo support.

Since the application became multilingual, models for translating text from everyone who writes to customer support have been integrated into the client management admin panel, with reverse conversion to the support agent's language. Such a simple mechanism that is still not used anywhere.

And that's all?

No, not all. The application has a section dedicated to learning, where literally everything has been redone according to modern scientific methodologies. Previously, the application only supported learning by character groups, but now it selects the correct pairs itself using the Koch method. At the same time, nothing prevents you from working with your own character groups as before.

Also, after learning, there should be a testing process for your knowledge. And it has also been redesigned, redesigned as it happens in world competitions. Character groups, time, errors, everything is like in real Morse code competitions.

Learning progress calculations have been redone; they now show the characters that need attention during study, where a person makes more mistakes.

A decent layer of changes, right? And all this was done in the evenings and on weekends with several Claude and Codex accounts. Limits were easily reached in one evening.

Yes, a colossal amount of work was done in a short time, but there is one more thing left.

About Neural Networks and AI

As a result, the application became as complete as possible, but the last detail remained, which I struggled with for a long time: decoding Morse code directly from radio traffic. And not just decoding, but recognizing complex, noisy traffic, where even a professional human would have difficulty hearing something. And not just one station, but several simultaneously.

And I must say, I wanted to add this functionality to the application for a long time, let's say, from the very beginning of its creation. And something was already implemented using algorithms. For example, when a person works with a key, they must send a dot and a dash of approximately the correct length, and the algorithm in the application must understand this. This is quite easy to do using Markov chains or other adaptive algorithms. This works well for a key, but applying the same approaches to reading radio traffic is obviously a failed idea.

When I was first developing the first version of my application, neural networks were not yet known, or rather, not known so widely. After all, in college, I even did projects where a simple single-layer network recognized handwritten input. But to teach a network to listen to radio traffic like this? Several years have passed, hardware capabilities have increased, and some projects related to neural networks and Morse code have started to appear. These were studies on the websites of foreign research institutes with small dataset examples and evaluations of certain networks.

I remember how about five years ago I browsed through existing projects to see what was available, and found several interesting solutions... not one, but several! But everything I found didn't work perfectly. Moreover, it was tailored either to a specific reception speed, or to clean sound, or to a single reception channel.

After tinkering a bit with existing solutions, I gave up on it, as I simply didn't have enough time for all the projects. But a month ago, I returned to finally finish what I started – it's been a long 12 years. The solution became this: I will train my own network, especially since the hardware now allows it. On my MacBook Air M3, training doesn't take as much time as it did 5 years ago on an Intel processor, and certainly not as much as 12 years ago.

Almost any neural network requires a dataset with data or a "teacher" – an already trained cool model that will train the "student," conduct "distillation." A large neural network trains a small one, and this process sometimes works better because the large model is trained on a labeled dataset, while the student is trained not only on the labels but also on the teacher's response: that the signal here is unclear, and look, it's completely bad here, and so on.

When I studied existing networks, including research in large foreign institutions, I saw that the data on which neural networks were trained was taken with labels by letters. This means that, for example, we take an audio file, then make a record: here, a dot-dash sounds from the 1st second to the 3rd, this is the letter "A." And so on throughout the dataset. Thus, the AI learns to match and classify sound elements with the symbols (tokens) specified in the file, that is, it actually learned to speak only English.

If I follow this approach, I would have to train 37 neural networks, yes, exactly 37 neural networks! for different local Morse code alphabets, for example, for Japanese, Thai, or any other. The Morse language is universal; it's dots, dashes, and pauses between them, so why not create one universal network that would work at a lower level? For this to work, the dataset would need to be labeled like this: a dot from second 1.23 to 1.27, and so on. This was just a hypothesis, but this is how the requirements were formed.

  • up to 16 stations simultaneously in the SSB receiver bandwidth, about 2.5–3 kHz;

  • speed from 5 to 100 WPM, manual key, iambic and machine;

  • noisy radio traffic: fading, interference, digital signals, receiver retuning, room and phone microphone;

  • output elements: dot, dash, letter and word boundaries, not letters. Letters are assembled from elements by the application;

  • minimum energy: the model runs on the phone in a streaming manner, without looking ahead;

  • one trainable neural network without pre-filters making decisions. Threshold and band-pass filters are deliberately not used before the network to avoid losing weak stations.

It's all about proper training

Now let's get back to what's needed for training. And, as I've already said, a dataset is required. A dataset is a huge amount of labeled data on which a neural network begins to form its classification vectors, learning from this data. The better and more correctly the data is prepared, the better the result. As I wrote above, obtaining such a huge dataset is quite a task, and labeling this data manually is a job for an eternity.

I decided to go a different way and do it in two steps. First, I decided to add realism to the program itself, and then, based on this, try to create a dataset generator.

What do I mean by realism? When you reach a certain stage of understanding Morse code by ear, and then enter radio traffic, you get lost. The sound is completely different: there is constant noise in radio traffic, wind moves the antenna, changing its reception or transmission characteristics, thunderstorms rumble in the upper atmosphere, and so on. The equipment itself also affects it: low-quality components, signal drift, and so on...

I've wanted to provide the ability to train on real radio traffic for a long time. Moreover, to allow filtering or, rather, adding only those noises that you specifically struggle with, that you want to work on separately.

In short, as you can already guess, features like noise and effects have been added to the program. The noises were broken down into typical ones like transformer hum and white noise, and the effects allowed adding key chatter and other tapping artifacts. At first, I solved the problem, as they say, head-on, getting the same result. And then I sat with Claude, added variety and realism, to a level that allowed approaching real radio traffic. https://youtu.be/TPFljf2fjD0

If you listen, you can, of course, hear synthetic notes, but... what about in practice? Based on this generator, a dataset was prepared with diverse stations, different speeds, tones, audibility levels, and key chatter. It turned out to be a very large, and most importantly, correctly labeled package of data, on which I decided to train the neural network.

Grand Plans

First, I made a plan together with Claude and decided what exactly would be used as the basis.

Chain from microphone to elements:

  1. Microphone 48 kHz → 8 kHz. FIR Kaiser filter (241 taps), the same in the application and in the data generator.

  2. Spectrogram. Four windows simultaneously: 8, 32, 64, and 128 ms. Step 4 ms, grid 31.25 Hz, 104 bands from 218.75 Hz. A short window accurately shows time and is needed for fast dots, a long window accurately shows frequency and is needed for weak and close stations.

  3. PCEN in logarithmic form. Trainable energy normalization for each band, works like a slow AGC and equalizes volume and fading.

  4. Band encoder. A 2D causal convolutional network with uniform weights at any frequency and two global context blocks across the entire band. For each band and 8 ms frame, it outputs:

    • station center map;

    • fractional frequency shift within the band;

    • key press probability;

    • embedding for the decoder.

  5. Tracker. The only non-neural network part, simple streaming rules. It accumulates confidence from the peaks of the center map, creates a track, guides the frequency with an α-β filter, and looks back 2 seconds when creating a track.

  6. Track decoder. A causal temporal convolutional network (TCN) of 16 blocks, dilations 1–64 twice, 128 and 256, with a receptive field of about 10 seconds. It reads embeddings and the spectrum around the track frequency and outputs CTC for five classes: silence, dot, dash, letter boundary, word boundary.

Scenes simulate:

  • stations: up to 16 simultaneously, 5–100 WPM, four types of keys and uneven handwriting;

  • transmitter: frequency drift, chirp, clicks, keying chirp;

  • propagation: fading according to the Watterson model (Rayleigh and Rice), up to 30 Hz Doppler, second path;

  • radio traffic: white, pink, atmospheric, and real band noise, digital interference (RTTY, FT8, and others);

  • receiver: SSB or CW filter, AGC, intermodulation overload, retuning in the middle of the scene, shutdown;

  • room: speaker, room impulse response (RT60 0.15–0.6 s, DRR 8–25 dB), microphone noise, recording level.

Scenes can be normal, quiet, containing only noise or only interference, with a late start, with two stations on the same frequency, with a strong station next to a weak one, and also with frequency retuning. Readability is measured on the already generated audio, not set by a formula. Stations and their parts, drowned in fading, are excluded from losses and evaluation. Training is done in batches of 10 GB, which is about 7760 scenes per batch. Each batch is generated anew and deleted after training, as the disk can only hold one or two at a time.

I'll say right away: it didn't go smoothly on the first try. Almost a month was spent on the chain of "training → testing → improvements → training", selecting network sizes, testing hypotheses, replacing datasets, and so on. The laptop was hot 24/7.

Learning from Mistakes

Element error. The proportion of Levenshtein edits (substitution, deletion, insertion) per token: dot, dash, letter boundary, and word boundary, relative to the length of the reference. The lower, the better. The metric is stricter than letter-based in one aspect and softer in another: omitting one dot is one error, even though the letter is already different.

Character Error Rate (CER)** for comparison with other works. Tokens are converted to letters according to the Latin alphabet, spaces are collapsed, and edits per character are counted.

Three evaluation levels:

  • ideal tracks: the decoder reads the station at the true frequency, without a tracker. This is a measure of the decoder itself;

  • entire system: the tracker finds the stations itself; a missed station is considered entirely erroneous. This is how it will be in the application;

  • real radio traffic: from recordings of radio stations

Synthetic validation: 1000 scenes, variant d, about 5.6 hours of audio. Models are compared by scenes, the difference is with a 95% confidence interval of paired bootstrap.

Comparing networks is a rather meticulous process, especially since it happens with different data, in different labs, etc., but approximate estimates can be gathered and compared.

Conclusions and Inputs

There is no ready-made labeled dataset of real radio traffic available in the public domain, so we made our own.

How recordings were obtained:

  1. Station W1AW (ARRL, Newington, Connecticut) transmits bulletins according to schedule, and ARRL publishes their texts.

  2. The same transmission was recorded simultaneously from several public remote KiwiSDR receivers at distances from 420 to 5800 km (Canada, USA, France, Netherlands) on several bands. This resulted in different signal levels, fading, noise, and interference with a single known text.

  3. The bulletin text was synchronized with the recording by time. The teacher model read the cleanest recording, and its decryption was compared with the text using approximate substring search. For other recordings, the labeling was transferred by the shift found by mutual correlation of signal envelopes. Sections where two or more letters diverged consecutively were considered a deviation of the transmission from the text and were not included in the evaluation.

Dataset: two transmissions, bulletin DX ARLD042 and propagation bulletin ARLP043, 18 WPM. Nine recordings with signal, about 25 minutes each, about 56 thousand tokens and 16.6 thousand letters.

Main conclusion: synthetic data transfers well to radio traffic. The error on real radio traffic is only 1–2 points higher than on synthetic data, and the model order is the same.

Important caveat about labeling. On loud recordings, all five tested models show the same 8–10% element error, including the teacher on the recording used to build the labels. This means it's the lower limit of the labeling itself: the transmission on the air sometimes differs from the text on the ARRL website, for example, in links, abbreviations, and numbers. The actual error on a strong signal is lower. For final figures, the labeling needs to be refined by ear.

How to read the comparison:

  1. Almost all impressive numbers were obtained on synthetic data: CER 0–2%. Different projects define SNR differently, in different bandwidths and from different signal strengths, so the thresholds in decibels are not directly comparable between projects.

  2. On real radio traffic, only one open measurement was found, by Sagnik-Barman: 17–38%. Our decoder is in the same range (18–20%), considering that:

    • it reads all stations in the band at once, not just one, the strongest;

    • it works in real-time streaming, without looking ahead;

    • the phone model weighs 1.3 million parameters;

    • our figure includes the lower limit of labeling of about 8% for elements, see section 6.

  3. We did not find a multi-station neural network decoder with published measurements. Sagnik-Barman directly calls simultaneous reading of all stations in the band an unsolved problem.

  4. DeepFist was tested on ARRL code practice recordings, according to the description, without radio traffic, noise, or fading. This is closer to our clean variant a than to real radio traffic.

A Few Conclusions

To improve signal reception quality, I plan to add a language model inside the search. The decoder outputs not a single answer, but probabilities per frame. A small character-based language model will adjust the choice only where the decoder itself was uncertain. Where the signal is clear, acoustics prevail, and the model will not be able to invent a confident call sign.

What else can be said about the process itself is that modern neural networks significantly accelerate any development, design, and planning processes. The path I have taken was previously covered by entire scientific research groups, and now it is sufficient to have the necessary expertise, a Pro account, and one person.

My application has reached the peak of its development; there is nowhere else to grow. Anyone who needs Morse code in one way or another knows about my project, and most of the improvements were made precisely due to feedback from people interested in my project.

Since I have touched upon the topic of further application development, here is the roadmap:

  1. Application of post-processing to improve received signal quality

  2. Improvements based on feedback on current functionality

  3. Improvements and optimizations for the iPhone Duo application

  4. Porting the codebase and launching the application on Android

  5. Porting functionality and codebase to Windows

A few words about connecting a telegraph key to the application and why it's needed. For connection, a Bluetooth adapter is used, which allows connecting the key literally directly to the program and practicing at any time of day or night. The adapter accepts both iambic and regular keys. The adapter was developed by me from scratch, and the firmware was rewritten with Claude.

The second version of the adapter is currently under development, and it will have reverse functionality: the adapter will act as a key. This allows, for example, connecting it to a real transceiver for working on the air, transmitting a signal with human-like tapping emulation. Or, for example, you can enable transmission of a specific signal at a specific time with repeat intervals, and so on.

Since I have to work on the project only in the evenings and on weekends, the process is not very fast, but it is moving forward. I am currently conducting final research and preparing the build of version 10 for publication in the App Store. This means you can try it out in a couple of days, and in the meantime, I am providing a few promo codes for the application.
