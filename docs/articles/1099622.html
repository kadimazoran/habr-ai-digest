I usually have ten to fifteen Claude Code sessions open. One is fixing tests in one repository, another is working on the frontend in a neighboring worktree, a third is waiting for my response from this morning, and I've honestly forgotten about a fourth. Each has its own sub-agents and MCP servers, some with Vite running, others with pytest. For a while, this worked fine, but then my 64GB machine started struggling with every window switch.

I opened the task manager and saw what anyone who works like this has probably seen: a wall of identical node and claude processes. You can see how much they consume, but not who they belong to. I could have closed a couple of windows at random and hoped for the best, but I didn't want to rely on luck in this situation.

That's how claude-load was born, a mod for Claude Code that breaks down machine load by session. The very first run showed 15 active sessions consuming a total of 10.8 GB. Most had been idle for a long time with merged PRs, and one was running a forgotten Python process, even though its parent process was gone.

Whose node is this?

Process names are useless here: all sessions share the same claude, node, and bash. However, Claude Code itself maintains a registry of active sessions. In ~/.claude/sessions/, there's a file named <pid>.json for each session, containing almost everything needed:

{ 
  "pid": 18636, 
  "sessionId": "a3a4722e-…", 
  "name": "Refactor the auth middleware", 
  "status": "busy", 
  "cwd": "C:\\work\\api", 
  "entrypoint": "claude-desktop" 
}

The format isn't documented anywhere, so the mod only extracts these fields from the file and can handle cases where Claude overwrites it. There are also *.key files with tokens nearby, which the mod doesn't open at all.

The rest involves traversing the process tree. The sampler gets a list of all processes with their parents and traces the PPID chain upwards from each until it hits a session's PID. Everything below it belongs to that session's load. Traced chains are remembered, so even hundreds of processes are processed in a single pass.

The first observation happened even before any graphs. A session that does nothing still consumes 0.5–0.7 GB. This is the claude process itself, about 300–450 MB, plus a set of MCP servers running on node, one for each session. Fifteen forgotten windows mean several gigabytes just sitting there.

In the pane, it looks like this. Each session has CPU, memory, and a six-minute graph. Orphaned processes are shown in a separate block, discussed below, and at the very end is everything not related to sessions, collapsed by name. A line like chrome ×31 sometimes immediately clears Claude of all suspicion.

The screenshots in the article are rendered with demo data; my actual sessions are named after my work projects. The screenshots show the English interface, but it generally speaks the language of Claude Code, which for me is Russian.

A button that could kill someone else's process

The most interesting part involves processes that don't belong to any session but clearly originated from them. Vite launched from a session I closed long ago. A language server without an editor. That forgotten Python process. I wanted to show them separately and allow termination with a single button.

The first version was simple: an orphan was any dev process outside of sessions with a noticeable load. It survived until the review, discussed below. It turned out that my live PowerShell, IDE helpers, and conhost were being classified as orphans, and the button next to them honestly offered to terminate them along with their entire descendant tree.

The same review found something worse. The 'terminate' button relied on a memory snapshot, which could be outdated, and it didn't verify the process name. Between the snapshot and the button press, the PID could be freed and assigned to someone else. Then taskkill /T would have targeted a completely unrelated process along with its children.

Now, things are stricter. An orphan is a process tree whose root's parent is genuinely dead. On Windows, this means the parent PID is not among the live ones, or the process with that PID was created after the child, meaning the number has been reused. On macOS and Linux, the root is reparented to init, systemd, or launchd. The tree is only displayed if it contains a genuine development tool and not just shells, and if it consumes at least 0.3% CPU or 150 MB. The terminal from which the session was launched and the sampler itself are never considered orphans.

To associate an orphan with something, its working directory is needed. On Linux, it's in /proc/<pid>/cwd; on macOS, lsof provides it. On Windows, there's no ready API, so the directory has to be read from the memory of another process: NtQueryInformationProcess gives the PEB address, from which the ProcessParameters are accessed at offset 0x20, and within that, at offset 0x38, lies the CurrentDirectory. It sounds scarier than it is: it's just a couple of ReadProcessMemory calls.

Before terminating, the mod takes a fresh snapshot, refuses to operate if it's older than 15 seconds, and verifies that the process under that PID is still the same one with the same name. Session processes and PIDs not present in the snapshot cannot be terminated from the pane at all. So, if you click 'Yes, terminate' half an hour after opening the pane, nothing terrible will happen.

The monitor shouldn't become part of the problem

If each of the fifteen sessions starts polling processes independently, the load monitor itself will become a load. Therefore, only one process per machine takes measurements. It writes to ~/.claude/state/load/snapshot.json, and the mod in each session simply reads this file every five seconds. There can be any number of sessions; the cost doesn't increase.

On Windows, the sampler is a hidden PowerShell process, launched by the mod when it detects an outdated snapshot. Two measurements on my machine identified this setup: Get-Process takes 76 ms, while a full CIM query with parents takes 400 ms. Therefore, Get-Process is read every four seconds, and the parent tree from CIM is queried only when new PIDs appear, and no more often than once every eight seconds. CPU usage is calculated by the difference in accumulated time between passes.

The sampler lives as long as someone is waiting for it. Each session touches the wanted file every 30 seconds, and after three minutes of inactivity, the sampler exits on its own. If it crashes, the first session to notice the old snapshot will launch a new one, and the PID file with command-line verification prevents a second instance from starting. On a machine with 12 threads and 15 sessions, all this costs about 0.35% CPU and 130 MB of RAM.

On macOS and Linux, a separate process isn't needed; ps is cheap enough. There, one of the sessions' mods holds an 'lease'—a file with its ID and timestamp—and takes the load measurements itself. If the lease isn't updated for 15 seconds, another session takes it. CPU calculation was tricky. The %cpu column in Linux shows the average over the process's entire lifetime, so it has to be calculated by the difference in the time column. And Linux's time is given in whole seconds, so two passes a second apart can show spikes that never occurred. Thus, passes occur no more often than once every four seconds and never overlap.

The mod, the engine, and five rejections

Mods were introduced in Claude Code version 2.1.287. They are a new type of plugin: a single TypeScript module that hooks directly into the agent process. A hook looks like ($, e, next), where $ is the engine interface with files, processes, timers, storage, and UI; e is the event; and next passes it along. The module has neither Node nor DOM; everything external goes through $. The interface is assembled from JSX: in the terminal, there are Box, Text, and Button; on the desktop, additionally Svg.

claude-load relies on five points. session.start starts a timer and registers /load; command.run handles the command; ui.render draws the pane and the line above the input field; and $.prompt.submit sends a request to the session to handle the load. Before loading, the engine statically parses the module, and I learned some of its rules only through rejections. Initially, it rejected a function to which I passed $ within a closure: $ can only be passed to top-level functions in the same file. I had to move the state to a separate object and lift the functions to the top. Then it turned out that $ is not passed via import either, so the other files were left with only pure functions. $.env.get accepts the variable name only as a literal, so $.env.get(win ? 'USERPROFILE' : 'HOME') turned into a ternary operator with two calls. Link only opens https, so navigating to another session via claude:// became a button that asks the OS to open the link. And Box doesn't have borderTop, so the line under the header was replaced by a capitalized header.

The good news is that mods have a real test kit. claude plugin test runs the mod on a live engine with mocked files, processes, clocks, and even pane button clicks. The test caught the error with $.env.get; claude plugin validate missed it. There's also a catch: the kit allows paths on the host OS, and in a Linux branch test on Windows, /home/u came to the mock as C:\home\u. The mock had to normalize them back. In total, 59 tests were accumulated: parsers for ps, vm_stat, /proc/meminfo and lsof, lease management, filters, termination confirmation, and all eight languages on both surfaces.

I didn't write the code

The title says "I wrote it," which is an exaggeration: I barely wrote it by hand. The mod was entirely created in Claude Code (Opus 5.5) over a couple of days, with me acting as the client and a picky reviewer. My comments in the session history are mostly: "make it prettier," "add filters," "looks very ugly." The latter refers to the bar above the input, after which it received an SVG graph and colored CPU and RAM.

Orchestration was the most beneficial. The main session maintained the architecture and distributed tasks to sub-agents, each with its own files, so they wouldn't fight over the same code. One wrote the sampler for macOS and Linux along with tests on recorded command output: there was no other way to test it on my Windows machine. Others translated the interface and README. Dictionaries are typed, so a forgotten key is caught by a test, and plural forms are taken from Intl.PluralRules: "1 session," "3 sessions," "15 sessions."

Before publication, there was one review pass by Opus on the entire repository. I've already mentioned the orphans and reused PID; those were its findings. In total, it self-corrected nine local defects, each with a test. For example, a path to a profile with an apostrophe like C:\Users\O'Brien broke the sampler launch command, and passes on Linux could overlap and draw false spikes. It didn't touch design decisions, but returned them to me.

Even the screenshots for the README were made by Claude. It laid out the HTML mock with the same SVG icons and graphs as in the mod and captured it in headless Chrome. Actual screenshots with my work project names shouldn't have been published to the public repository.

Twelve windows archived

The first cleanup worked immediately. The "Clean up with Claude" button sends a request to a built-in skill, and Claude sorts out idle sessions and orphans, asks once, and only touches approved items. Out of 15 active sessions, 12 were archived: eight with merged PRs and four forgotten ones without PRs. Occupied memory dropped from 35.2 to 31.2 GB. I also enabled auto-archiving of sessions in the desktop app upon merging their PRs, so forgotten windows won't accumulate anymore.

Now, about what the mod *can't* do. It hasn't run on a real Mac or Linux yet: everything is covered by tests on recorded output from ps, vm_stat, /proc/meminfo, and lsof, but that's not the same. CPU on Linux is calculated less precisely than on Windows because ps returns time in whole seconds; reading /proc/<pid>/stat would fix this. Strict PowerShell policies, like AllSigned or Constrained Language Mode, will prevent the sampler from starting, and the mod will report this instead of the perpetual "Waiting..."

Two more risks are beyond my control. The session registry is undocumented, and if Anthropic changes the format of ~/.claude/sessions, the mod will need updating. And the working directory on Windows is read from another process's memory. It's read-only and only for its own processes, but an antivirus or EDR might not like it. Everything else stays on the machine: no network requests, no telemetry.

How to try it

You need Claude Code 2.1.287 or newer. One command adds the repository as a marketplace and installs the mod for your user. On macOS, Linux, and Git Bash:

claude plugin marketplace add Gerrux/claude-load && claude plugin install claude-load@claude-load --config language=auto

In PowerShell:

claude plugin marketplace add Gerrux/claude-load; if ($?) { claude plugin install claude-load@claude-load --config language=auto }

In the desktop app, you can skip the terminal: '+' next to the input field → Plugins → Add marketplace → Gerrux/claude-load → Add plugin. After installation, run /reload-plugins and /load. The code is on GitHub under MIT, the README in Russian is also there, and for mods themselves, there's the Claude Code documentation.

And how many sessions do you keep open? If you're on Mac or Linux, please share what /load showed and what broke: this is the most useful feedback for the mod right now.
