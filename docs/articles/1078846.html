Four AI agents burned 40 million tokens arguing about code. I taught them to stop in time

I am writing my own IDE as a pet project. It has a name, but we will do without a product presentation here. I want to tell you about one feature that ultimately led me to a separate study.

If you have ever spent a long time fixing a bug with a coding agent, the situation is probably familiar. The model finds a plausible cause, confidently changes the code. It didn't help. You write: "Check yourself."

And then sometimes the most unpleasant part begins. The model has already latched onto its version and continues to build on it. Here it adds a condition, there an exception, then another check. A set of workarounds grows around an initially mediocre solution. You are already discussing how to make it all work, when it would be worth going back a step: did we even find the cause of the error?

I wanted to set such a stop before the first code edit. Let several independent versions appear first, and let someone try to challenge the decision while it hasn't yet turned into ten modified files.

The idea itself has been around for a long time: there is multi-agent debate, there is AutoGen and various ways to organize discussions between LLMs. I took this basis, built multi-role planning into the IDE, and described my own discussion management scheme in my work.

On screen, everything looked great. But I wanted to know how much benefit was hidden behind this beautiful conversation.

In the end, 480 main runs, two models, and several million tokens that could have been saved. And the most useful finding was not in the final table at all.

To start, I arranged a meeting for the models

Four roles: architect, developer, reviewer, and tester.

Each has its own question. What is the cause of the error? What to change? What will break because of it? How to check if the fix worked?

These are not four different neural networks gathered in one chat. In each experiment, the roles were performed by the same LLM, but with separate calls and different instructions. First DeepSeek, then the entire set of tasks was processed by Qwen.

The first round is independent: participants do not yet see each other's answers. Otherwise, instead of four versions, it is easy to get one version and three polite agreements with it.

Then they read each other's suggestions, criticize them, and a separate call collects the overall plan. Only after that is the patch generated.

In the experimental full council, all this cost ten calls per task: four initial answers, four criticisms, one overall plan, and one patch.

Ten, even when the additional round did not change the direction of the solution. The rules simply did not have an option "this is enough.".

And now we multiply the meeting by the number of tasks

Each round receives the context again. The same source files are sent to the model again, the answers become longer, the token counter grows.

And I caught myself thinking a rather common engineering thought: why run the expensive part of the process without checking if it's needed?

Thus, the Budgeted Verified Council — BVC appeared. The full council got a fork before the criticism.

The roles were supposed to return structured positions: the presumed cause of the error, the method of correction, affected dependencies, and tests. The system compared these fields and decided whether a second round was needed.

If there are no grounds to continue, we immediately collect the plan. This results in six calls instead of ten. If there are, we launch criticism and stick to the previous ten.

On paper, it sounds almost too simple: remove four extra calls, get savings.

But all the complexity is hidden in the word "extra." If an early stop throws away a useful check, then I have simply exchanged quality for a lower bill.

And I also had to make sure that the system correctly understood when the participants disagreed. This, as it turned out later, was a problem.

AND THEN THE TESTS BEGAN

I took 60 SWE-bench Verified tasks from 11 Python projects. Real issues and source code: you need to get a patch that applies to the correct repository state and passes the tests.

The sample was intentionally more complex than average: the easiest tasks, estimated at less than 15 minutes of work, were not included. Therefore, below are the results on these 60 tasks, not an assessment of the entire SWE-bench.

One plan is especially important here. Otherwise, one might attribute to four agents the benefit that comes from a simple request to think first.

Within each model series, the methods received the same task description and the same files. The context was selected by searching the repository; I checked all 245 selected files against the original revisions — they matched byte for byte. Reference patches and verification tests were not included in the model requests.

Settings and the list of tasks were fixed before obtaining the results. Failed answers also remained in the table: empty patch, broken format, inapplicable change. You can't count the success rate only among attempts that were liked.

An important limitation: this was a controlled planning test before a single patch. The agent could not endlessly run tests and write corrections based on their prompts.

First, 240 runs on DeepSeek. Then, the same 60 tasks and four modes on Qwen — another 240.

60 tasks × 4 modes × 2 models = 480 runs. Not 480 different tasks.

Each patch was checked by the official SWE-bench evaluator in a container: tests for the original bug should pass, and checks for previously working behavior should be preserved. The model's own opinion on how well it performed was not included in the result.

Savings really appeared on the first model

DeepSeek took the short route in 32 out of 60 tasks.

The full council used 600 calls, BVC used 472. In terms of tokens, it was 18.37 million versus 14.28 million: minus 22.2%.

At the fixed rate, the cost decreased from 2,402.61 to 1,838.46 rubles. The difference is 564.15 rubles, or 23.5%. This is a calculation for accounted call chains, not the full provider bill with all technical retries.

For a pet project, half a thousand rubles doesn't seem like a revolution. But something else was important to me: the stop rule really changed the computation cost. You could open a specific task and see where the system didn't make four extra calls.

At the same time, five BVC patches and six full council patches passed the tests. So it was too early to congratulate myself on "the same quality for less money.".

And then the savings almost disappeared.

I replaced the model. The council started arguing almost always again

On Qwen, the short route worked in only three out of 60 tasks. In the remaining 57, the system sent the roles for an additional round.

Token savings dropped from 22.2% to 2.1%. Same roles. Same tasks. Same rule.

From one final table, one might conclude that Qwen simply disagrees with itself more often. But I still had the roles' answers and the algorithm's decisions for each run. I went to analyze what exactly was considered a disagreement.

For comparison, the system expected a structured answer. If mandatory fields were missing or the answers could not be properly compared, the first experimental implementation also included criticism.

It turns out that it mixed two different situations:

  • participants proposed incompatible solutions;

  • the system did not receive sufficiently correctly formatted answers to compare the solutions.

In the second case, we don't yet know if there's a dispute. But we pay as if there is.

Upon re-examination of the saved answers, in 54 out of 57 such Qwen runs, mandatory data and a common set of fields for comparison were missing simultaneously. In one of the analyzed answers, the model hit the 4096 output token limit: almost the entire budget was spent on reasoning, and the final JSON was empty or truncated.

This was a discovery. I added discussion to catch code errors, and the experiment caught an error in the discussion management itself.

The difference is practical. A real conflict is worth sending for criticism. A corrupted answer should first be attempted to be restored or re-requested in a short format. If that fails, move to a backup plan, not call another meeting.

It was this boundary that I later corrected in the BVC source code. The results of the previous, fixed version are given below: I did not substitute it with the corrected one in the middle of the experiment.

Yes, in total BVC has 12 successful runs against 10 for the full council. But this is not yet proof of higher quality code correction. On the first model, one plan was ahead of BVC, on the second — vice versa. At the same time, one plan was cheaper than BVC in both series.

Briefly about statistics

The main comparison of the study is BVC versus a single preliminary plan, separately for each model. In both cases, the exact two-sided McNemar's test gave p = 0.625. Difference intervals include zero.

There is not enough data to declare BVC better. The absence of a significant difference also does not prove equal quality or lack of losses.

However, the resource result can be checked in the call logs. In this configuration, conditional criticism was indeed cheaper than mandatory. And the Qwen analysis showed why such an advantage cannot be automatically transferred to another model.

I also had to check the one who set the scores

After the success table, an uncomfortable question arises: why should we trust the test bench?

I ran three sets through it separately: empty changes, all 22 successful patches from the main DeepSeek series, and reference fixes from the dataset. Each set — twice, without new LLM response generation.

Empty changes did not pass even once: 0 out of 60 in both repetitions. All 22 previously successful patches passed the tests again in both repetitions.

But the reference ones — only 58 out of 60. Both times.

Two "correct answers" were applied and fixed the target bug, but failed other checks in the fixed environment. In the case of requests, these included network and timeout tests. This means that even a negative result from the bench cannot be unconditionally interpreted as "the model wrote incorrect code.".

These two tasks did not change the main statistical conclusion, but the limitation still had to be included in the study. The check did not pass its own criterion of 60 out of 60.

For me, this was another reason to preserve the entire chain: request, response, patch, test results. When a number raises questions, you need to be able to trace it back to where it came from.

Why it was worth doing all this

In my IDE, there is now an agent council — with independent solution versions, criticism, and an overall plan before the first code edit. The very process that I lacked when another "check yourself" ended with new workarounds.

I integrated it into the workflow and added discussion budget management. The second round is no longer mandatory by scenario: the system has a rule by which it decides whether to continue the discussion or to collect the plan. For me, this is an important part of the function — to manage not only what the agents talk about, but also how much this conversation costs.

Next, I tested this scheme on a separate experimental stand. In total, across two model series, BVC used 4.55 million fewer tokens and 140 fewer calls than the full council with mandatory criticism. This is an 11.3% token saving in the conducted tests. The idea has a measurable cost — and measurable savings.

The study also helped refine the algorithm itself: in the source code of the new version, response restoration is separated from substantive criticism. And the entire stand with tasks, patches, and logs remains for future checks. Now each change can be compared with the previous version under the same conditions.

This is why it was worth going through this whole journey. I wrote my own IDE, integrated an agent council into it, and developed a way to reduce the costs of their discussions. The feature works in the IDE, and the savings have been verified by a separate experiment. For a pet project that started with the desire to write code more conveniently, this is already a tangible result.
