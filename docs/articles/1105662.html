There's a moment familiar to anyone who has worked with AI agents for more than a week. You open a project, set a task, and the agent asks a question you've already answered. Yesterday. In detail, with examples.

You answer again. Half an hour later, it suggests fixing something you decided not to touch the day before yesterday. It suggests it convincingly – it doesn't know why you decided that. And an hour later, the context overflows, the conversation shrinks to a retelling, and half of what was discussed turns into a couple of lines.

I work in the Lamantin AI team, which makes kaeru — memory for AI agents. When we analyzed our agents' logs, we noticed that the agent sometimes re-asks things it has already recorded. In this article, I'll show how I work with memory throughout the day: what the agent sees at the start, what it records as it goes, and how it picks up a task in a new session.

In short. kaeru is a local MCP server that gives AI agents (Claude Code, Codex, Cursor, OpenCode, and others) long-term memory between sessions. Memory is stored as a graph: observations, decisions, tasks, hypotheses with verification results, and connections between them. Each entry has a change history. The agent can write to memory during work. When entering a project, it or its client requests a summary. Data remains on your machine; for teams, there's a shared server that you set up yourself. The source code is on GitHub.

Why not a rules file

The first thing everyone does is create a file. CLAUDE.md, AGENTS.md, .cursorrules, an Obsidian note — the names vary, but the essence is the same: text that the agent reads before working. I started this way too, and it works for a while. Problems arise about a month later:

  • The file is updated when someone remembers it. You or the agent at your request — usually three days after something was figured out, when most of the details have already slipped your mind.

  • The file only grows. It's easy to add to it, but scary to delete. The agent trusts a rule you entered yesterday just as much as a rule you canceled a month ago and forgot to delete.

  • The file records "what," but not "why." "Don't touch the parser" — but why? If the reason is long gone, there's no way to find out.

  • Everyone has their own file. If you're not working alone, each agent knows something different about the project.

There are more rigorous options. ADRs (Architecture Decision Records) solve the "why" problem but are written for major decisions. Task trackers for agents like beads are good at keeping track of the work plan but not what was discovered along the way.

These are all useful things, and we don't replace them. Rules files and ADRs are good for stable agreements that undergo review and live in git. But there's a working layer between commits: hypotheses, tests, specifics of environments, things the agent learned during work that didn't make it into a task or a document. Dragging it into the repository clutters the history; not recording it means losing it. Memory is made for this layer.

What kaeru is: memory for agents in one minute

kaeru is a server that runs on your machine and stores the agent's memory as a graph. The agent connects to it via MCP — a standard protocol through which Claude Code, Codex, Cursor, and other clients call external tools.

The memory contains entries of various types: observations ("customer files arrive in cp1251"), decisions, tasks with deadlines, hypotheses along with verification results, saved documents. A rule is an entry marked as a stable project constraint; a reminder is an entry that will surface on a specific date. Entries are linked, and each link has a meaning: this decision grew out of that observation, this entry replaces that one, this test disproved that hypothesis. The agent saves the entire chain from observation to decision — this is called a saved reasoning. Entries are organized by project: I have over thirty projects in one storage, and the agent works within the one it has open.

As it works, the agent chooses what to record. The server provides a short instruction upon connection via MCP, and in the project rules, I remind it when to read memory and what to put into it. For example, when recording a decision, the agent can link it to an observation with the same call.

kaeru is responsible for storage and summarization. When to request a summary and what to do when compressing the dialogue is decided by the client. For this, hooks are used — scripts that Claude Code or Codex run.

One reviewer of the draft put it best: the repository retains how things should be, while kaeru retains the "between the lines": how they got there, what was tried, and why something was abandoned.

Morning: the agent already knows where you left off

When opening a project, one context call is needed. In my setup, a hook does this at the start of a session. It identifies the project by the working folder, requests a summary, and provides it to the agent before the first task. This is my hook; it's not yet part of kaeru.
