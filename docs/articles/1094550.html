Once during cleaning, I found my old fitness tracker, the Xiaomi Mi Band 4. Essentially, it's a wearable computer with a battery, screen, sensors, and Bluetooth. Can anything be run on it? Theoretically, yes, but the problem is that I'm not a hardware hacking specialist and don't write in C for ARM. But perhaps the current generation of LLMs can help me run something interesting on it? For example, a NES emulator on which I can play Super Mario Bros with controls via the touchscreen and a Bluetooth keyboard? To me, all this sounds like science fiction. It would probably take a year of dedicated work. But I think it's worth a try.

How to communicate with this device? Before first use, the band asks to use the Mi Fit (Zepp Life) app. But why?

It's about cloud pairing:

  1. The band sends a random value and a public key fingerprint to the app via Bluetooth.

  2. The app and the band calculate the same key:

    D = SHA256(band_MAC_bytes || 16-byte_random) # 32 bytes
auth_key = first 16 bytes of D

  3. Zepp Life asks the cloud to sign D. The app sends the full 32-byte hash (D) and the public key fingerprint, and in return receives a signature from the server.

    Then it sends this signature to the band.

  4. The band verifies the signature.

    In Ghidra, it's visible that 0x616c → 0x2fefc performs ECDSA-secp256k1 verification with the band's trusted public key:

    ECDSA_verify(trusted_public_key, D, signature)

    If verification passes, you can proceed.

  5. After pairing confirmation, the band saves the key.

Next, on each connection:

  1. The band sends a new random challenge - a 16-byte random value.

  2. The app responds with the result of AES-128-ECB(auth_key, challenge).

  3. The band calculates the same with its saved key. If the results match, it allows access to protected operations.

If you have an Android phone with root (like I do), after cloud pairing, this key can be extracted from the app. It's stored in /data/data/com.xiaomi.hm.health/databases/origin_db_*.

The downloaded firmware is signed, and the band verifies this signature during updates. Of course, you could open the device and flash the memory chips directly, but you can't disassemble it carefully; it's waterproof. But you can try to do everything via Bluetooth. If a way is found to remotely execute custom code, we can patch the firmware from within. We'll disable signature verification and freely install modified firmwares through the standard update mechanism. Dreams…

Or is it still possible? The firmware is signed but not encrypted. This means it can be decompiled in Ghidra. I asked Codex to find all places in the firmware that process input data from Bluetooth. The most interesting findings were related to loading firmwares, resources, fonts, and watch faces.

I asked Grok to dig into these areas (as Codex refused), and after some time, the first bug was found. Resources are compressed, and there's an error in the decompression code: it can write beyond the allocated buffer and overwrite other RAM areas.

How can this lead to code execution?

  1. We upload a specially prepared resource update.

  2. We force the decompressor to write beyond the buffer.

  3. We continue writing until we overwrite a pointer that the installer uses.

  4. When decompression finishes, the installer uses this pointer to call a function.

  5. The overwritten pointer directs execution to our code.

We tried to do this. At first, the band disconnected a few seconds after sending the update. It crashed and rebooted, and it was unclear what exactly was happening there. Fortunately, the standard firmware had a useful diagnostic channel: the band's internal debug log, which can be downloaded via Bluetooth. In firmware 1.0.9.66, it's available as Huami recorded-data type 7 and is stored in a circular buffer of about 1 MiB. The logs are stored as plain readable text: messages about loading, battery, and sensors, Bluetooth events, update progress, and crash reports.

After obtaining the crash logs, we were able to understand what was actually happening:

  1. The first overflow went too far: writing continued to the end of RAM, after which the band crashed. Additionally, the buffer address changed between reboots, so the same overflow length didn't always lead us to the same address.

  2. We reduced the write. Now the band's radio processor was causing the crashes: its code and data were located between our buffer and the pointer we wanted to overwrite.

  3. Eventually, we overwrote the desired pointer. It looked promising, but the band crashed before decompression finished, so the installer didn't have time to use it.

  4. We stopped the overflow before the radio processor's memory. Decompression completed, but the desired pointer remained unchanged. The installer called the usual erase function and erased part of the resources.

  5. We tried filling the radio processor's memory with code that would make it loop infinitely. We hoped this would prevent it from crashing. But this didn't work either.

The memory was arranged like this:

Our decompression buffer
         ↓
Radio processor code and data
         ↓
Pointer we wanted to overwrite

If we wrote enough data to reach the pointer, we destroyed the radio processor's code and data along the way. If we stopped early enough not to affect them, we didn't reach the pointer.

After spending some time on this approach, I decided to look for another way.

Some time passed, and an idea came to me: we've seen many vulnerabilities in Android, iOS, and other systems where a specially crafted image caused an error in the image processing code. This could lead to memory corruption and code execution. Perhaps something similar could be done on this device?

After the failure with compressed resources, we tried another vector: a custom watch face, loaded as type 8 (HMDIAL). Digging into the firmware, we found another bug, this time in the BMP reading code.

This code works as follows:

  1. Reads one line of BMP, 120 pixels wide, into a small buffer.

  2. Converts pixels to the screen's color format and draws the line.

  3. Reuses the buffer for the next line.

The buffer is 360 bytes, just enough for 120 pixels at three bytes each.

Immediately after the buffer, the firmware stores a pointer to the list of watch face callback functions. The list has three elements, one for each built-in watch face. Each element points to a structure with five function addresses: rendering, update, clear, button event handling, and watch face screen entry.

And what happens if we load a 32-bit BMP? Now each pixel takes four bytes, and a line requires 480 bytes. The decoder still copies the entire line into a 360-byte buffer. The extra 120 bytes overwrite the memory after the buffer, including the pointer to the watch face callback function list.

We place our code and our callback function list into the BMP's pixel data. When the decoder copies the pixels to RAM, our code also gets there. The overflow replaces the original pointer with the address of our list. When the firmware uses this list again to handle an event, it calls our code.

There's one detail: built-in and loaded watch faces are handled differently. The band supports one loaded watch face, corresponding to value 0xfe. A separate entry with callbacks is used for its rendering and updating, which we haven't modified. But button events and watch face screen entry still go through the overwritten pointer. Therefore, these events can trigger our code.

Our plan:

  1. Place our functions, a list of three elements, and one structure with callback functions into the BMP pixels. Each line will contain the same bytes.

  2. Let the standard decoder copy each line into the buffer at a fixed address.

  3. A 480-byte line of a 32-bit BMP will overwrite the cached pointer to the list immediately after the 360-byte buffer and redirect it to our list.

  4. Subsequent accesses will go through this pointer and call our functions.
