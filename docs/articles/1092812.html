On October 6, 2026, Google DeepMind released EmbeddingGemma 2 — an open-source embedding model that converts text, code, images, video, and audio into vectors. All of them fall into a single, shared 768-dimensional space, allowing them to be compared with each other, for example, to search for videos by a text query.

The main feature of the model is its size. According to Google, on a Pixel 11 Pro, the text part occupies about 191 MB of RAM, and the full multimodal version — about 567 MB. Therefore, such a search can be run directly on the device, rather than sending data to a server.

In this article, we will break down how the model is structured, how it achieves its compactness, how to work with it, and what pitfalls are best to be aware of in advance.

▍ Embeddings in a Minute

An embedding is a list of numbers (a vector) that describes the meaning of content. Items with similar meanings get close vectors. The phrases "The weather is wonderful today" and "It's so sunny outside!" will be close to each other, while "He drove to the stadium" will be far from them.

Then it's simple: calculate the vector for the query, calculate the vectors for the documents, and find the closest ones using cosine similarity. This is how semantic search, RAG, clustering, duplicate detection, and recommendations work.

The main problem before was that each data type required its own model, and vectors from different models were incomparable. A text vector could not be placed next to an image vector. EmbeddingGemma 2 solves exactly this: all modalities fall into one common 768-dimensional space.

▍ What's New

The first EmbeddingGemma was released in September 2025, capable of handling only text, and according to the Japanese publication livedoor, it garnered over 20 million downloads. The second version looks like this:

  • built on the Gemma 4 architecture;

  • 740M parameters, but modular: 270M text + 170M vision + 300M audio;

  • Apache 2.0 license;

  • understands 100+ languages, and performs about 14% better than its predecessor on code tasks;

  • 8192 token context window, 4 times larger than the first version;

  • Matryoshka vectors: 768, 512, 256, or 128 dimensions;

  • optimized for phones and laptops.

What's interesting here.

Local and global attention. Five out of six layers look only at a window of 1024 tokens, and only every sixth layer sees the entire sequence. This significantly saves memory and computation for long inputs.

Huge vocabulary. 262,144 tokens is a lot. The model's parameters are divided into "backbone" (130M) and "embedder" (140M). Judging by the numbers, the embedder is mainly a token table: 262,144 × 512 ≈ 134M. This is simply a lookup of a string by index, not computation, so only the transformer with 130M parameters actually "works". Hence the modest demands on speed and memory. (This is my estimate based on the numbers in the card; Google has not published such a breakdown.)

Pooling. The outputs of all tokens are averaged into a single 512-dimensional vector, then a linear layer expands it to 768.

▍ One Vector for Everything: Token Budget

All modalities share a common window of 8192 tokens, and each consumes it according to its "tariff":

The arithmetic adds up: 280 × 29 ≈ 8120, 140 × 58 ≈ 8120, 25 × 327 ≈ 8175.

If images are needed more cheaply, you can reduce the budget per image (from 70 to 1120 "soft" tokens). Then up to ~114 images or frames will fit into the window, but details will be conveyed less effectively.

The most interesting part is interleaving. You can mix text, images, video, and audio into a single input, marking the media position with special tokens <|image|>, <|video|>, and <|audio|>. The output will be a single vector for the entire description. For example, a product card from a store: text, photos, and video review are converted into a single embedding that can be compared with a regular text query "waterproof trail running shoes.".

▍ Matryoshka in a Vector

The model is trained using the Matryoshka Representation Learning (MRL) method. The idea is that important information is packed into the first dimensions of the vector, like Matryoshka dolls nesting within each other. Therefore, a 768-dimensional vector can simply be truncated to 512, 256, or 128 dimensions.

Why? To save space and speed up search. If you have a million documents in float32, at 768 dimensions, this is about 3 GB of vectors, and at 128 — about 0.5 GB. A 6x difference.

▍ Code

The simplest scenario is text search using sentence-transformers:

from sentence_transformers import SentenceTransformer

model = SentenceTransformer('google/embeddinggemma-2')

query = 'What causes the northern lights?'
document = 'The northern lights are caused by charged particles from the sun.'

query_emb = model.encode(query, prompt_name='SearchQuery')
doc_emb = model.encode(document, prompt_name='Document')

print(model.similarity(query_emb, doc_emb))

Note the prompt_name. The model is trained with short instruction prefixes like task: search result | query: ... for queries and title: ... | text: ... for documents. It works without them, but accuracy is lower. If a document has a title, you need to format it manually:

doc_emb = model.encode(f'title: {title} | text: {content}')

Prefixes are available for search, question answering, fact-checking, code search, classification, clustering, and sentence comparison. Important: they are applied only to text; images, video, and audio are provided without prefixes.

Truncating the vector using the library's tools:

query_emb = model.encode(
    query,
    prompt_name='SearchQuery',
    truncate_dim=256,
    normalize_embeddings=True,
)

And if you truncate manually, don't forget to normalize the result:

import numpy as np

v = emb[:256]
v = v / np.linalg.norm(v)

Loading only the text part with correct precision:

import torch
from sentence_transformers import SentenceTransformer

dtype = torch.bfloat16 if torch.cuda.is_bf16_supported() else torch.float32

model = SentenceTransformer(
    'google/embeddinggemma-2',
    model_kwargs={'torch_dtype': dtype},
    config_kwargs={'vision_config': None, 'audio_config': None},
)

And multimodal interleaving, one vector for the entire product description:

model = SentenceTransformer('google/embeddinggemma-2')

emb = model.encode({
    'text': 'Waterproof running shoes. <|image|> Breathable mesh upper. <|image|> Grip test on wet rock: <|video|>',
    'image': ['shoe.jpg', 'mesh.jpg'],
    'video': 'demo.mp4',
})

Each placeholder in the text is filled with the corresponding key in order. The resulting vector is directly compared with any other EmbeddingGemma 2 vector, including a text query.

▍ Pitfalls

float16 breaks the model. Model activations exceed the float16 range, and you'll get NaN or silently corrupted embeddings, without an error. Use bfloat16 or float32. On most CPUs, this is float32.

Truncated vector but not normalized. A slice of a unit vector is no longer a unit. Ranking degrades silently: the numbers look plausible, but the results are worse.

Different dimensions for queries and documents. A 768-dimensional query cannot be compared with a 128-dimensional corpus.

Prefixes forgotten. The model won't break, but it will lose accuracy.

Languages are not equal. 100+ languages are declared, but Google itself states that quality may vary between them. For Russian, test on your own data.

No safety mechanisms. This is a pre-trained embedder without post-training for safety. Filtering of output and checks for bias must be done at your application level.

▍ Where to Get and How to Run

Weights are available on Hugging Face and Kaggle. For local execution, there are GGUF versions from Unsloth, and support is declared by MediaPipe, LiteRT, vLLM, and Ollama. For server deployment, there's a recipe in the SGLang documentation: the model in BF16 weighs about 1.5 GB, so almost any server GPU will suffice.

And if you want to try it without installation, on Hugging Face there's a demo webml-community/embeddinggemma-2-webgpu, where the model calculates embeddings directly in the browser using WebGPU.

▍ Conclusion

EmbeddingGemma 2 is not a record-breaker in absolute quality nor a revolution in text search. It's an engineering compromise, and a very successful one: a common space for five data types, modular loading, flexible vector truncation, and appetites that allow you to keep the model right in your pocket.

Whether on-device embeddings will become as standard as on-device speech recognition remains to be seen.
