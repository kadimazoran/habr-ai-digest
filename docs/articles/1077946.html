Mistake 1. Success is judged by final text, not system state

Symptom. In the report, a task is marked as completed because the agent wrote "done, request created." However, the database is empty.

Cause. This is the easiest way to write a check: compare the final response to a reference or give it to a judge. But the response and the action are different entities. The model can perfectly describe a result that didn't happen, and the text is flawless.

Consequences. Checking only the final text misses situations where the agent reports a successful action, even though the action didn't occur. This problem is well illustrated by τ‑bench from Sierra: the main criterion there is the correspondence of the final database state to the target state, and for some tasks, the mandatory text output is additionally checked. It's telling that in the original experiment, GPT-4o in the corresponding configuration solved less than half of the tasks.

How to fix. A task is considered successful by checking the state transition. Specifically, the transition, not its presence: if you only compare the final value, the test will pass even for an agent that did nothing—the required status was already in the fixture from the start. And you should separate transactional writes and event delivery: these are different levels, and they need to be waited for differently.
