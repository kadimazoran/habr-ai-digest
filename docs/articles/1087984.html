I'm a product designer with over six years of experience building SaaS. I can code, but I wouldn't call myself a full-stack developer. For several months, I've been building Kotomka alone, a life planner based on the PARA method: spheres, projects, tasks, calendar, habits, finances. It has a web version, a mobile version, synchronization between devices, and with Google and Apple calendars. Almost all the code is written by Claude Code. I set tasks, check results, and make decisions.

The first few weeks were euphoric: features appeared faster than I could think of them. Then two problems started. The interface began to fall apart, and users started losing data.

This article isn't about AI replacing programmers. It's about what had to be built around AI to stop the project from falling apart. Everything below is taken from a real repository, with real pitfalls.

Stack: Next.js 16 (App Router, effectively SPA), all state in a single React context plus LocalStorage, a server for sync and integrations, snapshots in Postgres (Neon), Vitest + React Testing Library, e2e tests, husky, Conventional Commits.

Part 1. AI Doesn't Remember Your Design System

Symptom

I ask Claude Code to fix a form on mobile, and it creates its own input size, even though a ready-made primitive exists in the project. I ask for a new screen, and the headings there are a pixel off from the adjacent ones. Each individual decision seems reasonable, but together it becomes a patchwork quilt.

The reason turned out to be trivial. There was no explicit design system. CLAUDE.md grew to 240 lines of solid prose, and it didn't mention UI at all. For each request, the model re-decided how a button should look. Complaining about this is as strange as scolding a new developer who hasn't been shown the guidelines.

Step 1. Measure, Don't Argue by Eye

First, I asked Claude Code to write an audit script. scripts/ui-audit.ts runs through the application screens in the browser, collects computed element styles, and groups them by role: headings, inputs, buttons, list items. The report includes the variance, i.e., how many different font-size, height, padding values occur for elements that should look the same.

The first run covered 3089 elements across 36 screens. The variance was even worse than I expected.

Step 2. Tokens and Pitfalls with tailwind-merge

After that, everything is standard: a scale of tokens in globals.css, three heading roles, UI components switched to size/variant without changing the public API. 90 arbitrary values like h-[37px] and hardcoded hex colors were replaced by tokens, leaving only isolated conscious exceptions like calc(). The ESLint rule for them is set to error. Mobile values live within the token itself via @media, so components don't have to worry about it.

And then the tabs started to "float," even though the token was specified correctly.

The root cause was in cn(). Inside it runs tailwind-merge, which doesn't know about custom text-* classes. It treats them as colors, thus conflicting with actual text colors, and silently drops one of the two.

This is fixed by extending the config:

// lib/utils.ts (simplified)import { extendTailwindMerge } from 'tailwind-merge'const twMerge = extendTailwindMerge({  extend: {    classGroups: {      'font-size': [{ text: ['body', 'caption', 'field' /* ...all tokens */] }],    },  },})

Since then, the rule is: a new text size token must be declared in cn(), otherwise it will be truncated. There's a separate test for this rule.

This same issue had a second layer. On iPhone, when entering an amount, the page zoomed. iOS zooms if an input has a font-size less than 16px, and in financial forms, text-sm overrode the mobile size of the primitive. The solution: a single token text-field: 14px on desktop, 16px on mobile, within the token. It was applied to all twelve financial inputs, and the zoom disappeared.

Step 3. Rules for AI, but Lazy Ones

The most counter-intuitive discovery: the more rules loaded into the context, the worse the model follows them and the longer it thinks. I had 951 lines in auto-load: CLAUDE.md for 241 lines and AGENTS.md for 710.

After reorganization, it became like this:

  • 117 lines are always loaded: CLAUDE.md for 110 lines and AGENTS.md for 7. This is the core: architecture, commands, key prohibitions.

  • 8 files in .claude/rules/ are loaded lazily, only when Claude touches files matching the mask in the frontmatter.

---paths:  - "src/components/**"  - "src/app/**/*.tsx"---# UI: rules for working with components...

You need to check what actually got into the context via /context. A separate script check-rules-globs.ts ensures that each mask matches at least one file. A dead mask is a rule that will never be loaded, and you can't know about it without checking.

And an honest addition. When I was preparing this article and recounted the lines in the current main branch, auto-load had already grown again: 157 lines instead of 117. CLAUDE.md grew to 135, and the rules file for audit mode is always loaded because it has no masks. There are now 13 lazy files. Rules grow just like code, and they also need periodic review.

Step 4. Component Inventory and the Lesson About Trust

For the model to reuse components instead of reinventing them, it needs to know what already exists. A script generates a component inventory: primitives from ui/ plus wrappers imported in at least two places. The "when to use" column is maintained manually; the generator doesn't overwrite it.

Upon selective review, it turned out that three out of four AI-generated descriptions were inaccurate. The model confused the boundary between two drawers and counted five mascot variants instead of nine. Documentation generated by AI and not verified by anyone is more dangerous than its absence: the model will confidently follow it.

Step 5. Prohibitions Instead of Requests

Rules in text are requests. It's more reliable to make violations impossible:

  • PreToolUse hook blocks the creation of new files in src/components/ui/. A new primitive is a decision I make, not a side effect of a task.

  • UI Audit Guard: a script compares the current audit with a baseline and fails only on a new value. The baseline is updated manually with a separate command, i.e., consciously. The guard is run by the command npm run ui-audit:check, locally and in CI. The very first run, by the way, showed that the committed report had long been outdated.

Part 2. Synchronization That Lost Data

Architecture

All user state is a single JSON snapshot with an integer version. The client sends changes with debouncing, and pulls them on tab focus and by timer. Conflicts are resolved on a "last write wins" basis: the server accepts a write only if the client's base version matches the current one, otherwise it responds with 409. The scheme is simple and understandable, but simple schemes can also have subtle points.

Bug 1. Text Rolls Back Immediately After Input

The user types, and after a second, part of the text disappears. It reproduced unstably, which is common for race conditions.

I asked for diagnosis in audit mode: don't touch the code, provide file:line links, add confidence labels, and put guesses in a separate section. This is a separate rule in .claude/rules/audit.md, and it disciplines the model significantly. Without it, it tends to "fix" based on the first hypothesis.

Here's what was found. The "unsent changes" flag is unique to the entire store. Push takes a snapshot at the start, and upon a 200 response, it resets the flag. Anything the user typed while the request was in flight was considered sent. The next pull brought the server version and overwrote the input.

The fix takes one line, but it's the right line:

const local = stateRef.currentawait push(local)// reset the flag only if nothing has changed during the requestif (stateRef.current === local) dirtyRef.current = false

The same defect was in the 409 handling branch, and it was broader than expected: the state equality check happened before the local edits check. Fixed by the same guard.

Pitfalls with Tests

The race condition test is written using fake timers and mocked fetch. I checked its integrity by reverting the fix: the test must fail. It failed.

Then it turned out that hooks from previous tests were not unmounted. RTL's auto-cleanup without globals: true in Vitest doesn't work, so their focus listeners were triggering other hooks and advancing the global version. We added cleanup() in afterEach and re-checked: each test fails exactly when its guard is removed. Luckily, there were no false positives. But I noted the lesson: a test that never fails proves nothing.

Bug 2. Ping-Pong Between Tabs

The next discovery was funnier. After a pull, the store normalizes data and gets a new object. The "don't send what just arrived" protection compared references, saw different objects, and sent the data back to the server. With two open tabs, this turned into an endless ping-pong: the version grew with each poll cycle with zero user actions.

For the article, I reproduced this in the test harness because a live run in two browser tabs requires a separate test database. Two "tabs" are two instances of the synchronization hook, each with its own store. The fake server behaves the same as the real one: it accepts a write only if the version matches. The time is simulated, 60 seconds, with zero user actions.

Before the fix, the server version grew from 5 to 9: plus one on each poll cycle. After the fix, it remained 5. Regression tests from the fix, run against the old code, fail exactly on this scenario.

We discussed four options. We chose this one: replaceState returns an already normalized object, and this is what gets put into lastSyncedRef. The option "normalize on the hook side" was rejected because it breaks the invariant "the store is the sole normalizer." The option "compare by content" was rejected due to the serialization cost on the hot path.

Bug 3. Loss on Reopening

The data in LocalStorage was intact, but on startup, the application saw that the server version was newer and chose the server version. The "unsent changes" flag lived only in memory, so after closing the tab, no one knew about them. Solution: an "unsent" marker in LocalStorage plus a push when the application goes into the background.

Speed

The initial poll interval was 15 seconds, and the send debounce was 1.5 seconds. For the scenario "added a task from the phone, looking at the laptop," this is an eternity. I wanted 1-3 seconds without "data updated" notifications and without rollbacks.

WebSockets and SSE were not needed. A light GET /api/state/version, which returns only a number, polling every 2 seconds, and a front-edge debounce with protection against parallel pushes were sufficient. The full snapshot is fetched only when the version has changed. Tested in production, synchronization feels instantaneous.

What I Learned From This

AI writes code quickly, but a human is responsible for architectural decisions. In all the stories above, the model excelled at finding causes and suggesting options. Choosing between options and seeing which invariant breaks was up to me.

Diagnosis first, then fix. Audit mode with confidence labels saved more time than any other setting.

Less context means better results, but it needs maintenance. 117 lines in auto-load worked better than 951. After a month, there were 157 again, so reviewing rules is now on my regular list.

Prohibitions are more reliable than requests. Hooks and guards continue to work when the model forgets the rules.

Verify what AI writes about its own code. The inventory and tests looked convincing, but there were errors in both.

Fast pre-commit is important. When e2e tests ran on every commit, development slowed down noticeably. Now e2e tests run in CI, and pre-commit (lint, tsc, unit tests) takes about 13 seconds.
