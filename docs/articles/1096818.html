But in commercial development, a more down-to-earth question sooner or later arises: what benefit does all this bring to the company? I managed to get a very specific answer to it, and also found out that a working product and a reliable product are not always the same thing.

How Developers Turned into a Search Engine with a Salary

A meme once appeared in our company: "Developers are a search engine with a salary." And it didn't arise out of nowhere. Managers would turn to developers five to ten times a day with client questions: why a certain function works this way, where specific logic is implemented, whether the system's behavior can be changed, and what's actually happening inside the project. Often, to answer, it was enough to open the code and understand a few files, but a manager couldn't always do it themselves. As a result, the developer was distracted from their work, the manager was nervous waiting for an answer, and the client waited. A wonderful organization of the process, in which everyone is busy, but no one is particularly happy.

Initially, I wanted to solve this specific problem. Thus, Repo Chat was born, allowing a manager to ask a question in plain language and get an answer based on the project's source code with links to specific files. Gradually, the idea evolved: if the system can already analyze existing code, why not teach it to perform small tasks independently? As a result, the second component, AI Workflow, was created, automating development from task definition to creating a merge request. A person describes the requirements and acceptance criteria, the agent makes changes, runs checks, and submits the result for review. If remarks are found, the task is returned for revision through the same agent.

Separately, I want to note that I didn't develop the project alone. My colleague also participated in the system's implementation, and it would be unfair to attribute all the results solely to myself. The idea and architectural development were only part of the work, without which the project would not have reached real-world use.

Why Not Just Use Claude Code or Codex?

A perfectly logical question. There are already tools on the market capable of analyzing repositories, writing code, and performing tasks independently. Why develop your own system when you can use a ready-made solution? The problem is that the technical capabilities of an AI agent and the ability to safely provide it to company employees are completely different things. Claude Code and Codex can work with code, but they need access to the relevant context for this. And this is precisely where organizational limitations begin.

Imagine a typical manager who needs to answer a client's question about the behavior of a specific website function. To use a standard coding agent directly, they would need to arrange access to the project and the corresponding environment. But giving managers direct access to the source code of commercial projects, Git repositories, and development tools for such questions is a questionable idea from a security and access control perspective. Even if an employee is proficient in programming, it doesn't mean they need such privileges to perform their job duties.

AI Workflow solves the problem differently. The system connects centrally to authorized repositories, and employees access specific functions through a unified interface. A manager can ask a question about the code or set a development task without gaining direct access to the repository and Git credentials. Project permissions and available actions are determined centrally, and the development result goes through the prescribed review and acceptance process.

This is the main difference between my system and simply using a coding agent. I wasn't trying to create a model that writes code better than Claude or Codex. I needed a manageable tool that would allow employees without direct access to source code to use AI development capabilities. And, as it turned out, this difference is much more important for business than another comparison of code generation quality.

How the Experiment Started Bringing Money

In commercial development, there are many tasks that don't require complex architectural solutions but regularly consume the team's time. Fixing form behavior, changing an interface, refining an existing component, or fixing a minor business logic defect. Each such task requires studying the context, implementation, verification, and delivery of the result, with the actual coding sometimes taking less time. AI Workflow allowed automating a significant part of this process, leaving task definition and result acceptance to humans.

In real projects, the system proved capable of performing more than just the simplest changes. It analyzed existing repositories, worked with multiple files, passed automated checks, and could independently break down large tasks into stages. By my estimate, about 70% of tasks were completed without significant rework: some were accepted immediately, others required minor corrections through the same agent. This is an operational observation, but the result was convincing enough to continue using the system in commercial work.

In the first two months, the additional income for the company related to the use of this system, according to our internal estimates, amounted to about 200 thousand rubles. We estimated another approximately 150 thousand as savings in working time and resources. Together, they provide an estimated economic effect of 350 thousand rubles. But even with this caveat, the result was significant: the internal experiment began to bring measurable benefits to the company, not just demonstrate the capabilities of modern language models.

This is where I encountered the main contradiction of the project. For business, the cost of work, deadlines, quality of results, and the ability to free up team resources are important. For a developer, this is supplemented by architectural reliability, process reproducibility, technical debt, and potential failure points. As long as the system performs tasks and economically justifies its existence, not all of its internal problems are noticeable to the business. And, as it turned out, a commercially successful product can be built on an architecture that its author later considers unsuccessful.

What Went Wrong

Problems began to emerge during operation, and they were not always related to the quality of the models themselves. For example, when checking working copies of repositories, it turned out that some of them had not been updated for months. Meanwhile, Repo Chat continued to answer user questions and refer to source files without warning about the outdated data. It's important to clarify that this applied to copies for analysis and file viewing: a separate mechanism was used to obtain the current repository state for development tasks. But the situation itself seemed quite absurd: the system confidently explained the project's structure without checking how accurately its understanding matched reality.

Other problems were also discovered. Updates to utility preparation files did not always make it into already created working branches, causing existing projects to continue using old mechanisms. The overall limit on parallel tasks could lead to delays in independent projects, despite isolated working environments.

The main mistake of my initial approach was an excessive focus on agent capabilities. I was interested in what tasks they could perform, how well they wrote code, and how many actions they could take without human intervention. Meanwhile, the reliability of the surrounding infrastructure remained secondary, although it is precisely what determines whether the system can be trusted for prolonged independent operation. The agent's ability to successfully complete a task does not yet mean that the orchestrator can correctly manage environments, account for state changes, and safely handle failures.

Money

It would be convenient to end this story with the conclusion that the first architecture turned out to be unsuccessful and autonomous AI agents are not yet ready for commercial development. The only problem is that the system continues to work, perform real tasks, and bring benefits to the company. Its shortcomings do not negate the economic value of the approach, but rather show what problems need to be solved before increasing the scale of autonomy. Abandoning a technology that has already demonstrated practical results solely due to dissatisfaction with the first implementation would be a rather strange business decision.

This is precisely why I am now working on a new project. Unlike AI Workflow, which was created to perform individual tasks in existing repositories, the new system is focused on managing entire projects: their state, dependencies, executors, memory, and recovery from failures. When designing, I try to pay more attention not to the number of actions an agent can perform, but to the reliability of the mechanisms that control these actions. However, I will no longer declare a new architecture successful before it is tested in real operation.

The first version left behind two results. As its creator, I do not consider its architecture an achievement to be proud of. As a person interested in the commercial application of AI, I see a working tool that has confirmed the economic potential of autonomous development. And now I have a perfectly rational reason to continue working, despite all the discovered shortcomings.

Money proved more convincing than my architectural claims.

P.S. About Data Security

Since we are talking about commercial repositories, I have separately provided for access restrictions to the source code. Each session runs in a separate clean virtual machine, tasks are isolated from each other unless a connection between them is explicitly specified during setup. The agent receives the project's dependency map and only the context necessary to complete the task. If access to a private module with sensitive data is required for work, the system reports a restriction rather than granting access automatically.

For tasks involving confidential information, there is a separate "Sensitive Information" flag that switches execution to a local model. Thus, the manager does not need direct access to the repository, and the agent operates within the scope of the permissions granted to it. Of course, this does not make the system invulnerable, but it allows for centralized control over access to source code and the execution environment.
