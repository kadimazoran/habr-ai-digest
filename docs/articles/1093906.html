Such requests are increasingly handled by the AI agent itself, which records what it has done.

Why Support Needs a Ticket

The first version of ITIL was released by the British government agency CCTA in 1989, when the first ticket tracking systems were already in operation in companies. Since then, support work has been described by one cycle: create a ticket, figure out what it's about and how urgent it is, if necessary, transfer it to the next level, and close it. The framework versions, tools, and role names have changed several times during this period, but the process of handling requests has remained the same.

The reason is that a support employee cannot start acting without recording what they are doing: otherwise, the request will be lost during shift changes, two support staff will work on the same issue, and a third will not know that someone from accounting has been waiting for a response since morning. The ticket simultaneously served as the support queue and memory, and it also recorded when responsibility for a request passed from one employee to another. Therefore, management accounting was also kept by tickets. SLAs were calculated based on them: response time and resolution time. Reports were also compiled on how many requests came in for each category and how many went to the second level, and the support employee's KPI was tied to the number of resolved tickets per shift.

The status "closed" did not guarantee that the issue was resolved. The support staff closes the ticket with the comment "please restart your computer," the user opens a new one an hour later, and the report shows two successfully processed requests, even though the malfunction has not been fixed. To distinguish such cases, ITSM has long separated the statuses "resolved" and "closed" and counts reopens. However, in first-line reports, the number of closed tickets is still most often looked at: it at least shows how many times an employee had to take a request for work.

Over thirty years, job descriptions, KPIs, management reports, and even career paths have been built around the ticket: a newcomer starts in the first line with passwords and printers and moves to the second line in a couple of years. Therefore, it is difficult for many to even imagine support where a request is resolved without a ticket in the queue. For some typical requests, it already works this way.

What Changes When an AI Agent Handles a Request

If we break down a typical request step by step, we can see how much manual work is involved. The user writes: "I can't log in, it says my account is blocked." A ticket is created and goes to the first-line queue, the support staff takes it, logs into the Active Directory console, unlocks the account, resets the password, provides the temporary one, and closes the ticket. Each of these steps is necessary because a person is involved in the process: tasks are handed over to them, and they are held accountable for the result.

Now, let's imagine an AI agent with access to AD handling the same request. It verifies the user's identity using a second factor, finds the account, and sees that it was blocked due to a series of failed login attempts. The agent checks that the attempts came from the user's own device, unlocks the account, resets the password, sends the temporary one to the channel associated with the account, and verifies that the login was successful. If the attempts came from external devices or addresses, the agent does not unlock anything and forwards the request to the security department.

All steps are performed by a single agent, there is no need to transfer the task, and a queue is not needed in this scenario. Password resets without a queue have long been handled by self-service portals (SSPR), but there the user chooses the action from a menu. The agent understands requests in free form and decides what to do, so this example shows how much manual work it takes away from the first line and where it can make mistakes. For such requests, the ticket, around which support work has been built for thirty years, ceases to serve as a queue, which is precisely what it was created for.

Gartner predicts in a March 2025 press release that by 2029, agent AI will autonomously resolve 80% of common customer service issues without human intervention. In internal support, the agent has more data and access: each user is already in the account directory, and the systems it needs to act in belong to the company itself. The main flow here consists of similar requests: password reset, network folder access, license, adding to a mailing list. However, the cost of an error is also higher: the agent changes passwords and access rights in corporate systems, and one incorrect action can leave an employee unable to work or expose their data to others.

Major incidents, changes, and anything requiring approval are still handled by humans, and for them, a ticket remains a way to agree on work. The flow of simple requests, for which companies maintain an entire first line, is no longer passing through the queue. This is also taken into account in ITIL: in 2026, PeopleCert released the fifth version of the framework and a separate module ITIL AI Governance on controlling AI work in service management.

What Working Without a Queue Leads To

The ticket provided support with four things: an responsible party for each decision; reports where employee work was behind a closed ticket; a flow of requests that indicated mass failures; simple requests on which newcomers learned. As long as the AI agent resolves a few dozen requests a day, the difference is almost invisible. When it handles the majority of typical requests, support begins to lose all four.

1. It's unclear who is responsible for the result

When a support agent closed a ticket, there was a specific employee behind each decision. An AI agent's action has no such person: the request was processed by the agent, the script was configured by the administrator, and the rights were granted by the security department. ISACA's 2025 material calls this one of the main challenges of auditing agent AI: if the agent acts independently, it's unclear who is responsible for its decision.

Imagine there are two Ivan Petrovs in AD: one from accounting and one from logistics. One writes "reset my password, I'm Petrov," the agent selects the wrong account and resets the password for the person who didn't ask for anything. The first Petrov still can't log in. The second discovers in the morning that his password doesn't work and goes to support, where there is no ticket or record of anyone changing his account, so they have to investigate manually through domain controller logs.

2. Reports overestimate the degree of automation

A chatbot that provides a user with a link to a password reset guide has formally processed the request, and many reports count this if the user writes "thanks, I understand" and closes the window. Whether they reset their password themselves, called a colleague, or postponed everything until Monday, the system does not check. Some companies try to maintain familiar reports: the AI creates a ticket, assigns it to itself, and closes it instantly. The number of closed tickets increases, but such a record doesn't show what the agent did or if the user's task was resolved.

3. Newcomers have nowhere to learn

It was on typical requests that first-line employees learned about the company's infrastructure before moving to the second line. If such requests are handled by an agent, the first line is reduced, and it's unclear where future second-line engineers will gain experience. Stanford researchers, in a 2025 paper using US data, note a relative employment decrease of 13% among workers aged 22-25 in professions most affected by AI. The decline is most significant where AI performs tasks instead of humans, and typical first-line requests fall into this category.

What to Consider a Ticket and How to Monitor an AI Agent

This raises two questions: what should now be considered the unit of support work, and how to track the agent's actions. The market does not yet have a definitive answer, so we will discuss and share our own leanings.

If an agent handles a request from start to finish, what should be considered a ticket? We can leave everything as is and create a ticket for every request, even if the agent closes it instantly. Reports will remain comparable to previous years, but they will mix consultations, completed actions, and resolved tasks. We can consider only those tickets that reached humans as tickets, and account for the agent's work separately. The first-line queue will become more accurate, but the support manager will no longer see in one report how many total requests came in and how they ended.

We prefer the third option: consider a request with a confirmed result as the unit of accounting, regardless of who handled it. To do this, AI actions can be divided into three levels:

  1. AI responded: provided instructions or a link to a knowledge base article. The user received a consultation, but whether they solved their problem is unknown.

  2. AI performed an action, such as unlocking an account, granting access, or restarting a service, but the result has not yet been verified.

  3. Result confirmed: the user logged into the system, the folder opened, the service is responding. Only such a request can be considered resolved.

Often, the user doesn't even need to be asked for confirmation. Password reset is confirmed by successful login in the AD log, service restart by a green status in monitoring. Therefore, verification can be automated just like the action itself.

All three levels and the recalculation of metrics work under one condition: every agent action is recorded somewhere. The agent itself keeps a record of the request, and errors like the Petrov case are investigated based on it. We would expect such a log to answer five questions about each action:

  • who initiated it: user, monitoring event, or another agent;

  • based on what data the agent selected the object, e.g., Petrov's account;

  • what was done, in which system, and with what rights;

  • how the result was verified;

  • how to roll back the action if the result was incorrect.

In the Petrov case, the log would show that the agent selected the account by last name and did not cross-reference it with the one the user passed the second-factor authentication for. Such a cross-reference can be added to the script, and in case of ambiguity, the agent should clarify which Petrov is being referred to. Mass failures are also visible from the log: 300 identical unlocks in an hour can be caught by a rule and forwarded to humans as a problem. Training newcomers is more difficult, and we don't have a ready-made solution. Perhaps the first line will analyze the agent's log and the requests it forwards to humans, and thus become familiar with the infrastructure.

The log also helps with the issue of responsibility if the agent has correctly configured rights. When an AI agent operates under a service account with domain administrator rights, the logs only show "svc_admin acted" without specifying at whose request. It is more reliable to limit the agent with a rights matrix: it can reset passwords, but not change membership in privileged groups, and for access to financial systems, it requests human approval. Then, for each action, it is clear who requested it and who approved it.

It is more convenient to keep a log where support work is accounted for. If records of actions are stored separately in AD, monitoring, and Jira logs, then for metrics or incident investigation, you will have to manually correlate events from three systems by time and account name. The ITSM platform already has a service catalog, CMDB, SLA, and rights, so it is logical to keep the AI agent's action log there as well and link it to the request record. A copy of the log for security investigations is sent to SIEM.

In SimpleOne, agents are assembled in the AI Agent Builder and act on behalf of the user who started the session, so the agent cannot obtain data unavailable to that user. Each agent step is recorded in the platform's log: the administrator sees which tools the agent called, what data it requested, and what it received in response. Summary

The ticket appeared so that people could agree on who took the task, at what stage it was, and to whom to transfer it. When typical requests are handled by an AI agent, there is no one to transfer the task to, and the ticket becomes a log of its actions on the request.

Nevertheless, we believe that accounting is still needed, but now the unit becomes a request with a confirmed result, and the action log serves as the basis for metrics and insurance in case the agent resets the password for the wrong person. Support that counts confirmed results sees in the report how many users gained access to the system or opened the necessary folder after the request.
