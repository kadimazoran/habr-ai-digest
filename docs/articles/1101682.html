Hello, Habr! My name is Anastasia, and I am the head of IT compliance at RGS. Before each planning cycle, I need to review and evaluate hundreds of tasks to determine which ones require attention first. This usually took a full working week, so I decided to find a way to simplify this process to free up time for more complex expert work. As a result, I managed to automate part of the routine using AI, and in this article, I want to share how, without a development budget or programming skills, I reduced the task review time from five working days to two.

Five hundred tasks and one expert

Before each planning cycle, development teams collect hundreds of tasks, and each is evaluated against several criteria to decide what to work on first. One of the criteria is IT compliance: how much the implementation of a task in the information infrastructure helps the company comply with legal requirements. Missing an important task means risking a fine; overestimating an unimportant one means taking up a slot in the plan that could be used for a necessary improvement.

The prioritization procedure had just started, and only two "trains," meaning two major development directions, were participating in the pilot. The very first cycle brought about 500 tasks, and their review took the entire working week of the sole expert in the department. During this time, tasks for which compliance exists were on hold: analysis of new tasks for setting and implementing requirements, and support for complex projects.

And the connection of the remaining trains was yet to come. If nothing changed, task evaluation would have taken up most of the quarter, and there was no possibility to expand the team for peak load. Keyword filtering doesn't work in this case: the wording is too different across teams, and you need to search for meaning, not words.

The first idea was modest: to teach AI to at least separate tasks that the expert needs to look at from those that can be skipped. Not to replace the expert, but to relieve them of routine work. Spoiler alert: it turned out to be more than intended.

Step #1: Test the hypothesis at minimal cost

The logic for evaluating the prioritization criterion is always the same: read the task description, compare it with the criteria, assign a score, close the task. A language model can do exactly that. But first, the idea needed to be tested, and as cheaply as possible.

I made an anonymized dump of tasks and gave it to several external models along with instructions on the criteria. It didn't work the first time, but after several iterations of changing the prompt and instructions, the models started giving stable results.

Then I compared the models' scores with my expert evaluations. The initial accuracy was about 60%, and the errors were more often on the side of overestimation. This was a year ago, at the very beginning of the search for solutions. For my task, this was a key takeaway: an overcautious model can reliably filter out what definitely doesn't require the expert's attention, and only a small portion of tasks will remain for manual review. The scores could be uploaded back into the system via a script through an administrator.

For a start, this was an encouraging conclusion: the model is more likely to err on the side of caution than to miss something important. This means it can be used at least as a filter, which already saves the expert's time. But the result can be improved.

Step #2: Local AI and automation

The first option had three weaknesses:

  • Manual work. Preparation of dumps, transfer to the model, collection of responses ate up part of the savings.

  • Anonymization. Along with details, some meaning was lost, which affected accuracy.

  • Dependence on external services. The tool could stop working in Russia at any moment, and there were no resources to urgently find an alternative.

There were two paths left: a corporate solution or a local model on a laptop. The corporate solution didn't work out immediately, so I went with the second. A local model runs directly on the computer: data doesn't go anywhere, and it doesn't depend on external services. However, a laptop's resources are limited, tasks have to be submitted in batches, and not every laptop can handle it. This means an orchestrator is needed to manage the process.

I managed to assemble a set of tools for my solution:

  • n8n as the orchestrator. This is a visual constructor where the process is assembled from ready-made blocks, and minimal programming skills are sufficient.

  • LM Studio and Ollama for running local models. In the end, I stuck with Ollama.

There might be a more elegant solution, but for a start and to save myself, this set was perfect: free, accessible, understandable to a non-specialist.

The pipeline is set up as follows: task dump, cleaning text from technical garbage, transfer to the model along with instructions, response in a strict format (score level and brief justification), saving the result.

It looks neat on the diagram, but this is how the simplest assembly in n8n looks in reality.

The key element is the database of verified scores (RAG). Upon receiving a task, the model finds similar tasks that I have already evaluated and relies on them. Simply put, it doesn't guess; it looks at how similar cases were evaluated by an expert.

How to check that the AI is not mistaken

There were more and more assembly options for automation, and a system was needed to compare them honestly. Using AI for this is overkill: a regular program can compare scores and calculate proportions. I wrote it with the help of AI (it's faster). The program compares the scores of several algorithms with expert scores and calculates four indicators:

  1. Exact match: the proportion of tasks with the same score as the expert.

  2. Match with tolerance: the error is no more than one scale step.

  3. Filtering out the unnecessary: whether the algorithm misses important tasks and sends unnecessary ones to the expert.

  4. Where errors are biased: overestimation means an unnecessary check, underestimation means a risk of missing something.

This is how the conversation "it seems to have gotten better" turned into concrete numbers.

From 20% to 80%

The first assemblies in n8n gave a dismal 20% accuracy: there was no database of verified scores yet. Then came modifications to the example selection from the database, prompt refinement, and selection of local models. Overly heavy models would completely freeze the laptop.

The first good working assembly on Qwen and GPT-oss models gave 70–80% accuracy on a test sample and processed 500 tasks in about 12 hours. However, on real tasks, it gives 55–60%: in a live stream, there are more new formulations and systems, as well as tasks from trains that are just being connected to prioritization.

Then came options for algorithm development:

  • multiple scores from different models or from the same model with different parameters;

  • additional knowledge;

  • enriched knowledge: embedded in the algorithm or connected via MCP.

The selection criterion was simple: if the accuracy of an option dropped when new trains were connected, it was discarded. The surviving options work longer than the initial assembly but provide 78–82% accuracy on real data, and the errors towards overestimation and underestimation are now balanced. As a result, it turned out to be more than intended: instead of a filter for the expert, it became an algorithm that immediately assigns the necessary values, and the expert checks them as needed. Computer time is cheaper than expert time: the more accurate the algorithm, the less manual verification is required.

Process and results

Before: only new tasks were evaluated manually, and it took a week for 500 tasks. Changed tasks were not re-checked due to lack of time.

Now: the prioritization system has changed, but the process has survived. The algorithm itself dumps new tasks and tasks with changed descriptions before implementation, assigns scores, sends the file for review, and records the criterion value in the field for priority calculation. Values can be recorded immediately or after review, as decided by the expert.

Results:

  • Time: 12–24 hours of algorithm operation for 500 tasks, including verification, two days instead of a week.

  • Accuracy: 78–82% on real data.

  • Coverage: changed tasks are also evaluated.

  • Scale: there were two trains, now there are nine, and the process handles it.

  • Cost: free tools, no development resources.

What's next

80% accuracy for a local solution is a good and stable result, and I will stop there and periodically check if the accuracy is not decreasing. It's time to return to corporate tools so that the process doesn't depend on a laptop or a single expert. A corporate instance of the algorithm already exists. For now, it operates in a limited mode but provides comparable accuracy six times faster. The limitations need to be removed for full use of all functions.

The approach itself, "read, compare with rules, evaluate," is suitable for many operational processes, and other functions can reuse this experience. A similar process is already being launched in a test mode using AI.

AI has not replaced the expert, but it has changed their role: instead of assigning numbers, the expert manages the process and makes decisions where they are truly needed.
