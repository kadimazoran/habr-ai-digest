I had 16 models, 7 search tools, 2 AI model providers, one company, and a bunch of questions about how AI models search for company information on the internet. What do they find, how do they process it, what conclusions do they draw, and how can we influence it.

What I Tested

In my previous article, I analyzed agentic search using the example of searching for people at Sber. This time, I will be checking company information itself. For the experiment, I decided to use information about Bitrix24. I chose it because the data is public: the company is hard to miss, it has an official website with prices, EGRUL (Unified State Register of Legal Entities), a blog, a webinar archive — everything an agent should be able to find when analyzing the market or conducting competitive analysis.

The question for all models is always the same, consisting of 7 points:

  • P1 — Legal entity and details (INN, OGRN, address). This was one of the traps a model could fall into. LLC "BITRIX24" in Kaliningrad is not the Bitrix24 we're looking for, but an empty holding company with no employees and OKVED code 64.20. If the agent confuses them, the numbers will look good but be incorrect.

  • P2 — Revenue for the last known year. Another bottleneck. Data for 2023 is available, but the company has not published data for 2024-25. It might be available in services like Rusprofile or Kontur, but I don't have paid access to them, and it wasn't intended by the design.

  • P3 — CEO and CMO with their positions. The CEO is listed in legal documents, and the marketing director actively gives comments in the media.

  • P4 — Products, tariffs, prices - all of this is on the company's website.

  • P5 — Product updates for 2026 - these can also be found on the website and in releases.

  • P6 — The two most recent past and two upcoming webinars (checked in mid-October).

  • P7 — Mentions in the media over the last 6 months (RBC, Vedomosti, Forbes, Kommersant, CNews, and others)

For each point, the model provides a confidence rating: "confident / not confident / don't know."

How I Calculated

Before the first run, I manually compiled a reference — the "gold standard," where I had pre-verified all company data.

Each point is evaluated on a three-point scale:

  • V ("Verified") — all key facts are correct and confirmed by a source. Awards 2 points

  • P ("Partial") — some facts are correct or there are omissions. Awards 1 point
  • N ("Not Found") — the point is failed or empty. Awards 0 points

The maximum score a model could get was 14 points. In addition to completeness, I counted E — the number of points with a verifiable error — and C (Confident Fabrications): this is when a fact is incorrect, but the model marked it as "confident." Such an error is more costly in production than an omission: confident answers will not be checked if people are unaware of them, they look convincing, or it's new information for someone who isn't an expert. The rating metric is net score = Completeness − E.

I evaluated manually and with the help of Grok Bot. I did not use an LLM judge like JEV this time.

How the Experiment Proceeded

This time, there were six stages to the experiment, each stage answering a specific question:

  1. Without Search — point zero: what models know about the company on their own, without using search.

  2. Search Matrix — I ran 2 free models on 7 search engines; one run per combination. The main goal was to understand the operation of search tools.

  3. Paid Models on the Best Search Engine

  4. Three Runs on a Pair — we check reproducibility; we find the spread of answers from the model

  5. Search with Wrapper — the code itself downloads sources, the model only extracts fields;

  6. Full Series — all models × Exa, Brave, DDG snapshots, and Brave; final summary

What Search Engines I Used

Before moving on to the results, a few words about each tool. What exactly the agent calls and what it gets in response.

Exa (exa.ai) — semantic search on its own index. A natural language query is matched with page embeddings. Returns full text, highlights, summary. On the free tier — $10 credits per month. Good at finding specific facts, not just links. Requires an API key, registration without a card.

DuckDuckGo (ddgs) — Python library duckduckgo-search, which parses the results from multiple engines. No API key, no SLA. Returns title, URL, and a snippet of about 200–300 characters. Okay for prototypes, fragile for production: temporary IP blocks and changes in search results without warning can occur.

Tavily — AI aggregator optimized for LLMs. Aggregates up to 20 sources, cuts content into chunks of 500–800 characters, and ranks by relevance. Provides 1,000 credits per month without a card. Returns already chunked content — no need to scrape yourself, but you can't influence the chunking.

SearXNG — self-hosted metasearch engine under AGPL. Aggregates up to 244 sources. JSON format needs to be enabled manually in the config. Returns snippets, no full text — to get the text, a separate fetcher is needed. Free when self-hosted, but setup takes time.

Firecrawl — this is a scraper, not a search engine. Renders a page in Chromium, removes ads and navigation, and returns clean markdown. Has a /search endpoint, but its task is not to find, but to read an already known URL. 1,000 credits per month without a card. Best used for reading pages from specific links found by another tool.

Keenable — its own index with point-in-time search. You can specify the indexing date and request "how it was then" — this distinguishes it from others. Public tier: 1,000 requests per hour per IP. With an API key — up to 100,000 requests per month for free.

Brave Search API — its own independent index of 30+ billion pages, not an aggregator of others' results. Has an /llm/context endpoint that breaks content into chunks for token budget — in theory, more convenient for agents. Requires an API key and a credit card. Free tier — 2,000 requests per month. Used up quickly, I added $5 to the account.

Step 2. Search Matrix

For the matrix, I needed models that honestly say "I don't know" rather than hallucinate. Why is SearXNG so bad? I ran a local instance without configuration — out of the box. It only returns snippets without full text. There was an illustrative story with dots: the agent found a link to helpdesk.bitrixrix24.ru — with a typo in the domain. The URL opened and returned HTTP 200. The agent confirmed the fact. The fact was incorrect — it linked to someone else's site. If Bitrix24 employees are reading this, you should pay attention to this; it might be a phishing page.

This is the main pattern of search errors: not a fabricated URL, but an incorrect reading of a live page. Out of approximately 66 URLs manually checked via curl, only 2 were dead. However, the story with bitrixrix24.ru indicates a more serious risk. The agent reaches pages that a person would never click on — because a typosquatted domain is simply not noticeable in search results. The page returns HTTP 200, the content looks plausible, and the fact goes into the answer with a "confident" label. In a real pipeline, this could be a phishing site, a competitor's page clone, or a satellite site with intentionally distorted data. It's worth adding domain validation to the wrapper before releasing the agent into production.

Step 3. Best Search Engine + Paid Models

Next, I took 8 paid models and ran them on Exa as the best search engine in the matrix. The average score for the answers was 11.1/14, 2 points better than the free ones. All 8 found CMO Vartanyan — a good sign: in step 1 (without search), no one mentioned him. MiMo reported on the 422 million from Kaliningrad: "this is an empty holding company with 0 employees — this is NOT the revenue of the Bitrix24 business." Sol wrote "don't know" for revenue — an honest gap instead of a fabrication.

Two observations from this series are worth special attention.

First: accuracy is more important than search cost. Exa spends credits on extracting full text — this is the reason for better results compared to DDG. DuckDuckGo is cheaper, but the agent only gets snippets and has to guess the rest.

Second: traps worked selectively. The Kaliningrad LLC caught only those who didn't perform an additional query to EGRUL. MiMo and Qwen Max did. Inkling did not.

Step 4. Spread Between Runs

After the initial results, I performed three runs for each pair (pair = "model + search engine") to understand how reproducible the search figures were. I think each of you can recall cases where the same prompt could yield different results.

If at the beginning, one run, as a single shot, could show whether the pair works/doesn't work, then further it was necessary to understand how reproducible or chaotic the model's answer would be. After all, the task is for it to be equally high-quality every time and for all queries.

Here's what I found: the spread between runs of the same model is 3–6 points. Sol received from 7 to 13 points on the same prompt and search engine. The difference between adjacent places in the ranking is about 1 point.

What the Agent Actually Does Under the Hood

This is the most interesting thing I found at the end. I looked at tool_calls.json for each run and saw a pattern that explains almost everything.

Two types of calls the agent makes: web_search — a query to the search engine, returns a list of links and snippets; web_extract — the agent visits a specific URL and reads the entire page. The first is to find, the second is to read.

Leaders hit the search limit and open pages. Qwen Max on Brave — about 23 web_search calls and 6 web_extract calls, 5–6 minutes per run. MiMo and Sol do roughly the same. They spend most of their tool budget on reading: searching is fast, reading is expensive.

Weak models hardly read pages:

  • Inkling: 7 searches, 0 web_extract, answer about 900 characters → completeness 3.7

  • Mistral: 7 searches, 0 extractions → 4.0 in all three Brave runs

  • gpt-oss: 6 searches and 1 extraction, 30 seconds → 5–6 points

  • Gemma: an average of 0.3 extractions per run

Sonnet and Gemini — an intermediate case: 7–11 searches, 0–1 extraction, 40–50 seconds. This resulted in fast but shallow answers. Sonnet on Brave averages 8 points, while on Exa search it gets 11.3. They manage to gather CEO, tariffs, and products — but there's no search budget left for webinars and recent media mentions.

If you want to speed up the agent, consider this trade-off first. Reducing the search limit means less web_extract, and thus — failures on difficult questions.

There's also a direct dependency here: the completeness of live search increases with the number of web_extract calls, not with the call to the model itself. "Find a link" and "read the page" are different actions, and the agent can do the first without the second.

You expect that the "smarter" the model, the more accurate it is. But in practice, tool_calls shows otherwise: the more accurate model is the one that goes to read pages after searching. Mistral is a strong model, but it hardly opens pages — and lags behind those that do.

Step 5. Who Works in What Mode

When I added the wrapper (the code collects a snapshot of sources, the model only extracts fields from a prepared dossier), unexpected inversions occurred.

What is this snapshot? Before running a series of tests, I run the collector script (collect.py) once, which downloads a fixed set of pages and saves them to snapshot.json with a sha256 hash. After that, all runs in the series receive the same source data — regardless of when they are launched. This removes random noise from live results and makes the runs reproducible.

Gemini 3.8 Flash on the DDG snapshot — 12 points and 0 errors in all three runs, almost for free. When using Brave, only 9.3: the agent stops early, hardly opening pages.

Mistral Large 3 and Gemma 4 31B are weak on live search (Brave 4.0 and 6.0 points respectively). On the DDG snapshot, the correctness of answers rises to 10.7: it's easier for them to write from a prepared dossier than to navigate pages themselves.

Nemotron 3 Super — on the contrary: live Brave 9.0, snapshots 3.3–3.7. The wrapper doesn't suit this model.

Luna on live Brave gets 7.3 points (gives empty answers for P2 and P7, stops early). On the snapshot, it consistently gets 11.0.

DeepSeek v4.1 Flash — a striking contrast between modes. On live Exa: 11.7 average (one of the leaders). On the DDG wrapper: 6.7 — below average for the entire sample. The Brave wrapper keeps it at 10.7. Possible reason: the live snapshot poorly covers the exact sources that DeepSeek is used to accessing during live search. Exa returns full pages; DDG snapshot — snippets for fixed queries. With the Brave wrapper, where the snapshot is richer, the model recovers.

The Hardest Question — Webinars

The webinar question turned out to be the most difficult for all models across all 90 runs. No model, no mode, managed without errors.

On live Exa search, the average score for P6 is 0.77 out of 2. On live Brave — 0.44. On the Brave snapshot — 0.36.

Why is it so difficult? Pages of past webinars are removed from the site after the event. For example, a meetup took place on October 6th — by October 13th, the page meetup-06102026.php already returns 404. The webinar list on bitrix24.ru is rendered by JavaScript — the extractor doesn't see it. The model picks up any dates it finds: partner events, foreign events, last year's events.

Also, all models fell into a recurring trap: they indicated February 25th as the "last webinar." Sol, Sonnet, and Qwen Max on the DDG snapshot fell into this — all three repeats of each. The code honestly chose the latest found in the snapshot, not knowing that more recent pages had already been deleted.

Even the code with direct fetchers only took 2 out of 4 slots (08.10 and 15.10). Pages 06.10 and 13.10 are unavailable, deleted, and DDG didn't capture them in the snapshot. Without paid search with cache or Wayback Machine, these slots cannot be filled.

Conclusion: events from the past week, deadlines, announcements, situational publications — the agent cannot retrieve them without a specialized tool. Prompts don't help here. This is a structural problem: no search engine in the experiment cached deleted pages fast enough for the agent to read them a week after the event.

The only way is either a specialized tool (Wayback Machine API, paid cache), or to retrieve data directly on the day of the event, not retrospectively. For a production agent, this means: webinars are better filled from a separate source with a schedule subscription, rather than relying on general web search.

Step 6 Code Searches, Model Only Extracts

In the last step, I swapped roles: search and verification are done by code, the model only extracts fields into JSON. This is what is usually called a harness — a wrapper around the model.

The hypothesis was simple: the main errors in live search are not model hallucinations, but incomplete page snapshots and incorrect dates. Code with deterministic rules should fix this.

The scheme is as follows:

  1. Downloads fixed sources in advance: EGRUL, bitrix24.ru/prices, helpdesk digests, DDG or Brave answers for specific publications

  2. The model receives a prepared dossier and returns fields: field, value, date, url, verbatim quote

  3. 8 conditions are checked: quote is on the page, year is present in the quote (not just in the URL), domain is in the whitelist, "holding ≠ product".

  4. Two independent calls for each item. A fact becomes "confident" only if both calls yield the same result. Otherwise, it's "for review."

Conclusions and Findings

1. Don't start with a wrapper. Start with live search and a good model. Top models on live Exa search gave 11.3–12.7. The same models on a snapshot with a wrapper (DDG) — 8.7–12.0. Freshness of results is more important than verification mechanics. Add the wrapper later — when there's a specific reason: errors of a particular type that the wrapper can fix. Until then, the wrapper will only weaken the result.

2. A good model is not necessarily expensive. MiMo v2.6 Pro on Brave cost about $0.03–0.06 per run with a completeness of 12.3 and zero confident errors. Sol for the same tasks — $0.2–0.4 with a completeness spread of 7–13. Test 2–3 cheap options before paying for a flagship.

3. Want less deception — verify facts, but remember the cost. A wrapper with verification almost eliminates confident errors. But 8–30 facts per run go to a human for verification. Suitable when an error is costly and there is a person in control. Not suitable for a humanless pipeline.

4. A wrapper harms a weak model. Mistral without a wrapper: 4.0; with a wrapper on the DDG snapshot: 10.7. Nemotron Super, on the contrary: 9.0 → 3.3. A wrapper is an amplifier: it lifts the strong, drowns the weak. If the agent with checks became worse — change the model, not fix the wrapper.

5. Check the tool before blaming the model. 9 "bad" Brave runs turned out to be an exhausted free limit — HTTP 402 on all searches. The models were not to blame. A test query to the search engine before running is mandatory. If all searches returned an error — the run doesn't count.

6. Add domain validation. The agent reaches typosquatted pages (like bitrixrix24.ru) that return HTTP 200 with plausible content. A whitelist of allowed domains in the wrapper is cheaper than dealing with the consequences.

7. Incident log is part of the results. False 429 due to substring search, self-induced 429 from 7 parallel Ollama calls, outdated models.json copy, deltas /key from parallel runs — without analyzing incidents, the team will repeatedly hit the same pitfalls. Publish the log along with the numbers.

8. Provider is part of the conditions. One model through different hosts — not one model. DeepSeek and GLM changed providers (from Ollama to Openrouter) in the middle of the experiment — these cells are incomparable. Record the provider in the metadata of each run.

9. The reference drifts. A live company changes every week. Version the reference with a cutoff date — otherwise, a repeat in a month will measure against a partially outdated standard.

10. MiMo v2.6 Pro — best price/quality ratio among the measured pairs. Completeness 12–12.3, zero confident errors, about $0.03–0.06 per run. 4–6 times cheaper than flagships with comparable cleanliness. Monitor the provider: MiMo via the Xiaomi provider sometimes responded in 7–19 minutes versus the norm of 5–6. Provider pinning here is not an option, but a necessity for reproducible results.

11. Completeness increases with the number of web_extract calls, not with the model call. Leaders make 22–23 searches and 5–6 page extractions. Weak ones — 7 searches and 0 extractions. If the agent found links but didn't visit the pages — it did half the job. This same rule explains why softening the search limit improves results more than replacing the model with a more expensive one.

12. Consider agent protection. During the search, the agent may encounter phishing pages or malicious information. In the best case, the work will be in vain. In the worst case, attackers will be able to exploit the vulnerability for their own purposes.

Good luck building agentic loops!
