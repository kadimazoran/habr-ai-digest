When an AI agent needs to work with dozens of tools, each call and its result can create an excessive load on the LLM's context. Codemode allows combining operations in code, but working with MCP introduces new limitations — from nested calls to unpredictable response formats. Over a year ago, I wrote articles advising against loading custom tools (including MCP servers) into the model's context, suggesting using scripts whenever possible.

Now, with the release of Pi 1.0, we've added MCP support through Codemode.

On one hand, this has been a long time coming, and on the other, this solution might have been unexpected for some. Therefore, I want to share my latest thoughts on what this all means.

What are Tools

When an agent's wrapper, like Pi, provides LLM tools for invocation, it passes their descriptions to the model, which are then converted into a specific token structure on the server side. Whether the model is inclined to call a particular tool depends on how it was trained with reinforcement learning.

One of the main reasons we prefer CLI and bash is the ability to easily combine calls. Additionally, during training, the model learns the principles of file system operation.

Therefore, when it executes the command echo foo > /tmp/test.txt, it understands that after this, a file named test.txt will appear in the /tmp directory.

However, bash has one fundamental limitation: it can only combine executable programs. Some tools are not programs; they are embedded directly into the LLM interaction interface, and there's no other way around it.

The most obvious examples are read or view_image. If a multimodal model needs to read an image, simply calling cat won't work: the agent's wrapper must pass the image data itself directly through the LLM interaction protocol.

Another clear example is sub-agents. Launching and managing them without the tools provided by the agent's wrapper is quite difficult.

Theoretically, one could create a CLI tool that interacts with an external wrapper via environment variables and Unix sockets, but the solution would be rather crude.

However, there's another problem: where exactly is the code executed.

Brain and Hands

To better understand this, we need to clarify where all the system components are executed. Typically, two different parts are involved.

  • The "brain" — the agent's wrapper. It runs on a separate machine and is considered trusted.

  • The "hands" — the part that often resides on the same machine but is directly responsible for executing tools. In Pi, we now call this part the execution environment, but essentially, it's the target environment where all operations are performed.

It is fundamentally important for us that there is a clear boundary between the "brain" (agent wrapper) and the target environment where bash runs and tools operate.

This separation has serious consequences. First and foremost, these two parts can have different file systems and different trust levels.

For example, if Gondolin or a similar isolation solution is used, all bash commands will be executed in a sandbox, but the agent wrapper itself will remain outside of it.

Agent Wrapper Management

And here we come to what Codemode is actually needed for.

It allows the LLM to describe complex operations and manage their execution on the agent wrapper's side, rather than in the target execution environment.

Codemode operates within the wrapper, in its own sandbox. In Pi, QuickJS is used for this within a WASM execution environment with intentionally introduced limitations:

  • no network or file system access;

  • no timers;

  • limited RAM.

The only way to interact with the outside world is by calling other tools. In principle, instead of JavaScript, Scheme or another language could have been used in Codemode.

If you are not yet familiar with Codemode, it is essentially a way to call tools directly from code in a specific language, in our case, JavaScript.

Thanks to this, calls can be combined without passing each one through the LLM's context.

The name itself was coined by colleagues from Cloudflare, who first proposed this term.

For example, if the LLM calls bash as a regular tool, we only pass the last 2000 lines of output to the context. If the agent needs more, it will have to access the file with the remaining output itself.

But if the same call is executed via Codemode, it receives more extensive results in a structured format.

More importantly, since Codemode uses JavaScript, the agent can describe parallel operations and simple workflows.

Currently, agents often use this scheme:

  1. First, they check 5–10 elements from a tool's response to understand the data structure.

  2. Then, they write a script for Codemode that processes the next n elements.

Codemode also allows saving state in the session history!

This means that one Codemode call can save data, and the next call in the same session can load it again.

And don't forget: all this happens on the agent wrapper's host, not in the target environment's sandbox.

In Pi, Codemode also provides access to calls that simply don't fit the traditional tool interface.

For example, if you need to generate images using the corresponding model or perform text classification with a single call to a classifier model, these Pi APIs are accessible through Codemode. As regular tools, they would just take up unnecessary space in the context.

Image Generation

Let's start with something simple: image generation.

Image generation is supported in the AI SDK core but is not exposed as a tool available to the agent.

Previously, image models could be used either through a specially written extension or by forcing the agent to run node and access internal APIs for image manipulation.

But since Codemode gives us access to some of the internal model APIs, the agent can now do this directly:

const [painter] = await models.getAvailableOfType("image");
const result = await models.generateImages(painter, {
  input: [{ type: "text", text: "A cute little puppy sitting on a grassy " +
    "lawn, soft natural light, photorealistic" }],
});
if (result.stopReason !== "stop") return result.errorMessage;

for (const block of result.output) {
  if (block.type === "image") image(block);
  else text(block.text);
}

Note that the image() call returns the image to the LLM as content of type image.

On the agent wrapper's side, it is immediately passed to the agent itself and saved to disk as a temporary artifact — in case the agent later wants to pass this image back to bash.

Classification

It's similar with classifier models, like Jev.

They also don't fit well into the agent's typical workflows through standard tools. But instead of creating a separate specialized tool for them, Codemode simply allows the agent to access the AI SDK directly and call them from there.

Below is how Jev is used for mass processing of GitHub Issues and rapid sentiment analysis:

const jev = await models.getModelOfType("classifier", "typesafe", "jev-latest");
const r = await tools.bash({
  command: "gh issue list --state open --limit 100 " +
    "--json number,title,body,comments",
});
const issues = JSON.parse(r.output);

const results = await Promise.all(issues.map(async (issue) => {
  const res = await models.classify(jev, {
    state: {
      title: issue.title,
      body: (issue.body || "").slice(0, 4000),
      comments: issue.comments.slice(-5).map(c => c.body.slice(0, 800)),
    },
    questions: {
      sentiment: {
        type: "choice",
        instructions: "What is the overall sentiment of the author towards pi?",
        criteria: {
          positive: "Appreciative, happy, constructive praise",
          neutral: "Matter-of-fact report or request without emotion",
          negative: "Frustrated, annoyed, upset, or angry",
        },
      },
      frustration: {
        type: "score",
        instructions: "How frustrated is the reporter?",
        criteria: ["not at all", "mildly", "clearly frustrated", "very angry"],
      },
      kind: {
        type: "choice",
        instructions: "What kind of issue is this?",
        criteria: {
          bug: "Bug report or regression",
          feature: "Feature request or enhancement",
          question: "Question or support request",
          other: "Docs, discussion, meta, spam",
        },
      },
    },
  });
  if (res.stopReason !== "stop") {
    return { n: issue.number, title: issue.title, error: res.errorMessage };
  }
  return { n: issue.number, title: issue.title, ...res.answers };
}));

store("sentiment_results", results);
return results
  .filter(r => !r.error)
  .sort((a, b) => b.frustration.score - a.frustration.score)
  .slice(0, 12)
  .map(r => `#${r.n} ${r.frustration.score.toFixed(2)} [${r.kind.choice}] ${r.title}`);

Note that in the example above, we also call store(), which saves the execution result in the session history. Thanks to this, the agent can retrieve this data again on the next Codemode call if it needs it.

Using Promise.all here is perfectly fine, as Pi itself limits the number of concurrently executing tool calls to four, queuing the rest.

A more interesting example is using Jev to control a game engine during debugging:

Codemode with Jev for Game Debugging

Here, the agent already knows about my tankctl command and quickly creates a minimal wrapper around it that controls the game loop and helps the user resolve the issue.

Notice how it organized a 30-step loop. At each step, the agent queries the game engine for a text representation of the current game state, and then queries Jev to determine the next action:

const jev = await models.getModelOfType("classifier", "typesafe", "jev-latest");
const tank = async (cmd) =>
  (await tools.bash({ command: `tools/tankctl "${cmd}"` })).output;
await tank("start --map assets/maps/night_arena.map");

const questions = {
  action: {
    type: "choice",
    instructions: "You control the tank '@' in a top-down tank game. " +
      "Choose the best next action.",
    criteria: {
      attack: "an enemy has line of sight to you and you can fire at it",
      approach: "no enemy has line of sight; drive toward the nearest enemy",
      dodge: "an enemy shot is heading at you and will hit soon",
      powerup: "a powerup is close and no enemy threatens you",
    },
  },
};

function commandFor(choice, st) {
  const p = st.player;
  const enemy = st.enemies.filter(e => !e.dead)
    .sort((a, b) => (b.los - a.los) || (a.dist - b.dist))[0];
  if (choice === "attack" && enemy) {
    return `fire_at tank ${enemy.id}; frames 30 until clear,damage,kill`;
  }
  if (choice === "dodge") {
    // move perpendicular to the closest incoming shot
    const s = st.projectiles.filter(s => !s.yours)
      .sort((a, b) => a.eta - b.eta)[0];
    const dir = s && Math.abs(s.vel[0]) > Math.abs(s.vel[1])
      ? (p.pos[1] > s.pos[1] ? "+down" : "+up")
      : (p.pos[0] > (s ? s.pos[0] : 0) ? "+right" : "+left");
    return `input ${dir}; frames 20 until damage; input stop`;
  }
  const powerup = st.powerups.filter(u => u.available)
    .sort((a, b) => a.dist - b.dist)[0];
  if (choice === "powerup" && powerup) {
    return `goto ${powerup.pos[0]} ${powerup.pos[1]} 180`;
  }
  return enemy ? `goto ${enemy.pos[0]} ${enemy.pos[1]} 90` : null;
}

const log = [];
for (let step = 0; step < 30; step++) {
  const st = JSON.parse(await tank("state"));
  if (st.state !== "playing") break;
  const threats = st.projectiles
    .filter(s => !s.yours && s.miss_dist < 1.5 && s.eta < 1.5)
    .map(s => `incoming shot dist ${s.dist} eta ${s.eta}s`)
    .join("\n") || "no incoming shots";
  const r = await models.classify(jev, {
    state: { map: await tank("view 8"), threats, hp: st.player.hp },
    questions,
  });
  if (r.stopReason !== "stop") {
    log.push(`#${step} classifier error: ${r.errorMessage}`);
    break;
  }
  const choice = r.answers.action.choice;
  const cmd = commandFor(choice, st);
  if (!cmd) break;
  log.push(`#${step} hp=${st.player.hp} ${choice} -> ${await tank(cmd)}`);
}
return log.join("\n");

Calling MCP Servers

Finally, Codemode is excellent for calling MCP servers.

Since we don't give the LLM direct access to MCP tools, the agent first uses available APIs to search for tools within Codemode to find out what capabilities the connected servers have.

Thanks to this gradual tool discovery, working with MCP is already quite convenient for many tasks today.

For example, here the agent directly accesses Sentry MCP without even performing a preliminary tool search.

It's likely that during reinforcement learning, it already learned how Sentry MCP is structured. At the same time, the agent learns about the existence of the Sentry server from the information we add to the system prompt. This means it's not acting entirely randomly.

const orgs = await tools.mcp__sentry__find_organizations({});
const { organizations } = orgs.structuredContent;
const results = await Promise.allSettled(organizations.map(org =>
  tools.mcp__sentry__find_projects({
    organizationSlug: org.slug,
    regionUrl: org.regionUrl,
  })
));
return organizations.map((org, i) => {
  const r = results[i];
  if (r.status !== "fulfilled") return { org: org.slug, error: String(r.reason) };
  if (r.value.isError) return { org: org.slug, error: r.value.content };
  return {
    org: org.slug,
    projects: r.value.structuredContent.projects.map(p => p.slug),
  };
});

Modern MCP Requires a Fight

I don't want to delve too deep into the topic of MCP, but in reality, this protocol greatly benefits from using Codemode.

The problem is partly that in practice, MCP is often oriented towards agent wrappers that do not yet (or ever?) use Codemode. However, the situation is gradually changing.

Meanwhile, as a temporary solution, we used Cloudflare's approach: running Codemode within the MCP server itself.

But now we have Codemode within Codemode, which is quite bad.

This leads to double JSON escaping, which small models easily get confused by, and the inner Codemode's code cannot call the outer one's tools.

For example, if you use Cloudflare's MCP servers in Pi, the agent has to write JavaScript and pass it through another layer of JavaScript.

The solution is far from optimal, although it's understandable why things turned out this way:

const accRes = await tools.mcp__cloudflare__execute({
  code: `async () => {
    const r = await cloudflare.request({ method: "GET", path: "/accounts" });
    return r.result.map(a => ({ id: a.id, name: a.name }));
  }`,
});
const accounts = JSON.parse(accRes.content.map(c => c.text).join(""));

const out = [];
for (const account of accounts) {
  const r = await tools.mcp__cloudflare__execute({
    account_id: account.id,
    code: `async () => {
      const r = await cloudflare.request({
        method: "GET",
        path: \"
/accounts/${accountId}/workers/scripts\"
      });
      return r.result.map(s => ({ id: s.id, modified: s.modified_on }));
    }`,
  });
  out.push({ account: account.name, workers: r.content.map(c => c.text).join("") });
}
return out;

What MCP Lacks

So, let's summarize: how well does Codemode work with MCP today?

Well... not great, to be honest.

The issue is that MCP servers are not yet fully designed for agent wrappers with Codemode, although, as far as I understand, most wrappers already support it.

For everything to work correctly, several points should be considered:

1. Structured Data

Codemode works better with calls that return neatly formatted JSON. Therefore, MCP servers should provide results in this format, and many currently do not.

The outputSchema mechanism in MCP is perfect for this.

2. Result Uniformity

An interesting failure case occurs when an MCP server returns data in inconsistent formats. For example, it tries to optimize token usage based on the number of items in the response.

As a result, a test request with five items succeeds, but when the server returns a maximum-sized batch, processing breaks.

3. Large Binary Data

Currently, MCP does not support transferring large amounts of binary data, so many interesting scenarios work very poorly.

We have to resort to all sorts of workarounds, such as using pre-signed URLs to upload files bypassing MCP.

4. Composable Tool Discovery

An MCP server can better understand which tool is suitable for a specific task than an MCP client.

However, there is currently no convenient mechanism that allows the agent wrapper to distribute tool discovery in parallel across multiple MCP servers.

Currently, it works through emergent behavior, and this approach scales poorly when working with multiple servers simultaneously.

The Future of Codemode

So, where have we ended up? Am I retracting what I wrote a year ago when I recommended using CLI?

I don't think so.

Moreover, from my perspective, the MCP ecosystem has adopted what we've been talking about for a year: code really works.

But Codemode goes beyond MCP. It gives the agent more freedom, allowing it to describe and execute complex operations directly through the wrapper.

However, some issues still need to be resolved.

For example, with Codemode, it's harder to ensure reliable execution with fault tolerance. Perhaps ideas from robust workflow execution engines should be borrowed, and call state snapshots should be saved.

Or maybe Starlark, with its determinism, would be a better fit for combining operations than JavaScript.

Working with images and binary data, as well as the inability of small models to effectively use this approach, all require further refinement.

So, Codemode is still far from a perfect solution. But it is already a very useful approach, and I am confident that we will use it more and more actively.

Connecting an MCP server to an AI agent is only half the task. Next, you need to teach the agent to select the right tools, combine their calls, and process the results without overloading the LLM's context. To do this, it's important to understand how agent architecture works, the role of reasoning and RAG, and when to distribute tasks among multiple agents.
