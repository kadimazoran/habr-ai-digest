You know that feeling when you read an article about local LLMs and think: 'Oh, that's easy. I'll just install Ollama, pull a model, and I'll have my own AI agent that knows all the code'?

I thought exactly that.

My name is Egor Laptev, I'm a QA Fullstack Java at SENSE on a project for a major Russian bank. I have a MacBook Pro M2 Pro with 32GB of RAM: not a top-tier machine, but a workhorse for development. I had no idea that 20 minutes after launching the model, my laptop would sound like a fighter jet taking off, and the CPU temperature would be high enough to fry an egg on the lid.

This is the story of how 'just running it locally' turned into an engineering project with a budget, calculations, and one almost-fried laptop.

Two Commands in the Terminal

It all started with two commands in the terminal:

ollama pull qwen-coder:3.5-72b

ollama run qwen-coder:3.5-72b

The model is Qwen Coder 3.5, with 72 billion parameters, which is considered heavy class in LLM terms. The internet says: '72B is for workstations, you need a server with 128GB'. But Ollama, with aggressive quantization to Q2_K (~26GB), 'fits' the model into 32GB. So technically, it fits if you compress it to a state where it starts doubting its own intelligence.

Yes, I know what you're thinking: 'Q2_K? That's just a jumble of tokens, all logic dies'. And you're right, but the goal was to see if a 72B model would even run on a laptop, and this experiment isn't production. For real work, I'd take Qwen 2.5 7B or 14B in Q4_K_M or Q8, which offers 90% of the quality at a third of the resources. But then this article wouldn't exist.

I didn't configure anything: no limits or GPU restrictions. Just ollama run and go.

The Fan Roared

Ollama took all available RAM, all 32GB: 32 gigabytes, and it consumed ALL of it. macOS started actively using swap, and the disk began to hum like a washing machine on spin cycle, while the CPU and GPU (we have unified memory, so it's the same) were at 100% for the entire inference period. The fan roared, and everything else on the machine became unusable: the browser lagged, the IDE froze, even `ls` in the terminal responded with a delay. After a few minutes, thermal throttling kicked in, and the system started forcibly reducing frequencies to avoid overheating.

Some might say: 'macOS won't let one process take all the memory'. And they'd be right: by default, there's a limit of ~70-75% of total RAM for the GPU. But Ollama + macOS, combined with the 72B model, went into heavy swapping: the model didn't fit into the allocated 75%, and macOS started actively reading and writing to the SSD. This is a slow death for the drive: constant load on NAND cells, heating, degradation. The MacBook suffered not only from CPU/GPU load but also from the SSD working overtime.

I looked at Activity Monitor, where all the graphs were red, and thought: 'This looks more like launching a rocket than deploying an agent'. Miraculously, the laptop survived, but I realized this couldn't continue.

Trying to Save the Situation: Memory Limit

The first thing I did was set a memory limit: let the model work within its budget, and the rest goes to the system and my windows. 4096 MB, as recommended in tutorials, didn't work: 72B in Q2_K weighs ~26GB, and it simply doesn't fit into 4GB; Ollama honestly reported a loading error. I had to raise the limit to 28GB, just enough for the model to fit, and not a gigabyte more. I have 32GB, and the model is struggling within 28GB. It sounds like torture, but it was the only thing that prevented the laptop from overheating.

# In Ollama config or via environment variables

OLLAMA_NUM_PARALLEL=1

# Memory limit via macOS system settings

As a result, the model responds, but the inference speed dropped to 1-2 tokens per second (for comparison, on an RTX 4090, the same model outputs 10-15 tok/s).

What does this mean in practice? A simple request like 'write a function to parse JSON' makes you wait a minute or two while the model generates the response. Tokens arrive one or two at a time, letter by letter, as if someone is typing on a 1985 typewriter.

Moving to a PC That Now Runs on an Agent

The solution was obvious: a workstation-level PC was needed.

The specs I had available:

  • GPU: RTX 4070 Ti Super 16GB

  • RAM: 32GB DDR5

  • SSD: 2TB NVMe Gen4

  • CPU: Intel Core i5-13600KF

72B in Q2_K (~26GB) doesn't fit entirely into 16GB of VRAM; part of the weights resides in RAM, and it's noticeable. But the model runs on this hardware:

  • 5-8 tokens per second — a simple request is answered in 10-20 seconds

  • IDE, browser, terminal can be kept open — everything works

  • GPU is not at 100%, but at 60-70% during inference

Sounds ideal, right? But now, when I run the agent:

  • GPU is at 80-90% during inference

  • Playing AAA titles is impossible (GPU is busy)

  • Video editing is possible, but slow (VRAM competition)

  • The PC is now 50% AI server and 50% personal computer

It's alive and fast, but I feel a bit sorry for my personal PC: it's now working for me 24/7, and I can't even play Cyberpunk without stopping the agent first.

RAG Database: The Wallet Starts to Twitch

And this is where it gets interesting. Because a model that just generates text isn't an agent yet. An agent is a model + context. And context is RAG (Retrieval-Augmented Generation).

I wanted the agent to know my domain: code, docs, processes, tickets, chats. To do this, I started building a RAG pipeline: vector database + embeddings + retrieval. And this is where I sat down to calculate how much all this actually weighs.

When Local, and When Cloud

Since the calculation turned out this way, the question remains what to run locally and what in the cloud. There's no single answer: much depends on your hardware, how sensitive the data is, and whether the agent needs 24/7 uptime. Below are the conditions under which I would choose one option or the other.

When running locally makes sense:

  • You already have powerful hardware (workstation, gaming PC with 24GB+ VRAM)

  • You need privacy (sensitive code, internal docs, client data)

  • You are experimenting and don't need 24/7 uptime

  • The model is small (7B-14B) and the task doesn't require deep reasoning

When cloud / corporate infrastructure is better:

  • You need speed and constant availability

  • You need a full RAG pipeline at scale (millions of chunks)

  • You don't want to maintain hardware (upgrades, replacements, cooling)

  • The cost of inference in the cloud is often lower than the amortized cost of hardware

The Laptop is Fine, and the Bill Remains

The MacBook is alive and completely fine. Throttling once isn't a disease; macOS simply reduced frequencies to avoid overheating. There's no damage or lasting consequences. It lives and works as before, perhaps it just gets a bit hotter under load sometimes, but as I've learned, that's not related to LLMs.

If we consider the total cost, the price of a local AI is made up of four parts:

  • Hardware: $3000-6500 (or your personal PC, which is now a server)

  • Electricity: $100-180/year (small, but not zero)

  • Time: setup, debugging, monitoring, upgrades

  • Limitations: your personal device now runs the agent

But the experience was worth it. Now I know that 7B-14B models can be run on my own hardware, while RAG on hundreds of gigabytes and fine-tuning are better left to the cloud.

As for my patience, it ran out: I don't want to wait a minute for every response.

If you're thinking 'I'll just run it on my PC', check out the 'RAG Database' section and do the math before deciding.
