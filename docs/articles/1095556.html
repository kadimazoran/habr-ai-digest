How a Session-Based Recommendation System Works: Graph, Metadata, and LightGBM

A visitor viewed item A. The graph suggests B, similar descriptions suggest C, and similar images suggest D. How can we combine these lists into recommendations without arbitrarily adding scores of different meanings? Using a working project on Coveo, I demonstrate the entire process: historical item graph, pre-computed description and image vectors, up to 300 candidates, and ranking with LightGBM. I cover source quotas, feature imputation, and pairwise learning, including cases where the purchased item isn't among the candidates. The model is trained, quality is measured, and recommendations are available via a local HTTP API. This article details the system's architecture, compares it with simpler methods, and discusses its limitations. The code and reproduction instructions are open-source. A visitor viewed item A. Based on browsing history, B is related to it, C is similar in description, and D is similar in image. Item A itself should also be considered: the visitor viewed it, but a purchase hasn't been registered yet. How can we assemble a list of no more than 20 recommendations from these suggestions?

Using this example, I'll break down the system I built for the Coveo SIGIR eCOM 2021, Public Data Release 1.0.0. From a historical catalog of 14,314 SKUs, it selects up to 300 candidates, calculates features for them, and passes them to LightGBM. The model ranks the items, and a local HTTP API returns up to 20 recommendations. The model is trained, and I'll present the evaluation results at the end.

Code: RecSys-Coveo.

In the previous article, I discussed the goals and limitations of purchase records. Here, I'll cover item selection, feature calculation, and training the ranker—the model that determines the output order.

First, let's recall the time rules. A session is a set of events with a common identifier in Coveo, and an SKU is an item identifier. Events with the same timestamp are considered a single block: their internal order is unknown. Recommendations are generated once, after the first block containing a viewed item with a valid SKU, provided no purchase has been registered in the session by the end of that block.

The model only sees events available at the time of recommendation generation. The goal is to identify various SKUs of registered purchases occurring after the recommendation in the same session. The observation window ends 24 hours later or at the last published record, whichever comes first.

What the Graph Knows About an Item

Before processing requests, I build the catalog, graph, and item statistics from 50,000 sessions in the A_G period. The presence of a purchase does not affect session selection. The next 50,000 sessions, from period B, are used for training the ranker. This separation prevents future purchases from period B from becoming graph edges and influencing the recommendations for the same session.

The graph nodes are items. There are three types of directed edges between them:

  • view → view;

  • view → add to cart;

  • view → purchase.

If a visitor purchased B after viewing A, the session contributes to a type 3 edge. A reverse edge B → A does not arise from this. The edge also doesn't indicate whether items are substitutes or complements; it reflects the sequence of actions.

After viewing item A, I look for subsequent views, add-to-cart actions, and purchases of other items within the same historical session. In the current configuration, I consider only the next ten blocks of item events and only actions that occurred no later than 30 minutes after viewing A. I do not build edges between events within the same block: their order is unknown. The longer the interval between events, the lower the pair's weight—it decays exponentially.

If multiple A → B pairs of the same type occur in a session, I take the maximum weight. Then, I sum the contributions from different sessions. One session contributes at most one unit to an edge, so repeated views of the same item pages don't create a strong link on their own.

In the current configuration, an edge must appear in at least three sessions. For each item and edge type, I store up to 100 neighbors with the highest weights.
