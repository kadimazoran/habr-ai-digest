Docker for the Paranoid: Organizing SSH Access for a Rootless Container Without Transferring the Private Key

SSH access is used in many scenarios, from working with repositories to automation and server management. But if the private key is available to the application itself, it can be stolen if the process is compromised. Replacing SSH with a token doesn't solve the problem: it will just be another secret accessible to the same process. In this article, we'll explore an architecture based on ssh-agent and rootless Docker, where a process can fully utilize granted SSH access without obtaining the private key itself. This restriction is enforced by the access scheme itself and remains even if the software inside the container is compromised. Foreword

SSH access is used everywhere: for working with repositories, servers, automation, and many other tasks. But how often do we think about the fact that the private key available to the application can be stolen?

You can replace SSH with another authentication method, such as a token. But if this token is available to the process itself, the problem remains the same: if it's compromised, it can also be read and taken away. We'll just replace one secret with another. Therefore, the task here is not to choose SSH, a token, or another mechanism, but to ensure that the secret itself is not available to the process at all.

Even if we trust our own software, vulnerabilities can appear in it and its dependencies. If the process is compromised, the secrets available to it are also at risk.

This problem is particularly acute in systems with AI agents. An additional API layer, such as an MCP server, is often used between the agent and the infrastructure, but it can also contain vulnerabilities.

In this article, we will examine an architecture in which a process can fully utilize SSH access, but the ability to obtain the private key itself is excluded at the architectural level.

The main idea.

  • The process can use its granted SSH rights to access authorized resources.

  • At the same time, the process does not get access to the private SSH key used for authentication.

  • Even if the process inside the container is compromised, the private SSH key should not become accessible to it.

Additionally, the container is run in rootless mode. In such a configuration, the scheme becomes more complex, so we will separately discuss the problems that arise during setup and ways to solve them.

How the article is structured.

The material is structured sequentially.

  • First, we'll discuss why a container might need SSH.

  • Then, we'll look at UID/GID mapping in rootless Docker and explain why standard mounting of SSH_AUTH_SOCK doesn't work for a process with a non-root UID.

  • After that, we'll consider minimal configuration examples for ssh-agent and the target container.

  • Finally, we'll test the scheme's operation, discuss bind mount specifics, and the protection boundaries.

A detailed description of how users are organized in Unix-like systems, how processes work, Unix sockets, and Docker isolation is beyond the scope of this article.

These topics are discussed here only to the extent necessary to understand and implement the described scheme. Brief explanations of key terms and mechanisms will be provided throughout the article.

Setting up rootless Docker and additional security measures.

It is assumed that rootless Docker and the user it runs as are already configured.

The article does not cover additional security measures such as limiting outgoing network traffic (egress), configuring firewalls, proxies, or network policies, nor isolation through virtual machines and microVMs. These measures can complement the described scheme but address separate tasks.

Introduction

A container may require full SSH access: to clone a private Git repository, perform git fetch, connect to a server, or run another program that uses OpenSSH.

A simple option is to place the private key inside the container or mount ~/.ssh:

docker run 
    -v ~/.ssh:/home/app/.ssh:ro 
    image-name

This option works but violates credential isolation:

The process inside the container gains direct access to the private key. Read-only mounting protects the file from modification but not from reading: the application can read the key and transfer it outside the container.

This article discusses a configuration with the following requirements and restrictions:

  • The Docker daemon must run in rootless mode, without root privileges on the host;

  • the process inside the container does not run as root;

  • Linux capabilities are removed from the container;

  • gaining new privileges is prohibited;

  • the root filesystem of the container is read-only;

  • the private key is not present in the container's mount namespace;

  • when using SSH, we prohibit StrictHostKeyChecking=no;

  • the private key must not be transferred to the container in a readable form:

    • simple transfer of the private key from a secrets store is not suitable: the key material still becomes accessible to the container process;

    • environment variables are not suitable for transferring the private key: the value becomes part of the process environment and is accessible to that process;

    • mounting the private key from the host makes it readable by the container process.

The scheme:

Instead of the key, a Unix socket for ssh-agent is passed to the container. SSH operations are then performed via the SSH agent without direct access to the private key material.

OpenSSH uses the SSH_AUTH_SOCK variable to work with the socket.

SSH_AUTH_SOCK is the standard OpenSSH mechanism for client access to ssh-agent. However, when working with containers in rootless Docker mode, technical difficulties arise, let's examine them.

The main technical problem with this scheme is related to UIDs:

The UID of the process inside a rootless container does not match its UID on the host.

But first, let's determine why a container needs SSH and consider an alternative solution.

Why SSH is Needed in a Container

Typical Scenarios

Typical cases where a container might need SSH access:

  • working with private Git repositories over SSH;

  • executing commands on remote servers;

  • transferring files via scp or rsync;

  • automated server deployment and maintenance;

  • accessing dependencies and Git submodules via SSH;

  • running tools that use OpenSSH and SSH_AUTH_SOCK as their standard authentication mechanism.

Alternative Solution

An alternative architecture is to not provide SSH access to the container at all, but to move Git or other external system operations to a separate API service.

For example, for AI Agents, the intermediate layer could be an MCP server.

However, such a service is not always a complete replacement for local git.

If the application works with its own working copy, for example, /container/workspace, then when transferring file and Git operations to an external service, two independent file systems arise:

The state of files needs to be synchronized separately. One option is to provide both components with a common working copy via a volume.

However, this solution introduces an additional trust boundary.

In this implementation, the process inside the container does not see the authorization secrets but can modify the shared working copy. Let's consider one of the risks of this architecture.

If the container and the MCP service use the same writable working copy, the process inside the container can modify its contents. If the MCP service runs Git hooks from this copy, the modified hook can execute in the service's environment with its access rights, including its available secrets.

This scenario is only applicable when the service uses a shared working copy, runs Git hooks, and does not isolate their execution. If hooks are disabled or executed in an isolated environment without secrets, this scenario is not realized.

When using a third-party MCP service, its implementation and access model become an additional trust boundary that needs to be assessed separately.

In the scenario under consideration, the container needs local OpenSSH with access to its own working copy.

Next, we return to the scheme with a separate ssh-agent and discuss its main technical problem—UID mapping.

How Rootless Docker Changes UIDs

Before we start configuring ssh-agent, let's briefly delve into the theory.

Theory: User Namespaces and UID/GID Mapping

In Linux, the User ID (UID) is a number that the kernel uses to check access rights. In a configuration without user namespaces, the UID of a process inside a container numerically matches its UID on the host. Rootless Docker uses user namespaces, so the same process has different UIDs inside the container and on the host.

For example, a process with UID 1000 inside the container might be represented on the host as UID 100999. This is not a new user in the host's /etc/passwd, but a result of namespace translation.

It's important to distinguish between:

  • UID inside the container—the process identifier in the container environment;

  • UID on the host—the identifier of the same process as seen by the host;

  • /etc/subuid and /etc/subgid—the ranges of identifiers that Docker can use for such translation.

For ssh-agent, the UID on the host side is crucial because the Unix socket client verification is performed by the kernel and the ssh-agent process in the host environment.

In a standard Docker daemon configuration, it runs with root privileges.

In rootless mode, Docker runs the daemon and containers within user namespaces under an unprivileged host user. Docker recommends this mode as one way to reduce the impact of daemon or runtime compromises.

User namespaces change the UID mapping between the container and the host.

  • In the examples, rootless Docker will run under the rootless-docker user.

  • And containers will run as the app user.

Here's how UIDs/GIDs might look for the user on the host and in the container:

host  UID 999 (rootless-docker) → container UID 0 (root) 
host  GID 999 → container GID 0 (root)

Here's how UIDs/GIDs might look for the app user on the host and in the container:

container UID 1000 (app) → host UID 100999 (UNDEFINED) 
container GID 1000 (app) → host GID 100999 (UNDEFINED)

This is how you can view the current mapping inside the container:

cat /proc/self/uid_map

Suppose we have many users. Here are the UIDs they would receive:

container UID 0     → host UID 999 
container UID 1     → host UID 100000 
container UID 2     → host UID 100001 
... 
container UID 1000  → host UID 100999

A formula for UIDs N >= 1 is apparent:

host UID = subuid_start + N - 1

Docker uses this scheme in rootless mode: UID 0 in the container maps to the user who started rootless Docker, and other UIDs are taken from the subordinate UID range. The same mechanism applies to GIDs.

The ranges are defined by the files /etc/subuid and /etc/subgid for users and groups, respectively.

Example of the /etc/subuid file:

rootless-docker:100000:65536 
john:165536:65536 
ci-runner:231072:65536

More details: https://docs.docker.com/engine/security/rootless/uid-gid-mapping/.

How to Calculate the Host UID Given its Container UID

To correctly configure the ssh-agent socket, you need to determine in advance which container user it should correspond to and calculate the corresponding UIDs/GIDs on the host.

ROOTLESS_USER=rootless-docker 
ROOTLESS_UID=$(id -u "$ROOTLESS_USER") 

# Get UID/GID from the container via the rootless Docker daemon for the desired user 
CONTAINER_UID=$(sudo -H -u "$ROOTLESS_USER" env DOCKER_HOST="unix:///run/user/$ROOTLESS_UID/docker.sock" docker run --rm image-name id -u app) 
CONTAINER_GID=$(sudo -H -u "$ROOTLESS_USER" env DOCKER_HOST="unix:///run/user/$ROOTLESS_UID/docker.sock" docker run --rm image-name id -g app) 

# Get the first UID/GID from the range settings for the desired user 
# Example: will take `100000` from the line `rootless-docker:100000:65536` 
SUBUID_START=$(awk -F: -v user="$ROOTLESS_USER" '$1 == user { print $2; exit }' /etc/subuid) 
SUBGID_START=$(awk -F: -v user="$ROOTLESS_USER" '$1 == user { print $2; exit }' /etc/subgid) 

echo "host UID: $((SUBUID_START + CONTAINER_UID - 1))" 
echo "host GID: $((SUBGID_START + CONTAINER_GID - 1))"

With SUBUID_START=100000 and SUBGID_START=100000, the result will be:

UID: 1000 -> 100999 
GID: 1000 -> 100999

Subsequently, 100999 will be used as the UID and GID for the ssh-agent process on the host.

In an automation system, these UIDs/GIDs should be calculated automatically. When changing the existing ranges in /etc/subuid and/or /etc/subgid, you should only do so considering existing files and running containers.

If you change the UID/GID of a user inside the container or the ranges in /etc/subuid and/or /etc/subgid, the numerical UIDs/GIDs of files already created on the host will not change, but their mapping to the owner inside the container will change. As a result, the container may no longer perceive these files as belonging to the expected user.

Now we know how the container process is represented on the host by its UID. This helps understand why the socket of the regular ssh-agent for the rootless-docker user cannot simply be mounted into the container.

Why Direct Mounting of SSH_AUTH_SOCK Doesn't Work for Non-Root UIDs

A common example of passing ssh-agent to Docker looks like this:

docker run 
    -e SSH_AUTH_SOCK=/ssh-agent 
    -v "$SSH_AUTH_SOCK:/ssh-agent" 
    image-name

In configurations without user namespaces, this is often sufficient.

The SSH client inside the rootless container runs as UID 1000, which is represented as UID 100999 on the host.

Suppose the ssh-agent on the host is run by the rootless-docker user with UID = 999, then:

From the host's perspective, these are different users. As a result, ssh-agent will reject the connection due to mismatched UIDs.

Furthermore, it's not enough to grant file access to the socket for all users, for example:

# Insecure diagnostic example: do not use this mode in a production configuration 
chmod 0666 agent.sock

After this, the connect() system call to the Unix socket might succeed, but ssh-add -l might still fail. ssh-agent checks the UID of the connecting process on the host side. If the UID does not match the UID of the ssh-agent process, and the client does not have EUID 0, the agent will reject the connection.

Therefore, instead of expanding socket permissions, it's necessary to align the UIDs of the client and ssh-agent:

To align UIDs, we will run a separate ssh-agent with the mapped UID of the container user and provide the container with only the directory containing its socket.

Setting Up the SSH Agent on the Host

Running ssh-agent with a Specific UID

systemd can run a process with a numerical UID 100999 without an entry for it in /etc/passwd. However, when using User=100999, all commands in the unit file, including ExecStartPost, will also be executed with this UID.

Therefore, the unit remains a root service, and only the ssh-agent itself is run with the mapped UID using setpriv. This allows ExecStartPost to read the private key belonging to root.

setpriv 
    --reuid=100999 
    --regid=100999 
    --clear-groups --inh-caps=-all --no-new-privs 
    /usr/bin/ssh-agent ...

setpriv runs a process with the specified UID/GID without creating a separate user or user session.

We use --clear-groups, --inh-caps=-all, and --no-new-privs to remove additional groups and avoid passing unnecessary privileges to the process.

For example, if the user running the process is in the docker group, the process could formally access /var/run/docker.sock if the socket permissions allow it. ssh-agent doesn't do this by default, but in case of a vulnerability or process substitution, such permissions become important.

Defining Variables

Let's define the variables that will be used in the configuration and for clarity in subsequent examples:

BASE=/opt/ssh-access 
IDENTITY=git 

# Main user for working with rootless Docker 
ROOTLESS_USER=rootless-docker 
ROOTLESS_UID=$(id -u "$ROOTLESS_USER") 
ROOTLESS_GID=$(id -g "$ROOTLESS_USER") 

# User under which the process runs inside the container 
CONTAINER_UID=1000 
CONTAINER_GID=1000 

# Calculation see above 
MAPPED_UID=100999 
MAPPED_GID=100999

File and Directory Structure

For the example, we will use the following structure on the host:

/opt/ssh-access/ 
├── .ssh/ 
│   └── git/ 
│       ├── key 
│       └── key.pub 
├── sockets/ 
│   └── git/ 
│       └── agent.sock 
└── ssh_known_hosts

The .ssh directory is not mounted into the container.

The container only gets access to sockets/git/ and the SSH server known hosts file ssh_known_hosts.

Why is ssh_known_hosts needed?

When connecting for the first time, SSH usually requires manual confirmation of the server's key. This is unacceptable for CI/CD and other automation.

Often, checking is disabled via StrictHostKeyChecking=no, but then the client stops verifying the server's authenticity.

Therefore, the server's key is pre-saved in ssh_known_hosts, and verification remains enabled.

Create the root directory for ssh-agent:

sudo install -d 
    -o "$ROOTLESS_USER" 
    -g "$ROOTLESS_GID" 
    -m 0711 
    "$BASE"

Permissions 0711 allow a process with the mapped UID to traverse the directory path but not list its contents.

The owner of the socket directories and the sockets themselves will be the mapped UID under which ssh-agent runs.

The rootless user's group allows Docker to use these directories as a source for bind mounts.

Create the directory for sockets (identities):

sudo install -d 
    -o "$MAPPED_UID" 
    -g "$ROOTLESS_GID" 
    -m 0710 
    "$BASE/sockets"

This directory will contain separate directories for SSH identities.

The scheme allows using multiple independent ssh-agent instances and sockets. In our configuration, each socket corresponds to a separate SSH identity.

For example, you can create identities like git, gitlab, or separate git-read and git-write with corresponding SSH keys having different access levels.

Each container can be granted access only to the directory of the required identity. Thus, the container receives only the SSH access it is permitted.

Then, create the directory for a specific identity (example for git):

sudo install -d 
    -o "$MAPPED_UID" 
    -g "$ROOTLESS_GID" 
    -m 0710 
    "$BASE/sockets/git"

A separate directory is created for each SSH identity because the container will be mounted with the directory itself, not the agent.sock file. This allows ssh-agent to recreate the socket within the already mounted directory.

Creating an SSH Key

The directory with the key must be accessible only to the root user:

sudo install -d 
    -o root 
    -g root 
    -m 0700 
    "$BASE/.ssh/git"

Let's create an Ed25519 key:

sudo 
    ssh-keygen 
    -t ed25519 
    -f "$BASE/.ssh/git/key" 
    -C 'container-git' 
    -N ''

A key pair will be created:

.ssh/git/key 
.ssh/git/key.pub

Add key.pub to the services you need to grant access to via this SSH key.

Systemd Service for Running ssh-agent

To separate SSH identities, you can create multiple sockets with separate ssh-agent instances.

In this template, %i will be replaced by a specific name, e.g., git. Specific examples of service startup will follow.

# /etc/systemd/system/container-ssh-agent@.service 

[Unit] 
Description = SSH agent for container identity %i 

[Service] 
Type = simple 

Environment = SSH_AUTH_SOCK=/opt/ssh-access/sockets/%i/agent.sock MAPPED_UID=100999 MAPPED_GID=100999 

# Remove old socket that might remain after an abnormal shutdown 
ExecStartPre = /usr/bin/rm -f -- /opt/ssh-access/sockets/%i/agent.sock 

# Instead of `100999`, specify the calculated `MAPPED_UID` and `MAPPED_GID` values 
ExecStart = /usr/bin/setpriv 
            --reuid=${MAPPED_UID} 
            --regid=${MAPPED_GID} 
            --clear-groups --inh-caps=-all --no-new-privs 
            /usr/bin/ssh-agent 
            -D 
            -a /opt/ssh-access/sockets/%i/agent.sock 

# Wait for the `ssh-agent` socket to be created 
# After the service starts, add the desired key using `ssh-add` 
ExecStartPost = /bin/sh -c 'while [ ! -S "$SSH_AUTH_SOCK" ]; do sleep 0.05; done; exec /usr/bin/ssh-add /opt/ssh-access/.ssh/%i/key' 

Restart = on-failure 

[Install] 
# Start this service automatically on normal system boot. 
WantedBy = multi-user.target

Sequence:

This command is executed on the host. The private key file is not mounted into the container and is not accessible to its processes.

Starting the Service

Let's reload the systemd configuration and start the service:

sudo systemctl daemon-reload 

# Start the service named `git`: the value `git` will be substituted into `%i` of the template 
sudo systemctl enable --now container-ssh-agent@git.service 

# check for successful startup 
systemctl status container-ssh-agent@git.service --no-pager -l 

# Check the created socket and its permissions: should be 100999:100999, i.e., `$MAPPED_UID:$MAPPED_GID` 
ls -ln /opt/ssh-access/sockets/git/agent.sock 

# Check all running `ssh-agent` services and their UIDs/GIDs 
ps -o pid,uid,gid,cmd -C ssh-agent

ssh-agent is configured and running. Now let's prepare ssh_known_hosts so the container can verify the authenticity of the remote SSH server.

Verifying the Remote SSH Server's Key

You should not disable the remote server key verification via StrictHostKeyChecking=no.

With this setting, the SSH client stops verifying if it's actually connecting to the expected server.

The scheme under consideration uses a separate file /opt/ssh-access/ssh_known_hosts, which is pre-populated with the verified server key.

First, create the file: sudo install -o root -g root -m 0644 /dev/null /opt/ssh-access/ssh_known_hosts. Then add the server keys:

  • get the server's public host key: ssh-keyscan -p 22 -t ed25519 git.example.com

  • verify its fingerprint against the key on the server itself or an officially published fingerprint

  • add the obtained line to the end of the /opt/ssh-access/ssh_known_hosts file

The example requests an Ed25519 host key. If the server uses a key with a different algorithm, specify it explicitly.

How to ensure the key is genuine?

  • if the server is yours, compare the result with its public host key directly on the server

  • a repeated ssh-keyscan from another computer can only be an additional, but not the primary, check

After verification, the file can be mounted into the container read-only.

Running and Verifying the Container

Running the Container with Limited Privileges

If you are creating the Dockerfile yourself, you need to create a non-root user for this scheme.

Example Dockerfile specifying USER 1000:1000:

FROM debian:bookworm-slim 

RUN apt-get update 
    && apt-get install -y --no-install-recommends 
        ca-certificates 
        git 
        openssh-client 
        util-linux 
    && rm -rf /var/lib/apt/lists/* 

# Common UID/GID for an unprivileged user: `1000:1000` 
RUN groupadd -g 1000 app 
    && useradd -m -u 1000 -g 1000 app && install -d -o app -g app /workspace

Build the demonstration image ssh-client:test:

sudo -H -u "$ROOTLESS_USER" env DOCKER_HOST="unix:///run/user/$ROOTLESS_UID/docker.sock" docker build -t ssh-client:test .

If you are already using a pre-built image, find out its default UID/GID:

# Use the obtained UIDs/GIDs instead of 1000:1000 in subsequent examples. 
sudo -H -u "$ROOTLESS_USER" env DOCKER_HOST="unix:///run/user/$ROOTLESS_UID/docker.sock" docker run --rm image-name id

Example of running a container from the ssh-client:test image:

sudo -H -u "$ROOTLESS_USER" env DOCKER_HOST="unix:///run/user/$ROOTLESS_UID/docker.sock" docker run --rm -it 
    --user 1000:1000 
    --read-only 
    --cap-drop ALL 
    --security-opt no-new-privileges 
    --tmpfs /tmp:rw,nosuid,nodev,noexec,size=64m 
    --tmpfs /workspace:rw,uid=1000,gid=1000 
    --workdir /workspace 
    -e SSH_AUTH_SOCK=/ssh-agent/agent.sock 
    -v /opt/ssh-access/sockets/git:/ssh-agent:ro 
    -v /opt/ssh-access/ssh_known_hosts:/etc/ssh/ssh_known_hosts:ro 
    ssh-client:test 
    sh

Note the --user, -e SSH_AUTH_SOCK, and two bind mounts: this is how the container gets access to ssh-agent and verified SSH host keys.

Operation and Limitations

Potential Issue with Bind Mounting

When working with the socket directory, you need to consider the behavior of bind mounts.

Imagine the container is already running with the mount:

/opt/ssh-access/sockets/git 
        ↓ 
/ssh-agent

Then the directory on the host is deleted and recreated:

rm -rf /opt/ssh-access/sockets/git 
mkdir /opt/ssh-access/sockets/git

The path has the same name, but the new directory is a different filesystem object.

The existing bind mount continues to refer to the old object.

You can check the mount source inside the container:

findmnt -T /ssh-agent -o TARGET,SOURCE,FSTYPE,OPTIONS -n

In this situation, the source might appear as:

/opt/ssh-access/sockets/git//deleted

Creating a new directory with the same path does not change the existing bind mount.

If you encounter this problem, the container must be restarted or recreated.

Therefore, you should not delete and recreate the directory itself used as the bind mount source. Files within it can be deleted and recreated.

How ssh-agent Restart Works in Our Scheme

Deleting the directory itself and restarting ssh-agent are different operations.

In the scheme we chose, the container mounts the directory, not the agent.sock file itself. Therefore, the new socket immediately becomes available inside the container.

With this scheme, restarting or recreating agent.sock within an existing directory does not require recreating the container.

systemctl restart container-ssh-agent@git.service

When restarting, the directory remains in place, and the socket within it is created anew:

Protection Boundary of This Scheme

ssh-agent does not prevent the container from using the loaded SSH identity. It does not transfer the private key material to the client.

The private key file remains on the host; after loading, the key is also stored in the memory of ssh-agent:

Within this scheme, the process inside the container does not receive the private key file and cannot read it via bind mount:

cat ~/.ssh/id_ed25519

However, the container can use the loaded SSH identity via ssh-agent, including signing operations.

If the container is compromised during operation, an attacker can use the loaded identity through the agent as long as they have access to the socket.

Therefore, access to SSH_AUTH_SOCK should be considered delegated access to the loaded SSH identity.

Another process that gains access to the agent's socket can use the keys loaded into it, so you need to be careful about separating services between users.

Final Architecture

The complete SSH authentication chain:

The container can simultaneously use the following restrictions:

  • Docker daemon runs in rootless mode;

  • the process runs without root privileges;

  • the root filesystem is read-only;

  • Linux capabilities are dropped;

  • no-new-privileges is enabled;

  • the private SSH key is not present in the container;

  • from SSH credentials, the container only gets access to the socket of the required ssh-agent.

The key technical element of this scheme is the matching of the ssh-agent process UID on the host with the UID to which the container user is mapped through the rootless user namespace.
