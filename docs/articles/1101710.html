OpenWebUI Pipes: Why Write Code When Settings Have Everything?

Configuring a custom model with tools and RAG in OpenWebUI is easy. Making it work predictably in production is harder. Our support bot on Gemma 4 initially responded plausibly but lacked system data. We figured out why and turned a "single model in the interface" into a deterministic pipeline using pipes. Read on

Author: Alexander Kazantsev, Head of Documentation and Content Department

OpenWebUI can utilize many things: custom models, knowledge bases (RAG), tools (MCP/tools), skills, etc. With each version, the environment offers more capabilities, and it seems that for a support AI bot, it's enough to create a custom model based on something open-source like Qwen-3.8 or Gemma 4, attach the necessary tools in the settings, fill in and connect the knowledge base – and you're done!

Honestly: we at HOSTKEY started exactly like that. And then we wrote several pipes for each support channel served by its own bot, because relying on settings, to put it mildly, yielded unpredictable results.

In this article, we won't explain "how to enable tools" – that's all in the OpenWebUI documentation – but rather "why enabling them is not enough" and how pipes for bots are currently structured, using the Remote Hands Request support as an example.

What Happens When You Rely on Model Settings

For example, let's take the custom model hostkeyrurhr, based on gemma4:26b-a4b-it-qat. Its settings (as seen in the OpenWebUI screenshot) include the following parameters:

  • Function Calling — Legacy;

  • Temperature — 0.2, think (Ollama) — Off, draft_num_predict — 1;

  • Knowledge — hostkey_ru collection, based on our client documentation;

  • Tools — status_ru_mcp, docs_url_ru (checking the status of websites, Invapi, and data centers in Russia, and MCP tool for requesting configurations of VPS and dedicated servers, and network traffic).

Let's ask a question for which the model has a suitable tool. The get_vps_list tool from the external MCP returns a list of VPS with prices by location, so let's ask about a cheap VPS in Germany.

The current list of servers and prices can be requested via API in Invapi, and our MCP server does exactly that, but the model doesn't access it. The response is built solely on RAG: it looks plausible, but it's not data from the system, but a retelling of instructions from the documentation. If you switch to Native mode, it gets even worse, and RAG also "drops out".

When requesting via API (e.g., via CURL), the situation is even more amusing: we get a bare tool_call with empty content. The client is obliged to call it and re-ask the model (which OpenWebUI effectively does). At the same time, there's no guarantee that the tool will be called, that the data will be included in the response, that it won't be mixed with RAG, and that the response will definitely be in Russian.

But before we dive into pipes, it's worth explaining why the model settings use Legacy and why you can't just switch to Native.

Legacy (Default). OpenWebUI doesn't rely on the model itself "knowing" how to call the right tools. Data from all connected tools are added to the general request context (usually mixed into the system prompt), and the model should then generate a response in the expected format based on this data, which is then parsed. This method works with any supported model, but its reliability is variable: the model might overcomplicate the call, generate invalid JSON, or simply ignore the tool.

Native (Agentic). Only the list of tools is passed to the model via a special API parameter, not as text in the prompt. A model trained on the tool calling format recognizes the parameter and generates a call in a structured form. OpenWebUI receives the ready response from the tool and doesn't have to guess what the model intended.

While Qwen3 family neural network models work well in both modes, Gemma 4 Native mode, even for the it (Instruction-Tuned) version, requires a specialized approach. This is precisely the work that the pipe handles (and not only this).

Why Gemma and not Qwen? It's about speed. With the thinking mode disabled, Gemma 4 provides a comparable (honestly, slightly worse) response in 5–7 seconds on a pair of 16 GB A4000s, while Qwen 3 "thinks" for 30–40 seconds.

Pipe (function) and Valves

A Pipe (also known as a function) is an OpenWebUI plugin that intercepts the request before it's sent to the model. Technically, it's a Python class with a pipe method that receives the request body and returns a string, JSON, or stream; inside, the pipe is free to call the LLM, MCP tools, edit the prompt, and enable/disable RAG as many times as needed.

It transforms "a single model in the interface" into a deterministic pipeline: the pipe is displayed in OpenWebUI as a separate model, meaning it can be assigned permissions, have its own settings, and be called "externally" via API. External clients only need to replace the custom model with the pipe model in their calls.

Valves are a configurable part of the pipe that controls how data "flows" through it. It's a nested class within Pipe, inheriting from BaseModel (plus a separate UserValves for user settings): it holds configurable parameters (keys, URLs, thresholds) that are saved in the database, displayed in the admin panel, and re-read on each request. These are essentially "handles" that configure the pipe's behavior without code edits, through the menu.

Valves have their limitations, and some things are not worth exposing in them, so we don't use them in our pipes at all – it's easier for us to rewrite prompts and parameter values in the pipe's code.

Pipes themselves are created in the Admin Panel - Function section.

Why Model Settings Are Not Enough

Besides non-functional tool calls, here's what else we found unsatisfactory with OpenWebUI's standard mechanisms:

  • The decision-making is done by the same model that provides the answer. There's no role separation into "fast router" and "responder model with RAG," etc. Everything goes through one model with the same settings, system prompt, temperature, and so on.

  • There's no control over the phase order. Standard tool calling doesn't guarantee the correct order of tool execution. For instance, we needed to get a keyword search first, then server availability and MCP Invapi tools, and only then the RAG response.

  • RAG cannot be disabled for specific steps, for example, during tool calls, to prevent data mixing.

  • There's no post-processing – language checks, trimming of trailing service information, discarding "placeholders," fallback. You can try to do this at the system prompt level, but it doesn't work very well.

  • Mandatory manual parsing of tool_calls when calling via API, as the model returns a bare call, not a ready response.

  • The user doesn't see what's happening inside the pipeline when multiple LLM requests and MCP calls appear as a "frozen" interface.

Anatomy of a Pipe

Let's break down the pipe using the hostkeyru_rhr_pipe example. It serves HOSTKEY's Russian-language support: answers questions about VPS, documentation, and common issues, while MCP tools pull up-to-date data from the systems. The final generation is then done by the custom model hostkeyrurhr, meaning the pipe intercepts the request, performs all preparatory work, and at the last step, sends an enriched prompt to the model with RAG enabled.

The pipe receives several arguments from OpenWebUI. Key ones include: body (messages, model, flags, tool_ids, features), tools (a dictionary of available MCP tools with callable functions), and __event_emitter__ (a status channel in the UI):

async def pipe( 
    self, 
    body: dict, 
    user: Optional[dict] = None, 
    tools: Optional[dict] = None, 
    metadata: Optional[dict] = None, 
    __event_emitter__=None, 
) -> Union[str, Generator, Iterator, Dict[str, Any]]: 
    messages = list(body.get("messages", [])) 
    if not messages: 
        return "Ошибка: пустой запрос." 
    user_wanted_stream = body.get("stream", False)

Next, the text is extracted from the user's last message – carefully, because the message can be multimodal (just text or a list of "text + image" blocks):

for i, msg in enumerate(reversed(messages)): 
    if msg.get("role") == "user": 
        user_msg_index = len(messages) - 1 - i 
        original_content = msg.get("content", "") 
        if isinstance(original_content, str): 
            user_query_text = original_content 
        elif isinstance(original_content, list): 
            text_parts = [item.get("text", "") for item in original_content if item.get("type") == "text"] 
            user_query_text = " ".join(text_parts).strip() 
        break

At this stage, only code is executed without involving neural networks.

A special mention for __event_emitter__. This is an argument that OpenWebUI passes to the pipe. It's implemented as an async function through which events can be sent to the chat: intermediate statuses, notifications, message updates.

The user sees them directly in the interface, where instead of an uninformative "frozen" progress bar, a changing stream of events appears: "Analyzing request > Extracting keywords > Searching documentation > Checking need for tool calls > Using tool > Forming final response.".

Technically, this is a wrapper around sending a status event:

async def emit_status(description: str, done: bool = False): 
    if __event_emitter__: 
        await __event_emitter__( 
            { 
                "type": "status", 
                "data": {"description": description, "done": done} 
            } 
        )

Displaying the operational status is critical for pipes that involve multiple sequential LLM requests and MCP calls. Without statuses, the user doesn't understand what's happening and often leaves the chat before receiving a result.

Phase -1. RHR Responsibility Zone Check: A Cascade of Three Echelons

The initial pipe lacked a check for "Is this an RHR request?" altogether. Consequently, requests like "issue me an invoice" and "SSH is not working" received the same response. This increased the workload on the department serving the servers, so we decided to ease their burden at the bot's response stage.

To achieve this, the new hostkeyru_rhr_pipe pipe introduced Phase -1, which is not a single LLM request but a cascade where each subsequent echelon is activated only if the previous one didn't provide a definitive answer.

Echelon 1 — Keyword Guard (_keyword_prefilter)

Written in pure Python, without LLM. The code searches the text for two sets of markers: RHR_KEYWORDS (ssh, reboot, raid, network, dns, not responding...) and CLIENT_SOFTWARE_SIGNALS (website code, nginx config, wordpress, laravel...). If only RHR keys are present, we set the parameter values to in_scope=True, edge, 0.9. If only software signals are present, then in_scope=False, client_software, 0.9. If both or neither are present, we return None and proceed.

This handles typical inquiries without a single model request.

Echelon 2 — LLM Classifier (_classify_rhr_scope + RHR_SCOPE_SYSTEM_PROMPT)

Here, we make a request to the gemma4nothink model with a temperature of zero. The prompt for the request embeds the full RHR_REGULATION, five critical rules ("grammatical form doesn't change the zone," "KEYWORD GUARD," "client_software requires explicit signals," "borderline cases = edge," "confidence calibration"), eight few-shot examples, and a strict JSON response format. The latter is parsed and converted into a digestible format for the third echelon. In case of any failure, we set the response: in_scope=True, unknown, 0.0.

Echelon 3 — Recheck (_recheck_rhr_scope + RHR_RECHECK_SYSTEM_PROMPT)

This is a safeguard against false negatives: a client with a real access problem won't be directed to billing. Recheck is triggered only if the first pass returned in_scope=False, the category client_software or unknown, and the confidence falls within the range [0.7, 0.85]. For categories like billing, client_area, legal, sales, abuse (where confidence is high) and for edge (where in_scope=True), recheck is not triggered.

The user sees changing statuses: "Checking Remote Hands responsibility zone...", "Borderline case – rechecking zone..." (only during recheck), "Request outside RHR zone, adding warning" / "Request within RHR zone, proceeding.".

Phase 0. Preliminary Documentation Search

The first short request is made simply to the gemma4nothink model (a base model, but with thinking disabled). Here, we need to transform the user's question into 2–3 keywords for searching.

The prompt (which we set specifically in the pipe, as it's a general model) strictly limits the query length, because long phrases yield poor search results:

router_messages = [{ 
    "role": "system", 
    "content": ( 
        "Перефразируй сообщение пользователя в поисковый запрос из 2-3 слов для поиска по документации HOSTKEY. " 
        "Выведи ТОЛЬКО ключевые слова через пробел. Ничего больше. " 
        "Хорошо: 'ssh подключение', 'gpu nvidia', 'ip адрес', 'смена ip адреса', 'резервные копии'. " 
        "Плохо: 'смена ip адреса или дополнительный ip' (слишком много слов). " 
        "Строгое ограничение: 2-3 слова." 
    ) 
}, {"role": "user", "content": user_text}]

Result: the model forms the desired query, which is sent to the MCP documentation search tool. In effect, we open the client documentation on behalf of the user, enter our query into the search bar, and retrieve the first results. The tool call goes directly (the entire MCP toolset "runs" locally on the same server as Ollama and OpenWebUI). The code has two paths: first, the tool is searched for in tools (where OpenWebUI sees it), and if it's not there, there's an HTTP fallback to the local MCP server:

MCP_BASE_URL = "http://host.docker.internal:8000" 
tool_path = "/docs_url_ru" 
tool_name = "search_hostkey_docs_ru" 
url = f"{MCP_BASE_URL}{tool_path}/{tool_name}" 
response = await self.client.post(url, json={"query": query, "limit": 5})

If the result is too short (less than the docs_retry_threshold value, which defaults to 400 characters), the pipe makes a repeat request with the raw user text to avoid losing relevant links.

The found links are saved in docs_result until the main model is called, which helps to get a more relevant answer and, importantly, relevant links to specific documentation sections, as we don't have them explicitly in our knowledge base.

In the status display, the user sees three events: "Extracting keywords for search..." before the LLM request, "Searching documentation: {query}" before the MCP call, and "Documentation found" after success. In case of an error – "Failed to retrieve documentation, proceeding..."

Phase 1. MCP Router

The second request is also made to gemma4nothink, but now as a "tool router." The model preliminarily decides whether a particular MCP tool is needed and calls it if necessary.

Here, we use a minimalist system prompt:

tool_checking_messages = [ 
    {"role": "system", "content": ( 
        "Ты — системный маршрутизатор. Твоя единственная цель — определить, " 
        "нужно ли вызвать инструменты MCP под запрос пользователя. " 
        "Если инструмент нужен, вызови его немедленно с правильными аргументами. " 
        "Если инструменты не нужны, ничего не вызывай и просто напиши: 'skip'.")}, 
    {"role": "user", "content": user_query_text}, 
]

Before executing the request, the pipe modifies its body: it removes knowledge/search tools, leaves only Russian-language tool options, disables RAG, and strictly replaces the model:

if "tool_ids" in body and body["tool_ids"]: 
    body["tool_ids"] = [t for t in body["tool_ids"] if "knowledge" not in t and "search" not in t] 
    body["tool_ids"] = self._filter_tool_ids_by_lang(body["tool_ids"]) 
body["docs"] = [] 
if "features" in body: 
    body["features"]["retrieval"] = False  # RAG выключен на время работы роутера 
body.setdefault("options", {})["temperature"] = 0 
body["model"] = "gemma4nothink" 
body["stream"] = False 
body["messages"] = tool_checking_messages

The response is parsed by the code. The tool_calls arguments are parsed using json.loads, the called function is searched for in tools (with a fallback by partial name match, because the function name in tool_call and the key in tools might not match), and the result is compiled into a final text summary:

for tc in tool_calls: 
    func_name = tc.get("function", {}).get("name") 
    func_args_str = tc.get("function", {}).get("arguments", "{}") 
    try: 
        args = json.loads(func_args_str) if isinstance(func_args_str, str) else func_args_str 
    except (json.JSONDecodeError, TypeError): 
        args = {} 
    callable_func = None 
    if tools: 
        if func_name in tools: 
            callable_func = tools[func_name].get("callable") 
        else: 
            for key, tool_data in tools.items(): 
                if func_name in key or key.endswith(f"_{func_name}"): 
                    callable_func = tool_data.get("callable") 
                    break 
    if callable_func: 
        try: 
            if asyncio.iscoroutinefunction(callable_func): 
                raw_result = await callable_func(**args) 
            else: 
                raw_result = callable_func(**args) 
            if isinstance(raw_result, dict): 
                mcp_data_summary += json.dumps(raw_result, ensure_ascii=False, default=str) + "\n" 
            else: 
                mcp_data_summary += str(raw_result) + "\n" 
        except Exception as e: 
            mcp_data_summary += f"[Ошибка MCP]: {str(e)}\n"

At this stage, the user (if in the chat) sees the message "Checking need for tool calls..." before the request, and before each MCP call: "Using tool: {func_name}". In case of an error, they receive the text: "Tool error: {error text}".

If the tool is not found in tools at all (e.g., the gemma4nothink model doesn't see this tool in OpenWebUI), the pipe also doesn't call anything, and the final response is built solely on RAG. Therefore, an important note: the same tools must be connected to both the general model and the specialized one! Otherwise, the router simply won't be able to call them.

Phase 2. Prompt Enrichment

There are almost no neural networks here. At this stage, we perform the final prompt assembly in code. If data from tools is available, it's added to the message along with documentation and instructions; if tools are not needed, only documentation is included. If even that is missing, only the instruction to respond in Russian is added to avoid getting an answer in English or Chinese:

strict_ru_instruction = ( 
    "\n\n[СТРОГАЯ ИНСТРУКЦИЯ: Сформируй итоговый ответ ИСКЛЮЧИТЕЛЬНО на русском языке. " 
    "Не используй английский, китайский, арабский или любой другой язык. " 
    "Сохраняй профессиональный стиль службы поддержки.]" 
) 
if mcp_data_summary and user_msg_index != -1: 
    enriched_text = ( 
        f"\n\nПользователь спрашивает: {user_query_text}\n\n" 
        f"АКТУАЛЬНЫЕ ДАННЫЕ ИЗ СИСТЕМЫ INVAPI (MCP TOOL RESULT):\n{mcp_data_summary}\n\n" 
        f"РЕЛЕВАНТНАЯ ДОКУМЕНТАЦИЯ:\n{docs_result}\n\n" 
        f"Инструкция: Сформируй итоговый ответ для пользователя. Полностью опирайся на данные из системы INVAPI выше и на документы из твоей встроенной Базы Знаний (RAG)." 
        f"{strict_ru_instruction}" 
    ) 
    if isinstance(original_content, list):                # не ломаем блок со скриншотом 
        original_content.append({"type": "text", "text": enriched_text}) 
    else: 
        messages[user_msg_index]["content"] = f"{original_content}{enriched_text}"

The instruction about Russian language is added to the message exactly once: either within the enriched_text or as a separate block if no enrichment occurred.

At this stage, it's important to erase traces of tools and bring RAG back:

if "tools" in body: del body["tools"] 
if "tool_ids" in body: del body["tool_ids"] 
if "docs" in body: del body["docs"] 
if "features" in body: body["features"]["retrieval"] = True   # возвращаем RAG обратно 
body["model"] = "hostkeyrurhr"

Phase 3. Final Generation

In this phase, the main request goes to the custom model hostkeyrurhr with RAG and streaming enabled, if the user requested it:

messages.insert(0, { 
    "role": "system", 
    "content": ( 
        "КРИТИЧЕСКОЕ ПРАВИЛО: Ты ДОЛЖЕН отвечать ТОЛЬКО на русском языке. " 
        "Никогда не используй английский, китайский, арабский или любой другой язык. " 
        "Если ты в чём-то не уверен, отвечай на русском. " 
        "Это обязательное требование — нарушения недопустимы." 
    ) 
}) 
body["messages"] = messages 
body["stream"] = user_wanted_stream 
final_response = await self._post_with_retry(body, headers)

In this phase, the user will see "Forming final response...". This is the last "long" stage, and until its completion, the user sees that the pipeline is still working.

Phase 4. Post-processing: Language Check, Placeholder Trimming, and Fallback

This is a layer that is completely absent in OpenWebUI's settings. Here, the finished response goes through code using regular expressions.

First, we look for Cyrillic characters, and if none are found but Latin characters are present, we consider the response not to be in Russian and that it needs to be redone or a fallback should be provided.

def checklanguage_heuristic(self, text: str) -> bool: 
    if not text or not text.strip(): 
        return True 
    cyrillic_pattern = re.compile(r'[\u0400-\u04FF]', re.UNICODE) 
    cleaned = re.sub(r'``[\s\S]*?``', '', text) 
    cleaned = re.sub(r'[^]+`', '', cleaned) 
    cleaned = re.sub(r'https?://\S+', '', cleaned) 
    if cyrillic_pattern.search(cleaned): 
        return True 
    latin_pattern = re.compile(r'[A-Za-z]', re.UNICODE) 
    if latin_pattern.search(cleaned): 
        print("[PIPE] Проверка языка НЕ ПРОЙДЕНА: Кириллица не обнаружена, вероятно не русский язык") 
        return False 
    return True

Inline code and links are removed before the check to avoid false positives on technical terms like SSH, IP, VPS. If the check fails, we re-request with an enhanced instruction, and after exhausting attempts, we provide a Russian fallback instead of a technical error.

The retry mechanism is as follows: a reminder is added to messages that the previous response contained non-Russian text, and the request is repeated. If, after all attempts, the language is still not Russian, the FALLBACK_RESPONSE is returned.

In addition to language checking, post-processing performs two other important functions worth mentioning separately.

Trimming the trailing "Continue" phrase

The final model adds a prompt at the end of the response: "If your question is not resolved and needs to be sent to our staff, click 'Continue' to send." This phrase is embedded in both the system prompt and the fallback placeholder, so it might be duplicated in the response or not needed at all if the request is not HR-related. Therefore, it needs to be trimmed.

The problem is that within the pipe, we don't know in advance if this phrase will be at the end, and simply cutting off the last N characters is not an option. Therefore, the pipe holds back a certain number of characters (the length of the longest trailing phrase + buffer) and only releases them when it's confident that it's not the end of the response. The tail is checked using stripprompt_footer with normalization of quotes and case.

Trimming placeholder paragraphs

If the response is short (less than 800 characters) and a fallback placeholder marker (FALLBACK_MARKERS) is found in the first 400 characters ("to be studied by our specialists," "click 'continue'," "escalate the issue to our team," etc.), the pipe cuts the response by paragraphs and discards those containing the marker. This is a safeguard against cases where the model itself inserts a placeholder template into the response, even though the question was within the RHR scope.

As a result, we get a response to our query with a warning. Yes, it's still not perfect, and there's room for improvement.

In terms of speed, the pipe adds an extra 5 to 10 seconds to the response time for additional LLM requests. However, this is not critical for us, and instead of 5-10 seconds, the response is delivered in 10-20 seconds, which is a very good result for our hardware and model.

Problems with Pipes

Let's be honest: a pipe is not just a plugin with settings, but code that needs maintenance. And any changes require edits to it.

  • The signature of pipe() and the format of tools are part of the OpenWebUI contract. When the environment is updated, they might change, and the pipe will need to be adapted.

  • Debugging is more complex than configuring a model. Instead of one prompt (in our case), we get five phases, three LLM requests, MCP calls, and post-processing.

  • A pipe doesn't negate normal RAG and system prompts with flexible custom model configuration. It only provides control over phase order and ensures that tools are called and data doesn't mix with RAG. If the knowledge base is empty or the prompts are poor, the pipe won't save you.

  • The same tools must be connected to both the general model and the specialized one. Otherwise, the router won't see them and will silently skip the call.

Summary

Configuring a custom model in OpenWebUI remains the simplest and fastest way to use a knowledge base, connect tools, and fine-tune model calls. However, for production support, this is unfortunately no longer sufficient.

The standard tool doesn't guarantee call order (and often cannot automatically call tools via API), doesn't allow "dampening" RAG during tool operation, doesn't separate the roles of "router" and "responder," and doesn't perform post-processing.

A pipe transforms "a single model in the interface" into a deterministic pipeline: a keyword guard and an LLM classifier filter out requests outside the responsibility zone, a separate step searches for documentation, another calls MCP tools with RAG disabled, the final model receives an already enriched prompt, and post-processing checks the language, trims service tails and placeholders, and provides a fallback response as a safety net.

It is precisely this scheme with phase separation, explicit RAG management, and post-processing that allows us to keep our support bots predictable: system data doesn't mix with documentation retellings, tools are triggered at the right moment, and responses are delivered in the correct language.
