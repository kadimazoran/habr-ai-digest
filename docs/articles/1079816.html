1. Three problems of the prototype and three solutions

Problems

  • NPC is static — it knows nothing about the game world and, as a result, invents facts on the fly. Ask an NPC merchant if they have a plumbus, and the NPC will readily offer to sell it and even name a price without batting an eye.

  • NPC cannot influence the game world. You couldn't ask "sell me the pistol, please" and receive the gun in your inventory, spending money in the process.

  • NPC is emotionally flat. The same unexpressive voice, the same facial expression, and the same "flat" response to any player remark (no matter how rude).

Solutions

Each flaw of the prototype is addressed by a separate component:

  • Agent knowledge base — a knowledge base (based on RAG principles) for the NPC, synchronized with the game world. The NPC analyzes the player's request, extracts facts from the knowledge base, and responds to the player accordingly.

  • Expressive Agent — the NPC analyzes the tone of the player's request (are they being rude?), the player's state (are they injured?), its own state, and along with the text response, returns an emotion tag corresponding to the situation. This tag determines which facial animation (MetaHuman) to apply and which voice sample to use for cloning during text-to-speech conversion.

  • Agent function‑calling — the NPC analyzes the player's request and game context, selects an action (from a predefined list), and returns it along with the response; the game logic executes the action.

Thus, the NPC ceases to be just a talking dummy. Now it relies on the current state of the game world and can influence that world.

If you don't want to delve into implementation details, you can check out the video demonstration of the NPC merchant in action: it shows goods, sells them, refuses when there's not enough money, and stays in character when players try to change the subject.

Workflow Diagram

  • The player asks a question using voice;

  • The STT plugin converts audio to text and passes it to the RAG plugin to extract game data relevant to the player's request;

  • The system prompt (NPC character description, instructions, etc.) is retrieved from the DataAsset, which, along with the request text and game data, is sent to the LLM;

  • The LLM analyzes the request and returns the response text, an emotion tag, and the name of the action the NPC should perform;

  • Based on the action name, the ActionHandler (Blueprint class) is retrieved from the DataAsset, which executes the corresponding game logic and updates the game world state;

  • Based on the emotion tag, the voice sample for voicing the text is retrieved from the DataAsset, and along with the response text, is sent to the TTS plugin for audio generation;

  • Based on the generated audio, a lipsync sequence is formed to synchronize the MetaHuman's lips with the audio response;

  • The MetaHuman's facial expressions change according to the emotion tag, and the NPC speaks the response.

In the diagram, we highlighted the part common to all NPC types (◇) (speech recognition and synthesis, lipsync for MetaHuman, LLM inference) and the part that changes from NPC to NPC (●).

Everything directly related to the NPC's personality (character description, voice samples for each emotion, and the set of actions available in the game) is stored in the Data Asset.

Thus, to add a new character, you just need to create an instance of the NPC DataAsset, open it in the Unreal Editor, and fill in the fields according to the template.

  • Name, Description — the character's name and personality description.

  • NpcVoices — five slots for voice samples (Neutral, Happy, Sad, Angry, Surprise), where audio assets are added.

  • ActionData — an array of actions available to the NPC in the game. You need to specify an action template (SellItem(item)) and list possible parameter values (item: pistol, shotgun, rocket_launcher). Each action is associated with two Blueprint assets:

    • DataGetter — a function to collect game information before sending it to the LLM (see Agent knowledge base).

    • ActionHandler — a function to execute the NPC's action. It's what changes the game world (see Agent function‑calling).

The editor won't let you make a mistake with types — you can't put a 3D mesh into a voice slot, or select a Blueprint that isn't an handler into an handler slot.

A bit about the "contract" of communication with the LLM. What the LLM receives and what it gives

JSON input — three fields: the player's request itself (request_of_user - result of STT conversion) plus game data: state_of_user and state_of_npc (see section 2):

{  
  "request_of_user": "show me what weapons you have",  
  "state_of_user":   "wounded, 250$ cash",  
  "state_of_npc":    "shotgun: 12 pcs, price 300$; pistol: 3 pcs, price 150$"
}

JSON output — also three fields: an emotion tag for MetaHuman facial animation and voice sample selection, the NPC's line for voicing, and an action in the game with parameters:

{  
  "emotion": "Happy",  
  "answer":  "Of course, here are the best guns in town!",  
  "action":  { "name": "ShowItemsByCategory", "parameters": { "category": "weapons" } }
}

Moreover, the LLM physically cannot violate this format. Both the object structure and the allowed values for emotion and action are defined by grammar at the sampling level — we'll cover how exactly in section 4.

What it runs on

The system framework (◇ in the diagram) is built from four plugins — all of which we have published on Fab:

  • ULlama — LLM inference within the engine on top of llama.cpp with CUDA acceleration. This plugin handles both the dialogue model (Qwen3.5 2B in fp16) and the embedding model (Qwen3-Embedding) for semantic search in the knowledge base (section 2);

  • SRS — player speech recognition, using the Qwen‑STT model;

  • SGS — speech synthesis with voice cloning, using the Qwen‑TTS model;

  • ULSS — MetaHuman lip animation based on audio.

Everything runs locally. No external APIs, no token fees, and no GDPR concerns. Of course, everything has a price...

How demanding is this system on hardware?

The main thing to understand about the load is that four neural networks reside on the graphics card simultaneously — the dialogue LLM, the embedding model for the knowledge base, the STT, and the TTS models. And all of this is in addition to the game itself.

In practice, the demo uses about 13 GB of video memory. This means the practical requirement is a card on the level of an RTX 3070 Ti with 16 GB of VRAM.

It's possible to use graphics cards with less memory: llama.cpp/gguf can keep part of the model layers on the GPU and compute the rest on the CPU. The VRAM requirement is reduced, but each layer offloaded to the CPU adds latency, and the pause between the player's question and the NPC's answer turns into an awkward silence.

The video memory consumption by the models does not depend on the number of NPCs on the level. The model itself doesn't change from NPC to NPC (it's loaded once).

Therefore, several NPCs can be present on the scene simultaneously: each with their own character, voice, and set of actions, but all on top of a single model in VRAM.

2. NPC knows: Agent knowledge base

Before sending the player's request to the LLM, we analyze it to understand what the player wants from the NPC, extract facts about the game world from the NPC's knowledge base, and add them to the request.

This way, the LLM will respond based on the actual game state. Now, let's figure out what we mean by "knowledge base." We mentioned RAG in the article title, but our knowledge base is structured differently from the standard in "classic" RAG.

What's actually in the knowledge base

Typically, a RAG system works with documents: text is cut into chunks, stored in a vector database, and for a query, the most similar chunks are retrieved and mixed into the prompt. Our base is structured somewhat differently. It does not store information about the game world. Instead of facts, it stores intentions — a list of everything the player might possibly ask this NPC (give a quest, sell an item, etc.).

Each intention is a signature of the form "action + parameters" (the intention field) linked to its context provider (the action field):

[
  {
    "intention": "SellItem | item: pistol",  
    "action": { "name": "SellItem",  "parameters": { "item": "pistol" } }
  },
  {
    "intention": "SellItem | item: shotgun",
    "action": { "name": "SellItem",  "parameters": { "item": "shotgun" } }
  }
]

The action field in this case is not the action the NPC will perform. It's just a key to the context provider: it tells us what facts to extract from the game for this intention. The LLM decides which action to take — it can respond with OutOfStock or NotEnoughGoldToBuy for the same intention SellItem.

Why this approach instead of "putting all facts into the base"? Facts change at runtime (items are bought, money is spent, the player is injured). Storing a copy in the base guarantees it will be out of sync with the game. Therefore, the base only answers the question "what is the player trying to achieve?", and the facts themselves are pulled from the game state at the time of the response. This ensures the information is always up-to-date.

How the player's intention is recognized

Once, during NPC initialization, all intentions (the intention field from the JSON above) are processed by the embedding model and converted into a vector index. Then, for each player request, semantic search is performed:

A computer understands numbers, not the meaning of words. The embedding model (not the one that dialogues with the player) converts text into a vector such that phrases close in meaning get close vectors (calculated using cosine similarity, Euclidean distance, or dot product, as chosen).

The phrases "Sell the shotgun" and "Old man, sell me the rifle" are different letter-wise but mean the same thing, so their vectors will be "close" (and the vector for the request "Sell ammunition" will be much "further").

The search is semantic: a dozen phrasings of the same request ("I'll take the pump-action," "Give me the double-barrel") lead to one intention ("SellItem | item: shotgun").

Where does the context come from?

Each intention has its own context provider (DataGetter Blueprint asset) with two fields: NPC state (what the merchant has in stock, at what price) and player state (how much gold). These provide the up-to-date information — and this is where the knowledge base "synchronizes" with the game.

The developer decides where to get the data from. Currently, DataGetter queries the game logic directly (inventory, money, health), but it could just as easily "go" to a database, an external service, or another RAG. Changing the source means adding a new DataGetter implementation. A trivial task that doesn't affect the LLM or the rest of the pipeline.

Both channels, along with the player's request, form the state_of_user, state_of_npc, and request_of_user at the model's input. The LLM only sees the prepared text. It doesn't matter to the LLM how the developer assembled it.

As a result, the NPC responds based on the facts of the game world. This, if not eliminates, then minimizes the probability of LLM hallucinations and deception by the player. The context at the input is the sole source of truth for the LLM.

3. NPC feels emotions: Expressive Agent

An NPC's emotion is the result of evaluating the situation it (the NPC) finds itself in. The LLM weighs the tone of the player's request, the game state, and reacts accordingly.

The player is rude, but they are injured, and their wallet is empty: the LLM weighs everything together and reacts with "Sad" — the merchant feels more pity than offense. The same phrase in different states yields different reactions.

And the tag arrives along with the response — in the emotion field of the same object from section 1.

The LLM always chooses from five: Neutral, Happy, Sad, Angry, Surprise. The model cannot invent anything like "Ecstatic-sad" — the GNBF grammar guarantees this (see section 4).

Emotion Tag → Voice and Facial Animation

The emotion tag branches into two channels (facial animation and voice generation + lipsync), "bringing the NPC to life".

Facial Animation

MetaHuman NPCs have a full facial rig and a set of animations with various emotions (Face_Joy, Face_Anger, Face_Neutral, etc.) "out of the box". Thus, upon receiving an emotion tag from the LLM, we simply activate the corresponding facial animation.

Voice Generation and Lipsync

In the character's DataAsset, within the NpcVoices field, there are voice samples with different emotions — one for each tag: Neutral, Happy, Sad, Angry, Surprise.

And these are references for cloning, not ready-made lines.

If the Happy tag arrives, we take the corresponding sample and synthesize the response text from the answer field in real-time using that voice.

Based on the synthesized audio file, the LipSync plugin generates lip movements (a set of lip "keypoint" positions for each audio frame). The lip movement animation is then "blended" with the facial animation.

This way, the NPC speaks any generated phrase in its own voice and with the required emotion. Simultaneously, the tag activates facial expressions, and lipsync adjusts lip movements to match the resulting audio.

Here's how it looks in action — in the video below.

The NPC sequentially speaks five lines — one for each of Neutral, Happy, Sad, Angry, and Surprise. The phrase for voicing and the emotion tag are fixed; the LLM is not involved in this process.

Now the NPC can show character and react to the player. It remains to enable it to interact with the player.

4. NPC acts: Agent function‑calling

The LLM analyzes the player's request and, along with the text response, returns an action for the NPC to perform. The game logic finds the handler by the action name and executes the command directly: deducts money, adds an item to the trade, updates the interface.

This means the phrase "sell me a medkit" not only gets a polite response but also leads to real changes in the game.

How it works

An NPC's action is the result of evaluating the player's request and the game world state (state_of_user, state_of_npc) based on instructions from the system prompt.

The system prompt defines:

  • the NPC's role, specialization, and personality;

  • which actions are available and when each is appropriate (e.g., DoNothing — when the question is completely irrelevant), along with strict requirements for each parameter;

  • the format of the response — JSON from section 1 (emotion + answer + action).
