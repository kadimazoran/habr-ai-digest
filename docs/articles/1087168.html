Stop, I started from the middle

I'm talking about KERNEL SHADOWS: 101 episodes in eight seasons, available on GitHub under GPL v3, for free. It's not a video course or a platform: it's a repository with text. A folder per episode, inside it a README with theory and a task, a starter file, tests, and a reference solution. You go through it in an editor with a terminal — I do it in Cursor. No registration required.

It looks like this:

git clone https://github.com/gfazzz/kernel-shadows.git
cd kernel-shadows/season-01-shell-foundations/s01e01-terminal-awakening
less README.md
cp starter/whereami.sh artifacts/
bash tests/test.sh

In starter/, you won't find the solution, but rather placeholders:

set -euo pipefail

# TODO 1: get the current absolute path (hint: a 3-letter command)
#         and save it to the 'here' variable.
here="" # <-- replace with the command call

# TODO 2: print the current directory and the home directory ($HOME).
echo "Current directory (pwd):   ${here}"

# TODO 3: determine if you are in the root directory "/", and print a clear status.

The test for it immediately fails, and that's normal:

  PASS: whereami.sh found
  PASS: bash syntax is correct
  PASS: shebang is present
  FAIL: current path /home/max/ops/deep/place is missing from output (script should print pwd)
  FAIL: $HOME (/home/max) is missing from output
  FAIL: path appears to be hardcoded: output does not change when changing directory
  Result: 3 passed, 3 failed

The third FAIL is for the very reason tests were written manually. It doesn't compare output text; it runs the script from two different directories and checks if the answer changes. A hardcoded path won't pass this.

The reference solution is nearby in solution/, and opening it before your attempt is the only way to ruin the course for yourself. make progress won't count the episode as completed; it's only done when the green test passes on your file.

Required software: bash, git, make, python3. No test requires root, network, docker, or hardware — more on that later.

A rule that had to be enforced

To prevent the course from devolving into bash scripting, I outlined the types of episodes for Claude and made balance a criterion for season acceptance:

Type

What you do

What the test checks

Automation

write a .sh

Configuration

edit a config file

config properties, idempotency

Investigation

work in CLI, gather a report

reproducibility of findings

Code

write a .py or .c

A season composed entirely of Automation tasks will not be accepted. Currently, the breakdown is: 25 episodes on automation, 38 on configuration, 30 on investigation, 8 on code. Scripts make up a quarter of the course.

Investigation sounds good right up until the first test

How do you verify that someone has understood an incident? Not "did they write a script?", but "did they understand?". Plus, I preemptively banned tests that require root, network, docker, clusters, or hardware.

The ban isn't out of asceticism. A course that requires setting up Kubernetes won't be completed by anyone, including the author — and it was primarily made for the author. A test that pokes a live network fails half the time, and the person concludes it's broken. The first version of the node accessibility episode honestly called ping, and I had to move away from that.

Now, the test places its own ping at the beginning of PATH:

cat > "${FAKEBIN}/ping" <<'MOCK'
#!/usr/bin/env bash
host="${!#}"
case "${host}" in
  up-*|10.0.0.1) exit 0 ;; 
  *)            exit 1 ;; 
esac
MOCK

It checks not connectivity, but the logic of the solution: did it save the return code, did it hardcode the status, does it distinguish between "no response" and "responded, but without the time= field"? The same has been done for ss, dig, ufw, and dpkg.

A config can be read with the eyes of the program that reads it

Next was systemd, and here the AI struggled for a long time, thinking it had hit a dead end. An episode about a unit: the user writes a .service file, but how can you be sure it's correct if systemd can't be run in the test?

It turns out, you don't need to run it. A unit is text with a known semantics, and the semantics can be reproduced. The test reads the file the way systemd does: sections are significant, the last assignment wins, an empty value resets the setting, comments are ignored. Then it compares the effective values with the service requirements. It separately catches pipelines in ExecStart (there's no shell, after all), After without Wants, and a setting that was reset by an empty assignment later in the file.

Unexpectedly, this proved more useful than running it. A running service answers the question "did it start now, on this system, with this environment?". The investigation answers "what is actually written here?", and that's the skill the person came for. The same method is used to check sshd_config, fstab, logrotate, compose.yaml, Kubernetes manifests, and auditd rules.

A pleasant side effect: the test catches things that surface weeks later in real life. A directive left inside a comment. A directive set twice. Host * at the beginning of ~/.ssh/config, which causes all subsequent private sections to become inactive.

You can argue with this, and I'll agree in advance: if you need to ensure that a service actually starts on your distribution with your SELinux, config parsing won't show that. For a learning task, the former is more important; for production, the latter. Two episodes where a live kernel is absolutely necessary (module compilation, insmod, reading /dev/shadow0) are moved to a separate goal and honestly print SKIP without Linux.

And forensics in life also works with a snapshot

Episodes on incident investigation are run on snapshots: output of ps, contents of /proc, logs, dump of /proc/net/tcp. You need to find a hidden process, a deleted binary, and a server control address encoded in little-endian. There's no compromise here: you can't ask a live machine with a rootkit about itself.

What broke

Tests that pass on my machine are not tests. Therefore, the Makefile has three targets, each introduced after a specific failure.

make test-repeat runs everything twice in a row. It catches episodes where the second run sees garbage from the first.

make test-locale runs under LC_ALL=C and with a foreign timezone and German locale. It catches checks that compare sorted output: in a different locale, sorting is different, and the test fails on a correct solution.

make clean-clone unpacks the course from scratch and runs it on a fresh clone. The most offensive discovery happened here: a typical .gitignore excludes *.log, keys, and .env, but in a Linux course, these are exactly the learning materials — fixtures for log analysis, training SSH and TLS keys, app.env for container episodes. Locally, everything is in place because you already have it, but in a clone, the tasks remain without input data. Now, ignoring is based on the launch directory, not the extension, and there's a CAPSLOCK comment in .gitignore so we don't overwrite it.

About AI, since nothing would have happened without it

I built both courses myself, with AI, and wrote almost no code by hand. The conclusion I drew from this is not what is usually expected.

AI didn't write code for me here; it did two other things.

First: it helped create a program for me. Not "generate a Linux course" — that results in a textbook table of contents, I tried. But a conversation about what I want to learn, in what order, with what material, and what should be the outcome. Previously, this was only available to those with a live mentor.

Second: it helps while I go through this course. The story includes a mentor named LILITH, and behind her is a regular chat in Cursor, open next to the code. You must proceed in Ask mode. In Agent mode, the assistant edits files itself: the episode will be marked as solved, and you won't type a single command. The first section of .cursorrules forbids it from writing to artifacts/, revealing the episode's solution, or retelling solution/ — but you switch the mode, not the file, so it's more of a reminder than a protection.

Therefore, at the end of each episode, the AI lists questions that are worth asking it, and one forbidden question. The forbidden one always looks completely reasonable and is detrimental precisely here. In the episode about packet analysis, it's "analyze the header for me": the hardcoded IP header length works for nine out of ten packets, and you have to find the tenth one yourself. In the profiling episode, it's "optimize my code": profile first, then optimize; doing it the other way around is guesswork.

Usually, the discussion about AI boils down to the fact that administrators and programmers will soon be obsolete. In my opinion, it's the opposite. What has become cheaper is not the profession, but the personal learning program: previously, between "I want to understand Linux" and "I understand" stood the search for a good course, someone else's pace, and someone else's topic order; now, it's an evening's conversation with an assistant. A person who can look at sshd_config and see that a directive is not active is needed just as much as they were needed before.
