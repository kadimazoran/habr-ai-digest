Good day! My name is Tatyana Pchelnikova, and I am a product owner in the Severstal IT team, which develops components for open automation systems. In this article, my team and I want to share how we came up with the idea to create an intelligent assistant and integrate it into our SeverCode development environment (hereinafter referred to as Flogic).

One of the key prerequisites for creating such tools is the market's need for qualified engineers: automation engineering is becoming a bottleneck. Innovation cycles are shrinking, system complexity is growing, and the number of experienced engineers is not keeping pace.

To address this problem, major vendors in the automation industry have begun creating assistants, such as Siemens' Eigen Engineering Agent. The agent connects to TIA Portal, gets project context, and performs tasks like writing code in SCL and LAD, generating HMI visualizations, and configuring drives and hardware. Despite all the advantages of this product, it has a significant limitation: like all Siemens products, it only works with Siemens. The Eigen Engineering Agent works exclusively with TIA Portal and SIMATIC S7-1200/1500.

It is also worth noting the recently released MCP Server CODESYS product, which supports direct interaction of an AI assistant with the development environment. This is an official add-on component for CODESYS that, via the Model Context Protocol (MCP), provides a direct link between large language models (LLMs) and the CODESYS development environment. The protocol itself is proposed by Anthropic and is an open standard, essentially a "USB interface for the AI world." CODESYS officially warns that when using cloud AI, all project data accessible to the user (including source code and library configurations) is transmitted to the provider's servers. If your use case involves confidential source code, you should consider a locally deployed LLM to avoid this risk.

For projects based on IEC 61499 developed in Flogic, there are no similar tools on the market. Thus, we have a dual picture: on one hand, AI assistants for industrial development are becoming a reality (Siemens, CODESYS); on the other hand, they are either tightly bound to a specific vendor's ecosystem or do not cover the IEC 61499 standard. At the same time, the key issue remains security: cloud LLMs require code to be transmitted to third-party servers, so for critical applications, a locally deployed model is preferred, and this requirement must be considered when choosing or creating a tool for Flogic.

After studying all the pros and cons of existing solutions, we thought, why not create our own Copilot? We wanted our Copilot to fulfill the need for a tool that would have functionality comparable to the Eigen Engineering Agent and work with the IEC 61499 standard without transmitting data outside the corporate network, as our LLM is deployed locally.

Currently, we have already created a prototype of Flogic Copilot, which is integrated into the Flogic IDE and can work with the project open in the development environment. Copilot does not have access to external sources and operates solely on the context of the project and connected libraries. This approach aligns with the principle of contextual conditioning; we analyze the project's data structures, blocks, parameters, and component interdependencies to generate results applicable directly to the current project. This will be a separate plugin, not an open-source solution.

What can Copilot already do?

Information and Reference Functions

The assistant provides answers to queries about the project structure and libraries: about the composition of applications, connections between blocks, sources of events and data, block logic, and ST code. It also performs semantic search for blocks in the OSCAT, Standard Library, and project types. Copilot can be invoked from the context menu by right-clicking on the project.

Example queries for Copilot:

  • "Where does the signal to PUMP_CTRL.START come from?"

  • "Which block in OSCAT implements a turn-off delay?"

  • "Tell me what the MUL function block does?"

Copilot also provides a detailed explanation of how a particular FB works and can help place it on the canvas.

This functionality is analogous to the Eigen Engineering Agent's capabilities for providing an "overview of devices and logic in TIA Portal" for quick project structure assessment. Siemens provides an example where a new engineer can ask "Show all blocks controlling station 3" and get an immediate answer, reducing adaptation time from weeks to days. When comparing with us, it is appropriate to compare based on the context coverage criterion: the Eigen Engineering Agent primarily responds based on the project structure within TIA Portal, whereas our assistant covers a broader context, including not only application composition and block connections but also semantic search across OSCAT and Standard Libraries, block logic, and ST code. It is on this criterion, the breadth of context coverage, including libraries and source code, that we are not inferior to Siemens' solution.

Project Verification

The assistant performs project checks using the Flogic development environment itself: it identifies type mismatches, unconnected ports, and parameter errors.

Example query: "Why is the FB_TON block displayed as erroneous?"

Running Blocks in the Interpreter

Blocks with code (Simple FB, Basic FB, functions) are executed in the Flogic interpreter with specified input values. The result is generated based on actual computation.

Example query: "What is the output Q value of the FB_TON block when IN=TRUE for 3 seconds and PT=5 seconds?"

Network Modification

Operations such as adding function blocks, setting parameters, renaming, and deleting elements are supported. Changes are presented to the user in a card with "Apply" or "Reject" options. In "Apply yourself" mode, the change occurs immediately, followed by verification of the result.

Example query: "Add a 5-second delay before starting the pump."

Similar functionality is present in TIA Engineering Copilot, which, according to Siemens' description, "autonomously performs complex engineering tasks, automatically generates and modifies project elements." Here, we can compare our solution not by the fact of automatic modification itself, but by the criterion of control and verifiability of changes. In our solution, each change goes through an explicit confirmation card "Apply" or "Reject," or through the "Apply yourself" mode with mandatory subsequent verification of the result. That is, in terms of control over changes, we are not inferior to our renowned colleague, and in terms of process transparency, we look just as good.

Developing New Blocks

The assistant generates new blocks in ST language, formatting them as Simple FB for the project and testing their operability within the Flogic development environment.

Example query: "Develop a function block to calculate the average value from three analog inputs."

Eigen Engineering Agent provides a comparable capability for SCL: "generation of SCL and LAD code, adaptation of existing logic, explanation of code behavior, management of engineering objects, generation of automatic test scenarios." Importantly, as in our solution, the generation is not of "generic code snippets": the agent applies specific knowledge of the standard's architecture and creates code considering already known built-in FBs in the library.

Modifying Algorithm Code

Changes to the algorithm code of project types are allowed without affecting the interface and instances in networks. Differences are presented using runs in "before" and "after" modes.

Transferring OSCAT Blocks

The transfer of OSCAT blocks to the project with dependency resolution is provided. This means an engineer can take the FB description from the OSCAT documentation, even copy existing code from the description into a chat with Copilot, and ask it to create an FB. The model will create the required FB, place it in the library, and correct the code with the nuances specific to the development environment.

The effectiveness of the solution is ensured by adhering to the following principles:

  • Contextual Conditioning. When processing a request, the model receives a slice of the project graph: blocks, connections, types, parameters. The response is generated within the boundaries of the provided context, without accessing external sources.

  • Computation Instead of Guessing. Block test results are generated by actually executing the code in a deterministic environment, meaning the model interprets the obtained results.

  • Engineer Control. Changes are presented in a card format. Even in the "Apply yourself" mode, verification and rollback are provided. The specialist has the opportunity to review the differences before and after making changes.

The key advantage of our product is that for environments supporting the IEC 61499 standard, such a tool has not existed before.

Our fundamental position is that the assistant is viewed as an engineer's tool, not a replacement for a specialist. The assistant provides answers, performs checks and calculations, and generates suggestions. Decision-making remains with the human. Our Copilot allows engineers to focus on higher-level system solutions rather than replacing them.

Where are we heading?

In future releases, we plan to implement the following functionality:

  • modifying the interface of existing types and ECC Basic FB;

  • creating sub-applications;

  • configuring devices, resources, and mapping;

  • loading to the controller and debugging on FORTE;

  • running service and composite blocks (timers, E_DELAY, E_CYCLE).

Thus, the creation of Flogic Copilot is primarily driven by the absence of Eigen Engineering Agent-class solutions on the market that are oriented towards the IEC 61499 standard. Our solution replicates their key principles: contextual conditioning, task execution with validation, and engineer control. At the same time, Siemens products, which have proven effective in the TIA Portal ecosystem, are limited to SIMATIC platforms.
