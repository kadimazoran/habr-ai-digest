In early April 2025, I posted a translation on Habr of Luciano Nooijen's note "Why I Stopped Using AI Code Editors" (original from April 1, 2025). I was publishing the translation between code reviews: while agents wrote code for a couple of projects, I checked diffs every few minutes and gave clarifying tasks.

In the same post, I wrote about our long walks in Samui with a friend, a very cool coder I look up to — 0xhyperdust. We discussed a lot about what our favorite activity would become in a few years and what to do right now to remain in demand. The main hypothesis was that in 2-3 years, we would become AI operators, tasked with understanding the global and local logic of projects, setting tasks, writing architectural code sections, and intervening when something goes wrong.

Luciano's article proposed the opposite view: remove LLM integrations from the editor and only interact with models manually to avoid losing skills. In the end, the post gathered 26 comments and 303 votes in a poll about how many programmers would remain in a couple of years.

Now, in October 2026, I've reread both the translation and the entire thread under it.

The irony is that today I literally agree with Luciano's title: I no longer need AI code editors. Only the reason is different. Instead of a code editor with autocompletion and a side chat, there are now agent wrappers where we work as orchestrators. More precisely, the human in this scheme is one of the orchestrators.

From AI Editors to Agent Wrappers

In the spring of 2025, for most developers, "AI in coding" meant autocompletion within an IDE or a web chat where code snippets were copied (by the way, @Spinoza0 rightly corrected Luciano in the comments back then, noting that even before ChatGPT's release in late 2022, GPT-3.0 was already available).

Almost all the criticism of AI in that thread targeted autocompletion and manual chat. Luciano wrote that because of Copilot, he started forgetting the syntax for unit tests. @0x6b73ca talked about embedded development: "I only write independently, I often use neural networks only to clarify unclear nuances or sometimes instead of a datasheet... and neural autocompletion often inserts what's not needed and it's just annoying."

A similar process was described by @itstranger: he abandoned Copilot because it didn't understand context, and in a chat with GPT, he asked it to generate "no more than one class/module/component" and "don't rewrite code with every edit, but briefly describe only the modification options." Otherwise, with any error, the model would go into a loop: revert module version, update back, reinstall, set a version from a non-existent link — even though the bug was elsewhere entirely.

Against this backdrop, @Volodrippa noted that he calmly codes with AI in Rust, Python, JS, and Swift, if using top-tier models, "not free web GPT and pathetic Copilot." And @dmatora left a comment that reads more interestingly than the article itself a year and a half later:

"Most people and companies don't yet understand how to fully realize the potential of neural networks, for example, platforms like Cursor use, let's say, less than 10% of its potential (personal estimated opinion based on professional experience). But those few who are already using it to its fullest are gaining an 'unfair' advantage in competitive struggle."

At the time, the assessment "Cursor uses less than 10% of its potential" seemed bold. By the fall of 2026, it became clear what those 90% were referring to.

The code editor itself was created for a person who reads files with their eyes and types text with their hands. When LLMs were added to it, the person still remained tied to the open file and the cursor. In 2026, the main work moved from the IDE to agent wrappers (Claude Code, Codex, custom agent pipelines with tool connections via MCP).

When my team works on several projects simultaneously, I hardly need to open a code editor. The project repository contains project rules (AGENTS.md, CLAUDE.md), architectural constraints, and tools connected via MCP — access to the database, logs, tasks, test environment. I set a task for the main agent, and then the orchestration chain works: the agent itself plans the steps, creates a branch or sandbox, launches sub-agents to search the code, write the implementation, run tests in the terminal, and perform initial reviews.

Routine coordination between files and the console is handled by agent orchestrators. The human acts as an orchestrator at a higher level: maintaining the overall architecture, linking the system to business goals, and intervening at complex junctures. In this approach, a code editor is useful only as a diff viewer.

"Tesla Autopilot," Skill Atrophy, and Two Rounds of METR Research

Luciano compared AI editors to Tesla FSD Autopilot, which he used from 2019 to 2021: you get used to the car staying in its lane on the highway, and when you switch to a regular car, you spend the first month relearning how to drive "automatically." Hence his main argument — with AI, you lose Fingerspitzengefühl ("feel at your fingertips"), that very intuition and feel for code details.

This effect was directly written about by @dmatora:

"Even at the stage of o1's release, I encountered the fact that my attempt to read and understand all the code changes made by AI slowed down progress significantly, and abandoning attempts to insert my two cents undoubtedly leads to a decrease in brain training and paralysis when disconnected from AI."

He also compared abandoning AI for brain training to abandoning a tractor in favor of a hoe, to which @krendelbok replied:

"Nonsense comparison. It's like using bombs to till fields, not a tractor. Because now, even after the best models, you have to rewrite the code, wasting time on verification."

Interestingly, this debate was experimentally tested in the summer of 2025. The research group METR conducted a randomized study (Measuring the Impact of Early-2025 AI on Experienced Open-Source Developer Productivity) with 16 experienced contributors to major open-source projects (average of 5 years of experience in the project and over a million lines of code). On a sample of 246 real tasks, half were done with early 2025 AI editors (mostly Cursor Pro with Claude 3.5 / 3.7 Sonnet), and half were done manually.

The measurements confirmed @krendelbok's point for the workflow of those years: developers expected a 24% acceleration, subjectively estimated a 20% time gain after task completion, but the tasks with AI took 19% more time according to the timer. When an experienced engineer sits in an editor over a large codebase, tries to manually review every piece of generated code, and corrects prompts, they spend more time on micro-control than they save on typing.

But by early 2026, the picture had changed. In August 2025, METR launched a new wave of measurements (57 developers, over 800 tasks), and in February 2026, they released a report on why the experiment could no longer be conducted using the old methodology (Changing Developer Habits Make Measuring AI Uplift Harder). Developers began to massively refuse to participate in the control group where AI had to be disabled, saved routine tasks for slots where AI was allowed, and switched to running multiple agents simultaneously, making it meaningless to measure the time a person spent in front of a single IDE window.

When development moves from the editor to parallel agent orchestration, the "feel at your fingertips" also changes. Remembering the exact syntax of mocks in unit tests is no longer required. Instead, intuition is needed at the architecture and review level: quickly spotting from an agent's plan or diff where it's carrying unnecessary state, breaking backward compatibility, or forgetting idempotency. If a person doesn't know how to program at all, they won't see this — Luciano's advice for beginners to understand how everything works under the hood remains valid.

The Debate on "Day Laborer Masons," High-Rises, and Technical Specifications

The longest thread in the comments under the April 2025 post began with a remark from @javax (+7):

"The thing is, an artist spends most of their working time painting. And a programmer (at least a senior one) doesn't program (as one might think), but communicates with people to understand what exactly needs to be programmed."

In response, @DenSigma wrote that all this stems from the underdevelopment of the IT industry:

"This doesn't happen in mechanical engineering. Everything is done according to a project there. The project documentation FULLY defines how the product must be manufactured. The current working style of a senior is like a day laborer mason discussing with a private client how to build a house. In IT, I rarely even see a technical specification for the 'product'."

Then followed a classic debate of a dozen comments. @javax argued that it's more important for the industry to deliver faster, and multi-year technical specifications are only used for software like pacemakers. @DenSigma cited residential high-rises and the navy as examples, where everything is built and modernized according to projects and estimates, and ironically commented on the readiness of IT professionals to change a website business card into a social network for ten million users on the fly.

He was answered by @qw1 (+5) — who pointed out that homeowners don't change the design of entrances or elevator capacity every day, whereas in IT, they ask to "make at least one button faster," move in three floors, and then demand to demolish the first floor for a supermarket without stopping construction — and @DezmontDeXa, who noted that seniors actually create the project, and a "simple worker/junior/neural network" can write the code according to the project, and if the client is willing to pay for changes, software is good because it allows for this.

In a year and a half, agent development has unexpectedly reconciled both camps.

As soon as teams tried to scale "vibe coding" with short prompts like "make me a shopping cart," it turned out that without project documentation, agents quickly wreck the architecture. Therefore, in 2026, the technical specifications and project documentation that @DenSigma wrote about have returned in the form of Spec-Driven Development: before launching coding sub-agents, we write specifications, fix contracts, data schemas, and test plans.

At the same time, clients, of course, haven't stopped changing requirements on the fly, as @qw1 wrote. It's just that before, "rebuilding the first floor for a supermarket" meant weeks of manual code rewriting with tape and electrical tape. Now that the main work is outsourced to specifications and autotests, the human orchestrator updates the project, and the agents rebuild the implementation according to the new inputs much faster.

"That's the point, seniors write little code, they can be left unchanged for now. But mid-levels can be replaced, and juniors will remain to help seniors — tweaking prompts."

What do the numbers show by the fall of 2026? If we take the study by the Stanford Digital Economy Lab (Erik Brynjolfsson and co-authors, Canaries in the Coal Mine? Six Facts about the Recent Employment Effects of Artificial Intelligence) based on millions of ADP payroll records up to 2026, the picture turned out to be very characteristic.

There was no mass reduction in developers — the employment of seniors and experienced engineers in older age groups remained stable and continued to grow. However, @vitalist84's prediction that "juniors will remain to help seniors tweak prompts" turned out to be the opposite. The employment of young developers aged 22-25 dropped the most — by almost 20% compared to the peak in late 2022, mainly due to a sharp slowdown in hiring for entry-level positions. It turned out that "tweaking prompts" without understanding the architecture is useless, and seniors now close junior's routine tasks with a swarm of sub-agents.

On the other hand, the hypothesis about custom software, which I myself brought up in the comments back then (@awaik), was fully confirmed:

"One of the hypotheses is that 'custom' applications will become in demand. One team/business — several applications created specifically for the needs of the team/business. In this scenario, the number of people employed in the industry may increase."

Then @Glen5 gave an example of a large company with 15,000 people, where five years ago there were dozens of internal Android applications, including a poll for vacation days, and @positroid added: "less time-to-market — more products and solutions for more clients."

In 2026, such custom tools are no longer a privilege of corporations with 15,000 employees — now any small team or even a single person creates them for themselves. I see it myself: we have several projects in development simultaneously, and for my personal productivity, I wanted to create a web application for notes based on the OBTF concept (One Big Text File in pure Markdown). I wanted it to be cache-first, work offline during walks, be able to insert voice-dictated text precisely at the cursor position, use the excess power of our server to recognize speech with a model fine-tuned for IT terminology, GigaAM-v3, and serve the file directly to Claude or ChatGPT via MCP (here's a detailed post about the app itself, and here — how we fine-tuned GigaAM-v3). Before, building such a custom project for my own habits would have been a waste of time, but with agent wrappers, it's easily built in parallel with the main work.

Even the question from @Alexis_Che in that thread — whether they had tried giving a neural assistant the task of drawing a part contour for laser cutting — is now routinely solved in 2026: the agent writes a parametric script in Python (CadQuery / build123d), checks the geometry, and exports the finished DXF.

Security, Responsibility, and "Soft Factory"

Two comments about security and business's attitude towards development are worth mentioning separately.

Luciano wrote in his article that if one AI writes code, another checks PRs, and a third deploys, we'll see a surge in security problems. @ALexKud (+7) added a very accurate argument about responsibility in the comments:

"They'll play with AI for a while, then realize that it all doesn't work without a person of appropriate qualification. Besides, you can't punish AI for errors, security holes, etc. You'll get a lot of code, and who will control all of it? More people and higher qualifications will be needed."

And @milkyway044 described his CEO's worldview:

"The company is a 'soft factory,' where speed is the main metric, quality is defined as 'reasonable sufficiency' (fulfilling the stated function, nothing more), and AI is a mandatory tool to achieve this speed and survive in competitive struggle... In his worldview, people (developers) are a replaceable resource. Their value is measured by the speed of plan execution. They are 'production units' in a 'soft factory.'"

Both hit the nail on the head. According to the Stack Overflow Developer Survey 2025 (about 49,000 developers), 84% of respondents use or are implementing AI tools, but the proportion of those who actively distrust the accuracy of raw AI output has increased from 31% to 46% (only 3% trust it unconditionally). And Veracode tests on more than 100 language models showed that while syntactic correctness is above 95%, only 55% of generated code passes security checks without additional restrictions — the remaining 45% contain classic vulnerabilities like XSS, log injection, and authorization errors. The research by Dan Boneh's group at Stanford and GitClear reports on increased code duplication say the same thing.

Companies that tried to build a "soft factory" literally according to the recipe from @milkyway044's comment — replacing engineering control with a race for generation speed — quickly got bogged down in bugs and vulnerabilities.

In the normal 2026 process, this problem is solved not by returning to manual coding, but by the architecture of the wrapper itself. One sub-agent writes the implementation in an isolated branch, another checks the diff for vulnerabilities and contract compliance with a separate checklist, linters, type checking, and autotests are definitely run, and key architectural decisions and final acceptance remain with the human orchestrator. Because @ALexKud is absolutely right: production and security are always the responsibility of a specific person, not a model.

The Bottom Line

My friend's and my hypothesis from our walks in Samui about developers transitioning to the role of AI operators came true even faster than in 2-3 years, only it went a step further.

Code editors themselves have ceased to be the place where we spend our workday. The development center has moved to agent wrappers. Within these wrappers, agent orchestrators now work, taking on the routine coordination of sub-agents, files, and tests, while the human acts as one of the orchestrators — the one who sets the meaning, architecture, and boundaries of what's permissible.

It's very interesting to hear how your work has changed over these one and a half years — especially if participants from that April 2025 discussion look into the comments. Do you write code by hand, use Cursor, or have you also moved to agent wrappers?
