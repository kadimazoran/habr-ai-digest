Developing an indie game is a constant struggle with resources. Usually, there isn't enough time, money, people, and, ideally, a couple more hours in the day.

When I started making Morveyn (https://habr.com/ru/articles/1100432/) - a turn-based RPG for Telegram, inspired by classic fantasy strategies like King's Bounty - it quickly became clear that writing a game and filling it with content are two completely different tasks.

The technical part was relatively clear: Next.js on the frontend, Java on the backend, game logic, server interaction, map generation. This is familiar territory for a developer.

But the graphics turned out to be a separate adventure.

The game needs dozens, and potentially hundreds, of images: units, character portraits, buildings, environmental objects, global map tiles, icons, and interface elements. Moreover, all of this must look as if it was created by a single artist for a single game.

Hiring an artist for every experimental asset at the MVP stage was irrational. So I decided to try generative AI.

Ultimately, Gemini became the main tool.

And that's when the most interesting part began.

One Beautiful Picture Isn't Victory Yet

Generating a cool fantasy knight is not difficult today. You just need to describe what you want to see, add a couple of stylistic references, and you can get a quite impressive result.

The problem starts when, after the knight, you need a goblin shaman. And after that - a skeleton warrior, an elven archer, a tower, a forest object, and a skill icon.

Each individual generation might look great. But if you put all the results side by side, you'll suddenly find that they look like they're from different games. And they even overlap.

One character looks like an illustration from a tabletop RPG. The second - like a modern 3D render. The third resembles concept art for an expensive computer game. The fourth looks like a children's book illustration.

Beautiful individually. Together - a visual catastrophe.

This is where I realized that the problem of generating game assets lies not so much in the quality of individual images, but in controlling variability.

A game asset must not just be beautiful. It must meet certain requirements:

  • have a predictable perspective;

  • occupy roughly the same image area;

  • maintain visual style;

  • be clearly visible at a small size;

  • not contain random decorative elements;

  • harmonize with other game objects.

Essentially, I needed not a neural network that can draw beautiful pictures, but a tool that can adhere to a visual specification.

Sounds familiar to a developer, doesn't it?

Prompting as Programming

My first approach was quite naive: describe each object separately.

"Draw a goblin shaman in the style of an old fantasy RPG."

Then:

"Draw a skeleton warrior in the style of an old fantasy RPG."

The problem is that the same wording doesn't guarantee the same interpretation. The model makes many creative decisions anew each time.

At some point, I decided to change my approach.

Instead of writing a new prompt each time, I divided the prompt into a constant and a variable part.

Tentatively:

Base part - visual specification:

  • painterly digital illustration;

  • style of classic 1990s fantasy strategies;

  • rich oil painting texture;

  • warm golden light from top left;

  • muted earthy palette;

  • dark brown wood tones and old gold accents;

  • unified visual style of the game world;

  • no inscriptions, logos, or watermarks.

Variable part - specific object:

  • goblin shaman with a wooden staff;

  • skeleton warrior with a rusty sword;

  • elven archer with a longbow;

  • stone tower with a red flag.

As a result, each new prompt became like calling a function with a parameter:

generateAsset(    style = COMMON_STYLE,    subject = "Goblin Shaman",    constraints = COMMON_RULES);

Of course, Gemini doesn't execute such code literally. But the engineering mindset itself proved useful.

I stopped perceiving each prompt as a separate work of art and started treating it as a generator configuration.

In my case, this resulted in separate common blocks for different types of images. For example, character portraits and global map objects received different descriptions of style and composition.

For portraits, the character's position (bust-up), three-quarter view, headroom, and a calm, blurred background are important.

For the map, the requirements are different: a unified viewing angle, consistent object scale, orthographic projection without perspective distortion, and warm light from the top left.

This is an important distinction. One universal prompt for the entire game would be too abstract. It's much more practical to have common rules for each category of assets.

This approach didn't make the results absolutely identical, but it significantly simplified style control.

The Most Underrated Part of a Prompt is What You Can't Draw

When we create a prompt for image generation, we usually focus on what we want to get.

But for game assets, it's equally important to define what we absolutely do not want to see.

Generative models love to embellish images. They want to add beautiful lighting, volumetric shadows, atmospheric haze, reflections, and additional decorative elements.

For a standalone illustration, this can be an advantage.

For a game object that needs to fit into a map tile of a few dozen pixels, it's more of a problem.

Let's imagine we need a simple unit for a tactical RPG.

Instead of a compact character, we get:

  • dramatic cinematic lighting;

  • complex perspective;

  • deep shadows;

  • particles and magical effects;

  • detailed background;

  • decorative elements that start to blend together after reducing the image size.

As a result, the character looks impressive on a large screen but turns into an unreadable blob in the game itself.

This is precisely why I started paying special attention to negative constraints.

In Stable Diffusion, there's a separate field for this: Negative Prompt. In Gemini, I used a different approach: I formulated prohibitions and restrictions directly in the text prompt.

For example, for game objects, you can use the following template:

Create a 2D fantasy RPG game asset. The character must have: - a clear silhouette; - simple readable shapes; - consistent visual style; - controlled composition; - minimal unnecessary details. Avoid: - photorealism; - 3D rendering; - anime and cartoon styles; - modern objects; - blurry details; - text and watermarks; - unnecessary frames and borders; - distorted anatomy; - cropped heads. The character must remain clearly recognizable when displayed at a small game resolution.

Of course, the constraints need to be adapted to the specific image category. For example, for Morveyn, I didn't want to completely remove complex backgrounds from portraits and story scenes. There, they, on the contrary, help convey the atmosphere of the world.

But for individual global map objects, the approach was different. I needed isolated trees, cities, and castles that could be placed on map tiles.

Therefore, for them, I used a separate compositional instruction and a bright pink background #FF00FF, which can be removed during post-processing.

At first glance, all this looks like an excessive number of restrictions.

But that's the point.

A good prompt not only tells the model what to draw. It limits the space of decisions the model can make independently.

This is especially important for objects that will be displayed at a small size.

In such conditions, silhouette readability is often more important than the number of details.

Composition: When Good Art Doesn't Fit the Game

The next problem turned out to be less obvious.

Even if Gemini generates objects in a similar style, they can be positioned very differently within the image.

One character occupies almost the entire canvas. Another leaves a huge empty space around it. A third is cropped at the legs. A fourth is depicted at a completely different angle.

For a regular illustration, this is not a problem.

For a game asset - a serious problem.

Especially if the images are to be used in the interface, on the map, or in a set of units.

Therefore, I started to fix compositional requirements separately:

  • the object is centered;

  • the character is fully contained within the image boundaries;

  • the same scale is used;

  • a consistent viewing angle is maintained;

  • no random elements are added around the object;

  • the background meets the requirements of the specific asset type.

For map objects, I went further. In the prompts, I separately specified that the object should occupy about 80% of the image width, the base should be centered at the bottom, and there should be no additional ground surface around it.

This helps place different objects on the map without the feeling that one castle is twice as large as another just because the model chose a different composition for it.

In addition, for all map objects, I fixed a common perspective: a top-down view at an angle of approximately 60 degrees. At the same time, buildings should have both roofs and front walls visible.

If a tree is depicted almost from the side, and a castle strictly from above, they no longer look like parts of the same game map.

This seems like a minor detail until you start assembling dozens of images into one system.

Then it becomes clear that a unified style is not just about the same palette and line thickness. It's also about unified compositional rules.

Background, Transparency, and Other Annoyances

The background is a separate story.

When generating game objects, you really want to get a PNG with transparency right away and just put it into the game.

But a generative model doesn't always understand transparency the way a graphics editor does.

Sometimes, instead of a real alpha channel, you get a checkered background that only mimics transparency. Sometimes the background has an almost uniform color, but colored halos remain around the character. Sometimes additional shadows or environmental elements appear that are difficult to remove automatically.

Therefore, I tried to separate two tasks:

  1. Get a good object with controlled composition.

  2. Prepare the image for use in the game.

For the second stage, separate processing can be used:

  • background removal;

  • alpha channel creation;

  • cropping the image to the object's boundaries;

  • size normalization;

  • converting images to a unified format.

For map objects, I chose a simple practical approach: generate them on a bright pink background. It's easier to remove programmatically than to try to automatically distinguish all shades of the background from the object's details.

This is especially convenient for trees, castles, and other objects that include green, brown, and gray shades. The pink color practically does not overlap with their natural palette.

For ground, water, and road textures, on the contrary, a background is not needed. There, I used separate prompts for seamless textures with uniform lighting and without objects or shadows.

This is an important point: you don't need to try to solve all problems with a single request to the neural network.

Image generation and game asset preparation are different stages of the pipeline.

If the generation result is good, but the background hinders its use, it's not a reason to discard the image.

References: Sometimes It's Better to Show Than Explain

Another useful technique is using existing images as references.

Not always, but in some cases, it significantly simplifies the work.

For example, you can spend a long time explaining to the model what the character's perspective should be, or show an image whose composition you like.

I periodically used this approach when a text description was not enough.

In Morveyn, I also provided for the creation of reference images that can be used for further generations.

For example, you can first generate several variants of Edric's portrait, choose the best one, and use it as a style sample for other characters.

And for global map objects, a successful variant of Morveyn's castle became a useful reference. Based on it, it's easier to maintain the scale, viewing angle, lighting, and level of detail of other buildings.

However, there's a nuance here: a reference can affect not only the desired composition but also other image characteristics.

The model might transfer unwanted details, change the color palette, or too literally repeat the source object.

Therefore, it's important to specify what exactly needs to be taken from the reference:

  • composition;

  • perspective;

  • proportions;

  • object placement;

  • overall visual language.

And separately indicate what should remain unique.

For example, if a reference is only needed for composition, don't ask the model to just "make a similar picture." It's better to clearly state that the placement and scale should be preserved, and the character and its details should be replaced.

Why Hundreds of Assets Are a Separate Engineering Task

When it comes to a single image, you can afford a dozen iterations and choose the best result.

But when you need to prepare several dozen units, dozens of environmental objects, buildings, portraits, and interface elements, the manual approach starts to scale poorly.

Several problems arise.

1. Unpredictability.

Even with the same prompt structure, the result can differ in composition, details, and visual execution.

2. Inconsistency.

After some time, you start to notice that new images differ slightly from old ones. And you have to go back to previous assets or correct new ones.

3. Quality Control.

You can't just accept all generation results. Each asset needs to be checked in the context of the game itself, not just evaluated individually.

4. Post-processing.

Removing the background, cropping, scaling, and preparing files can take no less time than the generation itself.

5. Accumulation of Visual Debt.

If you accept every beautiful result without checking its compliance with the overall style, after some time you'll have to redo entire groups of images.

In this sense, working with AI graphics turned out to be surprisingly similar to software development.

You can quickly write a few classes, but maintaining a large system without common rules, contracts, and checks is much more difficult.

Therefore, I started to view the set of prompts not just as a collection of text requests, but as part of the project's technical documentation.

Each asset has a filename, purpose, size, compositional requirements, and a description of what should be in the image.

This allows not only generating graphics but also linking them to specific game elements.

For example, tree_oak.png is not just a picture of an oak tree. It's a map object with specific requirements for scale, background, perspective, and base placement.

And portrait_knight.png is a portrait of a specific hero, whose appearance should match his figure in combat.

The larger the project becomes, the more useful this structure is.

My Best Practices

Based on the experiments, I have developed several rules for myself that significantly simplify the work.

1. First, define the visual style, then generate content.

Don't start by generating a hundred random objects. First, you need to achieve a few reference images that will define the look of the entire game.

2. Separate the constant and variable parts of the prompt.

Style, lighting, palette, composition, and constraints should be as stable as possible. Primarily, the object itself should change.

At the same time, for portraits, scenes, textures, and map objects, it's better to have separate rule blocks.

3. Don't forget negative constraints.

Specifying what not to add is sometimes as important as describing the desired result. This is especially true for unwanted visual styles, perspective distortions, complex lighting, backgrounds, and excessive decor.

4. Check the result at the actual game size.

An image might look great at 1024x1024 resolution but be completely useless after being scaled down to 64x64.

5. Separate generation and post-processing.

Don't force the AI to simultaneously draw the object, remove the background, adjust sizes, and prepare the final PNG.

6. Use references for complex composition.

If a specific perspective or object placement is important, it's sometimes easier to show an example than to try to describe everything in words.

7. Don't accept every beautiful result.

The main criterion is not the artistic value of an individual picture, but how well it fits into the overall visual system of the game.

8. Document requirements for each asset.

Specify the filename, purpose, size, background type, and compositional rules. This is especially important when graphics are created in several stages or when you have to return to them after weeks.

9. Generate multiple variants and choose the best one.

It's not always possible to get a suitable result on the first try. For map objects, I used the approach of three to four variants of each image to choose the one that best harmonizes with other elements.

10. Check commercial use terms.

If the game is planned for publication and monetization, it's important to check the license terms of the chosen generation service in advance.

Instead of a Conclusion

While working on Morveyn, I gradually came to an interesting conclusion: generative AI removes some of the artist's work, but it doesn't remove the developer's responsibility for the visual integrity of the product.

You can get an impressive illustration in a minute. But building an entire game universe based on it is a completely different task.

You need to define rules, fix the style, learn to limit the model's imagination, control composition, and organize the processing of results.

And perhaps the most important thing is to stop perceiving AI as a magic button.

For me, Gemini became another tool in the development of Morveyn. Quite powerful, sometimes unpredictable, but especially useful when you approach it not as a random picture generator, but as part of the production process.

Morveyn still has a lot of content ahead. This means the experiments with asset generation will continue.

And, apparently, the question of how to make the neural network draw exactly what you need will remain relevant for a long time.
