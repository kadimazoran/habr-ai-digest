When you enter a prompt into a large language model (LLM), the machine converts your text into numbers, processes them, and then returns the answer token by token. In this article, we will break down what inference (logical reasoning) in LLMs is and see how it works.

What are Large Language Models?

LLMs are simply neural networks built on the transformer architecture. Unlike previous generation architectures where text was processed sequentially, transformers can analyze entire text sequences in parallel. Therefore, transformers are much more efficient to train and deploy.

The fundamental component of these models is the transformer layer, which consists of two main components:

  1. Self-attention mechanism and

  2. Feed-forward neural network.

Dozens of such layers are stacked on top of each other in a large language model. This results in deep neural networks capable of capturing complex patterns present in language.

When operating, transformers rely on the self-attention mechanism, which assesses how each word relates to the entire sequence, not just to adjacent words.

Model size = number of parameters in the network. A model with 7 billion parameters contains 7 billion floating-point numbers that store the knowledge acquired by the model during training. These parameters are organized as weight matrices that transform the input data at each layer.

Models like GPT-4, Claude, and Llama are decoders-only transformers. This means they use only half of the original transformer architecture, i.e., the decoder. Thus, they are autoregressive, generating a new token at each pass based on all previously generated tokens. This is well-suited for text generation tasks.

Tokenization

Even before any computations, the model must convert your text input into numbers. During this process, called tokenization, text is broken down into smaller units called tokens.

In modern large language models, the most common tokenization method is Byte Pair Encoding (BPE) — merging the most frequent character pairs. BPE starts with a dictionary of individual characters and then, iteration by iteration, merges the most frequent adjacent token pairs, thereby creating new tokens.

# Example of BPE tokenization process # Input text: "unhappiness" # Initially: ['u', 'n', 'h', 'a', 'p', 'p', 'i', 'n', 'e', 's', 's'] # After merges: ['un', 'happi', 'ness']

Since BPE is used here, common words are represented as individual tokens (which is efficient), and rare or unknown words are broken down into familiar sub-word units (which is flexible).

During tokenization, the text you input is converted into UTF-8 bytes, after which the model applies learned merge rules and compresses the byte sequence into tokens. Each token is mapped to an integer ID, and the model can work with these IDs.

# Simplified tokenization process text = "The AI model generates text" tokens = tokenizer.encode(text) # [464, 15592, 2746, 18616, 2420]

Tokenization directly affects model performance and associated costs. More tokens mean more computations, higher API costs, and a greater chance of hitting context window limits. This is why processing non-English text often consumes more tokens—if the tokenizer was primarily trained on English data, foreign words usually require more tokens.

Token Embeddings

After the text is converted into tokens, the next step is to transform these discrete token IDs into continuous vector representations that a neural network can process. This is done through an embedding layer; essentially, we have a lookup table that maps each token ID to a high-dimensional vector.

If the model operates with a vocabulary of 50,000 tokens and the embedding dimension is 4,096, then the embedding matrix has a shape of [50000, 4096]. Each row corresponds to a token, and the values in that row form the embedding vector for that token.

token_id = 464  # Token ID for the word "The" embedding_vector = embedding_matrix[token_id] # Result: a vector consisting of 4096 floating-point numbers

These embedding vectors capture the semantic meanings learned during training. Words with similar meanings correspond to vectors that point in roughly the same direction in this high-dimensional space.

Transformers themselves do not automatically understand token order. To address this, positional encoding information is added to the embeddings, providing information about where each token is located in the sequence. Modern approaches use learned positional embeddings or relative positional embeddings, as in the case of Rotary Positional Embedding (RoPE) rotation in the attention layer.

Transformer Architecture

The transformer processes embeddings layer by layer. At each transformer layer, two main operations are performed: multi-head self-attention and a feed-forward neural network.

The self-attention mechanism computes three matrices for each token: Query (Q), Key (K), and Value (V). These are obtained by multiplying the input embeddings by three learned weight matrices.

# Self-attention computation Q = input @ W_query   # Shape: [batch, seq_len, dim] K = input @ W_key     # Shape: [batch, seq_len, dim] V = input @ W_value   # Shape: [batch, seq_len, dim]

The weight matrices W_query, W_key, and W_value are learned during training. They are initialized randomly and then adjusted during backpropagation to extract the most useful patterns from the embeddings.

Next, this mechanism calculates how much attention each token should pay to every other token. This is done by computing the scaled dot-product attention:

# Attention scores scores = (Q @ K.transpose()) / sqrt(dim) attention_weights = softmax(scores) output = attention_weights @ V

The scaling factor (square root of the dimension) prevents the dot products from becoming too large, as otherwise the softmax function would saturate and produce very small gradients during training.

With multi-head attention, this process is performed multiple times (in parallel) using different learned projection matrices. A model might use 32 attention heads, each learning to focus on different aspects of token relationships. The outputs from all heads are then concatenated and projected back to the model's dimension.

After applying attention, the output is passed through a feed-forward neural network, which consists of two linear transformations with a non-linear activation function in between. Typically, the dimensionality is increased by a factor of four before the backward projection.

# Feed-forward network hidden = activation(input @ W1 + b1)   # Expansion with quadrupled dimensions output = hidden @ W2 + b2              # Projection back

Inference Stages — Pre-fill and Decoding

The pre-fill stage occurs when you send your first prompt. The model processes all input tokens in parallel, simultaneously calculating the Query, Key, and Value matrices for each token. This phase is limited by available computational resources, meaning performance depends on GPU throughput.

During the pre-fill stage, the attention mechanism performs matrix multiplications, and GPUs are very good at this. All tokens can see all other input tokens, and the model calculates attention scores for every pair of positions in a batch operation.

# Pre-fill stage computation input_tokens = [token_1, token_2, ..., token_n] # Processes all tokens simultaneously for layer in model.layers: Q, K, V = compute_qkv(input_tokens) attention_output = attention(Q, K, V) layer_output = feedforward(attention_output)

In the pre-fill stage, the model outputs the first result token and collects the key-value cache (KV cache), which we will discuss shortly. The "time to first token" (TTFT) metric measures the duration of this phase and directly impacts user experience—how long the user has to wait to see any output.

The decoding stage begins after the first token is generated. The model produces tokens one by one, autoregressively. Each new token is computed based on all previous tokens, but only fresh queries, keys, and values need to be computed for the most recent tokens.

This stage is limited by memory capacity, not computational power. Most of the time, the GPU spends not on calculations but on loading data from memory. Matrix-vector operations are performed at each iteration, not matrix-matrix operations, so GPU saturation occurs after much less computation.

# Decoding stage computation current_token = first_generated_token while not done: # Compute only for the new token q_new = compute_query(current_token) # Retrieve cached K, V from previous tokens k_cached, v_cached = retrieve_cache() # Compute attention based on cached values attention_output = attention(q_new, k_cached, v_cached) next_token = generate_token(attention_output) current_token = next_token

The inter-token latency (ITL) is the time between two consecutive token generations in the decoding stage. This parameter determines how quickly the text stream flows to the user after generation begins.

Key-Value Cache

The key-value cache represents the most crucial optimizations for transformer inference. Without this cache, generating 100 tokens would require recalculating attention for all previous tokens 100 times, consuming enormous computational resources.

During autoregressive generation, the key and value matrices for previously processed tokens no longer change. Only one matrix—the query—needs to be computed for the new token. By caching the key and value matrices from all previous tokens, we avoid recomputing them.

You can get an idea of how this works from the following pseudocode.

class KVCache: def __init__(self): self.cache_k = None self.cache_v = None def update(self, new_k, new_v): if self.cache_k is None: self.cache_k = new_k self.cache_v = new_v else: # Concatenate new K, V with cached values self.cache_k = concat([self.cache_k, new_k], dim=1) self.cache_v = concat([self.cache_v, new_v], dim=1) def get(self): return self.cache_k, self.cache_v

The model maintains separate key and value caches for each transformer layer and each attention head. When generating the n-th token, the cache stores the key and value matrices for all n-1 previous tokens.

Thanks to key-value caching, performance can be dramatically accelerated. In practice, with key-value caching, 1000 tokens can be generated in about 10 seconds, whereas without caching, the same task takes 50 seconds—a fivefold difference.

However, maintaining the key-value cache consumes memory. The cache grows linearly with the sequence length. For a 13-billion-parameter model like LLaMA-2, approximately 1MB of cache storage is required per output token. A context of 1000 tokens requires 4GB just for the cache, which is comparable to the model size itself.

This memory pressure becomes very significant when working with long contexts or large batch sizes. Modern systems employ several strategies to manage the key-value cache memory: quantizing the cache to lower precision (4-bit or 2-bit keys and values), using a sliding window attention that only keeps the most recent tokens, or implementing attention approximations that reduce cache requirements.

When I first experimented with running a model on my own, I thought the slow responses were due to the GPU. Only later did I notice that the key-value cache was constantly spilling out of GPU memory.

Every time a user entered a long prompt, the latency increased sharply. A single fix—reducing precision from FP16 to INT8—cut the response time by more than half.

Matrix Multiplication

Matrix multiplication is the computational core of transformer inference. At each transformer layer, matrices are multiplied multiple times: Q, K, V are computed based on input values, attention is applied, and the feed-forward neural network is utilized.

GPUs use a tiling strategy for efficient matrix multiplication. A large matrix operation is divided into smaller fragments that fit into shared memory. This reduces the number of costly global memory accesses.

Each block of threads computes one fragment of the output tile, moving across fragments along the K dimension. This maximizes data reuse: once data is loaded into shared memory, all threads in the block can access it without generating global memory traffic.

This process can be further accelerated using tensor cores, which offload entire small matrix multiplication operations to hardware. This programming model supports 16x16x16 operations, but on hardware, they are automatically executed as multiple 4x4x4 operations.

Precision and Quantization in Inference

Inference in large language models is often performed at lower precision than training. While training typically uses FP32 or BF16 precision, inference can use FP16, INT8, or even INT4 with minimal quality loss.

FP16 (16-bit floating-point numbers) halve the memory and bandwidth requirements compared to FP32. Tensor cores achieve maximum throughput with FP16, making this precision the default for many inference configurations.

# Precision formats FP32: 1 sign bit, 8 exponent bits, 23 mantissa bits FP16: 1 sign bit, 5 exponent bits, 10 mantissa bits BF16: 1 sign bit, 8 exponent bits, 7 mantissa bits INT8: 8 bits for integer representation INT4: 4 bits for integer representation

Quantization allows converting model weights and activations to lower-precision formats. To maintain model quality, careful calibration is required. Post-training quantization analyzes activation distributions on representative data to determine optimal scaling factors.

A 7-billion-parameter model running at FP16 precision requires approximately 14GB of memory (7 billion parameters × 2 bytes per parameter). Quantizing to INT4 reduces this to 3.5GB, enabling inference on consumer-grade hardware.

Techniques like GPTQ GPTQ and AWQ AWQ allow scaling factors to vary per channel and per group, preserving more information from the original weights. Some methods quantize weights while keeping activations at high precision, balancing quality and performance.

End-to-End Inference Flow

Step 1: Tokenization. You type the prompt “Explain how transformers work,” and the tokenizer converts it into token IDs. The BPE algorithm breaks these tokens into sub-word units, resulting in something like [Explain, how, transform, ers, work].

prompt = "Explain how transformers work" token_ids = tokenizer.encode(prompt) # [22163, 703, 4659, 364, 990]

Step 2: Embedding Lookup. Each token ID is indexed into the embedding matrix, retrieving its corresponding embedding vector. If the model has 4096 dimensions, each token becomes a vector of 4096 floating-point numbers.

embeddings = embedding_matrix[token_ids] # Shape: [5, 4096]

Step 3: Add Positional Encoding. The model adds positional information to the embeddings so the attention mechanism knows the token order.

positions = [0, 1, 2, 3, 4] positional_embeddings = positional_encoding[positions] input_embeddings = embeddings + positional_embeddings

Step 4: Pre-fill Stage. The input embeddings pass through the transformer layer by layer. If the model has 32 layers, this happens 32 times.

hidden_states = input_embeddings for layer in model.layers: # Multi-head self-attention Q = hidden_states @ W_query K = hidden_states @ W_key V = hidden_states @ W_value attention_scores = (Q @ K.T) / sqrt(dim) attention_probs = softmax(attention_scores) attention_output = attention_probs @ V # Store keys and values in the cache for this layer kv_cache[layer].update(K, V) # Residual connection and layer norm hidden_states = layer_norm(hidden_states + attention_output) # Feed-forward network ffn_output = feed_forward(hidden_states) # Residual connection and layer norm hidden_states = layer_norm(hidden_states + ffn_output)

Step 5: Generate First Token. After the final layer, hidden states are projected to the vocabulary size via a linear layer, then softmax converts these logits into probabilities for all possible next tokens.

Step 6: Decoding Phase. Now, we decode tokens one by one. For each new token, we compute fresh Q, K, V values only for that token, and for all previous tokens, we retrieve existing values from the cache.

Step 7: Detokenization. Finally, the sequence of token IDs is converted back into text using the tokenizer's vocabulary.

output_text = tokenizer.decode(generated_tokens)

This entire process repeats for each generated token, so the key-value cache grows at each step. The decoding phase continues until the model generates a stop token or reaches the maximum context window length.

Inference Frameworks

Production LLM inference relies on specialized utility frameworks that automatically handle batching, memory management, and optimization.

vLLM implements PagedAttention for efficient key-value cache management and continuous batching for high throughput. Its throughput is 2-4 times higher than naive implementations on the same hardware.

NVIDIA's TensorRT-LLM provides highly optimized kernels specifically for NVIDIA GPUs, achieving near-theoretical peak performance. It utilizes technologies like on-the-fly batching and FP8 quantization support.

# Simplified vLLM usage example from vllm import LLM llm = LLM( model="meta-llama/Llama-2-7b-hf", tensor_parallel_size=2,  # Use 2 GPUs dtype="float16" ) outputs = llm.generate( prompts=["Explain transformers", "What is AI?"], sampling_params=SamplingParams(max_tokens=100) )

Hugging Face's Text Generation Inference (TGI) offers broad model support and features like continuous batching and token streaming. It also provides a production-ready HTTP API for deploying models.

Each framework involves different trade-offs between ease of use, performance, and model support. Choosing the right framework depends on your specific requirements, hardware, and model architecture.

Performance Metrics and Monitoring

To understand and monitor inference, several key metrics need to be tracked.

Time To First Token (TTFT) measures the latency during the pre-fill stage. This parameter directly impacts user experience—how long the user waits for the first output. Optimizing TTFT involves efficient prompt processing, often through prompt batching or speculative decoding techniques.

Inter-Token Latency (ITL) measures the time between the arrival of one token and the next during the decoding stage. Low ITL values result in a seamless and smooth user experience. This metric is heavily influenced by memory bandwidth and key-value cache efficiency.

Throughput, measured in tokens per second, quantifies the overall system capacity. High throughput allows serving more users concurrently. Various batching strategies significantly impact throughput.

# Performance monitoring start_time = time.now() first_token = model.generate_first_token(prompt) ttft = time.now() - start_time token_times = [] for i in range(num_tokens): token_start = time.now() token = model.generate_next_token() token_times.append(time.now() - token_start) itl = mean(token_times) throughput = num_tokens / sum(token_times)

GPU utilization indicates how efficiently the hardware is being used. Underutilization during decoding suggests memory bottlenecks. Monitoring tools like `nvidia-smi` provide real-time insights into GPU usage, memory consumption, and power draw.

Memory pressure, particularly the size of the key-value cache, affects the maximum context length and batch size. By monitoring cache memory, we prevent out-of-memory errors and guide quantization decisions.

Note

LLM inference converts text prompts into model responses. It involves tokenization, transformer layers with self-attention mechanisms, and autoregressive token generation.

In practice, the process occurs in two stages: first, the model fully processes your prompt in parallel, then it switches to sequential token generation. Consequently, the bottleneck shifts from computation to memory access.

Key optimizations include key-value caching to avoid redundant computations, batching for better GPU utilization, and quantization to reduce memory pressure.
