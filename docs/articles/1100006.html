A personal AI assistant can be convenient for working with text, but corporate infrastructure requires a different level of control. A user might accidentally pass a password or token to the model, and an agent might gain overly broad permissions and modify data where it shouldn't. At AGIMA, we are building a secure on-prem environment for AI agents: with permission checks, controlled access to internal systems, separation of language and infrastructure layers, and action auditing.

What We Are Building and What We Are Protecting

The main risk of corporate AI is not that the model makes formulation errors. It's more dangerous if an agent gains access to internal systems without clear boundaries. Therefore, before launching any scenario, we need to answer several questions:

  • Can the agent directly access Jira, 1C, financial systems, and other services?

  • How to distinguish data reading from a critical write action?

  • Where to store traces of the request, applied policies, and the result?

  • How to investigate an error and avoid creating dozens of unrelated bots?

We are building a managed corporate environment. The user interacts with the agent through a familiar interface, but the agent does not access internal systems directly. The request goes through permission checks, security policies, a Gateway for models, a Gateway for corporate tools, data sources, and auditing. The model is just one component in this path.

The entry point to the environment is a corporate chatbot in Mattermost. Technically, it's a Codex App Server connected to Mattermost via connectors. An employee chats with the bot as they would with a colleague, and everything else happens within the infrastructure layer.

We didn't arrive at this solution immediately. We tested various harnesses—wrappers that turn a model into an agent with tools—including OpenClaw and Hermes. Based on tests and research, pure Codex without additional wrappers proved more reliable: in conjunction with Mattermost, it has fewer bugs, and configuration is more flexible.

There's also an architectural reason. A messenger bot always knows who is messaging it, making it convenient to set up impersonation in conjunction with the MCP Gateway: the agent acts not on behalf of a general service account but on behalf of a specific employee and with their permissions.

One Secure Request Path

Let's walk through an anonymized scenario—from an employee's message to the result in the corporate system. To make it easier to read, here's a brief explanation of the layer roles:

  • The interface (Mattermost) receives the message and knows who sent it;

  • The agent on Codex App Server understands the task, selects a skill, and decides which tools are needed;

  • LLM Gateway handles access to language models, limits, and DLP checks;

  • MCP Gateway handles access to corporate systems on behalf of the user;

  • Vault stores secrets and credentials; access to it is via corporate SSO;

  • Auditing logs every step so the request path can be reconstructed.

Now let's see how the request passes through these layers.

  1. An employee messages the corporate AI agent in Mattermost. The messenger is just the entry point here; it can be replaced without rebuilding the rest of the environment.

  2. The connector passes the message, conversation context, and user ID to the Codex App Server. The interface itself doesn't decide which data can be read; its task is to deliver the request and not lose track of who it came from.

  3. The agent parses the request and determines which tools are needed. However, it does not directly access Jira, 1C, the financial system, or other services; all such calls go through the MCP Gateway—a single point of connection for corporate tools.

  4. MCP Gateway matches the request to the user's identity, role, and permissions and executes the call via impersonation—on behalf of the user and with their actual rights. If the employee doesn't have access to a system, the agent won't either.

  5. Credentials are stored in Vault, access to which is protected by corporate SSO. The Gateway retrieves the token for the required system from Vault at the moment of the call, so secrets do not end up in the model's context.

  6. Calls to the language model go through the LLM Gateway. DLP checks the request before sending it to the model and does not allow secrets and tokens to leave the permitted environment.

  7. The agent receives only the permitted context. Write operations are separated from the response and undergo separate control.

  8. The audit log (audit trail) records the initiator, applied policies, sources, and the result of the request.

Each layer is responsible for its boundary, so an error in one place doesn't grant the agent access to the entire infrastructure, and the log helps understand exactly where something went wrong. At the same time, we are describing an architectural principle: not every gateway is currently implemented equally in all scenarios.

Corporate Context Base and Two Gateways

It's not enough for an agent to connect to a set of documents. It needs to understand the company's processes and rules, which sources are relevant to the task, and who is responsible for their accuracy. This interconnected knowledge system can be described as a corporate ontology—a map of entities, processes, roles, and their relationships.

In practical terms, such a base helps link a request to the correct process step, data source, and skill. However, it does not replace access rights: the presence of an entity in the base does not yet mean that a specific employee can read or modify it.

This transforms the conversation from "let's write a prompt" into a more useful question: which process step are we improving, what data is needed, who is the owner, how to verify the result, and where should the human remain in the loop.

Boundaries of the Corporate Environment

On-prem does not mean it's enough to deploy the model within the perimeter. What matters are the permissions, secrets, and data accessible to the agent. Compliance with 152-FZ is part of the check, but it does not replace legal and information security reviews of the architecture.

Principles of the environment:

  • The agent acts only within the user's permissions;

  • The service account does not get unlimited access;

  • All calls to corporate systems go through the MCP Gateway and are executed on behalf of a specific user—with their access, not the bot's general permissions;

  • Each such call passes through a controlled layer and is logged for auditing;

  • Secrets are checked before being passed to the model;

  • Repeatable checks are implemented in code.

The architecture separates the interface, language layer, tool access, sources, policies, and auditing. Thus, the prompt does not become the sole security mechanism.

Two Gateways with Different Tasks

We use the term Gateway to refer to a controlled point of request passage. It's important not to confuse two different layers: the LLM Gateway works with language models, and the MCP Gateway works with AI agents' access to corporate systems.

LLM Gateway. This is a single point for routing requests to models. It's needed for managing keys, costs, and limits, centralized logging, replacing models without rewriting clients, and connecting general security policies and DLP.

MCP Gateway. This is a layer for secure access to tools and internal systems. It links the user's identity with permissions and executes requests on their behalf, without giving the language model direct access to tokens and services.

How it works for us. The MCP Gateway works in conjunction with the corporate chatbot and is connected to Vault—a secrets storage. Authorization in Vault is done via corporate SSO: the employee logs in with their account and provides credentials for the work systems the agent needs to interact with.

Everything else happens without model involvement. The Codex App Server passes the user's token to the MCP Gateway. Based on this, the Gateway retrieves the token for the required system—for example, ERP—from Vault and executes the request on behalf of the specific employee. The model doesn't see any secrets; it only receives the result of the call.

If we put it all together, the request path through both Gateways looks like this:

  1. Obtain the user ID and their permission context.

  2. Check the request and apply security restrictions before calling the model.

  3. Select the model, route, limits, and retry rules on the LLM Gateway side.

  4. Forward the request to the corporate system via MCP Gateway only after checking permissions.

  5. Do not place secrets and credentials in the language model's context.

  6. Separately control critical write operations. Human confirmation here is a target capability, not a function that is already working in all scenarios.

  7. Log the decision and result in the audit journal.

We don't want each bot to decide independently what to log, which rules to apply, and where to fetch data. The Gateway is needed as a common product layer, not just a technical adapter between a chat and a model.

DLP and Depersonalization

DLP and depersonalization solve different problems. DLP answers the question: can this content be passed further? Depersonalization answers the question: how to preserve the meaning of the request without revealing sensitive data to the model or an external service?

For example, an employee's name or contract number can be replaced with a placeholder. However, such a replacement by itself does not grant the agent the right to search for related data. Access rules must be applied first, and then only the permitted tool and context.

Another important boundary: depersonalization does not replace DLP, permission control, and auditing. It can reduce the amount of disclosed data but does not make any request automatically secure.

Here, we describe DLP at the architectural principle level: specific rules and component status are a matter for separate technical agreement.

A unified Gateway allows for versioning, testing, and centrally changing policies, rather than scattering them across bots and prompts.

Skills: Code for Rules, LLM for Meaning

A skill is not just a prompt. It's a reproducible scenario linked to a process, sources, permissions, and result verification. In it, the language model helps understand the request's meaning, and code performs predictable steps.

A skill should have:

  • Purpose and scope of application;

  • Associated process step;

  • Input data and allowed sources;

  • Security rules and required permissions;

  • Owner and version;

  • Quality criteria and verification method;

  • Execution mode: hint, draft, or action;

  • A clear way to cancel or decommission.

It's convenient to test such an architecture on three classes of tasks: financial operations, request routing, and searching corporate data. These are examples of task classes, not an assertion that each of them is already in industrial operation.

In the financial domain, a skill prepares a draft and checks mandatory fields but does not get write permissions for the final entry. In a sales scenario, it classifies the request and suggests a route, leaving ambiguous cases to a human. In data search, it responds only within the permitted context and logs sources.

The common criterion is one: input, action, control, and audit must be described separately. If the cost of an error is higher than saving a couple of minutes, rules, statuses, and validations should be implemented in code.

This is where the main engineering principle manifests: code is used by default, and LLM is connected where it's truly needed to understand natural language or broad context. Step-by-step operations, loops, API calls, checks, permissions, and system writes are more reliably performed by deterministic code.

Therefore, the minimal corporate AI skill card describes not only the prompt but also its operation:

Interface, Data, and Documentation

A separate portal for AI might be convenient, but employees already work in messengers and other familiar interfaces. Our entry point became Mattermost with a bot on Codex App Server, but the value here is in transmitting the request and context, not in the specific messenger.

The interface bot should not contain business logic. Its task is to receive a message, save the conversation context, send the event to the orchestrator, and display the result. Decisions about permissions, models, sources, and available actions are made by the platform.

Even a thin interface requires discipline: responses should go into the correct thread or context, commands and errors should be understandable, and refusals should explain which restriction was triggered.

Data: A Unified Company Context Base

Corporate data is distributed across work systems, documents, emails, and chats. Each source has its own owner, format, and access rules. Therefore, connecting all data directly to the model is not an option.

There's also a practical problem: data is difficult to extract from disparate systems and even harder to correlate. We solved it this way: workers fetch data from work systems and store it in a unified database with company context. Agents then work with this database: using SQL queries, they correlate data from different sources, obtain the necessary context, and perform analysis.

To ensure this database can be trusted, a managed pipeline is needed around it:

  • Systems are connected via controlled connectors and proxies;

  • Changes are synchronized considering owners and permissions;

  • Data undergoes preparation and quality checks before use in responses;

  • Access rights are linked to corporate identity;

  • For each assertion, the source and version can be traced;

  • Agent actions and infrastructure events are logged for auditing.

Such a layer is needed not only for document search. It allows explaining which sources were used, why the user had permission to see it, and what path the request took.

Pipeline Orchestrator: Agents That Work 24/7

In addition to agents that respond to employees in chat, the platform has a pipeline orchestrator—background agents that work around the clock. They are designed on a deterministic principle: most actions are performed algorithmically. Data retrieval, mapping, and processing are done by regular code, and LLM is called selectively—where algorithms fail.

The orchestrator can call the model in two ways:

  • Via OpenAI Agents SDK—when complex actions are needed: multiple steps, tool calls, intermediate decisions;

  • Via a regular API call with a prompt—when a single model call is sufficient.

This keeps the non-deterministic part small, and the pipeline's behavior predictable and verifiable. This is the same principle as in skills: code by default, LLM—where it's indispensable.

Documentation and Versions as Part of the System

Documentation should not be an add-on to the platform but part of its lifecycle.

Descriptions of processes, decisions, sources, and skills must have owners, versions, and a verification procedure. This way, the team understands exactly what the agent decided, on what rules it was based, and which executable scenario needs to be updated when a process changes.

For skills, a clear path is needed: description → review → tests → publication → usage monitoring → development or decommissioning. Personal automation should not remain a personal file forever without an owner and audit.

Auditing: Reproducibility and Control

An AI platform without auditing turns into a black box. There's an answer, but it's impossible to explain why it appeared and who authorized the action.

A minimal audit log should show:

  • Who initiated the request and through which interface;

  • Which skill, version, and route were involved;

  • Whether the request was allowed, masked, blocked, or sent for manual review;

  • What end-to-end trace links the request, agent activity, and infrastructure events.

The log itself also requires storage rules. Raw DLP matches can aid investigation but may simultaneously contain sensitive data. The format and retention period must be chosen in conjunction with development, information security, and legal departments.

Auditing is not for employee surveillance but for reproducibility: to understand what request came in, what restrictions were triggered, and why the system produced that specific result.

The more actions an agent can perform, the more important it is to predefine which events are mandatory for the log, who has access to it, and how incidents are investigated.

Conclusion: What This Environment Provides and Where Its Boundary Lies

Such a platform has five pillars: user rights, a knowledge base from processes, versioned skills, a replaceable interface, and control outside of LLM. This reduces dependence on a specific model but does not eliminate the need to test each integration.

A Fair Security Boundary

In such an environment, the Gateway protects tokens and limits the agent's access to corporate infrastructure, but it cannot prevent an employee from manually copying data to a personal AI service.

This requires measures at the device and work environment level: corporate devices and MDM, blocking external AI services, secure remote desktops, and anomaly detection signals.

No single component provides absolute security—only a combination of measures.

The final principle: no matter what the user writes to the model, it physically should not have access to places the employee themselves is not permitted to access. This is verified through permissions, infrastructure gates, and auditing.
