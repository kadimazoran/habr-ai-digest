There is Qwen 3.8 27B, fine-tuned (SFT + LoRA) on a corpus about the 1C:Enterprise platform – the model is available on Hugging Face. The model writes code well in the built-in language, but regularly makes mistakes in the 1C query language: it confuses virtual tables, puts parameters in the wrong place, and mixes in SQL constructs that don't exist in 1C.

Attempts to use the classic approach of further fine-tuning the model by collecting new datasets for the 1C query language yield no results. The accuracy gain is less than 1%. And it's a long and painful process.

During the struggles with Qwen models and analyzing model usage telemetry, a hypothesis emerged: the model's knowledge of SQL constructs interferes because the lexemes are similar (SELECT, WITH, JOIN, etc.).

This leads to the question: can we find specific neurons that "pull" the model towards the wrong answer and carefully suppress only them?

The article presents a complete pipeline I've named NERVE (Neuron Editing, Reweighted & Val-Evaluated):

  • we build a heatmap of neuron activation on "correct / incorrect answer" pairs;

  • we calculate gradient attribution — a prediction of how quality will change if a neuron is suppressed;

  • we greedily select neurons with validation on a hold-out set and a control half;

  • we accumulate confirmed edits into a set and export the edited model to GGUF.

All examples are on the 1c_lang_query dataset (1C queries). The code consists of fragments from the project, PyTorch + Hugging Face Transformers + PEFT.

1. What is a "neuron" in a transformer

Each Qwen layer contains an attention block and an MLP block. The MLP is structured using the SwiGLU scheme:

Here x is the hidden state of the token (dimensionality hidden_size), h is an intermediate vector (for Qwen 3.8 27B — 17,408 components), y is the MLP's contribution to the residual stream. We will call a component h_i a neuron, along with the corresponding column of the W_down[:, i] matrix: it is this column that determines what the neuron writes to the residual stream when activated.

From this, a simple and important fact follows: multiplying the column W_down[:, i] by a coefficient m is exactly the same as multiplying the neuron's activation h_i by m for every token. m = 0 turns off the neuron, m = 0.5 halves its activation, m = 1.5 doubles it. The edit does not change the architecture, survives quantization, and export to GGUF.

Search scale: 64 layers × 17,408 neurons = 1,114,112 candidates. Blindly iterating is pointless; a map is needed.

2. Data: "correct / incorrect" pairs

For the map, we need not just examples, but preference pairs — the same format as for DPO: one prompt, a chosen answer (correct 1C query) and a rejected answer (query with a typical error). In 1c_lang_query, there are about two thousand such pairs in the train set and a separate validation set.

The key idea: in a chosen and rejected pair, they usually match by 90–95%. If we average activations across the entire response, the common part will "wash out" the signal. Therefore, we will only compare differing tokens. We align the two token sequences using difflib.SequenceMatcher and mark everything that doesn't fall into common blocks:

def diff_token_mask(chosen_ids, rejected_ids): # Marks response tokens that are not in common blocks with the other side. import difflib chosen_mask = [False] * len(chosen_ids) rejected_mask = [False] * len(rejected_ids) matcher = difflib.SequenceMatcher(None, chosen_ids, rejected_ids, autojunk=False) for tag, c_start, c_end, r_start, r_end in matcher.get_opcodes(): if tag == "equal": continue for index in range(c_start, c_end): chosen_mask[index] = True for index in range(r_start, r_end): rejected_mask[index] = True # The side without differences gets a mask for the entire response if not any(chosen_mask): chosen_mask = [True] * len(chosen_ids) if not any(rejected_mask): rejected_mask = [True] * len(rejected_ids) return chosen_mask, rejected_mask

An important detail I stumbled upon: initially, the map was built based on differing tokens, and the quality check was calculated on the entire response. The edit effect was diluted by about 25 times, and honest improvements drowned in noise. Now, both the map and the check use the same diff mask.

3. Activation Heatmap

3.1. Capturing Activations with Hooks

The model is loaded in BF16, the LoRA adapter is merged into the weights (merge_and_unload), and a forward_pre_hook is attached to the input of each mlp.down_proj. The input to down_proj is the vector h:

modules = [(name, m) for name, m in merged.named_modules() if name.endswith("mlp.down_proj")] def make_hook(name): def hook(module, args): hidden = args[0] # [batch, seq, 17408] flat = hidden[0] if hidden.ndim == 3 else hidden rows = torch.tensor(current_mask, device=flat.device) selected = flat[rows].detach().float().abs() sums[name] = selected.sum(dim=0) # sum of |h| over diff tokens counts[name] = int(selected.shape[0]) return hook handles = [m.register_forward_pre_hook(make_hook(n)) for n, m in modules]

3.2. Statistics per Pair: Not Just the Average

One pair proves nothing. For all n pairs, we accumulate element-wise the sum, the sum of squares, and the count of pairs with a positive delta — this is enough to get the average, t-statistic, and sign consistency without storing all values:

def pair_statistics(sums, sumsq, positive, count): # Average, t-statistic, and proportion of pairs with the sign of the average. n = int(count) means, t_values, agreement = [], [], [] for i in range(len(sums)): mean = sums[i] / n if n > 1: variance = max(0.0, (sumsq[i] - n * mean * mean) / (n - 1)) std = math.sqrt(variance) t_value = mean / (std / math.sqrt(n)) if std > 0 else 0.0 else: t_value = 0.0 share_positive = positive[i] / n means.append(mean) t_values.append(t_value) agreement.append(share_positive if mean >= 0 else 1.0 - share_positive) return {"mean": means, "t": t_values, "agreement": agreement}

Why rank by |t| and not by |μ|: some neurons have a huge average delta, caused by two or three anomalous pairs. The t-statistic penalizes such variance. With a small number of pairs (less than 8), t is unreliable, and we fall back to ranking by |μ|.

3.3. From a Million Numbers to an Image

Each layer is a vector of 17,408 average deltas. For the heatmap, we create 128 bins by neuron index and take the average within each bin. This results in a 64 × 128 matrix: layers on the vertical axis, bins on the horizontal axis, color representing the sign and magnitude of the delta. For each layer, the top-64 neurons by |t| with delta, t, and agreement are saved separately — these are later selected as candidates for editing.

def bin_values(values, bin_count=128): # Average values across bins of equal width along the neuron index. totals = [0.0] * bin_count sizes = [0] * bin_count width = len(values) for index, value in enumerate(values): bucket = min(bin_count - 1, index * bin_count // width) totals[bucket] += float(value) sizes[bucket] += 1 return [totals[b] / sizes[b] if sizes[b] else 0.0 for b in range(bin_count)]

The first thing that caught my eye on the 1c_lang_query map: activation on incorrect answers exists in almost every layer. The model is literally "pulling out" SQL constructs from the entire depth of the network. This leads to a practical conclusion that determined the entire subsequent approach: it's necessary not only to strengthen "good" neurons but also to suppress incorrect ones!

4. Attribution: Which Neuron Actually Affects the Answer

Activation shows correlation, but not causation: a neuron might light up brightly on rejected and barely affect token choice. We need an estimate of contribution to quality. As the target metric, we take the margin — how much the model prefers the correct answer over the incorrect one on differing tokens:

This means a neuron with attr < 0 reduces the margin with its activity — this is the "erroneous" neuron. Suppressing it (m < 1) is expected to increase the margin. For a set of edits, the prediction simply sums up: Δmargin ≈ Σ (mᵢ − 1)·attrᵢ.

4.1. How to Get the Gradient for the down_proj Input

The trick is that the intermediate h is not a leaf in the computation graph, and autograd.grad cannot be directly computed for it after the forward pass. In the same pre-hook, we replace the input with a leaf:

def hook(module, args): hidden = args[0] if not attribution_active: return None leaf = hidden.detach().requires_grad_(True) # new leaf in the graph leaves[name] = leaf return (leaf,) + tuple(args[1:]) # down_proj now computes from the leaf def masked_mean_logprob(logits, input_ids, rows): positions = [i for i, flag in enumerate(rows) if flag and i > 0] if not positions: return None target = torch.tensor(positions, device=logits.device) picked = logits[0, target - 1].float() log_probs = torch.log_softmax(picked, dim=-1) tokens = input_ids[0, target].unsqueeze(-1) return log_probs.gather(-1, tokens).squeeze(-1).mean() with torch.enable_grad(): out = model(input_ids=ids, attention_mask=mask, use_cache=False) objective = masked_mean_logprob(out.logits, ids, diff_rows) names = list(leaves) grads = torch.autograd.grad(objective * sign, [leaves[n] for n in names], allow_unused=True) attr = {} for name, grad in zip(names, grads): if grad is None: continue product = leaves[name].detach().float() * grad.float() attr[name] = product.reshape(-1, product.shape[-1]).sum(dim=0) # [17408]

For chosen, we use sign = +1, for rejected — sign = −1, and sum them up: this gives exactly the gradient of the margin. The masked mean log p function considers the shift: token j is predicted by the logits of position j − 1:

def masked_mean_logprob(logits, input_ids, rows): # Calculates the mean log probability for masked tokens. positions = [i for i, flag in enumerate(rows) if flag and i > 0] if not positions: return None target = torch.tensor(positions, device=logits.device) picked = logits[0, target - 1].float() log_probs = torch.log_softmax(picked, dim=-1) tokens = input_ids[0, target].unsqueeze(-1) return log_probs.gather(-1, tokens).squeeze(-1).mean()

Attribution is computationally expensive (backward pass on a 27B model), so we build the map with attribution on a subsample: for 1c_lang_query — 512 pairs with a length up to 2048 tokens. The map without attribution is built on all 2010 pairs. For attribution, we also calculate the mean and t-statistic, and the top-64 neurons by |attr| are saved per layer.

5. How to Verify an Edit

Attribution is only a prediction. The decision for each edit is made based on the actual result on the hold-out validation set of the same dataset used to build the map. For each pair, we calculate:

  • nll_chosen — the average negative log probability across the entire correct response. Guard: the edit should not degrade the generation of the correct text overall;

  • margin — on differing tokens, as in attribution;

  • accuracy — the proportion of pairs with margin > 0.

To ensure measurements are comparable between runs, the validation pairs are sorted by query key (query_fingerprint, or sha1 of the last user message if it's missing). We can also enable a guard — using a few validation pairs from other datasets to prevent the edit from breaking adjacent skills. The guard is off by default: the check is performed strictly on the map's dataset.

The edit itself is applied "live" during verification to the loaded BF16 model and is always reverted:

def scale_columns(edits): # Multiplies down_proj columns by edit["scale"] and returns original values. saved = [] with torch.no_grad(): for edit in edits: weight = modules[edit["name"]].weight # [hidden, 17408] index = int(edit["index"]) saved.append((weight, index, weight[:, index].detach().clone())) weight[:, index].mul_(float(edit["scale"])) return saved def restore_columns(saved): with torch.no_grad(): for weight, index, column in saved: weight[:, index].copy_(column)

6. Multiplier Modes

How to turn selected neurons into specific coefficients m? There are four modes, with a strength parameter s ∈ [0, 1]:

1 + s for Δ > 0, 1 − s for Δ < 0

all selected, by the sign of the attribution

After experimenting with 1c_lang_query, the default mode became suppress: strengthening "good" neurons more often broke nll, while suppressing erroneous ones led to a stable increase in margin.

def signed_scales(edits, mode, value): result = [] for edit in edits: if mode == "suppress": source = edit.get("attr") if edit.get("attr") is not None else edit.get("delta") if source is None or source >= 0: continue # not erroneous — don't touch scale = 1.0 - value elif mode == "manual": scale = value else: source = edit["delta"] if mode == "sign" else edit["attr"] scale = 1.0 + value if source > 0 else 1.0 - value if source < 0 else 1.0 result.append({**edit, "scale": max(0.0, min(2.0, scale))}) return result

7. Greedy Selection with a Control Half

Taking the top-64 neurons immediately and suppressing them all is a bad idea: edits interact, and the sum of linear predictions no longer works. Therefore, the selection is greedy, one candidate at a time.

7.1. Splitting the Validation Set

The validation pairs of the dataset are split into two halves by a deterministic hash function of the query key: selection (on which decisions are made) and control (on which the result is checked). The same pair always goes into the same half.

def split_half(key: str) -> bool: # True — pair is in the selection half, False — in the control half. return int(hashlib.sha1(key.encode("utf-8")).hexdigest()[-1], 16) % 2 == 0

7.2. Candidates and Acceptance Rule

Candidates are the top-N neurons by |attr| across all layers of the map (in suppress mode — only those with attr < 0), excluding those already accepted. Then, for each candidate: apply the edit on top of the already accepted ones, measure on the selection half, accept or reject. Acceptance rule:

By default, ε = 0.002 (per token), τ_nll = 2%, guard tolerance τ_guard = 1% for nll and margin of each guard expert. Note: margin is compared to the current set (each accepted neuron must add value), while nll is compared to the baseline (drops should not accumulate).

baseline = score(select, guard) # without edits current = baseline accepted, kept = [], [] for edit in signed_scales(candidates, mode, s): saved = scale_columns([edit]) summary = score(select, guard) ok, reason = greedy_accept(baseline, current, summary, eps, nll_tol, guard_tol) if ok: kept.extend(saved) # edit remains in weights current = summary accepted.append(edit) else: restore_columns(saved) final_control = score(control) # final result checked on the second half confirmed = accepted and passes(baseline_control, final_control) restore_columns(reversed(kept))

A set is considered confirmed only if the margin increased on the control half and nll did not decrease beyond the tolerance. This is the main protection against overfitting to the validation set: greedy selection inevitably adapts to the noise of the set on which it makes decisions.

8. Hybrid Mode: Accumulating Edits Between Runs

One run of greedy selection involves several dozen candidates. We want to run the selection repeatedly: with a different mode, with different strength s, on subsequent candidates. For this, each map has a set of edits — a JSON file next to the map:

  • a new run starts on top of the set: the set's edits are applied to the weights before measuring the baseline;

  • neurons from the set are excluded from candidates;

  • accepted neurons are appended to the set only if the run is confirmed on the control set;

  • a separate check "entire set vs. baseline" shows the cumulative effect.

10. Results on 1c_lang_query

Example: How the Model Makes Mistakes Before Editing

One of the tasks from public benchmarks for 1C. Prompt:

It is necessary to output all dates (by day) from a given interval [&StartDate; &EndDate] inclusively, ordered by ascending, using a single query in the 1C query language. The interval is arbitrary (can be several years) and is passed as parameters. The date series is built using query tools, without loops or result processing in the module, without calendar tables from the configuration. In addition to dates, there should also be columns with months, days of the week, and the standard weekend (Saturday and Sunday) calculated.

Model's response before editing:

Solution: recursive query (recursive CTE) in 1C:Enterprise 8.3. In the 1C query language (starting from 8.3.17), there is the construct RECURSIVE OUTER JOIN, which allows "unrolling" a sequence directly in the query — without loops, without calendar tables, and without metadata objects.

Query.Text = "RECURSIVE OUTER JOIN Calendar | | SELECT |    Base.Date AS Date |  INTO Calendar | | FROM |    ( |        SELECT |            &StartDate AS Date |    ) AS Base | | JOIN OUTER Calendar | | SELECT |    Base.Date + 1 AS Date | FROM |    Calendar AS Base |    JOIN OUTER Calendar |        ON Base.Date + 1 <= &EndDate | | SELECT |    Calendar.Date AS Date, |    Month(Calendar.Date) AS Month, |    MonthName(Calendar.Date) AS MonthName, |    DayOfWeek(Calendar.Date) AS DayOfWeek, |    DayOfWeekName(Calendar.Date) AS DayOfWeekName, |    (DayOfWeek(Calendar.Date) >= 6) AS IsWeekend |FROM |    Calendar |ORDER BY |    Date";

The response looks confident, but almost every key line in it is a hallucination:

  • Recursive CTE is borrowed from SQL. The 1C query language does not have recursive queries, and "RECURSIVE OUTER JOIN" and the reference to version 8.3.17 are fabricated. This is exactly the transfer of SQL constructs that is visible on the heatmap in all layers.

  • Non-existent join. 1C does not have "OUTER JOIN" — it has LEFT, RIGHT, FULL, and INNER JOIN, and combining results is done using UNION (ALL).

  • Date arithmetic. In the query language, you cannot add a number to a date: to shift by one day, you need the function ADDDATE(&StartDate, DAY, 1). In the built-in language, Date + 1 means plus one second.

  • Fabricated functions. MONTH() and DAYOFWEEK() exist, but MonthName() and DayOfWeekName() do not; names are obtained through CASE...WHEN or FORMAT on the presentation side.

  • Broken package structure. INTO is placed in the middle of the construct, the temporary table refers to itself, and the package queries are not separated by a semicolon — such text would not even pass syntax control.

The correct solution is built without recursion: a temporary table of digits 0–9, its Cartesian product with itself gives a sequence of numbers N, and dates are obtained as ADDDATE(&StartDate, DAY, N) with filtering by &EndDate.

The Same Prompt After NERVE Editing

SELECT |    &StartDate + (D1.Digit * 1000 + D2.Digit * 100 + D3.Digit * 10 + D4.Digit) AS Date, |    MONTH(&StartDate + (D1.Digit * 1000 + D2.Digit * 100 + D3.Digit * 10 + D4.Digit)) AS Month, |    DAYOFWEEK(&StartDate + (D1.Digit * 1000 + D2.Digit * 100 + D3.Digit * 10 + D4.Digit)) AS DayOfWeek, |    CASE |        WHEN DAYOFWEEK(&StartDate + (D1.Digit * 1000 + D2.Digit * 100 + D3.Digit * 10 + D4.Digit)) IN (6, 7) |            THEN TRUE |        ELSE FALSE |    END AS IsWeekend |FROM |    (SELECT 0 AS Digit UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 |    UNION ALL SELECT 4 UNION ALL SELECT 5 UNION ALL SELECT 6 |    UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) AS D1, |    (SELECT 0 AS Digit UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 |    UNION ALL SELECT 4 UNION ALL SELECT 5 UNION ALL SELECT 6 |    UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) AS D2, |    (SELECT 0 AS Digit UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 |    UNION ALL SELECT 4 UNION ALL SELECT 5 UNION ALL SELECT 6 |    UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) AS D3, |    (SELECT 0 AS Digit UNION ALL SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 |    UNION ALL SELECT 4 UNION ALL SELECT 5 UNION ALL SELECT 6 |    UNION ALL SELECT 7 UNION ALL SELECT 8 UNION ALL SELECT 9) AS D4 |WHERE |    D1.Digit * 1000 + D2.Digit * 100 + D3.Digit * 10 + D4.Digit <= DATE_DIFF(&StartDate, &EndDate, DAY) |ORDER BY |    Date

The difference is qualitative. The model stopped inventing SQL constructs and returned to the idiom that 1C developers use to solve this problem in practice:

  • No recursion or fabricated syntax. Instead of "recursive CTE," it uses the Cartesian product of four tables of digits 0–9, i.e., a sequence of numbers 0…9999 (up to ~27 years — "several years" with a margin).

  • Only real query language functions. DATE_DIFF(..., DAY) for the interval boundary, MONTH() and DAYOFWEEK() for columns, CASE...WHEN...IN (6, 7) for weekends — all exist and are used correctly.

  • Correct structure. One query, correct nested UNION ALLs, WHERE condition, ORDER BY date. The interval is inclusive: when N = DATE_DIFF, &EndDate is also output.

One error still remains: &StartDate + N. Date shifting in the query language is done by the function ADDDATE(&StartDate, DAY, N); adding a number to a date is a carry-over from the built-in language (where +1 means a second, not a day). For a fully working query, it's enough to replace this expression in four places. It's indicative that the error shifted from the level of "incorrect language and fabricated solution architecture" to the level of "one incorrect function" — exactly what is expected from a targeted edit, not from retraining.

This example more honestly shows what the edit changes and what it doesn't.

What improved — the approach. The model before editing simply "flattened" the subquery into a chain of joins: the result is the same, but the temporary table DefaultValuesForUser is gone (and it might be used later in the package), and instead of FIRST 1, the join duplicates rows for each user group. The edited model proposed a classic 1C optimization: calculate user groups once into a temporary table, index it, and replace the correlated subquery with a join — while preserving the original package contract.

What remained problematic — accuracy. The edited model's response has two errors:

  • Incorrect join field — critical. The original condition AccessGroupsUsers.User = UserGroupMemberships.GroupMembership turned into AccessGroupsUsers.Link = …GroupMembership: the access group is compared with the user group, the query will return an empty result.

  • Non-existent index syntax. "CREATE INDEX ... ON Table(Field)" is SQL. In 1C, a temporary table index is specified in the query itself: INTO UserAccessGroups ... INDEX UserAccessGroups(AccessGroup).

Conclusion: the edit based on the 1c_lang_query map shifted the model towards the correct optimization idiom but did not teach it to accurately transfer join fields, and one SQL reflex (CREATE INDEX) survived suppression. This is expected: targeted editing removes specific "erroneous" directions in activations but does not add knowledge that the model lacks. Such cases are material for the next iteration: a new map based on pairs with errors in joins or for DPO.

11. Pitfalls and Limitations

  • One metric for map and verification. Margin across the entire response versus margin on diff tokens — a difference of tens of times. Any discrepancy in the mask between the map and the verification makes the results incomparable.

  • Linear prediction works only for small edits. For m = 0 and for large sets, the fact significantly diverges from Σ(m−1)·attr — therefore, the decision is made only based on measurement.

  • Overfitting to validation set. Greedy selection adapts to the chosen set. The control half is mandatory; I do not save a set without confirmation on the control half.

  • Adjacent skills. Without a guard, an edit can corrupt a related dataset. If experts overlap in vocabulary (1C queries in natural language and in query language), the guard should be enabled.

  • Cost. A map with attribution on 512 pairs and greedy selection on dozens of candidates — this is hours of GPU time on a 27B model. But it's still orders of magnitude cheaper than a new DPO cycle.

  • Truncation of long pairs. Pairs longer than max_length are truncated from the end; if the difference falls outside the boundary, the pair is excluded from the map.

Conclusions

Fine-tuned LLMs are not black boxes. A couple of simple tools — hooks on the down_proj input, statistics on pairs, and gradient attribution — provide a map showing which neurons are pulling the model towards errors. And a strict selection procedure with a hold-out set and a control half turns this map into a concrete, reproducible weight edit that can be exported to GGUF without changes.

The main practical lesson from 1c_lang_query: errors are "spread" throughout the network's depth, and it is more effective not only to strengthen correct neurons but also to suppress erroneous neurons.

Editing just 15 neurons gave a significant boost in understanding the 1C query language!
