Today we're building our own mobile phone from readily available materials bought on various marketplaces, with the help of artificial intelligence. We'll clarify upfront that this isn't about creating another iPhone killer or ultra-budget internet access. A simple calling phone is cheaper and easier to buy at the nearest mobile carrier store.

Although I can write code to some extent myself, we'll be actively using AI here. Primarily, to save time and avoid delving into the protocols for communicating with the radio module – information that will likely never be needed again.

I'll note that I only used the free versions of DeepSeek, Gemini, and ChatGPT in their limited free modes. There was no specific system for when or to whom to ask questions. I usually switched between them when one started to lag.

And for the cover image of this article, I tried generating it with the Artlist neural network for the first time.

So, to connect to a mobile network, you primarily need a radio module. I don't think I need to explain that soldering one from discrete components is an endeavor with no chance of successful implementation within a reasonable timeframe and budget.

It's easier to buy a ready-made radio module. I chose this one:

The SIM800C radio module itself is the green board under the shielding cover. The image shows the HW-537 implementation. The radio module is already soldered to a board with breakout pins and matching components.

Overall, it has everything needed to connect to the network and for "talking." But it lacks anything to control this module.

The module is controlled via AT commands through the UART port. It also responds to control scheme requests through this port. The RXD/TXD pins are visible in the top row. The SIM card is inserted on the other side of the module, not visible in the picture.

Logically, a microcontroller needs to be added to the project. I decided to use something from the STM32 family this time and simply asked Gemini which option would be best. It suggested the STM32L051C8T6.

The selection criteria here are not very complex. Minimal but sufficient functionality. Low power consumption. Low cost.

And the phone also needs some kind of screen for obvious reasons. I didn't try to invent anything special here. I took the familiar OLED SSD1306 with a resolution of 128x32:

The image is from the internet, but relevant. Apparently, I'm not the first to come up with this.

Next is power. For the first stage, I decided to use a simple USB connector to supply 5 volts and power the radio module and a 1117 regulator to get 3.3 volts for the STM32.

I started by asking DeepSeek a simple question: "*Tell me how to connect SIM800 HW537 to STM32L051*". In response, I received a table of pin connections for the two modules. Then I asked: "*The design includes a small LCD screen connected via I2C. I need to display a welcome message on power-up and the result of GSM initialization. The screen is 128x32.*" I also received a table of connections for this.

DeepSeek provided minimal code to get started with all of this. Just to power up the circuit and see that it's alive.

I connected all the mentioned components and discrete small parts for power on a breadboard. The circuit powered up, but the radio module didn't start properly. It consistently rebooted.

All three AIs assured me that the problem was most likely with the power supply. It's no secret, and it's written many places, that the SIM800C (and similar modules) can have peak current consumptions of up to 2 Amps when communicating with the base station. I hoped the power capacitors would handle this, but they didn't. I had to urgently add a lithium battery to the circuit, which can provide such current pulses.

I took a 75 mAh battery from a toy from FixPrice – a flying helicopter-like ball. I charged it directly in the ball and soldered the charged battery to my circuit. Just for testing.

Now everything started working fine. At this stage, my phone looked like this:

Let me explain a bit. At the top is a three-pin connector for flashing the STM32. In the center is a button to disconnect the battery.

The GSM antenna is actually an antenna from a Wi-Fi module, but they are essentially the same. Later, a proper antenna arrived, but there was no difference between them.

The functionality is quite primitive. Just answering calls or dialing a number. No call history or any other basic conveniences. But all these bells and whistles are just code extensions for the STM32. This can be worked on for a very long time, depending on the mood. Therefore, I decided to finish with the "material world." Make a case and install a proper battery.

These charging modules have a tiny SMD resistor that needs to be changed according to the optimal charging current for the battery. But I didn't do the calculations; I just asked Gemini, and it recommended 18 kOhm for 320 mAh. The charging current turned out to be about 180 mA.

The design includes all the connections to implement a sleep mode and extend battery life. However, there is no support for this mode in the code.

Without it, the phone operates for about six hours on a full charge. After that, the radio module turns off, and the microcontroller with the screen continues to work for many times longer. The screen displays that there is no connection with the radio module. More precisely, that there are no responses over UART.

Gemini estimated that implementing a standby mode would extend the device's operation to about nine days if not used for calls. And if a full 2000 mAh battery were installed, the phone should stay connected for about two months (without calls). It turned out to be a decent device for those who like to get lost in the woods.

SMS messages.

Although I wrote above that I decided not to significantly enhance the functionality, upon reflection, I decided that SMS messages wouldn't be superfluous.

Strangely enough, receiving SMS turned out to be not the easiest task. I thought that sending SMS with such a crude keyboard would be unnecessary – it would be extremely labor-intensive to type, but receiving SMS is quite feasible.

Next, as usual, there were questions for the AI, but none could offer working code. I wasn't even sure if SMS messages were even going to this SIM card. I had to figure it out and write the code myself. The sequence of command exchanges and responses in UART is too convoluted. As a result, none of the budget AIs could handle it without breaking what was already working.

SMS messages appeared. To read an incoming SMS, you need to "call 0." That is, press 0 and then the call button. The phone then displays the last SMS. If there is a new SMS, a "envelope" symbol will appear on the screen. If you close the SMS with an 'X', the envelope will disappear; if you use any other button, the envelope will remain.

When all this was working, I went back to the AI and asked it to add Cyrillic support. If anyone doesn't know, non-Latin characters are encoded with two bytes, so Russian SMS messages are twice as short.

Here, ChatGPT, together with DeepSeek, wrote the necessary functions and fonts. SMS messages could now be read in Russian.

You can see how many test attempts there were. At least somewhere my SMS allowance from my operator's plan came in handy.

The sound turned out to be very decent. It's loud and clear in both directions. A solid four, I'd rate it. If anyone attempts something similar with a soldering iron, be sure to install an SMD resistor of 0.1 uF directly between the microphone contact pads. Otherwise, the radio module will drown out all sound with its interference.
