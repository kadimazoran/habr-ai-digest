Completion gate for local models: how to separate a finished response from quality assessment

In one of the comparisons of local models, I got a result that is pleasant to show in a table: three routes completed ten out of ten scenarios. The median for the fast route was 28.9 seconds. The heavier one took 99.1 seconds, and the mixed one took 71.0.

If you look only at the "accepted" column, the routes are equal. If you add time, the fast one looks like the winner. If you consider result repairs, the picture changes again: the routes required three, two, and one correction, respectively.

But even after that, it's too early to choose a model. The table answers the question of whether the combination of the model and surrounding code passed the current set of checks. It does not yet show how good the created document is and whether a human can use it in their work.

This error did not arise in the model. I misidentified the unit of measurement. One metric included the finished response, valid JSON, the presence of mandatory documents, passing automated checks, and human content evaluation. This is how a high percentage appeared, from which it was impossible to understand the reason for success or failure.

To break down the result, I added a separate completion gate. Its task is more modest than quality assessment: to determine if a whole artifact exists that can be evaluated at all.

In the article, I will discuss the gate itself, the results of re-checking, and the limitations of the experiment. The route names here denote only fixed experimental configurations. This is not a model ranking or a recommendation for infrastructure selection.

What exactly was checked

Instead of a free-form response, the model was supposed to return a single JSON object with four Markdown documents:

{
  "artifacts": {
    "source_map": "# Source Map\n...",
    "system_context": "# System Context\n...",
    "review_findings": "# Review Findings\n...",
    "task_pack": "# Task Pack\n..."
  }
}

The documents described sources, system context, identified contradictions, and tasks for implementation. Not the section titles themselves were important, but the verifiable properties of the result:

  • the assertion must lead to a source;

  • an unknown field cannot be supplemented by guesswork;

  • conflicting versions of a requirement must remain a conflict;

  • an implementation task must refer to a solution and acceptance criteria;

  • the result must contain the documents themselves, not a promise to create them later.

This format allows for automated checks. It also creates a dangerous illusion: valid JSON is easily mistaken for a finished result.

For example, the following object passes superficial type checking:

{
  "artifacts": {
    "source_map": "results/source-map.md",
    "system_context": "results/context.md",
    "review_findings": "results/findings.md",
    "task_pack": "results/tasks.md"
  }
}

All four values are of string type. However, the user received paths to future files, not documents.

Another response looks more informative:

{
  "artifacts": {
    "source_map": "# Source Map\nSources are listed in the project",
    "system_context": "# System Context\nThe system is described in the documentation",
    "review_findings": "# Review Findings\nNo contradictions found",
    "task_pack": "# Task Pack\nRequirements need to be implemented"
  }
}

The schema is satisfied again: keys exist, strings are not empty, headers are in place. For the user, such a package is useless. It consists of placeholders that mimic the required form.

There is also a less accurate class of errors. The model manages to return three documents and half of the fourth, after which the runtime stops generation due to length, memory, or timeout limits. Such a response cannot be evaluated for completeness of requirements. The evaluation object was not created entirely.

Why a single pass rate is not enough

The phrase pass rate = 80% says nothing about the denominator. The eight successful cases could include responses that passed the schema on the first try, responses after format repair, completed documents with substantive errors, and results rejected by a human.

These events require different fixes. A timeout leads to runtime or response volume adjustments. Corrupted JSON requires contract and parser fixes. A missed requirement requires prompt, context, or model capability improvements. An incorrect acceptance criterion requires re-evaluation of the test itself.

A single percentage erases this diagnosis. Therefore, I divided the execution into sequential stages:

started
  → endpoint_completed | timeout | crash | out_of_memory
  → output_present
  → parseable
  → schema_valid_first_pass
      ↘ deterministic_repair → schema_valid_after_repair
  → artifacts_present
  → artifacts_non_placeholder
  → quality_eligible
  → quality_passed | quality_failed
  → accepted_by_human | rejected_by_human

The transitions up to quality_eligible describe the completeness of the result. After this boundary, content evaluation begins. The final decision is made by the human responsible for using the document.

What the completion gate does

The gate does not evaluate style, completeness of analysis, or correctness of the solution. It checks the prerequisites for evaluation.

In my case, the minimum set looked like this:

1. The process completed without timeout/crash/OOM.
2. The raw response was saved.
3. The parser can parse the response as JSON.
4. The object conforms to the schema version.
5. All four artifacts are present.
6. Each artifact contains text, not a path or placeholder.
7. Format repair, if any, is recorded separately.

Checking for placeholders requires caution. Banning a few phrases is not enough: the model will find another way to return a formally filled field. I used a combination of simple indicators:

  • minimum content length after removing the header;

  • presence of mandatory structural elements for a specific document;

  • banning values that look like file paths;

  • searching for known promises like "will be added later";

  • checking links between documents;

  • saving the reason for rejection instead of a general false.

This is not a foolproof protection against all meaningless responses. The gate only filters out cases that are definitely not suitable for quality assessment. The more semantic rules are included in the completion gate, the higher the risk of inadvertently turning it into another quality judge.

Re-checking changed the denominator

In the historical dataset, one scenario had 21 records. After adding the gate, I re-ran them. Only four records contained complete results suitable for further evaluation. The remaining 17 were incomplete or corrupted.

This does not mean that the model's quality has improved or worsened. I did not re-run the model or recalculate substantive evaluations. The composition of objects allowed to participate in such an evaluation has changed.

Before the gate, a truncated JSON could receive a zero score for requirement analysis. After the gate, it receives an incomplete status. This is more accurate: the response proves nothing about substantive quality because generation did not complete.

The separation also helps in the other direction. A valid schema no longer means success. If four strings contain paths or placeholders, the record does not reach quality_eligible.

During re-checking, I saved the original records and created a new derived evaluation. Four attempts received the afterScored=true field; 17 remained outside the quality denominator. Old data was not overwritten, so it is possible to restore both the previous report and the reason for the change.

The table does not allow naming a winner for four reasons.

First: "accepted" includes limited deterministic repair. Three Qwen results, two Bonsai results, and one mixed route result did not pass the contract in their original form. We are measuring the combination of model + prompt + schema + runtime + repair, not the isolated model.

Second: the set did not include some adversarial checks from an earlier experiment. It did not include full coverage of confidential data leakage, instruction substitution, and specially prepared contradictions. Success on role-playing scenarios cannot be extrapolated to absent risk classes.

Third: the saved records contain outputPreview, not full responses. Based on these fragments, preview_based_semantic_diff was calculated: 0.82, 0.87, and 0.88. Such values help choose the direction for the next run, but do not confirm the superiority of one route. Semantic comparison of full documents from these files is not reproducible.

Fourth: these are single saved runs. They show the ability to pass the contract, but not stability. For stability assessment, repetitions are needed with unchanged versions of the model, quantization, runtime, prompt, schema, and input data.

Why a route must be evaluated as a whole

The speed of the first response is rarely equal to the time until an accepted result. After the call, parsing, JSON repair, re-generation, automated checks, and manual verification may be required.

Therefore, I chose the fixed route as the unit of comparison:

model artifact
+ quantization
+ runtime build
+ generation parameters
+ prompt version
+ schema version
+ deterministic repair policy
+ hardware profile

Changing any element creates a new configuration. A Qwen result with one chat template version cannot be automatically transferred to another. Similarly, it cannot be assumed that updating the parser improved the model: it improved the route.

Different stages of work have different requirements. For a draft, latency is important. For identifying gaps and conflicts, the ability to hold multiple solution versions and refer to their basis is crucial. For structure checking, the model is not even necessary: types, mandatory fields, and known invariants are more reliably checked by ordinary code.

This leads to the hypothesis of role-based routing:

fast draft               → fast route
gap and conflict search    → heavier route
contract and mandatory links → deterministic code
permissible format repair  → limited repair step
decision on suitability   → human

The current data neither confirms nor refutes this hypothesis. The mixed route required fewer repairs in one set but was slower than Qwen-only. To make a decision, we need the cost and latency per accepted result, a series of repetitions, and full output data.

What to save for reproducibility

The model name and the final score do not allow repeating the experiment. For each run, I save or plan to save:

  • run_id, dataset and scenario identifiers;

  • exact model artifact, quantization, and version hash;

  • runtime build and chat template;

  • generation parameters;

  • prompt and JSON Schema versions;

  • input data hash;

  • full raw response and parsed object;

  • number of input and output tokens;

  • execution time and observed memory;

  • separate statuses: timeout, crash, and out-of-memory;

  • parsing and schema errors;

  • repair type and number of attempts;

  • completion gate result;

  • scenario check results;

  • human decision and reason for rejection.

Full inputs and outputs may contain work data. They cannot be published automatically. Aggregates, hashes, versions, and anonymized examples can be included in the public report, while original artifacts are stored securely.

A repeated run should receive a new run_id. Overwriting a failed attempt is convenient for a nice table but destroys the experiment history. A new schema or prompt also requires a new profile version.

Why an external test is not the truth

Deterministic code removes the situation where the model evaluates its own response. It does not guarantee the correctness of the criterion.

A test might require four headers and miss the empty text below them. It might look for the word OAuth and not recognize an equivalent description. It might check for a link to a source without verifying if the source confirms a specific conclusion.

Therefore, I distinguish three types of checks.

Contractual check confirms the form: the response exists, the parser reads it, the required fields are filled and do not consist of obvious placeholders.

Scenario check confirms an observable requirement. With one source, the system should not invent a conflict. With two incompatible API versions, it should show a discrepancy. An unknown value should not appear from a plausible template.

Human acceptance determines if the document is suitable for the original task. A responsible person checks the rationale, the clarity of the risk, and the consequences of the decision. An automated test does not get the right to accept a result just because it is executable.

If the criterion turns out to be incorrect, the task may pass all checks and be returned later. Such a case should be stored separately from a regular new request: link the new record to the closed one and indicate the criterion misdefinition as the reason for return. Then, the proportion of results that passed the test but were later returned due to incorrect definition of done can be measured.

Next experiment

The current summary already helps avoid choosing a model based on a false denominator. It is insufficient for comparing routes. The next run should address five gaps.

  1. All routes run the same versions of scenarios, inputs, prompts, and schemas.

  2. The system saves full responses, not just preliminary fragments.

  3. I run each scenario multiple times to assess stability.

  4. I include adversarial cases in the set: source conflicts, instruction substitution, data leakage, numerical inconsistency, and silent gaps.

  5. The report calculates total time, repairs, retries, and human acceptance.

Separately, the limit of local hardware needs to be checked. Based on current data, it cannot be asserted that heavier scenarios have already been tested in a private cloud: no such experiment has been conducted.

Short protocol before comparing models

Before a new run, I fix seven conditions:

  1. The exact configuration of the model, runtime, prompt, schema, and hardware is defined.

  2. Completeness is separated from quality and human acceptance.

  3. The system saves full raw responses and all repairs.

  4. Each metric has its own denominator.

  5. Routes receive identical scenarios.

  6. The set includes normal and adversarial cases.

  7. The person who accepts the result and is responsible for its use is named.

A completion gate does not make a model smarter or improve response quality. It draws a line up to which a quality metric still makes no sense.

First, the runtime must return a complete object. Then, the parser and external code check the contract. Scenario tests verify consistent document properties. After that, a human decides if the result can be used.

In my experiment, it was this separation that turned a nice "10 out of 10" from an answer into the beginning of diagnostics.
