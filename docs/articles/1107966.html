Basics

I think I've already mentioned several terms in the previous two sections that might not be clear to everyone. So let's briefly clarify what AI, AI agents, Harness, MCP, and tokens are.

AI

Artificial intelligence is a rather broad concept that encompasses many areas: from classic scoring models used for many years to large language models (LLMs) that have become widespread only a few years ago.

But in this article, we will only talk about one part of this large field – generative AI and, in particular, LLMs, as these are what we will be working with.

Generative AI (GenAI) is a field of artificial intelligence that combines models capable of creating content based on information learned during training. This can be text, images, video, or audio.

LLM (Large Language Model) is a type of generative artificial intelligence model trained on large volumes of text data to understand and generate natural language. Such models are capable of answering questions, analyzing information, and writing texts. Examples: GPT, Claude, Gemini, and Qwen.

Context

The context of a language model is one of the most important resources today, which is constantly lacking. It represents the maximum number of tokens (one token is approximately 3-4 characters of text) that the model can process at once.

I think you've heard news more than once that another model has received a context window of a million tokens. But in reality, even this volume is sometimes insufficient.

Therefore, one of the main and at the same time most complex tasks for a person working with AI at any level is context management. After all, the quality of the model's response directly depends on what information we provide to it. If poorly prepared or irrelevant context is provided as input, the result will likely be corresponding.

Message Types

In the previous section, we clarified what context is and why managing it is so important. But here arises a question: what does this context consist of? After all, when we communicate with ChatGPT, we only see our messages and the model's responses. In reality, it's a bit more complicated.

First of all, it's important to understand that context consists not only of our dialogue. It can also include system instructions, the results of tool usage, and other service information. At the same time, messages have different roles, which determine how the model perceives them.

Let's break down the main message types:

System message is a system prompt or initial instruction. When you first open ChatGPT or DeepSeek, the model already receives certain instructions, even if you haven't written anything yet. These can specify how the model should behave, in what style to respond, what limitations to adhere to, and how to work with available tools.

Moreover, such instructions can sometimes be quite extensive and occupy tens of thousands of tokens of the context window. Their size depends on the specific application and can vary greatly.

Human message (User message) are user messages. This is everything we send to the model: questions, instructions, code snippets, documents, and so on. This is the message type we interact with most often.

AI message (Assistant message) are the model's own responses. For example, when you ask ChatGPT to write a Python function, the generated code will be part of the assistant's message. These messages are also saved in the dialogue history and take up space in the context.

Tool message are the results of tool calls. For example, you asked an AI agent to read a file from your project. The model calls the appropriate tool, and it returns the file content. This result will be passed to the model as a Tool message.

Thus, even if you sent only one short message, there might be much more information in the context than you see in the interface.

But why separate messages into different types?

The fact is that not all instructions have the same priority for the model. For example, system instructions have a higher priority than regular user messages. And the content of a file or the result of a search obtained through a tool should not be perceived as new instructions to be followed.

For us now, the main thing is to understand two things: the context consists of different types of messages, and managing it means not just reducing the amount of text, but also correctly organizing the information that the model receives.

Tools and AI Agents

So, what is an AI agent and how does it differ from a regular LLM?

As I mentioned above, an LLM can generate sequences of tokens, but where does it get the information to answer our questions?

Primarily from the data it was trained on. That is, if the model received enough information on the topic of interest during training, it will likely be able to answer the question. But if the necessary information was not in the training data, the model may not know the correct answer.

However, this doesn't mean it will necessarily remain silent. Most likely, the model will still try to answer something, and here we encounter so-called hallucinations – situations where AI generates unreliable or completely fabricated information.

For example, a model trained on data up to 2025 will not inherently know today's weather or the score of yesterday's football match. It simply doesn't have access to this information.

In 2022-2023, this was generally acceptable. The very ability to communicate with a language model and get meaningful answers seemed incredible. But it quickly became clear that knowledge gained during training alone was not enough.

We wanted the model to be able to get up-to-date information, work with files, execute code, and somehow interact with the outside world.

To solve this problem, tools emerged – a mechanism that allows a language model to access external systems and receive the results of their work.

Tools

Tools are external functions that an AI model can call to obtain information or perform specific actions. For example, searching for information on the internet, reading and modifying files, executing program code, accessing databases, or interacting with other applications.

Perhaps one of the first and most important tools was internet search. But how does it work?

We've already discussed that to answer our requests, the model uses knowledge gained during training, as well as all information from its available context: our messages, previous responses, and system instructions.

Therefore, if we somehow add the necessary up-to-date information to the context to answer the question, the model will be able to use it.

This is precisely the principle on which tools operate.

For the model, a tool can be a regular function that it knows how to "call." For example:

@tool
def get_weather(city: str) -> str:
    """Gets the current weather in the specified city."""

    weather = weather_api.get(city)

    return f"Temperature: {weather.temperature}°C, {weather.description}"

But here's another problem. There can be a huge number of tools, and for each of them, developers have to write a separate integration. What if we want to use the same tool in different AI applications?

MCP

To solve this problem, at the end of 2024, Anthropic introduced the Model Context Protocol (MCP) – an open protocol that standardizes the interaction of AI applications with external tools and data sources.

Let's figure out why it's needed.

Imagine we want to give our AI agent access to GitHub. For example, so it can read code from repositories, create Issues, or work with Pull Requests.

Without MCP, we would have to implement the interaction with the GitHub API ourselves, describe the available functions, and explain to the model how to use them.

With MCP, things become a bit simpler. We can connect a ready-made MCP GitHub server, which already provides the necessary tools in a standard format. And if our AI application supports MCP, it will be able to discover and use these tools.

The same applies to MCP servers of other services. Here are some of them: https://glama.ai/mcp/servers?utm_source=chatgpt.com

AI Agent

The scheme we considered above already reflects the basic principle of an AI agent's operation.

AI Agent is a system capable of independently planning and executing a sequence of actions to achieve a set goal. To do this, the agent uses a language model for decision-making, interacts with tools, analyzes their results, and adjusts its further actions if necessary.

But how does it work in practice?

Let's consider one of the basic architectures of AI agents – ReAct (Reasoning and Acting). This approach formed the basis of many agent systems and continues to be used today.

ReAct is based on a fairly simple cycle:

  • Reasoning – the model analyzes the current task and decides what action needs to be performed.

  • Acting – the model selects a suitable tool and forms a request to call it.

  • Observation – the result of the tool's execution is returned to the model's context.

After that, the cycle repeats: the model analyzes the updated context and decides whether another action needs to be performed or if the final answer can already be formed.

For example, if you ask an agent to create a website, it might first create the necessary files, then install libraries, run the application, detect an error, and fix it. All this within a single task, without needing manual commands at each step.

Harness

The simple ReAct agent scheme we considered above has long been the basis for many agent systems. Moreover, this principle is still relevant today. But with the development of language models and the increasing complexity of tasks, it became clear that a single tool call cycle is no longer sufficient.

New problems arose: limited context, information loss between sessions, agent looping, errors when working with tools, lack of full planning and result verification mechanisms.

In parallel, the infrastructure around language models developed. Mechanisms for context management and long-term memory, saving state between sessions, working with files and the terminal emerged. Specialized skills, integrations via MCP, testing and self-correction systems, monitoring and logging tools, as well as the ability to delegate tasks to other agents were added.

Thus, a whole environment gradually formed around the language model, which is called Harness.

Harness (agent execution environment) is the infrastructure that organizes the work of an AI agent: it manages interaction with the language model, its context and state, provides tools, ensures their invocation, and controls the task execution process.

It is important to understand that Harness itself is not a language model. Moreover, the same LLM can show completely different results depending on the agent environment it operates in.

Vibe Coding Tools

Now that we've figured out how AI agents work, let's look at what tools allow us to use them for development.

Currently, there are many ready-made agent environments that handle context management, tool usage, and task execution. Therefore, we don't need to create all this infrastructure ourselves. It's enough to choose a suitable solution.

Among the most well-known tools in 2026, we can highlight Codex, Claude Code, OpenCode, and Hermes Agent.

Despite similar operating principles, each of them has its own specifics: interface, available models, customization options, and agent workflow organization.

Let's briefly review the main options, and then move on to practice.

Codex — OpenAI

Codex is an AI agent for programming from the creators of ChatGPT.

Its main task is to independently perform development-related tasks. For example, you can ask it to create a website, and Codex will write the code, create the necessary files, install libraries, and try to run the resulting application.

You can work with it through a separate application, a code editor, or the terminal. And you don't have to write code yourself: just describe your tasks in plain language.

Key Feature: a full-fledged agent environment for development, primarily focused on OpenAI models.

Claude Code — Anthropic

Claude Code is a direct competitor to Codex from Anthropic, the developer of the Claude model family.

In terms of capabilities, these tools are largely similar: both can work with entire projects, execute commands, modify files, and fix errors independently.

Claude Code is also available through a separate application, terminal, code editors, and browser.

Key Feature: tight integration with the Claude model family. Essentially, choosing between Codex and Claude Code largely means choosing between two ecosystems and approaches to organizing AI agent workflows.

Cursor

Cursor is primarily a code editor (IDE) with a built-in AI agent.

Its main difference from Codex and Claude Code is a greater emphasis on direct developer involvement. You see the project structure, can edit code yourself, track changes, and interact with the agent simultaneously.

Cursor supports models from different developers, including OpenAI, Anthropic, and Google.

OpenCode

OpenCode is an open-source AI agent for programming.

Its main advantage is the freedom to choose the language model. You can connect models from different developers, choose a provider and payment method yourself, or even use local models.

Otherwise, OpenCode solves the same tasks as the previously discussed tools: it can work with projects, write and edit code, execute commands, and fix errors.

Key Feature: open-source and the ability to choose models yourself and configure the environment for your tasks.

Hermes Agent

Hermes Agent differs somewhat from the previous solutions. It is a universal AI agent designed not only for programming but also for automating everyday tasks.

For example, you can interact with it via Telegram, assign it tasks like searching for information, working with files, writing code, and performing routine tasks.

One of Hermes' most interesting features is long-term memory. The agent can store information about the user, their preferences, and previous tasks, and gradually accumulate useful ways of working.

Hermes also allows you to use models from different developers.

Key Feature: versatility and advanced memory mechanisms that allow the agent to be used not only for development but also as a personal AI assistant.

In fact, any of the listed tools will be suitable for getting started.

If you just want to describe tasks and get working applications, I would start with Codex or Claude Code. If you are more comfortable working directly in a code editor, then Cursor.

OpenCode is suitable for those who want to choose models themselves and flexibly configure their environment. And Hermes Agent is particularly interesting if, in addition to development, you plan to automate everyday tasks.

Reasoning Levels

In addition to model selection, Codex allows you to adjust its reasoning level

Reasoning Effort is a parameter that determines how many computational resources the model can use to analyze a task and find a solution.

Simply put, we can ask the model to spend more effort thinking about the task before and during its execution.

Depending on the selected model, different levels are available:

Level

When to Use

Low

Simple and well-defined tasks

Medium

Everyday development, adding features, and fixing common errors

High

Complex tasks requiring deeper analysis

Extra High (XHigh)

Complex architecture, finding non-trivial errors, and multi-step tasks

Ultra

Especially difficult tasks where significant time and resources are acceptable

It's important to understand here that a high reasoning level doesn't guarantee a better result. Sometimes the model can solve a task on Low just as well as on High, but much faster.

Additionally, increasing the reasoning level can increase token consumption, and thus, the use of available limits.

For starters, I would recommend Medium. In my opinion, it's a good compromise between speed and quality. If the agent struggles with a complex task, you can try High.

Personally, I most often use Medium and High. With a properly formulated task, this is quite sufficient.
