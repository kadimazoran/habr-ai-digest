In the previous article, we discussed how to connect Qwen Code to your key and an OpenAI-compatible provider. What we will configure:

  1. QWEN.md — persistent instructions for the project.

  2. Rules — instructions that are loaded only when needed.

  3. Confirmation and Permission Modes — what the agent does by itself, and what only with your consent.

  4. MCP Servers — external tools.

  5. Sub-agents — specialized assistants with their own instructions and limited permissions.

  6. Sandbox — to ensure agent commands do not go beyond the project boundaries.

Everything has been verified against the Qwen Code documentation version 0.28.0 (November 2026). The project is developing rapidly, so if you have a different version, consult qwen --help and the documentation in the repository.

1. QWEN.md: Explain the Project Once

QWEN.md is a regular Markdown file that Qwen Code reads at the beginning of each session. It's best to put things here that you would otherwise have to repeat every time: how to build and test the project, team agreements, and what not to do.

There can be three files, and they are all loaded at once:

File

For Whom

~/.qwen/QWEN.md

For you, across all projects

QWEN.md in the project root

For the entire team, committed to git

.qwen/QWEN.local.md

Only for you and only in this project

The local file is loaded after the general one, so you can use it to supplement or override team instructions. You'll need to add it to .gitignore manually; Qwen Code won't do it for you.

If the repository already has an AGENTS.md file for other AI tools, Qwen Code will read it too. No need to duplicate.

Quick Start. The /init command will analyze the code and create a draft QWEN.md with build commands and discovered conventions. If the file already exists, it will suggest additions rather than overwriting it.

Example of a good QWEN.md:

# Project: Order API

Project Overview: @README.md

## Commands
- Install dependencies: `pnpm install` (not npm)
- Tests: `pnpm test`, single file: `pnpm test path/to/file.test.ts`
- Linter before commit: `pnpm lint --fix`

## Agreements
- Controllers do not access the database directly, only through repositories in `src/repositories/`
- New endpoints are described in `openapi.yaml` before implementation
- Migrations are not edited after merging, only new ones are added

## Forbidden
- Do not touch `src/legacy/` without explicit request
- Do not commit and push without my confirmation

You can include other files using @path/to/file, with paths relative to QWEN.md itself.

The main rule is to be concise and specific. The documentation explicitly warns: the longer the file, the worse the model follows it. "Use 2-space indentation in TypeScript" works, but "write code neatly" does not. Do not write in QWEN.md what the model can already understand from the code.

And another reason to keep it short: QWEN.md is included in every request of every session. Every extra line is tokens you pay for multiple times.

Auto-Memory. In addition to QWEN.md, Qwen Code itself saves notes about your preferences and the project in ~/.qwen/projects/<project>/memory/. You can manage it manually:

  • /remember always use snake_case in Python — remember immediately;

  • /forget old workaround for login bug — forget;

  • /memory — view loaded files and enable or disable auto-memory.

Auto-memory works "as much as possible." For things that must always be followed, write them in QWEN.md.

2. Rules: On-Demand Instructions

If QWEN.md becomes too long, some instructions should be moved to rules. A rule is a Markdown file in .qwen/rules/. Its main distinguishing feature is the paths: field. A rule with this field is added to the context only when the agent reads or edits a file that matches the pattern.

---
description: How we write React components
paths:
  - 'src/**/*.tsx'
  - 'src/**/*.jsx'
---

Only functional components. Tests reside next to the component. Do not move state that is only needed for one screen to the global store.

While the agent is editing the Makefile, the React instructions do not occupy its context. As soon as it opens a .tsx file, the rule is loaded and remains active until the end of the session.

A rule without paths: works the same way as QWEN.md: it's always loaded.

Where rules are located:

  • ~/.qwen/rules/ — your personal rules, loaded always;

  • .qwen/rules/ in the project — loaded only if you trust this folder (trusted folder).

A simple guideline: QWEN.md contains what's always true, while rules with paths: concern specific parts of the code.

These can be switched using Shift+Tab (or Tab on Windows) or the /approval-mode command. There's a separate shortcut for Plan: /plan enables it, /plan exit returns to the previous mode. To make a mode persistent, add the flag: /approval-mode plan --project for the project or --user for all projects.

Important detail: in recent versions, the default mode is Auto. This means that every terminal command, network request, or MCP tool call is evaluated by a separate classifier model. This is convenient, but:

  • the classifier involves additional API requests, meaning extra costs;

  • it uses a "fast" model, and if one isn't specified, it uses the main one, making each check as costly as a full request.

Therefore, if you're working in Auto mode, specify a cheap fast model with the /model --fast command or in the settings ("fastModel"). If you prefer predictability, switch to Auto-Edit: files are edited without questions, but commands require your "yes."

Granular Permissions

Modes can be supplemented with specific rules in settings.json:

{
  "permissions": {
    "allow": ["Bash(git status)", "Bash(git diff *)", "Bash(pnpm test *)"],
    "ask": ["Bash(git push *)"],
    "deny": ["Bash(rm -rf *)", "Read(.env)"]
  }
}

  • allow — executed without questions;

  • ask — always ask, even in permissive modes;

  • deny — completely forbidden.

The same can be configured interactively with the /permissions command.

.qwenignore

The .qwenignore file in the project root works like .gitignore: files and folders listed in it are excluded from tools that respect it. .agentignore and .aiignore are also supported.

# Generated and large files
/dist/
/coverage/
*.min.js

# Secrets
.env
.env.*

This saves context: the agent doesn't need to read build artifacts or minified files. However, this is not a secret protection measure: not all tools respect it. For .env files, add a deny rule as well, or better yet, use a sandbox (more on that below).

4. MCP: Connecting External Tools

MCP (Model Context Protocol) is an open standard that gives the agent access to external tools: databases, task trackers, internal APIs, documentation.

Adding a server is easiest with a command:

# Remote server via HTTP
qwen mcp add --transport http my-docs https://mcp.example.com/mcp \
  --header "Authorization: Bearer your-token"

# Local process
qwen mcp add my-tools --timeout 15000 python -m my_mcp_server

By default, the server is saved to user settings. The --scope project flag will save it to the project's .qwen/settings.json. You can remove a server with the command qwen mcp remove name.

The same in settings.json:

{
  "mcpServers": {
    "my-docs": {
      "httpUrl": "https://mcp.example.com/mcp",
      "headers": { "Authorization": "Bearer your-token" },
      "timeout": 5000
    },
    "my-tools": {
      "command": "python",
      "args": ["-m", "my_mcp_server"],
      "includeTools": ["search", "get_page"]
    }
  }
}

After adding, restart Qwen Code and check the connection with the command /mcp.

Which transport to choose:

  • http — for remote services, this is the recommended option;

  • stdio — for local programs and Docker containers;

  • sse — deprecated, only if the server does not support http.

Savings Tip. Each server's tool descriptions also consume context. Connect only what you actually use, and limit the set of tools via includeTools or excludeTools. Five "just in case" servers mean a constant token cost for every request.

5. Sub-agents: Specialized Assistants

A sub-agent is a separate AI assistant with its own instructions, its own set of tools, and its own context. The main agent passes a task to it, the sub-agent works independently and returns the result. Two main benefits:

  • The main session's context is not cluttered. A sub-agent might read a hundred files, while the main agent only receives the summary.

  • Permissions can be restricted. A reviewer who cannot edit anything physically cannot break the code.

You can create a sub-agent using the /agents create wizard, and view existing ones with the /agents manage command. However, it's more convenient to place the file manually:

  • .qwen/agents/ — project agents (have priority);

  • ~/.qwen/agents/ — your personal agents for all projects.

Example of a reviewer that only reads and works with a cheap model:

---
name: reviewer
description: Reviews changes before committing. Use after any code edit.
model: fast
tools:
  - read_file
  - grep_search
  - glob
  - run_shell_command
---

You are a code reviewer. Examine the changes using `git diff` and find:
logic errors, unhandled exceptions, security issues, violations of agreements from QWEN.md.

Do not fix anything. Return a list of remarks in descending order of importance, with the file, line number, and reason for each.

The reviewer lacks write_file and edit, so it cannot modify files. It needs the terminal for git diff, and this command is already in permissions.allow from section 3, so there will be no extra questions. The plan mode is not suitable here: in this mode, the agent does not execute commands at all.

And a tester that can write files:

---
name: test-writer
description: Writes and runs unit tests for the specified module.
approvalMode: auto-edit
tools:
  - read_file
  - write_file
  - edit
  - grep_search
  - glob
  - run_shell_command
---

You write tests. First, study the module and existing tests nearby, mimicking their style. Cover the main scenario, edge cases, and errors. After writing, run the tests and fix anything that fails. Do not change the module's code itself: if you find a bug, describe it in your response.

What's important to know about the fields:

  • model: inherit (default) — the same model as in the main session; fast — the fast model from settings; you can specify a specific model ID. This way, you can keep the expensive model as the main one and delegate routine tasks to a cheaper one.

  • tools — a whitelist. If it's absent, the sub-agent gets all tools, including MCP.

  • disallowedTools — a blacklist, e.g., mcp__slack, to disable an entire MCP server.

  • approvalMode — the main session's permissive mode takes precedence. If you are working in YOLO mode, a sub-agent with approvalMode: plan will still operate in YOLO. Therefore, the reliable restriction is the tools list, not the mode.

You can invoke sub-agents explicitly ("let the reviewer look at the changes"), or you can rely on the main agent: it decides which one to assign the task to based on the description field. To encourage it to do so, specify in the description when the agent should be used.

By the way, if you have Claude Code or Codex installed, Qwen Code can also pass tasks to them as built-in sub-agents. They operate with their own models and subscriptions.

6. Sandbox: Preventing the Agent from Exceeding Project Boundaries

Confirmation modes determine *whether* the agent will ask. The sandbox determines *what* it can do, even if it doesn't ask. If you work in Auto or YOLO mode at least occasionally, you need a sandbox.

Linux: Sandbox for Tools

Recent versions include a separate mode for Linux: Qwen Code itself runs as usual, while the agent's commands and file operations are executed in isolation via bwrap (Bubblewrap).

Install bwrap (in Debian and Ubuntu, the package is bubblewrap) and add it to your user settings in ~/.qwen/settings.json:

{
  "tools": {
    "executionSandbox": {
      "backend": "auto",
      "filesystem": "workspace-write",
      "network": "closed"
    }
  }
}

  • filesystem: workspace-write — writing is allowed only within the project folder; read-only — no writing at all.

  • network: closed — agent commands cannot access the network; open — the network is shared with the system.

This setting cannot be enabled or weakened from the project's .qwen/settings.json. This is intentional: a foreign repository should not be able to disable your sandbox.

Verify that everything is working:

qwen sandbox --verify

Limitations to be aware of in advance:

  • Reading is not restricted. The sandbox prevents writing outside the project, but commands can still read system files. It does not hide secrets in your home directory.

  • Many features are disabled. MCP servers, hooks, extensions, and the ACP mode do not work in this mode, meaning it cannot be used when Qwen Code is run as an agent within another application.

Docker and Podman: Isolate the Entire Environment

The second option works on any OS: Qwen Code runs entirely within a container, into which the project folder and ~/.qwen are mounted.

# One-time execution
qwen -s -p "run tests and figure out why they are failing"

# For the entire terminal session
export QWEN_SANDBOX=docker
qwen

Or permanently — in settings.json: {"tools": {"sandbox": true}}. The default image will be downloaded automatically; you can specify your own via tools.sandboxImage.

macOS: Seatbelt

On macOS, there's a built-in lightweight option without Docker: QWEN_SANDBOX=sandbox-exec. The profile is set by the SEATBELT_PROFILE variable. By default, it's permissive-open (writing only to the project, network allowed). The documentation recommends starting with this and then trying restrictive-closed if everything works.

Putting It All Together

This is what a configured project looks like:

my-project/
├── QWEN.md                  # Commands, agreements, prohibitions
├── .qwenignore              # Builds, minified files, secrets
└── .qwen/
    ├── settings.json        # Project mode, permissions, MCP
    ├── QWEN.local.md        # Personal notes (in .gitignore)
    ├── rules/
    │   └── react.md         # Rule with paths: for src/**/*.tsx
    └── agents/
        ├── reviewer.md      # Read-only, fast model
        └── test-writer.md   # Writes tests

And in ~/.qwen/settings.json — keys, fast model, and sandbox.

A 15-minute checklist:

  1. Run /init and condense the resulting QWEN.md to the most important points.

  2. Move instructions for specific code parts to .qwen/rules/ with paths:.

  3. Create .qwenignore for build artifacts and large files.

  4. Set a fast model via /model --fast if working in Auto mode.

  5. Add safe commands to allow and dangerous ones to deny in permissions.

  6. Connect one or two MCP servers you actually use.

  7. Create a reviewer sub-agent with read-only permissions.

  8. Enable the sandbox.

Most of these settings are configured once and save time and money on every session.
