Installation is standard: pip install pydantic-ai — however you prefer. In v2, the base installation has become more compact, specific providers are installed via separate extras, but the base installation is sufficient for a first look.

from pydantic_ai import Agent
from pydantic_ai.models.openai import OpenAIChatModel
from pydantic_ai.providers.openai import OpenAIProvider

# 1. Create a provider with your gateway settings
provider = OpenAIProvider(
    base_url='https://openai.bothub.chat/v1',  # Your gateway URL
    api_key='your-api-token-here'
)

# 2. Create a model, explicitly specifying the model name on the gateway
model = OpenAIChatModel(
    'gpt-6-luna',
    provider=provider
)

# 3. Pass the model to the Agent
agent = Agent(
    model,
    instructions='Respond concisely, in one sentence.'
)

result = agent.run_sync('Where did the phrase "hello world" come from?')
print(result.output)

The entire program is nine lines, half of which is boilerplate. run_sync is a synchronous wrapper around an asynchronous core: internally, everything is built on asyncio, but for scripts and notebooks, there are ready-made sync versions, and for a FastAPI service, it's the usual await agent.run(...). Asynchronicity is primary here, synchronicity is a convenient addition. For the Python ecosystem, this is an unusual arrangement; it's usually the other way around.

Tools and Dependencies

The classic way to describe a tool for LLMs is a dictionary, with the JSON schema of arguments in one place, a text description in another, and the function itself somewhere else (documentation). Such schemas are written manually, live separately from the code, and drift apart with each release. In Pydantic AI, only the function remains: you add a decorator, and the framework collects everything else itself. The signature turns into a JSON schema, the docstring goes to the model as a tool description.

Here's a support agent with two tools and dependencies:

from dataclasses import dataclass

import httpx
from pydantic_ai import Agent, ModelRetry, RunContext


@dataclass
class SupportDeps:
    http: httpx.AsyncClient
    api_base: str


support = Agent(
    'openai:gpt-6.1-sol',
    deps_type=SupportDeps,
    instructions='Assist the client with order inquiries.'
)


@support.tool
async def get_order(ctx: RunContext[SupportDeps], order_id: int) -> dict:
    """Return the order status by number."""
    r = await ctx.deps.http.get(f'{ctx.deps.api_base}/orders/{order_id}')
    r.raise_for_status()
    return r.json()


@support.tool_plain
def normalize_phone(raw: str) -> str:
    """Format the phone number to +7XXXXXXXXXX."""
    digits = ''.join(ch for ch in raw if ch.isdigit())
    if len(digits) != 11:
        raise ModelRetry('The number must contain 11 digits. Please try again.')
    return f'+7{digits[1:]}'

The model ultimately sees roughly the same thing you do: the function name, the argument schema, the description. The return value goes back into the dialogue as the result of the call, the model reads it and decides what to say next.

The decorators differ by one thing: @agent.tool expects RunContext as the first argument, @agent.tool_plain does not. Through the context, the tool accesses dependencies. Dependencies are described by a regular type (here, a dataclass with an HTTP client), declared in the agent constructor via deps_type, and passed as a value during execution: support.run(..., deps=SupportDeps(...)). No global variables or singletons: whatever the tool needs is in the type, and the static checker will warn you if you forget a field. This is also beneficial for testing: you can provide a mock instead of an HTTP client and run the agent without a network. Those who have worked with FastAPI will find the mechanism familiar to the point of absurdity: annotations describe the contract, the framework validates the input and throws errors until you fix it. Only the model becomes the consumer of the schema.

The docstring here is addressed to the model: its wording determines whether the model will choose the tool and with what arguments it will call it. "Return the order status by number" it understands immediately, "helper for working with orders" — already with difficulty. You should write it as if you were explaining to a new colleague. For those who don't like decorators, functions can be passed as a list to the constructor — Agent(..., tools=[get_order]), the effect is the same.

raise ModelRetry inside normalize_phone is a separate story. A regular exception from a tool flies upwards and crashes the execution. ModelRetry works differently: the error text is sent to the model itself, it tries to correct the arguments and call the tool again. The same mechanism is activated when the model passes arguments that don't match the schema: ValidationError is handled as another reason for a retry. By default, each tool has one retry attempt; the limit can be raised by the agent (retries={'tools': N}) or specifically — @agent.tool(retries=N). In v2, ToolFailed was introduced for cases where retrying is pointless: the model learns about the failure, but the retry budget is not spent.

Structured Output

As we found out at the beginning, everything breaks at the junction between the model's response and the application code. output_type closes exactly that gap. You describe a pydantic model, pass it to the constructor — and the agent is then obliged to return data according to a specific schema. An invalid response will not pass validation and will be sent back to the model for correction, a malformed JSON will no longer reach the business logic, and result.output in your code will be a ready-made typed object (documentation). The IDE suggests fields, mypy catches typos, and serialization is free.

from pydantic import BaseModel
from pydantic_ai import Agent, ModelRetry, RunContext


class RefundDecision(BaseModel):
    approved: bool
    amount: int
    reason: str


refund = Agent(
    'openai:gpt-6.1-sol',
    output_type=RefundDecision,
    instructions='Decide whether to approve a refund. Safe amounts are up to 50,000.'
)


@refund.output_validator
def check_limit(ctx: RunContext, decision: RefundDecision) -> RefundDecision:
    if decision.approved and decision.amount > 50_000:
        raise ModelRetry('Refunds over 50,000 require human approval. Return approved=False.')
    return decision

However, the schema only catches the format. The model can honestly fill in all the fields and produce something nonsensical from a business perspective — for example, approve a refund of a million. For such cases, there is @agent.output_validator — domain-specific validation on top of the schema. The function can be asynchronous, access the database, call external services — anything. A validation failure is sent to the model as an error message, and it regenerates the response with the correction in mind. The budget for output retries is one attempt by default, expandable via retries={'output': N}; when the budget runs out, the execution will fail with UnexpectedModelBehavior — you can't silently swallow the problem.

You can also pass a union to output_type. The agent above with output_type=[RefundDecision, str] will return either a structure or plain text — a clarifying question if data is insufficient. Pydantic AI registers each option as a separate output tool so that the schema doesn't grow and the model has an easier time hitting it. The result is then parsed using isinstance, and the dialogue with clarifications works without your orchestration at all. Not only BaseModel models are suitable — dataclasses, TypedDict, and everything else that Pydantic can validate.

We've also reached streaming. Structured output can be sent to the interface as it's generated: Pydantic can partially validate incomplete JSON, and stream_output() provides intermediate snapshots, each validated as much as it could be.

async with refund.run_stream('Client bought a toaster and returned it the same day') as result:
    async for decision in result.stream_output():
        render(decision)  # snapshot: some fields might not have arrived yet

For chat interfaces, the difference is significant: the user sees the response card while the model is still writing the last fields.

Tests Without a Single API Call

Typically, testing an agent looks like this: you set up an HTTP mock, stabilize the response, and pray that the format matches reality. Or, more often, the agent isn't tested at all because "it's a model, what's there to test" — I lived by this logic myself for a year. In Pydantic AI, the model is replaced entirely, and the combination of "agent + tools + dependencies + output" is run like regular Python code in pytest (documentation).

The simplest option is TestModel. It looks at the JSON schemas of your tools, generates valid arguments itself, calls each tool, and returns a summary. No AI inside, pure procedural code, so runs are deterministic. You can replace the model directly in the test:

import pytest
from pydantic_ai import models
from pydantic_ai.models.test import TestModel

from support import FakeHttp, SupportDeps, support  # agent from the previous section

pytestmark = pytest.mark.anyio
models.ALLOW_MODEL_REQUESTS = False  # an accidental real call will fail the test


async def test_support_flow():
    deps = SupportDeps(http=FakeHttp(), api_base='http://test')
    with support.override(model=TestModel()):
        result = await support.run('Where is my order 42?', deps=deps)

    assert 'get_order' in result.output  # output contains a summary of called tools

ALLOW_MODEL_REQUESTS = False protects against forgetting a substitution somewhere in the tests: a real call will fail with an error instead of silently deducting money from your key. And Agent('test') in the constructor provides the same TestModel — convenient for experiments.

It checks what most often fails: tools are registered and called, dependencies reach them, output is validated and returned. Most agent failures are in the boilerplate, and that's what's now under test. For scenarios requiring specific responses, there's FunctionModel: your function replaces the model, receiving the message history and returning a ModelResponse.

# from pydantic_ai import ModelResponse, ToolCallPart

def scripted_model(messages, info):
    return ModelResponse(parts=[ToolCallPart('get_order', {'order_id': 42})])


with support.override(model=FunctionModel(scripted_model)):
    ...  # the trajectory is predictable before execution

Such a test is stable any day and in any CI, while also documenting the expected trajectory: which tools are triggered and in what order. If there are many tests, the substitution can be moved to a pytest fixture with support.override(...). It doesn't test the live model — for response quality, go to evals, a separate tool in the Pydantic ecosystem. The agent logic itself, for which all this was written, is tested without a single token.

What v2 Brought

The second version was released on June 23, 2026, about ten months after 1.0 (announcement). The central novelty is called capability. It's a behavior block where instructions, tools, lifecycle hooks, and model settings are gathered together and connected to the agent in one move. Previously, all this was spread across the constructor with separate arguments, and in complex agents, it turned into a fifty-line monstrosity. Now, behavior is assembled from blocks, and a block is serialized into a spec file — you can commit it, give it to a colleague, or connect it to another agent.

CodeMode solves another problem — the cost of the agent cycle. The classic scheme: the model calls a tool, waits for the result, thinks, calls the next one, and each loop re-processes the entire dialogue history through the model. In CodeMode, the model writes code instead of a series of calls, which invokes tools like regular functions, and this code is executed once in the Monty sandbox, Pydantic's own mini-Python interpreter. For tasks with a dozen steps, token savings become noticeable, and the pauses between calls disappear.

ToolSearch is needed at the opposite end — when there are hundreds of tools. The schemas of all tools are by default in the prompt, and with a large set, the context runs out before the agent starts working. Tools marked with defer_loading=True are not included in the prompt: the model finds them on demand via ToolSearch, where on Anthropic and OpenAI Responses, the search is native, and in other cases, a local function with a strategy selection works — from keywords to BM25.

With migration, most projects will only need to change a couple of imports, but three behavioral changes are worth checking manually. The openai: prefix now leads to the Responses API, and the previous Chat Completions prefix is openai-chat: — the provider class from the first section is about that. The default end_strategy for cycle completion has changed to graceful, causing cancellations in the middle of a tool call to behave slightly differently. Instrumentation has been updated to v5 with its own token statistics — owners of custom dashboards, this is for you. The documentation contains a V1 → V2 migration map; it's worth opening it before updating production agents.

What You'll Need in Production

run and run_sync cover nine out of ten cases. When you need to look inside the cycle — draw each step in the interface, inspect tool calls, branch logic manually — there's agent.iter(). It yields the cycle by nodes, where you decide what to do with the model request and tool execution, and streaming events also arrive there. This is useful for chats with live tool status.

Limits are set at the execution level via UsageLimits — number of model requests, tokens, tool calls. The count is for the entire execution, including all cycle turns, so the agent cannot silently spend three times more than you budgeted. Exceeding the limit throws a regular exception and is caught near the execution — a safeguard that pays for itself from the very first lost cycle.

A document approval agent might wait for human signature for hours, but a nightly batch of a thousand documents must survive a service restart. For such scenarios, Pydantic AI works on top of durable execution: each step is saved, and after a failure, the process continues from the point of interruption, without repeated model calls. Integrations are ready-made — Temporal, DBOS, Prefect, Restate, AWS Lambda, Apache Airflow, plus lightweight options like Absurd and pgtask; chances are, something from the list is already in your infrastructure.

External tools are connected via MCP: toolsets=[MCPToolset(url)] is passed to the agent, and the server — local via stdio or remote via HTTP — becomes the source of tools. By marking a set with defer_loading=True, you can connect a hundred servers and not overpay for context.

Observability is handled by Logfire from the same team. One line logfire.instrument_pydantic_ai(), and traces show prompts, responses, tokens, and the cost of each run (documentation). Under the hood is OpenTelemetry, so traces go to any compatible system — Grafana, Jaeger, whatever you have set up. AI Gateway, a paid product from the same ecosystem, replaces twenty keys with one, supports failover between providers, and consolidates costs into a single quota.

Models on Your Own Hardware

The provider catalog has exceeded thirty-seven items — from OpenAI and Anthropic to Kimi, Qwen, Together, and OpenRouter (overview). But the test of flexibility is local execution. The reasons are varied: some medical data and client documents cannot be sent externally at all, some operate in an isolated enterprise network without internet, and some are tired of counting tokens on an agent that runs around the clock — your own graphics card pays for itself in a couple of months.

Connecting a local model looks modest:

from pydantic_ai import Agent

agent = Agent('ollama:qwen3')  # server on localhost:11434

If you need a non-standard server address — use an explicit provider (documentation):

from pydantic_ai.models.ollama import OllamaModel
from pydantic_ai.providers.ollama import OllamaProvider

model = OllamaModel(
    'qwen3',
    provider=OllamaProvider(base_url='http://gpu-box.local:11434/v1')
)

Self-hosting via vLLM uses a separate vllm: prefix, and any other OpenAI-compatible endpoint can be connected using the same OpenAIChatModel with Provider(base_url=...), as in the first section. You won't need to write your own model class.

Our gateway, by the way, is also an OpenAI-compatible endpoint, so a hybrid of "sensitive data runs locally, the rest goes to the cloud" is assembled with the same code. The models from the examples are available on BotHub, and the referral link will give you 300,000 CAPS for testing.

Small local models — usually 7–14 billion parameters — fail on strict contracts: tool-calling misses the schema, structured output is assembled with missing fields. This can be fixed by lowering ambitions: simpler argument schemas, smaller tasks, more modest output_type. It makes sense to increase the retry budget for such models in advance, and tests with TestModel will show exactly where the model stumbles, even before production. And choose a model with decent tool-calling support — among the lightweight open-source options, qwen models are currently the most sensible.

LangChain and Others

Comparing frameworks by GitHub stars is a useless activity; it's more meaningful by task. For a new Python project where the agent calls tools and must return structures, I would default to Pydantic AI. Typing is the load-bearing wall there: structured output, retries, validators, and tests come out of the box with a single mechanism, without add-ons.

LangChain has a broader ecosystem — over seven hundred integrations, LangGraph for complex state orchestration, and LangSmith for $39–399 per month. If your project relies on connectors to a dozen SaaS products, these are strong arguments, and LangGraph has been handling complex stateful pipelines for years — it's too early to bury it. But typing is bolted on, structured output is assembled with add-on parsers, and on a typical agent, the difference is noticeable to the naked eye: a benchmark from the betterclaw review showed about sixty lines for Pydantic AI versus two hundred for LangChain. Three times less glue code that you'll have to read, fix, and cover with tests. I wouldn't start a new project on LangChain in 2026; for an old one where you've already invested in state graphs and connectors, it's not worth migrating just for the sake of it.

CrewAI lives in a different dimension: it's about role-based agent teams — you describe an "researcher" and a "writer," and the framework manages the handover of work between them. For multi-agent simulations, it has its own niche, and there's little point in using Pydantic AI there. If you work in TypeScript, look at Mastra and Vercel AI SDK; AWS has its own Strands.

Sometimes, no one is needed at all. A single prompt and a single model call in a script — use the provider's SDK directly, there are fewer ceremonies; a framework for a single call is like driving to the store in a bulldozer. The line is drawn where tools, retries, and response structures appear: writing that by hand is painful.

The framework also has drawbacks, of course. The release rhythm is dense: during v1's lifespan, over a hundred releases came out, the changelog reads like a TV series, and even the most devoted fan can't keep up with all the changes. In complex scenarios, abstractions leak — you have to descend into the message history and low-level types, where all the API's beauty ends. And you have to accept the Pydantic ideology entirely: everything in the framework is through pydantic models; you can't validate "some other way" here. Personally, the third point doesn't bother me — validation through type models is exactly why I chose the framework — but in a team with a different style, heads will scratch over this.

Conclusion

In six months using Pydantic AI, I've migrated three agents, and none of them have required a single regular expression to parse model responses since. For me, this is a more significant indicator than any benchmark.

The direction of the topic is easy to guess: structured outputs have long been present in the SDKs of major providers, and Pydantic AI brings the idea to a complete cycle — from tool to test. The next layer of maturity lies in the ecosystem: evals for assessing response quality, Logfire for observability, durable execution for long processes. I bet that in a couple of years, arguing about agent typing will be as strange as arguing about web framework typing.
