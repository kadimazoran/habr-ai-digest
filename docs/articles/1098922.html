Finding Similar Notes in Obsidian Turned Out to Be Easier Than Safely Modifying Them

Two notes can be similar in meaning, but that's not a reason to merge them or delete one. I wanted to teach Veynrel not just to find such pairs, but to suggest actions for them. It quickly became clear that getting a recommendation from an LLM is much easier than safely applying it to Markdown. In this article, I'll break down how I implemented model quote verification, change preparation, protection against outdated files, and Undo. I'll show real TypeScript code, test results, and a small experiment with DeepSeek: all ten responses passed technical validation, but at least one thesis was only partially supported by the chosen quote. In a test Obsidian vault, there are two notes with the same title – Cache lifetime. One is in Study/Caching, the other in Study/Systems. The plugin notices the similarity, but what to do with this pair? The same term doesn't necessarily mean the same content: one file might contain a definition, the other an example or an important limitation.

I arrived at this task after a small experiment I wrote about on October 14th. Back then, I took 40 synthetic notes and analyzed ten found pairs. Nine matches seemed useful to me, but only in four cases would I have confidently created a link. It turned out that finding similar notes and deciding what to do with them are different tasks. I came to this conclusion manually, even before the plugin offered recommendations: I analyzed the found pairs myself and decided what to do with each. The plugin's recommendations grew out of this manual analysis.

I wanted the application to help choose an action after the search: leave the notes separate, link them, or carefully move some information. I connected a language model for pair analysis. But almost immediately, the next question arose: what if the recommendation is incorrect, and the application has already managed to change the Markdown?

In the latest versions of Veynrel, I've been focusing on the transition from the model's advice to writing to disk. Search, recommendation, and file modification rights have become separate stages. I'll show how this works with a pair of notes: from quote verification to precise diff and Undo.

The six screenshots of the main analysis were taken in a real Obsidian 1.13.7 on synthetic files with controlled local responses. They show the interface and safeguards, not the quality of a real LLM. Below, a new series of ten actual model requests is described separately; its only new frame is signed separately.

Two Notes with the Same Name

Two files with the same name but different paths. The model hasn't received their content yet before separate consent for analysis.

Semantic search works roughly like this: text is divided into meaningful fragments, numerical vectors are obtained for them, and then the system compares the proximity of the note representations. This helps find materials where the idea is formulated in different words.

Vector proximity doesn't tell you if documents should be merged. Even a similarity of 0.95 doesn't mean "95% confidence in a duplicate," but only proximity in the chosen vector space. Therefore, I call the search result a candidate. It gives a reason to open the pair, but not a command to delete, move, or write.

Next, the user can examine the two saved Markdown files and run the model analysis separately. For a remote provider, this means sending text externally; therefore, the plugin first shows the prepared request and requires consent. Local Ollama is possible, but it's also a configurable endpoint, not a reason to hide the fact of data transfer.

The First Temptation: Believing a Pretty Quote

You can ask the LLM to return an object with a recommendation and several quotes. On paper, everything looks reliable: the text is supported by "evidence." The problem is that the model itself formulates this evidence. Nothing prevents it from slightly rephrasing the source, confusing two notes, or citing a phrase that isn't there at all.

In Veynrel, I've separated these two roles.

Before calling the model, local code reads the saved files and prepares a catalog of fragments. For each, there's a source side (A or B), an exact text slice, and an ID like nonce:A:0. The catalog is built in advance, before user consent. Both these fragments and the full texts of both notes are sent in the request; limiting the catalog doesn't mean silently truncating the document.

After the response, the code doesn't accept an arbitrary quote from the model. It asks for an ID from the catalog, finds the original fragment, and inserts it itself.

Below is a shortened example of the actual contract form refs.v2. The IDs here are conditional: in a real request, they have a random prefix and must exactly match the provided catalog.

{ 
  "schema": "veynrel.relationship.refs.v2",
  "relation": "partial_overlap",
  "claims": [{
    "id": "c1",
    "kind": "shared",
    "text": "The notes intersect on the topic of cache lifetime",
    "evidenceA": "nonce:A:0",
    "evidenceB": "nonce:B:0"
  }],
  "explanation": {
    "text": "There is a common theme, but the contexts differ",
    "evidence": ["c1"]
  },
  "recommendation": {
    "action": "add_link",
    "reason": "Keep both notes and link them",
    "evidence": ["c1"]
  },
  "limitations": ["Only these two files were checked"]
}

evidenceA and evidenceB refer to fragments of the input catalog, while explanation.evidence and recommendation.evidence refer to claims from claims, e.g., c1. If these two ID spaces are mixed, even an outwardly correct JSON should be rejected.

Checking the reference to the source text in working TypeScript looks like this (one small part of the function is cut out):

const entry = typeof id === "string"
  ? catalog.fragments.find(f => f.id === id)
  : undefined;

if (!entry) {
  diagnostics.push({ field, side, code: "reference_unknown" });
  return null;
}
if (entry.side !== side) {
  diagnostics.push({ field, side, code: "reference_side_mismatch" });
  return null;
}
return entry.text;

If the ID is fabricated or belongs to another note, the check doesn't correct the link "by meaning." It returns an error, and the result doesn't proceed to the next stage. Incorrect schema, invalid fields, and outdated source snapshots are also rejected.

On the test pair, the model suggested a link, not a merge. The suggestion doesn't create any links yet.

The check only proves that the quote exists in the correct note. Whether the thesis is reasonable is decided by a human.

The "Add Link" Suggestion Is Not Yet an Edit

Suppose I agree: these documents should be linked. You can't just insert [[Cache lifetime]]: there are two files with that name. If you write an ambiguous link, you can easily end up in the wrong place. You also need to decide which note links to which, in which paragraph to place the link, and whether it's even possible to modify it. Markdown can contain lists, code blocks, tables, frontmatter, and inline links. Allowing the model to choose a "convenient place" here would be too bold.

For this, the recommendation goes through a separate planner. It doesn't execute the command from the JSON. Instead, it translates the allowed recommendation type into operation parameters: direction, location, confirmation. It may refuse on unsupported structures or missing data.

In this example, Study/Caching/Cache lifetime.md is being modified, and the target is Study/Systems/Cache lifetime.md.

For the selected direction, the link must resolve precisely to the target Obsidian file object. In the adapter, before writing, there's a direct check:

requireSafe(
  app.metadataCache.getFirstLinkpathDest(
    plan.targetPath.slice(0, -3), plan.sourcePath
  ) === plan.target.file,
  "stale"
);

This is a separate safeguard against errors with identical names. It checks where Obsidian will actually resolve the link. If the state of links or files has changed, the previous plan is considered invalid.

And even after that, the write operation is not performed. The plan contains the expected Markdown before and after the operation. The user sees the specific diff and confirms it separately.

This window shows both full texts and the diff; the top part is visible in the screenshot. Applying will require a separate click.

The plan does not cut out a fragment based on the model's approximate quote. For a regular link, it's constructed from the selected range of the saved document. If the markup is ambiguous, the operation is blocked.

Time Passes Between Preview and Save

Suppose I opened the diff, got distracted, added a paragraph to the same note, and returned to the "Apply" button. Even if the proposed link is still relevant, the plan was calculated based on the old version of the file.

The simplest and most dangerous implementation would be: take the prepared after and overwrite the document. My manual edit would disappear.

In Veynrel, the executor re-checks the plan before writing. It re-reads notes and metadata, checks the target file, and blocks writing if affected editors are open (even if their buffer currently matches: saving might be in the queue). After preparing and saving the journal, all this is re-checked again.

In practice, before applying, you need to close tabs with affected notes and re-confirm. This is not the most convenient option, but the plugin has no reliable way to stop a save that's already pending in the editor; I preferred an explicit refusal over the risk of overwriting someone else's edit.

The last safeguard is directly in Vault.process() – Obsidian's API for modifying a file relative to its current content:

await app.vault.process(note.file, current => {
  check();
  guard(note);
  requireSafe(current === before, "conflict");
  return after;
});

This is a fragment of the actual adapter, without function renaming. The condition current === before is the main invariant: writing the calculated after is allowed only if the file currently contains exactly the text on which the modification was based. There is no "almost the same Markdown" or space normalization in this check.

By the way, newline and BOM normalization is indeed used elsewhere in Veynrel: when searching for exact duplicates. But searching for identical content and protecting writes from lost changes are two different tasks. Normalization is appropriate there, but dangerous here.

For one note, this approach is relatively understandable. For multiple files, it's no longer honest to promise a single atomic operation: the first file might be saved successfully while the second write fails. In the project, these are separate executors and recovery states.

Why Regular Ctrl+Z Doesn't Work Here

If the task ended with writing, you could store the old text and return it upon request. However, after adding a link, a person might continue editing.

Let's imagine this sequence:

  1. The plugin wrote the new after content.

  2. I manually added another paragraph.

  3. A minute later, I pressed Undo for the plugin's operation.

Unconditional restoration to before would erase both the link and my new paragraph. Therefore, Undo must also check the current state, not just execute the reverse command.

For supported operations, Veynrel stores a persistent journal with original and expected content, checksums, and recovery copies. The journal is prepared before writing. After writing, the file is re-read, and only then is success marked.

During Undo, the code re-verifies that the content still exactly matches the written after, the file identity hasn't changed, there are no conflicting journals or open affected editors. Only then is the transition from after → before allowed. If I managed to add a paragraph, automatic undo is blocked, and my edit is preserved.

What if the application crashed at an inconvenient moment? For example, Vault.process already saved the file, but the applied mark in the journal wasn't saved. After restarting, you can't blindly repeat the operation. The system compares the persistent record with the actual text and shows the restored state. It doesn't perform an arbitrary recovery write on startup. I needed the plugin to be able to say what exactly was saved after a crash.

Run on a Real Model

Controlled responses are convenient for testing writing and undo. But the question remained: could a real model go through the same path without script assistance? I kept the production prompt, temperature=0, response limit of 8192 tokens, and disabled reasoning. There were no retries or JSON corrections; the backend provider within OpenRouter might have varied.

Before the first request, I saved the texts, paths, order, and SHA-256 of ten synthetic pairs: from almost identical notes to contradictions and insufficient context. I also included both Cache lifetime notes. The candidate list was formed by fixed artificial vectors, so this experience tests the language model and its integration, not the embeddings. The full report on ten pairs contains input notes, model responses, verification results, and the cost of each request.

All ten responses were readable JSON, passed refs.v2, fragment link verification, and the strict validator. Five times the model suggested adding a link, once considering a merge (consider_merge), and four times manual analysis. For six recommendations, preflight checks allowed proceeding to operation parameter selection. These are not yet ready edits, let alone file changes. I only completed one scenario with Apply and subsequent Undo. The median response time was 4.07 seconds, range 2.44–10.00; the total cost returned by the API was about $0.00227.

For Cache lifetime, the model identified common content and suggested a link. In this response, one thesis mentioned both deleting expired values and a five-minute example, but the chosen quote only supported the former. Both facts are in the original note, but there's nothing about five minutes in the attached fragment.

The result was 10 out of 10 technically valid responses, but at least one of them contained a thesis supported by its quote only partially. The validator checked the existence of the fragment and its belonging to the correct note. It did not check if this quote was sufficient for the entire assertion.

For the LR01 pair, the model suggested consider_merge. But this is not a command to automatically merge two documents. After selecting parameters, Veynrel built a plan to copy one selected paragraph from the second note to the first. The original second note remained unchanged. I checked the exact plan in the interface, confirmed Apply separately, then performed Undo. This was one full modification scenario with subsequent rollback, not a mass check of all Merge variants.

During Apply, one Markdown file out of twenty in the synthetic set changed. The hashes of all twenty were compared to detect random changes in the others; after Undo, each matched the original SHA-256 again. This confirms a specific copy operation with rollback, not a universal document merge.

I assessed the usefulness of the recommendations myself: I read all ten responses along with the original notes. I consider seven to be appropriate, meaning I would have taken the same action; three are debatable. The Cache lifetime pair is not among the debatable ones: the link is appropriate there, although the quote for one of the theses is incomplete. This is one person's assessment, and also the plugin author's, so it doesn't show how often the model chooses the best action. For that, recommendations need to be evaluated by other people.

Where the Protection Ends

The plugin does not have a transactional file system. Vault.process has no authority over all windows, third-party plugins, synchronization, and external applications simultaneously. Multi-document operations lack overall atomicity. Even a reliable journal allows detecting some conflicts and not corrupting a file during recovery, but it cannot always automatically fix any partial state.

And most importantly: Veynrel has other generative tools, such as creating new atomic notes. They have their own confirmations and can report partial results, but do not inherit the universal Undo from the executor described here. I do not transfer the guarantee of one operation to all interface buttons.

Conclusion

The principle turned out to be simple: the model suggests, the code verifies, the human chooses, and a separate executor writes, which can refuse. Not every recommendation should result in a modified file: sometimes the best comparison result is to leave the notes as they are.

The question from the real model run remains open: the check sees that the quote exists and is taken from the correct note, but it doesn't see if it supports the entire thesis. It seems to be not just about the model or the prompt: as long as one thesis can contain multiple facts with a single quote, the check won't catch it. Tests on real data are needed to understand how often this happens.
