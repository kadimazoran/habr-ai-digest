RAG: A Database That Understands Meaning

A large part of an LLM integrator's work is built on several core technologies, such as RAG (Retrieval-Augmented Generation) and agents.

RAG is when we give the LLM access to our data: documents, knowledge bases, contracts, client cards, even code. This data is cut into small semantic chunks – and each chunk is converted into a vector: a set of numbers reflecting the meaning of the text. The resulting array of vectors is stored in a vector database.

When a user sends a query, we convert this query into a vector in the same way, find the most semantically similar chunks in the database, and give them to the model so it can answer based on the found data.

Thus, RAG is a technology that provides search based on relevant information corresponding to the user's intent.

Intent is what the user wants to get, not the words they used to describe it.

When searching by vectors, short queries might not work: there won't be enough context for the LLM and the embedding machine, a one-word query might not get enough weight. Therefore, when working with RAG, standard text search is also used, allowing you to search for information even by individual words.

You can upload any documents to RAG – and find connections between them. We can find Vasya Pupkin, a driver, in our database and see in which documents he is mentioned. There will be our driver's card, a card from accounting, and what he transported. By identifying entities like "Vasya Pupkin, driver," we can understand what information can be extracted from RAG with the simplest search consisting of these three words. The developer's task is to understand exactly what we want to find – and upload the relevant information.

RAG is convenient: you can search for information based on a specific intent. And, of course, you can extend the system with classic search – by user ID or other formal data.

I worked with a system for legal contract analysis. We made two versions: a system that independently analyzed the contract, and a system that simply assisted lawyers and allowed them to discuss potential issues with a chatbot.

The first system performed a full analysis, carried out a lot of checks, articles and laws were loaded into the system... It was long, expensive – and the implementation efficiency was low: about 20%. And lawyers still manually double-checked the results.

But when we added an agent to Word – the work speed increased immensely. The agent allowed lawyers to work independently and interact with text snippets via chat.

Firstly, the specialists realized they wouldn't be replaced. And secondly, they got a controlled tool that helped them speed up their work by almost half.

Not only the technology is important, but also user perception – lawyers didn't fully trust an autonomous system, so an assistant helper was very welcome.

Agents and MCP: Handles for the Language Model

So, the RAG level is about identifying user intents, finding relevant answers and results, and ultimately providing the user with a relevant answer.

A more complex system level is not just to give an answer, but to perform actions necessary for the user.

For example, a user wants to return a product under warranty and writes about it in the chat. The chat can find relevant information and reply "yes-yes, of course, our policy allows returns" – but the chat cannot create a task in the CRM system or send an email to a manager.

We need to give the model tools for active actions. And here we come to the discussion of agents.

Agents are intermediaries that allow models to access external tools and perform actions – add tasks to trackers, send emails, write code.

And in this story, there are two important concepts: Tool Calling and MCP.

Tool Calling is the invocation of software tools; it works roughly like this:

  • the developer explains to the neural network in advance what "tools" are available to it (database search function, sending an email, command line...). All this is described and passed in the prompt;

  • when processing a query, the model understands that its own knowledge is insufficient – it selects the appropriate tool and indicates what needs to be done with this tool;

  • the agent application receives the command, launches the requested tool, and performs the required action (e.g., queries the database), receives the result, and passes it back to the model.

And MCP is a protocol that allows organizing and standardizing work with Tool Calling: after all, virtually all agents solve the same standard tasks, and it's much more convenient to solve these tasks in the same ways. Standardization allows using ready-made solutions and working on a project with colleagues. Don't just write Tool Calling – package tools as MCP servers, preferably as separate external services.

Let's move on to agents and orchestration. Orchestration is magic. When you have five agents – no problem. When you have 25 agents – it gets a bit tricky. When you have a hundred agents – it's a pain.

And that's why a lot of ways to manage agents have been invented. You can use regular Tool Calling and pass all information about available agents and tools directly to the LLM. At the initial stages, this solution works perfectly, no problems. You can use some frameworks on top of this solution – it will simplify the work.

It's very helpful to distribute available tools and delegate work with them across different departments. This is more practical than a monolith and greatly simplifies life. And if you need to create a prototype – I would recommend using an AI studio, regardless of whose it is – Google, Yandex, or any other. Use ready-made tools, save your nerves.

Large Models, Small Models, and Money

Large providers, large models, lots of memory – they've become commonplace: OpenAI, Anthropic, Google, Minimax, Llama, Qwen, DeepSeek, GLM, Kimi, and the like. Big, famous, and they want money.

But there are also small models, and they are usually open-source. And these models can often be used even on a laptop. Open-source models like GLM, Qwen, Gemma, Llama, open-source GPT can be deployed locally and you don't have to worry about rights and licenses: most of them are free. Often, these are small models, no more than 100 billion parameters.

Large models solve general tasks – and they are most often connected in the early stages of integration when it's not very clear what exactly needs to be done, for what purpose, and why.

But in 90% of cases, you can use small models – and they will successfully solve many tasks. Small models are sufficient, for example, for tasks where you don't need to generate a full answer using LLM, but can return a pre-written text. In such a situation, small models will save you not just a lot of money, but a very large amount of money.

The criteria for choosing a model are simple: first and foremost, consider how you will work with your client and how you can save money. Most models can already work with Tool Calling and function well with many languages, including Russian.

Production: Leaks, Metrics, Security

Let's look at a working prototype as an example – a RAG assistant for a university website. The project includes a sitemap crawler, indexing pages in Qdrant, a multilingual embedding model, FastAPI, LLM via API, a web interface, and question logging. What's needed to deploy the project to production?

And this isn't about architecture in the usual sense. It's more important to think about the project's workflow: who are the users, what do they want, what questions do they ask. And if the project has question logging – that's the most wonderful thing about this whole story.

I've had to review many queries, and it provides a lot of useful information. You can perform query analytics using LLM, understand user pain points – and ultimately figure out what to do about it.

In the university system, information about classes, sick leave, or academic leave would be useful – and you can add agents to the project and give users more capabilities.

There's another important aspect. The law restricts the transfer of personal data to third parties and requires storing Russian citizens' data within the country. Therefore, it's better to use an embedder on your side. Especially since there are now small and fast embedders.

For Production Ready, you need to ensure that the system does not transfer personal information to an external LLM. A local LLM will solve the data leak problem. Prompt injections and token theft are protected by separate measures: filters, limits, authorization.

To do the job really well, you need to collect quality metrics. These will be metrics that show customer satisfaction and the quality of responses, but there are a whole host of nuances here. For example, at what stage a user might drop off or when they are satisfied but don't report it – after all, not everyone gives five stars in a chat when they get a good answer to their question. In general, you need to be a bit more of a product manager to not only implement but also evaluate effectiveness.

What You Need to Know

The market is not yet fully formed, and skill requirements vary greatly. You could be an AI/ML developer, or you could be an LLM developer, because the necessary tools are actually known to both: RAG, agents, orchestration, LLM, building workflows and pipelines.

Regarding programming languages – most companies want to work with the languages they are used to. For popular languages, there are already libraries for working with OpenAI-like APIs, and small frameworks for working with MCP. I would recommend Java, C#, Go, simply because they are popular in enterprise.

It's absolutely normal to write different tools in different languages depending on the tool required. The stack can be anything – whatever is convenient for you or accepted in the team.

Knowledge in CI/CD and server assessment will be useful. You might have to deploy local LLMs, monitor their load, distribute infrastructure across servers, i.e., do MLOps.

Hiring managers say: "Commercial thinking is welcome, such as building a sales funnel, customer service, document management." Business always wants the end employee to be a jack of all trades.

A new specialty has even appeared in the industry – with a nice acronym, as it should be: FDE (Forward Deployed Engineer). This is a specialist at the intersection of software development, artificial intelligence, and business communication, who implements the company's products (often AI solutions) directly on the client's side.

The ideal for business is a developer-product-analyst-integrator, but it's better to find a separate expert for each position.
