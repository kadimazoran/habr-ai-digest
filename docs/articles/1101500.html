Why an agent loses context and submits work without proof

The problem is that team knowledge resides in TDR, work threads, and developers' minds. This information is invisible to the agent. Limited to a single repository, it is physically incapable of considering inter-service contracts and hidden context.

During long sessions, the goal of "completing the task" overrides the instruction "get approval first." Accumulated context is lost when the session is interrupted. The chat history with clarifications and human corrections is eventually deleted, and tracker statuses lag behind the actual situation.

The situation is exacerbated when the same agent writes and reviews code, turning the review into fitting the result to what has already been written.

Next, we will look at how the proposed setup solves these problems.

Task store and pipeline

The core of the setup is af-checks-context, a separate team git repository. We call it the store. It contains everything you need to know before you start looking at the code: projects and features (Onepager, TDR, research, design), the team's knowledge base, service specifications, and process descriptions.

The agent's session starts in the store. Service repositories are in adjacent directories. Therefore, the agent reads the team context before the code, and for an inter-service task, there's no longer a need to decide in advance which repository is "main."

Task pipeline: Jira card → plan → implementation → verification on kbranch with evidence → archive. kbranch is a staging environment where a service branch is deployed separately from others.

flowchart LR     J[Jira Card] --> P[Change and plan]     P --> A1{{Approval 1}}     A1 --> C[Code + e2e]     C --> K[Run on kbranch]     K --> A2{{Approval 2}}     A2 --> PR[PR for review]     PR --> M[Merge]     M --> AR[Retro and archive]

Within the pipeline, the process is divided into three stages:

  1. The agent creates a change: spec, design, tasks broken down by PR, and a test plan. A human approves the plan – this is point 1. Code cannot be touched before this.

  2. Before the PR for review, a human approves the result – this is point 2: the diff of the plan from point 1, the result of the run on kbranch, and the PR description.

  3. The task spec is merged into the accumulated service specifications.

The task's position is determined not by the model, but by a deterministic script of the engine based on artifacts: is there a change, is the plan approved, is there a worktree and commits, is the PR open, is it merged, is there a verification report. The current step is the first step with a failed gate. The hook places the position in the agent's context on every reply mentioning the task. Human approval is the only fact that cannot be derived from artifacts. We materialize it separately (I'll explain how we do it below).

Changes are verified on a staging environment with evidence. Before the kbranch gate, we had no staging environment verification at all. We took the idea from an internal skill for staging verification and added e2e. The test plan divides cases into automatic (e2e) and manual. A case is automatic by default. Manual is allowed only if there is a recorded reason why an autotest was not made: for example, metric observation, a special build, or one-time data. If there is no reason, it means the plan is incomplete.

e2e tests are created in parallel with the code. Code and test branches are linked via the task key, and production is not needed to run the tests. Service PR review begins only after running on kbranch. e2e failures caused by the environment are recorded with a FAIL status and the reason. Autotests cannot be switched to manual mode for the sake of a green report status.

The report is machine-readable by two fields: verdict (strictly pass) and the hash of the verified commit. Any task commit after this hash makes the report outdated.

We isolate each task in a separate worktree from a fresh master. A branch not from the current master has already cost us rework, so new-worktree.sh always fetches and builds a branch from origin/master.

The senior model maintains task context, plans the workflow, and verifies the result, while junior models solve narrow subtasks in their own isolated contexts. The staging verification is done not by the same agent who wrote the code, but by a separate session or sub-agent without implementation history.

Each developer has a local agent memory: facts from past sessions that the agent searches for before delving into an unfamiliar service. But this memory is personal and not visible to colleagues. Therefore, we have this rule: if knowledge can be useful to someone in the team or their agent, it goes into the store's knowledge/ via a PR. And in personal memory, we only write our preferences and guesses.

The nature of the model is probabilistic, so the same rule can be both considered and ignored. The store makes the agent's work predictable. The position is calculated by a script, gates control transitions between steps, and plan decisions are made by humans through approval. Verifications and records previously performed by the model are now performed by commands and hooks. What remains for the models is what requires judgment: discussing decisions, code, and analyzing findings.

Team processes in a single repository

Previously, processes lived in personal notes, minds, and Confluence pages that diverged from practice. Now, the process is represented as code in the same store.

The pipeline is built on a declarative approach: steps and gates are configured via YAML, and the gates themselves are implemented as small Python checks that are connected by name. Five scenarios are supported: task, simplified task without a spec (used for hotfixes), project, feature, and research.

Changing the process is a PR. The process and content land via separate PRs. The history of decisions, both for tasks and for the process, remains in git. Content includes knowledge and context: task specs and plans, project and feature documents, and the team's knowledge base. The agent lands it during work and creates a PR for auto-merge so that the next agent or colleague can immediately see the current state. The process defines the rules of the game: scripts, hooks, pipelines, and agent settings. Such a PR is merged only by a human.

Verifications are deterministic. Before pushing, a landing script locally runs the store linter, pipeline validation, and tests of affected parts, and appends the result to the PR description. The store bot compares this result with the PR head and decides whether it's a process PR or a content PR. The model in the bot reviews only content and can only call a human.

Diagrams do not diverge from the process. Mermaid diagrams of pipelines in documents are generated from YAML; the linter fails if the diagram diverges from the declaration.

The engine is separated from the team profile. The core knows nothing about our team: Jira, staging, and service names live in the profile. The test enforces the boundary – the core cannot mention the tracker, company, or staging environment. Another team can take the engine and connect its own profile.

The process is executed by the agent on each task, and the linter and hooks monitor it. Therefore, the regulations do not diverge from practice: if a rule stops working, it is changed via a PR, not by verbal agreement.

Why a spec doesn't belong in a service repository

Many of our features are cross-service. It would be logical to place the spec in the repository of the service where it originated. But a contract that multiple services read does not belong to any single one of them.

First, we tried a hybrid approach: place internal specs in the service repository, and cross-service ones in the store. The argument for the hybrid was significant: since the design is refined during implementation, the agent would have to write clarifications in someone else's repository. Ten days later, we abandoned the hybrid. The pilot showed no benefit from having the spec in the service repository – documentation and PR descriptions always remained more valuable. Now, all specifications reside in the store, and the capability is named after the owning service.

What we lost: the spec no longer appears in the code PR diff.

What we compensated with:

  • the spec is reviewed by a human before the code – this is plan approval;

  • each code PR description includes a link to the change;

  • the store linter turns red if work on a task is merged but the change is not archived;

  • the service retains its own docs/ directory, describing everything its users need – without reference to OpenSpec or similar specification formalizations. There are no links to the store there: colleagues from other teams do not have access to it.

Agent bypass of rules

Illusion of control

The first version of the gates was honest only on paper. "Do not touch code before plan approval" was text in the instructions, and the gates checked for existence, not content. The approval gate passed any non-empty field – plan_approved: false resulted in "✓ plan approved (False)", and the agent itself could write the field. The staging verification gate checked that the path existed – even a directory named after the report passed.

In one task, the design was rewritten and the delta spec was deleted, but the approval given before these edits remained green. In another task, the session that wrote the code, after a FAIL on staging, rewrote the test plan and declared PASS.

We tied gates to content, moved prohibitions to runtime, and left the basis for decisions to humans. Approval stores the plan hash: specs, design, test plan cases, and breakdown by PR. We normalize service strings (PR links, merge marks, checkmarks). If the plan's meaning changes, the approval is reset, and the gate names the files that changed this meaning. The verification report is read by verdict and the hash of the verified commit.

Before calling a tool, the hook prohibits code changes in the task worktree until the plan is approved, changes to approval fields (both via editor and Bash), and commits to the main store checkout. If the engine fails to load, the hook doesn't stay silent but prohibits changes in the task worktree. Static prohibitive rules in the agent's settings cover immutable things: editing the local file with the approver's login and direct merging of PRs. The agent itself does not approve editing its own settings.

Initially, we wanted a separate team to handle approvals, launched by a human, and the agent to be forbidden from doing so. In practice, approving this way turned out to be too difficult: it would deter the team. Now, a human writes approve AF-NNNNN in a separate reply, and only the entire reply is counted. "Approve, but fix..." and "do not approve" are not accepted. A hook on a human's reply writes a mark with the task key, which lasts for 10 minutes. The agent launches the approval command: without a fresh mark, it refuses; with a mark, it records the date, login, and plan hash, and clears the mark. The hook prohibits the agent from writing the mark. The agent hasn't lost the command – it has lost the right to create its basis.

The agent confidently draws conclusions from its local worldview

The reviewing agent reported that the spec contradicted the code of a neighboring service. It seemed convincing. However, the spec was correct because it turned out that the agent's local service checkout was 36 commits behind origin/master. The missing commit introduced the necessary behavior.

Now, sub-agent findings are treated as hypotheses. The orchestrator first verifies them against origin after git fetch, and only then rewrites the spec or brings it to a human. The main store checkout is updated at the start of each session. Hooks take code from its master, even if the session is opened in a lagging worktree.

Better no gate than one that lies or is silent

The hook recognized tasks by the pattern XX-123. Because of this, it responded to requests like "fix file reading in UTF-8, small fix" with a "tact 1, do not touch code" block. Triggers could be HTTP-500, SHA-256, keys from other teams, or even the name of a temporary directory. Now, for replies, a whitelist of prefixes is used to recognize tasks. If the key is not on the list, the hook returns "nothing found in the store."

The hook prohibited Bash commands where the approval field was simply mentioned in the documentation text. Now it parses the command and looks for the record, not just the word.

The session start hook ran a full store check, which took 14.6–18 seconds with a 15-second timeout. In approximately every second session, the context silently failed to reach the agent, and the error was not visible. The hook was split into fast and slow. A broken engine now reports itself explicitly: an empty summary is indistinguishable from "no work."

The change being verified set the rules for its verification

The store bot decided whether a PR was process-related or content-related based on a list of process paths from the config. It read the config from the PR head itself. We checked: a PR that removes skills/ from process paths was classified as content – the bot approved it, and it merged without human intervention. Now, verification rules are taken from the target branch, and editing the config itself is always considered a process change.
