ChatGPT Limits and Local LLMs: My Experiment with Hermes Agent

I tested if local LLMs could offload work from Hermes Agent on a home PC with an RTX 3080 and 32GB RAM. I compared Qwen and GLM on architectural tasks, editing, and data extraction, experimented with different quantizations, and connected Hermes on a Mac to a Windows-based model. This article details the test conditions, speed and memory benchmarks, specific errors, and the reasons for ultimately choosing Qwen3.5 9B. While the connection worked, achieving the expected response quality and confirming cloud limit savings has not yet been successful. Read on.

Sometimes, in an hour of working with a cloud model, I exhaust my available limit. Then I wait four hours for it to reset. The task is already in my head, I want to continue, but I have to stop.

Lately, I've been looking more and more at the next ChatGPT tier for 100 euros. But my stinginess is kicking in: before paying more, I want to understand if I can do some of the work on my own computer.

I use Hermes Agent: I analyze technical documents, prepare texts, and review architectural decisions. A single request from me might involve reading several files, calling tools, and making repeated calls to the model, creating presentations, drawio diagrams, and other files. In this mode, the limit is consumed noticeably faster than in short chat conversations.

This is how I arrived at local LLMs. I wanted to maintain the familiar quality, and I was willing to wait longer for a response. I tested Qwen and GLM on my home PC, compared quantizations, connected the models to Hermes, and provided access to one of them from my Mac Neo.

Some might find this experiment amateurish: there are plenty of reviews online. But I wanted to try it myself, on my own hardware and for my own tasks. Such experience is more valuable to me than someone else's rating: now I understand exactly where the result is unsatisfactory.

What I Had

I didn't buy any new equipment. I used my home Windows PC:

  • Intel Core i9-10900;

  • 32 GB of RAM;

  • RTX 3080 with 10 GB of VRAM.

I used Ollama to run the models. The main executor in Hermes remained the cloud model; I connected local models separately and tested them both via API and within the agent itself.

This article is about a specific series of my trials. For each task in the comparative run, I received one final answer, so I wouldn't judge the entire Qwen or GLM family based on them. I was severely limited by my hardware. I prepared the test scripts and analyzed the answers using a paid cloud model. I saved the original local responses without corrections so as not to accidentally present the results of cloud post-processing as the capabilities of the local model.

At First, It Looked Promising

I started with Qwen3.5 9B in Q4_K_M. In the first short requests, it generated around 89 tokens per second on the GPU. Editing a small Russian text also seemed quite suitable for draft work.

But the very first architectural case showed why speed alone is not enough.

The prompt was roughly as follows:

The CRM sends an order via an integration service to the ERP. The ERP is sometimes unavailable or responds after a timeout. The CRM repeats the request, causing duplicates. We need to propose a solution and separately analyze the situation where the ERP has already created the order, but the response was lost.

The response contained familiar terms: queue, unique identifier, idempotency, state storage. At the same time, the model recommended saving the successful status immediately after sending the request or confirmation from the queue.

It is at this point that the solution breaks down. Confirmation of sending does not indicate whether the ERP has created the order. If the result is unknown, you cannot simply record success and return it on the next attempt.

In such an analysis, it's important for me to see if the ERP can handle a retry with the same key, if it allows finding an already created order, and how order creation is linked to key fixation. These capabilities were not confirmed in the prompt. Without clarification, the model should not promise safe retries of business operations or consider a lost response as proof of failure.

With reasoning enabled, the response became more accurate: it included a check of the key on the ERP side, and the model more clearly stated its assumptions. However, the description of storing the key in Redis with TTL left open the question of how order creation and key fixation are coordinated.

If you skim the response, such errors are easily missed. The text looks professional, but a crucial condition is lost within it.

Qwen 9B, GLM, and Qwen 27B on Identical Tasks

Next, I compared three models in Q4_K_M:

  • qwen3.5:9b;

  • glm-4.7-flash:latest;

  • qwen3.5:27b.

I gave them four tasks: analyze CRM-ERP integration risks, choose a data change transmission scheme, edit technical text without adding facts, and read a test file extracting data into JSON.

In this series, I configured a 32,768 token context window and enabled reasoning. The initial generation budget was 8192 tokens; if the response was cut off by the limit, a retry with a 16384 budget was provided. For text tasks, I used temperature 1.0, top_p 0.95, and seed 42. For the task with the tool, I used temperature 0.7 and top_p 1.0; num_batch was 128.

In this comparison, file reading was performed by a limited test handler. I tested the full Hermes cycle with its history, skills, and all tools separately later.

The example with change history is particularly telling. If a row changes multiple times between two polls, reading its current state again will not restore intermediate versions. An additional mechanism is needed to promise the saving of every change. The larger Qwen's response lacked this justification.

Also, one task's prompt simultaneously included a delay of no more than five minutes and the potential unavailability of the sole receiver for thirty minutes. No model explicitly addressed this contradiction. A queue can help preserve events but won't deliver them to an unavailable system within five minutes.

GLM and Qwen 27B correctly extracted all six verifiable values from the test file. However, both models added Markdown formatting around the JSON, even though only JSON was required. The values were correct, but the response format was violated. All three models, however, wrapped the JSON in a Markdown block, when only an object was required. I removed the wrapping separately for diagnostics. As a result, both the original response with the format violation and the result of its content verification are stored.

Will Less Aggressive Quantization Help

After comparing the families, I separately tested GLM-4.7-Flash in Q4_K_M, Q5_K_M, and Q6_K.

Quantization allows storing weights with lower precision and reducing their size. As you move to higher bit depths, precision loss usually decreases, but the model occupies more memory. The number of its parameters does not change because of this. The K-quantizations designation also does not mean that absolutely every weight occupies exactly four, five, or six bits.

I wanted to check how much quantization losses affect errors specifically in my tasks.

For comparison, I used Unsloth's control builds from a single pinned revision. I used identical tasks, generation settings, and a 16,384 token window. The initial budget and response processing were also the same.

Q6 showed some improvements. For example, in editing, it preserved the meaning of the phrase "implementation of the mechanism is not yet confirmed," whereas the Q4/Q5 controls wrote "the algorithm is not approved." For a technical document, the difference is significant: the absence of implementation confirmation and the absence of algorithm approval mean different things.

However, architectural errors remained. In one response, Q6 claimed that if the handler crashed between reading an event and marking it as processed, the events would be lost. In the described scheme, the record is preserved; the risk of duplicate delivery needs to be addressed first. In the data extraction task, the model correctly filled in the main fields and then added an unknown property to the list, which the source file had already explicitly defined.

Q6 worked, required more memory, and generated slower. I didn't see a noticeable advantage that would justify switching the working GLM from Q4. I cannot claim that any Q6 is useless or that Q8 definitely won't help: I didn't run Q8 in this series at all.

These results apply to the 16K window. Migrating them to 64K without separate memory checks would be risky: even in this run, the system RAM reserve for Q6 dropped to 5.29 GiB.

What Happened Inside Hermes

A model's response via API doesn't yet show how it will behave within the agent. It needs to select a tool, provide an exact path, read the result, and not hallucinate if the tool returns an error.

In a separate test, Qwen 9B as the main model for a local profile replaced (why?) the disk in the path from C: to Q:. The file wasn't read, but a response with data still appeared. Only one out of seven fields matched the control result.

In another run, the same Qwen received the task as a delegated executor with an explicit response schema. It read the correct file and returned the correct values for all seven verifiable fields.

The first run took 58.33 seconds, the second took 221.56 seconds. Another local sub-agent was running during the second run, so the time difference cannot be solely attributed to the task setup method.

What was most unpleasant for me in the first result was the willingness to continue after a read error. If the model didn't receive the source, I need a response stating that, not plausibly filled fields. The successful second run is useful, but after the first, I want to check repeatability on several tasks.

Which Model I Ultimately Kept

For further work on Windows, I kept Qwen3.5 9B in Q4_K_M. The main reason is memory consumption. With a configured 65,536 token window, the model fit entirely into VRAM and left more free system RAM.

In the tested run, Ollama showed about 7.03 GB of VRAM for the model. The minimum free system RAM was 19.26 GB. However, the total GPU utilization with Windows and other applications reached 9.67 GB out of 10 GB. The VRAM margin is still small.

Reasoning was disabled for the tested Qwen routes. For the local profile, I configured a 65536 window: my version of Hermes refused to launch the main agent with the initially selected 32K due to its minimum window requirement. I did not bypass this check.

Here too, the allocated window was tested, not processing a 64,000-token document. And these memory measurements were taken in a different series than the comparative model run above.

Qwen was kept because it puts less strain on system memory. Errors in responses have not disappeared. Comfortable long-term work alongside other applications and independent task execution still need to be verified.

What About the Mac and What's Configured on It

Since the model was already running on my home PC, I wanted to give Hermes on my wife's Mac access to it. This is her work laptop, and it also has demanding tasks, though not architectural ones. I didn't need to run a heavy model on the Mac itself for this.

I kept the main cloud model on the Mac. I connected the local GLM on Windows for delegated subtasks. The setup became:

Hermes on Mac
  ├─ cloud model coordinates work
  └─ local sub-agent:
       tools run on Mac
       model request → HTTPS gateway in home network
                       → Ollama / GLM on Windows PC

I set up access via HTTPS with certificate verification and a separate client key. I kept Ollama on the PC's loopback interface; I did not expose its API directly to the home network. The gateway provides access to the list of allowed models and generation, without loading or deleting models.

For testing, I had the actual sub-agent read a test file on the Mac. The tool ran on the Mac, the content was sent to the model on the PC, and the result was returned to Hermes on the Mac. The logs confirmed the necessary read and two Qwen calls via HTTPS. There was no substitution of the local response with a cloud one in this test.

It's important to understand where the data ends up: the file remains on the Mac, but the read text is transferred to the Windows PC for processing. The term "local" here refers to the home network and my equipment.

For the gateway, I also configured it to start after logging into Windows and to restore its child process after a crash.

On the gateway, I limited the number of active requests and added a waiting queue. However, Hermes on Windows continued to access Ollama directly, bypassing this queue. I have not yet tested simultaneous operation of two full clients. Therefore, it cannot be assumed that the gateway is already managing the entire overall load.

What I Learned from These Trials

On my PC, I was able to run both a small Qwen and larger models, compare quantizations, and connect another computer to the local server. I didn't need to buy new hardware for this, although initially, I wanted to buy an additional 32 GB of RAM.

The quality was worse than I hoped. The models identified some problems but made errors in the very areas for which I asked them to analyze the task. In the agent scenario, I separately encountered a response for a file that the model couldn't read.

Therefore, my next task is to find several useful operations that Qwen performs well and consistently: extracting specified facts, editing short fragments, summarizing provided material. When testing, I will check how much cloud post-processing remains after each result. And I also need to somehow get Hermes to use the free model more often.

On the bright side, I now have my own local LLM in case of a zombie apocalypse. If the internet goes down, I won't be completely lost with texts and local files. As long as there's electricity!)
