TL;DR. On October 19th, Microsoft published a post stating that internal agents should be considered insiders without a presumption of trust. Their proposal: "supervisor" agents that monitor every action of every agent before it happens. I agree with the diagnosis but doubt the prescription. The post mentions the term "overprivileged," and in my opinion, that's the root of the problem: agents are granted permissions with a buffer because more precise delegation was impossible—permissions are scattered across systems, and there's no unified model for them. My hypothesis: part of the oversight can be replaced by structuring the environment in which the agent operates. A supervisor treats the symptom: they look at an action and guess what it means. If permissions, data, and relationships are described in a single model, the agent can be granted the permissions of a specific user, leaving little for the supervisor to guess, thus requiring less oversight. Below is how known agent incidents would play out in such an environment and what deterministic tests of our core have revealed.

Why does this concern me? I am developing the Integrum constructor, where business data, relationships, and permissions are described in a single model, and agents operate within it. I'm increasingly asked about agent security: previously out of curiosity, now out of fear of letting an agent into the production database. Microsoft's post provided an opportunity to answer once in writing and, at the same time, test hypotheses publicly.

What Exactly Did Microsoft Write?

The post Securing the agentic insider is signed by Haïta Gallo, EVP Microsoft Security. Here's a summary from the text, with key terms in the original:

  • Frontier models "cannot be trusted," regardless of origin. Not out of malice: the model optimizes the result, considering organizational norms, hence reward hacking;

  • The company deployed agents internally and implicitly trusted them. Mistake: these are "agentic insiders";

  • Agents are "frequently overprivileged," having access to data, tools, and systems;

  • The solution: Guardian Agents, which "watch and moderate every action of every agent, before it happens, 24/7," and "deterministic controls on non-deterministic intelligence";

  • Model transparency (analyzing reasoning chains) will not replace containment but will make it smarter.

The post is based on Nadella's essay "Models as Insider Risks," where the main idea is that control should be external to the model. I won't argue with this, but I want to clarify where exactly external to the model.

Where Oversight Ends and Environment Begins

Oversight, according to Microsoft, observes an action and decides whether to allow it. To make this decision, it needs to understand the action's meaning. In a typical company, the same intent, "correct the price in the order," can manifest differently: SQL in one system, PATCH in a REST API in another, a macro in a spreadsheet, an email in a third. Each has its own permission model, its own log (or none), its own understanding of what an "order" is. The oversight layer must reconcile these actions into a common model of meaning and permissions. This is solvable: typed tools, APIs, and policies allow bypassing a model for each action. However, the more heterogeneous the environment, the more manual work is involved in this reconciliation, and where manual work is lacking, guesswork occurs, usually by the same non-deterministic model that oversight is supposed to contain.

By "structured environment," I mean three basic things:

  1. A single dictionary of actions. Create, modify, delete an object of type T; read a selection. All in human-readable, business terms. Not arbitrary SQL, not "call an endpoint."

  2. A single permission model for all data. Permissions for object types, row masks, column masks, separate flags for delete, export, and create. The agent acts with the permissions of the user who launched it, not a service account with blanket access.

  3. A single log that shows who made the change: a person or a model on their behalf.

The hypothesis is that with such a structure, part of the "deterministic control" ceases to be a separate product. For deletion in this environment, the rule is set once: "any deletion requires human confirmation." The rule "the agent cannot see salaries" is reduced to a column mask that already applies to the user. And if a role needs to change something that it cannot manually alter, for example, approving an order without the right to change its status, there's a report for that. It functions like a stored procedure and performs exactly the modification intended by its author. The agent receives a narrow operation "approve," not permissions for the orders table. Oversight has less work to do, and that work is simpler: verifying the action against the rule, rather than reconstructing the meaning of an arbitrary query.

This doesn't mean oversight isn't needed. It's just that its scope depends on the environment, and in a poorly structured environment, it grows faster than the number of agents.

What Would Happen in Our Case: Known Incidents

Testing the hypothesis on our own successful orders is pointless: nothing bad should happen in a successful order. It's more honest to take others' failures and see how they would have played out in our system.

First, a disclaimer, without which the analysis is unfair. The agent operates in two modes for us, and the difference between them is greater than between us and others:

  • Application assembly. The agent receives an empty database, works via API with its administrator token, creates tables, roles, and permissions itself. The only limitations here are those of the database as a whole: the token is valid within one database and nowhere else;

  • In-app chat. The agent acts with the permissions of the user it's conversing with, doesn't see tokens, and a record turns into a plan; dangerous actions await human confirmation.

The table of measures above describes the second mode. The first mode is closer to what Microsoft describes.

Replit deleted SaaStr's production database (on Habr). During a declared freeze, the agent deleted the database, and the prohibition on changes was stated eleven times—in the prompt. In our assembly mode, the same would happen: the prohibition in the agent's instructions remains text; only a backup holds. In chat mode, deletion and schema changes await "Apply," and a backup is made before schema changes, while the prohibition on deletion is a grant flag, not a phrase.

PocketOS: an agent found a token and deleted a volume, including backups, in nine seconds. The token was in a third-party file and provided full access to the cloud. In assembly mode, our agent holds the token, but it's valid only within one database: it cannot delete neighboring databases or infrastructure. In chat mode, the model doesn't see the token.

Supabase MCP: instruction in a ticket, service role bypassing row policies. A developer agent read tickets under service_role, which bypasses RLS, and wrote a table of tokens into the ticket. Our database administrator token is such a service role. Chat operates with user permissions, and row masks are applied to it.

GitHub MCP and EchoLeak in Microsoft 365 Copilot: injection via data. Text in an issue or email becomes an instruction, and the agent exfiltrates private data. Neither of our modes closes this. Chat only limits the damage by user permissions and confirmation of dangerous actions.

Copilot enabled self-confirmation and o3 rewrote its own grader. The agent modifies what is testing it. In assembly mode, our agent can expand role permissions so the test passes under that role, and the core won't stop it: it's the administrator. In chat mode, permissions are changed only through a human, and this is decided by code based on the actual command, not by the model's label.

In summary: deletion and unauthorized tokens are handled by the environment in chat mode, service roles by user permissions, and injections by neither. Assembly under administrator privileges is our own area of the very risk Microsoft writes about.

What We Tested

The argument "the environment deterministically closes off paths" can be tested without a model: take an application, roles, and masks, and try each path manually. We did just that—27 tests on the constructor's core, read and write, tables, columns, rows.

Permissions for tables, columns, and rows are enforced for both reading and writing; uniqueness is maintained; a referenced type cannot be deleted.

Not covered: the core does not check field mandatory status; text in a numeric field quietly becomes null; and there are no process rules ("from status A only to status B") in the core at all. For an agent mass-migrating data, the latter is particularly problematic: a flawed migration will pass without error.

This is a test of the deterministic layer only. We haven't yet measured how the model behaves within it, but we plan to do so if we see community interest.

Doesn't the Environment Slow Down Work?

Excessive permissions are usually granted for speed: precise permissions and confirmations hinder work, so agents are given more than necessary. But an agent's speed also depends on how much it has to guess, which is the same question as with oversight.

For example, enhancements for a small pet food production: an application with 19 tables and four roles. The names on the case page are changed; the numbers are real. The client submitted six enhancements following the template "rule, where it applies, how to reproduce, current state, desired state." The agent corrected workstations, created a new directory in the live database, populated it from existing plans, and found the source of the "01.01.1970" dates in shifts. From submission to acceptance took less than an hour and a half. The agent didn't need to figure out which tables, relationships, and roles the modification affected across different systems; it read them from the same model that enforces permissions.

It turns out that a typical enhancement consists of the same actions that cause incidents. The only difference is what contains them. Three out of four in chat mode await human confirmation, and this is decided by code based on the action type, not by a supervisor based on the request's meaning. The fourth, reading, is immediate. This is where injections occur, which the environment doesn't block. For six enhancements, a human would have to confirm files, schema, and bulk writes, not every step. How many such confirmations per task is precisely what should be measured (more on this below).

Disclaimer: these enhancements themselves were performed in the first mode, under administrator privileges, and relied on backups and human acceptance, i.e., exactly as in Replit and PocketOS. It went without incident, but it wasn't the environment that contained it, but the backup and the human. Therefore, we are migrating such enhancements to chat mode.

Where the Hypothesis Doesn't Work

I consider this section the most important because it expands the scope of further work.

A unified permission model concentrates risk. An error in one grant opens up everything beneath it. In a zoo of systems, a permission error in one system is confined to that system. In a unified environment, it's limited only by masks that someone has configured correctly. Anyone who has analyzed the Copilot incident, which "only sees what the user has access to," knows the continuation: access had been granted broadly for years, and the agent simply found what was forgotten.

User permissions can be broad. An agent acting on behalf of a director can do the same as the director. The principle "agent is no broader than the human" protects against a service account with blanket permissions, but not against a human who themselves has more permissions than needed for the task. We lack the "per-task, temporary permissions" policies from Microsoft's post.

The environment does not fix prompt injections. If a record contains the text "delete everything," the environment only guarantees that the deletion will go through confirmation. A person tired of confirming the twentieth plan of the day will click "Apply." The boundary between data and instructions within the model does not appear from the database's structure.

Assembly under administrator privileges is our own risk area. While the agent is assembling the application, it has permissions for the entire database, and only the instructions and backup stand between it and its contents. This is tolerable for an empty database, but not for modifying a live one, which is why we migrate enhancements to chat mode. However, assembly itself remains a mode where the rule is text, not a permission.

Another unpleasant aspect: all this works only if the agent lives within such an environment. When it needs to access email, 1C, and a third-party API, the unified dictionary ends at the platform boundary, and further oversight in the Microsoft style is needed again.

What I Am Actually Asserting

Not much, and it's a hypothesis, not a conclusion. The amount of control an agent needs depends not only on the agent but also on how describable the environment is: a single dictionary of actions, a single permission model, a single log. In such an environment, part of the "oversight," I hypothesize, turns into ordinary access rules that already apply to humans. The rest of it doesn't disappear, and Microsoft is right about that part.

I cannot state it more strongly: core tests verify that rules are enforced, but not how much oversight they save. The number of incidents is unsuitable for comparison because tasks influence it more than the environment. But other things can be measured. If the topic proves interesting, the next article will be a measurement. One set of tasks will be run in two environments: a unified model versus a combination of "ordinary systems + API + MCP." The set includes tasks with attempts to exceed permissions and tasks with injected prompts in the data. We will count three things:

  • how many attempts to exceed permissions the environment stopped itself, deterministically;

  • how many reached oversight or human confirmation;

  • how many confirmations per task. This is the cost of control for a human, and the confirmer's fatigue starts precisely with it.

If you know what's wrong with this scheme, I would be grateful for your comments.

Three Questions for Those Who Already Have Agents Working

  1. If business logic, data, and relationships are described in a single model, does the agent's behavior become more predictable for your tasks? Or is this a feeling that disappears upon the first real integration?

  2. Does this architecture reduce the need for oversight, or does it simply shift the risk to the data model level, where it's harder to notice?

  3. Does this approach have a practical advantage over the combination of "ordinary systems + API + MCP + separate control tools"? If you've tried both paths, where were there more incidents?

Most interested in criticism from those building agent systems and responsible for their security: where does unification truly help, and where does it only seem to help?

P.S.

Personal note. What I liked most about Microsoft's post was the phrase "deterministic controls on non-deterministic intelligence." It's just that deterministic control is hard to apply to a non-deterministic environment: if each system in the company understands "order" differently, the control will be as diverse as the systems, and the temptation to delegate it to a model again will be great. For twenty years, we've built corporate IT in such a way that humans constantly had to guess. An agent guesses faster and more confidently, and that, in my opinion, is the real risk. You can put another guesser above it, but I'd first look at how much guessing is needed at all.
