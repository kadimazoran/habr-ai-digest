I've collected the rules by which the agent created it into an open Agent Skill for Claude Code, Codex, and ChatGPT. All code is open-source under MIT: https://github.com/kiselas/every-frame-is-code

Out of the box, agents draw poorly

Modern models are excellent at writing code for Canvas and Three.js. The problem isn't the code, but the taste. If you ask to "create a beautiful animation" without specifics, Claude and GPT produce almost the same thing:

  • dark blue or almost black background, turquoise or amber accents;

  • bloom on everything;

  • random particles to fill the void;

  • all-caps title in the center;

  • everything moves linearly and simultaneously;

  • the only transition is a crossfade.

Each of these techniques is fine if chosen consciously. It's bad when they appear by default. The second class of problems is technical: the animation is tied to requestAnimationFrame and accumulates state, so it cannot be seeked or honestly rendered into a video — screen recordings with heavy frames result in stutters.

I've solved both problems with a single set of rules. Technical rules define the architecture, artistic rules define what a motion designer would tell an intern.

One function instead of a timeline: draw(ctx, t)

The entire film is a function that draws a complete frame based on time t and remembers nothing about previous frames. Everything else follows from this:

  • seeking to any second: the frame doesn't depend on previous ones;

  • rendering without stutters: the browser waits for each frame, no matter how long it takes to draw, and the MP4 still gets a smooth 60 fps;

  • one-line edits: change a curve or color, re-render, and get the same film with exactly one difference;

  • synchronized audio: the score reads the same list of events as the drawing code.

The contract with the renderer consists of three globals: meta, draw(t), and ready. The ready flag is set only after document.fonts.ready. If this is not done, the first frames will be drawn with a fallback font, and the text will "jump" in the video.

5 rules of determinism, or why Math.random() is forbidden

A pure time function requires discipline. The main rules:

1. Math.random() is forbidden in the drawing code. Only a seeded generator, like mulberry32:

Randomness is generated once during initialization, and only read in the frame.

2. Particles without state. A typical particle system stores positions and velocities and updates them every frame. Here, each particle receives constant parameters, and its age is calculated cyclically from t.

This is the basis for the fire in the demo: 650 particles, color based on particle age from a "white → yellow → orange → red → dark" ramp, additive blending (globalCompositeOperation = 'lighter'), and pre-rendered sprites instead of createRadialGradient for each particle. A gradient for each particle in every frame is the most common bottleneck in Canvas animations.

3. Trails without accumulation. A classic trail is a semi-transparent fill over the previous frame, and it breaks determinism. The replacement: draw the object at several past moments with decreasing transparency.

4. Spring in a closed form. Spring animation is usually integrated in steps, and the result depends on the frame rate. For a damped oscillator, there is an analytical solution, and it is already a pure time function.

5. If simulation is unavoidable (fluids, cloth, collisions), in render mode it's stepped with a fixed dt = 1/FPS strictly in frame order. For seeking in live mode, snapshots of the state are cached every N seconds.

The scene with the engraving in the demo clearly shows determinism: a line draws an astrolabe, the frame rewinds and plays again, exactly the same.

Rendering without stutters: virtual time, Playwright, and ffmpeg

The render script is 75 lines long. It opens the page with ?render, waits for ready, reads meta, and in a loop by frames calls __draw(t), captures the canvas, and pipes the PNG to ffmpeg's stdin.

Time here is virtual: frame 1234 always corresponds to t = 1234 / 60, even if it took half a second to draw. That's why 20,000 shader particles with bloom in Three.js produce the same smooth 60 fps in MP4 as a blank screen. The --from and --to parameters allow rendering only a portion to check an edit.

Audio without samples and a bug with negative time

Music is synthesized with Web Audio: oscillators, filtered noise, envelopes. No samples. The main principle: the visuals and audio read the same data structure — BPM, event list, voiceover timings. Therefore, a beat on screen and a beat in the music coincide by design, not by adjustment.

All synthesis functions accept a context, so the same score works in two modes. In live preview, it's a regular AudioContext. In rendering, OfflineAudioContext calculates the entire track faster than real-time, and the page outputs WAV in base64.

The render script sees __renderAudio, saves the WAV to a temporary folder, and pipes it to ffmpeg as a second input. It mixes in the voiceover, if any, via amix.

The pitfall I stumbled upon during the demo's publication. In live mode, sound is enabled by click, and a click can occur mid-film. Then, past events need to be skipped.

The check currentTime > 0 was needed to avoid skipping events in offline rendering. However, a newly created AudioContext also has currentTime equal to zero. As a result, when clicking at the 20-second mark, the score tried to schedule past notes at negative times and crashed with RangeError: Time must be a finite non-negative number. The visuals continued, so the bug didn't manifest during local checks "from the beginning." It's fixed with one line: in offline mode, T(x) = x ≥ 0, and the check is not needed at all.

13 transitions as data instead of one crossfade

Transitions are described by an array, like scenes and events. Each scene is drawn to its own offscreen buffer, and the transition blends two buffers based on progress p:

The subtlety is that both scenes continue to live during the transition: the scene is selected by key, and drawn by the current t. Otherwise, the outgoing scene "freezes," and the transition looks cheap.

The catalog contains 9 transitions on Canvas 2D (iris, push, wipe, whip pan, zoom-through, glitch, light leak, dip, crossfade) and 4 on GLSL (burn dissolve, wave, chromatic split, luma wipe). But the main point of the chapter isn't the code, but the hierarchy. The best transition is motivated by the movement within the frame: a foreground object obscures the camera, the camera zooms into a detail, a flash fills the frame with white. The worst is a crossfade as the sole tool. Rule for the agent: no more than two or three types of transitions per video, and each type tied to meaning.

The agent checks itself: the contact sheet

The most underestimated part. An agent that has written code and said "done" almost always makes mistakes in composition: text overlaps an object, nothing happens for three seconds, an element goes off-screen. It doesn't see this itself because it doesn't look at the result.

Therefore, after each render, the kit forces the agent to assemble a contact sheet (a frame every half second on one image), look at it, and describe what it sees before making any corrections:

./render/contact-sheet.sh out.mp4 sheet.png

A multimodal model reads such an image well: it reveals rhythm, empty areas, repeated shots, and brightness jumps. Then, edits are made by timecodes: "at 0:14 the caption overlaps the sphere" instead of "something seems wrong." There's a checklist for verification: text within safe zones, reading time at least 0.3 seconds per word plus one second, no static segments longer than two seconds, cuts on strong beats, loudness around -14 LUFS, two renders match.

Taste in rules: what weans the model off defaults

The agent masters the technique easily, but taste is harder. Several rules from the brief had the most noticeable effect:

  • Nothing moves linearly. Every movement follows a curve; large objects have overshoot and undershoot. Appearance uses outExpo, disappearance uses inExpo, movement within the frame uses inOutCubic.

  • Stagger instead of simultaneity. Group elements start with a 30–80 ms offset.

  • Boldness in one place. One memorable solution per video; everything else is disciplined.

  • Style follows theme. The history of science — engraving and aged paper. Code — phosphor terminal and ASCII. Children's theme — gouache and warm light. Space doesn't have to be neon: linocut or Soviet popular science illustration would also work.

  • One world, not slides. The camera moves in continuous space, scenes flow into each other.

The demo shows this with a single composition run through 12 palettes with cuts in sync. The cuts accelerate towards the climax, and before it, there's a second of complete silence.

How to package rules into an Agent Skill

The kit is formatted as an Agent Skill — an open format understood by Claude Code, Codex, and ChatGPT. It's a folder with SKILL.md, which has a description in its header. This tells the agent when to connect the skill.

The body of SKILL.md is a short router. First, the agent must read a concise brief of 20 rules, and then only the chapters needed for the task: for a game — about game feel, for 3D — about Three.js. This way, the context isn't cluttered with almost 70 KB of text when only a fifth is needed.

Installation in Claude Code:

git clone https://github.com/kiselas/every-frame-is-code ~/.claude/skills/motion-kit

In Codex, it's the same, but in the ~/.agents/skills/motion-kit folder. For ChatGPT and Claude.ai, there's a zip that's built in CI for each release tag and uploaded via skill settings.

Where the approach doesn't work

  • Rendering via canvas screenshots is reliable but not fast. For a minute of 1080p60, that's 3600 screenshots, so it's more convenient to render drafts at 30 fps and in chunks using --from/--to.

  • Complex character animation is not a strong suit of the approach. Strong suits are motion graphics, typography, effects, stylized scenes, infographics, and mini-games.

  • Rules don't replace direction. The kit weans the model off defaults, but the best results are achieved when you set the style.
