The logical question arose: how to spend it? According to the contest rules, a grant is given to projects with a clear development plan. Finding an Idea, Getting Acquainted with Yandex's Plugin, and My Own Domain

While thinking about where to direct the grant and my efforts, I first searched for: "What project is most promising to write right now?" The answer was obvious and expected: a product for local AI coding.

The idea seemed excellent to me for four reasons:

  1. The topic itself is very interesting to me, as ML has been my hobby for the last few years.

  2. My np and a couple of my own linear algebra libraries could be used as a foundation (which couldn't be submitted to the contest directly due to the "one project – one developer" rule).

  3. Double bonus: this tool would remain with me even after the grant ends, and I could use it for my own work. Tools make tools that make tools that...

  4. The entire community could use it for free.

It was mid-2026. No sooner said than done: I decided to write my own local coding agent without these drawbacks.

Around the same time, I stumbled upon a VS Code plugin from Yandex — SourceCraft Code Assistant (as far as I understood, a fork of Roo Code). When I saw that SourceCraft published it on the marketplace with a binding to its own domain, I decided that a proper extension publication wouldn't be possible without my own domain. The question arose: what to name the project? I wanted the name to be related to coding (since that was my focus), and at the same time reflect a love for minimalism — as an old C++ enthusiast, a lover of low-level optimization and squeezing every byte, I wanted something compact. Thus, the name TinyCoder was born, and I immediately registered the domain for it and all related projects — tinycoder.dev.

I decided to use Yandex's plugin itself to test the process, but quickly realized that working with it was painful:

  • You can't interrupt the dialogue. If the model goes off track, you can't just add a reply to the queue and hope the model sees it. You have to press Cancel to stop the model's processing, after which all the painstakingly typed messages from the queue disappear without a trace, and only then can you write a new message. I developed a whole ritual: write text → copy to buffer in case of cancellation → press Cancel to bypass the limitation and interrupt the dialogue → paste from buffer → press Enter. Convenient? Undoubtedly.

  • Visual noise. The assistant was too talkative, and almost every line started with the useless SourceCraft Assistant said, which just took up screen space.

Nevertheless, I continued to use it because the grant could be spent on Yandex's cloud LLMs, which SourceCraft Assistant supported, and I preferred to work in VS Code. Although the work itself increasingly less involved manual code editing, and eventually, the need and sense for it disappeared altogether. The need for an editor as such diminished. However, I still used it to push to the repository — I didn't trust the model with this operation.

There was also an option to rent a powerful virtual machine with a GPU using the grant money, but it seemed too expensive — the budget wasn't unlimited. In the end, I continued working on my old home PC: Intel i7-4790K, 32 GB DDR3, and an RTX 2080 Ti (11 GB) graphics card.

Concept and Goal: Minimum Footprint and Outperforming llama.cpp

I conceived TinyCoder as a tool that is minimal in size but maximally "smart" and versatile in functionality. I had to start and debug the base on my old RTX 2080 Ti (which is what I'm still doing).

Strangely enough, the very first tentative attempts yielded results — I managed to beat llama.cpp on CPU during the prefill stage (processing the input prompt) by about 30%. Then began several months of continuous "tuning" with neural networks. Most of the time, I ran DeepSeek V4, and later switched to DeepSeek V4.1 Flash — they turned out to be cheaper and at the same time produced better code than more expensive models like gpt‑oss-120b or Qwen3-235B.

In parallel, I had to manage to create not only a fast inference engine but also a convenient harness (wrapper around the model) before the grant ran out. This was precisely where the biggest problems lay: I had only two examples before my eyes — SourceCraft Assistant and OpenCode. I had to urgently switch to the latter after SourceCraft broke on October 11, 2026, following an incident at a Yandex data center. As a result, I managed to outperform llama.cpp not only on CPU but also on GPU.

How Inference Works Under the Hood (tinycoder-inference)

tinycoder-inference is not a wrapper around ggml or PyTorch, but an engine written from scratch in C++20 and CUDA without a single third-party inference library inside (external code only uses my np library and the standard cuBLAS for dense matrix multiplications). All kernels for dequantization, int8 stream-K MMA GEMM, warp flash attention, Gated‑Delta‑Net recurrent kernels, and samplers are implemented directly in the repository.

What the engine can do right now:

  • Supported model families: Qwen2.5, Qwen3.6, and Qwen3.8 (both dense qwen35 and MoE qwen35moe), Ornith, Gemma 4, and Prism ternary models Ternary-Bonsai.

  • Native support for two formats without conversion: Model::load automatically detects the input format. Supported formats include GGUF v3 (K-quants from Q2_K to Q6_K, IQ series IQ2_XXS—IQ4_XS, and ternary pq2_0) and EXL3 — the exllamav3 format is read directly from the Hugging Face directory (config.json + *.safetensors + tokenizer.json) without PyTorch and Python overhead per token.

  • Two paths for prefill and fast decode: when processing the input prompt, the engine chooses between cuBLAS fp16 and its own int8 MMA kernel (quantizes activations to Q8_0 and reads blocks directly from VRAM). During generation, GEMV kernels with on-the-fly dequantization and CUDA Graph computation graph capture are used.

  • Running large MoE models on 11 GB VRAM: for models that don't fit entirely into video memory, a hybrid mode is implemented — the dense part of the model remains in VRAM, and experts (e.g., from the 34.4 GB Ornith-1.5-35B-A3B) are streamed through the arena layer.

  • Context scheduler based on actual memory: instead of hard constants, the engine measures free VRAM/RAM before loading the model and selects the KV cache precision itself (f32 with int8 mirror or pure int8). This allows fitting up to 196,352 tokens of context for a 9B model and up to 64,256 tokens for a 27B model on an RTX 2080 Ti.

  • CPU backend with on-the-fly SIMD instruction selection (runtime dispatch): if there's no graphics card, the engine automatically detects the available instruction set (AMX, AVX-512, AVX2, or scalar fallback) and parallelizes computations via OpenMP.

Architecture: Separating the Engine from the Plugin and Writing an API Gateway in Go

To avoid being tied to a single editor, I separated the original product into an independent C++20/CUDA engine tinycoder-inference and the VS Code plugin-harness itself (it connects to the core via CMake FetchContent and communicates with it through an N-API bridge).

Then, I wanted even greater versatility — so that the engine could be used with any external harness (OpenCode, Roo Code, Cline, etc.). This led to the idea of implementing a standard OpenAI API. What to write it in? I professionally develop in Go, so the solution was obvious: create a separate Go project — tinycoder-openai — which interfaces with my C++ library via CGO.

The idea paid off completely: the Go service executable itself weighs only 9 MB, and all the native C++/CUDA components are moved to a shared library libtinycoder_bridge.so weighing 145 MB (no Python stack and heavy external frameworks — except for the system CUDA Toolkit/cuBLAS). The gateway supports out-of-the-box:

  • Two popular APIs: OpenAI endpoints (/v1/chat/completions, /v1/responses) and Anthropic Messages API (/v1/messages).

  • Agent interaction: built-in tool_calls and SSE streaming with keep-alive during long prefill times.

  • Safe generation interruption: cooperative abort within the C++ model layer loop for instant VRAM release.

  • Memory management: lazy model loading on the first request and automatic VRAM unloading via LRU timeout.

Why the Focus Shifted to the Engine

Ultimately, I focused my main efforts on developing the inference engine rather than the harness. As it seemed to me, unlike the world of harnesses (where there are already choices), the world of local engines is still characterized by disarray and chaos: there is no single, powerful solution that would bring together under one umbrella all quantization formats, support for graphics cards available to ordinary consumers, good out-of-the-box support for NVLink and low-bit quantizations.

Every developer and user should have the opportunity to run the exact model and quantization that best suits their task, rather than adapting to the limitations of a specific library. Therefore, the project's focus gradually shifted to the main idea — to create a local engine that is ideal for me: it runs on very modest and old hardware, but allows comfortable operation of quite powerful models.

What the Engine Has Been Tested On

Currently, the entire base is debugged on the Turing architecture (RTX 2080 Ti), debugging is in progress for Ampere (RTX 3090), and newer graphics cards work via compatible PTX JIT or basic SASS.

Development Plans

But there is still a lot of work ahead. In the near future:

  • Speculative decoding

  • Separate optimized kernels for modern GPUs: specialized CUDA kernel tuning for RTX 4090 and 5090 (Ada Lovelace and Blackwell) to maximize throughput and tensor core utilization on each architecture.

  • Multi-GPU and NVLink: running large models on multiple graphics cards in one PC with support for direct exchange via NVLink.

  • Distributed inference over a local network: the ability to combine the computing resources of multiple home machines into a single cluster for running heavy checkpoints.

  • Intel Core Ultra NPU support: porting inference to the integrated neural accelerators of modern Intel processors for autonomous operation without discrete graphics.

  • New quantization algorithms: expanding support for modern ultra-low-bit weight compression formats.
