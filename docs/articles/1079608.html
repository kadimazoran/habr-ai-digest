The webinar from which I made the article was conducted by Lauren Tan from Cursor. The webinar topic is trust in AI agents in development: how to reach the point where agents merge PRs without your involvement (about a built verification system).

Below is a summary for those who want to understand the case in Russian. Enjoy )

Lauren Tan joined Cursor five months ago; before that, she worked at Meta on the React compiler and at Netflix as a tech lead. She talks about how she built a workflow with agents that allows her to wake up and see 20 merged pull requests without needing to personally review each one before merging. She believes the key problem when working with agents is trust. When you don't trust an agent, you are forced to constantly engage in the process and check every action. This greatly limits your productivity; you cannot parallelize work and run multiple agents simultaneously because you don't trust any of them.

Lauren draws a parallel with managing people. If you are a manager and don't trust your team, you start micromanaging, spending time checking every commit. It's the same with agents. But if you can build a system that gives you confidence in their work, you move to a new level where agents work autonomously, and you only review changes that have already been accepted.

Lauren showed a graph with the level of trust on the vertical axis and time on the horizontal axis. A year ago, when few people used agents for coding, developers had to sit next to the agent, read every output, correct prompts, and couldn't run more than a few agents in parallel. Lauren admits that her first month at Cursor was not very productive because she was just getting acquainted with the codebase and didn't understand what the agents were doing. However, as she gained skills in managing agents, her personal productivity increased sharply. Last month, she merged a thousand pull requests, and in the first 12 days of the current month, almost 800. This sounds incredible, and she understands that listeners will have questions about the quality of such code. PR length ranges from 50 to 1000 lines.

According to Lauren, the most important skill in the arsenal of anyone working with agents is verification (AI Evals). Verification means the agent's ability to independently run code, take CPU traces, open an iOS simulator, or otherwise test its work in a real environment. This closes the loop. Verification doesn't guarantee that the code will be good in terms of architecture, but it guarantees that the code will be correct. And that's a huge step forward towards trust.

As an example, Lauren tells a story about the agent window in Cursor, which is called Glass internally. When she joined, she was tasked with helping with this component because it was written in React, and she had relevant experience. But the deadlines were very tight, and she realized she couldn't figure out the performance issues alone. She opened Chrome DevTools, looked at flame graphs, but the codebase was new to her. Then she decided to involve an agent, but the agent also had no idea what to do. The process was slow because she was the sole verifier—she would run the build, see it didn't work, copy errors and screenshots, pass them to the agent, wait for corrections, and so on. It was a bottleneck.

Then she created a skill called control glass, which allowed the agent to manage the process independently, i.e., run a local build, connect via Chrome DevTools Protocol, take traces, and analyze them. But even then, the agent didn't know how the agent window itself was structured. If someone reported that the left sidebar was lagging or the PR tab wasn't working, the agent would start searching randomly in the code, not understanding how to get to the desired UI element. This made it almost useless.

The solution was a feature map—feature map. This is a file that describes all the main interface elements—how to access them, what keyboard shortcuts exist, what DOM attributes are used to highlight elements via CDP. Lauren implemented this in her plugin Pstack, which can be found by searching for "Pstack cursor". It has a command create verification skill that analyzes the code and builds an initial feature map. This allows the agent to process even very vague reports, such as just a screenshot with three question marks. The agent knows where a particular function is located, how to reproduce an action, and what to look for.

The Pstack plugin provides agents with enhanced context about the codebase, functions, and navigation methods. This plugin relies on the Pretext library (Lauren recommends looking into it) to ensure reliable verification and reduce the need for constant manual oversight.

The Pstack plugin was not born as a standalone product but as a set of skills that Lauren wrote for herself while observing agent failures. She noticed that an agent would often confidently state the cause of an error without reading the code that might have been affected. So, she created the HAL skill, which instructs the agent not to guess but to always read the relevant code and use sub-agents for searching. This is similar to working with a new engineer who doesn't know the business context. You give them instructions, and through skills, you can extract much more intelligence from the model because LLMs work by predicting the next token, and if you give them quality initial tokens, they will follow a more reasonable pattern.

But skills.md needs to be maintained because the product changes. For this, Lauren uses evals—essentially, modular tests for agents. Pstack has an eval playbook where the main coordinator agent creates a rubric of what the skill should do, launches multiple sub-agents in separate directories (with directory names chosen so the agent doesn't guess it's being tested, otherwise it might change its behavior), then evaluates the result, and you can use different judge models for cross-checking. Lauren runs such evals every time she changes skills and uses loops (for) to bring the evaluation to an ideal state.

However, your observation and intuition remain critically important. Lauren advises being an active driver, not a passive observer. Open every tool call, read the agent's thought blocks, look for places where it stumbles, and turn each such place into a new skill.

When local verification is debugged, you can move on to cloud agents. Lauren emphasizes that this is the next level, but you shouldn't jump directly from full control to a thousand cloud agents—you'll just waste a lot of tokens and money. You need to build trust gradually.

Inside Cursor, developers use an agent named Benny, who automatically handles all incoming bug reports. Benny runs in the cloud, opens its own instance of Cursor, uses the same verification skills to navigate the application, and tries to reproduce the problem. If the bug is already fixed in the main branch, Benny confirms it, and all that's left is to release a new build. This saves hours of manual labor and provides information to the entire team, not just an individual developer.

A separate topic that Lauren touches upon is refactoring and code rewriting. She says that despite Meta having tens of thousands of great developers, the overall code quality is not very good (she said nothing about the current code quality with agents at Cursor, except that feedback is often very poor). Lauren believes that projects created from scratch using vibe coding are particularly dangerous. When there are no constraints, agents solve each task in the shortest way, and over time, the codebase turns into chaos that no human understands, and the agents themselves figure it out in their own way and structure it to solve tasks in the shortest path, not in a way that is understandable to humans. In large companies like Meta or Google, there are strict frameworks, regulations, and safeguards designed for the most inexperienced engineers. In such an environment, agents can already work well because the constraints are built-in by experienced engineers.

For Grokbot, Cursor's new product that orchestrates agents, Lauren created an architecture called Dune. This is not an open library but a set of principles that can be adopted. The main idea is to make the shortest path also the most correct one. For example, each function is placed in its own directory, and agents know that to change a specific function, they should only work within that folder.

CI is annoying with its strictness; strict CI checks (disallowing useEffect, disallowing comments, checking dependency graphs, etc.) make the coding process meticulous and irritating. The CI implements checks at the dependency graph level so that code from the renderer process does not import heavy modules that should only run in the main Electron process. All patterns that are poorly handled by agents are prohibited: for example, useEffect in React, because it's a common cause of performance issues and agents often use it incorrectly. Even comments in the code are prohibited because agents tend to insert meaningless notes like "Lauren said never to do this," which only clutters the code.

Lauren builds a system with several levels. The strongest is static analysis and CI checks, which strictly prevent violations. Then come linters and compiler diagnostics. And only then come the rules and skills that an agent might forget to apply. She warns that if you rely solely on text-based rules, the codebase will quickly turn into garbage. Therefore, any remarks you frequently make in reviews should be turned into automated checks.

Regarding token costs, Lauren admits she works at a company with a virtually unlimited token budget, but she suggests viewing the issue as ROI. Yes, initial refactoring and skill creation consume many tokens, but if you choose a development model where agents write most of the code, the costs will be recouped through reduced hiring and increased team speed. Furthermore, the Grok 4.6 model was recently released, which is significantly smarter at the same token cost, further improving the price-performance ratio.

Lauren notes that the current architecture benefits not only developers. At Grokbot, designers and product managers can also submit code because strict constraints make the process safe even for non-professional engineers. For example, one PM independently fixed a bug, submitted a pull request, and it passed all checks. This allows the team to move much faster.

In conclusion, Lauren reiterates that the path to trust has no shortcuts. Every developer has their own quality standards, and only through constant observation, skill creation, and automated verification can you reach a level where agents work on autopilot, and you can focus on higher-level tasks.
