Classic and Agentic RAG

I won't go into a detailed explanation of the RAG concept, as there's already a simple and detailed explanation on Habr. In short, it's a system to constrain LLMs so that the model answers based on the company's internal knowledge base, rather than the documents it was trained on. To achieve this, when a user asks a question, the system finds fragments in the base that are most relevant to the query and includes these fragments in the LLM's context.

A classic RAG pipeline operates in a single pass: a query comes in, the system accesses the database once, generates an answer, and stops. Such a pipeline is simple to build and test, and its operational cost is predictable.

Agentic RAG is structured as a feedback loop. The LLM itself decides which search tool to use, how many times to access the database, and whether to access it at all. For a simple question, an intelligent agent will perform similarly to a classic pipeline. For a complex one, it will perform multiple iterations: first, it will search, then evaluate what's missing, adjust the query, and access the database again. This cycle continues until the LLM is confident that the answer is complete.

Note

There's a nuance with terminology here. Strictly speaking, a pipeline becomes agentic only when the LLM controls the entire process, meaning the pipeline is non-deterministic. For example, if we decide to improve the system's response quality for complex queries and add a step to evaluate the intermediate answer quality using a small LLM, followed by a single re-search in the database if the intermediate answer quality is low. In this case, the pipeline is still considered classic, not agentic, because the set, number, and order of search and generation steps are deterministic, i.e., "hardcoded" into the system.

The flexibility of an agentic pipeline comes at a cost. An agentic system is slower and more expensive, has more failure points, and is harder to test because, in addition to the final answer quality, you need to verify if the agent chose the right tools, if the number of steps was optimal, and so on.

In practice, a hybrid approach works well, using a cheap router model that decides whether to send the query to a classic or an agentic RAG. Approximately 80% of user queries are simple and are efficiently handled by the classic pipeline. The remaining complex ones are routed to the agentic pipeline. I don't recommend starting a project directly with agentic RAG. Even when it's evident that a simple scheme won't suffice, a classic pipeline is still needed as a baseline for comparison.

Data Handling Nuances 

The successful operation of RAG systems primarily depends on data quality. It must be up-to-date, consistent, and complete. However, developers often have limited influence over this; it requires expert time, which, based on experience, is never enough for a "general cleanup of the catalog." We have a Data Validator module for this procedure, which assists analysts by finding duplicates, inconsistencies, and suggesting ways to handle them (merging, archiving outdated information, etc.). Our solution is not universally applicable, so ML engineers often have to work with what's available. In such cases, correct data processing becomes a key aspect of the work.

In a RAG system, data is prepared during the indexing stage, which typically includes chunking (splitting into fragments), vectorization, and building a storage (e.g., a vector or graph index).

Indexing

This stage can be compared to organizing a pile of books into a cataloged library storage, allowing for quick and easy information retrieval.

Chunking

Documents like a lengthy Confluence article or a hundred-page PDF are unsuitable for search due to their size, so they are broken down into fragments, also known as chunks. There are several ways to split text into chunks: you can simply divide it into equal-length pieces, split by structural blocks (if they exist, like in markdown), or ask an LLM to identify semantic blocks and cut along their boundaries. The latter approach increases indexing costs but significantly improves quality for poorly structured documents containing mixed text, tables, and screenshots. This method also results in semantically coherent chunks, preventing extraneous context from being mixed in.

The chunk size in tokens depends on the RAG system's tasks. For a question-and-answer database, around 200 tokens per chunk are sufficient, allowing a question and its answer to fit within a single fragment. For typical informative articles in Russian, I aim for approximately 1000 tokens, and for dense legal documents, I use even more.

Chunk length and data type can be critical for successful search. I encountered a RAG assistant that consistently provided nonsensical answers, despite adequate model and other parameter settings. It turned out the database was chunked into fragments of 100 tokens. For Russian, this is quite small, and the content was rich: instructions with Excel functions and their explanations. Splitting into such small pieces turned them into incoherent snippets of formulas and fragments of descriptions. During search, a jumble of information was pulled, from which the model could not construct a meaningful answer.

Adjacent chunks must have an overlap, typically around 10% of the chunk size (e.g., 100 tokens for a 1000-token chunk). This prevents the semantic flow from breaking at the fragment boundaries.

Index Types

Further processing of chunks depends on the type of storage for our data, which determines how we will perform searches in the future. A semantic index uses vector representations of text, converting chunks into dense vectors (embeddings). Such an index is excellent for capturing the semantic nuances of natural language queries and user intent. 

A full-text index excels at keyword and term searches and is built around word frequency. For this, chunks are converted into sparse vectors (typically using the BM25 algorithm). 

For classic RAG, a hybrid approach is usually optimal: both indexes are created, and the search results from the semantic and full-text indexes are merged into a common list.

Besides semantic, full-text, and hybrid indexes, there's also a graph index. To create it, an LLM extracts entities and their relationships from documents, forming connected groups and semantic descriptions, and then builds a graph. Graph search works best for multi-hop queries where the answer needs to be assembled from several disparate sources. An example from banking: a user asks a RAG assistant about approximate loan conditions for their specific case, but no single article contains the complete answer. In this scenario, the graph helps the model connect conditions from one document with the client's specific circumstances from another and employee benefits from a third.

However, we jokingly call graphs "the path through Mordor." They are more complex to create, more expensive to maintain, and the graph needs to be rebuilt every time documents are added. The advice here is simple: start with hybrid search, and only resort to graphs if the response quality still suffers with well-annotated data.

Vectorization 

In a semantic index, the choice of vectorizer/embedder heavily depends on the environment. In environments with external API access, we use OpenAI text-embedding-3-large. In closed environments, we use BGE-M3; in our experience, it's the best open-source model and a versatile choice. E5 is also frequently used. We've tried Qwen Embedding, but it performed worse than BGE-M3 on our tasks.

For full-text search, no vectorizer is used at all; BM25 (or another algorithm) builds a sparse vector for each chunk. The dimensionality of this vector equals the vocabulary size, and non-zero values represent term weights based on their importance in the documents.

Search

We will examine the most typical case of hybrid search, where the search is performed simultaneously on semantic and full-text indexes.

  1. First, the system prepares the search query. Depending on the implementation, the query can be rewritten, expanded, or split into parts to stylistically align it with the chunks in the database, thereby obtaining more representative search results. Additionally, real-world systems almost always support dialogue history: it's first determined whether the current query is self-contained or related to the previous *k* exchanges (e.g., five), after which the history of *k* exchanges or its shortened version is appended to the query.

  2. Next, the user's query is transformed into a dense vector (semantic search) and a sparse vector (keyword search). Naturally, we use the same vectorizer or algorithm as during index creation. 

  3. Search in the semantic index is typically conducted based on the cosine similarity between the query vector and the database chunk vectors. For full-text search, the engine iterates through the inverted index, retrieving lists of chunks where terms/keywords appear, and calculates a cumulative score for each chunk. In hybrid search, the two result lists are merged into one using the Reciprocal Rank Fusion algorithm and passed further down the pipeline, for example, the top-10 candidates.

  4. The next stage often involves a re-ranker (most commonly a cross-encoder), which reorders the top chunks to optimize the output. The transformer model processes the list and assigns a semantic relevance score for each "query – candidate" pair. Fragments are sorted by score, and for generation, for instance, the top 3–5 most important ones are sent.

Top-N Search Vulnerabilities 

  1. The value of N is fixed. With a small N, coverage obviously suffers, but a very large N is not a panacea either. If the desired chunk is at position N+1, falling short by a fraction of a percent from its neighbor, it won't be included in the context. Simply increasing N won't solve the problem, as a large N increases the system's cost and response time. Furthermore, a larger number of chunks will inevitably introduce more noise into the context, reducing answer quality.

  2. The search evaluates the proximity of each chunk to the query but does not evaluate chunks relative to each other. Whether they complement each other or provide new information is not considered by either the search or the re-ranker. Chunks close to the query are usually close to each other as well. Therefore, the top results can be filled with duplicates, wasting context space.

  3. There is no holistic representation of the database. For general questions like "What topics can you tell me about?", the system cannot list more than N topics because it physically cannot see the entire database. Complex multi-hop queries, which require discovering non-obvious connections not present in a single chunk, suffer the most.

Generation

At the final stage, the prompt plays a crucial role. It explicitly incorporates the retrieved chunks, the role, task, and constraints, as well as rules for handling sources. For instance, we often require a link to the source after each fact. There is no single standard; the template is always adapted to the specific system and then refined iteratively.

Among the generation parameters, temperature is the most important. For factual answers, it's kept close to zero; high temperature adds creativity and, along with it, hallucinations.

If the risk of providing a false answer is high (e.g., the assistant interacts not with an internal user but with a client), it's beneficial to add a critical evaluation and final correction step. In this case, the draft answer goes through an LLM judge: it cross-references the draft with the retrieved chunks, identifies statements not present in the context, and formulates the final answer.

Quality Evaluation

A scientific approach to RAG evaluation seems effective but falters in practical scenarios. For example, to assess search quality, it's suggested to calculate Recall@K, i.e., the proportion of cases where the relevant chunk appeared in the top results. If Recall@10 < 0.7, other metrics can be disregarded. Additionally, metrics like NDCG and MRR are evaluated, which indicate how high relevant documents rank in the results. For generation, there are even more metrics, ranging from answer relevance and completeness to hallucination frequency and citation correctness.

The problem is that creating test datasets and annotating them for metric calculation is feasible only for academic teams or product teams building RAG in-house, dedicating many expert hours to it.

In custom development, things are a bit different because a typical client for RAG systems has neither datasets nor an understanding of metrics. The client wants it to "work with 95% accuracy" – whatever that may mean :) A contractor cannot create meticulously annotated datasets according to all rules without the client's expert assistance, who are already overloaded. The assistant is implemented precisely to alleviate their workload.

What to do in such a situation? In practice, LLM-as-a-judge is used, where a judge model evaluates the quality of the system's answers against a reference answer. If the service already functions in some capacity (e.g., human-provided technical support), it's optimal to take real historical queries from the current service, phrased exactly as users asked them, and the employee's answers. For a new service with no historical data, it's highly desirable for the client to provide at least 20 examples of questions and their reference answers for system calibration. Otherwise, all test data will have to be synthesized. It's best to synthesize at least with some input on expected typical user queries (user stories). Then, these questions must be run through the system, and the resulting answers sent to the client's expert for correction: are the questions adequate, and are the answers correct? In my experience, experts find it much easier to correct a draft than to write their own "reference answer."

The test set of question – system answer – reference answer is sent to the LLM judge, who is asked to evaluate the quality of the system's answer compared to the reference. The model can operate on a binary scale of "good/bad," but I prefer a scale from 1 to 10; based on our experiments, it's more informative and reproduces more consistently from run to run. You define the scale and conditions in the LLM judge's prompt: what warrants a deduction, when to assign a one, and when a ten.

When the system goes into production, it can be monitored similarly. To do this, continue creating new datasets in the same way: collect real people's questions, run them through the system and the LLM judge, validate them through experts (not all, but a random 5–10% or the most problematic ones), and check the system's answers for deviations from the reference. Even more importantly, use the same reference datasets before releasing any changes. If you've changed a table parser or chunk size, run the system against the dataset and ensure it hasn't regressed.

And finally: do not rely on user ratings (answer good/bad). People very rarely give likes/dislikes to an answer and even less frequently write anything substantive in comments if the answer was unsatisfactory. A single 'dislike' without context is useless because it's unclear if the system made a mistake and what needs correction. So, CSI in RAG system accuracy evaluation is secondary at best.

What Breaks

Degradation Over Time

Let's return to the main problem of RAG systems, which I mentioned in the introduction: it works perfectly in demos, but after six months in production, the accuracy of answers drops. The primary reason for this degradation is the data. The database continues to grow, new documents are added every few days, and old, irrelevant ones are forgotten. Inconsistencies accumulate, noise increases, and finding target chunks becomes more difficult.

Manually cleaning the database is expensive, and clients will never do it, so we developed our own data validator for this task. It searches the database for duplicates, similar documents, and inconsistencies, highlighting suspicious areas for human review and decision-making. The validator can be set to a specific skepticism level; the higher it is, the more potential errors it will find, requiring the expert to manually check them all. However, for instance, the validator will detect two different numbers in the same templated banking document even at a low skepticism level. The balance between expert workload and the need for surgical precision must be found empirically.

Quality can also decline when the system's audience changes, and new users start asking different questions. Their behavior is difficult to predict in advance, so new datasets must be compiled from their questions, and the system tuned accordingly. Of course, one could create datasets from anticipated new client questions beforehand, but the accuracy of such an approach is questionable. If you knew exactly what you would be asked, you would write an FAQ, not build a RAG. Therefore, when the audience changes, the quality of answers will suffer regardless.

Simply Low Quality

If the desired quality cannot be achieved at all, there are usually two reasons. Check them in order.

  1. First, check the chunks retrieved for the query. It's possible that the necessary fact is not included in the Top-N selection at all. In this case, the search needs fixing.

  2. If the chunk with the required fact is in the selection, but the answer is still poor, the problem lies in generation. The prompt needs to be addressed.

Search is primarily fixed by rewriting the query, which I've already discussed. Separating databases by domain also helps: if a company has IT, HR, and legal departments, they can be safely separated because there are almost no questions at the intersection of domains. Instead of one database, create three, implement a router/classifier, and the system will answer more accurately for each. This also prevents cross-contamination, where financial information leaks into answers for HR questions. If query routing doesn't help, implement metadata filtering. As a last resort, use a graph. Under the watchful eye of Sauron.

Low Productivity

If your system has achieved the desired level of accuracy but responds too slowly or consumes too many tokens, this can also be addressed by simplifying the pipeline and minimizing LLM calls. For example, implement caching so that identical or very similar questions can be answered without searching the database.

Conclusion

To summarize my recommendations: if you are building a RAG system, start with classic hybrid search and invest in data. Add agentic loops and especially graphs only when you are sure you have hit the limitations of the simple approach and the knowledge base is definitely in order. In my experience, problems most often lie with the source data.
