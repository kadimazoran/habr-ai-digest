I have released version 1.3 of Ru-Jev. This is an open model for typed decisions for Russian-language text. It runs on a CPU and can be deployed within a closed loop. In this release, I trained the model to be less dependent on the specific wording used by the caller to name response options. The result is definite. The new version is more accurate than the old one on unfamiliar names that are common or borrowed words. There is no gain on abbreviations and codes. Below, I provide both parts of the result and how I tested them.

The model and code are under the MIT license. Weights are available on Hugging Face in the repository besktech/ru-jev.

What is this model?

Ru-Jev receives context and a set of options. It outputs the probability of each option and selects one. The model does not generate text. It supports three forms of decision-making: yes or no, selection from a set, and ordinal scale.

Structurally, it is a pairwise cross-encoder. NLI classifiers without fine-tuning and re-rankers belong to the same family. Each pair of “context plus option” is evaluated by a separate pass through the mmBERT-base encoder. This is 307 million parameters, of which 110 million are outside the embedding matrix. Then, the scores are normalized by softmax across options, with temperature calibration on top.

This architecture has two consequences. The result is independent of the order of options because the options do not see each other. However, the decision time increases with the number of options, and with eighteen options, the model is slower than models that process all options in a single pass.

The name refers to Jev, a commercial decision model from TypeSafe AI. Ru-Jev is not affiliated with TypeSafe. The model was not trained on Jev's responses, and Jev's API was not called in this work.

Why is this useful for a closed loop?

I have had text classifiers in operation for many years. In the citizen feedback processing system I wrote about earlier, each prediction was verified by an operator. The main time was spent on this verification, not on the model's work. The next step in such a system is a confidence threshold. Above the threshold, the model answers on its own; the rest goes to a human. The threshold only works if the model's probabilities are calibrated.

What changed in 1.3

Version 1.1 saw each routing scenario in two forms: an English key and a regular Russian word. Version 1.3 stores multiple forms for each label and randomly picks one for each training example. The forms were taken from the data collector without rephrasing.

  • For MASSIVE intents (60 labels): English key, Russian label, key in Cyrillic according to transliteration rules, truncated Cyrillic form of this key.

  • For MASSIVE scenarios (18 labels): English key, Russian word, Russian phrase.

  • For toxicity: five phrasings for two labels instead of one.

  • For review sentiment: five phrasings for the set of labels, for review rating: four, instead of one.

Besides augmentation, the versions differ in three other aspects. Between them, I fixed the validation split, and some tasks received a different division. Version 1.1 was trained for three epochs, version 1.3 for four, so their learning rate schedules differ. There was also an intermediate version 1.2 with other minor fixes. Therefore, below I talk about the difference between two trained models. Augmentation is consistent with it as a cause, but it is not a strict ablation.

How I tested

All tests of phrasings are conducted on the same 1000 questions from the original validation split of MASSIVE scenarios. No version was trained on these examples, but both used them for epoch selection and temperature tuning. Each question has one correct scenario out of eighteen. Only the names of the scenarios change.

I ran each dictionary in two settings.

  • Five options in the question. The correct label and four distractors, the same for all dictionaries and models. Random guessing is 0.20.

  • Eighteen options in the question, i.e., all labels. Random guessing is 0.056.

The model evaluates each option separately, so a five-option answer is precisely obtained from an eighteen-option run by re-normalizing the relevant five scores. I do not compare absolute accuracies and effect sizes between the settings. The two settings were needed because the effect size depends on the number of options, and differently for different dictionaries. Measuring in only one setting was misleading.

The dictionaries were obtained in three different ways.

  • Main benchmark. Six dictionaries were written in the project during model development, before these measurements. These are the English key, Russian word, Russian phrase, jargon from Anglicisms (“weather”, “small talk”, “food delivery”, “logistics”), service names (“weather service”), and request descriptions. The jargon dictionary was added to the repository six and a half hours before the transliteration rules. It was not adjusted to the rules, but it already existed when they were written.

  • Dictionaries by rule. Codes like ALARM_SCN and three-letter abbreviations like “БУД”. These were generated by rule by the AI agent that trained the model. They were only run in the five-option setting.

  • Independent dictionary. Service slang (“synoptic”, “wake-up call”) and opaque codes (“ПГД”, “БДК”). This was written by a separate AI assistant session that did not train the model and did not see the scores for these dictionaries. I provided it verbatim.

I compared each label with all variant strings in the training mixtures of both versions, by exact match and by prefix in both directions, for correct labels and distractors. The comparison revealed an important point. The dictionaries “English key” and “Russian word” are training styles for both versions, all 18 labels. Therefore, they serve as controls, not as tests. “Russian phrase” is present in the training of 1.3 for all 18 labels, and in the training of 1.1 only for two, one of which coincides with the Russian word, so an improvement on it is expected by design. Jargon, service names, and request descriptions remain held-out for both versions. There are no exact matches with training for services and descriptions, but all description labels and two service names have a prefix connection with training options, so they do not have a strict cutoff.

Jargon has two cutoffs. “Clean” excludes three labels that coincide with the output of the transliteration rule (audio, news, weather). “Strict” excludes all labels with exact or prefix matches to training, leaving 11 labels and 625 questions. The independent dictionary also uses a strict cutoff that excludes prefix connections.

For each comparison, an exact paired McNemar's test and a confidence interval are calculated, where labels are resampled first, and then questions within labels. The label is generalized, not an individual question. There are 9 to 18 labels in the cutoff, so these intervals are wide and approximate. P-values are adjusted using the Holm-Bonferroni method for 23 comparisons, excluding controls.

Before releasing the scores, I recorded the reading rule in the repository. It states what result I will consider a transfer and what I will not. The time of recording is visible in the commit history.

In words, 1.3 is more accurate. On all held-out dictionaries of words, common or borrowed, 1.3 is more accurate than 1.1 in both settings. There are fourteen such cells, including cutoffs for all labels, and the sign is the same everywhere. This is most evident in jargon. On the strict cutoff, where there are no labels with exact or prefix matches to training, the gain is +0.235 with five options and +0.142 with eighteen. The confidence interval for labels is above zero with five options and crosses zero with eighteen. For all jargon labels, the interval is above zero in both settings.

Slang behaves differently in the two settings. With five options, the gain is +0.166, and the confidence interval for labels is above zero. With eighteen, the gain is +0.050. The reading rule, recorded before the scores were revealed, counts this as a transfer; raw p = 0.016. However, it does not withstand the Holm-Bonferroni correction, and the confidence interval for labels crosses zero. In terms of labels, it's more of a reshuffling. Five labels improved, six worsened, with large shifts in both directions. “Reference bureau” increased from 0.000 to 0.585, “lists” dropped from 0.534 to 0.086. I added the five-option slang analysis only after the rule was established.

No useful gain on abbreviations and codes. On three-letter abbreviations, 1.3 is not better. On all labels, the difference is −0.024 and not significant; on the clean cutoff, it's −0.060. The gap between the cutoffs is created by one excluded label, on which 1.3 increased from 0.000 to 0.829. Neither version reads opaque codes. With eighteen options, 1.1 is below the random level; 1.3 is at its level. Codes like ALARM_SCN are easily handled by both versions because they contain a trained key entirely, and I do not consider them a test of robustness.

Confidence. Where accuracy increased, the area under the curve of "coverage and risk" (AURC, lower is better) decreased in most cases. The exception is slang for all labels with eighteen options, where it increased from 0.354 to 0.395. On strict jargon, it dropped from 0.235 to 0.078 with five options and from 0.452 to 0.418 with eighteen. This means the confidence threshold works better in these cases. The number of errors with confidence above 0.8 behaves worse. With five options on jargon, it dropped from 110 to 62 per thousand. With eighteen, it increased on jargon for all labels from 79 to 109 (on the strict cutoff from 112 to 160) and on strict slang from 151 to 191, because 1.3 is generally more confident. On service names, it decreased from 123 to 87. On abbreviations, it increased from 77 to 118. Augmentation by itself does not make confidence safe on unfamiliar labels. The temperature needs to be selected for your labels.

The conclusion is as follows. The version trained on multiple forms of each label is more accurate on unfamiliar names that are words, including types of words not present in training, such as slang and service names. There is no useful gain on abbreviations and codes. I have not investigated why this is the case separately. My explanation is that codes or abbreviations have almost no semantic basis. Augmentation styles should be selected based on the vocabulary actually used in your organization.

Four errors in my measurements

The first comparison of versions showed a clear accuracy gain and two drops. None of the three actually existed. I found each error myself, and the card indicates which numbers were removed.

Dataset split via a shared generator. The collector split the validation set for each task using a modular random number generator, shared across the entire file. New label styles in one task shifted the stream, and all subsequent tasks received a different split. As a result, 90.3 percent of the new RuCoLA validation set was in the training data for version 1.1. The drop from 0.909 to 0.647 was an evaluation of the old model on its own training examples. On held-out examples, it was 0.650. The fix is to seed the split by task name, i.e., random.Random(f"split:{task}").

String comparison only by text. A string with the same text in 1.3 might carry a phrasing of an option that 1.1 had not seen. Then, running 1.1 on it measures robustness, not accuracy. When both text and phrasings matched, out of nine comparable tasks, six remained. The increase in toxicity from 0.722 to 0.954 was precisely due to this. 1.3 was trained on all five toxicity phrasings, while 1.1 was trained on one.

Mixed denominators. The summary string 0.7948 vs. 0.7920 was calculated on half the strings, while the table next to it calculated all. The calibration advantage of 0.0172 vs. 0.0160 was removed from this single split. Both figures made it into the published card and were removed.

Integrity check against an outdated reference. To estimate the variance due to the seed, I retrained both versions. The mixture on the remote machine matched the local one by sha256, by the number of strings, and by the composition of tasks. However, the local copy was assembled before the commit with transliteration styles, and the runs that were supposed to replicate 1.3 were trained without them. This was only caught by checking the content. Intents had 120 different variant strings in the old copy and 198 after rebuilding. These runs were not published anywhere and are excluded from all results.

I derived a general rule: an artifact should be tested against the content that the change is supposed to affect, not against a hash of a copy of unknown age. Robustness to phrasings should be measured with varying numbers of options.

Limitations

Each version was trained once. There is no repeat of 1.3 with a different seed. Two correct repetitions of the 1.1 recipe yielded 0.658 and 0.622 on jargon, compared to 0.633 for the released version; on the clean cutoff, 0.645 and 0.599. I only measured the variance due to the seed for 1.1, only on jargon, and only with five options. Small differences in the table should not be considered reproducible. The gains on jargon are large relative to this variance.

The versions differ not only in augmentation, so shifts on unfamiliar datasets cannot be attributed to augmentation alone.

Each naming style is represented by one dictionary of eighteen labels. All dictionaries were written in my project or by AI agents working within it. None were collected from real systems. Abbreviations and codes like ALARM_SCN were run only with five options.

The phrasing tests were conducted on one routing task. The model only responds within the provided set and cannot say that none of the options are suitable, so the option "none of the above" must be explicitly provided. Tasks requiring reasoning with training sets smaller than a thousand strings remain weak.

How to run

Launch code
import json, torch, torch.nn as nn
from huggingface_hub import hf_hub_download
from safetensors.torch import load_file
from transformers import AutoModel, AutoTokenizer

REPO = "besktech/ru-jev"


class Scorer(nn.Module):
    def __init__(self, repo):
        super().__init__()
        self.backbone = AutoModel.from_pretrained(repo)
        self.head = nn.Linear(self.backbone.config.hidden_size, 1)
        self.head.load_state_dict(load_file(hf_hub_download(repo, "head.safetensors")))

    def forward(self, ids, mask):
        cls = self.backbone(input_ids=ids, attention_mask=mask).last_hidden_state[:, 0]
        return self.head(cls).squeeze(-1)


calib = json.load(open(hf_hub_download(REPO, "calibration.json")))
T = calib["temperature"]
tok = AutoTokenizer.from_pretrained(REPO)
model = Scorer(REPO).eval()

context = "Приложение падает при входе после обновления."
options = ["техническая проблема", "оплата, счета и возвраты", "продажи"]

with torch.no_grad():
    enc = tok([context] * len(options), options, truncation=True,
              max_length=calib["max_len"], padding=True, return_tensors="pt")
    probs = torch.softmax(model(enc["input_ids"], enc["attention_mask"]) / T, dim=0)

for option, p in zip(options, probs.tolist()):
    print(f"{p:.3f}  {option}")

On the published weights, this yields 0.947 for technical problem, 0.039 for sales, and 0.013 for payments.

Dividing by temperature before softmax is mandatory, otherwise the threshold logic does not work. Previous versions are on branches. If your code depends on the behavior of 1.1, specify revision="v1.1".

The demo on Hugging Face shows examples pre-calculated on the released weights. You cannot enter your own options there; the code above is required for that.

Data and licenses

The MIT license covers the code and weights. Training data retains its original licenses. Thirteen tasks are collected from open datasets: six tasks from Russian SuperGLUE, RuCoLA, one reasoning task from two MERA datasets (ruOpenBookQA and ruWorldTree), four ruMTEB tasks (review sentiment, review rating, MASSIVE intents, and scenarios), and a toxicity dataset.
