Hello, Habr! This is Ivan Sorokin, you know me from articles about far2l, its ideological successor f4, and the port of Dos Navigator to modern systems. I want to tell you about a new project (actually, projects) that you will surely like and find useful!

Introducing fix-it-in-wine and dllmgr. The first is a skill that allows you to assign an AI agent the task of fixing compatibility errors of Windows applications with Wine. The second is something like a package manager for DLLs: it allows you to install fixed libraries independently of the main Wine, share them, and use ready-made solutions from other developers.

But the main idea here is not even to teach AI to fix Wine errors. It is to change the very model of development and distribution of compatibility fixes.

I want to try to solve two problems at once:

  1. Fixing Wine remains a task for programmers and requires very high competence. AI agents could take on a significant part of this work, but Wine does not accept generated code, considering it a risk to the project.

  2. Even when a fix exists, the path from detecting a problem to its appearance for users often goes through a limited number of overloaded developers and maintainers (of both Wine itself and distributions).

We can chase Windows like this for a long time. We need a different way to organize the ecosystem!

From Waiting for a Fix to Solving the Problem Independently

Let's imagine a common situation: a Linux user launches a necessary Windows program under Wine and discovers that something is not working. The application crashes, doesn't display interface elements, incorrectly handles input, or behaves differently than in Windows.

What can be done?

Try a different version of Wine. Look for a suitable workaround. Check WineHQ AppDB and Bugzilla. Possibly, install an alternative build or try different environment settings.

If nothing helps, you are left waiting for a fix or figuring out the source code yourself.

The latter is simply unrealistic for most users. Wine is a large and complex project, and fixing one bug may require understanding the Windows API, Wine's internal architecture, the behavior of a specific application, and the interaction of many libraries.

What if, instead, we give an AI agent a task: "Fix this program under my Wine"?

This is exactly why I started developing the fix-it-in-wine skill.

The agent gets the ability to sequentially investigate the problem:

  • Run the application and collect Wine logs

  • Find relevant error messages in WineHQ Bugzilla

  • Determine which DLL or Windows API function might be causing the incorrect behavior

  • Build the necessary library separately from the rest of Wine

  • Prepare a fix and test it on the specific application

  • Install the fixed DLL only for the selected application, without affecting the system Wine

  • Roll back changes if necessary

Of course, the presence of an agent does not guarantee that any error will be fixed. But it allows automating a significant part of the work that previously required direct human involvement familiar with the Wine codebase — especially if agents share developed diagnostic tools through a common coordination repository.

The result: no more need to learn C, WinAPI, and Wine internals just to fix one broken dialog box once in a lifetime.

dllmgr: A Package Manager for Wine DLLs

The next question is: what to do with an already found fix?

Suppose the agent fixed an error in a library. The user got a working program. But where to store the result and how to help other people use it?

This is what the second project, dllmgr, is for.

Its task is to manage alternative DLL implementations and individual fixes for Wine: libraries are treated as independent components, whose versions and variants can be distributed independently of the main Wine.

The user will be able to choose:

  • The standard library from their Wine version

  • A newer implementation of the same DLL from another Wine release, which is not yet in their distribution's repositories

  • An alternative library maintained by an independent developer

  • A variant of the original library from vanilla Wine with a specific fix for a specific bug (and everything can be built right on your computer)

A catalog of fixes, checks for using replaced libraries, diagnostic tools, and a tool for rolling back installed libraries are already ready.

The result is a package manager for Wine components. Winetricks on steroids :)

At the same time, dllmgr itself does not guarantee unconditional interchangeability of any DLLs from any Wine versions with each other; this is out of scope. But they are compatible, and dllmgr will allow writing and using a recipe for using a new library in your Wine.

The Main Bottleneck is Not Just Technical

Now, about why all this is being done.

Wine has been developing for decades and solves an extremely complex problem. The number of existing Windows applications is huge, and the variety of their behavior, dependencies, and errors is practically infinite.

At the same time, the number of people with sufficient expertise to develop and maintain Wine fixes is limited.

This creates a bottleneck.

Even if a problem is well-studied and a fix already exists, incorporating it into the main Wine requires checking the quality of the implementation, compliance with the project's architecture, adherence to development rules, review, and further maintenance.

All these requirements are justified. Without them, a large project would quickly turn into an unmaintainable collection of special cases.

But for a user who needs one specific Windows program, the result often looks the same: the desired fix is unavailable until it has gone through the entire process to the main project and the corresponding release.

And what if, instead of a few dozen or hundreds of developers, thousands of users with AI agents start generating fixes?

The throughput of the existing process will not automatically increase. On the contrary: the flow of proposed changes may become completely overwhelming for Wine maintainers.

Therefore, we need to scale not only the production of fixes but also the method of their delivery.

What if we stop requiring every fix to be included in Wine?

The idea behind dllmgr is to separate two fundamentally different processes:

1. Solving a specific user's problem

A user needs their application to work here and now. They don't necessarily have to wait for a universal fix that has passed all integration stages into the main Wine.

If a fixed DLL solves the problem, passes the necessary checks, and does not disrupt the operation of other components in use, it can be distributed as an independent variant of the library.

2. Creating a universal fix in Wine

This is a different task. Here, the quality of implementation, architectural compatibility, absence of regressions, and long-term maintainability are important.

This should still be done by Wine developers according to their project's rules.

At the same time, independent developers will be able to maintain fixes for individual libraries. Users will be able to choose the desired variants. AI agents will be able to create and test new solutions based on existing ones.

This even creates the possibility of a decentralized fix market, where the results of work become available to users without necessarily going through the entire integration queue.

How to Help Main Wine Without Creating Parallel Chaos?

There is a fundamental point: I am not suggesting abandoning sending research results back to Wine; on the contrary, it is one of the main goals of fix-it-in-wine.

However, there is a problem with AI-generated code. Submitting such code to the main Wine is problematic due to project requirements. Bombarding Wine developers with AI-generated patches that their own rules prohibit accepting is a bad idea. Therefore, a different approach is proposed:

Submit not the AI-written code, but verifiable results of the analysis of the program's behavior and the found solution.

  • Which program and under what conditions works incorrectly

  • How to reproduce the problem

  • What is the expected behavior under Windows and the actual behavior under Wine

  • Which API calls are involved in the error

  • What is the presumed cause of the discrepancy

  • What change in behavior eliminates the problem

  • Which tests reproduce the error without the fix and pass successfully after it

  • What results were obtained during the actual execution of the application

All this information can be added to existing WineHQ Bugzilla reports or used to create new ones, with user verification and confirmation before publication.

The Wine developer receives an already analyzed problem: with diagnostics, a description of the causes, experimental results, and already devised reproducible tests, and can implement the fix themselves, in accordance with all Wine rules.

As a result, AI takes on a significant part of the research and experimental work without imposing its code on upstream. In my opinion, this is a much more constructive model for interacting AI agents with large mature open-source projects than constant arguments about whether AI code can be merged (and whether it can be done without human review) or not. And it is potentially applicable far beyond just Wine.

Why This Can Significantly Accelerate Ecosystem Development

Let's try to imagine that this approach becomes widespread.

A user discovers an error in a Windows application and assigns an agent to fix it.

The agent finds the cause, creates a fixed library, verifies the result, and prepares a ready-made solution.

The fix appears in the catalog, after which other users can use it.

The next agent encountering a similar problem will no longer start the investigation from scratch: it can find an existing DLL variant and try to apply it.

In parallel, diagnostic results are sent to WineHQ Bugzilla.

Wine developers receive higher-quality bug reports, and successful solutions can eventually turn into fixes for the main Wine.

Thus, several sources of acceleration arise:

  • Mass participation of interested users, who no longer need to become programmers for this

  • Reuse of fix ideas instead of repeatedly investigating the same bug independently

  • Finer granularity compared to PlayOnLinux and similar tools (faster downloads, builds, tests - shorter feedback loops)

  • The ability to concurrently maintain multiple library versions by independent developers – competition always improves product quality

  • Reduced load on Wine maintainers by separating local fix delivery from their integration into upstream – they can focus more on fixes with already precise descriptions of causes

  • Improved quality of bug reports submitted to Wine – the agent won't forget to attach a log

It is the combination of these factors, in my opinion, that can provide a much greater effect than simply automatically generating patches.

What Works Now

Both projects are still in the early stages of development, but they already contain useful working fixes! As well as very useful auxiliary tools.

In fix-it-in-wine, diagnostic scripts, WineHQ Bugzilla error search, local DLL building, installation of local replacements, and rollback of changes are ready.

In dllmgr, the fix catalog format, its verification and indexing, as well as experimental scenarios for applying individual fixes that are already ready, are implemented. Full CLI, TUI, and graphical interfaces for the manager are still planned (TUI will be done first).

There is also the first completed practical result: a fixed comctl32 library that solves a problem documented in Wine Bugzilla as bug 59609 in FastStone Image Viewer. The first example of how a fix for a specific application error can be prepared and distributed separately from the main Wine with a one-click installation (see scripts/apply-faststone-fix.sh). Or, for example, AVIF support in Wine: it will work in any compatible image viewer, not just FastStone! (link).

What's Next

In the near future plans include developing the fix catalog, automating their application, checking compatibility, and preparing new reproducible test scenarios on real applications. Far3, PuTTY, Photoshop CS2 – these are the applications whose bugs agents will fix first as showcases after they finish with FastStone. Suggest yours!

The goal is to eventually reach a situation where, to install a fix, a user only needs to provide the agent with a link to a ready-made recipe, and the agent will independently install the necessary tools, check the environment, apply the fix, and test the result. Also, to bring dllmgr to the point where it can work by default in "one-button mode": "install all fixes for all my programs and ensure they are updated and new ones are pulled in if necessary."

But a more interesting long-term goal is the emergence of a community of independent maintainers of DLLs and fixes, capable of developing in parallel with the main Wine, while maintaining constructive feedback with it.
