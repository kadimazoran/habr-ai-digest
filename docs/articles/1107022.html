An AI agent can figure out how a website works, find a bug, and suggest a reasonable fix. But what if the solution is technically correct, but the user authorized something else entirely? And who should verify the agent's actions before they become real changes?

In the first article, I explained how I gave an AI agent access to MODX via MCP, and in the second, how we organized its independent work with live websites. By then, a decent infrastructure had already emerged around MCP: file operations, locks, backups, change history, and browser checks.

However, this was not enough to perform complex tasks, maintain state between sessions, and manage the agent's independent decisions. This led me to develop Site Agent Runtime — a separate, multi-component system for managing autonomous AI agents. MODX was the starting point, but most of the problems encountered are not specific to a particular CMS. The same issues arise when working with repositories, server infrastructure, databases, and other external systems.

The full implementation of Runtime is in a private repository and is still under development. In this article, I will discuss one of its components — ChangeSet, which is responsible for preparing, verifying, and committing change plans. It does not make any changes to the site itself, which is a fundamental feature of the architecture.

Why an Agent's Decision Isn't Yet a Reason to Change a Website

Suppose a user asked to change the content of a MODX page. The agent studied the site and decided it would be easier to modify a global chunk. Technically, the decision is reasonable, but it would change dozens of other pages along with the desired one.

The agent correctly understood the site's structure but proposed an operation the user did not authorize. Such behavior can be restricted by instructions, but I wanted the observance of task boundaries to be ensured by programmatic checks, not by the model's attentiveness.

Therefore, in Site Agent Runtime, I separated decision-making, plan preparation, and execution. The corresponding part of the architecture looks like this:

TaskSpec formalizes the task and permissible actions. Resolver maps them to specific site objects, DecisionSet records technical decisions. ChangeSet transforms them into a verifiable plan, which can then be passed to a separate Executor.

Why didn't I leave all checks to the executor? Because then I would have to store and reconcile plans that might initially contradict the task. It's more logical to detect such problems before committing the document, leaving the Executor with checks directly related to the execution of operations.

ChangeSet is a declarative document describing changes, the initial state of objects, dependencies, risks, conditions for verifying the result, backups, and rollbacks. But the main work is not in saving JSON.

The bindscope() method associates each operation with a specific target defined by the Resolver and checks its type, status, and permissible action, as well as the correspondence of the identifier to the original object, if specified in the operation. If updating a resource is allowed, but the agent proposes deleting it, the operation is rejected. The same happens when trying to modify an unrelated object.

Dependencies are also considered. For example, changing an element used by multiple resources requires explicit confirmation regardless of the risk assessment proposed by the agent. And read_set saves information about the original objects and their checksums for subsequent verification of data relevance.

At the same time, ChangeSet does not try to re-explore the entire CMS. It works with the results of previous components and is responsible for its own invariants. Otherwise, quite quickly, there would be several independent mechanisms, each trying to figure everything out on its own. A familiar story: we wanted to divide responsibilities, but got several universal components instead of one.

Two Successful Writes and One Lost Change

During the implementation of ChangeSet, a problem arose that was completely unrelated to artificial intelligence. It was a standard concurrent write, with rather curious behavior.

I chose JSON files for storing documents. With a small number of tasks, this is a simple option that doesn't require a separate DBMS. Writing is done through a temporary file with flush, fsync, and then os.replace(), and fcntl.flock is used for synchronization.

It seemed like everything was covered: files are replaced atomically, writing is protected by a lock. But let's see what happens if two processes read the same version of a ChangeSet almost simultaneously.

Each will prepare its own changes. The first will get the lock and save the new version, the second will wait for the lock to be released and write its own.

Both operations will complete without errors, the JSON will remain correct, and the file system will not complain. Only the result of the first process will disappear.

This is a classic lost update. Atomic replacement protects against partial file writes but doesn't guarantee that the new version is prepared based on the current state. The lock also doesn't help if it only protects the saving of an already prepared document.

What's particularly interesting is that the file system honestly did everything it was asked to do. The problem was that I wasn't asking for enough.

It would have been possible to hold an exclusive lock throughout the entire preparation of changes. But then one process would block others even during operations that don't require access to storage.

I chose optimistic control of concurrent changes: preparation is done without a lock, and immediately before saving, the current state is re-read and compared with the original.

with self._locked():
current = self._read_existing(task_id)
if current != existing:
raise ChangeSetError(
"Concurrent ChangeSet modification; reload and retry"
)
self._atomic_json(self._path(task_id), document)

If another process managed to change the document, the operation is rejected. Instead of silent overwriting, we get an explicit conflict.

But another subtlety emerged here. ChangeSet has a revision number. It would seem that we could compare only this number, not the entire document. Why complicate things? It turned out we couldn't.

The seal() operation transitions the plan from draft to sealed, fixing its content. At the same time, the revision number does not necessarily increase. Consequently, a process with an old draft copy might not notice the sealing and overwrite the document, which can no longer be modified in the usual way.

This leads to an interesting situation: the revision number is the same, but the document's state is fundamentally different. Therefore, I compare the entire previously read document, including its state.

The problem, which initially looked like a standard concurrent write, turned out to be also a matter of correctly defining the object's state. A single revision number is not enough to describe the lifecycle of a ChangeSet.

How to Test an Error That Doesn't Always Occur

Concurrent errors are inconvenient because a regular test might pass dozens of times, even if the problem hasn't disappeared. Everything depends on the order of operations, and relying on a favorable thread schedule is a dubious testing strategy.

Therefore, in test_competing_writers_cannot_lose_revision, I used threading.Barrier. Two threads read the same initial version of a ChangeSet, after which the barrier holds them until they both reach the desired point. Then they continue execution and try to save their changes.

The test verifies that exactly one operation completes successfully, the second receives a conflict, and the saved document has the expected revision.

It is important here to distinguish between the scenario and the method of its verification. The described problem can occur when multiple processes work with a shared file storage, but this specific test uses two threads of a single process. The concurrent verification mechanism is performed by the actual ChangeSet methods, without replacing their logic.

A separate test_concurrent_seal_cannot_be_overwritten_by_stale_draft simulates a situation where the document was sealed between the initial read and the write attempt. A stale draft should not overwrite a sealed document, even if the revision numbers match.

Thus, the tests verify not just the correctness of individual methods, but specific invariants of the concurrent state. The source code is available in the repository, and automated checks are run in GitHub Actions on Linux with Python 3.10–3.13.

What If the Agent Changes Its Mind?

The next question concerns an already committed plan. While a ChangeSet is in draft state, it can be edited. But after calling seal(), the regular set() method no longer allows changing the content. Otherwise, the purpose of commitment is lost: we checked one plan, but intend to execute another.

A separate amend() method is provided for making corrections. It saves the history of amendments and changes to the set of operations, increments the revision, and returns the document to draft state. The previous approval is reset: if the user approved the modification of three resources, adding a fourth should not automatically inherit their permission.

The integrity of the plan is controlled using a canonical SHA-256 hash. Before committing, ChangeSet checks under a lock whether the actual content of the draft matches the saved hash. For a committed document, the hash is also recalculated during subsequent state checks. If the data has changed, but the checksums remain the same, the component will detect a discrepancy.

This is checked, in particular, by the test_frozen_payload_recalculated, which specifically modifies the content of a committed document. After the substitution, ChangeSet should consider the plan not ready for execution.

However, integrity control and authorization checks are completely different tasks. SHA-256 allows detecting integrity violations but does not establish who exactly changed the document.

Suppose the agent prepared a high-risk operation and calls approve(source="user"). It looks convincing, but source is just a string that the agent can provide itself. Based on this parameter alone, it's impossible to determine if the user actually authorized anything.

This means the agent first proposes a dangerous operation and then claims that the user approved it. Convenient, of course, but it has little to do with security.

Therefore, in the published ChangeSet, the approve() method intentionally rejects any calls. There is no independent trusted confirmation mechanism here, and pretending to have one using a string argument seemed like a bad idea to me. Plans requiring approval cannot be sealed by bypassing this restriction.

Corresponding situations are checked by automated tests, including attempts to pass off untrusted confirmation as genuine.

When a Correct Plan Becomes Incorrect

Suppose a ChangeSet has passed all checks. The operations match the task, the document is sealed, and the checksums match. Can we guarantee that nothing will be broken during execution? Not necessarily. Because the website itself might have changed during the plan preparation.

For example, the agent read a MODX resource, prepared a new version, and sealed the ChangeSet. While it was doing this, another user changed the content of the same resource. If we now simply apply the prepared data, we might overwrite someone else's work.

In the second article on agents working with live websites, I already discussed the need to re-read files and check the initial state before writing. However, Runtime faces a more general task: how to ensure consistency between the prepared plan and the state of the external system at the moment of execution?

ChangeSet uses read_set and checksums of the initial data. Additionally, it considers stale state markers saved by State Guard. However, State Guard does not monitor site changes independently, and a successful check does not rule out an object change just before writing.

This is a classic TOCTOU race — time-of-check to time-of-use. To eliminate such a gap, checking the expected state must be atomically linked to the change operation itself, for example, through compare-and-swap or equivalent conditional writes.

The complexity lies in the fact that different CMSs and other external systems offer different capabilities for this. A universal execution contract is yet to be developed, and it would be incorrect to attribute to ChangeSet guarantees that the Executor should provide.

This is where the meaning of separating responsibilities becomes particularly evident. ChangeSet is responsible for plan consistency, revision control, integrity, and adherence to established constraints. Checking the state of the external system at the moment of writing remains an execution-level task.

What's the Result

ChangeSet is just one part of a significantly larger system. For full autonomous operation, task management, state saving, authorization control, operation execution, and error handling are necessary. Site Agent Runtime continues to be developed, and not all architectural questions have definitive answers yet.

However, the work on ChangeSet has already shown why it's not enough to simply expand the capabilities of an AI agent and provide it with new tools. It's also necessary to create a software environment that controls its decisions and allows them to be verified by ordinary, quite deterministic mechanisms.

And here lies a curious paradox: the more autonomy artificial intelligence gains, the more serious engineering work is required from ordinary programmers.
