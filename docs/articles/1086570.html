The Platform in Brief

Essentially, MWS AI Agents Platform is an environment where you can build an agent, connect it to data and corporate systems, deploy it, and monitor it. It's the necessary boilerplate for a generative AI solution to work in production, but pre-built and in one place. At the core of the platform is a development environment with a scenario constructor, a sandbox, experimentation tools, and an "AI team" that builds agents based on text descriptions. Beneath this lie tools for working with data and models: RAG, agent memory, labeling, and fine-tuning. You can connect almost any model: our Cotype, your own, or external ones. Agents communicate with corporate systems via APIs and MCP. Enterprise requirements run through all layers: role-based access control, language model protection, operation within a closed environment, and fault tolerance.

Now, let's dive into the key components in more detail.

Project Constructor

This is one of the main components of the platform, and it's based on a graph. Simply put, a project is assembled from components like Lego bricks.

These components are agents, code blocks, data source queries, handlers, and other elements. Arrange them on the graph, and you get a process where, for example, one step is executed, then another, a condition is checked, and you move to a third step.

An agent loop can also be contained within such a project. In this case, some decisions are made by the LLM.

This means you don't have to choose between a rigid scenario and a fully autonomous agent. If a business process has strict boundaries and is predictable, it's simpler and more reliable to describe it with ordinary logic. An agent is best suited for steps where the decision depends on context.

The constructor's menu also provides access to other platform sections:

  • AI Services — this is where you'll find tools for working with AutoML models (classifiers and named entity recognition — NER).

  • Dialogs — conversation history.

  • Data Labeling — tools for labelers.

  • Channels — HTTP adapters through which the assembled solution is published externally.

  • MCP Hub — built-in MCP servers and the ability to connect your own.

Virtual Development Team

You can create AI projects through the constructor or via prompts. For this, the platform has a group of specially trained AI agents – AI Force or the "AI team." This module grew out of an internal competitive project; you can read about it here. The agent team knows the platform's structure, understands the abstractions available within it, and has access to the tools. This means it works with the same platform entities that a user would interact with when building an AI agent manually.

There are several roles within the "AI team." The "Manager" communicates with the user: clarifies the task, gathers requirements, and presents a plan for approval. The "Architect" selects the project type and designs the scenario graph. They rely on a catalog of proven archetypes, and the concept is verified even before assembly. The "Developer" builds the scenario according to the concept using the platform's tools, validates the structure, corrects common errors, and runs the project on the platform's engine.

If a test fails or the user requests changes, the developer makes targeted edits to the scenario and runs the checks and tests again. The cycle repeats until the project works.

Knowledge Bases and RAG

You can create knowledge bases for projects, upload documents of various formats, and search this data in different ways: by vector similarity, standard text search (including BM25), or combine multiple methods and even prioritize them by assigning weights.

Fragments found by the search are sent for processing, and the agent can use them. This allows building RAG scenarios to rely not only on the language model's knowledge but also on relevant company data.

Testing

You can pre-configure test sets on the platform and run them for the entire project or for individual components.

For example, if a project contains a component based on an LLM, a set of input data and expected results is created for it. Then, each test is run through the engine, and the same test can be repeated. This is important due to the non-deterministic nature of LLMs – a single successful run doesn't mean much for them. Usually, multiple test runs are executed in parallel to check the stability of the solution. The virtual development team can also create such tests.

The logic here is traditional for software development: the project is changed, tests are run, results are analyzed, the solution is adjusted, and then re-checked. However, in this case, not only code but also model behavior is tested.

Security and Deployment

The platform was initially designed for large companies and government organizations with their strict compliance procedures, security requirements, traceability, and technological independence. Therefore, it includes action auditing and logs, access levels, and rights for editing and publishing versions. There are also secret variables and environments inaccessible directly to project users.

MWS AI Agents Platform is included in the register of domestic software. The primary delivery method is within a local environment, including for the language model. If a company's policy allows the use of external LLMs, custom security rules can be configured for them.

How to Learn to Design Agent Systems?

Many people know how to use ready-made agents. The situation is more complex with designing agent architecture. It's advisable to understand how agents, tools, context, memory, and knowledge bases work. Without this, it's difficult to build a robust system.

Therefore, interactive training is built into the platform. Users go through scenarios within the interface and get acquainted with the platform's components. You can start with a very simple project, then move on to an agent that makes its own decisions, calls tools, and accesses the knowledge base, and then to more complex solutions that combine document processing, agent loops, and human involvement. Tools for Controlling Agent Actions

The degree of an agent's autonomy is determined by the project design. The agent itself can be thought of as an LLM control system with tools and context, but the platform user decides which tools to give the agent.

For example, they can allocate a sandbox for an agent to create files, write code, and execute it within the user's session. Another agent might be given access to external tools or services. For sensitive operations, human confirmation might be required.

Imagine an agent that helps a passenger change a flight ticket. It might determine that it needs to call the tool to transfer the booking to another flight. However, the project developer can set a rule: confirmation is required before executing this tool. Otherwise, the action will be stopped.

Moreover, confirmation can be technical. For instance, the request might go to the user or security service. This differs from a regular message in a dialogue where the agent says, "Please confirm the transfer."

The restriction is embedded in the tool invocation logic: the agent cannot ignore it. In addition to confirming tools, you can insert human waiting points into the graph or give the agent a tool to contact a human. For example: if there's not enough information, stop the agent loop and request clarification. In other words, implement the human-in-the-loop principle.

Agent Memory

Agent memory has several mechanisms. The simplest is short-term memory within the current session. The agent remembers a certain number of previous messages and uses them as context for the next request. The size of this memory can be limited, even to zero: then the agent will stop remembering user utterances.

Long-term memory works differently – it has a separate storage. Information that appears during project operation and should be preserved between sessions can be recorded there. What exactly is saved is determined in the project settings. You can save entire messages, select specific data, or automate fact extraction.

For example, during a conversation, a user mentions they don't like a certain food. The system can extract this fact and save it to the long-term memory profile. When the same user returns in another session, the agent will have access to the accumulated facts.

Some decisions about what exactly to extract from memory can be made by the agent itself within the project settings.

You cannot put everything the system has ever learned into the model's context. Context is a limited and expensive resource. Therefore, one of the architecture's tasks is to provide the model only with the information needed for the current operation.

The same applies to tools. If an agent potentially has access to dozens or hundreds of functions, there's no need to include a description of all functions in the context every time. It's better to pre-determine which set of tools is needed at which stage. Essentially, this is context engineering: managing what data, knowledge, instructions, and tools the model sees at a specific moment.

Memory Profiles

The platform allows creating memory profiles and defining which agents have access to which data. For example, your agent analyzes contact center operator dialogues with clients and checks their compliance with regulations. In complex cases, such as a situation for which there is no regulation and it's difficult to assess, it calls a human, who explains how to act correctly.

Information entered by a human can be saved, used to form an additional instruction, and placed in long-term memory or a knowledge base. When a similar situation arises, the agent will use it and won't bother the human.

How such knowledge is saved depends on the project: you can use long-term memory, a knowledge base, data from user dialogues, or test results, or you can combine them.

A small clarification. After an agent learns a fact and saves it to long-term memory, and then takes it into account in the context during the next interaction, it might seem to the user that the agent has "learned." Technically, the agent has rather "remembered": it operates in the old way, albeit with new data.

This is how an agent project evolves after launch: new scenarios appear, knowledge and context accumulate. This increases the system's accuracy and reliability.

Agent Orchestration and Interaction

When a project involves more than one agent, you need to decide how they will interact and pass work to each other. There are three main schemes:

Passing work through a graph. One agent completes its part of the task, writes the result to variables, and then control passes to the next agent via the graph. You can add a condition: if one topic is identified, one agent continues the work; if another, then another. This results in a relatively easy-to-control architecture.

One agent uses others as tools. There is a main agent that decides which specialized agent is needed at the moment. It can call one agent, get the result, think, and then call another. If necessary, the main agent will call several agents in parallel, collect their results, and continue working.

Free-form model, where multiple agents in a shared environment see each other and distribute tasks among themselves with almost no central control. That is, if ten agents are placed in the system and one new file arrives, they independently decide who will process it and who will interact with whom for this purpose. This mode is not yet supported as a basic scenario on the platform: it's not sufficiently manageable and is quite specific for practical projects.

The architecture resolves conflicts. If agents follow the graph sequentially, the order is already defined. If there's a main agent calling other agents as tools, it makes the decision, and the others return results to it.

How does the system know which agent to send a request to? There's no magic here either: first, an event enters the project – user text, a file, or another type of content. The project can be triggered by time or another system event. Then, the initial logic determines where to send the request. For this, you can use simple rules and regular expressions, apply a classifier, or an LLM.

A separate scenario can act as a router: it receives input data, determines its type or the user's intent, and then redirects control to the appropriate part of the project. Thus, agent selection becomes another part of the architecture design.

Monitoring and Observability

If a regular program behaves incorrectly, a developer looks for an error in the code. When an agent system behaves incorrectly, you need to understand what context the model received, what tool it called, what data it passed on, and where exactly the behavior diverged from expectations.

It's impossible to completely eliminate language model errors. However, their occurrence can be reduced through a combination of different engineering practices: properly designing prompts and context, and conducting tests.

If too much information, contradictory instructions, or poorly assembled context is passed to the model, the quality of its work will decrease. Therefore, you need to see exactly what the model received. Traces are used for this: what came into a specific context, what document was found, what text went through a chain of transformations, and what it turned into. This can be analyzed separately for each agent in the chain.

I've already mentioned test runs above – for projects with LLMs, you need significantly more of them. Then, observability is required. For this, all events within projects are collected into detailed logs. Based on these logs, you can build views and see which projects are running, which components are being called, and how individual operations are proceeding. There is separate observability for models: how they are deployed, how they work, and how much resources they consume.

In general, the correctness of an agent's operation is built systemically: through project architecture, context quality, observability, testing, and control of critical actions.

Implementation Cases

Currently, MWS AI Agents Platform is actively used within MTS. It powers, among other things, a multi-agent solution for contact center automation, consisting of three major modules:
