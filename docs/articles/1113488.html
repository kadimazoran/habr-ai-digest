From Attempting to Write My Own Manager to a Zoo of Utilities

My transition to Herdr began with an attempt to invent it myself. In early March 2026, three weeks before the first appearance of herdrdev/herdr on GitHub, I started a project called ClaudeAgent in Delphi. I wanted to create a simple window that launches console agents by folders and shows who is busy with what. It didn't get past the prototype stage because everything came down to emulating a terminal (VT) within my own window.

Instead of a unified environment, a combination of three tools around Windows Terminal (wt.exe) gradually emerged. Dozens of tabs with console agents omp (oh-my-pi), agy (antigravity-cli), PowerShell shells, and SSH sessions lived in Windows Terminal itself. Nearby, a custom dashboard omp-usage-dashboard running on Node.js 24 spun in the browser, displaying remaining provider quotas, DeepSeek balance, token counters from stats.db, and a list of active sessions. To see open tabs and switch to the desired one with a Focus button, the Windows server would query PowerShell UI Automation (tabs.ps1 and focus.ps1) and match sessions by their title text. The third part was a floating launcher, OmpLauncher, written in Delphi 13 VCL, featuring a folder tree, a list of the last 15 projects, model presets for omp (--config), plugin presets for agy (--add-dir), selection of agy orchestrator models, and a button to open folders in Total Commander. Upon clicking a button, it would assemble an argument string and open a new tab via wt.exe -w 0 nt ....

This setup worked for three to four projects, but it started to fall apart as the number of sessions grew. If two agents had similar titles, UI Automation might switch to the wrong tab. When an agent got stuck waiting for permission or a user question, it wasn't visible in the general tab feed, and I had to check them manually. Remote machines were in separate SSH windows, and accidentally closing Windows Terminal or restarting the shell would kill all running processes.

Why a Terminal and Herdr, Not Antigravity, Codex, or Claude Desktop

When it comes to terminal multiplexers for agents, people usually ask why bother with the console and shells like Herdr when providers already have their own graphical applications (Claude Desktop, Codex, Antigravity, Cursor).

In practice, it's rare to stay within the tools of a single vendor. During a workday, different combinations run in parallel across various folders: sometimes omp with DeepSeek or a local model in Strata is more convenient, sometimes agy in orchestrator mode with Gemini 4, sometimes Claude Code, and alongside them, PowerShell, git, msbuild, and a remote SSH terminal on a lab bench are open. Proprietary desktop clients either tie you to one provider or turn your desktop into three to four heavy Electron windows, which you still have to jump between.

Even more essential is a live pseudo-terminal (PTY) next to the agent. When an agent is building a project, running tests, or editing a config, the built-in chat without a full shell is inconvenient. A tab where the agent works on the left, and a build log, Far file manager, or a Python script in the same directory is open in a neighboring panel (split) is much more useful.

Finally, herdr-app is written in Rust and the GPUI framework without Electron or WebView, keeps the entire interface in understandable text files, and aggregates agents from all machines into a single list. Table 1 summarizes the differences between the three approaches.

How Herdr 2 Works: herdr-core and herdr-app

Under the name Herdr on GitHub, there are two different branches under the Apache-2.0 license. The original herdrdev/herdr (over 50 thousand stars) remains a console TUI multiplexer with its own built-in server. In the fall of 2026, Herdr 2 was released, divided into a background core herdrdev/herdr-core (the hc command) and a native desktop client herdrdev/herdr-app using Rust and GPUI. Sessions from the old TUI do not appear in the new herdr-app because the application only works with herdr-core. On my Windows 11, I currently have hc 0.1.22 and herdr-app 0.1.18 installed.

The herdr-core itself draws nothing. It runs a background daemon, owns all local and remote PTYs, parses terminal states, and maintains the tree of spaces, tabs, and panes. The herdr-app window acts as one of the core's clients. If you close the window, update herdr-app, or the graphical interface crashes, the running agents and shells continue to operate within herdr-core, and upon reopening the window, they will be back in their places.

The workspace within the window is divided into spaces (Space—usually a project or folder on a specific machine; if no name is given, it inherits the repository name or current directory), tabs (Tab), and panes (Pane), which host either a terminal or a mod panel (file tree, git diff viewer, third-party panel). Panes can be split horizontally and vertically, dragged by their top handle, and maximized (zoom).

Remote machines can be connected to a single window via SSH through Settings -> Machines or the command hc machine add. Figure 1 shows my working herdr-app 0.1.18 window: in the Spaces block under This computer, the local spaces MultilayerLab and cleanyourtv are open, and immediately below them is the remote machine workpc (hc 0.1.22, connected state). Everything is consolidated in one sidebar and one overall Agents list.
