Where should a developer invest their efforts in the AI era?

In writing code? In testing? Undoubtedly, these skills remain important. But increasingly, these are the areas where AI agents can significantly accelerate a team's work.

The real bottleneck lies earlier – at the design stage.

System design is one of the most cognitively complex parts of engineering work. Before the first line of code appears, dozens of questions need to be answered:

  • Where are the system boundaries?

  • Who are the users, external actors, and services?

  • What components will be needed, and what is each of them responsible for?

  • How do they interact: synchronously or asynchronously?

  • What data is transferred between them?

  • What APIs and event contracts need to be defined?

  • Where and how is data stored?

  • What integrations, load, fault tolerance, security, and concurrency requirements exist?

  • What constraints cannot be violated?

  • How do we know when a change is truly ready?

The more accurately a team answers these questions before implementation, the lower the cost of errors and rework later. Good design doesn't guarantee a perfect result, but it creates the necessary foundation for it.

From Document to Executable Plan

The problem with traditional documentation is that it often lives separately from development: diagrams are in one tool, decisions in a wiki, contracts in another system, and the actual implementation in repositories. As a result, both engineers and AI agents have to manually piece together the context.

Viaduct proposes making the architectural model the central point of work on a system: not a static diagram "for reporting," but a living representation of context, containers, components, documentation, interaction sequences, and API contracts. Within the model, you can describe C4 levels, data flows, call sequences, ER models, and attach Markdown descriptions and contracts directly to the elements they relate to. You can also integrate Figma for UI components and link each element to a specific Node.

By connecting a design system, the project gets all the necessary base tokens from the UI project.

Thus, documentation becomes not an appendix to the code, but a structured context through which the system can be understood and modified.

How It Works

A developer or architect first designs the change from start to finish:

  1. Describes which parts of the system are affected. All C4 layers help here, depending on the depth of system and its element elaboration.

  2. Adds or refines services, components, connections, and data flows. A well-defined data flow in Magic Flow allows the agent to best understand specific integrations and what happens at each step.

  3. Defines interactions between participants. For presentation between teams, you can play through the desired magic flow to ensure all agreements are correct.

  4. Specifies contracts, constraints, storage, and integration requirements. You can describe any contract (Rest, GRPC), topics in Kafka, or queues in RabbitMQ.

  5. Formulates acceptance criteria. For a Change Set, it's best to try to describe the Acceptance Criteria well, as is typical in a development task.

  6. Creates a Change Set – a set of agreed-upon changes in the architectural model. It specifies the version within which we want to implement. We briefly describe what needs to be done, any constraints or wishes, as well as a set of Acceptance Criteria. After creation, we copy the code to be inserted for the agent with MCP connected.

After this, the Change Set becomes an understandable work plan for the AI agent: what needs to be implemented, why it needs to be done, which services are affected, which contracts must be preserved, and by what criteria the result will be accepted.

Why This is Important

AI performs well in implementation when the task has clear boundaries. But if you give an agent a vague instruction like "add a feature," it will have to guess:

  • which part of the system to change;

  • which contract to consider the source of truth;

  • what dependencies the change will affect;

  • what cannot be broken;

  • what compromise between speed, scalability, and complexity is acceptable.

A high-quality architectural model eliminates a significant portion of this guesswork. It transforms the team's intention into context, and context into an executable task.

This is precisely why the right investment for a developer in the AI era is not to abandon programming, but to strengthen engineering thinking: decomposition, system design, data modeling, API design, formulation of constraints, and acceptance criteria.
