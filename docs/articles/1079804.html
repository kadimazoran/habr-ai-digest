Why Your LLM Gets Dumber on Large Documents and How to Fix It

LLM large context doesn't guarantee quality answers: when working with voluminous documents, the model can lose important details and find facts within the text less effectively. In this article, we'll explore why Full-Context and basic RAG face limitations, and how the Semantic Gatekeeper approach improves answer accuracy by preparing relevant context before passing it to the main model. Probing LLMs with Documentation

For the sake of a clean experiment, let's take a real dataset—500 pages of technical documentation for network equipment (our favorite logs, IP addresses, firmware versions). We'll break it down into 5 segments of 100 pages each: A, B, C, D, E.

Next, we need to ask 10 questions whose answers lie strictly within segment C (the golden mean) and see what comes of it.

Strategy #1: Full-Context (feed everything whole)

Let's start with the simplest option: stuffing all 500 pages into the GPT-4o context. But the result was not very interesting, as we got an accuracy of only 34%, and the first token appeared only after 14 seconds (which is quite a lot, you must admit).

And of course, there were hallucinations: the model began to combine IP addresses from segments A and E, creating non-existent routes.

In reality, this option is practically useless.

Strategy #2: Naive RAG (vector search, top-5 chunks)

Now let's complicate the implementation a bit by slicing the data into chunks. Here we get an accuracy of 42%, which is better, but not by much. At the same time, the answer came in 1.1 seconds, which is fast, but what's the point of speed if the answer is wrong?

The essence of the problem here is that we lose context between chunks, and because of this, the model doesn't understand the overall picture.

As a result, we arrive at the disappointing conclusion that both approaches are inapplicable, as Full-Context is expensive and stupid, while Naive RAG is fast but also not very smart.

RAPTOR, Self-Refine, and Other Trendy Stuff

Before moving on to a truly working solution, let's analyze why some existing patterns don't work in 2026.

RAPTOR (Recursive Abstractive Processing)

This pattern builds cluster trees, summarizing them at each level. It sounds powerful, but in practice, it's great for retelling "in general," but it kills accuracy. For example, ask RAPTOR for the driver version on page 245 of our documentation, and it will give you the average temperature of the hospital. Because summarization averages facts, which is good for analytics, but for tech support and other tasks requiring accuracy, it's death.

Self-Refine / ReAct (iterative refinements)

This model, as they say, goes in circles, meaning it rereads the context and constantly refines. It sort of works, but it requires 5–7 requests to an expensive LLM, and the cost of one session can reach $0.5. Now multiply that by 1000 users a day, and you get quite serious expenses.

The first solution that might come to mind in such a situation is increasing the chunk size.

If the model gets lost in the middle of a 500-page document, let's make chunks of 10K tokens. But after such a change, the model gets lost in the middle of each chunk and only gets worse.

Thus, we arrive at the disappointing conclusion that a new approach is needed to ensure accuracy, speed, and at an acceptable price.

Semantic Gatekeeper

Imagine you have an expensive and talented lawyer in your company (our large LLM). You wouldn't dump 500 pages of a contract on them and say, "Figure it out." Instead, you'd first give the contract to a junior assistant who would extract key facts (amounts, dates, parties), assess which part of the contract is relevant to your question at all. As a result, the assistant would present only the most important information to the lawyer on one page. This is exactly how our "Semantic Gatekeeper" will work.

The role of the assistant will be performed by Mistral-7B-Instruct in 4-bit quantization. It costs pennies (in terms of money and resources) but knows how to read and analyze.

Let's see how it all works. First, we perform a rough vector search across the knowledge base and retrieve not 5 chunks, but 50, to be sure not to miss a relevant piece. Then, we run each of these 50 chunks through Mistral-7B with a simple task: "Rate the relevance of the chunk to the question from 0 to 1. Extract 3 key facts from it. Respond in JSON format."

We also prohibit the model from fantasizing, meaning it doesn't generate coherent text but only extracts facts from the original chunk. This minimizes the probability of hallucinations.

Next, we use a dynamic priority buffer, meaning we sort the 50 chunks by their score and discard everything below 0.6. From the remaining ones, we take the TOP-10 by relevance.

An important point here is that we don't place these chunks in the order they were in the document. Instead, we sort them in descending order of importance, and the most relevant one becomes the first.

Earlier, we talked about the model forgetting the middle. Let's try to trick it. To do this, at the beginning of the prompt, we'll place compressed synopses of all 10 chunks (about 2000 tokens), and at the very end of the prompt, we'll duplicate the most relevant chunk entirely, without compression.

Now the most important facts are at the beginning (as a brief summary) and at the end (as a detailed original). The model sees them in both zones of high attention concentration, and it's impossible for it to avoid the facts.

How It Looks in Practice

For Mistral-7B inference, we use vLLM—it consumes less memory and works faster than out-of-the-box transformers. Here's the working code for our pipeline in Python:

from vllm import LLM, SamplingParams
import json

# Load Mistral-7B in 4-bit quantization
# Fits on A100 40GB without issues
llm = LLM(
    model="mistralai/Mistral-7B-Instruct-v0.3",
    quantization="AWQ",  # 4-bit quantization
    dtype="half",
    max_model_len=4096
)

def gatekeeper_filter(query, chunks, top_k=10):
    """
    query: user's question
    chunks: list of 50 chunks (text)
    top_k: how many best to keep
    """
    prompt_template = """
    [INST]
    Your task is to analyze a document fragment.
    User question: {query}
    
    Fragment text:
    {chunk}
    
    Respond strictly in JSON format:
    - "score": a number from 0 to 1 (how relevant the chunk is to the question)
    - "facts": an array of up to 3 key facts (short sentences from the text)
    
    Example: {{"score": 0.85, "facts": ["Server restarted at 14:32", "Error E531"]}}
    [/INST]
    """
    
    # Prepare a batch of prompts for 50 chunks
    batch_prompts = [
        prompt_template.format(query=query, chunk=chunk) 
        for chunk in chunks
    ]
    
    # Run inference with low temperature (determinism)
    sampling_params = SamplingParams(
        temperature=0.0,      # No creativity, only facts
        max_tokens=200,
        stop=["\n\n"]         # To avoid generating extra text
    )
    
    outputs = llm.generate(batch_prompts, sampling_params)
    
    # Parse JSON from responses
    parsed_results = []
    for i, output in enumerate(outputs):
        raw_text = output.outputs[0].text
        try:
            # Find { ... } in the response
            start = raw_text.find('{')
            end = raw_text.rfind('}') + 1
            json_str = raw_text[start:end]
            data = json.loads(json_str)
            parsed_results.append({
                "score": float(data.get("score", 0.0)),
                "facts": data.get("facts", [])[:3]
            })
        except (json.JSONDecodeError, ValueError):
            # If the model messed up, assign a low score
            parsed_results.append({"score": 0.0, "facts": []})
    
    # Sort by score in descending order
    scored_chunks = list(zip(chunks, parsed_results))
    scored_chunks.sort(key=lambda x: x[1]['score'], reverse=True)
    
    # Take top-K
    top_chunks = scored_chunks[:top_k]
    
    # Component B: form compressed context from facts
    compressed_facts = []
    for chunk_data, meta in top_chunks:
        compressed_facts.extend(meta['facts'])
    
    # Limit length to avoid overflowing context
    compressed_context = " ".join(compressed_facts[:40])
    
    # Duplicate the best chunk entirely at the end
    best_chunk_raw = top_chunks[0][0] if top_chunks else ""
    
    return {
        "compressed_context": compressed_context,
        "anchor_chunk": best_chunk_raw
    }

# Form the final prompt for GPT-4

{result['compressed_context']}

{result['anchor_chunk']}
