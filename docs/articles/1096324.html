Imagine this situation. You've set up an AI agent and used it to build a new product in two weeks – for example, an order approval system. In it, a manager creates an order, a financier checks it, a supervisor approves it, and then delivery is initiated. The system works, and users can go through the entire process from start to finish. But suddenly, details emerge that were difficult to foresee: for example, orders over 100,000 rubles must be confirmed by the director.

You open the code to make these changes and face a problem. The requirement for mandatory approval of large orders by the director is written in three places at once: in the interface, the server-side, and the instructions for the AI agent. Moreover, the wording differs, and it's unclear which one is correct. If you change the limit in one place, the others will continue to function as before: the interface won't display a notification about approval by the new person, the server will allow a large order without the director, and the AI agent will prompt users with the old workflow. The more new requirements appear, the harder it becomes to understand where related rules are located, what needs to be changed, and whether this change will disrupt the work of other parts of the system.

From this, it's often concluded that vibe-coding cannot be used to build serious products. We propose a fresh perspective – don't demand perfect code from the first version of a product, but instead, create a complete description of the service in parallel with development. We'll explain what it provides, how to create it, and where to store it.

How to Create the Description

The description needs to capture two entities.

The first is the domain model, which is what the product consists of. The team needs to list the main objects of the system, their characteristics, relationships between them, user roles, possible states, and constraints. For example, for an order approval system, you need to specify that it has orders, clients, and contracts; an order has a number, amount, and date; each order is linked to a client; and managers, financiers, and directors can work with it. You also need to record the possible states of an order – for example, 'draft,' 'under review,' and 'approved'; and constraints: for instance, the order amount cannot be negative.

The second is what I call the semantic contract. Essentially, it's a set of rules that define how the product should work, regardless of the programming language used or the interface through which the user interacts with it. If the domain model answers the question 'What does the product consist of?', then the semantic contract answers 'How should it work?'.

In this part, the company needs to describe the actions that can be performed in the system: who has the right to perform them, under what conditions, what should happen as a result, and how to verify that the action was performed correctly. For clarity, let's take the action 'approve order.' Here, you can specify that a financier or director can approve it. To do this, the client's name, payment amount, and date must be specified in the order beforehand. After approval, the order status changes to 'approved,' participants receive a notification, and the action is logged. If the status changes but the notification is not sent, the system should retry sending it without re-approving the order. If the order amount exceeds the set limit, it must be confirmed by the director.

The basic unit of a semantic contract is a product capability, which is an action beneficial to the user, with clear conditions and a verifiable result. For example, 'approve order' is a product capability, while the 'Approve' button is just one way to use it. Today, the user clicks a button, tomorrow they give a command to an AI agent, and later they initiate the same action from another program. The interaction method changes, but the approval rules remain the same.

Where to get this information? There are several sources. The first is the requirements and decisions of the product owner. They help understand what the system should do. The second category includes code, interface, roles, permissions, data structure, and logic. They show how the system currently works. End-to-end scenarios, automated tests, actual data changes, and confirmation from the responsible employee constitute the third category and allow verification of whether the desired result was achieved. If all these sources contradict each other, the system should not independently choose the 'correct' version. Discrepancies must be recorded and passed to the person responsible for the product.

Why Describing Buttons and Requests Is Not Enough

The simplest way to document system operation is to write: 'button #143 initiates request #27.' This might be sufficient for automating an existing interface. For product development, it is not. This is because such a description does not explain why the user performs the action, under what circumstances it is allowed, and what result is considered correct. If the button is moved or the technical implementation of the request is changed, the description becomes outdated.

Therefore, it's better to build the description from the user's task: what the person wants to do → which product capability they are using → which object they are working with → what rules apply → what result the system should achieve. The specific button or other interface element appears only after this.

Where to Store the Description

Store it in the same place as the code, i.e., in the product repository, in a separate folder. Write it in plain text files, for example, in Markdown and YAML formats: they are equally easy for humans and AI agents to read. This way, the description is included in the version history, and it's visible who changed a rule, when, and why. Every change to the description is reviewed by the product owner, just like code changes. This ensures the description stays up-to-date with the system, unlike a document in a chat that no one opens after a month. The agent only needs to be given the path to the folder: before working, it will read the rules and operate within their boundaries. Place verification scenarios nearby and link them to product capabilities. This way, after each change, the system will compare the result with the description.

Why Businesses Need a Description

There are five main values of a semantic description.

1. The product's meaning lives longer than any code.
Entities, capabilities, rules, permissions, states, workflows, and expected results are no longer scattered across the interface, server, database, tasks, and AI instructions. They are collected into a single product model, and the model can be verified. The team sees two layers at once: how the system is structured today and how it should work even if the code changes.

2. The architecture can be refactored as many times as needed.
Even if the code transforms, the product's meaning and operating criteria remain unchanged. Therefore, the initial interface can be safely replaced if necessary, and a monolithic server can be split into independent services. The way system parts exchange data can also be rethought, and the AI model or its provider can be changed.

3. The product can be easily packaged into a new interface.

Web interfaces, mobile applications, programmatic interfaces (APIs), automated processes, and AI agents provide access to the same product capabilities. There's no need to re-interpret permissions, preconditions, and successful outcomes five times. A new channel receives a ready-made semantic contract, and the team only designs the appropriate presentation and adapter for the specific implementation.

4. Any new version can be verified against business results.
A new version is checked not against the old screen appearance, but against the business meaning: have the rules, permissible states, permissions, and expected results remained in place? Acceptance tests and regression tests for already working scenarios are derived from the semantics. This shows where the system behaves differently from what is documented. The agent receives boundaries within which it operates autonomously. Powerful models enhance this scheme, but the framework remains the source of truth.

5. The product accumulates verified experience.
The system records a trace of user actions (the sequence of their steps) with semantic annotations. It shows who is performing the action and what role they play, which entity they are working with and in what state it is, which interface elements they use, what steps they take, how it all ends, where they make mistakes, and how they correct them. Interface elements and available steps are linked to the framework, so the trace shows not a series of clicks, but the user's actual path and goal. The agent studies it, comparing user steps with expected states and results. It also identifies goals that people repeat, workarounds, and places where the fact diverges from the rule. Then, a human reviews the agent's findings. Verified findings become tests, examples for the agent, refined rules, and context for the company or an individual. This way, the product continuously evolves and improves.
